## 7. 扩展场景（同难度梯度，可选方向）

> 完整的高阶场景地图（7 大族群 23 个场景：富文本/协同/音视频/GIS/3D/微前端/在线 IDE/百万级性能/AI 原生前端等）见 [react-高阶场景全景图.md](../react-高阶场景全景图/README.md)。

| 场景 | 核心技术 | 对标 |
|---|---|---|
| 节点编排画布（n8n/Dify 式工作流） | reactflow（自研节点/边/自动布局/小地图） | n8n、Dify |
| 富文本/文档编辑器 | prosemirror 生态（tiptap）、协同（Yjs） | Notion 类 |
| 复杂数据表格 | tanstack table（分组/虚拟/行内编辑/列拖拽），ag-grid | 飞书表格 |
| 画布类编辑器（白板/海报） | react-konva / Pixi、坐标系与缩放平移变换 | excalidraw、稿定 |
| 公式编辑器 | 语法树 + monarch/lezer | Excel 公式栏 |

这五个场景与前面六章共享同一个内核（schema/注册表/递归/undo），但各自往下再挖一层专用技术。每个场景按"核心技术地图 → 最小可行切入点 → 对标项目的正确打开方式"三段展开，目标是让你用一章的时间做出"能玩起来"的最小版本，再决定是否深入。

### 7.1 节点编排画布（n8n/Dify 式工作流）

**是什么**：一张无限画布上摆"节点"（一步操作：调接口、条件判断、代码块），节点之间连线定义执行顺序，产物是工作流 schema。与第 6 章低代码的区别：低代码搭的是"页面"（树结构），编排搭的是"流程"（图结构）——因此渲染层从"递归树"变成"图布局 + 边路由"。

**核心技术地图**：

- **@xyflow/react（reactflow 的新包名）**：React 生态节点画布的事实标准。它管最难的通用部分——画布缩放平移（viewport）、节点拖动、边命中、小地图（MiniMap）、背景网格（Background）、撤销的基础数据结构（nodes/edges 就是两个受控数组）。你只负责自定义节点内容与交互。
- **自定义节点与连线桩**：每个节点是一个普通 React 组件；`Handle` 组件声明"输入桩/输出桩"（source/target），桩的 `position` 决定边从哪里进哪里出。
- **自动布局**：reactflow 不管布局，节点坐标由你维护。接 dagre（有向图布局，`@dagrejs/dagre`）做"一键整理"：建图 → `layout()` → 把算好的 x/y 写回节点。
- **流程语义层**（真正的业务）：schema 设计（节点/边/参数）、执行引擎（拓扑遍历或事件驱动）、环检测（工作流里"不允许环"通常是硬约束——这里就必须建依赖图了，对照第 6 章"深度上限 vs 依赖图"的取舍讨论，语境不同选择反转：流程图的边是静态字面量，建图毫无歧义）。

**最小可行切入点**：做一个 5 种节点的工作流编辑器——开始、HTTP 请求、条件分支、结束、备注。步骤：(1) `useNodesState`/`useEdgesState` 管两个数组，先允许手动拖摆、手动连线；(2) 每种节点写一个自定义组件（HTTP 节点展示 url 与状态灯）；(3) 接 dagre 实现"自动布局"按钮；(4) "运行"按钮 = 从开始节点拓扑遍历，逐节点把执行日志打到右侧面板、节点状态灯依次变绿——到这一步 n8n 的核心体验已经有了。

```tsx
// workflow/FlowEditor.tsx —— 最小骨架
import { useCallback } from 'react';
import {
  ReactFlow, Background, Controls, MiniMap,
  type Node, type Edge, type Connection, addEdge,
  useNodesState, useEdgesState,
} from '@xyflow/react';
import '@xyflow/react/dist/style.css';
import { HttpNode, StartNode, EndNode, NoteNode, BranchNode } from './nodes';

const nodeTypes = { http: HttpNode, start: StartNode, end: EndNode, note: NoteNode, branch: BranchNode };

export function FlowEditor() {
  const [nodes, setNodes, onNodesChange] = useNodesState<Node>([]);
  const [edges, setEdges, onEdgesChange] = useEdgesState<Edge>([]);

  const onConnect = useCallback(
    (conn: Connection) => setEdges((eds) => addEdge({ ...conn, animated: true }, eds)),
    [setEdges],
  );

  return (
    <ReactFlow
      nodes={nodes} edges={edges}
      nodeTypes={nodeTypes}          // type 字符串 → 自定义节点组件（第 1 章注册表思想）
      onNodesChange={onNodesChange}  // 受控：拖动/选择的变更回调，schema 化与 undo 都挂在这层
      onEdgesChange={onEdgesChange}
      onConnect={onConnect}
      fitView
    >
      <Background /> <Controls /> <MiniMap />
    </ReactFlow>
  );
}
```

**对标项目的正确打开方式**：**Dify**（开源，`langgenius/dify`）的 workflow 编辑器就是 `@xyflow/react` 写的 React 应用——读它的 workflow 组件目录，重点看：自定义节点组件如何与表单抽屉联动、边（分支条件）的数据结构、"运行"时如何在画布上叠加执行状态。这是"reactflow 大型实战"最直接的教材。**n8n** 的编辑器 `packages/frontend/editor-ui` 是 **Vue 3** 实现——别去抄它的 React 写法（没有），要看的是它的**产品与节点协议设计**：节点 schema（inputs/outputs/parameters 声明）、参数的表达式语法、执行数据在节点间的传递模型（每个节点能引用上游节点输出）。交互与协议读 n8n，React 实现读 Dify，reactflow 官方文档的 examples（xyflow.com）当字典查。

### 7.2 富文本/文档编辑器

**是什么**：Notion/飞书文档式的块编辑器：内容是一棵结构化文档树（段落、标题、图片、"信息卡片"块），支持格式刷、协同、斜杠命令。与 `<textarea>` 的本质差异：内容模型是树不是字符串，编辑产生的是"事务（Transaction）"不是字符差量。

**核心技术地图**：

- **ProseMirror 模型层**（一切的根）：文档 = 符合 Schema 的 Node 树（Node 带类型、属性、内容约束）；编辑 = EditorState 上派发 Transaction（对文档树的原子变更序列）；插件系统挂在 Transaction 生命周期上（keymap 快捷键、history 撤销、collab 协同、decorations 装饰高亮）。直接写 ProseMirror 学习曲线陡。
- **tiptap**：ProseMirror 的"友好发行版"——把模型层封装成扩展（Extension）API，React 集成开箱即用（`useEditor` + `EditorContent`），自定义块节点用 `NodeView` 渲染真正的 React 组件。入门顺序：tiptap 起步，理解不了行为时下沉到 ProseMirror 文档查根因。
- **自定义块（NodeView）**：Notion 感的来源——文档树里的某个节点类型由你的 React 组件渲染（进度条、投票卡片），可选中、可拖拽、内部还能有交互。
- **协同（Yjs）**：y-prosemirror 把 ProseMirror 的 Transaction 与 Yjs 文档双向绑定（第 6 章选修一的 Yjs 概念在这里落地）；`y-websocket` 做通道；awareness 做协作者光标。
- **安全**：粘贴与 HTML 导入必须消毒（DOMPurify）——富文本是 XSS 的传统重灾区。

**最小可行切入点**：不碰协同，先做"带两个自定义块 + 斜杠命令 + 本地持久化"的编辑器。步骤：(1) tiptap `StarterKit` 跑通基础编辑；(2) 写一个 mention 扩展（`@` 触发人员选择）与一个 info-card 块节点（NodeView 渲染 React 卡片，可改颜色）；(3) 斜杠命令菜单（`/` 弹出命令列表，tiptap 的 Suggestion 工具函数）；(4) `editor.getJSON()` 存 localStorage，刷新恢复；(5) 加 y-websocket + Collaboration 扩展，两个浏览器窗口同编一段文字看光标。

```tsx
// editor/RichEditor.tsx —— 起步骨架
import { useEditor, EditorContent } from '@tiptap/react';
import StarterKit from '@tiptap/starter-kit';

export function RichEditor({ onChange }: { onChange: (json: unknown) => void }) {
  const editor = useEditor({
    extensions: [StarterKit],   // 段落/标题/加粗/撤销等基础能力
    content: { type: 'doc', content: [{ type: 'paragraph' }] },
    onUpdate: ({ editor }) => onChange(editor.getJSON()), // 文档树 JSON = 你的 schema（又是协议！）
  });
  return <EditorContent editor={editor} />;
}
```

**对标项目的正确打开方式**：Notion 不开源，对标三件套——**BlockNote**（开源的 Notion 风块编辑器，基于 tiptap/ProseMirror，React 友好，读它如何组织"块"的 NodeView 与拖拽把手，是"自定义块"最佳实战教材）；**tiptap 官方仓库的 demos 与文档**（Extension API 设计教科书）；**AFFiNE / AppFlowy** 这类完整开源文档产品（看"编辑器如何嵌进产品"：块管理、页面树、权限，而不是去通读）。读 ProseMirror 本体源码不作为入门要求，先把它的官方文档"Introduction"与"Transform"两章读明白——它解释了"为什么编辑器必须是不可变文档树 + 事务"，这个心智模型比抄任何代码都值钱。

### 7.3 复杂数据表格

**是什么**：飞书表格/BI 明细页级别的表格——万行数据、分组折叠、多级表头、行内编辑、列拖拽换序、列宽拖拽、选中导出。它考验的不是"渲染表格"（那是一行 `map`），而是把排序/过滤/分组/分页/选中/列宽全部做成**受控状态机**之后的组合爆炸管理。

**核心技术地图**：

- **@tanstack/react-table（headless）**：核心设计是"无 UI 的表格状态机"——列定义（`ColumnDef`）+ 数据 + 一组行模型（`getCoreRowModel` / `getSortedRowModel` / `getFilteredRowModel` / `getGroupedRowModel` / `getExpandedRowModel` / `getPaginationRowModel`，按需接通、层层叠加）。UI 完全自己画（`flexRender` 渲染单元格），正好复用第 6 章注册表思想做"单元格渲染器注册表"。
- **虚拟滚动**：@tanstack/react-virtual 只渲染可视行，`estimatedRowSize` 定高先行，变高行（展开详情）是进阶题。
- **行内编辑**：单元格三态（展示态/编辑态/提交中）状态机；Esc 回滚、Enter 提交、Tab 跳下一格——交互细节的密度不低于架构。
- **列操作**：列宽拖拽（resize 的 mousemove 计算）、列拖拽换序（第 1 章 dnd-kit 复用）、列固定（sticky 定位）。
- **服务端模式**：数据量真大时 `manualPagination: true`，把排序/过滤参数发给后端，行模型只剩 core——"客户端全量"与"服务端分页"两种模式的切换要在架构第一天就想好。

**最小可行切入点**：1 万行 mock 数据（可控制行数与列类型）+ 客户端全家桶。步骤：(1) 基础表格 + 排序 + 过滤；(2) 分组 + 展开（`getGroupedRowModel` + `getExpandedRowModel`，按部门分组折叠）；(3) 接 react-virtual 虚拟滚动，Profiler 验证滚动时首行渲染开销恒定；(4) 行内编辑（数字列与下拉列两种单元格编辑器）；(5) dnd-kit 列拖拽换序 + 列宽拖拽；(6) 勾选导出 CSV。

```tsx
// table/BigTable.tsx —— headless 用法骨架
import { useMemo } from 'react';
import {
  useReactTable, getCoreRowModel, getSortedRowModel,
  getGroupedRowModel, getExpandedRowModel, flexRender,
  createColumnHelper, type SortingState,
} from '@tanstack/react-table';
import { useState } from 'react';

interface Row { id: string; name: string; dept: string; score: number }

const col = createColumnHelper<Row>();

export function BigTable({ data }: { data: Row[] }) {
  const [sorting, setSorting] = useState<SortingState>([]);
  const columns = useMemo(() => [
    col.accessor('dept', { header: '部门' }),                 // 分组列放前
    col.accessor('name', { header: '姓名' }),
    col.accessor('score', { header: '分数' }),
  ], []);
  const table = useReactTable({
    data, columns,
    state: { sorting }, onSortingChange: setSorting,          // 受控：排序状态在手里才能做 undo 与 URL 同步
    getCoreRowModel: getCoreRowModel(),
    getSortedRowModel: getSortedRowModel(),
    getGroupedRowModel: getGroupedRowModel(),                 // 分组与展开按需接入，不用的模型零开销
    getExpandedRowModel: getExpandedRowModel(),
  });
  return (
    <table>
      <thead>{table.getHeaderGroups().map((hg) => (
        <tr key={hg.id}>{hg.headers.map((h) => (
          <th key={h.id} onClick={h.column.getToggleSortingHandler()}>
            {flexRender(h.column.columnDef.header, h.getContext())}
          </th>))}
        </tr>))}
      </thead>
      <tbody>{table.getRowModel().rows.map((row) => (
        <tr key={row.id}>
          {row.getVisibleCells().map((cell) => (
            <td key={cell.id}>{flexRender(cell.column.columnDef.cell, cell.getContext())}</td>))}
        </tr>))}
      </tbody>
    </table>
  );
}
```

**对标项目的正确打开方式**：**飞书表格**当体验基准（亲手列出它哪些交互你没做：多级表头、单元格复制区域、冻结行列），不读源码（闭源）。开源侧：**AG Grid 社区版**（源码开放，读它解决"列宽拖拽时的重绘策略"与"列 pin 的 DOM 结构"这类硬骨头，它的文档本身就是复杂表格需求词典）；**Univer**（原 Luckysheet 的继任者，开源，看"表格 → 电子表格"的最后一步：公式引擎与二维网格的协同设计，正好接住 7.5 公式编辑器）；**@tanstack/table 官方 examples**（几乎每个 feature 一个可运行示例，当字典查）。不要一上来读 ag-grid 全部源码——按 feature 带着问题跳读。

### 7.4 画布类编辑器（白板/海报）

**是什么**：excalidraw 白板、稿定设计海报编辑器这类"自由画布"：元素可任意拖放、缩放、旋转，画布本身可缩放平移。与第 6 章画布的本质差异：低代码画布是"DOM 布局流"（元素按文档流排），这里是"绝对坐标系"（元素有 x/y/w/h/rotation，没有文档流）——一切交互变成**坐标系之间的数学**。

**核心技术地图**：

- **场景图（scene graph）**：元素列表 `{ id, type, x, y, width, height, rotation, zIndex, props }`，渲染顺序 = 数组顺序。没有 DOM 层级，"选中集合"是 id 的 Set。这是所有画布类产品的心脏，先把这个 schema 定下来。
- **react-konva**（Canvas 2D）：`Stage/Layer/Group/Rect/Text` 声明式映射到 Konva 场景树；`Transformer` 组件是神器——挂到选中元素上自动出现 8 个缩放柄 + 旋转柄，拖动直接改 width/height/rotation，手写这套柄的数学要一周，用它十分钟。
- **两个坐标系与变换公式**：屏幕坐标（px）与世界坐标（画布逻辑坐标）。缩放平移后：`世界 = (屏幕 - 视口偏移) / 缩放比`，反向 `屏幕 = 世界 × 缩放比 + 视口偏移`。所有交互（点击命中、拖动增量、框选矩形）都必须先做这个换算——和第 6 章 iframe 坐标换算是同一门课的不同考题。
- **滚轮缩放与空格平移**：`wheel` 事件里"以鼠标为中心缩放"（缩放时保持指针下的世界点不动，要反推视口偏移）；按住空格临时切平移模式（Figma/Excalidraw 通例）。
- **性能量级选择**：几百元素 Canvas 2D（react-konva）够用；上万元素或粒子特效上 WebGL（PixiJS）。先用 Canvas 2D，瓶颈证实了再换。

**最小可行切入点**：海报编辑器。步骤：(1) react-konva 画 4 种元素（矩形/圆/文字/图片）；(2) 点击选中（命中由 Konva 的事件系统代劳）+ `Transformer` 缩放旋转；(3) 拖动移动（`dragboundfunc` 限制在画布内）；(4) 滚轮缩放 + 空格平移；(5) undo/redo（元素数组快照或 immer patch，第 1 章 1.5 复用）；(6) `stage.toDataURL()` 导出 PNG。

```tsx
// poster/PosterCanvas.tsx —— 选中与 Transformer 的核心骨架
import { useRef, useState, type KonvaNodeComponent } from 'react';
import { Stage, Layer, Rect, Text, Transformer } from 'react-konva';
import type Konva from 'konva';

interface Shape { id: string; type: 'rect' | 'text'; x: number; y: number; w: number; h: number; text?: string }

export function PosterCanvas({ shapes }: { shapes: Shape[] }) {
  const [selectedId, setSelectedId] = useState<string | null>(null);
  const trRef = useRef<Konva.Transformer>(null);
  const selectedRef = useRef<Konva.Node | null>(null);

  // 选中变化时把 Transformer 挂到对应节点上（Konva 命令式 API 与 React 声明式的经典缝合点）
  const attach = (node: Konva.Node | null) => {
    selectedRef.current = node;
    const tr = trRef.current!;
    if (node) { tr.nodes([node]); tr.getLayer()!.batchDraw(); }
    else tr.nodes([]);
  };

  return (
    <Stage width={800} height={600}>
      <Layer>
        {shapes.map((s) => s.type === 'rect'
          ? <Rect key={s.id} x={s.x} y={s.y} width={s.w} height={s.h} fill="#8cf"
              draggable
              ref={(node) => { if (node && s.id === selectedId) attach(node); }}
              onClick={(e) => { e.cancelBubble = true; setSelectedId(s.id); }} />
          : <Text key={s.id} x={s.x} y={s.y} text={s.text} fontSize={24} draggable
              ref={(node) => { if (node && s.id === selectedId) attach(node); }}
              onClick={(e) => { e.cancelBubble = true; setSelectedId(s.id); }} />)}
        <Transformer ref={trRef} rotateEnabled keepRatio={false} /> {/* 缩放旋转柄零成本获得 */}
      </Layer>
    </Stage>
  );
}
```

**对标项目的正确打开方式**：**excalidraw**（开源，`excalidraw/excalidraw`）——手绘风白板，读它的正确姿势是跳过 UI 层直奔三处：`src/element`（元素类型定义——一份教科书级的场景图 schema，注意它如何处理 rotation 与 bound text）、`src/actions/`（每个编辑操作一个 action 对象，do/undo 语义内建——命令模式的现代实现）、渲染层如何做脏矩形/分片重绘。**稿定**类商业产品闭源，当体验基准（模板系统、字体排版、导出多规格切图）。react-konva 文档的 demos 覆盖了拖拽/变换/事件全部基础题，照着敲一遍再动手设计自己的场景图。

### 7.5 公式编辑器

**是什么**：Excel 公式栏 / Notion 公式属性那类输入：输入 `=SUM(A1:A10) * rate`，实时语法高亮、错误下划线、引用变量补全、即时算出预览值。它是一条完整的编译器流水线（词法 → 语法 → AST → 求值）跑在一个输入框里，与第 1 章"手写 100 行 mini 求值器"是直系亲属。

**核心技术地图**：

- **流水线四段**：tokenize（数字/标识符/单元格引用 `A1` 与区间 `A1:B10`/运算符/字符串/括号）→ parse（优先级爬升或 Pratt 解析，处理一元负号、函数调用的参数列表）→ AST → evaluate（递归求值 + 引用解析：`A1` 去变量池/单元格取值）。第 1 章练过前半段，这里新增"引用与依赖"。
- **语法高亮两条路**：Monaco 的 **Monarch**（声明式正则 tokenizer，几十行配置就有专业高亮，接第 5 章 Monaco 编辑器顺理成章）或 CodeMirror 6 的 **lezer**（真增量解析器，高亮/折叠/错误定位一步到位，成本是要写文法）。
- **即时反馈**：光标停驻处的 token 高亮同源引用（Excel 点 A1 时同色高亮所有 A1）——要求 token 级位置信息贯穿流水线，这是"编辑器级"与"玩具级"的分水岭。
- **依赖与环**：公式引用变量/单元格，值变化要重算依赖它的公式（依赖图 + 拓扑排序）；`A1 = B1` 且 `B1 = A1` 是环，求值要检测并给出 `#CYCLE!` 类错误而不是死循环——第 6 章"依赖图 vs 深度上限"在这里有了最纯正的用武之地（引用是静态的，建图零歧义）。

**最小可行切入点**：Monaco + Monarch 路线一天可成。步骤：(1) 注册 `formula` 语言与 Monarch 规则（数字/运算符/函数名/引用/字符串五类 token）；(2) 复用第 1 章 mini 求值器，前面加一层"引用 token → 变量取值"的预处理（`A1` 替换为变量池的值或 `undefined` 报错）；(3) 输入防抖 → parse → AST → 求值，结果与第一个语法错误显示在输入框下方；(4) 变量面板点选插入引用；(5) 进阶：把引用依赖建成图，改变量后只重算受影响公式，构造环验证 `#CYCLE!`。

```ts
// formula/evalWithDeps.ts —— 引用解析 + 环检测（求值器扩展）
import { parse, evaluate } from '../expr';

type CellMap = Record<string, string | number>; // 'A1' → 值或公式字符串（以 '=' 开头）

export function evalFormula(expr: string, cells: CellMap): { value?: unknown; error?: string } {
  const visiting = new Set<string>(); // DFS 的“在途”集合：遇到在途引用 = 环
  const resolved = new Map<string, unknown>();

  function resolveRef(ref: string): unknown {
    if (resolved.has(ref)) return resolved.get(ref);
    if (visiting.has(ref)) throw new Error(`#CYCLE! 引用环：${[...visiting, ref].join(' → ')}`);
    const raw = cells[ref];
    if (raw === undefined) throw new Error(`#REF! 未知引用 ${ref}`);
    if (typeof raw !== 'string' || !raw.startsWith('=')) return raw;   // 字面量直接返回
    visiting.add(ref);
    const value = evaluate(parse(raw.slice(1), { ref: resolveRef }));  // 求值器里引用回调到这里递归
    visiting.delete(ref);
    resolved.set(ref, value);
    return value;
  }

  try {
    return { value: evaluate(parse(expr.startsWith('=') ? expr.slice(1) : expr), { ref: resolveRef }) };
  } catch (e) {
    return { error: (e as Error).message };
  }
}
```

### 7.6 数据透视表（拖字段 + 聚合引擎）

**是什么**：Excel 透视表 / BI 交叉表那类交互：左侧一个字段列表，拖到行区/列区/值区，引擎立刻按维度分组聚合出一张交叉表，行头列头可以再拖拽换序、值区可以换聚合方式（求和/计数/平均），格子能双击钻取展开明细。与 7.3 复杂表格的区别：表格消费的是**已算好的行**，透视表自己**造行**——"行"是维度分组的结果，拖一个字段进列区，行数瞬间乘上该字段的基数。它依然是同一个内核：透视配置本身是一份 schema（字段区布局 + 聚合声明），聚合引擎是纯函数，渲染是递归树。

**核心技术地图**：

- **PivotSchema**：`rows`（行维度，有序，支持多层）/ `cols`（列维度）/ `values`（度量 + 聚合器声明）/ 字段元数据（名字、类型、格式化）。它就是可序列化的"透视状态"，URL 同步、保存、协同都以它为准。
- **聚合引擎（纯函数）**：输入全量数据 + PivotSchema，输出一棵"维度树"——每个内点是一个维度值的分组，叶子挂聚合结果。多级行维度 = 树的深度；行+列双维 = 先按行分组，行分组内再按列分组，渲染时把列分组转置成表头。
- **聚合器注册表**：`sum/count/avg/min/max/distinctCount` 每个就是一个 `{ name, init, step, finalize }` 三件套——又是注册表模式（第 1 章），新增"中位数"不改引擎。
- **字段拖拽区**：dnd-kit 三种 droppable（行区/列区/值区），区内 dnd-sortable 换序（第 1/3 章复用）；字段从"字段列表"拖入区、区之间互拖、拖回列表 = 移除。
- **钻取展开**：聚合树天然是树——行头的每一层默认折叠为聚合值，点击展开子级，展开态记在 PivotSchema 之外的本地表态（`expandedKeys`），不污染可序列化配置。
- **性能边界**：聚合是 O(n × 维度深度)，1 万行 × 3 级维度在主线程 10ms 级；10 万行仍可行但要放 Worker；百万行不要在前端聚合——数据量到那个级别，正确架构是后端预聚合/OLAP 引擎，前端只拿结果（何时该退到那条路，见第 6 章"与 BI 报表的边界"一节）。

**最小可行切入点**：1000 行订单 mock（部门/人员/季度/金额），做行=部门、列=季度、值=金额求和的交叉表。步骤：(1) 写 PivotSchema 类型与聚合引擎纯函数（先用 `Map` 单级分组，跑通"拖字段 → 重算 → 渲染"闭环）；(2) 升级到多级行维度（部门下钻到人）；(3) 值区支持换聚合器（sum/avg/count）；(4) 行区字段拖拽换序（把"部门"与"季度"对调，表格主轴跟着变）；(5) 格子 hover 显示构成明细的 tooltip，双击钻取。

```ts
// pivot/engine.ts —— 聚合引擎核心（纯函数，可单测）
export type AggregatorName = 'sum' | 'count' | 'avg' | 'distinctCount';

export interface Aggregator {
  init(): unknown;
  step(acc: unknown, row: Record<string, unknown>, field: string): unknown;
  finalize(acc: unknown): number | string;
}

export const aggregators: Record<AggregatorName, Aggregator> = {
  sum: {
    init: () => 0,
    step: (acc, row, field) => (acc as number) + Number(row[field] ?? 0),
    finalize: (acc) => acc as number,
  },
  count: {
    init: () => 0,
    step: (acc) => (acc as number) + 1,                    // 计数不关心字段
    finalize: (acc) => acc as number,
  },
  avg: {
    init: () => ({ sum: 0, n: 0 }),
    step: (acc, row, field) => {
      const a = acc as { sum: number; n: number };
      return { sum: a.sum + Number(row[field] ?? 0), n: a.n + 1 };
    },
    finalize: (acc) => {
      const a = acc as { sum: number; n: number };
      return a.n === 0 ? 0 : a.sum / a.n;
    },
  },
  distinctCount: {
    init: () => new Set<unknown>(),
    step: (acc, row, field) => {
      (acc as Set<unknown>).add(row[field]);
      return acc;
    },
    finalize: (acc) => (acc as Set<unknown>).size,
  },
};

export interface PivotConfig {
  rows: string[];                // 行维度字段名，有序：['dept', 'owner']
  cols: string[];                // 列维度字段名：['quarter']
  values: { field: string; agg: AggregatorName }[];  // 多度量 = 多个值列
}

export interface PivotTreeNode {
  key: string;                   // 维度值路径，如 'dept:研发>owner:张三'
  dimValue: string;
  children: Map<string, PivotTreeNode>;   // 下一级维度分组
  leaves: { field: string; agg: AggregatorName; acc: unknown }[];  // 每级都挂聚合（父级=子级汇总）
}

export function aggregate(
  data: Record<string, unknown>[],
  config: PivotConfig,
): PivotTreeNode {
  const root: PivotTreeNode = {
    key: '', dimValue: '', children: new Map(),
    leaves: config.values.map((v) => ({ ...v, acc: aggregators[v.agg].init() })),
  };
  const groupFields = [...config.rows, ...config.cols];

  for (const row of data) {
    let node = root;
    // 每行先沿维度路径找/建分组节点，并在沿途每一级 step 聚合（父级自然汇总子级）
    for (const field of groupFields) {
      const dimValue = String(row[field] ?? '(空)');
      let child = node.children.get(dimValue);
      if (!child) {
        child = {
          key: `${node.key}${node.key ? '>' : ''}${field}:${dimValue}`,
          dimValue, children: new Map(),
          leaves: config.values.map((v) => ({ ...v, acc: aggregators[v.agg].init() })),
        };
        node.children.set(dimValue, child);
      }
      child.leaves.forEach((leaf, i) => {
        leaf.acc = aggregators[leaf.agg].step(leaf.acc, row, config.values[i].field);
      });
      node = child;
    }
  }
  return root;
}
```

渲染侧的对应关系：行头 = `rows` 分支的树（按 `expandedKeys` 裁剪）；列头 = 每个行叶子下 `cols` 分支转置后的笛卡尔展开；单元格 = 对应行叶子下、对应列分组的 `finalize` 结果。多度量时每个 (行, 列) 交叉点渲染 `values.length` 个值。

**对标项目的正确打开方式**：**Excel 透视表**与**飞书/Superset 仪表盘的透视组件**当交互规范，亲手记录三个细节：拖出字段后表格如何避免整页闪烁（行列头结构不变时只重算格子）、空分组显示什么、多度量时列头的两层结构（度量在维度内侧还是外侧）。开源读两个：**react-pivottable**（pivottable.js 的 React 封装，代码量小，重点读它的聚合器表与 TableRenderer 如何从聚合结构生成矩阵）；**Superset**（`superset-ui` 的 pivot 类图表插件，重点读"查询层算什么、前端算什么"的切分——它把聚合下推到 SQL，前端只做透视排布，对照你前端聚合版能看清两条路线的成本分界线）。

### 7.7 多步骤动态向导（Wizard / 分步表单）

**是什么**：保险投保、开店流程那类长表单：N 步、每步一组字段、上一步/下一步、每步离开前校验本步、步骤可能条件跳转（选了"企业用户"多出一步资质上传）、中途保存草稿下次从断点继续、最后一步汇总所有答案提交。它不是"多个表单页面拼起来"——多出来的一层是**步骤编排本身也是 schema 驱动的**：下一步去哪是一个表达式，步骤清单可以由后端下发。内核依然是：向导协议（steps 数组，每步复用第 2 章字段协议）+ 一个"当前步 + 访问历史"的小状态机。

**核心技术地图**：

- **向导协议**：`steps: StepSchema[]`，每步内嵌第 2 章的字段数组；`nextExpr`（可选）声明条件路由——默认走 `steps[i+1]`，声明了则求值返回目标步骤 id。条件路由复用第 1 章表达式引擎，求值上下文是当前全量表单值。
- **步骤状态机**：`current` + `visited`（走过哪些步的有序记录）。规则三条：前进必须先通过当前步校验；后退永不清值不校验（用户回去改答案是他的权利）；`nextExpr` 求值失败按默认下一步走并上报（表达式坏了不能把人困在当前步）。
- **条件步骤的"复活"问题**（本场景最深的一个坑，见下文展开）：用户走到第 4 步后回第 1 步改了答案，导致第 2 步（企业资质）本不该再出现——它的已填数据要不要清？
- **草稿与断点续填**：每步通过校验即分片保存（`{ stepId, values, savedAt }`），恢复时定位到"最远一个已通过校验的步"，而不是"第一个没填的步"（可能因条件路由永远不可达）。
- **提交口径**：每步即存（服务端分片落库，最后一步只是"标记完成"）vs 最后一次性提交（事务性好，但中途退出丢全部）。长流程选前者 + 最后一步做一次全量复核接口，短向导选后者。

**最小可行切入点**：一个 4 步开店向导（基本信息 → 主体类型 → 企业资质[条件步] → 确认提交）。步骤：(1) 写 WizardSchema 类型，步骤 1/2/4 用第 2 章字段协议直接描述；(2) 实现 `nextExpr`：第 2 步声明 `"$step.values.userType === 'company' ? 'step-qual' : 'step-confirm'"`；(3) 步骤状态机 hook（前进校验/后退保值/visited 记录）；(4) 草稿分片存 localStorage，刷新后回到断点；(5) 汇总页递归只读渲染所有"实际访问过"的步骤答案。

```ts
// wizard/useWizard.ts —— 步骤状态机（草稿与校验接入点已标注）
import { useCallback, useMemo, useState } from 'react';

export interface StepSchema {
  id: string;
  title: string;
  fields: unknown[];             // 第 2 章字段协议，此处不展开
  nextExpr?: string;             // 条件路由：返回目标 stepId
}

export function useWizard(steps: StepSchema[], initialValues: Record<string, unknown>) {
  const [values, setValues] = useState(initialValues);
  const [currentId, setCurrentId] = useState(steps[0].id);
  const [visited, setVisited] = useState<string[]>([steps[0].id]);

  const index = useMemo(() => steps.findIndex((s) => s.id === currentId), [steps, currentId]);
  const current = steps[index];

  const resolveNext = useCallback(async (step: StepSchema): Promise<string> => {
    if (!step.nextExpr) return steps[Math.min(index + 1, steps.length - 1)].id;
    // evaluate 来自第 1 章表达式引擎；上下文暴露 $step.values
    const next = await evaluate(step.nextExpr, { $step: { values } });
    return typeof next === 'string' && steps.some((s) => s.id === next)
      ? next
      : steps[Math.min(index + 1, steps.length - 1)].id;   // 求值失败/非法目标：默认下一步兜底
  }, [index, steps, values]);

  const next = useCallback(async () => {
    const ok = await validateStep(current.id, values);     // 只校验当前步字段（第 2 章 path 级校验复用）
    if (!ok) return false;
    const nextId = await resolveNext(current);
    setCurrentId(nextId);
    setVisited((v) => (v.includes(nextId) ? v : [...v, nextId]));
    saveDraft({ stepId: current.id, values, savedAt: Date.now() });   // 通过一步存一片
    return true;
  }, [current, resolveNext, values]);

  const back = useCallback(() => {                          // 后退：不校验、不清值
    const prevId = visited[visited.length - 2];
    if (prevId) {
      setVisited((v) => v.slice(0, -1));
      setCurrentId(prevId);
    }
  }, [visited]);

  return { values, setValues, current, index, next, back, visited };
}
```

**条件步骤的"复活"问题**（本场景标志性的坑）。症状：用户以"企业用户"走到资质步填了营业执照号，回第一步改成"个人用户"，再前进——直接跳到了确认页，但提交的数据里营业执照号还在，后端以"个人用户却带企业资质"拒绝入库。根因：条件路由只是"跳过渲染"，已填数据还躺在表单值里；而"这一步当前是否可达"没有任何一处显式计算。修法分两步：其一，提供 `isStepReachable(stepId)` 工具——从第 1 步开始按当前值逐步模拟 `nextExpr`，得出当前值下的可达步骤集合（求值是纯函数，模拟代价可忽略）；其二，提交前（以及汇总页渲染前）对 values 做一次**可达性裁剪**：不可达步骤的字段不进 payload。裁剪而不是删除——用户来回切换类型时，切回"企业用户"之前的填写内容还在，这是体验的加分项而不是漏洞。

```ts
// wizard/reachability.ts —— 可达性模拟与提交裁剪（复活问题的两步修法落地）
import type { StepSchema } from './useWizard';

/** 模拟：从第一步起按当前值求值 nextExpr，返回当前值下"真正能走到"的步骤 id 集合 */
export async function reachableSteps(
  steps: StepSchema[],
  values: Record<string, unknown>,
): Promise<Set<string>> {
  const reachable = new Set<string>([steps[0].id]);
  let current = steps[0];
  // 沿链模拟（无环向导最多走 steps.length 步，防御性上限防 nextExpr 写出环）
  for (let i = 0; i < steps.length; i++) {
    let nextId = steps[Math.min(steps.indexOf(current) + 1, steps.length - 1)].id;
    if (current.nextExpr) {
      const r = await evaluate(current.nextExpr, { $step: { values } });
      if (typeof r === 'string' && steps.some((s) => s.id === r)) nextId = r;
    }
    if (reachable.has(nextId)) break;            // 回到走过的步 = 模拟结束
    reachable.add(nextId);
    current = steps.find((s) => s.id === nextId)!;
  }
  return reachable;
}

/** 提交裁剪：只把"可达步骤"的字段放进 payload。裁剪不删除——values 本体不动 */
export async function buildPayload(
  steps: StepSchema[],
  values: Record<string, unknown>,
): Promise<Record<string, unknown>> {
  const reachable = await reachableSteps(steps, values);
  const fieldsOfReachable = new Set(
    steps.filter((s) => reachable.has(s.id)).flatMap((s) => fieldNames(s.fields)),
  );
  return Object.fromEntries(
    Object.entries(values).filter(([k]) => fieldsOfReachable.has(k)),
  );
}

// fieldNames(fields)：从第 2 章字段协议数组里取字段名列表，实现略（10 行内）
```

草稿的断点恢复也有一个容易写错的细节：恢复落点要选"**可达集合内**最远一个已通过校验的步"，而不是"第一个没填的步"——条件路由下"第一个没填的步"可能根本不可达（个人用户永远不该落到资质步），把用户放上去就是当场制造一个复活 bug。`reachableSteps` 在恢复时同样先算一遍，落点从 `visited ∩ reachable` 里挑。

### 7.8 资源排期网格（周视图拖拽调班）

**是什么**：值班表 / 会议室预订 / 医生排班那类"资源 × 时间"网格：行是资源（人/房间/设备），列是时间（周视图的 7 天或日视图按半小时分格），事件块（班次/预订）横跨若干格，可以拖动改时间、拖边缘改时长、拖到另一行换资源，落点有冲突检测。与 7.4 画布编辑器是同一门坐标课的不同考题：7.4 是"连续世界坐标 + 自由变换"，这里是"离散资源轴 × 连续时间轴 + 吸附对齐"——数学更简单，但**拖拽的语义约束**（吸附、冲突、跨日）更密。

**核心技术地图**：

- **数据模型**：`resources`（行）+ `events`（`{ id, resourceId, start, end, title }`，start/end 为 ISO 时间）。事件是**跨格的区间**而不是格子集合——区间运算（重叠检测、边界吸附）全部基于分钟数做，渲染时才换算成像素。
- **时间 ↔ 像素换算**：两个方向的纯函数——像素差 → 分钟数（`Δpx / slotHeight * snapMinutes`，再向 snap 取整）、分钟数 → 像素（反之）。吸附粒度 `snapMinutes`（15/30 分钟）决定"手感"，取整用 `Math.round(delta / snap) * snap` 而不是 floor——拖到两格中间时贴向近的那格。
- **拖动与拉伸的命中区分**：事件块本体按下 = 移动；上下边缘 6px 热区按下 = 改时长（resize）；`pointerdown` 时判 `offsetY` 落在哪。移动时水平方向跨日（指针离开当前列），垂直方向一般禁止跨资源（跨资源换人是显式操作，常放在拖起时按住 Alt 或拖到行头区）。
- **冲突检测**：落点合法性 = 同资源下新区间与既有事件（排除自身）不重叠，`aStart < bEnd && bStart < aEnd` 的标准区间重叠判定，O(n) 扫该资源的事件即可。冲突时两种产品语义：硬拒绝（落点弹回）vs 并排渲染（重叠事件各占一半宽）——会议室排班要硬拒绝，"两人共用大会议室"场景要并排，做成配置。
- **为什么不用 dnd-kit**：这里的拖拽目标是"指针在网格里的位置"而不是"某个 draggable 与某个 droppable 的关系"，用原生 pointer 事件 + 换算函数代码量更小、控制更细（吸附、跨列、resize 热区都是纯数学）。dnd-kit 更适合第 3 章那种"物料 → 容器"语义。这是一次很好的判断练习：**先看交互语义，再选库**。

**最小可行切入点**：3 个会议室 × 1 周的预订表。步骤：(1) 网格渲染（CSS grid：首列资源名，7 列日期，事件块 `gridRow` 定位、高度按分钟换算）；(2) 换算纯函数 + 单测（含跨日、snap 取整、DST 边界）；(3) pointerdown 三态命中（移动/resize/无效）+ pointermove 实时预览（半透明影子块）+ pointerup 落点校验；(4) 冲突检测与硬拒绝（拒绝时影子块变红 + 弹回动画）；(5) undo（事件数组 immer patch，第 1 章 1.5 复用）；(6) 持久化。

```ts
// schedule/geometry.ts —— 时间/像素换算与冲突检测（纯函数）
export interface GridGeometry {
  slotMinutes: number;   // 一格多少分钟（30）
  slotHeight: number;    // 一格多少像素（28）
  dayStartMin: number;   // 网格每天从第几分钟开始（8:00 → 480）
}

export function pxToMinutes(px: number, g: GridGeometry): number {
  return (px / g.slotHeight) * g.slotMinutes;
}

export function snap(minutes: number, g: GridGeometry): number {
  return Math.round(minutes / g.slotMinutes) * g.slotMinutes;
}

/** 拖动结果：给定原事件与指针增量（px 与天数），算出新区间（吸附后） */
export function applyDrag(
  ev: { start: string; end: string },
  deltaPxY: number, dayDelta: number, g: GridGeometry,
): { start: Date; end: Date } {
  const start = new Date(ev.start);
  const end = new Date(ev.end);
  const durationMin = (end.getTime() - start.getTime()) / 60000;
  const snapped = snap(pxToMinutes(deltaPxY, g), g);
  const nextStart = new Date(start);
  nextStart.setDate(nextStart.getDate() + dayDelta);          // 跨日
  // "当天第几分钟 + 吸附后的增量"再吸附到 slot 网格——保证任何起点拖完都落在整格上
  const minutesOfDay = nextStart.getHours() * 60 + nextStart.getMinutes();
  nextStart.setHours(0, snap(minutesOfDay + snapped, g), 0, 0);
  const nextEnd = new Date(nextStart.getTime() + durationMin * 60000);
  return { start: nextStart, end: nextEnd };
}

/** 冲突检测：同资源下与既有事件（排除自身）是否重叠 */
export function hasConflict(
  resourceId: string,
  candidate: { start: Date; end: Date },
  events: { id: string; resourceId: string; start: string; end: string }[],
  selfId?: string,
): boolean {
  return events.some((e) => {
    if (e.resourceId !== resourceId || e.id === selfId) return false;
    const s = new Date(e.start).getTime();
    const en = new Date(e.end).getTime();
    return candidate.start.getTime() < en && s < candidate.end.getTime();
  });
}
```

组件侧骨架（pointer 三态命中 + 影子预览）：

```tsx
// schedule/EventBlock.tsx —— 拖拽交互骨架（样式与渲染细节略）
import { useRef, useState } from 'react';

type DragMode = 'move' | 'resize-top' | 'resize-bottom' | null;

export function EventBlock({ ev, geometry, onCommit }: {
  ev: { id: string; start: string; end: string; title: string };
  geometry: GridGeometry;
  onCommit: (next: { start: Date; end: Date }) => void;
}) {
  const [mode, setMode] = useState<DragMode>(null);
  const startY = useRef(0);

  return (
    <div
      style={{ position: 'absolute', left: 4, right: 4, top: 0, height: '100%', cursor: 'grab' }}
      onPointerDown={(e) => {
        e.currentTarget.setPointerCapture(e.pointerId);       // 后续 move/up 都回到本元素
        startY.current = e.clientY;
        const rect = (e.currentTarget as HTMLDivElement).getBoundingClientRect();
        const edge = 6;                                        // 边缘热区
        setMode(e.clientY - rect.top < edge ? 'resize-top'
              : rect.bottom - e.clientY < edge ? 'resize-bottom'
              : 'move');
      }}
      onPointerMove={(e) => {
        if (!mode) return;
        // 实时影子预览：applyDrag/resize 的结果只写本地 preview 态，不写真实数据
      }}
      onPointerUp={(e) => {
        if (!mode) return;
        const deltaPx = e.clientY - startY.current;
        // onCommit(applyDrag(ev, deltaPx, dayDelta, geometry)) —— 真实提交只发生在 up，
        // 且 onCommit 内部先 hasConflict，冲突则不落库并触发回弹动画
        setMode(null);
      }}
    >
      {ev.title}
    </div>
  );
}
```

两个标志性的坑。坑一：**用 Date 的本地时区做"存储单位"**。症状：排班表跨时区协作后，A 排的班在 B 的屏幕上漂了一小时；夏令时切换日出现 23/25 小时的天。根因：渲染换算用了 `getHours()`（本地时区相关），持久化存了本地字符串。修法：**存储一律 UTC/ISO（`toISOString()`），只在渲染最后一刻换本地**；网格的 dayStart 用本地时刻定义（值班表是本地概念），但换算链路里传的是绝对时间戳。坑二：**拖拽中每帧写状态**。症状：拖动时整个网格每帧重渲染，50+ 事件时掉帧。根因：pointermove 里 setState 驱动 React 重渲染做影子预览。修法：影子块用 ref 直接改 `style.transform`（脱离 React 渲染，与第 1 章大 schema 树"交互层绕开 React"同一招），只有 pointerup 才走一次 setState 提交。

**对标项目的正确打开方式**：**FullCalendar** 当交互规范与实现教材（core 开源；resource-timeline 等插件收费——不买也能读 core：重点读它的 snapping、`eventDrop`/`eventResize` 的回调契约设计——**所有拖拽结果都以"待确认回调"交给业务层**而不是直接落库，这个契约值得照抄）；**react-big-calendar**（开源，localizer 抽象层——文化/历法适配全部收口在一个接口里，是"可插拔本地化"的好样本，但拖拽体验一般，别抄交互）；**飞书/Google 日历的拖拽手感**当体验基准：亲手测三次"拖到边界外松手""拖到网格顶部外""快速甩动"，记录它们如何处理（自动滚动、边界钳制、惯性取消）——这三处是你的版本最容易露馅的地方。
