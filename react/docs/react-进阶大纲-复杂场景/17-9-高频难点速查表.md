## 9. 高频难点速查表

| 症状 | 根因 | 解法 |
|---|---|---|
| 输入一个字符全表/整页重渲染 | 全量受控 state | path 级 selector 订阅 + Node memo |
| Cmd+Z 逐字符回退 | 补丁未合并 | immer patch 防抖合并 |
| 拖进嵌套容器判定错乱 | 碰撞策略单一 | pointerWithin + closestCorners 组合 |
| 拖动时源位置布局跳动 | 原元素被修改 | DragOverlay 替身渲染 |
| monaco 光标跳动/撤销栈丢失 | 受控 setValue | 非受控 model 模式 |
| 编辑态点击触发了组件自身行为 | 事件穿透 | 编辑模式 pointer-events:none + capture 拦截 |
| 联动/事件死循环 | 循环依赖 | 单轮求值限制/依赖图/动作深度上限 |
| 面板高频刷新卡顿 | 全量 setOption + 大数据 | 数据抽样、增量更新、visibilitychange 暂停 |
| 旧 schema 页面白屏 | 协议无版本 | 协议 version + migration 链 |
| 用户自定义 JS 拿到全局对象 | new Function 并不隔离 | iframe sandbox / quickjs |

表格保留如上。下面每行展开机制解释——为什么这个根因导致这个症状、解法背后的原理——让这张表脱离上下文也能独立读懂。

**行 1（输入一个字符全表重渲）**：机制链条是"全量受控 state → 每次击键 setState 在表单根部 → 根组件重渲染 → 所有子组件因父级重渲染而重渲染（没有 memo 时 React 默认全量向下）"。50 个字段里 49 个的 props 其实没变，但 React 不知道——它只比对新旧 props 引用，而根 state 变化制造了全新的 props 对象树。解法原理：path 级 selector 让每个字段组件用 `useStore(s => s.form[path])` 只订阅自己的值切片，zustand 用引用比较判定切片没变就跳过该组件的重渲染；Node 组件再包 `memo`，把"父级树更新"的传导也挡住。两层防线各挡一个传染路径（state 订阅路径与父级 props 路径）。

**行 2（Cmd+Z 逐字符回退）**：机制是"每次击键产生一个独立的 immer patch（如 `{op:'replace', path:['form','name'], value:'张三明'}`）→ 每个补丁单独进 undo 栈 → Cmd+Z 一次弹一个补丁 = 撤一个字符"。补丁本身没有错，错在**粒度**：用户心智里"输入完这句话"是一个操作，但系统记成了 N 个操作。解法原理：对同一 `path` 的连续 value 替换补丁做防抖合并（如 300ms 窗口）——相邻补丁互为逆操作，合并时保留窗口首的旧值与窗口尾的新值，中间值全部丢弃，语义上等价于"一次输入"。

**行 3（嵌套容器拖放判定错乱）**：机制是"单一 closestCenter 策略只算拖拽中心到各 droppable 中心的距离 → 嵌套场景里外层容器与内层容器的中心可能离指针更近的是外层（内层很小/指针在内层边缘）→ 拖进小容器被判定进大容器"。几何上"中心距离"无法表达"指针在谁里面"这个语义。解法原理：pointerWithin 先回答"指针落在哪些 droppable 的矩形内"（包含关系无歧义），有唯一命中直接用；没有命中（指针在容器间隙）再退回 closestCorners 按四角距离选最近者。两段策略把"包含优先、距离兜底"变成算法，与人对拖放的直觉一致。

**行 4（拖动时布局跳动）**：机制是"拖起的元素若被设为 `position: absolute` 或 `display: none`，它会脱离/离开文档流 → 兄弟元素回流补位 → 画布整体塌一下；后续每帧拖动又触发重排"。dnd-kit 不移动原元素（只加 transform），但 sortable 围绕原位的位移动画若与你的布局冲突同样会闪。解法原理：DragOverlay 把"视觉替身"渲染到 `position: fixed` 的传送门层，完全脱离文档流随指针移动；原元素留在原地（或保持占位尺寸），布局零回流。视觉与布局解耦后，拖动期间的重排次数从 O(帧数) 降到 0。

**行 5（monaco 光标跳动/撤销栈丢失）**：机制是"受控模式下每次 React 渲染都调用 `editor.setValue(newValue)` → setValue 是一次'全文档替换编辑'：光标被重置到文档头/尾，撤销栈里被压入整段替换 → 用户按一次 Cmd+Z 撤回的不是自己的编辑而是那次 setValue → 撤销栈瞬间被污染"。解法原理：非受控 model 模式——编辑器自己持有 model 作为唯一事实源，React 只在"外部数据真的变了"（如导入 JSON）时用 `executeEdits` 做一次带精确 range 的编辑（它是一条普通编辑，光标与撤销栈语义都正确），日常输入完全由 model 内部消化，React 侧只读不写。

**行 6（编辑态点击触发组件自身行为）**：机制是"画布里的业务组件（按钮/链接/视频）注册了自己的 onClick/onPlay → React 合成事件沿组件树冒泡 → 目标组件自己的 handler 先于/独立于画布的选中逻辑执行 → 点'删除按钮'真的触发了删除接口"。编辑器要的是"点击=选中"，组件要的是"点击=干活"，两者对同一事件有冲突的诉求。解法原理分两层：`pointer-events: none` 让组件根本不成为事件目标（点击命中的是画布容器/包裹层，天然只剩选中语义）；对必须接收事件定位的场景（如需要在 iframe 或第三方组件上命中），在 capture 阶段（事件到达目标前）`stopPropagation`，让组件的 handler 收不到事件。前者"物理隔离"，后者"拦截"，优先用前者。

**行 7（联动/事件死循环）**：机制是"联动表达式或事件动作构成环：A 依赖/触发 B、B 依赖/触发 A → 每次变更重新点燃对方 → 求值或动作无限自激"。三种解法对应三层精确度：单轮求值限制（每轮渲染/每次触发只求值一遍，第二轮的变更留到下一轮——简单但可能"该联动的不联动"）、依赖图（静态解析表达式/动作的引用关系建图，保存时检测环——最精确，但动态引用覆盖不全，见第 6 章路线 6 的完整讨论）、动作深度上限（运行时递归深度熔断——兜底一切静态分析漏掉的动态环）。三者的关系是递进兜底而非三选一。

**行 8（面板高频刷新卡顿）**：机制是"每次 tick 都对 echarts 全量 `setOption`（携全量新数组）→ echarts 对所有序列重新 diff、重新布局坐标轴与图例 → 数据点上千时每次都是几十毫秒级的 JS + 渲染开销 → 5s 刷新一屏 20 个面板 = 主线程常年被占"。三个解法各断一根传导路径：数据抽样/downsampling 把"传给 echarts 的点数"从源头砍掉（图表视觉密度有上限，超出就是浪费）；增量更新（追加新点而非整包替换）让 echarts 走 append 路径避免全量 re-layout；visibilitychange 暂停把"页面不可见时依然在烧 CPU"这条最冤的路径直接掐断——setInterval 在后台标签页里仍会执行（只是被浏览器降频到最低 1 次/秒），不主动停就永远在烧。

**行 9（旧 schema 白屏）**：机制是"协议无版本号 → 平台升级后渲染器按新协议解释旧 JSON → 读到不存在的字段/结构时抛 TypeError → React 组件树自底向上卸载 → 白屏"。数据与代码的版本错配没有任何运行时保护。解法原理：version 字段让数据自述版本；migration 链把任意旧版本逐级升级到当前版本（每级一个纯函数，可测试、可回溯），渲染器永远只面对"当前版本"一种输入——错配在入口处被消化，而不是在渲染深处爆炸。配套兜底：未知 type 渲染占位组件 + Error Boundary，保证未及迁移的页面降级可打开（第 6 章路线 9）。

**行 10（自定义 JS 拿到全局对象）**：机制是"`new Function` 创建的函数永远运行在**当前领域**的全局作用域里，且 JS 的对象引用图（`obj.constructor.constructor` → Function 构造器）从任何内建对象都能走回全局——'遮蔽变量名'式的沙箱只是把名字藏起来，引用图没断"（第 6 章路线 7 的两行逃逸代码可现场复现）。解法原理是领域隔离：iframe `sandbox="allow-scripts"`（不给 allow-same-origin）给脚本一个 opaque origin 的独立全局与原型链，读宿主 cookie/DOM 直接抛 SecurityError；quickjs-emscripten 更进一步——独立 WASM 解释器，全局对象完全由宿主注入，没有"藏"只有"给"。两者的共同本质：不是挡住路，而是换了一个世界。

### 补充：整合与协同期难点（做第 6 章之后才会遇到的新坑）

上表 10 行覆盖的是五大场景内部的坑。第 6 章把五个项目整合成平台、接入协同与远程物料之后，有一批**新的**难点开始出现——它们不属于任何单一场景，只在"整合态"下暴露。什么时候该回来查这张表：

- 平台接入第一个远程物料/第三方组件之后（行 11、12）
- 画布改为 iframe 方案、或宿主与画布消息交互变复杂之后（行 15）
- 两人以上同时打开同一个编辑器之后（行 14）
- 页面物料/节点数量上一个数量级之后（行 13、16）

| 症状 | 根因 | 解法 |
|---|---|---|
| 远程物料加载后页面崩，控制台报 invalid hook call | 物料包把 React 打了进去，双 React 实例 | 物料构建 external + 宿主注入 react；或模块联邦 shared 单例 |
| schema 导出再导入，按钮全"没反应" | Setter 把回调函数存进了 props，JSON 序列化静默丢函数 | 协议禁存函数（事件走 events、插槽走 children），保存前 typeof 扫描 |
| 大树/大表快速滚动时白屏、行反复跳跃 | 变高行 + 行高估算偏差，测量回填抖动总量 | 定高优先；变高行 measureElement 回写实测高度 + 滚动锚定 |
| 协同会话里 Cmd+Z 把同事刚拖的组件撤掉了 | undo 栈把远端更新也记了进去 | Yjs UndoManager 只 track 本地 origin，各端只撤自己的 |
| 画布/宿主执行了陌生来源发来的 postMessage 指令 | 消息监听没校验来源 | 握手协议 + 校验 e.source/e.origin + 消息带序号 |
| 改一个无关变量，整组组件全重渲染甚至无限循环 | selector 内联 filter/map 每次返回新引用 | useShallow 比较、派生移出 selector、useMemo 缓存 |

**行 11（远程物料 invalid hook call）**

- 机制链条：物料包独立构建时没把 `react`/`react-dom` 声明为 external → 物料产物里打进了**另一份** React → 宿主页面同时存在两个 React 实例 → 物料组件渲染时调 `useState`，它调用的是**物料那份 React** 的 dispatcher，而组件树却挂在**宿主这份 React** 上——dispatcher 没被宿主渲染管线装上，React 报 invalid hook call（页面崩）。
- 解法原理：**保证单例**——动态 import 路线里物料构建 external 掉 react，由宿主通过 import map/全局注入同一份（第 6 章路线 10 铁律一）；模块联邦路线里声明 `shared: { react: { singleton: true } }` 让运行时协商出唯一实例。
- 验证手段：构建期检查最可靠——物料产物的依赖清单里不允许出现 `react`（CI 卡点），比出事后排查便宜一个数量级；运行时探针（比双 React 的 version 对象）只当辅助。

**行 12（schema 导入后事件全丢）**

- 机制链条：某个自定义 Setter 图省事，把 `onChange` 回调（函数）或 ReactNode 直接存进了节点 `props` → `JSON.stringify` 序列化 schema 时**函数类型的值被静默丢弃**（JSON 规范没有函数类型，stringify 不报错、不警告，直接跳过）→ 数据库里这份 schema 的事件/回调字段是空的 → 重新导入渲染，按钮看着都在、点了没反应。
- 静默是它最毒的地方：导出时零报错，问题在数天后导入时才显形——因此防线必须前置到保存时，而不是导入时。
- 解法原理：协议里禁止函数与不可序列化值——回调语义用声明式事件表达（第 6 章路线 1 的 `events`/actions），插槽内容用 children 节点表达；保存/导出入口做一次扫描，把静默丢失变成即时报错。
- 配套扫描函数（保存与导出共用，约 20 行）：

```ts
// schema/serializableGuard.ts —— 保存/导出前的"不可序列化值"守卫
import { isValidElement } from 'react';

export function findUnserializable(
  node: unknown, path: string,
): { path: string; reason: string }[] {
  const hits: { path: string; reason: string }[] = [];
  if (typeof node === 'function') hits.push({ path, reason: 'function' });
  else if (isValidElement(node)) hits.push({ path, reason: 'ReactElement' });
  else if (Array.isArray(node)) {
    node.forEach((v, i) => hits.push(...findUnserializable(v, `${path}[${i}]`)));
  } else if (node && typeof node === 'object') {
    for (const [k, v] of Object.entries(node)) {
      if (k.startsWith('x-')) continue;                // x-* 扩展字段透传区另行约定（第 6 章路线 9）
      hits.push(...findUnserializable(v, `${path}.${k}`));
    }
  }
  return hits;
}
// 用法：findUnserializable(schema, '$') 非空 → 保存拒绝并回显 path 列表
```

**行 13（快速滚动白屏/跳跃）**

- 机制链条：虚拟列表靠 `estimatedRowSize` 估算总高 → 变高行（展开详情、换行文本）实际渲染后测得真实高度回写 → 总高与每行偏移全部重算 → 滚动条位置跳变 → 浏览器按错误的偏移渲染了"空"区域（白屏一闪）；估算与实测交替生效时行位置反复横跳。
- 解法分三层：能定高就定高（分组/多列表让每组内部定高）；必须变高时用 `measureElement`（tanstack virtual）把实测高度写进尺寸缓存，并给滚动容器开 `overflow-anchor`（浏览器滚动锚定）减弱跳动；行高方差极大（聊天消息）时上"按预估分页 + 二分定位"的进阶方案（第 5 章场景的延伸，选修）。
- 验收标准只有一个：从顶滚到底再回顶，任意行停留位置偏差不超过一行。

**行 14（协同 Cmd+Z 撤掉别人的操作）**

- 机制链条：编辑器自己维护了一份全局 undo 栈（或把 Yjs 文档的所有变更不分来源全记进 UndoManager）→ 协作者通过 y-websocket 推来的 update 也被记为"你的操作" → 你按 Cmd+Z 时把远端 update 逆向回滚——对方眼睁睁看着刚拖好的组件消失，且毫无提示为什么。
- 解法原理：`Y.UndoManager` 默认只跟踪**本地 origin** 的变更（`trackedOrigins` 含本地 transaction 的 origin）。踩坑的两种形态：自己在外面包了一层"全局快照 undo"取代 UndoManager（快照无法区分作者），或创建 UndoManager 时把所有 origin 都加了进去。
- 修法边界：协同模式下 undo 一律走 `Y.UndoManager` 且只 track 本地；快照式 undo（第 1 章 1.5 的方案）只用于单人编辑器。第 6 章路线 10 说"协同编辑器与单人编辑器 undo 的本质差异"指的就是这一行。

**行 15（postMessage 来者不拒）**

- 机制链条：iframe 画布与宿主的通信通道是 `window.addEventListener('message', ...)`，它接收**任意**窗口发来的消息——不只是你的画布 iframe：页面上嵌的第三方统计脚本、广告 iframe、甚至恶意页面把你整个编辑器嵌进外层，都能向你的宿主/画布发消息 → 消息协议里 `kind: 'updateSchema'` 这类指令一旦没校验来源就被执行，等于把编辑器的写接口暴露给全世界。
- 解法原理：通道上验证身份——宿主侧比对 `event.source === iframe.contentWindow` 且 `event.origin` 在白名单内，画布侧对称校验反向消息；再给消息加递增序号（seq）丢弃乱序/重放。
- 升格理解：第 6 章路线 2 把"宿主校验 e.source"当作通信正确性细节提过，这一行把它升格为**安全边界**——postMessage 协议的第一条消息应该是握手，握不过去的后续全部丢弃（完整握手实现见第 6 章"与 BI 报表、流程编排的边界"一节的消息桥代码）。

**行 16（selector 新引用引发全量重渲染）**

- 机制链条：`useStore(s => s.nodes.filter(n => n.visible))` 这类内联 selector 每次执行都**新建数组** → `useSyncExternalStore` 对 getSnapshot 的结果做 `Object.is` 比较 → 每次比较都是"变了"（引用不同）→ 组件在任何 store 变更后都重渲染；极端情况下 React 检测到"渲染中 snapshot 不一致"进入重试循环，控制台刷 `The result of getSnapshot should be cached` 警告，页面卡死。
- 解法三层：能用 equality hook 就用（zustand v5 的 `useShallow` 让 selector 结果做浅比较）；把派生计算移出 selector（store 里存原始数据，组件内 `useMemo` 依赖真正的输入做 filter）；或把派生做成 store 的具名方法（createSelector 思路）。
- 判断口诀：**selector 里出现 `.filter` / `.map` / `.slice` / 对象字面量 就该警觉**。原理详解见《学习大纲》阶段 10 的 `useSyncExternalStore` 一节，本行是它在五大场景里最常见的现身形态。
