## 10. 节奏安排（10 周）

| 周 | 内容 | 里程碑 |
|---|---|---|
| 1–2 | 底座 + Schema 动态表单 | mini formily（性能达标） |
| 3–4 | 表单设计器 | 设计器↔渲染器闭环 |
| 5–6 | 拖拽仪表盘 | dashboard JSON 进出 |
| 7 | JSON 编辑器 | 可视化/源码双入口 |
| 8–10 | 低代码整合 | mini 低代码平台发布 |

表格不动。要展开的是每个场景内部的**章内节奏**——同一套循环要在 10 周里跑 5 遍，跑得越标准，产出越扎实。

### 10.1 每章节奏公式：协议设计（半天）→ 按路线逐步实现（主体）→ 对照对标开源校验设计 → 写一篇复盘

每章节奏：**协议设计（半天）→ 按路线逐步实现（主体）→ 对照对标开源校验设计 → 写一篇复盘**。
复盘必须回答：我的协议和 formily/amis 的差距在哪？哪里的性能没做 path 订阅？

这两行是全篇的总纲，逐段拆成可执行的操作说明。

**第一段：协议设计（半天）怎么过**。半天 = 4 小时，切成四块，每块有明确产出物：

1. **第 1 小时：写 TS 类型，不写实现**。把本章实体的节点/字段/配置全部写成 discriminated union 与 interface（第 1 章 1.1 的方法）。硬性纪律：类型里不允许出现 `any`；枚举值穷举（`type: 'input' | 'select' | ...`）。类型写不顺 = 协议没想清，此时写代码必返工。
2. **第 2 小时：手写样例数据**。3 份合法 JSON（简单/典型/边界各一）+ 2 份非法 JSON（故意缺字段、错误枚举）。合法样例之后就是你的开发与测试夹具；非法样例用来验证 TS 报错信息是否能指引排错。手写 JSON 时会发现类型里没定义的隐含约束（比如"数组字段必有 itemSchema"），当场回改类型。
3. **第 3 小时：画数据流图**。一张图三个角色（编辑器/协议/渲染器），箭头标"谁产出、谁消费、何时求值"。第 6 章开头的架构图就是这一步的成品形态。图里每一个箭头都要能回答"同步还是异步、单向还是双向"。
4. **第 4 小时：写"协议十问"文档**。十个问题写进 README：key 用什么？隐藏字段的值保不保留？表达式什么时候求值？version 从几开始？未知 type 怎么办？……能答的直接写答案，不能答的标"待实现期验证"。这份文档是第四段复盘的对照组。

**第二段：按路线逐步实现（主体）怎么排**。操作规则五条：

1. **路线即顺序**：每章"实现路线"的编号就是依赖顺序，不要跳步——第 6 章不先做协议升级就做 EventSetter，setter 产出的数据无处安放，必然返工。
2. **每条路线以"可演示"收尾**：一条路线完成的定义是能对别人演示它的效果（路线 2 完成 = 拖组件进 iframe 画布落点正确），不是"代码写完了"。演示不出来的路线等于没做完。
3. **坑即测试**：每个 ⚠️ 坑位在修完后写一个最小复现测试（构造该 schema/操作序列，断言修复行为）。坑是免费的测试用例设计书。
4. **时间盒**：单条路线卡住超过预计 2 倍时间，先做一个能跑的简化版跳过去，在复盘里记录欠账——进度比完美重要，欠账清单防止遗忘。
5. **每周一次"组装日"**：把当周产物与前几章接起来跑一遍（如第 7 周把 JSON 编辑器接进第 3/4 章的导入导出）。集成问题暴露得越频繁，最终整合周（8–10 周）越轻松。

**第三段：对照对标开源校验设计怎么操作**。不是"通读源码"，是三个固定动作：

1. **字段级对照**：打开对标项目的协议定义（formily 的 JSON Schema 映射、amis 的 Schema 类型/文档），把它的顶层域列成清单（type/props/visible/hidden/onEvent/api/…），逐项问"我的协议有吗？没有是没想到还是故意不要？"。故意不要的写进 README 的设计决策一节（例如"我不做 xxx 因为场景不需要"），想到但没做的进欠账清单。
2. **机制级对照**：挑一个你刚实现完的机制（如 path 订阅、动作链），去看对标项目的同一机制（formily 的 autorun、amis 的 actions），对比触发时机、批量合并、错误处理三个维度。差异点写进复盘——通常你会发现对方多做了"批量/边界/降级"中的一项。
3. **issue 抽查**：在对标仓库搜你踩过的坑关键词（如 undo input、nested droppable），看它是否也踩过、怎么修的。这是第 8 章"issue 驱动读法"的日常化。

**第四段：写一篇复盘，两个必答题怎么对照着答**。复盘文章结构固定：协议终稿（类型 + 一份典型 JSON）、架构图、三个最深的坑（症状/根因/修法）、与对标的三处差异、欠账清单。两个必答题的答法：

1. **"我的协议和 formily/amis 的差距在哪？"**——用第三段的字段级对照清单直接回答：列出"它有我没有"的每一项，标注"没想到 / 想到故意不要 / 想到没做"。这份清单本身就是差距的完整刻画，避免"感觉差挺多"式的空话。重点解释"故意不要"的项——那是你的协议与它们的场景差异所在，也是面试时讲得最出彩的部分。
2. **"哪里的性能没做 path 订阅？"**——不是凭记忆回答，用 Profiler 走一遍：打开第 2 章产出的 20 字段表单（或本章页面），在任一输入框打字，看 Profiler 的 commit 火焰图——重渲染组件数应为 1；再打开第 6 章页面改一个变量，记录受影响组件数与理论值（只应影响绑定该变量的组件）。凡"实际 > 理论"的位置逐个归因：漏了 selector？依赖收集没覆盖该表达式？还是 memo 被 props 内联对象击穿？每个归因写一行修法。两个场景都测过且数字达标，这题才算答完——这也是表格里"性能达标"里程碑的验收动作。

这套"协议 → 实现 → 对照 → 复盘"的循环跑满 10 周，你收获的不只是五个项目，而是一套可复用的方法论：拿到任何"描述型 UI/流程"需求，先设计协议、再搭注册表与递归渲染、用对照开源校验决策、以复盘沉淀判断力——这正是从"会用 React"到"能定义系统"的那一步。

### 10.2 弹性变奏：压到 6 周或拉到 16 周

10 周是默认拍子（按每天 1.5–2 小时的投入估）。真实约束常常不答应：下周入职新团队要快速拿产出，或者相反，你每周只有周末两块时间。变奏的前提是知道每章的**不可让渡核心**——砍掉核心等于白学，砍掉外围只是少些厚度。先给核心清单，再给两张变奏表。

各章不可让渡核心（砍任何一条，后面章节会还债）：

| 章 | 不可让渡核心 | 可以砍的外围 |
|---|---|---|
| 1 底座 | 注册表、递归渲染器、表达式引擎求值链路、immer patch undo | Undo 的三种实现对比只留 patch 版；大 schema 性能只做验证不做优化 |
| 2 动态表单 | 字段协议 + path 级订阅（性能达标这条主线） | 校验进阶（异步校验、联动去抖）只做一例 |
| 3 设计器 | 设计器↔渲染器闭环（拖拽产 schema、schema 驱渲染） | 多物料精雕、Setter 全家桶——留 input/select 两个 setter 即可 |
| 4 仪表盘 | dashboard JSON 进出 + 布局模型 | 图表只接 2 种；自动刷新/可见性暂停留为 TODO |
| 5 JSON 编辑器 | 双向同步的冲突裁决策略 | 高级 Monaco 配置、JSONPath 增强 |
| 6 低代码整合 | 协议升级 + 渲染器 + 动作引擎的最小闭环、migration 链 | iframe 画布、协同、远程物料（全部选修） |

**压缩版：6 周**（入职前突击/项目空档期）。原则：外围全砍、对照动作从"三个"减到一个、组装日照留——集成问题暴露是全大纲最贵的学费，砍它省下的两天会在第 5 周加倍还。

| 周 | 内容 | 说明 |
|---|---|---|
| 1 | 底座 + 动态表单核心 | 表单只做 10 字段、订阅性能验收做满（这是主线不能糊） |
| 2 | 设计器闭环 | 拖拽生成 + 实时预览跑通即可，物料 3 种 |
| 3 | 仪表盘 | 布局 + 1 种图表 + JSON 导入导出 |
| 4 | JSON 编辑器 | 可视化/源码双入口 + 单向优先裁决 |
| 5 | 低代码整合（上） | 协议升级、渲染器、变量系统 |
| 6 | 低代码整合（下）+ 总组装 | 动作引擎最小版、migration 链、五项目串联演示 + 复盘 |

压缩版的对照动作只保留"字段级对照"一件（每章 1 小时：列对标协议的顶层域，逐项问"我有吗"）——机制级对照与 issue 抽查砍掉，但每章复盘的两个必答题保留，它们是防止"只冲速度不辨方向"的锚。选修（第 6 章路线 10、第 7 章扩展场景）在压缩版里**全部显式跳过**并写进欠账清单，而不是"有时间就做"——后者等于给自己埋永久性焦虑。

**拉伸版：16 周**（每周投入不足或想深挖）。原则：不是把每章都摊薄变慢，而是**保持章内节奏不变、把多出的周花在"第 10 章之外的第二层"**：

| 插入位 | 多出的周做什么 |
|---|---|
| 第 2 章后 +1 周 | 源码地图 8.1–8.3（rjsf / react-grid-layout / dnd-kit）——与刚做完的表单/设计器对照最热乎 |
| 第 4 章后 +1 周 | 源码地图 8.7（grafana）+ 第 7 章扩展场景选一个（推荐 7.6 透视表：复用度最高） |
| 第 5 章后 +1 周 | 第 7 章再选一个场景，或源码地图 8.4–8.6（amis/formily/lowcode-engine，为第 6 章储备） |
| 第 6 章后 +2 周 | 8.9–8.11（React 本体与中型库）+ 二刷性能：用 Profiler 把五个项目各跑一遍，欠账清单清一轮 |
| 机动 +2 周 | 每章多出的时间自然沉淀；断档恢复缓冲（对照《学习大纲》36 的"中断与重启"——那是"停了怎么回来"，本节是"主动改变拍子"，两者互补） |

拉伸版最大的风险不是慢，是**无限延期**——多出的时间像海绵，永远吸得下"再研究研究"。治理：每 4 周做一次 go/no-go 复盘（这 4 周的产出能演示吗？不能的话是哪条路线卡住了？），并给拉伸版设硬终点日期。

go/no-go 复盘的固定模板（15 分钟填完，贴在 NOTES 里）：

```text
# Sprint N go/no-go（日期）
## 能演示什么（对照该章验收清单逐条）
- [x] …
- [ ] …（未达成项）
## 未达成项的卡点归类
- 协议没想清 / 实现超时 / 对照走偏 / 断档
## 下个 4 周的动作
- go：继续下一章，理由…
- 调整：砍 X 保 Y
- no-go：降级到压缩版（说明触发条件）
```

两种变奏的取舍口诀：**压缩版赌时间、拉伸版赌纪律**——前者要接受"每个主题都浅一层"，后者要接受"每 4 周审视一次自己有没有在假学习"。知道自己缺时间还是缺纪律，选变奏就不会纠结。

### 10.3 串行与并行：项目排布取舍 + 团队共读节奏

**单人默认串行，三个理由**。其一，章内复用是纵向的：第 3 章的设计器直接 import 第 2 章的字段渲染，并行做这两章的人会在"协议还没定型"时就互相依赖对方的产物，结果两边各猜一边。其二，心智切换成本高于想象：表单的"订阅粒度"思维和画布的"坐标/命中"思维切换一次要半小时进入状态，每天切换等于每天白扔一小时。其三，10.1 的"每周组装日"依赖前章产物已就绪，并行会把它变成"集成失败观摩日"。所以默认串行；唯一值得并行的窗口是**等待型并行**——比如第 4 章的图表库在装依赖/跑示例的间隙，把第 5 章 Monaco 的文档先读了。并行的是"读与试"，不是"两条实现主线"。

**两人以上：可以并行，但按"底座合流"切**。正确切法不是按章切，而是按层切：

1. **第 1 周全员共学底座**（第 1 章）——底座是所有场景的公共语言，这一周谁都不能缺席，且一起踩坑能对齐术语。
2. **第 2 周起按场景分领**：每人认领一章当 owner（A 做表单、B 做设计器、C 做仪表盘），其余人对该章是"评审人"角色。owner 制的价值：每章的复盘文章有主笔，协议决策有人拍板。
3. **组装日全员合流**：每周一次，各 owner 把当周产物接到底座上演示——底座是共享仓库（只由一人维护、按周发 tag），任何人不直接改底座、只提 PR。这条治理防止并行最常见的死法：第 4 周发现三个人各改了一版"注册表"，合不回去。
4. **第 6 章低代码整合必须全员上**：它是总装，三人分别认领协议/画布/动作引擎三条线，正好对应 10.1 的路线分组，天然适合并行。

**共读会的节奏（每周 90 分钟，三段固定）**：第一段 20 分钟"演示验收"——当周 owner 对着该章验收清单逐条演示（做不出的当场记欠账，不解释为什么不做了）；第二段 40 分钟"坑复盘"——owner 讲本周最深的三个坑，按"症状→根因→修法"讲，其他人的提问只允许"换我我会怎么写"式的问题（禁止"为什么不直接用某库"式的 Cheap Shot，那条留给第三段）；第三段 30 分钟"对照互评"——各自亮出字段级对照清单（10.1 第三段的产物），互评"故意不要"的决策是否站得住。共读会最大的退化方向是变成"念文档会"——铁律是**没带可演示产物的人不发言**，三代之后这条会内化成团队文化。

**验收的交叉原则**：owner 不能验收自己的章——每章的验收清单由非 owner 的人拿着勾（参考共读会第一段的演示），交叉验收逼出的"为什么这里卡顿"往往比自查多一倍。团队场景下这条比任何工具都值得坚持。

共读会退化信号与处置（机制化治理，不靠自觉）：

| 退化信号 | 判定 | 处置 |
|---|---|---|
| 某人连续两次没带可演示产物 | 参与度问题 | 按纪律不发言；线下 1:1 问卡点（多半是断档，转《学习大纲》36 的恢复流程） |
| 演示段变成"讲 PPT" | 产出注水 | 铁律重申：只演示可运行的东西，截图不算 |
| 坑复盘段鸦雀无声 | 没人再踩新坑 = 没人在推进 | 检查是不是集体进入"只读不写"状态 |
| 对照互评变成互相吹捧 | 决策质量下降 | 强制要求每人挑一处"故意不要"的决策唱反调 |
| 组装日频繁失败合不进去 | 底座治理失守 | 回到底座单人维护 + 周发 tag 的规则，重跑一次合流 |

单人计划的你可能会问：这套团队节奏与我何干？两处直接可用——其一，一人分饰两角（实现者 + 评审者）交叉验收自己：隔天用"非 owner 心态"重看昨天的验收清单，效果远好于连续自查；其二，多数人最终要把这套能力带进团队，这份节奏表就是现成的落地方案——学完大纲的你，往往就是团队里那个该发起共读会的人。
