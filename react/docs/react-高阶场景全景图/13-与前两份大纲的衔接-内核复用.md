## 与前两份大纲的衔接（内核复用）

- 生成式 UI（F1）＝ schema 渲染器（进阶大纲 §1.3/§2）
- Agent 画布（F2）＝ 节点编排（A4）+ Setter 体系（进阶大纲 §3）
- 在线 IDE（D4）＝ JSON 编辑器（进阶大纲 §5）+ 安全沙箱（进阶大纲 §6.7）
- 插件化（D1）＝ 注册表模式（进阶大纲 §1.2）的架构级放大
- 协同（B1）＝ Undo/Redo 补丁思想的分布式延伸（进阶大纲 §1.5）

五条映射逐条讲清"具体复用什么、在哪里接缝"。

**第一条：生成式 UI（F1）＝ schema 渲染器（进阶大纲 §1.3/§2）**。具体到代码级：F1.7 的 demo 里，`UiNode` 协议就是进阶大纲 §1.1 的 discriminated union 节点协议；`registry: WidgetMap` 就是 §1.2 的组件注册表（连"带物料元信息"的扩展位都保留了——生成式 UI 的组件市场就是物料系统的另一种卖法）；`RenderNode` 递归渲染器就是 §1.3 的 `renderNode`，连"key 用节点 id、Node 组件 memo"两个戒律都一字不差；如果生成式 UI 要做"填表后提交"的交互（比如 LLM 生成一张订单表单），§2 的动态表单整套（Field 组件、path 级订阅、visibleWhen 联动、校验）直接搬来。唯一的接缝在数据生产端：§1 的生产者是"设计器拖拽"（§3）或"手工 JSON"，F1 换成"LLM 结构化输出"——所以你在 §1 练的协议设计能力（可序列化、声明式、版本号、稳定 id）在这里是生死线：协议设计得好，LLM 的约束 schema（zod）就好写，strict 模式拒掉非法输出的能力就强。两种应用共享同一条内核，这就是"学习成本最低"的结构性原因。

**第二条：Agent 画布（F2）＝ 节点编排（A4）+ Setter 体系（进阶大纲 §3）**。拆到组件级：画布层——A4 的 React Flow 全套（自定义节点/边、isValidConnection 类型校验、dagre 布局、小地图）原样复用；属性层——选中 Agent 节点时右侧面板渲染参数表单，这正是 §3 表单设计器"属性区"的运行态版：节点协议里的 `paramsSchema`（本篇 F2.1 已给出类型）就是 §3 里物料的"setters 声明"，面板按 schema 渲染"模型选择器、温度滑杆、prompt 多行文本"的过程，就是 §2 动态表单的渲染过程（连"字段用 selector 只订阅自己的 value"的性能纪律都适用）。接缝在两点：一是变量的求值上下文——Agent 的 `{{node_1.output}}` 引用复用 §1.4 表达式引擎，把 `$form` 换成 `$nodes`；二是运行态（本篇 F2.2 新增的 rAF 合并层）挂在 A4 的静态画布之上，静态结构与动态监控分离，DSL 序列化时剥离 `run` 字段。

**第三条：在线 IDE（D4）＝ JSON 编辑器（进阶大纲 §5）+ 安全沙箱（进阶大纲 §6.7）**。在线 IDE 的三个核心件都能在前两份大纲里找到原型：编辑器——§5 已经为 JSON 场景啃过 Monaco（取值模型、光标控制、校验标注），D4 把语言从 JSON 扩展到任意语言（Monarch tokenizer/Lezer 语法），编辑器容器的工程问题（多 Tab、虚拟文件系统、TS Worker）是 §5 的外推；预览沙箱——§6.7 的"安全执行用户 JS"（iframe 沙箱、错误透传）就是 CodeSandbox 式预览的安全底座，D4 的增量是构建链（sandpack/WebContainers/esbuild-wasm/import maps）；版本对比——本篇 F2.4 的 monaco DiffEditor 直接是 §5 选型的复用。接缝认识：在线 IDE = "编辑器（§5）+ 沙箱（§6.7）+ 构建（新知识）"，真正要新学的只有构建管线一块。

**第四条：插件化（D1）＝ 注册表模式（进阶大纲 §1.2）的架构级放大**。§1.2 的注册表是"一个对象映射 + 元信息"，解决"组件从哪来"；D1 把同一个模式放大三个数量级：扩展点从"组件类型"变成**contribution points**（VSCode 式声明：插件声明"我要贡献一个面板 + 三个命令 + 一种物料"，宿主按声明合并进注册表）；注册来源从"编译期静态"变成**运行时动态**（CDN ESM / 动态 import，要处理加载失败降级与版本兼容）；信任模型从"全信任"变成**能力授权**（插件只能用宿主暴露的白名单 API，对应注册表元信息里的权限声明）。接缝在于：做 D1 之前必须先把 §1.2 的注册表用熟（你低代码平台里的物料系统就是现成宿主），否则 contribution points 的设计会退化为"什么都往全局塞"。这也是为什么 D1 的入手路径是"给第 6 章低代码平台做插件系统"——宿主已经有了，缺的只是放大。

**第五条：协同（B1）＝ Undo/Redo 补丁思想的分布式延伸（进阶大纲 §1.5）**。§1.5 的三种 undo/redo 实现里，`immer produceWithPatches` 生成正/反补丁的思想，在 B1 里的对应物是 CRDT 的**操作与逆操作可交换合并**：本地编辑 = 产生一个操作（patch），撤销 = 应用逆操作，协同 = 把操作广播给别人并保证任意顺序应用结果一致（CRDT 的数学保证，last-write-win 做不到）。更直接的复用在工程层：Yjs 的更新（update）就是一棵文档补丁的二进制编码，`Y.applyUpdate(doc, update)` 与"把 immer patch 应用到 draft"在心智模型上同构；两个 Tab 协同的调试、离线 edits 的合并回放，用的正是 §1.5 练过的"补丁流思维"。接缝认识：先把 §1.5 的补丁（含合并补丁防逐字符回退的坑）吃透，B1 的学习曲线会从"全新领域"降为"补丁思想的分布式版本"——省下的时间拿去攻 CRDT 真正的新知识（Yjs 的数据结构与 awareness）。

至此，23 个场景、7 大族群、"怎么选"与三条建议全部展开。回到开篇那句话：没人能全学——现在你已经有了完整的地图与每条路线的成本收益账，挑 2–3 个深扎 4–6 周，其余的知道"它是什么、难在哪、复用什么"就够。这份全景图的价值不在"都做一遍"，而在你面对任何一个新需求时，能立刻认出它是哪个场景的变体、内核在哪儿已经写过。

**动手前 30 分钟的五问评估法**（对着表逐条回答，答不全就先别写代码）：

1. 这个场景的**状态核心**是什么数据结构？（有序序列 / 树 / 图 / 网格）
2. 前两份大纲与本文里，哪个内核操作过**同构结构**？（G.3 前缀和管过序列、§1.2 注册表管过集合、§1.5 补丁流管过文档树）
3. 渲染瓶颈大概率在**列表、画布还是表单**？——决定第一个性能原型先做哪一块；
4. "必须新学"里哪些是**协议/标准**（保值：WebRTC、CRDT 语义、坐标系），哪些是**库用法**（贬值：某个构建器/打包器的 API）？前者上不封顶地投入，后者用到再学；
5. 第一周能不能交付一个"**内核复用 + 桩实现**"的骨架？——不能，说明对场景的拆解还停留在名词层，回去补场景调研而不是写代码。

最后诚实地标注三类**没有可复用内核的净新知识**：实时传输协议族（WebRTC/编解码）、图形像素管线（Canvas/WebGL 渲染分级）、地理坐标数学（投影/瓦片）。遇到它们的正确心态不是"又是全新的，学不动了"，而是按全新领域重新排期——这张表的意义正在于把"学不动了"翻译成"还剩多少是真的要学"。

**五问法示范（以 A2 表格为例，其余场景照此格式填写）**：

1. 状态核心：行列二维网格 + 单元格之间的公式依赖图；
2. 同构内核：G.3 的前缀和管住行、列两个方向的窗口，§1.5 命令栈管单元格编辑的 undo/redo；
3. 瓶颈排序：先二维虚拟化（渲染），后公式重算（计算）——反过来做会先卡在错误的层；
4. 保值/贬值分账：依赖图与拓扑重算是协议级知识（保值），某个网格库的事件 API 是库用法（贬值，用到再查）；
5. 第一周骨架：定高二维窗口 + 桩公式引擎（只支持四则运算），先跑通"编辑 → 重算 → 渲染"闭环，列锚定与引用错误提示放第二周。

（其余每个场景动手前照此格式各写一份五问答卷，每份不超过 10 行——写不进 10 行，说明第 1 问的状态核心还没想清楚，先回去补拆解再开工。）

### 补充：内核复用矩阵 v2——五个跨场景内核 × 七族映射与最小掌握路径

前文的五条映射与速查表都是**垂直方向**的：站在某个场景里，自下而上问"它能复用多少已写过的内核"——这是**省钱视角**。但 A–G 各族补充小节展开之后，浮现出一个此前没人明说的水平结构：**有几个技术内核在多个族群各出现一次，每次换一层皮**（列表里叫虚拟化、图形里叫 LOD、协同里叫离线队列）。v2 把问题倒过来：站在内核上，横向问"掌握它，七族里哪些场景的成本直接下降"——这是**投资视角**：场景会过期，内核不会；按内核组织学习，一次投入在七族复利。

入选标准（防止"万物皆内核"的通货膨胀）：至少在三个族有直接展开的文本依据，且存在一天内可完成的练习闭环。筛出五个：Worker 通信、离线队列、协同数据模型、LOD 分级渲染、流式状态机。

**总矩阵**（● 该族有直接展开的文本；○ 间接出现/同构变体；— 无）：

| 内核 | A 编辑器 | B 实时协同 | C 图形可视化 | D 应用架构 | E 性能离线 | F AI 原生 | G 交互底座 |
|---|---|---|---|---|---|---|---|
| Worker 通信与计算卸载 | ○ 公式重算下沉 | ○ 搜索/解密 | ● 聚合与渐进渲染 | ● 构建管线 | ● 全套拆解（大本营） | ○ 懒计算/调度 | — |
| 离线队列与操作补发 | ○ 离线 edits | ● 补发与回放（大本营） | ○ 瓦片缓存 | ○ 桌面端离线 | ● 队列重放（大本营） | ○ 中断重发 | — |
| 协同数据模型 | ● 接 B1 即协同 | ● 选型决策树（大本营） | ○ 白板协同 | ○ 多端同步 | ● 冲突解决 | ○ 多用户编排 | — |

逐个说明"它统一了什么"、文本依据与最小掌握路径。**统一了什么**是最重要的一栏——这是面试里"讲内核不讲场景"时的开场句。

**内核一：Worker 通信与计算卸载**。统一的是"主线程只做 UI，重活搬走再拿回结果"的通信纪律。文本大本营在 `08-E-极端性能与离线.md` E1：任务下沉、Comlink RPC、transferable 零拷贝、OffscreenCanvas；C 族实例在 `06-C-图形与可视化.md`（supercluster 在 Worker 建索引查询、大规模节点图的渐进渲染）。容易被忽略的同构：F2.2 的 rAF 合并（`09-F-AI-原生前端-当下最热-且与你的-Schema-线天然衔接.md`）是它的调度近亲——一个是空间卸载（搬去别的线程），一个是时间卸载（切碎到别的帧），心智同源。最小掌握路径（1–2 天）：100 万行数据排序做两版——主线程版 vs Worker + Comlink 版，再对比 transferable 前后的内存曲线；把三组数字写进一篇短笔记。过关标准：能讲清"什么时候不该用 Worker"（通信与拷贝成本超过计算收益的边界）。

**内核二：离线队列与操作补发**。统一的是"操作先落本地队列、恢复后按序重放、冲突按规则收敛"的断网生存模式。大本营有两处：`05-B-实时与协同.md` 补充三（断线重连、离线补发、并发回放测试——把"网会不会断"从祈祷变成测试用例）与 `08-E-极端性能与离线.md` E2（IndexedDB 持久化与队列重放）。同构变体散在各族：B2 的乐观发送、F1.4 的编辑重发、D5 桌面端的离线操作。最小掌握路径（1–2 天）：给一个 todo 应用加"断网可写、恢复自动重放"——操作序列化进 IndexedDB 队列，online 事件触发重放，重放要幂等（用客户端操作 id 去重）。过关标准：拔网线写三条、恢复后不重不丢，且能说清"为什么去重键要用操作 id 而不是时间戳"。

**内核三：协同数据模型**。统一的是"多个写入方、乱序到达、最终一致"的一致性选型能力。大本营在 `05-B-实时与协同.md` 补充一（LWW/乐观锁/OT/CRDT 决策树——本矩阵五内核里"决策价值"最高的一个：多数团队的真实错误不是选错算法，而是根本不知道有档位之分）与补充二（选择性 Undo 与权限）。它与全图的关系是乘法：A 族任何场景接上它就变协同编辑器（`02-全景总览.md` 依赖关系段的原话），E2 的尽头也是它。最小掌握路径（2 天）：不用 Yjs，手写 LWW-Register（值 + 逻辑时钟，双端乱序到达取赢家），再用 Yjs 做同样实验对照行为差异——你会亲眼看到 LWW 丢失并发写、CRDT 保留并发插入的那一幕。过关标准：能对着决策树说出自己当前项目"该在哪一档、为什么"。

**内核四：LOD 与分级渲染**。统一的是"按视距/视口决定渲染精度"的信息分级——列表虚拟化是它在滚动维度的形态，瓦片金字塔是地理形态，THREE.LOD 是三维形态，可视区外不渲染是会话形态。大本营在 `06-C-图形与可视化.md` 补充二（大规模节点图：LOD 三级 + 滞回——滞回是防抖动的关键补丁）；实例横跨 A2 二维虚拟化、E1、F1.6、G.6（`10-G-交互底座-复杂交互组件自研-性价比最高.md`）。它可能是覆盖面最广的内核（矩阵里 ● 最多的一行）。最小掌握路径（1–2 天）：1 万节点的图按缩放切三级细节（远=纯色点/中=简化形/近=完整形），加切换滞回；对比无 LOD 的帧率。过关标准：能解释"为什么 LOD 切换必须带滞回"（临界缩放处的抖动机理）。

**内核五：流式渲染状态机**。统一的是"数据没到齐也要立刻开始正确地渲染"——半成品状态（未闭合的代码块、半个 JSON、组合中的输入法文本）不是异常，是常态。大本营在 `09-F-AI-原生前端-当下最热-且与你的-Schema-线天然衔接.md` F1.1–F1.4（收集/完成/中断/重生的显式状态机）。最容易被忽略的谱系：A 族的 IME 组合态是最古老的流式问题（composition 事件就是在"字没打完"时保证不破坏 DOM），B2 的乐观 UI 是"流式确认"（先渲染本地值、服务端 ack 后校正），E1 的分帧是时间维度上的流。最小掌握路径（1 天）：fetch ReadableStream 做打字机 + 中断按钮，状态机显式建模五态（idle/streaming/aborted/done/error），非法状态转换直接抛错——例如从 aborted 直接转 streaming 必须经过显式 reset。过关标准：中断后立刻重生成，消息列表无重复无残留，且状态转换全部走过断言。

矩阵的三种用法。**用法一，面试重构叙事**：把简历上的场景清单重写成内核清单——"我做过的四个项目，底层其实是三个内核的四种组合"，这在高级岗面试里比罗列项目高一个层级。**用法二，排期折算器**：速查表的"预估复用"列是场景口径，v2 给的是内核口径——新需求来了先扫这五行，命中的 ●/○ 越多，越接近"组合已知积木"而非"学习新领域"，估算时按前者报价。**用法三，学习顺序的最终依据**：如果对"先学哪个场景"犹豫，答案永远是"先补它依赖的内核"——内核是场景的公因数，公因数学一遍，所有场景的学费一起打折。这与 `../react-高阶场景-第二辑/14-3-10-与内核的复用关系-为什么它被列为三星.md` 的结论同源：场景的星级是现象，内核的复用率才是原因。

速览卡顺带回答一个高频问题："六个内核先练哪个？"不按表的顺序，按你的处境：**时间只剩一天** → 校验与容错（最便宜、当天毕业）；**在做性能优化** → LOD 和 Worker（当周就能用上）；**产品要加离线/协同** → 离线队列 + 协同数据模型（成对练，队列是工程半、选型是决策半）；**在 AI 产品线上** → 流式状态机最先（F1 的一切都站在它上面）。没有处境的按 v2 原则：先补你主场景依赖的那个。

处境之外还有一个练习法层面的建议，值得单独立段：**用一个宿主项目练多个内核，而不是每个内核开一个 demo**。六个内核各自的最小练习（速查卡第三列）如果分开做，你会攒六个半成品仓库——每个都只到"过关标准"，互不相干。更好的做法是选一个功能密度足够高的宿主（现成的好选择：一个本地优先的笔记应用，或一个带 AI 对话的待办工具），把六个内核依次"装"进去：

| 装进宿主的顺序 | 内核 | 在宿主里的形态 |
|---|---|---|
| 1 | 边界校验与容错 | 所有入口（导入文件/AI 输出/本地缓存读取）统一过三层校验 |
| 2 | 流式渲染状态机 | AI 对话的收集/中断/重生成 |
| 3 | LOD 与分级渲染 | 长笔记列表的分级渲染（折叠态只渲染摘要行） |
| 4 | Worker 通信 | 全文搜索下沉（含结果转移回主线程） |
| 5 | 离线队列 | 断网可写、恢复重放 |
| 6 | 协同数据模型 | 双标签页共写（先 LWW 后 Yjs 对照） |

一宿主多内核的三个好处：内核之间的真实接口被逼出来了（队列重放后的数据要过校验、Worker 结果要进 LOD 分级——单独练习时这些衔接根本不会出现）；作品集从"六个练习"变成"一个有深度的应用"（面试叙事升一个层级）；维护成本只付一份。代价是宿主要先花一两周搭到"能用"——这恰好也是 `01-这张全景图怎么用.md` 季度规划模板的标准开局，两者可以同一个季度做。

六内核还有一个此前没说破的共同点，用 `03-React-相关度过滤视图.md` 的折旧维度一照便知：**内核几乎全是范式级资产**——窗口计算、队列重放、一致性选型、分级渲染、状态机建模、分层校验，没有一个是"某库的用法"；而每个内核又各自锚着一块协议级的骨头（渲染管线之于 LOD、HTTP 缓存语义之于队列、CRDT 数学之于协同、SSE 之于流式、zod 背后的类型系统之于校验）。这个结构解释了 v2 投资视角的底气从哪来：练内核买到的不是"又一项技能"，而是**范式级主体 + 协议级锚点**的复合资产——按 03 的记账科目，是同时往两个最抗折旧的账户存款。反向推论也成立：如果一个"看起来像内核"的东西主体是库级知识（某状态库的用法、某平台的配置），它再热门也过不了 v2 的入选标准——这条隐含标尺与更新三的否决互为表里。

矩阵 v2.1 的收尾用法不变，只把 v2 的三种用法升级一句：排期折算器现在扫的是**六行**；学习顺序的答案仍是"先补内核"。与 `02-全景总览.md` 深读索引补遗的分工照旧：那边管"读哪份文件"，这边管"练哪个内核"；两边共用同一条维护规则——新增补充小节时，回查两张表。

最后用一个完整用例把 v2.1 的三件更新串起来——**排期折算器的实战**。需求：给 SaaS 产品加"AI 助手配置 + 客户离线可用"两条线。先扫六行：命中"边界校验与容错"（AI 输出协议要校验）、"流式渲染状态机"（助手对话）、"离线队列与操作补发"（离线可用）、"协同数据模型"（离线合并策略要选型）四行。折算：四个内核都有文本依据（F 补充一、F1.1–1.4、B 补充三/E 补充二、B 补充一），复用口径下这不是"四个新领域"而是"四个内核的应用"——排期按各内核的"必须新学"增量报（校验一天、流式状态机三天、队列两天、选型一天，合计一周内核熟化 + 各自的场景装配时间）；再对照速查表把场景层复用（注册表/渲染器之于配置界面）叠上，整单报价从"没做过，估三个月"变成"内核熟化一周 + 装配三周，风险在 XX"。**矩阵的折算不是让数字变好看，是让估算的结构从"拍脑袋"变成"内核价目表 + 装配工时"**——这也是内核视角与场景视角（速查表）必须配合使用的原因：内核管深度的价，场景管宽度的价。

从 v2 到 v2.1 还有一条元经验值得留档：**矩阵应该随文本生长而小步快跑**。v2 一次性筛五个内核、v2.1 只做了三处小更新（增补依据、收编一个、否决两个半）——如果等"内容全齐"再做大版本，矩阵会在半旧状态下被引用很久（02 的空档标注过时就是教训）。版本号给读者的承诺是"我反映的是截至该版本的现实"，小版本勤发，比大版本憋着不发诚实。

最后把六内核接回本篇开头的五问评估法（动手前 30 分钟那套）：五问法的第 2 问"哪个内核操作过同构结构"，在 v2 时代只能对着一列场景答案猜；v2.1 之后它有了精确的查找表——六内核 × 七族的矩阵行列交叉即是答案。第 2 问的操作升级为：把需求的状态核心（第 1 问的产物）在矩阵里横着扫一遍，命中的 ●/○ 格子就是"你已经会的部分"，剩下的才是第 3–5 问要处理的真增量。五问法管"这一次怎么动手"，六内核管"这段时间练什么"——一个战役、一个军费，合起来才是完整的复用体系。
