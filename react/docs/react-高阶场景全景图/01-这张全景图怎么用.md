## 这张全景图怎么用

### 第一步：按"方向 × 兴趣 × 机会"挑出你的 2–3 个

挑场景不要凭"哪个听起来酷"，用一个三变量筛选：

- **方向（权重最高）**：你的职业方向决定主场景。做 BI 的深扎大数据可视化，做 IM 的深扎长会话与性能，做低代码平台的深扎插件化与在线 IDE 底座。方向不对的场景，学到 ★★★★ 也不会有生产环境给你练手，投入产出比断崖式下跌。
- **兴趣（决定你能不能熬过第 3 周）**：4–6 周深扎的中段（第 3–4 周）必然进入"啃硬骨头"的枯燥期——读源码、调不可复现的 bug。兴趣是唯一能扛你过这一段的燃料。方向选主场景，兴趣选副场景，两者可以不是同一个。
- **机会（放大收益）**：当下市场什么岗位在溢价，就把它当加分项。写作本文时（2025–2026），F 族 AI 原生前端处于需求爆发期；但风口场景的溢价衰减也快，别把全部筹码押在"热"上。

推荐的一个稳定组合结构是：**1 个方向主场景（★★★★ 以上，4–6 周）+ 1 个兴趣副场景（★★★~★★★★，3–4 周）+ G 族交互底座（★★★，2–3 周，性价比打底）**。G 族特殊在它不是"一个场景"而是所有场景的地基——浮层、虚拟滚动、键盘导航、无障碍，任何主场景都直接受益，所以永远值得排进计划。

另外挑之前先看一眼后文的"依赖关系"小节：有些场景之间存在先后依赖（例如 B1 协同编辑依附于 A1 富文本——单机编辑都做不对，协同只会错得更快），选了下游场景却跳过上游，第 2 周就会卡死。

### 第二步：按 4–6 周的节奏深扎，每周有验收物

"深扎"不是"看教程看 4 周"。以下节奏表经过了多个场景的验证，直接套用：

| 周次 | 做什么 | 验收物 |
|---|---|---|
| 第 0 步（1–2 天） | 跑通 2 个官方 demo，确认"就是要它" | demo 在本地跑起来，改一处代码看到效果 |
| 第 1 周 | 用起来 + 魔改：照着官方文档把 demo 改出 3 个自己的功能 | 一个"改过的 demo"，能讲清每个功能背后的机制 |
| 第 2 周 | 最小复刻：把 demo 从零写一遍，不用脚手架 | 一个最小内核（通常 100–300 行），理解每行为什么存在 |
| 第 3–4 周 | 核心机制攻关：按本篇"核心技术"清单逐项实现，硬骨头都在这里 | 核心机制清单全部打勾，每项配一个能复现的测试 |
| 第 5 周 | 组合与工程化：接入自己业务（低代码平台/组件库），补性能与边界 | 在真实项目里跑起来，或一个可发布的 npm 包 |
| 第 6 周 | 收尾输出：修已知问题、写总结文章、代码整理开源 | 一篇技术文章 + 一个仓库；文章是最好的面试弹药 |

两个执行原则：

- **每周必须有验收物**。没有产出物的周等于没学——"看了很多文档"不产生能力增量。
- **允许第 3 周弃坑**。如果第 3 周发现自己对该场景实在无感，弃坑换场景的成本（3 周）远低于"含恨学完 6 周却再也不碰"的沉没成本。全景图让你弃坑时知道下一站去哪。

### 第三步：把全景图当"索引"而不是"任务清单"

23 个场景的正文展开程度不同：A 族（编辑器家族）在本篇逐场景详解（A1–A5 是全篇最厚的部分）；B–G 族本篇给到"核心技术清单 + 入手路径"的粒度，深扎细节一部分在《react-高阶场景-第二辑.md》，一部分要直接去啃开源项目。把本篇当地图索引：想做什么，先查表定位族群 → 读族群小节建立整体认知 → 进具体场景小节拿入手路径 → 出发。

### 补充：季度规划模板——把"挑 2–3 个场景"落成日历

前文三步法回答了"选什么、怎么深扎、怎么当索引"，但落不到日历上：第二步的 4–6 周节奏表按接近全职的投入设计，在职者每周只有 8–10 小时，一个 ★★★★ 场景实际会摊到 10–12 周——**季度（12–13 周）才是真实的交付单位**。选 OKR 而不是任务清单作为模板，原因只有一个：OKR 强迫把"学过什么"改写成"能做出什么"，这正是本篇"每周必须有验收物"原则的宏观版。

模板五栏，抄进笔记就能用：

| 栏位 | 填写规则 | 反例（不许这么写） |
|---|---|---|
| 目标 O | 一句能力主张："季度末能独立从零做出 X，并讲清每个机制为什么存在" | "深入学习富文本"（学到什么程度？无法验收） |
| KR ×3–4 | 每条 = 可验收物 + 数字；至少 1 条压测数字、1 条对外输出（文章/分享/PR） | "读完 ProseMirror 官方文档"（阅读不是验收物） |
| 周排布 | 把 KR 摊到 13 周，标注依赖顺序——先上游后下游（对照 `02-全景总览.md` 各族的"依赖关系"段） | 13 周平均用力，没有给第 3–4 周"啃硬骨头期"留余量 |
| 弃坑检查点 | 固定写在第 6 周末：本篇第二步"允许第 3 周弃坑"的季度版，做一次中评 | 一路硬扛到第 12 周，才发现兴趣错配 |
| 缓冲 | 默认留 2 周（约 15%）不排任务，吸收加班、需求插队、生病 | 排满 13 周，一个意外全盘崩掉 |

示例一：风口冲浪季（主 F1 流式对话 + 副 G 族）。

| 栏位 | 内容 |
|---|---|
| O | 季度末能独立交付"生产级"流式对话前端：不卡输入框、可中断重发、万级消息不重渲染 |
| KR1 | 流式 Markdown 渲染：未闭合代码块不闪屏（对照 `09-F-AI-原生前端-当下最热-且与你的-Schema-线天然衔接.md` 的 F1.2 验收），中断/重生成/编辑重发状态机全覆盖 |
| KR2 | 长会话压测：1 万消息会话首屏 < 1s、快速滚动无白屏、10 分钟内存平稳——三个数字写进 README |
| KR3 | G 族副线：虚拟滚动 + Cmd+K 两个组件仓库，各配一篇坑笔记 |
| KR4 | 对外输出：一篇"流式渲染三条路与踩坑"文章，或给 AI SDK 类开源项目提一个被合并的 PR |
| 弃坑检查点 | 第 6 周：若增量解析仍讲不明白，降级为"吃透 F1.1–F1.4 + demo"，F1.7 生成式 UI 移到下季 |

示例二：长线筑壁启动季（主 A1 富文本 + 副 B1 预研）。长线场景更要按季切片——"6 个月无正反馈"是弃坑的头号原因，切片就是把正反馈颗粒度从"成品"降到"季度里程碑"：

| 栏位 | 内容 |
|---|---|
| O | 季度末有一个"能用"的 mini 块编辑器：标题/列表/图片/斜杠命令/块拖拽，命令栈完整可撤销 |
| KR1 | 最小内核从零复刻一遍（不用脚手架），能讲清 Schema/State/Transaction/PluginView 四件套 |
| KR2 | 斜杠命令面板 + 块拖拽完整，各配 3 个边界用例（中文输入法、双击选中、跨块拖拽） |
| KR3 | B1 副线：两个 Tab 用 y-websocket 协同同一段纯文本（先不接富文本，只吃透 Y.Doc/awareness） |
| KR4 | 对外输出：一篇"ProseMirror 四件套图解"——教是最快的学，也是长线季度里唯一的正反馈来源 |
| 弃坑检查点 | 第 6 周：若四件套心智模型未建立（标准：能向同事讲清一次 Transaction 的完整生命周期），触发 `11-怎么选-按职业方向匹配.md` 的止损清单评估 |

示例三：稳健转型季（主 G + 副 E1）——最常见的"第一季"。从业务 CRUD 转向场景深扎，最稳的开局不是追风口，而是把底座与一个"任何团队都用得上"的场景练扎实，本季的隐形目标是建立"数字说话"的肌肉记忆：

| 栏位 | 内容 |
|---|---|
| O | 季度末你对"列表为什么会卡"有一套方法论：Profiler 定位 → 分层治理 → 数字验证 |
| KR1 | G 族两件套（虚拟滚动 + 浮层）自研完成，各配坑笔记 |
| KR2 | E1 主线：10 万行表格 DOM 版 vs Canvas 版各一版，Profiler 录屏 + 帧率/内存对比数字 |
| KR3 | 把结论反哺一个真实业务列表，PR 合并进主干 |
| KR4 | 对外输出：一篇"虚拟滚动：原理层 + React 实现层"双笔记账文（`03-React-相关度过滤视图.md` 六步法的第 6 步产物） |
| 弃坑检查点 | 第 6 周：若还没用 Profiler 定位过一次真实的重渲染问题，范围收缩到 KR1+KR2 |

季末做一次季度复盘（30 分钟，与 `12-给-React-开发者的三个-最值钱-建议.md` 的周复盘衔接——周复盘管节奏，季复盘管方向）：

```markdown
# Q_ 复盘
- KR 达成：_ / 4（未达成项归因三选一：知识断层 / 时间不足 / 方向错误）
- 本季最深的一个点：（能对外讲 15 分钟的那个；答不出 = 本季深度不足，下季减宽度）
- 下季唯一变化：（只允许改一个变量：换主场景 / 换副场景 / 调时间预算——同时改两个等于没复盘）
```

两条使用纪律。**其一，KR 的粒度对齐第二步节奏表的"验收物"列**——季度表不替代那张 6 周表，而是它的容器：把每个 KR 按周拆开，就是你已经在用的那张表。**其二，副场景不许升级**：季度中途砍掉副场景、全力保主场景是允许的；反过来把副场景升成第二个主场景，几乎必然两个都烂尾——季度规划的第一价值，就是强制你承认"时间只有这么多"。

### 补充：面试叙事与团队共读——全景图作为"沟通工具"的两种用法

前文三步都是单人学习视角。但全景图还有一层被低估的价值：它是一套**行业术语的坐标系**——面试时帮你把经历翻译成面试官听得懂的深度信号；带团队时帮你把散落的需求翻译成可分工的场景地图。两种用法各给一套可直接照抄的操作法。

**用法一：面试叙事法——用全景图组织"我最难的 X"故事线**。`12-给-React-开发者的三个-最值钱-建议.md` 已给单作品的三段压缩模板（场景识别 → 内核复用 → 量化收益，30 秒电梯版）；这里补 3 分钟深挖版，四段结构：

1. **场景定位**（30 秒）：一句话把项目钉在地图上——"这是 B2 长会话场景的变体，难点不在聊天本身，在万级消息的渲染与会话切换"。定位的价值是瞬间校准面试官预期：他知道接下来听的是"内核级"还是"业务级"的讲述。骨架直接借 `02-全景总览.md` 各族"共同内核"段的分层（如 B 族的连接 → 协议 → 一致性 → 乐观 UI 四层），用它组织讲述顺序。
2. **取舍叙事**（60 秒）：讲"当时有三个选项、为什么选这个"。这是区分度最大的一段——背 API 的人讲不出取舍。素材直接借全景图各场景的选型内容（如 B 族补充一的 LWW/乐观锁/OT/CRDT 决策树）："我们评估过 LWW 和 CRDT，但协同粒度只到字段级且并发极低，LWW + 服务端定序够用，省掉 CRDT 的元数据成本"。
3. **内核复用**（60 秒）：从哪些写过的地方搬了什么——`13-与前两份大纲的衔接-内核复用.md` 的映射就是现成话术；强调"只新写了 WW"，面试官由此推断你的边际成本意识，这比"全部自己实现"加分。
4. **量化结果与遗憾**（30 秒）：数字收尾（没有数字就压测出一个，这是 12 篇的铁律），并主动讲一个没做好的点——"图片消息的动高测量还是全量校正，滚到顶部会抖，正确做法是分级估算"。主动暴露边界比完美叙事更可信，因为它证明你知道下一层在哪。

高频追问的应对同样有套路。被问"为什么不用现成的 XX 库"：用全景图语言回答成本结构——"XX 库解决的是 ★★ 难度层的问题，我们的卡点在 ★★★★ 层的 YY（动高校正/IME/断线合并），库在这一层是黑盒，排查成本高于自研"。被问"如果重做会怎么改"：回到第 2 段的三个选项里挑另一个，讲清什么条件下它更优——取舍能正反讲，才是真懂。

一个完整的示范（B2 长会话变体，约 90 秒，可直接改写成你的版本）：

> 我最难的项目是一个客服工作台的会话模块，本质是 B2 长会话场景的变体——难点不在聊天本身，在三个数字：单会话一万条消息、客服同时开 8 个会话、图片消息占比 40%。
>
> 当时有两个方案：全量交给 react-virtuoso 这类成熟库，或自研动高虚拟化。我们选了自研，因为卡点在动高测量——图片异步加载会持续击穿库的测量缓存，这是 ★★★★ 层的问题，库在这一层是黑盒，改造成本反超自研。
>
> 实现上我复用了两个写过的内核：前缀和管窗口高度（E1 的骨架），乐观 UI 管发送/撤回状态（B 族共同内核的第四层）。真正新写的只有图片行的分级高度估算，两百行以内。
>
> 结果：8 会话同开内存从 1.9GB 降到 600MB，快速滚动白屏率从肉眼可见降为 0。没做好的是向上翻页的锚定偶发抖动，正确做法是 load-more 时冻结滚动位置再补数据——这个我复盘过，写在了博客里。

**用法二：团队共读与内部分享的运营法**。全景图按族群分章、每章自带"共同内核 + 依赖关系"，天然适合当团队教材。共读会的**会议机制**（90 分钟三段制、演示验收、交叉验收、退化信号治理）在 `../react-进阶大纲-复杂场景/18-10-节奏安排-10-周.md` 已写透，直接照用，此处不重复；这里只补全景图特有的三件运营套件：

- **分组认领**：A–G 七族按业务归属认领，不按兴趣轮转——做 IM 的领 B 族、做低代码平台的领 A 族 + D1、做数据产品的领 C 族。只有业务近的族群，分享里"我们业务的映射"那一段才讲得出来，这是共读会不退化成"念文档会"的第一道保险（第二道保险是 18-10 的铁律：没带可演示产物的人不发言）。
- **七族七讲**：一个季度的系列分享排期，两周一讲，每讲 70 分钟固定切分——本族共同内核 20 分钟（02 篇那一段 + 自己的展开）→ 一个场景深挖 30 分钟（挑本族正文中你最吃得透的一个）→ 业务映射 20 分钟（我们产品里哪三个需求是它的变体、当时怎么做的、对照文档差在哪）。第三段是全场的价值来源，允许讲翻车——翻车映射比成功故事更能让团队记住边界。
- **需求映射工作坊**：季度规划时开一次，两小时——把下季度前端需求清单摊开，逐条对照全景图定位"这是哪个场景的变体、难度几星、我们团队有没有人碰过"，输出一张"自研 / 采购 / 绕开"初判表交给技术负责人，判据用 `03-React-相关度过滤视图.md` 新增的团队规模裁剪规则。这是全景图对团队最直接的产出：它把"这个需求为什么难、要几个人几周"从拍脑袋变成查表。

七族七讲要撑过整个季度，需要最小化的角色分工（会议流程仍按 18-10 的机制走）：

| 角色 | 职责 | 轮换 |
|---|---|---|
| 发起人 | 排期、守住"没产物不发言"铁律、维护需求映射表 | 固定一人（通常是最先读完全景图的你） |
| 当期 owner | 本族三段分享、准备演示产物、会后归档材料 | 每讲轮换 |
| 评审人 | 拿验收清单交叉验收 owner 的演示（不许自己验自己） | 非 owner 轮流 |

角色表的意图只有一个：把共读从"发起人的热情"变成"团队的结构"——热情会消退，结构会留下。发起人的隐性收益也值得说透：你会自然成为团队"场景问题"的第一求助对象，这正是技术影响力的起点。

两种用法的共性一句话：**单人学习时全景图是地图，对外沟通时它是术语表和坐标系**——能把任何一段经历、任何一个需求钉进网格里的人，在面试官和技术负责人眼里就是"有体系的人"。

### 补充：需求驱动倒查——接到陌生需求后的 30 分钟动线

前文三步法、季度规划、面试叙事都是**计划内**用法：你主动挑场景、排日历。但在职者最高频的其实是**计划外**场景：需求评审会上被点名"这个前端能不能做、要多久"，或者老板丢来一个你从没做过的东西。这一节给一条 30 分钟动线，把散在四份文档里的既有工具串成流水线。先说清楚它的定位：**这条动线不产生任何新知识，只做编排**——每一站都指向一个已经写透的工具，工具本身的细节回原文读，本节只解决"先查哪张表、后过哪道闸"。

动线总表（时间盒合计 30 分钟，超时说明该需求值得正式立项而不是倒查）：

| 步骤 | 时间盒 | 用什么工具（都在已有文档里） | 该步产出 |
|---|---|---|---|
| 1 拆解 | 0–5 分钟 | `../react-学习大纲/38-进阶篇-复杂业务场景.md` 的五步拆解法与拆解单 | 一张子问题清单（数据/渲染/交互/性能四个轴） |
| 2 定位 | 5–10 分钟 | `03-React-相关度过滤视图.md` 的翻译器表 + `02-全景总览.md` 的深读索引矩阵 | 每个子问题钉到一个场景；钉不到的标红 |
| 3 算账 | 10–15 分钟 | `13-与前两份大纲的衔接-内核复用.md` 的速查表（复用率/必须新学两列） | "必须新学"清单与总量估算 |
| 4 决策 | 15–25 分钟 | `03-React-相关度过滤视图.md` 的立项五问 + 四档团队策略矩阵 | 自研 / 二开 / 采购 / 绕开的初判与理由 |
| 5 产出 | 25–30 分钟 | 下面的半页纸模板 | 一页可进评审记录的答复 |

时间盒为什么这样切：前三步全是**查表**（拆解有拆解单、定位有两张矩阵、算账有速查表），所以各 5 分钟足够；第 4 步是动线里唯一需要**真思考**的环节（五问的每一条都要对着自己团队的实情作答），给它两倍时间；第 5 步只是誊写。如果你发现自己在第 1–3 步耗时超倍，多半是把"查表"做成了"重读文档"——倒查法假设你已经读过全景图正文，表格对你才有索引意义。

逐步展开，每步只讲判断点：

- **第 1 步拆解**：照抄学习大纲 38 的五步法（数据长什么样 / 渲染长什么样 / 交互长什么样 / 性能边界在哪），唯一升级点在它的第 5 问——那边问"映射回学习大纲哪一节"，全景图用户把映射目标换成第 2 步的场景矩阵。
- **第 2 步定位**：先查 03 翻译器表（业务原话 → 场景），查不到的子问题再用 02 深读索引矩阵反查（场景 → 主题 → 文件）。关键判断点：**映射不到任何场景的子问题单独标红**——标红项才是这个需求的真实增量，也是排期风险的全部来源；全部映射上了的需求，本质是"已知积木的拼装"，报价可以激进。
- **第 3 步算账**：只看 13 速查表两列——预估复用决定"便宜的部分"，必须新学决定"贵的部分"。排期永远按必须新学估，不按场景总量估（13 的原话）。
- **第 4 步决策**：过 03 的立项五问（三年后谁维护 / 缩编退化 / 比价 / 隐藏成本 / 两本账），再按团队规模行查四档策略矩阵。
- **第 5 步产出**：填下面的半页纸，进评审记录或甩进需求群，格式让人挑不出"拍脑袋"。

```markdown
## [需求名] 倒查单（30 分钟版）
- 场景定位：主体 = XX 场景的变体（难度 ★X），附属 = YY、ZZ
- 复用账：可复用内核 A/B/C；必须新学 = ...（估 X 人周）
- 标红项（映射不到的子问题）：1. ... 2. ...
- 策略初判：自研 / 二开（基于什么开源）/ 采购（对照过哪家）/ 绕开（改方案的代价）
- 答复口径：能做，X 人周，前提是 ...；或：建议不做，因为 ...
```

一个完整走查示例（30 秒版）。需求原话："运营想要一个可配置的告警规则界面，让客户自己配'当 XX 指标连续 3 次超过阈值就通知谁'"。

| 步骤 | 这个需求上的动作 |
|---|---|
| 拆解 | 数据 = 条件树（JSON）；渲染 = 递归树表单；交互 = 增删条件组 + 试运行；性能 = 条件数 <100，无压力 |
| 定位 | 翻译器表直接命中"要让客户自己配规则/告警"→ 查询构建器（`../react-高阶场景-第二辑/04-3-动态查询构建器-规则引擎-UI-全量展开.md`），试运行面板就是它的 3-7 节 |
| 算账 | 递归渲染器 + Setter + json-logic 全是进阶大纲已写内核，复用约七成；必须新学只剩"通知渠道的字段元数据" |
| 决策 | 二开边界清晰，无需自研规则引擎；立项五问全过（维护者就是本团队） |
| 答复 | 能做，2 人周，前提是后端确认 json-logic 规则可执行 |

这个需求从"没做过"变成"查表 + 一个人周的真实增量"——倒查法的全部价值就是**把陌生感从报价里挤出去**。

也有**不用倒查**的两类情况，识别它们同样省时间：需求明显落在你已深耕的场景内（直接报价，倒查是对自己经验的侮辱）；或者需求小到不含任何场景难度（改个样式、加个字段——做完就走，别给它三十分钟）。倒查法是为"陌生且复杂度存疑"的需求设计的，把简单需求也过一遍流程，是它的第二种滥用。

两个最常见的翻车形态，先打预防针：**其一，把倒查单当技术方案**——它是"能不能做、值不值得做"的评审答复，不是设计文档；立项之后该画的架构图、该写的方案一样不能少，倒查单里"必须新学"的每一项都应转化成方案里的风险章节。**其二，查了不记**——口头倒查完就散，下次同类需求再查一遍。倒查单值得归档：同一个团队半年攒下十几张倒查单，就是你们团队私有的"需求 → 场景"翻译表，比任何通用矩阵都准（它带着你们业务的标红项）。

最后处理动线与季度规划的冲突——这是倒查法最容易翻车的地方。插队需求带来的学习点，先问它与你的季度主线（本篇季度规划模板的 O/KR）是否相关，按两种情况分流：

- **无关的只做交付、不加深扎**：用倒查单完成工作，别顺手启动新场景——那等于季度中途给副场景升级，是季度模板明令禁止的动作。省下的警惕就是你季度主线按时交付的余量。
- **正命中主线的按 KR 吸收**：真实业务是比 demo 好十倍的练手场——把它写进当季 KR，同时砍掉一个等效的自拟任务，总量守恒。这是插队需求唯一"赚到了"的形态。

一条反提醒收尾：倒查法最容易被滥用成"什么需求都敢接"。30 分钟动线的产出如果是"必须新学 > 2 人周"或标红项超过两个，正确答案常常是 03 四档里的"绕开"（改产品方案回避）或直接说"不做"。**敢于把"不做"写进倒查单，才是这条动线的目的**——全景图给你的不只是接活的底气，还有拒绝的依据。
