## 解决实际编码问题的工作流

遇到问题时按此顺序：

1. **读警告**：控制台/react-devtools 的 warning 往往直接指出原因
2. **最小复现**：新开一个文件，把问题缩到 20 行以内
3. **分层定位**：渲染层（值对不对）→ 时机层（effect/事件）→ 环境层（构建/缓存）
4. **查权威来源**：react.dev 搜索 → 该库 GitHub issues → Release Notes（升级踩坑）
5. **沉淀**：把解法记进自己的"React 踩坑笔记"，按场景归档

五步逐条展开成可执行的操作：

**第 1 步：读警告。** 操作：打开浏览器控制台（配合 React DevTools 的警告面板），把 warning 的关键句子**原文**复制出来，先当搜索词。要建立的心态是：React 的 warning 不是噪音，而是免费诊断书——每条警告都精确对应一类已知错误模式。对照速查：`Each child in a list should have a unique "key"` → 列表身份错乱（阶段 10 第 2 条）；`Can't perform a React state update on an unmounted component` → 卸载后 setState，effect 没清理异步回调；`Warning: An update ... not wrapped in act` → 测试里更新没进 act 边界（阶段 8 第 4 条）；`The final argument passed to useEffect changed size between renders` → 依赖数组长度变了。忽略警告的代价是：真正的信号混在噪音里被一起扔掉。

**第 2 步：最小复现。** 操作流程：(a) 新建 `src/debug/Bug.tsx`，把可疑组件**连同最少的数据**复制进来；(b) 从路由上只挂载这一个文件；(c) 循环做两件事——删掉一段代码 → 问题还在？继续删；问题消失？恢复刚才删的那段，往更深处删。20 行以内还复现不了时，结论同样宝贵：**问题不在组件本身，而在父级传参、Provider、路由层或构建配置**——排查方向立刻从"读组件代码"切换到"打印输入与检查环境"。

**第 3 步：分层定位。** 三层从便宜到贵，顺序不能反：

- **渲染层（值对不对）**：DevTools 选中组件看 props/state 的实际值。典型命中：传了 `0`/空数组/`NaN`、`&&` 短路成了 `0`、对象每次渲染都是新引用。
- **时机层（effect/事件）**：值都对，但出现的时机不对。命中竞态、闭包旧值、双执行（StrictMode 开发期故意双调用 effect 是特性不是 bug）、事件没触发（被 `preventDefault`/`stopPropagation`/条件卸载吞了）。
- **环境层（构建/缓存）**：代码"看起来对"但运行不对。命中依赖版本（升级后 API 变了）、构建缓存（`rm -rf node_modules` 重装试试）、浏览器缓存与 Service Worker、Next.js 的缓存分层（阶段 9 第 4 条那张表）。

**第 4 步：查权威来源。** 严格按顺序：react.dev 站内搜索（中文版可用，覆盖 90% 概念问题）→ 出问题的库的 GitHub Issues（搜**报错原文**，不是搜你的猜测）→ Release Notes（凡"升级后突然坏"的问题，先翻最近一版 changelog 的 Breaking Changes）。给自己设个止损：任何一条搜索链路超过 20 分钟没进展，就换下一条，不要在同一个帖子里面细抠。

**第 5 步：沉淀。** 格式建议固定五栏：场景（一句话）/ 症状（报错原文或现象）/ 根因（一句话机制）/ 修法（diff 或关键行）/ 参考链接。按场景归档（表单、请求、路由、SSR……）。判断一条记录"沉淀成功"的标准：三个月后自己只看前两栏就能想起修法。本文档每个知识点末尾的"常见坑（症状→根因→修法）"就是这个格式的公共版——你的笔记是它的私有版。

### 补充：生产环境问题专项工作流

上面五步的前提是"问题在你手里能复现"。线上问题的三个前提全部反着来：**不能复现**（用户的环境你拿不到）、**不能打断点**（不能在用户浏览器里暂停）、**时间倒流不了**（发生的那一刻已经过去）。所以线上问题的流程是另一套，三条铁律先行：**先止血再定位**（每分钟都在丢用户的钱）、**一切靠上报**（阶段 8 第 7 条的 Sentry 体系是唯一的信息源）、**版本是最强变量**（九成线上问题是"上一个版本还好好的"）。

**四步流程（按序执行，每步有明确出口）。**

**第 1 步：确认影响面（5 分钟内）。** 打开 Sentry 的 issue 看 four 个数字：影响用户数、错误次数的突增时间点、对应的 release 版本、浏览器/设备分布。两个决定性判断：突增时间点是否恰好对准某次部署（对准 → 直奔第 2 步止血，定位交给第 3 步）；是否集中在某一款浏览器或某类老设备（集中 → 兼容性问题方向，Polyfill/语法目标，去第 3 步看构建配置 diff）。

**第 2 步：止血（用户不等你定位）。** 三种手段按代价从小到大：功能开关关闭新路径（有 feature flag 就秒级止血，这也是"高危新功能必须挂开关上线"的原因）；回滚到上一个 release（Vercel 上一键回滚，数据库有迁移的要先确认兼容）；降级（错误边界兜底 + 关闭非核心模块）。止血后必须在事故记录里写明"止血用了什么、根因未明、待定位"——止血不是结束。

**第 3 步：定位。** 工具链按序：sourcemap 还原堆栈（配置在阶段 8 第 7 条，堆栈能从 `main-B3xK9.js:2:84512` 还原到 `src/api.ts:42` 是一切定位的前提）；Sentry 的会话录像（replay）回看用户操作序列；仍不够就做**版本 diff**——两个 release 之间 `git log` + 变更文件清单，改动面通常很小；怀疑引入点更早，用 `git bisect` 让 git 替你二分历史提交（操作见阶段 6 的调试方法论）。定位产出物是一句话根因，格式与第 5 步沉淀的"根因"栏相同。

**第 4 步：补防（不做这步，同类问题三个月后重来）。** 三件事缺一不可：**先写复现测试再修复**（复现测试红了 → 修复 → 绿，这条测试从此进回归套件——阶段 8 的测行为范式直接搬用）；修复上线后确认 Sentry 上该 issue 趋零；检查同类模式是否还有（grep 同款写法，一次修一类而不是一处）。

**上报信息最小集（review 上报代码时逐项核对）。** userId（定位到人可查操作日志）、release 版本（没有它 diff 无从谈起）、route（哪个页面）、UA 与屏幕（兼容性判断）、错误 digest/id（App Router 下 error.tsx 的 digest 能对上服务端日志，见阶段 9 补充节）、发生前的最后三个用户事件（breadcrumb）。少于这六项的上报，第 3 步的效率直接减半。

**本地无法复现的三板斧。** 其一，**造生产 shape 的数据**：拉一份脱敏的真实数据（或按真实接口响应手造），九成"本地好的线上坏"是数据分支——某个字段为 null、数组为空、层级深一层。其二，**对齐环境变量**：比对线上与本地 `.env` 差异，API 基址、灰度开关、特性开关常常不同。其三，**对齐构建产物**：用 `npm run build && npm run preview` 跑生产构建复现（开发构建好而生产坏的经典来源：压缩触发的 bug、`import.meta.env` 替换、StrictMode 双执行的差异）。

**两个高频坑。** 其一，"让用户清缓存就好了"——这不神秘：Service Worker 缓存的旧资源与新后端/新前端不匹配（环境层的缓存问题，见第 3 步分层定位）；根治靠 SW 版本更新策略，而不是教用户清缓存。其二，止血后忘记摘掉功能开关：三周后新功能"莫名失效"，排查半天发现开关还关着——止血动作必须登记到事故记录并带"待恢复"标记。

**低频复现的加练：只影响 1% 灰度用户的问题。** 影响面小不等于可以慢：把 Sentry 的采样对准该版本（`tracesSampleRate` 临时调高、错误会话 100% 录像，配置见阶段 8 第 7 条），再从上报最小集里找共性维度（同一机型？同一入口路由？同一租户？）——十份错误报告里的共同点，往往就是复现条件。

**事故处理记录模板（处理完 24 小时内填写，进踩坑笔记同一归档体系）。**

```markdown
## 事故：[一句话标题]（[日期]）
- 影响面：[用户数/请求数/时段]，版本 [release]，浏览器分布 [如 Safari 16 占 90%]
- 止血：[方式 + 时间点]，开关待恢复：[是/否，flag 名]
- 根因：[一句话机制，格式同第 5 步沉淀的"根因"栏]
- 定位路径：[sourcemap / replay / 版本 diff / bisect 中哪条命中]
- 补防：[复现测试的文件名；同类扫描的结论]
```

**预防性建设清单（不出事时做的三件事，出事时每件都在救你）。**

1. **高危功能挂开关上线**：新支付链路、新渲染逻辑默认 flag 关闭，灰度放量——第 2 步的止血速度从"分钟级回滚"变成"秒级关开关"。
2. **告警阈值而不是报表**：Sentry 配"新错误类型出现即告警"（first-seen issue），而不是每天看报表——第 1 步的"确认影响面"能提前到用户投诉之前。
3. **每个 release 可回滚**：数据库迁移先写"兼容旧代码"的版本（加列不删列、双写过渡），保证应用层永远能回退——回滚是止血手段里破坏面最小的一种，前提是数据结构允许。

**与本地五步工作流的关系一句话**：本地五步（本文上半部分）回答"怎么找到根因"，生产四步回答"在不能复现的约束下怎么行动"——第 3 步定位一旦拿到可复现路径（三板斧成功），就切回本地五步的循环继续；两套流程在"沉淀"处汇合，用同一份五栏笔记归档。
