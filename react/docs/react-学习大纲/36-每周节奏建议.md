## 每周节奏建议

- 60% 时间写代码（场景 demo / 项目）
- 20% 时间读官方文档对应章节
- 20% 时间复盘重构（把前一天写的烂代码改好，比多写新代码更有价值）

按每天 1–2 小时展开成落地方法：

**60% 写代码（约每天 45–70 分钟）。** 关键是"提前列清单、当天不开天窗"：每周日花 10 分钟把当周要做的 demo 抄成任务清单（每条对应大纲里一个场景，如"阶段 7 第 3 条：泛型 Select"），每天完成 1–2 条、勾掉。每个 demo 严格走三步——先自己写（不看任何参考）、再对照官方文档修正、最后**故意改坏一次**观察症状（比如删掉 key、去掉依赖数组）。故意制造 bug 的 10 分钟，比多看两遍正确代码的记忆深一个量级。

**20% 读文档（约每天 15–25 分钟）。** 不要"通读官方文档"，要**带着当天的代码读**：今天写了受控表单，晚上就读 react.dev 的 `<input>` 与"表单"章节对应小节。判断读到位的标准：能在文档里找到"你今天写的那行代码"对应的原则或反例。每周留一次 30 分钟的"补课位"，把这周遇到的警告逐条去文档里查到出处。

**20% 复盘重构（约每天 15–25 分钟）。** 固定动作：第二天开始新任务前，**先重构昨天的代码**——用今天新学的标准（比如今天学了类型收窄，回去给昨天的请求状态改成判别联合；学了测行为不测实现，回去改昨天的测试断言）。配合两件小工具：一个 `NOTES.md` 踩坑笔记（按上面工作流第 5 步的格式记），一个 git 习惯——每个 demo 单独 commit，commit message 写"当时为什么这么改"。三个月后回看这些 commit，就是一份私有的成长曲线图。

### 补充：中断与重启——断档恢复与防弃坑

60/20/20 描述的是理想周。真实学习里最大的敌人不是难度，是**中断**：一次加班、一场旅行、一个无聊的周末，两周没碰代码后再回来，"之前学到哪了"都想不起来，弃坑大多发生在这个重启失败的瞬间。这一节给恢复流程和防弃坑机制。

**断档三档恢复法（按断的时间长短选档，从轻到重）。**

- **断 1–3 天（加班/生病）**：直接重启，不补课。回到断点的前一个 demo，**重敲一遍**（不是重读）——手指记忆比阅读记忆可靠，20 分钟后状态就回来了。切忌"断三天补三天"，那会制造新的拖延。
- **断 1–2 周（假期/项目突击）**：花一个"重启日"做三件事：翻 `NOTES.md` 最近五条坑、把断点所在阶段的产出项目跑起来（`npm run dev` 点一遍功能）、重做该阶段清单里**最后一个完成的** demo。三件事的共同点：只用旧知识制造"我还会"的手感，不碰新内容。
- **断 1 个月以上**：不要按断点硬续。做一次**降级重入**：回到当前阶段开头的第一个场景，快速过一遍（写过的可以抄自己的旧代码再改）；过起来毫无障碍就跳到断点，卡壳严重就从上一阶段的产出项目验收清单（33 的项目线）走一遍查漏。宁可重叠一周，不要悬空硬续——每个悬空的知识点都会在后面收利息。

**存档点机制（让重启变便宜的关键）。** 每完成大纲的一个场景，在 `NOTES.md` 里记一行固定格式的存档：`[日期] 完成场景 X-Y；下一个是 X-Z；当前项目卡在 ___`。重启时第一件事是读最近三条存档，而不是翻代码——存档点写得越勤，重启成本越低。git 的 commit 历史是第二套存档（"每个 demo 单独 commit"的又一个理由）。

**每周复盘五问（周日晚 10 分钟，固定模板）。**

1. 本周勾掉了哪些清单项？没勾的卡在哪一步？
2. 本周写的代码里，明天会用什么新标准重构它？（对应 20% 复盘位）
3. 本周遇到的最难一个坑，沉淀进 NOTES 了吗？（没沉淀的当场补）
4. 下周清单列好了吗？（只列场景编号，周日列好，工作日不开天窗）
5. 节奏健康吗？——连续三天没碰代码 = 触发上面的恢复流程。

**防弃坑三招（机制而非意志力）。**

- **最小日剂量**：状态最差的日子，保底动作是"读一节文档 + 敲其中一段代码"（15 分钟）。 streak 不中断的意义不在这一天学到多少，在"身份没断"——我还是在学习的人。
- **难度熔断**：同一个问题卡超过两天，强制降级——跳过它做下一个场景，在 NOTES 记 `[TODO] 回来补：场景 X-Y 卡在 ___`。卡死最消耗动机，带着 TODO 前进比原地硬耗好。
- **进度可视**：一张勾选清单贴在每天都看得见的地方（哪怕就是 33 项目线那张表打印出来）。学习动力的最大来源是"可见的进展"，弃坑的前兆是"感觉学了又好像什么都没学"——可视清单是对这种错觉的直接反驳。

**存档点行的固定格式（NOTES.md 顶部，倒序追加）。**

```markdown
## 进度存档
- [11-05] 完成 7-3 泛型组件；下一个：7-4 ReactNode vs FC；项目卡在 Select 的 satisfies 用例
- [11-03] 完成 7-2 状态收窄；下一个：7-3；无阻塞
- [10-30] Lv1 翻新（Zustand）通过验收；下一个：7-2；无阻塞
```

三栏口径：`完成什么 / 下一个是哪节 / 当前卡在哪`。重启日的第一个动作是读这三行——30 秒接上下文，比翻 git log 或代码快一个量级。"卡在哪"一栏尤其重要：它就是难度熔断跳过的问题清单，每两周扫一遍，能补的回头补，确认不重要的划掉。

**断档信号自查表（每周复盘第 5 问的展开）。**

| 信号 | 判定 | 动作 |
|---|---|---|
| 连续 1–2 天没碰代码 | 正常波动 | 直接重启，重敲上一个 demo |
| 连续 3–7 天没碰 | 触发恢复流程 | 断 1–2 周档：重启日三件事 |
| 超过 2 周 | 危险区 | 断 1 月档：降级重入 |
| 同一场景卡超过 2 天 | 难度熔断 | 跳过 + 记 TODO，做下一场景 |
| 周清单勾掉不到一半 | 节奏过载 | 下周清单砍半，先保 streak |

这张表的用途是把"要不要休息一下"的情绪决策换成机械决策——出现信号就执行动作，不和自己辩论。弃坑几乎都发生在"再想想"的犹豫期，而不是疲劳期。
