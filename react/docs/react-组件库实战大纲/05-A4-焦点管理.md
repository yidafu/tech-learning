## A4. 焦点管理

- **焦点陷阱**（Modal 内 Tab 循环：可聚焦元素查询 + wraparound + Shift+Tab）
- 打开时记住触发元素，关闭时焦点还回
- **roving tabindex**（Tabs/Radio 组的键盘模型：只有一个 tab stop，方向键移动）
- `:focus-visible` 与 `:focus` 样式区分（键盘用户才显示焦点圈）

### A4.1 为什么焦点是弹层组件的一等公民

Tab 键是键盘用户与读屏用户的"光标"。弹层打开时若什么都不做，焦点还留在触发按钮上，读屏会继续念按钮后面的页面内容——对话框对他们是隐形的。所以 dialog 模式的硬性要求（A5 的 APG 表也这么写）：**打开即把焦点移入弹层，存续期间焦点出不去（陷阱），关闭时把焦点还回触发元素**。这三件事分别对应本节三个实现；做错任何一个，可访问性审计（axe/Storybook a11y 插件）都会亮红。

### A4.2 焦点陷阱完整实现

机制分步：

1. **可聚焦元素查询**：用一组选择器穷举"默认可聚焦"元素（a[href]、button、input、select、textarea、iframe、contenteditable）加上"`tabindex` 非 -1"的自定义元素；
2. **过滤不可见项**：`display: none` 的元素仍会被 `querySelectorAll` 查到，但它不可聚焦——用 `getClientRects().length > 0` 过滤（有布局盒子才算活着）；
3. **Tab 拦截**：在容器上监听 keydown，捕获 Tab 后不让默认行为发生（`preventDefault`），改为手动 `focus()` 目标元素；
4. **wraparound**：焦点在最后一项上按 Tab → 跳回第一项；在第一项上按 Shift+Tab → 跳到最后一项；焦点不在容器内（被脚本移走了）→ 拉回第一/最后一项。

```tsx
// useFocusTrap.ts
import * as React from 'react';

/** 可聚焦元素查询选择器：默认可聚焦元素 + tabindex 正值/0 的自定义元素 */
const FOCUSABLE_SELECTOR = [
  'a[href]:not([disabled])',
  'button:not([disabled])',
  'input:not([disabled]):not([type="hidden"])',
  'select:not([disabled])',
  'textarea:not([disabled])',
  'iframe',
  '[contenteditable="true"]',
  '[tabindex]:not([tabindex="-1"])',
].join(', ');

function getFocusable(container: HTMLElement): HTMLElement[] {
  return Array.from(container.querySelectorAll<HTMLElement>(FOCUSABLE_SELECTOR)).filter(
    (el) => el.getClientRects().length > 0 // 过滤 display:none / 隐藏祖先里的"假可聚焦"
  );
}

export function useFocusTrap(active: boolean) {
  const containerRef = React.useRef<HTMLDivElement>(null);

  React.useEffect(() => {
    if (!active) return;
    const container = containerRef.current;
    if (!container) return;

    // 打开即聚焦：优先开发者指定的元素（data-autofocus），否则第一个可聚焦元素
    const initial =
      container.querySelector<HTMLElement>('[data-autofocus]') ?? getFocusable(container)[0];
    initial?.focus();

    const onKeyDown = (e: KeyboardEvent) => {
      if (e.key !== 'Tab') return;
      const focusable = getFocusable(container); // 每次现查：内容可能刚渲染/刚卸载
      if (focusable.length === 0) {
        e.preventDefault(); // 容器内没有可聚焦元素：吞掉 Tab，别让焦点逃逸
        return;
      }
      const first = focusable[0];
      const last = focusable[focusable.length - 1];
      const current = document.activeElement;

      if (e.shiftKey) {
        // Shift+Tab：第一项上按 → 回到最后（循环边界）
        if (current === first || !container.contains(current)) {
          e.preventDefault();
          last.focus();
        }
      } else {
        // Tab：最后一项上按 → 回到第一（wraparound）
        if (current === last || !container.contains(current)) {
          e.preventDefault();
          first.focus();
        }
      }
    };

    container.addEventListener('keydown', onKeyDown);
    return () => container.removeEventListener('keydown', onKeyDown);
  }, [active]);

  return containerRef;
}
```

放进 Modal（同时把 A2/A3 的能力拼上）：

```tsx
// TrapModal.tsx
import * as React from 'react';
import { useFocusTrap } from './useFocusTrap';
import { useFocusReturn } from './useFocusReturn';
import { useMountTransition } from './useMountTransition';

export function TrapModal({
  open,
  onClose,
  children,
}: {
  open: boolean;
  onClose: () => void;
  children: React.ReactNode;
}) {
  const trapRef = useFocusTrap(open);       // 焦点陷阱
  useFocusReturn(open);                     // 打开记住触发元素、关闭还回（A4.3）
  const { mounted } = useMountTransition(open, 200); // 退出动画（A3）

  React.useEffect(() => {
    if (!open) return;
    const onKey = (e: KeyboardEvent) => {
      if (e.key === 'Escape') onClose();    // Esc 关闭（dialog 模式标配，A5）
    };
    document.addEventListener('keydown', onKey);
    return () => document.removeEventListener('keydown', onKey);
  }, [open, onClose]);

  if (!mounted) return null;
  return (
    <div ref={trapRef} role="dialog" aria-modal="true" style={{ position: 'fixed', inset: 0 }}>
      {children}
      <button onClick={onClose}>关闭</button>
    </div>
  );
}
```

### A4.3 打开记住触发元素，关闭还回

```tsx
// useFocusReturn.ts
import * as React from 'react';

/** active 变 true 的那一刻记住当前焦点元素；变 false（或组件卸载）时把焦点还回去 */
export function useFocusReturn(active: boolean) {
  const triggerRef = React.useRef<HTMLElement | null>(null);

  React.useEffect(() => {
    if (!active) return;
    triggerRef.current =
      document.activeElement instanceof HTMLElement ? document.activeElement : null;
    return () => {
      const el = triggerRef.current;
      // 判活：关闭前触发元素可能已随列表一起卸载（如表格行里的按钮），
      // 对已断开的节点 focus() 无效，焦点会丢在 body 上——这是可接受的下线
      if (el && el.isConnected) el.focus();
    };
  }, [active]);
}
```

两个细节：为什么在 **effect** 里记而不是渲染期——effect 时机是"打开这个提交已上屏"，此刻 `document.activeElement` 正是触发元素；渲染期记可能早于浏览器的焦点移动。为什么 `cleanup` 里还——`active` 变 false 或组件直接卸载两种路径都走 cleanup，统一覆盖。

### A4.4 roving tabindex 完整实现

**问题**：Tabs/Radio 组/菜单有 N 个同类项。如果每项都 `tabIndex: 0`，键盘用户要按 12 次 Tab 才能穿过 12 个 tab；如果都 -1，又完全到不了。APG 的解法是 **roving tabindex（游动制表位）**：**整组只有一个 tab stop（当前活动项），Tab 进出组件只停一次；组内导航用方向键**，方向键同时移动焦点和"游标"（tabIndex 0 的那项）。

```tsx
// useRovingIndex.ts
import * as React from 'react';

export interface RovingOptions {
  count: number;
  /** 方向：决定哪些方向键生效；'both' 用于菜单这类两轴都要的场景 */
  orientation?: 'horizontal' | 'vertical' | 'both';
  /** 到边界是否回绕（Tabs/Radio 组默认回绕） */
  loop?: boolean;
}

/**
 * roving tabindex：activeIndex 项 tabIndex=0（唯一 tab stop），其余 -1；
 * 方向键移动 activeIndex 并真实 focus 新项。
 * "选中"语义留给调用方：Tabs 把 activeIndex 当选中；Radio 把 activeIndex 当 checked。
 */
export function useRovingIndex({
  count,
  orientation = 'horizontal',
  loop = true,
}: RovingOptions) {
  const [activeIndex, setActiveIndex] = React.useState(0);
  const itemRefs = React.useRef<Array<HTMLElement | null>>([]);
  const activeIndexRef = React.useRef(0);
  activeIndexRef.current = activeIndex; // keydown 里要读最新索引，不吃闭包旧值

  const move = React.useCallback(
    (index: number) => {
      const next = loop
        ? ((index % count) + count) % count        // -1 → count-1，count → 0：循环边界
        : Math.min(count - 1, Math.max(0, index)); // 不回绕：钳在边界
      setActiveIndex(next);
      itemRefs.current[next]?.focus();             // tabIndex 变化之外，焦点必须真的移过去
    },
    [count, loop]
  );

  const handleKeyDown = React.useCallback(
    (e: React.KeyboardEvent) => {
      const mainNext = orientation === 'vertical' ? 'ArrowDown' : 'ArrowRight';
      const mainPrev = orientation === 'vertical' ? 'ArrowUp' : 'ArrowLeft';
      // 'both'（菜单类）：另一对方向键也映射到前/后
      const isNext =
        e.key === mainNext || (orientation === 'both' && e.key === 'ArrowDown');
      const isPrev =
        e.key === mainPrev || (orientation === 'both' && e.key === 'ArrowUp');

      if (isNext) { e.preventDefault(); move(activeIndexRef.current + 1); return; }
      if (isPrev) { e.preventDefault(); move(activeIndexRef.current - 1); return; }
      if (e.key === 'Home') { e.preventDefault(); move(0); return; }        // 组首
      if (e.key === 'End')  { e.preventDefault(); move(count - 1); return; } // 组尾
    },
    [orientation, move, count]
  );

  /** 每一项展开：唯一 tab stop 由这个 tabIndex 计算保证 */
  const getItemProps = (index: number) => ({
    ref: (el: HTMLElement | null) => { itemRefs.current[index] = el; },
    tabIndex: index === activeIndex ? 0 : -1,
  });

  return { activeIndex, setActiveIndex, move, handleKeyDown, getItemProps };
}
```

**Tabs 消费方**（横向、方向键即选中——APG 的"selection follows focus"自动激活模式）：

```tsx
// Tabs.tsx
import * as React from 'react';
import { useRovingIndex } from './useRovingIndex';

export interface TabItem { value: string; label: string; content: React.ReactNode }

export function Tabs({ items }: { items: TabItem[] }) {
  const { activeIndex, setActiveIndex, handleKeyDown, getItemProps } = useRovingIndex({
    count: items.length,
    orientation: 'horizontal', // Tab 条横向：左右键
  });
  const active = items[activeIndex];

  return (
    <div>
      <div role="tablist" aria-orientation="horizontal" onKeyDown={handleKeyDown}>
        {items.map((item, i) => (
          <button
            key={item.value}
            type="button"
            role="tab"
            id={`tab-${item.value}`}              // 与面板的 aria-labelledby 互指
            aria-selected={i === activeIndex}
            aria-controls={`panel-${item.value}`} // 声明"我控制哪个面板"
            onClick={() => setActiveIndex(i)}     // 鼠标点击也要同步游标
            {...getItemProps(i)}                  // ref 注册 + tabIndex 0/-1
          >
            {item.label}
          </button>
        ))}
      </div>
      <div
        role="tabpanel"
        id={`panel-${active.value}`}
        aria-labelledby={`tab-${active.value}`}
        tabIndex={0} // 面板本身可 Tab 进入：Tab 键离开 tablist 后落进面板
      >
        {active.content}
      </div>
    </div>
  );
}
```

**RadioGroup 消费方**（纵向、方向键移动即选中——radio 的 APG 语义，与 Tabs 的差别就在这一行）：

```tsx
// RadioGroup.tsx
import * as React from 'react';
import { useRovingIndex } from './useRovingIndex';
import { useEffect, useRef } from 'react';
import { useControllableState } from './useControllableState';

export interface RadioOption<T extends string> { value: T; label: string }

export function RadioGroup<T extends string>({
  name,
  options,
  value,
  defaultValue,
  onChange,
}: {
  name: string;
  options: RadioOption<T>[];
  value?: T;
  defaultValue?: T;
  onChange?: (value: T) => void;
}) {
  // 选中值是双模式的（复用 A1）；键盘游标（activeIndex）是另一个独立状态
  const [selected, setSelected] = useControllableState<T>({ value, defaultValue, onChange });
  const { activeIndex, move, handleKeyDown, getItemProps } = useRovingIndex({
    count: options.length,
    orientation: 'vertical', // 单选组常纵向：上下键
  });

  // "移动即选中"的正确实现：handleKeyDown 内部的 move 是 setState，
  // 本次 onKeyDown 闭包里的 activeIndex 仍是旧值（直接读会滞后一拍）。
  // 所以这里只标记"这次移动来自键盘"，等游标真正变化后在 effect 里同步选中。
  const movedByKeyboard = useRef(false);
  useEffect(() => {
    if (!movedByKeyboard.current) return;
    movedByKeyboard.current = false;
    const current = options[activeIndex];
    if (current && selected !== current.value) setSelected(current.value);
    // eslint-disable-next-line react-hooks/exhaustive-deps -- 只随游标移动同步
  }, [activeIndex]);

  return (
    <div
      role="radiogroup"
      onKeyDown={(e) => {
        handleKeyDown(e);
        // 方向键被消费（defaultPrevented）说明游标动了：radio 语义要求"移动即选中"。
        // 不要在这里读 activeIndex——那是本次渲染的旧闭包值，新游标要下一轮渲染才到达
        if (e.defaultPrevented) movedByKeyboard.current = true;
      }}
    >
      {options.map((opt, i) => (
        <label key={opt.value}>
          <input
            type="radio"
            name={name}
            checked={selected === opt.value}
            onChange={() => {
              move(i);            // 鼠标点选也要把游标（tab stop）搬过来
              setSelected(opt.value);
            }}
            {...getItemProps(i)}  // 原生 radio + 同 name 本来就有方向键行为，
                                 // 但 tabIndex 被我们接管后，行为也必须由我们接管
          />
          {opt.label}
        </label>
      ))}
    </div>
  );
}
```

注意上面 RadioGroup 的一个时序坑（也是 roving tabindex 组件的通病）：`onKeyDown` 里不能直接读 `activeIndex` 来做"移动即选中"——`handleKeyDown` 内部的 `move` 是 `setState`，本次事件闭包捕获的还是上一轮渲染的旧游标，直接读会**滞后一拍**（选中的是上一个停留项）。正确做法如上：事件里只打标记，在 `useEffect([activeIndex])` 里等游标真正变化后再同步选中值。这正是《学习大纲》闭包陷阱专题在组件层的又一次现身。

### A4.5 :focus-visible 与 :focus 的区别

`e.target.focus()`（脚本）——浏览器有一套"焦点是否来自键盘"的启发式判定：最近一次输入是键盘（Tab、方向键），或焦点目标是文本输入框，就命中 `:focus-visible`；鼠标点出来的 focus 只命中 `:focus`。所以组件库的焦点样式纪律：

```css
/* focus.css —— 键盘用户才显示焦点圈，鼠标用户不被打扰 */
.btn {
  outline: none; /* 先清默认样式，统一自绘（前提是下面两条都写了） */
}
/* 焦点来自键盘导航：显示焦点圈 */
.btn:focus-visible {
  outline: 2px solid var(--color-primary);
  outline-offset: 2px;
}
/* 焦点来自鼠标点击：:focus 命中但 :focus-visible 不命中 → 不画圈 */
.btn:focus:not(:focus-visible) {
  outline: none;
}
```

反例警告：只写 `.btn:focus { outline: none; }` 是可访问性头号杀手——键盘用户完全失去"我在哪"的反馈。清掉默认 outline 的唯一正当理由是"换成了更好的 :focus-visible 样式"。

### A4.6 常见坑

1. **陷阱查一次列表就缓存**。症状：弹层内懒渲染的表单区域永远聚焦不进去。根因：可聚焦元素列表在打开时算一次存了 ref。修法：每次 Tab 按下现查（A4.2 写法），内容是动态的。
2. **焦点还回去没反应**。症状：关闭 Modal 后焦点丢在 body，Tab 从头开始。根因：触发元素已被卸载（行删除）或变成 disabled（focus() 静默失败）。修法：`isConnected` 判活（A4.3）；业务上重要的场景在关闭回调里显式指定还焦目标。
3. **roving 后 Tab 顺序错乱**。症状：Tab 进入组件后，组内每项还能再停。根因：`getItemProps` 忘了展开（或元素自身 tabIndex=0 覆盖了它）。修法：确认 tabIndex 计算真的落到每个元素上；用键盘实际走一遍"Tab 进入 → 方向键 → Tab 离开"三段。

### A4.7 焦点陷阱的性能与边界：排序、可见性与缓存失效

**是什么**：A4.2 的"每次 Tab 现查 querySelectorAll"是正确性优先的保守实现。工业级 trap 还有三个进阶议题：① 查询结果的**顺序**是错的（DOM 序 ≠ Tab 序，正 `tabindex` 必须排前）；② 可见性过滤漏了 `visibility: hidden`（`getClientRects` 只能过滤 `display: none`）；③ 大弹层（几百个可聚焦节点）每次 Tab 全量查询 + 强制布局有可感知成本，需要缓存 + 失效策略。

**为什么难**：

1. HTML 规范的 Tab 序是**正 tabindex 按值升序在前、0 与无 tabindex 按 DOM 序在后**——`querySelectorAll` 永远返回 DOM 序，弹层里只要有人写了 `tabIndex={3}`，A4.2 的实现就把焦点 wrap 到错误的元素上（"陷阱方向反了"的疑难杂症多半是这个）；
2. `visibility: hidden` 的元素**有布局盒**（`getClientRects().length > 0`），能混过 A4.2 的过滤，Tab 进去焦点"消失"；
3. 缓存的失效时机比缓存本身难：内容懒加载、按钮 disabled 切换、面板折叠展开都会改可聚焦集合。

**机制**：

1. **正确的 tabbable 算法**：查询 → 逐元素可见性过滤（`checkVisibility` 优先，退化到 computedStyle）→ 正 tabindex 升序桶 + DOM 序桶拼接；
2. **缓存层**：列表缓存进闭包，`MutationObserver` 监视容器子树（childList + 关键 attributes）置脏，Tab 按下时脏了才重查；
3. 另一条路线对照：**环形哨兵法**（sentinel）——容器首尾各放一个隐形 tab stop，焦点落到哨兵即拉回真实首/尾项，完全无查询、O(1)；代价是"全禁用容器"时焦点会落在哨兵上抖动，需要兜底。Radix 的 FocusScope 是查询法的工业化，老牌 focus-trap 库多用哨兵法，两条路线在真实库里都活着。

```ts
// tabbable.ts —— 规范 Tab 序：正 tabindex 升序在前 + 可见性双重过滤
const FOCUSABLE_SELECTOR = [
  'a[href]:not([disabled])',
  'button:not([disabled])',
  'input:not([disabled]):not([type="hidden"])',
  'select:not([disabled])',
  'textarea:not([disabled])',
  'iframe',
  '[contenteditable="true"]',
  '[tabindex]:not([tabindex="-1"])',
].join(', ');

/** 逐元素可见性：display:none（无布局盒）与 visibility:hidden（有盒但不可见）都要过滤 */
export function isTabbable(el: HTMLElement): boolean {
  if (el.getClientRects().length === 0) return false; // display:none / 未渲染
  if (typeof el.checkVisibility === 'function') {
    // Chrome 105+：一次判定 visibility/content-visibility 等 CSS 态
    return el.checkVisibility({ checkVisibilityCSS: true });
  }
  const visibility = getComputedStyle(el).visibility; // 旧浏览器退化路径
  return visibility !== 'hidden' && visibility !== 'collapse';
}

/** 查询 + 排序：返回符合 HTML 规范 Tab 序的可聚焦元素 */
export function getTabbableInOrder(container: HTMLElement): HTMLElement[] {
  const nodes = Array.from(
    container.querySelectorAll<HTMLElement>(FOCUSABLE_SELECTOR)
  ).filter(isTabbable);

  const positive = nodes
    .filter((n) => n.tabIndex > 0)
    .sort((a, b) => a.tabIndex - b.tabIndex); // 桶一：正 tabindex，值升序
  const rest = nodes.filter((n) => n.tabIndex <= 0); // 桶二：0 或原生默认，保持 DOM 序
  return [...positive, ...rest];
}
```

```tsx
// useFocusTrapCached.ts —— 缓存 + MutationObserver 失效：Tab 时只在脏了才重查
import * as React from 'react';
import { getTabbableInOrder } from './tabbable';

export function useFocusTrapCached(active: boolean) {
  const containerRef = React.useRef<HTMLDivElement>(null);

  React.useEffect(() => {
    if (!active) return;
    const container = containerRef.current;
    if (!container) return;

    let cache: HTMLElement[] | null = null; // null = 脏，需要重查
    const mo = new MutationObserver(() => { cache = null; });
    // 失效源：节点增删 + 会改变可聚焦性的属性（disabled/hidden/tabindex/类与样式）
    mo.observe(container, {
      childList: true,
      subtree: true,
      attributes: true,
      attributeFilter: ['disabled', 'hidden', 'tabindex', 'aria-hidden', 'class', 'style'],
    });

    const onKeyDown = (e: KeyboardEvent) => {
      if (e.key !== 'Tab') return;
      const focusable = (cache ??= getTabbableInOrder(container));
      if (focusable.length === 0) { e.preventDefault(); return; }
      const first = focusable[0];
      const last = focusable[focusable.length - 1];
      const current = document.activeElement;
      if (e.shiftKey && (current === first || !container.contains(current))) {
        e.preventDefault(); last.focus();
      } else if (!e.shiftKey && (current === last || !container.contains(current))) {
        e.preventDefault(); first.focus();
      }
    };

    container.addEventListener('keydown', onKeyDown);
    return () => {
      mo.disconnect();
      container.removeEventListener('keydown', onKeyDown);
    };
  }, [active]);

  return containerRef;
}
```

坑：

1. **弹层里有 `tabIndex={3}` 时 wrap 方向错乱**。症状：Shift+Tab 没回到"视觉上的第一个"元素。根因：DOM 序实现违反规范 Tab 序（本节机制 1）。修法：换成 `getTabbableInOrder`；同时立个库规——弹层内禁止业务元素写正 tabindex（正 tabindex 是全局 Tab 序干预，弹层语义天然局部，两者冲突）。

3. **缓存与 disabled 脱钩**。症状：提交中按钮变 disabled 后 Tab 仍停上去（focus 静默失败，焦点丢 body）。根因：`attributeFilter` 漏了 `disabled`，缓存不知道元素失效。修法：失效源清单照抄上面代码；review 时问一句"还有哪个属性能改变可聚焦性"。
4. **哨兵法遇上全禁用容器**。症状：焦点在哨兵与容器间抖动。修法：哨兵 focus 时若真实列表为空，改 focus 容器自身（`tabIndex=-1`）——哨兵法的固有复杂度，也是查询法至今仍是主流的原因。

### A4.8 focus-visible 与键盘用户检测：把浏览器启发式变成可编程信号

**是什么**：A4.5 讲了 `:focus-visible` 的 CSS 用法；本节把"焦点来自键盘还是指针"变成 **JS 可读的信号**。组件库需要它的典型场景：roving tabindex 用 `focus()` 移动焦点后，要不要给目标项画焦点圈——浏览器对**程序性 focus()** 的 `:focus-visible` 判定继承"上一次输入的 modality"，多数时候恰好正确，但混合输入（触屏 + 键盘）与旧浏览器（Safari 15.4 前无 `:focus-visible`）需要库自己掌握真相。

**为什么难**：

1. modality（输入方式）是**全局且时变**的状态：鼠标用户点了一下、再按 Tab——此刻是键盘用户；触屏用户点了输入框——浏览器按启发式给 `:focus-visible`。CSS 选择器无法被 JS 查询"元素此刻是否命中 :focus-visible"（`element.matches(':focus-visible')` 在多数浏览器实现为总是 false，不能依赖）；
2. 老浏览器没有 `:focus-visible`，CSS 只写 `:focus` 会打扰鼠标用户，只写 `:focus-visible` 会丢键盘用户——需要 JS 兜底；
3. 检测本身要零成本：不能每次 focus 都跑一遍重逻辑。

**机制**（what-input 库与 focus-visible polyfill 的共同内核）：

1. 全局捕获监听三类输入：keydown（导航键/字符键）→ `keyboard`；pointerdown → 按 pointerType 分 `pointer`/`touch`；
2. modality 变化时写 `<html data-whatinput="...">`——CSS 有一条完整的兜底链；
3. 库内消费：`useInputModality()`（useSyncExternalStore 订阅），roving 移动焦点时据此决定是否补 `data-focus-visible`。

```ts
// inputModality.ts —— 全局输入方式跟踪（模块级单例，注册一次）
export type InputModality = 'keyboard' | 'pointer' | 'touch' | 'initial';

let current: InputModality = 'initial';
const listeners = new Set<(m: InputModality) => void>();

function setModality(next: InputModality): void {
  if (current === next) return;
  current = next;
  if (typeof document !== 'undefined') {
    document.documentElement.dataset.whatinput = next; // CSS 兜底钩子
  }
  listeners.forEach((fn) => fn(next));
}

/** 修饰键组合（快捷键）不算"键盘导航"：它不产生焦点移动 */
function isFocusMovingKey(e: KeyboardEvent): boolean {
  if (e.ctrlKey || e.metaKey || e.altKey) return false;
  return (
    e.key === 'Tab' ||
    e.key.startsWith('Arrow') ||
    ['Home', 'End', 'Enter', ' '].includes(e.key) ||
    e.key.length === 1 // 可打印字符（typeahead 等）
  );
}

if (typeof window !== 'undefined') {
  // 捕获阶段：抢在一切业务监听之前更新（A6.2 顺序结论的工程红利）
  window.addEventListener('keydown', (e) => {
    if (isFocusMovingKey(e)) setModality('keyboard');
  }, true);
  window.addEventListener('pointerdown', (e) => {
    setModality(e.pointerType === 'touch' ? 'touch' : 'pointer');
  }, true);
}

export function getInputModality(): InputModality {
  return current;
}

export function subscribeModality(fn: (m: InputModality) => void): () => void {
  listeners.add(fn);
  return () => { listeners.delete(fn); };
}
```

### A4.9 嵌套对话框的焦点归还栈与 autofocus 争议

**是什么**：A4.3 的"打开记住、关闭还回"在单层对话框成立。嵌套链（Modal 里开 Select、Select 里开 DatePicker）上它会漏两种情况：① 父层先关（Esc 关 Modal 时子面板还开着）——子层记录的触发元素已随父层卸载，独立记录法各还各的会还到"尸体"上；② 还原目标该沿栈向下**找最近仍连接的**，而不是固定"自己记录的那个"。本节把归还升级成全局栈，并处理初始焦点的两个争议：autofocus 语义与初始焦点落点。

**为什么难**：

1. 独立记录的隐含前提是"子层记录时焦点必在父层内、且父层活得比子层久"——两个假设在异常关闭序（父先关、批量关闭）下都塌；
2. `focus()` 默认带滚动（元素滚进视口）——还焦瞬间页面跳滚，用户视角是"关了个弹窗页面飞了"；
3. autofocus 有两套语义在打架：HTML 的 `autofocus` 是**文档加载期**语义；动态挂载的对话框需要的是**挂载时**语义。React 的 `autoFocus` prop 部分补齐但有多弹层竞态问题。

**机制**：

1. **全局栈**：module 级数组，每层 open 时 push `{ trigger }`；关闭时把自己**及以上**的全部弹掉（父先关时上面的都是失效层），然后从弹剩的栈顶向下找第一个 `isConnected` 的 trigger 还焦；
2. `focus({ preventScroll: true })`：还焦不抢滚动位置；
3. **初始焦点策略**（含争议仲裁）：
   - 优先 `[data-autofocus]`（开发者显式指定，A4.2 同款约定，不使用原生 `autofocus`——原因见坑 2）；
   - 其次第一个可聚焦元素（Radix/antd 的默认）；
   - 都没有则容器自身（`tabIndex=-1`）兜底；
   - 争议仲裁：APG 对话框模式的指引是初始焦点应服务对话框的**主要目的**——纯确认框落到主操作（"确定"）合理；含表单的对话框落到第一个输入框合理；**没有共识的场景**（如含长列表的抽屉）主流库默认"第一个可聚焦"，因为"确定性"比"猜测意图"更重要。库的选择：默认第一个可聚焦 + `data-autofocus` 逃生舱，文档明示。

```ts
// focusReturnStack.ts —— 全局焦点归还栈
interface DialogLayer {
  trigger: HTMLElement | null; // 打开那一刻的 activeElement（可能在父弹层内）
}

const stack: DialogLayer[] = [];

/** 弹层打开时调用；返回 release（关闭/卸载时调用，幂等） */
export function pushDialogLayer(): () => void {
  const layer: DialogLayer = {
    trigger:
      document.activeElement instanceof HTMLElement ? document.activeElement : null,
  };
  stack.push(layer);
  return () => popFrom(layer);
}

function popFrom(layer: DialogLayer): void {
  const idx = stack.lastIndexOf(layer);
  if (idx === -1) return; // 幂等：StrictMode 双 cleanup、重复调用都安全
  stack.length = idx;     // 弹掉自己 + 以上所有层（父先关：上面全是失效层）
  focusNearestAvailable(idx - 1);
}

/** 沿栈向下找最近一个仍连接在文档中的触发元素（A4.3 isConnected 判活的栈化推广） */
function focusNearestAvailable(from: number): void {
  for (let i = from; i >= 0; i--) {
    const el = stack[i]?.trigger;
    if (el && el.isConnected) {
      el.focus({ preventScroll: true }); // 还焦不抢滚动位置
      return;
    }
  }
  // 整条栈都没有活着的触发元素：焦点自然落在 body——可接受的下线（A4.3 同款）
}
```

```tsx
// useDialogFocus.ts —— 打开入栈 + 初始焦点 + 关闭出栈
import * as React from 'react';
import { pushDialogLayer } from './focusReturnStack';

const FOCUSABLE_IN_DIALOG =
  'button:not([disabled]), a[href], input:not([disabled]), ' +
  'select:not([disabled]), textarea:not([disabled])';

export function useDialogFocus(
  open: boolean,
  containerRef: React.RefObject<HTMLElement | null>
) {
  React.useEffect(() => {
    if (!open) return;
    const release = pushDialogLayer();
    const container = containerRef.current;

    if (container) {
      // 初始焦点三级策略：data-autofocus > 第一个可聚焦 > 容器自身（tabIndex=-1 兜底）
      const initial =
        container.querySelector<HTMLElement>('[data-autofocus]') ??
        container.querySelector<HTMLElement>(FOCUSABLE_IN_DIALOG);
      if (initial) {
        initial.focus({ preventScroll: true });
      } else {
        container.tabIndex = -1; // 容器兜底聚焦的前提：编程可聚焦
        container.focus({ preventScroll: true });
      }
    }
    return release;
  }, [open, containerRef]);
}
```

坑：

1. **还焦导致页面跳滚**。症状：长页面底部关弹窗，页面滚回触发器。根因：`focus()` 默认滚动元素进视口。修法：统一 `preventScroll: true`（栈实现已带）；业务确需"滚回触发器"的场景显式 scrollIntoView——两个关注点分开。
2. **用原生 `autofocus` 属性做对话框初始焦点**。症状：时灵时不灵；两个弹层同时挂载时焦点去了后挂的那个。根因：HTML `autofocus` 语义是文档加载期一次性，动态插入时浏览器行为不一；React 的 `autoFocus` 在 mount 时生效但不受你控制层级次序。修法：一律走 `[data-autofocus]` 查询（A4.2 与本节同一约定）。
3. **Toast 这类非模态进了栈**。症状：Toast 消失时焦点被"还"走，打断用户输入。根因：非模态没有"打开时抢焦点"的语义，自然也不该有"关闭时还焦点"。修法：只有模态（`aria-modal`/_trap 类）入栈；Toast 的容器不接 useDialogFocus。
4. **release 时序与退出动画**。A3.4 的退出动画期间 DOM 还在——release 应发生在**动画结束真卸载时**还是 `visible=false` 时？正确答案是后者（逻辑关闭即还焦，用户已经开始与背景交互了），但 `useMountTransition` 的 unmounted 时机在动画后——所以 useDialogFocus 的 effect 依赖应该是 `visible`（逻辑态）而非 `mounted`（实现态），两个状态机的依赖选择本身就是 A3 的考点回流。
