## Lv4 范式之争（组件之上的认知）

前面 Lv1–Lv3 练的是"怎么写组件"，Lv4 回答"**写完之后放在哪、给谁用**"。同一个 Dialog，可以做成带完整样式的成品（antd）、只带行为不带样式的半成品（Radix）、或者干脆变成你仓库里的一段源码（shadcn）——三条路线是对"组件库到底交付什么"的三种回答。

| 路线 | 代表 | 思想 |
|---|---|---|
| 全家桶（带样式） | antd / arco / semi | 开箱即用，主题 token 化 |
| **Headless（无样式）** | **Radix UI（交互圣经）**、HeadlessUI、Base UI | 只做行为/无障碍，样式全给消费者 |
| 复制粘贴式 | shadcn/ui | 源码进你的仓库，cva 管理变体，彻底可控 |

逐行展开。

**第一行：全家桶（带样式）—— antd / arco / semi：「开箱即用，主题 token 化」。** 交付的是**成品**：装上就能用，视觉统一、交互统一、连 Table/Form/DatePicker 这种成本极高的组件也白拿。它真正的工作量在"主题 token 化"：上一节看过，一个 `colorPrimary` 种子进 ConfigProvider，全库几百个组件的 hover/active/disabled/边框/背景色由派生算法自动算出，暗色/紧凑模式只是换一个 algorithm。开箱即用的代价同样明确：**定制的天花板**——改结构（往 DatePicker 面板里塞自定义区域）、改行为（Table 排序逻辑长在自己的数据流里）都要绕着它的受控协议走，深度定制往往以 fork 告终；再就是包体积与升级耦合（大版本 breaking 靠 codemod 迁移）。适合：中后台、交付节奏快、视觉要求"统一体面"而非"独一无二"。

**第二行：Headless（无样式）—— Radix UI（交互圣经）、HeadlessUI、Base UI：「只做行为/无障碍，样式全给消费者」。** 交付的是**行为与无障碍**：状态机、键盘模型、焦点管理、ARIA、Portal、退出动画时机——一个 className 都不掺和。Radix 被称为"交互圣经"不是客套：它把 WAI-ARIA Authoring Practices（A5 说的圣经）逐组件**工程化翻译**了一遍——Dialog 的焦点陷阱与焦点还回、Tabs 的 roving tabindex、Select 的 typeahead、受控/非受控双模式（A1）、SSR 安全的 id——每一样都是你 Part A 苦练的内功的标准答案，而且每个组件只有几百行，是最易吸收的源码读物（本大纲"源码阅读优先级"第一条）。看它交付一个 Dialog 的形态：

```tsx
import * as Dialog from '@radix-ui/react-dialog';

export function HeadlessDialog() {
  return (
    <Dialog.Root>
      <Dialog.Trigger asChild>
        <button className="你的样式">打开</button>
      </Dialog.Trigger>
      <Dialog.Portal>
        <Dialog.Overlay className="fixed inset-0 z-50 bg-black/50" />
        <Dialog.Content className="fixed left-1/2 top-1/2 z-50 w-96 -translate-x-1/2 -translate-y-1/2 rounded-lg bg-white p-6">
          <Dialog.Title className="text-lg font-medium">标题</Dialog.Title>
          <Dialog.Description className="mt-2 text-sm text-gray-500">
            焦点陷阱、Esc 关闭、滚动锁、aria 属性、退出动画挂载时机——Radix 全包，
            样式一行不插手。
          </Dialog.Description>
          <Dialog.Close asChild>
            <button className="mt-4">关闭</button>
          </Dialog.Close>
        </Dialog.Content>
      </Dialog.Portal>
    </Dialog.Root>
  );
}
```

这条线的两个兄弟定位不同：**HeadlessUI** 是 Tailwind 团队出品，组件少而精（Listbox、Combobox、Menu、Dialog、Tabs 等），与 Tailwind 生态无缝，特点是简单克制、附 Transition 助手；**Base UI** 是 MUI 团队联合 Radix 与 Floating UI 的核心维护者打造的新一代 headless 库（2025 年已发布 1.0 稳定版，首发 35 个组件，包名 `@base-ui-components/react`），定位是 Radix 思路的现代化继任者：组件与 hooks 双形态输出、动画/过渡一等公民、体积更收敛。三者的共同哲学不变：**样式权完全交给消费者，行为与无障碍做到满分**。适合：有自己的设计系统、视觉必须独此一家、团队养得起样式层。

**第三行：复制粘贴式 —— shadcn/ui：「源码进你的仓库，cva 管理变体，彻底可控」。** 交付的是**起点而非依赖**：CLI（`npx shadcn@latest add dialog`）把组件源码复制进你的 `components/ui/` 目录，从那一刻起它是**你的代码**——没有 node_modules 里的黑盒，没有"想改一行只能 fork"的天花板。底下两层技术支撑：行为层直接复用 Radix（shadcn 的 Dialog 就是上文那段 Radix 包了 Tailwind 皮），变体层用 cva 管理（下节展开）。它的"升级策略"也自成一派：组件库语义化版本保护不了你改过的源码，shadcn 的答案是**版本化脚手架**——升级时 CLI 重新拉取新源码与你本地版本做 diff，由你逐块决定采纳与否；换句话说它放弃了"无痛升级"，换来了"任何改动都合法"。代价：初始要接受一整套 Tailwind + 目录约定，组件质量由你自己的仓库负责。适合：独立产品、创业团队、任何"设计终会长出自己的样子"的项目。

**cva（class-variance-authority）：变体的类型安全管理**（本大纲 Lv4 原始要点）。当样式变成"variant × size × 状态"的组合表，手拼 className 字符串很快失控：拼错没人报错、重复类互相覆盖。cva 把变体表声明成数据，类型系统自动接管。完整示例（shadcn 同款结构，cva + tailwind-merge 集成）：

```bash
npm i class-variance-authority clsx tailwind-merge
```

```tsx
// components/ui/button.tsx —— cva 变体定义 + cn 工具 + 类型安全的 Button
import { cva, type VariantProps } from 'class-variance-authority';
import { clsx, type ClassValue } from 'clsx';
import { twMerge } from 'tailwind-merge';
import type { ButtonHTMLAttributes } from 'react';

// cn：先 clsx 做条件拼接，再 twMerge 让冲突的 Tailwind 类"后者胜"
// （业务传 className 覆盖组件默认类就是这么实现的）
export function cn(...inputs: ClassValue[]) {
  return twMerge(clsx(inputs));
}

// cva(基础类, { variants, defaultVariants })：变体即数据
const buttonVariants = cva(
  // base：所有变体共享的底座
  'inline-flex items-center justify-center gap-2 whitespace-nowrap rounded-md text-sm font-medium transition-colors disabled:pointer-events-none disabled:opacity-50',
  {
    variants: {
      variant: {
        default: 'bg-primary text-primary-foreground hover:bg-primary/90',
        destructive: 'bg-destructive text-white hover:bg-destructive/90',
        outline: 'border border-input bg-background hover:bg-accent',
        secondary: 'bg-secondary text-secondary-foreground hover:bg-secondary/80',
        ghost: 'hover:bg-accent hover:text-accent-foreground',
        link: 'text-primary underline-offset-4 hover:underline',
      },
      size: {
        default: 'h-9 px-4 py-2',
        sm: 'h-8 rounded-md px-3 text-xs',
        lg: 'h-10 rounded-md px-8',
        icon: 'h-9 w-9',
      },
    },
    defaultVariants: {
      variant: 'default',
      size: 'default',
    },
  },
);

// 类型安全的关键一招：VariantProps 从 cva 定义"反查"出 variant/size 的字面量联合类型
// 于是 <Button variant="destuctive">（拼错）直接编译报错，而不是静默无样式
export interface ButtonProps
  extends ButtonHTMLAttributes<HTMLButtonElement>,
    VariantProps<typeof buttonVariants> {}

export function Button({ className, variant, size, ...rest }: ButtonProps) {
  return (
    <button
      className={cn(buttonVariants({ variant, size }), className)} // 调用方 className 最后合并 → 可覆盖
      {...rest}
    />
  );
}
```

cva 的机制两句话：`cva()` 返回一个**类名生成函数**（`buttonVariants({ variant, size })` → 拼好的字符串）；`VariantProps<typeof buttonVariants>` 用 TypeScript 的类型推导**从值反推出类型**——变体表既是运行时数据又是编译时类型源，一处定义、两处消费，永不漂移。`tailwind-merge` 解决 Tailwind 的类冲突语义：`px-4 px-8` 保留后者、`p-4 px-3` 收敛为后者补集、任意值 `w-[20px]` 也能识别；若你用了插件生成的自定义工具类（如 typography 的 `prose`），默认字典不认识，需用 `extendTailwindMerge` 注册。这也是 `cn()` 里 `className` 必须放最后的原因：调用方永远赢。

**建议：行为学 Radix，工程学 antd，形态学 shadcn**——论证展开。这句话不是三选一，是**三个学习方向的分工**：

- **行为学 Radix**：学"交互应该长什么样"。读 Radix 源码等于读 APG 的工程化标准答案——每种组件的键盘模型、焦点纪律、aria 结构、受控协议都摆在你面前，几百行一个，吸收成本最低。学完它，你自己写任何交互组件都有一把尺子。
- **工程学 antd**：学"一个库如何被几千个团队用十年"。token 派生体系、ConfigProvider 的全局注入口（上一节）、monorepo 分包、changesets 与 codemod 的版本纪律、双 React 版本测试矩阵（Part C 的全部话题）、以及 Wave 波纹、两字中文加空格、滚动锁宽度补偿这类真实边界 bug 的沉淀——这些是 Radix（刻意做小）永远不会教你的。
- **形态学 shadcn**：学"现代组件库的组装形态"。compound 组件 + cva 变体 + Tailwind token + cn 覆盖链，这套"形态"已经成为新组件库的事实模板——哪怕你用 antd 做业务，内部二方库长什么样也大概率向它看齐。

三线合一的真实项目形态也很常见：中后台用 antd 抢交付、设计系统层用 Radix 自建、内部工具用 shadcn 快速起盘——按团队所处阶段取用，而不是站队。

Lv4 选型常见坑（症状 → 根因 → 修法）：

| # | 症状 | 根因 | 修法 |
|---|---|---|---|
| 1 | Headless 组件"丑到不能用"就放弃 | 拿成品库的预期去用无样式库 | Radix 是给有设计系统/愿意写样式团队的，先备好 Tailwind 或样式层 |
| 2 | shadcn 组件升级后自己改的逻辑丢了 | 复制粘贴式放弃 semver 保护，盲目覆盖 | 用 CLI 的 diff 升级，逐块审阅；自己的扩展放 wrapper 层而非改源文件 |
| 3 | variant 拼错静默失效 | 变体用字符串拼接而不是 cva 声明 | cva + VariantProps，让拼错变编译错 |
| 4 | 业务 className 覆盖不了组件默认样式 | 类冲突没有仲裁（后写的类不一定赢） | cn() 里 twMerge 兜底，className 放最后 |
| 5 | antd 深度定制改到 fork | 把"带样式成品"当成"可塑毛坯"用 | 结构级行为级定制一开始就该选 Headless 路线 |

### 补充：headless vs 有样式的边界决策——同一组件三种形态的取舍与自研库选型

**是什么。** 边界决策回答的是"我的库交付到哪一层、把哪一层让给消费者"。把组件拆成三层所有权——**行为层**（状态机/键盘/焦点/ARIA）、**结构层**（DOM 形状与层级）、**视觉层**（token/样式）——三种形态就是三份不同的"所有权分割协议"。

**为什么值得单列。** 边界画错的代价是对称的：往右多拿一点（库替用户做了样式/结构决策），就复刻 antd 的"定制天花板"，深度定制以 fork 告终；往左多让一点（行为之外全交给消费者），没有设计系统的团队拿到的就是"裸奔的半成品"，每个组件都在重复发明样式。自研库选型的第一步不是选技术栈，是把这张所有权表先填出来。

**机制分步。**

1. **所有权对照**：

| 所有权层 | antd | Radix | shadcn |
|---|---|---|---|
| 行为（状态机/键盘/焦点/ARIA） | 库 | 库 | 复用 Radix（间接） |
| 结构（DOM 形状） | 库（配置驱动） | 库默认，`asChild` 让渡（见下节） | 你的源码 |
| 视觉（token/样式） | 库 + token 受控开口（上文 ConfigProvider） | 完全归消费者 | 你的源码（cva 约定） |
| 升级单位 | npm 包 semver | npm 包 semver | CLI diff 逐块审阅 |

2. **同一需求在三形态下的真实体感**——"带清空按钮的部门选择器"：

| 判据 | 选带样式成品 | 选 headless 自建 | 选复制粘贴形态 |
|---|---|---|---|
| 目标用户 | 业务团队、交付节奏快 | 有设计系统的平台团队 | 独立产品/小团队 |
| 样式存量 | 无，或愿意被统一 | 已有 token 体系 | 接受 Tailwind 起点，之后长出自己的 |

| 定制预期 | 换色/密度级 | 结构级定制是常态 | 行为级定制是常态 |

坑（症状 → 根因 → 修法）：

| # | 症状 | 根因 | 修法 |
|---|---|---|---|
| 1 | 二方库 fork antd 组件改样式，升级即地狱 | 把"带样式成品"当"毛坯"用 | wrapper + token/ConfigProvider；深度定制走 Radix 自建 |
| 2 | 全组用 headless 但没有设计系统 | 样式层无人维护，组件裸奔 | 先落 token 与基础样式层，再上 headless |
| 3 | shadcn 源码在每个 app 各拷一份 | 复制粘贴形态 × 多副本 = 必然漂移 | 源码收进 monorepo 共享包（[26-C1](26-C1-仓库-pnpm-monorepo-components-hooks-tokens.md) 的 internal package） |
| 4 | 以为 asChild 是"样式透传" | asChild 让渡的是结构与事件，不碰样式 | 样式仍走 className/cva 链（上文 cva + [09-A8.3](09-A8-ref-体系与-API-生态.md) 合并纪律） |

### 补充：asChild/slot 模式——Radix Slot 的实现原理、props 合并顺序与多子元素报错

**是什么。** `<Dialog.Trigger asChild><button/></Dialog.Trigger>` 的含义：库组件**不渲染自己的 DOM**，把行为 props（事件、aria、`data-state`、ref）注入消费者提供的那个子元素。Radix 把这个机制抽成了独立包 `@radix-ui/react-slot`，是全部 `Primitive.*` 的 asChild 底座。

**为什么值得单列。** asChild 是 headless 路线"结构让渡"的实现关键，而它难在**合并契约**：事件 handler 谁先执行？className 谁覆盖谁？ref 怎么合？多子元素/纯文本子节点为什么必须报错？这五个问题答错一个，消费者就会在某个边界场景踩雷（比如 preventDefault 时机）。它也是上文 [09-A8.3 props 合并纪律](09-A8-ref-体系与-API-生态.md)的极致形态——那节讲"库怎么把自己包的元素 props 透传下去"，Slot 讲"库怎么把 props 注入消费者包的元素"。

**机制分步。**

1. **children 校验**：asChild 要求恰好一个 React **元素**子节点——多子、纯文本、空都抛错（错误信息要把"该传什么"说清楚，这是库的教养）。
2. **注入手段**：`React.cloneElement(child, mergedProps)`（[12-Lv2](12-Lv2-弹层与反馈组件-功力主考场之一.md) 的 Trigger 写过它的朴素用法）。
3. **五类 props 的合并契约**（与 Radix 源码一致）：
   - 事件 handler（`on*` 两边都是函数）：**两者都执行，消费者的先**——消费者可以先行 `preventDefault`，库随后做收尾；链式合并不短路。
   - `className`：拼接，库的在前、消费者的在后（配合 cva/twMerge 时消费者仍能赢冲突类）。
   - `style`：浅合并，消费者的键覆盖库。
   - `id` 与其余普通 props：**消费者覆盖库**（库的只是默认值）。
   - `ref`：合成（composeRefs），两边的 ref 都收到节点。
4. **Slottable**：多子场景（如 `<Trigger asChild>` 里还有库渲染的额外内容）用同包的 `Slottable` 标记"哪一个是被注入者"，其余子节点成为克隆后元素的 children——Radix Dialog.Close 的图标排布就靠它。

**完整代码**（教学版 MiniSlot，契约与 Radix 对齐）：

```tsx
// MiniSlot.tsx —— asChild 的全部机制在 60 行内
import React, {
  type ReactElement, type ReactNode,
} from 'react';

type PossibleRef<T> = React.Ref<T> | undefined;

function setRef<T>(ref: PossibleRef<T>, value: T | null): void {
  if (typeof ref === 'function') ref(value);
  else if (ref != null) (ref as React.RefObject<T | null>).current = value;
}

export function composeRefs<T>(...refs: PossibleRef<T>[]) {
  return (node: T | null) => {
    for (const r of refs) setRef(r, node);
  };
}

function isPlainObject(v: unknown): v is Record<string, unknown> {
  return typeof v === 'object' && v !== null && !Array.isArray(v);
}

/** 合并契约：事件链式（消费者先）、className 拼接、style 浅合并、其余消费者覆盖库 */
export function mergeProps(
  childProps: Record<string, unknown>,
  slotProps: Record<string, unknown>,
): Record<string, unknown> {
  const merged: Record<string, unknown> = { ...slotProps }; // 库 props 是默认底座
  for (const key of Object.keys(childProps)) {
    const fromChild = childProps[key]; // 消费者
    const fromSlot = slotProps[key];   // 库
    if (key === 'className' && typeof fromChild === 'string' && typeof fromSlot === 'string') {
      merged[key] = `${fromSlot} ${fromChild}`.trim();
    } else if (key === 'style' && isPlainObject(fromChild) && isPlainObject(fromSlot)) {
      merged[key] = { ...fromSlot, ...fromChild };
    } else if (
      key.startsWith('on')
      && typeof fromChild === 'function'
      && typeof fromSlot === 'function'
    ) {
      merged[key] = (...args: unknown[]) => {
        (fromChild as (...xs: unknown[]) => void)(...args); // 消费者先执行
        (fromSlot as (...xs: unknown[]) => void)(...args);  // 库随后收尾，不短路
      };
    } else {
      merged[key] = fromChild; // 其余：消费者覆盖库
    }
  }
  return merged;
}

export function Slot({
  children,
  ...slotProps
}: { children: ReactNode } & Record<string, unknown>): ReactElement {
  const items = React.Children.toArray(children);
  const child = items[0];
  if (items.length !== 1 || !React.isValidElement(child)) {
    throw new Error('Slot: asChild 期望恰好一个 React 元素子节点（多子/纯文本/空都不行）');
  }
  const element = child as ReactElement<Record<string, unknown>>;
  // React 19：ref 就在 props 上；≤18：从 element 本体兜底取（Radix 同款兼容）
  const { ref: propsRef, ...childRest } = element.props as {
    ref?: PossibleRef<HTMLElement>;
  } & Record<string, unknown>;
  const legacyRef = (element as unknown as { ref?: PossibleRef<HTMLElement> }).ref;
  const childRef = propsRef ?? legacyRef;
  const { ref: slotRef, ...slotRest } = slotProps as {
    ref?: PossibleRef<HTMLElement>;
  } & Record<string, unknown>;
  const mergedRef = childRef || slotRef ? composeRefs(childRef, slotRef) : undefined;
  return React.cloneElement(element, {
    ...mergeProps(childRest, slotRest),
    ref: mergedRef, // cloneElement 的 config.ref 是覆盖式，必须传合成后的
  });
}
```

### 补充：严格受控 API vs 自由组合 API——何时锁死 API 表面，何时开放 render props

**是什么。** 两种 API 哲学：**严格受控**（antd Table 的 `columns` 协议、Form 的 `rules`——表面窄而深，结构私有，行为可预测）vs **自由组合**（Radix 的 compound + asChild、render props——库只定协议，结构全开放）。注意区分：[02-A1](02-A1-受控-非受控双模式-30-行-hook-处处要用.md) 讲的是"值"的受控协议（value/onChange 仲裁），本节讲的是"结构"的受控协议——库要不要把 DOM 形状承诺出去。

**为什么值得单列。** 这不是品味之争，四个可度量的代价被这个决定左右：学习成本、定制上限、**破坏性变更频率**（自由 API 把内部结构承诺出去之后，任何结构改版都是 breaking）、测试与文档成本。成熟库的答案是**分层开放**：默认严格，逐层开逃生舱，而不是二选一。

**机制分步。**

1. **四个判据**：① 使用场景收敛度（80% 场景能预设 → 严格默认值赢）；② 定制点的位置——视觉定制给 `className`/cva 就够，结构定制才给 render props/slot，行为定制走受控 props + 事件；③ 破坏性变更的代价（你对消费者暴露的每一层结构，都是未来升级的债）；④ 文档与测试成本（每个自由开口都要文档化"可依赖什么"并加测试钉死）。
2. **分层开放模型**：L0 语义 props（严格）→ L1 `className`/`style`（[09-A8.3](09-A8-ref-体系与-API-生态.md) 合并纪律）→ L2 具名 render props（只开真正高频定制的部位）→ L3 headless hook（结构完全归消费者）。**升级要按档位来**：L2 泛滥（每个部位一个 xxxRender）是升 L3 的信号，不是继续加 L2 的理由——antd 在 v5 迭代里把 `dropdownRender` 等一批渲染插槽统一更名收敛（旧名保留兼容），就是 API 表面治理的公开案例。
3. **何时锁死**：组件的成功路径高度一致（StatCard、Result、空态）；有性能或无障碍整体契约要保（虚拟列表内部的 DOM 结构、焦点次序）——结构自由会破坏库的隐含承诺。**何时开放**：消费者的结构差异是常态（卡片头部、表格单元格、弹层内容）；你已经看到大量"绕过 API 往里塞 div"的下游代码——那是 API 表面不够用的实证。

**完整代码**（同一个 StatCard 的三档演进）：

```tsx
// StatCardTiers.tsx —— L0 严格 → L2 render props → L3 headless
import { useEffect, useState, type ReactNode } from 'react';

// L0：结构私有，只暴露语义 props——80% 用户的最短路径
export function StatCard({
  label, value, tone = 'default',
}: {
  label: string;
  value: number;
  tone?: 'default' | 'positive' | 'negative';
}) {
  return (
    <div className="rounded-lg border p-4">
      <div className="text-xs text-gray-500">{label}</div>
      <div className={tone === 'positive' ? 'text-green-600' : tone === 'negative' ? 'text-red-600' : ''}>
        {value}
      </div>
    </div>
  );
}

// L2：只开"值区"一个具名插槽，默认实现兜底——L0 用户无感升级
export function StatCardSlot({
  label, value, renderValue,
}: {
  label: string;
  value: number;
  renderValue?: (value: number) => ReactNode;
}) {
  return (
    <div className="rounded-lg border p-4">
      <div className="text-xs text-gray-500">{label}</div>
      {renderValue ? renderValue(value) : <div>{value}</div>}
    </div>
  );
}

// L3：headless——数据/状态归库，结构完全归消费者（用 rollup 数字举例）
export function useRollup(pollUrl: string, intervalMs = 5000) {
  const [value, setValue] = useState<number | null>(null);
  const [error, setError] = useState<Error | null>(null);
  useEffect(() => {
    let alive = true;
    const tick = async () => {
      try {
        const res = await fetch(pollUrl);
        if (!res.ok) throw new Error(`HTTP ${res.status}`);
        const data = (await res.json()) as { value: number };
        if (alive) {
          setValue(data.value);
          setError(null);
        }
      } catch (e) {
        if (alive) setError(e instanceof Error ? e : new Error(String(e)));
      }
    };
    void tick();
    const id = window.setInterval(tick, intervalMs);
    return () => {
      alive = false;
      window.clearInterval(id);
    };
  }, [pollUrl, intervalMs]);
  return { value, error, isLoading: value == null && error == null };
}
```
