## A1. 受控/非受控双模式（30 行 hook，处处要用）

- 原理：外部传 `value` 则受控（内部不存状态），否则用内部 state；`onChange` 永远回调
- 坑：受控↔非受控切换警告；`defaultValue` 只能消费一次（惰性初始化）；受控组件不回显的 bug

### A1.1 是什么：状态所有权的两种形态

"受控/非受控"描述的是**组件值的所有权归谁**：

- **受控（controlled）**：调用方传 `value`，组件只是展示。值变不变完全由外部 state 决定，用户输入只通过 `onChange` 上报，组件自己无权改值。这是"状态提升"在组件库场景的化身。
- **非受控（uncontrolled）**：调用方最多传 `defaultValue` 作为初值，之后值归组件内部 state 所有，外部想读只能拿 ref。

一个合格的库组件必须**同时支持两种形态**：`<Input defaultValue="a" />` 在纯展示页直接可用；同一个 `<Input value={form.name} onChange={...} />` 在受控表单里也行为正确。判定规则只有一条：**`value !== undefined` 即受控**（对 boolean 组件同理，`checked !== undefined`）。

### A1.2 为什么需要：三种调用场景缺一不可

1. **原型/静态页**：调用方懒得建 state，传个 `defaultValue` 就走，非受控是最低成本路径。
2. **表单与联动**：输入框 A 联动清空输入框 B、提交前校验取值——值必须住在表单 store（或 `useForm`）里，受控是唯一选择。
3. **受控切换成本**：如果库只支持受控，第 1 类用户被迫写一堆 `useState`；只支持非受控，第 2 类用户拿不到值。所以 antd、Radix、Base UI 的做法一致：**双模式是默认 API 契约**，实现收敛到一个 hook 里，所有带值组件复用。

### A1.3 怎么做：useControllableState 完整实现

机制分四步：

1. **受控判定**：每次渲染算 `isControlled = value !== undefined`，渲染的是 `isControlled ? value : internalState`。
2. **惰性初始化**：内部 `useState(defaultValue)` 只在首次渲染消费 `defaultValue` 一次——这是 useState 的语义，也正是我们想要的行为（后续改 `defaultValue` 不影响现值）。
3. **写路径统一**：暴露一个 `setValue`。它先解析函数式更新得到新值；新旧值不同则**总是**回调 `onChange`（受控与否都回调，调用方靠它回写）；然后**仅非受控时**写内部 state（受控时内部不存，等 props 回流）。
4. **模式切换检测**：用 ref 记住上一次是否受控，渲染期间发现切换就 `console.warn`。这种切换是契约违反：非受控切受控，内部 state 瞬间作废；受控切非受控，值会"跳"回陈旧的内部 state。

完整代码：

```tsx
// useControllableState.ts
import * as React from 'react';

/** 更新动作：直接给值，或基于上一个值计算（对齐 useState 的函数式更新） */
export type SetStateAction<T> = T | ((prev: T | undefined) => T);

export interface UseControllableStateParams<T> {
  /** 受控值：传了（!== undefined）即为受控模式 */
  value?: T;
  /** 非受控初值：只在首次渲染消费一次 */
  defaultValue?: T;
  /** 值变化回调：受控与非受控模式下都会触发 */
  onChange?: (value: T) => void;
}

export function useControllableState<T>(
  params: UseControllableStateParams<T>
): [T | undefined, (action: SetStateAction<T>) => void] {
  const { value: valueProp, defaultValue, onChange } = params;

  // ── 步骤 1：受控判定 ─────────────────────────────────────────
  const isControlled = valueProp !== undefined;

  // ── 步骤 4：受控↔非受控切换警告（渲染期间比较上一次模式）────
  const wasControlledRef = React.useRef<boolean | null>(null);
  if (
    wasControlledRef.current !== null &&
    wasControlledRef.current !== isControlled
  ) {
    console.warn(
      `[useControllableState] 组件在受控与非受控之间切换（${wasControlledRef.current ? '受控→非受控' : '非受控→受控'}）。` +
        `这会导致值跳变。请保证 value 要么一直传、要么一直不传。`
    );
  }
  wasControlledRef.current = isControlled;

  // ── 步骤 2：内部 state，defaultValue 惰性消费一次 ─────────────
  const [internalState, setInternalState] = React.useState<T | undefined>(defaultValue);

  // 内部 state 的最新值镜像（供下面的稳定 setter 读，避免闭包过期）
  const internalStateRef = React.useRef<T | undefined>(internalState);
  internalStateRef.current = internalState;

  // 用 ref 保存"最新的一切"，让下面的 setter 可以稳定引用（不随渲染重建）
  const isControlledRef = React.useRef(isControlled);
  isControlledRef.current = isControlled;
  const valueRef = React.useRef<T | undefined>(valueProp);
  valueRef.current = valueProp;
  const onChangeRef = React.useRef(onChange);
  React.useEffect(() => {
    onChangeRef.current = onChange; // 回调永远指向最新一次渲染传入的函数
  }, [onChange]);

  // 渲染用的值：受控取 props，非受控取内部
  const value = isControlled ? valueProp : internalState;

  // ── 步骤 3：统一的写路径 ─────────────────────────────────────
  const setValue = React.useCallback((action: SetStateAction<T>) => {
    const prev = isControlledRef.current
      ? valueRef.current                    // 受控：基准是外部最新值
      : internalStateRef.current;           // 非受控：基准是内部最新值
    const next =
      typeof action === 'function'
        ? (action as (p: T | undefined) => T)(prev)
        : action;

    if (!Object.is(next, prev)) {
      onChangeRef.current?.(next);          // onChange 永远回调（受控与否无关）
    }
    if (!isControlledRef.current) {
      setInternalState(next);               // 只有非受控才写内部状态
    }
  }, []);

  return [value, setValue];
}
```

三个容易被问的实现细节：

- **为什么 `onChange` 在新旧值相同（`Object.is` 相等）时不回调**：避免调用方 `setState(同值)` 触发无意义的重渲染链；这也是 React 自身 `useState` 的 bail-out 语义。
- **为什么要 `internalStateRef` 镜像**：`setValue` 被缓存成了稳定引用（`useCallback` 空依赖），闭包里的 `internalState` 会过期；受控基准走 `valueRef` 同理。
- **警告为什么写在渲染期间而不是 effect**：切换发生在渲染时，effect 里警告会晚一拍且在并发渲染下可能不触发；渲染期间 `console.warn` 是安全的（不产生副作用语义冲突）。

### A1.4 三个双模式组件：Switch / Input / Select

**Switch**（boolean 值，考点：点击后 UI 是否翻转取决于谁）：

```tsx
// Switch.tsx
import * as React from 'react';
import { useControllableState } from './useControllableState';

export interface SwitchProps {
  checked?: boolean;                            // 受控：传了它就是受控模式
  defaultChecked?: boolean;                     // 非受控初值
  onCheckedChange?: (checked: boolean) => void; // 命名对齐 WAI-ARIA 的 switch 模式
  disabled?: boolean;
  className?: string;
}

export const Switch = React.forwardRef<HTMLButtonElement, SwitchProps>(
  function Switch({ checked, defaultChecked = false, onCheckedChange, disabled, className }, ref) {
    const [state, setState] = useControllableState<boolean>({
      value: checked,
      defaultValue: defaultChecked,
      onChange: onCheckedChange,
    });

    return (
      <button
        ref={ref}
        type="button"                       // 防止在 form 里被当成 submit 触发器
        role="switch"                       // ARIA switch 语义（详见 A5）
        aria-checked={state ?? false}
        aria-disabled={disabled}
        disabled={disabled}
        className={className}
        onClick={() => setState((prev) => !prev)} // 点击只"上报意图"：受控时 UI 动不动看 props
      >
        <span className="switch-thumb" />
      </button>
    );
  }
);
```

**Input**（string 值，考点：`defaultValue` 只消费一次）：

原生 `<input>` 的 `value` 类型是 `string | ReadonlyArray<string> | number | undefined`，`onChange` 是完整事件对象。库组件不想要这么宽的签名——受控判定要的是干净的 `string | undefined`，业务方九成只关心值。所以先用 `Omit` 把值三件套从原生 props 里剔除，再按库的语义重新声明：

```tsx
// Input.tsx
import * as React from 'react';
import { useControllableState } from './useControllableState';

export interface InputProps
  extends Omit<
    React.ComponentPropsWithoutRef<'input'>,
    'value' | 'defaultValue' | 'onChange'
  > {
  value?: string;   // 显式收回并收窄：受控判定只认 string | undefined
  defaultValue?: string;
  onValueChange?: (value: string) => void;               // 值回调：业务最常用的形态
  onChange?: React.ChangeEventHandler<HTMLInputElement>;  // 原生事件回调保留给高级用法
}

export const Input = React.forwardRef<HTMLInputElement, InputProps>(
  function Input({ value, defaultValue, onValueChange, onChange, ...rest }, ref) {
    const [state, setState] = useControllableState<string>({
      value,
      defaultValue,
      onChange: onValueChange,
    });
    return (
      <input
        ref={ref}
        value={state ?? ''}
        onChange={(e) => {
          setState(e.currentTarget.value); // 统一走双模式写路径：受控与非受控都在这里分叉
          onChange?.(e);                    // 原生事件仍透传（A8 的 props 合并纪律）
        }}
        {...rest}
      />
    );
  }
);
```

这个"Omit + 重新声明"的纪律不只为类型好看：如果放任原生 `value` 混进 `rest` 再 `{...rest}` 展开，组件会在 JSX 里同时写 `value={state}` 和 `rest` 里的 `value`，展开顺序一旦颠倒，受控判定整个失效——这也是 antd 的 Input 选 `onChange: (e) => void`、而新一代库（Radix 系）选 `onValueChange` 这类收敛式签名的原因：**库的 props 协议必须是显式的，不能靠继承来的宽类型蒙混**。

**Select**（考点：一个组件里有两个受控维度——`value` 与 `open` 各自独立双模式）：

```tsx
// MiniSelect.tsx
import * as React from 'react';
import { useControllableState } from './useControllableState';

export interface SelectOption { value: string; label: string }

export interface MiniSelectProps {
  options: SelectOption[];
  value?: string;                      // 维度一：选中值
  defaultValue?: string;
  onChange?: (value: string) => void;
  open?: boolean;                      // 维度二：展开状态（也允许受控！）
  defaultOpen?: boolean;
  onOpenChange?: (open: boolean) => void;
}

export const MiniSelect = React.forwardRef<HTMLButtonElement, MiniSelectProps>(
  function MiniSelect(props, ref) {
    const { options, value, defaultValue, onChange, open, defaultOpen, onOpenChange } = props;

    // 两套双模式互不干扰：父组件可以只受控 value、放开 open
    const [selected, setSelected] = useControllableState<string>({
      value, defaultValue, onChange,
    });
    const [isOpen, setOpen] = useControllableState<boolean>({
      value: open, defaultValue: defaultOpen, onChange: onOpenChange,
    });

    return (
      <div className="mini-select">
        <button
          ref={ref}
          type="button"
          aria-haspopup="listbox"                 // 触发器语义（A5 详述）
          aria-expanded={isOpen ?? false}
          onClick={() => setOpen((prev) => !prev)}
        >
          {options.find((o) => o.value === selected)?.label ?? '请选择'}
        </button>
        {isOpen && (
          <ul role="listbox" className="mini-select__list">
            {options.map((opt) => (
              <li
                key={opt.value}
                role="option"
                aria-selected={opt.value === selected}
                onClick={() => {
                  setSelected(opt.value);
                  setOpen(false);               // 选中后收起（受控 open 时只是上报）
                }}
              >
                {opt.label}
              </li>
            ))}
          </ul>
        )}
      </div>
    );
  }
);
```

**验证矩阵**（写完三个组件后逐行手测，这是 A1 的验收标准）：

| 操作 | 非受控（只传 default*） | 受控（传 value + onChange） |
|---|---|---|
| 点击 Switch / 输入 Input | UI 立即变化，`onChange` 回调 | **UI 不动**，只有 `onChange` 回调；父组件回写 value 后才动 |
| 外部异步把 `value` 改为 'x' | 无该 props，无效果 | UI 同步为 'x' |
| 挂载后再改 `defaultValue` | **无效果**（惰性消费一次） | — |
| 先传 `value` 后移除该 prop | 控制台切换警告，退回内部 state | — |
| Select 只受控 `open` 不受控 `value` | — | 展开收起由父管，选中值自由 |

### A1.5 受控不回显的 bug 复现

症状：受控模式下输入框打字无反应、Switch 点不动，控制台可能伴随 React 警告。两个复现：

```tsx
// 复现一：调用方的 bug —— 传了 value 却不处理变化
function FrozenInput() {
  const [value, setValue] = React.useState('初始');
  return <input value={value} onChange={(e) => {
    // 忘了 setValue：受控值永远不变 → 输入无反应（React 还会警告 value 无 onChange 处理）
    console.log('用户想输入', e.target.value);
  }} />;
}

// 复现二：组件库的 bug —— 受控时仍把值写进内部 state，渲染却信内部 state
function BuggySwitch({ checked, defaultChecked }: { checked?: boolean; defaultChecked?: boolean }) {
  // 错误：渲染基准永远是内部 state → 外部受控 value 变了 UI 不跟（脱钩）
  const [internal, setInternal] = React.useState(defaultChecked);
  return (
    <button type="button" role="switch" aria-checked={internal}
      onClick={() => setInternal(!internal)}>
      {String(internal)}
    </button>
  );
}
```

复现一是**受控语义的正确表现**（父不回写，UI 就该不动）——修法在调用方：`setValue(e.target.value)`。复现二是**组件实现错误**——修法即 A1.3 的 hook：渲染基准 = `isControlled ? valueProp : internalState`，两者取其一，永不同时信两个来源。

### A1.6 常见坑

1. **`value !== undefined` vs `'value' in props`**。症状：调用方写 `<Input value={cond ? text : undefined} />`，条件翻转时组件在受控/非受控间横跳并触发警告。根因：`undefined` 被当成"没传"。修法：契约上明确"不传就不受控"，调用方应整体不传 props（用条件展开 `{...(cond ? { value: text } : {})}`）；库侧保持 `!== undefined` 判定即可。
2. **`defaultValue` 传了 `null`**。症状：`useState(null)` 后 `value ?? ''` 渲染为空但类型上是 null，后续逻辑按 string 处理崩掉。根因：API 类型没收窄。修法：props 类型只允许 `undefined`（不写 `| null`）；需要"清空"语义时走显式的 `allowClear`/`reset()`（A8 的实例方法）。
3. **受控 + `useState` 镜像双写**。症状：输入偶发"吞字"或回退一个字符（中文输入法组合期间尤其明显）。根因：组件内部 `useEffect(() => setInternal(value), [value])` 做了受控镜像 + 组合输入（`compositionstart/end`）期间强制回写 DOM。修法：删掉镜像 state，非受控就完全交给 `useState`，受控就完全交给 props——同一个值的来源必须唯一。

### A1.7 受控报警：把双模式契约做成运行时校验

**是什么**：A1.3 的切换警告只覆盖了"模式切换"一种违规。完整的双模式契约还有两条：`value` 与 `defaultValue` 互斥（同传是未定义行为）、受控模式下不允许出现"传了 `value` 却没有对应回调"的半受控用法。把契约收敛成一个**可单测的纯函数校验器**，开发期在 hook 里调用，生产构建剔除——这是 antd 的 `devWarning`、Radix 的 `console.warn` 段落的通用形态。

**为什么难**：

1. 类型层管不住。理论上可以用可辨识联合表达互斥（`{ value: T } | { defaultValue: T }`），但业务代码里大量 `value={cond ? text : undefined}` 的间接写法让联合类型形同虚设；而且"这轮传下轮不传"（模式切换）在类型上完全合法。
2. React 只对原生 `input` 的"value 无 onChange"发警告，对库组件的契约一无所知。
3. 报警不能刷屏：每次渲染都 `console.warn` 会在高频输入时把控制台打爆，必须做"同一违规只报一次"。

**机制**：

1. 校验器是纯函数：输入"上一次快照 + 本次 props"，输出违规列表（可穷举单测）；
2. hook 里只在"违规集合变化"时输出，天然去重（StrictMode 双渲染也只报一次）；
3. 分级：同传 `value` + `defaultValue` 用 `console.error`（行为未定义）；模式切换用 `console.warn`；
4. `process.env.NODE_ENV !== 'production'` 守卫 + 打包器 dead-code elimination，生产零成本（C 篇构建产物的纪律前哨）。

```ts
// checkControllableProps.ts —— 纯函数：可单测的契约校验器
export type ControllableViolation =
  | { kind: 'both'; name: string; defaultName: string }
  | { kind: 'switch'; name: string; from: boolean; to: boolean };

export interface CheckSnapshot {
  /** 上一次渲染是否受控；null 表示首次渲染（首次切换不算违规） */
  wasControlled: boolean | null;
}

export function checkControllableProps(
  componentName: string,
  valueProps: { value?: unknown; defaultValue?: unknown },
  prev: CheckSnapshot | null
): { violations: ControllableViolation[]; next: CheckSnapshot } {
  const violations: ControllableViolation[] = [];
  const isControlled = valueProps.value !== undefined;

  if (isControlled && valueProps.defaultValue !== undefined) {
    violations.push({ kind: 'both', name: 'value', defaultName: 'defaultValue' });
  }
  if (prev?.wasControlled != null && prev.wasControlled !== isControlled) {
    violations.push({
      kind: 'switch', name: 'value',
      from: prev.wasControlled, to: isControlled,
    });
  }
  return { violations, next: { wasControlled: isControlled } };
  // componentName 供调用方（hook）拼错误信息用；纯函数本身不碰 console，测试无噪音
  void componentName;
}
```

```tsx
// useControllableWarning.ts —— 开发期报警：违规集合变化时才输出
import * as React from 'react';
import {
  checkControllableProps,
  type CheckSnapshot,
  type ControllableViolation,
} from './checkControllableProps';

function format(componentName: string, v: ControllableViolation): string {
  if (v.kind === 'both') {
    return (
      `[${componentName}] 同时传了 ${v.name} 与 ${v.defaultName}：` +
      `受控优先生效，${v.defaultName} 被静默忽略。请只传其一。`
    );
  }
  return (
    `[${componentName}] 在受控/非受控之间切换` +
    `（${v.from ? '受控→非受控' : '非受控→受控'}），值会跳变。` +
    `请保证 ${v.name} 要么一直传、要么一直不传。`
  );
}

export function useControllableWarning(
  componentName: string,
  props: { value?: unknown; defaultValue?: unknown }
): void {
  if (process.env.NODE_ENV === 'production') return; // 生产剔除（打包器会裁掉整个分支）
  const prevRef = React.useRef<CheckSnapshot | null>(null);
  const lastReportedRef = React.useRef('');

  const { violations, next } = checkControllableProps(
    componentName, props, prevRef.current
  );
  prevRef.current = next;

  const message = violations.map((v) => format(componentName, v)).join('\n');
  if (message !== '' && message !== lastReportedRef.current) {
    console.error(new Error(message)); // 用 Error 包一层：控制台能跳到调用方堆栈
    lastReportedRef.current = message; // 同一违规不再重复报（输入高频渲染下不刷屏）
  }
}
```

接入方式：在 A1.3 的 `useControllableState` 顶部加一行 `useControllableWarning('useControllableState', params)`；组件层再传自己的名字（如 `'Select'`），让用户在控制台一眼看到是谁违规。boolean 组件把 `checked/defaultChecked` 映射到 `value/defaultValue` 再调同一个校验器，别名对不需要第二套逻辑。

坑：

1. **报警重复两次**。症状：StrictMode 下同一条警告打印两遍。根因：报警写在 effect 里（双调用）。修法：渲染期同步比较"上次集合"（上面的 ref 快照法），StrictMode 的双渲染第二次比较结果为"没变化"，自然去重。
2. **`'value' in props` 式误报**。症状：调用方写 `<Input value={cond ? text : undefined} />` 被判为模式切换。根因：校验器与实现采用了不同判定（A1.6 坑 1）。修法：校验器与渲染判定共用同一入口（都走 `!== undefined`），报警文案里给出条件展开的写法建议。
3. **报警没带组件名/修法**。症状：用户截图来问"这个警告哪来的"。修法：文案必含 componentName 与一句修法（上面 format 的模板），这是库的可支持性成本最低的投入。

### A1.8 defaultValue 快照与重渲染边界

**是什么**：`useState(defaultValue)` 只消费一次（A1.1），意味着**父组件后续改 `defaultValue` 一律无效**。对静态表单这是特性（父刷新不打扰用户输入）；对"异步详情数据驱动表单初值"（接口回来才有 defaultValue）这是缺陷——组件早已用 `undefined` 初始化完了。本节明确这条重渲染边界的语义，并给出异步初值的三种策略与其中最细粒度一种的实现。

**为什么难**：

1. 初值到达时机与挂载时机解耦：接口 300ms 后回来，`defaultValue` 才第一次有值——但组件已经不是"首次渲染"了；
2. "外部初值同步"必须让位于"用户已输入"：接口晚到时用户可能已经填了几个字段，粗暴同步会吃掉输入；
3. 引用类型初值（数组/对象）每次渲染都是新引用，靠引用触发的 effect 一碰就死循环。

三种异步初值策略对比（先决策再动手）：

| 策略 | 做法 | 代价 | 适用 |
|---|---|---|---|
| key 重置 | `<Form key={data.id}>` 整体重挂载 | 焦点、滚动、退出动画全丢 | 编辑对象整体切换 |
| 等数据再挂载 | `data ? <Form/> : <Skeleton/>` | 多一层加载态 | 初值是硬前置 |
| pristine 同步（本节） | 组件内跟踪"用户是否编辑过"，未编辑期间接受新 defaultValue | 实现最细、要防引用抖动 | 表单先上屏、数据后到 |

**机制（pristine 同步）**：

1. `pristineRef`：任一写路径触发即置 false（用户已接管所有权）；
2. 同步条件三连：非受控 && pristine && `!Object.is(defaultValue, lastSynced)`——引用比较防止同值新引用反复触发；
3. `lastSyncedRef` 记录"已经同步过的那份初值"，是防抖动的基准线。

```tsx
// useAsyncDefaultValue.ts —— 非受控 + 未编辑期间接受迟到的 defaultValue
import * as React from 'react';
import { useControllableState, type SetStateAction } from './useControllableState';

export interface UseAsyncDefaultValueParams<T> {
  value?: T;
  /** 非受控初值：允许异步到达；仅在组件未被用户编辑期间生效 */
  defaultValue?: T;
  onChange?: (value: T) => void;
}

export function useAsyncDefaultValue<T>({
  value,
  defaultValue,
  onChange,
}: UseAsyncDefaultValueParams<T>): [T | undefined, (action: SetStateAction<T>) => void] {
  const [state, setState] = useControllableState<T>({ value, defaultValue, onChange });
  const pristineRef = React.useRef(true);
  const lastSyncedRef = React.useRef<T | undefined>(defaultValue);

  React.useEffect(() => {
    if (value !== undefined) return;                    // 受控：props 就是真相，无需同步
    if (!pristineRef.current) return;                   // 用户编辑过：外部初值让位
    if (Object.is(defaultValue, lastSyncedRef.current)) return; // 没真变（防引用抖动）
    lastSyncedRef.current = defaultValue;
    setState(defaultValue as SetStateAction<T>);
  }, [value, defaultValue, setState]);

  const set = React.useCallback(
    (action: SetStateAction<T>) => {
      pristineRef.current = false;                      // 一切写路径都视为"用户已编辑"
      setState(action);
    },
    [setState]
  );

  return [state, set];
}
```

坑：

1. **内联对象/数组初值打回用户输入**。症状：父组件每帧传新引用的 `defaultValue`（没 useMemo），组件在用户未输入期间被反复重置。根因：`Object.is` 对同内容不同引用判"变了"。修法：文档强制初值 memo 化；或库侧对小体积值做结构比较（先量化成本再上）。
2. **key 重置滥用**。症状：`key={JSON.stringify(data)}` 导致每次数据刷新整个表单重建、焦点丢失。修法：key 只绑"编辑对象身份"（如 `data.id`），不绑内容。
3. **reset 与 pristine 的契约**。症状：业务调 `form.resetFields()` 之后，新的 defaultValue 又不生效了。根因：reset 恢复了值但没恢复 pristine。修法：库的 reset 必须**同时**置 `pristine = true` 并更新 `lastSyncedRef` 基准——这两个 ref 是一套语义，拆开必出 bug。

### A1.9 表单级泛化：一次接入整个表单的 useControllable

**是什么**：A1.3 是"一个字段一个 hook"。表单场景的真实需求是"一个 store 接管 N 个字段"，并且**字段级混合受控**依然成立：`name="city"` 的字段外部受控、`name="remark"` 的字段完全非受控，同住一个表单里互不干扰。antd Form（rc-field-form）、react-hook-form 都是这一层的产物——本节手写它的最小内核，看清"双模式 hook 上移到表单级"后多出来的三件事：注册时序、字段订阅、卸载保留策略。

**为什么难**：

1. 字段挂载顺序不定、动态增删（条件字段、分步表单），store 不能假设字段集合固定；
2. 重渲染边界：一个字段击键不能让全表单重渲染——必须字段级订阅（30 个字段的全表单受控会让每次击键渲染 30 个组件，这正是"全受控表单"被诟病的原因）；
3. 受控与非受控字段混住：外部 `value` 与 store 内部值谁是真相，必须有一条不二义的所有权规则。

**机制**：

1. **store**：`values` 对象 + 按字段名的 listener 集合；`setValue` 同值短路（`Object.is`），变更只通知该字段的订阅者；
2. **字段订阅**：`useSyncExternalStore` 以字段为粒度订阅，`getSnapshot` 返回 store 里的原始值（引用天然稳定——A5 常见坑 1"getSnapshot 现场造新引用"的反面教材在 Toast 节讲过，同一纪律）；
3. **字段级双模式**：外部传了 `value` 的字段，读取以外部为准（受控），写入仍回写 store（供 `getValues()` 汇总）并回调字段级 `onValueChange`——所有权规则一句话：**读受外部、写必经 store**。

```tsx
// formStore.ts —— 表单级受控泛化：字段订阅制 store + Form/useField
import * as React from 'react';

type Listener = () => void;

export interface FormStore<T extends Record<string, unknown>> {
  getValue<K extends keyof T & string>(name: K): T[K] | undefined;
  setValue<K extends keyof T & string>(name: K, value: T[K]): void;
  subscribe(name: string, listener: Listener): () => void;
  getValues(): T;
}

export function createFormStore<T extends Record<string, unknown>>(): FormStore<T> {
  let values = {} as T;
  const listeners = new Map<string, Set<Listener>>();

  return {
    getValue: (name) => values[name],
    setValue: (name, value) => {
      if (Object.is(values[name], value)) return; // 同值短路：不打扰任何订阅者
      values = { ...values, [name]: value };      // 整体替换 values，字段引用稳定
      listeners.get(name)?.forEach((fn) => fn()); // 只通知这一字段的订阅者
    },
    subscribe: (name, listener) => {
      let set = listeners.get(name);
      if (!set) listeners.set(name, (set = new Set()));
      set.add(listener);
      return () => set.delete(listener);
    },
    getValues: () => values,
  };
}

const FormStoreContext = React.createContext<FormStore<Record<string, unknown>> | null>(null);

export function Form<T extends Record<string, unknown>>({
  initialValues,
  onFinish,
  children,
}: {
  initialValues?: Partial<T>;
  onFinish?: (values: T) => void;
  children: React.ReactNode;
}) {
  const storeRef = React.useRef<FormStore<T> | null>(null);
  if (storeRef.current === null) storeRef.current = createFormStore<T>();

  React.useEffect(() => {
    // initialValues 只在挂载时灌一次：表单级的 defaultValue 惰性消费（A1.1 的纪律上移一层）
    (Object.keys(initialValues ?? {}) as (keyof T & string)[]).forEach((k) => {
      storeRef.current!.setValue(k, initialValues![k]);
    });
    // eslint-disable-next-line react-hooks/exhaustive-deps -- 初值只灌一次是本 API 的语义
  }, []);

  return (
    <FormStoreContext.Provider
      value={storeRef.current as unknown as FormStore<Record<string, unknown>>}
    >
      <form
        onSubmit={(e) => {
          e.preventDefault();
          onFinish?.(storeRef.current!.getValues());
        }}
      >
        {children}
      </form>
    </FormStoreContext.Provider>
  );
}

export interface UseFieldOptions<T> {
  /** 字段级受控值：传了它，本字段读以它为准（与 A1.3 同一条判定） */
  value?: T;
  onValueChange?: (value: T) => void;
}

export function useField<T>(name: string, options?: UseFieldOptions<T>) {
  const store = React.useContext(FormStoreContext);
  if (!store) throw new Error('[useField] 必须在 <Form> 内使用');

  // 字段级订阅：本字段值变化才触发本组件重渲染（重渲染边界的实现核心）
  const storeValue = React.useSyncExternalStore(
    React.useCallback((cb: Listener) => store.subscribe(name, cb), [store, name]),
    () => store.getValue(name) as T | undefined,
    () => undefined // SSR：表单初值本就该由服务端注入 HTML，客户端 hydration 后首拍为空
  );

  const setValue = React.useCallback(
    (next: T) => {
      store.setValue(name, next); // 写必经 store：getValues() 才能汇总到非受控字段
      options?.onValueChange?.(next);
    },
    [store, name, options]
  );

  // 所有权规则：读受外部（受控），否则读 store（非受控）
  const value = options?.value !== undefined ? options.value : storeValue;
  return { value, setValue };
}
```

使用形态（一个表单里混两种模式，代码完全对称）：

```tsx

  );
}

function RemarkInput() {
  const { value, setValue } = useField<string>('remark'); // 纯非受控：提交时 getValues 能拿到
```

与成熟库的对照（知道我们省了什么）：rc-field-form 还有字段注册/卸载的 `preserve`（卸载后值是否保留）、依赖联动 `shouldUpdate`、校验器队列；react-hook-form 走另一极端——**非受控优先**（register + ref，不击键不重渲染），受控需求用 `Controller` 补。我们的 80 行内核对应它们的"值所有权 + 订阅"骨架，其余都是外围。

坑：

1. **getSnapshot 返回新引用**。症状：接入后 `Maximum update depth exceeded`。根因：某字段值是对象，`getValue` 现场拼新对象返回。修法：store 里字段值**整字段替换**（`values = { ...values, [name]: value }`），任何派生值（如 `getValues()` 的聚合）绝不能当 getSnapshot。
2. **受控字段的"影子值"打架**。症状：受控字段的外部 value 变了，`getValues()` 里却是旧值。根因：受控字段没回写 store。修法：把"写必经 store"写进 API 契约（本节实现即如此）；或提供 `watch(name)` 读取时优先合并外部受控值——但两条路只能选一条并写死文档。
3. **字段卸载值残留**。症状：切换步骤后提交，上一步的字段值还在 `getValues()` 里。根因：store 不知道字段卸载（我们没做注册生命周期）。修法：加 `register/unregister`，默认保留（antd 的 `preserve` 语义），业务要"切走即清"时显式配置——**默认值的选择就是 API 设计**，不能含糊。
4. **SSR 首拍闪烁**。`getServerSnapshot` 返回 undefined 后客户端首拍是空表单，若 initialValues 已知，应在服务端渲染时就注入 store（用 `useRef` 初始化时灌初值，而不是 effect 里），避免 hydration 后二次跳动。
