### 坑

#### ⚠️ 坑 1：操作符切换后旧 value 类型残留（`>` 的数字 vs `in` 的数组）

- **症状**：用户把"金额 > 100"的操作符从 `>` 换成 `in`，值编辑器切成多选框但显示为空；保存后后端执行报 `{"in": [{"var": "amount"}, 100]}`——`100` 不是数组，规则引擎抛类型错误。或反向：`in` 换成 `>`，值编辑器是数字框却收到 `["BJ"]`，渲染 NaN。更隐蔽的变体：`between` 切到 `=`，value 是 `[100, 200]` 二元数组，比较永远为 false 且不报错。
- **根因**：`operator` 与 `value` 是状态里两个独立字段，编辑器各改各的。切操作符只写了 `operator`，旧 `value` 原地保留——它对新操作符来说类型是错的。UI 上"编辑器正确切换了"掩盖了"数据没清干净"：用户看到空的多选框以为没选值，不知道底下压着一个数字 100。根子是**联动变更被拆成了两次非原子更新**。
- **修法**：联动收敛为一次原子更新——§3.3 的 `applyOperatorChange` 是唯一出口，切换操作符的瞬间按新编辑器重置 value：

```ts
// 唯一合法的操作符切换路径（回顾 §3.3，坑 1 的正解）：
// QueryRow 里 onChange 调 applyOperatorChange，而不是手动 {...node, operator: next}
export function applyOperatorChange(
  node: ConditionNode,
  nextOperator: Operator,
  field: FieldMeta | undefined,
): ConditionNode {
  if (!field) return { ...node, operator: nextOperator }
  const editor = resolveValueEditor(field, nextOperator)
  // 关键：value 与 operator 在同一个新对象里落位，不存在"新操作符配旧值"的中间态
  return { ...node, operator: nextOperator, value: defaultValueFor(field, editor) }
}
```

再补两道纵深防御：值编辑器入口做类型规整（数组进单值编辑器按空处理而非崩溃）；§3.5 转换层对 in/between 的 value 做形状检查（非二元数组/非数组直接抛，脏数据死在关口不进后端）。

#### ⚠️ 坑 2：元数据删除字段后，存量规则条件悬空（需要迁移或标红提示）

- **症状**：某次需求迭代把字段表里的 `deptCode` 下掉了。之后打开两年前配置的告警规则，页面白屏（`fieldMap.get('deptCode')` 为 undefined，取 `field.operators` 崩溃）；修好白屏后又发现字段下拉显示空白行、操作符下拉是空的，用户不知道这行是什么、能不能删；最坏情况：后端规则引擎执行该规则时静默跳过悬空条件——该告的警没人告。
- **根因**：协议里的 `field` 是字符串引用，字段元数据表是独立演进的数据源，两者之间**没有外键约束**——元数据删除不级联、不检查存量引用。这是所有"数据引用另一份可变数据"系统的通病（模板过期、看板引用下线组件、菜单引用下线权限码，全是同构问题）。
- **修法**：三道防线，缺一不可。

第一道，**下线流程改为软删除**：元数据不物理删除，打 `deprecated: true`（§3.3 已支持）——新规则的字段下拉过滤掉它（§3.2 的 filter），存量规则渲染正常但标红提示"字段已下线"（§3.6 校验已产出该错误）。给元数据变更立规矩：删除必须先跑引用审计、观察一个发布周期、再物理清理。

第二道，**渲染容错**：渲染层对悬空字段永远不崩，降级为"红牌行"：

```tsx
// DanglingFieldRow.tsx —— 悬空字段的降级渲染：不崩溃、标红、可手动删除
import type { ConditionNode } from './condition-tree'

export function DanglingFieldRow({ node, onRemove }: {
  node: ConditionNode
  onRemove: () => void
}) {
  return (
    <div className="qb-row qb-row--error" role="alert">
      <span className="qb-dangling-field">未知字段「{node.field}」（已下线）</span>
      <span className="qb-row-error">该条件已失效，请删除此行或联系管理员迁移规则</span>
      <button type="button" onClick={onRemove}>删除此行</button>
    </div>
  )
}
```

第三道，**批量审计与迁移**：管理侧脚本扫全库规则，产出悬空报告，并提供自动剥离（剥离后必须重新过人工确认，因为删条件会改变规则语义——"且"关系里删一行，规则变宽松）：

```ts
// rule-audit.ts —— 存量规则体检：悬空字段审计 + 自动剥离
import type { ConditionTree, ConditionTreeNode } from './condition-tree'
import { createGroup } from './tree-ops'
import type { FieldMeta } from './field-meta'

export interface DanglingReport {
  ruleId: string
  nodeId: string
  field: string
}

export function auditTree(ruleId: string, tree: ConditionTree, fieldMap: Map<string, FieldMeta>): DanglingReport[] {
  const reports: DanglingReport[] = []
  const walk = (n: ConditionTreeNode): void => {
    if (n.kind === 'condition') {
      if (!fieldMap.has(n.field)) reports.push({ ruleId, nodeId: n.id, field: n.field })
      return
    }
    n.children.forEach(walk)
  }
  walk(tree)
  return reports
}

/** 自动剥离悬空条件（空组随之剪枝）。注意：剥离改变规则语义，产物必须走人工确认再落库 */
export function stripInvalidNodes(node: ConditionTreeNode, fieldMap: Map<string, FieldMeta>): ConditionTreeNode | null {
  if (node.kind === 'condition') return fieldMap.has(node.field) ? node : null
  const children = node.children
    .map(c => stripInvalidNodes(c, fieldMap))
    .filter((c): c is ConditionTreeNode => c !== null)
  return children.length > 0 ? { ...node, children } : null
}
```

#### ⚠️ 坑 3：深层嵌套 UI 溢出（缩进 + 折叠策略）

- **症状**：用户嵌了 6 层组，每层缩进 16px 加边框圆角，内容区被挤得只剩三分之一，第 5 层的值编辑器（尤其 between 的双输入框）横向溢出、被右边缘裁切；换成小屏笔记本或平板，第 4 层就开始溢出。滚动条出现后，用户拖拽排序时看不到目标组全貌，误操作率飙升。
- **根因**：横向空间是线性资源，嵌套深度每加一，内容区宽度就减 16px+边框——递归结构与有限视宽是天然矛盾。而"嵌套深度上限"校验（§3.6）挡的是协议层，用户在达到上限前就已经处在不可用的 UI 里了：**校验上限（协议健康）与视觉可用性（交互健康）是两条线，后者必须由渲染策略自己解决**。
- **修法**：缩进封顶 + 折叠 + 面包屑三招。

```tsx
// DeepGroupFrame.tsx —— 深层组的"封顶缩进 + 默认折叠 + 路径面包屑"策略
import { useState, type ReactNode } from 'react'
import type { GroupNode } from './condition-tree'
import { countConditions } from './tree-ops'

export function DeepGroupFrame({ node, depth, breadcrumb, children }: {
  node: GroupNode
  depth: number
  breadcrumb: string   // 如 "根 › 内层1 › 内层2"，渲染在折叠条上
  children: ReactNode
}) {
  const [collapsed, setCollapsed] = useState(depth > 3) // 第 3 层以下默认折叠：先给全景，再按需展开
  const indent = Math.min(depth - 1, 3) * 16            // 缩进第 3 层封顶，不再线性吃宽度

  return (
    <div
      style={{
        marginLeft: indent,
        // 超过封顶深度后改用左侧色条表达层级，宽度成本恒定（2px），与深度无关
        borderLeft: depth > 3 ? '2px solid #9aa8b8' : undefined,
        paddingLeft: depth > 3 ? 8 : undefined,
      }}
    >
      <button type="button" className="qb-collapse-toggle" onClick={() => setCollapsed(c => !c)}>
        {collapsed ? '▸' : '▾'} {breadcrumb}
        <span className="qb-collapse-summary">
          {node.combinator === 'and' ? '且' : '或'} · {countConditions(node)} 个条件
        </span>
      </button>
      {!collapsed && <div className="qb-collapse-body">{children}</div>}
    </div>
  )
}
```

策略拆解：**封顶缩进**让宽度损失是 `O(min(depth, 3))` 而非 `O(depth)`，第 4 层起改用左色条+深度徽标表达层级，视觉信息不丢、宽度成本恒定；**默认折叠**（深于 3 层）保证用户看到的永远是一屏内的全景，折叠条上的"且/或 · N 个条件"摘要让不开折叠也能掌握结构；**面包屑**解决"我这是在第几层"的迷失问题。三招叠加后，再配合 §3.6 的 `maxDepth` 校验（默认 5），UI 可用性与协议健康同时闭环。产品层面还有一招治本：当检测到用户连续点"+ 子组"到第 3 层时，浮层提示"深层逻辑建议拆分为两条规则或使用表达式"——**在问题发生前引导，好过发生后补救**。

对标：**react-querybuilder（必读）**、json-logic.com、Retool 的 filter。

**react-querybuilder（架构必读）**：本章所有实现它的源码里都有对应物，读它的正确姿势是带着对照表读——`Rule`/`RuleGroup` 两个递归组件对应本章 QueryRow/QueryGroup；它的组合器模型在"组级 combinator"（默认）之外还提供 `independentCombinators` 模式（每两行之间独立放一个且/或选择器，表达力更强、复杂度也更高），本章行间 chip 是组级模型的轻量增强；它的可定制架构是精华——内部每一个控件（字段下拉、操作符下拉、值编辑器、拖拽把手、行/组容器）都通过 `controls` 属性可替换（v6 及之前叫 `controlElements`），配合按 UI 库分包的 `@react-querybuilder/antd`/`/material`/`/chakra`/`/mantine`/`/bootstrap`/`/dnd`，一套核心逻辑换皮即用——这正是"注册表换组件"思想推到极致的形态，本章 §3.4 的 `valueEditorRegistry` 是它的最小版。它的 `formatQuery` 能把内部查询对象导出为 sql / 参数化 SQL / MongoDB / json-logic / Elasticsearch / CEL / SpEL 等目标，`@react-querybuilder/parse` 提供 `parseSql` / `parseMongoDb` / `parseJsonLogic` / `parseSpel` / `parseCEL` 反向解析——与本章 §3.5 的转换层一一对位，读它的转换器源码（尤其各方言的边界 case 处理）等于给自研转换层做 code review。

**json-logic.com（执行端标准）**：它是"规则即 JSON"的跨语言标准——同一份规则，JS/Java/PHP/Python 都有实现，前后端可各自原生执行，这正是 §3.7 前端试运行与后端执行共用一份规则的基石。适用边界要认清：它擅长**对单条数据的布尔判定**（字段比较、且或非、嵌套），不擅长聚合与时间窗（"过去 5 分钟平均值 > 阈值"这类需要先聚合再判定的逻辑，属于流处理/规则引擎的职责，json-logic 只能表达聚合后的结果判定）；操作符集固定但可通过 `add_operation` 扩展（§3.7 的 `dateAfter` 示例）；深层数据取值靠 `"a.b.0.c"` 字符串路径，没有类型检查，字段名打错在编译期无感、只能靠试运行与 golden case 兜住。安全边界：规则是数据不是代码，不会像 eval 一样执行任意逻辑，但自定义算子若封装了危险能力（发请求、读文件）就等于开了口子——算子注册表要当攻击面管理。

**Retool 的 filter（交互参考）**：它的过滤面板是"渐进式披露"的教学样本——初始只有一行条件，第一行配置完才浮现"AND"按钮，用户从不需要面对一个空组；每个字段按类型给默认操作符（数字给 `=`、文本给 `contains`、枚举给 `in`），把最常用的路径铺到最短；无值操作符选中后值控件原地收起（对应本章 `none` 编辑器）；多条件升组时提供"advanced condition"入口把已有多行包进一个可切且/或的组（对应本章"+ 子组"的逆向操作，值得补一个"包组"交互）；全部操作 inline 在表格上方完成，绝不弹模态框。抄交互时抄的是这三条原则：渐进披露、按类型缩短路径、就地完成，而不是像素。

#### ⚠️ 坑 4：受控 value 引用不稳——父组件每帧新建初始树，编辑器"打一个字重置一次"

- **症状**：编辑器每秒"闪"一次或输入偶发丢失；DevTools 里 QueryBuilder 的 props `value` 每帧都是新对象；更隐蔽的变体——页面挂了个定时器（或 3.3.3 的后台保鲜），用户正在第 3 行打字，树突然回到几秒前的状态。
- **根因**：受控组件的 value 来自父组件渲染体内联创建的数据——`<QueryBuilder value={urlTree ?? createGroup()} …>`（每次渲染新树）或 `useEffect` 里 `setTree(JSON.parse(savedText))` 的引用每次不同。若编辑器内部任何地方以 `value` 引用为 effect 依赖（如 3.2.1 的 `useMemo(() => flattenTree(tree), [tree])` 本无害，但试运行 3.7 的防抖 effect 会跟着重跑），外部同内容的新引用会让"编辑中的树"被外部值覆盖。根子是**真相源边界模糊**：编辑期间真相源应是组件 state，外部 value 只在"确实发生变化"时回流。
- **修法**：初始值惰性初始化（`useState(() => parse(search))`，函数式初始化只跑一次）；外部回流前做内容比对——`treeEquals` 用签名序列化比对（3.8.3 的 `fullSignature` 现成）：

```ts
// tree-equals.ts —— 内容相等：忽略 id/引用，只比语义签名（AST 级，不比字符串）
import type { ConditionTree } from './condition-tree'

export function treeEquals(a: ConditionTree, b: ConditionTree): boolean {
  const sig = (n: ConditionTree): string =>
    n.kind === 'group'
      ? `${n.combinator}:(${n.children.map(sig).join(',')})`
      : `${n.field}|${n.operator}|${JSON.stringify(n.value)}`
  return sig(a) === sig(b)
}

// 受控回流守卫：外部值变化但内容没变时，不打断编辑中的 state
useEffect(() => {
  if (!treeEquals(tree, incoming)) setTree(incoming)
}, [incoming])
```

URL 回填只在挂载时做一次，后续路由参数变化若确需同步，走"未编辑（无脏值）才同步"守卫。

#### ⚠️ 坑 5：同一节点的多条校验错误只剩一条——`Map<nodeId, error>` 的覆盖

- **症状**：between 条件既"上限填成了文本"又"下限大于上限"，UI 只显示后者；某个空组同时触发"组不能为空"与"条件数超限"，只看到一条——用户修完一条刷新出另一条，来回两次才修干净。
- **根因**：§3.2 的错误索引是 `new Map(errors.map(e => [e.nodeId, e]))`——**Map 的键唯一，同 nodeId 的多条错误只保留最后一条**。校验器（§3.6）每条件可能产出多条（between 的形状与大小、in 的空集与非法选项），一进 Map 就互相覆盖。
- **修法**：索引改 `Map<nodeId, TreeValidationError[]>`（聚合侧 groupBy），行组件取 `errors.get(node.id) ?? []` 全量渲染：第一条展开 + `还有 N 处` 折叠；或者键加序号（`nodeId:idx`）保住列表结构但行内取值变绕——推荐前者：

```ts
// 错误索引的一行修复：Map<nodeId, error[]>（QueryBuilder 的 errors useMemo 内）
const errorIndex = new Map<string, TreeValidationError[]>()
for (const e of validateTree(value, fieldMap, opts)) {
  const list = errorIndex.get(e.nodeId) ?? []
  list.push(e)
  errorIndex.set(e.nodeId, list)         // 同节点多条错误按序全保留
}
```

配套一条单测：构造一个双错误条件（between 值形状错 + 下限大于上限），断言行内错误文案出现两次。

#### ⚠️ 坑 6：筛选条件序列化进 URL——超长被网关截断，或未编码字符还原出错树

- **症状**：高级筛选（3.0.1 业务③）分享链接，条件多了三层嵌套后链接两三千字符：微信里打不开、Nginx 返回 414；另一变体——条件值含 `&`、`+`、`#`（如订单号 `SO+2026`），接收方解析 query 时树被腰斩或值变样。
- **根因**：URL query 的两个硬边界没进设计——长度边界（浏览器 2K~8K 起，网关常见上限 4K~8K，超长直接拒）与字符边界（query 有保留字，条件树的 JSON 裸拼、`encodeURIComponent` 漏一处就静默损坏）。条件树是嵌套 JSON，体积随深度线性涨，"分享筛选"功能上线时没人测过 30 条件的树。
- **修法**：三档方案按序实施——① 短键映射压缩（体积通常砍 60%+）；② 压缩后再 `encodeURIComponent` 一次（唯一出口，收发都走同一对函数）；③ 超过阈值（如 1500 字符）不再进 URL，改"存服务端换短码"，还原时按 id 拉取——阈值判断在生成侧，不在接收侧（接收方无法知道被截断，只能失败）。短键映射的最小实现：

```ts
// url-codec.ts —— 树 ↔ URL 的唯一编解码出口（收发共用，禁止裸拼 query）
const SHORT_KEYS: Record<string, string> = {
  kind: 'k', combinator: 'c', children: 'n', id: 'i',
  field: 'f', operator: 'o', value: 'v',
}
const LONG_KEYS = Object.fromEntries(Object.entries(SHORT_KEYS).map(([l, s] as const) => [s, l]))

function shorten(node: Record<string, unknown>): Record<string, unknown> {
  const out: Record<string, unknown> = {}
  for (const [key, val] of Object.entries(node)) {
    const short = SHORT_KEYS[key] ?? key
    out[short] = Array.isArray(val) ? val.map(x => (x && typeof x === 'object' ? shorten(x) : x)) : val
  }
  return out
}

export function encodeTreeToQuery(tree: ConditionTree): string {
  return encodeURIComponent(JSON.stringify(shorten(tree as unknown as Record<string, unknown>)))
}
export function decodeTreeFromQuery(raw: string | null): ConditionTree | null {
  if (!raw) return null
  try {
    const parsed = JSON.parse(decodeURIComponent(raw)) as Record<string, unknown>
    return restoreLongKeys(parsed) as ConditionTree      // LONG_KEYS 反向替换，过程对称
  } catch {
    return null                                          // 坏链接降级为"无筛选"，绝不抛错炸页面
  }
}
```

（`restoreLongKeys` 是 `shorten` 的镜像遍历，略。id 进 URL 与否是个取舍：进则链接更长但回填后可编辑定位，不进则短——分享场景推荐不进，回填后 `deepCloneWithNewIds` 重发。）

#### ⚠️ 坑 7：多标签页并发编辑同一条规则——后保存者静默覆盖先保存者

- **症状**：运营 A、B 同时打开规则 R（一个从列表页、一个从钉钉通知深链），A 花 20 分钟改完保存；B 的页面还开着两小时前的版本，点了个"微调"保存——A 的 20 分钟成果无声消失，没有任何提示，直到 A 次日发现规则"回去了"。
- **根因**：编辑页是"打开时快照 + 提交时整树覆盖"的写模型，规则表没有版本控制——最后写入胜出（last write wins）。Web 应用的多标签页是常态入口，而查询构建器的编辑会话长（配置一棵树十几分钟），并发窗口极大。
- **修法**：乐观锁（CAS）。规则表带 `version` 字段，打开编辑器时记下 `baseVersion`，保存时带条件提交，影响行数为 0 即冲突——返回 409 + 服务端当前版本：

```ts
// 保存链路的冲突处理（REST 的 If-Match 形态）
async function saveRule(ruleId: string, baseVersion: number, tree: ConditionTree): Promise<'ok' | 'conflict'> {
  const res = await fetch(`/api/rules/${ruleId}`, {
    method: 'PUT',
    headers: {
      'Content-Type': 'application/json',
      'If-Match': String(baseVersion),        // 我改的是第几版
    },
    body: JSON.stringify({ tree }),
  })
  if (res.status === 409) return 'conflict'   // 服务端已是更高版本——有人先保存了
  if (!res.ok) throw new Error(`保存失败 HTTP ${res.status}`)
  return 'ok'
}
```

冲突后的两条路：**加载最新版重新编辑**（丢本地改动，高危，需二次确认）或**基于差异合并**（用 3.8.3 的结构化 diff 展示"你的改动 vs 他人改动"，人工合并——规则树节点有签名可配对，比文本合并可用得多）。配套：保存成功后 UI 明确展示当前版本号，让"我改的是第几版"可见。

#### ⚠️ 坑 8：SSR / 水合期生成 id——服务端与客户端 id 不同，hydration 报错或交互错乱

- **症状**：Next.js 等 SSR 框架里渲染编辑器首屏，控制台 `Hydration failed because the server rendered HTML didn't match the client`；或水合不报错但"删除第 2 行删掉的是第 3 行"（DOM 上的 id 与客户端树里的 id 对不上，事件寻址错行）。
- **根因**：初始树在**渲染体内**调用 `createGroup()` / `genId()`——SSR 在 Node 进程生成一套 UUID，水合时浏览器又执行一遍生成另一套。id 是 key、事件寻址、错误定位的地基（§3.1），两套 id 意味着服务端 HTML 与客户端虚拟树描述的不是同一棵树。`genId` 的 `Math.random()` 降级分支（§3.1）在两端必然不同，`crypto.randomUUID()` 也一样。
- **修法**：id 生成只发生在**事件与惰性初始化**里（用户点"+ 条件"、`useState(() => …)` 的首次执行——函数式初始化在客户端水合时不会重跑）；SSR 首屏需要的初始树用**确定性数据**（接口返回的存量树自带 id，或用内容派生的确定性 id）；实在要在渲染期建空树的，首帧渲染固定占位 id、挂载后再换真 id：

```tsx
// NewRuleEditor.tsx —— 新建规则的 SSR 安全写法：占位树用固定字面量 id，水合后换真 id
// 关键：占位树全树无随机——字面量 id 两端（Node/浏览器）逐字节一致，水合才能对上
const PLACEHOLDER_TREE: ConditionTree = {
  kind: 'group', id: 'root', combinator: 'and',
  children: [
    { kind: 'condition', id: 'row_1', field: 'amount', operator: '>', value: null },
  ],
}

function NewRuleEditor() {
  const [tree, setTree] = useState<ConditionTree>(PLACEHOLDER_TREE)  // 同一引用，两端一致
  const hydrated = useRef(false)

  useEffect(() => {
    if (hydrated.current) return            // 只在水合完成后执行一次（effect 不在服务端跑）
    hydrated.current = true
    setTree(deepCloneWithNewIds(PLACEHOLDER_TREE))  // 换成真 UUID，此后交互一切正常
  }, [])

  return <QueryBuilder value={tree} onChange={setTree} fields={ORDER_FIELDS} />
}
// 注意不能写成 useState(() => createGroup(...))——惰性初始化在服务端与客户端水合时各跑一次，
// genId 两端必然不同，水合照样 mismatch。占位树的"确定性"必须来自字面量，不来自"只跑一次"。
```

#### ⚠️ 坑 9：触屏设备拖不动行——dnd-kit 的 PointerSensor 缺 `touch-action: none`

- **症状**：桌面端拖拽排序一切正常，平板/手机上按住把手拖动——行不动，页面跟着滚；或拖动起手就触发浏览器长按菜单/文字选择，拖拽从未激活。
- **根因**：PointerSensor 监听 pointer 事件，但触屏上 pointerdown 之后浏览器默认行为是滚动——`touch-action` 没有禁用时，浏览器会把指针移动接管为滚动手势，dnd-kit 根本收不到后续 move 事件（这是规范行为不是 bug）。§3.2 的实现只配了 `activationConstraint: { distance: 5 }`，没配 touch-action，把手是普通 `span`。
- **修法**：把手元素加 `touch-action: none`（只加在把手上，加在整行会杀掉行内输入框的滚动与长按选词）：

```css
.qb-drag-handle {
  touch-action: none;        /* 触屏上把手区域的手势全部让给拖拽 */
  -webkit-user-select: none; /* 顺带：长按不选字 */
  user-select: none;
}
```

需要长按拖动语义（防误触）时补 TouchSensor：`useSensor(TouchSensor, { activationConstraint: { delay: 150, tolerance: 5 } })`——150ms 长按激活，期间移动 5px 内不算（滚动照常）。移动端交互的完整清单（iOS 双击缩放、橡皮筋等）属《学习大纲》阶段 4 移动端话题，此处只修拖拽激活这一处。

#### ⚠️ 坑 10：NaN 静默进树——数字编辑器把非有限数传上树，比较永远 false 且不报错

- **症状**：用户在数字框输入极端写法（粘贴 `1e999`、输入法切错输入了全角数字），保存一路绿灯；规则上线后**从不命中**——执行日志里条件是 `amount >= Infinity` 或 `NaN`，json-logic 的 `NaN >= x` 恒 false，不抛错不告警。
- **根因**：`NumberEditor` 的 `onChange={e => Number(e.target.value)}`——`type="number"` 的输入框对多数非法输入回空串，但**程序化赋值与极端值**仍可能产出 `Infinity`/`NaN`；`Number('')` 是 0（空串变零也是一类事故——"没填"变"填了 0"，风控规则 `amount > 0` 从此命中所有数据）。§3.6 校验只查了 `typeof v !== 'number'`——NaN 的 typeof 恰好是 number，类型检查对它免疫。
- **修法**：数字编辑器出口做有限性守卫（空串→null 交校验报"必填"，非有限→null 交校验报"格式"）：

```ts
// NumberEditor 的 onChange 正解：三态处理，任何情况下不允许 NaN/Infinity 上树
onChange={e => {
  const raw = e.target.value
  if (raw === '') return onChange(null)            // 空 = 未填，不是 0
  const n = Number(raw)
  onChange(Number.isFinite(n) ? n : null)          // 非有限数按未填处理，校验层给人话报错
}}
```

校验层补一条：`field.valueType === 'number'` 分支增加 `v !== null && !Number.isFinite(v)` 的防御（转换层 3.5.1 的 IR 前段同样兜一道）——三关各拦一次，任何一关漏了都有下一关。**浮点数的"看起来是数字但不是数"（NaN/Infinity/空串转 0）是数字输入的三连雷，缺省的 `Number()` 一个都挡不住**。
