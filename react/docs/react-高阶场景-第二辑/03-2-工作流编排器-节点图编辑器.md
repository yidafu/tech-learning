## 2. 工作流编排器 / 节点图编辑器

**基础**：全景图 A4 + F2。增量：

1. **节点 DSL**：`{ id, type, position, data, next: [...] }`；邻接表 → DAG 校验（拓扑排序 + 环检测，保存前必验）
2. **自定义节点 = 节点内嵌表单**（mini Setter 面板直接长在节点上）、折叠/展开、状态徽标（idle/running/success/error）
3. 连线校验：handle 类型约束（输出→输入、类型不匹配禁止连接）、连线规则回调
4. 自动布局：dagre（快）vs ELK（质量高）；用户手动布局后锁定
5. **运行态性能**：后端推送节点状态 → 高频 `setNodes` 必须合并批量更新（rAF 聚合，否则 100 节点流式更新直接卡死）
6. 撤销重做、小地图、快捷键（Cmd+D 复制节点带偏移）
7. DSL 语义升级：条件分支节点、并行网关、循环节点怎么表达

对标：n8n（源码可读性好）、Dify、Langflow、bpmn.js（重量级 BPMN，按需）

先对齐全景图的两个坐标：A4（节点编排画布）给出了 React Flow 的技术栈清单——自定义节点/边、连线校验、自动布局、运行态可视化；F2（Agent 工作流画布）进一步指出 Dify/Coze 的编排页 = A4 节点画布 + 低代码 Setter。本章就沿着这两条展开：先定协议（2.1），再把编辑器体验做全（2.2–2.6），最后给协议升级留出语义空间（2.7）。技术底座用 @xyflow/react（React Flow v12，包名从 reactflow 迁移而来，API 以 v12 为准）。

一个前置认知：工作流编辑器 = **图数据结构编辑器** + **每节点一个迷你表单**。前者是本章新知识（DAG、拓扑、连线校验、布局），后者是《进阶大纲》§3 Setter 的又一次复用——引言暗线在场景 2 的落点。

### 2.1 节点 DSL：`{ id, type, position, data, next }` 与 DAG 校验（保存前必验）

**是什么**：工作流的持久化协议。每个节点自带后继列表 `next`（邻接表），边不需要单独存储——渲染时从邻接表派生。画布坐标 `position` 只是编辑器视图信息，调度器执行时忽略它。

**为什么需要**：协议决定一切下游能力。`next` 放在节点里（而非独立的 edges 数组）有两个好处：校验时邻接表零转换成本；保存的 JSON 与调度器的输入是同一份数据，不存在"编辑器格式 → 执行格式"的双向同步。代价是 React Flow 需要 nodes/edges 两套视图状态——派生函数一行 `flatMap` 解决。

完整 TS 类型：

```ts
/** 节点类型枚举：协议演进的锚点，2.7 会在这里扩 condition/parallel/join/loop */
export type WfNodeType = 'start' | 'http' | 'condition' | 'parallel' | 'join' | 'loop' | 'end';

export interface WfNode {
  id: string;
  type: WfNodeType;
  position: { x: number; y: number }; // 画布坐标（编辑器专用，调度器忽略）
  data: Record<string, unknown>;      // 类型私有配置：url/method（http）、branches（condition）...
  next: string[];                     // 后继节点 id 列表 —— 邻接表本体
}

export interface WorkflowDSL {
  version: 1; // 协议版本号：迁移与兼容的依据（《进阶大纲》§1.1 的原则）
  name: string;
  nodes: WfNode[];
}

/** DSL → React Flow 的 edges：邻接表派生边，渲染层与协议层解耦 */
export function dslToEdges(dsl: WorkflowDSL): { id: string; source: string; target: string }[] {
  return dsl.nodes.flatMap(node =>
    node.next.map(target => ({ id: `${node.id}->${target}`, source: node.id, target })),
  );
}
```

#### 邻接表 → DAG 校验：Kahn 拓扑排序 + 环检测

**为什么保存前必验**：调度器按拓扑序推进执行（某节点完成后才调度其后继）。图里一旦有环，两种死法：按拓扑序调度 → 环上节点永远等不到"入度清零"，流程**卡死挂起**；按事件驱动调度 → 环上节点互相触发，**无限循环打爆下游**。而且工作流的执行通常发生在保存之后的某个异步时刻（定时触发/事件触发），运行期才发现环，代价是"失败的 run + 告警 + 人工回滚"；保存时前端拦截，代价是一次本地校验。此外后端也有校验，但前端先验能省一次网络往返，并把错误**定位到具体节点**（高亮成环路径），体验完全不同。

**Kahn 算法分步**：

1. 预检结构错误：`next` 指向不存在的 id（悬空边）、自环（`next` 含自身）、重复边——这些比环更常见，先挡掉；
2. 统计每个节点的**入度**（有多少条边指向它）；
3. 把入度为 0 的节点全部入队（没有前置依赖，可以立刻执行）；
4. 出队一个节点，"删掉"它的所有出边（后继入度减一），后继入度归零则入队；
5. 重复直到队空。**若出队数量 < 节点总数，说明剩下的是环**（环上节点入度永远无法归零）——被剩下的节点集合就是环成员，直接用于画布高亮。

完整代码：

```ts
export interface DagValidation {
  ok: boolean;
  cyclicNodes: string[]; // 参与环的节点 id（画布高亮用）
  errors: string[];      // 其它结构错误（人话报错，直接可展示）
}

export function validateDag(dsl: WorkflowDSL): DagValidation {
  const errors: string[] = [];

  // 步骤 1：结构预检——id 唯一性、悬空 next、自环、重复边
  const ids = new Set(dsl.nodes.map(n => n.id));
  if (ids.size !== dsl.nodes.length) errors.push('存在重复的节点 id');
  const edgeKeys = new Set<string>();
  for (const node of dsl.nodes) {
    for (const next of node.next) {
      if (!ids.has(next)) {
        errors.push(`节点 ${node.id} 的 next 指向不存在的节点 ${next}`);
        continue;
      }
      if (next === node.id) {
        errors.push(`节点 ${node.id} 自连（自环）`);
        continue;
      }
      const key = `${node.id}->${next}`;
      if (edgeKeys.has(key)) errors.push(`重复连线：${key}`);
      edgeKeys.add(key);
    }
  }
  if (errors.length > 0) return { ok: false, cyclicNodes: [], errors };

  // 步骤 2：入度表（邻接表就是 node.next，无需另建）
  const indegree = new Map<string, number>(dsl.nodes.map(n => [n.id, 0]));
  const nodeById = new Map(dsl.nodes.map(n => [n.id, n]));
  for (const node of dsl.nodes) {
    for (const next of node.next) {
      indegree.set(next, (indegree.get(next) ?? 0) + 1);
    }
  }

  // 步骤 3：入度为 0 的节点入队
  const queue: string[] = [...indegree.entries()].filter(([, d]) => d === 0).map(([id]) => id);
  const ordered: string[] = [];

  // 步骤 4：出队 → 后继入度减一 → 归零入队
  while (queue.length > 0) {
    const id = queue.shift()!;
    ordered.push(id);
    for (const next of nodeById.get(id)!.next) {
      const remain = (indegree.get(next) ?? 0) - 1;
      indegree.set(next, remain);
      if (remain === 0) queue.push(next);
    }
  }

  // 步骤 5：摘不完 = 有环；剩下的就是环成员
  if (ordered.length === dsl.nodes.length) {
    return { ok: true, cyclicNodes: [], errors: [] }; // ordered 本身就是一个合法拓扑序，可直接喂给调度器
  }
  const cyclicNodes = dsl.nodes.filter(n => !ordered.includes(n.id)).map(n => n.id);
  return {
    ok: false,
    cyclicNodes,
    errors: [`检测到环，涉及节点：${cyclicNodes.join(' → ')}`],
  };
}
```

保存按钮的接线方式：`const check = validateDag(currentDsl)`；`!check.ok` 时保存按钮置灰 + 错误面板列出 `errors` + 画布上把 `cyclicNodes` 对应节点标红（把 id 集合存 state，自定义节点读它渲染红框）。

**常见坑**：

- **症状**：校验通过但运行时还是卡死。**根因**：环检对了，但流程没有 `start`/`end` 语义，调度器从"入度 0 节点"开始跑、到"出度 0 节点"结束，而协议里某些节点（如手动审批回调）入度不为 0 也没有 start 边。**修法**：校验里加业务断言——恰一个 `start`、至少一个 `end`、除 `end` 外节点必须有后继（`next.length > 0`）。
- **症状**：删除节点后 `next` 悬空，校验报错用户却看不到哪条边。**根因**：悬空边在 `dslToEdges` 派生时 target 不存在，画布上根本不渲染，错误不可见。**修法**：删除节点时**级联清理**所有指向它的 `next` 项（删除操作在协议层完成，而不是只删 nodes 数组）。
- **症状**：2.7 引入循环节点后，合法流程被环检测误杀。**根因**：循环的语义回边若写进 `next`，DAG 不再成立。**修法**：见 2.7——把循环语义放进节点 `data`，邻接表保持无环（这是协议设计的关键权衡）。

### 2.2 自定义节点 = 节点内嵌表单（mini Setter 面板）、折叠/展开、状态徽标

**是什么**：n8n/Dify 式节点——双击节点（或选中即）在节点卡片上直接编辑配置，而不是只能去右侧属性面板。节点 = 卡片头部（图标 + 标题 + 状态徽标）+ 可折叠的表单体（mini Setter 面板）。

**为什么需要**：工作流配置的上下文在"图"上——用户想一边看连线一边改某个节点的 URL，来回切换右侧面板会丢上下文；节点上直接改，视线不用离开图。而表单体本身不新做——就是《进阶大纲》§3 的 Setter 体系（字段声明 + 值编辑器）缩小尺寸嵌进节点，所以叫"mini Setter 面板直接长在节点上"。

**机制分步**：

1. 定义节点的 data 类型（协议与 UI 的契约）；
2. 写自定义节点组件：`NodeProps<TypedNode>` 泛型拿到类型安全的 data；修改 data 用 `useReactFlow().setNodes` 按节点 id 精确更新（只换这一个节点的 data，其它节点引用不变）；
3. 折叠/展开就是 data 里的一个布尔位，折叠时只渲染头部行（handle 必须始终渲染——连线依赖它，藏了 handle 已有连线会视觉断裂）；
4. 状态徽标：data.status 四态映射到颜色圆点。

```tsx
import { memo, useCallback } from 'react';
import { Handle, Position, useReactFlow, type Node, type NodeProps } from '@xyflow/react';

/**
 * http 节点的 data 协议：mini Setter 表单与状态徽标的数据来源。
 * 注意用 type 别名而不是 interface：v12 要求 data 满足 Record<string, unknown>，
 * type 别名有隐式索引签名、可直接满足；interface 需要额外声明索引签名。
 */
export type HttpNodeData = {
  title: string;
  method: 'GET' | 'POST';
  url: string;
  collapsed: boolean; // 折叠态：只渲染头部（2.2）
  status: 'idle' | 'running' | 'success' | 'error'; // 运行态徽标（2.5 推送）
};

/** 类型化节点：Node<data, type>，让 NodeProps 拿到精确类型 */
export type HttpNode = Node<HttpNodeData, 'http'>;

const STATUS_META: Record<HttpNodeData['status'], { color: string; label: string }> = {
  idle: { color: '#8c8c8c', label: '空闲' },
  running: { color: '#1677ff', label: '运行中' },
  success: { color: '#52c41a', label: '成功' },
  error: { color: '#ff4d4f', label: '失败' },
};

function HttpNodeView({ id, data, selected }: NodeProps<HttpNode>) {
  const { setNodes } = useReactFlow();

  /** mini Setter 的统一写入口：只改当前节点的某个字段，其它节点引用不动（性能关键，见 2.5） */
  const updateData = useCallback(
    <K extends keyof HttpNodeData>(key: K, value: HttpNodeData[K]) => {
      setNodes(nodes =>
        nodes.map(n => (n.id === id ? { ...n, data: { ...n.data, [key]: value } } : n)),
      );
    },
    [id, setNodes],
  );

  const badge = STATUS_META[data.status];

  return (
    <div
      style={{
        minWidth: 240,
        borderRadius: 8,
        background: '#fff',
        border: selected ? '2px solid #1677ff' : '1px solid #d9d9d9',
        boxShadow: '0 2px 8px rgba(0,0,0,0.08)',
        fontSize: 12,
      }}
    >
      {/* 输入/输出端口：id 携带数据类型（2.3 的协议），且任何渲染分支都必须保留 Handle */}
      <Handle type="target" position={Position.Left} id="in:json" />

      {/* 头部：标题 + 状态徽标 + 折叠开关（折叠态只渲染这一行） */}
      <div
        style={{
          display: 'flex',
          alignItems: 'center',
          gap: 8,
          padding: '8px 12px',
          borderBottom: data.collapsed ? 'none' : '1px solid #f0f0f0',
        }}
      >
        <strong style={{ flex: 1 }}>{data.title}</strong>
        <span style={{ color: badge.color, whiteSpace: 'nowrap' }}>● {badge.label}</span>
        <button onClick={() => updateData('collapsed', !data.collapsed)} style={{ border: 'none', cursor: 'pointer' }}>
          {data.collapsed ? '展开' : '折叠'}
        </button>
      </div>

      {!data.collapsed && (
        <div style={{ padding: 12, display: 'grid', gap: 8 }}>
          {/* mini Setter 面板：字段声明 + 值编辑器。与右侧属性面板共用同一套 Setter 实现，
              区别只是"容器"从面板变成了节点卡片——暗线：Setter 第 N 次复用 */}
          <label style={{ display: 'grid', gap: 4 }}>
            请求方式
            <select value={data.method} onChange={e => updateData('method', e.target.value as 'GET' | 'POST')}>
              <option value="GET">GET</option>
              <option value="POST">POST</option>
            </select>
          </label>
          <label style={{ display: 'grid', gap: 4 }}>
            URL
            <input value={data.url} onChange={e => updateData('url', e.target.value)} style={{ width: '100%' }} />
          </label>
        </div>
      )}

      <Handle type="source" position={Position.Right} id="out:json" />
    </div>
  );
}

// memo：props 不变不重渲染——2.5 的性能策略依赖这一点
export default memo(HttpNodeView);
```

`nodeTypes` 的定义位置是第一个高频坑，先立规矩：**必须定义在组件外（模块级）**。React Flow 内部按引用比较 nodeTypes，组件内定义 = 每次渲染新对象 = 控制台警告 `It looks like you've created a new nodeTypes or edgeTypes object` + **所有节点被卸载重建**（输入框焦点丢失、动画重放）：

```ts
// ✅ 模块级：引用永远稳定
import type { NodeTypes } from '@xyflow/react';
import HttpNodeView from './HttpNodeView';
export const nodeTypes: NodeTypes = { http: HttpNodeView };
```

**常见坑**：

- **症状**：在节点输入框打字，每敲一个字符画布轻微卡顿，节点多时明显。**根因**：`updateData` 每次都 `setNodes` 触发整个 nodes 数组协调。**修法**：节点数量在几十个时 React Flow + memo 的默认表现可接受（未变更节点引用不变、memo 跳过）；上百节点的高频编辑场景，把节点配置挪到外部 store（zustand），节点组件用 selector 只订阅自己的 data（思路同《进阶大纲》§1.7 path 级订阅）；文本输入的 undo 合并遵循 §1.5 的 300ms 防抖合并规则。
- **症状**：折叠节点后连线"消失"一半。**根因**：折叠分支里把 Handle 一起裁掉了。**修法**：Handle 永远渲染（上面代码的位置），折叠只裁表单体。

### 2.3 连线校验：handle 类型约束、onConnect 校验、isValidConnection

**是什么**：不是任意两端口都能连。三类规则：**方向**（输出→输入，React Flow 用 handle 的 `type="source"/"target"` 天然表达）、**数据类型**（`out:table` 只能接 `in:table`，不匹配禁止连接）、**拓扑**（连上会成环的禁止）。

**为什么需要**：工作流是有向无环图，坏连线在保存时被 2.1 校验拦下——但那是"最后一道门"；交互层的校验让用户**根本画不出**坏边（拖动时目标端口不响应/变灰），错误在发生前就被消灭。三层防线各司其职：拖动时实时校验（体验）→ connect 时兜底（防御）→ 保存时全量校验（正确性）。

**机制：handle id 协议**。端口的数据类型编码在 handle id 里——`in:json`、`out:table`，冒号后是类型标签。校验只做字符串比较，不需要额外的端口元数据表（也可以用 `data-*` 属性或独立注册表，id 内嵌最简单且序列化免费）：

```ts
/** 从 handle id 解析数据类型："out:table" → "table"；无协议前缀视为 any（兼容旧数据） */
function portType(handleId: string | null | undefined): string {
  return handleId?.includes(':') ? handleId.split(':')[1] : 'any';
}

/** 连线成环检测：若从 target 沿现有边可达 source，则新增 source→target 必成环（DFS 可达性） */
export function createsCycle(edges: { source: string; target: string }[], source: string, target: string): boolean {
  const adjacency = new Map<string, string[]>();
  for (const edge of edges) {
    const list = adjacency.get(edge.source) ?? [];
    list.push(edge.target);
    adjacency.set(edge.source, list);
  }
  const visited = new Set<string>();
  const stack = [target]; // 从 target 出发找 source
  while (stack.length > 0) {
    const id = stack.pop()!;
    if (id === source) return true; // target 的下游绕回了 source：闭环
    if (visited.has(id)) continue;
    visited.add(id);
    stack.push(...(adjacency.get(id) ?? []));
  }
  return false;
}
```

`isValidConnection`（React Flow 的连线规则回调）：拖动过程中每次悬停到候选端口都会调用，返回 false 则该端口不响应吸附，用户"连不上"——这是体验最好的一层。`onConnect` 是连线真正建立前的兜底：

```tsx
import { useCallback } from 'react';
import {
  addEdge,
  Background,
  BackgroundVariant,
  Controls,
  MiniMap,
  ReactFlow,
  ReactFlowProvider,
  useEdgesState,
  useNodesState,
  type Connection,
  type NodeTypes,
} from '@xyflow/react';
import '@xyflow/react/dist/style.css';
import HttpNodeView, { type HttpNode } from './HttpNodeView';

// 模块级定义（2.2 的规矩）：引用稳定，否则每次渲染都警告并重建全部节点
const nodeTypes: NodeTypes = { http: HttpNodeView };

const initialNodes: HttpNode[] = [
  {
    id: 'fetch-orders',
    type: 'http',
    position: { x: 0, y: 80 },
    data: { title: '拉取订单', method: 'GET', url: 'https://api.example.com/orders', collapsed: false, status: 'idle' },
  },
  {
    id: 'calc-metrics',
    type: 'http',
    position: { x: 360, y: 80 },
    data: { title: '计算指标', method: 'POST', url: 'https://api.example.com/metrics', collapsed: false, status: 'idle' },
  },
];

const initialEdges: { id: string; source: string; target: string }[] = [
  { id: 'fetch->calc', source: 'fetch-orders', target: 'calc-metrics' },
];

export function FlowEditor() {
  const [nodes, setNodes, onNodesChange] = useNodesState<HttpNode>(initialNodes);
  const [edges, setEdges, onEdgesChange] = useEdgesState(initialEdges);

  /** 规则回调：拖动中实时调用，false = 目标端口不吸附（画不出坏线的第一道防线） */
  const isValidConnection = useCallback(
    (connection: Connection) => {
      // 规则 1：禁止自连
      if (connection.source === connection.target) return false;
      // 规则 2：端口数据类型匹配（out:json 只能接 in:json；any 万能）
      const from = portType(connection.sourceHandle);
      const to = portType(connection.targetHandle);
      if (from !== 'any' && to !== 'any' && from !== to) return false;
      // 规则 3：不能连出环（2.1 的环检测在这里前置到交互层）
      if (createsCycle(edges, connection.source, connection.target)) return false;
      return true;
    },
    [edges],
  );

  /** 兜底：即使程序化触发 connect（绕过拖拽），也过一遍同样的规则 */
  const onConnect = useCallback(
    (connection: Connection) => {
      if (!isValidConnection(connection)) return;
      setEdges(eds => addEdge({ ...connection, type: 'smoothstep' }, eds));
    },
    [isValidConnection, setEdges],
  );

  return (
    <div style={{ width: '100vw', height: '100vh' }}>
      <ReactFlow
        nodes={nodes}
        edges={edges}
        nodeTypes={nodeTypes}
        onNodesChange={onNodesChange}
        onEdgesChange={onEdgesChange}
        onConnect={onConnect}
        isValidConnection={isValidConnection}
        fitView
      >
        <Background variant={BackgroundVariant.Dots} gap={16} />
        <MiniMap pannable zoomable nodeColor={n => (n.type === 'http' ? '#e6f4ff' : '#f0f0f0')} />
        <Controls />
      </ReactFlow>
    </div>
  );
}

// 业务页面挂载（后续 toolbar/快捷键也要求在 ReactFlowProvider 内使用 useReactFlow）
export default function Page() {
  return (
    <ReactFlowProvider>
      <FlowEditor />
    </ReactFlowProvider>
  );
}
```

补一个细节：`isValidConnection` 也可以挂在**单个 Handle** 上（v12 的 `<Handle isValidConnection={...}>`），用于"某个端口有专属规则"的场景（例如 join 节点只接受来自 parallel 的输入）；画布级与端口级同时存在时，两者都通过才可连。

**常见坑**：

- **症状**：用户反馈"明明类型一样还是连不上"。**根因**：handle 没写 `id`，React Flow 默认 id 为 `null`，`portType(null)` 走了 any 以外的分支或两边都成了 any 之外的空值比较失败。**修法**：所有自定义端口一律显式写 id 并遵守 `in:<type>`/`out:<type>` 协议；any 规则只放给显式声明的端口。
- **症状**：连线成环没被拦住。**根因**：只校验了类型没校验拓扑；或 `isValidConnection` 闭包里的 edges 是旧值（依赖数组漏了 edges）。**修法**：三条规则全上；`useCallback` 依赖 `[edges]`（上面代码）；保存前仍跑 2.1 全量校验兜底。
- **症状**：`onConnect` 里 `addEdge` 后边没出现。**根因**：`addEdge` 返回新数组，但写成了 `setEdges(addEdge(connection, eds))` 且参数里的 eds 来自外层闭包旧值。**修法**：永远用函数式更新 `setEdges(eds => addEdge(...))`。

### 2.4 自动布局：dagre vs ELK；用户手动布局后锁定

**是什么**：把"一坨随机坐标的节点"自动整理成分层清晰的正交流程图。两个引擎：dagre（快、简单）与 ELK/elkjs（慢、质量高）。

**为什么需要**：用户从模板/代码生成的 DSL 没有坐标（`position` 全 0）；导入别人的工作流想重排；画布连线交叉成蜘蛛网。自动布局是"导入即能用"的前提。

**选型对比**：

| 维度 | dagre（@dagrejs/dagre） | ELK（elkjs） |
|---|---|---|
| 算法 | Sugiyama 分层布局的精简实现 | ELK Layered（完整的分层+正交边路由） |
| 布局质量 | 边是直线/贝塞尔，交叉多 | 边走正交折线，同层对齐好，接近手画 |
| 性能 | 几十至几百节点瞬时 | 同规模慢一个量级（大图可考虑 web worker） |
| 包体 | 小 | 大（内嵌 Java 转译的 JS） |
| 端口/分组 | 不支持复杂端口约束 | 支持（ports、compound graph） |
| 建议 | 节点数 < 100 的常规工作流 | 追求 n8n 级观感、或有分组/复杂端口时 |

dagre 接入（注意 dagre 返回**节点中心点**坐标，React Flow 要**左上角**坐标，必须减半宽高）：

```ts
import dagre from '@dagrejs/dagre';
import type { Edge, Node } from '@xyflow/react';

/** dagre 自动布局：direction LR = 自左向右（贴合工作流阅读习惯），TB = 自上而下 */
export function layoutWithDagre(nodes: Node[], edges: Edge[], direction: 'LR' | 'TB' = 'LR'): Node[] {
  const g = new dagre.graphlib.Graph();
  // margin 留出画布内边距；nodesep 同层间距；ranksep 层间间距
  g.setGraph({ rankdir: direction, nodesep: 40, ranksep: 80, marginx: 40, marginy: 40 });
  g.setDefaultEdgeLabel(() => ({})); // dagre 要求每条边有 label（可为空对象）

  for (const node of nodes) {
    // v12 里 React Flow 测量后的真实尺寸在 node.measured；未测量（未渲染过）时回退估算值
    g.setNode(node.id, { width: node.measured?.width ?? 260, height: node.measured?.height ?? 90 });
  }
  for (const edge of edges) {
    g.setEdge(edge.source, edge.target);
  }

  dagre.layout(g);

  return nodes.map(node => {
    const { x, y, width, height } = g.node(node.id); // 中心点坐标
    return { ...node, position: { x: x - width / 2, y: y - height / 2 } }; // 转左上角
  });
}
```

ELK 接入（异步 API；边必须带 id；返回的就是左上角坐标）：

```ts
import ELK from 'elkjs';
import type { Edge, Node } from '@xyflow/react';

const elk = new ELK(); // 模块级单例：实例化有成本，不要每次布局新建

/** ELK 分层布局：正交边路由，布局质量对标 n8n */
export async function layoutWithElk(nodes: Node[], edges: Edge[], direction: 'RIGHT' | 'DOWN' = 'RIGHT'): Promise<Node[]> {
  const graph = {
    id: 'root',
    layoutOptions: {
      'elk.algorithm': 'layered', // 分层布局（Sugiyama 家族完整实现）
      'elk.direction': direction,
      'elk.layered.spacing.nodeNode.betweenLayers': '80', // 层间距
      'elk.spacing.nodeNode': '40', // 同层间距
    },
    children: nodes.map(n => ({
      id: n.id,
      width: n.measured?.width ?? 260,
      height: n.measured?.height ?? 90,
    })),
    // ELK JSON 图格式：sources/targets 为数组，且每条边必须有 id
    edges: edges.map((e, i) => ({ id: e.id || `elk-edge-${i}`, sources: [e.source], targets: [e.target] })),
  };

  const laid = await elk.layout(graph);
  const byId = new Map((laid.children ?? []).map(c => [c.id, c]));
  return nodes.map(node => {
    const pos = byId.get(node.id);
    // ELK 输出左上角坐标（与 dagre 的中心点不同），直接可用
    if (!pos || pos.x === undefined || pos.y === undefined) return node;
    return { ...node, position: { x: pos.x, y: pos.y } };
  });
}
```

**用户手动布局后锁定（用户位置优先策略）**：自动布局是"一次性重排"，它会**覆盖**用户辛苦拖好的位置——直接放一个"自动布局"按钮，用户点一次骂一次。策略三选一：

1. **全局标记 + 确认**（实现最简，推荐起步）：任何手动拖拽（`onNodeDragStop`）把画布标记为"手动布局过"；此后点自动布局先弹确认"将覆盖当前手动排列"；
2. **节点级锁定**：`data.positionLocked: true` 的节点不参与自动布局（dagre 仍会给它算位置，但布局后写回时跳过），适合"钉住"关键节点只整理其余；
3. **完全手动 opt-in**：导入 DSL 时自动布局一次，之后按钮藏进菜单——尊重"画布是用户的领地"。

实现（策略 1 + 策略 2 的写回跳过）：

```tsx
import { useCallback, useRef } from 'react';
import { Panel, ReactFlow, useReactFlow, type Node } from '@xyflow/react';

/** 布局工具栏：作为 <ReactFlow> 的子组件渲染（这样才能用 useReactFlow） */
export function LayoutToolbar() {
  const { getNodes, getEdges, setNodes, fitView } = useReactFlow();
  const manuallyLaid = useRef(false); // 全局标记：true = 用户拖过，自动布局需确认

  const onAutoLayout = useCallback(() => {
    if (manuallyLaid.current && !window.confirm('自动布局会覆盖手动排列的位置，继续？')) {
      return; // 用户位置优先：宁可放弃自动布局，不悄悄毁掉手动成果
    }
    setNodes(nodes => {
      const laid = layoutWithDagre(nodes, getEdges());
      // 策略 2：钉住的节点不写回新坐标
      return nodes.map((node, i) =>
        (node.data as { positionLocked?: boolean }).positionLocked ? node : laid[i],
      );
    });
    manuallyLaid.current = false;
    // 下一帧再 fitView：等 setNodes 的状态落地，拿到的是新坐标
    requestAnimationFrame(() => void fitView({ padding: 0.15, duration: 300 }));
  }, [setNodes, getEdges, fitView]);

  return (
    <Panel position="top-right">
      <button onClick={onAutoLayout} style={{ padding: '4px 12px' }}>
        自动布局
      </button>
    </Panel>
  );
}

// ReactFlow 上监听拖拽结束，置手动标记：
// <ReactFlow onNodeDragStop={() => { manuallyLaid.current = true; }} ... />
```

**常见坑**：

- **症状**：布局后节点挤成一坨或尺寸全是默认值。**根因**：首次渲染前就布局——`node.measured` 还没填充，全部回退默认宽高，而实际节点（含展开的表单）高矮不一。**修法**：导入 DSL 后先渲染一帧（让 React Flow 完成测量）再触发布局；或在布局前手动遍历 DOM 读节点尺寸写入 measured。
- **症状**：ELK 布局抛"edge id 重复/缺失"。**根因**：边没 id 或复用了旧 id。**修法**：edges 生成时统一 `crypto.randomUUID()`（2.6 的 Cmd+D 复制同理）。
- **症状**：自动布局把 undo 栈打断——一次布局回退成几十步节点移动。**根因**：每个节点 position 变化被当作独立变更入栈。**修法**：布局操作在**快照级 undo** 里只记一次（2.6 的 commit 时机：布局前 commit 一次快照）。

### 2.5 运行态性能：后端高频推送节点状态 → rAF 聚合批量 setNodes（重点）

**场景还原**：点"运行"后，工作流引擎在后端执行，通过 WebSocket/SSE 把节点状态流式推给前端——`fetch-orders: running`、`calc-metrics: running`、`fetch-orders: success`……大工作流（100 节点）运行高峰期，每秒几十上百条消息。全景图 F2 把这一条列为 Agent 画布的核心技术点，原因就是它**最容易把编辑器做卡**。

**"100 节点流式更新直接卡死"的机理，用数字推演**。先看反例（多数人的第一版写法）：

```tsx
// 反例：每条推送一次 setNodes，且 map 里把所有节点都换成新对象
const ws = new WebSocket('wss://api.example.com/runs/run-42/stream');
ws.onmessage = event => {
  const patch = JSON.parse(event.data) as { nodeId: string; status: string };
  setNodes(nodes =>
    nodes.map(n => ({ ...n, data: { ...n.data, status: n.id === patch.nodeId ? patch.status : n.data.status } })),
  );
};
```

两个错误叠加：

1. **更新频率失控**：50 条消息/秒 = 50 次 `setNodes`/秒。每条 WS 消息是独立的宏任务，React 18 的自动批处理**跨不过**任务边界——50 次真实的 reconciliation。而屏幕只有 60fps，用户根本看不到两次渲染之间的中间态：这些更新里约 80% 是纯浪费的协调开销。
2. **重渲染范围失控**：`map` 里 `{...n}` 给**所有** 100 个节点都造了新对象。React Flow 内部对节点组件做了 memo（我们也给自定义节点包了 memo），但 memo 比较的是引用——引用全变，100 个节点的组件**全部重渲染**。50 msg/s × 100 节点 = 每秒 5000 次节点组件渲染，每次渲染又生成一批新对象喂给 GC。

60fps 的帧预算是 16.6ms。假设每次全图协调 2ms，仅协调就吃掉 50 × 2 = 100ms/s 看似不多，但它**挤占的是同一个主线程**：与拖拽、动画、canvas 绘制抢帧，帧时间一超 16.6ms 就掉帧；GC 停顿再来插一脚，用户感受到的就是"点运行，画布冻住"——卡死不是崩溃，是主线程持续过载。

**修法：rAF 聚合 + 引用稳定性**。两招分别对付上面两个错误：

```tsx
import { useCallback, useEffect, useRef } from 'react';
import { useReactFlow, type Node } from '@xyflow/react';

export type NodeRunStatus = 'idle' | 'running' | 'success' | 'error';

/** 后端单条推送的补丁 */
interface StatusPatch {
  nodeId: string;
  status: NodeRunStatus;
}

/**
 * 运行态状态同步器：高频推送 → rAF 聚合 → 每帧最多一次 setNodes。
 * 用法：const { applyPatch } = useStatusSync(); 然后 ws.onmessage 里 applyPatch(JSON.parse(e.data))。
 */
export function useStatusSync() {
  const { setNodes } = useReactFlow();

  // 帧内补丁队列：Map 的 key 去重——同一帧内同一节点的多次推送只保留最后一条
  const pendingRef = useRef(new Map<string, StatusPatch>());
  const rafIdRef = useRef<number | null>(null);

  /** 落盘：把这一帧攒的补丁一次性合并进 nodes */
  const flush = useCallback(() => {
    rafIdRef.current = null;
    const pending = pendingRef.current;
    if (pending.size === 0) return;
    const patches = new Map(pending);
    pending.clear();

    setNodes(nodes =>
      nodes.map((node): Node => {
        const patch = patches.get(node.id);
        // 关键：未命中补丁的节点返回原引用——memo 生效，只有真正变化的节点重渲染
        if (!patch) return node;
        return {
          ...node,
          data: { ...node.data, status: patch.status },
        };
      }),
    );
  }, [setNodes]);

  /** 入队：补丁先进帧队列，帧内第一次补丁才调度 rAF */
  const applyPatch = useCallback(
    (patch: StatusPatch) => {
      pendingRef.current.set(patch.nodeId, patch); // 同节点多次推送：Map 覆盖，只留最新
      if (rafIdRef.current === null) {
        // requestAnimationFrame：与浏览器渲染节拍对齐，每帧最多 flush 一次（≤60 次/秒）
        rafIdRef.current = requestAnimationFrame(flush);
      }
    },
    [flush],
  );

  // 卸载清理：取消未执行的帧回调，避免卸载后 setState
  useEffect(() => {
    return () => {
      if (rafIdRef.current !== null) cancelAnimationFrame(rafIdRef.current);
    };
  }, []);

  return { applyPatch };
}
```

与 WebSocket 的接线（含消息协议的判别联合类型）：

```tsx
import { useEffect } from 'react';

/** 与后端约定的流消息协议 */
type RunStreamMessage =
  | { kind: 'node-status'; payload: { nodeId: string; status: NodeRunStatus } }
  | { kind: 'run-finished'; runId: string }
  | { kind: 'run-failed'; runId: string; nodeId: string; message: string };

export function useRunStream(runId: string | null) {
  const { applyPatch } = useStatusSync();

  useEffect(() => {
    if (!runId) return;
    const ws = new WebSocket(`wss://api.example.com/runs/${runId}/stream`);
    ws.onmessage = event => {
      const msg = JSON.parse(event.data) as RunStreamMessage;
      // 每条消息只做"入队"这个 O(1) 动作，重活留给 rAF 的 flush
      if (msg.kind === 'node-status') applyPatch(msg.payload);
    };
    return () => ws.close();
  }, [runId, applyPatch]);
}
```

效果量化：50 msg/s 的推送被压到 ≤60 次/秒的 setNodes（通常一帧一次），每次只重建**发生变化**的节点对象（一帧内通常 1–5 个）——每秒节点组件渲染从 5000 次降到一两百次，且与渲染节拍对齐零浪费。三个工程要点再强调一遍：

1. **Map 去重的语义正确性**：一个节点在 16ms 内从 running→success→error，用户只应看到最终态，中间态本来就不该渲染——聚合不是妥协，是更正确的语义；
2. **未变更节点引用必须原样返回**：`if (!patch) return node` 这一行是整个策略的命门，删掉它 memo 全部失效；
3. **调度时机**：用 rAF 而不是 `setTimeout(0)`——后者仍可能一帧内触发多次；也不是节流（固定间隔），rAF 自动适配刷新率且在渲染前执行。

**常见坑**：

- **症状**：状态还是延迟好几秒才刷新。**根因**：聚合做在了**后端→前端**之间还有一层 100ms 的消息合并，或者 flush 里 `setNodes` 用了非函数式更新读到旧 nodes。**修法**：前端聚合保留（rAF），后端合并去掉或控制在 50ms 内；`setNodes` 一律函数式。
- **症状**：节点闪一下旧状态再变新状态。**根因**：推送乱序（WS 重连后重放），旧补丁覆盖新补丁。**修法**：补丁携带递增序号/时间戳，flush 时丢弃比已应用序号更老的补丁。
- **症状**：几百节点 + 运行态下拖拽画布仍然卡。**根因**：rAF 只解决了更新频率，节点渲染总量还在。**修法**：`<ReactFlow onlyRenderVisibleElements>`（视口裁剪）+ 折叠节点表单体（2.2 的 collapsed 默认 true，运行态全量折叠）双管齐下。

### 2.6 撤销重做、小地图、快捷键（Cmd+D 复制节点带偏移）

#### 撤销重做（复用《进阶大纲》§1.5）

§1.5 给了三种实现（命令模式 / immer produceWithPatches / zundo）。工作流编辑器的选型建议：**快照式**——nodes/edges 两个数组总量小（几十 KB），全量快照 + 50 步上限的内存代价可忽略，换来的是"任何操作（拖动、连线、删除、布局、批量粘贴）零差异接入"——不用为每种操作写 do/undo 对偶。immer patches 方案在"单字段编辑极多"的场景更省内存，但接入成本高；快照式是编辑器规模小几十倍于文档编辑器时的理性选择。

快照式通用 hook（无 React Flow 依赖，任何编辑器可搬）：

```tsx
import { useCallback, useRef, useState } from 'react';

const HISTORY_LIMIT = 50; // 50 步：再多内存不值、用户也回不去那么远

/** 泛型快照式历史栈：T 是被编辑状态的快照类型 */
export function useHistory<T>() {
  const pastRef = useRef<T[]>([]);
  const futureRef = useRef<T[]>([]);
  const [, setVersion] = useState(0); // 仅用于驱动 canUndo/canRedo 重渲染

  /** 在"破坏性操作发生前"记录现状 */
  const commit = useCallback((present: T) => {
    pastRef.current = [...pastRef.current, present].slice(-HISTORY_LIMIT);
    futureRef.current = []; // 新操作清空 redo 栈（§1.5 的规则）
    setVersion(v => v + 1);
  }, []);

  /** 撤销：传入"当前状态"，返回要回到的快照 */
  const undo = useCallback((present: T): T | undefined => {
    const past = pastRef.current;
    if (past.length === 0) return undefined;
    const prev = past[past.length - 1];
    pastRef.current = past.slice(0, -1);
    futureRef.current = [present, ...futureRef.current];
    setVersion(v => v + 1);
    return prev;
  }, []);

  /** 重做：传入"当前状态"，返回要前进到的快照 */
  const redo = useCallback((present: T): T | undefined => {
    const future = futureRef.current;
    if (future.length === 0) return undefined;
    const next = future[0];
    futureRef.current = future.slice(1);
    pastRef.current = [...pastRef.current, present];
    setVersion(v => v + 1);
    return next;
  }, []);

  return {
    commit,
    undo,
    redo,
    canUndo: pastRef.current.length > 0,
    canRedo: futureRef.current.length > 0,
  };
}
```

与 React Flow 的接线——关键是**commit 时机选在破坏性操作发生前**（拿到的是"改之前"的快照），并用 `getNodes()/getEdges()` 这类命令式读取器避免闭包过期：

```tsx
import { useCallback, useEffect } from 'react';
import { useReactFlow, type Connection, type Node, type Edge } from '@xyflow/react';

interface FlowSnapshot {
  nodes: Node[];
  edges: Edge[];
}

export function useFlowUndoRedo(
  setNodes: (updater: (nodes: Node[]) => Node[]) => void,
  setEdges: (updater: (edges: Edge[]) => Edge[]) => void,
) {
  const { getNodes, getEdges } = useReactFlow();
  const { commit, undo, redo } = useHistory<FlowSnapshot>();

  /** 各破坏性操作的入口：先 commit 当前，再改。连线即"先快照再校验加边"（校验规则同 2.3） */
  const beforeConnect = useCallback(
    (connection: Connection) => {
      if (connection.source === connection.target) return; // 与 2.3 相同的兜底规则
      commit({ nodes: getNodes(), edges: getEdges() }); // 连线前的快照
      setEdges(eds => [
        ...eds,
        {
          id: crypto.randomUUID(),
          source: connection.source,
          target: connection.target,
          sourceHandle: connection.sourceHandle,
          targetHandle: connection.targetHandle,
          type: 'smoothstep',
        },
      ]);
    },
    [commit, getNodes, getEdges, setEdges],
  );
  const beforeDragStop = useCallback(() => {
    commit({ nodes: getNodes(), edges: getEdges() }); // 拖拽结束改坐标前（一次拖拽 = 一步 undo）
  }, [commit, getNodes, getEdges]);

  /** Cmd+Z / Cmd+Shift+Z */
  useEffect(() => {
    const onKey = (e: KeyboardEvent) => {
      if (!(e.metaKey || e.ctrlKey) || e.key.toLowerCase() !== 'z') return;
      e.preventDefault();
      const present = { nodes: getNodes(), edges: getEdges() };
      const target = e.shiftKey ? redo(present) : undo(present);
      if (target) {
        setNodes(() => target.nodes.map(n => ({ ...n })));
        setEdges(() => target.edges.map(e2 => ({ ...e2 })));
      }
    };
    window.addEventListener('keydown', onKey);
    return () => window.removeEventListener('keydown', onKey);
  }, [undo, redo, getNodes, getEdges, setNodes, setEdges]);

  return { beforeConnect, beforeDragStop };
}
```

注意 §1.5 的合并规则在这里的体现：**节点内文本输入**（mini Setter 的 URL 框）如果每次 keystroke 都 commit，undo 会逐字符回退——正确做法是输入防抖 300ms 合并为一次快照；拖拽天然是"结束时快照一次"（`onNodeDragStop`），不需要合并。

#### 小地图

`@xyflow/react` 内置，`<MiniMap>` 放进 `<ReactFlow>` 子组件即可（2.3 的编辑器里已接入）。两个实用 prop：`pannable`（拖动小地图视口平移画布）、`zoomable`（小地图内滚轮缩放）；`nodeColor` 按节点类型/状态着色——运行态把 running 节点染成品牌蓝，小地图就成了"运行进度总览"。节点很多时加 `nodeStrokeWidth={2}` 提升辨识度。

#### 快捷键 Cmd+D：复制选中节点带偏移

"带偏移"是产品语义：副本落在原位置右下 32px，用户一眼分辨"这是复制出来的"，并且可以连按 Cmd+D 连续铺开一排。实现要点：复制**节点**的同时复制**两端都在选区内的边**（只复制节点会得到一堆孤岛）；新 id 用 `crypto.randomUUID()`；副本成为新选区（原选中取消）：

```tsx
import { useEffect } from 'react';
import { useReactFlow, type Edge, type Node } from '@xyflow/react';

const DUPLICATE_OFFSET = 32; // 副本偏移：右下 32px，连按可铺开一排

export function useDuplicateShortcut() {
  const { getNodes, getEdges, setNodes, setEdges } = useReactFlow();

  useEffect(() => {
    const onKeyDown = (e: KeyboardEvent) => {
      if (!(e.metaKey || e.ctrlKey) || e.key.toLowerCase() !== 'd') return;
      // 正在输入类控件里打字时不触发（否则复制不了文字还误删节点）
      const active = document.activeElement;
      if (
        active instanceof HTMLElement &&
        (active.tagName === 'INPUT' || active.tagName === 'TEXTAREA' || active.isContentEditable)
      ) {
        return;
      }
      e.preventDefault(); // 抢掉浏览器"添加书签"默认行为

      const nodes = getNodes();
      const edges = getEdges();
      const selected = nodes.filter(n => n.selected);
      if (selected.length === 0) return;

      // 新旧 id 映射：副本取全新 id
      const idMap = new Map<string, string>(selected.map(n => [n.id, crypto.randomUUID()]));

      const clones: Node[] = selected.map(n => ({
        ...n,
        id: idMap.get(n.id)!,
        selected: true, // 副本成为新选区
        position: { x: n.position.x + DUPLICATE_OFFSET, y: n.position.y + DUPLICATE_OFFSET },
        data: { ...n.data }, // data 浅拷贝；若 data 内含可变引用（数组/对象配置），按需深拷贝
      }));

      // 边：两端都在选区内才复制（孤立的选外边不跟）
      const clonedEdges: Edge[] = edges
        .filter(e => idMap.has(e.source) && idMap.has(e.target))
        .map(e => ({
          ...e,
          id: crypto.randomUUID(),
          source: idMap.get(e.source)!,
          target: idMap.get(e.target)!,
          selected: false,
        }));

      setNodes(nds => [
        ...nds.map(n => (n.selected ? { ...n, selected: false } : n)), // 原选中取消；未选中的保持引用
        ...clones,
      ]);
      setEdges(eds => [...eds, ...clonedEdges]);
    };

    window.addEventListener('keydown', onKeyDown);
    return () => window.removeEventListener('keydown', onKeyDown);
  }, [getNodes, getEdges, setNodes, setEdges]);
}
```

**常见坑**：

- **症状**：Cmd+D 后副本和原件叠在一起分不清。**根因**：忘了加偏移。**修法**：就是那 32px——它不是装饰，是可用性。
- **症状**：undo 一步回退了"半次"操作（节点回来了边没回来）。**根因**：nodes 与 edges 的快照来自不同时刻（一次 commit 只截了一个数组）。**修法**：快照必须**原子**——`{ nodes: getNodes(), edges: getEdges() }` 作为一个整体进出栈（上面 FlowSnapshot 的意义）。
- **症状**：删除节点后 undo，节点回来了但引用它的连线没了/悬空。**根因**：React Flow 删除节点时会级联删边，undo 只恢复了节点快照……实际上快照式会整体恢复——真正的坑是把删除入口做成了自定义逻辑只删节点。**修法**：一切破坏性操作走同一套"先 commit 再改"的入口，不自造旁路。

### 2.7 DSL 语义升级：条件分支、并行网关、循环节点怎么表达

**问题**：2.1 的 DSL 只有"顺序后继"（`next`），表达不了三种控制流——条件分支（走哪条路）、并行（同时走多条路）、循环（同一段路走多遍）。这一节回答"它们在协议里怎么表达"，顺带给出 2.1 留下的悬念的答案：**怎么表达循环而不破坏 DAG 校验**。

**总设计原则：把控制流语义放进节点 `data`，不放进边。** 边永远只表达"顺序邻接"（DAG 可校验）；分支/汇合/循环的"路由决策"是节点的运行时行为，由调度器解释执行。这样 2.1 的 Kahn 校验一行不用改，协议的静态可分析性保住了——这也是 n8n/BPMN 的共同做法（BPMN 的网关是图元素但语义在引擎）。

#### 条件分支节点：protocol + 语义

```json
{
  "id": "cond-pay",
  "type": "condition",
  "position": { "x": 640, "y": 120 },
  "data": {
    "branches": [
      { "id": "br-paid", "when": { "field": "status", "operator": "==", "value": "paid" }, "next": ["task-refund"] },
      { "id": "br-pending", "when": { "field": "status", "operator": "==", "value": "pending" }, "next": ["task-remind"] }
    ],
    "default": ["end"]
  },
  "next": []
}
```

**运行语义**：调度器执行到 condition 节点时，按 `branches` 数组**顺序求值** `when`（`field` 是从执行上下文取值的点分路径，如 `result.ok`），**第一个命中分支的 `next` 进入调度队列，其余分支不执行**（互斥单选，与并行网关的本质区别）；全不命中走 `default`（缺省必须存在，否则流程有断头路）。注意 `next` 数组留空——分支节点的出边全部由 `data.branches[].next` 与 `data.default` 携带。**DAG 校验口径**：condition 节点的有效邻接 = 所有 `branches[].next` ∪ `default`，校验器把它们并入邻接表即可（2.1 的校验函数给 condition 类型做一个 next 合并的预处理）。

条件谓词的类型与求值器（调度器与"试运行面板"共用——后者是给用户即时验证规则正确性的调试面板，思想同场景 3 的试运行）：

```ts
export interface ConditionWhen {
  field: string; // 从执行上下文取值的路径，如 "status" / "result.ok"
  operator: '==' | '!=' | '>' | '<' | 'in';
  value: unknown;
}

/** 谓词求值：operator 有限集，纯函数，前后端可共用同一实现 */
export function evalCondition(when: ConditionWhen, variables: Record<string, unknown>): boolean {
  const left = variables[when.field.split('.')[0]]; // 简化：完整实现应走 1.4 的 getByPath
  switch (when.operator) {
    case '==':
      return left === when.value;
    case '!=':
      return left !== when.value;
    case '>':
      return Number(left) > Number(when.value);
    case '<':
      return Number(left) < Number(when.value);
    case 'in':
      return Array.isArray(when.value) && when.value.includes(left);
  }
}
```

#### 并行网关：fork + join 成对

```json
{
  "id": "fanout-1",
  "type": "parallel",
  "position": { "x": 640, "y": 300 },
  "data": { "joinId": "join-1", "mode": "all" },
  "next": ["task-email", "task-sms", "task-report"]
}
```

```json
{
  "id": "join-1",
  "type": "join",
  "position": { "x": 1280, "y": 300 },
  "data": { "fanoutId": "fanout-1", "mode": "all" },
  "next": ["end"]
}
```

**运行语义**：`parallel` 是 fork——`next` 的**全部**后继并发入队（互斥分支的对照组：并行 = 多选全选）；`join` 是汇合点——调度器在 fork 时初始化计数器，每个分支执行到 join 时计一次数：`mode: 'all'` 表示收齐全部到达才放行 `join.next`（`Promise.all` 语义）；`mode: 'any'` 表示任一到达即放行并取消其余（`Promise.race` 语义，用于"超时或成功，先到先用"）。`joinId/fanoutId` 互相引用构成"网关对"——调度器据此知道"该等谁、等几个"，而不是"凡多入边就等全部"（后者无法表达 diamond 型汇聚）。**DAG 校验口径**：join 的入边正常入邻接表（parallel.next 已覆盖），无环问题；校验器加两条断言：`parallel.next.length >= 2`（单分支的并行没有意义）、`join.data.fanoutId` 指向的必须是 parallel 且其 `joinId` 指回自己（成对校验，防孤儿网关）。

#### 循环节点：子段引用而非回边（本节最重要的设计决策）

```json
{
  "id": "loop-retry",
  "type": "loop",
  "position": { "x": 320, "y": 460 },
  "data": {
    "kind": "count",
    "count": 5,
    "bodyStart": "task-call",
    "bodyEnd": "task-check",
    "breakWhen": { "field": "result.ok", "operator": "==", "value": true },
    "maxDurationMs": 600000
  },
  "next": ["end"]
}
```

**运行语义**：`bodyStart → bodyEnd` 是主图上的一个**节点区段**（不是子图——它们就是普通节点，别的工作流也可以引用它们）；调度器循环执行该区段：一轮跑到 `bodyEnd` 后求值 `breakWhen`，未命中且未达 `count` 上限（`kind: 'count'`）就"跳回" `bodyStart` 再来一轮；命中跳出条件或达到上限则从 `loop` 节点自身的 `next` 正常出口。`maxDurationMs` 是安全阀，防 breakWhen 永不命中的死循环。**为什么这样设计**：如果把"回边"写进 `bodyEnd.next`（`next: ["task-call", ...]` 指回循环头），邻接表立刻成环，2.1 的 DAG 校验要么误杀、要么对 loop 类型开洞——校验的完备性就破了。现在的方案里，**循环的"回"是调度器按 loop 节点语义驱动的运行时跳转，图结构上仍是 DAG**——表达力升级，校验规则零改动。代价是静态分析器（如"这个节点会被执行吗"）需要理解 loop 语义，但这是可接受的交换：正确性靠结构，灵活性靠语义。

#### 把语义跑起来：一个可运行的 mini 调度器

上面的语义说明浓缩成代码（http 节点真实 fetch，condition/parallel/loop 按上述规则路由，状态回调对接 2.5 的推送通道）：

```ts
/** 与 2.5 的 NodeRunStatus 同名同义；调度器与编辑器共用这套状态词汇 */
type NodeRunStatus = 'idle' | 'running' | 'success' | 'error';

interface ConditionData {
  branches: { id: string; when: ConditionWhen; next: string[] }[];
  default: string[];
}

interface ParallelData {
  joinId: string;
  mode: 'all' | 'any';
}

interface LoopData {
  kind: 'count' | 'while';
  count: number;
  bodyStart: string;
  bodyEnd: string;
  breakWhen: ConditionWhen;
  maxDurationMs: number;
}

/**
 * mini 调度器：解释执行 WorkflowDSL。
 * onStatus 对接 2.5 的 useStatusSync.applyPatch——运行态可视化就是"调度器回调 → rAF 聚合"这一条链。
 */
export async function runWorkflow(
  dsl: WorkflowDSL,
  onStatus: (nodeId: string, status: NodeRunStatus) => void,
): Promise<void> {
  const nodeById = new Map(dsl.nodes.map(n => [n.id, n]));
  const variables: Record<string, unknown> = {}; // 执行上下文：上游输出并入，供条件求值读取

  // 全局时长安全阀：整个 run 超过截止时间即抛错终止——
  // 与 loop 节点自身的 maxDurationMs 呼应，双保险防"breakWhen 永不命中"式死循环拖垮引擎
  const deadline = Date.now() + 10 * 60 * 1000; // 10 分钟
  const assertWithinDeadline = (): void => {
    if (Date.now() > deadline) throw new Error('运行超时：触发全局安全阀（10 分钟）');
  };

  /** 执行单节点，返回"路由结果"：接下来该入队的节点 id 列表 */
  const execute = async (node: WfNode): Promise<string[]> => {
    onStatus(node.id, 'running');
    assertWithinDeadline(); // 每个节点执行前检查一次
    try {
      switch (node.type) {
        case 'http': {
          const { url, method = 'GET' } = node.data as { url: string; method?: 'GET' | 'POST' };
          const res = await fetch(url, { method });
          Object.assign(variables, await res.json()); // 输出并入上下文
          break; // 落到末尾的"成功 + next"
        }
        case 'condition': {
          const { branches, default: fallback } = node.data as ConditionData;
          for (const branch of branches) {
            if (evalCondition(branch.when, variables)) {
              onStatus(node.id, 'success');
              return branch.next; // 互斥单选：第一个命中即路由
            }
          }
          onStatus(node.id, 'success');
          return fallback;
        }
        case 'parallel': {
          const { joinId } = node.data as ParallelData;
          onStatus(node.id, 'success');
          // fork：全部分支并发推进，每条分支各自执行到 join 前停下（runBranch 的 stopAt）
          await Promise.all(node.next.map(branchStart => runBranch(branchStart, joinId)));
          const join = nodeById.get(joinId);
          return join ? join.next : []; // 汇合后放行 join 的后继（mode: 'all' 语义）
        }
        case 'loop': {
          const data = node.data as LoopData;
          onStatus(node.id, 'success');
          for (let round = 0; round < data.count; round++) {
            await runBranch(data.bodyStart, data.bodyEnd); // 跑一轮循环体区段
            if (evalCondition(data.breakWhen, variables)) break; // 命中跳出条件提前结束
          }
          return node.next; // 正常出口
        }
        case 'start':
        case 'join':
        case 'end':
          break; // 纯控制节点：无副作用，直接走 next
      }
      onStatus(node.id, 'success');
      return node.next;
    } catch (err) {
      onStatus(node.id, 'error');
      throw err; // 上抛终止整个 run（生产实现应支持 error 分支续跑与超时控制）
    }
  };

  /** 沿单链推进：start 一路向后；分支/循环体场景下走到 stopAt 停 */
  const runBranch = async (startId: string, stopAt?: string): Promise<void> => {
    let cursor: string | undefined = startId;
    while (cursor !== undefined && cursor !== stopAt) {
      const node = nodeById.get(cursor);
      if (!node) throw new Error(`未找到节点 ${cursor}`);
      const next = await execute(node);
      cursor = next[0]; // 链内节点取首个后继推进；多后继的路由已在 execute 内处理
    }
  };

  const start = dsl.nodes.find(n => n.type === 'start');
  if (!start) throw new Error('缺少 start 节点');
  await runBranch(start.id);
}
```

（生产化清单：http 节点加超时与重试、condition 支持 &&/|| 组合谓词（届时直接复用场景 3 的条件树协议）、并行 `mode: 'any'` 的取消传播、断点续跑。这个 mini 版的价值在于**语义正确**——它就是上面三个 JSON 的可执行注释。）

**常见坑**：

- **症状**：并行分支里有一个节点失败，join 永远等不齐，流程挂起。**根因**：`mode: 'all'` 只数"到达"，失败分支抛错后没有 token 到达 join。**修法**：失败也计为一种到达（携带 error 状态），由 join 的失败策略（fail-fast 或忽略失败分支）决定放行行为。
- **症状**：循环体里的节点状态在画布上"闪"——running/success 高速交替。**根因**：每轮循环都推送状态，多轮循环在视觉上叠成频闪。**修法**：2.5 的 rAF 聚合天然把频闪压成最终态；再给 loop 节点的 data 加"当前轮次"徽标，比频闪更有信息量。
- **症状**：编辑器里 loop 的 bodyStart/bodyEnd 改了，画布上没有任何连线提示循环范围。**根因**：循环区段不占边，画布不可见。**修法**：渲染层给 `bodyStart..bodyEnd` 区段画一条**虚线回边**（仅视觉，不进邻接表）+ 区段底色蒙版——视觉有环、结构无环，两个世界各取所需。

### 对标：n8n（源码可读性好）、Dify、Langflow、bpmn.js（重量级 BPMN，按需）

对标行保留并展开——四个项目按"定位 + 对前端作者的参考价值 + 可读性"评价：

- **n8n**：工作流自动化平台，400+ 集成节点生态最大。前端 Vue 3（editor-ui 包），但**源码可读性是四者中最好的**：节点协议（`INodeType` 声明式描述 + `execute` 执行函数分离）、参数体系（`INodeProperties` 就是 Setter 的字段声明——声明式 schema 驱动表单）、连线校验、执行事件流（前端订阅 run data 更新节点状态，正是 2.5 的课题），目录结构按职责切分清晰。做通用工作流编辑器，**首选精读**——即便技术栈是 Vue，概念与 React Flow 完全同构。
- **Dify**：LLM 应用编排平台，定位是"AI 应用"而非通用自动化：节点粒度大（LLM/知识检索/HTTP/条件分支），DSL 是 YAML（应用导出格式），面向 AI 工程师。前端 React + React Flow，其自定义节点（参数面板内嵌节点、调试侧栏、单节点试运行）与 F2 画像完全对得上；monorepo 里前后端耦合较深，可读性中等，按需查阅（节点 UI 与运行日志面板值得抄）。
- **Langflow**：Python 生态的 LLM 流程编排（后端 Python，前端 React Flow）。前端代码对 React Flow 的用法覆盖全面——多 handle 类型、端口校验、拖入面板、聊天试运行；仓库以 Python 为主，前端阅读入口在 `frontend`，可读性中等偏上。适合对照"React Flow 的边界在哪"：它的节点参数面板比 Dify 薄，但画布交互做得很满。
- **bpmn.js**：Camunda 出品的 BPMN 2.0 标准编辑器/渲染器，重量级选手。定位是**标准业务流程**（审批流、跨系统流程），强在：符合 BPMN 2.0 XML 规范、可直接对接 Activiti/Flowable/Camunda 流程引擎、语义完备（事件、网关、泳道、边界事件）。代价：自定义节点要学它的扩展体系（moddle 定义、palette/provider 注册），改造成本显著高于 React Flow 从零写。**按需选择**：做"标准审批流对接流程引擎"上 bpmn.js；做"产品内的工作流编排"（本章语境）React Flow + 自定义 DSL 更自由、更轻。

一句话收束本章：n8n 教你节点协议怎么设计，Dify/Langflow 教你 AI 编排的节点形态怎么做，bpmn.js 提醒你标准化是有代价的——而这一切的底座，就是 2.1 的 DSL + 2.2 的自定义节点 + 2.5 的运行态更新管道。

（追加批次：2.8–2.11 是第二批增量，分别补齐端口协议的动态性、边的工程细节、批量交互与执行态可视化；DSL 与调度器语义（2.1/2.7）、高频更新管道（2.5）不变。）

### 2.8 动态端口：分支端口与端口元数据注册表

**是什么**：2.2/2.3 的端口是**静态**的——组件里写死一个 `in:json` 一个 `out:json`。动态端口指端口的**数量与类型随节点 data 变化**：condition 节点每个分支一个出端口（外加 default 兜底端口）、join 节点按上游分支数出现入端口、"字段映射"类节点按上游输出字段动态生成端口。同时，端口元数据从 2.3 的"handle id 内嵌类型标签"升级为**端口注册表**——`node.type → (data) => PortSpec[]` 的纯函数。

**为什么难**：

1. **边的寻址会失效**。React Flow 的边通过 `(nodeId, handleId)` 寻址，端口消失（用户删了一个分支）时挂在它上面的边就成了悬空引用——不清理，2.1 的校验直接报错，且报错发生在用户"改表单"这个完全无害的动作之后，体验极差；
2. **id 协议装不下动态端口**。2.3 的 `out:json` 约定是"一个冒号、后段是类型"；分支端口的 key 要携带分支身份（`out:<branchId>`），id 里塞不下两段语义还想要稳定解析——这正是元数据升级为注册表的动机；
3. **端口增删与表单编辑是两个 actor**。加端口不需要动边，删端口必须同步清边——差异要显式建模，不能指望渲染层"顺手"处理。

**关键机制**：

1. `PortSpec { key, direction, type, label? }`——`key` 必须是**稳定标识**（branchId），绝不能用数组下标；
2. 注册表按 node.type 注册解析器，编辑器渲染与连线校验**共用同一份**（单一事实来源）；
3. 连线校验的类型查询升级为"先查注册表、查不到再走 2.3 的 id 内嵌协议"（静态端口节点零改动）；
4. **删端口必清边**：在 data 变更入口（删除分支的按钮）同步 `setEdges` 过滤。

端口注册表与悬空边检测：

```ts
/** 端口元数据：动态端口的规格。key 必须稳定（如 branchId），绝不使用数组下标 */
export interface PortSpec {
  key: string; // 即 handle id，如 "out:br-a1" / "in:json"
  direction: 'in' | 'out';
  type: string; // 数据类型标签（连线校验用），如 'json' / 'table'
  label?: string; // 端口旁的显示名，如分支名
}

/** 端口解析器：按节点类型注册，输入 data 输出当前端口集——渲染与校验共用 */
export type PortResolver = (data: Record<string, unknown>) => PortSpec[];

const portRegistry = new Map<string, PortResolver>();

export function registerPorts(nodeType: string, resolve: PortResolver): void {
  portRegistry.set(nodeType, resolve);
}

export function resolvePorts(nodeType: string, data: Record<string, unknown>): PortSpec[] {
  return portRegistry.get(nodeType)?.(data) ?? [];
}

/** 类型查询升级：先查注册表；未注册类型回退 2.3 的 id 内嵌协议（静态端口零改动） */
export function portTypeOf(
  node: { type: string; data: Record<string, unknown> },
  handleId: string | null | undefined,
): string {
  if (handleId != null) {
    const port = resolvePorts(node.type, node.data).find(p => p.key === handleId);
    if (port) return port.type;
  }
  return handleId?.includes(':') ? handleId.split(':')[1] : 'any';
}

/** 悬空边检测：端口消失后挂在它上面的边（删除分支后的清理依据，也用于保存前校验） */
export function findDanglingEdges(
  nodes: { id: string; type: string; data: Record<string, unknown> }[],
  edges: { id: string; source: string; sourceHandle?: string | null; target: string; targetHandle?: string | null }[],
): string[] {
  const nodeById = new Map(nodes.map(n => [n.id, n]));
  return edges
    .filter(edge => {
      const source = nodeById.get(edge.source);
      const target = nodeById.get(edge.target);
      if (!source || !target) return true; // 节点没了：同样悬空（级联清理见 2.1 坑 2）
      const sourceKeys = new Set(
        resolvePorts(source.type, source.data).filter(p => p.direction === 'out').map(p => p.key),
      );
      const targetKeys = new Set(
        resolvePorts(target.type, target.data).filter(p => p.direction === 'in').map(p => p.key),
      );
      const staleSource = edge.sourceHandle != null && !sourceKeys.has(edge.sourceHandle);
      const staleTarget = edge.targetHandle != null && !targetKeys.has(edge.targetHandle);
      return staleSource || staleTarget;
    })
    .map(edge => edge.id);
}
```

condition 节点注册动态端口（与 2.7 的 `branches` 协议对齐——每个分支一个出口）：

```ts
interface BranchItem {
```

自定义节点的动态 Handle 渲染（多端口沿侧边均分；删除分支的同步清边）：

```tsx
import { memo, useCallback } from 'react';
import { Handle, Position, useReactFlow, type Node, type NodeProps } from '@xyflow/react';

export type ConditionNodeData = {
  title: string;
  branches: BranchItem[];
  collapsed: boolean;
  status: 'idle' | 'running' | 'success' | 'error';
};
export type ConditionNode = Node<ConditionNodeData, 'condition'>;

function ConditionNodeView({ id, data, selected }: NodeProps<ConditionNode>) {
  const { setNodes, setEdges } = useReactFlow();
  const outs = resolvePorts('condition', { ...data }).filter(p => p.direction === 'out');

  const updateData = useCallback(
    <K extends keyof ConditionNodeData>(key: K, value: ConditionNodeData[K]) => {
      setNodes(nodes =>
        nodes.map(n => (n.id === id ? { ...n, data: { ...n.data, [key]: value } } : n)),
      );
    },
    [id, setNodes],
  );

  /** 加分支：只增端口，不动边——新增端口不可能产生悬空 */
  const addBranch = () => {
    updateData('branches', [
      ...data.branches,
      { id: crypto.randomUUID(), when: { field: '', operator: '==', value: '' }, next: [] },
    ]);
  };

  /** 删分支：端口消失，挂在它上面的边必须同步清理（两个 actor 一次提交里做完） */
  const removeBranch = (branchId: string) => {
    updateData('branches', data.branches.filter(b => b.id !== branchId));
    setEdges(edges => edges.filter(e => e.sourceHandle !== `out:${branchId}`));
  };

  return (
    <div
      style={{
        minWidth: 240,
        borderRadius: 8,
        background: '#fff',
        border: selected ? '2px solid #1677ff' : '1px solid #d9d9d9',
        fontSize: 12,
      }}
    >
      <Handle type="target" position={Position.Left} id="in:json" />
      <div style={{ padding: '8px 12px', fontWeight: 600 }}>{data.title}</div>
      {!data.collapsed && (
        <div style={{ padding: 12, display: 'grid', gap: 8 }}>
          {data.branches.map(branch => (
            <div key={branch.id} style={{ display: 'flex', gap: 4 }}>
              <input
                value={String(branch.when.field)}
                placeholder="字段"
                onChange={e =>
                  updateData(
                    'branches',
                    data.branches.map(b =>
                      b.id === branch.id
                        ? { ...b, when: { ...b.when, field: e.target.value } }
                        : b,
                    ),
                  )
                }
              />
              <button onClick={() => removeBranch(branch.id)}>删</button>
            </div>
          ))}
          <button onClick={addBranch}>+ 分支</button>
        </div>
      )}
      {/* 动态出端口：沿右侧边均分；handle 永远渲染（2.2 的规矩） */}
      {outs.map((port, i) => (
        <Handle
          key={port.key}
          type="source"
          position={Position.Right}
          id={port.key}
          style={{ top: `${((i + 1) / (outs.length + 1)) * 100}%` }}
        />
      ))}
    </div>
  );
}

export default memo(ConditionNodeView);
```

**选型与学习路径**：静态端口（固定的 in/out 一对）覆盖 80% 的节点类型，不要为了"通用"全盘动态化——动态端口的成本在悬空边治理与测试矩阵（端口数 0/1/N × 连线状态）。判断信号：节点配置里存在"可增删的列表"且列表项语义上就是路由出口（分支、并行腿、字段映射），才值得动态端口。路径：先写注册表与 `portTypeOf`（把 2.3 的 `isValidConnection` 里两处 `portType(...)` 换成 `portTypeOf(node, handleId)`）→ 再做节点的动态 Handle 渲染 → 最后补 `findDanglingEdges` 进保存前校验。

**常见坑**：

- **症状**：在中间位置插入一个分支后，原有的边全接到了错误的分支上。**根因**：handle 用数组下标当 key（`out:0`、`out:1`），插入后下标整体位移，边的 `sourceHandle` 指向的 key 没变但语义变了。**修法**：key 一律用稳定 id（branchId，上面代码的 `out:${branch.id}`）。
- **症状**：删分支后保存被 2.1 校验拦下，报"next 指向不存在的节点"。**根因**：端口消失但边没清，序列化时分支的 `next` 还带着旧值（或派生 edges 与 data 不一致）。**修法**：`removeBranch` 里同步 `setEdges`（上面代码）；保存前再跑一遍 `findDanglingEdges` 兜底。
- **症状**：分支到十几个，节点被 Handle 撑得极高。**根因**：端口均分策略下端口数与高度线性相关。**修法**：端口超过 6 个折叠为"+N 出口"聚合端口，点击展开；或分支编辑挪到 2.2 的折叠表单里，画布只显示前 3 个端口。

### 2.9 边的路由与编辑体验：边型选型、布局弯折、避障与重连

**是什么**：三个此前只当黑盒用的能力展开——**边型**（连线画成什么形状：贝塞尔/平滑折线/直角）、**边路由**（线走哪条路径：让 2.4 的 ELK 布局顺手把弯折点也算了）、**边编辑**（连错了不用删了重来：拖端点重连；拖新节点到线上自动拆边插入）。

**为什么难**：默认的贝塞尔边在 LR 分层图里交叉严重、方向感差；smoothstep 不避障，线直接穿过节点卡片；而"改连线"的常用诉求（换目标、中间插节点）在只有"删除 + 重连"的世界里要多操作两三次。环检测已在 2.3 展开，本节所有校验直接复用。

**边型选型**（内置四型对比）：

| 边型 | 形状 | 适用 | 代价 |
|---|---|---|---|
| `default`（bezier） | 三次贝塞尔曲线 | 少量边的美化展示、原型期 | 分层图里交叉多、走向难读 |
| `straight` | 直线 | 稀疏图、强调"直接" | 穿节点最严重 |
| `step` | 直角折线（无圆角） | 正交流程图骨架 | 视觉生硬 |
| `smoothstep` | 圆角直角折线 | **LR/TB 工作流默认之选** | 不避障（线穿节点） |

**机制一：自定义正交边 + ELK 弯折点**。2.4 的 `layoutWithElk` 调用 `elk.layout(graph)` 时，ELK Layered 的返回值里**每条边都带 `sections[].bendPoints`**（布局引擎已做过边避让）——把它存进 `edge.data.bends`，自定义边优先按弯折点画折线；节点一旦被拖动，布局弯折点即失效，自动退回 smoothstep：

```tsx
import { memo } from 'react';
import { BaseEdge, getSmoothStepPath, type Edge, type EdgeProps } from '@xyflow/react';

export type OrthoEdgeData = { bends?: Array<{ x: number; y: number }> };
export type OrthoEdge = Edge<OrthoEdgeData, 'ortho'>;

/** 正交边：有布局弯折点按弯折点画（ELK 避障结果），没有则退回 smoothstep */
function OrthoEdgeView({
  id,
  sourceX,
  sourceY,
  targetX,
  targetY,
  sourcePosition,
  targetPosition,
  markerEnd,
  data,
}: EdgeProps<OrthoEdge>) {
  const bends = data?.bends;
  const path =
    bends && bends.length > 0
      ? [
          `M ${sourceX} ${sourceY}`,
          ...bends.map(b => `L ${b.x} ${b.y}`),
          `L ${targetX} ${targetY}`,
        ].join(' ')
      : getSmoothStepPath({
          sourceX,
          sourceY,
          sourcePosition,
          targetX,
          targetY,
          targetPosition,
          borderRadius: 12,
        });

  // BaseEdge 自带 20px 宽的透明命中区（interactionWidth），细线也好点选
  return <BaseEdge id={id} path={path} markerEnd={markerEnd} />;
}

export default memo(OrthoEdgeView);
```

从 ELK 结果提取弯折点（衔接 2.4 的 `layoutWithElk`——把 `elk.layout` 的返回图也交出来）：

```ts
import type { Edge } from '@xyflow/react';
import type { ElkNode } from 'elkjs';
import type { OrthoEdgeData } from './OrthoEdgeView';

/** ELK 布局图的边路由 → edge.data.bends；无弯折的边保持原样 */
export function withElkBends(laidGraph: ElkNode, edges: Edge[]): Edge<OrthoEdgeData>[] {
  const bendsByEdge = new Map<string, Array<{ x: number; y: number }>>();
  for (const edge of laidGraph.edges ?? []) {
    const section = edge.sections?.[0];
    if (section?.bendPoints && section.bendPoints.length > 0) {
      bendsByEdge.set(edge.id, section.bendPoints.map(b => ({ x: b.x, y: b.y })));
    }
  }
  return edges.map(edge => {
    const bends = bendsByEdge.get(edge.id);
    return bends ? { ...edge, data: { ...edge.data, bends } } : (edge as Edge<OrthoEdgeData>);
  });
}
```

**机制三：拖节点到线上插入（drop-on-edge）**。从节点面板拖一个新节点、落点贴近某条边时，把 `A→B` 拆成 `A→新→B`——n8n 式"顺手插一步"的体验。判定用点到线段距离（边以两端节点边缘中点近似）：

```tsx
import {
  useReactFlow,
  type Edge,
  type Node,
} from '@xyflow/react';

const DROP_HIT_RADIUS = 28; // 距边线的命中半径（画布坐标）

/** 点到线段距离：插入判定的几何底座 */
function distToSegment(
  px: number, py: number,
  x1: number, y1: number,
  x2: number, y2: number,
): number {
  const dx = x2 - x1;
  const dy = y2 - y1;
  const lenSq = dx * dx + dy * dy;
  const t = lenSq === 0 ? 0 : Math.max(0, Math.min(1, ((px - x1) * dx + (py - y1) * dy) / lenSq));
  return Math.hypot(px - (x1 + t * dx), py - (y1 + t * dy));
}

/** 落点附近是否有边（用两端节点边缘中点连线近似边路径；LR 布局下误差可接受） */
export function findEdgeAtPoint(
  point: { x: number; y: number },
  nodes: Node[],
  edges: Edge[],
): Edge | null {
  const nodeById = new Map(nodes.map(n => [n.id, n]));
  let best: { edge: Edge; dist: number } | null = null;
  for (const edge of edges) {
    const s = nodeById.get(edge.source);
    const t = nodeById.get(edge.target);
    if (!s || !t) continue;
    const sw = s.measured?.width ?? 260;
    const sh = s.measured?.height ?? 90;
    const tw = t.measured?.width ?? 260;
    const th = t.measured?.height ?? 90;
    const dist = distToSegment(
      point.x, point.y,
      s.position.x + sw, s.position.y + sh / 2, // 源节点右边缘中点
      t.position.x, t.position.y + th / 2,      // 目标节点左边缘中点
    );
    if (dist <= DROP_HIT_RADIUS && (!best || dist < best.dist)) best = { edge, dist };
  }
  return best?.edge ?? null;
}

/** onDrop 接线：命中边则拆边插入，否则普通落点 */
export function useDropOnCanvas() {
  const { screenToFlowPosition, getNodes, getEdges, setNodes, setEdges } = useReactFlow();

  return useCallback(
    (event: React.DragEvent) => {
      event.preventDefault();
      const nodeType = event.dataTransfer.getData('application/reactflow-node');
      if (!nodeType) return;
      const position = screenToFlowPosition({ x: event.clientX, y: event.clientY });
      const hit = findEdgeAtPoint(position, getNodes(), getEdges());

      const newNode: Node = {
        id: crypto.randomUUID(),
        type: nodeType,
        position,
        data: {},
      };
      if (!hit) {
        setNodes(nodes => [...nodes, newNode]);
        return;
      }
      // A→B 拆成 A→新→B（sourceHandle/targetHandle 沿用原边，端口协议 2.8 兜底校验）
      setNodes(nodes => [...nodes, newNode]);
      setEdges(edges => [
        ...edges.filter(e => e.id !== hit.id),
        {
          id: crypto.randomUUID(),
          source: hit.source,
          target: newNode.id,
          sourceHandle: hit.sourceHandle,
          type: 'ortho',
        },
        {
          id: crypto.randomUUID(),
          source: newNode.id,
          target: hit.target,
          targetHandle: hit.targetHandle,
          type: 'ortho',
        },
      ]);
    },
    [screenToFlowPosition, getNodes, getEdges, setNodes, setEdges],
  );
}
```

**选型与学习路径**：边型直接全局默认 `smoothstep`（`defaultEdgeOptions={{ type: 'smoothstep' }}`），追求 n8n 观感时上"ELK 布局 + bends 正交边"组合；**不要自研避障**（A* 网格路由器的实现成本远超收益，那是专门的图形学课题——大图可视化的边处理见全景图 06-C，本节不越界）。路径：先统一边型与 `defaultEdgeOptions` → 接 onReconnect（半小时的活，体验提升立竿见影）→ 再做 ELK bends → 最后做 drop-on-edge。

**常见坑**：

- **症状**：控制台警告 `It looks like you've created a new edgeTypes object`，边闪烁。**根因**：`edgeTypes` 写在组件内，每次渲染新引用。**修法**：模块级常量——与 2.2 的 nodeTypes 同一条规矩。
- **症状**：节点拖了半格，边的弯折点还停在旧位置，线"折空"。**根因**：bends 是布局时刻的绝对坐标，节点动了就失真。**修法**：`onNodeDrag` 一开始就清该画布全部 bends（上面注释代码），退回 smoothstep。
- **症状**：重连后旧边还在、出现平行双线。**根因**：`onReconnect` 里手写"删旧加新"只加了没删，或没用 `reconnectEdge` 工具函数。**修法**：统一用 `reconnectEdge(oldEdge, newConnection, edges)`。
- **症状**：拖节点到线上释放，每次都插不进去、变成普通落点。**根因**：命中半径太小/太大，或节点拖拽用的是 dnd-kit 面板而非 React Flow 原生拖入，`getData` 的 MIME 对不上。**修法**：半径按节点宽度的一半起步（24–32）；面板拖拽在 `onDragStart` 里 `setData('application/reactflow-node', type)` 并 `effectAllowed = 'move'`。

### 2.10 画布交互进阶：框选、对齐分布、网格吸附与只读锁定

**是什么**：多节点批量操作与画布模式管理四件套——**框选**（橡皮筋多选 + Shift 加选）、**对齐/分布**（选集一键左对齐/垂直居中/等距分布）、**网格吸附**（snapToGrid）、**只读与锁定**（运行详情页内嵌画布、个别节点钉死）。底层几何（求交、吸附参考线）在场景 1 的 1.2 与场景 5 白板的路线 4 已完整展开，本节只讲 React Flow 的开关矩阵与命令实现。

**为什么难**：React Flow 把这些能力做成了**一组分散的 props 开关**（`selectionOnDrag`、`panOnDrag`、`nodesDraggable`、`deleteKeyCode`……），单个都简单，组合出的"模式"（编辑/只读/锁定）需要自己定义并保证一致性；对齐/分布是命令式几何计算，且必须与 2.6 的快照纪律配合（一次对齐 = 一步 undo，而不是每个节点一步）。

**机制一：框选与多选**。两个关键开关：`selectionOnDrag`（拖空白即框选）与 `panOnDrag` 的配合——开了框选就得把平移让给滚轮/触控板（`panOnScroll`），否则两个行为抢"拖空白"这一个手势；`multiSelectionKeyCode`（默认 Shift）控制点击加选。推荐组合：桌面端 `panOnScroll zoomOnScroll={false}` + `selectionOnDrag` + `panOnDrag={false}`... 注意这是"Figma 手势"（拖 = 框选、滚轮 = 缩放、空格+拖 = 平移），与默认的"拖 = 平移、Shift+拖 = 框选"是两种习惯，按用户群选一个并保持全局一致。

**机制二：对齐与分布命令**（纯函数，输入选中节点输出新 position 数组；尺寸用 `node.measured`——2.4 的回退约定不变）：

```ts
import type { Node } from '@xyflow/react';

type Rect = { x: number; y: number; w: number; h: number };

function rectOf(node: Node): Rect {
  return {
    x: node.position.x,
    y: node.position.y,
    w: node.measured?.width ?? 260,
    h: node.measured?.height ?? 90,
  };
}

export type AlignMode = 'left' | 'hcenter' | 'right' | 'top' | 'vcenter' | 'bottom';

/** 对齐：以选集 bbox 的对应边/中线为目标线，逐个改 position；未移动的节点保持原引用 */
export function alignSelection(nodes: Node[], mode: AlignMode): Node[] {
  if (nodes.length < 2) return nodes;
  const rects = nodes.map(rectOf);
  const left = Math.min(...rects.map(r => r.x));
  const right = Math.max(...rects.map(r => r.x + r.w));
  const top = Math.min(...rects.map(r => r.y));
  const bottom = Math.max(...rects.map(r => r.y + r.h));

  return nodes.map((node, i) => {
    const r = rects[i];
    let { x, y } = r;
    switch (mode) {
      case 'left': x = left; break;
      case 'right': x = right - r.w; break;
      case 'hcenter': x = (left + right) / 2 - r.w / 2; break;
      case 'top': y = top; break;
      case 'bottom': y = bottom - r.h; break;
      case 'vcenter': y = (top + bottom) / 2 - r.h / 2; break;
    }
    return x === r.x && y === r.y ? node : { ...node, position: { x, y } };
  });
}

/** 分布：沿轴等间距。节点 < 3 或已重叠（gap < 0）返回 null——工具栏按钮置灰的依据 */
export function distributeSelection(nodes: Node[], axis: 'h' | 'v'): Node[] | null {
  if (nodes.length < 3) return null;
  const keyed = nodes
    .map(node => ({ node, rect: rectOf(node) }))
    .sort((a, b) => (axis === 'h' ? a.rect.x - b.rect.x : a.rect.y - b.rect.y));
  const first = keyed[0].rect;
  const last = keyed[keyed.length - 1].rect;
  const spanStart = axis === 'h' ? first.x : first.y;
  const spanEnd = axis === 'h' ? last.x + last.w : last.y + last.h;
  const totalSize = keyed.reduce((sum, { rect }) => sum + (axis === 'h' ? rect.w : rect.h), 0);
  const gap = (spanEnd - spanStart - totalSize) / (keyed.length - 1);
  if (gap < 0) return null; // 有重叠：等距分布无解，交还用户手动整理

  let cursor = spanStart;
  return keyed.map(({ node, rect }) => {
    const next: Node = {
      ...node,
      position: axis === 'h' ? { x: cursor, y: rect.y } : { x: rect.x, y: cursor },
    };
    cursor += (axis === 'h' ? rect.w : rect.h) + gap;
    return next;
  });
}
```

**常见坑**：

- **症状**：开了框选后画布拖不动了，用户只能用滚轮。**根因**：`selectionOnDrag` 与 `panOnDrag` 抢同一个"拖空白"手势，`panOnDrag={false}` 后没给平移留替代入口。**修法**：`panOnScroll` + 空格临时平移（监听 keydown 切 `panOnDrag`），或保留默认"Shift 框选"方案不动。
- **症状**：对齐三个节点，undo 要按三次才回去。**根因**：每个节点的 position 变化各自入栈。**修法**：命令级快照——`applyAlign` 里一次 `commit`（上面代码），与 2.4 自动布局的快照纪律一致。
- **症状**：只读模式里按 Backspace，节点还是被删了。**根因**：只关了 `nodesDraggable`，`deleteKeyCode` 还是默认值。**修法**：props 矩阵里显式 `deleteKeyCode: null`（上面代码）。
- **症状**：锁定节点单点拖不动，但框选后拖选区它跟着走。**根因**：拦截做在节点组件的 pointer 事件上，框选拖动走的是 changes 管线。**修法**：锁定拦截必须在 `onNodesChange` 管线（上面代码），事件层拦截只能算 UI 增强。

### 2.11 执行态可视化进阶：运行事件流、进度回放与日志面板联动

**是什么**：2.5 解决"高频状态**怎么刷**"（rAF 聚合管道），本节解决"执行过程**怎么看**"——三件事：**运行事件流**（把一次 run 的全部事件按序落成日志，而不是刷完即逝）；**进度回放**（历史 run 拖时间轴重现任意时刻的画布状态——"昨晚两点那次失败走到哪了"）；**节点↔日志双向联动**（点节点过滤日志、点日志定位节点）。单节点的输入输出调试面板已由全景图 F2.3 展开，本节不重讲。

**为什么难**：直播态看一遍就过去，出问题要能"倒带"；一次大 run 的事件几千条，回放不能每条 setNodes（那是 2.5 反例的原样重演）；回放与直播共享同一条渲染管道（都改 `data.status`），否则两套状态语义必然漂移；时间轴要同时支持"拖到某刻"（随机访问）与"倍速播放"（顺序推进）两种驱动。

**关键机制**：

1. **事件协议**：在 2.5 的推送消息上补 `seq`（全局递增）与 `ts`，并增加日志类事件——直播态照旧走 `applyPatch`，同时 append 进环形缓冲；
2. **快照折叠**：`foldEvents(events, uptoSeq)` 从头重放事件序列、计算任意时刻的全节点状态 Map——回放的随机访问就是一次 fold + 一次批量 setNodes；
3. **播放器**：倍速播放用 rAF 推进 seq 指针（"真实时间 × 倍速 = 回放时间"的插值思想与全景图 06-C 地图轨迹回放同源），每帧最多 fold + setNodes 一次——2.5 的纪律在回放侧的翻版；
4. **联动**：日志行点击 → `setCenter` 定位节点；节点选中 → 日志列表按 nodeId 过滤。

事件协议与折叠：

```ts
export type NodeRunStatus = 'idle' | 'running' | 'success' | 'error';

/** 运行事件：直播、回放、日志面板共同的唯一事实来源 */
export interface RunEvent {
  seq: number; // 全局递增：并发分支的事件也严格有序（2.5 坑 2 的乱序问题在这里根治）
  ts: number;
  kind: 'run-start' | 'node-status' | 'node-log' | 'run-finish';
  nodeId?: string;
  status?: NodeRunStatus; // kind = node-status
  level?: 'info' | 'warn' | 'error'; // kind = node-log
  message?: string;
}

/** 折叠：重放事件序列到 uptoSeq，得到该时刻的全节点状态（回放随机访问的核心） */
export function foldEventsToStatus(events: RunEvent[], uptoSeq: number): Map<string, NodeRunStatus> {
  const status = new Map<string, NodeRunStatus>();
  for (const event of events) {
    if (event.seq > uptoSeq) break;
    if (event.kind === 'node-status' && event.nodeId && event.status) {
      status.set(event.nodeId, event.status); // 后到覆盖先到：同节点多轮循环取最新
    }
  }
  return status;
}
```

直播态接入（在 2.5 的 `useRunStream` 上加两件事：环形缓冲 + 边激活集合）：

```tsx
import { useCallback, useEffect, useRef } from 'react';
import { useReactFlow, type Node } from '@xyflow/react';

const LIVE_BUFFER_LIMIT = 5000; // 环形缓冲：防长 run 把内存吃穿（完整历史回放走后端分页）

/** 直播 → 事件缓冲：每条推送同时进 2.5 的 rAF 管道（画布）与环形缓冲（日志/回放） */
export function useLiveEventCollector() {
  const bufferRef = useRef<RunEvent[]>([]);
  const { setNodes, setEdges } = useReactFlow();

  const ingest = useCallback(
    (event: RunEvent) => {
      const buffer = bufferRef.current;
      buffer.push(event);
      if (buffer.length > LIVE_BUFFER_LIMIT) buffer.splice(0, buffer.length - LIVE_BUFFER_LIMIT);

      if (event.kind === 'node-status' && event.nodeId && event.status) {
        // 画布高亮：走 2.5 的 applyPatch（此处示意直接 setNodes，工程上换 applyPatch 通道）
        setNodes(nodes =>
          nodes.map(node =>
            node.id === event.nodeId && (node.data as { status?: NodeRunStatus }).status !== event.status
              ? { ...node, data: { ...node.data, status: event.status } }
              : node,
          ),
        );
        // 边激活：正在执行的节点与直接前驱之间的边加 animated（React Flow 内置流动虚线）
        if (event.status === 'running') {
          setEdges(edges =>
            edges.map(e =>
              e.target === event.nodeId
                ? { ...e, animated: true }
                : e.animated
                  ? { ...e, animated: false }
                  : e,
            ),
          );
        }
      }
    },
    [setNodes, setEdges],
  );

  useEffect(() => () => { bufferRef.current = []; }, []); // 切 run 清缓冲
  return { ingest, bufferRef };
}
```

回放控制器（rAF 推进 seq，每帧一次 fold + 批量写回）：

```tsx
import { useCallback, useEffect, useRef, useState } from 'react';
import { useReactFlow } from '@xyflow/react';

export function useReplayController(events: RunEvent[]) {
  const { setNodes } = useReactFlow();
  const [playing, setPlaying] = useState(false);
  const [speed, setSpeed] = useState(1);
  const [playheadSeq, setPlayheadSeq] = useState(0); // 当前回放到的事件序号
  const maxSeq = events.length > 0 ? events[events.length - 1].seq : 0;
  const rafRef = useRef<number | null>(null);
  const lastTsRef = useRef<number>(0);

  /** 把某时刻的状态快照写回画布：只更新发生变化的节点（引用稳定性纪律同 2.5） */
  const applySnapshot = useCallback(
    (uptoSeq: number) => {
      const snapshot = foldEventsToStatus(events, uptoSeq);
      setNodes(nodes =>
        nodes.map((node): Node => {
          const next = snapshot.get(node.id);
          if (!next) return node;
          return (node.data as { status?: NodeRunStatus }).status === next
            ? node // 状态没变：原引用返回，memo 生效
            : { ...node, data: { ...node.data, status: next } };
        }),
      );
    },
    [events, setNodes],
  );

  // 播放：rAF 推进 seq（真实时间 × speed），每帧最多一次 fold + setNodes
  useEffect(() => {
    if (!playing) return;
    lastTsRef.current = performance.now();
    const tick = (now: number) => {
      const dt = now - lastTsRef.current;
      lastTsRef.current = now;
      setPlayheadSeq(prev => {
        const next = Math.min(maxSeq, prev + Math.max(1, Math.round((dt / 1000) * speed * 20)));
        return next;
      });
      rafRef.current = requestAnimationFrame(tick);
    };
    rafRef.current = requestAnimationFrame(tick);
    return () => {
      if (rafRef.current !== null) cancelAnimationFrame(rafRef.current);
    };
  }, [playing, speed, maxSeq]);

  // playhead 变化 → 快照写回（拖时间轴与播放共用一条路）
  useEffect(() => {
    applySnapshot(playheadSeq);
  }, [playheadSeq, applySnapshot]);

  // 播完自动停
  useEffect(() => {
    if (playing && playheadSeq >= maxSeq) setPlaying(false);
  }, [playing, playheadSeq, maxSeq]);

  const toggle = useCallback(() => setPlaying(p => !p), []);
  const seek = useCallback((seq: number) => setPlayheadSeq(Math.max(0, Math.min(maxSeq, seq))), [maxSeq]);

  return { playing, toggle, seek, playheadSeq, maxSeq, setSpeed, speed };
}
```

**常见坑**：

- **症状**：拖时间轴画布狂卡。**根因**：seek 过程中每经过一个事件都 setNodes 一次，等于把 2.5 的反例重演。**修法**：playhead 是唯一状态，快照写回在 `useEffect([playheadSeq])` 里一次完成（上面代码）；拖动中的连续 seek 会被 rAF 与 React 批处理自然合并。
- **症状**：并行分支的事件在回放里"超前生效"。**根因**：事件按到达顺序（ts）排序，而 fold 要求按 seq 全序。**修法**：缓冲阶段就按 seq 稳定排序；显示时间用 ts、重放顺序用 seq，两套口径别混。
- **症状**：直播看着正常，切到回放再切回来，节点状态"冻住"。**根因**：直播与回放双写 nodes，回放的最后快照覆盖了直播最新状态，且 WS 通道没断、新事件还在进缓冲但 applySnapshot 停了。**修法**：模式互斥——进入回放先暂停直播写回（ingest 只进缓冲不改画布），退出回放时用缓冲尾部 fold 一次最新快照再恢复直播。
- **症状**：折叠节点（2.2 的 collapsed）在回放里完全看不出状态变化。**根因**：回放只改 status，而折叠态的表单体不渲染、徽标又在表单体里。**修法**：状态徽标必须在头部行渲染（2.2 的实现已保证）；回放模式下可再强制全部折叠换流畅度——两者不冲突。

### 2.12 节点面板（Palette）：注册、搜索与三种添加方式

**是什么**：画布左侧的节点库——按分类分组、可搜索、能把节点"放进"画布。三种添加路径：**拖拽**（主路径，从面板拖到画布任意位置）、**点击**（快速追加到视口附近的空位）、**搜索回车**（面板内 Cmd/Ctrl+F 聚焦，回车落中心——键盘党的 n8n 式路径）。

**为什么难**：面板是节点生态的门面——节点类型到 30+ 时"找到想加的节点"比"加上之后"更影响体验；新节点的**默认值**决定第一次使用印象（URL 空着、method 给 GET，用户只需改一个字段）；拖入落点要与已有节点避让，否则每次拖入都叠在别人身上；面板的元数据与 2.8 的端口注册表如果各写一份，迟早漂移成两个真相。

**关键机制**：

1. **元信息注册表**：`NodePaletteMeta { type, label, group, keywords, defaultData, defaultSize }`——与 2.8 的 `portRegistry` 平行的"元信息先行"层（暗线：与场景 1 的 `MaterialMeta` 两层注册表同构——元信息同步、实现异步）。面板列表**派生**自注册表，不手写数组；
2. **defaultData 是工厂函数不是对象**：`() => ({ ... })`——对象会在所有新建节点间共享引用（2.6 的 Cmd+D 已提示过 data 拷贝问题，这里在源头堵死）；运行态字段（`status: 'idle'`、`collapsed`）统一由创建函数注入，物料声明不用关心；
3. **搜索**：label 前缀 + keywords 别名包含匹配（keywords 手写同义词与英文缩写，拼音匹配是锦上添花，先用 keywords 覆盖高频别名）；分组折叠态记忆在 localStorage；
4. **落点避让**：目标位置与现有节点碰撞时沿对角线级联偏移（+40/+40），撞 50 次仍无位就认命放下（画布无限大，50 步内必然空旷）；
5. **MIME 协议复用**：面板拖拽 `setData('application/reactflow-node', type)`——与 2.9 的 drop-on-edge 同一条数据通道，onDrop 统一入口。

```ts
const CASCADE_STEP = 40;
const CASCADE_LIMIT = 50;

/** 落点避让：与现有节点碰撞则沿对角线级联偏移；50 步内必然空旷（画布无限） */
export function findFreePosition(
  desired: { x: number; y: number },
  size: { width: number; height: number },
  occupied: Array<{ x: number; y: number; width: number; height: number }>,
): { x: number; y: number } {
  const collides = (x: number, y: number) =>
    occupied.some(
      o =>
        x < o.x + o.width && x + size.width > o.x && y < o.y + o.height && y + size.height > o.y,
    );
  let { x, y } = desired;
  for (let i = 0; collides(x, y) && i < CASCADE_LIMIT; i++) {
    x += CASCADE_STEP;
    y += CASCADE_STEP;
  }
  return { x: Math.round(x), y: Math.round(y) }; // 取整：像素对齐减轻 subpixel 模糊
```

### 2.13 子流程：引用、参数映射与画布进入模式

**是什么**：subflow 节点——画布上的一个节点代表**一整张工作流**（n8n 的 sub-workflow、Dify 的子应用）。协议：`type: 'subflow'`，`data` 里带引用（`workflowRef` + 版本策略）与参数映射（父上下文的哪些值作为子流程输入）。双击节点"进入"子流程的编辑画布（面包屑导航返回）。

**为什么难**：三个边界问题。**引用的边界**：子流程被改了，引用它的父流程受不受影响（版本策略）——与场景 1 物料版本（1.7）同族问题换了宿主；**执行的边界**：子流程的内部变量会不会污染父流程上下文；**图的边界**：子流程引用成环（A 引 B、B 引 A）会让加载器死循环。另外画布交互上"进入子流程"有两种做法要选型。

**关键机制**：

1. **协议**：`SubflowNodeData { workflowRef, version, paramMapping, outputs }`——`paramMapping` 是"子流程输入名 → 父上下文取值路径"的映射表（求值复用 2.7 的 `getByPath` 思想）；`outputs` 声明子流程结束时哪些变量回流父上下文（显式声明，不隐式全量合并）；
2. **执行语义两派对比后选"运行时调用"**：静态内联（保存时把子流程节点替换成其 DSL 拼进父图——调度器零改动，但失去边界：子流程无法独立重试、无法有自己的 run 记录与回放）vs 运行时调用（调度器遇到 subflow 递归跑子 run——边界清晰、2.11 的事件流天然按 run 分档）。选运行时调用，对齐 n8n 的 `executeWorkflow`；
3. **画布进入模式选"路由切换"**：React Flow 的 parent/child 嵌套渲染（子节点随父拖动）语义上不适合"子流程"（它不是分组，是另一张图）；路由切换（`/flows/:flowId`）让编辑器整体换 DSL，undo 栈按流程天然隔离，面包屑 = 栈；
4. **环引用检测**：加载父 DSL 时沿 `workflowRef` 做 DFS，命中"访问中"节点即环——**在加载时发现，不是运行时死循环了才**；
5. **版本策略**：`latest`（跟随最新，开发期方便）vs `pinned`（锁版本，生产稳态）——协商机制一句话指路场景 1 的 1.7（物料 → 工作流，同一套"引用 + 版本 + 迁移"问题族）。

环引用检测（加载时）：

```ts
/**
 * subflow 引用环检测：沿 workflowRef 做 DFS，"访问中"命中即环。
 * 输入是已加载的 DSL 集合（编辑器打开父流程时预取直接子流程，孙子按需取）。
 * 返回环路径（人话报错用），无环返回 null。
 */
export function detectSubflowCycle(
  loaded: Map<string, WorkflowDSL>,
  rootId: string,
  maxDepth = 20, // 深度上限：即使无环，20 层嵌套的子流程也该重构了
): string[] | null {
  const visiting = new Set<string>();
  const done = new Set<string>();
  const path: string[] = [];

  const dfs = (id: string, depth: number): string[] | null => {
    if (done.has(id)) return null;
    if (depth > maxDepth) return [...path, `${id}(超过深度上限)`];
    if (visiting.has(id)) return [...path.slice(path.indexOf(id)), id]; // 环：截取从重复点到当前的路径
    visiting.add(id);
    path.push(id);
    const dsl = loaded.get(id);
    if (dsl) {
      for (const node of dsl.nodes) {
        if (node.type === 'subflow') {
          const ref = (node.data as SubflowNodeData).workflowRef;
          const cycle = dfs(ref, depth + 1);
          if (cycle) return cycle;
        }
      }
    }
    visiting.delete(id);
    path.pop();
    done.add(id);
    return null;
  };

  return dfs(rootId, 0);
}
```

**常见坑**：

- **症状**：子流程里写的变量莫名出现在父流程的条件判断里，行为时好时坏。**根因**：子流程与父流程共享了同一个 variables 对象（2.7 的 runWorkflow 内部 `Object.assign(variables, ...)` 写穿）。**修法**：`executeSubflow` 给子流程全新上下文对象 + `outputs` 白名单回流（上面代码的隔离是设计约束，不是优化）。

- **症状**：进入子流程后按 Cmd+Z，把父流程的编辑也回退了。**根因**：undo 栈是全局单例。**修法**：undo 栈随 `flowId` 键控（路由切换即换栈，2.6 的 useHistory 实例挂在编辑器会话上）。
- **症状**：打开父流程白屏/卡死。**根因**：A 引 B、B 引 A，预取子流程时无限递归。**修法**：加载器入口先跑 `detectSubflowCycle`（预取集合上），有环直接报"引用环：A → B → A"并拒绝打开——死循环永远轮不到运行时。
- **症状**：子流程删了几个输出变量，父流程引用它的节点静默拿到 undefined。**根因**：`outputs` 白名单没有校验对端。**修法**：保存子流程时校验"被引用的 outputs 是否仍被产出"（编辑器知道父引用方时做跨流程校验；不知道就运行前把 undefined 输出标 warning）。

### 2.14 失败处理与人工节点：error 路由、重试与审批挂起

**是什么**：2.7 的 mini 调度器是"一错全停"（catch 里上抛终止 run）。生产工作流需要三块补丁：**错误也是路由**（节点失败不终止，走 `errorTo` 分支——告警、降级、补偿逻辑继续编排）；**瞬时故障自动重试**（5xx/超时按策略退避重试，4xx 不浪费子弹）；**人工节点**（执行到"等人审批/确认"时 run 挂起持久化，人处理完恢复继续——把调度器从内存函数变成可中断的状态机）。

**为什么难**：error 路由要防"错误处理链自身成环"（errorTo 的目标又失败，错误无处可去）；重试必须区分**可重试**（瞬时：5xx、网络、超时）与**不可重试**（确定性：4xx、校验失败）——盲目重试 4xx 是打服务器的脸；人工节点改变了 run 的生命周期模型——run 不再是"启动后跑到完"，而是可挂起（suspended）、可恢复（resume），**上下文必须能安全持久化**（函数、class 实例进不了 localStorage）；前端画布要表达"挂起中"并给审批入口。

**关键机制**：

1. **error 路由协议**：节点 `data.errorTo?: string[]`——执行失败时路由到错误分支而非上抛。校验器加一条断言：**errorTo 的目标不得再配置 errorTo**（二层错误无处路由，直接 fail run + 告警——错误处理链必须收敛）；
2. **重试协议**：`data.retry: { maxAttempts, backoffMs, backoff: 'fixed' | 'exponential', retryOn: 'transient' | 'all' }`；判定瞬时错误靠**分类后的错误类型**（自定义 HttpError 携带 status），不是靠 message 字符串；每次重试发事件（2.11 的 RunEvent 加 `node-retry` kind，日志面板与回放直接受益）；
3. **人工节点**：`type: 'human'`，执行语义 = 挂起：把 `{ runId, nodeId, variables 快照 }` 持久化，run 状态置 `suspended`，**调度器以特殊信号退出**（不是 error，不进 errorTo）；审批动作（同意/驳回 + 表单）通过 store 的 `resume(runId, decision)` 恢复——重建 variables、从挂起节点的 next 继续；
4. **run 状态机**：`running → succeeded | failed | suspended`，`suspended → running`（恢复）——run 记录的最小持久化模型；
5. **前端呈现**：human 节点挂起态徽标 `waiting`（2.2 的四态扩成五态）；恢复事件照走 2.11 的事件流——回放里审批等待期表现为时间轴上一段静止，语义正确。

错误分类与重试：

```ts
/** 结构化错误：分类是重试决策的依据。status 0 = 网络层失败/超时（fetch reject 或 AbortError） */
export class HttpError extends Error {
  constructor(
    readonly status: number,
    readonly url: string,
  ) {
    super(`HTTP ${status} ${url}`);
    this.name = 'HttpError';
  }
}

/** 瞬时错误判定：5xx、网络失败可重试；4xx 是确定性失败，重试只会放大流量 */
export function isTransientError(err: unknown): boolean {
  if (err instanceof HttpError) return err.status === 0 || err.status >= 500;
  if (err instanceof TypeError) return true; // fetch 的网络层错误（断网/DNS）是 TypeError
  return false; // 未知错误保守视为不可重试——宁可显式 fail 进 errorTo
}

export interface RetryPolicy {
  maxAttempts: number; // 含首次执行：3 = 首次 + 重试 2 次
  backoffMs: number;
  backoff: 'fixed' | 'exponential';
  retryOn: 'transient' | 'all';
}

export const sleep = (ms: number): Promise<void> => new Promise(resolve => setTimeout(resolve, ms));

/** 重试包装器：策略 + 抖动退避（1.8 的抖动思想——防下游恢复瞬间的重试风暴） */
export async function withRetry<T>(
  task: () => Promise<T>,
  policy: RetryPolicy,
  onRetry?: (attempt: number, err: unknown) => void,
): Promise<T> {
  let lastErr: unknown;
  for (let attempt = 1; attempt <= policy.maxAttempts; attempt++) {
    try {
      return await task();
    } catch (err) {
      lastErr = err;
      if (policy.retryOn === 'transient' && !isTransientError(err)) throw err; // 确定性失败立即上抛
      if (attempt === policy.maxAttempts) break;
      onRetry?.(attempt, err); // 发 node-retry 事件（2.11 的通道）
      const base = policy.backoff === 'exponential' ? policy.backoffMs * 2 ** (attempt - 1) : policy.backoffMs;
      await sleep(base + Math.random() * base * 0.3);
    }
  }
  throw lastErr;
}
```

```ts
      }
    }
  }
```

```ts
export type RunState = 'running' | 'suspended' | 'succeeded' | 'failed';

/** 挂起信号：不是错误——不进 error 路由、run 置 suspended 而非 failed */
export class SuspendSignal extends Error {
  constructor(readonly runId: string, readonly nodeId: string) {
    super(`run 挂起于节点 ${nodeId}`);
    this.name = 'SuspendSignal';
  }

/** 持久化的 run 记录：variables 必须是结构化克隆安全的纯数据（无函数/Date 用 ISO 字符串） */
export interface RunRecord {
  runId: string;
  workflowId: string;
  state: RunState;
  /** 挂起时的完整执行上下文快照（恢复时重建） */
  variables: Record<string, unknown>;
  suspendedAtNode?: string;
  updatedAt: number;
}

export interface RunStore {
  save(record: RunRecord): Promise<void>;
  load(runId: string): Promise<RunRecord | null>;
  /** 审批恢复：decision 由审批 UI 产出。幂等键 = runId + nodeId——重复点击只生效一次 */
  resume(runId: string, decision: { approved: boolean; payload?: Record<string, unknown> }): Promise<void>;
}

/** 恢复：从挂起记录重建上下文，从审批节点的 next 继续（调度器的 runBranch 起点） */
export async function resumeRun(
  runId: string,
  decision: { approved: boolean; payload?: Record<string, unknown> },
  deps: {
    store: RunStore;
    loadWorkflow: (workflowId: string) => Promise<WorkflowDSL>;
    runWorkflow: (dsl: WorkflowDSL, onStatus: (id: string, s: 'idle' | 'running' | 'success' | 'error') => void, initialVariables?: Record<string, unknown>, startAtNextOf?: string) => Promise<Record<string, unknown>>;
  },
): Promise<void> {
  const record = await deps.store.load(runId);
  if (!record || record.state !== 'suspended' || !record.suspendedAtNode) return; // 不存在/非挂起态：幂等返回
  const dsl = await deps.loadWorkflow(record.workflowId);
  const node = dsl.nodes.find(n => n.id === record.suspendedAtNode);
  if (!node) throw new Error(`挂起节点 ${record.suspendedAtNode} 已不存在于工作流（改版后恢复，见 1.7 版本协商）`);
  const variables = { ...record.variables, ...(decision.payload ?? {}) };
  if (!decision.approved) {
    // 驳回：走该节点的 errorTo（未配置则 run 置 failed）
    const errorTo = (node.data as { errorTo?: string[] }).errorTo;
    if (!errorTo?.length) throw new Error('审批驳回且未配置 errorTo，run 终止');
    await deps.runWorkflow(dsl, () => {}, variables, node.id); // 从驳回分支续跑（调度器按 errorTo 路由）
    return;
  }
  await deps.runWorkflow(dsl, () => {}, variables, node.id); // 同意：从 next 续跑
}
```

**常见坑**：

- **症状**：下游服务已恢复，却被重试风暴二次打挂。**根因**：指数退避没加抖动，或 `retryOn: 'all'` 把 4xx 也重试。**修法**：抖动退避（上面代码）+ 默认 `transient`；重试上限 3–5 次，更多次交给 errorTo 的人工介入。
- **症状**：errorTo 分支里的节点又失败，run 悄悄消失，没有任何终态。**根因**：错误处理链二层失败后既不 fail 也没告警。**修法**：validateErrorRoutes 不收敛即拒绝保存（上面代码）；运行时二层错误直接置 failed + 告警事件，绝不静默。
- **症状**：恢复后 variables 里 Date 变成了空对象、函数丢了。**根因**：JSON 序列化只认纯数据。**修法**：快照前做安全序列化（Date → ISO 字符串，函数本来就不该进上下文——上下文只放数据，行为在节点协议里）。
- **症状**：两个人同时点"同意"，run 跑了两遍。**根因**：resume 无幂等。**修法**：幂等键 `runId + nodeId`（store 层 CAS：state 从 suspended → running 只成功一次）；UI 层再加 pending 防抖。
- **症状**：挂起期间工作流被改版，恢复后跑错逻辑。**根因**：恢复时按 workflowId 取了最新版。**修法**：RunRecord 记录挂起时的 DSL 版本（1.7 的版本协商再登场），恢复优先取同版本；同版本不可得时明确报错人工处理，不要"猜着跑"。

### 2.15 画布类应用的测试策略：纯函数层、组件层与 E2E 拖拽

**是什么**：把前三批写的代码按可测性分层：**纯函数层**（validateDag、createsCycle、alignSelection、distributeSelection、foldEventsToStatus、resolvePorts、findFreePosition、detectSubflowCycle——占了本章代码量的一半）、**调度器层**（依赖注入后的 runWorkflow）、**节点组件层**（HttpNodeView 等自定义节点）、**E2E 层**（Playwright 在真实画布上拖拽连线）。策略 = 宝押在纯函数层，组件层薄测，E2E 只走关键路径。

**为什么难**：画布交互依赖指针捕获、坐标换算、HTML5 DnD 协议——而 jsdom 没有布局（`getBoundingClientRect` 全是 0），照抄普通页面的测试写法会全军覆没；React Flow 是重依赖，mock 太深测试变脆（测的是 mock），mock 太浅跑不起来；拖拽连线的 E2E 需要精确的 pointer 事件序列，差一个 `pointerup` 就是"没松手"。

**关键机制**：

1. **纯函数层：表驱动测试**。图算法天然适合"构造小图 + 断言结论"：validateDag 的每个分支（环/悬空/自环/重复边）一张表；distributeSelection 的边界（<3 节点、重叠返回 null）；foldEvents 的乱序回放。再进一步是性质测试（fast-check：随机生成 DAG，断言"校验通过的图拓扑排序必满足偏序"——不变量比样例更防回归）；
2. **调度器层：依赖注入 + fake**。2.7 的 runWorkflow 直接调全局 fetch——为了可测，把 `fetch` 与 `store` 收进 `deps` 参数（默认值指向全局实现，生产行为不变）；
3. **组件层：普通 React 组件直测**。自定义节点只是 React 组件——直接 `render(<HttpNodeView {...props} />)`，不需要 ReactFlow 环境；`useReactFlow` 用 `vi.mock` 保留原模块其余导出只替换它；
4. **E2E 层：稳定选择器 + pointer 序列**。React Flow 的 DOM 自带稳定属性：节点 `.react-flow__node[data-id]`、端口 `.react-flow__handle[data-nodeid][data-handleid]`、边 `.react-flow__edge`——选择器全走它们；连线 = mouse.down → move（带 steps 平滑插值）→ up；面板的 HTML5 DnD 在 Playwright 里要手动构造 DataTransfer（`page.evaluateHandle` 在页面上下文创建，跨进程传引用而非值）；
5. **可测性设计**：点击添加（2.12 的 onAdd）是比 DnD 更可测的等价路径——给每个"拖拽才能用"的功能留键盘/点击备选，E2E 优先走备选路径，拖拽只留一条冒烟。

纯函数层（vitest，表驱动）：

```ts
import { describe, expect, it } from 'vitest';
import { validateDag, type WorkflowDSL, type WfNode } from '../src/dsl';

const node = (id: string, next: string[] = [], type: WfNode['type'] = 'http'): WfNode => ({
  id,
  type,
  position: { x: 0, y: 0 },
  data: {},
  next,
});

const dslOf = (nodes: WfNode[]): WorkflowDSL => ({ version: 1, name: 'test', nodes });

/** 表驱动用例的类型：可选断言字段让一张表覆盖"通过/环/结构错误"三类结论 */
interface DagCase {
  name: string;
  nodes: WfNode[];
  expectOk: boolean;
  expectCyclic?: string[]; // 参与环的节点（排序后比较）
  expectErrorIncludes?: string; // 报错文案包含的片段
}

describe('validateDag 表驱动', () => {
  it.each<DagCase>([
    {
      name: '线性图通过',
      nodes: [node('a', ['b']), node('b', ['c']), node('c')],
      expectOk: true,
    },
    {
      name: '两节点成环——剩余集合即环成员',
      nodes: [node('a', ['b']), node('b', ['a'])],
      expectOk: false,
      expectCyclic: ['a', 'b'],
    },
    {
      name: '环外节点不影响环成员判定',
      nodes: [node('a', ['b']), node('b', ['a']), node('c')],
      expectOk: false,
      expectCyclic: ['a', 'b'],
    },
    {
      name: '悬空 next 报结构错误',
      nodes: [node('a', ['ghost'])],
      expectOk: false,
      expectErrorIncludes: '指向不存在的节点',
    },
    {
      name: '自环直接拦截',
      nodes: [node('a', ['a'])],
      expectOk: false,
      expectErrorIncludes: '自连',
    },
  ])('$name', ({ nodes, expectOk, expectCyclic, expectErrorIncludes }) => {
    const result = validateDag(dslOf(nodes));
    expect(result.ok).toBe(expectOk);
    if (expectCyclic) expect([...result.cyclicNodes].sort()).toEqual(expectCyclic);
    if (expectErrorIncludes) expect(result.errors.join('\n')).toContain(expectErrorIncludes);
  });
});
```

E2E 层（Playwright：连线走 pointer 序列，面板拖入走 DataTransfer 构造）：

```ts
import { expect, test, type Locator } from '@playwright/test';

const center = async (loc: Locator) => {
  const box = await loc.boundingBox();
  if (!box) throw new Error(`元素未渲染：${await loc.count()}`);
  return { x: box.x + box.width / 2, y: box.y + box.height / 2 };
};

test('拖 handle 连线：两点之间出现新边', async ({ page }) => {
  await page.goto('/flows/wf-demo');
  await page.locator('.react-flow__node[data-id="fetch-orders"]').waitFor();

  const source = await center(
    page.locator('.react-flow__node[data-id="fetch-orders"] .react-flow__handle.source'),
  );
  const target = await center(
    page.locator('.react-flow__node[data-id="calc-metrics"] .react-flow__handle.target'),
  );

  await page.mouse.move(source.x, source.y);
  await page.mouse.down();
  await page.mouse.move(target.x, target.y, { steps: 12 }); // steps 插值：模拟真实拖动路径，避免跳变丢 hover
  await page.mouse.up(); // 缺了这步 = "没松手"，React Flow 不会提交连线

  const edges = page.locator('.react-flow__edge');
  await expect(edges).toHaveCount(2, { timeout: 3000 }); // 初始 1 条 + 新连 1 条
});

test('从面板拖入新节点（HTML5 DnD 需要页面上下文的 DataTransfer）', async ({ page }) => {
  await page.goto('/flows/wf-demo');
  // Playwright 的鼠标拖拽不触发 HTML5 dragstart——DataTransfer 必须在页面上下文创建（evaluateHandle 传引用）
  const dataTransfer = await page.evaluateHandle(() => new DataTransfer());
  await page.locator('[data-node-type="http"]').dispatchEvent('dragstart', { dataTransfer });
  const canvas = await center(page.locator('.react-flow'));
  await page.locator('.react-flow').dispatchEvent('dragover', {
    dataTransfer,
    clientX: canvas.x,
    clientY: canvas.y,
  });
  await page.locator('.react-flow').dispatchEvent('drop', {
    dataTransfer,
    clientX: canvas.x,
    clientY: canvas.y,
  });
  const count = await page.locator('.react-flow__node').count();
  expect(count).toBeGreaterThanOrEqual(3);
});
```

**选型与学习路径**：测试比例建议 70/20/10（纯函数/组件/E2E 用例数）——纯函数毫秒级跑数千用例，E2E 一条几十秒，把布局敏感的断言尽量下沉成纯函数（如 dagre 布局结果不要在 E2E 里断像素，而是断"布局函数输出的坐标单调递增"）。Playwright 基础（选择器策略、trace 调试）在《学习大纲》30 阶段已展开，指路不重讲。路径：先给 2.1/2.10/2.11 的纯函数补表驱动用例（存量收益最大）→ 调度器 deps 注入改造 + fake fetch → 节点组件直测 → 最后 E2E 两条冒烟（连线 + 拖入）。

**常见坑**：

- **症状**：jsdom 里跑 fitView/布局相关测试全挂，报 NaN 或 0 尺寸。**根因**：jsdom 没有布局引擎，`node.measured`、`getBoundingClientRect` 全是空/0。**修法**：布局断言下沉纯函数（layoutWithDagre 接受显式尺寸入参）；组件测试里需要尺寸的用例显式传 measured prop，别依赖 DOM 测量。
- **症状**：E2E 连线"拖了但没连上"，手动点没问题。**根因**：mouse.up 之前 moves 太少（steps=1 直线跳变，中途没经过 React Flow 的 drop 判定区）或漏了 up。**修法**：`steps: 10+` 的插值移动 + 显式 up；仍不稳时给 handle 加大命中区（`connectionRadius` 调大）。
- **症状**：面板拖入用例里 `event.dataTransfer` 是 null。**根因**：dispatchEvent 的 init 对象里的 DataTransfer 在 Node 侧构造——跨进程传不过去（结构化克隆不支持）。**修法**：`page.evaluateHandle(() => new DataTransfer())` 在页面上下文创建，handle 以引用传入（上面代码的写法）。
- **症状**：组件测试每跑一条就警告 "created a new nodeTypes object"。**根因**：测试文件把包装组件写在测试函数体内。**修法**：与 2.2 同一条规矩——模块级定义，测试文件也不例外。
- **症状**：2.5 的 useStatusSync 测试里 flush 永不执行。**根因**：rAF 在 jsdom 里存在但与 fake timers 不联动。**修法**：用 `vi.useFakeTimers({ toFake: ['requestAnimationFrame', 'setTimeout'] })` 或测试直接调用内部 flush（把 flush 从 hook 里抽出为可独立测试的纯函数是更好的解）。
