### 与内核的复用关系：为什么它被列为 ★★★

本文档开头那条暗线在这里兑现——本章一个新内核都没有造，全书三个内核各就各位：

1. **递归渲染器（《进阶大纲》§1.3）→ QueryGroup**：`node.kind === 'group' ? <QueryGroup/> : <QueryRow/>` 的判别分发，与动态表单 `registry[node.type]` 的注册表分发是同一台发动机的两种进气方式。而且本章把递归从"渲染"扩到了"更新"（§3.2 的 tree-ops 全是递归纯函数）与"转换"（§3.5 的 toJsonLogic 递归下降）——递归内核的复利在本章又复利了一次。
2. **Setter 体系（《进阶大纲》§3）→ 值编辑器**：`valueEditorRegistry` 就是 Setter 注册表的二维化（字段 × 操作符 → 组件），组件本体（单选/多选/日期/远程搜索）与属性面板是同一批；§3.0 画像里"高级筛选"业务的字段元数据表，与动态表单 schema 同源下发，一次定义两处消费。
3. **表达式引擎（《进阶大纲》§1.4）→ 试运行面板**：表达式引擎的"编译协议 → 运行时求值"链路，在试运行面板里落地为"条件树 → json-logic → `jsonLogic.apply`"——换了一种协议，跑的是同一条求值管线，而且这次求值结果直接变成 UI 高亮（§3.7 的 hitMap）。

所以优先级的账很好算：**三个已摊销的内核 + 一个新协议 + 一层转换 = 一个完整的高频业务功能**，新增学习成本只剩"条件树协议"与"协议转换层"两块，而这两块恰恰是可迁移资产——任何"前后端契约设计 + 多方言适配"的场景（报表查询、权限数据范围、CDP 人群圈选）都长这个样子。再叠加毕业项目的组装视角：登录后"告警规则配置页（3： 查询构建器）→ 保存为 json-logic 给后端执行"是整套 SaaS 底座里唯一把"编辑器族"和"平台能力族"缝起来的页面——做完它，前面所有章节的投入在这一个页面上完成合流，这就是 ★★★ 的成色。

#### 补充：内核复用热力表——七个内核的复用度盘点

**是什么**：把本章真正动用过的内核逐个列出，标注"从上一个项目搬过来时动了多少"。热力分三档：●●● 整机复用（代码级直接搬）、●●○ 配置化复用（结构不变、按新场景换注册表/协议）、●○● 思想复用（同一套设计判断，代码重写）。这张表是站在**本序列视角**的盘点；跨文档的全景视角见 `../react-高阶场景全景图/13-与前两份大纲的衔接-内核复用.md` 的复用矩阵 v2.1，两者不重复。

**为什么值得单列一张表**：上文的"三个内核"讲的是**主干复用**（讲清 ★★★ 的定价逻辑），但实际动手时你会触碰七个内核——多出来的四个（树更新、拖拽、受控纪律、错误定位）没有出现在定价账里，因为它们已经内化成"不用想就会做的动作"。内化的资产最怕的是**意识不到它在产息**：热力表的作用是把隐性资产显性化，下一次评估同类需求时，你能报出"复用约七成"这种有依据的数字，而不是凭感觉。

| 内核 | 来源 | 在本序列的落点 | 热力 | 搬运时动了什么 |
|---|---|---|---|---|
| 递归渲染器（判别分发） | 进阶大纲 §1.3 | `QueryGroup` / `QueryRow` 两类分发 | ●●● | N 种注册表分发 → 2 种判别联合分发，是**收缩**不是改造 |
| 递归树更新（不可变变换 + 结构共享） | 进阶大纲 §1.7 性能线的副产物 | `tree-ops.ts` 全部纯函数 | ●●● | 从"路径寻址（setByPath）"换成"按 id 寻址"，其余原样 |
| Setter / 注册表体系 | 进阶大纲 §3 属性面板 | `valueEditorRegistry` | ●●○ | 一维（type → 组件）升二维（字段类型 × 操作符 → 组件） |
| 表达式求值管线 | 进阶大纲 §1.4 | 试运行面板 `jsonLogic.apply` | ●●○ | 自研表达式 → json-logic 方言；AST 缓存思路原样保留 |
| 嵌套拖拽（dnd-kit） | 进阶大纲 §1.6 | 行排序 + 跨组移动 + 防环 | ●●○ | 平面排多了"每组一个 SortableContext + 组防环"两件事 |
| 受控纪律（value/onChange + id key） | 学习大纲阶段 3 | 全部编辑器与行组件 | ●●● | 零改动，纪律级复用 |
| 校验错误定位（id 索引错误表） | 动态表单的 remapIndexed 思路 | `errors: Map<nodeId, ...>` 下发行内 | ●○● | 换了数据形状，"错误跟着节点 id 走"的设计判断不变 |

**读表的方法**：热力不是越高越好——●○● 的"思想复用"恰恰是**学习完成的标志**（你已经不需要抄代码，只需要那个判断）。真正的红旗是一行都不沾的项目：如果你评估一个树形编辑器需求时发现七个内核一个都用不上，先怀疑自己没找到复用点，再怀疑它真的是新场景。

**练习册的用法**：按需挑做，不必顺序全刷——2 和 6 优先（一个练元数据来源、一个练裁剪判断）；3 只在你要做大数据量场景时做。每个练习的"唯一新学"控制在一步，这是刻意设计：**迁移练习的价值在"复用部分零卡顿"，新学太多就变成新项目了**。做完任一练习，回热力表把对应行的热力改写一遍（比如"字段元数据"从 ●●○ 升 ●●●），这张表会从静态盘点变成你的成长记录。
