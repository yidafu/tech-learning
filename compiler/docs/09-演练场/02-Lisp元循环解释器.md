## 为什么从 Lisp 开始

Lisp 诞生于 1958 年，是第二古老的高级语言（仅次于 Fortran），却拥有最年轻的语法——因为它几乎**没有语法**：

```lisp
(+ 1 2 (* 3 4))     ; 这是一段程序
["+", 1, 2, ["*", 3, 4]]   ; 这就是它的 AST（数组表示）
```

**语法即数据（homoiconicity）**：括号前缀表达式既是源码文本又是语法树。别的语言要写 300 行 parser 才能拿到 AST，Lisp 的 parser 是 20 行的 `read`。这就是宏系统、代码即数据哲学的源头，也是我们第一个实现它的原因——**它把"词法+语法"两个阶段压缩成一层**，让你直接站在语义层的门口。

## 读取器：20 行的 lexer + parser 合体

```js
function tokenize(src) {
  const noComments = src.replace(/;[^\n]*/g, '');
  return noComments.match(/\(|\)|'|"(?:[^"\\]|\\.)*"|[^\s()'"]+/g) ?? [];
}

function read() {
  const t = tokens[pos++];
  if (t === '(') {           // 左括号：递归读到右括号，收集成一个数组
    const list = [];
    while (tokens[pos] !== ')') list.push(read());
    pos++;
    return list;
  }
  if (t === "'") return [new LSym('quote'), read()];  // 'x ≡ (quote x)
  return atom(t);            // 数字转 number，其余是符号
}
```

对照主线的第二、三阶段：tokenize 干了 lexer 的活（一行正则），read 干了 parser 的活（递归下降的最小形态——文法只有 `expr → atom | '(' expr* ')'`）。**没有优先级、没有结合性、没有歧义**：前缀表达式里运算符永远在操作数前面，天然无歧义。Pratt 解析要解决的整个问题域在这里根本不存在。

## eval：十条规则走天下

```js
function evaluate(x, env) {
  if (x instanceof LSym) return env.lookup(x);   // 符号：查环境
  if (!Array.isArray(x)) return x;               // 字面量：自求值
  const [head, ...rest] = x;
  if (head instanceof LSym) switch (head.name) {
    case 'quote':  return rest[0];
    case 'if':     return evaluate(rest[0], env) !== false
                     ? evaluate(rest[1], env) : evaluate(rest[2], env);
    case 'define': /* 绑定到 env */ return;
    case 'set!':   /* 沿 env 链找到并改写 */ return;
    case 'lambda': return { params, body, env };  // 闭包：代码 + 定义环境
    case 'begin':  /* 顺序求值取最后一个 */ return;
    case 'let':    /* 脱糖为 lambda 调用 */ return;
  }
  return applyFn(evaluate(head, env), rest.map(a => evaluate(a, env)));  // 应用
}
```

整门语言的核心语义就这一屏。两个观察：

- **special forms 是"不求值第一个参数"的例外**：`(quote x)` 的 x 不求值、`(define n v)` 的 n 不求值、`if` 的分支惰性求值。应用规则（最后那行）假设所有参数先求值——special form 就是不遵守这条假设的形状。宏系统本质上是"用户自定义 special form"。
- **动态类型的代价**：每一步 `evaluate` 都要区分符号/数组/字面量。主线第四阶段的 checker 在编译期做完这些，VM 里一条指令一个动作——同一个决策，提前到编译期就是静态语言，留在运行期就是动态语言。

### 逐 token 推演：read 怎么长出树

以 `(* (+ 1 2) 3)` 为例，跟一遍 tokenize + read 的全程（pos 是游标）：

| 步 | tokens[pos] | read 动作 | 返回/状态 |
|---|---|---|---|
| 1 | `(` | 进入 list 分支，开新数组 `[]` | 递归中 |
| 2 | `*` | atom → 符号 `*` | 收入数组 |
| 3 | `(` | 又见左括号，**再递归**开内层数组 | 递归中（嵌套一层） |
| 4 | `+` | 符号 `+` | 收入内层 |
| 5 | `1` | 数字 1 | 收入内层 |
| 6 | `2` | 数字 2 | 收入内层 |
| 7 | `)` | 内层 read 返回 `["+",1,2]` | 收入外层，游标越过 `)` |
| 8 | `3` | 数字 3 | 收入外层 |
| 9 | `)` | 外层 read 返回 `["*",["+",1,2],3]` | **AST 完成** |

三步读法：递归深度就是括号嵌套深度——**read 的调用栈自动管理了"当前在解析哪一层"**，不用显式的栈数据结构；第 3 步内层返回后直接被当作一个元素收进外层——复合表达式的"自包含性"让 parser 天然增量化；`'x` 的 sugar 展开发生在 read 层而非 eval 层——宏这类"读代码的代码"改造的就是这一层。

### 逐步求值 trace：eval/apply 双循环

把上面的树交给 `evaluate`，环境 env 里有全局定义。跟一遍完整求值：

| 步 | 求值对象 | 命中哪条规则 | 结果/状态 |
|---|---|---|---|
| 1 | `["*",["+",1,2],3]` | 数组 + head 是符号 → 应用规则 | 先求 head `*`，再逐个求 rest |
| 2 | `*` | LSym → env.lookup | 查得内建乘法函数（假设环境已注入） |
| 3 | `["+",1,2]` | 应用规则（递归） | 求值成为子任务 |
| 4 | `+` | lookup | 内建加法函数 |
| 5/6 | `1`、`2` | 非数组字面量 → 自求值 | 1、2 |
| 7 | apply(`+`,[1,2]) | — | **3**（内层返回） |
| 8 | `3`（外层 rest 第二项） | 自求值 | 3 |
| 9 | apply(`*`,[3,3]) | — | **9** ✅ |

读这张表的钥匙是第 1 步与第 7 步：**evaluate 负责"把表达式变成值"，apply 负责"把值（函数）用在一组值上"**——SICP 把这对互递归叫 eval/apply 循环。第 3 步的递归点是树遍历解释器的本质：控制流就是 JS 调用栈本身，**调用栈深度 = 表达式嵌套深度**。深递归的 Lisp 程序会在这里撞 JS 的栈上限——第五阶段字节码 VM 把这个栈从"宿主调用栈"搬进"自己管理的 Value 栈"，深递归就不再受宿主约束，这是"编译到字节码"除了性能之外的第二个理由。

## special forms 全家福：求值规则的例外清单

把演练场实现的 special forms 按求值行为分三类（每一类都是对"先求值所有参数"这条应用规则的某种偏离）：

| Special form | 哪些参数不求值/晚求值 | 为什么必须 special |
|---|---|---|
| `quote` | 全部不求值 | 返回的是**代码本身**不是值 |
| `if` | 只求值条件 + 选中的一支 | 惰性是 if 的语义本体 |
| `define` / `set!` | 第一个参数（名字）不求值 | 绑定的是符号不是符号的值 |
| `lambda` | 体整个不求值 | 打包成闭包，留到调用时 |
| `let` | 脱糖后等价 lambda | 绑定结构是语法不是函数调用 |
| `begin` | 无偏离（顺序全求值） | 只是**求值时机**的顺序保证，严格说可以做成函数 |

一个判别式帮你理解边界：**"能写成普通函数的都不是 special form"**。`begin` 恰好是可写成函数的那类（参数按序求值、取最后——JS 里 `(a, b)` 逗号表达式同理）；而 `if` 做成函数会把两条分支都求值，`quote` 做成函数拿到的是 x 的值而不是 x 本身。宏系统（用户自定义"读代码的代码"）之所以可能，正因为 special forms 是一组**有限、可枚举的求值例外**——用户宏被展开成这些例外上的普通代码。

## 环境链与闭包

```js
class Env {
  constructor(outer) { this.map = new Map(); this.outer = outer; }
  lookup(sym) {
    for (let e = this; e; e = e.outer)
      if (e.map.has(sym.name)) return e.map.get(sym.name);
    throw new LispError(`未定义的变量：${sym.name}`);
  }
}
```

闭包计数器示例的机制：`make-counter` 的 `let ((n 0))` 创建子环境 E1，返回的 lambda 捕获 E1。两次调用 `make-counter` 生成两个独立的 E1——所以两个计数器互不影响。这与第五阶段 upvalue 拆盒解决的是**同一个问题**（变量逃出作用域后如何存活），方案却是"整环境保留" vs "只把被捕获的变量搬进盒子"——前者省事，后者省内存。

## quote 与 eval：一对互逆算子

special form 清单里 `quote` 与全局函数 `eval` 值得放在一起看——它们是一对**互逆**：

```lisp
(quote (+ 1 2))   ; → [+ 1 2]（不求值，拿到代码本身）
(eval  (quote (+ 1 2)) user-env)   ; → 3（把代码当程序再跑一遍）
```

`quote` 把"程序"折叠成"数据"，`eval` 把"数据"展开成"程序"——往返一圈回到原点。折叠之后，普通列表操作就能改造代码：`(list '+ 1 2)` 用纯数据操作拼出一段程序，交给 eval 就能跑。**运行期代码生成**的最小演示就是这个三步：折叠 → 变换 → 展开。

三个工程化身（从近到远）：

1. **模板引擎与ORM 的 query builder**：拼接出"代码/查询文本"再交给执行器——折叠/变换/展开三步的粗糙版；
2. **Babel/codemod**：AST 进 → 变换 → AST 出，折叠展开发生在编译期而不是运行期——更安全（类型可查）也更贵（要有完整 parser）；
3. **Forth/汇编的立即词与自修改代码**：数据与指令同存储、按需执行——Lisp 的 homoiconicity 是同一思想在表达式层的版本。

也要记下这条路的**代价**：运行期 eval 意味着运行期必须有完整的求值器（树遍历/字节码/JIT 至少一个）驻留内存，且 eval 的代码字符串绕过一切静态检查——主线第四阶段 checker 对它无能为力。工业语言的处理分两派：Lisp/Scheme 保留 eval 但劝退热路径使用；JS 的 CSP 限制 eval、TS 干脆让 `eval` 里的东西类型全变 any。**"代码即数据"的表达力红利，对应的是"代码脱离静态分析"的安全税**——这是 homoiconicity 的完整账单。

## 元循环：用 Lisp 写 Lisp 的求值器

Lisp 的著名魔术——eval 本身可以用 Lisp 定义（SICP §4.1）。在此之前先补一块地基：**apply 遇到的两种"函数值"**。演练场里查环境可能查到两类可调用物：

| | 内建函数（builtin） | lambda 闭包 |
|---|---|---|
| 物理形态 | JS 原生函数 | `{ params, body, env }` 三元组 |
| apply 动作 | 直接 `fn(args)` 借宿主能力 | 新建 `Env(closure.env)` 绑参 → 逐个 `evaluate(body)` |
| 参数个数 | 由宿主函数自己容忍 | 绑参时校验，不匹配抛 LispError |
| 例子 | `+`、`*`、`list`、`car` | `make-counter` 返回的计数器 |

这个二分是所有 Lisp 实现的公共地基：**内建 = 逃逸到宿主语言的 FFI 边界，闭包 = 语言自己的语义对象**。对照第五阶段 VM：内建对应 natives 表（04 册"反向调用"一节），闭包对应 FnProto + upvalue——形态不同，职责分工一模一样。也注意绑参那一行 `new Env(closure.env)`：新环境的外层是**闭包的定义环境**而不是调用方环境——这行代码就是"词法作用域"的全部实现，写错成 `new Env(callerEnv)` 整门语言立刻变动态作用域（误区清单会再回到它）。

### let 脱糖手推：`(let ((n 0)) (lambda () (setq n (+ n 1))))`

`let` 的脱糖方向是把"绑定区 + 体"翻译成"lambda 立即调用"：

```lisp
(let   ((n 0))  body)
≡ ((lambda (n) body) 0)     ; 绑定表变形参、体变函数体、初值表变实参
```

跟一遍这个例子的求值（全程 trace）：

| 步 | 动作 | 环境状态 |
|---|---|---|
| 1 | evaluate 整个 let（脱糖后的 lambda 调用） | 全局 env |
| 2 | 求 `(lambda (n) …)` → 闭包 C，捕获**全局 env** | — |
| 3 | 实参 `0` 自求值 | — |
| 4 | apply C：新建 E1（外层 = 全局），绑 `n→0` | E1{n:0} → 全局 |
| 5 | evaluate 体 → `(lambda () …)` 闭包 C2，**捕获 E1** | — |
| 6 | let 返回 C2；E1 不再被栈引用，但 C2.env 仍指着它 | C2 ≔ {body, E1} |

第 6 步就是闭包捕获的机制现场：**E1 的存活不靠栈帧而靠 C2 的引用**——GC 视角它是"被闭包持有的可达对象"（第六阶段根集合外的第二类保活者）。两次 `make-counter` 走两遍第 4 步，生成两个独立 E1，这就是"两个计数器互不影响"的机制出处。

Lisp 的著名魔术——eval 本身可以用 Lisp 定义（SICP §4.1）：

```lisp
(define (eval exp env)
  (cond ((symbol? exp) (lookup exp env))
        ((pair? exp)
         (if (special-form? (car exp))
             (eval-special (car exp) (cdr exp) env)
             (apply (eval (car exp) env)
                    (eval-args (cdr exp) env))))
        (else exp)))   ; 字面量
```

我们用 JS 写的 `evaluate` 是它的直译。**"语言实现者与语言用户用同一种语言"**不是趣味魔术：Babel 插件用 JS 处理 JS AST、`eval`、IDE 的语言服务，全是元循环思想的工程化身。第八阶段写 Babel 插件时你会再次站在这里。

## 性能画像与错误处理：两块照出主线价值的镜子

### 热点画像：钱都花在哪

给树遍历解释器做一次定性热点画像（不用 profiler 也能推出来）：

| 热点 | 每次求值的成本 | 字节码 VM 的对应解法 |
|---|---|---|
| `evaluate` 头部的三连判型 | 每节点 2~3 次 instanceof/Array.isArray | 编译期判型完毕，指令分派直接到动作 |
| `env.lookup` 环境链遍历 | O(链深)，链深随嵌套增长 | 编译期解析成槽位，`GET_LOCAL i` 固定偏移 |
| `rest.map(a => evaluate(a, …))` | 每次应用分配一个中间数组 | 参数按序压栈，零中间分配 |
| 闭包对象 `{params, body, env}` | 每次创建 lambda 分配 | FnProto 与闭包分离：代码共享，闭包只装 upvalue |

四行合起来的结论：**树遍历的成本结构是"每次执行重付一遍编译期本可预付的钱"**。字节码 VM 的本质是一台"把判断换成查表、把查找换成偏移"的机器——第五阶段逐条指令对照时，每一处都能回指这张表的某一行。也注意最后一行的 FnProto/闭包分离：这就是 Lisp 册"整环境保留"在真实引擎里的瘦身版，主线第五阶段的 upvalue 拆盒是它的完成形态。

### 错误处理：抛异常 vs 收集诊断

演练场 Lisp 遇到 `(foo 1` 未闭合括号、未定义符号、参数个数不匹配，处理方式都是**抛一个 LispError 即停**——第一个错误终止一切。主线 mini 语言的 parse/check 阶段却是**收集诊断、一次报多个**（第三阶段错误恢复册）。这条差异值得展开，因为它是两类工具的架构分野：

| | 演练场 Lisp（即停） | 主线 mini（恢复后继续） |
|---|---|---|
| 适合场景 | REPL 交互、教学演示 | 批量编译、IDE 后台检查 |
| 用户代价 | 一错一跑，改一轮跑一轮 | 一轮看全部错误，批量修复 |
| 实现代价 | 几乎为零 | panic mode 同步点、毒化类型传播 |
| IDE 可行性 | 不可行（无部分结果） | 可行（诊断列表实时更新） |

演化的方向也是确定的：**任何"工具化"的语言实现最终都要走恢复式**——tsc 一次报几十个错、rustc 的 suggestion 批量给出，背后都是第三阶段那套"同步点 + 毒化值"机制。演练场保持即停不是偷懒：二十行的求值器要同时演示恢复，注意力就散了——**教学品与工程品的分界常常不在正确性，而在错误路径的投入**。

## 环境图手推：三次求值画出整张链

环境链是本册最容易"看着懂、画不出"的部分。用一段程序把图亲手画一遍：

```lisp
(define (make-adder n)
  (lambda (x) (+ x n)))
(define add5  (make-adder 5))
(define add10 (make-adder 10))
(add5 1)   ; → 6
(add10 1)  ; → 11
```

逐步建图（E0=全局，每次 apply 新建一层）：

| 事件 | 新环境 | 外层 | 新绑定 | 谁引用它 |
|---|---|---|---|---|
| evaluate `(define (make-adder …) …)` | —（define 绑进当前层） | — | E0: make-adder→闭包C1(捕获E0) | E0.map |
| apply C1 实参 5 | **E1** | E0 | E1: n→5 | 返回的闭包C2.env |
| define add5 | — | — | E0: add5→C2(捕获E1) | E0.map |
| apply C1 实参 10 | **E2** | E0 | E2: n→10 | 返回的闭包C3.env |
| define add10 | — | — | E0: add10→C3(捕获E2) | E0.map |
| evaluate `(add5 1)` | **E3** | C2.env=E1 | E3: x→1 | 求值后即弃 |
| evaluate `(+ x n)` in E3 | — | 沿 E3→E1→E0 查 | x=1(E3)、n=5(E1)、+=(E0) | — |

```text
E0 {make-adder, add5, add2, …, +}      ← 全局
 ↑            ↑
E1 {n:5}     E2 {n:10}                 ← 两个独立闭包环境
 ↑            ↑
C2 (add5)    C3 (add10)                ← 闭包对象持有 env
E3 {x:1} → E1 → E0                     ← 调用帧环境（临时）
```

三步读法：**E1 与 E2 同形不同体**——同一个 lambda 每次调用都造新环境，"两个计数器互不影响"的一般化就是它；**E3 是临时的**（调用帧），返回后无引用即成垃圾（GC 视角第六阶段的可达性分析在这里生效）；**查找路径 E3→E1→E0 长度=3** 是本例的上限——嵌套 lambda 每深一层链长一格，lookup 成本随之线性涨（性能画像表第二行"编译期定槽位"要解决的正是这个）。

把这张图与第五阶段 VM 的栈+upvalue 布局对照着画第二遍：E3 变成 VM 调用帧（数组），E1 里被捕获的 n 变成堆上的 upvalue 盒子，闭包对象从 `{params, body, env}` 缩成 `{FnProto, upvalues[]}`——**同一语义，两种物理**，这是"解释器 → 编译到字节码"改造里语义保持的最难一环。

## 与 mini 语言主线对照

| | 演练场 Lisp | 主线 mini |
|---|---|---|
| 词法+语法 | 一层 read（20 行） | lexer + Pratt parser（两阶段） |
| 类型检查 | 无（运行时报错） | resolve + check 双遍（编译期） |
| 执行方式 | 树遍历解释（evaluate 递归） | 编译到字节码 + 栈式 VM |
| 变量访问 | 名字查环境链（O(链深)） | 编译期定槽位，`GET_LOCAL i` O(1) |
| 错误处理 | 抛异常即停 | 诊断收集 + 错误恢复，一次报多个 |

树遍历解释器（tree-walking interpreter）是每个真实引擎的起点：Ruby（YARV 之前）、早期 PHP、Babel 的模板求值都是它。它慢在哪里？**每个节点每次执行都要重新判型、重新查环境**——这正是字节码存在的理由，也是第七阶段优化的对象。

## 动手路线：三步把"读过"变成"写过"

按递进顺序动手（每步都有明确的验收），比通读十遍更接近"理解"：

| 步 | 动作 | 验收标准 |
|---|---|---|
| 1 | 在演练场页面求值自测 1~4 的表达式 | 每题先写预期再对结果，错的说出哪张表对应的行 |
| 2 | 加 `(and a b)` / `(or a b)` special form（自测 5） | `(and false (error "boom"))` 不抛错 |
| 3 | 加 `(cond (p e) …)` special form（自测 9） | 多分支各只求值被选中的一支 |
| 4 | 加 `(map f lst)` **内建**并解释它为什么不能是宏 | 对 `(map (lambda (x) (* x x)) '(1 2 3))` 得 `(1 4 9)` |
| 5 | 给求值器加调用深度计数，构造自测 8 的无限递归 | 观察深度上限与 JS 栈溢出报错的先后 |

第 4 步藏着本册最深的一课：`map` 看似只是工具函数，但它**接收代码（lambda）作为参数、在循环里多次调用它**——高阶函数是"把 special form 的求值控制权交还用户"的第一步。写完回头看：special forms 解决"我不想立即求值"，高阶函数解决"我想在恰当时机反复求值"，宏再进一步"我想改写求值前的代码"——三层递进是 Lisp 语义扩展的完整阶梯，也是主线各阶段"内建 vs 用户可编程"边界的预演。

- **"Lisp 没有 AST，源码就是 AST"**：准确说法是**读层产物即 AST**（数组/符号对象）。"源码文本 = AST"省掉的是 parser 的歧义处理，不是表示本身——你依然要区分"代码形态的列表"与"待求值的数据"，quote/eval 的分界就在这里；
- **"动态作用域就是环境链"**：本演练场的 lambda 捕获**定义环境**，是词法作用域。真正做错成动态作用域的写法是"调用时传当前环境"——1960s 早期 Lisp 1.5 之后早已修正，SICP 的元循环求值器明确强调这一点；
- **"special form 是特殊函数"**：函数的求值入口统一走应用规则；special form 在 `evaluate` 的 switch 里**抢在应用规则之前**被识别。把 special form 理解成"编译器内建关键字"更贴切——它们是求值器的保留字；
- **"元循环是 Lisp 玩具特性"**：元循环的真实工程形态是**自托管（self-hosting）**——Rust 编译器用 Rust 写、Go 1.5 自举（第一册 T 形图）。能用自己语言写自己的求值器，等于语言的表达力通过了最苛刻的验收；
- **"树遍历慢是 JS 写法问题"**：换成 C 写树遍历一样慢——慢在"每个节点每次执行重新判型/查环境"的结构性成本，不是实现语言的锅。这就是为什么所有热路径解释器最终都走向字节码（CPython 3.13 也在加实验 JIT）。
