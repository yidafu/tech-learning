# 第八阶段导览：现代编译器与前端工程实战

## 阶段目标

1. 独立写出 Babel 插件：visitor + path 抽象 + 作用域查询，处理"匹配 → 变换 → 回写"全流程。
2. 自研一个 mini-lint：规则引擎（遍历 + 匹配 + 诊断 + autofix），对照 ESLint 架构说清差距。
3. 画出 tsc 的核心阶段（Program / Checker / Transformer / Emitter），解释增量编译与 isolatedModules 的约束根源。
4. 总结 esbuild / SWC 的性能手段（原生语言、并行、单遍、低内存 AST），并给出工具链选型决策树。
5. 完成毕业项目三选一。

## 实战路线一：Babel 深度（必修）

- **架构**：@babel/parser（acorn fork）→ AST → @babel/traverse（visitor 遍历）→ @babel/generator（打印）。plugin 是"visitor 的集合 + 一些 state"；preset 是 plugin 的打包。
- **path 抽象**：path 不是节点本身，是"节点 + 位置 + 上下文"（parent、scope、替换/删除自身的操作）。`path.replaceWith(node)`、`path.remove()`、`path.skip()` 是三大常用操作——操作的是路径，框架负责修补树的其余部分。
- **scope/binding 查询**：`path.scope.getBinding('x')` 查到 x 的声明绑定（引用列表、是否常量）——重命名/内联类变换的正确性全靠它，这正是第四阶段符号表在工具层的复刻。
- **编译时代码生成**：babel-plugin-macro 的思路——源码里一个"宏调用"在编译期被展开成任意 AST。对照：这就是 Lisp macro 在 JS 生态的受限版。

## 实战路线二：mini-lint / code-mod（必修）

- **规则引擎三要素**：遍历器（复用你的 parser 产物或直接用 @babel/traverse）、规则（`{ meta, create(ctx) → visitor }`）、诊断与修复（autofix = 返回替换区间 + 文本，与第四阶段诊断设计同构）。
- **对照 ESLint**：Linter 编排（文件 → AST → 规则并发遍历 → 诊断聚合）、RuleTester（规则的单测契约）。mini-lint 只实现核心 20%，但结构完全对应。
- **code-mod 思维**：批量重构 = "模式匹配 + 保语义变换"——比 lint 的 autofix 更激进，需要快照测试兜底（不改变程序可观察行为）。

## 实战路线三：Babel 插件（必修，任选一题）

- 自动埋点：函数入口/出口插入统计调用（处理 async、箭头函数、生成器的边界）。
- import 去重与排序：模块图分析 + 合并同源导入。
- 编译期常量折叠：把第七阶段的 pass 搬到 Babel 插件上（纯函数标注才折叠，处理 `process.env` 这类"编译期已知"值）。
- 工程要点：插件的单测（fixture 转换快照）、与 @babel/parser + traverse + generator 的独立组合（不经过 @babel/core 编译全流程的轻工具）。

## 深读路线四：TypeScript 编译器架构

- **核心阶段**：ts.createProgram（源文件集 + 类型引用图）→ Checker（类型检查与推导，占 tsc 大头）→ Transformer（语法降级，plugin 注入点）→ Emitter（逐文件输出 + sourcemap）。前四阶段的结构在 tsc 里一一对应：Program≈resolve、Checker≈check、Transformer+Emitter≈lowering+生成。
- **增量编译**：.tsbuildinfo 存"上次的类型图状态"，重编译只处理受影响文件——符号表版本化的工程实践。
- **isolatedModules 的约束根源**：单文件转译（esbuild/swc 场景）看不到跨文件类型，所以 `const enum` 内联、类型再导出这类"需要全程序信息"的语法被禁。
- **选做**：ts.createProgram + TypeChecker API 写一个"导出类型 → 文档/markdown"工具——这是理解 Checker API 的最快路径。

## 深读路线五：esbuild / SWC 为什么快

- **四个手段**：原生语言（无 GC 压力的内存布局、无 JIT 预热）；并行（词法/解析按文件并行，Go 协程 / Rust rayon）；单遍设计（解析与转换合并，不反复遍历）；低内存 AST（指针紧排、字符串驻留，cache 友好）。
- **代价**：esbuild 不做类型检查、不支持的语法转换直接报错——"砍掉流水线的一段换取十倍速度"的工程决策。
- **生态一瞥**：Oxc（Rust 工具链套件：parser/linter/transformer 分层复用）、rolldown（Rollup 兼容的打包器）。**选型决策树**：要类型检查 → tsc 在链上；只要转译+打包 → esbuild/SWC；要深度 AST 定制 → Babel。

## 选做路线六：WASM 后端

- **同构性**：wasm 本身就是栈式字节码 VM——你的 mini VM 与它结构同源（栈、控制流、函数表），只是 wasm 由浏览器引擎执行。
- **wat → wasm**：手写 wat 文本（`(module (func (export "add") (param i32 i32) (result i32) local.get 0 local.get 1 i32.add))`），用 wabt 工具链编译为二进制并在浏览器跑通——理解"模块/函数/指令"三层格式。
- **mini → wasm**：把 lowering 目标从自家字节码换成 wasm（表达式子集先行）；体会"IR 设计决定了后端好不好写"。
- **工具链应用**：wasm 版 parser / 压缩器（如 esbuild 的部分对手）为什么在浏览器里快——接近原生的执行 + 无 GC 的线性内存。

> 本路线已展开为 [Wasm 专题](../11-Wasm专题/01-导览.md)（五册：二进制格式/表达式与控制流后端/线性内存与互操作/工具链与性能实测/mini→Wasm 实践）——毕业项目 C 的完整施工图。

## 毕业项目（三选一）

- **A. 完整 mini 语言工具链**：lexer → parser → checker → IR → VM + 优化 + REPL，外加一个浏览器内 playground（在线编辑器 + 运行输出，参考 js-ts 站的 TS Playground 思路）。验收：playground 能跑闭包计数器 + fib(25) + map/filter 三件套。
- **B. 生产级 Babel/SWC 插件**：在真实项目（公司代码或开源项目）落地一个插件，附 fixture 测试集与收益数据（代码量/体积/埋点覆盖率）。
- **C. mini-to-WASM 编译器**：表达式与函数子集编译到 wasm，浏览器 demo 页展示"mini 源码 → wat → 运行结果"三栏对照。
