# 类型推导：从 HM 合一到泛型实现

> [返回：第四阶段导览](01-导览.md)
> 对应大纲第 3 条（进阶）。`let f = (x) => x` 不写一个类型标注，checker 怎么知道 `f: (α) → α`？本册讲 Hindley-Milner 的合一算法（50 行代码量级），以及泛型的两种落地——擦除与单体化。

## 为什么需要推导

上一册的 `synthExpr` 是**自底向上**的：子表达式类型已知才能合成父表达式。但 lambda 参数没有标注时：

```
(x) => x + 1      ← x 的类型是什么？没人说过
```

答案分两步：先给 x 发一个**类型变量** α（占位），继续向上综合；遇到 `x + 1` 时规则要求 number × number，于是 **α 必须是 number**——把这条"方程"解出来，类型就推出来了。推导的本质：**类型检查 = 解类型方程组**。

### 推导不是猜：三个词撑起整个框架

| 词 | 角色 | 对照 |
|---|---|---|
| 类型变量（α、β……） | 未知数——"还没确定的类型"的占位 | 解方程里的 x、y |
| 约束 | 方程——规则表在节点处要求"两边必须相等" | `x + 1` 逼出 α = number |
| 替换表（Subst） | 解集——已确定变量的"变量 → 类型"映射 | 消元法写下的中间结果 |

"推导 = 解方程组"由此有了可操作的形状：**遍历 AST 生成约束 → 合一求解 → 把解代回类型**。它不猜、不学习、不查概率表——每一步要么是等式求解、要么是矛盾报告。这也是 HM 系统能"解释为什么"的原因：**解是构造出来的，不是搜出来的**。

```mermaid
flowchart LR
    A["AST 遍历"] --> B["规则表在节点处产生约束"]
    B --> C["unify：查表 / 绑定 / 矛盾报告"]
    C --> D["替换表 Subst"]
    D --> E["apply 代回 → 最终类型"]
```

### 推导的入口地图：什么位置会"发变量"

不是所有节点都参与推导。mini / TS 里真正"发变量"的位置就四类：

| 位置 | 发生什么 | 本册哪一节 |
|---|---|---|
| 无标注的 lambda 参数 | 发新变量占位，等约束上门 | "为什么需要推导"开头 |
| 函数调用 | 实参类型与形参（可能含变量）合一 | unify 逐步演算 |
| let / const 绑定 | 右值类型先推，再过宽化规则 | tsc 对照：宽化 |
| return / 函数返回 | 收集各 return 的类型，合一为返回类型 | 05 册的返回值推导 |

其余节点（字面量、二元运算）都只是**约束的生产者**——规则表在节点处写出方程，真正"解题"的时机集中在上面四处。入口少的系统好调试：约束溯源只需盯住四个位置。

## 合一（unification）：解方程的算法

**合一**：给两个类型（可含类型变量），求一个**替换（substitution）**使两者相等，或报告矛盾。

```ts
type Subst = Map<string, Type>;              // 类型变量名 → 类型

function unify(a: Type, b: Type, s: Subst): boolean {
  a = apply(s, a); b = apply(s, b);          // 先各自代入已知解
  if (a.kind === 'typeVar')
    return a.name === (b as any).name ? true          // 同一变量：恒等
         : (s.set(a.name, b), true);                  // 否则绑定（occur check 见下）
  if (b.kind === 'typeVar') return unify(b, a, s);
  if (a.kind !== b.kind) return false;                // number vs string：矛盾
  if (a.kind === 'fn' /* && b.kind === 'fn' */)
    return a.params.length === b.params.length
        && a.params.every((p, i) => unify(p, (b as FnType).params[i], s))
        && unify(a.ret, (b as FnType).ret, s);
  return true;                                        // 同名基础类型
}
```

**occur check**：绑定 `α → list(α)` 前检查 α 是否出现在右部——出现即无限类型，拒绝（否则 `apply` 无限递归）。mini 单类型参数场景几乎触发不了，但**没有 occur check 的合一器是一颗定时炸弹**（早期的一些 ML 实现因此栈溢出）。

**apply**：把替换沿类型树递归代入（带着已知解继续解），与 unify 交替进行直到不动点。

### unify 逐步演算：两个具体输入

光看代码不够，给两个真实输入把 `unify` 跑一遍。

**演算一（成功）**：`id: (α → α)` 的调用 `id(1)`。调用规则要把"函数类型"与"实参构造的期望函数类型"合一：`unify(α → α, number → δ)`（δ 是新发的结果变量）：

| 步 | 动作 | 替换表 s |
|---|---|---|
| 1 | `apply(s)`：两边尚无约束，原样 | {} |
| 2 | 两侧都是 fn：长度相等 → 逐参数 `unify(α, number)` | α → number |
| 3 | 返回值 `unify(α, δ)`：**先 apply**——左 α 代入已知解变 `unify(number, δ)` | α → number |
| 4 | 右侧 δ 是变量 → 绑定 δ → number | {α → number, δ → number} |
| 5 | 返回 true；调用表达式类型 = `apply(s, δ)` = **number** | — |

第 3 步是 `apply` 与 `unify` 交替的全部意义：**不先代入就会写出"α = δ"这种绕开已知解的条目**——替换表将自相矛盾（α 同时等于 number 和一个未解变量）。合一的正确性一半在 unify 本身，一半在"每次比较前先 apply"。

**演算二（失败）**：`fn f(x) { return x + 1; }` 之后调用 `f("s")`：

| 步 | 动作 | 替换表 s |
|---|---|---|
| 1 | 发变量 x: α；体 `x + 1` 触发数值加法行：`unify(α, number)` | α → number |
| 2 | 函数体定型：f 的类型即 `(number → number)` | — |
| 3 | 调用 `f("s")`：实参侧 `unify(number, string)` | — |
| 4 | `a.kind !== b.kind` → **false** | 报 E0403：期待 number，实给 string |

失败的演算同样"有始有终"：矛盾点（string 对 number）能精确报出。**替换表走过的每一步都是诊断素材**——05 册"类型从这里推导"的错误链，消费的就是这条轨迹。

### occur check 的受害者：不动点为什么推不出来

看 `fn f(x) { return f(x); }`（自引用）：

| 步 | 动作 | 结果 |
|---|---|---|
| 1 | 发变量：f: α，x: β；体 `f(x)` 是调用 | 约束开始积累 |
| 2 | 调用规则：`unify(α, (β → γ))`，γ 新发 | α 是"f 自己的类型" |
| 3 | **occur check**：绑定 α → (β → γ) 前检查 α 是否出现在右部——α 正是右部的头 | **出现 → 拒绝，报"类型不可推导"** |

第 3 步不是实现技巧而是语义结论：若放行，替换表里出现 `α = β → γ` 而 γ 还要继续等于 f 的返回类型——`apply` 展开永远到不了底（无限类型）。**简单类型 λ 演算因此表达不出任意不动点**：Y 组合子在这个类型系统里写不出来，要靠递归类型 `μα` 或显式 fix 算子补。[演练场的 λ 演算归约器](../09-演练场/05-Lambda演算归约器.md) 里随便一个自引用项，搬进本册的类型系统都会被 occur check 拦下——无类型世界的自由，是有价签的。

### 工程化补遗：工业实现用什么数据结构做合一

教学版是"Map 替换表 + 每次比较先 apply"；工业实现常见两个升级：**路径压缩**（变量链直接指向最终解，摊还近乎 O(1)，省掉反复沿链 apply）与**并查集风格的合一表**（rustc 的推断引擎用 ena 这个并查集 crate 管理类型变量的等价类）。另一个方向是把合一从"一次性求解"变成"常驻基础设施"：tsc 的 checker 给类型关系做了大量缓存，避免深结构的重复求解。第八册读 tsc 源码时你会认出本册的每一个概念——只是每个都穿上了缓存与增量的外衣。

### 推导一个完整例子

```
fn apply2(f, x) { return f(f(x)); }        // 无标注
```

1. 发变量：`f: β, x: γ`，函数整体 `apply2: (β, γ) → δ`。
2. `f(x)`：调用要求 β 是函数 `(γ') → ε`，实参 γ 与参数 γ' 合一 → β = `(γ) → ε`。
3. `f(f(x))`：外层调用要求 β 再是函数 `(ε) → ζ`，与已知 β 合一：`(γ)→ε = (ε)→ζ` → **γ = ε**、δ = ζ。
4. 结果：`apply2 : ((γ) → γ, γ) → γ`——"给一个 α→α 的函数和一个 α，返回 α"。推导器推出了泛型，代码里没有一个类型标注。

把这四步翻译成**替换表状态**——每一步的方程与解：

| 步 | 触发的 unify 调用 | 替换表 s（累积） |
|---|---|---|
| 2 | `unify(β, (γ → ε))` | β → (γ → ε) |
| 3a | `unify(β, (ε → ζ))`：**先 apply**——β 已解出，代入后变 `unify((γ → ε), (ε → ζ))` | 不变 |
| 3b | 结构递归：`unify(γ, ε)` → 绑定 γ → ε；`unify(ε, ζ)` → 绑定 ζ → ε | γ → ε，ζ → ε |
| 4 | 求整体类型：`apply(s, β)` 解成 (ε → ε)，γ 解成 ε，δ 解成 ζ 再解成 ε——**替换表沿链解开，全体坍缩到一个变量** | 最终重命名即 ((γ) → γ, γ) → γ |

第 3b 步的"ε 同时是参数类型与返回类型"正是"同一个 α"的来源：**一次绑定让 f 的进出两道门共享同一个变量**。unify 的每一步都只是在做两件事：查表、绑新条目——算法的全部神秘感到此拆完。

这就是 Hindley-Milner（HM）的威力：**let 多态**（每个 let 绑定的泛型类型在不同调用点独立实例化）。Haskell/OCaml/Elm 的整个类型系统就是它 + 一层语法。

### 解的一般性：为什么绑定要"最少够用"

演算一里 `unify(α, number)` 绑定 α → number——这是方程**逼出来**的唯一解。反过来设想一个"多事"的合一器：解方程时顺手把还没被约束的 β 预设成 number——类型不错，但**过度承诺**：β 本可以在下一次调用里成为 string，被预设钉死后多态直接死掉。合一文献把这叫**最一般合一（most general unifier）**：解必须"最少够用"，不给方程之外的变量添约束。let 多态能工作，前提正是每一步都保持最一般——泛化收集到的 ∀ 变量才真的是"未被钉死"的。

### 算法 W 与 let 多态：一次泛型调用的手推

把"let 多态"展开成可推演的两步：**泛化（generalize）**与**实例化（instantiate）**。手推自测第 1 题的程序：

```ebnf
let id = fn(x) { return x; };   # 推出 α → α
let a = id(1);
let b = id("s");
```

| 步 | 动作 | 状态 |
|---|---|---|
| 1 | 推 `fn(x) { return x; }`：x: α，体返回 α → `id: α → α` | 单态视角到此为止 |
| 2 | **泛化**：α 没有被任何外部约束钉死 → 升格为类型方案 `∀α. α → α` | id 的 α 从此"冻结" |
| 3 | `id(1)`：**实例化**——发**新**变量 β，得 `β → β`；与调用合一 → β = number；`a: number` | β 用完即弃 |
| 4 | `id("s")`：再实例化——**再发新变量 γ** → γ = string；`b: string` | γ 与 β 互不相干 |
| 5 | 反证：若第 3、4 步共享同一个变量，α 在第 3 步被钉成 number，第 4 步 `unify(number, string)` 爆炸 | **多态的全部价值在"每次调用发新变量"** |

步 2 的判定条件（"没有被外部约束钉死"）就是泛化的门槛：**λ 参数里的变量不能泛化**（它们会被调用点的实参类型污染），let 绑定的可以——"let 多态"名字里的 let 就是指这个位置。call-by-value 语言（OCaml/SML）在这里还要加一道**值限制**（value restriction）：只有"句法值"（lambda、字面量）才允许泛化，防止可变引用与多态私通外泄；Haskell 因惰性求值与纯函数性免了这道闸。mini v0.1 不做这些（fn 参数单态），泛化/实例化约 80 行留给选做任务——**本节表格就是那 80 行的验收演算**。

### 实例化的实现：为什么"发新变量"只是拷贝

实例化的代码与 tysEqual 惊人地像——**又是那趟"遍历类型"**：

```ts
function instantiate(t: Type, fresh: Map<string, Type>): Type {
  switch (t.kind) {
    case 'typeVar': {                                  // 方案里的变量 → 新鲜变量
      if (!fresh.has(t.name)) fresh.set(t.name, mkTypeVar());
      return fresh.get(t.name)!;
    }
    case 'fn': return { kind: 'fn',                    // 结构递归：参数与返回值都走一遍
      params: t.params.map(p => instantiate(p, fresh)),
      ret: instantiate(t.ret, fresh) };
    default: return t;                                 // 基础类型原样返回
  }
}
```

判等（tysEqual）、代入（apply）、实例化（instantiate）——三种遍历共享同一个结构递归骨架，差别只在"遇到类型变量时做什么"：比较、查表替换、发新变量。**类型代数的递归定义决定了整个 checker 的代码形状**，这是上一册"类型相等 = 结构递归相等"在第三处的回声。

## 泛型的两种实现

推导出泛型类型后，运行时怎么处理"还没确定的类型"？

| | 擦除（uniform representation） | 单体化（monomorphization） |
|---|---|---|
| 策略 | 泛型只在编译期，运行时统一表示（指针/盒子） | 每个实例化复制一份特化代码 |
| 运行时开销 | 有（装箱/拆箱、动态分派） | 近零（就是手写特化代码） |
| 编译开销 | 小 | 大（代码膨胀：`List<int> + List<string>` 两份代码） |
| 限制 | 无法 `T instanceof`、反射残缺 | 需要静态已知实例化集；动态加载难 |
| 代表 | **TypeScript**、Java、Go | **Rust**（静态分发）、C++ 模板 |

TS 的 `Array<number>` 编译后就是 `Array`——所以 `x instanceof Array<number>` 不存在、`readAnything<T>(): T` 里 `typeof T` 拿不到任何东西。Rust 相反：`Vec<i32>` 与 `Vec<String>` 是两段不同的机器码。**第八阶段写 Babel 插件处理 TS 代码时，"类型已被擦除"是默认前提**。

mini 的选择：v0.1 **不做 let 多态**（fn 参数必须标注或整体推导为单态）——HM 完整版作为本阶段选做任务（约 80 行：类型变量 + unify + 实例化），它是理解 tsc 推导的最短路径。

### 两个极端之外：具体化与 shape 模板化

擦除与单体化不是全部选项。把各家放一排：

| 实现 | 策略 | 一句话 |
|---|---|---|
| .NET（C#） | **具体化（reification）** | 泛型保留到运行时：`List<int>` 与 `List<string>` 是不同的运行时类型，可反射 |
| Java | 擦除 + 补丁 | 类型变量变 Object，用点插 checkcast，协变重写用桥方法垫平 |
| Go | **shape 模板化 + 字典** | 运行时表示相同的类型共享一份代码，差异经字典参数传入 |
| Kotlin | 擦除（JVM 所限）+ 逃逸口 | 只有 `inline` 函数的 `reified` 参数能在运行时拿到 T |

三条路对应"运行时是否保留类型"的三个答案：不留（擦除）、全留（具体化）、半留（按运行时表示分组）。mini 的泛型只活在 checker 里，进入第五阶段指令流后不再有类型痕迹——**擦除在语言设计阶段就完成了**，VM 因此可以假设"指令层只有形状，没有类型标签"。

### 擦除之后：类型信息在编译产物里去哪了

| 编译产物 | 类型痕迹 |
|---|---|
| TS → JS | 全部抹掉；`.d.ts` 声明文件是唯一幸存者——类型信息的对外快照 |
| Java → class 文件 | 指令流里泛型换成 Object + 强转；Signature 属性保留泛型签名，`getGenericReturnType` 这类反射 API 从那里读 |
| Rust → 机器码 | 单体化后每个实例自带具体类型，运行时反而不需要类型标签 |

一张表读出设计取舍：擦除的世界里类型是**编译期的私产**（要对外服务就另开一份声明文件）；单体化的世界里类型是**编译期的分身术**（一份泛型声明展开成 N 份特化机器码）。表里没有任何一行把类型带进"值"本身——**类型不占运行时内存，除非语言刻意让它占**（.NET 那列）。

## tsc 对照：宽化与收窄

两个 TS 特有的推导概念（读 tsc/写 TS 时的必备词汇）：

**宽化（widening）**：`let x = "hello"` 推出 `x: string` 而非字面量类型 `"hello"`——可变绑定的字面量类型会被"宽化"（`const x = "hello"` 保持 `"hello"`）。规则表：let → 宽化、const → 保留、有显式标注 → 标注。mini 的 `let x = 1` 同理推 number（迷你宽化）。

### 宽化的手推：`let x = "hello"` 的完整旅程

把宽化做成可推演的步骤——`let x = "hello"` 从字面量到绑定的类型旅程：

| 步 | 阶段 | 类型 |
|---|---|---|
| 1 | synthExpr(StringLiteral) | `"hello"`（字面量类型） |
| 2 | 绑定检查：x 是 `let` → 查宽化规则表 | let → 宽化 |
| 3 | 宽化：`"hello"` → `string` | string |
| 4 | 写入符号表：x: string | 后续引用全部拿到 string |

三组对照走同一张表：`const x = "hello"` 在步 2 查表得 const → 保留，x: `"hello"`；`let x: "hello" = "hello"` 步 2 有显式标注 → 标注生效。**字面量类型像"票据"：刚推出来时最精确，落进绑定前按规则兑换**——宽化规则表只有三行，却解释了 TS 里 const 推断比 let"更聪明"的全部现象。mini 的迷你宽化是这张表的单行版（let → number/string 基础类型）。

**收窄（narrowing）**：`unknown`/联合类型沿控制流变窄：

```ts
function f(x: string | number) {
  if (typeof x === 'string') {
    x.length          // 此块内 x: string——被 if 条件"收窄"
  }
  x.length            // 报错：string | number
}
```

实现视角：checker 在遍历 IfStmt 时维护 `(Symbol → Type)` 的**分支内覆写表**——then 分支应用条件蕴含的类型关系、离开分支丢弃。这已经是**控制流敏感的类型分析**，与第七阶段的数据流分析（沿 CFG 传播事实集合）同源：**narrowing = 在类型格上跑数据流**。tsc 的 CFA narrowing、Rust 的 match exhaustiveness 检查都在这个框架里。

### 收窄谓词全家福与覆写表手推

"覆写表"展开成可推演的机器需要两件套：**谓词提取**（条件表达式里榨出类型情报）与**进出分支的表维护**。TS checker 能识别的谓词形状：

| 条件 | then 分支内 x | else 分支内 x |
|---|---|---|
| `typeof x === 'string'` | string | 排除 string 的剩余类型 |
| `x instanceof Date` | Date | 剩余类型 |
| `x === 'a'`（字面量比较） | 字面量 'a' | 剩余类型 |
| `'id' in x` | 带 id 字段的形状 | 不带的形状 |
| `x.kind === 'circle'`（判别字段） | 对应 union 成员 | 其余成员 |

mini 的规则表里没有这一列的对应物——`if` 条件必须 bool（05 册 checkStmt 的 requireBool），**谓词提取器整个不存在**。这是"条件必须布尔"换来的第二笔简化红利（第一笔是上一册的规则表一行化）。

覆写表手推（正文那个函数，逐步）：

```ts
function f(x: string | number) {
  if (typeof x === 'string') { x.length; }    // ①
  else { x.toFixed; }                          // ② else：排除 string → number
  x.toFixed;                                   // ③ 全部离开：弹回 union → 报错
}
```

| 时点 | 覆写表内容 | 当前 x 类型 |
|---|---|---|
| 函数入口 | （空） | string \| number |
| ① 块内 | x → string | string |
| 离开 ① | （弹回） | string \| number |
| ② 块内 | x → number | number |
| 离开 ② | （空） | string \| number |
| ③ | （空） | string \| number → `toFixed` 不在 string 上，**报错** |

"弹回"这个动作就是数据流分析的**汇合（meet）**——两条出边的事实按分支收拢，[07-第七阶段数据流分析](../07-第七阶段/02-数据流分析.md) 的格与不动点把"弹回"形式化。tsc 的 CFA 收窄与那册的常量传播是同一台机器的两种载荷：**分支里压事实，出口处做汇合**。

### tsc 与 HM 的分野：一个对照实验

收束本册的对照实验——同一个 identity，两边命运不同：

| 写法 | 系统 | 结果 |
|---|---|---|
| `let f = \x -> x` | Haskell（HM） | `f :: a -> a`——α 从使用处统一解出，自动泛化 |
| `const f = (x) => x` | TS | 无上下文时报 implicit any；TS 推不出"x 是什么" |
| `function f<T>(x: T): T { return x; }` | TS | 合法——**T 在声明处确定，调用处实例化** |

TS 的泛型必须显式声明类型参数：约束系统在**声明处**取 T、在调用处解 T；HM 在**使用处**一路解 α。原因不在能力高下：TS 的类型可能深不见底（几百字段的结构、重载、字面量宽化、any），让使用处完全决定参数类型会让错误报告与性能双双失控。**mini 选 HM 是教学选择，tsc 选约束系统是工程选择**——两者共享本册的全部词汇：变量、约束、合一、实例化。

### 对照实验的实跑收据

上表三行的"结果"列都是 tsc 可复现的行为。tsc 5.9.3、`--strict`，三组实跑：

**第一组：无上下文 λ 与显式泛型**（对照实验表的三行）：

```ts
const f = (x) => x;                    // 无标注参数
const g = <T,>(x: T): T => x;          // 声明处带 T
const r2 = g("s");                     // 调用处实例化
```

```text
c4.ts(1,12): error TS7006: Parameter 'x' implicitly has an 'any' type.
```

整份文件**只有这一条诊断**：第 2、3 行零诊断——T 在声明处签发、在调用处实例化（表格第 3 行的实跑版）。TS7006 的读法比表面更有信息量：**TS 不是"推不出就给 any"，是"推不出就拒绝"**——implicit any 是错误不是类型；写 `(x: any) => x` 才是显式放弃。对照 HM 的处理（演算一）：无标注参数照样推进——发变量 α、等约束上门、约束来了就解。**两边对"未知"的态度在 TS7006 这一行上分岔**：HM 给未知发占位符继续求解，TS 把无约束参数挡在门口逼你表态。

**第二组：宽化的两面**（宽化手推表的运行收据）：

```ts
let x = "hello";
x = "hi";                              // 无诊断
const y = "hello";
if (y === "hi") {}                     // 有诊断
```

```text
c5.ts(5,5): error TS2367: This comparison appears to be unintentional because
the types '"hello"' and '"hi"' have no overlap.
```

同一对字符串字面量，`let` 那一半赋值毫无动静（`x` 已宽化成 `string`，`"hi"` 是合法的 `string`）；`const` 那一半连赋值都不用试，直接比较就触发 TS2367——错误信息把 `y` 的真实类型 **`'"hello"'`**（带引号的字面量类型）印在纸上。宽化手推表步 3"宽化：`"hello"` → `string`"与"const → 保留"两行，这是它们的运行收据。自查一问：`let z: "hello" = "hello"`（显式标注字面量类型）之后 `z === "hi"` 报不报？——答不出回到宽化手推表步 2（标注行优先于 let 宽化）。

**第三组：泛型的 emit 侧写**（"泛型的两种实现"表的擦除列）：

```js
// function g<T>(x: T): T { return x; } 的 emit 输出：
function g(x) {
    return x;
}
```

T 没有留下任何运行时痕迹（tsc 5.9.3 实跑验证）——擦除列的实跑版。mini 里同样的推导结果只活在 checker 内存里，连 emit 都不参加。两边的"擦除"发生在不同深度，但结论一致：**推导出的类型进了检查，进不了运行时**。

## 常见误区

- **"类型变量就是 any"**——α 要求**一个**一致解（所有出现处同时满足），any 是**放弃求解**。演算二里 α 被钉成 number 后再喂 string 会报错；换成 `x: any` 则彻底静默——推导在加强检查，any 在取消检查，方向相反；
- **"unify 是比字符串"**——不是：先 apply（带着已知解）、再结构递归、变量才绑定。跳过 apply 的合一器会推出自相矛盾的替换表（演算一第 3 步的反面）；
- **"泛型 = 模板"**——单体化语言（Rust、C++ 模板）里接近成立；擦除语言（TS/Java）里泛型不产生任何代码，"模板"无从谈起。说"泛型"前先问运行时语义属于哪一列；
- **"收窄是语法糖"**——收窄是**控制流敏感的类型分析**：条件提谓词、覆写表随分支进出、出口做汇合——它的复杂度与第七阶段数据流分析同阶，不是 switch/case 的改写；
- **"TS 能像 Haskell 那样全自动推导"**——对照实验一节：TS 连 `(x) => x` 都要求标注或上下文；全自动只属于 HM 的小而纯的世界；
- **"擦除是 TS 的缺陷"**——擦除与单体化是两种自洽的取舍：TS 的运行时是宿主 JS，"保留类型"没有可落地的运行时对象；Rust 的运行时是自己的机器码，单体化才有意义。脱离"宿主是什么"谈优劣没有意义——表里每一列都绑在各自的运行时模型上。
