# 类型推导：从 HM 合一到泛型实现

> [返回：第四阶段导览](01-导览.md)
> 对应大纲第 3 条（进阶）。`let f = (x) => x` 不写一个类型标注，checker 怎么知道 `f: (α) → α`？本册讲 Hindley-Milner 的合一算法（50 行代码量级），以及泛型的两种落地——擦除与单体化。

## 为什么需要推导

上一册的 `synthExpr` 是**自底向上**的：子表达式类型已知才能合成父表达式。但 lambda 参数没有标注时：

```
(x) => x + 1      ← x 的类型是什么？没人说过
```

答案分两步：先给 x 发一个**类型变量** α（占位），继续向上综合；遇到 `x + 1` 时规则要求 number × number，于是 **α 必须是 number**——把这条"方程"解出来，类型就推出来了。推导的本质：**类型检查 = 解类型方程组**。

## 合一（unification）：解方程的算法

**合一**：给两个类型（可含类型变量），求一个**替换（substitution）**使两者相等，或报告矛盾。

```ts
type Subst = Map<string, Type>;              // 类型变量名 → 类型

function unify(a: Type, b: Type, s: Subst): boolean {
  a = apply(s, a); b = apply(s, b);          // 先各自代入已知解
  if (a.kind === 'typeVar')
    return a.name === (b as any).name ? true          // 同一变量：恒等
         : (s.set(a.name, b), true);                  // 否则绑定（occur check 见下）
  if (b.kind === 'typeVar') return unify(b, a, s);
  if (a.kind !== b.kind) return false;                // number vs string：矛盾
  if (a.kind === 'fn' /* && b.kind === 'fn' */)
    return a.params.length === b.params.length
        && a.params.every((p, i) => unify(p, (b as FnType).params[i], s))
        && unify(a.ret, (b as FnType).ret, s);
  return true;                                        // 同名基础类型
}
```

**occur check**：绑定 `α → list(α)` 前检查 α 是否出现在右部——出现即无限类型，拒绝（否则 `apply` 无限递归）。mini 单类型参数场景几乎触发不了，但**没有 occur check 的合一器是一颗定时炸弹**（早期的一些 ML 实现因此栈溢出）。

**apply**：把替换沿类型树递归代入（带着已知解继续解），与 unify 交替进行直到不动点。

### 推导一个完整例子

```
fn apply2(f, x) { return f(f(x)); }        // 无标注
```

1. 发变量：`f: β, x: γ`，函数整体 `apply2: (β, γ) → δ`。
2. `f(x)`：调用要求 β 是函数 `(γ') → ε`，实参 γ 与参数 γ' 合一 → β = `(γ) → ε`。
3. `f(f(x))`：外层调用要求 β 再是函数 `(ε) → ζ`，与已知 β 合一：`(γ)→ε = (ε)→ζ` → **γ = ε**、δ = ζ。
4. 结果：`apply2 : ((γ) → γ, γ) → γ`——"给一个 α→α 的函数和一个 α，返回 α"。推导器推出了泛型，代码里没有一个类型标注。

这就是 Hindley-Milner（HM）的威力：**let 多态**（每个 let 绑定的泛型类型在不同调用点独立实例化）。Haskell/OCaml/Elm 的整个类型系统就是它 + 一层语法。

## 泛型的两种实现

推导出泛型类型后，运行时怎么处理"还没确定的类型"？

| | 擦除（uniform representation） | 单体化（monomorphization） |
|---|---|---|
| 策略 | 泛型只在编译期，运行时统一表示（指针/盒子） | 每个实例化复制一份特化代码 |
| 运行时开销 | 有（装箱/拆箱、动态分派） | 近零（就是手写特化代码） |
| 编译开销 | 小 | 大（代码膨胀：`List<int> + List<string>` 两份代码） |
| 限制 | 无法 `T instanceof`、反射残缺 | 需要静态已知实例化集；动态加载难 |
| 代表 | **TypeScript**、Java、Go | **Rust**（静态分发）、C++ 模板 |

TS 的 `Array<number>` 编译后就是 `Array`——所以 `x instanceof Array<number>` 不存在、`readAnything<T>(): T` 里 `typeof T` 拿不到任何东西。Rust 相反：`Vec<i32>` 与 `Vec<String>` 是两段不同的机器码。**第八阶段写 Babel 插件处理 TS 代码时，"类型已被擦除"是默认前提**。

mini 的选择：v0.1 **不做 let 多态**（fn 参数必须标注或整体推导为单态）——HM 完整版作为本阶段选做任务（约 80 行：类型变量 + unify + 实例化），它是理解 tsc 推导的最短路径。

## tsc 对照：宽化与收窄

两个 TS 特有的推导概念（读 tsc/写 TS 时的必备词汇）：

**宽化（widening）**：`let x = "hello"` 推出 `x: string` 而非字面量类型 `"hello"`——可变绑定的字面量类型会被"宽化"（`const x = "hello"` 保持 `"hello"`）。规则表：let → 宽化、const → 保留、有显式标注 → 标注。mini 的 `let x = 1` 同理推 number（迷你宽化）。

**收窄（narrowing）**：`unknown`/联合类型沿控制流变窄：

```ts
function f(x: string | number) {
  if (typeof x === 'string') {
    x.length          // 此块内 x: string——被 if 条件"收窄"
  }
  x.length            // 报错：string | number
}
```

实现视角：checker 在遍历 IfStmt 时维护 `(Symbol → Type)` 的**分支内覆写表**——then 分支应用条件蕴含的类型关系、离开分支丢弃。这已经是**控制流敏感的类型分析**，与第七阶段的数据流分析（沿 CFG 传播事实集合）同源：**narrowing = 在类型格上跑数据流**。tsc 的 CFA narrowing、Rust 的 match exhaustiveness 检查都在这个框架里。
