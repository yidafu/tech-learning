# 二进制格式与 WAT：一个模块的逐字节解剖

> [返回：Wasm 专题导览](01-导览.md)
> 第五阶段你设计过 mini 的 Chunk（指令流 + 常量池）。本册看一份**工业标准**是怎么回答同样问题的：一个 `.wasm` 文件里每个字节是什么、为什么这么排。读完能徒手拆开任何 wasm 模块的头几十个字节，并说清它与 mini 字节码在设计上的三处关键分歧。

## 从 WAT 开始：同一个函数的两种写法

wasm 有两种等价表示：二进制（`.wasm`，给机器）与文本（`.wat`，S 表达式，给人）。一个两数相加的模块：

```wat
(module
  (func (export "add") (param i32 i32) (result i32)
    local.get 0        ;; 压第 0 个参数
    local.get 1        ;; 压第 1 个参数
    i32.add))          ;; 弹两个、压和——函数体结束时栈上恰好一个 i32，即返回值
```

与 mini 的 `GET_LOCAL 0 / GET_LOCAL 1 / ADD / RETURN` 逐条对应——**同是栈机，连助记符都像**。不同在于：参数与返回值的**类型写在签名里**，`i32.add` 的类型写在指令名里，没有显式 `RETURN`（栈顶即返回值）。

### WAT 的两套写法：线性与折叠

上文用的是**线性写法**——指令一行一条，栈机本来的样子。WAT 还有**折叠写法**（folded）：把"先压操作数、再压运算"嵌成 S 表达式：

```wat
;; 线性（你的 emit 产出的形态）        ;; 折叠（读别人的 wat 常见）
local.get 0                           (i32.add (local.get 0)
local.get 1                                    (local.get 1))
i32.add
```

两种写法装配出**完全相同的字节**：折叠只是"把栈序嵌进括号"的语法糖——最内层括号先求值，正好对应栈上先压的数。写自己的模块用线性（与 emit 一一对应，脑内栈轨迹不中断），读行业 wat 两套都要认识。

### 栈机手演：add(7, 35) 的每一步

前文全是"静态"的字节与类型，补上"动态"的一半——引擎逐指令推进 `add(7, 35)`：

| 步 | 指令 | 动作 | 操作数栈 |
|---|---|---|---|
| 1 | `local.get 0` | 取 local 0（第 1 个参数）压栈 | `[7]` |
| 2 | `local.get 1` | 取 local 1 压栈 | `[7, 35]` |
| 3 | `i32.add` | 弹两个、压和 | `[42]` |
| 4 | `end` | 函数体收尾 | 返回 42 |

三件事值得说：

1. **参数就是 local**：调用方按签名顺序把实参放进被调函数的 local 0、1——mini 的 `CALL` 压栈实参、被调方按槽取，约定同源；
2. **每条指令的栈效应静态可知**：`local.get` 净 +1、`i32.add` 净 -1——这张表与下一节验证器的类型栈是同一轨迹的两种投影（一个记值、一个记类型）；
3. **`end` 是检查点**：函数收尾时栈上必须恰是签名的返回值，多一个少一个装载期就被拒（本册最后一节展开）。

06 册的 fib 就是这条轨迹的递归展开——步 3 的位置换成 `call`，就是"一次全新的函数体执行"。

## 逐字节解剖：41 个字节

上面的模块编译后恰好 41 字节。结构只有一条规则：**文件头 + 若干段；每段 = 段号（1 字节）+ 内容长度 + 内容**。

```text
00 61 73 6d              魔数 "\0asm"——文件类型标识
01 00 00 00              版本 1（小端 u32）

01 07                    ── 类型段（id=1），内容 7 字节
   01                       1 个函数类型
   60 02 7f 7f 01 7f        0x60=函数类型标记；2 个参数 i32(0x7f) i32；1 个结果 i32

03 02                    ── 函数段（id=3），内容 2 字节
   01 00                    1 个函数，它的签名 = 类型表第 0 项

07 07                    ── 导出段（id=7），内容 7 字节
   01                       1 个导出
   03 61 64 64              名字：长度 3 + "add"
   00 00                    导出种类 0=函数；函数索引 0

0a 09                    ── 代码段（id=10），内容 9 字节
   01                       1 个函数体
   07                       本函数体 7 字节
   00                       0 组局部变量声明
   20 00                    local.get 0
   20 01                    local.get 1
   6a                       i32.add
   0b                       end（函数体结束）
```

三个值得停一下的设计：

1. **签名与代码分家**：函数段只存"第 i 个函数用哪个类型"，代码段才是函数体——引擎读完前三段就知道全部函数签名，可以**边下载边并行编译**各函数体（流式编译）。mini 的 FnProto 把签名、常量、代码捆在一个对象里，对单线程解释器足够，对"下载中就开工"的引擎不够；
2. **处处带长度**：每段、每个函数体前都有字节长度——不认识的段可以整段跳过（向前兼容），函数体可以**惰性编译**（先跳过，调用时再编）；
3. **没有常量池**：`i32.const 42` 的立即数直接内联在指令后。mini 用常量池是因为值是 64 位 double 与字符串，内联太胖；wasm 靠下一节的变长编码把小整数压到 1 字节，池子就不需要了。

### 段布局推演：从零拼出这 41 字节

字节表可以"倒着算"出来——不背字节，只算长度。规则一条：**vector = 个数 + 逐项内容；段 = id（1 字节）+ 内容长度 + 内容**。

| 段 | 内容构成 | 内容长度 | 段头字节 |
|---|---|---|---|
| type（id=1） | `01`（1 个类型）+ `60 02 7f 7f 01 7f`（函数类型 6 字节） | 7 | `01 07` |
| function（id=3） | `01`（1 个函数）+ `00`（用 type 表第 0 项） | 2 | `03 02` |
| export（id=7） | `01`（1 个导出）+ `03 61 64 64`（"add"）+ `00 00`（种类+索引） | 7 | `07 07` |
| code（id=10） | `01`（1 个函数体）+ `07`（体长）+ `00 20 00 20 01 6a 0b` | 9 | `0a 09` |

总数复核：8（文件头）+ (1+1+7) + (1+1+2) + (1+1+7) + (1+1+9) = 8+9+4+9+11 = **41** ✓。

两个推演中容易卡住的点：

- **export 项的字节序**：名字长度在前、名字居中、种类与索引殿后——"长度前置"是全格式的一贯风格（LEB128 续位、段长度、函数体长度做的是同一件事：**让解析器每一步都知道"这块有多大"**）；
- **code 段的双重长度**：先"1 个函数体"（vector 计数），再"这个函数体 7 字节"（函数体自己的封装）——内层长度是前文"惰性编译"的物理基础：引擎可以只读外层列出函数体边界，暂不解析内容。

### 加一个函数要动哪几段

把模块扩成"add 与 sub 两个导出函数"（sub 的签名与 add 完全相同），四段的变化：

| 段 | 变化 | 为什么 |
|---|---|---|
| type | **不变** | sub 签名 `(i32,i32)->i32` 与 add 相同——type 段"去重复用"，直接复用第 0 项 |
| function | `01 00` → `02 00 00` | 函数数 +1；新函数也指向 type 0 |
| export | 追加 `03 's''u''b' 00 01`（6 字节） | 名字、种类（函数）、函数索引 1 |
| code | 追加一个 7 字节函数体 | `00 20 00 20 01 <i32.sub> 0b`，与 add 同形 |

这张表是"签名与代码分家"的直接收益：**签名不重复、函数体互相独立、导出只是命名层追加**。反向做减法（删掉 sub）就是同一张表倒着走。06 册的 `buildModule` 逐函数生成类型、没做查重——多个同签名函数会带重复类型字节，代价与修法在那边讨论。

### 文件头：8 字节里有什么

`00 61 73 6d` 是魔数 `"\0asm"`，`01 00 00 00` 是版本 1（小端 u32）。魔数的职责与一切二进制格式相同：**装错文件在第一个字节就报错**，而不是解析到一半莫名其妙。版本字段让未来的 v2 与老引擎互相当场拒收，不至于按错版本的语义曲解字节。8 字节之后一切皆段——空模块（`(module)`）就只有这 8 字节，本文的 41 = 8 + 33（四个段之和）。

## LEB128：让小数字只占一个字节

模块里的整数（长度、索引、立即数）全部用 **LEB128** 变长编码：每字节低 7 位存数据，最高位是"后面还有"标志。

手算 `624485`（= 二进制 `100110 0001110 1100101`，从低位起 7 位一组）：

| 组（低 → 高） | 7 位数据 | 续位 | 字节 |
|---|---|---|---|
| 第 1 组 | `1100101` | 1（还有） | `0xE5` |
| 第 2 组 | `0001110` | 1（还有） | `0x8E` |
| 第 3 组 | `0100110` | 0（结束） | `0x26` |

得 `E5 8E 26`——4 字节的 u32 压成 3 字节；而上表里的 `07`、`09`、`00` 这些小数字只占 1 字节。**真实程序里小整数占绝大多数**（局部变量索引、短长度），这是 wasm 体积小的第一功臣。有符号版（SLEB128）用于 `i32.const -1` 这类立即数：符号位扩展到最后一组的第 7 位，`-1` 编码为单字节 `7F`。

### 解码方向：把 LEB128 手算倒过来

编码会了，解码是同一张表的逆向。拿 `E5 8E 26` 还原：

| 字节 | 低 7 位 | 拼接（后组在前） |
|---|---|---|
| `E5` | `1100101` | `1100101` |
| `8E` | `0001110` | `0001110 1100101` |
| `26` | `0100110` | `0100110 0001110 1100101` |

得 `0100110 0001110 1100101`₂ = 624485 ✓。解码循环只有两句：**取低 7 位、左移拼上；看最高位决定要不要继续**——与第五阶段解释器的取指循环同构，也是一切变长编码（UTF-8 同款骨架）的通用形状。

### SLEB128 手演：负数的"剩余全 1"收尾

有符号版多一条规则：**最后一组的第 7 位是符号位**，负数要一直编到"剩余位全 1"为止。手算 `-123`：

1. 123 = `1111011`（7 位）；-123 的补数表示是 `…111 0000101`（高位无限补 1）；
2. 从低位取 7 位：`0000101`（值 5），剩余位不全为 1 → 续位 1，首字节 `0x85`；
3. 剩余全 1 → 收尾字节 `0x7F`（低 7 位全 1，符号位即 1）。

得 `85 7F`。反向验算：`5 | (0x7F << 7)` = 5 + 16256 = 16261；按 14 位解读、最高位 1 → 16261 − 16384 = **-123** ✓。与 ULEB128 的关键差异就一句：**结束条件是"剩余全 0"还是"剩余与符号一致"**——同一副变长骨架，两种"什么时候能停"。

### 不是所有立即数都走 LEB128：f64 的 8 字节小端

`i32.const`、长度、索引走 LEB128；`f64.const` 不走——它是 IEEE 754 的 8 字节**原样小端**排在指令后（03 册映射表的 `0x44` + 8 字节）。25.0 的字节是 `44 00 00 00 00 00 00 39 40`：大端直觉写 `0x4039`，落进文件高字节在后。原因直接：LEB128 赚的是"高位冗余"的钱，浮点位模式没有这个性质（尾数近随机），压了反而要付编解码复杂度——**按值域选编码**是二进制格式的通用决策。06 册实测踩过端序坑（`setFloat64` 第四参数），疫苗就是这里。

## 段的家族

| id | 段 | 装什么 | 本专题用到 |
|---|---|---|---|
| 1 | type | 函数签名表（去重复用） | 02、06 |
| 2 | import | 从宿主导入的函数/内存/表/全局 | 04（`print`） |
| 3 | function | 每个函数 → 类型索引 | 02、06 |
| 4 | table | 函数引用表（间接调用） | 04 |
| 5 | memory | 线性内存的初始/最大页数 | 04 |
| 6 | global | 全局变量 | 04（堆顶指针） |
| 7 | export | 导出给宿主的名字 | 02、06 |
| 8 | start | 实例化时自动执行的函数 | — |
| 9 | element | 表的初始内容 | 04 |
| 10 | code | 函数体（局部声明 + 指令） | 全程 |
| 11 | data | 内存的初始内容（字符串常量等） | 04 |
| 0 | custom | 自定义段：`name`（调试名）、sourcemap 地址、DWARF | 05 |

段必须按 id 升序出现（custom 段可插在任意位置）——解析器一遍扫完，无需回头。

### custom 段的两条特权

id=0 的 custom 段是家族里的特例，两条特权各对应一个工程场景：

1. **可插在任意位置**（不受 id 升序约束）：name 段可以紧跟 code 段（调试友好），也可以缀在文件尾（发布工具 strip 只砍尾部）；
2. **内容对引擎不透明**：每段带长度，引擎遇到不认识的 custom 段整段跳过——第三方调试信息、sourcemap、profiler 元数据都走这条路进文件，**核心格式永远不用为此改版**。

代价是 custom 段不参与任何执行语义。05 册"调试版带名、发布版剥名"之所以可行，根子就在"名字住在引擎不需要的段里"。

### 从字节到能调用：实例化的流水线

验证只是检票，一段字节到"能被调用"还要过三站：

```mermaid
flowchart LR
    B["字节流<br>magic + version + 各段"] --> V["validate<br>类型栈逐指令检查"]
    V --> L["link<br>import 段逐项对上宿主对象"]
    L --> I["init<br>memory/data/table/global 填初值"]
    I --> X["exports<br>宿主拿到调用句柄"]
```

- **validate**：本册最后一节——类型栈扫描，任何一步不符整模块拒绝；
- **link**：import 段声明的每个名字都要在宿主提供的对象里找到**且签名吻合**，找不到或对不上实例化当场失败——04 册的 `print`、06 册的 `env.print` 都走这一步，"链接在实例化这一刻完成"说的就是它；
- **init**：data 段把字节写进线性内存（04 册的字符串）、element 段填函数表（04 册的 `call_indirect`）、global 赋初值；若模块带 start 段（id=8），此刻自动执行入口函数——本专题不用它，06 册解释为什么导出 main 代替。

### 工具对照：同一份字节的三种读者

本册的字节规则在三套工具里有三种"读者"，对照着看规则为什么长这样：

| 读者 | 怎么用这些字节 | 它逼着格式做什么 |
|---|---|---|
| `wat2wasm`（wabt，汇编器） | WAT 文本 → 字节，逐段装配 | 格式必须能从线性文本**无歧义**生成——这就是"长度前置 + id 升序" |
| `wasm2wat`/`wasm-objdump`（反汇编） | 字节 → 可读文本/段表 | 每段可独立解析、可整段跳过（custom 特权）——否则调试工具没法做 |
| 引擎（V8/SpiderMonkey 等） | 验证 → 实例化 → 执行 | 每步失败都要**确定性地报错**（验证错误/链接错误/trap 三分类） |

第四种读者是 06 册的你：`buildModule` 手拼字节。它的存在反过来检验了格式的下限——**wasm 是极少数"一个下午手写装配器"还能跑通的现代格式**，m 字节码、JVM class（常量池 + 跳转回填）都比它繁。读 05 册工具链表时带上这张表：wabt 四件套管的是前两种读者，引擎是第三种，06 册是第四种。

## 结构化控制流：没有跳转地址的跳转

这是 wasm 与 mini 字节码**最大的分歧**。mini 的 `JMP off` 可以跳到任意偏移；wasm 根本没有"跳到某地址"的指令，只有三种**带标签的嵌套块**和"跳出第 N 层"：

```wat
block          ;; br 到它 = 跳到块【末尾】（向前跳，相当于 break）
  loop         ;; br 到它 = 跳回块【开头】（向后跳，相当于 continue）
    ...
    br_if 1    ;; 条件成立则跳出往外数第 1 层（即 block）；0 是最内层
    br 0       ;; 无条件跳到最内层 loop 的开头
  end
end
```

为什么宁可麻烦编译器也要这样设计：

- **可验证**：跳转目标只能是外围某个块的头或尾，不可能跳进一条指令的中间、不可能跳到栈深度对不上的位置——验证器一遍线性扫描就能证明安全（下一节）；
- **易编译**：嵌套块直接对应编译器后端需要的结构化控制流图，引擎不用从乱跳里重建循环结构，单遍就能出机器码；
- **紧凑**：标签是相对嵌套深度（通常 0~3），1 字节；不需要像 mini 那样先占位、后回填偏移。

代价由**生成 wasm 的编译器**承担：扁平的跳转必须"装回"嵌套块——03 册的正题。

### 标签算术：br 的深度怎么数

`br N` 的 N 是"从当前位置往外数第 N 个打开的块"；落点由**那一层块的种类**决定：

| 当前位置 | 指令 | 落点 | mini 语义对照 |
|---|---|---|---|
| `block` 内 | `br 0` | 跳到 block 之后（向前） | `JMP L_end`——break |
| `loop` 内 | `br 0` | 跳回 loop 开头（向后） | `JMP L_top`——continue |
| `block { loop { … } }` 内 | `br 1` | 跳到 block 之后 | 从循环体里 break 整个循环 |
| 任意 | `br_if N` | 同 `br N`，栈顶 i32 为真才跳 | 条件版 |

两条铁律：

1. **只能往外跳**：N 往外数，跳进更深的块、跳进兄弟块都不可能——标签集合在指令结构里静态封闭，这是验证器能一遍扫完的前提；
2. **N 只定"哪一层"，块种类才定"头还是尾"**：loop 层落到块头，block/if 层落到块尾。初学最容易把两个变量混成一个。

03 册的 while 模式（`block { loop { … br_if 1 … br 0 … } }`）就是这张表的直接应用：`br_if 1` = 条件不成立时 break，`br 0` = continue。

## 装载期验证：字节码版的类型检查器

模块在实例化前必须通过**验证**。算法就是第四阶段 checker 的镜像：沿指令流模拟一个**类型栈**（只推类型，不算值）：

```text
指令              类型栈（验证器的视角）
local.get 0       [i32]
local.get 1       [i32, i32]
i32.add           [i32]            ← 要求栈顶两个 i32，弹出后压 i32
end               [i32]            ← 与签名 (result i32) 吻合 ✓
```

任何一步对不上——栈上类型不符、分支两臂留下的值不一致、函数末尾栈深不对——整个模块被拒绝，一条指令都不会执行。这带来 wasm 性能模型的根基：**类型错误在装载期全部排除，运行期不需要任何类型检查**；能在运行期出的错只剩少数几种 **trap**（内存越界、整数除零、间接调用签名不符、`unreachable`），每种都是确定性的立即中止，不存在"未定义行为"。

对照 mini：mini 靠 checker 保证字节码良型，但 VM **信任**编译器（emit 顺序写错就是栈失衡崩溃）；wasm 的引擎**不信任**任何模块生产者，所以把 checker 的工作在字节码层重做一遍。06 册你会亲身体会——你的后端写错一处，验证器当场用报错教你做人。

### 三个手造反例：验证器怎么拒绝你

验证器的执法面，用三个反例各踩一脚（第 2、3 条的报错文本 06 册实测过）：

| 反例 | 违反的规则 | 引擎的反应 |
|---|---|---|
| 只压一个 i32 就 `i32.add` | 操作数栈不够弹，类型不匹配 | 模块被拒 |
| 两臂都 return 的函数结尾无可执行路径 | fallthru 栈深不符——`expected 1 elements on the stack for fallthru, found 0`（06 册实测） | 模块被拒；补 `unreachable` 消除 |
| `local.get 2` 但只声明 2 个槽 | 索引越界——`invalid local index`（06 册实测） | 模块被拒 |

三个反例对应三种 emit 失职：栈序写错、控制流收尾漏算、槽位记账漏声明——**都在装载期被拦，一条指令都不会跑**。这正是"引擎不信任模块生产者"：你的 emit 有 bug 不在用户面前崩溃，而在实例化时给你自己报错。还剩一类错误验证器**故意不管**：除零、越界、`call_indirect` 签名不符——依赖运行期的值，装载期判不了，落进 trap 家族（04 册）。

### 值栈与类型栈：同一轨迹的两张脸

把本册开头的手演表与验证器的表并排放：

| 时刻 | 栈里是什么 | 谁在检查 |
|---|---|---|
| 装载期（验证器） | 只有类型：`[i32, i32]` | 逐指令静态推演，不执行 |
| 运行期（执行） | 真值：`[7, 35]` | 引擎直接执行，**不再查类型** |

运行期唯一保留的动态检查就是 trap 家族——装载期不可判定的那一小撮。这个分工就是 wasm 性能模型的全部：**检查要么提前到装载期（一次性付清），要么明确列入 trap 清单（确定性中止）**，没有第三种"边跑边猜"的中间态。对照 JS 引擎：类型检查混在执行里（内联缓存加速、去优化兜底），05 册"wasm 无去优化"的根源在此。

## 镜像对照：mini Chunk 与 wasm 模块

| 设计点 | mini（第五阶段） | wasm | 分歧的原因 |
|---|---|---|---|
| 执行模型 | 栈机 | 栈机 | 同源：编译器好写、指令紧凑 |
| 值类型 | 运行时带标签的 Value | `i32/i64/f32/f64`，全静态 | wasm 面向静态语言，零运行时判型 |
| 常量 | 常量池 + 索引 | 立即数内联（LEB128） | 小整数 1 字节，不需要池 |
| 控制流 | `JMP` 相对偏移 + 回填 | `block/loop/if` + 嵌套深度 | 可验证、易编译 |
| 函数 | FnProto 对象（常量池里） | 类型段 + 函数段 + 代码段 | 流式/并行/惰性编译 |
| 内建 | `NATIVE n` | import 段，实例化时由宿主提供 | 宿主无关（浏览器/Node/独立运行时） |
| 安全 | 信任编译器 | 装载期验证 + 运行期 trap | 执行不可信代码 |
| 调试信息 | 行号表（教学版省略） | custom 段（name/DWARF） | 可整段剥离，不影响执行 |

### 对照表逐行读：每个分歧回答一个问题

- **值类型行回答"为什么 wasm 不需要运行时判型"**：mini 的 Value 是"什么都能是"的运行时标签；wasm 四型是编译期就说清的承诺——05 册实测一稳态贴硬件下限，前提就是机器码里没有判型分支；
- **常量行回答"池子去了哪"**：按需内联了。小整数 1 字节（LEB128）、f64 恒 8 字节——立即数比"池地址 + 间接"便宜时，池子没有存在的理由。mini 的字符串仍需要池式管理（06 册子集直接砍掉）；
- **控制流行回答"patchJump 去哪了"**：嵌套块把"回填偏移"换成"深度计数"——03 册正题；
- **函数行回答"FnProto 拆成了什么"**：type/function/code 三段分立（上文已推演），换来流式/并行/惰性三种编译策略；
- **内建行回答"print 从哪来"**：import 段 + 实例化链接，宿主无关——同一段字节在浏览器、Node、独立运行时都能实例化（只要宿主供得起 import）；
- **调试信息行回答"行号表去哪了"**：custom 段——"可剥离"是它与执行信息的本质区别，05 册"编两次"由此而来。

## 常见误区

- **"WAT 是 wasm 的源语言"**：二进制才是标准本体，WAT 是给人读写的文本投影——`wat2wasm` 是汇编器不是编译器，真正的源语言是 C/Rust/你的 mini；
- **"LEB128 万能省空间"**：只赚"高位全 0/全 1"的钱——索引、长度赚翻了，f64 位模式一点不赚（所以走定长小端）；代价是不能随机寻址，想知道第 N 个元素在哪必须从头解码；
- **"每段带 id，顺序无所谓"**：正相反——id 决定顺序（升序），custom 是唯一例外。顺序固定的收益是解析器一遍扫完；
- **"验证通过 = 运行安全"**：验证只保证字节码良型（栈序、索引、类型）；越界、除零、间接调用签名不符都是**运行期 trap**——依赖值，装载期判不了。两层安全各管一段；
- **"41 字节是 wasm 的最小模块"**：空模块只有 8 字节文件头；41 是"一个可导出 add"的量级感。工业模块的头 8 字节与它完全相同——格式没给小模块任何特殊待遇；
- **"blocktype 0x40 是一种类型"**：它是"无结果"的标记字节，不是类型表的一项——03 册的 `0x7c`（f64）才是把块结果类型写进指令流的形态；
- **"br_if 0 就是 continue"**：在 `loop` 里是，在 `block`/`if` 里是 break——落点看块的种类（"标签算术"一节）。
