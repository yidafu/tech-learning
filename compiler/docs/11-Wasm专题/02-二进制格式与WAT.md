# 二进制格式与 WAT：一个模块的逐字节解剖

> [返回：Wasm 专题导览](01-导览.md)
> 第五阶段你设计过 mini 的 Chunk（指令流 + 常量池）。本册看一份**工业标准**是怎么回答同样问题的：一个 `.wasm` 文件里每个字节是什么、为什么这么排。读完能徒手拆开任何 wasm 模块的头几十个字节，并说清它与 mini 字节码在设计上的三处关键分歧。

## 从 WAT 开始：同一个函数的两种写法

wasm 有两种等价表示：二进制（`.wasm`，给机器）与文本（`.wat`，S 表达式，给人）。一个两数相加的模块：

```wat
(module
  (func (export "add") (param i32 i32) (result i32)
    local.get 0        ;; 压第 0 个参数
    local.get 1        ;; 压第 1 个参数
    i32.add))          ;; 弹两个、压和——函数体结束时栈上恰好一个 i32，即返回值
```

与 mini 的 `GET_LOCAL 0 / GET_LOCAL 1 / ADD / RETURN` 逐条对应——**同是栈机，连助记符都像**。不同在于：参数与返回值的**类型写在签名里**，`i32.add` 的类型写在指令名里，没有显式 `RETURN`（栈顶即返回值）。

## 逐字节解剖：41 个字节

上面的模块编译后恰好 41 字节。结构只有一条规则：**文件头 + 若干段；每段 = 段号（1 字节）+ 内容长度 + 内容**。

```text
00 61 73 6d              魔数 "\0asm"——文件类型标识
01 00 00 00              版本 1（小端 u32）

01 07                    ── 类型段（id=1），内容 7 字节
   01                       1 个函数类型
   60 02 7f 7f 01 7f        0x60=函数类型标记；2 个参数 i32(0x7f) i32；1 个结果 i32

03 02                    ── 函数段（id=3），内容 2 字节
   01 00                    1 个函数，它的签名 = 类型表第 0 项

07 07                    ── 导出段（id=7），内容 7 字节
   01                       1 个导出
   03 61 64 64              名字：长度 3 + "add"
   00 00                    导出种类 0=函数；函数索引 0

0a 09                    ── 代码段（id=10），内容 9 字节
   01                       1 个函数体
   07                       本函数体 7 字节
   00                       0 组局部变量声明
   20 00                    local.get 0
   20 01                    local.get 1
   6a                       i32.add
   0b                       end（函数体结束）
```

三个值得停一下的设计：

1. **签名与代码分家**：函数段只存"第 i 个函数用哪个类型"，代码段才是函数体——引擎读完前三段就知道全部函数签名，可以**边下载边并行编译**各函数体（流式编译）。mini 的 FnProto 把签名、常量、代码捆在一个对象里，对单线程解释器足够，对"下载中就开工"的引擎不够；
2. **处处带长度**：每段、每个函数体前都有字节长度——不认识的段可以整段跳过（向前兼容），函数体可以**惰性编译**（先跳过，调用时再编）；
3. **没有常量池**：`i32.const 42` 的立即数直接内联在指令后。mini 用常量池是因为值是 64 位 double 与字符串，内联太胖；wasm 靠下一节的变长编码把小整数压到 1 字节，池子就不需要了。

## LEB128：让小数字只占一个字节

模块里的整数（长度、索引、立即数）全部用 **LEB128** 变长编码：每字节低 7 位存数据，最高位是"后面还有"标志。

手算 `624485`（= 二进制 `100110 0001110 1100101`，从低位起 7 位一组）：

| 组（低 → 高） | 7 位数据 | 续位 | 字节 |
|---|---|---|---|
| 第 1 组 | `1100101` | 1（还有） | `0xE5` |
| 第 2 组 | `0001110` | 1（还有） | `0x8E` |
| 第 3 组 | `0100110` | 0（结束） | `0x26` |

得 `E5 8E 26`——4 字节的 u32 压成 3 字节；而上表里的 `07`、`09`、`00` 这些小数字只占 1 字节。**真实程序里小整数占绝大多数**（局部变量索引、短长度），这是 wasm 体积小的第一功臣。有符号版（SLEB128）用于 `i32.const -1` 这类立即数：符号位扩展到最后一组的第 7 位，`-1` 编码为单字节 `7F`。

## 段的家族

| id | 段 | 装什么 | 本专题用到 |
|---|---|---|---|
| 1 | type | 函数签名表（去重复用） | 02、06 |
| 2 | import | 从宿主导入的函数/内存/表/全局 | 04（`print`） |
| 3 | function | 每个函数 → 类型索引 | 02、06 |
| 4 | table | 函数引用表（间接调用） | 04 |
| 5 | memory | 线性内存的初始/最大页数 | 04 |
| 6 | global | 全局变量 | 04（堆顶指针） |
| 7 | export | 导出给宿主的名字 | 02、06 |
| 8 | start | 实例化时自动执行的函数 | — |
| 9 | element | 表的初始内容 | 04 |
| 10 | code | 函数体（局部声明 + 指令） | 全程 |
| 11 | data | 内存的初始内容（字符串常量等） | 04 |
| 0 | custom | 自定义段：`name`（调试名）、sourcemap 地址、DWARF | 05 |

段必须按 id 升序出现（custom 段可插在任意位置）——解析器一遍扫完，无需回头。

## 结构化控制流：没有跳转地址的跳转

这是 wasm 与 mini 字节码**最大的分歧**。mini 的 `JMP off` 可以跳到任意偏移；wasm 根本没有"跳到某地址"的指令，只有三种**带标签的嵌套块**和"跳出第 N 层"：

```wat
block          ;; br 到它 = 跳到块【末尾】（向前跳，相当于 break）
  loop         ;; br 到它 = 跳回块【开头】（向后跳，相当于 continue）
    ...
    br_if 1    ;; 条件成立则跳出往外数第 1 层（即 block）；0 是最内层
    br 0       ;; 无条件跳到最内层 loop 的开头
  end
end
```

为什么宁可麻烦编译器也要这样设计：

- **可验证**：跳转目标只能是外围某个块的头或尾，不可能跳进一条指令的中间、不可能跳到栈深度对不上的位置——验证器一遍线性扫描就能证明安全（下一节）；
- **易编译**：嵌套块直接对应编译器后端需要的结构化控制流图，引擎不用从乱跳里重建循环结构，单遍就能出机器码；
- **紧凑**：标签是相对嵌套深度（通常 0~3），1 字节；不需要像 mini 那样先占位、后回填偏移。

代价由**生成 wasm 的编译器**承担：扁平的跳转必须"装回"嵌套块——03 册的正题。

## 装载期验证：字节码版的类型检查器

模块在实例化前必须通过**验证**。算法就是第四阶段 checker 的镜像：沿指令流模拟一个**类型栈**（只推类型，不算值）：

```text
指令              类型栈（验证器的视角）
local.get 0       [i32]
local.get 1       [i32, i32]
i32.add           [i32]            ← 要求栈顶两个 i32，弹出后压 i32
end               [i32]            ← 与签名 (result i32) 吻合 ✓
```

任何一步对不上——栈上类型不符、分支两臂留下的值不一致、函数末尾栈深不对——整个模块被拒绝，一条指令都不会执行。这带来 wasm 性能模型的根基：**类型错误在装载期全部排除，运行期不需要任何类型检查**；能在运行期出的错只剩少数几种 **trap**（内存越界、整数除零、间接调用签名不符、`unreachable`），每种都是确定性的立即中止，不存在"未定义行为"。

对照 mini：mini 靠 checker 保证字节码良型，但 VM **信任**编译器（emit 顺序写错就是栈失衡崩溃）；wasm 的引擎**不信任**任何模块生产者，所以把 checker 的工作在字节码层重做一遍。06 册你会亲身体会——你的后端写错一处，验证器当场用报错教你做人。

## 镜像对照：mini Chunk 与 wasm 模块

| 设计点 | mini（第五阶段） | wasm | 分歧的原因 |
|---|---|---|---|
| 执行模型 | 栈机 | 栈机 | 同源：编译器好写、指令紧凑 |
| 值类型 | 运行时带标签的 Value | `i32/i64/f32/f64`，全静态 | wasm 面向静态语言，零运行时判型 |
| 常量 | 常量池 + 索引 | 立即数内联（LEB128） | 小整数 1 字节，不需要池 |
| 控制流 | `JMP` 相对偏移 + 回填 | `block/loop/if` + 嵌套深度 | 可验证、易编译 |
| 函数 | FnProto 对象（常量池里） | 类型段 + 函数段 + 代码段 | 流式/并行/惰性编译 |
| 内建 | `NATIVE n` | import 段，实例化时由宿主提供 | 宿主无关（浏览器/Node/独立运行时） |
| 安全 | 信任编译器 | 装载期验证 + 运行期 trap | 执行不可信代码 |
| 调试信息 | 行号表（教学版省略） | custom 段（name/DWARF） | 可整段剥离，不影响执行 |

## 自测

2. 把函数改名为 `sum`（导出名 3 → 3 字符不变）哪些字节会变？改成 `plus` 呢——除了名字本身，还有哪一个字节必须跟着改？

5. 验证器的类型栈与第四阶段 checker 的"表达式类型推导"是什么关系？为什么通过验证后引擎可以不做运行时类型检查？
6. wasm 把签名（函数段）与函数体（代码段）拆开，给引擎换来了哪两种编译策略？
