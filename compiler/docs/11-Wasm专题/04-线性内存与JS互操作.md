# 后端二：线性内存与 JS 互操作

> [返回：Wasm 专题导览](01-导览.md)
> 数值在栈与局部变量里就够用了；但数组、字符串、闭包环境这些**堆数据**，wasm 给出的答案不是"另一个 JS 堆"，而是一块**线性内存（linear memory）**——一大块你自己管的字节数组。本册把 mini 的数组搬进去、让 JS 站在门口递东西，顺便算清这块内存的 GC 账。

## 线性内存：一块巨大的数组

```wat
(memory (export "memory") 1)          ;; 1 页 = 64 KiB，可 grow
```

- 内存以**页**为单位（64 KiB），初始页数写在 memory 段，运行时 `memory.grow` 加页；
- 读写只有一族指令：`i32.load` / `i64.store` / `f64.load` …，操作数是**地址**（i32，字节单位）加静态的 `offset`/`align` 修饰——寻址最终是 `base + offset`；
- 没有结构、没有对象头、没有标签——**第 8 个字节到第 16 个字节是什么，完全由你的编译器说了算**。mini 的堆住在 JS 堆里（GC 专题的主场）；wasm 的堆是一块**自留地**，一切布局自己做主。

## 数组搬家：布局与 bump 分配器

mini 的数组是 `Obj` 堆对象；wasm 里我们给 `[len: i32][e0: f64][e1: f64]…` 的连续布局（头部占一个 8 字节槽，元素 8 字节对齐）。分配器选最简单的 **bump**（bump pointer）：全局一个堆顶指针，分配 = 取旧值、指针前移：

```wat
(module
  (memory (export "memory") 1)
  (global $hp (mut i32) (i32.const 8))       ;; 堆顶；0 号槽保留给"空指针"

  (func $alloc (param $n i32) (result i32)   ;; 申请 n 字节，返回旧堆顶
    (local $p i32)
    global.get $hp  local.set $p
    global.get $hp  local.get $n  i32.add  global.set $hp
    global.get $hp  memory.size  i32.const 16  i32.shl  i32.gt_u   ;; 超出当前内存？
    if
      global.get $hp  memory.size  i32.const 16  i32.shl  i32.sub  ;; 缺口按页补齐
      i32.const 65535  i32.add  i32.const 16  i32.shr_u
      memory.grow  i32.const -1  i32.eq                        ;; grow 失败 → trap
      if  unreachable  end
    end
    local.get $p)

  (func $newArray (export "newArray") (param $len i32) (result i32)
    (local $p i32)
    local.get $len  i32.const 1  i32.add  i32.const 3  i32.shl   ;; (len+1)*8 字节
    call $alloc  local.set $p
    local.get $p  local.get $len  i32.store                      ;; 头部写长度
    local.get $p)

  (func $get (export "get") (param $a i32) (param $i i32) (result f64)
    local.get $i  local.get $a  i32.load  i32.ge_u               ;; i >= len ？
    if  unreachable  end                                         ;; 是 → 显式 trap
    local.get $a  local.get $i  i32.const 1  i32.add  i32.const 3  i32.shl  i32.add
    f64.load))                                                   ;; 地址 = a + (i+1)*8
```

`set` 同形：越界检查后 `f64.store`。三个布局决策值得说：

1. **地址公式 `a + (i+1)*8`**：`+1` 跨过长度头，`*8` 是 f64 步长——这条式子就是 mini 的"数组寻址"从运行时对象下沉到**编译期算术**的全程；
2. **长度头是 i32、槽却是 8 字节**：为元素保持 8 字节对齐（未对齐的 f64 访问在部分架构上降速）；
3. **`i32.ge_u`（无符号比较）一石二鸟**：`i = -1` 的无符号值是 4294967295，比任何合法长度都大——**负索引与超大索引走同一个检查**，连符号判断都省了。

## 越界的两层

wasm 的 `load/store` 自带边界检查：地址越界当场 trap。那为什么还要自己插 `unreachable` 检查？**信息量**——引擎的 trap 只有"越界了"，你的检查可以带行号、带变量名、走 mini 的 RuntimeError 回溯格式。这正是第四阶段的路线：**静态层能兜的（类型）静态兜掉，运行层的（边界）给足上下文再兜**。

## JS 一侧：实例化与零拷贝视图

```js
const { instance } = await WebAssembly.instantiate(bytes);   // 异步：下载 + 编译 + 验证
const { memory, newArray, get, set } = instance.exports;

const p = newArray(3);
const view = new Float64Array(memory.buffer, p + 8, 3);      // 直接映射线性内存
view.set([1.5, 2.5, 3.5]);
get(p, 1);        // 2.5 —— wasm 读到的就是你刚写的那块
set(p, 0, 9.5);
view[0];          // 9.5 —— 同一块内存的两个名字：零拷贝，没有序列化
```

**坑（实测行为）**：任何一次 `memory.grow` 都会换一个新的 `ArrayBuffer`，旧视图全体 **detach**——`view.length` 变 0、读写抛错。凡是缓存了视图的地方（渲染循环里的顶点缓冲！），grow 之后必须重建。习惯：把"取视图"封装成函数，别长期持有。

字符串过边界同理：JS 用 `TextEncoder` 编码后写进内存，传**指针 + 长度**一对 i32；回程 `TextDecoder` 解码。mini 的 `NATIVE n`（print/clock）在 wasm 侧的落点是 **import**——模块声明"我要一个 `(f64) -> ()` 的函数"，实例化时由 JS 提供：

```wat
(import "env" "print" (func $print (param f64)))
;; 实例化：WebAssembly.instantiate(bytes, { env: { print: console.log } })
```

导入函数的索引排在模块内函数**前面**（`call 0` 就是 print）——链接在实例化这一刻完成，这是"编译期 call 静态索引"哲学的另一半。

## 函数表与 `call_indirect`：函数值的第一步

mini 的函数是一等公民（`CLOSURE` 压栈、`CALL` 弹出调用）；wasm 的 `call` 只认静态索引。动态分派靠**函数表**：

```wat
(type $unary (func (param f64) (result f64)))
(table 2 funcref)                        ;; 函数引用的数组
(elem (i32.const 0) $double $square)     ;; 槽 0、1 的初始内容

(func (export "apply") (param $f i32) (param $x f64) (result f64)
  local.get $x
  local.get $f                           ;; 参数先压、表索引最后压
  call_indirect (type $unary))           ;; 运行时按槽取函数、核对签名后调用
```

槽越界、槽是空的、签名对不上——三种情况**当场 trap**（C 的函数指针乱调是未定义行为，这里是确定性报错）。mini 闭包的 wasm 路线图由此清晰：**函数值 = 表索引（i32）**；真闭包再补一块"环境记录"放进线性内存，函数值升级为 (表索引, 环境指针) 二元组——upvalue 拆盒从 JS 对象搬进自留地，留作本专题之后的功课。

## 这块内存的 GC 账

线性内存 JS 的 GC **看不见**，bump 指针只进不退。三条出路，按使用模式选：

| 使用模式 | 还法 | 一句话 |
|---|---|---|
| 一次性计算（编译一个文件、跑一轮模拟） | **不还**——用完整个模块/实例丢弃，浏览器回收整个内存 | 模块即 arena |
| 长驻分轮（每请求/每帧一批对象，轮内活、轮间死） | **epoch reset**：每轮结束把堆顶指针拨回起点 | GC 专题 05 册 arena 思想的浏览器版 |
| 对象生死交错 | 自由链表/RC 自己上，或…… | 等 WasmGC（05 册）让 struct/array 变成引擎托管对象 |

顺带一个站群内呼应：webgl 站物理专题的选型里 rapier 用 Rust 编译到 wasm——Rust 的所有权在**编译期**决定释放点，线性内存里没有 GC 也可以安全地"用完即还"，正是第三行的高配版。
