# 后端二：线性内存与 JS 互操作

> [返回：Wasm 专题导览](01-导览.md)
> 数值在栈与局部变量里就够用了；但数组、字符串、闭包环境这些**堆数据**，wasm 给出的答案不是"另一个 JS 堆"，而是一块**线性内存（linear memory）**——一大块你自己管的字节数组。本册把 mini 的数组搬进去、让 JS 站在门口递东西，顺便算清这块内存的 GC 账。

## 线性内存：一块巨大的数组

```wat
(memory (export "memory") 1)          ;; 1 页 = 64 KiB，可 grow
```

- 内存以**页**为单位（64 KiB），初始页数写在 memory 段，运行时 `memory.grow` 加页；
- 读写只有一族指令：`i32.load` / `i64.store` / `f64.load` …，操作数是**地址**（i32，字节单位）加静态的 `offset`/`align` 修饰——寻址最终是 `base + offset`；
- 没有结构、没有对象头、没有标签——**第 8 个字节到第 16 个字节是什么，完全由你的编译器说了算**。mini 的堆住在 JS 堆里（GC 专题的主场）；wasm 的堆是一块**自留地**，一切布局自己做主。

### 地址空间地图：前 8 字节的约定

本册模块的线性内存从字节 0 起长这样：

```text
0            8                                64 KiB（1 页，可 grow）
├── 保留  ├──├──────────── 堆（bump 分配）────────────→
   空指针    hp 从这里起步（global $hp 初始 8）
```

**为什么 0 号要留空**：OS 世界里"地址 0 不可访问"由硬件页表保证（空指针解引用必崩）；wasm 的线性内存没有这层语义——地址 0 是合法地址，从 0 load 会安静地读出数据。于是"空指针"只能靠**分配器约定**：`$alloc` 永不从 0 起发地址，让 `p == 0` 永远指不到任何真数据。mini 侧因此获得一个干净的判空协议：指针值为 0 = 没有对象。**"空指针"不是硬件恩赐，是分配器纪律**——这是本册第一个"把运行时假设显式化"的例子。

### load/store 的完整形状：base + offset

一族读写指令的公共形状是"动态 base + 静态 offset"：

```wat
f64.load offset=8 align=3     ;; 读 base+8 起的 8 字节；align=3 即 2³=8 字节对齐提示
```

- **offset 是编译期常量**：地址算术里"结构头多大"这类固定部分可以折进 offset，动态部分只留 base——本册的地址公式 `a + (i+1)*8` 把全部算术交给指令序列，两种分工都合法；
- **align 是对数形式的提示**：`align=3` 说"我保证 8 字节对齐"——引擎据此选最快路径；访存**允许**不对齐（提示说谎不 trap），只是部分架构上慢。数组布局把头部做成 8 字节槽，正是为了让所有元素访问都天然对齐；
- **地址是 i32**：4 GiB 寻址上限，64 位平台上的 wasm 也如此——大块数据的规划要在这 4 GiB 里做（memory64 提案在放宽它）。

### 页与 grow：memory.size 的 16 次移位

`$alloc` 里那句 `memory.size  i32.const 16  i32.shl` 值得单独解码：

- 内存按**页**计量，`memory.size` 返回**当前页数**；左移 16 位 = 乘 65536 = 换算成字节数（1 页 = 64 KiB = 2¹⁶ 字节）；
- `memory.grow` 的返回值是 grow **之前**的页数；失败（内存不足/超上限）返回 `-1`——`$alloc` 检查 `-1` 后 `unreachable`，把"分配失败"变成确定性 trap；
- 每次 grow 至少加 1 页：`(缺口 + 65535) >> 16` 就是"向上取整页数"——wat 里 `i32.const 65535  i32.add  i32.const 16  i32.shr_u` 那两行。

内存只会变大不会缩小：**grow 不可逆**。这与"GC 账"一节"bump 指针只进不退"是同一种单向性——wasm 把线性内存设计成"只涨的画布"，回收全靠上层策略。

## 数组搬家：布局与 bump 分配器

mini 的数组是 `Obj` 堆对象；wasm 里我们给 `[len: i32][e0: f64][e1: f64]…` 的连续布局（头部占一个 8 字节槽，元素 8 字节对齐）。分配器选最简单的 **bump**（bump pointer）：全局一个堆顶指针，分配 = 取旧值、指针前移：

```wat
(module
  (memory (export "memory") 1)
  (global $hp (mut i32) (i32.const 8))       ;; 堆顶；0 号槽保留给"空指针"

  (func $alloc (param $n i32) (result i32)   ;; 申请 n 字节，返回旧堆顶
    (local $p i32)
    global.get $hp  local.set $p
    global.get $hp  local.get $n  i32.add  global.set $hp
    global.get $hp  memory.size  i32.const 16  i32.shl  i32.gt_u   ;; 超出当前内存？
    if
      global.get $hp  memory.size  i32.const 16  i32.shl  i32.sub  ;; 缺口按页补齐
      i32.const 65535  i32.add  i32.const 16  i32.shr_u
      memory.grow  i32.const -1  i32.eq                        ;; grow 失败 → trap
      if  unreachable  end
    end
    local.get $p)

  (func $newArray (export "newArray") (param $len i32) (result i32)
    (local $p i32)
    local.get $len  i32.const 1  i32.add  i32.const 3  i32.shl   ;; (len+1)*8 字节
    call $alloc  local.set $p
    local.get $p  local.get $len  i32.store                      ;; 头部写长度
    local.get $p)

  (func $get (export "get") (param $a i32) (param $i i32) (result f64)
    local.get $i  local.get $a  i32.load  i32.ge_u               ;; i >= len ？
    if  unreachable  end                                         ;; 是 → 显式 trap
    local.get $a  local.get $i  i32.const 1  i32.add  i32.const 3  i32.shl  i32.add
    f64.load))                                                   ;; 地址 = a + (i+1)*8
```

`set` 同形：越界检查后 `f64.store`。三个布局决策值得说：

1. **地址公式 `a + (i+1)*8`**：`+1` 跨过长度头，`*8` 是 f64 步长——这条式子就是 mini 的"数组寻址"从运行时对象下沉到**编译期算术**的全程；
2. **长度头是 i32、槽却是 8 字节**：为元素保持 8 字节对齐（未对齐的 f64 访问在部分架构上降速）；
3. **`i32.ge_u`（无符号比较）一石二鸟**：`i = -1` 的无符号值是 4294967295，比任何合法长度都大——**负索引与超大索引走同一个检查**，连符号判断都省了。

### $alloc 逐行读：grow 的三步舞

分配函数只有六行 wat，却完整走完"检查 → 补页 → 交付"三步：

| wat 片段 | 在做什么 |
|---|---|
| `global.get $hp  local.set $p` | 记下旧堆顶——这就是要返回的地址 |
| `… i32.add  global.set $hp` | 堆顶前移 n 字节（先斩后奏：申请即占坑） |
| `hp  memory.size<<16  i32.gt_u` | 新堆顶超出当前内存字节数？（无符号比较：hp 永远非负） |
| `hp − 内存字节数` | 超出部分 = 缺口 |
| `+65535 >>16  memory.grow` | 缺口向上取整成页数，交给 grow |
| `−1  i32.eq  if  unreachable` | grow 失败 → 确定性 trap，而不是静默返回坏指针 |

两个细节：**grow 只在"真的不够"时发生**——不 grow 也能继续分配，直到撞线；**trap 优于坏指针**——C 的 malloc 返回 NULL 让调用方自己查，这里直接把错误炸在分配点上，调用方代码里根本不存在"忘了判空"这个 bug 类别。

### 分配手演：连续两次 newArray(3)

把整条链手演一遍（全新实例，`$hp` 初始 8）：

| 步 | 动作 | $hp | 返回/内存 |
|---|---|---|---|
| 1 | `newArray(3)` → `alloc(32)`（(3+1)×8） | 8 → 40 | 返回 `p=8`；头部 `[8..12)` 写 len=3 |
| 2 | `get(8, 0)` | 40 | 地址 `8+(0+1)*8=16`，读 `[16..24)` |
| 3 | `newArray(3)` 再来一次 → `alloc(32)` | 40 → 72 | 返回 `p=40` |
| 4 | `get(40, 2)` | 72 | 地址 `40+(2+1)*8=64`，读 `[64..72)` |

第 1、3 步合看：bump 分配的"O(1)、无空闲列表、无合并"全部兑现，代价记在"GC 账"一节。第 4 步展开：40~72 这 32 字节的结构是 `[len:i32 + 4 字节填料][e0][e1][e2]`——头部占一个 8 字节槽，`i32.store` 只写前 4 字节，后 4 字节是对齐填料。**同一套地址公式**吃下任意 (指针, 下标) 组合，这就是"数组寻址下沉到编译期算术"的完整含义。

### 布局的另一种选法：头部为什么是 8 字节

把头部压到 4 字节（len 本来就是 i32，只占 4）行不行？行，代价看清楚：

| 方案 | 头部 | 元素对齐 | 每 n 元素数组的开销 |
|---|---|---|---|
| 本册（头 8 字节槽） | len + 4 字节填料 | 每个元素都 8 对齐 | 8 字节 |
| 紧凑版（头 4 字节） | len 紧贴 e0 | e0 落在 4 对齐地址 | 4 字节 |

省下的每数组 4 字节，换来的是**所有 f64 元素访问不再天然对齐**——部分架构降速、对齐提示失效。教学模块选"对齐优先"；真实引擎各有更细的账（V8 的定长数组头、Rust Vec 的胖指针都在这个问题上做过不同取舍）。**布局是"每字节成本 × 访存速度"的联立方程，没有免费解**。

## 越界的两层

wasm 的 `load/store` 自带边界检查：地址越界当场 trap。那为什么还要自己插 `unreachable` 检查？**信息量**——引擎的 trap 只有"越界了"，你的检查可以带行号、带变量名、走 mini 的 RuntimeError 回溯格式。这正是第四阶段的路线：**静态层能兜的（类型）静态兜掉，运行层的（边界）给足上下文再兜**。

### 两层检查各挡什么：语义层与沙箱层

"为什么两层都要"展开成分工表：

| | 你的 `i32.ge_u` + `unreachable` | 引擎的边界检查 |
|---|---|---|
| 服务对象 | mini 程序员（语言语义） | 宿主（沙箱安全） |
| 报什么错 | 带行号、变量名，走 mini 的 RuntimeError 格式 | 统一的 trap（"越界了"到此为止） |
| 能否被省略 | 编译器可以偷懒（省指令） | **不可省略**——引擎不信任模块 |
| 挡住的错误 | 负索引、`i >= len` | 任何模块算出的非法地址 |

关键在第 3 行：**引擎的检查不依赖你自觉**。哪怕一个恶意或有 bug 的模块直接 `i32.const 999999  i32.load`，引擎也会在内存边界上拦下——这是"验证 + trap"安全模型的运行期半边（02 册）。你自己的检查买的是**语义信息**：错误以 mini 程序员能读懂的形状出现。两层各挡各的，谁也不替代谁。

### trap 之后：实例还活着

wasm 的 trap 只炸掉**当前这次执行**：调用栈展开，控制流回到宿主（JS 侧表现为一个异常），而实例本身——线性内存内容、全局、函数表——原样保留，下一次调用照常。这与进程级的段错误完全不同：**trap 是函数级的确定性异常，不是实例级的死刑**。工程含义：把"可能越界的计算"放进 try/catch 包着的调用里，实例可以复用——mini 的 REPL/三栏 demo 正需要这个性质（用户输入越界下标，页面不该重载）。

## JS 一侧：实例化与零拷贝视图

```js
const { instance } = await WebAssembly.instantiate(bytes);   // 异步：下载 + 编译 + 验证
const { memory, newArray, get, set } = instance.exports;

const p = newArray(3);
const view = new Float64Array(memory.buffer, p + 8, 3);      // 直接映射线性内存
view.set([1.5, 2.5, 3.5]);
get(p, 1);        // 2.5 —— wasm 读到的就是你刚写的那块
set(p, 0, 9.5);
view[0];          // 9.5 —— 同一块内存的两个名字：零拷贝，没有序列化
```

**坑（实测行为）**：任何一次 `memory.grow` 都会换一个新的 `ArrayBuffer`，旧视图全体 **detach**——`view.length` 变 0、读写抛错。凡是缓存了视图的地方（渲染循环里的顶点缓冲！），grow 之后必须重建。习惯：把"取视图"封装成函数，别长期持有。

字符串过边界同理：JS 用 `TextEncoder` 编码后写进内存，传**指针 + 长度**一对 i32；回程 `TextDecoder` 解码。mini 的 `NATIVE n`（print/clock）在 wasm 侧的落点是 **import**——模块声明"我要一个 `(f64) -> ()` 的函数"，实例化时由 JS 提供：

```wat
(import "env" "print" (func $print (param f64)))
;; 实例化：WebAssembly.instantiate(bytes, { env: { print: console.log } })
```

导入函数的索引排在模块内函数**前面**（`call 0` 就是 print）——链接在实例化这一刻完成，这是"编译期 call 静态索引"哲学的另一半。

### 实例化的对话时序：两次握手

`WebAssembly.instantiate(bytes, imports)` 幕后是一段固定时序：

| 阶段 | 谁做什么 | 失败形态 |
|---|---|---|
| 编译 | 字节流 → 引擎内部模块（可流式、可后台线程） | 验证错误（02 册）——Promise reject |
| 链接 | import 段逐项到 `imports` 对象里**按名字**找、**核对签名** | 找不到 / 签名不符 → 实例化错误 |
| 初始化 | memory 分页、data 写入、table/element 填充、global 赋初值 | 页数上限等资源问题 |
| 交付 | `instance.exports` 可用，宿主开始调用 | — |

"链接在实例化这一刻完成"的工程含义：**import 的签名错配不是运行期 bug 而是装载期异常**——JS 侧传了个 `(x, y) => …` 给声明为 `(f64) -> ()` 的 print，页面当场报错，不用等到第一次 print 才炸。类型又赢一次：02 册验证器管模块内部，实例化管模块与宿主的接缝。

### 索引空间全景：call 的数字从哪来

模块内每条 `call N` 的 N 都指向**统一的函数索引空间**——import 先占、模块内函数后继：

| 函数索引 | 是谁 | 怎么来的 |
|---|---|---|
| 0 | `print`（import） | import 段按声明顺序先编号 |
| 1, 2, … | 模块内函数 | function 段按声明顺序续编 |

这条排序规则解释了三件事：**`NATIVE n` 与 `CALL` 在 wasm 里合并成一条 `call`**（03 册映射表早有预言）；06 册 fib 模块里 `call 1` 是 fib、`call 0` 是 print（索引空间图）；**编译器必须在 emit 前知道 import 个数**——06 册"两遍扫描"里 `IMPORTS.length` 那个偏移量就是在算这个。

### 字符串过界：逐步推演

"指针 + 长度"协议从 JS 侧走一遍（任意 Unicode 串）：

| 步 | 侧 | 动作 | 边界上是什么 |
|---|---|---|---|
| 1 | JS | `TextEncoder.encode(s)` → UTF-8 字节 | JS 的 Uint8Array |
| 2 | JS | 分配 len 字节（导出的分配函数） | 拿到指针 p |
| 3 | JS | `new Uint8Array(memory.buffer, p, len).set(bytes)` | **字节已进线性内存** |
| 4 | JS→wasm | 调用导出函数，传 `(p, len)` 两个 i32 | 两个整数——一指针一长度 |
| 5 | wasm | 按 `p + i` 逐字节读 | UTF-8 字节流 |
| 6 | wasm→JS | 返回 `(p, len)`；JS `TextDecoder.decode(new Uint8Array(memory.buffer, p, len))` | 还原成 JS string |

三步各有坑位：第 1 步 UTF-8 的**字节数 ≠ 字符数**（长度传字符数就截断）；第 2 步分配算的是字节数；第 3 步做完才能传指针——**顺序错了（先传后写）传过去的是没填的内存**。05 册 bindgen 一节说的"编组代码自动写"，就是把这张表自动化。

## 函数表与 `call_indirect`：函数值的第一步

mini 的函数是一等公民（`CLOSURE` 压栈、`CALL` 弹出调用）；wasm 的 `call` 只认静态索引。动态分派靠**函数表**：

```wat
(type $unary (func (param f64) (result f64)))
(table 2 funcref)                        ;; 函数引用的数组
(elem (i32.const 0) $double $square)     ;; 槽 0、1 的初始内容

(func (export "apply") (param $f i32) (param $x f64) (result f64)
  local.get $x
  local.get $f                           ;; 参数先压、表索引最后压
  call_indirect (type $unary))           ;; 运行时按槽取函数、核对签名后调用
```

槽越界、槽是空的、签名对不上——三种情况**当场 trap**（C 的函数指针乱调是未定义行为，这里是确定性报错）。mini 闭包的 wasm 路线图由此清晰：**函数值 = 表索引（i32）**；真闭包再补一块"环境记录"放进线性内存，函数值升级为 (表索引, 环境指针) 二元组——upvalue 拆盒从 JS 对象搬进自留地，留作本专题之后的功课。

### apply(1, 5.0) 逐步执行：call_indirect 的三道门

```text
指令序列（emit 出的）        栈
local.get $x                [5.0]
local.get $f                [5.0, 1]        ← 表索引最后压
call_indirect (type $unary)
  ├─ 门 1：弹索引            [5.0]           → 槽 1
  ├─ 门 2：槽里有函数吗？    [5.0]           → $square ✓（空槽 → trap）
  └─ 门 3：签名吻合吗？      [5.0]           → (f64)->f64 与 type $unary ✓
    调用 $square(5.0)        [25.0]
```

三道门对应三种 trap（正文已列：越界、空槽、签名不符）。**门 3 是 C 函数指针永远没有的**：C 的 `(int(*)(int))ptr` 转换只在编译期撒谎，运行时闭眼调；wasm 把"这个槽里的函数是不是这个形状"做成运行期事实——mini 的 `CALL` 弹出函数值直接调用（运行时对象自带签名），动态性被 `call_indirect` 如实接住。

### 表在字节里长什么样：table 段与 element 段

02 册段家族表的 id=4 与 id=9 在本册模块里的分工：

| 段 | 内容 | 本模块的值 |
|---|---|---|
| table（id=4） | 表的元素类型 + 初始/最大槽数 | `(table 2 funcref)`：2 个槽，元素是函数引用 |
| element（id=9） | 初始填充：哪个偏移、哪些函数 | `(elem (i32.const 0) $double $square)`：槽 0、1 |

两个段**必须配对出现**：table 声明"有多大的柜子"，element 填"柜子里 initially 放什么"。运行期还能用 `table.set` 动态改柜子——`call_indirect` 的门 2/门 3 因此必须是**运行期检查**（柜子内容装载期不可知，02 册"验证不管"的又一例）。这也是"函数值 = 表索引"路线的扩展点：运行期往表里塞新函数，函数值系统就能动态生长。

### 从表索引到真闭包：二元组的布局草图

路线图（函数值 = 表索引；真闭包 = 二元组）落到内存布局上是这样的草图：

```text
函数值（无捕获）：    [表索引: i32]                        —— 就是一个数
闭包（有捕获）：      [表索引: i32][env 指针: i32]          —— 两数成对
env 记录（线性内存）： [upvalue 计数][u0][u1]…              —— bump 分配的一块
```

调用约定随之升级：`call_indirect` 之外，把 env 指针作为**多出来的第一个参数**传进去（C 世界的 `this` 指针同型）。upvalue 的读写在 env 记录里完成——第四阶段闭包分析的"捕获集"，在 wasm 里变成"env 记录里占几个槽"。本专题不做它，但布局先立此存照：**栈机、表、线性内存三件套拼起来，一等函数就没有死角**。

## 这块内存的 GC 账

线性内存 JS 的 GC **看不见**，bump 指针只进不退。三条出路，按使用模式选：

| 使用模式 | 还法 | 一句话 |
|---|---|---|
| 一次性计算（编译一个文件、跑一轮模拟） | **不还**——用完整个模块/实例丢弃，浏览器回收整个内存 | 模块即 arena |
| 长驻分轮（每请求/每帧一批对象，轮内活、轮间死） | **epoch reset**：每轮结束把堆顶指针拨回起点 | GC 专题 05 册 arena 思想的浏览器版 |
| 对象生死交错 | 自由链表/RC 自己上，或…… | 等 WasmGC（05 册）让 struct/array 变成引擎托管对象 |

顺带一个站群内呼应：webgl 站物理专题的选型里 rapier 用 Rust 编译到 wasm——Rust 的所有权在**编译期**决定释放点，线性内存里没有 GC 也可以安全地"用完即还"，正是第三行的高配版。

### 三行账的选择流程：一张决策图

GC 账表按使用模式三选一，选择流程画成图：

```mermaid
flowchart TD
    S["分配了线性内存里的对象"] --> Q1{"对象的生命周期<br>跟什么走？"}
    Q1 -->|"跟一次任务<br>（编译/模拟/请求）"| A1["不还：任务结束<br>丢整个实例/模块"]
    Q1 -->|"跟一轮循环<br>（每帧/每请求一批）"| A2["epoch reset：<br>轮末 hp 拨回起点"]
    Q1 -->|"生死交错<br>（长驻对象图）"| A3["自由链表/RC 自己上<br>或等 WasmGC"]
```

### epoch reset 的两行实现与它的前提

账表第二行的实现只要一条指令序列（`$heapBase` 是堆起点，本册是 8）：

```wat
(func $reset (global.get $heapBase) (global.set $hp))
```

便宜到近乎免费，但安全性靠一条**纪律**保证：**轮与轮之间不留引用**——上一轮的指针在 reset 后仍"合法"（地址在内存范围内），读到的却是新分配覆盖后的垃圾。这是 GC 专题 arena 的同款前提（[免 GC 的内存管理](../10-GC算法专题/05-免GC的内存管理.md)），也是它比 tracing GC 危险的地方：错误不是"忘了回收"（内存涨），而是"用回收过的"（静默脏数据）。mini 的分轮场景（每帧一批实体）恰好满足纪律，第二行对游戏/物理负载是白拿的收益。

### 内存用量怎么看：一个只涨不跌的仪表

线性内存没有 per-object 元数据，"现在用了多少"只有一个读数：`memory.buffer.byteLength`（当前页数 × 64 KiB）。bump 指针只进不退意味着：

- **hp 的锯齿不是内存降了**：每轮 reset 把 hp 拨回起点，但页不还——仪表上真实下降的是 hp，页数只升不降；
- **泄漏的形状**：不 reset 又持续分配 → 页数阶梯上涨 → `memory.grow` 频繁触发 → **视图反复 detach**（JS 一侧的实测坑）→ 缓存的视图全废。一个内存 bug 以三个症状出现，源头都在 bump 指针的单向性；
- 对照 JS 堆：DevTools 能看对象级保留树；线性内存里只有自己的分配器知道"40 号地址是什么"——**自留地的自由与孤独**。

## 常见误区

- **"线性内存是 JS 堆的一部分"**：它是独立的 ArrayBuffer，归 wasm 实例所有——`memory.buffer` 只是 JS 侧的视图窗口。所以 grow 能整体换底（detach 视图），JS 的 GC 也看不见里面的内容；
- **"地址 0 由硬件保护"**：线性内存没有空页保护，从 0 load 安静读数——空指针语义靠分配器约定（前 8 字节保留）；
- **"自己检查了越界，引擎就不用查了"**：反了——引擎的检查不可省略（沙箱底线），你的检查买的是**语义**不是安全。两层各挡各的；
- **"`call_indirect` 是 unsafe 的函数指针"**：三种失败全是确定性 trap，比 C 的未定义行为安全得多；它是"动态但可验证"的调用——mini 函数值路线正吃这个性质；
- **"GC 账的'不还'是内存泄漏"**：泄漏 = 长驻实例里无限增长；"模块即 arena"是**有意的生命周期设计**——实例丢弃时整块内存由引擎回收，宿主 GC 接手；
- **"零拷贝 = 跨边界免费"**：零拷贝只对**住在线性内存里的数据**成立（TypedArray 视图）；标量参数每次调用仍按值过界（05 册边界税）。数据不搬进线性内存，就没有零拷贝可谈。
