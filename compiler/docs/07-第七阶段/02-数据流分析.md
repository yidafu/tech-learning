# 数据流分析：格、不动点与 worklist

> [返回：第七阶段导览](01-导览.md)
> 对应大纲第 1 条。优化的一切"依据"都来自分析：要知道 `x*0` 能不能删，先得知道 `x` 是不是常量；要知道某条指令是不是死代码，先得知道它的结果还有没有人读。本册把"分析"本身讲透：**在 CFG 上解一组联立方程，解法是迭代到不动点**。代码全部在本机 Node 24 实跑验证（输出为真实运行结果），IR 沿用[第五阶段的 TAC/CFG 形态](../05-第五阶段/02-中间表示家族.md)。

## 把"分析"变成方程

数据流分析的统一骨架：**给每个程序点关联一个"事实"**（一个集合、一个映射……），然后沿 CFG 的边传播事实直到稳定。`IN[b]` / `OUT[b]` 是基本块 b 入口/出口处的事实，两者由两件事联系起来：

- **transfer（传递函数）**：块内语句怎么改写事实——`OUT = f_b(IN)`（前向）；
- **meet（汇合）**：多条边进入同一点时事实怎么合并——`IN[b] = ⋁ { OUT[p] | p ∈ pred(b) }`。

方向与合并方式组合出四类经典分析：

| 分析 | 方向 | 合并 | 事实问的问题 | 服务于 |
|---|---|---|---|---|
| 到达定值 | 前向 | may（并集） | 哪些**赋值**能（沿某条路）到达此点 | 公共子表达式、未初始化检测 |
| 活跃变量 | 后向 | may | 哪些变量在此点**之后还会被读** | 死代码消除、寄存器分配 |
| 可用表达式 | 前向 | must（交集） | 哪些表达式**所有路径**都算过且操作数未变 | 全局 CSE |
| 常量传播 | 前向 | 逐值 meet | 每个变量在此点**一定**是什么值 | 折叠、死分支裁剪（[下一册](04-经典优化pass.md)） |

**may 与 must 的语义差别**：may 问"有没有可能"（一条边成立即可并进来），must 问"是否必然"（所有边都成立才保留）。同是前向，到达定值用并集、可用表达式用交集——因为"可能有定值到达"和"表达式一定可用"回答的是不同的问题。搞混 meet 方向是数据流 bug 的第一大来源（比 off-by-one 还常见）。

## 格与不动点：为什么迭代会停

把"事实"放进**半格**（semilattice）：一族值 + 一个 meet 操作 `∧`，满足幂等（x∧x=x）、交换、结合。格上有偏序：`a ≤ b ⟺ a ∧ b = a`。任何有限高度的格 + 单调传递函数，迭代求解必然收敛——**Kleene 不动点定理**的直觉版：

1. 从 ⊤（格顶，"什么都不知道"）出发；
2. 每轮迭代，事实只会沿格"向下"走（单调性保证不会回头）；
3. 格的高度有限（比如 |变量集| 层），事实最多下降有限次 → 必然停在某个不动点。

活跃变量的格是"变量集合按 ⊆ 排列"：⊤=∅，每并进一个新变量就"下降"一步，最坏下降 |V| 步。**这就是收敛性的全部秘密：事实只增不减，有限集合必然到头**。

两个工程上重要的推论：

- **初始化决定解的方向**。may 分析全初始化为 ∅（⊤），迭代只会把解变大——得到的是**最小不动点**（最精确的 may 解）。must 分析非入口块必须初始化为全集（⊤），否则交集一下就空了——这是初学者第二常见的错误：把可用表达式的初值设为 ∅，跑出来"处处无可用表达式"，看似收敛实则全错。
- 迭代解 ≤ 理想解（沿所有真实路径汇合的 MOP 解）。对 distributive 的分析（上述三种集合分析都是），两者相等；常量传播不满足分配律，迭代解可能比理想解保守——够用，但要知道这个差距存在。

## 通用 worklist 求解器：完整实现

反复"全图扫一遍直到无变化"是能用但浪费的；worklist 只重算"邻居刚变过"的块。下面是完整实现（TS，本册/03/04 册共用这套 IR——比第五阶段的字节码多一层"终结指令"抽象，因为**分支条件和返回值也是变量的使用**，不建模它们，活跃变量会漏报）：

```ts
// ---- IR：三地址码 + 显式 CFG（对应第五阶段 05-02 册的 TAC）----
interface Instr {
  op: string;               // 'add' | 'lt' | 'copy' | 'print' | ...（表达式身份用）
  dest: string | null;      // 定义的目标变量；null = 无定义（print）
  srcs: readonly string[];  // 读取的变量
}
type Term =                                        // 块的终结指令（最后一条，决定后继）
  | { op: 'ret'; srcs: readonly string[] }
  | { op: 'jmp' }
  | { op: 'br'; cond: string };                    // 条件分支：cond 真→succ[1]，假→succ[0]
interface Block {
  id: number;
  instrs: Instr[];           // 普通指令（块内顺序执行，无跳转）
  term: Term;                // 终结指令（读 use 集合，不定义变量）
  succ: number[]; pred: number[];
}
const termUses = (t: Term): readonly string[] =>
  t.op === 'ret' ? t.srcs : t.op === 'br' ? [t.cond] : [];
```

```ts
// ---- 通用求解器：一个 Spec 描述一种分析，solve 负责迭代 ----
interface Spec<A> {
  direction: 'forward' | 'backward';
  top: A;                    // 除入口外所有块的初值（may 用 ∅，must 用全集）
  boundary: A;               // 入口之前（或出口之后）的边界事实
  meet: (xs: A[]) => A;      // ∨（may）或 ∧（must）
  eq: (a: A, b: A) => boolean;
  transfer: (b: Block, x: A) => A;   // forward: IN→OUT；backward: OUT→IN
}

function solve<A>(cfg: Block[], spec: Spec<A>): { in: A[]; out: A[]; visits: number } {
  const inF = cfg.map(() => spec.top);
  const outF = cfg.map(() => spec.top);
  const atEdge = (b: Block): A => {                 // 汇合邻居；边界只钉在入口/出口
    if (spec.direction === 'forward') {
      const ns = b.pred.map(p => outF[p]);
      return spec.meet(b.id === 0 ? [spec.boundary, ...ns] : ns);
    }
    const ns = b.succ.map(s => inF[s]);
    return spec.meet(b.succ.length === 0 ? [spec.boundary, ...ns] : ns);
  };
  const work = [...cfg.map(b => b.id)];             // 初始全部入队
  let visits = 0;
  while (work.length) {
    const id = work.shift()!;
    visits++;
    const b = cfg[id];
    const x = atEdge(b);
    const y = spec.transfer(b, x);
    const changed = spec.direction === 'forward' ? !spec.eq(inF[id], x) || !spec.eq(outF[id], y)
                                                 : !spec.eq(outF[id], x) || !spec.eq(inF[id], y);
    if (spec.direction === 'forward') { inF[id] = x; outF[id] = y; }
    else { outF[id] = x; inF[id] = y; }
    if (changed)                                    // forward: OUT 变→后继重算；backward: IN 变→前驱重算
      for (const n of spec.direction === 'forward' ? b.succ : b.pred)
        if (!work.includes(n)) work.push(n);
  }
  return { in: inF, out: outF, visits };
}

const setEq = <T>(a: Set<T>, b: Set<T>) => a.size === b.size && [...a].every(x => b.has(x));
const unionAll = <T>(xs: Set<T>[]): Set<T> => { const s = new Set<T>(); for (const x of xs) for (const e of x) s.add(e); return s; };
const interAll = <T>(xs: Set<T>[]): Set<T> =>
  xs.length === 0 ? new Set<T>() : xs.reduce((s, x) => new Set([...s].filter(e => x.has(e))), xs[0]);
```

这三处是本实现踩过并修掉的坑，每个都值得抄进你的工程笔记：

1. **终结指令的 use 必须建模**。`br cond` 读 `cond`、`ret v` 读 `v`。漏掉的话，活跃变量分析会告诉你"分支条件是死变量"——然后死代码消除 pass 就敢把它删了，程序直接错。
2. **boundary 只钉在入口/出口，不参加内部节点的 meet**。边界事实（"入口处无任何变量活跃"、"入口处无任何定值到达"）只能约束入口块。如果把 ∅ 混进 must 分析每个汇合点，交集瞬间清空——第二节的"全错"警告的代码版。
3. **重入队方向跟着信息流走**：前向分析 OUT 变了入队**后继**，后向分析 IN 变了入队**前驱**。写反了不报错，但会把 worklist 退化成接近全图重扫。

## 三大分析的实例化

每个分析只是一个 `Spec`。到达定值用"定值 id = 块号.指令号"标识；可用表达式预先建"表达式键 → 操作数表"的全表，kill 时按操作数命中：

```ts
// ---- 分析一：活跃变量（backward may）----
function liveVars(cfg: Block[]) {
  return solve<Set<string>>(cfg, {
    direction: 'backward', top: new Set(), boundary: new Set(),
    meet: unionAll, eq: setEq,
    transfer: (b, out) => {
      let live = new Set(out);
      for (const s of termUses(b.term)) live.add(s);   // 终结指令先执行：先并它的 use
      for (let i = b.instrs.length - 1; i >= 0; i--) { // 逆序扫：先 use 后 def
        const d = b.instrs[i];
        if (d.dest) live.delete(d.dest);
        for (const s of d.srcs) live.add(s);
      }
      return live;
    },
  });
}

// ---- 分析二：到达定值（forward may）----
function reachingDefs(cfg: Block[]) {
  const killOf = new Map<string, Set<string>>();      // 变量 → 它所有定值的 id
  for (const b of cfg) b.instrs.forEach((d, idx) => {
    if (!d.dest) return;
    if (!killOf.has(d.dest)) killOf.set(d.dest, new Set());
    killOf.get(d.dest)!.add(`${b.id}.${idx}`);
  });
  return solve<Set<string>>(cfg, {
    direction: 'forward', top: new Set(), boundary: new Set(),
    meet: unionAll, eq: setEq,
    transfer: (b, inS) => {
      const s = new Set(inS);
      b.instrs.forEach((d, idx) => {
        if (!d.dest) return;
        for (const o of killOf.get(d.dest)!) s.delete(o);  // kill：同变量其它定值
        s.add(`${b.id}.${idx}`);                           // gen
      });
      return s;
    },
  });
}

// ---- 分析三：可用表达式（forward must）----
function availableExprs(cfg: Block[]) {
  const exprKey = (d: Instr) => `${d.op}(${d.srcs.join(',')})`;
  const exprSrcs = new Map<string, string[]>();       // 表达式键 → 操作数表（kill 判定用）
  for (const b of cfg) for (const d of b.instrs)
    if (d.dest && d.op !== 'copy') exprSrcs.set(exprKey(d), [...d.srcs]);
  return solve<Set<string>>(cfg, {
    direction: 'forward',
    top: new Set(exprSrcs.keys()),                    // must 的 ⊤ = 全部表达式
    boundary: new Set(),                              // 入口之前无任何可用表达式
    meet: interAll, eq: setEq,
    transfer: (b, inS) => {
      const s = new Set(inS);
      for (const d of b.instrs) {
        if (d.dest)                                   // kill：一切读 d.dest 的表达式
          for (const [k, srcs] of exprSrcs) if (srcs.includes(d.dest)) s.delete(k);
        if (d.dest && d.op !== 'copy') s.add(exprKey(d));   // gen
      }
      return s;
    },
  });
}
```

注意常量折叠视角下的一个细节：`copy` 指令（`x = y`）在可用表达式里既不 gen 也不算表达式——复制传播是另一类优化（[04 册](04-经典优化pass.md)单独讲），混进 CSE 的格只会让 kill 集算错。

## 跑起来：max 与循环的真实输出

用第五阶段的 max 函数（`t1 = a > b; if t1 goto L1; ...`）与一个求和循环做例子，实际运行输出：

```text
== max · 活跃变量 ==  visits=4
  B0  in={a, b}  out={a, b}
  B1  in={b}     out={}
  B2  in={a}     out={}

== loop · 活跃变量 ==  visits=15
  B0  in={n, one}            out={i, n, one, s}
  B1  in={i, n, one, s}      out={i, n, one, s}     ← 循环头：四个变量跨迭代活跃
  B2  in={i, n, one, s}      out={i, n, one, s}
  B3  in={i, n, one, s}      out={i, n, one, s}
  B4  in={s}                 out={}                 ← 出口只剩返回值活跃
```

读两张表练手感：

- **max**：`t1` 不在任何 in/out 里——它在 B0 内定义、被 B0 的 `br` 消费，从不跨块活；`a`/`b` 活到 B1/B2 各自的 `copy`。寄存器分配器看到这张表就知道：两支各只需留一个寄存器。
- **loop**：循环不变量 `n`、`one` 在**整张图都活跃**（每个迭代都要读）——这正是[循环不变量外提](04-经典优化pass.md#循环优化一瞥)的判据来源；`i`/`s` 是循环携带依赖，活跃区间覆盖全环。

到达定值在循环上的输出同样值得读一遍（visits=9）：循环体里的四个定值 `2.0~2.3` 沿回边**绕一圈回到自己**（`B1 in` 含全部 7 个定值）——**回边就是"方程组里引用自己的未知数"**，这正是不动点迭代不可替代的原因：线性扫描解不了环上的联立方程。

## 实测：朴素法、worklist、有序 worklist

同一个 loop CFG、同一个活跃变量分析，三种解法的块访问次数（本机实测，visits 计数）：

| 解法 | visits | 说明 |
|---|---|---|
| 朴素：反复全扫直到无变化 | 20（4 轮 × 5 块） | 每轮都重算没变的块 |
| worklist（FIFO，自然序） | 15 | 只重算受影响块 |
| worklist（沿信息流方向排序） | 10 | 后向分析按"逆 RPO"出队，一次推进到位 |

结论有三条：

1. **worklist 的收益来自"不重算没变的块"**，循环越深、图越大越明显；
2. **出队顺序是免费的加速器**：前向分析用 RPO（深度优先后序的逆序，[下一册](03-SSA构建.md)会再次遇到它）、后向分析用逆 RPO——信息沿边单向传播时，一次扫描就能送到底；
3. 顺序只影响**速度**不影响**结果**——格上的最小不动点是唯一的，这是"敢随便换顺序"的底气。

## 常量传播：一个不是集合的分析

常量传播把"事实"从集合换成**每个变量一个格值**：⊤（未见过）→ c（常量）→ ⊥（非常量）。meet 规则：`⊤ ∧ x = x`；`c ∧ c = c`（相等时）；其余 → ⊥。它展示格框架的另外两点：

- **格不一定是布尔格**：值域是"变量 → 格值"的映射，meet 逐变量进行；
- **它不满足分配律**，迭代解可能比理想解保守（菱形分支两侧算出不同常量、汇合后 ⊥，即使真实路径上只能走一边）。所以它通常配"条件常量传播"（SCCP）：把 CFG 的边可达性也放进格一起算，死分支里的定值不再污染汇合点——[04 册](04-经典优化pass.md)的实现走的就是这个方向的简化版。

## 附：把 solve 变成产品：三个工程陷阱

骨架（worklist + 传递函数 + 格）人人会写，真实分析器的好坏差在三个陷阱的处理上。开列之前先立一条判据：**"分析结果随无关因素变化"就是陷阱信号**——无关因素包括块编号、文件拆分方式、语句的无关重排；正确的分析只随语义变化。三个陷阱逐一对照这条判据：

| 陷阱 | 症状 | 正解 |
|---|---|---|
| **传递函数写成了依赖 visit 顺序** | 同一 CFG 换块号就得出不同解 | 传递函数必须是"输入格值 → 输出格值"的纯函数；块内顺序可以吃（语句序），块间顺序绝不能吃 |
| **不动点判定用"集合相等"而非格相等** | may 分析里 `{a} 与 {a,b}` 被误判为稳定/不稳定 | 比较用格的偏序（子集判定）而不是深相等——半格理论第 3 节的直接变现 |
| **worklist 无界重复入队** | 巨型函数上分析跑不完 | 出队时只在"格值真的变高"时把后继入队（惰性传播）；配合 RPO 初始序，实测轮数逼近 02 册定理的界 |

三个陷阱的共同根因是同一条：**格理论不是装饰，是约束条件的来源**——传递函数的单调性、解的最小性、终止性，每一条都对应一个"写错就出事"的工程点。这也解释了为什么本册先讲半格再讲框架再讲实例：直接从实例入手的人会撞完这三个陷阱，从理论入手的人把它们当约束提前规避。mini 项目的 07 册实践把 solve 搬上字节码时，会再遇到一个变形陷阱（抽象栈的深度分歧——分支两侧栈深不一致怎么合流），那是本册"合流运算符"在栈式机上的自然延伸。

最后一个自查口径：写完任何数据流分析，用"扰动重跑"验证一遍——手工改一个块的输入格值，确认最终解要么不变、要么沿格单调变化。这一步抓的是"传递函数里有隐藏的非单调副作用"，是三个陷阱里最难从代码 review 看出来的那个。

三个陷阱之外，再留一张"分析选型速查"——拿到一个待分析问题时先对号入座：

| 要回答的问题 | 分析族 | 方向 | 初始化 | 本册对应 |
|---|---|---|---|---|
| "这里的值有没有可能是 null？" | may（可能） | 前向 | ⊥（空集） | 常量传播一族 |
| "这里的值一定是常量几？" | must（必然） | 前向 | ⊤（全集） | 常量传播 |
| "这个变量后面还会被读吗？" | may（会活跃） | 后向 | ⊥ | 活跃变量 |
| "这个表达式还能直接复用吗？" | must（可用） | 前向 | ⊤（入口外） | 可用表达式 |

对号入座的价值：**方向与初始化不是拍脑袋的选择，是从"may/must × 前向/后向"推出的机械结果**——写新分析前先在这张表上找到自己的格子，格子的四个参数就全定了。07 册实践里 DCE 用到的是第一格与第三格的组合（不活跃即死），04 册的 LVN/GVN 用的是第四格的表达式复用——这张表是连接"学一个框架"与"用一打分析"的枢纽。

最后给一个"手算一场"的完整练习配方（把本册的方法论压成可执行的七步）：

1. 画出 CFG，标出每个块的基本块内容与终结指令；
2. 从速查表找到格子，写下方向、初值、合流运算符；
3. 写每个块的传递函数（先在纸上写" Kills / Gen"的集合表达式）；
4. 选遍历序（RPO / 逆 RPO），列出第一轮的出队顺序；
5. 逐块算 in/out，标注哪些块的格值发生了变化；
6. 第二轮直到没有任何格值变化——写下最终解；
7. 扰动验证：手工改一个块，确认解的移动方向与格序一致。

七步跑过两个不同格子的分析（比如常量传播与活跃变量），"框架"就从名词变成了肌肉记忆——这正是 03 册 SSA 构建要用到 pruned 判断时的底气来源。

收尾一个"分析器 code review 检查单"，给未来读同事的分析代码（或读开源实现）用：

- 传递函数是否纯函数——块间顺序换了结果变不变？
- 合流运算符与 may/must 口径一致吗——may 用并、must 用交，写反立刻全错；
- 初值是否按格子填——must 前向非入口块给了 ⊥ 吗？
- worklist 会不会风暴——格值不变时后继是否还入队？
- 结果有没有随块号/拆分变化的迹象——扰动重跑过了吗？

五条全过，这个分析器才能进主分支——数据流分析的 bug 从不报错，只是静默给出"看起来合理"的错误集合，review 是唯一防线。

读完合上书前的最后一问（自测零号题）：本册的 solve 循环、半格、传递函数三件套，与第三阶段 Pratt 解析器的"绑定力表 + 爬升循环"有什么结构上的共性？——提示：两者都是"一个数据结构（格/优先级）承载全部决策，一个循环机械执行"。这个视角是全课程的统一论：编译器各阶段的复杂度都不在控制流，在**数据结构的设计**——数据结构选对了，算法只是几行循环。本册的格、03 册的支配树、Pratt 的绑定力表、字节码设计的指令表，是同一个论点在四个阶段的四次现身——带着这个论点进入 08 阶段，Babel 的 Path 体系与 tsc 的 Symbol 图会读得更快。

下一册 SSA 构建正好是这句论点的证明现场：支配树选对了，φ 插入只是几行 worklist；反过来随便一个"看起来差不多"的遍历序（自测 4 的 CFG DFS 反例）就会产出错误的版本链。往下读时带着这个对照。

一句话收束本册：**数据流分析 = 在格上对"传递函数 × 合流运算"做不动点迭代**——其余一切（方向、初值、遍历序、速度）都是这句话在具体问题上的投影。
