# 实践：给 mini 字节码写优化 pass 与收益分析

> [返回：第七阶段导览](01-导览.md)
> 对应大纲实践任务 0~4。[02 册](02-数据流分析.md)给了分析、[04 册](04-经典优化pass.md)给了 TAC 上的 pass 与管线，本册把它们落到**第五阶段的栈式字节码**上：划分基本块、跑四连 pass、重写跳转偏移，最后用基准数据回答那个最重要的问题——**优化到底值了多少**。全部代码在本机 Node 24 实跑验证，输出为真实运行结果；IR 与[第五阶段字节码设计](../05-第五阶段/03-字节码设计.md)一致（教学版子集，不含 CALL/CLOSURE 的完整语义）。

## 为什么在字节码层再写一遍

TAC 显式命名每个临时变量，数据流一目了然；栈式字节码则**把数据流藏进了栈里**——`GET_LOCAL 1; CONST 2; DIV` 里"DIV 读谁"没有名字，要看栈的模拟。在字节码层重写一遍 pass，练的正是**从隐式栈使用里恢复显式数据流**：这也是 Lua、Erlang 这类寄存器化改造（把栈机 IR 转寄存器 IR）第一步要做的事。另一个现实理由：`mini build --optimize` 优化的是产物（字节码），不是中间形式——优化留在 IR、又要在产物上重做，等于白干。

## 基础设施：decode、基本块、CFG

两个决定后面所有 pass 的选择：

**选择一：把 `code: number[]` 解码成指令对象数组**，跳转的相对偏移换算成**目标指令的下标**——所有 pass 在对象数组上做增删标记，不再手工维护字节数组：

```ts
function decode(code: number[]): Ins[] {
  // Ins = { op, arg?, src, dead, tgt } ; tgt = JMP/JMP_IF_FALSE 的目标下标
  // JMP 偏移语义(03 册): 目标 = 下一条指令地址 + off → 换算后直接记 tgt
}
```

**选择二：基本块的 leader 三规则**（与 02 册在 TAC 上的一致）：入口、跳转目标、跳转/RETURN 的下一条。块内顺序执行无跳转；块的"终结指令"决定后继。

> **血泪栏：手算相对偏移，三次全错**。本册的开发过程里，手写字节码的 `JMP`/`JMP_IF_FALSE` 偏移算错了三次：跳进 else 块中间（优化器的栈模拟直接崩）、回边差 2 字节（块结构错乱）、差 1 字节（死循环）。每次的错误都只差一两条指令的宽度——这正是 03 册"相对偏移比绝对地址好修，**仍要小心**"的注脚，也是**为什么 encode 阶段要用"记录标签地址 → 统一回填"而不是手算**。生产编译器的 emit 侧全是标签制（label + backpatch），本册的 decode/encode 是它的手工镜像。

## 四连 pass

### pass 1：块内常量折叠 + 栈/槽传播

对每个基本块**模拟执行**一遍：栈上每个元素记 `{v, from}`——值（若已知）与**产生它的指令**；局部槽同理记已知值。

- `CONST` 压已知值；`GET_LOCAL s` 若槽已知 → **就地替换成 CONST**（值入池），压已知值；`SET_LOCAL s` 弹栈并记槽值；
- 二元算术/比较：两个操作数都已知且都是 number → **折叠**——把左操作数的 `from` 指令改写成 `CONST 结果`，右操作数与运算指令标 dead（它们是纯供给指令，删除安全）；
- `JMP_IF_FALSE`：条件已知 → 恒真直接删（落穿）、恒假改 `JMP`；**供值的 CONST 也一并 dead**（它只服务于这个已死的分支判断）；
- **不可折叠的边界**：`DIV`/`MOD` 除数为 0 不折——运行时除零错误是**可观察行为**（04 册的规矩，字节码层同样成立）；遇未建模指令（CALL 等）保守清空整个栈与槽表。

一个实现细节藏着经典的求值顺序陷阱：把 `GET_LOCAL` 替换成 `CONST` 时，必须**先取出槽值再改写 `arg`**——`it.arg = pool.length; pool.push(slots.get(it.arg))` 这种一行写法，`it.arg` 已经变成池索引，取到的槽是 `undefined`。本册开发中真实踩中，栈模拟随后把"常量"传播成 undefined，除法折叠悄悄失效——**数据流 pass 的 bug 大多不崩，只是悄悄变笨**。

### pass 2：死存储消除

全函数统计：对每个槽 `s`，若**没有任何活着的 `GET_LOCAL s`**，则所有 `SET_LOCAL s` 改成 `POP`（弹栈保栈平衡，不直接删——喂值指令还压着栈）。槽 `s` 的供值链接下来交给窥孔收尸。

### pass 3：窥孔

| 模式 | 替换 | 备注 |
|---|---|---|
| `CONST x; POP` | 全删 | **兜住 pass 2 换出来的 POP 残骸**——喂值链在此整体消失 |
| `NOT; NOT` | 全删 | 双重否定 |
| `JMP L1`，L1 处是 `JMP L2` | 改 `JMP L2` | 跳转 threading |
| `JMP` 的目标是下一条活指令 | 删 | 直落即达 |

### pass 4：可达性清扫 + encode 重写

从入口块沿 CFG 后继 BFS，不可达块（死分支的尸体）整体标 dead。然后 encode：活指令顺序线性化，**每个跳转按目标指令的新地址重算相对偏移**（`off = 新目标地址 − (本条地址 + 2)`）。

主循环：四连跑完 encode 一轮，新 code 与上一轮逐字节比较，相同则到不动点（[04 册管线](04-经典优化pass.md)的"跑到不动点"，此处以字节码形态复现）。

## 实测一：吃满全部 pass 的例子（27 字节 → 3 字节）

直译 emit（不做任何前端折叠）的 mini 源码：

```text
let n = 50;                 // 槽1
let half = n / 2;           // 槽2
if (1 < 2) { return half } else { return 999 * 1 }
```

优化前（27 字节，真实 disasm 输出）：

```text
   0 CONST          0   ; 50
   2 SET_LOCAL      1
   4 GET_LOCAL      1
   6 CONST          1   ; 2
   8 DIV
   9 SET_LOCAL      2
  11 CONST          2   ; 1
  13 CONST          1   ; 2
  15 LT
  16 JMP_IF_FALSE   3   ; -> 21
  18 GET_LOCAL      2
  20 RETURN
  21 CONST          3   ; 999
  23 CONST          2   ; 1
  25 MUL
  26 RETURN
```

优化后（**3 轮到不动点，3 字节**）：

```text
   0 CONST          8   ; 25
   2 RETURN
```

逐 pass 对账（谁吃了谁）：

| 指令 | 消失原因 |
|---|---|
| `GET_LOCAL 1`(ip4) | pass 1 槽传播：槽1 已知 50 → 替换为 CONST |
| `DIV`(ip8) | pass 1 折叠：50/2 → 25（除数非零合法） |
| `GET_LOCAL 2`(ip18) | pass 1：槽2 已知 25 → 替换为 CONST |
| `CONST 1; CONST 2; LT; JIF`(ip11~17) | pass 1：1<2 恒真 → JIF 删除、供值 CONST 一并 dead |
| else 块(ip21~26) | pass 4：分支死后不可达，整体清扫 |
| `SET_LOCAL 1/2` | pass 2：槽再无人 GET → 改 POP |
| `CONST 50; POP` 等残骸 | pass 3：窥孔 `CONST; POP` 收尸 |

语义对照（教学解释器实跑）：**前 `ret 25`，后 `ret 25`**，动态指令数 12 → 2。

## 实测二：预期提升但没提升（本阶段的重点案例）

迭代版 `sum(n)`（`while (i > 0) { acc += i; i -= 1 }`）——直觉上"优化器总该做点什么"：

```text
--- 优化前(34 字节) ---            --- 优化后(1 轮,34 字节) ---
   0 CONST 0 ; 0                      (逐字节相同,零变化)
   2 SET_LOCAL 1
   ... 循环体 GET/CONST/ADD/SET ...
  29 JMP -24 ; -> 8
  31 GET_LOCAL 1
  33 RETURN
```

优化器跑了一轮就到不动点——**一条指令都没动**。为什么：

- 循环体里每个操作数都来自上一轮循环（槽值未知），**没有可传播的常量**；
- 每个槽都有活的 GET，没有死存储；
- 跳转目标都是真实的基本块，窥孔无模式可配。

基准数据（`sum(1_000_000)`，教学解释器，3 次取中位，M4 Pro / Node 24）：

```text
优化前 71ms / 动态指令 13,000,010   vs   优化后 69ms / 动态指令 13,000,010
```

差异 2ms 在噪声内，动态指令数**完全相同**——正确结论不是"优化器没用"，而是：

1. **静态优化消灭的是静态指令，解释执行的耗时由动态指令数决定**——sum 的动态指令全部来自循环体，而循环体恰好无可优化；
2. 收益要到别处找：字节码体积（I-cache/加载）、以及**给更强后端铺路**——若 mini 有 JIT，循环体内 `CONST 0/1` 的类型信息、基本块边界、CFG 都是优化器的输入。这正是 esbuild/terser 的处境：minify 对运行速度通常也无感，卖点是体积。

（对照：实测一的 12→2 是**动态指令**层面的真实缩减——因为被优化的代码在热路径之外的主干上。什么程序有收益？**常量配置驱动的分支**、模板生成的重复代码、`DEBUG` 开关——"直译 + 后期统一优化"的管线里，前端越笨，优化器的舞台越大。）

## 与 04 册 TAC 管线的关系

同一对"分析 + 转换"在两种 IR 上的两次实现：TAC 册的 `pipeline()` 是函数式的（每个 pass 独立作用于 Cfg），本册的 pass 共享 `dead` 标记与一次 encode——工程上后者的"标记-清扫-重排"更接近真实字节码优化器（LLVM 后端 MachineFunction 级 pass 也是标记+统一重组）。两册代码可以互相印证：把实测一的例子手工翻成 TAC，跑 04 册的管线，得到的语义结果相同、轮数相同。

## 自测

1. 栈式字节码上做常量传播，为什么必须模拟栈而不是只看局部槽？（提示：`DIV` 的操作数在栈上，槽表管不到它们）
2. 死存储 pass 为什么把 `SET_LOCAL s` 改成 `POP` 而不是直接删除？把整个链条（改 POP → 窥孔收尸）走一遍，说明每一步各删了什么。
3. 你的优化器把 `sum` 的 `JMP` 回边错误地 threading 到了 `RETURN`——哪个 pass 最可能背锅？怎么用"逐 pass 打印 disasm"定位？
4. 把实测一改成 `if (2 < 1)`（恒假分支），优化后的字节码是什么？`999 * 1` 的折叠还会发生吗——为什么"不可达代码也值得折叠"在这个例子里无所谓，但在**体积**维度上是成立的？
5. 71ms vs 69ms 为什么不能写成"性能提升 2.8%"？给出三个理由（提示：中位数、噪声、动态指令数不变时耗时差异的语义）。
