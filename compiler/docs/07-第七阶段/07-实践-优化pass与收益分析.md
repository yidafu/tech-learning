# 实践：给 mini 字节码写优化 pass 与收益分析

> [返回：第七阶段导览](01-导览.md)
> 对应大纲实践任务 0~4。[02 册](02-数据流分析.md)给了分析、[04 册](04-经典优化pass.md)给了 TAC 上的 pass 与管线，本册把它们落到**第五阶段的栈式字节码**上：划分基本块、跑四连 pass、重写跳转偏移，最后用基准数据回答那个最重要的问题——**优化到底值了多少**。全部代码在本机 Node 24 实跑验证，输出为真实运行结果；IR 与[第五阶段字节码设计](../05-第五阶段/03-字节码设计.md)一致（教学版子集，不含 CALL/CLOSURE 的完整语义）。

## 为什么在字节码层再写一遍

TAC 显式命名每个临时变量，数据流一目了然；栈式字节码则**把数据流藏进了栈里**——`GET_LOCAL 1; CONST 2; DIV` 里"DIV 读谁"没有名字，要看栈的模拟。在字节码层重写一遍 pass，练的正是**从隐式栈使用里恢复显式数据流**：这也是 Lua、Erlang 这类寄存器化改造（把栈机 IR 转寄存器 IR）第一步要做的事。另一个现实理由：`mini build --optimize` 优化的是产物（字节码），不是中间形式——优化留在 IR、又要在产物上重做，等于白干。

### 栈效果表：恢复数据流的第一张草稿

"从隐式栈使用里恢复显式数据流"的第一步是**给每条指令标注栈效果**——压几个、弹几个、弹上来的值去哪。拿本册最小的三元组演示（第五阶段栈机语义）：

| 指令 | 压/弹 | 栈效果 | 数据流读法 |
|---|---|---|---|
| `GET_LOCAL 1` | 压 1 | 栈 +1，元素 = 槽 1 的值 | **use**：读槽 1 |
| `CONST 2` | 压 1 | 栈 +1，元素 = 常量 2 | 定值源：常量 |
| `DIV` | 弹 2 压 1 | 栈 −1，元素 = 栈顶两元素相除 | use-use-def：读栈顶两个、产生一个值 |

二元运算的"弹 2 压 1"正是隐藏的数据流节点：`DIV` 有两个 use（栈顶、次顶）一个 def（结果），只是 use 的"名字"是**栈位置**而不是变量名。栈模拟 pass 的全部工作就是**给栈位置编号、追踪每个编号的来源**——[02 册](02-数据流分析.md)的 use-def 链在栈机上的等价物是 pass 1 里 `{v, from}` 的 **from 指针链**。栈效果表写错一条（比如把 `DIV` 写成弹 1），数据流就整体错位——这也是先在纸面上钉死指令集语义、再写 pass 的原因。

### 两套 IR 的 pass 差异总表

"再写一遍"的差异值得成表——同名 pass 在两种 IR 上长得不一样的地方（每行都会在四连 pass 里遇到）：

| 关注点 | TAC（04 册） | 字节码（本册） | 差异根源 |
|---|---|---|---|
| 值的身份 | dest 名字 | 栈位置 + 槽号 | 栈机把名字藏进了栈 |
| 定值点 | 每条带 dest 的指令 | `SET_LOCAL` + "运算压栈"两条路径 | 二元运算的 def 隐式发生 |
| use 的收集 | 直接读 `srcs` | 模拟栈、回溯栈元素的 from | use 不出现在指令编码里 |
| 死代码判据 | dest 无人读 | 槽无人 GET + 供给链无人消费 | 两级判据（槽级 + 指令级） |
| 删除动作 | 从 `instrs` 里 filter | 标 `dead`，encode 时跳过 | 字节数组的地址耦合 |
| 分支裁剪 | 删死边 + 改 term | 改 `JMP`/标 dead + 重算偏移 | 跳转是相对偏移不是引用 |

最后一列是理解这张表的钥匙：**差异全部来自 IR 的表示选择，不来自优化思想**——思想（分析 → 标记 → 改写）在两个世界一字不差。所以"再写一遍"练的不是新 pass，是**把同一思想适配到不同表示的能力**——这正是真实编译器里 middle-end pass 被移植到新 IR 时的日常工作。

## 基础设施：decode、基本块、CFG

两个决定后面所有 pass 的选择：

**选择一：把 `code: number[]` 解码成指令对象数组**，跳转的相对偏移换算成**目标指令的下标**——所有 pass 在对象数组上做增删标记，不再手工维护字节数组：

```ts
function decode(code: number[]): Ins[] {
  // Ins = { op, arg?, src, dead, tgt } ; tgt = JMP/JMP_IF_FALSE 的目标下标
  // JMP 偏移语义(03 册): 目标 = 下一条指令地址 + off → 换算后直接记 tgt
}
```

**选择二：基本块的 leader 三规则**（与 02 册在 TAC 上的一致）：入口、跳转目标、跳转/RETURN 的下一条。块内顺序执行无跳转；块的"终结指令"决定后继。

> **血泪栏：手算相对偏移，三次全错**。本册的开发过程里，手写字节码的 `JMP`/`JMP_IF_FALSE` 偏移算错了三次：跳进 else 块中间（优化器的栈模拟直接崩）、回边差 2 字节（块结构错乱）、差 1 字节（死循环）。每次的错误都只差一两条指令的宽度——这正是 03 册"相对偏移比绝对地址好修，**仍要小心**"的注脚，也是**为什么 encode 阶段要用"记录标签地址 → 统一回填"而不是手算**。生产编译器的 emit 侧全是标签制（label + backpatch），本册的 decode/encode 是它的手工镜像。

### decode 的手推：偏移在这里退场

把实测一的片段过一遍 decode（跳转换算用 03 册语义：目标 = 下一条地址 + off）：

```text
输入字节:  … [16] JMP_IF_FALSE 3  [18] GET_LOCAL 2  [20] RETURN …
decode 后（指令下标 9~11）:
  #9  { op:'JMP_IF_FALSE', arg:3, src:16, tgt:12 }   ← 目标字节地址 = 18+3 = 21 → 指令下标 12
  #10 { op:'GET_LOCAL', arg:2, src:18 }
  #11 { op:'RETURN', src:20 }
```

`arg` 里的相对偏移 3 被**立刻换算**成 `tgt: 12`（目标指令的下标）——此后所有 pass 只读 `tgt`，偏移语义彻底退场。这个选择的回报在 encode 时刻结算：pass 4 重算偏移时用同一张换算表的逆过程（`off = 新目标地址 − (本条地址 + 2)`，与 03 册编码侧公式一致），**decode/encode 一对、语义只写一遍**。血泪栏的三次手错，全是在"偏移还是目标"两个心智模型之间切换时发生的——decode 阶段强制归一到"目标"，模型只剩一个，错就没有土壤。

### leader 三规则在实测一上的一次验证

选择二的三规则用实测一的 disasm 验证一遍（规则：入口；跳转目标；跳转/RETURN 的下一条）：

| 规则 | 产生的 leader |
|---|---|
| 规则 1：入口 | ip 0 |
| 规则 2：跳转目标 | ip 21（`JMP_IF_FALSE` 的目标） |
| 规则 3：跳转/RETURN 的下一条 | ip 18（JIF 的下一条）与 ip 21（RETURN 的下一条） |

ip 21 被两条规则同时命中（既是跳转目标又是 RETURN 的下一条）——leader 集合去重后只有三个：**三个基本块 = 主干 [0..15]、then 块 [18..20]、else 块 [21..26]**，恰好是 CFG 的菱形。验证后继：主干的终结是 JIF（双后继 18/21），then/else 的终结是 RETURN（零后继）。块划分是一次 O(n) 扫描，但它是全部四连 pass 的地基——pass 1 的"块内模拟"以块为界清空栈与槽表，**块切错了，模拟从第一个块就错起**。

## 四连 pass

### pass 1：块内常量折叠 + 栈/槽传播

对每个基本块**模拟执行**一遍：栈上每个元素记 `{v, from}`——值（若已知）与**产生它的指令**；局部槽同理记已知值。

- `CONST` 压已知值；`GET_LOCAL s` 若槽已知 → **就地替换成 CONST**（值入池），压已知值；`SET_LOCAL s` 弹栈并记槽值；
- 二元算术/比较：两个操作数都已知且都是 number → **折叠**——把左操作数的 `from` 指令改写成 `CONST 结果`，右操作数与运算指令标 dead（它们是纯供给指令，删除安全）；
- `JMP_IF_FALSE`：条件已知 → 恒真直接删（落穿）、恒假改 `JMP`；**供值的 CONST 也一并 dead**（它只服务于这个已死的分支判断）；
- **不可折叠的边界**：`DIV`/`MOD` 除数为 0 不折——运行时除零错误是**可观察行为**（04 册的规矩，字节码层同样成立）；遇未建模指令（CALL 等）保守清空整个栈与槽表。

一个实现细节藏着经典的求值顺序陷阱：把 `GET_LOCAL` 替换成 `CONST` 时，必须**先取出槽值再改写 `arg`**——`it.arg = pool.length; pool.push(slots.get(it.arg))` 这种一行写法，`it.arg` 已经变成池索引，取到的槽是 `undefined`。本册开发中真实踩中，栈模拟随后把"常量"传播成 undefined，除法折叠悄悄失效——**数据流 pass 的 bug 大多不崩，只是悄悄变笨**。

### 实测一第一块的栈/槽模拟逐步表

把 pass 1 在实测一主路径块上的模拟逐指令走一遍（指令编号对齐下文 disasm 的 ip；栈元素记 `值`，槽记 `槽号 = 值`）：

| 步 | 指令（ip） | 栈（自底向上） | 槽表 | 触发的动作 |
|---|---|---|---|---|
| 1 | `CONST 50`（ip0） | `[50]` | {} | 压已知值 |
| 2 | `SET_LOCAL 1`（ip2） | `[]` | {1=50} | 弹栈记槽 |
| 3 | `GET_LOCAL 1`（ip4） | `[50]` | {1=50} | 槽已知 → **就地替换成 CONST**（值入池） |
| 4 | `CONST 2`（ip6） | `[50, 2]` | {1=50} | 压已知值 |
| 5 | `DIV`（ip8） | `[25]` | {1=50} | 双已知 → **折叠**：ip4 改写为 `CONST 25`，ip6 与本条标 dead |
| 6 | `SET_LOCAL 2`（ip9） | `[]` | {1=50, 2=25} | 弹栈记槽 |

第 3 步的"就地替换"把 `GET_LOCAL` 变成 `CONST 50`——从这一刻起这条指令**供给已知值**，第 5 步的折叠才有原料。逐步表也解释了为什么折叠改写的是**左操作数的 from 指令**（ip4）而不是 DIV 自己：供给链最上游改写一次、下游标 dead 即可，三处动作分别对应"换值、删右源、删运算"——下文逐 pass 对账表里 `DIV(ip8)` 消失的机制细节就在这一步。

### "除零不折"的完整推理链

pass 1 的边界条款值得单独走一遍推理，因为它展示了"可观察行为"如何在字节码层落地。源程序 `let x = 1 / 0;` 直译出 `CONST 1; CONST 0; DIV`——若折叠：mini 的 DIV 语义是"运行时抛错"，编译期算不出结果（**错误也是结果的形态**）。折叠器若把"错误"折成某个默认值或跳过，程序就从"抛错"变成"不抛错"——可观察行为改变，违反 04 册铁律。对照的合法折叠：`50/2` 编译期算出 25，与运行时行为完全一致 → 折叠。判定函数里 `null = 不可折叠` 的返回约定承担的正是这个分支：**折叠规则跟着语言语义走**——若哪天 mini 的 DIV 改成"除零得 NaN"（IEEE 风格），这条边界就消失、`1/0` 变成可折叠。同一条指令、两种语义、两种折叠决策，规则没有自相矛盾。

### pass 2：死存储消除

全函数统计：对每个槽 `s`，若**没有任何活着的 `GET_LOCAL s`**，则所有 `SET_LOCAL s` 改成 `POP`（弹栈保栈平衡，不直接删——喂值指令还压着栈）。槽 `s` 的供值链接下来交给窥孔收尸。

### 死存储判据的两级结构

"槽 s 没有任何活着的 `GET_LOCAL s`"是**槽级**判据；它触发的是改写（SET→POP），**指令级**的清除留给窥孔。为什么不一步到位、直接删 `SET_LOCAL s`？——不行：喂值指令（`CONST x` 或一段供给链）还压着栈，删了 SET，栈深就错了，后续所有栈模拟全错位。`SET → POP` 是**保栈平衡的最小改写**：弹掉喂进来的值、栈深复原、供值指令留在原地；然后窥孔的 `CONST; POP` 模式才有一条固定的"残骸形态"可匹配。两级结构的分工：**槽级判据管"该不该死"，指令级模式管"怎么删干净"**——判据与动作分离，每一步只做一种决定。

### pass 3：窥孔

| 模式 | 替换 | 备注 |
|---|---|---|
| `CONST x; POP` | 全删 | **兜住 pass 2 换出来的 POP 残骸**——喂值链在此整体消失 |
| `NOT; NOT` | 全删 | 双重否定 |
| `JMP L1`，L1 处是 `JMP L2` | 改 `JMP L2` | 跳转 threading |
| `JMP` 的目标是下一条活指令 | 删 | 直落即达 |

### 模式表的顺序敏感：为什么 `CONST; POP` 必须有人收尸

窥孔表四行的排列不是随便的——它们之间有**生产与消费**关系：pass 2 把死存储改成 `POP`，代码里才出现 `CONST x; POP` 残骸；窥孔第一行把残骸整体清除。若把 pass 3 排在 pass 2 之前，第一行永远匹配不到（残骸还没产生），清不掉的 `CONST; POP` 又会让"槽再无人 GET"的判断失效——**顺序错了不是慢，是结果错**。窥孔内部自己也要迭代：`JMP L1`，L1 处是 `JMP L2` 的 threading 可能暴露新的直落模式，直落删除又可能让新的 threading 显形——单遍扫描在链式模式上会漏，实现跑窥孔到自身不动点。这张表与 [04 册](04-经典优化pass.md)窥孔表是同一张的"字节码方言版"，多出来的第一行就是本册管线特有的残骸清理位。

### pass 4：可达性清扫 + encode 重写

从入口块沿 CFG 后继 BFS，不可达块（死分支的尸体）整体标 dead。然后 encode：活指令顺序线性化，**每个跳转按目标指令的新地址重算相对偏移**（`off = 新目标地址 − (本条地址 + 2)`）。

主循环：四连跑完 encode 一轮，新 code 与上一轮逐字节比较，相同则到不动点（[04 册管线](04-经典优化pass.md)的"跑到不动点"，此处以字节码形态复现）。

### encode 重写的算术：删指令之后偏移怎么变

pass 4 的偏移重算公式（`off = 新目标地址 − (本条地址 + 2)`）用一个自足的小例子手推一遍——三条活指令、一条条件跳转：

```text
活指令序列:   #0 CONST 0        #1 JMP_IF_FALSE tgt=#2     #2 RETURN
线性化地址:   0                 2                          4
encode:       JMP_IF_FALSE off = 4 − (2 + 2) = 0；验证：下一条地址 4 + 0 = 4 ✓（指到 RETURN）
```

现在删掉 #0（比如它被死存储链收走）：#1 地址变 0、#2 地址变 2，重算 `off = 2 − (0 + 2) = 0`，验证 `2 + 0 = 2` ✓ 仍指到 RETURN——**目标没变（下标稳定），偏移跟着地址重算**。关键读法：目标用的是"下标"（pass 间稳定），偏移用的是"地址"（线性化后才存在），encode 阶段把下标翻译回地址再算偏移。血泪栏里"差 1 字节"一类错误的常见来源，正是把"目标下标"当"偏移"用——两种模型的宽度不同（2 字节指令）。另一个推论：**"偏移全部不变"与"编码逐字节相同"互为充要**——这正是本册用"逐字节比较"判不动点的合法性依据：偏移语义在 decode/encode 之间是无损往返的。

## 实测一：吃满全部 pass 的例子（27 字节 → 3 字节）

直译 emit（不做任何前端折叠）的 mini 源码：

```text
let n = 50;                 // 槽1
let half = n / 2;           // 槽2
if (1 < 2) { return half } else { return 999 * 1 }
```

优化前（27 字节，真实 disasm 输出）：

```text
   0 CONST          0   ; 50
   2 SET_LOCAL      1
   4 GET_LOCAL      1
   6 CONST          1   ; 2
   8 DIV
   9 SET_LOCAL      2
  11 CONST          2   ; 1
  13 CONST          1   ; 2
  15 LT
  16 JMP_IF_FALSE   3   ; -> 21
  18 GET_LOCAL      2
  20 RETURN
  21 CONST          3   ; 999
  23 CONST          2   ; 1
  25 MUL
  26 RETURN
```

优化后（**3 轮到不动点，3 字节**）：

```text
   0 CONST          8   ; 25
   2 RETURN
```

逐 pass 对账（谁吃了谁）：

| 指令 | 消失原因 |
|---|---|
| `GET_LOCAL 1`(ip4) | pass 1 槽传播：槽1 已知 50 → 替换为 CONST |
| `DIV`(ip8) | pass 1 折叠：50/2 → 25（除数非零合法） |
| `GET_LOCAL 2`(ip18) | pass 1：槽2 已知 25 → 替换为 CONST |
| `CONST 1; CONST 2; LT; JIF`(ip11~17) | pass 1：1<2 恒真 → JIF 删除、供值 CONST 一并 dead |
| else 块(ip21~26) | pass 4：分支死后不可达，整体清扫 |
| `SET_LOCAL 1/2` | pass 2：槽再无人 GET → 改 POP |
| `CONST 50; POP` 等残骸 | pass 3：窥孔 `CONST; POP` 收尸 |

语义对照（教学解释器实跑）：**前 `ret 25`，后 `ret 25`**，动态指令数 12 → 2。

### 数字对账：27、3、12、2 各是怎么来的

四个数字全部能从已保留的 disasm 逐项数出来——**实测报告里的每个数都该能这样回溯**：

```text
27 字节 = 16 条指令的字节数和：
  带操作数（2 字节）11 条：ip 0, 2, 4, 6, 9, 11, 13, 16, 18, 21, 23
  无操作数（1 字节） 5 条：ip 8, 15, 20, 25, 26
  11×2 + 5×1 = 27 ✓（最后一条 RETURN 在 ip26，占 1 字节，总长 27）
```

- **3 字节**：优化产物 2 条指令 = `CONST`(2) + `RETURN`(1) ✓；
- **池索引 8**：原 disasm 只引用池槽 0~3（50、2、1、999），产物却引用槽 8——优化过程按需向池追加了传播/替换产生的新值，具体编号取决于追加顺序，不必对号入座；
- **12 条动态指令** = 实际执行路径上的指令数：`CONST/SET/GET/CONST/DIV/SET/CONST/CONST/LT/JIF/GET/RETURN`（ip0~20 的直落路径，else 块没跑）；
- **2 条动态指令** = 优化产物全量执行一遍。

最有含金量的是第三条：**动态指令数是"解释器真跑了多少条"的计数**，它把"代码行数"与"执行成本"解耦——27 字节里没执行的 else 块（6 字节 3 条）不进动态账。收益分析先看动态指令数再看毫秒数：毫秒受机器/负载/GC 干扰，动态指令数是确定性的结构量。

## 实测二：预期提升但没提升（本阶段的重点案例）

迭代版 `sum(n)`（`while (i > 0) { acc += i; i -= 1 }`）——直觉上"优化器总该做点什么"：

```text
--- 优化前(34 字节) ---            --- 优化后(1 轮,34 字节) ---
   0 CONST 0 ; 0                      (逐字节相同,零变化)
   2 SET_LOCAL 1
   ... 循环体 GET/CONST/ADD/SET ...
  29 JMP -24 ; -> 8
  31 GET_LOCAL 1
  33 RETURN
```

优化器跑了一轮就到不动点——**一条指令都没动**。为什么：

- 循环体里每个操作数都来自上一轮循环（槽值未知），**没有可传播的常量**；
- 每个槽都有活的 GET，没有死存储；
- 跳转目标都是真实的基本块，窥孔无模式可配。

基准数据（`sum(1_000_000)`，教学解释器，3 次取中位，M4 Pro / Node 24）：

```text
优化前 71ms / 动态指令 13,000,010   vs   优化后 69ms / 动态指令 13,000,010
```

差异 2ms 在噪声内，动态指令数**完全相同**——正确结论不是"优化器没用"，而是：

1. **静态优化消灭的是静态指令，解释执行的耗时由动态指令数决定**——sum 的动态指令全部来自循环体，而循环体恰好无可优化；
2. 收益要到别处找：字节码体积（I-cache/加载）、以及**给更强后端铺路**——若 mini 有 JIT，循环体内 `CONST 0/1` 的类型信息、基本块边界、CFG 都是优化器的输入。这正是 esbuild/terser 的处境：minify 对运行速度通常也无感，卖点是体积。

（对照：实测一的 12→2 是**动态指令**层面的真实缩减——因为被优化的代码在热路径之外的主干上。什么程序有收益？**常量配置驱动的分支**、模板生成的重复代码、`DEBUG` 开关——"直译 + 后期统一优化"的管线里，前端越笨，优化器的舞台越大。）

### 什么时候字节码优化才有运行时收益

把"收益要到别处找"展开成一张机会表——静态优化在解释执行世界里能吃到肉的负载形状：

| 负载形状 | 为什么有收益 | 实测对应 |
|---|---|---|
| 常量配置驱动的分支 | 前端直译留下一整片死分支，pass 4 整块清扫 | 实测一（12→2） |
| 模板生成的重复代码 | 生成器不知道哪些插值是常量，优化器统一折叠 | 04 册管线例子的形态 |
| `DEBUG` 开关类代码 | 常量传播把开关变成死边 | 04 册 `debug=false` 死分支 |
| 大量直落的跳转碎片 | 窥孔 threading 收割 | 第五阶段 lowering 产生的冗余跳转 |
| 纯循环热点 | **没有**（除非引入更强的机器） | 实测二（34 字节纹丝不动） |

这张表的正反两半合起来就是选型结论：**解释器 + 静态优化**的组合适合"前端笨、控制流死"的程序；"前端聪明、运行时热"的程序要换机器——寄存器式字节码（[05-第五阶段字节码设计](../05-第五阶段/03-字节码设计.md)的栈式对比）、JIT（[05 册](05-JIT视角.md)）、或 AOT。优化器不改变这个排序，它只是让每个组合在自己的位置上不浪费。

### 格论对读：循环体为什么无可传播

把"一条指令都没动"翻译成 [02 册](02-数据流分析.md)的语言。本册 pass 1 是**块内**模拟——循环体的每个块从头开始，槽表清空，入口处的 `i = 0` 帮不到循环体。即便升级成 02 册的全局 worklist，答案也一样：

```text
入口块:  i = 0            → OUT: 槽 i = const 0
循环头:  meet(入口出边, 回边出边) → 槽 i = meet(const 0, ⊥) = ⊥
                                  槽 acc = ⊥（回边带回的值来自循环内未知计算）
循环体:  操作数槽全 ⊥ → 无折叠、无替换、传播停摆
```

循环携带槽天然是格的 ⊥ 收集器——02 册"菱形汇合"的结论在回边上的重演：**只要有一条来路不知道值，汇合处就必须保守**。所以"零变化"不是管线偷懒，是保守分析的数学下界。突破它需要两类更重的机器：归纳变量分析（把 `i` 识别为归纳变量、按递推关系特化）、或跨迭代的复制传播——都超出四连 pass 的预算，也是静态优化对循环"天然沉默"的普遍原因。对照 [05 册](05-JIT视角.md)：JIT 换了个路数——不猜值，赌观测过的类型，循环恰恰是它最擅长的地方。

### 动态指令数的对账：13,000,010 怎么凑出来

`13,000,010` 的主体能从循环结构估出来：每次迭代的动态指令 = 条件判断 + 循环体 + 回边（`GET_LOCAL`/`CONST`/比较/`JMP_IF_FALSE`，加 `acc` 与 `i` 各自的读-算-写，再加 `JMP`，量级 13 条上下），1,000,000 次迭代 ≈ 13,000,000；余下的个位数是**序言**（`i = 0` 的初始化）与**尾声**（最后一次条件判断 + `GET_LOCAL`/`RETURN`）。对账的意义不在凑齐精确拆分，而在建立直觉：**动态指令数 ≈ 每迭代指令数 × 迭代次数**，所以解释执行的耗时模型是"线性于迭代数 × 单条解释成本"——优化若不削减每迭代的指令数，耗时曲线纹丝不动。71ms/69ms 与 13,000,010/13,000,010 这两组数的一致性（时间差在噪声内、指令数逐条相同）就是"静态优化没碰到循环"的完整证据链。

## 收益分析的方法论：让数字可信的三条纪律

实测一、二合起来演示了正反两个样本，把测量纪律显式化（本册基准数据按这三条产生）：

1. **控制变量优先于秒表**：动态指令数是确定性的结构量（跑多少次都一样），毫秒是随机变量（受机器、负载、GC、CPU 频率影响）。收益分析的第一句话永远说结构量——实测一说"12→2"比说"快了 X ms"硬得多；
2. **中位数 + 多次测量抗噪声**：单次计时可能撞上一次 GC 停顿或调度毛刺；取多次的中位数能滤掉单侧毛刺。但**中位数救不了系统性差异过小的测量**——2ms/71ms 的差异贴着噪声地板，任何统计手段都不能把它升格为结论；
3. **"没提升"要给机制解释，不是给道歉**：实测二的价值在于三条 bullet 把"为什么不动"钉死在格论上（循环携带槽 ⊥）——**负结果只有配上机制才成为知识**。反例是"优化器看起来没用"这种无机制结论，它既不能推广也不能证伪。

三条纪律与 [02 册](02-数据流分析.md)"解的精度由格决定"同构：测量能提升的只是**读数的置信度**，改变不了被测系统的信息上限——循环体里没有常量，测一万次也测不出常量来。

## 与 04 册 TAC 管线的关系

同一对"分析 + 转换"在两种 IR 上的两次实现：TAC 册的 `pipeline()` 是函数式的（每个 pass 独立作用于 Cfg），本册的 pass 共享 `dead` 标记与一次 encode——工程上后者的"标记-清扫-重排"更接近真实字节码优化器（LLVM 后端 MachineFunction 级 pass 也是标记+统一重组）。两册代码可以互相印证：把实测一的例子手工翻成 TAC，跑 04 册的管线，得到的语义结果相同、轮数相同。

### 对拍表：同一个例子在两种 IR 上的形态

把实测一的源码手工翻成 [04 册](04-经典优化pass.md)的 TAC（直译、未优化），两个世界的 pass 各自处理同一份语义：

```text
源:  let n = 50; let half = n / 2; if (1 < 2) { return half } else { return 999 * 1 }

TAC 形态（04 册 IR）:              字节码形态（本册 IR）:
B0: n    = const 50                CONST 50; SET_LOCAL 1
    half = div(n, 2)               GET_LOCAL 1; CONST 2; DIV; SET_LOCAL 2
    t1   = lt(1, 2)                CONST 1; CONST 2; LT
    br t1 → [B1, B2]               JMP_IF_FALSE → else
B1: ret half                       GET_LOCAL 2; RETURN
B2: t2   = mul(999, 1)             CONST 999; CONST 1; MUL
    ret t2                         RETURN
```

对拍的三点读法：

1. **栈机的"槽"对 TAC 的"名字"**：`half` 在 TAC 是显式定值名，在字节码是槽 2——两个世界各自维护"值从哪来"的账本（TAC 用 dest 名，字节码用 from 指针）；
2. **常量路径逐点对应**：TAC 的 `div(n,2)` 折叠 ⇄ 字节码的槽传播 + DIV 折叠；`br t1` 死边 ⇄ `JMP_IF_FALSE` 恒真删除——语义相同、机制同名；
3. **轮数的实测结论一致**（本节开头的断言）：两套 pass 拓扑同构时，"机会链"的长度（折叠→死分支→清扫→收尸）同构，轮数作为链长的度量也同构——轮数不是语义属性，但也不是随机数。

## 调试优化器：逐 pass dump 与语义对拍

优化器的 bug 与解释器不同：它不崩，只是**悄悄变笨或悄悄改错**（pass 1 的求值顺序陷阱是变笨样本；血泪栏的跳转 threading 是改错样本）。两类 bug 对应两件基础设施，写 pass 之前先备好：

1. **逐 pass dump**：每跑完一个 pass 打印一次 disasm（优化前/块划分/pass1/pass2/pass3/pass4/encode 各一份）。定位"哪一步引入的错"靠二分 dump——实测一"逐 pass 对账"表的工程版就是这串 dump；
2. **语义对拍器**：优化前后各跑一遍教学解释器，比较可观察行为（返回值 + print 序列）。它测不出"变笨"，但能拦住"改错"——本册两个实测例子的"语义对照"行就是它的输出形态。

再往上一层是随机程序差分（[第八阶段](../08-第八阶段/02-Babel深度剖析.md)的 Babel 实践会重逢的思想）：随机生成 mini 程序 → 优化 → 前后执行比对，把"手挑例子"升级成"批量检验"。教学项目做到"逐 pass dump + 对拍"已能覆盖绝大多数 bug；差分是工程化门槛，知道有这层即可。
