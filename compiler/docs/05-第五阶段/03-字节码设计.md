# 字节码设计：栈式指令集

> [返回：第五阶段导览](01-导览.md)
> 对应大纲第 2 条。指令集是 mini VM 的"ABI"——设计定下来，编译器（emit 侧）与 VM（执行侧）就各自开发。本册定稿 mini 指令集全集、Chunk 编码与反汇编器。

## 栈式 vs 寄存器机

同一个 `a + b`：

```
;; 栈式（JVM、CPython、早期 V8）        ;; 寄存器式（Lua 5、Dalvik）
GET_LOCAL 0        ; 压 a               ADD R3, R1, R2
GET_LOCAL 1        ; 压 b
ADD                ; 弹两个、压结果
```

| | 栈式 | 寄存器式 |
|---|---|---|
| 指令长度 | 短（操作数隐式在栈顶） | 长（要编码寄存器号） |
| 指令条数 | 多（每值一压一弹） | 少（一条顶三条） |
| 编译器复杂度 | 低（表达式天然映射栈） | 高（要做寄存器分配） |
| 解释执行开销 | 多（每条指令一次栈读写） | 少 |

mini 选**栈式**：编译器简单是决定性因素（教学项目），且与 JVM/CPython/JS 引擎同构——学完直接能对照真实引擎的字节码（V8 `%PrintBytecode` 的输出形态几乎一样）。

### 同一表达式的两版对比

把对比做实——`a * b + c * d`（四个变量在槽 0~3）在两种机器上的编译产物：

```text
;; 栈式（mini 风格）              ;; 寄存器式（Lua 5 风格）
GET_LOCAL 0    ; 栈 [a]           MUL R4, R0, R1
GET_LOCAL 1    ; 栈 [a, b]        MUL R5, R2, R3
MUL            ; 栈 [t1]          ADD R6, R4, R5
GET_LOCAL 2    ; 栈 [t1, c]
GET_LOCAL 3    ; 栈 [t1, c, d]
MUL            ; 栈 [t1, t2]
ADD            ; 栈 [t1+t2]
```

| 指标 | 栈式 | 寄存器式 |
|---|---|---|
| 指令条数 | 7 | 3 |
| 栈深峰值 | 3（左子树值 + 两个右操作数同栈） | ——（无需求值栈） |
| 活跃值存放 | 全在栈上，指令几乎零操作数 | 每值一个寄存器号，每条指令 3 个操作数 |
| 编译期要做的事 | 无（表达式树天然映射） | 虚拟寄存器分配（局部变量与临时值统一编号） |

别急着用"条数"下结论：寄存器版 3 条但每条带 3 个操作数，栈版 7 条几乎零操作数——**谁的字节流更小取决于操作数编码宽度与表达式形状**，不是"条数少就省"。Lua 5.0 的论文正是算过这笔账才转向寄存器式（顺带把"栈管理"的开销从执行路径上删掉）；而 JVM/CPython/wasm 坚守栈式，买的是指令流紧凑与**栈效果可静态验证**（wasm 装载期就靠这一点，见 [Wasm 专题](../11-Wasm专题/03-表达式与结构化控制流.md)）。

真实 VM 的站位一张表：

| VM | 形态 | 备注 |
|---|---|---|
| JVM / .NET CIL / wasm | 栈式 | 公开契约，服务多语言前端 |
| CPython | 栈式 | 解释器即终点（新近版本加自适应特化） |
| Lua 5 / Dalvik(ART) | 寄存器式 | 指令分发开销敏感的场景 |
| V8 Ignition | 寄存器式 + 累加器 | 用一个隐式累加器压缩最常见指令的操作数 |
| mini | 栈式 | 教学取舍：编译器简单第一 |

## Chunk：代码的容器

```ts
export interface FnProto {                    // 一个函数的"原型"：代码 + 元数据
  readonly name: string;
  readonly code: readonly number[];           // 指令流（op + 内联操作数）
  readonly constants: readonly (number | string)[];  // 常量池
  readonly nLocals: number;                   // 局部变量槽位数（参数 + let，checker 已分配）
  readonly upvalueDesc: readonly { name: string; isLocal: boolean; index: number }[];
  readonly start: number;                     // 源码位置（运行时错误回溯用）
}
```

设计要点：

- **常量池**：字面量去重后存表，指令只带索引——`CONST 3` 比"内联 64 位 double"省指令空间；且第七阶段按索引做 CSE/驻留更方便。
- **行号表**：教学版省略，生产实现（如 V8 的 feedback slot、JVM LineNumberTable）必须有——运行时错误没行号等于盲修。mini 用 `FnProto.start` + 简化映射兜底。
- **upvalue 描述表**：闭包捕获的变量"名单"（是否来自直接外层、槽位号）——解释器一册详述。

### FnProto 字段走读：谁写入、谁消费

| 字段 | 谁写入 | 谁消费 | 一句话理由 |
|---|---|---|---|
| `name` | 编译器（FnDecl） | 回溯打印、dis 标题 | 报错至少要说清"哪个函数" |
| `code` | emit | VM 取指 | 指令流本体，op 与内联操作数交错 |
| `constants` | `constIndex` | CONST / CLOSURE / NATIVE | 去重后的字面量与子 FnProto |
| `nLocals` | checker 的槽位分配 | Frame 初始化 locals 数组 | 参数 + let 的槽位总数 |
| `upvalueDesc` | 自由变量分析（第四阶段） | CLOSURE 执行时捕环境 | 捕获名单：来自哪一帧、哪个槽 |
| `start` | 编译器 | RuntimeError 回溯 | 运行时错误定位到源码的最低保障 |

两个值得多看一眼的字段：`nLocals` 是 **Frame 的尺寸说明书**——VM 压帧时按它一次开好槽位数组，执行期不再变长；`upvalueDesc` 的 `isLocal` 区分"捕获来自直接外层的栈槽"（true）与"来自更外层已捕获的 upvalue"（false）——闭包嵌套时沿这条链逐层穿出去，04 册展开。

### 操作数编码：mini 的简化与真实世界的账

mini 的 `code` 是 `number[]`——每个 op 与操作数占一个数组元素，宽窄一视同仁。真实字节码是**字节流**，编码宽窄就是钱：

- **JVM**：操作码 1 字节 + 定宽操作数（按指令取 u8/u16/u32），常规跳转是 16 位偏移（32 位版本另有指令）——紧凑，但"操作数宽度"本身是指令集的一部分；
- **wasm**：指令用 LEB128 变长编码，小数值少占字节——常量与索引大都是小值，变长在代码体积上赚回不少；
- **V8 Ignition**：一字节操作码 + 寄存器号操作数，配一个累加器把"上一个结果"隐式化——寄存器式也照样能压宽度。

mini 用 `number[]` 换掉了这整层复杂度：跳转偏移直接是"元素个数"而不是"字节数"——教学上值回票价；但要记得**真实移植时所有偏移公式都要乘上编码宽度**，这正是"相对偏移"决策在低层语言里必须配一张偏移对拍表的原因。

### 常量池的三个问题

1. **去重的 key 怎么定**：05 册的 `constIndex` 用 `` `${typeof v}:${v}` `` 拼串——`number:1` 与 `string:1` 天然分开；但 `number:0` 会把 `0` 与 `-0` 归并成一项（`String(-0)` 是 `"0"`）——对教学项目无伤，但要知道这是 key 设计的一个隐藏决定；
2. **池子里的东西活得多久**：常量池随 FnProto 存活，FnProto 被 Closure 引用——第六阶段 GC 里它们是"永生倾向"的常驻民（池子可达即整池可达，见 [第六阶段 · 运行时对象模型](../06-第六阶段/02-运行时对象模型.md)）；
3. **索引宽度是合同**：池子多大，索引就得多宽。mini 用一个 JS number 装索引（无压力）；JVM 用 u16 装常量池计数（写超大类文件时的经典报错来源）。**索引宽度定小了以后改不动**——字节码一旦成为契约，改宽度就是破坏兼容。

## mini 指令集全集（v1，34 条）

```
;; ── 常量与局部变量 ──────────────────────────
CONST i          ; 压 constants[i]
GET_LOCAL s      ; 压 locals[s]
SET_LOCAL s      ; 弹出存入 locals[s]
GET_UPVALUE u    ; 压第 u 个捕获变量（经闭包环境）
SET_UPVALUE u

;; ── 算术与比较（number 域）─────────────────
ADD  SUB  MUL  DIV  MOD       ; 弹两个 number，压结果
ADD_STR                         ; 弹两个 string，压拼接（类型分派在编译期！）
NEG                             ; 弹一个，压负值
NOT                             ; bool 取反
LT GT LE GE EQ_EQ NOT_EQ        ; 弹两个，压 bool（number/number 与 string/string）

;; ── 控制流 ────────────────────────────────
JMP off          ; 无条件跳（off 相对当前 ip）
JMP_IF_FALSE off ; 弹一个，假则跳（真值语义只认 bool——checker 保证）
POP              ; 丢弃栈顶

;; ── 函数与调用 ────────────────────────────
CLOSURE f        ; constants[f] 是 FnProto，压 Closure{proto, upvalues}
CALL argc        ; 弹 argc 个参数 + callee，压帧执行，结果落栈
RETURN           ; 栈顶作返回值弹帧
RETURN_UNIT      ; 无返回值路径（checker 保证两态互斥）

;; ── 内建 ──────────────────────────────────
NATIVE n         ; constants[n] 是内建函数引用（print/clock/…）
```

三条设计决策：

1. **类型化指令（ADD 与 ADD_STR 分列）**：`inferredType`（第四阶段注记）让**编译期**就选好指令，VM 运行时零类型分派——这是静态类型语言 VM 的经典红利（JVM 的 iadd/dadd 同理）。动态语言（Lua/Python）只能运行时判型，每条算术指令都要过类型检查。
2. **跳转用相对偏移**：`JMP off` 相对当前 ip——第七阶段做死代码消除搬动指令块时，相对偏移比绝对地址好修（仍然要小心，见 optimizer 的"标签重写"练习）。
3. **EQ_EQ 只写一条**：number/string 各自比较语义塞同一条指令（编译期类型已知，语义无歧义）——指令少一条，文档好写一分。

### 真值语义只认 bool：一条被 checker 兜住的窄约定

`JMP_IF_FALSE` 的注释里藏着一条重要的窄约定：**真值语义只认 bool**——条件位置的值必须是 true/false，数字 0、空串都不作数。这是静态类型的又一处红利：checker 在类型检查阶段就拒绝"把 number 当条件"，VM 的 JMP_IF_FALSE 于是可以不查任何真值转换表。

对照动态语言：JS 的 truthy/falsy（0、""、null 都算假）与 Python 的 truthy（空容器算假）都要在**每次条件跳转的执行路径上**做真值归约——语义灵活，代价摊进了最热的指令。mini 把这层灵活让渡给类型系统，换来条件跳转的零分派——"语义放在编译期还是执行期"是指令集设计反复出现的主题（ADD 与 ADD_STR 分列是同一主题的另一处）。

### EQ_EQ 的语义矩阵

一条指令、两种类型域，语义矩阵其实很小：

| 编译期类型 | EQ_EQ 的语义 | 不可能出现（checker 拒绝） |
|---|---|---|
| number / number | 数值比较 | number 与 string 比 |
| string / string | 逐字符比较（或驻留后指针比较，见第六阶段内联化讨论） | —— |
| bool / bool | 同值比较 | —— |

矩阵第三列是 EQ_EQ 敢只写一条的全部底气：**混类型比较在编译期就报错了**，运行时永远只见同域比较。动态语言做 `==` 要在运行时处理"任何类型 vs 任何类型"的完整矩阵——那是一整页规则表，mini 用类型系统把它压缩成三行。

### 新增一条指令的检查单

34 条不是终点（数组指令、循环糖都可能进后续版本），但指令表每长一格，四处地方要同步长：

1. **opcode 枚举与 OP_INFO**：名称 + 操作数字节数（反汇编器吃这张表）；
2. **VM 的 case**：栈效果与速查表一致，弹压配平；
3. **emit 侧的降级规则**：哪个 AST 形态会选中它、编译期怎么判型；
4. **速查表与 dis 测试**：语义表加一行，golden 快照重冻。

四处少一处，bug 会以"反汇编读不通"、"栈失衡"、"该选它没选它"三种面貌分别出现——**新增指令的成本不在实现，在四处同步**。这也是指令集"宁少勿多"的工程理由：每条指令都是长期维护的公共面积。

### 指令语义速查表（栈效果视角）

34 条按"栈怎么变"过一遍——`[a, b] → [r]` 读作"弹两个、压一个"：

| 指令 | 栈效果 | 语义要点 |
|---|---|---|
| CONST i | `[] → [c]` | 从常量池取，不动池子 |
| GET_LOCAL s | `[] → [v]` | 读当前帧槽位（只读，栈不弹） |
| SET_LOCAL s | `[v] → []` | 弹出写入槽位——let 与赋值共用 |
| GET/SET_UPVALUE u | 同上，经闭包盒 | open 读栈槽 / closed 读盒子（04 册） |
| ADD SUB MUL DIV MOD | `[a, b] → [r]` | **先弹的是右操作数**（压栈次序：左先右后） |
| ADD_STR | `[s1, s2] → [s]` | 编译期已判 string，运行时零分派 |
| NEG / NOT | `[v] → [r]` | 一元：弹一压一 |
| LT GT LE GE EQ_EQ NOT_EQ | `[a, b] → [bool]` | 结果只压 true/false（真值语义只认 bool） |
| JMP off | 不弹不压 | 相对偏移，只有 ip 变化 |
| JMP_IF_FALSE off | `[v] → []` | 弹出判假；假才跳——条件被消费 |
| POP | `[v] → []` | 表达式语句的"收据" |
| CLOSURE f | `[] → [Closure]` | 按 upvalueDesc 当场捕环境 |
| CALL argc | `[callee, a1..aN] → [r]` | 压帧或回调 native（04 册约定） |
| RETURN | `[v] → （弹帧）` | v 落到调用者栈顶 |
| RETURN_UNIT | `[] → （弹帧）` | 无值路径，调用者不收 |
| NATIVE n | `[] → [Native]` | 内建引用入栈，随后照常 CALL |

这张表建议打印出来贴在屏幕边——写 VM 时九成的 bug 是"以为弹了两个、实际弹了一个"。特别盯住 ADD 家族的**操作数次序**：emit 先左后右，执行先弹右后弹左——次序弹错，`a - b` 会算成 `b - a` 且**不报错**（语义悄悄反转）。

### `2 * 3 + 1` 的逐指令推演

先在这里演一遍（常量池 [2, 3, 1]，emit 先左后右）：

| 步 | ip | 指令 | 执行后的栈 |
|---|---|---|---|
| 1 | 0 | CONST 0 | [2] |
| 2 | 2 | CONST 1 | [2, 3] |
| 3 | 4 | MUL | [6] |
| 4 | 5 | CONST 2 | [6, 1] |
| 5 | 7 | ADD | [7] |

5 条指令、栈深峰值 2。同一表达式的"兄弟" `1 + 2 * 3` 在同样的先左后右次序下峰值就不是 2 了：先压 1 再编右子树，CONST 连发三个才轮到 MUL——峰值 3。**栈深峰值 = 表达式形状 × 操作数发射次序**，两种次序都合法、结果都是 7，但峰值不同（05 册的实现是先左后右，读者可拿两种次序各推一遍对比）。这件事的工程意义在装载期验证：每条指令的栈效果静态可推，"运行期弹空栈"就能在执行前被证明不可能（wasm 验证正是这么做的，见 [Wasm 专题](../11-Wasm专题/03-表达式与结构化控制流.md)）；编译期顺手把峰值算出来，VM 还可以预开精确大小的求值栈——栈式机少有人提的第二个红利。

## 反汇编器：第一个"调试器"

```ts
export function disassemble(fn: FnProto): string {
  const lines: string[] = [];
  let ip = 0;
  while (ip < fn.code.length) {
    const op = fn.code[ip] as OpCode;
    const [name, arity] = OP_INFO[op];            // 名称 + 操作数字节数
    const args = fn.code.slice(ip + 1, ip + 1 + arity);
    lines.push(`${String(ip).padStart(4)} ${name.padEnd(14)} ${args.join(' ')}`);
    ip += 1 + arity;
  }
  return lines.join('\n');
}
```

`fib` 的输出长这样（读字节码是本阶段的"内功"，每个 bug 都该先看它）：

```
   0 CLOSURE        0        ; fib
   2 SET_LOCAL      0
   4 GET_LOCAL      0
   6 CONST          1        ; 25
   8 CALL           1
  10 RETURN
```

### 逐行读一遍这段反汇编

这段是**顶层 script 的 FnProto**（不是 fib 本体）——它干的事是"定义 fib 并调用"：

| ip | 指令 | 在做什么 |
|---|---|---|
| 0 | CLOSURE 0 | 常量池 0 号是 fib 的 FnProto → 压 Closure{proto, upvalues} |
| 2 | SET_LOCAL 0 | 函数名绑定：存进脚本帧槽 0 |
| 4 | GET_LOCAL 0 | 取出函数值压栈（CALL 的 callee 位） |
| 6 | CONST 1 | 常量池 1 号是 25 → 压参数 |
| 8 | CALL 1 | 一参一 callee → 压帧执行 fib |
| 10 | RETURN | fib 返回 75025 落栈后，脚本帧收尾 |

两个读法要点：其一，**函数名的绑定就是一条 SET_LOCAL**（脚本槽 0 存 fib 自己）——fib 体内对 `fib` 的自引用经 GET_UPVALUE 指回脚本帧的这个槽（`upvalueDesc` 登记的是"直接外层、槽 0"），取回函数值再照常 CALL——**递归在字节码层没有任何特殊指令**，就是"闭包取自己"；其二，`CALL 1` 的操作数是**参数个数**而不是函数——栈上 callee 正好压着 1 个参数，约定见 04 册。

读反汇编的三步固定动作：先看 CLOSURE/CONST 的池索引对不对（emit 侧 bug 多半在这）；再看 JMP/JMP_IF_FALSE 的偏移与落点（回填差一在这里现形）；最后脑内跑栈、核对每条语句前后深度一致（栈平衡不变式）。

工程习惯：`mini dis fib.mini` 命令打印全部函数的字节码 + 常量池——**"编译器以为它生成了什么"与"VM 实际执行了什么"的对照镜**，编译期 bug（emit 顺序错）与运行期 bug（栈失衡）靠它分家。

### 字节码快照：给优化器立基准

dis 的输出还有一个远期用途：**冻结成 golden 文件**。05 册的验收清单里有"三件套的字节码 golden 文件冻结"——第七阶段优化器每改写一轮指令流，都拿新 dis 与 golden 对比：

- 输出行为不变 + 指令流变了 → 优化生效的正常证据；
- 输出行为变了 → 优化改坏了语义，立刻回退。

字节码快照把"优化不改语义"从一句口号变成可 diff 的事实——这是栈式字节码"线性、可重写"两条 IR 准则的直接红利（02 册）。

## 装载期验证：字节码为什么能当契约

栈式字节码有一个寄存器机难以匹配的性质：**栈效果可以静态推演**——每条指令弹几压几是确定的，于是"拿到一段字节码、不执行它"就能验证：

- **栈不会弹穿**：模拟执行一遍，任何时刻栈深不为负——弹空栈的字节码在装载期就拒绝；
- **跳转不落半条指令**：跳转目标必须是某条指令的起点（落进操作数中间 = 把数据当代码执行）；
- **类型一致性**：JVM 的验证器推演每个程序点"栈上应该是什么类型"（配合记录汇合点状态的元数据），wasm 验证对每个操作推演值类型栈（i32/f64……）。

这就是字节码能当**公开契约**的深层原因：Java/Kotlin/Scala、C/Rust→wasm 的前端可以互不信任地共享同一个字节码层，因为装载期验证把"畸形字节码"挡在执行之前。mini 的取舍是**信任自家 checker**（编译期已保证类型与栈平衡，VM 不设验证器）——教学项目的合理简化，但要知道省掉了什么：把 mini 字节码交给"别人手写的" emit，一个栈失衡 bug 就能直接崩穿解释器。第七阶段会重新撞上这个问题——**优化器改写指令流，恰恰是"字节码来自不可信来源"的最现实场景**，所以 pass 的正确性论证要按验证器的标准做（[第七阶段 · 经典优化 pass](../07-第七阶段/04-经典优化pass.md)）。

## 常见误区

- **"栈式机字节码一定更省空间"**——不一定：条数多但操作数窄 vs 条数少但操作数宽，谁赢取决于编码宽度与表达式形状（见两版对比的账）；
- **"寄存器机的寄存器 = 真实 CPU 寄存器"**——Lua/Dalvik/Ignition 的"寄存器"是**栈帧槽位的别名**；解释执行时它只是数组下标，物理寄存器分配是后端 JIT 的事；
- **"常量池去重只是省内存"**——它同时是优化素材（第七阶段按索引做 CSE）与语义决定（驻留与 GC 根），见常量池三问；
- **"跳转用绝对地址更直观"**——绝对地址在指令块搬动后全部失效；相对偏移也要重算，但"块内相对关系"不变，重写范围小——第七阶段死代码消除搬动指令块时，这笔账才显出来；
- **"操作数次序是小事"**——ADD 先弹右后弹左，`a - b` 弹反了就变成 `b - a` 且不报错。次序是 ABI 的一部分：文档 + 测试双保险；
- **"34 条是能力上限"**——指令集按需生长（数组指令、循环糖都可能进后续版本），但每加一条都要回答三件事：栈效果是什么、checker 怎么判型、反汇编怎么打印；
- **"装载期验证可省，反正编译器正确"**——字节码一旦成为契约（被第三方生成、被优化器改写），验证就是安全的最后一道闸；mini 省掉它省的是实现量，不是这个观念；
- **"反汇编器只是个打印函数"**——它是 emit 与 VM 之间唯一的仲裁者：没有它，跳转差一与栈失衡都只能靠断点单步硬猜。dis 的可读性（列宽、池内联注释）直接决定调试效率；
- **"golden 快照只对优化器有用"**——它同样是本阶段的回归护栏：每拼装一个新特性（CALL、CLOSURE、native），先确认已有快照不变，再冻新的。

## 工业对照：字节码在真实引擎里的一生

把 mini 的 Chunk 对到四家真实产物，各自的"字节码 + 元数据"清单：

- **JVM class 文件**：常量池 + 每个方法的 `Code` 属性（`max_stack`、`max_locals`、指令流、`LineNumberTable`）。对照 mini 的 FnProto：`max_stack` ↔ 编译期算出的栈深峰值（见逐指令推演的红利），`max_locals` ↔ `nLocals`，行号表 ↔ mini 用 `start` 兜底的那层信息。**验证器在装载期吃这份数据**（上一节）；
- **CPython 的 code 对象**：`co_code`（指令流）、`co_consts`（常量）、`co_names`（名字表）、`co_varnames`/`co_nlocals`（局部变量）——与 FnProto 的字段几乎一一对应，只是它运行时判型、指令全集里没有"类型化分派"的 ADD/ADD_STR 之分；
- **V8**：Ignition 生成字节码，每个函数还配一个 **feedback vector**——按调用点记录"这里见过什么类型/什么形状"，是解释器收集运行时信息、JIT 消费运行时信息的通道（第七阶段内联缓存的前置）。mini 没有这层：类型编译期已知，不需要运行时反馈；
- **wasm 模块**：type/function/code/memory/export 等分节组成，code 节里是函数体的栈式指令流，装载期统一验证。mini→wasm 的第二个后端（[Wasm 专题 · 实践-mini到Wasm](../11-Wasm专题/06-实践-mini到Wasm.md)）会把 34 条指令逐条映射过去。

一张表收拢"谁的字节码负责什么"：

| | 字节码的角色 | 元数据配了什么 | 谁验证它 |
|---|---|---|---|
| JVM | 公开契约（多语言目标） | Code 属性、行号表、栈图状态 | 装载期验证器 |
| CPython | 解释器的私有输入 | code 对象字段 | 无（信任自家编译器） |
| V8 | 解释执行 + JIT 的源 | feedback vector | 信任自家编译器 |
| wasm | 公开契约（多语言目标） | 类型节、导入导出节 | 装载期验证（规范强制） |
| mini | VM 的私有输入 | FnProto 元数据 | 无（信任 checker） |

读法：**字节码是不是"契约"，决定验证器在不在**——JVM 与 wasm 是公开契约，验证器是规范的一部分；CPython、V8、mini 是私有输入，验证可以省。两条路线 mini 都见过一面：现在站在"私有输入"这一列，第七阶段做优化时就要按"验证器标准"自律。
