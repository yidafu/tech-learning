# 字节码设计：栈式指令集

> [返回：第五阶段导览](01-导览.md)
> 对应大纲第 2 条。指令集是 mini VM 的"ABI"——设计定下来，编译器（emit 侧）与 VM（执行侧）就各自开发。本册定稿 mini 指令集全集、Chunk 编码与反汇编器。

## 栈式 vs 寄存器机

同一个 `a + b`：

```
;; 栈式（JVM、CPython、早期 V8）        ;; 寄存器式（Lua 5、Dalvik）
GET_LOCAL 0        ; 压 a               ADD R3, R1, R2
GET_LOCAL 1        ; 压 b
ADD                ; 弹两个、压结果
```

| | 栈式 | 寄存器式 |
|---|---|---|
| 指令长度 | 短（操作数隐式在栈顶） | 长（要编码寄存器号） |
| 指令条数 | 多（每值一压一弹） | 少（一条顶三条） |
| 编译器复杂度 | 低（表达式天然映射栈） | 高（要做寄存器分配） |
| 解释执行开销 | 多（每条指令一次栈读写） | 少 |

mini 选**栈式**：编译器简单是决定性因素（教学项目），且与 JVM/CPython/JS 引擎同构——学完直接能对照真实引擎的字节码（V8 `%PrintBytecode` 的输出形态几乎一样）。

## Chunk：代码的容器

```ts
export interface FnProto {                    // 一个函数的"原型"：代码 + 元数据
  readonly name: string;
  readonly code: readonly number[];           // 指令流（op + 内联操作数）
  readonly constants: readonly (number | string)[];  // 常量池
  readonly nLocals: number;                   // 局部变量槽位数（参数 + let，checker 已分配）
  readonly upvalueDesc: readonly { name: string; isLocal: boolean; index: number }[];
  readonly start: number;                     // 源码位置（运行时错误回溯用）
}
```

设计要点：

- **常量池**：字面量去重后存表，指令只带索引——`CONST 3` 比"内联 64 位 double"省指令空间；且第七阶段按索引做 CSE/驻留更方便。
- **行号表**：教学版省略，生产实现（如 V8 的 feedback slot、JVM LineNumberTable）必须有——运行时错误没行号等于盲修。mini 用 `FnProto.start` + 简化映射兜底。
- **upvalue 描述表**：闭包捕获的变量"名单"（是否来自直接外层、槽位号）——解释器一册详述。

## mini 指令集全集（v1，34 条）

```
;; ── 常量与局部变量 ──────────────────────────
CONST i          ; 压 constants[i]
GET_LOCAL s      ; 压 locals[s]
SET_LOCAL s      ; 弹出存入 locals[s]
GET_UPVALUE u    ; 压第 u 个捕获变量（经闭包环境）
SET_UPVALUE u

;; ── 算术与比较（number 域）─────────────────
ADD  SUB  MUL  DIV  MOD       ; 弹两个 number，压结果
ADD_STR                         ; 弹两个 string，压拼接（类型分派在编译期！）
NEG                             ; 弹一个，压负值
NOT                             ; bool 取反
LT GT LE GE EQ_EQ NOT_EQ        ; 弹两个，压 bool（number/number 与 string/string）

;; ── 控制流 ────────────────────────────────
JMP off          ; 无条件跳（off 相对当前 ip）
JMP_IF_FALSE off ; 弹一个，假则跳（真值语义只认 bool——checker 保证）
POP              ; 丢弃栈顶

;; ── 函数与调用 ────────────────────────────
CLOSURE f        ; constants[f] 是 FnProto，压 Closure{proto, upvalues}
CALL argc        ; 弹 argc 个参数 + callee，压帧执行，结果落栈
RETURN           ; 栈顶作返回值弹帧
RETURN_UNIT      ; 无返回值路径（checker 保证两态互斥）

;; ── 内建 ──────────────────────────────────
NATIVE n         ; constants[n] 是内建函数引用（print/clock/…）
```

三条设计决策：

1. **类型化指令（ADD 与 ADD_STR 分列）**：`inferredType`（第四阶段注记）让**编译期**就选好指令，VM 运行时零类型分派——这是静态类型语言 VM 的经典红利（JVM 的 iadd/dadd 同理）。动态语言（Lua/Python）只能运行时判型，每条算术指令都要过类型检查。
2. **跳转用相对偏移**：`JMP off` 相对当前 ip——第七阶段做死代码消除搬动指令块时，相对偏移比绝对地址好修（仍然要小心，见 optimizer 的"标签重写"练习）。
3. **EQ_EQ 只写一条**：number/string 各自比较语义塞同一条指令（编译期类型已知，语义无歧义）——指令少一条，文档好写一分。

## 反汇编器：第一个"调试器"

```ts
export function disassemble(fn: FnProto): string {
  const lines: string[] = [];
  let ip = 0;
  while (ip < fn.code.length) {
    const op = fn.code[ip] as OpCode;
    const [name, arity] = OP_INFO[op];            // 名称 + 操作数字节数
    const args = fn.code.slice(ip + 1, ip + 1 + arity);
    lines.push(`${String(ip).padStart(4)} ${name.padEnd(14)} ${args.join(' ')}`);
    ip += 1 + arity;
  }
  return lines.join('\n');
}
```

`fib` 的输出长这样（读字节码是本阶段的"内功"，每个 bug 都该先看它）：

```
   0 CLOSURE        0        ; fib
   2 SET_LOCAL      0
   4 GET_LOCAL      0
   6 CONST          1        ; 25
   8 CALL           1
  10 RETURN
```

工程习惯：`mini dis fib.mini` 命令打印全部函数的字节码 + 常量池——**"编译器以为它生成了什么"与"VM 实际执行了什么"的对照镜**，编译期 bug（emit 顺序错）与运行期 bug（栈失衡）靠它分家。

## 自测

1. 手写 `1 + 2 * 3` 的栈式字节码（5 条），并验证栈深峰值是 2。
2. 为什么 `JMP_IF_FALSE` 弹栈而 `JMP` 不弹？短路求值的字节码（上册）依赖这个差异的哪一点？
3. `GET_LOCAL` 与 `GET_UPVALUE` 的语义差异一句话说清——谁在什么场景用后者？
4. 把 `ADD` 改成"运行时判型的通用 ADD"要付出什么？动态语言 VM 每条算术指令多花的是什么成本？
