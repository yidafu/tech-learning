### 2.2 环境变量解析：envNumber 的三个陷阱

开关的解析不写在 demo 里，而是收进 core 的工具函数（逐字摘录 `src/core/config.ts`）：

```ts
/** 读一个可选的数字环境变量；未设置、空串或不是有限数字时返回 fallback。 */
export function envNumber(raw: string | undefined, fallback: number): number {
  if (raw === undefined || raw.trim() === "") return fallback;
  const n = Number(raw);
  return Number.isFinite(n) ? n : fallback;
}
```

五行代码防了三个实打实的陷阱，`config.test.ts` 把它们各测了一遍（本机 `npx vitest run` 实跑：`src/core/config.test.ts (7 tests)` 全绿）：

| 陷阱 | envNumber 的对策 | 测试名（逐字） |
|---|---|---|
| 未设置（undefined） | 直接返回 fallback | `未设置时返回 fallback` |
| 空串——`Number("") === 0`，会把「没设」误读成「设了 0」 | trim 后判空串 | `非法值回退 fallback`（断言里有注释点破这个陷阱） |
| 非数字 / NaN / Infinity | `Number.isFinite` 收口 | 同上 |

demo 侧的调用就一行干净：`const targetFps = envNumber(process.env.MINI_GUI_FPS, 60);`——「环境变量 = 字符串」的脏活全部封装在 core，apps 只拿类型安全的数字。这个函数也是「core 无 raylib 依赖」的第一个受益者：它的测试不需要窗口。

### 2.3 两个驱动常量与往返折叠

实验设计浓缩在两个常量与一个函数里（逐字摘录）：

```ts
// 两种驱动方式的对照：
//   delta 驱动：速度以「像素/秒」定义，位移 = 速度 × 本帧耗时
//   逐帧驱动：速度以「像素/帧」定义，位移与帧率绑死（反例）
const SPEED_PX_PER_SEC = 120;
const STEP_PX_PER_FRAME = 2; // 只有恰好 60fps 时才等价于 120 px/s

const TRACK_LEFT = 60;
const TRACK_LEN = WIDTH - 120;
```

`120 px/s` 与 `2 px/frame` 是**故意调成 60fps 下等价**的一对——「看起来都对」的假象只在 60fps 成立，§4 的实验正是要打破它。

路程到坐标的折叠用 `pingPong`（逐字摘录 `src/core/config.ts`）：

```ts
/** 把单调增长的路程折成 [left, left+len] 内的往返坐标（demo 动画用）。 */
export function pingPong(distance: number, left: number, len: number): number {
  if (len <= 0) return left;
  const cycle = distance % (len * 2);
  return left + (cycle <= len ? cycle : len * 2 - cycle);
}
```

读法：路程对 `2*len` 取模得周期相位，前半周期正向走、后半周期反向折返。四个测试各钉一个性质：`前半程线性增长`、`后半程折返`、`循环周期为 2*len`、`len<=0 时不发散`——最后一条是防御：len 非正时返回起点而不是发散，让 demo 在窗口极窄时也不会画出轨道外。**注意 pingPong 只影响「画在哪」，不影响路程累计**——`deltaDistance`/`frameDistance` 是单调递增的原始数据，折返只是显示层的事。这让退出统计（§7）报告的「总路程」有唯一确定的含义。

### 2.4 可变状态：八个累积器

主循环前集中声明了全部可变状态（逐字摘录）：

```ts
let frames = 0;
let elapsed = 0;
let deltaDistance = 0;
let frameDistance = 0;
let maxDt = 0;

let playerX = WIDTH / 2;
let playerY = 330;
let clicks = 0;
let lastKey = 0;
```

前五个是**测量仪器**（帧数、总耗时、两条路程、最大帧间隔），后四个是**业务状态**（玩家位置、点击计数、最后键码）。分开声明不是排版洁癖：测量仪器永远只增不改语义，业务状态每帧被更新逻辑改写——第八阶段做事件回放测试时，「可回放」的前提就是这两类状态能从回放中重建，而测量仪器不能（也不需要）。

## 3. 帧循环四步

`01-window.ts` 的主循环把每帧切成固定的四步（顺序是铁律）：

```ts
while (!windowShouldClose()) {
  const dt = getFrameTime();      // ① 时间：先取本帧 delta
  // ② 输入：轮询鼠标键盘的「现在」与「本帧边沿」
  const mouse = getMousePosition();
  if (isMouseButtonPressed(MOUSE_BUTTON_LEFT)) clicks += 1;
  // ③ 更新：用 dt 推进所有状态（唯一允许改状态的地方）
  deltaDistance += SPEED_PX_PER_SEC * dt;
  // ④ 绘制：begin/endDrawing 之间只读状态画图
  beginDrawing();
  clearBackground(RAYWHITE);
  drawCircle(pingPong(deltaDistance, TRACK_LEFT, TRACK_LEN), 120, 14, SKYBLUE);
  endDrawing();
}
```

为什么顺序是铁律：

- **输入在更新前**——本帧的状态变化能立刻反映到画面，不会延迟一帧
- **更新在绘制前**——绘制代码只读状态（纯函数口味），想加「帧率无关的重放测试」（第八阶段）时这是前提
- **绘制区只画不算**——`begin/endDrawing` 之间混入重逻辑会拖长批处理提交，帧时间立刻变差（第 4 册 §3 的批模型）

真实代码里四步带注释分段，且第一步还兼做测量（逐字摘录）：

```ts
  // ---- 1. 时间 ----
  const dt = getFrameTime();
  frames += 1;
  elapsed += dt;
  if (dt > maxDt) maxDt = dt;
```

注意 `dt` 的语义：**上一帧的耗时**。首帧它覆盖的是「窗口创建到第一圈循环」的时间，天然偏大——这就是 §4 里 maxDt 尖峰的来源之一。循环末尾还有回归出口（逐字摘录）：

```ts
  if (exitAfterSeconds > 0 && elapsed >= exitAfterSeconds) break;
```

注意 break 在 `endDrawing()` 之后：退出前的最后一帧是完整的（截图取证依赖这一点，§6）。

把四步与第 2 册的一帧图对齐，可以看到这个最小骨架离「框架」还差什么：

```text
① 时间   dt 采样               ← E 层的帧计时，框架时代的「动画系统」要接管它
② 输入   原始轮询               ← 框架时代要升级成「事件总线」（第五阶段）
③ 更新   直接改 let 变量        ← 框架时代要升级成「UI = f(state)」（第七阶段）
④ 绘制   每帧全量手画           ← 框架时代要升级成「脏标记 + 局部重绘」（第六阶段）
```

四步的顺序不变，每一步的「实现浓度」逐阶段升级——这也是为什么本册值得逐行读：它是后面七个阶段的对照组，每长出一层机制，都回来问一句「01-window.ts 里这段现在归谁管了」。

## 4. delta time：帧率无关的动画

demo 里有两个球在同一屏做对照运动：

```ts
deltaDistance += SPEED_PX_PER_SEC * dt;  // 位移 = 速度 × 时间
frameDistance += STEP_PX_PER_FRAME;      // 位移 = 步长 × 帧数
```

**实跑：同样跑约 2 秒，换三档目标帧率**（`MINI_GUI_SECONDS=2`，输出原文）：

```text
MINI_GUI_FPS=30 : frames=61   elapsed=2.027s avgFps=30.1  maxDt=60.09ms
                  deltaDistance=243.2px frameDistance=122.0px
MINI_GUI_FPS=60 : frames=116  elapsed=2.012s avgFps=57.7  maxDt=91.27ms
                  deltaDistance=241.4px frameDistance=232.0px
MINI_GUI_FPS=120: frames=225  elapsed=2.006s avgFps=112.2 maxDt=58.17ms
                  deltaDistance=240.7px frameDistance=450.0px
```

整理成表（距离单位 px），并附手工验算列——三组数字都能从定义直接推出来：

| targetFps | 实际 avgFps | frames | delta 路程 | 验算 120×elapsed | 逐帧路程 | 验算 2×frames |
|---|---|---|---|---|---|---|
| 30 | 30.1 | 61 | **243.2** | 120×2.027=243.24 | 122.0 | 2×61=122 |
| 60 | 57.7 | 116 | **241.4** | 120×2.012=241.44 | 232.0 | 2×116=232 |
| 120 | 112.2 | 225 | **240.7** | 120×2.006=240.72 | 450.0 | 2×225=450 |

验算全对上（avgFps 同理：61/2.027=30.09≈30.1、116/2.012=57.7、225/2.006=112.2）——**实验数字不是碰巧的，是定义的可复现**：delta 路程 = 速度 × 实际耗时，逐帧路程 = 步长 × 帧数。这也是回归断言的写法指南：对「定义可推导的量」用紧容差，对「调度相关的量」（如 frames 精确值）用宽容差。

三个读数：

1. **delta 路程 ≈ 241~243px 稳如磐石**（理论值 = 速度 120 × 实际耗时 2.0x 秒；波动全部来自退出时间的零头）。帧率砍半路程不变——这就是「帧率无关」。
2. **逐帧路程 122 → 450px**：帧率越高跑得越快，450/122 ≈ 3.7 倍的漂移。60fps 下碰巧「看起来对」的游戏（STEP=2 恰好在 60fps 等价 120px/s），放到高刷屏上就是快进。
3. **avgFps 追不上 targetFps**（57.7/60、112.2/120）：软件帧限制是「等到至少 16.67ms」而非精确等待，加上 vsync 与调度抖动（macOS 还隔着一层 GL→Metal 兼容，第 4 册 §2），实际帧率永远略低于目标——第六阶段做帧预算时要按这个现实校准。三档的亏空比例分别是 3.8%、4.6%、6.5%，帧率越高亏空越明显。

> 顺带解释 `maxDt=91.27ms` 的尖峰：首帧包含窗口创建、默认字体上传等一次性成本（第 4 册 §2 的启动日志就是清单）。动画逻辑对此要有心理预期——**用 dt 驱动的动画天然免疫这个尖峰**（首帧 dt 大，位移一步到位，不会「卡住」）。另一个反直觉细节：maxDt 最大的一档反而是 60fps（91.27ms），不是 30fps——调度抖动是随机事件，2 秒窗口内谁撞上首帧+系统抖动谁大，与目标帧率无单调关系。

## 5. 输入反馈：轮询的三种问法

demo 把鼠标键盘反馈画在屏上，也把三种问法用全了（输入段逐字摘录）：

```ts
  // ---- 2. 输入（轮询：每帧主动去问「现在是什么状态」）----
  const mouse = getMousePosition();
  const leftDown = isMouseButtonDown(MOUSE_BUTTON_LEFT);
  if (isMouseButtonPressed(MOUSE_BUTTON_LEFT)) clicks += 1;
  const key = getKeyPressed();
  if (key !== 0) lastKey = key;
```

| 问法 | demo 用途 | 语义 |
|---|---|---|
| `isMouseButtonDown` | 按住时实心圆，松开空心圆 | **状态**：现在是否按着 |
| `isMouseButtonPressed` | 计数 `clicks` | **边沿**：本帧是否刚按下 |
| `isKeyDown(KEY_W)` | WASD 移动方块（`move = 200 * dt`） | 状态流：持续按键 |
| `getKeyPressed()` | 记录 `lastKey` | **键码流**：本帧任意按键（0=无） |

更新段的键盘部分（逐字摘录）：

```ts
  const move = 200 * dt;
  if (isKeyDown(KEY_A)) playerX -= move;
  if (isKeyDown(KEY_D)) playerX += move;
  if (isKeyDown(KEY_W)) playerY -= move;
  if (isKeyDown(KEY_S)) playerY += move;
```

三个细节：

- WASD 移动用 `200 * dt`：又是 delta 驱动，键盘手感不会随帧率变化——与 §4 同一条物理公式（位移 = 速度 × 时间）的第二处应用；斜向移动（同时按 W 和 D）每帧走 √2 倍距离，这种「速度向量未归一」的小瑕疵先记下，第四阶段做布局无关的输入语义时顺手修。
- `leftDown` 在输入段采样、在绘制段使用（画实心还是空心圆）——状态语义幂等，跨段持有是安全的；`isMouseButtonPressed` 的边沿只在输入段消费一次（§4 第 2 册的「边沿恰好消费一次」纪律）。
- `getKeyPressed()` 的 0 是「无」的哨兵值，`if (key !== 0)` 把它挡在外面；它是第五阶段「键盘事件规范化」的原始素材（keycode → 事件对象的翻译工作那时做）。

## 7. 回归出口：统计打印

demo 退出时打印两行统计，这是「跑起来才算」文化的落点——所有后续阶段的 demo 都遵守这个约定（逐字摘录）：

```ts
console.log(
  `[01-window] targetFps=${targetFps} frames=${frames} elapsed=${elapsed.toFixed(3)}s ` +
    `avgFps=${(frames / elapsed).toFixed(1)} maxDt=${(maxDt * 1000).toFixed(2)}ms`,
);
console.log(
  `[01-window] deltaDistance=${deltaDistance.toFixed(1)}px frameDistance=${frameDistance.toFixed(1)}px`,
);
```

`console.log` 在原生进程里直通 stdout（ScriptC 支持），所以 demo 的行为断言可以完全走 shell：跑 2 秒、grep 输出、对数字。本册 §4 的三组数据就是这么采的（`MINI_GUI_SECONDS=2 MINI_GUI_FPS=30/60/120` 各跑一次）。

两行输出按「确定性」分了类，写回归断言时照此选容差：

| 字段 | 可否精断 | 理由 |
|---|---|---|
| `targetFps` | 是 | 你自己设的输入 |
| `frames` / `elapsed` | 紧容差 | 定义可推导（elapsed ≈ SECONDS + 最后一帧零头） |
| `avgFps` / `maxDt` | 宽容差 | 含调度抖动，每次跑必不同 |
| `deltaDistance` | 紧容差 | = 120 × elapsed，物理量 |
| `frameDistance` | 精断 | = 2 × frames，整数 |

一行 shell 就能做出「跑起来才算」的门禁（示意）：

```bash
MINI_GUI_SECONDS=2 MINI_GUI_FPS=60 npx scriptc-raylib run src/apps/01-window.ts --dev \
  | grep -E '\[01-window\]'   # 退出码 0 且两行齐全 = demo 还活着
```

## 8. 常见误区

**误区 1：「dt 就是 1/targetFPS，动画里写 `x += 120/60` 就行。」**
真实 dt 每帧都不同：§4 的数据里 maxDt=91.27ms（约 5.4 个「正常帧」）。写死等效步长等于假设帧时间恒定——首帧尖峰、窗口拖动、系统抖动全都会被这个假设放大成可见的卡顿或跳变。正确姿势永远是用 `getFrameTime()` 的实测值（或者更进一步，用固定时间步长积分，第六阶段再谈）。

**误区 2：「更新逻辑放进 begin/endDrawing 里也一样，反正在一个循环里。」**
一样的是「会被执行」，不一样的是「执行时机与代价」。批处理窗口内混入重逻辑会拉长「攒顶点到提交」的路径（第 4 册 §3），且让「绘制只读状态」的纪律破功——第八阶段的事件回放测试、以及一切「纯函数化绘制」的推理都建立在这条纪律上。四步顺序是铁律不是建议。

**误区 3：「逐帧驱动在 60fps 校准过，速度就是对的。」**
§4 的数据是反例本身：60fps 时 232px「看起来对」，120fps 就变 450px——约 1.9 倍快进；数据表两端的 122px → 450px（3.7 倍）则是 30fps 慢放与 120fps 快进的合力。「在某一个帧率下正确」是逐帧驱动最危险的属性——它让 bug 在开发机上隐形，在用户的 120Hz 屏幕上显形。判定标准很简单：速度的单位如果是「每帧」就是错的，「每秒」才是对的。

**误区 4：「实测数字必须逐位复现，不然就是环境坏了。」**
本册数字里，`deltaDistance`（紧容差）与 `frameDistance`（精确）是物理量，可强断言；`frames`、`avgFps`、`maxDt` 是调度量，换一台机器、甚至同一台机器再跑一次都会漂（elapsed 的零头不同）。把回归写成「所有数字精确相等」会把偶发抖动当成故障；正确的断言分层见 §7 的表。同理，本册三组数据是 2026-11-14 本机的一次采样——**规律（delta 稳、逐帧漂）可复现，具体小数位不可**。

## 9. 延伸阅读与本册小结

三座邻站与本册的接口：

- **webgl 站《第一个WebGL程序》**（第一阶段）：同样是「第一个窗口」叙事，但宿主是浏览器的 canvas + requestAnimationFrame。它的 rAF 回调模型与我们的 while 轮询模型是「帧循环」的两种宿主形态；delta time 的推导两边完全同构——对照读能看清「哪些是 GUI 的本质（dt 公式），哪些是宿主的形状（循环由谁驱动）」。
- **react 站**：本册的「绘制只读状态」与 React 渲染函数的纯函数要求是同一条纪律（render 期间不许副作用）；第八阶段的事件回放测试与 react 站的「重放断言」思路也同源。
- **compiler 站**：§2 的 envNumber 三个陷阱（尤其是 `Number("") === 0`）是「字符串→数字」类型边界的老问题，compiler 站前端工具链部分对这类隐式转换有系统梳理。

本册小结：

- 帧循环四步铁律：时间 → 输入 → 更新 → 绘制（绘制只读）；break 出口在 endDrawing 之后。
- delta 驱动 = 速度 × dt：三档帧率下路程恒定 241~243px；逐帧驱动漂移 3.7 倍（122→450px）。验算列证明数字是定义的必然。
- 实际帧率永远略低于 targetFPS（30.1/57.7/112.2 对 30/60/120）；首帧 maxDt 尖峰（91.27ms）是一次性成本，dt 驱动天然免疫。
- 轮询三问法：状态 / 边沿 / 键码流——第五阶段事件总线的原料；边沿要全帧恰好消费一次。
- 截图必须在 endDrawing 之后（之前只有清屏色）；画面四元素与绘制调用一一对应。
- 统计两行直通 stdout：物理量紧断言、调度量宽容差——「跑起来才算」落进 shell。
