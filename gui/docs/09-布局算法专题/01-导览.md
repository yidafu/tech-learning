## 1. 一个坐标系：先分清五种布局在解什么问题

五种布局不是五种「风格」，而是五类不同的**几何合同**。给一组子元素和一块画布，先问两个问题就能选对工具：

```text
Q1 子的位置怎么定？
     排队（一个接一个）      → Flow / Flex
     对号入座（看格子的）    → Grid
     贴边（相对父/兄弟）      → Constraint
     报坐标（自己说了算）     → Absolute
Q2 谁在上面？
     按「后画的在上」        → Stack / Z（所有布局共有的第三根轴）
```

```text
父容器 (w × h)
┌────────────────────────────────────────────┐
│ Flow    │ A B C ┆ D E    ← 装不下就换行      │ 排队型：游标推进
│ Grid    │ ┌─┬──┬─┐                            │ 落座型：先解轨道表
│         │ ├─┼──┼─┤   ← 先算「列宽×行高」再入座  │
│         │ └─┴──┴─┘                            │
│Constr.  │ A[8,8]───────B[贴A右缘-贴父右缘]     │ 贴边型：解线性方程
│         │        C[父中心, 50%宽]              │
│ Abs.    │      ┌────┐ ← x/y 是声明值不是算出来的│ 报坐标型：不解方程
│         │      │浮层│                             │
│ Stack/Z │ 底图 → 内容 → 角标   ← 后画的在上      │ 第三轴：z 序
└────────────────────────────────────────────┘
```

一句话版：**Flex/Flow 管「排」，Grid 管「落」，Constraint 管「贴」，Absolute 管「浮」，Stack 管「叠」**。真实应用的界面是五者的组合：页面骨架用 Grid/Flex，卡片内部用 Flow，表单对齐用 Constraint，角标/浮层用 Absolute，遮罩+对话框用 Stack。

## 2. 共同前提：三句话布局协议（第四阶段立起的）

五种算法看起来差异巨大，但它们**全部**跑在同一条协议上（详见 [../04-第四阶段/03-布局协议.md](../04-第四阶段/03-布局协议.md)）：

1. **约束向下**：父给每个子一套 `BoxConstraints`（min/max 宽高区间）——「你最多多大、至少多大」；
2. **尺寸向上**：子在约束内完成自己的子树布局，回报 `{width, height}`；
3. **位置归父**：子的 `x/y` 由**父**写入——子永远不知道自己的绝对位置。

协议带来两个直接推论，每个布局器都必须回答：

- **给子什么约束？** Flex 给「主轴无界松约束」（量自然宽度）；Grid 给「全松 → 列宽紧 → 格紧」三遍递进；Constraint 直接给「解算结果的紧约束」；Absolute（Positioned）给「双边锚定的紧约束或父的松约束」。**约束策略就是布局算法的身份证**。
- **布局是几遍的？** 本专题五种全是**一遍**（depth-first，每子恰好 layout 一次）——除了 Grid 的 auto 轨道（同一子被量三遍：自然尺寸 → 列宽定形 → 格子定形）和 Flow 的 stretch（第二遍紧约束重排）。遍数是布局器最重要的性能账，每一册都会单独记账。

## 4. 手算文化：为什么每册都有「纸上推导」

本专题的验收标准不是「代码能跑」，而是「**你读完能在纸上算出任意输入的布局结果**」。为此每册遵守三条纪律：

1. **算法写成可执行的判定式**——不是「适当排列」这类描述，而是 `cursor + mainGap + w > maxMain` 这种能逐符号代数字的式子；
2. **每个测试先手算再实跑**——`flow.test.ts` 等文件里的注释就是推导过程，期望值全部来自纸面；
3. **边界都给出确定性规则**——空行必收、余数按列序 +1、乱序推入也能解……歧义在规范里就地杀死。

一个自查样本（Flow 册会完整推导）：容器宽 100，子 [60×30, 60×30, 30×30, 40×40]——

```text
i=0: 行空，必收            → 行1=[60]        行宽 60
i=1: 60+0+60=120 > 100     → 封行1，开行2    行2=[60]        行宽 60
i=2: 60+0+30=90  ≤ 100     → 收              行2=[60,30]     行宽 90
i=3: 90+0+40=130 > 100     → 封行2，开行3    行3=[40]        行宽 40
行高 = 30, 30, 40 → 总高 100；lineCount=3
```

四行演算，三个断言（行数/尺寸/坐标）全部落定。这就是五册反复出现的节奏。

## 5. 与其它阶段的关系

- **向上**（声明式）：这五个布局器目前只在 RenderObject 层。声明式层的对接（`vflex()` / `vgrid()` 这类虚拟节点）留作毕业项目扩展——第七阶段的 VElement 模式可以逐个套用。
- **向下**（绘制）：布局产出的 `x/y/width/height` 是 Painter 坐标系里的一切——第二阶段的裁剪烘焙、第六阶段的重绘边界都以「布局之后的盒子」为输入。
- **横向**（事件）：Grid/Constraint 的子可以重叠（Grid 允许 overlap、Stack 本来就是叠的）——命中测试的**逆序试探**保证「后画的先命中」，见 [06 册第 2 节](./06-堆叠分层Stack.md)。

## 常见误区与正解

五种布局各有一条最典型的误解，多数来自「用 CSS 直觉套自研布局器」。CSS 的容错能力（自动重排、隐式约束兜底）掩盖了大量边界，自研时这些边界必须显式写进规范，否则同一份输入在不同实现里会算出不同结果。

| 误区 | 为什么错 | 正解 |
|---|---|---|
| Flow 与 Flex 是同一个东西的两种叫法 | Flex 是主轴单行（或受控换行）的分配算法，带剩余空间分配语义；Flow 的核心是贪心装行加游标推进，判定式完全不同 | 两者共享三句话协议但算法分册：装行判定与第二遍拉伸见 [02-流式布局Flow](02-流式布局Flow.md) |
| 网格轨道一遍就能算完 | 自动轨道的宽度取决于内容，内容尺寸又依赖给它的约束——必须先量自然尺寸、再定列宽、最后按格子紧约束定形 | 这是三遍递进而非一遍：轨道三型的解算顺序见 [03-网格布局Grid](03-网格布局Grid.md) |
| 约束布局只要逐条解方程就行 | 逐条解要求方程有序；乱序给出的锚点约束照样能解，但存在依赖环时任何顺序都无解 | 用 Kahn 工作清单建模：乱序推入可以、成环必须报错；循环、悬空、欠定的判定见 [04-约束布局Constraint](04-约束布局Constraint.md) |
| 绝对定位不解方程、性能最好，应该多用 | 省下的是计算，失去的是自适应：父尺寸一变，所有锚定关系全靠手工跟进，界面失去随内容伸缩的能力 | 绝对定位只留给浮层、角标等真正脱离排班的少量元素，见 [05-绝对定位Absolute](05-绝对定位Absolute.md) |
| 叠放顺序是布局属性，要在布局阶段算出来 | 纵深是独立于几何的第三根轴：绘制顺序等于子序，命中顺序等于子序倒序，与坐标解算无关 | 布局只产盒子；纵深序由绘制与命中两处的遍历方向约定，见 [06-堆叠分层Stack](06-堆叠分层Stack.md) |

## 术语速查表

五种布局共用一套词汇，但每个词在不同布局里的角色不同。本表统一口径，读分册遇到参数名或英文原词时按需检索。

| 术语 | 英文 | 一句话解释 |
|---|---|---|
| 约束 | constraints | 父传给子的宽高区间合同：「至少多大、最多多大」 |
| 游标推进 | cursor advance | Flow 沿主轴累积宽度、超过容器就封行的贪心过程 |
| 贪心装行 | greedy packing | 能装就装、装不下才换行；不求全局最优，但只需一遍 |
| 轨道 | track | Grid 的列或行；轨道尺寸先于子元素解算 |
| 跨格 | span | 一个子占据多列或多行；入位时用前缀和定位起始格 |
| 先量后定形 | measure then resolve | 自动轨道先以松约束量自然尺寸，再参与轨道分配 |
| 锚点 | anchor | Constraint 中把一个边缘钉到父或兄弟边缘的约束关系 |
| 拉伸 | stretch | 双边同时钉死使子被强制拉到解算宽度，需要第二遍紧约束重排 |
| 紧约束 | tight constraints | 最小值等于最大值的约束，子没有任何选择余地 |
| 欠定 | underdetermined | 约束条件不足以唯一确定位置，需要默认规则兜底 |
| 纵深序 | z-order | 第三根轴：绘制按子序、命中按子序倒序的约定 |
| 手算用例 | worked example | 输入、纸上推导、代码断言三者对齐的验收样本 |

## 验收清单（DoD）

本专题的验收口径不是「代码能跑」，而是「纸上算得出、边界说得清、对标对得上」。逐条自检，打不上勾的就回到对应分册重算一遍。

- [ ] 能在纸上完整算出导览里的流式用例：四个子在宽一百容器里封三行的每一步判定
- [ ] 能说出网格剩余空间按比例分配时余数的确定性舍入规则，并解释为什么不能随机分
- [ ] 能写出约束锚点方程的六种解法表，并各举一个最小输入
- [ ] 能构造循环、悬空、欠定三类错误的最小复现，并指出各自在哪个阶段被检测
- [ ] 能背出五种布局分别给子什么约束——约束策略即布局器的身份证
- [ ] 能口述每种布局的遍数账：每个子被布局几次、什么条件下会被量多遍
- [ ] 能画图解释堆叠的绘制顺序与命中顺序为什么相反，并举按钮压在图片上的例子
- [ ] 能为 CSS、Flutter、Android 各指出五种布局的对应物，并说出至少一处行为差异
- [ ] 专题新增的手算断言能一一对应到分册里的推导过程，期望值有纸面来源

做完这九条，五种布局算法就不再是一册册读过的文字，而是能随身携带、随时在纸上展开的工具——这也是本专题与前面各阶段最大的不同：它考核的是推导能力，而不是记忆能力。
