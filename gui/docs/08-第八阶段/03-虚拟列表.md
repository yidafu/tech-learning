## 1. 概念坐标：从「全部建树」到「只建可见」

普通列容器（Flex 列）与虚拟列表的本质差：

```text
Flex 列：10000 行 = 10000 个渲染对象 = 10000 次 layout/paint 记账（第六册压测的百倍成本）
虚拟列表：池 = 可见行数 + 缓冲（demo：220px 视口 / 40px 行高 = ceil+2 = 8 行）
         滚动 = 改 scrollTop → rebind：把池行「重绑」到新的数据区间
         万级行从头到尾只有 8 个渲染对象
```

数据结构四件套（逐字字段）：`rows`（数据引用）、`rowHeight`（行高常量，demo 40）、`pool`（RenderObject 池）、`scrollTop/velocity`（位置与惯性）。两个**观测口**：`liveRows`（本帧实际挂载池行数——虚拟化是否生效的直接证据）、`maxRowSeen`（滚动到过的最大行号——「从未见过全部行」的证明）。

## 2. rebind：池化的核心动作（逐行走读）

```ts
  private rebind(): void {
    if (this.makeRow === null || this.bindRow === null) return;
    const first = Math.floor(this.scrollTop / this.rowHeight);   // ① 首可见行号
    const need = Math.min(this.visibleRowCount(), this.rows.length); // ② 需要的池行数
    // ③ 池扩容（只增不减——滚动回落时池行复用，不销毁）
    while (this.pool.length < need) {
      const make = this.makeRow; // ScriptC：字段函数直接 this.fn() 撞 SC1090，读局部再调（事件槽同款）
      if (make === null) return;
      const row = make({ label: "" }, -1);
      this.pool.push(row);
      this.appendChild(row);     // ← 挂上渲染树（池行是 list 的 children）
    }
    this.liveRows = need;
    // ④ 重绑：按数据区间换内容
    for (let i = 0; i < this.pool.length; i++) {
      const row = this.pool[i]!;
      if (i < need) {
        const dataIndex = first + i;
        const data = this.rows[dataIndex];
        if (data !== undefined) {
          row.x = 0;
          row.y = dataIndex * this.rowHeight - this.scrollTop;   // ⑤ 位置 = 数据位 − 滚动位
          row.width = this.width;
          row.height = this.rowHeight;  // ← 池行不递归 layout（尺寸常量）——记账要记全：
          ...                            //    漏 height → 全行零高不可见（demo08 截图实抓）
          const bind = this.bindRow;
          if (bind !== null) bind(row, data, dataIndex);         // ⑥ 内容重绑（markNeedsPaint 在回调里）
          if (dataIndex > this.maxRowSeen) this.maxRowSeen = dataIndex;
        }
      } else {
        row.y = -10000;    // 多余池行藏到视口外（绘制剔除自然不可见）
      }
    }
    this.markNeedsPaint();
  }
```

六个步骤一张表：

| 步 | 动作 | 成本 |
|---|---|---|
| ①② | 首行号 + 需求行数（整数除法 + min） | O(1) |
| ③ | 池扩容（初次 need 次，之后 0 次） | 摊销 O(1)/帧 |
| ④ | 遍历池行：算位置、换内容 | O(池) = O(可见+2) |
| ⑤ | 行位置 = 数据位 − 滚动位（内容坐标 → 视口坐标的手工变换） | O(1)/行 |
| ⑥ | bind 回调（业务方换文案/色） | O(1)/行 |
| 收尾 | 一次 markNeedsPaint（整池统一标，不逐行） | O(树深) |

**「重绑不重建」**：池行的渲染对象身份永不变——列表项里的动画、输入缓冲（如果有）跟着池行走。代价是**身份与数据解耦**：池行 i 在滚动后绑的是另一条数据——「行状态」必须跟着数据走而不是跟着节点走。这是与第七阶段 keyed 协调相反的哲学：keyed 保身份（状态在节点），池化保节点（状态在数据）。两者的选择判据在 §5。

## 3. 两个实抓 bug：集成期发现的内核缺陷

demo08 集成时，本文件贡献了两个教科书级缺陷（都已修，注释保留）：

**bug 1：无界哨兵误判**。performLayout 的高度守卫原版只判 `c.maxHeight === Infinity`，但 Flex 传给子的主轴哨兵是 `MAX_SAFE_INTEGER`（≈9×10¹⁵）——`9e15 ≠ Infinity` → 列表把 9e15 当真实视口高 → `visibleRowCount = ceil(9e15/40) ≈ 2.3×10¹⁴` → `need = min(巨大, 10000) = 10000`——**万级行全建**，虚拟化失效。修复：双判哨兵（`=== Infinity || >= MAX_SAFE_INTEGER`）。教学点：**「无界」在约束系统里有两种表示**，只防一种等于没防。第七阶段 Grid 的无界退化规则（flex→auto）用的是同一哨兵判定——横竖呼应。

**bug 2：池行记账漏 height**。rebind 给池行记 x/y/width 但漏了 height——池行默认 height=0，`paintSelf` 画的全是零高矩形，**屏幕上一行都没有**（无头测试的 `children.length` 与 `liveRows` 全过——它们不看几何！）。截图实抓。修复一行 `row.height = this.rowHeight`。教学点：**「挂上了」≠「画得出」**——池化路径绕过了布局递归（行尺寸常量，直接记账），记账就必须自担完整性；漏一项的后果是静默不可见，比崩溃难查得多。像素探针（05 册）在这个 bug 上的表现：`regionHasColor(行区域)` 同样测不出（零高矩形无像素）——**几何类缺陷的最后防线是截图人眼**。

## 4. 滚动与惯性

滚轮入口（逐字语义）：`handleWheel(dy)` → `scrollTop += dy * WHEEL_STEP_PX`（40px/格）→ `velocity = dy * 800`（惯性初速）→ rebind + markNeedsPaint。`update(dt)`（宿主每帧调）：`scrollTop += velocity * dt`、指数衰减 `velocity *= max(0, 1 − 6dt)`、阈值 4px/s 以下清零——与第六阶段 ScrollView 同一惯性模型（代码同款，参数各调）。`scrollTop` 夹在 [0, maxScroll]，`maxScroll = rows.length × rowHeight − height`（数据高 − 视口高）。

失效通道值得注意：**滚动只标 paint 不标 layout**（03 册调用面清单的虚拟列表行）——池行 y 是重绑时直接赋值，父布局不变，滚动帧成本 = O(池) 重绑 + O(边界) 重录。demo08 实测滚动帧 repainted=1（列表所在边界）vs 稳态帧 0。

## 5. 池化 vs keyed：两种身份哲学的对照

| | 虚拟列表（池化） | keyed 协调（第七阶段） |
|---|---|---|
| 节点数 | 常量（可见+缓冲） | = 数据项数 |
| 身份 | 节点身份无关数据（重绑换内容） | 节点身份 = 数据身份（key 对应） |
| 状态住哪 | 必须在**数据**里（节点会被换绑） | 可以在**节点**里（焦点/动画跟节点走） |
| 适用 | 万级同构行（日志/表格/消息流） | 几十~几百异构项（表单/卡片流） |
| 滚动成本 | O(池) 重绑 + O(边界) 重录 | 无滚动特化（数据多时先炸内存） |

选择判据一句话：**行内有无随行存续的状态**？无（纯展示行）→ 池化完胜；有（行内输入框、展开动画）→ 要么状态上提进数据（受控组件化），要么放弃池化。第八阶段 demo 的池行是纯展示（色块+文案），所以池化无代价；真实消息流列表的「行内正在输入」就要按这条判据重新设计。

## 6. 「布局分帧」为什么本版不需要

导览提到的「布局分帧」（把一帧排不完的布局摊到多帧）在虚拟列表形态下**天然不需要**：每帧布局成本 = 池行记账 O(8) + 容器 O(树深)，微秒级。分帧的适用场景是「单帧布局量真的大」——比如首帧整树 10⁴ 节点全排。本框架的对应方案已经在别处：首帧成本压在 2.85ms（千盒压测），万盒冷帧估算 ~25ms（一次性，可接受）。工程化清单里「超预算帧拆两帧呈现」仍是一条合法 TODO，但要先有「哪帧超了」的观测（06 册 HUD）再动手。

## 8. 本册小结

- 虚拟列表 = 池（可见+缓冲）+ rebind（位置换算 + 内容重绑）+ 惯性；万级行从头到尾 8 个节点
- rebind 六步账：首行号/需求/扩容/遍历换绑/收尾一次标脏；行位置 = 数据位 − 滚动位（内容系→视口系手工变换）
- 两个集成期实抓 bug：无界哨兵双判（Infinity vs MAX_SAFE_INTEGER——「无界」的两种表示）、池行记账漏 height（挂上 ≠ 画得出，静默不可见比崩溃难查）
- 滚动只走 paint 通道（池行 y 直接赋值），滚动帧成本 O(池)+O(边界)
- 池化 vs keyed 的判据：行内状态随数据还是随节点；纯展示行池化完胜，带状态行先状态上提
- 布局分帧在本形态不需要：每帧布局 O(池)，先观测后优化

**装配入口**（逐字）：

```ts
  setRows(rows: VirtualRowData[]): void {
    this.rows = rows;
    this.scrollTop = clamp(this.scrollTop, 0, this.maxScroll());
    this.markNeedsLayout();
  }

  setRowFactory(make, bind): void {
    this.makeRow = make;
    this.bindRow = bind;
    // 池清空重建
    for (const r of this.pool) this.removeChild(r);
    this.pool = [];
    this.markNeedsLayout();
  }

  maxScroll(): number { return Math.max(0, this.rows.length * this.rowHeight - this.height); }
  visibleRowCount(): number { return Math.ceil(this.height / this.rowHeight) + 2; }  // +2 缓冲
```

**滚动与惯性**（逐字）：

```ts
  handleWheel(dy: number): void {
    this.scrollTop = clamp(this.scrollTop + dy * 40, 0, this.maxScroll());
    this.velocity = dy * 80;
    this.rebind();
    this.markNeedsPaint();
  }

  onWheel(ev: WheelEvent): boolean { this.handleWheel(ev.dy); return true; }  // 消费：不冒泡

  update(dt: number): void {                    // 宿主每帧调（惯性推进）
    if (this.velocity === 0) return;
    this.scrollTop = clamp(this.scrollTop + this.velocity * dt, 0, this.maxScroll());
    const decay = Math.max(0, 1 - 6 * dt);      // 指数衰减（第六阶段同款）
    this.velocity = this.velocity * decay;
    if (Math.abs(this.velocity) < 4) this.velocity = 0;
    this.rebind();
    this.markNeedsPaint();
  }
```

**视口与绘制**（逐字）：

```ts
  protected clipsContent(): boolean { return true; }   // 视口裁剪：池行越界部分被剪（第三阶段协议）

  protected paintSelf(p: Painter): void {              // 只画滚动条——池行由基类 children 循环画
    if (this.rows.length === 0 || this.rows.length * this.rowHeight <= this.height) return;
    const thumbH = Math.max(24, (this.height / (this.rows.length * this.rowHeight)) * this.height);
    const thumbY = (this.scrollTop / this.maxScroll()) * (this.height - thumbH);
    p.fillRect({ x: this.width - 6, y: thumbY, width: 4, height: thumbH }, { r: 89, g: 99, b: 110, a: 255 });
  }
```

「clipsContent=true + paintSelf 只画滚动条」的分工是第三阶段裁剪协议的直接复用：池行 y 出视口的部分被基类的 clipRect 剪掉——虚拟列表自己只负责「把行摆对位置 + 画滚动条」。

## 附录 B：无界哨兵的三处对照

| 位置 | 哨兵值 | 判定写法 | bug 历史 |
|---|---|---|---|
| Flex 传子主轴 | `MAX_SAFE_INTEGER` | 直接传（不判） | — |
| Grid 无界退化 | `maxW === Infinity` | `kind === auto \|\| !widthBounded`（widthBounded 判 Infinity） | 无（auto 兜底吸收） |
| 虚拟列表视口 | `MAX_SAFE_INTEGER` 与 `Infinity` 都可能出现 | 原版只判 `=== Infinity` → **bug**；现版双判 | demo08 实抓 |

规则句：**「无界」在约束系统里有两个表示（真无界 Infinity / 哨兵 MAX_SAFE_INTEGER），任何「无界就给默认值」的守卫必须双判**。写成 lint 式检查项：grep `=== Infinity` 逐处审「它想防的是哪种无界」。

## 附录 C：滚动帧失效账手算

滚一格（dy=1）的完整账（对照 demo08 实测 repainted=1）：

```text
wheel → handleWheel(1)：
  scrollTop += 40（如 0→40）
  velocity = 80（惯性）
  rebind()：first 0→1；8 个池行全部重绑（y 各 -40、内容换绑 → 每行 markNeedsPaint）
  markNeedsPaint（list 自己）
失效冒泡：8 行的 markNeedsPaint → 最近重绘边界（listBoundary）入队；list 自己的也入队同一边界
flushPaint：边界重录 = 8 行 + 滚动条 ≈ 17 条命令；根 blit 更新
repainted = 1（一个边界）——与实测吻合 ✓
```

对比「非池化万行列」的滚动帧：10000 行全部 markNeedsPaint → 一个边界重录 20001 条命令——**池化的收益在滚动帧失效账上是 10000/8 ≈ 1250×**。

## 附录 D：缓冲行数的权衡算术

`visibleRowCount = ceil(视口/行高) + 2` 的 +2 是上下各一缓冲——为什么不加 0、为什么不是 +10：

```text
+0：快速滚 40px（一格）时新行刚好从边缘进入但池里没有 → 一帧白边（可见瑕疵）
+2：滚一格后上一帧的缓冲行成为可见行（无需新 mount）→ 视觉无缺
+10：池行 20 个——每帧 rebind 成本 ×2.5、重录命令 ×2.5，换「快速滚 10 格不白边」
     ——惯性滚 10 格/帧只在甩滚时发生，甩滚本来就会跳（可接受）
```

选 +2 的依据：**一格滚轮（40px）≤ 一行高（40px）**——缓冲 ≥ 1 就能覆盖单格步进；上下各一（对称防抖）取 2。若把滚轮步长改大（如 120px），缓冲要 ≥ 3。**缓冲 = ceil(滚轮步长 / 行高)** 是通用公式。

## 附录 E：池行文本的取舍（色块 vs RenderText 池化）

demo 池行画色块+缘条，不画文本（paintSelf 注释「教学版池行不接排版引擎」）——真实列表要文本怎么办：**RenderText 也可以池化**。方案：池行 = Flex[ RenderText ]，bind 回调调 `text.setText(spans)`（同值短路 + 内部 markNeedsLayout）——每次重绑走文本布局（行内度量/断行）。成本：每行 setText 的 layout 是 O(行文本)；对照「每行一个渲染对象不池化」是 O(全表)。RenderText 的 setStyle 同值短路（第七阶段）保证「没变的行零失效」——池化 + 文本引擎的组合成立，毕业项目选题 A 的文件列表就这么接。

## 附录 F：变高行的纸面稿（rowHeight 常量的代价与出路）

本版把行高钉成常量（`rowHeight`，demo 40px）——`first = floor(scrollTop / rowHeight)` 是 O(1) 整数除法。变高行（消息流里的长段落）的正确姿势是**前缀和索引**：

```text
offsets[i] = Σ heights[0..i)                  // 建一次 O(n)，数据变更时增量维护
first = upperBound(offsets, scrollTop) - 1    // 二分 O(log n)
行 y = offsets[i] - scrollTop                 // 与本版 rebind ⑤ 同式，只是查表换掉乘法
```

三个连带改动：①`need` 不能再用 `ceil(视口/行高)+2`——改「从 first 向下累加行高直到超出视口 + 缓冲」（池大小变为内容相关，上限仍可钳）；②滚动条 thumb 用 heights 总和而非 `rows.length × rowHeight`；③**估计行高与实测行高的偏差修正**：行挂载后实测高度 ≠ 估计值 → 修正 offsets 并补偿 scrollTop（否则滚动条跳变、内容位置漂移——所有虚拟列表库的 scroll anchoring 问题）。工程化三步走：初始全用估计值、挂载后写回实测值、数据变更批量重建前缀和——本册四件套之外只加一个 offsets 数组与一次补偿。

## 附录 G：虚拟列表在后端换型时的账（06 册扩展线的呼应）

| 成本项 | 软件后端（raylib，实测口径） | GPU 后端（估算口径） |
|---|---|---|
| rebind O(池) | 8 行记账，1μs 级 | 同（CPU 侧不变） |
| 重录/提交 | 17 条命令 ≈ 0.14μs（8ns/条） | 批次提交 1 批 ≈ 50μs |
| 滚动帧总账 | repainted=1，p95 0.07ms 级 | 提交主导——**池大小直接进帧时间** |

GPU 后端下「+2 缓冲」这类常数开始有真实价格：池从 8 行涨到 20 行，提交的几何批次翻倍——附录 D 的「缓冲 = ceil(滚轮步长/行高)」公式在 GPU 后端要加一项「批次预算」。虚拟化在两种后端都是必需品（万行没有池化之外的活路），但它的调优旋钮（缓冲/池策略）**由后端定价**——又一个「每册数字标注本后端口径」的实例，与 06 册附录 B 的批次算术同一条账。

## 附录 H：池化的内存账（「每千行成本」的另一面）

```text
非池化万行：10000 × (RenderObject 头部 ≈48B + 行字段) ≈ 10000 × 120B ≈ 1.2MB 堆
            + children 数组 10000 个引用 ≈ 80KB + 布局/绘制双 dirty 标志的记账面
池化 8 行：8 × 120B ≈ 1KB + 数据数组（VirtualRowData 引用，本来就要存）≈ 0 增量
```

稳态内存差三个数量级，但真正的收益不在内存而在 **GC/分配压力**：非池化版若滚动时随数据重建行对象（常见错误实现），每秒产生数千个短命对象 → GC 停顿直接进帧预算（垃圾回收是 06 册分段账里没有显示的第四个隐藏维度——JS 运行时才有的税）；池化版滚动帧**零分配**（rebind 只改现有对象的字段）。账本规则：度量「每千行成本」时把分配率（对象/秒）与帧时间并列——后者是现在的账，前者是未来的账。

## 附录 I：滚动条几何的手算（paintSelf 两式的数字代入）

```text
demo08 口径：rows=10000、rowHeight=40、视口 height=220、scrollTop=40
数据总高 = 10000 × 40 = 400000；maxScroll = 400000 − 220 = 399780
thumbH = max(24, 220/400000 × 220) = max(24, 0.121) = 24      ← 万行下拇指取最小值
thumbY = 40/399780 × (220−24) = 0.0196                        ← 近顶端
```

两式一起读出拇指的物理意义：**拇指长 = 视口占数据高的比例**（下限 24px 防失真——十万行时比例式小于 1px，没有下限就画不出来）；**thumbY = 滚动进度 × 可滑行程**。这是 §2 rebind 手算之外的第二个纸上练习，顺手可得一条黄金用例：scrollTop=399780（底端）时 thumbY 应恰等于 220−24=196——底端对齐的边界断言。
