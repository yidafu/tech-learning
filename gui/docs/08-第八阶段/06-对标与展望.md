> 本册把八阶段攒下的机制账本对准工业坐标——Flutter / Qt Widgets / Slint / GPUI / egui 五家的渲染后端、布局协议、响应式模型、事件分发各是什么取舍、为什么；然后给三条「本框架再进一步」的扩展线（GPU 后端 / 无障碍 / 声明式 DSL），每条都从已有机制出发指出「改动量在哪、破坏什么假设」。对照以公开架构资料为准（标注非本机实测），本框架侧全部有实测数字。

## 1. 五框架总表（架构资料口径）

| 维度 | Flutter | Qt Widgets | Slint | GPUI | egui |
|---|---|---|---|---|---|
| 模式 | 保留模式（三树） | 保留模式（QObject 树） | 保留模式（编译期描述） | 保留模式 + Entity | **立即模式**（每帧全量 UI） |
| 渲染后端 | Impeller/Skia（GPU） | QPainter（软件）+ RHI（GPU 可选） | 自研 femtovg/Skia（GPU） | 自研 GPU（wgpu 系） | epaint → GPU（tessellated） |
| 布局协议 | 约束下/尺寸上（单遍）+ relayout boundary | layout 系统（QLayout 约束求解） | 约束式（声明在 .slint） | Taffy（flexbox，多遍） | 每帧即时计算（无约束传递） |
| 响应式 | setState→build（全量子树） | 信号/槽（手写更新） | 声明式绑定（属性追踪） | Entity 状态 + 手动失效 | 立即重算（无失效概念） |
| 事件 | 命中测试→冒泡 | 事件过滤器/重载 | 声明式 handler | 焦点+按键表 | 即时查询（ui.interact） |
| 文本 | 完整 shaping（harfbuzz） | 完整 shaping | 完整 | 较简（GPU 字形图集） | 较简（fonts baseline 网格） |
| 语言 | Dart | C++ | .slint DSL + Rust/C++ | Rust | Rust（立即 API） |

本框架（mini-gui）在这张表里的位置：**保留模式 + 单遍约束 + signals 细粒度 + 软件后端（raylib）+ TypeScript→原生**——最接近的一行是 Slint（保留模式 + 声明式绑定 + 约束布局），最大差距在后端（raylib 是游戏库的软件/简单 GPU 通道，非渲染框架）。

## 2. 五个对照点的深读

**① 保留 vs 立即（egui 那一格）**。立即模式每帧重建整个 UI 描述、无失效概念——它的「测试」正好反过来：不测「失效传播对不对」（没有失效），测「每帧构建成本」。第六册的欠活清单在立即模式里不存在（每帧都是全欠）。egui 用「每帧全量构建很便宜」换掉了整个失效层——代价是大树/重控件时的 CPU 常驻。本框架的反面选择（保留 + 欠活）在 idle 帧 0.014ms 上有数字优势。

**② 单遍约束 vs Taffy 多遍**。GPUI 用 Taffy（Firefox 的 flexbox 实现）——完整 CSS flex 语义（可换行/基线/嵌套 stretch）必然多次遍历。本框架的单遍约束 + 三种手写布局（Flex/Flow/Grid/Constraint）是「语义换性能」的取舍：语义少，遍数少。第 09 专题的差距清单（minmax/subgrid/基线对齐缺席）就是这张表的逐格展开。

**③ 细粒度信号 vs setState**。Flutter 的 setState 全量子树重建 + diff——react 站路线 A。Slint 的属性绑定（编译期静态依赖图）——本册 signals 路线的静态化版本（依赖在编译期已知，运行时零收集成本）。第七阶段的动态收集 vs Slint 静态绑定是同一 spectrum：动态=灵活、静态=便宜可验证。

**④ 文本系统的深度差**。五家里四家有完整 text shaping（harfbuzz 系：连字/双向/变宽字体），本框架第三阶段的排版是「逐字符 advance + 贪心断行」——CJK 单行 OK，阿拉伯语/连字/emoji 序列全部不接。这是本框架与五家**最大**的工程差距（比渲染后端还大）——文本是 UI 框架的第二座大山（第一座是布局）。

**⑤ 软件后端的账**。raylib 通道的 draw call 单价 8ns（06 册实测）让「整段 replay」成为合理默认；GPU 后端下 draw call 变贵（管线切换/批次合并压力），第三道防线（脏矩形/scissor 合批）从「负收益」翻正——后端换型会**反转**第六册的部分结论。这就是为什么每册的实测数字都标注「本后端口径」。

## 3. 扩展线一：GPU 后端

改动面（从已有机制出发）：

```text
1. Painter 接口不变（CommandSink 消费者）——新增 GPUBackend implements CommandSink
2. DrawCmd 的 fillRect/rounded/circle → 顶点批（tessellation 缓存，几何不变时可复用）
3. 文本 → 字形图集（SDF 或位图图集）——第三阶段的 TextLayout 兼容（advance 不变）
4. replay → 提交批次（跳过未变批次：图层缓存的 GPU 版 = 批次哈希）
5. clip → scissor 保持（GPU 原生支持）；透明度/混合 → 新命令类型
```

被打破的假设清单（第六册结论逐条复核）：①「整段 replay 0.016ms 便宜」→ GPU 批次提交约 50~200μs，第三道防线**翻正**；②「blit 是命令拷贝」→ GPU 版可升级为真图层纹理（合成器语义）；③「软件限帧亏空 4.6%」→ vsync 语义变化（帧率钉死刷新率）。工作量主战场在 backend 一层 + 文本——内核零改动（Painter 契约的兑现）。

## 4. 扩展线二：无障碍

现状诚实盘点：零无障碍——没有语义树、没有读屏接口、焦点只有键盘环。扩展的最小面：

```text
语义树 = VElement 树的投影（semantic(label, role, actions)）
  role：button/text/list/editableText…（VNode kind 天然映射）
  label：控件的文本（RenderButton.label / TextField.text）
  actions：click/setText（映射到已有回调）
平台桥：macOS NSAccessibility / Linux AT-SPI（宿主层新文件）
```

关键设计判断：语义树**不要挂渲染树**（几何与语义正交——装饰盒无语义、文本盒有）——挂 VElement 层（第七阶段的协调树天然有身份与类型）。第七阶段的 keyed 复用在这里二次兑现：语义节点身份稳定 → 读屏的「跟随焦点」不漂移。工作量：vdom 加一投影函数 + 宿主桥——又一个「内核零改动」的扩展。

## 5. 扩展线三：声明式 DSL

第七阶段的 VNode 字面量已是声明式；DSL 的增量是**编译期**：

```slint  // 假想的 mini-gui DSL
component Counter {
  property <int> count;
  Text { text: "count: " + count; }
  Button { text: "+"; clicked => { count += 1; } }
}
```

编译期红利对照第七阶段机制：依赖静态化（signals 的动态收集→编译期依赖表——Slint 路线）、布局常量折叠（约束在编译期可解的直出尺寸）、类型检查提前。代价：工具链（DSL 编译器 = ScriptC 的翻版工作）。诚实评估：VNode 字面量 + TS 类型已经给了 80% 的静态检查红利，DSL 的边际价值在「非程序员写 UI」场景——本课程定位（理解框架原理）下优先级最低，列此仅作完整性。

## 7. 本册小结

- 五框架总表一张：本框架最近 Slint（保留+声明绑定+约束），最大差距在文本 shaping
- 立即 vs 保留的实测对照：egui 无失效层（每帧全量）vs 本框架 idle 0.014ms——欠活清单的数字优势
- GPU 后端扩展：Painter 契约兑现（内核零改动）；第三道防线结论会反转（draw call 单价变化）
- 无障碍扩展：语义树挂 VElement（身份稳定 = 读屏跟随不漂移）——keyed 的二次兑现
- DSL 扩展优先级最低（VNode+TS 已有 80% 静态红利）——诚实排序
- 能力地图七维自评：四个四星（布局/失效/事件/响应式/工具链）、两个两星（文本/控件库）——毕业选题的依据

## 附录 A：五框架逐家短评（本课程可各学三件事）

**Flutter**——三棵树的教科书。可学：①Widget/Element/RenderObject 分层（本课程第四阶段的直系对标）；②RelayoutBoundary/RepaintBoundary 的工业实现（第六阶段术语全借自它）；③Impeller 的预编译着色器思路（06 册 GPU 线的参照）。不必学：Dart isolate 模型、platform channel——与 UI 内核机制正交。

**Qt Widgets**——三十年保留模式的老兵。可学：①信号/槽的显式连接（与本课程 signals 自动收集对照——显式的优劣）；②QPainter 的状态机 API（本课程 Painter 的祖师爷）；③事件过滤器链（第五阶段冒泡链的另一种形态）。差距点：自绘不如 QML/Flutter 现代，但控件工程化程度是天花板——毕业项目参照它的控件规格。

**Slint**——编译期声明式的范本。可学：①.slint DSL → 静态属性依赖图（第七阶段 signals 的静态化）；②轻量运行时（嵌入式友好，对照本框架的 raylib 依赖）；③属性绑定的双向推导。最接近本框架的工业物——读它的源码就像读「工程化的 mini-gui」。

**GPUI**（Zed 编辑器的 UI 框架）——GPU 优先 + Rust 所有权模型的 UI。可学：①Entity 状态管理（View 持有状态、通知更新——保留模式的另一种状态归属）；②Taffy 集成（flexbox 完整语义的遍数代价实证）；③文本渲染走 GPU 字形图集。可参照其性能数据理解「GPU 后端反转第三道防线结论」。

**egui**——立即模式的极致。可学：①每帧全量构建的心智（与本课程保留模式对照——没有失效层是什么体验）；②epaint 的镶嵌缓存（即时模式也要缓存，缓存的是镶嵌结果不是失效状态）；③一行代码一个控件的 API 人体工学。本课程 idle 帧 0.014ms 的对照组——立即模式永远没有「空闲帧免费」。

## 附录 B：GPU 后端的批次算术（第三道防线反转的推演）

```text
软件后端（raylib 现状，06 册实测）：
  replay 2001 条命令 = 0.016ms（单价 8ns）→ 脏矩形求交 20μs ≥ replay 16μs → 第三道防线负收益

GPU 后端（估算口径，非实测）：
  提交单价：一个 draw call ≈ 20~100μs（状态切换/驱动开销），批次合并后 5~20 批/帧
  整段提交：10 批 × 50μs = 500μs
  脏矩形方案：求交 20μs + 只提交 1 批脏区 50μs = 70μs → 净赚 430μs（7×）
```

**同一套机制，换后端结论反转**——这就是每册数字都标「本后端口径」的原因。批次合并（把同材质命令并成一个 draw call）是 GPU 后端的新增课题：显示列表的「同色/同纹理相邻合并」排序机会（第二阶段末册的伏笔）在 GPU 后端第一次变成刚需。

## 附录 C：无障碍语义树的投影函数（伪码）

```ts
// 从 VElement 树投影语义树——挂在协调层，不碰渲染树
interface SemanticNode { role: string; label: string; actions: string[]; children: SemanticNode[] }

function project(el: VElement): SemanticNode | null {
  const v = el.vnode;
  if (v.kind === "button") return { role: "button", label: v.label, actions: ["click"], children: [] };
  if (v.kind === "text")   return { role: "text", label: spansToString(v.spans), actions: [], children: [] };
  if (v.kind === "row" || v.kind === "column") {
    const kids = el.children.map(project).filter((n): n is SemanticNode => n !== null);
    return kids.length === 1 ? kids[0] : { role: "group", label: "", actions: [], children: kids };
  }
  return null;   // box/padding/boundary：纯装饰，无语义（跳过）
}
```

要点：语义树是协调树的**投影**（一次遍历、跳过装饰节点）；key 稳定性直接给出「同一控件跨更新的语义身份」——读屏的焦点跟随靠它。平台桥（NSAccessibility/AT-SPI）消费这棵树，宿主层新文件——内核与 vdom 都不改。

## 附录 D：DSL 映射表（假想 .minigui → VNode）

| DSL 写法 | VNode 产物 | 编译期可做的事 |
|---|---|---|
| `Text { text: "count: " + count }` | `{ kind:"text", spans:[{text:...}] }` + count 的依赖登记 | 依赖静态化（省读时收集） |

## 附录 G：GPU 文本管线的账（扩展线一的文本难点展开）

§3 说「文本 → 字形图集」，两种图集的算术：

```text
位图图集（raylib 现状同款思路）：
  纹理 = Σ (字形位图 + 1px padding)；32px 底字形、ASCII 95 字 + CJK 样本 200 字 ≈ 300 字形
  ≈ 300 × 40×40 × 4B ≈ 1.9MB——一次性烘焙，运行时零栅格化
  失真条件：目标字号 ≠ 底字号时缩放采样糊——本框架字号档位制（TextLayout 按 fontSize 键缓存）
  下字号集合有限，烘焙按档位全量出 → 无缩放场景（第三阶段设计的隐含红利）

SDF 图集：
  每字形存有符号距离场（8bit 单通道），着色器按目标字号重建边缘——任意字号锐利
  代价：烘焙贵（每字形一次距离变换）、需着色器、半透明边缘的调参
  本框架接 GPU 的顺序：位图图集先行（延续档位制），「无限字号」需求真出现再上 SDF
```

「字号档位制」是本框架隐含的第三条路线：工业框架选 SDF 是因为 CSS 任意 px 缩放；本框架的档位约束反而省掉整条 SDF 管线——**约束换管线**的又一实例（对照 §2 对照点②的「语义换遍数」）。

## 附录 H：无障碍平台桥对照（扩展线二的落地面）

| 桥 | 平台 | 语义树消费方式 | 本框架映射难度 |
|---|---|---|---|
| NSAccessibility | macOS | 推送：App 发通知 + 读屏属性查询（AXUIElement 反向调用） | 宿主层实现协议方法——附录 C 投影函数直接喂 |
| AT-SPI | Linux | 拉取：D-Bus 注册树，读屏主动遍历 | 树缓存 + 变更事件——keyed 身份直接当路径分量 |
| UIA | Windows | 拉取：Provider 接口 + 事件 | 同 AT-SPI 形态 |
| DOM/ARIA | Web | 浏览器从 DOM 投影语义树 | 对照：ARIA 就是「给投影函数的标注」——role/label 的 HTML 版 |

四家收敛成两类：**推送（macOS）vs 拉取（Linux/Windows）**。投影函数（附录 C）是共同上游——语义树一次生成、四座桥各自消费。工作量真相：投影约 100 行、每桥 300~800 行胶水——**无障碍贵在桥不在模型**；这就是 §4 的最小面只到投影为止的原因（桥是宿主工程，不动内核）。

## 附录 J：三条扩展线的优先级推演（为什么排 GPU > 无障碍 > DSL）

§3~§5 的顺序不是随手写——按「解锁收益 × 复用已有机制」打分：

| 线 | 复用已有机制 | 新增主要工作 | 解锁的能力 | 序 |
|---|---|---|---|---|
| GPU 后端 | Painter 契约（内核零改动）/ DisplayList 批次化 | backend 一层 + 文本图集 | 帧预算量级下降 + 第三道防线翻正 | 1 |
| 无障碍 | VElement 身份（keyed）/ 协调树 | 投影函数 + 平台桥 | 读屏可达（合规刚需） | 2 |
| DSL | VNode 字面量 / signals | DSL 编译器全链 | 非程序员 UI + 依赖静态化 | 3 |

GPU 排第一的理由是**杠杆**：不动内核（Painter 契约的兑现）却翻正一条已论证的结论（第三道防线）——「扩展检验架构」的教科书案例。无障碍第二：模型侧近乎免费（投影函数），贵在四座桥的胶水（附录 H），且价值不由性能定。DSL 第三的全部理由在 §5（VNode + TS 已拿走 80% 红利）。毕业延伸若只做一条，选 GPU——它是唯一**会推翻本课程某条实测结论**的线，做它的过程就是重走第六册的度量方法论（先预算表、后实测、结论可反转）。
