## 2. pixel-probe：无头像素断言的机制

核心问题：不开窗口，怎么断言「某个点是什么颜色」？答案：**DisplayList 是命令化的绘制记录，取色可以在命令流上模拟**（`pixel-probe.ts`，逐字要点）：

```ts
export function pixelAt(list: DisplayList, x: number, y: number): Color | null {
  // 从后向前扫命令流：后画的盖前画（绘制序 = z 序）
  for (let i = list.commands.length - 1; i >= 0; i--) {
    const cmd = list.commands[i]!;
    if (isClippedOut(cmd.clip, x, y)) continue;        // ① 裁剪外：跳过（不是停止！）
    if (cmd.op === "fillRect") {
      if (inRect(cmd.rect, x, y)) return cmd.color;    // ② 命中即返回（最上层）
    } else if (cmd.op === "fillRoundRect") {
      if (inRect(cmd.rect, x, y) && inRoundedCorner(cmd.rect, cmd.radius, x, y)) return cmd.color;
    } else if (cmd.op === "fillCircle") {
      if (distSq(cmd.center, x, y) <= cmd.radius * cmd.radius) return cmd.color;
    }
    ... // 描边（边带判定）/ 文本（字形栅格太大，返回 null = 不判定）/ 图片（教学版不判定）
  }
  return null;   // 全部命令都不命中 → 背景（透明）
}
```

三个设计决策：

| 决策 | 理由 | 代价 |
|---|---|---|
| **从后向前扫、命中即返回** | 后画的在上（绘制序=z 序的镜像）——第一个命中的就是眼睛看到的 | O(n) 最坏；够用 |
| 裁剪用 continue 不用 break | 中间命令可能被裁剪、后面的命中（裁剪是按命令的，不是按流的） | 不能提前退出 |
| 文本命令返回 null | 字形栅格判定需要字体引擎——教学版画「不判定」标签 | 文本覆盖区域只能靠「背景色不可见」间接断言 |

配套 `regionHasColor(list, rect, color)`：区域内任一点命中即真——「这块区域有没有出现这个颜色」的廉价断言（对零高矩形 bug 这类「几何丢失」同样无效，见 §4 复盘）。

**断言粒度的取舍**（导览自测 4 的正面回答）：「断某点颜色」比「断整屏快照」好在三点——①失败信息精确到点（期望蓝实测白 → 立刻知道哪个元素没了）；②对无关区域不敏感（加个按钮不会弄红别处测试）；③无需基线文件（快照测试要维护黄金图与兼容性）。代价是**只测得动「点态事实」**——「整体布局好不好看」快照更合适。两者互补：像素探针做正确性回归，快照做视觉评审（人工看）。

## 3. 事件回放：把「跑起来才算」固化

第五阶段的输入抽象（轮询模型）给了回放天然入口：**构造 UiEvent 数组 → 依次 dispatch**——宿主的 poll() 只是事件源，测试可以自己当事件源：

```ts
// widgets-scene.test 的焦点编辑回放（逐字语义）
scene.focus.dispatchKey(keyEvent(0, 269, 1));  // End
scene.focus.dispatchKey(keyEvent(0, 72, 2));   // 'H'
expect(scene.field.getText()).toBe("edit meH");
```

回放三纪律：

1. **走真实路由**：回放经 `focus.dispatchKey` / `dispatcher.dispatch`，**不要直接调控件 onKey**——07 册焦点标志缺陷就是直接调用绕过了路由层才漏掉的（直接调用测试绿、集成红）。回放的价值=覆盖真实接线。
2. **时序用 time 字段**：手势状态机（双击窗口判定）依赖事件时间戳，回放时 time 单调递增，别全传 0。
3. **指针事件带坐标语义**：`pointerEvent(phase, x, y, button)` 的 x/y 是窗口坐标——回放点击 = 先算目标控件窗口坐标（mount 后从树读 x 累加），再发 down/up 对。

「事件回放 + 失效账」的组合拳（06 册审计钩子）：回放一段交互序列后断言 repaintedNodes/失效通道分布——**行为级回归**（改了 X，失效账不该爆）。

## 4. 复盘：demo08 集成期的「三绿一红」

demo08 集成实抓了四个缺陷，检出通道各不相同——这是本册最贵的教材：

| 缺陷 | 无头单测 | 无头集成 | 像素探针 | 截图 | 检出通道 |
|---|---|---|---|---|---|
| ① 焦点标志不同步（键全吞） | 绿（各自手工设标志） | 绿（直接调控件） | — | **红**（键入无反应） | L4 人工 |
| ② 无界哨兵误判（万行全建） | 绿 | **红**（liveRows=10000） | — | 伴随卡顿 | **L2 集成** |
| ③ 池行漏 height（零高不可见） | 绿（children/liveRows 全过） | 绿 | 同样测不出（零高无像素） | **红**（列表空白） | L4 截图 |
| ④ 槽位返回型运行期炸 | —（ScriptC 编译过） | — | — | **红**（启动即崩） | L4 运行 |

四个通道的检出矩阵不是装饰——它回答「该写哪种测试」：**逻辑缺陷用 L1/L2 抓，几何缺陷靠 L4 截图，集成缺陷（接线/路由）必须 L2 直连真实路由**。像素探针的能力边界也要诚实：③ 它测不出（零高矩形无像素可取）——「元素存在但不可见」是像素断言的盲区，探针的 `regionHasColor` 会返回 false（没有颜色）但无法区分「没画」和「画成零高」。补法：L2 断言渲染对象的 width/height 几何（池行记账完整性）——**像素断言测「画成什么样」，几何断言测「有没有资格画」**，两层都要。

## 5. 布局黄金用例：手算-断言对的编制法

第四阶段起的布局测试全是黄金用例形态（手算期望 → 代码断言），编制纪律五条：

1. **输入极小**：2~4 个节点的树，每条断言都能在纸上 30 秒内重推；
2. **断言三件套**：容器尺寸、子位置、失效次数（layoutCount）——尺寸对位置错/位置对失效错都是常见 bug 形态；
3. **边界必有一条**：空容器、单子、超约束溢出、无界退化——每册的「手算用例全表」里边界行从不缺席；
4. **注释即推导**：期望值写「为什么」（`// 60+0+30=90 ≤100 → 同行`）——测试是可读的第二教材；
5. **观测口锁不变量**：mainOverflow/lineCount/liveRows 这类「只读产物」直接断言——它们是布局器的自报告。

第 09 专题五册的 19 条手算断言、03 册失效组的对账单（附录 E）、本册像素探针——三套编制法覆盖「算法正确 / 失效正确 / 视觉正确」。

## 附录 A：pixel-probe 全量源码走读

```ts
export function pixelAt(list: DisplayList, x: number, y: number): Color | null {
  for (let i = list.commands.length - 1; i >= 0; i--) {   // 倒序：后画的在上
    const cmd = list.commands[i]!;
    if (!clipContains(cmd.clip, x, y)) continue;           // 命令自带 clip：不含此点则跳过
    switch (cmd.op) {
      case "fillRect":
        if (inRect(cmd.rect, x, y)) return cmd.color;
        break;
      case "fillRoundRect":
        if (inRect(cmd.rect, x, y) && inRounded(cmd.rect, cmd.radius, x, y)) return cmd.color;
        break;                                             // 圆角角部判定（半径圆内）
      case "fillCircle":
        if (inCircle(cmd.center, cmd.radius, x, y)) return cmd.color;
        break;
      case "strokeRect":
        if (onRectBorder(cmd.rect, cmd.thickness, x, y)) return cmd.color;
        break;                                             // 边带判定（厚度内）
      case "text":
        break;                                             // 字形栅格不判定（返回上层继续找底色）
      case "drawImage":
        break;                                             // 教学版不判定
    }
  }
  return null;                                             // 全不命中 → 背景/透明
}

export function regionHasColor(list: DisplayList, rect: Rect, color: Color): boolean {
  // 采样步进 2px 扫描 rect（面积大时的降采样；教学版 rect 小直接逐点）
  for (let y = rect.y; y < rect.y + rect.height; y += 2) {
    for (let x = rect.x; x < rect.x + rect.width; x += 2) {
      const c = pixelAt(list, x, y);
      if (c !== null && c.r === color.r && c.g === color.g && c.b === color.b) return true;
    }
  }
  return false;
}
```

三处诚实标注：①`clipContains` 用的是**命令自带 clip**（录命令时的 scissor 快照——第三阶段的裁剪烘焙）；②文本不判定——probe 对文本区域返回 null，测「文本遮住了背景色」要用「背景色取不到」反证；③2px 降采样对小色块可能漏采——regionHasColor 用于「大色块存在性」，单点用 pixelAt。

**断言范本**（pixel-probe.test 全 8 条的编制法）：


## 附录 E：像素探针的性能账（为什么它只在测试里用）

pixelAt 最坏 O(命令数)/次取色，regionHasColor 是 O(采样数 × 命令数)——按 06 册压测口径（2000 命令显示列表）算：

```text
单次 pixelAt 最坏：2000 次判定 ≈ 10μs 级
regionHasColor(100×100)：2500 采样 × 2000 命令 = 5×10⁶ 判定 ≈ 20ms 级——一条断言 20ms
```

为什么不能二分提速：命令流**按绘制序不按空间序**排列，且每条 clip 各异——空间索引（R-tree/网格）对测试代码是负资产（测试要「明显慢但绝对对」，不要「快但有索引 bug」）。测试预算的定位：探针断言单测 <50ms/条、全库 204 断言 <30s——L3 的 8 条探针贡献约 100ms，占比健康。**测试代码的性能标准是「总时长可接受」而非「算法最优」**——这句是给毕业项目写测试时的预先豁免。

## 附录 F：黄金用例的反例集（绿但错的四种形态）

手算-断言对会失败在「对不上」；更危险的是**绿但错**：

| 形态 | 症状 | 例子 | 防御 |
|---|---|---|---|
| 断言同义反复 | 期望值是从代码里抄的 | 期望值写成 `list.lineCount` 而非字面量 3 | 手算值写死为字面量（纪律五的另一半） |
| 手算本身错 | 断言与实现一起错向 | 行宽公式漏 gap，期望也漏 gap | 两处独立推导（09 专题手算表的「先纸后码」） |
| 弱断言 | 断言真但没锁住不变量 | 只断 children.length 不断几何——demo08 bug 2 全绿漏网 | 断言三件套（尺寸+位置+失效） |
| 时序耦合 | 换执行顺序就红 | 手工设 focused 后再测路由 | 回放走真实路由（纪律一） |

demo08 的 bug 2 是「弱断言」的教科书案例：无头测试断 children.length 与 liveRows——**它锁的是「挂了几个」，不是「挂在哪、多大」**。防御不是多写断言，是每条断言问自己「什么 bug 会逃过这条断言」。四形态自查放进毕业项目门 1 的 PR 清单。

## 附录 H：探针断言的失败信息设计（失败可读性三行格式）

```ts
expect(pixelAt(list, 50, 30), `期望 ${fmt(RED)} 实测 ${fmt(pixelAt(list, 50, 30))} @ (50,30)——按钮背景中心`);
```

失败信息三要素：**期望值、实测值、探针点的语义上下文**（「按钮背景的中心」而非裸坐标）——没有上下文的 `expect null toEqual RED` 要在脑内重建整棵布局树才能定位；有上下文的一行直接指出「哪个元素的那一面丢了」。黄金用例纪律「注释即推导」在探针上的对应物：**坐标即推导**——每个探针点旁注明它想证明什么。vitest 的 expect 第二参数（自定义消息）是探针测试的强制项（pixel-probe.test 全 8 条都带）；毕业项目的像素断言沿用此格式（门 1 的「探针 ≥2 条」验收含可读性检查）。

## 附录 I：测试资产的维护成本账（204 断言的重构敏感度分级）

| 断言族 | 数量级 | 对什么重构敏感 | 敏感度 |
|---|---|---|---|
| 手算布局断言（四布局器） | 19+ | 布局公式改动 | 高（应然——公式的回归网） |
| 失效账断言（pipeline/场景） | ~20 | 失效传播机制 | 高 |
| 回放断言（焦点/编辑/手势） | ~15 | 事件路由接线 | 中（约定变则测试变） |
| 像素探针 | 8 | 调色板 / 绘制层序 | 中 |
| 控件与池化（widgets/scene） | ~15 | 控件内部实现 | 低（观测口隔离） |

读法：**敏感度 ≠ 坏**——高敏感断言就是回归网的本职（改布局公式就该炸一片）；坏的是「对无关重构敏感」（脆）。观测口（liveRows/mainOverflow/colWidths）的存在意义就是把脆压到最低：断言读自报告值而不是 peek 私有字段。全库 30 秒内跑完 → 高敏感的重构成本可控（改什么立刻知道炸了什么，改完 30 秒知道全貌）。
