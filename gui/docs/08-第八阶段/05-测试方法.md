## 2. pixel-probe：无头像素断言的机制

核心问题：不开窗口，怎么断言「某个点是什么颜色」？答案：**DisplayList 是命令化的绘制记录，取色可以在命令流上模拟**（`pixel-probe.ts`，逐字要点）：

```ts
export function pixelAt(list: DisplayList, x: number, y: number): Color | null {
  // 从后向前扫命令流：后画的盖前画（绘制序 = z 序）
  for (let i = list.commands.length - 1; i >= 0; i--) {
    const cmd = list.commands[i]!;
    if (isClippedOut(cmd.clip, x, y)) continue;        // ① 裁剪外：跳过（不是停止！）
    if (cmd.op === "fillRect") {
      if (inRect(cmd.rect, x, y)) return cmd.color;    // ② 命中即返回（最上层）
    } else if (cmd.op === "fillRoundRect") {
      if (inRect(cmd.rect, x, y) && inRoundedCorner(cmd.rect, cmd.radius, x, y)) return cmd.color;
    } else if (cmd.op === "fillCircle") {
      if (distSq(cmd.center, x, y) <= cmd.radius * cmd.radius) return cmd.color;
    }
    ... // 描边（边带判定）/ 文本（字形栅格太大，返回 null = 不判定）/ 图片（教学版不判定）
  }
  return null;   // 全部命令都不命中 → 背景（透明）
}
```

三个设计决策：

| 决策 | 理由 | 代价 |
|---|---|---|
| **从后向前扫、命中即返回** | 后画的在上（绘制序=z 序的镜像）——第一个命中的就是眼睛看到的 | O(n) 最坏；够用 |
| 裁剪用 continue 不用 break | 中间命令可能被裁剪、后面的命中（裁剪是按命令的，不是按流的） | 不能提前退出 |
| 文本命令返回 null | 字形栅格判定需要字体引擎——教学版画「不判定」标签 | 文本覆盖区域只能靠「背景色不可见」间接断言 |

配套 `regionHasColor(list, rect, color)`：区域内任一点命中即真——「这块区域有没有出现这个颜色」的廉价断言（对零高矩形 bug 这类「几何丢失」同样无效，见 §4 复盘）。

**断言粒度的取舍**（导览自测 4 的正面回答）：「断某点颜色」比「断整屏快照」好在三点——①失败信息精确到点（期望蓝实测白 → 立刻知道哪个元素没了）；②对无关区域不敏感（加个按钮不会弄红别处测试）；③无需基线文件（快照测试要维护黄金图与兼容性）。代价是**只测得动「点态事实」**——「整体布局好不好看」快照更合适。两者互补：像素探针做正确性回归，快照做视觉评审（人工看）。

## 3. 事件回放：把「跑起来才算」固化

第五阶段的输入抽象（轮询模型）给了回放天然入口：**构造 UiEvent 数组 → 依次 dispatch**——宿主的 poll() 只是事件源，测试可以自己当事件源：

```ts
// widgets-scene.test 的焦点编辑回放（逐字语义）
scene.focus.dispatchKey(keyEvent(0, 269, 1));  // End
scene.focus.dispatchKey(keyEvent(0, 72, 2));   // 'H'
expect(scene.field.getText()).toBe("edit meH");
```

回放三纪律：

1. **走真实路由**：回放经 `focus.dispatchKey` / `dispatcher.dispatch`，**不要直接调控件 onKey**——07 册焦点标志缺陷就是直接调用绕过了路由层才漏掉的（直接调用测试绿、集成红）。回放的价值=覆盖真实接线。
2. **时序用 time 字段**：手势状态机（双击窗口判定）依赖事件时间戳，回放时 time 单调递增，别全传 0。
3. **指针事件带坐标语义**：`pointerEvent(phase, x, y, button)` 的 x/y 是窗口坐标——回放点击 = 先算目标控件窗口坐标（mount 后从树读 x 累加），再发 down/up 对。

「事件回放 + 失效账」的组合拳（06 册审计钩子）：回放一段交互序列后断言 repaintedNodes/失效通道分布——**行为级回归**（改了 X，失效账不该爆）。

## 4. 复盘：demo08 集成期的「三绿一红」

demo08 集成实抓了四个缺陷，检出通道各不相同——这是本册最贵的教材：

| 缺陷 | 无头单测 | 无头集成 | 像素探针 | 截图 | 检出通道 |
|---|---|---|---|---|---|
| ① 焦点标志不同步（键全吞） | 绿（各自手工设标志） | 绿（直接调控件） | — | **红**（键入无反应） | L4 人工 |
| ② 无界哨兵误判（万行全建） | 绿 | **红**（liveRows=10000） | — | 伴随卡顿 | **L2 集成** |
| ③ 池行漏 height（零高不可见） | 绿（children/liveRows 全过） | 绿 | 同样测不出（零高无像素） | **红**（列表空白） | L4 截图 |
| ④ 槽位返回型运行期炸 | —（ScriptC 编译过） | — | — | **红**（启动即崩） | L4 运行 |

四个通道的检出矩阵不是装饰——它回答「该写哪种测试」：**逻辑缺陷用 L1/L2 抓，几何缺陷靠 L4 截图，集成缺陷（接线/路由）必须 L2 直连真实路由**。像素探针的能力边界也要诚实：③ 它测不出（零高矩形无像素可取）——「元素存在但不可见」是像素断言的盲区，探针的 `regionHasColor` 会返回 false（没有颜色）但无法区分「没画」和「画成零高」。补法：L2 断言渲染对象的 width/height 几何（池行记账完整性）——**像素断言测「画成什么样」，几何断言测「有没有资格画」**，两层都要。

## 5. 布局黄金用例：手算-断言对的编制法

第四阶段起的布局测试全是黄金用例形态（手算期望 → 代码断言），编制纪律五条：

1. **输入极小**：2~4 个节点的树，每条断言都能在纸上 30 秒内重推；
2. **断言三件套**：容器尺寸、子位置、失效次数（layoutCount）——尺寸对位置错/位置对失效错都是常见 bug 形态；
3. **边界必有一条**：空容器、单子、超约束溢出、无界退化——每册的「手算用例全表」里边界行从不缺席；
4. **注释即推导**：期望值写「为什么」（`// 60+0+30=90 ≤100 → 同行`）——测试是可读的第二教材；
5. **观测口锁不变量**：mainOverflow/lineCount/liveRows 这类「只读产物」直接断言——它们是布局器的自报告。

第 09 专题五册的 19 条手算断言、03 册失效组的对账单（附录 E）、本册像素探针——三套编制法覆盖「算法正确 / 失效正确 / 视觉正确」。

## 附录 A：pixel-probe 全量源码走读

```ts
export function pixelAt(list: DisplayList, x: number, y: number): Color | null {
  for (let i = list.commands.length - 1; i >= 0; i--) {   // 倒序：后画的在上
    const cmd = list.commands[i]!;
    if (!clipContains(cmd.clip, x, y)) continue;           // 命令自带 clip：不含此点则跳过
    switch (cmd.op) {
      case "fillRect":
        if (inRect(cmd.rect, x, y)) return cmd.color;
        break;
      case "fillRoundRect":
        if (inRect(cmd.rect, x, y) && inRounded(cmd.rect, cmd.radius, x, y)) return cmd.color;
        break;                                             // 圆角角部判定（半径圆内）
      case "fillCircle":
        if (inCircle(cmd.center, cmd.radius, x, y)) return cmd.color;
        break;
      case "strokeRect":
        if (onRectBorder(cmd.rect, cmd.thickness, x, y)) return cmd.color;
        break;                                             // 边带判定（厚度内）
      case "text":
        break;                                             // 字形栅格不判定（返回上层继续找底色）
      case "drawImage":
        break;                                             // 教学版不判定
    }
  }
  return null;                                             // 全不命中 → 背景/透明
}

export function regionHasColor(list: DisplayList, rect: Rect, color: Color): boolean {
  // 采样步进 2px 扫描 rect（面积大时的降采样；教学版 rect 小直接逐点）
  for (let y = rect.y; y < rect.y + rect.height; y += 2) {
    for (let x = rect.x; x < rect.x + rect.width; x += 2) {
      const c = pixelAt(list, x, y);
      if (c !== null && c.r === color.r && c.g === color.g && c.b === color.b) return true;
    }
  }
  return false;
}
```

三处诚实标注：①`clipContains` 用的是**命令自带 clip**（录命令时的 scissor 快照——第三阶段的裁剪烘焙）；②文本不判定——probe 对文本区域返回 null，测「文本遮住了背景色」要用「背景色取不到」反证；③2px 降采样对小色块可能漏采——regionHasColor 用于「大色块存在性」，单点用 pixelAt。

**断言范本**（pixel-probe.test 全 8 条的编制法）：


## 附录 E：像素探针的性能账（为什么它只在测试里用）

pixelAt 最坏 O(命令数)/次取色，regionHasColor 是 O(采样数 × 命令数)——按 06 册压测口径（2000 命令显示列表）算：

```text
单次 pixelAt 最坏：2000 次判定 ≈ 10μs 级
regionHasColor(100×100)：2500 采样 × 2000 命令 = 5×10⁶ 判定 ≈ 20ms 级——一条断言 20ms
```

为什么不能二分提速：命令流**按绘制序不按空间序**排列，且每条 clip 各异——空间索引（R-tree/网格）对测试代码是负资产（测试要「明显慢但绝对对」，不要「快但有索引 bug」）。测试预算的定位：探针断言单测 <50ms/条、全库 204 断言 <30s——L3 的 8 条探针贡献约 100ms，占比健康。**测试代码的性能标准是「总时长可接受」而非「算法最优」**——这句是给毕业项目写测试时的预先豁免。

## 附录 F：黄金用例的反例集（绿但错的四种形态）

手算-断言对会失败在「对不上」；更危险的是**绿但错**：

| 形态 | 症状 | 例子 | 防御 |
|---|---|---|---|
| 断言同义反复 | 期望值是从代码里抄的 | 期望值写成 `list.lineCount` 而非字面量 3 | 手算值写死为字面量（纪律五的另一半） |
| 手算本身错 | 断言与实现一起错向 | 行宽公式漏 gap，期望也漏 gap | 两处独立推导（09 专题手算表的「先纸后码」） |
| 弱断言 | 断言真但没锁住不变量 | 只断 children.length 不断几何——demo08 bug 2 全绿漏网 | 断言三件套（尺寸+位置+失效） |
| 时序耦合 | 换执行顺序就红 | 手工设 focused 后再测路由 | 回放走真实路由（纪律一） |

demo08 的 bug 2 是「弱断言」的教科书案例：无头测试断 children.length 与 liveRows——**它锁的是「挂了几个」，不是「挂在哪、多大」**。防御不是多写断言，是每条断言问自己「什么 bug 会逃过这条断言」。四形态自查放进毕业项目门 1 的 PR 清单。

```text
   （MINI_GUI_SECONDS=2 MINI_GUI_SHOT=... --dev + 日期 + 机器口径）
2. 比对：重跑后逐字节比（filecmp 同异）——有差 → 人工看并排 diff 图
```

成本记账（为什么探针为主、快照为辅）：基线跨平台不可移植（字体栅格化差异，04 册 font.ts 的候选表换字体即全变）；每次改主题/调间距都要重录基线（人工一步）；diff 图审读无法自动化（要人眼）。探针无基线、无审读——**点态事实归探针，整体观感归快照 + 人眼**：§2 结论的操作化，也是本框架不默认做快照 CI 的诚实理由。

## 附录 H：探针断言的失败信息设计（失败可读性三行格式）

```ts
expect(pixelAt(list, 50, 30), `期望 ${fmt(RED)} 实测 ${fmt(pixelAt(list, 50, 30))} @ (50,30)——按钮背景中心`);
```

失败信息三要素：**期望值、实测值、探针点的语义上下文**（「按钮背景的中心」而非裸坐标）——没有上下文的 `expect null toEqual RED` 要在脑内重建整棵布局树才能定位；有上下文的一行直接指出「哪个元素的那一面丢了」。黄金用例纪律「注释即推导」在探针上的对应物：**坐标即推导**——每个探针点旁注明它想证明什么。vitest 的 expect 第二参数（自定义消息）是探针测试的强制项（pixel-probe.test 全 8 条都带）；毕业项目的像素断言沿用此格式（门 1 的「探针 ≥2 条」验收含可读性检查）。

## 附录 I：测试资产的维护成本账（204 断言的重构敏感度分级）

| 断言族 | 数量级 | 对什么重构敏感 | 敏感度 |
|---|---|---|---|
| 手算布局断言（四布局器） | 19+ | 布局公式改动 | 高（应然——公式的回归网） |
| 失效账断言（pipeline/场景） | ~20 | 失效传播机制 | 高 |
| 回放断言（焦点/编辑/手势） | ~15 | 事件路由接线 | 中（约定变则测试变） |
| 像素探针 | 8 | 调色板 / 绘制层序 | 中 |
| 控件与池化（widgets/scene） | ~15 | 控件内部实现 | 低（观测口隔离） |

读法：**敏感度 ≠ 坏**——高敏感断言就是回归网的本职（改布局公式就该炸一片）；坏的是「对无关重构敏感」（脆）。观测口（liveRows/mainOverflow/colWidths）的存在意义就是把脆压到最低：断言读自报告值而不是 peek 私有字段。全库 30 秒内跑完 → 高敏感的重构成本可控（改什么立刻知道炸了什么，改完 30 秒知道全貌）。

## 附录 J：工程三陷阱：测试方法的三个高危现场

**陷阱一：把「直接调方法」当集成证据（绕过路由的绿）**

- 触发场景：给 TextField 写「编辑」测试时直接 `tf.onKey(keyEvent(...))`——widgets.test 的单元层写法。错不在写法本身（L1 单元就该这么写），错在把它当成「输入链路没问题」的证据。
- 根因：直接调用绕过了焦点路由（focus.dispatchKey 的可聚焦检查、focused 守卫、沿父链冒泡）与手势状态机（gestures 的双击窗口判定）。demo08 缺陷①（焦点标志不同步）正是这个形态——各自直接调全绿、窗口键入无反应，路由层缺陷对直接调用天然免疫。
- 规避：分清两句话——「这个控件的编辑逻辑对不对」用直接调（L1）；「这套接线能不能把键送进来」用回放（scene.focus.dispatchKey，widgets-scene.test 范式）。两句各配各的测试，前者不能顶替后者。

**陷阱二：frame 之前读布局产物**

- 触发场景：mount 之后立刻断言 size / textLayout / 子几何——读到的全是构造默认值（宽高 0）。
- 根因：布局只发生在 flushLayout（帧循环里），mount 只开欠条不排版。观测口读数有前置条件——owner.frame() 至少跑过一次。vdom.test 的 flush helper（mount 完立即 frame）就是把这一步固化进 helper，让每个用例不必靠记性。
- 症状：断言红得莫名其妙（期望 30 实测 0）；更糟的变体是断言被改成「大于等于 0 就行」——碰巧过的弱断言（附录 F 形态三的近亲）。
- 规避：几何断言的前置动作写进装配 helper（flush / buildXxxScene 返回前 frame 完）；review 时看到 size 断言，先向上找 frame 调用再读期望值。

**陷阱三：回放后不 frame 就探针（读到上一帧的显示列表）**

- 触发场景：回放一次点击 → 立即 pixelAt 断言按钮变色——拿到的是改动之前的命令流。
- 根因：改动只开欠条，欠条要等下一帧 frame() 消化，显示列表（边界图层）是 flushPaint 的产物。与陷阱二同源但发生在绘制通道，还多一层：如果本次改动触发重入欠账（布局结果又引发新布局），要 frame 两次才收敛——第六册 §6 的观察手段是 layoutPasses 连续加二。
- 规避：「回放 → frame → 探针」写成固定三段式节奏；对收敛帧数有疑虑的用例 frame 两次再断言，并把「为什么是两帧」写成注释——时序注释是给下一个改失效系统的人留的路标。

## 决策速查表：一个缺陷该派哪层测试去抓

| 缺陷形态 | 首选层 | 断言形态 | demo08 对应 |
|---|---|---|---|
| 布局算术错（公式/钳制） | L1 黄金用例 | 手算字面量三件套 | —（四布局器全靠它） |
| 失效账错（多标/漏标/错通道） | L2 无头集成 | repainted / layoutPasses 对账 | pipeline 失效组 |

| 视觉存在性（色块、z 序） | L3 探针 | pixelAt / regionHasColor | — |
| 几何完整性（挂上了但零高零宽） | L2 几何断言 + L4 截图 | width/height 字面量 + 人眼 | 缺陷②③ |

## 手算/走查配方：为一次改动配三件套的五步编制法

配方：给「虚拟列表滚动一格」配 L2 三件套（挂载参数沿 widgets.test：300×200、行高 40、万行数据）。

1. 列不变量：滚动不改池大小、不改节点身份、只改绑定与位置、失效走 paint 通道；
2. 选层：不变量全部无头可观测 → L2（复用 widgets.test 的 list() 装配）；
3. 手算期望（字面量）：handleWheel(1) → scrollTop = 0 + 40 = 40；first = floor(40/40) = 1；need = min(ceil(200/40) + 2, 10000) = 7；绑定区间 [1, 7]；池行 0 的新标签「1: row 1」；maxRowSeen = 7；
4. 断言三件套：身份（children 与滚动前逐项相同）、几何（池行 0 的 y = 1×40 − 40 = 0，顶到视口顶）、失效（frame 后 repainted ≥ 1）；
5. 失败信息带语义：每个 expect 附「滚动一格后池行应重绑到区间 1..7」式的上下文（附录 H 的坐标即推导纪律）。

```ts
vl.handleWheel(1);
expect(vl.liveRows).toBe(7);                                // 池大小不变
expect(vl.children).toEqual(before);                        // 节点身份不变
expect((vl.children[0] as RowProbe).label).toBe("1: row 1"); // 手算字面量
expect(vl.maxRowSeen).toBe(7);
```

自验：40 与 40 整除故 first = 1、区间 [1, 7] 共 7 行、行 0 的 y = 40 − 40 = 0——每一步可独立纸推。这条测试与 widgets.test 现有的「滚动 1000 行」互补：那边验长程不漂移（maxRowSeen 在 106 到万之间、children 身份恒定），这边验单格精确账。编制法的浓缩版就是第 5 节的黄金用例纪律加一个动作——**期望值永远先出现在纸上，再出现在代码里**。

## 与真实框架对照（概念对照）

| 本框架 | 生态对应 | 概念异同 |
|---|---|---|
| 黄金用例（手算-断言对） | 各端 table-driven 单测 / Flutter matcher | 同构：期望值独立于实现推导 |
| 事件回放（SyntheticEventSource、focus.dispatchKey） | Flutter WidgetTester 的 sendKeyEvent、React Testing Library 的 user-event | 同构：测试自己当事件源；差异在覆盖的路由层深度 |
| 像素探针（DisplayList 虚拟取色） | golden file 快照、端到端截图比色 | 探针是「点态、无基线」路线；快照是「整屏、有基线」路线 |
| 失效账对账（repainted / layoutPasses） | Flutter 的 repaint rainbow 计数、调试统计直读 | 同一思想：把框架内部计数当公共断言面 |
| bench 阈值（中位 / p95 上限） | CI 性能回归门 | 共同纪律：计时进阈值门，不进随机断言 |

概念对照的读法：五类资产在主流生态里都有亲戚，本框架的特殊性只在**无头程度**——DisplayList 与失效计数是内核自带的一等观测面，于是 L2/L3 可以完全不开窗口跑（全库 30 秒）。对毕业项目的含义一句话：给新控件配测试时先问「这条断言能不能不开窗口」，把 L4 留给只有真渲染才暴露的几何与接线——§4 那张四缺陷检出矩阵，就是这句口号的完整成本表。

## 附录 K：四层的「抓不到」清单与成本档位

每层的价值都可以反过来读：它抓不到什么。四层各自的盲区与档位（成本口径沿用本册既有数字）：

| 层 | 抓不到的缺陷 | 为什么抓不到 | 单次成本 |
|---|---|---|---|
| L1 单元 | 接线/路由缺陷、时序缺陷、渲染结果 | 直接调用绕过路由；无 frame 无显示列表 | 毫秒级/条 |
| L2 无头集成 | 像素层错误、原生后端差异、ScriptC 编译期陷阱 | L2 消费的是纯 TS 内核；编译器差异只有原生编译暴露 | 毫秒级/条 |
| L3 探针 | 「存在但不可见」（零高/零宽）、文本覆盖区、字体渲染正确性 | 零高矩形无像素可取；text 命令不做字形判定 | 约 20ms/条（附录 E） |
| L4 窗口实跑 | 廉价回归（慢、人工、无内部账） | 只有外部观感，探不到 pendingBoundaries 这类内部状态 | 2 秒/次 + 人眼审图 |

读这张表的方法是把 §4 的检出矩阵竖过来：矩阵回答「这个 bug 是谁抓到的」，本表回答「这个 bug 为什么恰好只有它能抓」。三条推论：其一，任何一层的盲区都恰好是邻层的职责——「逻辑归 L1/L2、几何归 L4、接线归 L2」的分法不是偏好而是互补结构的必然；其二，L3 的盲区（零高不可见）解释了为什么 bug 2 需要几何断言补位——**像素断言测「画成什么样」，几何断言测「有没有资格画」**，两层合起来才覆盖渲染链；其三，L4 的不可替代性只值六个缺陷里的五个（附录 D 时间线），所以「交付前真跑窗口」是抽查级纪律而非全量级——L4 永远不该是回归网的主体。

## 附录 L：像素探针的纸面走查（两条黄金用例逐命令手算）

**用例一：遮挡（pixel-probe.test 的「后画的盖前画」）**。命令流两条：fillRect(0,0,100,100) 红、fillRect(40,40,30,30) 蓝。

```text
pixelAt(list, 50, 50)：倒序扫——先遇蓝矩形：40 ≤ 50 < 70 含 (50,50) → 返回蓝 ✓（最上层）
pixelAt(list, 10, 10)：蓝矩形不含（10 < 40）→ 继续；红矩形 0 ≤ 10 < 100 含 → 返回红 ✓
pixelAt(list, 200, 200)：两条都不含 → 循环走完 → 返回 null（= 背景）✓
```

**用例二：描边边带（strokeRect 判定式的代入）**。命令 strokeRect(10,10,50,50) thickness 4：外带 = x 从 8 到 62（10−2 起、50+4 宽），内芯 = x 从 12 到 58。

```text
点 (10,10)：在外带内（8 ≤ 10 < 62）且不在内芯内（10 < 12）→ 返回描边色 ✓
点 (30,30)：在外带内、也在内芯内（12 ≤ 30 < 58）→ 不算边带 → 继续扫 ✓
```

再配 regionHasColor 的一笔采样账：区域 100×100、步进 2 → 采样点 x、y 各取 0,2,…,98 共 50 个值 → 2500 次采样，每次 pixelAt 最坏扫全命令流——附录 E「一条断言 20ms 级」的算术来源就是这两个数的乘积。三步走查的价值在失败一侧：探针断言红了的时候，按「倒序第一命中」的规则从命令流末尾往回推，第一条几何覆盖该点且未被裁剪的命令就是实测色的来源——失败调试与编制用例用的是同一张纸。

## 附录 M：L4 窗口抽查的最小作业程序（两分钟版）

L4 贵且不可省（§4 的结论），贵就贵在人工——所以它必须是**清单驱动**的抽查，不是「跑起来看一眼」。两分钟作业程序七步：

1. 跑窗前写下本次要验证的要素清单（对着上次的问题写，例如「滚动条 thumb、聚焦框高亮」）；
2. `MINI_GUI_SECONDS=2 MINI_GUI_SHOT=shot.png` 跑对应 demo（附录 C 的 window-smoke 脚本）；
3. HUD 数字逐项读：frames 与 elapsed 的比值、稳态 repainted 是否为 0、passes 与 frames 的关系（passes = frames + 1 的定义量不破）；
4. 截图逐要素过（demo08 口径：池行、缘条、滚动条、聚焦输入框、HUD、布局间距——一项一勾，不合并）；
5. 交互抽查各来一次：滚轮滚动、Tab 走焦点、按钮点击——键入与指针路径只有 L4 有真实宿主；
6. 截图与上一版并排比（人工看，或走附录 G 的基线流程）；
7. 记录：日期、机器口径、新发现——写进 demo 注释或册子的实跑记录，让下一次的清单有据可依。

两条纪律的理由都要说得出：**为什么两秒够**——附录 D 的时间线里，窗口侧缺陷（键入无反应、列表空白、启动即崩）都在启动后前几秒内暴露，两秒窗口加一次交互抽查的检出面已经覆盖它们；**为什么逐项勾选**——bug 2 那种「画面上看着该有东西的位置实际空白」，人眼扫一遍是抓不住的，眼睛也会「看了没看见」，清单是给人眼用的防漏断言。L4 的产出物因此是「一份勾选记录」而不是「一次运行」——记录进册子，才与全库断言构成同一张回归网。
