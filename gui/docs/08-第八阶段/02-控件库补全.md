# 02. 控件库补全：TextField 的完整解剖

> [返回：第八阶段导览](01-导览.md)
> 对应大纲条目：第八阶段 1（TextField 光标选区、开关类控件、Dialog/Overlay、菜单）。
> 本册走读 `core/widgets/text-field.ts`（175 行）——第三阶段光标几何（offsetToX/xToOffset）承诺的兑现现场，外加 demo08 集成时**实抓的两个内核缺陷**（焦点标志不同步、池行记账缺 height）。读完你应当能：手推任意按键序列的光标与文本状态、说清桌面 IME 的边界、列出「键盘可完整操作」的验收面。

## 1. 概念坐标：TextField = 光标几何 + 键盘编辑 + 焦点

```text
第三阶段（文本）：layoutText / offsetToX / xToOffset —— 量与映射，当时承诺「第五阶段输入框直接用」
第五阶段（事件）：FocusManager / dispatchKey —— 键盘路由
第八阶段（本册）：RenderTextField —— 把两者焊在一起：
    键码 → 编辑动作 → 文本/光标变更 → markNeedsLayout/Paint
    点击 → xToOffset（中点吸附）→ 光标落位
```

字段表（逐字要点）：`text`（内容）、`caret`（0..len）、`textLayout2`（第三阶段 TextLayout，paintSelf 与 xToOffset 共用——**私有字段命名 `textLayout2` 避开与基类 `layout` 方法撞名**，ScriptC 命名冲突的实测规避）、`focused`（基类 RenderObject 的标志，第八册 §4 讲它差点失灵）。

## 2. 键码表：raylib 数值的平台无关封装

```ts
  static readonly KEY_BACKSPACE = 259;
  static readonly KEY_DELETE = 261;
  static readonly KEY_RIGHT = 262;
  static readonly KEY_LEFT = 263;
  static readonly KEY_HOME = 268;
  static readonly KEY_END = 269;
  static readonly KEY_ENTER = 257;
  static readonly KEY_KP_ENTER = 335;
```

键码常量收在类上（对照第五阶段散在 focus.ts 的同款数值）：编辑键的语义归属控件，不该由路由层知道。可打印区 `code >= 32 && code <= 126`（ASCII）——**CJK 走 IME，教学版明确不接**（第 6 节的边界账）。

## 3. 编辑操作全表：光标与文本的状态机

`onKey` 的完整分支（逐字语义，手算用例直接代）：

| 键码 | 动作 | 光标变化 | 文本变化 | 失效通道 |
|---|---|---|---|---|
| Backspace(259) | 删光标前字符 | caret-1（若>0） | 移除 [caret-1, caret) | layout（→级联 paint） |
| Delete(261) | 删光标后字符 | 不动 | 移除 [caret, caret+1) | layout |
| ←(263) | 左移 | max(0, caret-1) | — | paint only |
| →(262) | 右移 | min(len, caret+1) | — | paint only |
| Home(268) | 行首 | 0 | — | paint only |
| End(269) | 行尾 | len | — | paint only |
| Enter(257/335) | 提交 | — | 触发 onSubmit | — |
| 32..126 | 插入字符 | caret+1 | 前插 ch | layout |

三条失效纪律在表里可见：**移动光标只标 paint**（几何没变，只是光标画在哪）；**改文本标 layout**（宽度可能变 → 父排列可能变）；**onChanged 回调只在真正改文本时发**（`afterEdit` 统一出口）。手算用例（widgets.test 逐条）：`"abc"` 光标 0 → End → ← → Delete 得 `"ab"` → Backspace 得 `"a"`——三条通道（layout/paint/回调）在四个动作里各出现一次。

**光标初始在 0 不是在尾**——demo08 集成时测试第一版就栽在这里（按 H 得到 "Hedit me" 而非 "edit meH"）。约定写死：程序化聚焦不动光标，用户点击/方向键才移动；要尾插先按 End。

## 4. 焦点标志：demo08 实抓的内核缺陷

onKey 第一行守卫（逐字）：`if (!this.focused) return false;`——`focused` 是**节点上的标志**。demo08 集成时发现：`FocusManager.focusNode(field)` 只更新了**管理器侧**的 `this.focused` 引用，**节点侧的 `focused` 标志从没被点亮**——键全被守卫吞掉，文本纹丝不动。第五阶段的焦点测试能过是因为测试手工设了 `tf.focused = true`（绕过了缺陷）。

修复（focus.ts，逐字）：

```ts
    // 管理器侧引用 + 节点侧标志必须同步点亮/熄灭——
    // 之前只记管理器侧，控件自身的 focused 守卫永远不亮（demo08 集成实测抓到）
    const prev = this.focused;
    if (prev !== null && prev !== node) prev.focused = false;
    if (node !== null) node.focused = true;
```

配套的内核改动：`focused = false` 从 TextField 上移到 **RenderObject 基类**（与 canFocus 配对——焦点是节点级概念，任何可聚焦控件都要这个标志，不该每控件自declare）。这个 bug 的教学价值：**单元测试全绿 ≠ 集成可用**——第五阶段的焦点单测、第八阶段的 TextField 单测各自通过（各自手工设标志），拼起来才发现路由层没人点灯。「无头全绿 + 窗口必验」的纪律（第六册 §2）第三次兑现。

## 5. 点击定位与 paintSelf

点击（逐字语义）：命中点的窗口 x 减去**沿父链累加的自身偏移**得局部 x → `xToOffset(textLayout2, 0, localX, measurer)` 中点吸附 → caret。与绘制共享同一套坐标合同（paint 局部坐标 = 窗口 − Σ偏移）——命中与绘制对齐的又一次兑现（第五阶段修过的「命中对绘制错」在这里的正面应用）。

paintSelf 四层（逐行）：边框（聚焦 accent / 失焦 border）→ 底色（聚焦时 lerp 微亮）→ 文本（12,10 起，fontSize）→ 光标（聚焦时 `12 + offsetToX(layout, 0, caret)` 处 2×(h-16) accent 竖条）。第三阶段的两个几何函数在 paint 与 hit 各用一次——**「测量=绘制」铁律**保证两个函数拿到同一个 layout。

## 6. 明确不做的边界（IME 与选区）

| 不做 | 为什么 | 工程化路径 |
|---|---|---|
| IME 合成中态 | ScriptC/raylib 无输入法事件面（拿不到 preedit/preedit-cursor） | 平台层补 ime 事件 → 控件加 preedit 槽 |
| 选区拖拽 | 需要 shift+点击/拖拽手势 + 选区绘制（第三阶段 span 着色可复用） | 手势层加 drag-select → anchor/focus 两光标 |
| 剪贴板 | raylib 有 GetClipboardText/SetClipboardText，教学版未接 | Ctrl+C/V/X 三键 + 系统剪贴板直通 |
| 多行 | 单行布局（textLayout2 单行）；多行 = 每行一个 TextLayout + 行游标 | 第三阶段断行器的直接复用 |

「明确不做」不是偷懒清单，是**边界声明**：毕业项目的文本编辑器选型（07 册）会用这张表倒推工作量。

## 8. 本册小结

- TextField = 第三阶段光标几何 + 第五阶段焦点路由的焊接点；`textLayout2` 命名规避与基类 layout 撞名
- 键码表收控件、编辑操作四通道失效纪律（移动→paint、改文→layout、提交→回调、插入→layout+onChanged）

- 焦点标志双面同步（管理器引用 + 节点标志）是 demo08 实抓的内核缺陷；`focused` 上移基类与 canFocus 配对
- IME/选区/剪贴板/多行四项明确不做，各留工程化路径——边界声明是选型依据

## 附录 A：RenderTextField 全量源码走读（分段）

**构造与字段**（逐字）：

```ts
export class RenderTextField extends RenderObject {
  private text = "";
  private caret = 0;                    // 光标 offset（0..len）
  private fontSize: number;
  private measurer: TextMeasurer;
  private textLayout2: TextLayout | null = null;   // ← 命名避开与基类 layout 方法撞名
  focused = false;                      // （第八册 §4 后改由基类声明）

  constructor(fontSize: number, measurer: TextMeasurer) {
    super();
    this.fontSize = fontSize;
    this.measurer = measurer;
    this.canFocus = true;               // 可聚焦：FocusManager 的收集条件
  }
```

五个字段、一个构造三行——控件的「状态面」就这么小。`canFocus = true` 是焦点系统的注册方式（focus.ts 的 collectFocusables 按 it 收集）。

**setText 与光标钳制**（逐字）：

```ts
  setText(t: string): void {
    this.text = t;
    this.caret = clamp(this.caret, 0, t.length);   // 程序化改文不动光标语义，只钳合法性
    this.markNeedsLayout();
    this.markNeedsPaint();
  }
```

**onKey 全分支**（逐字，第 3 节状态机的源文本）：

```ts
  onKey(ev: KeyEvent): boolean {
    if (!this.focused) return false;               // 守卫：非聚焦不消费（集成缺陷的案发现场）
    const code = ev.code;
    if (code === RenderTextField.KEY_BACKSPACE) {
      if (this.caret > 0) {
        const head = this.text.slice(0, this.caret - 1);
        this.text = head + this.text.slice(this.caret);
        this.caret -= 1;
        this.afterEdit();                          // 统一出口：标脏 + onChanged
      }
      return true;                                 // 消费（不冒泡）
    }
    if (code === RenderTextField.KEY_DELETE) {
      if (this.caret < this.text.length) {
        this.text = this.text.slice(0, this.caret) + this.text.slice(this.caret + 1);
        this.afterEdit();
      }
      return true;
    }
    if (code === RenderTextField.KEY_LEFT)  { this.caret = Math.max(0, this.caret - 1); this.markNeedsPaint(); return true; }
    if (code === RenderTextField.KEY_RIGHT) { this.caret = Math.min(this.text.length, this.caret + 1); this.markNeedsPaint(); return true; }
    if (code === RenderTextField.KEY_HOME)  { this.caret = 0; this.markNeedsPaint(); return true; }
    if (code === RenderTextField.KEY_END)   { this.caret = this.text.length; this.markNeedsPaint(); return true; }
    if (code === RenderTextField.KEY_ENTER || code === RenderTextField.KEY_KP_ENTER) {
      const cb = this.onSubmit;
      if (cb !== null) cb(this.text);
      return true;
    }
    if (code >= 32 && code <= 126) {               // 可打印 ASCII（IME 边界见 §6）
      const ch = String.fromCharCode(code);
      this.text = this.text.slice(0, this.caret) + ch + this.text.slice(this.caret);
      this.caret += 1;
      this.afterEdit();
      return true;
    }
    return false;                                  // 未消费：冒泡给父（快捷键等）
  }

  private afterEdit(): void {
    this.markNeedsLayout();
    const cb = this.onChanged;
    if (cb !== null) cb(this.text);
  }
```

读法四点：①「消费/不消费」的返回值语义——未识别键 return false 让父链继续（快捷键系统的挂点）；②Backspace 与 Delete 的字符串切片互为镜像（caret-1 前删 / caret 后删）；③onChanged 只在文本真变时发（光标移动不发）；④ScriptC 的字符串拼接没有复合赋值——`head + this.text.slice(...)` 是全量重建（O(n) 每键，万字符文本每键 O(n)——工程化加 rope/span 缓冲，教学版明账）。

**点击定位与绘制**（逐字）：

```ts
  onPointerDown(ev: PointerEvent): void {
    if (this.textLayout2 === null) return;
    let wx = 0;                                    // 沿父链累加自身偏移（与绘制同一坐标合同）
    let node: RenderObject | null = this;
    while (node !== null) { wx += node.x; node = node.parent; }
    this.caret = xToOffset(this.textLayout2, 0, ev.x - wx, this.measurer);
    this.markNeedsPaint();
  }

  protected paintSelf(p: Painter): void {
    const border: Color = this.focused ? PALETTE.accent : PALETTE.border;
    const bg: Color = this.focused ? lerpColor(PALETTE.surface, PALETTE.accent, 0.06) : PALETTE.surface;
    p.fillRect({ x: 0, y: 0, width: this.width, height: this.height }, border);
    p.fillRect({ x: 1, y: 1, width: this.width - 2, height: this.height - 2 }, bg);
    p.text(this.text, 12, 10, this.fontSize, PALETTE.text);
    if (this.focused && this.textLayout2 !== null) {
      const cx = 12 + offsetToX(this.textLayout2, 0, this.caret, this.measurer);
      p.fillRect({ x: cx, y: 8, width: 2, height: this.height - 16 }, PALETTE.accent);  // 光标
    }
  }
```

绘制四层与聚焦态两档（边框色 + 底色微亮 lerp 0.06）——「聚焦态可见性」是无障碍的最低配：键盘用户靠它知道输入去哪了。光标 x = 左内边距 12 + 第三阶段 offsetToX——**承诺兑现的一行**（第三册注释「第五阶段输入框直接用」）。

## 附录 F：光标状态机的三组纸上推演（自测 1 的完整答案）

练习一（删改混合，widgets.test 序列的推广）——`"abc"` 光标 2 起：

| 步 | 按键 | text | caret | 失效通道 |
|---|---|---|---|---|
| 0 | — | `abc` | 2 | — |
| 1 | Delete | `ab` | 2 | layout + onChanged |
| 2 | End | `ab` | 2（len=2，已在尾） | paint only |
| 3 | Backspace | `a` | 1 | layout + onChanged |
| 4 | 输入 X | `aX` | 2 | layout + onChanged |

注意第 2 步：End 在已行尾时 caret 不变，但 onKey 分支**仍然 markNeedsPaint**——光标移动没有做「同值短路」（每按一次多一条光标命令的重画）。这是明账优化点：先比较 caret 是否真的变了再标脏，可省稳态连按的重画（对照第七阶段 setText 的同值短路——同一条纪律在控件层的缺席处）。

练习二（边界对撞）：空文本 `""` 光标 0——Backspace（`caret > 0` 不成立）、Delete（`caret < len` 不成立）、←/→（钳制后原值）**四个键全部消费且全部无效**（返回 true 保持吞键不冒泡）。黄金用例的边界行从这里出（第五册纪律三：空容器行从不缺席）。

练习三（点击中点吸附）：`"ab"` 每字符 advance 8px，点击局部 x=12：候选边界 0/8/16，12 恰在 8..16 的中点 → 吸附 offset 2（≥中点向右取）——**吸附方向是约定不是推导**，必须写死并在测试里断言（widgets.test 的「点击定位」条就是这条锚点；换实现时它是回归参照）。

## 附录 G：组合键的路线图（Shift+Left 选区纸面稿）

附录 B 说 modifiers 已在事件结构上、控件未消费——接上它需要的最小状态机（毕业选题 C 的第一步）：

```text
状态新增：anchor: number | null（选区锚点；null = 无选区）
Shift+Left：anchor === null ? anchor = caret（先记锚）：不动；caret = max(0, caret - 1)
Shift+Right：对称（caret = min(len, caret + 1)）
无 shift 的移动键：先清 anchor（选区塌缩到 caret）
Backspace/Delete（有选区）：删 [min, max) 区间，caret = min——不再按单字符分支走
渲染：选区高亮 = anchor..caret 区间先画底色带再画文本（第三阶段 span 着色直接复用）
```

五条状态迁移 + 两条派生——选区的工作量集中在**迁移完整性**：每个移动键都要处理「有选区时无 shift」的塌缩分支，漏一个就是悬挂选区 bug（高亮残留但语义已丢）。这就是 §6 边界表给「选区拖拽」留两条工程化路径的原因：状态机小、分支面大——典型的「状态少、迁移多」控件，用黄金用例的边界行一条条锁（Shift 组合 × 8 个移动键 = 8 条最小用例）。

## 工程三陷阱

三个坑都来自「单测各自绿、拼起来才露馅」或「教学边界挡不住真实入口」——与 §4 的复盘同族，但每条是独立病灶。每条给触发场景、根因（带读码收据）与规避。

### 陷阱一：Tab 路径的焦点标志仍未双面同步（读码实据）

- **触发场景**：两个输入框 A、B，用户按 Tab 把焦点从 A 切到 B，然后键入、看边框。
- **根因**：`src/core/events/focus.ts` 里双面同步（`prev.focused = false` 加 `node.focused = true`）只写在 `focusNode` 里；而 `focusNext/focusPrev` 的落点 `applyIndex` 仍然**只写管理器侧**——方法体三行：取节点、`this.focused = node`、推日志，节点侧标志既不点亮也不熄灭。这正是 §4 那个缺陷的原始形态，在 Tab 路径上原样存活：修复覆盖了抓到 bug 的那条路径，没覆盖**所有写焦点的地方**。
- **症状的分层**（为什么它难查）：键入**能用**——`dispatchKey` 的冒泡链从管理器引用出发，路由不读节点标志；但**视觉**全错——paintSelf 用节点侧 `this.focused` 决定边框色与光标显隐，于是 A 的边框还亮着、B 看着没聚焦、光标画在 A 里。「功能对、状态显示错」是集成缺陷里最难定位的一类，无头单测若只断言键路由就抓不到。
- **规避**：`applyIndex` 复用 focusNode 的双面同步（或直接改成调用 focusNode）；测试口径——焦点类断言必须**同时**断言管理器引用与节点标志两个面，缺一个面就复刻一遍 demo08 的教训。

### 陷阱二：代理对被 Backspace 砍半

- **触发场景**：程序化 `setText` 注入含 emoji 的文本（比如用户名里带 U+1F600，UTF-16 占两个 code unit、`length === 2`），光标停在其后按一次 Backspace。
- **根因**：caret 与 `text.length` 都是 UTF-16 code unit 口径，onKey 的删除是 `slice(0, caret − 1)` 一次砍一个 code unit（text-field.ts Backspace 分支原文）——对代理对而言，第一刀只砍掉高位代理，留下孤立的低位代理挂在字符串里。
- **症状**：删一次出现乱码（渲染层画出替换字形或空白），再删一次才干净；onChanged 多发一次中间态回调——若上游拿它做持久化，存进库里的是半只字符。注意 §6 的「不接 IME」边界挡不住这条：入口是 `setText` 不是键盘，教学版自键入 32..126 的 ASCII 永远不产生代理对，**程序化注入即触发**。
- **规避**：删除前判 `charCodeAt(caret − 1)` 是否落在高位代理区（0xD800 到 0xDBFF），是则步长取 2；或把 caret 升级为 code point 口径并统一换算函数。更狠的兜底是输入与注入两侧都锁 ASCII——但要写进边界文档（§6 的表加一行），别让调用方以为随便 setText 都安全。

### 陷阱三：每键双 O(n) 的线性退化

- **触发场景**：单框注入万字符文本后连续键入，输入延迟随文本长度线性上涨。
- **根因是两处叠加**：其一，onKey 的字符串编辑是 `head + this.text.slice(...)` 全量重建（附录 A 读法四点已记账：每键 O(n)）；其二，`performLayout` 每次都调 `layoutText` **全量重测**（text-field.ts 布局段第一行，无任何增量缓存）——每键 afterEdit 标 layout，下一帧对整条文本重测一遍 advance。字符串重建加测量重建，每键两遍 O(n)。
- **症状**：`layoutPasses` 计数完全正常（失效纪律没标错），但单趟布局耗时在涨——只看趟数的性能观测会漏掉它，「趟数不等于耗时」在控件层的活例（度量口径见 [06-性能度量](../06-第六阶段/06-性能度量.md)）。
- **规避**：工程化三步——文本缓冲换 rope 或 span 结构（改哪补哪）、字符 advance 表缓存并增量更新、TextLayout 只在文本真变时重建。教学版保留 O(n) 是附录 A 的明账；毕业选题若做编辑器（[07-毕业项目](07-毕业项目.md) 选题 C），这张账必须翻。

## 决策速查表

| 决策点 | 选项 | 选它的条件 | 避开它的条件 |
|---|---|---|---|
| caret 口径 | UTF-16 code unit（现状，随 text.length） | 纯 ASCII 场景、教学版 | 要支持 emoji 或增补平面字符——升 code point 口径（陷阱二） |
| 删除步长 | 固定 1 | 键入侧锁 ASCII 时成立 | 文本可能含代理对——先判高位代理再定步长 |
| 光标失效通道 | paint only（§3 表） | 移动光标：几何没变、只是光标画在哪 | 光标位置开始参与裁剪或滚动联动——升 layout 通道 |
| 文本失效通道 | layout（afterEdit 统一出口） | 一切文本变更（宽度可能变 → 父排列可能变） | 只改视觉层（选区高亮、占位提示色）→ paint |
| 聚焦入口 | 点击、Tab、程序化 focusNode 三入口并存 | 程序化聚焦不动光标（§3 约定） | 「聚焦顺带清空或置尾」的隐式行为——demo08 测试第一版栽的坑 |
| 光标移动短路 | 不比较直接标 paint（现状） | 教学版：省一次比较 | 高频连按（长按方向键、手柄）——附录 F 练习二的优化点，先比较 caret 变没变 |
| 长文本缓冲 | 全量字符串 + 全量重测 | 百字符内、低频输入 | 编辑器类选题——rope 或 span 缓冲 + 增量测量（陷阱三） |
| 组合键接入 | 控件侧消费 modifiers（附录 G 路线图） | 需要选区或剪贴板时 | 全局快捷键——走父链冒泡（onKey 返回 false 的出口），不进控件 |
| 键码归属 | 收在控件类上（KEY_BACKSPACE 等静态常量） | 编辑键语义归控件（§2 的取舍） | 路由层感知具体键码——焦点系统只认 Tab 与冒泡 |
| 光标闪烁 | 不做（常亮竖条，仅聚焦时画） | 教学版与极简场景 | 工程化必做——AnimatedValue 或定时器驱动 paint 通道（对照真实框架表的差距二） |
| onSubmit 之后 | 什么都不做（控件只发事件） | 表单语义归上层组件 | 控件自作主张清空或缓存——隐式副作用（聚焦侧已犯过一次的病） |
| 文本长度上限 | 不设限（教学版明账） | demo 与测试场景 | 有真实用户输入的工程——上限加钳制加提示，陷阱三的退化从源头挡掉一半 |

## code review 检查单

审输入类控件代码按这 9 条过，每条对应本册或附录出现过的具体病灶：

- [ ] 事件入口第一行有守卫（`if (!this.focused) return false` 口径）：非聚焦不消费；返回值的消费语义（true 截断冒泡、false 放行父链）在每个分支都正确。
- [ ] 每个分支的失效通道对号：改文本走 layout、移光标走 paint、提交走回调不发失效——通道标错的现象是「改了不重排」或「重排了没必要」（§3 三条纪律）。
- [ ] caret 每次变更后仍在 0..len 区间：移动分支的钳制、setText 的 clamp，两处都要在。
- [ ] 状态变更有没有同值短路：对照第七册 setText 的守卫——光标移动是已知缺席处（附录 F 练习二），新增字段不许再欠这笔账。
- [ ] 边界行覆盖：空文本四键全消费且全部无效、行尾按 End 不动、点击中点吸附方向——三条黄金边界（附录 F）进测试。
- [ ] 回调纪律：onChanged 只在文本真变时发、onSubmit 不改控件状态；回调触发时机在标脏之后（回调里抛异常不阻断失效链）。
- [ ] 焦点写入点全部双面同步（管理器引用 + 节点标志）——新增任何写焦点的地方都要过这一条（陷阱一）。
- [ ] 每键成本有没有隐性 O(n)：字符串重建与测量重建两条都要查（陷阱三）；文本长度上限有没有声明与钳制。
- [ ] 命中与绘制共用同一坐标合同与同一 TextLayout（私有槽 `textLayout2`）：测量的 advance 与绘制的偏移必须同源，否则回到第五阶段「命中对绘制错」的老病。

## 反模式对照

| 反模式 | 症状 | 正确做法 |
|---|---|---|
| 键码数值散落路由层：dispatcher 里写 259 判断退格 | 换平台/换键码表要全局搜数字；控件不可复用 | 键码常量收控件类上（§2），路由层只认 Tab 与「是否有人消费」 |
| 失效通道一把梭：改什么都 markNeedsLayout | 光标移动也全树重排，帧账本 layout 次数虚高 | 按变更性质分通道（§3 表）：几何变才 layout，纯外观 paint |
| 回调里做重活：onChanged 直接同步写盘或重排整页 | 每键一次重活，输入卡顿；回调抛异常可能截断后续失效 | 回调只转发轻事件，重活丢给信号/异步层；标脏先于回调（afterEdit 的顺序） |
| 借别人的失效：指望 HUD 或邻居每帧标脏带重自己 | 邻居一优化，自己冻结——动画册陷阱一的同族病 | 控件自己标脏（afterEdit / 光标分支各自收尾），不依赖外部节拍 |
| 隐式聚焦副作用：focusNode 顺带清空或全选 | 调用方 unknowingly 丢内容；demo08 第一版现象的镜像 | 聚焦只改焦点状态；内容操作是显式 API（setText/clear），各走各的 |
| 边界靠手感：不加边界用例，靠手点 | 空文本四键、代理对、中点吸附方向全成回归雷区 | 黄金用例的边界行制度化（[05-测试方法](05-测试方法.md) 纪律三），附录 F 三组推演直接改造成断言 |
| 忽略返回值语义：父节点明明处理了键却返回 false | 键被父链重复消费，一次按键两次生效 | 消费即 true、未消费即 false——每个分支显式 return（onKey 全分支的既有纪律） |
| 焦点日志当唯一调试手段：只看 FocusManager.log | 日志只记管理器侧视角，节点标志的错位看不见——陷阱一正藏在这层盲区里 | 断言两个面加窗口视觉验证（第六册「无头全绿 + 窗口必验」纪律的第四次兑现） |

## 手算/走查配方

**配方一：一次键入的完整链路账**（从物理键到像素，七个站点）。背景：文本 "edit me"、光标在尾（刚按过 End），焦点在本框，按一次字符键 H（code 72）：

1. **事件产生**：宿主循环从平台层取键，包成 KeyEvent（code + modifiers）送进 `FocusManager.dispatchKey`（apps/08-widgets.ts 的接线，widgets-scene 同构）。
2. **路由决策**：Tab 先被焦点系统吃掉（本例不是 Tab）；然后从管理器侧 `this.focused` 起沿父链逐节点调 onKey——焦点节点先吃。
3. **守卫**：field.onKey 第一行 `if (!this.focused) return false`——这一步依赖节点标志被正确点亮（陷阱一的现场）。
4. **分类**：72 落在 32..126 → 插入分支：slice 拼接前插 "H"、caret 加一、afterEdit。
5. **回调**：afterEdit 先 markNeedsLayout 再发 onChanged("edit meH")——回调只在文本真变时发、且在标脏之后（检查单第 6 条的顺序依据）。
6. **布局**：flushLayout 重排本框 → performLayout 里 layoutText 全量重测（陷阱三的 O(n) 现场）→ textLayout2 换新；布局完成级联标 paint。
7. **绘制**：paintSelf 四层重画——光标 x = 12 + offsetToX(textLayout2, 0, caret)；caret 在尾时 offsetToX 等于整条文本 advance 合（第三阶段几何函数的兑现点）。

对账：本键成本 = 1 次 O(n) 字符串重建 + 1 次全量重测 + 1 次 layout + 1 次 paint + 1 次 onChanged。对照按一次 End：仅第 1 到 3 步加 paint——无重建、无重测、无回调。两列账并排，三条失效纪律（§3）就不再是背诵条目。

**配方二：组合键选区状态机纸上推演**（附录 G 状态机的第一组实算）。文本 "hello"、caret 5、anchor null：

1. Shift+Left：anchor 为 null → 先记 anchor=5；caret = 4。状态：text "hello"、caret 4、anchor 5（选区 [4,5)）。
2. Shift+Left：anchor 已有 → 保持 5；caret = 3。选区 [3,5)。
3. Backspace（有选区）：删 [3,5) 区间 → text "hel"；caret = min = 3；anchor 塌缩（置 3 或 null，迁移表第 5 条的约定点）。
4. 失效：layout（文本变了）+ onChanged("hel")；渲染侧选区高亮带清零（anchor..caret 区间画底色的那条路径不再命中）。
5. 边界外推：caret 0 时 Shift+Left → caret 保持 0、anchor 记 0、选区空区间 [0,0)——高亮带零宽不可见但 anchor 已立；此时直接按 Backspace（无选区语义）走单字符分支删不到东西——与附录 F 练习二的「全消费全无效」边界同构。

每个键一个迁移，每步断言三件事：text、caret、anchor——三变量状态机的黄金用例就从这两条配方里出。

**配方三：帧统计对账练习**。§7 实跑窗口那行统计的每个数字都有出处：frames=115 是 60fps 两秒少掉的 5 帧（首帧装配与截图开销）；layoutPasses=116 与 paintPasses=116 是「每帧各跑一趟 flush」的**趟数口径**——趟数不等于实际工作量，根没脏时布局缓存直接跳过（owner.ts 里 flushLayout/flushPaint 各自在入口加一的实现）；repainted=0 是稳态真没重画——hud 同文本 setText 短路、无光标命令、无滚动；liveRows=8 是虚拟列表只挂可见窗口。对账练习：给「用户正在键入」的同一张表手推预期——repainted 至少出现一次重录（文本框有脏必录，若它不在重绘边界内则上溯到最近边界或根），layout 趟数不变但实际重排发生——再回配方一的链路账逐站点核对各计一次，这张对账表就是 [06-性能度量](../06-第六阶段/06-性能度量.md) 账本条目的控件版。

## 与真实框架对照（概念对照）

| 教学版机制 | 浏览器 input（概念对照） | Flutter EditableText（概念对照） | Qt QLineEdit（概念对照） | Chromium 编辑器（概念对照） |
|---|---|---|---|---|
| onKey 键码分派编辑动作 | beforeinput/input 事件 + 默认行为拦截 | Intent/Action 体系：键盘意图与控件解耦 | QKeyEvent + 内建 undo 命令栈 | 编辑命令器统一受理按键 |
| caret 为 UTF-16 offset | selectionStart 同为 code unit 口径——代理对问题在 Web 同样存在 | TextSelection 用 code unit，删除按 grapheme 走 | 光标以字符计，内部按 Unicode 处理 | selection 以 code unit 存、以 grapheme 呈现 |
| 不接 IME（§6 边界表） | compositionstart/update/end 三事件 | 平台 TextInput 插件承载 composing | inputMethodEvent 携带 preedit | IME session 分 preedit 与 commit 两阶段 |
| xToOffset 中点吸附定位 | caretRangeFromPoint | TextPainter 的 getPositionForDownstream（含 upstream/downstream 口径） | 光标点检索内建于控件 | 位置命中走行盒模型 |
| paintSelf 画光标竖条 | caret-color 定制 | RenderEditable 自绘 caret | 控件内画光标 | 合成层的 caret 实现 |
| onChanged 只报真变更 | input 事件（每次编辑必发） | onChanged（控制器监听） | textEdited 信号 | 事件上报带编辑范围 |

三点口径差值得带走。其一，**UTF-16 caret 口径不是教学版偷懒**：浏览器的 selectionStart 同口径，陷阱二的代理对问题在真实 Web 上以 Intl.Segmenter 或 grapheme 库的形式解决——口径是一致的，补丁是通用的。其二，教学版光标**不闪烁**、无 composition 中态，这是与表内所有真实框架共有的两条差距；工程化时先做闪烁（定时器驱动 + paint 通道，动画册的 AnimatedValue 可直接复用）再做 IME（平台事件面，[04-平台细节](04-平台细节.md) 的边界清单里留了口子）。其三，**消费/冒泡的最小形**：Flutter 用 Intent/Action 把「按键意图」与「控件处理」解耦，教学版 onKey 的返回值就是这套体系的极简版——理解了返回值语义，Intent 体系只剩「意图对象化」一层皮。
