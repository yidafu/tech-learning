> 本册收第七阶段的尾：Effect.stop 作为生命周期钩子的最小面、ThemeTokens 查表式的主题实现、单向数据流的回路纪律，以及 reactive-scene demo 的窗口实测数据（2026-11-14）。读完你应当能：说清「热切换主题为什么不重建树」的完整链路、指出 dispose 缺失会在哪泄漏、把 token 纪律迁移到任何新控件。

## 1. Effect.stop：生命周期钩子的最小面

第三册已经读过 stop 的机制（`stopped = true`，run 短路，订阅边不摘）。本册从**生命周期**角度重新审视它：effect 的创建 = 挂载（首次 run + 建立订阅），`stop()` = 卸载（从此不再被调度）——这就是声明式世界里的 didMount/unmount 对：

```ts
// 挂载即订阅：组件装配时创建 effect
const bound = effect(() => { counterText.setText([{ text: `count: ${count.get()}` }]); });
// 卸载即停止：控件销毁时
bound.stop();
```

三条纪律（从机制反推的工程规则）：

| 纪律 | 理由 | 违反后果 |
|---|---|---|
| **谁创建谁 stop**：effect 的生命周期 ≤ 创建它的组件 | 订阅边不摘（第三册的取舍），死 effect 靠标志短路 | 组件销毁后 effect 仍被调度收集（白付遍历），且闭包捕获的渲染对象无法回收 → 内存泄漏 |
| **stop 之后不要再 set 依赖它的状态会怎样** | 短路在 run 入口，收集阶段它照旧入列（`collectInto` 没查 stopped！） | 每波一次空收集——小泄漏；`effects.indexOf` 清单里躺着死项 |
| **回调里创建的 effect 必须可触达**（存成员/返回句柄） | 局部 effect 没人能 stop | 同上，且是永久泄漏 |

第三条值得展开：`collectInto` 的实现（第三册逐字）里 effect 层去重用 `effects.indexOf(this) < 0`，**没有检查 stopped**——被 stop 的 effect 若仍被订阅图覆盖，每波照样进清单、run 时才短路。这是「stop 不摘边」取舍的另一面：**运行成本省了，收集成本还在**。彻底修法是 stop 时沿自己的 deps 摘订阅边（O(依赖数)），工程化清单（毕业项目）里留了这一条。

对照表：

| 钩子 | mini-gui | Flutter | React（react 站） |
|---|---|---|---|
| 挂载 | Effect 构造（首次 run） | initState | useEffect(fn, []) |
| 卸载 | `stop()` | dispose | useEffect 返回的清理函数 |
| 每帧 | tick（动画）/ effect 调度 | build | render |
| 依赖摘除 | 不摘（标志短路） | ChangeNotifier.removeListener | 每次依赖数组变化先跑清理 |

「标志短路 vs 真摘边」是教学与工程的分水岭：React 的清理函数模式把摘除责任交给用户（useEffect 返回 cleanup），Flutter 的 dispose 是框架回调。mini-gui 的 stop 是两者中更简的那个——**代价诚实写在这**：长会话高频创建/销毁 effect 的界面（列表虚拟化、动态弹窗）会积累死订阅，必须配摘边才算工程闭环。

## 2. 主题即 token 表：ThemeTokens 的完整链路

reactive-scene.ts 的主题（逐字）：

```ts
interface ThemeTokens {
  bg: Color;
  text: Color;
  muted: Color;
}

const LIGHT: ThemeTokens = { bg: rgba(245, 246, 248), text: rgba(31, 35, 40), muted: rgba(89, 99, 110) };
const DARK: ThemeTokens  = { bg: rgba(24, 26, 31),  text: rgba(230, 237, 243), muted: rgba(145, 152, 161) };

const theme = (): ThemeTokens => (dark.get() ? DARK : LIGHT);
```

三件套的设计决策：

**① token 是普通对象，不是响应式对象**。响应式的锚点只有一个：`dark` 是 `SignalB`——主题对象本身（LIGHT/DARK）是不可变常量，`theme()` 是普通函数，每次 render() 时调用。**响应式只住在「选择哪个主题」这一层**，token 值不订阅、不传播——切换主题走的是粗粒度路径（render() 重新执行 → 整树 reconcile），不是「每个颜色一个信号」的细粒度路径。

**② 颜色以值传到 VNode**：`color: t.muted` 进 VNode 描述，经 updateElement 的**同值守卫**落到渲染对象——「暗色切换后 200 个文本对象只有颜色字段真的变了」才会 markNeedsPaint。同值守卫在这里的收益形状变了：不是「颜色没变就不标」（切换主题时颜色全变），而是**跨波幂等**——同一主题下每波 render() 产出的都是相同颜色值，守卫把「重放 render」的写放大归零。

**③ 主题态与业务态分离**：`count/items` 是业务，`dark` 是呈现——都在 signals 层，但消费点不同（细粒度文本 vs 粗粒度整树）。这个分层没有机制强制，是**纪律**：token 只被 render() 读、控件永不直接查主题。

## 3. 热切换全链路：点一下 theme 按钮

手推 `dark.set(!dark.get())` 的完整旅程（这是本册的核心手算）：

```text
1. dark.set(true)：SignalB 通知订阅者
2. 订阅者是谁？——粗粒度 effect（fn = comp.update(render())），它运行时读了
   render() 里的 dark.get()（经 theme()）+ items.get() + ……全部收进它的订阅
   counterText 的细粒度 effect 只读了 count ——不在此列，不会被调度
3. 粗粒度 effect.run() → render() 重算：
   theme() 返回 DARK；每个 text VNode 的 color 变成 DARK.muted
   → comp.update(新 VNode 树) → keyed 协调（05 册）
      - 六个按钮：同 kind 无 key 按位复用 → updateElement
        label 同值短路；onClick 新闭包重新布线（值比较不适用闭包）
      - 列表文本：同 keyFor 复用 → setStyle(color: DARK.muted) —— 就地改样式！
4. 失效账：每个变色的渲染对象 markNeedsPaint（paint 通道，非 layout）
   ——颜色不影响布局，无一次 markNeedsLayout
5. flushPaint：重录的边界 = 有变色内容的最小重绘边界 + 祖先链
6. 呈现：根图层重放——界面已换肤，树没有重建（六个按钮的渲染对象原样）
```

**「不重建树」的三个证据**：①六按钮的 VElement 身份保留（keyed/按位匹配都在同 kind 分支）；②渲染对象只走 setStyle/字段赋值；③失效通道只有 paint。对照反面写法「主题变化时整树 dispose + remount」：所有焦点/动画状态丢失、冷帧成本全额重付——token 表 + 就地更新的组合是「热切换」的全部机制。

窗口实跑（07-reactive，2026-11-14，60fps）：点 theme 后 waves +1、下一帧 HUD 刷新、截图验证背景/文字色全部翻转且按钮位置不动——六要素截图分析逐项过。帧数 116/2s 与切换前无差（热切换成本 ≈ 一次粗粒度协调 + 全屏 paint，量级 1ms 内）。

## 4. 单向数据流：回路纪律

第七阶段的数据流是单向的圆环（mermaid 在导览里画过，这里加文字规则）：

```text
signal（唯一可变状态）
  → effect/render()（读：产出 VNode 描述）
  → update/reconcile（diff + 应用）
  → RenderObject（失效机器消化）
  → 控件回调（onClick 等）→ 只允许调用 signal.set
  → 回到环首
```

三条铁律（从机制反推）：

1. **回调只写信号，不碰渲染对象**。reactive-scene 的六个按钮（逐字）：`onClick: () => count.set(count.get() + 1)`——没有一个按钮直接 setText/markNeedsPaint。回路必须在 signal 处合拢，否则「两份账本」的命令式宗罪（第二册）从后门回来。
2. **render() 里禁止写**。render 被粗粒度 effect 每波调用，若 render 里 set（哪怕是防御性 set），effect 内写自己订阅的信号 → 死循环。教学版没有机制拦截（react 用 StrictMode 的双调用逼你暴露），只有纪律——工程化时值得加「render 中 set 抛错」的调试断言。
3. **读用 get、写用 set，不摸 value 字段**。`count.value = 5` 绕过 notifySubs——不传播的写等于没写（更糟：状态变了视图没变，难查）。TS 可以把 value 设为 private + get/set 方法；教学版字段公开 + 纪律约束（ScriptC 对访问器支持有限）。

## 5. 对照与迁移

| 机制 | mini-gui | Flutter | Web |
|---|---|---|---|
| 主题载体 | Token 对象 + render 查表 | `Theme.of(ctx)`（InheritedWidget 沿树下发） | CSS 自定义属性（变量） |
| 切换成本 | 粗粒度协调 + 全屏 paint | 依赖 Theme 的子树 rebuild | 变量继承，浏览器自动重绘 |
| 热切换保树 | keyed 复用（VElement 身份） | Element 树复用（同 widget 类型） | DOM 不重建 |
| 生命周期 | Effect.stop | dispose | (React) cleanup |
| 数据流 | 单向环（signal→render→reconcile→回调→set） | 单向（setState→build） | 单向（state→render→event） |

迁移纪律（把这套带回任何项目）：**token 只在 render 查、状态只在 signal、回调只 set**——三句话与具体框架无关。CSS 变量方案的「切换不重建」与本节机制同构（变量在层叠里求值，DOM 不动）；Flutter 的 InheritedWidget 是「依赖沿树登记」的另一实现（它有机制化的 dependOnInherited，mini-gui 用粗粒度 effect 的隐式订阅替代）。

## 6. 本册小结

- Effect.stop = 最小生命周期面：构造即挂载、stop 即卸载；订阅边不摘 → 收集成本仍在，彻底修法（摘边）留给工程化
- 主题 = 不可变 token 对象 + 一个 SignalB 锚点 + render 查表——响应式只住「选哪个」，token 值不订阅
- 热切换全链路手算：dark.set → 粗粒度波 → keyed 复用 → setStyle 就地改色 → 全 paint 通道 → 树不重建（六按钮身份保留）
- 同值守卫在主题场景的新价值：跨波幂等——重放 render 的写放大归零
- 单向数据流三铁律：回调只 set、render 禁写、get/set 走方法不摸字段——没有机制强制，全是纪律（render 内 set 值得加调试断言）
- 窗口实测：切换帧成本毫秒级、waves+1、六要素截图全过

## 自测

1. 「stop 不摘边」的两面（运行省、收集在）——推演一个「列表每秒创建/销毁 10 个 effect」的场景，一分钟后每波多付多少收集成本？摘边实现要遍历什么？
2. 为什么 `counterText` 的细粒度 effect 在主题切换时不会被调度？它的订阅清单里有什么、没有什么？
3. 手推：若把主题实现改成「每个 token 一个 Signal」（bgS/textS/mutedS），热切换链路会变成什么样？失效账与现在差在哪？哪种更适合「只有局部控件参与主题」的界面？
4. 单向流铁律 2（render 禁写）——构造一个「render 里防御性 set」导致死循环的具体代码，并说明为什么机制层没有拦（教学版拦截器怎么写？）。
5. 「回调只 set」如果违反（按钮 onClick 里直接 setText），第六阶段的失效机器还能兜住吗？视觉对不对？那违反的代价到底是什么（用第二册的两份账本概念回答）？
6. 同值守卫在主题切换场景是「跨波幂等」——如果 token 里含非值类型（如回调表/字体句柄），幂等还成立吗？守卫的比较策略要不要分层（值比 ===、对象比引用）？
7. 把本册三铁律迁移到你熟悉的前端框架，逐一找到对应物（谁在当 signal、谁在当 render、回调是否只写状态）；有哪条在你的框架里是机制强制的？

## 附录 C：单向流违规的三个事故样本（伪码）

**样本一：回调直接摸渲染对象**

```ts
{ kind: "button", label: "+", onClick: () => {
    count.set(count.get() + 1);
    counterText.setText([{ text: `count: ${count.get()}` }]);  // ← 多余且有害
} }
```

害处：细粒度 effect 也会因 count 变化被调度 → setText 跑两次（一次手动一次订阅）→ 同值短路救了第二次，但「两份账本」已成型：哪天细粒度 effect 被改名/删除，手写那行没人记得它是唯一来源——视图悄悄失联。

**样本二：render 里防御性 set**

```ts
const render = (): VNode => {
  if (count.get() > 100) count.set(100);   // ← render 内写！
  ...
};
```

后果：粗粒度 effect 的 fn 里 set(count) → count 通知订阅者 → **包含自己在内的 effect 重新入列** → 无限循环（教学版无「render 中禁止 set」断言，真会转死）。修法：钳制逻辑放进 computedN（cappedCount = computed(() => min(count.get(), 100))）——写逻辑住信号层，render 保持纯读。

**样本三：绕过 get/set 摸字段**

```ts
count.value = 42;   // ← 不通知！
```

状态变了、视图不动——比崩溃更难查。三个样本的共同教训：**回路的完整性依赖每个参与者守规矩**，框架层能拦的（render 内 set、value 直写）在工程化阶段应补调试断言（开发模式抛错，生产模式放行）。

## 附录 E：死 effect 的泄漏检测方法

「stop 不摘边」的泄漏怎么被观测到？给收集清单加观测口（不改内核语义，纯测量）：

```ts
// dev 断言：每波统计参与收集的 effect 中 stopped 的占比
let deadPerWave = 0;
// 在 Effect.collectInto 里（教学版可包一层 wrapper effect 观测）：
//   if (this.stopped) deadPerWave += 1;
```

判读标准：稳态界面 deadPerWave 应为 0；持续 >0 且随操作增长 = 有组件销毁时漏 stop。定位法：给每个 effect 一个 debugName（构造参数），泄漏报告直接点名。工程化修法（毕业项目清单）：stop 时沿 deps 摘订阅边——每个被摘信号 `subs.splice(indexOf(this), 1)`，成本 O(自己的依赖数)；收益是收集遍历不再经过死节点、且渲染对象闭包可被 GC。**先观测再修**——没有 deadPerWave 数字之前，「要不要摘边」是品味之争，有了数字它是算术题。

## 附录 F：token 化改造清单（六步，可迁移）

把一个「颜色硬编码」的控件改造成主题可切换（任何栈通用）：

| 步 | 动作 | 自检 |
|---|---|---|
| 1 | 列出控件全部字面颜色 | grep 十六进制/rgba 字面量 |
| 2 | 语义化命名（bg/text/muted/accent…）——按**用途**不按色值 | 同用途多处引用必须同名 |
| 3 | 建 Token 接口 + 两套常量 | 接口字段 = 语义名集合 |
| 4 | 控件改为查表（构造参数或 render 查） | 字面量清零 |
| 5 | 切换入口：一个信号（如 dark）+ render 读表 | 切换不重建树 |
| 6 | 审计：切换波后 repainted 分布 = 变色控件数 | 同值守卫兜底幂等 |

第 2 步是设计决策的重心：`gray3` 是色值命名（换主题即失效），`muted` 是用途命名（换主题只换值）——token 化的本质是**把颜色从「视觉参数」升格为「语义承诺」**。

## 附录 G：与 react 站的对照实验设计

第三册实践任务 4（「同一个小场景，全量重渲染 vs signals 的更新次数计数对比」）的可执行设计：

```text
场景（两站同构）：100 行列表 + 一个计数文本 + 主题切换按钮
变量：每点一次 "+"，两站各记：重渲染组件数 / DOM(渲染对象) 操作数 / 实际失效通道数
测法：react 站用 Profiler 组件计 render 次数；本站用 waves + markNeedsXxx 审计钩子
预期：react 站 = 1 个组件重渲 + diff 全列表（O(100) 比较，DOM 0 操作——虚拟 DOM 的收益）；
     本站 = 1 次细粒度 setText（O(1)）+ 0 次粗粒度波（count 不订阅粗粒度面时）
结论形态：两站各自的最优场景（变更半径大 vs 小）用数字说话
```

实验的诚实预期：**react 站在这场景也不慢**（100 行的 diff 是亚毫秒）——对照实验的价值不是「谁更快」，是**把「更新粒度」从直觉变成三个可数的观测面**。这一课与第六册的度量课同源：先有观测口，再谈架构优劣。

## 附录 H：dispose 缺失的三个工程补法

「stop 不摘边 + VElement 无 dispose 钩子」在真实项目里的三种补法，按侵入度排序：

| 补法 | 做法 | 适用 |
|---|---|---|
| ① Host 级注册表 | 全局 effect 注册表（挂载点自动登记，attach 时按 owner 记账），销毁子树时统一 stop 其中注册项 | 想不动控件代码 |
| ② RAII 包装 | `effectAutoStop(fn, owner)` 返回带 owner 的句柄，owner 销毁回调里批量 stop | 控件自己管理 |
| ③ VElement.dispose 钩子 | reconcileChildren 卸载前调 child.dispose?.()（可选钩子，有就调） | 最正统，改协调器 |

三者都要回答同一个问题：**「谁在什么时机知道子树被卸载了」**。教学版里答案只有 reconcileChildren 的卸载循环（附录 A 的 detachElement）——所以 ③ 是机制上最自然的落点。工程补法之间的取舍其实是「显式生命周期 vs 容器托管」：React 走 ③（unmount 回调），Flutter 走 ②（State.dispose 手写），Vue 的 onUnmounted 是 ②③ 混合。mini-gui 的毕业项目建议从 ③ 起步——钩子可选（不破坏现有 358 行的 vdom），有状态控件（TextField/动画行）各自实现 dispose 调自己的 stop。

## 附录 I：render() 的成本剖面与惰性描述

粗粒度波每帧跑 render()——它的成本构成值得拆开：

```text
render() 每波：构造 11 个 VNode 对象（demo 实测）+ 6 个按钮闭包 + keyFor × 3
           = ~20 次小对象分配/波
60fps 下    = ~1200 分配/秒（年轻代压力，但量级极小）
```

对照大列表（1000 行 VNode + 闭包）：每波 ~3000 分配——仍然是微秒级构造，但 GC 频率开始可测。工程化的三个缓解台阶（按代价排序）：①惰性构造（只有 count 分区变了才重建那一段——分区函数 return 缓存引用）；②子树引用共享（不变的子树返回**同一引用**，reconcile 靠引用相等短路整棵比较——React memo 的思路）；③描述池（复用 VNode 对象，改字段）。教学版一个都不做，render() 每波全量构造——**先有 waves 与审计钩子的数字，再决定要不要做**（第六册方法论在此复用）。
