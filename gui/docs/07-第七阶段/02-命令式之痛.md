# 命令式之痛：为什么需要声明式层

> [返回：第七阶段导览](01-导览.md)
> 对应大纲条目：第七阶段 1（样板代码剖析、UI = f(state)、两条路线的抉择）。
> 本册以第五阶段的 interactive-scene 为解剖样本（`scenes/interactive-scene.ts`，258 行），数一数「改一处状态」要在多少个地方写代码；然后给出 UI = f(state) 的两条实现路线（全量重渲染 + diff / 细粒度依赖追踪），解释本课程为什么两条都要讲、而本站选择后者。实跑依据：`npx grep` 调用点统计 + `reactive.test.ts` / `vdom.test.ts`（2026-11-14 全库 25 文件 201 断言绿）。

## 1. 解剖样本：第五阶段的按钮发生了什么

第五阶段的交互场景（按钮三态 + 焦点环）有一个典型更新：鼠标悬停让按钮变色。命令式写法的完整链条（摘自 interactive-scene.ts，逐字结构）：

```ts
// 悬停进入
btn.isHovered = true;               // ① 状态字段
btn.markNeedsPaint();               // ② 手工标脏（绘制通道）
// 焦点环动画里……
btn.requestFocus();                 // ③ 手工维护焦点状态
btn.markNeedsPaint();               // ④ 又一次手工标脏
// 点击回调里……
counterLabel.setText(`count: ${n}`); // ⑤ 手工改文本
counterLabel.markNeedsLayout();      // ⑥ 手工标脏（布局通道）
counterLabel.markNeedsPaint();       // ⑦ markNeedsLayout 会级联，这行可省——但你知道吗？
```

三宗罪数得出来：

| 宗罪 | 表现 | 代价 |
|---|---|---|
| **状态与视图两份账本** | `count` 存在回调闭包里，`count: ${n}` 又抄进 setText | 两处必须人肉同步；漏一处就是「点了没反应」或「显示错误值」 |
| **标脏靠人脑** | 哪些通道要标（layout/paint）依赖记忆 | 标少了白改（显示不更新），标多了白付重排 |
| **没有合并语义** | 一个回调里改 5 个状态 → 5 次散装标脏 | 全靠帧尾一次 flush 兜底合并（第六阶段），代码层面看不出「这批是一个事务」 |

grep 实证（本仓 labs 全树）：`markNeedsPaint` 出现 41 处、`markNeedsLayout` 出现 37 处、`setText` 15 处——每一处都是「状态变更」与「失效声明」的手工配对。这不是写得差，是**命令式范式的固有税**：视图更新的责任分散在每一个改状态的现场。

## 2. UI = f(state)：把视图变成状态的函数

声明式的目标一句话：**视图是状态的纯函数，改状态 = 重算函数，其余全自动**。

```ts
// 期望的写法：状态 → 描述，没有第二条命令链
function render(): VNode {
  return h("column", { gap: 12 }, [
    h("button", { label: "-", onClick: () => count.set(count.get() - 1) }),
    h("text", `count: ${count.get()}`),
    ...
  ]);
}
comp.update(render());   // 状态一变，重新执行 render()，框架自己算增量
```

「其余全自动」里的「其余」是三件事：**重新执行**（拿到新描述）、**算差异**（新描述 vs 已挂载的树）、**应用差异**（只改需要改的渲染对象）。这三件事怎么实现，就是两条路线的分叉点：

| | 路线 A：全量重渲染 + diff | 路线 B：细粒度依赖追踪 |
|---|---|---|
| 代表 | React（react 站复刻过全量） | Solid / preact-signals / Vue |
| 重算单位 | 整棵 render()（函数组件级） | 读过该信号的精准订阅者 |
| diff 范围 | 新旧两棵 VDOM 树全遍历 | 无树级 diff——订阅关系直接指向更新目标 |
| 更新粒度 | 组件子树重渲 → 再 diff 到 DOM | 节点级：哪个 RenderText 变了就 setText 哪个 |
| 心智模型 | 「每次都从头描述，diff 保证最小变更」 | 「谁读了你，谁就自动更新」 |
| 代价 | 大树上的 O(n) 遍历每次都要付 | 依赖图维护成本；动态依赖（条件读取）要重建 |

## 3. 为什么本站两条都提、实现选 B

react 站的源码复刻已经把路线 A 讲透了（Fiber 全量 diff、reconcile、双缓冲）。本站如果再实现一遍路线 A，两站重复；选路线 B 的三个理由：

**① 与本站内核正交且互补。** 自绘内核的更新粒度天然是「节点级」（RenderObject 上的 markNeedsXxx）——细粒度响应式与它**同构**：signal 变化直接映射到「哪个渲染对象标哪个脏」，中间不需要树级 diff 的翻译层。全量路线则要把 diff 结果再翻译成节点级操作，多一层。

**② 教学价值在依赖图。** 读时收集、写时拓扑传播、diamond 恰算一次（glitch-free）——这套机制是通用的响应式素养（Vue/Solid/preact-signals 底层都是它），学了到处能用；而 diff 算法在 react 站已有完整一册。

**③ demo 数字可直接对照。** 第七阶段 demo 同屏并存两种粒度（`reactive-scene.ts` 文件头注释原文：「粗粒度：effect(() => comp.update(render()))；细粒度：count 的 effect 直接 setText」）——计数器点一下，细粒度路径只碰一个 RenderText，粗粒度路径整树 reconcile 但 keyed 复用。**更新粒度变成可观测的量**（waves 计数器 + paintSelf 计数），这正是本站的实跑文化能吃到的红利。

## 4. 痛点的量化：变更半径对比

用「给计数器加一个上限 10 的约束」这个假想需求，数两条路线各要改几处：

```text
命令式（第五阶段形态）：
  ① onClick 回调里加 if (n < 10)
  ② 按钮的禁用态判断（如果做了三态）再加一处
  ③ 计数文本 setText 的格式（如果上限要显示"10/max"）再改一处
  → 3 处手工点，漏一处就是状态与视图脱钩

声明式（本阶段形态）：
  ① render() 里 count.get() 改成 cappedCount()
  （computedN 自动依赖上限信号；按钮态如果要跟着禁用，也是 render 表达式的一部分）
  → 1 处；视图是 f(state) 的一个表达式，改 f 就完
```

半径对比的本质：命令式把「视图 = 状态的投影」这件事**摊开**到了每个更新现场（所以要人肉保持同步）；声明式把它**收敛**成一个函数（改函数即可）。收敛的代价是框架要多做三件事（重算/差异/应用）——第七阶段后面四册就是把这三件事各拆一册。

## 5. 一个诚实的边界：声明式不消灭标脏

值得先打预防针：本阶段的声明式层**没有**取消 markNeedsXxx，只是把它从用户代码里拿走、交给框架的更新器。vdom.ts 的 updateElement 里（逐字摘录，第八册细读）：

```ts
    if (box.boxWidth !== v.width || box.boxHeight !== v.height) {
      box.boxWidth = v.width;
      box.boxHeight = v.height;
      box.markNeedsLayout();     // ← 框架替你标，标脏本身还在
    }
```

框架标脏的优势不是「没有标脏」，而是**标得准**：先比较（同值短路，不脏白付），再按属性归类通道（尺寸→layout、颜色→paint、文本→setText 内部自理）。命令式代码里「标脏靠人脑」的宗罪由一处集中逻辑终结——这处逻辑写对一次，全库受益。这也是为什么第七阶段叫「声明式**层**」而不是「声明式内核」：下面还是那台失效机器（第六阶段），上面只是换了个驾驶方式。

## 6. 本册小结

- 命令式三宗罪：状态与视图两份账本、标脏靠人脑、无事务语义——grep 实证 markNeedsXxx ×78 处分散配对
- UI = f(state) 的两条实现路线：全量重渲染 + diff（react 站）与细粒度依赖追踪（本站）；差异在「重算单位」与「diff 范围」
- 本站选细粒度的三理由：与自绘内核的节点级更新同构、依赖图机制通用、demo 可观测两种粒度并存
- 变更半径量化：加一个约束，命令式 3 处手工点 vs 声明式 1 处表达式
- 诚实边界：声明式不消灭标脏，只是把「标得准」的责任从每个现场收敛到框架更新器

## 附录 A：第五阶段的完整回调样本（命令式原貌）

interactive-scene.ts 里「按钮三态」的完整命令式链（结构摘录）：

```ts
class RenderButton extends RenderObject {
  label: string;
  hovered = false;
  pressed = false;
  focused = false;

  onPointerMove(ev: PointerEvent): boolean {
    const inside = /* 命中判断 */;
    if (inside && !this.hovered) {
      this.hovered = true;
      this.markNeedsPaint();              // ← 状态与标脏必须成对出现
      return true;
    }
    if (!inside && this.hovered) {
      this.hovered = false;
      this.markNeedsPaint();
      return true;
    }
    return false;
  }

  onPointerDown(ev: PointerEvent): boolean {
    this.pressed = true;
    this.markNeedsPaint();
    return true;                           // 消费：不让冒泡继续
  }
}
```

数一数「三态」的维护成本：三个布尔字段 + 三处事件回调 + **六次 markNeedsPaint**（每条状态迁移路径各标一次）。这就是「标脏靠人脑」的实体：hovered 的 enter/leave 两条路径、pressed 的 down/up 两条、focused 的进入/移出两条——漏掉任何一条就是一个可见 bug（悬停变色了不回退、按下态卡住）。声明式版本里这些字段全消失：按钮的样子是 `h("button", { label, pressed, hovered })` 的函数输出，迁移路径不再需要各自配对失效。

## 附录 B：demo 里两种粒度的并排源码

reactive-scene.ts 的两段 effect（逐字）——第七阶段的核心实验就在这两段的对照里：

```ts
  // 细粒度：计数文本只挂一个 effect，直接 setText
  effect(() => {
    counterText.setText([{ text: `count: ${count.get()}` }]);
  });

  // 粗粒度：整树 reconcile（主题/列表结构变化走这里）
  effect(() => {
    const node = comp.update(render());
    if (node.parent === null) stack.appendChild(node);
    waves.value += 1;
  });
```

同一个 `count` 信号，两个消费者：细粒度 effect 的 fn 只读 count → 只订 count → count 变化时**只跑这一段**（一次 setText，一个文本叶子失效）；粗粒度 effect 的 fn 读了 render() 里读过的一切（count、items、dark）→ 任一变化都触发**整树 reconcile**。观察它们的手段是 waves 计数器与 HUD——点 "+" 时两段都跑；点 theme 时只有粗粒度跑；细粒度不写也会因同值短路而零失效。**「粒度」不是框架给的，是订阅面画的**：fn 读什么，粒度就是什么。

## 附录 C：对照表——同一件事的两种写法

| 任务 | 命令式（第五阶段写法） | 声明式（第七阶段写法） |
|---|---|---|
| 按钮三态 | 3 字段 + 3 回调 + 6 次标脏 | `h("button", { label })`，样式是 label/pressed 的函数 |
| 计数显示 | 回调里 setText + 标脏 | `h("text", \`count: ${count.get()}\`)` |
| 滚动位置 | scrollBy 内部 placeContent + 标脏 | 滚动仍走命令式（渲染层属性，非状态） |
| 主题切换 | 逐控件遍历改色 | dark.set(!dark.get()) |
| 列表增删 | 手工 appendChild/removeChild | items.set(newArray)，keyed 协调 |
| 焦点管理 | 手工 requestFocus + 标脏 | （教学版仍命令式——焦点是命令式保留区） |

「滚动与焦点仍是命令式」这一行值得诚实面对：声明式不是宗教。**连续高频变化**（滚动/拖拽/动画）走属性通道更直接（不经过描述→diff，失效成本 O(1)）；**离散状态驱动的外观**（按钮三态、列表、主题）才值得走描述→协调。真实界面是两者的混合——本站 demo 自己就是（reactive-scene 里 counterText 挂渲染层、按钮走声明式）。

## 附录 D：痛点审计方法（拿任何代码库都能跑）

第二册的方法论沉淀——如何系统量出一个 UI 代码库的命令式税：

```bash
# ① 找标脏调用面（视图更新的手工税）
grep -rn "markNeedsPaint\|markNeedsLayout" src/ | wc -l
# ② 找「状态字段 + 文本同步」的双账本对
grep -rn "setText" src/ | wc -l
# ③ 事件回调密度（状态变更现场）
grep -rn "onPointerDown\|onClick\|onKey" src/ | wc -l
```

本仓第五阶段代码的实测（2026-11-14）：markNeedsXxx ×78、setText ×15、回调入口 ×23——**每 1000 行 UI 代码约 20 处手工配对点**。审计的判断标准不是绝对数（框架内部实现也调 markNeedsXxx，那是合法的），而是**分布**：调用点若集中在框架 render/ 内（合法），税为零；若散落在场景/控件层（本仓 scenes/ 目录，税全在）。把 ③ 的回调点逐个检查「回调里有没有直接 setText/标脏」——有即命中宗罪一（双账本）。这套审计跑在 react 站的旧代码上同样有效（grep setState 的分布），方法跨框架。

## 附录 E：UI = f(state) 的形式化一刻

把两条路线写进同一组符号，差异立刻显形：

```text
状态 s：视图可读的全部事实
描述 d = render(s)        ← render 是纯函数：同 s 必得同 d
已挂树 t（VElement 树 + 渲染树）

路线 A（全量）：s' 到来 → d' = render(s') → diff(t, d') → 补丁 t
路线 B（细粒度）：s' 到来 → 只重算「订阅了 s 的部分」→ 直接得出补丁
```

关键洞察：**两条路线的「补丁」是同一个东西**（渲染对象上的失效标记集合）——差异全在「怎么算出补丁」。路线 A 的 diff 是补丁推导器（通用、但每次全量遍历）；路线 B 的订阅图是**预计算的推导缓存**（每次只走受影响的边）。这解释了它们的一切实证差异：A 的成本 = render 全量 + 遍历（与变更无关），B 的成本 = 受影响子图（与变更半径成正比）。也解释了互补性：A 适合「变更半径大而频繁」（diff 摊销），B 适合「变更半径小」（直奔目标）。react 站与本站的分工在符号层面就是「diff 推导器」与「订阅图」的分工。

## 附录 F：为什么不选 MVVM/双向绑定

第三条路线（Angular/Vue 早期的双向绑定：视图字段 ↔ 状态字段双向同步）没有进入本课程的对比表，理由要诚实写清：双向绑定 = **两条单向流的叠加**（state→view 的渲染 + view→state 的表单同步），它没有消除第二册的「两份账本」，只是把同步自动化到绑定层。代价是同步逻辑的黑盒化（哪个输入改了哪个状态，IDE 里追不到）。本站选单向环（附录 C 的铁律）+ 信号（显式 get/set）的路线，与 React/Solid/Svelte5 的一致胜于与 Angular 的相似——教学立场：**宁可手写三行 set，不要一行不可追的黑盒同步**。真需要表单双向，在单向环上包一个「输入事件 → set」的小工具函数就够（第八阶段控件库的 TextField 就是这么接的：onChanged → count.set）。

## 附录 G：第三种粒度——渲染层直通区（混合架构的完整理由）

第二册说过「声明式不消灭标脏」，附录 C 的对照表里也留了两行命令式区（滚动/焦点）。这里把混合架构的判断标准写全——**什么时候该留在渲染层直通**：

| 判断维度 | 描述→协调 | 渲染层直通 |
|---|---|---|
| 变更频率 | 离散（点击/状态切换） | 连续（每帧：滚动/拖拽/动画） |
| 变更半径 | 可枚举的状态面 | 连续量（scrollY 一个浮点数） |
| 描述成本 | 值对象便宜 | 每帧构造整棵 VNode 树纯浪费 |
| 失效成本 | 波合并后 O(脏子树) | O(1)（属性赋值 + markNeedsPaint） |

reactive-scene 的滚动条、focus 环、动画面板**全部**留在第五阶段的命令式形态——它们每帧都变，走描述→diff 每帧多付一次 render() + 全树 reconcile（附录 waves=frames 的原因）。混合架构的一句话判据：**状态离散走声明式，量连续走直通；两者共用同一棵渲染树与同一台失效机器**。react 站在 scroll 上也是这个结论（受控滚动没有走 state）——两个范式在「哪里画线」上惊人一致。

## 附录 H：从命令式到声明式的迁移路线图（五步）

拿一个存量命令式界面迁移到第七阶段形态的操作序列：

| 步 | 动作 | 验收 |
|---|---|---|
| 1 | 跑附录 D 审计，圈出场景层的 markNeedsXxx/setText 现场清单 | 手工配对点计数在案 |
| 2 | 抽状态：散在闭包/字段里的计数、开关、列表 → 提升为信号 | 状态唯一来源（signal） |
| 3 | token 表：字面颜色→语义 token（第六册附录 F 六步） | 字面量清零 |
| 4 | 视图函数化：把「组装控件的代码」改写成 render() 返回 VNode | 回调只剩 set |
| 5 | 分区：连续变化区保留渲染层直通；离散区全走声明式 | 附录 G 的判据逐区过一遍 |

每步独立可验收、可回退——迁移不是重写，是**把两份账本合并成一份**的渐进过程。第五步的「分区」是精髓：迁移的终点不是「全声明式」，是「每处变更走它最便宜的通道」。

## 附录 I：本站在课程地图上的坐标（三站三角）

声明式层的知识在 tech-learning 站群里被刻意拆成三份，互为犄角：

| 站 | 覆盖 | 本站对应 |
|---|---|---|
| react 站（源码复刻） | 全量重渲染、Fiber/reconcile、双缓冲、调度 | 附录 E 的「路线 A」完整实现 |
| 本站（gui） | 细粒度 signals、节点级协调、与自绘内核同构 | 附录 E 的「路线 B」实现 |
| browser 站 | 渲染管线/合成器（描述怎么变成像素） | 两站协调结果的最终去处 |

三角的交汇点是「**描述 → 像素**」这条链：react 站与 Vue/Solid 的生态定位之争（框架层），本站的渲染对象与失效机器（内核层），browser 站的管线（宿主层）。读完三站，同一段 JSX/VNode 在你眼里应当展开成三张不同的账：订阅图（谁读了这个状态）、协调账（哪些身份保留）、管线账（哪些失效通道走了）。三份账在真实工程里同时发生——课程把它们拆开讲，是为了每张账都看得清。

## 附录 J：声明式的隐性成本（诚实账本）

声明式不是免费的，三笔隐性成本如实记：

1. **描述构造的分配压力**：每波 render() 新建 N 个 VNode 对象（本 demo 每波 ~11 个，大列表每帧几百上千）——JS 引擎的年轻代 GC 压力。waves=frames 的 demo 形态下每秒 60 波 × 每波 11 对象 = 660 对象/秒的分配率。工程缓解：惰性描述（只重建变化分区）、对象池、或「描述复用」（不可变树共享子树引用——React 的 memo 思路）。
2. **调试栈更深**：出问题时调用链是「信号 → effect → render → update → reconcile → updateElement → markNeedsXxx → flushLayout → flushPaint」八层——命令式时代是三层。观测口（waves/审计钩子）的存在价值在这里：**栈深补偿靠数据面**，日志里打印「本波变更哪些节点失效」比断点栈好查。
3. **抽象泄漏的反向税**：updateElement 的同值守卫让人忘记底层会失效——「为什么改了颜色没刷新」这类 bug 的根源往往是守卫比对了错误的相等（对象引用 vs 值）。纪律（第六册自测 6 的分层比较策略）就是为这最后一层准备的。

三笔成本都有对价：GC 换心智（不手工记账本）、栈深换粒度（更新自动分配）、守卫换安全（同值不失效）。**范式选择的本质是「哪种成本你付得起」**——这是本册最后一句，也是全阶段最实用的一句。

## 附录 K：一句话答案备忘（面试与 code review 即用）

把全册结论压成六条速答——每条都能独立站住：

1. **命令式的税 = 状态与失效的手工配对**——grep markNeedsXxx 的分布（框架内 vs 场景层）就是税表。
2. **UI = f(state) 两条实现**——A 全量 diff（react 站），B 订阅图直通（本站）；补丁相同，推导路径不同。
3. **选 B 的硬理由**——与保留模式内核的节点级失效同构，diff 终点即内核节点，无翻译层。
4. **粒度不是框架给的，是订阅面画的**——fn 读什么，粒度就是什么（附录 B 两个 effect 的实证）。
5. **变更半径**——加约束：命令式 3 处 vs 声明式 1 处表达式；离散走声明式、连续走直通（附录 G）。
6. **声明式有三笔隐性成本**（分配/栈深/守卫泄漏）——范式选择是「哪种成本付得起」（附录 J）。

这六条在本册各有一节完整的推导支撑；背结论不如背结论的出处——被追问时按「出处节号 → 源码行号 → 实测数字」的链条下钻。
