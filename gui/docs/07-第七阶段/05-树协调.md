## 1. 概念坐标：协调 = 身份分配

上一册的 updateElement 解决了「同类型节点怎么更新」；本册解决「**哪些新 VNode 对应哪些旧 VElement**」——即身份分配问题。三条规则（`vdom.ts` 注释原文）：

```text
同 key（双方都带 key 时必须相等）→ 复用（状态保留）
任一方无 key          → 按「第一个未占用的同类型」匹配
都没匹配上           → 新建（mount）
```

身份的价值在状态：VElement 保住了，它的渲染对象就保住了——焦点、动画中态、输入缓冲都在渲染对象/控件状态里。**复用 ≠ 快（省构造），复用 = 对（状态不丢）**——顺序要摆正。

## 2. reconcileChild：单子路径（三行判断）

```ts
function reconcileChild(el: VElement, v: VNode | null, m: TextMeasurer): void {
  const existing = el.children[0] ?? null;
  if (v === null) {                       // 新描述没孩子 → 卸载
    if (existing !== null) detachChild(el, existing);
    return;
  }
  if (existing === null) {                // 原来没孩子 → 挂载
    attachChild(el, v, m);
    return;
  }
  if (existing.vnode.kind !== v.kind) {   // 类型变 → 换子
    detachChild(el, existing);
    attachChild(el, v, m);
    return;
  }
  updateElement(existing, v, m);          // 同类型 → 原地更新
  existing.vnode = v;
}
```

「最小 reconcile」的单子版就这四个分支：无/挂、有/卸、异型/换、同型/更。注意单子路径**不看 key**——单子的身份就是「这个位置」，没有歧义。

## 3. reconcileChildren：列表路径全量走读

核心函数整段（逐字，注释保留）：

```ts
function reconcileChildren(el: VElement, newKids: VNode[], m: TextMeasurer): void {
  const oldEls = el.children.slice();
  const used: boolean[] = [];
  for (let j = 0; j < oldEls.length; j++) used.push(false);

  const kept: VElement[] = [];

  for (const nv of newKids) {
    let matched = -1;
    for (let j = 0; j < oldEls.length; j++) {
      if (used[j]) continue;
      const oe = oldEls[j]!;
      if (oe.vnode.kind !== nv.kind) continue;
      if (nv.key !== undefined || oe.vnode.key !== undefined) {
        if (oe.vnode.key !== nv.key) continue;  // 任一方带 key：必须相等才复用
      }
      matched = j;
      break;
    }
    if (matched >= 0) {
      used[matched] = true;
      const keptEl = oldEls[matched]!;
      updateElement(keptEl, nv, m);
      keptEl.vnode = nv;
      kept.push(keptEl);
    } else {
      kept.push(mount(nv, el, m));              // 新建
    }
  }

  // 卸载未复用的
  for (let j = 0; j < oldEls.length; j++) {
    if (!used[j]) detachElement(el, oldEls[j]!);
  }

  // 重排：先全部摘下、按新序挂回（渲染树上 remove+append 保持父指针）
  for (const child of el.children.slice()) {
    el.node.removeChild(child.node);
  }
  el.children = [];
  for (const child of kept) {
    el.children.push(child);
    child.parent = el;
    el.node.appendChild(child.node);
  }
  el.node.markNeedsLayout();
}
```

算法骨架：**对每个新 VNode 在旧 VElement 数组里线性找匹配**（key 优先、无 key 退化为「未占用的同类型」）→ 匹配上则 updateElement + 记 kept 顺序 → 没匹配上 mount 新建 → 收尾卸载未复用 + 按新序重挂。复杂度 O(new × old)（嵌套线性扫描）——教学版的诚实取舍，对照表在 §6。

三个语义细节：

1. **key 的不对称规则**（`nv.key !== undefined || oe.vnode.key !== undefined`）：只要**任一方**带 key，就必须 key 相等才算匹配——「旧的带 key、新的不带」不能偷偷按位置配对（否则身份语义会被无 key 的新项污染）。都无 key 才按位。
2. **匹配只看第一次命中**（`break`）：同 key 出现两次（使用者写错）时第二个会被当新键 mount——不去重不报错，教学版容忍这个坑（第 8 节列进「明确不做」）。
3. **重排用 clear + 重挂**而不是最小移动：`removeChild × n + appendChild × n`，O(n) 的树操作换代码极简。渲染对象没有「插入到第 i 位」的 API（appendChild 尾插），最小移动算法要设计索引维护——工程化课题（§6 对照 React 的可插拔移动策略）。

## 4. 手算三个场景（keyed 三断言的推演）

设旧列表 `[A(key1), B(key2), C(key3)]`，逐场景推 kept/detached/moves：

**场景一：头插 `X(key0)` → `[X, A, B, C]`**

```text
X(key0)：扫旧数组——kind 匹配但 key 不等（key1/key2/key3 ≠ 0）→ mount 新建
A(key1)：匹配 old[0] → updateElement(A) → kept=[A]
B(key2)：匹配 old[1] → kept=[A,B]
C(key3)：匹配 old[2] → kept=[A,B,C]
卸载：used[0..2] 全 true → 无
重挂序：A, B, C, X？——不对：kept 是按「新列表遍历序」push 的 → [X, A, B, C] ✓
断言：头插新 key，旧节点全部复用（测试 75 行）✓
```

**场景二：删中间 `B` → `[A, C]`**

```text
A → matched old[0]；C → matched old[2]（old[1] 是 B，key 不匹配被 continue）
卸载：used[1] = false → B 被移除
身份结果：A、C 的渲染对象原样保留，B 整棵丢弃
断言：「同 key 复用（删除中间项后其余节点身份不变）」✓
```

**场景三：轮转 `[A,B,C]` → `[C,A,B]`（shuffle 按钮的真实路径）**

```text
C(key3) → matched old[2]；A(key1) → old[0]；B(key2) → old[1]
kept = [C, A, B]（按新序）；卸载无
重挂：先摘 3 个、按 [C,A,B] 逐个 appendChild
身份结果：三个全复用——只是挂序变了；焦点在 B 上就跟着 B 走 ✓
断言：「顺序重排：节点按 key 跟随移动」✓
```

**场景四（无 key 退化）**：旧 `[text"α", text"β"]` → 新 `[text"β", text"γ"]`——都没有 key：新[0]"β" 匹配 old[0]"α"（第一个未占用同类型）→ **updateElement 把 α 的文本改成 β**；新[1]"γ" 匹配 old[1] → 文本 β→γ。节点全复用但内容全部改写——身份按位置分配的固有行为（测试 96 行「无 key 退化为按位同类型复用」）。这在「列表项带输入框」时会灾难：第 0 位输入的内容留在了第 0 位，跟内容挪动无关。

## 5. keyFor：内容派生 key 的实战

reactive-scene.ts 的列表（逐字，注释保留）：

```ts
  // 稳定 key：从标签内容派生（demo 内标签唯一）。用下标当 key 会让增删/换序
  // 失去身份追踪——beta(new,key0) 会错配 alpha(old,key0)，节点复用与状态保持
  // 全部失效（实测踩过）。
  const keyFor = (label: string): number => {
    let h = 7;
    for (let i = 0; i < label.length; i++) h = h * 31 + (label.charCodeAt(i) % 97);
    return h;
  };
```

**下标 key 事故**的手算（注释说的那个坑）：`[alpha, beta]` 用下标 key（0,1）→ 删头后 `[beta]` 的新描述 key=0 → 匹配旧 key0（**alpha 的节点**）→ updateElement 把 alpha 的文本改成 beta——**身份错配**：如果 alpha 行有输入框/焦点/动画，用户看到的是「beta 长着 alpha 的状态」。内容派生 key（hash(label)）在「内容唯一」的列表里给出稳定身份——删头后 beta 的 key 不变，匹配 beta 自己的旧节点，alpha 被正确卸载。

key 的三条使用纪律（从场景四与 keyFor 注释提炼）：

| 纪律 | 违反后果 |
|---|---|
| key 用**内容身份**（id/唯一标签），不用下标 | 增删/换序时状态错配（上面的 alpha/beta 事故） |
| 同列表内 key 唯一 | 重复 key 的第二个被静默 mount（不报错） |
| 同一列表的 key 策略统一（全带或全不带） | 「任一方带 key 即必须相等」规则会拆散旧的按位配对 |

## 6. 与 React diff 的对照

| 机制 | mini-gui（教学版） | React（react 站复刻） |
|---|---|---|
| 匹配算法 | 每新项线性扫旧数组，O(new×old) | 同层单向遍历 + key→index 映射，O(new+old) |
| key 判定 | 任一方带 key 即须相等 | 有 key 走 key 表，无 key 按位 |
| 移动策略 | clear + 按新序重挂（O(n) 树操作，无 move 语义） | 最小插入/删除/移动集（LIS 优化移动） |
| 跨层移动 | 不支持（换父 = 摘下重挂） | 不跨层（reparent 即重建） |
| 失效下发 | updateElement 就地赋值 + markNeedsXxx | host diff → DOM 增删改 |

三点解读。其一，**算法复杂度差一个量级但绝对值都不大**：千项列表的 O(n²) 是 10⁶ 次比较 ≈ 1ms 量级，React 的 O(n) 是 10³ 次——工程上 React 的映射表方案显然对，教学版保留 O(n²) 是为了「30 行读完」。其二，**移动策略是真正的大分叉**：clear+重挂简单但每个子树都要走一次 appendChild（父节点 markNeedsLayout），最小移动则连 DOM/渲染树操作都省；React 的 LIS 方案值一套独立分册。其三，**失效下发终点不同**：React 到 DOM 属性级（setAttribute/remove），本实现到渲染对象字段赋值 + 失效标记——保留模式内核的直接红利（第四册的老话题在本册兑现）。

## 8. 本册小结

- 协调 = 身份分配：同 key 复用（状态=对）> 同类型按位（快但可能错配）> mount 新建
- reconcileChild 四分支是「最小 reconcile」的全部；单子不看 key（位置即身份）
- reconcileChildren 线性扫描匹配 + kept 新序 + clear/重挂；O(new×old) 的教学取舍（React 用 key 映射降到 O(n)）
- key 的不对称规则：任一方带 key 即须相等——防「旧有 key 新无 key」的身份污染
- 下标 key 事故手算：删头后 beta 错配 alpha 的节点——状态错配不是性能损失，是**正确性损失**；内容派生 key（keyFor hash）是 demo 的解
- 无 key 退化在「带输入列表」是灾难源：位置身份 + 内容改写 = 输入内容留在位置上
- 移动策略 clear+重挂 vs React 最小移动（LIS）：教学版选简单，工程版选省树操作——差一个分册的课题

1. 「复用 ≠ 快，复用 = 对」——举一个「复用了但更慢」和「不复用但更快」各自成立的场景。

4. 下标 key 事故里，如果列表项是纯文本（无状态），错配还有害吗？这个答案如何影响「什么时候可以偷懒用下标 key」？
5. clear+重挂的 O(n) 树操作 vs 最小移动——在「每帧都在 shuffle 的动画列表」场景下两者的失效账差多少？什么时候必须上最小移动？
6. keyFor 用 hash(label)——如果列表项可重名（两个 "item"），会撞 key。给出三个层级的修复方案（内容加 id / 挂载时分配自增 id / 允许重复但保序）与各自的取舍。

## 附录 A：detach 的实现与卸载语义

```ts
function detachChild(el: VElement, child: VElement): void {
  el.node.removeChild(child.node);          // 渲染树摘除（父指针维护在基类里）
  const idx = el.children.indexOf(child);
  if (idx >= 0) el.children.splice(idx, 1); // 协调树摘除
  child.parent = null;
}
```

「卸载」的语义边界要诚实：教学版**没有 dispose 钩子**——子树里若挂着 effect/动画（比如列表项自带闪烁光标），detach 后这些 effect 不会被自动 stop（第六册的泄漏场景在这里具象化）。React 用 unmount 回调、Flutter 用 dispose 生命周期补这个洞；教学版的补法是「列表项的 effect 由列表的宿主编排创建/stop」（谁创建谁 stop 纪律的列表版）。工程化清单里「VElement 可选 dispose 钩子」是一条真实的 TODO。

## 附录 B：混合 key 场景手算（部分带 key）

规则「任一方带 key 即须相等」在混合列表下的行为——旧 `[A(k1), B, C(k3)]`（B 无 key）→ 新 `[B(k2), A, C]`（B 突然带 key2，A/C 无 key）：

```text
B(k2)：扫旧——old[0]=A(k1) kind 匹配但「任一方带 key 且不等」continue；
       old[1]=B(无key)：oe.key undefined、nv.key=2 → 带任一方 → 必须相等 → undefined ≠ 2 → continue！
       old[2]=C(k3) 不等 → 无匹配 → mount 新建 B
A（无key）：old[0]=A(k1)——nv 无 key、oe 有 key1 → 「任一方带 key」成立、key 不等 → continue！
       old[1]=B（used？未 used——但旧 B 已被跳过未占）→ kind 匹配？旧 B 是同 kind（假如同为 text）→
       按「第一个未占用同类型」匹配 old[1] → updateElement(B旧 → A新)！
C（无key）：old[2]=C(k3) 同理 continue → old[1] 已占用 → ……最终可能 mount 新建
卸载：旧 A(k1) 从未被匹配 → 被卸载
```

结论：**同一列表里 key 策略漂移（今天带明天不带）会大规模错配**——旧 A(k1) 被卸载、新 A 错配到旧 B 的节点上。这就是「key 策略统一」纪律的机制来源：这条不对称规则是**保护**（宁可重建也不能身份污染），但它要求使用者不漂移。React 同样要求 key 稳定性，错误用法同样炸——这不是教学版独有的坑。

## 附录 C：markNeedsLayout 收尾的必要性

reconcileChildren 末尾的 `el.node.markNeedsLayout()`（逐字）值得单独说：**为什么统一标一次，而不是每个变更点各标？** 三个理由：①增删/重排改变子数量与顺序 → 容器尺寸与排列必变（布局失效语义正确）；②子项各自的 updateElement 已经精确标过自己的脏（颜色/文本），容器级布局失效是**补充**而不是重复（同帧合并吃掉重复）；③一次容器级标脏的成本是 O(树深) 冒泡，比在每个子项里散标更少调用点。对照「只在子项标、容器不标」的错误推演：改子不增删时碰巧够用（子标脏会冒泡），一旦增删，容器的 children 数量变了但无人告知 → 排列结果错——这正是失效「标对方向」纪律（03 册附录 A）的列表版。

## 附录 E：对账单方法——每波更新的失效审计

树协调的回归测试不该只看「节点复用了没」，还要看**失效账**：每波更新后，markNeedsXxx 的调用清单应当与「真实变更」精确一致。观测手段（无头，接在 demo 的 waves 处）：

```ts
// 审计钩子：包一层 owner，记录本波的失效通道分布
function audit(owner: PipelineOwner, label: string): void {
  console.log(`[${label}] layout=${owner.layoutPasses} paint=${owner.paintPasses} ` +
              `repainted=${owner.repaintedNodes}`);
}
```

对账基准（附录 A~D 各场景的期望账）：

| 场景 | 期望 layout | 期望 repainted | 违例信号 |
|---|---|---|---|
| 头插 X | +1（容器子数变） | 复用节点中仅内容变者 | repainted = 全部 → 同值守卫失效 |
| 删中间 B | +1 | A/C 若纯文本同值 = 0 | A/C 也被重录 → key 错配 |
| 轮转 [C,A,B] | +1 | 0（内容全同值，纯重排） | >0 → 文本被改写（无 key 退化发作） |

「轮转后 repainted 应为 0」是最锋利的一条：keyed 正确时重排只动树序、不动内容——repainted 非 0 即说明身份分配错了（下标退化或 key 漂移）。这个对账单把第五册的四个手算场景变成了四条可跑的回归——手算文化的闭环：**纸面推演 → 断言锁死 → 审计对账**。

## 附录 F：keyed 协调 × 重绘边界：复用的双层红利

身份保持的价值不止「焦点/输入状态不丢」——它还与第六阶段的重绘边界发生化学反应：

```text
keyed 复用正确时：行内变更 → 行的重绘边界重录（变更半径 = 一行）
keyed 错配时（下标 key 事故）：内容全部改写 → 3 行的文本都要重录
                              ——而且这些行各自的重绘边界全部标脏
                              ——重录半径从 1 行扩到全列表
```

也就是说：**key 错配的账单不止「状态错」，还有「重录半径扩到全表」**——失效机器把每个错配的文本叶子标脏，冒泡到各自的重绘边界，一批无辜边界开始重录。虚拟列表（第八阶段）对这个尤其敏感：池行复用模型下「重绑」是常态，key/身份语义设计错了，每滚一屏就是全屏重绘。第五册的身份语义与第八阶段的池化在同一个问题上汇合——「身份 = 失效半径的下界」。

## 附录 G：工程三陷阱：keyed 协调的三个高危现场

**陷阱一：重复 key 的静默 mount（性能失血型）**

- 触发场景：列表项可重名（两条数据过 keyFor 后同值，或两行共用同一字面量 key）。reconcileChildren 的匹配内层循环「第一个命中即 break」，同 key 的第二项在旧数组里找不到仍未占用的等 key 槽位 → 走 `kept.push(mount(nv, el, m))` 新建分支。
- 根因：key 唯一性零校验。§3 的语义细节 2 写得很清楚：不去重、不报错，错误被静默降级为「新建」。
- 症状：不炸、测试不红——但那几行**每次更新都整行重建**：行内动画从头播放、子渲染对象每次全新分配；在附录 D 那种「波数≈帧数」的 demo 里表现为持续分配压力。核对手段：附录 E 对账单里这几行的 repainted 贡献恒非零。
- 规避：keyFor 冲突审查（hash 前把 label 拼上行 id 再散列）；或在开发构建里对「同一波 mount 出的 key 集合」做去重断言，重复即告警。

**陷阱二：顶层 kind 变化 = 整树重建（状态湮灭型）**

- 触发场景：`Component.update` 的顶层分支（`vdom.ts`：`if (this.root.vnode.kind !== v.kind)` 即整树重建）。把外层容器从 column 换成 row、或临时在外面包一层 padding——顶层 kind 变了。
- 根因：组件根没有「别的旧 VElement」可比对 key——根的身份就是 kind 本身，类型变即整棵 mount。子级才有 keyed 细粒度路径。
- 症状：焦点丢、动画重放、输入缓冲清空——用户视角是「页面闪了一下，全部重来」。
- 规避：顶层放一个永不变 kind 的容器（boundary 或方向固定的 flex），把「换布局」降级为它的子级变化——子级走 reconcileChild / reconcileChildren 的增量路径。这一条与 04 册「signal 只包叶子」的粒度纪律同源：**重建半径由身份层级决定，把身份层放高，重建半径就大**。

**陷阱三：绕过协调手动搬节点（父指针守卫炸雷型）**

- 触发场景：手写「跨列表拖拽」，直接 `rowB.appendChild(nodeA)` 而不先从 rowA 摘下。`render-object.ts` 的 appendChild 开头就是守卫：`if (child.parent !== null) throw new Error(...)`（原文提示「先 detach」）。
- 根因：渲染树的父指针是单值字段，appendChild 的守卫拒绝「一子多父」；协调函数内部全部是先 detachChild（渲染树、协调树同摘）再挂。
- 症状：运行期抛错——这其实是好事，守卫把语义错误挡在入口。更隐蔽的变体是只调 removeChild 不摘 VElement.children 数组：渲染树与协调树从此各说各话，下一波 reconcile 的匹配扫描基于脏数据。
- 规避：搬移一律走 detachChild，或者用 reconcileChildren 的 kept 序直接表达目标位置——**树结构变更的唯一写入口应当是协调层**，这与第六册「setText 是文本唯一入口」是同一条设计纪律。

## 决策速查表：身份策略怎么选

| 场景 | 策略 | 落点 | 一句理由 |
|---|---|---|---|
| 一次性静态渲染（永不增删重排） | 无 key | reconcileChildren 按位路径 | 位置即身份，零心智负担 |
| 几十到几百项、会增删重排 | keyed + 内容派生 key | keyFor（reactive-scene.ts） | 增删移动时状态跟着数据走 |
| 行内有输入框/焦点/动画 | keyed，key 用数据 id | 附录 A 的 dispose 课题 + 谁创建谁 stop | 状态在节点，身份必须保 |
| 万级同构行（日志/表格/消息流） | 放弃 keyed，上池化 | 08 册 RenderVirtualList | 节点数常量化，状态上提进数据 |
| 单子槽（容器只有一个孩子） | 不用 key | reconcileChild 四分支 | 位置无歧义，key 无意义 |
| 列表项类型可能切换 | keyed + 行内换 kind | reconcileChild 的「类型变 → 换子」 | 行内节点重建，但行身份由 key 保持 |

读表方法：先问「这个列表会不会在多次更新之间保持续期」。不会（整表换数据）则任何策略都对；会，再按规模与状态归属往下选。最后一列的判据与第八阶段虚拟列表的「行内状态住哪」是同一句话的两面：keyed 是「状态跟着节点」，池化是「节点跟着数据」——选错方向的账单都是身份错配。

## 手算/走查配方：纸上推演七步法

对任意「旧列表 → 新列表」序列通用的配方：

1. 抄下旧数组的 kind/key 序列，新数组每项一行；
2. 逐新项扫描：先 kind 过滤，再 key 判定（任一方带 key 即须相等；双方都无 key 取第一个未占用的同类型）；
3. 命中 → 记 used、续写 kept；未命中 → 标 mount；
4. 扫完新表，used 为假的旧项记 detach；
5. 数树操作：detach 各付 1 次 removeChild；clear 阶段 removeChild 数 = 摘完后仍挂在 children 里的个数；appendChild 数 = kept 长度；
6. 收尾断言：容器级 markNeedsLayout 恰好 1 次（附录 C 的必要性论证）；
7. 语义复核：kept 里每一对「新项 ↔ 旧槽」会不会错配状态（内容身份还是位置身份）。

**示例**（重复 key 现场手算）：旧 `[A(k1), B(k2), C(k3)]` → 新 `[C(k3), A(k1), A(k1), B(k2)]`。

```text
C(k3)    → 扫描：old[0] k1≠k3 跳、old[1] k2≠k3 跳、old[2] k3=k3 命中 → used[2]，kept=[C]
A(k1)    → old[0] 命中 → used[0]，kept=[C,A]
A(k1)二  → old[0] 已 used 跳、old[1] k2≠k1 跳、old[2] 已 used 跳 → 无匹配 → mount 新建 A′
B(k2)    → old[1] 命中 → used[1]，kept=[C,A,A′,B]
卸载：used 全 true → 无
摘树：detach 0 次；clear 阶段 removeChild × 3（A、B、C 都还挂着）；appendChild × 4
标脏：markNeedsLayout × 1
```

结果自验：复用 3（C、A、B 的渲染对象原样保留）、新建 1（A′——旧 A 已被占用，第二个 key1 找不到空槽）、卸载 0；树操作合计 3 次 removeChild + 4 次 appendChild + 1 次容器标脏。读数要点：A′ 与旧 A **不共享任何状态**——两个 key1 的行各自为政，第二个永远是新节点。这正是「同列表 key 必须唯一」纪律的机制演示：不唯一不会报错，只会让身份语义静默失效；如果 A 行带着输入框，第二个 key1 每波都是空的。

- [ ] 列表 key 是否来自内容身份（id 或唯一字段），而不是数组下标或循环序号？
- [ ] 同一列表内 key 是否唯一、策略是否统一（全带或全不带，不漂移——附录 B 的混合场景）？
- [ ] 列表项有状态（输入/焦点/动画）时，状态是确认跟节点走（keyed 保身份）还是已上提进数据（池化）？二选一并写进注释。
- [ ] 顶层组件 kind 是否稳定（不因配置切换而整树重建——附录 G 陷阱二）？
- [ ] 有没有在协调层之外直接对渲染树 appendChild/removeChild（父指针守卫与双树一致性——陷阱三）？

## 与真实框架对照（概念对照）

| 概念 | mini-gui | React | Flutter |
|---|---|---|---|
| 协调节点 | VElement（记具体渲染对象引用，零向下转型） | Fiber | Element |
| 身份键 | VNode.key（number） | key prop（任意稳定值） | Key / ValueKey / GlobalKey |
| 无 key 退化 | 按位同类型复用 | 同类型按位更新 | 无 key 的 Element 按位复用 |
| 顶层类型变化 | 整树重建（Component.update 分支） | 根 fiber 替换 | runtimeType 变即 Element 重建 |
| 卸载钩子 | 无（dispose 是工程化 TODO） | effect 清理函数 | State.dispose |
| 移动策略 | clear + 重挂 | 最小移动（LIS） | 子 Element 按新序改挂、渲染对象跟着换父 |

概念对照的读法：三家都在解「描述序列 → 节点身份」同一道题，分歧集中在两处——**身份键的表达力**（React 与 Flutter 的 key 可以是任意稳定值，mini-gui 钉成 number，教学够用）与**卸载补偿**（两家都有生命周期钩子兜底 effect 清理，教学版靠「谁创建谁 stop」纪律）。读 Flutter 的多子协调源码会发现它与 reconcileChildren 骨架同构：核心分歧从来不在「怎么找匹配」（都是 key/类型两道过滤），而在「找到之后怎么少动树」——React 的 LIS 移动集与 Flutter 的「渲染对象重新挂父」，都是把 mini-gui 那步 clear + 重挂做精细之后的形态。

## 反模式对照：列表协调的六个反模式

| 反模式 | 症状 | 正确做法 |
|---|---|---|
| 下标当 key | 删头后全部行内容被改写（§5 的 alpha/beta 事故），行内状态错位 | key 用内容身份（keyFor / 数据 id） |
| key 用随机数（每次渲染重新生成） | 每波全量 mount + 全量卸载；waves 与 frames 同涨时分配压力放大 | key 必须跨更新稳定：内容派生或持久 id |
| 顶层容器 kind 随配置漂移 | 焦点与动画整树重来（附录 G 陷阱二） | 顶层 kind 固定，布局变化下放子级 |
| 在回调里手动 appendChild「补节点」 | 渲染树与协调树失一致，下一波 diff 错配 | 树变更只走 render() 描述 + reconcile |
| 「复用只是省构造，下标 key 无所谓」 | 真正的损失是正确性：状态错配不是慢，是错 | 复用的第一性是身份，性能只是副产品 |
| 依赖重复 key 静默 mount 的「碰巧能跑」 | 那几行每波重建，动画重放、分配压力（附录 G 陷阱一） | key 唯一 + 开发期重复断言 |

六个反模式里最有欺骗性的是第二、五两个。第二（随机 key）的代码看起来「很现代」——keyed 写法一字不差，但 key 值每波都换，身份语义完全落空：匹配扫描永远找不到等 key 槽，等于每波把整列表推倒重建，比老老实实按位复用还慢，还丢了状态。第五（性能辩解）则是认知错位：下标 key 在「纯静态展示 + 从不增删」时确实无害（此时按位与 keyed 结果一致），于是这个辩解「局部正确」，一旦列表开始增删重排，账单立刻从性能栏转到正确性栏——检查单第 1 条要问的就是这个转移发生在什么时候。

## 附录 H：keyed 复用与布局缓存的交互账（一次重排后的 flush 走查）

协调的树操作只是上半场，下半场是下一次 flushLayout 怎么消化这棵被动过的树。以手算配方示例（kept 等于 `[C, A, A′, B]`，A′ 新建）为底，走一遍失效与消化（松约束下的典型路径，纸上走查）：

```text
reconcileChildren 收尾：el.node.markNeedsLayout()
  → 容器 flex 自己标脏 → 冒泡：flex 非边界（松约束、非固定尺寸）→ 传染父……
  → 到某个边界（紧约束祖先或 isFixedSize 节点）上报 owner.scheduleLayoutBoundary
下一帧 flushLayout：
  ① root.layout(tight/loose)——根不脏 + 约束没变 → 布局缓存短路（O(1)，layoutCount 不加）
  ② 队列里那个边界 → boundary.layout(lastConstraints) → performLayout 重跑沿途排列
  ③ 沿途对每个孩子调 child.layout(c)：
     C、A、B：不脏 + constraintsEqual 成立 → 短路（复用身份保住了 _lastConstraints，
             缓存钥匙原样有效——「复用 = 保缓存」的机制来源）
     A′：新建节点 needsLayout 初始 true（render-object.ts 字段字面量）且
         _lastConstraints 为 null → 必跑 performLayout（文本度量一次）
```

对账：本次 flush 的 performLayout 增量 = 边界到容器沿途的排列节点 + A′ 自己 = 复用节点贡献为零。反过来推「如果走的是 mount 全列表」：四个孩子全部 needsLayout 初始 true，全表文本度量 × 4，再加 flex 全排列——这就是「身份丢失 → 缓存钥匙全换」的量化形态。两层结论叠在一起：**keyed 复用同时省两笔账——身份账（状态不丢）与缓存账（lastConstraints 与不脏标志原样有效）**；而 mount 新建的隐性价格也是两笔——构造 + 首次布局。把 §7 的 HUD 数字与这笔账对读：waves 涨一拍，layoutPasses 只涨一次 flush，但 performLayout 的增量由「这波里 mount 了几个新节点」决定——观测口能分辨「重排波」与「换血波」。

## 附录 I：keyFor 的散列读法（稳定性优先于分布性）

reactive-scene.ts 的 keyFor 是一行多项式滚散（逐字）：`let h = 7; for (...) h = h * 31 + (label.charCodeAt(i) % 97);`。纸面代入两个真实标签（demo 初始列表的 alpha 与 beta，小写字母的 charCode 减 97 即贡献值）：

```text
"alpha"：a→0, l→11, p→15, h→7, a→0
  h=7 → 7×31+0=217 → 217×31+11=6738 → 6738×31+15=208893
      → 208893×31+7=6475690 → 6475690×31+0=200746390
"beta"：b→1, e→4, t→19, a→0
  h=7 → 7×31+1=218 → 218×31+4=6762 → 6762×31+19=209641 → 209641×31+0=6498871
```

先说清这两个数的用途边界：绝对值无关紧要，**唯一被消费的性质是「同一标签在两次 reconcile 之间算出同一个值」**——它不落显示、不落布局，只参与匹配循环的相等判断。所以评价 keyFor 不看散列分布均匀度，看稳定性与冲突面。

冲突面的小证明（demo 域内成立）：小写字母的 charCode 在 97 到 122 之间，模 97 后落 0 到 25；多项式乘 31 的 base 是 31，而每位数字 0 到 25 严格小于 base——**base 进制表示唯一的经典条件满足**，于是「纯小写标签 → keyFor 值」是单射，demo 的 alpha/beta/gamma/item 系列（纯小写加零）不可能互撞。这个证明的边界也要会说：数字与大写字母的 charCode（如 '0' 是 48）小于 97 时模 97 原样保留，贡献值 48 大于 base 31——进制唯一性论证失效，冲突重新变得可能（需要特定的进位凑配，但「不可能」变成了「没证明不可能」）。工程化的做法是给散列的输入域写注释（「本 demo 标签为纯小写唯一」）或干脆拼上 id 再散列。

另一个藏在 render() 里的细节与 key 纪律呼应：列表项文案是 `labels.indexOf(label)` 拼出来的——indexOf 只认第一个同名项，两个重名标签会拿到**同一下标文案与同一个 key**。demo 用「标签唯一」的约定同时保住了 key 唯一与文案正确两件事；约定一破，两处一起破——这也是「key 用内容身份」必须配「内容唯一」前提的具体形态。
