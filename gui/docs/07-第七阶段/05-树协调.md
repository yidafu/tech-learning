## 1. 概念坐标：协调 = 身份分配

上一册的 updateElement 解决了「同类型节点怎么更新」；本册解决「**哪些新 VNode 对应哪些旧 VElement**」——即身份分配问题。三条规则（`vdom.ts` 注释原文）：

```text
同 key（双方都带 key 时必须相等）→ 复用（状态保留）
任一方无 key          → 按「第一个未占用的同类型」匹配
都没匹配上           → 新建（mount）
```

身份的价值在状态：VElement 保住了，它的渲染对象就保住了——焦点、动画中态、输入缓冲都在渲染对象/控件状态里。**复用 ≠ 快（省构造），复用 = 对（状态不丢）**——顺序要摆正。

## 2. reconcileChild：单子路径（三行判断）

```ts
function reconcileChild(el: VElement, v: VNode | null, m: TextMeasurer): void {
  const existing = el.children[0] ?? null;
  if (v === null) {                       // 新描述没孩子 → 卸载
    if (existing !== null) detachChild(el, existing);
    return;
  }
  if (existing === null) {                // 原来没孩子 → 挂载
    attachChild(el, v, m);
    return;
  }
  if (existing.vnode.kind !== v.kind) {   // 类型变 → 换子
    detachChild(el, existing);
    attachChild(el, v, m);
    return;
  }
  updateElement(existing, v, m);          // 同类型 → 原地更新
  existing.vnode = v;
}
```

「最小 reconcile」的单子版就这四个分支：无/挂、有/卸、异型/换、同型/更。注意单子路径**不看 key**——单子的身份就是「这个位置」，没有歧义。

## 3. reconcileChildren：列表路径全量走读

核心函数整段（逐字，注释保留）：

```ts
function reconcileChildren(el: VElement, newKids: VNode[], m: TextMeasurer): void {
  const oldEls = el.children.slice();
  const used: boolean[] = [];
  for (let j = 0; j < oldEls.length; j++) used.push(false);

  const kept: VElement[] = [];

  for (const nv of newKids) {
    let matched = -1;
    for (let j = 0; j < oldEls.length; j++) {
      if (used[j]) continue;
      const oe = oldEls[j]!;
      if (oe.vnode.kind !== nv.kind) continue;
      if (nv.key !== undefined || oe.vnode.key !== undefined) {
        if (oe.vnode.key !== nv.key) continue;  // 任一方带 key：必须相等才复用
      }
      matched = j;
      break;
    }
    if (matched >= 0) {
      used[matched] = true;
      const keptEl = oldEls[matched]!;
      updateElement(keptEl, nv, m);
      keptEl.vnode = nv;
      kept.push(keptEl);
    } else {
      kept.push(mount(nv, el, m));              // 新建
    }
  }

  // 卸载未复用的
  for (let j = 0; j < oldEls.length; j++) {
    if (!used[j]) detachElement(el, oldEls[j]!);
  }

  // 重排：先全部摘下、按新序挂回（渲染树上 remove+append 保持父指针）
  for (const child of el.children.slice()) {
    el.node.removeChild(child.node);
  }
  el.children = [];
  for (const child of kept) {
    el.children.push(child);
    child.parent = el;
    el.node.appendChild(child.node);
  }
  el.node.markNeedsLayout();
}
```

算法骨架：**对每个新 VNode 在旧 VElement 数组里线性找匹配**（key 优先、无 key 退化为「未占用的同类型」）→ 匹配上则 updateElement + 记 kept 顺序 → 没匹配上 mount 新建 → 收尾卸载未复用 + 按新序重挂。复杂度 O(new × old)（嵌套线性扫描）——教学版的诚实取舍，对照表在 §6。

三个语义细节：

1. **key 的不对称规则**（`nv.key !== undefined || oe.vnode.key !== undefined`）：只要**任一方**带 key，就必须 key 相等才算匹配——「旧的带 key、新的不带」不能偷偷按位置配对（否则身份语义会被无 key 的新项污染）。都无 key 才按位。
2. **匹配只看第一次命中**（`break`）：同 key 出现两次（使用者写错）时第二个会被当新键 mount——不去重不报错，教学版容忍这个坑（第 8 节列进「明确不做」）。
3. **重排用 clear + 重挂**而不是最小移动：`removeChild × n + appendChild × n`，O(n) 的树操作换代码极简。渲染对象没有「插入到第 i 位」的 API（appendChild 尾插），最小移动算法要设计索引维护——工程化课题（§6 对照 React 的可插拔移动策略）。

## 4. 手算三个场景（keyed 三断言的推演）

设旧列表 `[A(key1), B(key2), C(key3)]`，逐场景推 kept/detached/moves：

**场景一：头插 `X(key0)` → `[X, A, B, C]`**

```text
X(key0)：扫旧数组——kind 匹配但 key 不等（key1/key2/key3 ≠ 0）→ mount 新建
A(key1)：匹配 old[0] → updateElement(A) → kept=[A]
B(key2)：匹配 old[1] → kept=[A,B]
C(key3)：匹配 old[2] → kept=[A,B,C]
卸载：used[0..2] 全 true → 无
重挂序：A, B, C, X？——不对：kept 是按「新列表遍历序」push 的 → [X, A, B, C] ✓
断言：头插新 key，旧节点全部复用（测试 75 行）✓
```

**场景二：删中间 `B` → `[A, C]`**

```text
A → matched old[0]；C → matched old[2]（old[1] 是 B，key 不匹配被 continue）
卸载：used[1] = false → B 被移除
身份结果：A、C 的渲染对象原样保留，B 整棵丢弃
断言：「同 key 复用（删除中间项后其余节点身份不变）」✓
```

**场景三：轮转 `[A,B,C]` → `[C,A,B]`（shuffle 按钮的真实路径）**

```text
C(key3) → matched old[2]；A(key1) → old[0]；B(key2) → old[1]
kept = [C, A, B]（按新序）；卸载无
重挂：先摘 3 个、按 [C,A,B] 逐个 appendChild
身份结果：三个全复用——只是挂序变了；焦点在 B 上就跟着 B 走 ✓
断言：「顺序重排：节点按 key 跟随移动」✓
```

**场景四（无 key 退化）**：旧 `[text"α", text"β"]` → 新 `[text"β", text"γ"]`——都没有 key：新[0]"β" 匹配 old[0]"α"（第一个未占用同类型）→ **updateElement 把 α 的文本改成 β**；新[1]"γ" 匹配 old[1] → 文本 β→γ。节点全复用但内容全部改写——身份按位置分配的固有行为（测试 96 行「无 key 退化为按位同类型复用」）。这在「列表项带输入框」时会灾难：第 0 位输入的内容留在了第 0 位，跟内容挪动无关。

## 5. keyFor：内容派生 key 的实战

reactive-scene.ts 的列表（逐字，注释保留）：

```ts
  // 稳定 key：从标签内容派生（demo 内标签唯一）。用下标当 key 会让增删/换序
  // 失去身份追踪——beta(new,key0) 会错配 alpha(old,key0)，节点复用与状态保持
  // 全部失效（实测踩过）。
  const keyFor = (label: string): number => {
    let h = 7;
    for (let i = 0; i < label.length; i++) h = h * 31 + (label.charCodeAt(i) % 97);
    return h;
  };
```

**下标 key 事故**的手算（注释说的那个坑）：`[alpha, beta]` 用下标 key（0,1）→ 删头后 `[beta]` 的新描述 key=0 → 匹配旧 key0（**alpha 的节点**）→ updateElement 把 alpha 的文本改成 beta——**身份错配**：如果 alpha 行有输入框/焦点/动画，用户看到的是「beta 长着 alpha 的状态」。内容派生 key（hash(label)）在「内容唯一」的列表里给出稳定身份——删头后 beta 的 key 不变，匹配 beta 自己的旧节点，alpha 被正确卸载。

key 的三条使用纪律（从场景四与 keyFor 注释提炼）：

| 纪律 | 违反后果 |
|---|---|
| key 用**内容身份**（id/唯一标签），不用下标 | 增删/换序时状态错配（上面的 alpha/beta 事故） |
| 同列表内 key 唯一 | 重复 key 的第二个被静默 mount（不报错） |
| 同一列表的 key 策略统一（全带或全不带） | 「任一方带 key 即必须相等」规则会拆散旧的按位配对 |

## 6. 与 React diff 的对照

| 机制 | mini-gui（教学版） | React（react 站复刻） |
|---|---|---|
| 匹配算法 | 每新项线性扫旧数组，O(new×old) | 同层单向遍历 + key→index 映射，O(new+old) |
| key 判定 | 任一方带 key 即须相等 | 有 key 走 key 表，无 key 按位 |
| 移动策略 | clear + 按新序重挂（O(n) 树操作，无 move 语义） | 最小插入/删除/移动集（LIS 优化移动） |
| 跨层移动 | 不支持（换父 = 摘下重挂） | 不跨层（reparent 即重建） |
| 失效下发 | updateElement 就地赋值 + markNeedsXxx | host diff → DOM 增删改 |

三点解读。其一，**算法复杂度差一个量级但绝对值都不大**：千项列表的 O(n²) 是 10⁶ 次比较 ≈ 1ms 量级，React 的 O(n) 是 10³ 次——工程上 React 的映射表方案显然对，教学版保留 O(n²) 是为了「30 行读完」。其二，**移动策略是真正的大分叉**：clear+重挂简单但每个子树都要走一次 appendChild（父节点 markNeedsLayout），最小移动则连 DOM/渲染树操作都省；React 的 LIS 方案值一套独立分册。其三，**失效下发终点不同**：React 到 DOM 属性级（setAttribute/remove），本实现到渲染对象字段赋值 + 失效标记——保留模式内核的直接红利（第四册的老话题在本册兑现）。

## 8. 本册小结

- 协调 = 身份分配：同 key 复用（状态=对）> 同类型按位（快但可能错配）> mount 新建
- reconcileChild 四分支是「最小 reconcile」的全部；单子不看 key（位置即身份）
- reconcileChildren 线性扫描匹配 + kept 新序 + clear/重挂；O(new×old) 的教学取舍（React 用 key 映射降到 O(n)）
- key 的不对称规则：任一方带 key 即须相等——防「旧有 key 新无 key」的身份污染
- 下标 key 事故手算：删头后 beta 错配 alpha 的节点——状态错配不是性能损失，是**正确性损失**；内容派生 key（keyFor hash）是 demo 的解
- 无 key 退化在「带输入列表」是灾难源：位置身份 + 内容改写 = 输入内容留在位置上
- 移动策略 clear+重挂 vs React 最小移动（LIS）：教学版选简单，工程版选省树操作——差一个分册的课题

6. keyFor 用 hash(label)——如果列表项可重名（两个 "item"），会撞 key。给出三个层级的修复方案（内容加 id / 挂载时分配自增 id / 允许重复但保序）与各自的取舍。

## 附录 A：detach 的实现与卸载语义

```ts
function detachChild(el: VElement, child: VElement): void {
  el.node.removeChild(child.node);          // 渲染树摘除（父指针维护在基类里）
  const idx = el.children.indexOf(child);
  if (idx >= 0) el.children.splice(idx, 1); // 协调树摘除
  child.parent = null;
}
```

「卸载」的语义边界要诚实：教学版**没有 dispose 钩子**——子树里若挂着 effect/动画（比如列表项自带闪烁光标），detach 后这些 effect 不会被自动 stop（第六册的泄漏场景在这里具象化）。React 用 unmount 回调、Flutter 用 dispose 生命周期补这个洞；教学版的补法是「列表项的 effect 由列表的宿主编排创建/stop」（谁创建谁 stop 纪律的列表版）。工程化清单里「VElement 可选 dispose 钩子」是一条真实的 TODO。

## 附录 B：混合 key 场景手算（部分带 key）

规则「任一方带 key 即须相等」在混合列表下的行为——旧 `[A(k1), B, C(k3)]`（B 无 key）→ 新 `[B(k2), A, C]`（B 突然带 key2，A/C 无 key）：

```text
B(k2)：扫旧——old[0]=A(k1) kind 匹配但「任一方带 key 且不等」continue；
       old[1]=B(无key)：oe.key undefined、nv.key=2 → 带任一方 → 必须相等 → undefined ≠ 2 → continue！
       old[2]=C(k3) 不等 → 无匹配 → mount 新建 B
A（无key）：old[0]=A(k1)——nv 无 key、oe 有 key1 → 「任一方带 key」成立、key 不等 → continue！
       old[1]=B（used？未 used——但旧 B 已被跳过未占）→ kind 匹配？旧 B 是同 kind（假如同为 text）→
       按「第一个未占用同类型」匹配 old[1] → updateElement(B旧 → A新)！
C（无key）：old[2]=C(k3) 同理 continue → old[1] 已占用 → ……最终可能 mount 新建
卸载：旧 A(k1) 从未被匹配 → 被卸载
```

结论：**同一列表里 key 策略漂移（今天带明天不带）会大规模错配**——旧 A(k1) 被卸载、新 A 错配到旧 B 的节点上。这就是「key 策略统一」纪律的机制来源：这条不对称规则是**保护**（宁可重建也不能身份污染），但它要求使用者不漂移。React 同样要求 key 稳定性，错误用法同样炸——这不是教学版独有的坑。

## 附录 C：markNeedsLayout 收尾的必要性

reconcileChildren 末尾的 `el.node.markNeedsLayout()`（逐字）值得单独说：**为什么统一标一次，而不是每个变更点各标？** 三个理由：①增删/重排改变子数量与顺序 → 容器尺寸与排列必变（布局失效语义正确）；②子项各自的 updateElement 已经精确标过自己的脏（颜色/文本），容器级布局失效是**补充**而不是重复（同帧合并吃掉重复）；③一次容器级标脏的成本是 O(树深) 冒泡，比在每个子项里散标更少调用点。对照「只在子项标、容器不标」的错误推演：改子不增删时碰巧够用（子标脏会冒泡），一旦增删，容器的 children 数量变了但无人告知 → 排列结果错——这正是失效「标对方向」纪律（03 册附录 A）的列表版。

## 附录 E：对账单方法——每波更新的失效审计

树协调的回归测试不该只看「节点复用了没」，还要看**失效账**：每波更新后，markNeedsXxx 的调用清单应当与「真实变更」精确一致。观测手段（无头，接在 demo 的 waves 处）：

```ts
// 审计钩子：包一层 owner，记录本波的失效通道分布
function audit(owner: PipelineOwner, label: string): void {
  console.log(`[${label}] layout=${owner.layoutPasses} paint=${owner.paintPasses} ` +
              `repainted=${owner.repaintedNodes}`);
}
```

对账基准（附录 A~D 各场景的期望账）：

| 场景 | 期望 layout | 期望 repainted | 违例信号 |
|---|---|---|---|
| 头插 X | +1（容器子数变） | 复用节点中仅内容变者 | repainted = 全部 → 同值守卫失效 |
| 删中间 B | +1 | A/C 若纯文本同值 = 0 | A/C 也被重录 → key 错配 |
| 轮转 [C,A,B] | +1 | 0（内容全同值，纯重排） | >0 → 文本被改写（无 key 退化发作） |

「轮转后 repainted 应为 0」是最锋利的一条：keyed 正确时重排只动树序、不动内容——repainted 非 0 即说明身份分配错了（下标退化或 key 漂移）。这个对账单把第五册的四个手算场景变成了四条可跑的回归——手算文化的闭环：**纸面推演 → 断言锁死 → 审计对账**。

## 附录 F：keyed 协调 × 重绘边界：复用的双层红利

身份保持的价值不止「焦点/输入状态不丢」——它还与第六阶段的重绘边界发生化学反应：

```text
keyed 复用正确时：行内变更 → 行的重绘边界重录（变更半径 = 一行）
keyed 错配时（下标 key 事故）：内容全部改写 → 3 行的文本都要重录
                              ——而且这些行各自的重绘边界全部标脏
                              ——重录半径从 1 行扩到全列表
```

也就是说：**key 错配的账单不止「状态错」，还有「重录半径扩到全表」**——失效机器把每个错配的文本叶子标脏，冒泡到各自的重绘边界，一批无辜边界开始重录。虚拟列表（第八阶段）对这个尤其敏感：池行复用模型下「重绑」是常态，key/身份语义设计错了，每滚一屏就是全屏重绘。第五册的身份语义与第八阶段的池化在同一个问题上汇合——「身份 = 失效半径的下界」。
