## 阶段目标

学完本阶段，你应该能不查资料做到：

- 写出 signals 三原语的内核实现：读时收集依赖、写时按拓扑序传播、每个 computed 一帧只算一次（glitch-free）
- 用 diamond 依赖图解释朴素实现为什么会算两次、层级排序如何修掉它
- 实现函数组件 → RenderObject 树的挂接与最小 reconcile（同位置同类型复用）
- 实现 keyed 列表更新，并说清它与 React keyed diff 在更新粒度上的差别
- 把主题做成 token 表，控件样式全部查表，热切换主题不重建树

## 实践任务清单

1. signals 内核 + 断言：依赖失效正确、diamond 恰好更新一次、effect 清理不泄漏
2. 最小 reconcile + keyed 列表（头插/删除/移动三个场景断言节点复用而非重建）
3. 用声明式 API 重写第五阶段三件套，统计代码量与更新粒度的变化
4. 对照实验：同一个小场景，全量重渲染 vs signals 的更新次数计数对比

## 常见误区与正解

声明式阶段的误区大多带着 React 直觉。本阶段走 Solid 式节点级更新路线，两套心智模型在「什么时候算、每次算多少」上完全不同；带着错误直觉实现，代码能跑，架构却会越写越拧。

| 误区 | 为什么错 | 正解 |
|---|---|---|
| 有了 signals 就不再需要列表协调 | 信号解决的是「值级更新」：依赖它的节点原地刷新；列表增删改变的是树结构本身，值级机制覆盖不到 | 值级更新归 signals，结构级增删移动归最小协调与键控列表，两层各管一段互不越界，见 [05-树协调](05-树协调.md) |
| 依赖收集需要在编译期静态分析组件函数 | 静态分析只能猜「可能读了什么」，条件分支里读不到的路径会误报或漏报，猜错一次更新链就断 | 读时动态收集：响应式上下文里真实读过谁就登记谁，每次重算时重建依赖并清理旧账，见 [03-signals内核](03-signals内核.md) |
| 计算属性加了缓存就天然不会重复计算 | 缓存只保证「不重复执行函数」，挡不住同一批写入里两个上游先后标脏、各自触发一次重算的菱形结构 | 用拓扑层级排序保证同批只算一次：先算低层级再算高层级，做到无毛刺 |
| 列表的键用数组下标最省事 | 下标随插入删除整体漂移：头插一项等于全部键变化，节点被误判为「内容变了」而整列表重建，复用率归零 | 键必须取业务身份，即数据自身的稳定标识；下标仅在只追加、从不插入删除的场景可用 |
| 副作用的清理函数是可选项 | 不清理则旧订阅一直挂在信号上：订阅泄漏、闭包持有已卸载节点，长会话内存持续上涨且难以回收 | 卸载与重跑之前先执行清理；本阶段的断言「清理不泄漏」就是针对这条纪律 |

## 术语速查表

响应式术语最大的混乱在于「信号、观察、订阅」在不同社区指向不同粒度。本表统一到本阶段的实现口径，读分册遇到英文原词时随时回来对齐。

| 术语 | 英文 | 一句话解释 |
|---|---|---|
| 信号 | signal | 可写的响应式数据源；读它的人被登记，写它时通知所有订阅者 |
| 计算属性 | computed | 由其它信号推导的惰性缓存值：依赖标脏、读取时才重算 |
| 副作用 | effect | 自动订阅函数体内读过的信号，依赖变化时被调度重跑 |
| 依赖收集 | dependency tracking | 响应式上下文运行期间，把真实读过的信号登记为依赖的过程 |
| 拓扑层级 | level | 依赖图上的深度序号，保证更新按先上游后下游的顺序执行 |
| 菱形问题 | diamond problem | 一个信号分叉又汇合到同一计算，朴素实现会把它算两次 |
| 无毛刺 | glitch-free | 同一批写入下每个计算恰好重算一次，中间态永不被读到 |
| 批处理 | batch | 批内写入只收集不执行，退出时统一跑一轮，避免中间态抖动 |
| 函数组件 | function component | 把属性与作用域映射为界面描述的纯函数，声明式 API 的基本单元 |
| 协调 | reconcile | 新旧两棵界面描述树的比对与复用：同位置同类型即复用节点 |
| 键控列表 | keyed list | 列表项携带稳定标识的协调策略，移动与删除靠键对号入座 |
| 单向数据流 | unidirectional data flow | 数据只从状态流向视图，一切更新都必须回到状态源头发起 |
| 设计令牌 | design token | 颜色、间距、字号等样式的命名常量表；主题即令牌表的一整套取值 |

## 与真实框架对照

本阶段每一步都能在工业框架里找到对应物。下表重点看「更新粒度」一行：它正是本阶段与 react 站源码复刻互为正交的原因——一个把成本花在比对，一个把成本花在追踪。

| 维度 | 本项目 | Solid.js | Svelte 5 | React |
|---|---|---|---|---|
| 响应式内核 | 手写信号三原语：读时收集、拓扑传播 | 同思路的成熟实现，存储体系完备 | 编译期生成的信号 | 无细粒度信号，靠重渲染间接达成 |
| 组件形态 | 函数组件加最小协调 | 函数组件仅执行一次，节点常驻 | 编译产物即响应式语句 | 函数组件反复执行，靠比对对齐 |
| 更新粒度 | 节点级：信号直达绑定它的渲染槽位 | 节点级，业界标杆 | 编译期确定的细粒度 | 组件级：组件函数整体重跑再比对 |
| 列表协调 | 最小键控协调，断言节点复用而非重建 | 键控块 | 键控块 | 键控子元素的比对算法 |
| 主题方案 | 令牌表查表，热切换不重建树 | 以层叠样式变量为主 | 组件级样式加变量 | 主题对象经上下文下发，切换触发重渲染 |

读完本阶段再看 React 的重渲染模型，会更清楚它贵在哪、又值在哪：贵在每次都重跑组件函数，值在模型单一、心智负担低、并发特性生态成熟。两条路线没有高下，只有取舍；理解取舍比站队重要。
