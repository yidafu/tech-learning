# 性能度量：观测口、压测方法与诚实账本

> [返回：第六阶段导览](01-导览.md)
> 对应大纲条目：第六阶段 5（帧时间、绘制计数、脏区面积比、压测方法）。
> 本册把散落前四册的观测口收编成一张度量地图，并给出一套可复制的无头压测方法——全部数字来自 2026-11-14 本机实跑（`npx tsx` 压测脚本 + `npx vitest run` 无头断言 + `MINI_GUI_*` 窗口三件套）。读完你应当能：为任意「感觉变慢了」定位到哪一段流水线、给优化前后配出可信的对照数字、识别哪些「优化」其实是负收益。

## 1. 度量的第一课：先问「离预算多远」

性能工作的第一条纪律不是「跑 profiler」，是**先定预算**：

```text
60fps → 每帧 16.6ms。流水线各段的预算分配（教学版口径）：
  输入轮询     < 0.5ms   （05 阶段：一次 poll + 分发）
  动画 tick    < 0.1ms   （值推进，无布局）
  flushLayout  < 2ms     （脏子树重排，布局缓存兜底）
  flushPaint   < 3ms     （脏边界重录 + blit）
  replay 呈现  < 5ms     （整段重放到 raylib，第三阶段命令自包含的红利）
  剩余         ~6ms      （raylib 的 swap/等待、调度抖动、系统噪声）
```

有了预算表，每个测量值先归档到「离预算几倍」，再决定要不要动它：

| 测量值 | 离预算 | 结论 |
|---|---|---|
| 空闲帧 0.014ms | 预算的 0.08% | **永远不用优化** |
| 1000 盒冷帧 2.85ms | 17% | 不急；万盒规模才紧张 |
| 单叶变更 p95 0.145ms | 0.9% | 不急，但它是分布尾部的信号源 |
| 05 册实测 targetFPS 亏空 4.6% | 供给侧 | 软件限帧的固有成本，不是你的 bug |

反面教材是「看到一个数就想优化」：空闲帧 0.014ms 里的 p95 尖峰 0.068ms 优化掉 50% 也省不出 0.04ms——而付出的复杂度是真实的。**度量的产出是「不动手」的决定，和「动手」的决定一样多**。

## 2. 观测口地图：三层度量面

mini-gui 的观测口分三层，从无到有按需启用：

| 层 | 手段 | 观测口 | 回答的问题 |
|---|---|---|---|
| L1 无头计数 | vitest 断言 | `layoutPasses` / `totalPerformLayouts` / `paintPasses` / `repaintedNodes` / `layer.commands.length` / `layoutCount` | 逻辑对不对：该少的少了吗？该不变的不变吗？ |
| L2 无头计时 | `npx tsx` + `performance.now()` | 各段耗时中位/p95、冷帧/空闲帧/变更帧 | 多少毫秒：预算还剩多少？瓶颈在哪段？ |
| L3 窗口实跑 | `MINI_GUI_SECONDS/FPS/SHOT` | HUD（fps/repainted/cmds）、帧统计、截图 | 用户看到什么：帧率、渲染正确性、视觉回退 |

三层各有一个「只有它能抓到」的案例，各记一次血泪：

- **L1 抓逻辑回退**：`pipeline.test` 的「干净边界子树被 blit 到子偏移处」——双重平移 bug 的断言面（`expect(before).toEqual({ x: right.x, y: right.y })` 直接失败 200≠100）。
- **L2 抓性能回退**：附录压测的「单叶变更 p95」——如果哪次改动让 0.074ms 翻倍，无头断言全绿、只有 L2 能看见。
- **L3 抓渲染回退**：blit 忘平移命令几何那次，无头测试全绿（坐标合同在录放两侧各自成立），**只有截图暴露**动画面板盖住静态文字。

三层的成本依次上升（L1 毫秒级、L2 要写脚本、L3 要开窗口），收益互补、不可互替。「无头全绿 + 窗口必验」是本阶段的交付纪律，不是仪式。

## 3. 四个计数观测口的精确语义

L1 的四个数字经常被读错，逐个钉死语义（源码依据见 `《03》`）：

| 观测口 | 语义 | 不是什么 |
|---|---|---|
| `layoutPasses` | flushLayout 被调用的**次数**（每帧 +1，含空跑） | 不是布局工作量 |
| `totalPerformLayouts` | 全树 performLayout 执行次数**累计** | 不随 idle 帧变化——工作量度量 |
| `paintPasses` | flushPaint 调用次数 | 同 layoutPasses |
| `repaintedNodes` | **本帧**重录的边界/根数（每帧清零重计） | 不是被 blit 的边界数，不是子树节点数 |

配对用法（02 册实跑表的活例）：`layoutPasses = frames + 1` 是**定义量**（每帧必调 + 首帧多一次），它坏了说明帧循环结构坏了；`repaintedNodes = 2` 是**物理量**（动画面板边界 + 根），它涨了说明失效边界漏了；`frames` 本身是**调度量**（115~118 漂移），优化它没有意义。三类量混读是性能面板最常见的错误——「帧数降了」可能只是调度抖动，而 passes 不变。

## 4. 无头压测方法：可复制的骨架

完整压测脚本（本次实跑用 `/private/tmp/mini-gui-bench/bench.ts`，关键段如下，可直接改路径复跑）：

```ts
function bench(boundaries: boolean, label: string): void {
  const { root, leaves } = buildTree(boundaries);        // 50 行 × 20 盒 = 1000 盒
  const owner = new PipelineOwner();
  owner.mount(root, { width: 640, height: 900 }, { tightRoot: true });

  let t0 = performance.now();
  owner.frame();                                          // 冷帧
  const cold = performance.now() - t0;

  const idle: number[] = [];                              // 空闲帧 ×100
  for (let i = 0; i < 100; i++) {
    t0 = performance.now();
    owner.frame();
    idle.push(performance.now() - t0);
  }

  const single: number[] = [];                            // 单叶变更 ×200
  for (let i = 0; i < 200; i++) {
    const leaf = leaves[(i * 7) % leaves.length]!;
    leaf.boxWidth = 14 + (i % 3);
    leaf.markNeedsLayout();
    t0 = performance.now();
    owner.frame();
    single.push(performance.now() - t0);
  }
  ...                                                     // 中位/p95 汇总（同款方法测合并失效）
}
bench(false, "无边界(1000盒)");
bench(true,  "每行边界(50边界)");
```

方法论的六条纪律：

1. **中位数为主、p95 为辅**——中位答「常态多快」，p95 答「坏的时候多坏」；只看均值会被首帧尖峰污染（02 册 maxDt 的教训）。
2. **对照要同树**——「无边界 vs 每行边界」是同一棵树的两种包裹，结构变量唯一。
3. **采样够多**——单叶 200 次、空闲 100 次；少于 30 次的 p95 就是噪声。
4. **冷热分开**——首帧含窗口/字体/整树首排，永远单独报。
5. **计数与计时同跑**——`repaintedNodes`、`totalPerformLayouts`、`layer.commands.length` 与耗时同帧采，发现「快了但计数涨了」的假优化。
6. **脚本在库里，数字在册里**——本次脚本在 /tmp 是因为它是测量工具而非交付物；固化成回归时应进 `labs/mini-gui/bench/` 并在册中留复跑命令。

### 5.4 分段计时：layout 与 paint 各占多少

同一次变更帧拆开计（segments 脚本：flushLayout 与 flushPaint 分别夹表，200 次单叶变更取中位；2000 盒树）：

| 场景 | layout | paint | 合计 | 布局占比 |
|---|---|---|---|---|
| 冷帧（全树首排） | 1.37 ms | 1.23 ms | 2.60 ms | 53% |
| 单叶变更（中位） | **0.009 ms** | **0.047 ms** | 0.055 ms | **16%** |
| 根图层命令数 / 整段 replay 中位 | — | — | 2001 条 / **0.016 ms** | — |

两个推翻直觉的读数：

**读数一：稳态变更帧里布局已经「消失」**。0.009ms——relayout boundary（isFixedSize 叶子自己是边界）+ 布局缓存把单叶变更的布局成本压到微秒级；剩下的 84% 全是 paint（根图层重录 2001 条命令）。结论直接改写优化优先级：**这个形态下优化布局是零收益，全部注意力给绘制**（重录半径/呈现合批/合成器）。与 §5.1「totalPerformLayouts 双设计相同」互为印证——边界省的从来不是布局。

**读数二：整段 replay 只要 0.016ms**。2001 条命令的逐条 execute 全程 16μs，占 16.6ms 预算的 **0.1%**。这一锤定音地回答了「第三道防线值不值得做」：脏矩形方案要先对 2001 条命令做矩形求交（保守 5~10ns/条 = 10~20μs），再 scissor 提交——**求交成本 ≥ 整段重放成本**，净收益为零甚至为负。§6 的第四个负收益样本由此而来：§5 的纸面算术（「提交量上限缩到 0.8%」）混淆了「提交量」与「耗时」——raylib 的 draw call 便宜到求交抢跑。

方法论价值：分段计时把「优化哪一段」从品味题变成算术题。三段账（layout/paint/replay）一旦分开，预算表的空洞立即显形——本形态下三段全部远离预算，真正的瓶颈在 raylib 提交侧（窗口实测的 frames 漂移），无头压测根本测不到它（§8 第 4 条的活例）。


## 6. 三个「负收益优化」的识别样本

度量不止用来找瓶颈，更用来拦住假优化。本次压测顺手验证的三个直觉，全部被数据否决或限定：

**直觉一：「给所有节点加边界总是更好」**——否。空闲帧 0.014ms 双设计相同（没有失效就没有区别）；单叶变更的 2× 收益只在「变更局部」时存在；附录 E/F 的纸面账显示粒度太细时 blit 树本身变成成本中心。正确决策是按**变更的空间局部性**选粒度。

**直觉二：「合并失效收益很小吧，标脏已经很便宜了」**——否，且方向反了。标脏确实便宜（0.039ms 里的大头是 flush），但 flush 的次数决定总账：200 叶逐帧还账 ≈7.8ms vs 合并一帧 0.065ms（`《03》`§6.1，≈120×）。合并的收益不在 mark 里，在 **flush 次数**里——这就是「帧尾一次 flush」铁律的量化依据。

**直觉三：「命令数涨了说明优化失败」**——不一定。1001 条命令是**结构量**（树的形状决定）；单叶变更后命令数不变而 p95 降半，恰恰说明 blit 起了作用（paintSelf 省了、命令拷贝补上）。行为看 repaintedNodes 与时长，结构看命令数——三个口径各管各的。

识别假优化的通用流程：**改之前跑基线 → 改之后同口径重跑 → 计数与计时一起看 → 「快了但计数涨了」要追因**。压测脚本固化进 bench/ 后，这三步就是 CI 里的一行命令。

### 6.4 第四个负收益样本：「给 replay 加脏矩形裁剪」

§5.4 的实测补上了本册最后一个反直觉结论。§5 的纸面算术算出过「单叶变更的提交量上限缩到 0.8%」——听起来 120×。但分段计时给出分子分母的另一半：整段 replay 才 0.016ms，脏矩形方案的命令求交本身要 10~20μs。**省下的（0.016ms）≈ 花掉的（0.015ms）**，净收益 ≈ 0。

教训的通用形态：**「减少工作量」不等于「减少耗时」——要先量单位工作的成本**。命令提交的单价是 8ns（2001 条 / 16μs），这个量级下一切花哨的过滤逻辑都要先跟 8ns 打擂台。脏矩形真正登场要等两个条件之一：命令单价变贵（GPU 提交、真实光栅化），或命令数变到万级（求交 O(n) 线性，但 scissor 节省的光栅化面积开始占主导）。这正是《04》说「万盒以上才值得」的实测注脚。


## 7. HUD 与截图：窗口侧的最后两件武器

L3 的两个观测手段各有不可替代性：

**HUD 帧统计**（`fps ${getFPS()} repainted ${n} cmds ${m}`）：raylib 的 `getFPS()` 是滑动窗口平均（ ours 是自己的亏空结论 59<60 的来源）；repainted/cmds 是自产观测口的实时投影。02 册讲过的「显示滞后一帧」（实参先于赋值求值）在 HUD 上永久存在——面板实现守则：**显示值永远标注采样时刻，或者接受一帧滞后并在标题里写明**。

**截图断言**（`MINI_GUI_SHOT` + 图像分析）：像素级正确性的最后防线。本阶段两次实战：动画场景六要素（静态文字/方块/圆/HUD 行）齐活无错位；双重平移事故只有截图能抓（无头两层各自成立、合成后漂移）。截图的弱点也要诚实：它是**点采样**——截图那一帧刚好动画在半程，断言「圆在 (230,140)」就取决于时机。工程做法是配合 `MINI_GUI_SECONDS` 在稳态帧截图（比如第 120 帧），或按动画相位挑帧。

## 8. 度量的边界：这些数字不能外推

诚实声明四条，防数字被误用：

1. **绝对值不可移植**。0.014ms / 2.85ms 是本机（macOS arm64、tsx 直跑 TS）数字；换机器、换 ScriptC 原生产物、换 raylib 后端都会变。**可移植的是比例与不变量**（空闲帧 ≈ 冷帧的 0.5%、repainted 1 vs 2、passes=frames+1），不是毫秒数。
2. **1000 盒不代表真实 UI**。真实界面是文本（排版贵）+ 图片 + 深树；1000 个 RenderBox 是「最便宜的一千个节点」。压测结论外推到文本树时要重新测——文本度量有缓存（第三阶段），行为不同。
3. **中位数与 p95 都不是尾部**。真掉帧要看 p99 / max 与长会话分布（GC 累积、图层内存增长）；本次 200 采样对 p99 太薄。压测骨架固化为回归时，采样数要升到 1000+。
4. **无头与窗口不等价**。无头压测测不到 raylib 的提交/等待侧（GPU 交互、swap 阻塞）；窗口实测的 frames 漂移里混着系统噪声。两层数字永远分开报，不混算。

## 9. 本册小结

- 度量第一课是预算表：16.6ms 分五段记账，每个测量值先归档「离预算几倍」再决定动不动手
- 三层度量面：无头计数（逻辑对）→ 无头计时（多少毫秒）→ 窗口实跑（用户所见）；各有一案只有它能抓（断言面/分布尾/截图）
- 四个计数口语义钉死：passes 是次数、totalPerformLayouts 是工作量、repaintedNodes 是本帧重录数；物理量/定义量/调度量三类混读是面板大忌
- 压测六纪律：中位+看 p95、对照同树、采样 ≥100、冷热分开、计数计时同跑、脚本入库
- 实测总账：空闲帧 0.014ms（预算 0.08%）、分段账 layout 0.009 / paint 0.047 / replay 0.016ms；、单叶 p95 边界粒度 2.0×、合并失效 120×、供给侧亏空 4.6%
- 四个负收益样本：全节点加边界 ✗、合并收益小 ✗、命令数涨=失败 ✗——度量拦假优化
- 四条边界：绝对值不可移植、千盒非真实 UI、p99 需千级采样、无头与窗口分开报

## 附录 A：分段计时脚本全文（可直接复跑）

放在 `/tmp` 的测量脚本全文——固化成回归时移入 `labs/mini-gui/bench/segments.ts` 并加 CI 阈值断言：

```ts
import { performance } from "node:perf_hooks";
import { rgba } from "./src/core/color.ts";
import { RenderBox, RenderColoredBox } from "./src/core/render/layout-widgets.ts";
import { FlexDirection, RenderFlex } from "./src/core/render/flex.ts";
import { PipelineOwner } from "./src/core/render/owner.ts";
import { DisplayList } from "./src/core/painter.ts";

const RED = rgba(200, 60, 60);
function build(n: number): { root: RenderColoredBox; leaves: RenderBox[] } {
  const root = new RenderColoredBox(rgba(245, 246, 248));
  const col = new RenderFlex({ direction: FlexDirection.column, gap: 2 });
  const leaves: RenderBox[] = [];
  for (let r = 0; r < n / 20; r++) {
    const row = new RenderFlex({ direction: FlexDirection.row, gap: 2 });
    for (let i = 0; i < 20; i++) {
      const box = new RenderBox(14, 14, RED);
      row.appendChild(box);
      leaves.push(box);
    }
    col.appendChild(row);
  }
  root.appendChild(col);
  return { root, leaves };
}

const owner = new PipelineOwner();
const { root, leaves } = build(2000);
owner.mount(root, { width: 640, height: 1400 }, { tightRoot: true });

// 冷帧分段
let t = performance.now();
owner.flushLayout();
const layoutMs = performance.now() - t;
t = performance.now();
owner.flushPaint();
const paintMs = performance.now() - t;
console.log(`冷帧: layout ${layoutMs.toFixed(2)} + paint ${paintMs.toFixed(2)} = ${(layoutMs + paintMs).toFixed(2)}ms`);

// 稳态：单叶变更分段 ×200 取中位
const segs: { l: number; p: number }[] = [];
for (let i = 0; i < 200; i++) {
  const leaf = leaves[(i * 7) % leaves.length]!;
  leaf.boxWidth = 14 + (i % 3);
  leaf.markNeedsLayout();
  t = performance.now();
  owner.flushLayout();
  const l = performance.now() - t;
  t = performance.now();
  owner.flushPaint();
  const p = performance.now() - t;
  segs.push({ l, p });
}
const med = (a: number[]): number => a[Math.floor(a.length / 2)]!;
const ls = segs.map((s) => s.l).sort((a, b) => a - b);
const ps = segs.map((s) => s.p).sort((a, b) => a - b);
console.log(`单叶变更中位: layout ${med(ls).toFixed(3)} | paint ${med(ps).toFixed(3)} | 和 ${(med(ls) + med(ps)).toFixed(3)}ms`);

// replay 整段（注意目标必须是 CommandSink——DisplayList 本身；传 StatefulPainter 会炸：它不是 sink）
const layer = root.layer!;
const reps: number[] = [];
for (let i = 0; i < 50; i++) {
  t = performance.now();
  layer.replay(new DisplayList());
  reps.push(performance.now() - t);
}
reps.sort((a, b) => a - b);
console.log(`根图层 ${layer.commands.length} 条命令，整段 replay 中位 ${med(reps).toFixed(3)}ms`);
```

两个复跑提示（都实测踩过）：①脚本放 /tmp 时 import 用绝对路径——相对路径按脚本所在目录解析，不是 CWD；②replay 的目标是 `DisplayList`（它实现了 CommandSink），传 `StatefulPainter` 会 `execute is not a function`——Painter 是录制前端不是回放端，两个身份别混。

## 附录 B：把压测固化成回归的清单

| 步骤 | 内容 | 验收 |
|---|---|---|
| 入库 | bench 脚本移入 `labs/mini-gui/bench/`，package.json 加 `"bench": "tsx bench/segments.ts"` | `npm run bench` 一键复跑 |
| 基线 | 首跑数字记入 `bench/BASELINE.md`（本机 + 日期 + Node 版本） | 基线可追溯 |
| 阈值 | CI 里对**中位数**断言（如 空闲帧 < 0.05ms、单叶 < 0.15ms）——阈值放 5× 余量防环境抖动 | 回归即红 |
| 豁免 | p95/冷帧**只记录不断言**（尾部噪声大，误报伤 CI 信任） | 报表可见、门禁不拦 |
| 快照 | 计数类（repaintedNodes/命令数）用 vitest 断言，不走计时 bench | 逻辑回退零容忍 |

阈值为什么放 5×？本机两次同脚本重跑的抖动实测：冷帧 2.03→2.85ms（±40%）、单叶中位 0.036→0.039ms（±8%）。**尾部噪声 > 中位噪声一个量级**——断言盯中位、放五倍余量，报表记录全部，门禁只拦真正的大回退（比如 paintedNodes 从 2 涨到 2001 这种结构性劣化，vitest 层就红）。
