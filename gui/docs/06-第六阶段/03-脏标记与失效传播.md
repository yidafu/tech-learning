# 脏标记与失效传播：自底向上标脏、自顶向下消化

> [返回：第六阶段导览](01-导览.md)
> 对应大纲条目：第六阶段 2（失效传播：markNeedsLayout/markNeedsPaint、首个脏节点、同帧合并失效）。
> 本册走读 `core/render/render-object.ts` 的两个 mark 方法与 relayout 边界判定、`core/render/owner.ts` 的两个 flush 队列，外加 `pipeline.test.ts` / `layout.test.ts` 的失效组断言与一次 tsx 无头压测（2026-11-14 本机实跑）。读完你应当能：手推任意「改一处」在树上的失效传播路径、算出该帧的 flush 成本、说清「已脏即停」守卫为什么差点吞掉首帧。

## 1. 概念坐标：失效 = 一张欠条

第三阶段的布局协议让「改一处」天然要重算一串：叶子尺寸变了 → 父的排列要重算 → …直到某个「尺寸不受子影响」的节点。失效传播要回答的不是「怎么重算」（那是 flush 的事），而是两个更省的问题：

```text
① 这一串重算的终点在哪？（relayout boundary：冒泡到哪为止）
② 什么时候算？（不是立刻算，是记账——下一帧 flush 一起算）
```

于是「改一处」的全部成本被压缩成一张欠条：

```text
leaf.markNeedsLayout()
  → 冒泡到 relayout boundary（比如叶子自己：isFixedSize 尺寸不随约束变）
  → boundary 上报 owner.scheduleLayoutBoundary(this)
  → 返回。全程 O(树深)，零布局计算
下一帧 owner.frame() → flushLayout() → 只对队列里的 boundary 调 layout()
```

树上一万个节点，一次失效的成本是 O(深度) 的标记 + 一帧后 O(脏子树) 的重算——中间隔着一帧，N 次 mark 合并成一次 flush。这就是「合并失效」的全部机制，没有任何魔法。

## 2. markNeedsLayout：冒泡 + 边界 + 上报

源码整段（`render-object.ts`，逐字）：

```ts
  markNeedsLayout(): void {
    if (this.needsLayout) return; // 已脏：冒泡在第一次变脏时已发生
    this.needsLayout = true;
    if (this.relayoutBoundary === this || this.parent === null) {
      // 边界（或根）：冒泡到此为止，但必须有人记得来重排这棵子树 —— 上报 owner
      if (this.owner !== null) this.owner.scheduleLayoutBoundary(this);
      return;
    }
    this.parent.markNeedsLayout(); // 不是边界 → 传染给父（父的尺寸可能因此变）
  }
```

三个要点：

**① 「已脏即停」在这里是安全的**。`if (this.needsLayout) return` 的理由写进了注释：已脏说明冒泡**第一次**变脏时就发生过了——路径上需要标脏的祖先当时已全部标过，上报也已发出。这与绘制侧的同名守卫形成对照（第 3 节：绘制侧为什么一度不敢用）。

**② 边界判定是三选一**（`updateRelayoutBoundary`，逐字）：

```ts
  private updateRelayoutBoundary(c: BoxConstraints): void {
    const tightNow = c.minWidth === c.maxWidth && c.minHeight === c.maxHeight;
    if (tightNow || this.isFixedSize() || this.parent === null) {
      this.relayoutBoundary = this;
    } else {
      const p = this.parent;
      this.relayoutBoundary = p !== null ? p.relayoutBoundary : this;
    }
  }
```

| 条件 | 为什么「子变我不变」 | 例子 |
|---|---|---|
| 约束紧（min=max） | 紧约束下子被钳死，尺寸由父定 | 窗口根、`SizedBox` |
| `isFixedSize()` 覆写为 true | 尺寸来自自身参数，不问子 | `RenderBox(14,14)`、文本（度量完即定） |
| 根 | 没有父可传染 | 任何树 |

边界在**每次 layout 后**重算（约束从松变紧的节点当场升级为边界）。压测里的 1000 个 `RenderBox(14,14)` 叶子全部是「isFixedSize → 自己是自己的边界」——这是后面「单叶变更只花 0.039ms」的前提。

**③ 上报而非入栈。** `scheduleLayoutBoundary` 把 boundary 塞进 `pendingBoundaries` 队列；flush 时逐个 `node.layout(node.lastConstraints ?? loose(rootSize))`（owner 逐字）。注意**约束从哪来**：boundary 的 `_lastConstraints` 缓存了上次收到的约束（`layout()` 里 `_lastConstraints = c`），重排沿用旧约束——「边界外世界没变」的兑现。

## 3. 布局缓存：不脏 + 约束没变 = 白嫖

`layout()` 开头的短路（逐字）：

```ts
  layout(c: BoxConstraints): void {
    const constraintsChanged = this._lastConstraints === null || !constraintsEqual(this._lastConstraints, c);
    if (!this.needsLayout && !constraintsChanged) {
      return; // 布局缓存：不脏 + 约束没变 → 直接复用
    }
    ...
    this.layoutCount += 1;
    this.performLayout(c);
```

`layoutCount` 是观测口：`performLayout` 真跑了多少次。`layout.test.ts` 的「同样状态再 flush：零 performLayout」（实跑）锁死它——树挂上不动，第二次 `flushLayout` 的 `totalPerformLayouts` 增量为 0。这条缓存让 flushLayout 的队列消化变成**三段成本**：

```text
boundary 自己：必重算（脏）
boundary 子树：layout() 被递归调用 → 不脏 + 约束没变 → 短路跳过（O(1) 每节点）
boundary 祖先：压根不碰（不在队列里）
```

压测里的 `totalPerformLayouts = 21302`（200 次单叶变更 + 100 次 200 叶合并后累计）能对上账：20200（叶）+ 1052（首帧整树）≈ 21252，余量来自合并轮里叶子被重复标脏的计数——每一笔都能指出是谁花的。

## 4. markNeedsPaint：没有守卫的冒泡（事故复盘）

绘制侧的失效方法（逐字）：

```ts
  markNeedsPaint(): void {
    this.needsPaint = true;
    let node: RenderObject = this;
    while (node.parent !== null && !node.isRepaintBoundary()) {
      node = node.parent;
      node.needsPaint = true;
    }
    if (node.owner !== null) node.owner.schedulePaintBoundary(node);
  }
```

三处与布局侧刻意不同：

**① 循环而非递归**——布局侧要「边界才停」，绘制侧是「**最近的**重绘边界才停」，用 while 沿父链找第一个 `isRepaintBoundary()`。边界判定只有一个来源：`RenderRepaintBoundary` 覆写返回 true（22 行的透明容器，布局上完全透传）。

**② 路径上的祖先全部标脏**。循环体里 `node.needsPaint = true` 不能省：父层即使自己重录，它的**图层里含着 blit 来的子内容**——子变了，blit 进来的拷贝就过期了。这个「祖先链补偿」在 flushPaint 里还有一步队列补脏（owner 侧），两道保险。

**③ 没有「已脏即停」守卫——这是事故现场**。初版这里写过 `if (this.needsPaint) return;`，实测炸了：`RenderObject` 的两个脏标志**初始值就是 true**（`needsPaint = true` 是字段声明的初始字面量，`mount` 依赖它完成首帧绘制）。于是「首帧前从未被调度过的节点」永远命中「已脏即停」，`markNeedsPaint` 直接 return——**边界从未上报**，`flushPaint` 的队列是空的，首帧只有根被 owner.mount 显式标过。修法与理由都写在注释里（原文）：

```ts
  /** 绘制失效：自底向上冒泡到最近的重绘边界（或根），边界上报 owner。
   *  注意不做「已脏即停」守卫：初始态 needsPaint=true 的节点从未被调度过，
   *  早停会把它们的边界吞掉（实测踩过：首帧只重录了根）。去重在 flushPaint 做。 */
```

去重交给 flushPaint 的 `pending.indexOf(node) < 0` 判断——重复入队是廉价的（一次线性查重），吞掉边界是昂贵的（首帧白屏）。**「守卫放哪一层」是失效系统设计的经典决策**：布局侧守卫安全（`needsLayout` 初始 false，第一次变脏必冒泡）；绘制侧守卫致命（初始 true，第一次调用就是假阳性）。

## 5. flushLayout / flushPaint：队列消化与排序

`flushLayout`（逐字，省略观测口）：

```ts
  flushLayout(): void {
    const root = this.root;
    if (root === null) return;
    root.layout(this.tightRoot ? tight(this.rootSize) : loose(this.rootSize));
    // 根没变脏时布局会被缓存跳过，但边界子树仍要按缓存约束重排
    const pending = this.pendingBoundaries;
    this.pendingBoundaries = [];
    for (const node of pending) {
      node.layout(node.lastConstraints ?? loose(this.rootSize));
    }
  }
```

两个细节：根**永远先试**（首帧整树布局靠它；稳态帧它被缓存短路，O(1)）；队列消化用**交换后清空**（`pending = this.pendingBoundaries; this.pendingBoundaries = []`）——消化期间新的失效进入新队列，天然防重入死循环。

`flushPaint` 多两步，都是合成正确性的代价（逐字段）：

```ts
    // 祖先链失效传播：blit 过旧内容的边界/根要标脏并入队（否则 skip 条件会跳过它们）
    for (const node of queued) {
      let a = node.parent;
      while (a !== null) {
        if (a.isRepaintBoundary() || a === root) {
          a.needsPaint = true;
          if (pending.indexOf(a) < 0) pending.push(a);
        }
        a = a.parent;
      }
    }
    ...
    // 深度大的先录（内层边界先更新，外层 blit 到的才是新内容）
    pending.sort((a, b) => this.depthOf(b) - this.depthOf(a));
```

**祖先链补脏**与 markNeedsPaint 路径标脏是两道保险：mark 只标「从脏节点到边界的直系路径」，flush 这里补「边界以上的全部重绘边界」——因为 blit 树是**跨层**的（根图层 blit 着每个干净边界的拷贝），任何一处重录都让上层拷贝过期。

**深度降序**是合成正确性的时序保证（原文注释即证明）：内层先录新内容，外层重录时 blit 到的才是新图层。反例推演（09 专题《堆叠分层》§6.5 写过完整三边界手算）：A 先录（blit 进旧 B）→ B 再录新内容 → 根 blit 的 A 里封着旧 B，新探针消失一帧。

最后 `clearPaintDirty(node)` 整子树清脏——录过的子树视为最新，不用逐节点对账。

### 5.5 边界不是终身制：每次 layout 后重算

`updateRelayoutBoundary` 在 `layout()` 的**末尾**执行（第 2 节的源码顺序：performLayout → 钳制 → updateRelayoutBoundary → markNeedsPaint）。这意味着边界身份随约束动态变化——同一条三节点链（根 → Align → 盒子），两次 flush 之间可以换边界：

```text
首次 flush（tightRoot=false，根收 loose(640×900)）：
  根：tightNow=false，isFixedSize=false，parent=null → 边界 = 自己（根兜底）
  Align：非紧、非固定 → 继承父的边界 = 根
  盒子(14×14)：非紧（0..640）、isFixedSize=true → 边界 = 自己 ✓

第二次 flush（owner.resize + tightRoot=true，根收 tight(640×900)）：
  根：tightNow=true → 边界 = 自己
  Align：收到的约束仍是松（Align 内部 loosen 后传子……不对——Align 自己收的是根的紧约束）
  → Align：tightNow=true（min=max=640/900）→ 边界 = 自己（升级！）
  盒子：isFixedSize → 边界仍是自己
```

推论：`Align` 在松约束下「盒子变尺寸它要跟着变」（必须冒泡到根），紧约束下它自己被钉死「子变我不变」（升级为边界）。同一节点、同一代码，**约束一换边界身份就换**——这就是为什么重算放在 layout 末尾：只有重算完尺寸，才知道新约束下的边界归属。

## 6. 合并失效：重入语义与攒批时间账

flushLayout 消化队列用的是**交换后清空**：

```ts
const pending = this.pendingBoundaries;
this.pendingBoundaries = [];
for (const node of pending) { node.layout(...); }
```

消化期间如果 layout 过程触发新的 `markNeedsLayout`（比如某个 performLayout 改了文本导致自己重标），新欠条进入**清空后的新队列**——本帧不消化，留给下一帧。这是刻意设计，三个理由：

| 理由 | 展开 |
|---|---|
| 防死循环 | 当场消化新队列 = while 循环，layout 互相触发永不收敛（布局抖动场景） |
| 有界成本 | 一帧最多消化「帧开始时的欠条量」，长尾可预测 |
| 语义干净 | 「一帧内最多排一次布局」——新失效的答案依赖本轮布局结果，本帧算不了 |

代价要诚实：**新失效要多等一帧**。对动画类连续失效没有影响（每帧本来就要 tick）；对「布局结果触发新布局」的连锁场景（自动换行引发滚动条出现又引发宽度变化），表现为两帧收敛而不是一帧——比死循环好，比 CASSOWARY 式一步收敛慢。观察手段：`layoutPasses` 连续 +2 而不是 +1，就是发生了重入欠账。

flush 消化的入口行为见 §5.5/§6.1 的机制部分；这一节先把「攒批」的时间账摆出来——合并失效的全部收益都来自这里。

### 6.1 攒批时间账：一帧还一笔 vs 一笔还一帧

同一帧内多次失效的消化账（无头压测 2026-11-14，tsx 实跑，1000 盒树）：

| 场景 | 帧数 | 每帧成本（中位） | 总账 |
|---|---|---|---|
| 200 个叶逐个改、逐帧 flush | 200 帧 | 0.039 ms | ≈ 7.8 ms |
| 200 个叶同一帧标脏、一次 flush | 1 帧 | 0.065 ms | 0.065 ms |

**≈ 120×**。合并的机制零成本：`pendingBoundaries` 是数组，mark 是 push，flush 是一次遍历——「攒一批」天然免费。反过来的教训是 flush 的时机：**每输入事件 flush 一次**就把合并浪费光（200 次 flush 各自消化 1 个边界）；**每帧 flush 一次**才吃满。这也是宿主循环把 `owner.frame()` 固定在帧尾的原因（`《02》`的第 3 节）。

三条限制也如实写：

- **跨帧不合并**：上一帧的队列在上一帧消化完了，欠条不积压。这是「一帧内最多排一次布局」的语义，代价是输入事件到上屏固定间隔一帧。
- **不同轴不合并**：`markNeedsLayout` 与 `markNeedsPaint` 是两个队列。布局失效会级联绘制失效（`layout()` 末尾 `markNeedsPaint()`，逐字注释「重排过的子树必然要重画」），反过来不成立。
- **队列去重是线性的**：`indexOf` 查重 O(队列长)。一帧内几千个边界同脏时这是可测的成本——工程化时换 Set（ScriptC 教学版保守走数组）。

## 7. 实测：三个不变量

pipeline.test.ts 的失效组（实跑，2026-11-14，全库 25 文件 201 断言绿）：

```text
✓ 无变化帧：零重录、零 paintSelf          —— repaintedNodes=0，paintCount 不增
✓ 左面板变化：只有左边界 + 根重录          —— repaintedNodes=2，右探针 paintCount 不变
✓ 布局失效级联绘制失效                     —— markNeedsLayout → frame 后 paintCount 必 +1
```

加上 tsx 压测的两个数字，失效系统的三张底牌：

| 观测 | 数字 | 含义 |
|---|---|---|
| 空闲帧成本 | 中位 **0.014 ms**（1000 盒树） | 欠活清单的兑现：没欠条 ≈ 白送一帧 |
| 单叶变更成本 | 中位 0.039 ms / p95 0.145 ms | 边界 + 缓存把 O(整树) 压成 O(脏子树) |
| 合并收益 | 200 叶合帧 ≈ 逐帧的 1/120 | 攒批免费，flush 时机决定能否吃到 |

## 8. 与其他框架的对照

| 机制 | mini-gui | Flutter | 浏览器 |
|---|---|---|---|
| 布局失效 | `markNeedsLayout` → relayout boundary 队列 | `markNeedsLayout` → `PipelineOwner.flushLayout`（同名同构） | style invalidation set（过滤掉不影响布局的类名变更） |
| 绘制失效 | `markNeedsPaint` → repaint boundary 队列 | `markNeedsPaint` → `flushPaint` | paint invalidation → 脏矩形合并 |
| 合并点 | 帧尾 `owner.frame()` | `SchedulerBinding` 帧尾持久回调 | 渲染帧边界（rAF 前） |
| 布局边界三条件 | tight / isFixedSize / 根 | sizedByParent + 紧约束 + isRepaintBoundary 类似组合 | 无显式边界（全树 style recalc 有 hash 缓存） |
| 已脏即停 | 布局侧有、绘制侧无（初始脏事故） | 两侧都有（`_needsLayout` 初始 false，无此事故面） | 失效集天然幂等 |

Flutter 的同名方法是本册的直系对标（术语都借自它）；差异在「初始脏」：Flutter 节点创建时 `_needsLayout = false`，首帧靠 `view` 显式 mark——mini-gui 选了「生来即脏」，省掉首帧的显式标脏，代价就是这次守卫事故。两个方向都成立，关键是**知道初始值是谁在消费**。

## 9. 本册小结

- 失效传播 = 两张欠条清单：`pendingBoundaries`（布局）/ `pendingPaintBoundaries`（绘制）；mark 是 O(树深) 的记账，flush 是 O(脏子树) 的还账
- relayout 边界三条件：约束紧 / isFixedSize / 根——每次 layout 后重算；边界重排沿用 `_lastConstraints` 缓存
- 布局缓存短路：不脏 + `constraintsEqual` → `performLayout` 都不进（`layoutCount` 观测口锁死）
- 绘制侧无「已脏即停」：初始 `needsPaint=true` 会把从未调度过的边界吞掉（实测事故）；去重移交 flushPaint
- flushPaint 三件套：祖先链补脏（blit 拷贝过期补偿）+ 深度降序（内层先录）+ 整子树清脏
- 合并失效免费，收益由 flush 时机决定：帧尾一次 flush，200 叶合并 ≈ 逐帧的 1/120（实测）
- 空闲帧 0.014ms：失效系统做对了的唯一证明方式，就是「什么都不变时什么都不做」

| 调用点 | 触发场景 | 失效类型 |
|---|---|---|
| `render-object.appendChild/removeChild` | 树结构变化 → 子树尺寸必变 | layout |
| `RenderText.setText` | 文本内容变化 → 重新度量断行 | layout（→级联 paint） |
| `RenderScroll.scrollBy` | 滚动位置变化——**不标布局**，只 `placeContent` + markNeedsPaint | paint only |
| `owner.mount/resize` | 根尺寸变化 | layout（整树） |
| `RenderTextField.setText`（第八阶段） | 文本变化 | layout |
| `RenderVirtualList.rebind`（第八阶段） | 行池重绑 → 行位置变 | paint（池行 y 是直接赋值） |

清单里的对照案例正是「标对脏」的教学点：`scrollBy` **刻意不标布局**——滚动只改内容 y（纯绘制变化），布局缓存全部保留，这是滚动帧 0.014ms 的另一半原因（滚动帧 ≈ 空闲帧 + 一次 blit 偏移修正）。而 `setText` 必须标布局——文本宽度影响父 Flex 的排列。**标错方向的代价**：该标布局的只标了绘制 → 命中对、绘制错（第五阶段的真实事故）；不该标布局的标了 → 白付整行重排。审查口诀：**「这次变化会不会改变任何节点的尺寸？」会 → layout；只是位置/外观 → paint。**
