## 1. 概念坐标：局部重绘的三道防线

「改一处只重画一处」在自绘框架里是三道防线，逐级缩小成本：

```text
第一道  失效截断   markNeedsPaint 在最近重绘边界停住           —— 已做（第 6 阶段 03）
第二道  图层重录   脏边界子树重录自己的图层（局部坐标）；        —— 已做（本册 §2~§4）
                   干净边界被父 blit（命令拷贝）搬进祖先图层
第三道  呈现合批   replay 只提交脏矩形 ∩ scissor 的命令          —— 没做（§5 诚实账本）
```

本版框架把第一、二道做实了，第三道停留在「可行路径」的纸上设计。这样分工的理由：一、二道是**正确性**（不截断就全树重画，不算就错位），第三道是**纯性能**（多提交了也不会错，只是费电）。教学版先把对的做对，贵的做便宜。

三道防线各自有一张成本账，本册给第一道配了实跑数字；第二道给机制加对照实验；第三道给可复制的纸面算术。

## 2. RenderRepaintBoundary：22 行的完整源码

整个类贴出来（`repaint-boundary.ts`，逐字）：

```ts
// 重绘边界：isRepaintBoundary = true 的透明容器（布局约束透传，尺寸 = 子）。
// owner.flushPaint 只重录脏边界；干净边界被父 blit（图层合成）。
import type { BoxConstraints } from "./constraints";
import { RenderObject } from "./render-object";

export class RenderRepaintBoundary extends RenderObject {
  isRepaintBoundary(): boolean {
    return true;
  }

  protected performLayout(c: BoxConstraints): void {
    const child = this.children[0];
    if (child === undefined) {
      this.setSize(c, { width: c.maxWidth, height: c.maxHeight });
      return;
    }
    child.layout(c);
    child.x = 0;
    child.y = 0;
    this.setSize(c, child.size);
  }
}
```

四个观察点：

| 观察点 | 内容 | 为什么值得强调 |
|---|---|---|
| 全部行为就两件 | `isRepaintBoundary() → true` + 布局透传 | 重绘边界是**协议角色**不是功能：所有重活都在 owner 的 flushPaint 和基类 paintInto 里 |
| `performLayout` 与 GridCell/Positioned 同构 | 透传约束、尺寸抄子、x/y 清零 | 单子容器的三件套在框架里出现了第三次——「透传容器」是最常见也最无聊的布局器 |
| 无子时拿满约束 | `setSize(c, {maxWidth, maxHeight})` | 空边界当「占位框」用时不炸 |
| 命名 | `RenderRepaintBoundary`（非 RepaintWidget） | 教学版只有 RenderObject 层，声明式包装是第七阶段的事 |

**什么时候该套这个类**——收益条件算术见 §6；§7 的对照实验给出实测答案：每行一个边界，1000 盒树的单叶变更 p95 从 0.145ms 降到 0.074ms，冷帧从 2.85ms 降到 1.57ms。

## 3. 重录与合成的坐标合同

`flushPaint` 的录入循环（`owner.ts`，逐字，省观测口）：

```ts
    for (const node of pending) {
      if (!node.needsPaint && node.layer !== null) continue;
      const list = new DisplayList();
      const painter = new StatefulPainter(list);
      node.paintInto(painter);   // 图层是局部坐标（父在 blit 时补偏移）
      node.layer = list;
      this.clearPaintDirty(node);
      this.repaintedNodes += 1;
    }
```

合同一句话：**图层内容 = 边界局部坐标（原点 = 边界左上），偏移由父在 blit 时补**。两个方向撑住它：

- **录**：`paintInto` 不自带平移（`paint()` 才自带，`flushPaint` 走 `paintInto`）。这里曾有双重平移事故（录时烘进自身 x/y → 父再补一次 → 内容漂到 2× 偏移；右面板 2×100=200 被黄金用例实抓，修复全过程在《09 专题·堆叠分层》§6.2）——坐标合同必须唯一，平移的归属权只许发生一次。
- **放**：基类 `paintInto` 遍历子时对干净边界做 `translate(child.x, child.y) + blit(child.layer)`（`render-object.ts`，逐字）：

```ts
      if (!child.needsPaint && child.layer !== null && child.isRepaintBoundary()) {
        // 图层合成：干净的边界子树在子偏移处重放缓存，不重画
        p.save();
        p.translate(child.x, child.y);
        p.blit(child.layer);
        p.restore();
      } else {
        child.paint(p);
      }
```

skip 条件三连（`!needsPaint && layer !== null && isRepaintBoundary()`）每项都不能少：脏了要走重录、没录过没有东西可放、非边界的子树要走正常递归。

## 4. blit 的诚实账本：命令拷贝省了什么、没省什么

`DisplayList.blit`（`painter.ts`）是逐条命令拷贝 + 平移，不是 GPU 图层引用。省与不省的账目：

| 项 | blit 后 | 说明 |
|---|---|---|
| `paintSelf` 重跑 | **省了** | 子树绘制逻辑（含文本排版回查、颜色计算）不执行——这就是 repaintedNodes 只数录入边界的原因 |
| 根图层命令数 | **不省** | 拷贝命令进祖先图层，根图层照样有 1001 条（压测实测，见 §7） |
| replay 提交量 | **不省** | 呈现段整段重放（本版无第三道防线），命令条数即提交量 |
| 内存 | 多了一份拷贝 | 每个边界图层 = 一份命令数组；blit 还在祖先里复制一份——纯教学取舍，真实框架在合成器层持引用 |

压测给了「省了 paintSelf」的直接证据：1000 盒树无边界设计，单叶变更后 `repaintedNodes = 1`（根重录，跑 1001 次 paintSelf）；每行边界设计 `repaintedNodes = 2`（该行边界 + 根，paintSelf 总量 ≈ 该行 20 + 根 1 + blit 拷贝）——**p95 帧成本 0.145ms → 0.074ms 的差额就是省下的 paintSelf 与拷贝成本的净值**。

「不省命令数」这一条在第六阶段 demo 的 HUD 上可见：`cmds 6` 恒定——根图层里动画面板的三条命令每帧被 blit 刷新内容，条数永远 6（《02》§6 的逐条账）。诚实声明也写进了 owner 注释（原文）：

```ts
    // 教学口径：blit 是命令拷贝不是 GPU 图层引用，省的是「重跑子树的 paint 逻辑」，
    // 不省命令数——真实框架在合成器层做引用（见《06》的诚实账本）。
```

## 5. 第三道防线：本版没做，纸上先算

呈现段的现状（`apps/06-pipeline.ts`）：

```ts
  if (rootLayer !== null) rootLayer.replay(backend);   // 整段重放，不挑命令
```

后端有 scissor 能力（`RaylibBackend.applyClip` 把命令自带的 clip 落成 `beginScissorMode/endScissorMode`，帧末 `endFrame()` 复位）——但 scissor 目前只用于**正确性**（第二阶段的裁剪），还没用于**性能**（限定提交范围）。第三道防线的纸面设计：

```text
脏矩形 = 本帧所有重录边界的 (layerRect + 父链偏移) 求并集 → clip 到根
replay 时：命令 rect ∩ 脏矩形 = 空的跳过；命中的走 scissor 提交
```

收益上限的算术（拿 §7 的压测数字）：单叶变更时脏矩形 ≈ 该行 20 盒的包围盒（~340×14 px）；整窗 640×900 = 576000 px²，脏区 ≈ 4760 px²——**提交量理论上限缩到 0.8%**。实际能吃到多少取决于命令的空间分布（并集越大折扣越狠）和每命令的求交成本（O(命令数) 的矩形求交本身要 0.1ms 量级）。1000 盒规模下净收益可能只有 2~5×，万盒以上才显著——这就是「第三道防线留作课题」的量化理由。

何时**不**值得做也明确：目标帧率下整段重放本来就用不完预算（压测冷帧才 2.85ms，60fps 预算 16.6ms）——先度量，再优化（《06》的第一课）。

## 6. 收益条件算术：边界何时划算、何时纯亏

设子树 S 挂上重绘边界，其后发生 n 次局部失效（每次只脏 S 内部）：

```text
收益 = n × (S 的 paintSelf 全量成本) − (边界本身的录放摊销 + blit 拷贝成本)
```

两种极端：

| 场景 | 判定 | 理由 |
|---|---|---|
| S 很大、偶尔变（工具栏、表格） | **大赚** | 每次失效只录 S 自己，邻居零成本；n 越大赚越多 |
| S 很小、邻居很大、S 偶尔变 | 赚（邻居角度） | 隔离作用：不设边界则 S 一变全树重录（压测 repainted 1 vs 2 的对照） |
| **S 自己每帧都变**（动画、闪烁光标） | **纯亏** | 每帧都要重录 S + blit 拷贝，边界没省任何东西，还多付图层内存 |
| S 每帧变 + 邻居巨大 | **必须设** | 亏的是 S 自己的摊销，救的是邻居的整树重录——06 demo 的动画面板就是这种 |

第六 demo（`anim-scene.ts`）的选择逻辑值得抄：动画面板**每帧都变**，加边界是「自己纯亏、邻居大赚」——静态面板（blitted, painted once）得以真的只画一次。判据一句话：**重绘边界隔离的是变更的辐射范围；给常变节点加边界，买的不是它自己的性能，是邻居的**。

反面案例也给一个：给每帧变的高频节点**包多层**边界——录放+blit 成本按层数翻倍，收益零。压测里 50 边界是「每行一个」的粗粒度，不是每盒一个；粒度选择本身是成本核算（边界越多，冷帧越贵、blit 树越深），没有免费粒度。

## 7. 对照实验：无边界 vs 每行边界（2026-11-14 tsx 实跑）

1000 盒（50 行 × 20 盒）无头压测，同树两种设计各跑全流程：

| 指标 | 无边界 | 每行边界（50 个） | 差额来源 |
|---|---|---|---|
| 冷帧（首帧全量） | 2.85 ms | 1.57 ms | 边界子树用独立 painter 录入，父层只做拷贝 |
| 空闲帧中位 | 0.014 ms | 0.014 ms | 欠活清单不区分设计：没欠条就零成本 |
| 空闲帧 p95 | 0.068 ms | 0.033 ms | p95 的偶发尖峰来自根试排（被缓存短路）的抖动 |
| **单叶变更 p95** | **0.145 ms** | **0.074 ms** | **2.0×**：重录半径从整树缩到一行 |
| 单叶变更中位 | 0.039 ms | 0.026 ms | 中位数太小，差异被 JS 定时精度吃掉 |
| 首次单叶变更 repaintedNodes | 1（根） | 2（该行边界 + 根） | 失效截断的直接证据 |
| 根图层命令数 | 1001 | 1001 | blit 是命令拷贝——诚实账本（§4） |
| totalPerformLayouts | 21302 | 21302 | **边界只影响绘制，不影响布局** |

最后一行是最容易被误解的一条：重绘边界（repaint boundary）与重排边界（relayout boundary）是**两套独立机制**——前者截断绘制失效，后者截断布局失效（`《03》`§2 的三条件）。给子树套 `RenderRepaintBoundary` 不会让它变成布局边界；「布局也要隔离」得靠约束收紧或 isFixedSize。

## 8. 与其他框架的对照

| 机制 | mini-gui | Flutter | 浏览器 |
|---|---|---|---|
| 边界组件 | `RenderRepaintBoundary`（手挂） | `RepaintBoundary` widget（同名同宗） | 无显式组件（合成层自动提升：will-change、3D transform） |
| 图层内容 | DisplayList 命令数组 | `Picture`（Skia 录制流） | 合成层的绘制记录 |
| 合成 | blit 命令拷贝（教学取舍） | Layer Tree → 合成线程真合成 | 合成器线程 |
| 脏矩形 | 未做（§5 纸面设计） | repaint gap/脏区由 engine 内部处理 | 脏 rect 融合到 tile |
| 「自动加边界」 | 无 | scroll view / text field 内置 | 常见动画元素自动提升 |

Flutter 的 `RepaintBoundary` 与本类同名同宗，连「给滚动视口内置边界」的建议都一致；差异在合成：Flutter 的合成在**另一个线程**（layer tree 提交后合成器并行），mini-gui 的 blit 在同一线程同步拷贝——教学版把这个成本摆在明面上（§4 账本），工程版把它移进合成器就是真实的下一步。

## 9. 本册小结

- 三道防线：失效截断（已做）→ 图层重录+blit 合成（已做）→ 呈现合批（未做，纸上算术：1000 盒规模收益上限 2~5×，万盒以上才值得）
- `RenderRepaintBoundary` 只有 22 行：协议角色 `isRepaintBoundary()=true` + 布局透传；所有机制在 owner 与基类
- 坐标合同唯一：「图层 = 局部坐标，偏移父补」；录走 `paintInto`（无自带平移）、放走 `translate + blit`；双重平移事故是合同被破坏的反例
- blit 诚实账本：省 paintSelf 重跑（repainted 1→2 的来源），不省命令数（根图层恒 1001 条）、不省 replay 提交量、多一份内存
- 收益算术：边界隔离变更辐射范围；给常变节点加边界买的是邻居的性能；多层边界是纯亏
- 重绘边界 ≠ 重排边界：压测 totalPerformLayouts 双设计相同，布局隔离是另一套机制
- 实测：单叶变更 p95 0.145 → 0.074ms（2.0×）、冷帧 2.85 → 1.57ms、空闲帧 0.014ms 双设计相同

## 附录 A：scissor 的现状走读（第二道防线的正确性部分）

第三道防线（性能）没做，但 scissor 的**正确性**用法早在第二阶段就绪——走读一遍现状，第三道要加的只是「谁来算脏矩形」：

```ts
// RaylibBackend.applyClip（逐字要点）
applyClip(clip: Rect | null): void {
  if (clip === null) { endScissorMode(); return; }
  beginScissorMode(clip.x, clip.y, clip.width, clip.height);
}
```

- 每条 `DrawCmd` 自带 `clip` 字段（第二阶段「命令自包含」的决策）；`replay` 时逐条 `applyClip(cmd.clip)`——裁剪随命令走，重放侧零上下文。
- 帧末 `backend.endFrame()` 调 `applyClip(null)` 复位——raylib 的 scissor 是全局态，不复位会漏到下一帧（第二阶段实测踩过）。
- 第三道防线要做的只是：replay 前**先算脏矩形并集**，命令 rect 与脏区无交的整段跳过，有交的走现有 applyClip 限幅。机制全在，缺的是「脏区记账」。

## 附录 B：脏矩形并集手算

两块脏区求并的算术（纸面可算）：

```text
R1 = (100, 200, 60×60)  动画面板内的方块
R2 = (140, 240, 80×50)  同面板内的圆

并集 = (min x, min y, max right − min x, max bottom − min y)
     = (100, 200, max(160,220)−100, max(260,290)−200)
     = (100, 200, 120×90)
面积 120×90 = 10800 px²；两块原面积 3600+4000=7600 px² —— 并集多付 3200 px²
```

这就是「合批 vs 精确」的权衡现场：并集让 replay 一次 scissor 提交两块脏区（GPU 状态切换省一次），代价是多刷了不相交的 3200 px²。工业做法按「面积增益 / 状态切换成本」决定合并或分块——教学版纸上算到这一步即可。

## 附录 C：根图层 1001 条命令的手工对账

压测里「根图层命令 1001 恒定」可以逐条数出来（1000 盒树）：

```text
1   根 ColoredBox 的背景 fillRect
1000  50 行 × 20 盒的 fillRect（经 blit 拷贝进根图层——命令拷贝不省条数）
----
1001 ✓
```

对账的意义：命令数是**结构量**（树形状决定），不是**行为量**（变更多少不影响）。所以「单叶变更后根命令仍是 1001」不是浪费的证据，而是「blit=拷贝」的证明。真正的行为量是 repaintedNodes（1 vs 2）与帧时长（p95 2×）。

## 附录 D：透传容器三胞胎

`RenderRepaintBoundary.performLayout` 与另两个类逐字级相似（透传约束、尺寸抄子、x/y 清零）：

| 类 | 所在册 | 额外职责 |
|---|---|---|
| `RenderGridCell` | 09 专题·Grid | 声明 (col,row,span) 供外层消费 |
| `RenderPositioned` | 09 专题·Absolute | 声明四边锚点供 Stack 消费 |
| `RenderRepaintBoundary` | 本册 | 声明「我是重绘边界」供 owner 消费 |

三个类是同一个模式：**数据节点**——自己不做几何计算，只携带声明，算法活在唯一的容器/owner 里。这是「位置归父」协议的副产品：声明式的数据放在节点上，行为收敛在一处。新增布局角色时先问「这是数据节点还是行为容器」，能省一半代码。


## 附录 E：边界粒度的成本核算

「每行一个边界」不是终点，粒度本身有账可算。设 n 个候选边界点（每盒/每行/每面板）：

```text
每盒 1000 个边界：冷帧多付 1000 次 DisplayList 分配 + 父层 1000 次 blit 拷贝
                 单叶变更只重录 1 盒（半径最小，≈0）——但 blit 树深 +1000
每行 50 个边界：冷帧多付 50 次分配/拷贝；单叶变更重录 1 行（20 盒）
每面板 1 个边界：冷帧 +1；单叶变更重录全面板（1000 盒）——等于没边界
```

收益曲线在两个端点都差：粒度太细，blit 树本身变成成本中心（每次合成要穿 1000 层）；粒度太粗，重录半径退化回整树。**最优粒度 ≈ 「变更的空间局部性」**：一起变的放一个边界里。本压测的变更模式是「单盒尺寸变」→ 行粒度恰好命中；若变更是「整列高亮」→ 列粒度才是对的。粒度选错的信号就是 repaintedNodes 偏大或冷帧异常——观测口永远先于直觉。

## 附录 F：blit 树深度对冷帧的影响（纸面推演）

附录 E 讨论了粒度对「单叶重录半径」的影响，这里补另一维——**合成深度**。n 层嵌套边界时，一次 flushPaint 的合成路径：

```text

深层（每盒边界再嵌套行边界）：根重录 = 50 次 blit，其中每次 blit 的目标图层里
                              又嵌着 20 次 blit——拷贝树化
命令拷贝总量 = 深度 × 命令数：嵌套设计把拷贝量乘了层数
```

1000 盒、每盒边界的极端设计：根图层 1001 条命令照旧（内容不变），但**录放过程**要穿过 1000 个 DisplayList 的分配与拷贝——冷帧从 2.85ms（无边界）涨到明显更高（边界分配本身不是免费的）。这就是附录 E「blit 树本身变成成本中心」的机制注脚：粒度换来的重录半径收益，要拿合成深度和图层内存来付。观测口依然是 repaintedNodes 与冷帧时长——先量再定粒度。
