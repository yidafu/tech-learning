# 第七阶段导览：缓存与异步消息

> [返回：后端开发学习大纲](../后端开发学习大纲.md)
> 本文是第七阶段的入口。缓存解决「读太慢」，消息解决「写太慢 / 耦合太紧」；两者的共同敌人都是**一致性**与**重复**。这一阶段的核心能力是：知道每种优化会引入哪种新的失败模式。

**建议时长**：2 周。本阶段的实验都要求压测数据，不接受「感觉快了」。

## 阶段目标

1. 为给定场景选出合适的 Redis 结构，并说清「为什么不用 Hash/不用 List」。
2. 解释 Cache-Aside 下「先删缓存再写库」与「先写库再删缓存」各自的不一致窗口，以及延迟双删的适用边界。
3. 区分穿透、击穿、雪崩三种失效模式，各给出至少两种工程解法。
4. 说清 Kafka 的「分区内有序、跨分区无序」，以及「至少一次」语义下消费侧必须做什么。
5. 配置一套可靠的消费链路：手动 ack、重试退避、死信队列、幂等消费，并能排查积压。
6. 解释为什么 `@Scheduled` 在多实例下会重复执行，以及 ShedLock 的互斥原理与失效场景。
7. 说出「消息队列不能当数据库用」的三条理由（顺序、查历史、事务）。

## 知识点地图

### 1. Redis 数据模型（02 册）

- **结构选型的判据是「访问模式」**：整体读写用 String/Hash；排行榜/去重用 ZSet/Set；队列用 Stream（而不是 List，Stream 有消费组与 ack）。
- **原子性靠 Lua**：多命令组合必须走 Lua 或 `MULTI`，否则并发下「判断 + 写入」之间有窗口。Lua 里不要写循环大 key。
- **过期与淘汰是两件事**：`maxmemory-policy` 决定内存满时淘汰谁，`expire` 决定单个 key 何时消失。`allkeys-lru` 下**没设过期的 key 也会被淘汰**，缓存与「半持久数据」不能混在一个实例。
- **大 key / 热 key**：大 key 导致单次操作阻塞与网络拥塞；热 key 导致单分片打满。治理手段：拆分、本地缓存、读写分离。

### 2. 缓存模式（03 册）

- **Cache-Aside 是默认选择**：读 miss 回源并回填；写时「更新库 + 删除缓存」。删除比更新好——更新在并发下会产生旧值覆盖新值。
- **不一致窗口**：删除缓存后、下一次读回填前，若有并发读，会回填旧值。延迟双删、订阅 binlog 失效、或用版本号校验都是补丁；**没有缓存能同时满足强一致与高性能**。
- **TTL 是最后的一致性保障**：所有缓存都必须有 TTL，即使业务上「永不变」。

### 3. 三种失效（04 册）

| 模式 | 现象 | 解法 |
|---|---|---|
| 穿透 | 查不存在的 key，每次都打到 DB | 布隆过滤器、空值缓存（短 TTL）、参数校验 |
| 击穿 | 热点 key 过期瞬间，大量并发回源 | 单飞（进程内合并）、逻辑过期 + 异步刷新、互斥重建 |
| 雪崩 | 大量 key 同时过期或 Redis 整体不可用 | TTL 加随机抖动、多级缓存、降级开关、集群高可用 |

- **多级缓存（Caffeine + Redis）**：本地缓存最快但一致性最差（多实例各自持有），需要「变更广播」或「短 TTL + 可接受陈旧」的业务前提。

### 4. 消息模型（05 册）

- **Kafka**：分区日志、消费者拉取、offset 自管理、分区内严格有序、天然支持重放与多消费组。适合「高吞吐 + 事件流 + 可重放」。
- **RabbitMQ**：队列 + exchange 路由、推送模式、单条 ack、路由灵活。适合「任务分发 + 复杂路由 + 低延迟」。
- **投递语义**：生产端 `acks=all` + 幂等生产者，消费端手动提交 offset，才能做到「不丢但可能重复」；**「恰好一次」只在流处理内部成立，跨系统仍是至少一次**。
- **顺序性**：要顺序就给同一个 key 用同一个分区/队列键；跨分区顺序只能靠业务层排序。

### 5. Spring 集成（06 册）

- `@KafkaListener` 默认批量/单条消费要显式配置；`ackMode` 与 `enable.auto.commit` 的组合决定了「什么时候算消费成功」。
- **重试与死信**：本地重试（快速、会阻塞分区）与转发到重试 topic（不阻塞、有延迟）要分清；死信队列必须有人看，否则等于黑洞。
- **积压排查顺序**：消费速率 vs 生产速率 → 单条处理耗时 → 是否有分区倾斜 → 消费者实例数是否小于分区数 → 是否在同步调用慢下游。

### 6. 定时任务（07 册）

- `@Scheduled` 在每个实例都会跑，多副本部署即重复执行。`ShedLock` 用共享存储（DB/Redis）加锁，缺点是「持锁进程崩溃要等锁过期」。
- **任务即消息**：把定时任务改成「定时投递消息 + 消费者处理」，天然获得重试、可观测、水平扩展。

## 阶段实践

1. 把骨架里的热点读接口压到 10k QPS（无缓存），记录 DB QPS 与 P99；
2. 依次加 Caffeine → Redis → 两级缓存，每加一层记录命中率、P99、DB QPS 变化；
3. 人为让热点 key 过期，观察是否出现击穿，再验证单飞是否生效；
4. 用 Kafka 做一条「下单 → 扣库存」的异步链路，制造一次重复投递并验证消费幂等。
