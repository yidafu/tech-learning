# 02. 选题与需求拆解：把「做什么」写成可测的数字

> [← 第十二阶段导览](01-导览.md) · 毕业项目的第一步不是写代码，是把选题定下来、把需求拆成用户故事、接口清单、数据模型和一串可测的数字——后面三册的所有决策都要拿这一册的产物当依据。

## 1. 三个候选选题：难点与练习价值

三个选题都能走完「单体 → 基线 → 拆分 → 生产化」的全流程，差别在于每一步的「难」长在哪里。选型前先看清各自的账：

| 选题 | 写热点（练锁与并发） | 读热点（练缓存） | 跨服务流程（练一致性） | 核心技术清单 |
|---|---|---|---|---|
| 订单系统 | 库存扣减（单行热点更新） | 商品详情/订单列表高频读 | 下单 → 扣库存 → 支付 → 发货，天然跨上下文 | 乐观锁/悲观锁、幂等键、状态机、Outbox/Saga |
| 短链服务 | 写少（生成短链）但 ID 生成是并发点 | 302 跳转读多写少，QPS 集中在一条路径 | 生成 → 落库 → 预热 → 统计上报 | ID 生成器、缓存预热与命中率、限流、压测调优 |
| 预约系统 | 时段冲突（同 slot 并发占座） | 时段表/可约容量高频读 | 预约 → 占座 → 支付/取消 → 超时释放 | 乐观锁版本号、延迟任务、对账、超时释放 |

**为什么这样设计这三个选题**：它们分别把全站三个「事故高发区」放大成主矛盾——订单把[第六阶段](../06-第六阶段/01-导览.md)的事务与一致性当主菜，短链把[第七阶段](../07-第七阶段/01-导览.md)的缓存与限流当主菜，预约把[第六阶段 04 册](../06-第六阶段/04-并发控制-乐观锁-悲观锁与唯一约束.md)的并发控制当主菜。做题的过程就是把对应阶段的知识「用在必须用的地方」。

**坑/取舍**：短链看起来最简单（功能就两个接口），所以它的坑全在数字上——缓存命中率、热 key、限流阈值，做不出数字的短链项目等于没做；订单的功能最多，最容易陷入「堆功能」而忘了量化；预约居中，但「超时释放」这个环节逼你面对延迟任务与对账，工程含量不低。

## 2. 选题决策的四个判据

导览里给过一句「共同要求」，这里把它展开成四个可判定的判据——选题不是凭兴趣，是按判据核对：

| 判据 | 定义 | 自问 | 不满足的后果 |
|---|---|---|---|
| 有写热点 | 存在并发写同一行/同一键的路径 | 「两个请求同时写，会出什么错？」答不出具体错误就不是写热点 | 锁与幂等没有用武之地，[第六阶段](../06-第六阶段/01-导览.md)白学 |
| 有读热点 | 存在 QPS 远高于写、可缓存的读路径 | 「哪个接口承担 80% 的读流量？」 | 缓存与压测没有对象，[第七阶段](../07-第七阶段/01-导览.md)白学 |
| 有跨服务流程 | 至少一条流程跨两个限界上下文 | 「拆分后哪条流程要跨服务走完？」 | 拆分后没有一致性问题，消息与 Saga 白学 |
| 有可量化非功能指标 | 能写出目标 QPS/P99/错误率/数据规模的数字 | 「做完了拿什么数字证明它合格？」 | 「跑通了」就是终点，毕业项目退化成 demo |

**为什么必须四条全满足**：毕业项目的验收（[06 册](06-复盘报告与验收清单.md)）是「有数字、有记录、能交接」，不是「功能跑通」。四个判据分别对应验收的四类证据来源：锁与幂等的并发测试、缓存的命中率报告、拆分后的对账脚本、压测的 P99 曲线。缺一条，验收就缺一类证据。

**坑/取舍**：最容易踩的是第四条——选题定了却写不出指标，说明对系统的量级没有概念，应该回头补调研（参考同类系统的公开数字：短链跳转服务的常见量级、电商订单峰值的常见量级），而不是硬编一个数。

## 3. 需求拆解的链条：四步走

选定题之后按一条固定的链条拆，每一步的产物是下一步的输入：

```mermaid
flowchart LR
  A[用户故事清单] --> B[接口清单<br>方法/路径/幂等/错误码]
  B --> C[数据模型<br>表与索引]
  C --> D[非功能指标<br>可测的数字]
  D -.->|反查覆盖| A
```

1. **用户故事清单**：每个故事一句话，格式「作为 X，我要 Y，以便 Z」。控制在 8~12 个，超过说明范围没裁（见第 7 节）。
2. **接口清单**：每个故事映射到 1~3 个接口，每个接口四件套齐全：方法、路径、幂等策略、错误码。故事覆盖不到接口 = 漏功能；接口没有故事支撑 = 多余功能。
3. **数据模型**：从接口的读写模式反推表结构——一个接口高频按什么查，那里就该有索引；一个接口要更新什么行，那里就是并发热点。
4. **非功能指标**：从业务量级推数字，见第 6 节。

**为什么顺序不能乱**：先写代码再补接口文档的项目，接口契约永远是「实现长什么样文档就长什么样」；反过来「故事 → 接口 → 模型 → 指标」的链条让每一层都有上一层的依据，[第四阶段 08 册](../04-第四阶段/08-REST契约-幂等-分页-版本化与OpenAPI.md)的契约先行的起点就在这里。

**坑/取舍**：链条走到第四步常会反过来推翻第一步——发现某个故事根本没有可测的指标支撑（比如「查看订单详情」对 P99 没有独立要求），这是正常的：指标是按「整个系统的服务等级」定义的，不是每个接口各配一套；但**写热点接口必须有独立的指标行**，因为它决定容量。

## 4. 接口清单：表格化示例（订单选题）

以订单选题为例，给出一份合格的接口清单长什么样。这是 M1 里程碑验收的核心产物：

| # | 方法 | 路径 | 幂等策略 | 典型错误码 | 支撑的用户故事 |
|---|---|---|---|---|---|
| 1 | POST | /api/orders | 幂等键（Idempotency-Key 头 + 去重表） | 400 参数错 / 409 库存不足或状态冲突 / 429 限流 | 下单 |
| 2 | GET | /api/orders/{id} | GET 天然幂等 | 404 不存在 / 403 越权 | 查订单详情 |
| 3 | GET | /api/orders?cursor=… | 幂等，游标分页 | 400 游标非法 | 订单列表 |
| 4 | POST | /api/orders/{id}/payment | 幂等键 + 状态机校验（已支付再付返回上次结果） | 409 状态不允许 / 402 支付失败 | 支付 |
| 5 | POST | /api/orders/{id}/cancel | 幂等 + 状态机校验 | 409 已发货不可取消 | 取消 |
| 6 | POST | /api/orders/{id}/shipment | 幂等 + 状态机校验（内部接口，网关不暴露） | 409 未支付不可发货 | 发货 |

每列的来历都有依据：幂等策略的写法来自[第六阶段 05 册](../06-第六阶段/05-幂等-幂等键-去重表与状态机.md)（重复请求的六种来源决定了哪些接口必须做幂等）；错误码体系来自[第四阶段 06 册](../04-第四阶段/06-错误模型-ProblemDetail与错误码.md)（409 表「请求合法但与当前状态冲突」）；「内部接口不暴露」的约束在拆分后会变成服务边界的第一道线。

**坑/取舍**：最常漏的是第 4 行的「已支付再付返回上次结果」——幂等不只是「拒绝重复」，而是「重复请求返回相同结果」。接口清单里不写清楚，实现时就会做成 409，然后支付回调重试把订单打成异常。

## 5. 数据模型：表与索引跟着读写模式走

从第 4 节的接口反推：接口 3 按「用户 + 时间」查列表，接口 1 要扣库存，接口 4/5/6 都要按状态机流转。由此得出核心两表（简化到能说清问题的最小集）：

```sql
-- 订单表：状态机流转 + 用户维度列表查询
create table orders (
    id            bigint primary key,
    user_id       bigint      not null,
    status        varchar(16) not null,          -- CREATED/PAID/CANCELED/SHIPPED/DONE
    amount_cents  bigint      not null,
    idempotency_key uuid,
    version       int         not null default 0,
    created_at    timestamptz not null,
    paid_at       timestamptz
);
-- 接口 3：按用户倒序查列表（游标分页的排序键）
create index idx_orders_user_created on orders (user_id, created_at desc);
-- 接口 1：幂等去重（第六阶段 05 册的去重表思路，直接落在唯一索引上）
create unique index uk_orders_idem_key on orders (user_id, idempotency_key);
-- 接口 6：定时任务扫超时未支付单
create index idx_orders_status_created on orders (status, created_at) where status = 'CREATED';

-- 库存表：写热点本体，扣减的所有故事都在这一行
create table inventory (
    sku_id     bigint primary key,
    available  int  not null check (available >= 0),
    version    int  not null default 0
);
```

三处刻意的设计：`check (available >= 0)` 把「超卖」挡在数据库层而不是应用层——应用层判断在并发下永远有窗口期，唯一可靠的兜底是约束；部分索引 `where status = 'CREATED'` 只服务超时扫描这一条慢查询，把索引体积压到最小；`version` 字段为乐观锁预留（预约选题里它是主角，订单里它是库存扣减的备选方案，见[第六阶段 04 册](../06-第六阶段/04-并发控制-乐观锁-悲观锁与唯一约束.md)）。

**坑/取舍**：数据模型阶段最常见的错误是「按页面长什么样建表」而不是「按查询怎么跑建表」。页面要展示的字段未必需要独立列，接口按什么过滤排序才是索引设计的唯一输入——[第五阶段 04 册](../05-第五阶段/04-SQL与索引-执行计划与慢查询.md)的执行计划思维从这一步就开始用。

## 6. 非功能指标：一段从需求到数字的推导

指标不能拍脑袋，要能展示推导过程。以订单选题为例，演示一遍完整推导：

```text
业务设定（假设值，写在报告里，注明是假设）：
- 用户 10 万，日均下单 2 万单，支付成功率 85%
- 流量集中在 20:00~22:00，占全天 40%

推导链：
1. 平均下单 QPS = 20000 单 / 86400s ≈ 0.23 QPS —— 无意义，要算峰值
2. 峰值集中系数：40% 流量压在 2h → 峰值时段平均 ≈ 20000×0.4/7200 ≈ 1.1 QPS
3. 突发系数 1.5~2（大促/整点活动）：下单写峰值 ≈ 2.2 QPS
4. 读写比：详情页+列表页浏览与下单比约 30:1 → 读峰值 ≈ 66 QPS
5. 每次下单跨 3 次库存读 + 1 次库存写 → 库存服务读 ≈ 200 QPS（拆分后）

结论指标（写进验收）：
- 下单写路径：目标 50 QPS（预留 20 倍余量，验证的是架构不是容量）
- 商品/订单读路径：目标 200 QPS，缓存命中率 ≥ 90%，DB QPS ≤ 20
- 全部接口：P99 ≤ 200ms（单体基线 ≤ 150ms），P999 ≤ 800ms
- 错误率：4xx 之外的成功率 ≥ 99.9%，5xx ≤ 0.1%
- 数据规模：订单表按 2 年 1500 万行设计，idx_orders_user_created 的查询在千万级仍走索引（EXPLAIN 验证）
```

四个数字的口径来自[第十阶段 08 册](../10-第十阶段/08-压测与调优方法论.md)（压测场景怎么设计）与[第一阶段 02 册](../01-第一阶段/02-一次请求的十五站主时间线与账本.md)（P50/P99 按账本口径统计）。两条设计意图要写明：目标是「学习项目」的指标，写路径 50 QPS 是给架构留验证空间，不是宣称生产容量；数据规模指标强制你验证「索引在大表上还活着」，这是[第五阶段 04 册](../05-第五阶段/04-SQL与索引-执行计划与慢查询.md)的收官动作。

**坑/取舍**：最常见的失败是指标只写 QPS 不写错误率与数据规模——QPS 达标但 5xx 2% 的系统没有验收资格；而数据规模不设定，压测就只会在几百行的小表上跑，索引失效根本不会暴露。

## 7. 范围裁剪纪律：明确不做什么

毕业项目 3~4 周，范围裁剪不是偷懒，是让每个环节都有时间做到「有数字」。裁剪要写成明文清单，每条带理由：

| 明确不做 | 理由 |
|---|---|
| 真实支付渠道对接 | 支付在流程里用一个「支付上下文」模拟（本地决策成功/失败即可），拆分后它就是一个独立的假下游——故障演练（[05 册](05-生产化收尾与故障演练.md)）正好拿它注入超时 |
| 注册/登录/OAuth2 全套 | 认证用预置 JWT 直发（[第九阶段 03 册](../09-第九阶段/03-会话-JWT与OAuth2-OIDC.md)已练过），本项目只练授权与越权回归 |
| 管理后台 UI | 管理操作做成内部接口 + curl 集合，界面不是验收对象 |
| 多租户 | 单租户已够支撑全部知识点，多租户隔离是[第九阶段 05 册](../09-第九阶段/05-授权落地与多租户数据隔离.md)的既有练习 |
| 国际化、复杂促销规则 | 与四个判据无关，纯功能堆料 |

裁剪的总原则：**只裁「与四个判据无关的」，不裁「让流程跨上下文的」**。比如「取消订单」看起来可有可无，但它引入了状态机的逆向路径和「发货后不可取消」的冲突分支，是幂等与状态机的重要练习，不能裁。

**坑/取舍**：范围膨胀的典型信号是「实现清单比接口清单长」——出现了接口清单里没有的接口（第 3 节说过：接口没有故事支撑就是多余功能）。每多一个功能，压测、测试、文档的工作量按环节叠加，最后牺牲的一定是数字质量。

## 8. 自测

1. 三个选题里，短链的写热点在哪里？（提示：不在「写短链」这个业务动作上）
2. 四个判据分别对应验收的哪四类证据？你的选题四条怎么逐条满足？
3. 接口清单里「幂等策略」一列，为什么下单写「幂等键 + 去重表」而取消写「幂等 + 状态机校验」？两者防的是同一种重复吗？
4. `check (available >= 0)` 为什么必须放在数据库层？应用层的 `if (available > 0)` 漏了什么？
5. 你的选题从业务设定到目标 QPS 的推导链是什么？哪一步用了突发系数、哪一步用了读写比？
6. 范围裁剪里「支付用模拟上下文」的设计，在拆分和故障演练两步分别派上什么用场？
