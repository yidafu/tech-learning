# 05. 生产化收尾与故障演练：让系统「降级但不崩」

> [← 第十二阶段导览](01-导览.md) · 功能与拆分完成之后，最后一段路是「敢上线」：补齐可观测、安全、弹性、交付四张清单，然后用三类故障注入验证——系统的价值不在于不出故障，在于故障发生时按预案降级。

## 1. 生产化收尾清单

四个类目逐条核对，每条都链接到前序阶段的对应分册——这一册不重新讲原理，只做「清点与验收」：

**为什么清单要「链接式清点」而不是重新展开**：毕业项目的时间预算有限，原理在各阶段都练过了，这里只做两件事——核对「做了没有」、验收「按分册的标准做对了没有」。清单本身会进入[06 册](06-复盘报告与验收清单.md)的交接手册。

**坑/取舍**：最容易敷衍的是「密钥外置」——本地开发用 `application-local.yml` 放明文然后写进 `.gitignore`，看似没事，镜像构建时被 COPY 进层里。验收动作必须是对**构建产物**（镜像层、CI 缓存）做扫描，不是对源码。

## 2. 三类故障的预期行为与不合格表现

演练设计的核心是**先写预期，再注故障**。三类故障覆盖了拆分后最常见的三种崩法：

| 故障 | 注入方式 | 预期行为（合格） | 不合格表现 |
|---|---|---|---|
| 下游超时（库存服务 200ms 预算打满） | 注入工具给库存接口加 3s 延迟 | 下单快速失败（200ms 预算耗尽即 503），P99 有界，线程池不堆积，熔断打开后直接走降级；库存恢复后熔断半开自愈 | 下单 P99 涨到 3s+；Tomcat 线程被拖住排队；连接池被占满引发全站故障（雪崩） |
| 数据库抖动（PG 延迟 500ms / 短暂拒绝连接） | 注入 DB 代理延迟或 kill 连接 | 慢查询触发限流降级：读走缓存兜底、写路径按开关降级为排队或拒绝；告警触发；恢复后连接池自愈、无泄漏 | 每个请求都超时报 500（500 风暴）；连接池泄漏（恢复后活跃连接不回落）；无限重试放大 DB 压力 |
| 消息积压（Kafka 分区积压 10 万条） | 停掉消费者再放流量 | 消费恢复后按幂等语义追平积压，不重复处理业务（幂等键去重生效）；积压深度指标可见，扩容消费者有预案 | 重复消费导致重复扣库存/重复发货；消费者再均衡风暴；积压被丢弃（跳过消息保进度） |

三类故障的判定逻辑各有侧重：下游超时验的是**弹性三件套**（超时/熔断/降级）的真实接线——配置存在不代表生效；DB 抖动验的是**降级路径**与**资源自愈**；消息积压验的是**幂等消费**与**追平能力**（[第七阶段 06 册](../07-第七阶段/06-Spring消息集成-幂等消费-重试死信与积压.md)）。

**为什么这三类**：它们分别对应[第十一阶段 04 册](../11-第十一阶段/04-服务间通信-同步与异步.md)预言的三种崩法（同步链雪崩、共享资源饱和、异步链滞留）。演练合格的标准只有一条：**降级但不崩，恢复后自愈或按预案恢复**。

## 3. 故障注入的配置

注入用 Resilience4j 的容错配置 + 注入工具的故障规则（如 Chaos Mesh/Toxiproxy 对网络层注入，或自写延迟过滤器对应用层注入）。先看应用侧「本来就该有」的配置——演练首先验证这些配置真实生效：

```yaml
# 库存调用的弹性配置：超时预算 200ms（04 册的契约承诺），熔断与降级兜底
resilience4j:
  circuitbreaker:
    instances:
      inventory:
        slidingWindowSize: 20
        failureRateThreshold: 50        # 失败率过半即熔断
        waitDurationInOpenState: 20s    # 熔断 20s 后半开试探
        automaticTransitionFromOpenToHalfOpenEnabled: true
  timelimiter:
    instances:
      inventory:
        timeoutDuration: 200ms          # 与 Gateway 契约一致：超时即失败，不拖上游
  retry:
    instances:
      inventory:
        maxAttempts: 2                  # 仅幂等 reserve 允许重试一次（幂等键保证安全）
        waitDuration: 50ms
```

```kotlin
// 应用侧的降级开关：演练时拨动它验证降级路径真实可用，而不是只存在于文档里
@Component
class InventoryDegradation(
    @Value("\${inventory.degradation.enabled:false}") private val enabled: Boolean,
    private val outbox: OutboxWriter,
) {
    // 降级模式：库存预扣改为「先记账后补扣」——下单照常接受，扣减动作进 Outbox 延迟执行。
    // 代价是超卖风险窗口（业务侧需接受），所以开关只允许在演练/大促预案中开启并记录审计。
    fun reserveOrDefer(cmd: PlaceOrderCommand, reserveId: UUID): ReserveTicket =
        if (enabled) {
            outbox.append(DeferredInventoryReserve(cmd.skuId, cmd.quantity, reserveId))
            ReserveTicket.deferred(reserveId)
        } else {
            throw InventoryUnavailableException("inventory down and degradation off")
        }
}
```

**坑/取舍**：注入配置最大的陷阱是「演练专用配置泄漏到生产」——注入规则必须与预发环境绑定，且启动时打印注入状态；另一陷阱是只注入「干净故障」（纯延迟），真实故障是混合的（延迟 + 偶发断连 + 半死不活），演练后期至少跑一轮混合故障。

## 4. 演练的执行方式

演练按四段式执行，每一段都要留下记录（进入[06 册](06-复盘报告与验收清单.md)的复盘报告）：

```mermaid
flowchart LR
  A[① 预案书写<br>预期行为+观察指标+回退动作] --> B[② 预发注入<br>注入工具按预案加故障]
  B --> C[③ 观察取证<br>指标面板+日志+trace 三路取证]
  C --> D[④ 复盘记录<br>预期 vs 实际逐条核对]
```

1. **预案书写**：把第 2 节表格里该故障的「预期行为」展开成具体数字——「下单 P99 在 250ms 内、错误率 < 5%、无 500 风暴、熔断 20s 内打开」。没有数字的预期等于没有预期。
2. **预发注入**：环境必须是预发（与生产同构但隔离），注入工具选型：网络层用 Toxiproxy（加延迟/断连最贴近真实），应用层用注入开关。**生产环境的首次演练（如果有）只做「读路径 + 最小剂量」**，写路径故障的首次验证永远在预发。
3. **观察取证**：观察指标面板（错误率、P99、线程池、连接池、熔断状态、积压深度）+ 日志（降级是否触发、有无异常堆栈）+ trace（故障期间的链路在哪一跳变红）。三路证据互相印证，单看指标会误判。
4. **复盘记录**：每条演练项按「预期 vs 实际」逐条核对，实际不符预期的写成缺陷进入下一轮修复——**演练的产出不是「通过」两个字，是缺陷清单**。这也是[第十阶段 04 册](../10-第十阶段/04-并发-幂等与故障注入测试.md)的故障注入测试在系统级的延伸。

**坑/取舍**：最常见的执行缺陷是「注入后只看有没有报错」——报错正确（快速失败）与报错错误（线程堆积后超时）在「有 5xx」这个粗粒度上看起来一样，必须看 P99 形态与线程池曲线才能区分。

## 5. 容量与成本的粗算

用 03 册的基线数字走一遍完整演算（数字是示例，替换成你的实测值）：

```text
输入（来自 03 册基线与 02 册指标定义）：
- 写路径峰值目标：50 QPS（02 册指标），单实例写极限 240 QPS（03 册基线）
- 读路径峰值目标：200 QPS，调优后单实例读极限约 600 QPS（缓存命中后）
- 冗余系数 1.5（扛一个实例挂掉 + 流量迁移，见 11-09 册）

演算：
1. 写路径实例数 = 50 × 1.5 / 240 ≈ 0.3 → 取 2 个（最小可用副本，无单点）
2. 读路径实例数 = 200 × 1.5 / 600 = 0.5 → 取 2 个（同上）
3. 单体（含网关职责）2 实例 + 库存服务 2 实例 = 4 个 2C4G
4. 峰值 CPU 校验：50/240 ≈ 21% 写、200/600 ≈ 33% 读，均低于 50% 预警线，合理

月成本粗算（按常见云 2C4G ≈ 200 元/月、PG 8C32G ≈ 1200 元/月、
Redis 2G ≈ 150 元/月、Kafka 3 节点最小规格 ≈ 900 元/月）：
- 应用 4 × 200 = 800 元
- PG（拆分后仍共享实例，schema 隔离）= 1200 元
- Redis + Kafka = 1050 元
- 合计 ≈ 3050 元/月（学习项目口径；生产口径还要加监控、备份、多可用区，约 ×2）
```

演算的价值不在省钱，在**把「容量」从抽象概念变成三行乘法**：单实例极限（压测得出）× 冗余系数（架构决策）× 目标流量（02 册指标）。三个数里任何一个是拍的，结论就是错的——这就是为什么容量公式（[第十一阶段 09 册](../11-第十一阶段/09-大型应用工程化-联调-灰度与容量.md)）的参数来源必须是压测。

**坑/取舍**：成本粗算最常被忽视的是中间件的最小规格占大头——学习项目 4 个应用实例才 800 元，PG + Kafka 占了 2250 元。这条认知在架构评审里很值钱：「加一个服务」的成本经常不在它的实例上，而在它顺手要求的那套共享中间件升级上。

## 6. 自测

1. 生产化清单为什么做成「链接式清点」？四类目里哪一条最难自动验收、为什么？
2. 下游超时注入下，线程堆积的全过程是什么？熔断在哪一环把它拦住？
3. 消息积压演练里，「幂等去重生效」具体怎么验证？（提示：消费侧要留什么证据？）
4. 演练预案为什么必须写数字？「下单 P99 250ms 内」这个数从哪来？
5. 容量演算的三个输入数分别来自哪一步的工作？任何一个拍脑袋会怎样？
6. 「演练的产出是缺陷清单」——如果你三类故障全一次通过，应该怀疑什么？
