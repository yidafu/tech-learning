# 03. 模块化单体与压测基线：先有对照组，再谈拆分

> [← 第十二阶段导览](01-导览.md) · 拆分是拿「基线」当对照组做实验：没有单体的 QPS/P99/资源曲线，拆完的每一笔成本都无法证明。这一册把单体做完整——分模块、契约先行、测试齐全——然后压出一组以后所有决策都要引用的数字。

## 1. 为什么必须先做完整的单体

一句话：**没有基线的拆分，是在没有对照组的情况下做实验**。拆分后 P99 从 150ms 涨到 210ms，你无法判断这是「拆分的固有税」还是「拆分方式错了」；缓存命中率从 92% 掉到 70%，你无法判断是序列化开销还是架构把热路径拉长了。[第十一阶段 02 册](../11-第十一阶段/02-该不该拆-单体-模块化单体与微服务判据.md)的结论是「拆分的动机来自团队规模与变更频率，不是 QPS」，而证明「不是 QPS」这件事本身，就需要一个 QPS 达标的单体。

更深的理由是迁回的可能性：模块化单体把限界上下文的边界用编译器和测试锁死，之后拆或不拆变成一个纯收益判断——拆，边界已验证；不拆，单体已经能扛。直接上微服务的项目恰恰丢掉了这个退路：边界错了就要跨网络改。

**坑/取舍**：最大的心理障碍是「先做单体是不是白费功」。不是——单体阶段的接口契约、数据模型、测试、压测脚本全部直接进入后续阶段，报废的只有「模块间调用从进程内换成 HTTP」这一件事，而这本来就是要换成 HTTP 的。

## 2. 模块划分：限界上下文变成 Gradle 模块

以订单选题为例，按[第十一阶段 03 册](../11-第十一阶段/03-服务边界-DDD限界上下文与数据所有权.md)的限界上下文切模块：每个上下文一个 Gradle 模块，各自拥有自己的表，**模块之间只通过接口与事件通信，不共享数据库表、不共享领域对象**。

```kotlin
// build.gradle.kts —— 模块定义与依赖方向（settings.gradle.kts 里 include 这四个模块）
// 依赖方向单向：bootstrap 收拢装配，context 之间不互相 import
plugins {
    kotlin("jvm") version "2.2.0"
}

// order-context 依赖 shared-kernel 与 inventory-context 的「接口」模块，不依赖其实现
dependencies {
    implementation(project(":shared-kernel"))        // 值对象、错误模型、Outbox 基础设施
    implementation(project(":inventory-context-api")) // 只有接口：InventoryGateway
    implementation(project(":payment-context-api"))   // 只有接口：PaymentGateway
}

// 关键约束：order-context 的 build.gradle.kts 里没有 inventory-context（实现模块）——
// 想绕过接口直接拿实现，编译不过。边界用构建脚本锁住，不靠自觉。
```

模块间解耦的另一半是事件：下单成功要通知库存、通知支付，order-context 不去调用它们的实现，而是发出领域事件——

```kotlin
// order-context 内：发布事件（经 Outbox 保证与业务写入同事务，见第六阶段 06 册）
class OrderPlaced(
    val orderId: Long,
    val userId: Long,
    val skuId: Long,
    val amountCents: Long,
) : DomainEvent

@Service
class PlaceOrderService(
    private val orderRepo: OrderRepository,
    private val inventory: InventoryGateway,   // 进程内实现；拆分后换 HTTP 实现的是同一个接口
    private val outbox: OutboxWriter,
    private val tx: TransactionTemplate,
) {
    fun place(cmd: PlaceOrderCommand, idempotencyKey: UUID): OrderView = tx.execute {
        val order = orderRepo.insert(cmd, idempotencyKey)          // 唯一索引挡重复提交
        inventory.reserve(cmd.skuId, cmd.quantity)                  // 同步调用：库存不足要立刻回 409
        outbox.append(OrderPlaced(order.id, order.userId, order.skuId, order.amountCents))
        order.toView()
    }!!

    // 支付成功不直接改订单，监听事件——写路径与通知路径解耦
    @EventListener
    fun onPaymentSucceeded(event: PaymentSucceeded) {
        orderRepo.transition(event.orderId, OrderStatus.PAID)
    }
}
```

为什么「同步调用接口 + 异步事件」这样分：库存扣减的结果直接决定下单能不能成功（要同步返回 409），必须同步；「支付成功」只是通知性质的后续，异步事件让支付上下文挂了也不影响下单。这条「哪些必须同步、哪些改事件」的判断在拆分后会原样迁移成「哪些走 HTTP、哪些走消息」（[04 册](04-拆出两个服务-边界-通信与数据迁移.md)第 3 节）。

**坑/取舍**：模块划分最常见的腐化是「图省事直接 import 邻居的实现类」—— Gradle 依赖锁不住语义，还得靠 ArchUnit/自测规则 + 代码评审守。另一个坑是事件满天飞：一次下单发五个事件、五个监听器互相触发，链路变成事件网。原则：**事件只承载「已经发生的事实」，下游各自决策要不要反应；命令式的「请你去干活」走同步接口。**

## 3. 契约先行：接口定义先于实现，用测试锁住

每个 context-api 模块里的接口不是「顺手写的」，而是从[02 册](02-选题与需求拆解.md)的接口清单翻译来的，先写接口与契约测试、后写实现：

```kotlin
// inventory-context-api：拆分前后不变的契约。拆分时换实现不换契约，
// 契约测试（第十阶段 03 册）锁住两边。
interface InventoryGateway {
    /**
     * 预扣库存。语义承诺：
     * - 成功返回预扣记录号，失败抛 InsufficientStockException（映射 409）
     * - 幂等：同一 reserveId 重复调用返回首次结果（幂等键协议）
     * - 超时预算：200ms（超过即视为失败，上游快速失败）
     */
    fun reserve(skuId: Long, quantity: Int, reserveId: UUID): ReserveTicket
}

// 契约测试：进程内实现与未来的 HTTP 实现跑同一套测试
abstract class InventoryGatewayContractTest {
    abstract fun gateway(): InventoryGateway

    @Test fun `预扣成功返回票据`() { /* … */ }

    @Test fun `同一 reserveId 重放返回首次结果`() {
        val id = UUID.randomUUID()
        val first = gateway().reserve(SKU_A, 2, id)
        val replay = gateway().reserve(SKU_A, 2, id)
        assertEquals(first, replay)            // 幂等语义是契约的一部分
    }

    @Test fun `并发预扣不超卖`() { /* 多协程并发扣到 0，断言无一次成功越过库存线 */ }
}
```

**为什么契约先行**：拆分时最贵的错误是「以为接口语义很简单，拆完才发现隐含行为没传过去」。比如 `reserve` 的幂等语义——进程内调用天然重入，HTTP 调用重试就会重复扣；这条语义若不写进契约测试，拆完才发现就是线上事故。[第十一阶段 08 册](../11-第十一阶段/08-多服务可观测性与契约治理.md)的契约治理，起点就是这份先行的契约。

**坑/取舍**：契约测试的最大误区是只测「成功路径」——幂等重放、超时、并发这些「失败语义」恰恰是跨进程后最先坏掉的，必须显式写进抽象类的测试集。

## 4. 关键路径测试清单

测试清单按「正路径 + 反路径 + 并发」三栏组织，每条都要能进 CI（[第十阶段 02 册](../10-第十阶段/02-测试金字塔与切片测试.md)的分层、[10-03 册](../10-第十阶段/03-Testcontainers与契约测试.md)的真数据库）：

| 路径 | 正路径用例 | 反路径用例 | 并发用例 |
|---|---|---|---|
| 下单 | 库存足 → 建单成功 → 事件落 Outbox | 库存不足回 409；幂等键重放返回原单；参数非法回 400 | 100 并发抢 10 件库存：恰好 10 单成功 |
| 支付 | 未支付单支付 → 状态变 PAID | 已支付重放返回首次结果；CREATED 之外状态回 409 | 同一订单两笔并发支付：只有一笔生效 |
| 取消 | CREATED 单取消 → 状态 CANCELED → 库存回补 | 已发货不可取消回 409；重复取消幂等 | 取消与支付并发：状态机保证只有一个胜者 |

清单的取舍逻辑：正路径证明「功能对」，反路径证明「错误语义对」（错误码与幂等行为是契约），并发用例证明「锁与约束生效」。三条全齐才允许进压测——**在语义不正确的东西上压出的数字没有意义**。

**坑/取舍**：并发用例最容易写成「偶发通过」的伪测试——100 个协程抢库存，`check (available >= 0)` 兜底后应用层的 bug 被掩盖，测试照样绿。并发测试要断言「成功次数 == 可用库存」这个精确等式，而不是「没有异常」。

## 5. 压测基线的产出

基线压测按[第十阶段 08 册](../10-第十阶段/08-压测与调优方法论.md)的方法执行：脚本、场景、逐步加压找拐点。产出不是一张截图，是一张基线表 + 三个结论：

| 指标 | 数值（示例，你的数字以实测为准） | 备注 |
|---|---|---|
| 下单写路径极限 QPS | 240（拐点） | 再加压错误率爬升 |
| 下单 P50 / P99 / P999 | 18ms / 132ms / 310ms | P99 尾部主要来自数据库锁等待 |
| 读路径 QPS（未加缓存） | 95 | 全部打到 PG，连接池 20 满载 |
| 错误率（拐点前） | < 0.1% | 全部 4xx 业务错 |
| CPU / 内存 | 55% / 70% | 单实例 2C4G |
| HikariCP 活跃连接 | 18 / 20（读路径） | 下一调优动作的依据 |

三个必须写进基线报告的结论：

1. **账本里最慢的三站**：按[第一阶段 02 册](../01-第一阶段/02-一次请求的十五站主时间线与账本.md)的账本口径，本例是「⑨ 连接池取连接 + SQL 执行」（P99 贡献 68ms）、「⑦ 事务开启到提交的持锁时长」（41ms）、「⑩ 库存扣减的行锁等待」（23ms）。这三站就是拆分与调优的靶子。
2. **容量结论**：2C4G 单实例写 240 QPS，[05 册](05-生产化收尾与故障演练.md)的容量公式直接引用这个数。
3. **拐点行为**：拐点后错误类型是连接池等待超时还是数据库锁超时——这决定后面的调优动作是扩池还是改锁。

**坑/取舍**：基线最常见的缺陷是「只有一组数，没有拐点曲线」——不知道系统在什么压力下开始变质，就没有「极限」的概念，容量规划变成拍脑袋。第二个常见缺陷是压测后没记录环境（实例规格、PG 版本、数据量），半年后数字没法复现。

## 6. 拆分前必须回答的五个问题

基线到手后、动手拆之前，逐条回答——每问都对应[第十一阶段](../11-第十一阶段/01-导览.md)的一类坑：

| # | 问题 | 对应的坑 | 不合格答案的特征 |
|---|---|---|---|
| 1 | 拆分动机是什么？「团队规模 × 变更频率」还是「QPS 不够」？ | 11-02：单服务的天花板来自团队与变更 | 「微服务更先进」「面试要考」 |
| 2 | 第一个拆谁？边界判据（语言独立、数据耦合最小、团队收益）逐条打分了吗？ | 11-03：拆错的边界用分布式事务和共享库互相还债 | 按代码目录大小选 |
| 3 | 跨服务的调用清单里，同步与异步各是哪些？超时预算与重试策略定了吗？ | 11-04：同步调用链雪崩 | 「都同步，简单」 |
| 4 | 数据所有权怎么切？迁移、对账、回滚点各在哪一步？ | 11-03/11-09：一服务一库被共享表架空 | 「先共享库，以后再拆」 |
| 5 | 拆分后的可观测性怎么接？trace 能跨服务串起来吗？ | 11-08：链路断裂排障靠猜 | 「先把功能跑通，观测以后补」 |

五个问题全有具体答案才动手。这份 Q&A 直接写进 ADR（[06 册](06-复盘报告与验收清单.md)第 2 节的格式），成为「当时为什么这样拆」的原始记录。

**坑/取舍**：五个问题里最容易被敷衍的是第 4 问——数据切割做一半发现两张表互相外键引用，于是「暂时共享数据库」。这个妥协一旦做出，拆分就退化成「两个进程一个库」：边界全靠自觉，事务还能跨进程，等于付出了分布式的成本却没拿到分布式的任何收益。

## 7. 自测

1. 「没有基线的拆分是没有对照组的实验」——对照组具体对照什么？拆分后你打算做哪几组对比？
2. 模块间「同步走接口、异步走事件」的判断标准是什么？下单里的库存扣减为什么同步、支付成功为什么异步？
3. 契约测试为什么要写成抽象基类让两个实现跑同一套？哪类「失败语义」最容易漏测？
4. 并发测试断言「成功次数 == 可用库存」防的是什么伪绿？`check` 约束和应用层判断的关系是什么？
5. 基线报告里的「最慢三站」怎么从账本口径得出来？它和调优动作是什么关系？
6. 五个问题里第 4 问不合格（共享数据库）时，为什么说「付出了分布式的成本却没拿到收益」？
