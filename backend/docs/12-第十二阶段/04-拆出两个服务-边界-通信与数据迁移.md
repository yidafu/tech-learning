# 04. 拆出两个服务：边界、通信与数据迁移

> [← 第十二阶段导览](01-导览.md) · 基线在手，这一册做本阶段最重的一步：选边界、拆数据、双写过渡、切读切写，最后量化拆分的税——每一笔延迟与复杂度成本都要有前后对照表。

## 1. 按边界选第一个要拆的服务

以订单选题为例，候选是库存上下文与支付上下文（订单主表留在原地，作为流程的编排方）。三个判定标准逐条打分：

| 判定标准 | 拆库存服务 | 拆支付服务 | 理由 |
|---|---|---|---|
| 数据耦合最小 | 高：库存表无外键指向订单，只有 skuId 引用 | 高：支付记录只引用 orderId | 两者的表都只被「 ID 引用」，没有跨表 join |
| 团队/技术收益最大 | 高：库存是写热点（03 册基线里最慢三站之一），独立伸缩与调优收益直接 | 中：模拟的假下游，独立价值主要在故障演练 | 库存的锁竞争隔离出去，单体立刻减负 |
| 语言/技术独立潜力 | 高：库存扣减是纯 CPU+DB 的窄接口，最像「将来换语言重写」的候选 | 低：支付未来通常接外部渠道，形态是适配器 | 窄接口是拆分的黄金起点 |

结论：**先拆库存服务**。它满足[第十一阶段 03 册](../11-第十一阶段/03-服务边界-DDD限界上下文与数据所有权.md)的「一服务一库」，接口窄（reserve/confirm/release 三个方法），且拆走后单体的基线痛点（行锁等待）直接改善——拆分收益可以被压测证明。

**为什么「窄接口」是第一优先**：拆分的本质是「原来一次函数调用，现在一次网络调用」。接口越窄，要迁移的语义越少（幂等、超时、重试全部好定义）；接口越宽（比如返回整个库存聚合对象），跨进程后每次调用都在付序列化税，还容易被当成「远程对象」误用。[第十一阶段 04 册](../11-第十一阶段/04-服务间通信-同步与异步.md)的「消息 vs RPC 选择表」落到这里：窄的命令式调用走同步 RPC，其余走事件。

**坑/取舍**：先拆「最难的上下文」还是「最简单的」？答案是拆「边界最干净、收益最可证」的——太难的全是分布式事务，做不完；太简单的（如通知服务）拆了没有任何可量化的收益，纯交学费。

## 2. 拆分的完整步骤清单

六步走，每一步都保持「线上可存活」，顺序不可调换：

```mermaid
flowchart LR
  A[① 接口收口<br>单体内部先走 Gateway] --> B[② 数据所有权切割<br>库存表迁出，停互写]
  B --> C[③ 双写过渡<br>新旧库存并存，写双读旧]
  C --> D[④ 切读<br>读走新服务，对账验证]
  D --> E[⑤ 切写<br>写走新服务，旧库只收]
  E --> F[⑥ 下线旧模块<br>删代码删表]
```

1. **接口收口**：单体内部，order-context 对库存的调用全部改走 `InventoryGateway`（03 册已就位），消灭对 inventory-context 实现类的任何直接引用。此步不改变行为，是后面一切的前提。
2. **数据所有权切割**：库存表迁到新服务名下，单体对它的所有写操作停止（改走 Gateway），只剩读过渡期。外键、跨表 join 逐一消灭。
3. **双写过渡**：新库存服务上线但还没当家——Gateway 的实现切成「双写」：先写旧库（权威），再写新服务，失败告警但不阻断。
4. **切读**：读流量切到新服务，同时跑新旧对账（第 4 节），对账不一致率归零。
5. **切写**：写路径切到新服务，旧库变成只读影子，再观察一个业务周期。
6. **下线旧模块**：删 inventory-context 的代码与旧表，双写逻辑摘除。

**为什么必须先切读后切写**：写是危险动作（错了产生脏数据），读是安全动作（错了顶多显示错）。切读让新服务先在「错误无损」的场景下证明自己对账能过关，再承担写——顺序颠倒的话，第一个接全量写流量的新服务连「自己读自己写的数据是否正确」都没验证过。

**坑/取舍**：六步最容易塌在第 2 步——发现单体的某个报表 join 了库存表。处理纪律：报表改成走 Gateway 批量查询或订阅事件落宽表，**宁可报表多花一天，不做「暂时共享库」的妥协**（03 册第 6 节的第 4 问）。

## 3. 同步与异步通信的落位

03 册的判断原样迁移，逐条落位：

| 调用 | 拆分前（进程内） | 拆分后 | 为什么 |
|---|---|---|---|
| 下单 → 扣库存 | 同步接口 `reserve` | 同步 HTTP（Boot 4.1 HTTP Service Clients），超时 200ms | 结果直接决定下单成败，要立刻回 409 |
| 下单成功 → 通知 | Outbox 事件 | Outbox 事件 → Kafka（不变） | 通知性质，新服务挂了也不影响下单 |
| 库存预扣 → 确认/回滚 | 同步接口 | 同步 HTTP | 与 reserve 同属命令语义 |
| 库存变更 → 对账/报表 | 进程内查询 | 消费事件落宽表 | 跨服务查询不该每次都 RPC（11-03 册） |

```kotlin
// 拆分后的 Gateway HTTP 实现：契约不变，实现换网络。
// 超时与重试预算按第十一阶段 04 册：超时 < 上游超时，重试只在幂等操作上做。
@Component
class HttpInventoryGateway(private val client: InventoryHttpClient) : InventoryGateway {

    override fun reserve(skuId: Long, quantity: Int, reserveId: UUID): ReserveTicket {
        return try {
            client.reserve(skuId, quantity, reserveId)     // 幂等键放进请求头，服务端去重
        } catch (e: ConnectException) {
            throw InventoryUnavailableException(e)         // 连接失败 → 映射 503，快速失败
        } catch (e: SocketTimeoutException) {
            // 超时的调用结果未知：服务端按幂等键去重，所以允许安全重试一次
            return client.reserve(skuId, quantity, reserveId)
        }
    }
}
```

**坑/取舍**：最容易犯的是「把事件改成同步 RPC 补偿」——下单后想「确认库存」，改成了下单事务里再调一次 HTTP。这一改，下单事务里挂上了外部 IO（[第六阶段 03 册](../06-第六阶段/03-编程式事务与事务边界设计.md)的事务边界灾难），库存服务一抖，单体连接池被拖爆。纪律：**事务内只允许进程内操作与 DB 写，网络调用要么在事务前、要么经 Outbox 异步。**

## 4. 数据迁移：快照、增量、对账、回滚点

库存表迁出的具体做法，四个动作按序执行：

1. **快照回填**：停写窗口（或低峰）导出旧库快照，导入新服务的库。数据量小（本选题 < 100 万行）可以一次完成；量大用「快照 + 从库导出」。
2. **增量同步**：快照之后新产生的写，由双写（第 2 节第 3 步）实时追平。双写期间旧库是权威源，新库追进度。
3. **新旧对账**：对账 SQL 定期跑，不一致率必须归零才允许切读、切写：
4. **回滚点**：每一步定义回退动作——双写期间回滚 = 新服务摘除、旧库继续权威（无数据损失）；切写之后回滚 = 反向双写（新库权威、旧库追写），需要提前把反向同步写好。

```sql
-- 新旧对账：按 sku 对比可用量。容差 0，任何一行不一致都告警。
-- 版本号 version 新旧独立递增，不参与比对。
select coalesce(o.sku_id, n.sku_id) as sku_id,
       o.available as old_available,
       n.available as new_available,
       n.updated_at as new_updated_at
from old_inventory o
full outer join new_inventory n on n.sku_id = o.sku_id
where o.available is distinct from n.available
   or o.sku_id is null
   or n.sku_id is null
limit 100;   -- 告警只贴前 100 行，修完一轮再跑

-- 双写期间的对账要排除「正在途」的写：以旧库 committed_at 早于 5 秒前为界，
-- 太新的行允许滞后，否则对账永远追不上双写的写入速度。
```

**坑/取舍**：对账最常漏的是「漏行」——full outer join 检查两边都有，别忘了单边缺失（新库少一行）也是不一致。另一个坑是对账跑得比写入还慢，永远报不一致；用时间界限排除在途行（见 SQL 注释）是标准解法。

## 5. 拆分成本的量化：前后对照表

毕业项目必须量化「拆分交的税」，这是与「直接上微服务」最大的区别——你知道自己付出了什么：

| 维度 | 单体基线（03 册） | 拆分后 | 成本来源 |
|---|---|---|---|
| 下单 P99 | 132ms | 171ms | +1 次网络往返（~3ms）+ 两次序列化（~4ms）+ Gateway 超时预算占用 |
| 下单 P999 | 310ms | 590ms | 尾部放大：库存服务 GC/抖动直接进入下单尾部 |
| 极限 QPS | 240 | 218 | 链路变长，吞吐受最慢一跳约束；换独立伸缩后读路径反升 |
| 部署单元 | 1 个 | 3 个（网关 + 单体 + 库存） | 发布顺序纪律、联调环境、镜像成本 ×3 |
| 依赖拓扑 | 无 | 单体 → 库存服务 → 共享 PG/Kafka | 新增故障面：库存服务抖动传导到下单 |
| 可观测 | 进程内账本 | 必须跨服务 trace 才能看全一条请求 | 11-08 册的观测成本 |
| 一致性 | 本地事务 | reserve + Outbox + 对账 | 第 4 节的全部机制 |

两个结论要写进报告：**延迟税是结构性的**（+1 往返无法消除，只能通过并行化摊薄），**复杂度税远大于延迟税**（部署 ×3 与故障传导才是日常运维的真实负担）——这正是[第十一阶段 02 册](../11-第十一阶段/02-该不该拆-单体-模块化单体与微服务判据.md)「拆分动机必须是团队与变更」的数字注脚。同时记录收益项：库存扣减的行锁等待从单体的最慢三站里消失，库存服务可独立扩容调优。

**坑/取舍**：对照表最常见的缺陷是只报「变坏的数」不报「变好的数」（或反之），复盘时结论失真。每一行都要写成本来源，让数字可解释；解释不了的数字（P99 忽然涨了 40ms 找不出原因）不能进报告，先查清再写。

## 6. 灰度与回滚在本步的落位

拆分不是一次性切换，用[第十一阶段 09 册](../11-第十一阶段/09-大型应用工程化-联调-灰度与容量.md)的三件套控制节奏：**进入条件**（契约测试全绿、对账归零、容量评估过）、**观察指标**（切读阶段盯新服务的 P99 与对账不一致率；切写阶段盯下单成功率和 409 比例）、**回滚阈值**（对账不一致 > 0 或下单错误率 > 0.1% 立即回退）。

灰度按配置开关控制 Gateway 的实现选择，比例从小到大：`inventory.gateway.mode = dual-write → shadow-read(5%→50%→100%) → cut-over`。每一步切流前观察窗口不少于一个业务高峰。回滚在本步的落位见第 4 节的回滚点——**双写期间回滚零数据损失，这就是双写存在的意义**。

## 7. 「每一步旧代码能否存活」矩阵

拆分期间最容易恐慌的问题是「我现在回退，旧的还活着吗」。把六步写成矩阵，每一步动手前先看这行：

| 步骤完成后 | 单体旧代码可用？ | 旧库存库可用？ | 新服务可用？ | 回退动作 | 数据损失 |
|---|---|---|---|---|---|
| ① 接口收口 | 是 | 是（权威） | 未上线 | 无需回退 | 无 |
| ② 数据切割 | 是 | 是（权威，仅剩读） | 未上线 | 恢复直连表（需重新编译） | 无 |
| ③ 双写 | 是 | 是（权威） | 是（影子） | 摘除双写，旧库照常 | 无 |
| ④ 切读 | 是（读走新） | 是（写权威） | 是（读） | 配置回 read-old | 无 |
| ⑤ 切写 | 是（读写走新） | 只读影子 | 是（读写权威） | 反向双写切换 | 理论无（需反向同步就绪） |
| ⑥ 下线 | 否（已删） | 否（已删） | 是 | 只能前滚修复 | — |

矩阵的设计逻辑：**第 ①~④ 步任何时刻回退都是零损失，第 ⑤ 步的回退要有反向双写兜底，第 ⑥ 步之后没有退路**——所以第 ⑥ 步必须在第 ⑤ 步观察满一个业务周期、所有告警静默之后才允许执行。「下线旧模块」是唯一不可逆的一步，也是唯一不着急的一步。

## 8. 自测

1. 三个判定标准给「先拆库存」的打分里，哪一条在你自己的选题里可能反过来（比如预约选题拆「时段」还是拆「支付」）？为什么？
2. 六步清单里为什么切读必须先于切写？「先切写」会跳过哪个验证环节？
3. 超时的 reserve 调用为什么敢重试一次？如果服务端没有幂等键去重，这里会发生什么？
4. 对账 SQL 为什么要排除「5 秒内在途」的行？full outer join 防的是哪两类不一致？
5. 前后对照表里「P999 310→590ms」的放大机制是什么？延迟税和复杂度税哪个在日常运维里更贵？
6. 矩阵里第 ⑤ 步回退为什么需要「反向双写就绪」这个前提？没准备好就回退会怎样？
