# 07. 手写一个迷你容器

> [← 第三阶段导览](01-导览.md) · 用一百多行 Kotlin 把「扫包 → 注册 → 构造器注入 → 扩展点 → 代理」串起来；写完之后，Spring 的每个类名都不再是黑盒，而是「这里多做了一步什么」。

## 1. 目标与边界

迷你容器要还原五件事，对应 Spring 里五个类：

| 能力 | 迷你实现 | Spring 对应 |
|---|---|---|
| 扫包 | `Files.walk` 遍历 class 目录 | `ClassPathScanningCandidateComponentProvider` |
| 注册表 | `LinkedHashMap<String, Class<*>>` | `DefaultListableBeanFactory.beanDefinitionMap` |
| 单例缓存 | `ConcurrentHashMap<String, Any>` | `DefaultSingletonBeanRegistry.singletonObjects` |
| 构造器注入 | 唯一构造器 + 递归解析 | `ConstructorResolver` |
| 扩展点 + 代理 | 一个 `afterInitialization` 钩子 + JDK 代理 | `BeanPostProcessor` + `AbstractAutoProxyCreator` |

不实现的：条件装配、多作用域、销毁回调、事件、三级缓存、CGLIB。**每一项不实现，都会在最后一节的对照表里体现为一个具体的代价**——这比「抄一遍 Spring」有用得多。

读法建议：先看每段代码，再读它后面那段「与 Spring 差在哪」。代码本身十分钟能看完，差值才是需要记住的部分——因为你线上遇到的每个「注解不生效」，几乎都能在某个差值里找到对应。

## 2. 第一段：扫包

```kotlin
@Target(AnnotationTarget.CLASS)
@Retention(AnnotationRetention.RUNTIME)
annotation class MiniComponent

@Target(AnnotationTarget.FUNCTION)
@Retention(AnnotationRetention.RUNTIME)
annotation class Log

private fun scanClasses(pkg: String): List<Class<*>> {
    val path = pkg.replace('.', '/')
    val loader = Thread.currentThread().contextClassLoader
    return loader.getResources(path).asSequence().flatMap { url ->
        if (url.protocol != "file") emptySequence()          // jar 内需要 ClassGraph，这里先跳过
        else Files.walk(Path.of(url.toURI())).use { stream ->
            stream.filter { it.toString().endsWith(".class") }.toList().asSequence().map { file ->
                val relative = file.toString().substringAfter("$path/").removeSuffix(".class")
                Class.forName("$pkg.${relative.replace('/', '.')}")
            }
        }
    }.toList()
}
```

这段代码只做一件事：把「包名」变成「类列表」。与 Spring 的差别有两处，都很关键。

**Spring 不加载类**。它用 `SimpleMetadataReader`（ASM）读 `.class` 的注解元数据，判断 `@Component` 是否在，全程不触发类初始化。所以 Spring 能扫描一个「依赖缺失、一加载就 `NoClassDefFoundError`」的类并安全跳过；上面的实现一旦 `Class.forName` 就会炸。这也是为什么 `@ConditionalOnClass` 必须基于元数据而不是反射。

**Spring 支持 jar**。生产环境里，你的类在 `BOOT-INF/classes`，依赖的类在 `BOOT-INF/lib/*.jar`，`url.protocol` 是 `jar` 而不是 `file`。上面用 `emptySequence()` 跳过，等价于「只扫自己的 classes 目录」——恰好够 demo 用，但也是「为什么第三方 starter 的组件能被扫到」这个问题的答案所在。实际工程里用 ClassGraph 一行就能覆盖两种情况：`ClassGraph().acceptPackages(pkg).scan().use { it.allClasses }`，它替你处理了 jar、模块化、嵌套 jar 三种容器格式。

这也是「自己写框架」与「用框架」的分水岭：你写的版本在 IDE 里跑得好好的，一打成 fat jar 就失效——**classpath 的形状变了，而扫描逻辑假设了它没变**。Spring 之所以在这里绕了 ASM 一大圈，本质上是在为「打包方式不可控」付代价。

## 3. 第二段：注册表与单例缓存

```kotlin
class MiniContext(private val basePackage: String) {

    private val definitions = LinkedHashMap<String, Class<*>>()     // 定义表：只有元数据
    private val singletons = ConcurrentHashMap<String, Any>()       // 单例表：真正的对象
    private val creating = LinkedHashSet<String>()                  // 正在创建中的 beanName
    private val postProcessors = mutableListOf<MiniBeanPostProcessor>()

    fun scan(): MiniContext {
        scanClasses(basePackage)
            .filter { it.isAnnotationPresent(MiniComponent::class.java) }
            .forEach { definitions[it.simpleName.replaceFirstChar(Char::lowercaseChar)] = it }
        return this
    }
}
```

两张表分开，是第 02 册那个结论的最小复现：`scan()` 结束时**一个对象都没创建**，但你已经有完整的「谁是谁」清单。后面 `start()` 才按需实例化——这就是「注册后、实例化前」那段窗口，Spring 用它跑条件装配与定义改写，这里什么都没有，所以迷你容器天然不支持 `@Conditional`。

beanName 用「类名首字母小写」，与 Spring 的 `AnnotationBeanNameGenerator` 一致；不一致的是冲突处理——Spring 会抛 `ConflictingBeanDefinitionException`，这里后注册者静默覆盖前者。**静默覆盖是最糟的默认值**，Spring 在这点上比迷你实现严格得多。

用 `LinkedHashMap` 而不是 `HashMap`，是为了让「实例化顺序 = 扫描顺序」可复现。可复现的顺序在排障时非常值钱：同一份代码两次启动打印出不同的 Bean 创建顺序，就没法用「上次是好的」来定位。Spring 的 `beanDefinitionNames` 也是有序 List，原因相同。

## 4. 第三段：构造器注入与递归依赖

```kotlin
fun getBean(type: Class<*>): Any {
    singletons.values.firstOrNull { type.isInstance(it) }?.let { return it }

    val (name, impl) = definitions.entries.firstOrNull { type.isAssignableFrom(it.value) }
        ?: error("没有可用的 Bean: ${type.name}")
    return create(name, impl)
}

inline fun <reified T : Any> getBean(): T = getBean(T::class.java) as T

private fun create(name: String, type: Class<*>): Any {
    singletons[name]?.let { return it }        // 命中单例缓存（对应 getSingleton 的一级查找）
    check(creating.add(name)) { "循环依赖：$name 在创建过程中被再次请求，栈=$creating" }

    // ① 实例化：唯一构造器，逐参数递归解析（对应 createBeanInstance）
    val ctor = type.declaredConstructors.single()
    val args = ctor.parameterTypes.map { getBean(it) }.toTypedArray()
    var bean: Any = ctor.newInstance(*args)

    // ② 初始化 + 扩展点（对应 initializeBean）
    postProcessors.forEach { bean = it.afterInitialization(bean, name) }

    // ③ 代理（对应 wrapIfNecessary）
    bean = proxify(bean, type)

    singletons[name] = bean
    creating.remove(name)
    return bean
}
```

三行代码藏着三个设计决策：

**`declaredConstructors.single()`** 要求「恰好一个构造器」。Spring 面对多个构造器时按 `@Autowired` → 无参 → 唯一构造器的优先级挑一个，还要处理参数歧义、`@Qualifier`、可选依赖。迷你实现用 `single()` 直接把这个复杂度挡在门外——这恰好反证了「单构造器 + 构造器注入」为什么是最优实践：**它让容器不需要做选择**。

**递归调用 `getBean(it)`** 就是依赖解析的全部。参数类型如果是接口（`Greeting`），`definitions` 里存的实现类会通过 `isAssignableFrom` 命中；如果有两个实现，`firstOrNull` 随便挑一个——Spring 在这种情况下抛 `NoUniqueBeanDefinitionException` 并要求 `@Primary`/`@Qualifier`。**迷你容器的「能用」建立在「类型不歧义」这个未言明的约定上**，这也是真实项目里接口只有一个实现的常见原因（不一定是设计选择，可能是容器逼的）。

**`creating` 集合**是 `singletonsCurrentlyInCreation` 的翻版。它在 `create` 开头 `add`、结尾 `remove`，一旦同一个名字第二次进来就抛异常。构造器注入下这是唯一正确的行为：没有对象就没有早期引用，解不了环（02 册 §6）。如果你的迷你容器想支持 setter 注入，`creating` 检查之后还得加一套早期引用缓存——那就是三级缓存的起点。

**这里故意没有属性填充**。Spring 的 `create()` 之后还有 `populateBean`（字段/setter 注入），而迷你容器把「依赖从哪来」唯一地收敛到构造器参数上。这带来一个很有意思的对照：真实项目里「为什么我的 Bean 是 null」这个头号问题，在这个容器里根本不可能发生——不是因为它更强，而是因为它拒绝接受会引发该问题的写法。**很多框架问题的根治手段是「不支持」**。

## 5. 第四段：`BeanPostProcessor` 钩子

```kotlin
interface MiniBeanPostProcessor {
    fun afterInitialization(bean: Any, name: String): Any = bean
}

fun start(): MiniContext {
    // ① 先造 BPP 本身（对应 registerBeanPostProcessors）
    definitions.entries
        .filter { MiniBeanPostProcessor::class.java.isAssignableFrom(it.value) }
        .forEach { (name, impl) -> postProcessors += create(name, impl) as MiniBeanPostProcessor }

    // ② 再实例化其余单例（对应 preInstantiateSingletons）；已建好的会被缓存挡回
    definitions.forEach { (name, impl) -> create(name, impl) }
    return this
}
```

**为什么 BPP 必须先造**：它们要参与后面每个 Bean 的初始化。Spring 的 `registerBeanPostProcessors` 就是这一步，且顺序由 `PriorityOrdered` → `Ordered` → 无序 决定；迷你容器按扫描顺序，不排序——所以如果你的 BPP 有前后依赖，行为不可预期。这一条差异在真实项目里表现为「自定义 BPP 有时生效有时不生效」，根因就是没实现 `Ordered`。

只留 `afterInitialization` 一个钩子，是因为它承载了最关键的能力：**换掉返回值**。`beforeInteractions`、属性注入、Aware、销毁这些钩子都可以省，唯独这一个不能——AOP 全靠它。

排序缺失的具体后果值得推演一遍：假设你有两个 BPP，一个负责「给 Bean 加指标计时」，一个负责「给 Bean 套事务代理」。按扫描顺序先跑计时的，最终 `singletons` 里存的是「事务代理外面包了计时」还是「计时外面包了事务代理」，取决于类名的字典序——而这两种嵌套的语义完全不同（计时是否包含代理开销、事务是否覆盖计时代码）。Spring 用 `PriorityOrdered`/`Ordered` 把这件事变成显式契约，不是官僚，是**让顺序不再是巧合**。

## 6. 第五段：`@Log` 代理

```kotlin
private fun proxify(bean: Any, type: Class<*>): Any {
    val logged = bean.javaClass.methods
        .filter { it.isAnnotationPresent(Log::class.java) }
        .map { it.name }.toSet()
    if (logged.isEmpty()) return bean

    val ifaces = type.interfaces
    require(ifaces.isNotEmpty()) { "${type.name} 用了 @Log 却没有接口：迷你容器只实现 JDK 代理" }

    return Proxy.newProxyInstance(type.classLoader, ifaces) { _, method, args ->
        if (method.name !in logged) return@newProxyInstance invoke(bean, method, args)
        val t0 = System.nanoTime()
        try {
            invoke(bean, method, args)
        } finally {
            println("[mini-aop] ${type.simpleName}.${method.name} ${(System.nanoTime() - t0) / 1_000}µs")
        }
    }
}

private fun invoke(target: Any, method: Method, args: Array<Any>?): Any? =
    try {
        method.invoke(target, *(args ?: emptyArray()))
    } catch (e: InvocationTargetException) {
        throw e.targetException          // 与 Spring 一致：剥掉反射包装，让上层看到原始异常
    }
```

四个要点：

**注解要读实现类的方法**。接口上的 `Method` 对象不带 `@Log`，必须去 `bean.javaClass.methods` 里找同名方法。这正是 Spring 用 `AopUtils.getMostSpecificMethod` 的原因——切点匹配必须在「最具体的实现方法」上做。

**只支持 JDK 代理**，因此要求目标类实现接口。Spring 默认走 CGLIB，正是为了摆脱这个要求（04 册 §2）。把 `require` 写成明确报错，比静默返回原对象好——**AOP 失效最怕的就是静默**。

**异常要剥包装**。`Method.invoke` 把目标抛的异常包进 `InvocationTargetException`，不剥的话上层永远看不到业务异常，`@Transactional` 的回滚规则也会判断错（Spring 在 `JdkDynamicAopProxy.invoke` 里做了同样的事）。

**代理必须替换掉返回值**，而不是「在原对象上加工」。`create` 里那行 `bean = proxify(bean, type)` 之后，`singletons` 里存的、`getBean` 返回的都是代理——这一点与 Spring 完全一致。

还有一处值得留意：这里只有**一个**切面，所以「切面链」这个概念在迷你容器里不存在。Spring 里多个 Advisor 会组成链表，按 `@Order` 嵌套（04 册 §4），而 `proxify` 只会 `if (@Log) 打日志 else 直调`。当你发现「日志切面记录的时间和事务提交时间对不上」时，问题必然出在链的顺序上，而不是某个切面本身——迷你容器恰好把这个变量消掉了，用它做对照实验很容易看清因果。

## 7. 装配、演示与测试

```kotlin
interface Greeting { fun hello(name: String): String }
interface Report { fun render(): String }

@MiniComponent
class GreetingService : Greeting {
    @Log override fun hello(name: String): String = "hello, $name"
}

@MiniComponent
class ReportService(private val greeting: Greeting) : Report {
    @Log override fun render(): String = inner()                 // 自调用：不经过代理
    @Log fun inner(): String = greeting.hello("mini")            // 跨 Bean：经过代理
}
```

`ReportService.inner()` 不在 `Report` 接口里，JDK 代理根本看不到它——这既是限制，也是对「自调用」最直观的证明：**代理只认得接口，`this` 调用连代理的门都进不去**。

demo 的三个刻意设计：两个接口分开（`Greeting` 与 `Report`）是为了让代理边界清晰；`ReportService` 通过构造器拿到 `Greeting`，是为了验证「注入的值本身已是代理」；`inner()` 不进接口，是为了让自调用失效成为可断言的事实而不是口头结论。测试里还留了一个 `com.acme.mini.cycle` 包，用来触发 `creating` 的报错——一个容器如果没测过循环依赖，等于没测过依赖解析。

```kotlin
class MiniContextTest {

    private val ctx = MiniContext("com.acme.mini").scan().start()

    @Test
    fun `构造器注入生效`() {
        assertEquals("hello, mini", ctx.getBean<Report>().render())
    }

    @Test
    fun `代理生效且自调用不生效`() {
        val out = captureStdout { ctx.getBean<Report>().render() }
        assertEquals(1, out.lines().count { "ReportService.render" in it })   // 外层被拦
        assertEquals(0, out.lines().count { "ReportService.inner" in it })    // 自调用没被拦
    }

    @Test
    fun `跨 Bean 调用经过代理`() {
        val out = captureStdout { ctx.getBean<Report>().render() }
        assertEquals(1, out.lines().count { "GreetingService.hello" in it })
    }

    @Test
    fun `构造器循环依赖被拒绝`() {
        val ex = assertThrows<IllegalStateException> { MiniContext("com.acme.mini.cycle").scan().start() }
        assertTrue(ex.message!!.contains("循环依赖"))
    }

    private inline fun captureStdout(block: () -> Unit): String {
        val origin = System.out
        val buffer = ByteArrayOutputStream()
        System.setOut(PrintStream(buffer, true))
        return try { block(); buffer.toString() } finally { System.setOut(origin) }
    }
}
```

第三个断言的读法要小心：`GreetingService.hello` 被拦是因为 `ReportService` 注入到的 `greeting` 是**代理**（构造器参数 `Greeting` 解析到的 `singletons` 值已经是代理）。这正好验证了「外部调用走代理」的另一半：容器内的依赖注入拿到的也是代理，所以跨 Bean 调用天然生效——**自调用是唯一的例外**。

## 8. 迷你容器 vs Spring

| 能力 | 迷你容器 | Spring | 差距意味着什么 |
|---|---|---|---|
| 扫包 | `Files.walk`，仅目录 | ASM 元数据，支持 jar | 依赖里的组件扫不到；无法「不加载类就判断」 |
| 注册 | 无条件的 `Map.put` | 条件 + 覆盖策略 + `role` | 没有 `@Conditional`，也没有冲突检测 |
| 实例化 | 唯一构造器 + 递归 | 构造器选择、`@Qualifier`、`ObjectProvider` | 类型歧义直接失效 |
| 循环依赖 | 抛异常 | 三级缓存（Setter 场景） | 只覆盖「最健康」的写法 |
| 扩展点 | 1 个（afterInit） | 12 个（定义期 + 实例期 + 销毁期） | 无法改定义、无法接管属性填充 |
| 代理 | JDK only | JDK + CGLIB，Advisor 链 | 无接口不可用；单切面，无顺序概念 |
| 作用域 | 单例 | 6 种 | 没有 request/session |
| 销毁 | 无 | `@PreDestroy`、`DisposableBean` | 连接、线程不会被回收 |
| 事件 | 无 | `ApplicationEvent` + 多播器 | 没有「启动完成」这类通知 |

把这张表从下往上读一遍，你会发现**Spring 的复杂度几乎全部来自「让不适合理想的代码也能跑」**：没有接口就上 CGLIB、类型歧义就报错并给 `@Primary`、需要循环依赖就三级缓存、停机要收尾就销毁回调。而迷你容器之所以能只有一百多行，是因为它对使用者的代码提了五个硬要求：有接口、单构造器、类型不歧义、不用条件、不关心销毁。

如果要继续补，按「收益 / 成本」排序的建议是：先加销毁（`@PreDestroy` 反射调用，约 20 行，立刻让连接池可用），再加 prototype 作用域（约 15 行，但要想清销毁责任），然后才是条件装配（约 60 行，且必须引入「两阶段过滤」才能谈性能），最后才是三级缓存（约 40 行，但会连带把「代理何时生成」的问题一起引进来）。**这个顺序恰好也是 Spring 自身演进的顺序**——框架的每一层复杂度，都是为了解决上一层暴露出来的真实问题。

这五个要求，恰好就是第三阶段反复强调的「健康的写法」。**框架的复杂度与你的代码规约程度成反比**——这是手写容器最大的收获。
