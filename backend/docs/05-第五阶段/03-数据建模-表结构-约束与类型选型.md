# 03. 数据建模：表结构、约束与类型选型

> [← 第五阶段导览](01-导览.md) · 表结构没有「标准答案」，只有「这个设计替谁挡掉了哪类错误」。**你的判据不是范式，是三件事：哪条业务不变量必须由数据库保证、主要查询能否走索引、加一个字段要不要改结构。** 这三件事答不上来，表建得再"规范"也只是把问题推到上线后。

## 1. 先定判据：三种都"能跑"的表结构，选哪个

同一个订单域，至少能写出三种都跑得通的表结构：

**A. 按页面建表**——前端详情页要展示什么，表里就有什么列：`receiver_name`、`receiver_phone`、`address_text`、`total_amount`、`status_text`。

**B. 按领域建表**——订单是聚合根，收货信息是值对象，金额有明细，状态有明确取值集合。

**C. 按查询建表**——先列出所有查询与排序，让每个查询都能命中一个索引，其余字段合并成 JSON 列。

三者在上线第一个月都看不出差别。差别在**第二次需求变更**时才爆发：

| 需求变更 | 按页面建表 | 按领域建表 | 按查询建表 |
|---|---|---|---|
| 加「部分退款」 | `status_text` 塞不进两个状态，加一列 `refunded_amount`，再改所有读的地方 | 加 `refund` 子表，订单状态机加一条迁移 | 改 JSON 结构，所有按 `status` 过滤的索引重建 |
| 改「收货人可以有多个」 | 整表加 `receiver2_*`（真实发生过） | 值对象拆表，改动局部 | 与按页面建表同样痛 |
| 查「上月某状态订单金额合计」 | 全表扫描 + 应用层求和 | 索引 + 聚合 | 取决于有没有为这个查询建过索引 |

结论不是「一定要按领域建」，而是：**按页面建表把成本推给了未来，按查询建表把成本推给了扩展性，按领域建表把成本推给了当下的设计时间**。选哪个取决于这张表要活多久、变更频率多高。订单、账务、库存这类「要活五年、改一次要停机」的表，必须按领域建；纯日志、埋点、临时报表表，按查询建更省事。

## 2. 从需求推表：订单域走一遍

需求原文往往长这样：

> 用户下单时可选多个商品，每个商品有下单时的价格快照（后续改价不影响已下单订单）；订单支持部分退款；一张订单可以有多个收货地址（用户改地址后旧地址仍要能查）；订单状态必须按「待支付 → 已支付 → 已发货 → 已完成」推进，已完成的订单不能退款。

在这段需求里，能被翻译成**结构约束**的是这几句：

- 「改价不影响已下单」→ 订单明细必须存 `unit_price` 快照，不能 join 商品表取当前价
- 「部分退款」→ 退款必须是子表，退款金额逐笔记录，订单上的 `paid_amount` 是聚合值
- 「旧地址仍要能查」→ 地址不能就地更新，要么版本化，要么快照到订单上
- 「状态按顺序推进，已完成不能退款」→ 状态是枚举 + 迁移规则，不是自由文本

对应的 DDL：

```sql
CREATE TABLE orders (
    id             uuid          PRIMARY KEY,
    user_id        bigint        NOT NULL,
    status         text          NOT NULL,
    currency       char(3)       NOT NULL,
    total_amount   numeric(14,2) NOT NULL,
    paid_amount    numeric(14,2) NOT NULL DEFAULT 0,
    refunded_amount numeric(14,2) NOT NULL DEFAULT 0,
    created_at     timestamptz   NOT NULL,
    paid_at        timestamptz,
    version        bigint        NOT NULL DEFAULT 0,

    CONSTRAINT orders_status_check
        CHECK (status IN ('PENDING','PAID','SHIPPED','COMPLETED','CANCELLED')),
    CONSTRAINT orders_amount_non_negative
        CHECK (total_amount >= 0 AND paid_amount >= 0 AND refunded_amount >= 0),
    CONSTRAINT orders_refund_le_paid
        CHECK (refunded_amount <= paid_amount),
    CONSTRAINT orders_paid_has_time
        CHECK ((status = 'PENDING') = (paid_at IS NULL))
);

CREATE TABLE order_items (
    order_id    uuid          NOT NULL REFERENCES orders (id),
    line_no     int           NOT NULL,
    sku_id      bigint        NOT NULL,
    sku_name    text          NOT NULL,      -- 快照
    unit_price  numeric(14,2) NOT NULL,      -- 快照
    quantity    int           NOT NULL CHECK (quantity > 0),
    PRIMARY KEY (order_id, line_no)
);

CREATE TABLE order_addresses (
    id          bigserial     PRIMARY KEY,
    order_id    uuid          NOT NULL REFERENCES orders (id),
    receiver    text          NOT NULL,
    phone       text          NOT NULL,
    detail      text          NOT NULL,
    is_current  boolean       NOT NULL DEFAULT false,
    created_at  timestamptz   NOT NULL
);

CREATE UNIQUE INDEX order_addresses_one_current
    ON order_addresses (order_id) WHERE is_current;

CREATE TABLE refunds (
    id          uuid          PRIMARY KEY,
    order_id    uuid          NOT NULL REFERENCES orders (id),
    amount      numeric(14,2) NOT NULL CHECK (amount > 0),
    reason      text          NOT NULL,
    created_at  timestamptz   NOT NULL
);
```

有几个决定值得单独说明，它们和「范式」无关，全是**把需求里的一句话落成一条库能拒绝的规则**：

- `order_items` 用 `(order_id, line_no)` 联合主键，不用代理 id：这一行的身份就是「哪张订单的第几行」，代理 id 只会让唯一性约束变成一个额外索引。
- `order_addresses` 的部分唯一索引 `WHERE is_current` 保证「一张订单最多一个当前地址」——这条规则用应用层校验在并发下必然失守，用库约束是零成本的。
- `CHECK ((status = 'PENDING') = (paid_at IS NULL))` 把「待支付必无支付时间、其余必有」写成约束。这类「两列之间的状态一致性」是最容易被漏掉、也最容易在线上造出脏数据的一类规则。
- `refunded_amount <= paid_amount` 放在库上，退款并发时由数据库而不是你的 if 语句来兜底。

## 3. 主键选型：`bigserial`、UUID、UUIDv7、雪花

主键不是"随便一个唯一列"，它是三件事的叠加：**物理存储顺序、对外暴露的安全性、生成位置（数据库还是应用）**。

| 方案 | 体积 | 写入顺序性 | 可猜测 | 可客户端生成 | 跨库合并 |
|---|---|---|---|---|---|
| `bigserial` / `identity` | 8 字节 | 完美（单调递增） | 可猜（遍历 id 就是遍历数据） | 否 | 需重新编号 |
| UUIDv4 | 16 字节 | 差（随机） | 不可猜 | 是 | 天然可合并 |
| UUIDv7 | 16 字节 | 好（时间前缀有序） | 不可猜（含时间戳） | 是 | 天然可合并 |
| 雪花 ID（int64） | 8 字节 | 好 | 可猜（时间可反推） | 是（需 workerId） | 需保证 workerId 不冲突 |

**随机 UUID 的代价是可以量出来的**，不是玄学。B-tree 索引是按主键顺序组织的，随机主键意味着每次插入都可能落在任意一个叶子页上：

```sql
-- 观察页分裂：同一张表，两种主键，插入 200 万行后比较
SELECT relname,
       n_live_tup,
       n_tup_ins,
       pg_size_pretty(pg_relation_size(relid))  AS heap,
       pg_size_pretty(pg_relation_size(relid, 'main')) AS heap_main
FROM pg_stat_user_tables WHERE relname IN ('t_serial','t_uuid4');

-- 索引平均页密度（fillfactor 命中情况）
CREATE EXTENSION IF NOT EXISTS pgstattuple;
SELECT 't_uuid4' AS t, avg_leaf_density FROM pgstatindex('t_uuid4_pkey')
UNION ALL
SELECT 't_serial', avg_leaf_density FROM pgstatindex('t_serial_pkey');
```

随机主键的叶子页密度通常在 60%~70%，而顺序主键接近 90%。这意味着**同样的数据量多占 30%~40% 的索引空间，且每次插入多一次随机 IO**。写放大在高频写入表上会直接变成 WAL 体积和 autovacuum 压力。

选型建议按场景直接对号入座：

- **纯内部表、不出现在 URL 里、单库单写入点**：`bigint GENERATED ALWAYS AS IDENTITY`，简单、省空间、顺序写最优。是否可猜不重要——权限校验不该依赖「猜不到 id」。
- **id 出现在 URL / API 里，且不能让外部推算数据量或遍历**：UUIDv7。它同时满足「不可猜」和「顺序写」。PG 18 及以上内置 `uuidv7()`；17 及以下要有序 uuid 需要扩展或应用侧生成。
- **客户端要离线生成、或要合并多端数据（同步类应用）**：UUIDv7，生成位置天然在客户端。
- **分库分表、需要全局唯一且要求 int64 体积**：雪花 ID，但 workerId 分配本身就是一套需要运维的子系统——单体阶段不要提前引入。

**不要用 `text` 存 UUID 再自称「用 UUID 了」**：`text` 版本占 36 字节、比较走字符串、索引更大，且 `uuid` 类型的合法性校验完全丢失。

## 4. 类型选型的六条铁律

类型选错是「上线三个月后才发现」的典型：改类型在大表上意味着重写表、锁表、跨版本兼容，成本比一开始选对高两个数量级。

**一、金额用 `numeric(p,s)`，永远不用 `float`/`double`。** 二进制浮点无法精确表示 0.1，累加会产生分位误差。`numeric(14,2)` 表示最大 9999 亿、两位小数。若业务要求「最小货币单位整数存储（分）」，`bigint` 也可行，但要接受「所有读写点都必须乘除 100」这个代价——一旦漏一处，就是 100 倍金额事故。**多币种时必须单独存 `currency`**，且 ISO 4217 里 JPY 没有小数位、某些币种有三位，`numeric(x,2)` 是隐含的「两位小数假设」，要显式确认。

**二、时间用 `timestamptz`，不用 `timestamp`。** `timestamp`（无时区）存的是「墙上时间」，含义随服务器时区漂移；`timestamptz` 存 UTC 时间点，展示时才按会话时区转换。线上最常见的翻车是：容器时区是 UTC、开发机是 CST，`timestamp` 字段在生产上整体偏移 8 小时。规则是**入库一律 UTC 时间点，时区只活在展示层**。

**三、枚举：`text` + `CHECK` 优先，PG 原生 `enum` 慎用。** 原生 `enum` 的坑在演进：加值要 `ALTER TYPE ... ADD VALUE`（且新值不能在同一事务里使用），**删值做不到**，改名要重建类型，用 `enum` 的列做迁移比 `text` 难得多。`text + CHECK` 的代价是约束要跟着改，但改约束是普通 DDL，可以零停机。状态取值稳定、且你确定永不需要删值（如性别、币种）时，原生 `enum` 可以省 4 字节，但省下来的空间通常不值得换来迁移的麻烦。

**四、多状态不要用一堆 `boolean`。** `is_paid`、`is_shipped`、`is_refunded` 三个布尔能表示 8 种组合，其中 5 种是非法状态，而数据库无法阻止你写出 `is_refunded = true AND is_paid = false`。状态是**互斥的一维取值**，就该用单列 + `CHECK`。多个布尔列真正的用武之地是「彼此独立、可任意组合」的开关（如通知渠道：邮件/短信/站内信）。

**五、JSONB 的边界：结构不确定可以，需要被约束和查询不行。** 适合 JSONB 的三类场景：第三方回调的原始 payload（你不想为它建表）、审计快照（历史那一刻的完整状态）、扩展属性（用户自定义字段）。**不适合**的三类：要按内部字段过滤/排序（除非建表达式索引，且索引要跟着结构改）、要被外键约束、要和其它表 join。判断标准一句话：**如果这个字段会出现在 `WHERE` 或 `ORDER BY` 里，它应该是列。**

**六、`varchar(n)` 的 `n` 不是性能选项。** PG 里 `varchar(n)` 与 `text` 存储与性能完全一致，`n` 只起长度校验作用。写 `varchar(255)` 的理由只有「业务上确实最多 255 字符」。反过来说，**该加长度约束的地方往往被漏掉**：手机号、邮编、国家代码这类有明确格式的值，用 `text` 加 `CHECK` 比放任不管强。

```sql
-- 类型选型的正例：每一列的类型都在表达业务约束
CREATE TABLE payments (
    id             uuid          PRIMARY KEY,
    order_id       uuid          NOT NULL REFERENCES orders (id),
    channel        text          NOT NULL
        CHECK (channel IN ('ALIPAY','WECHAT','CARD','BALANCE')),
    amount         numeric(14,2) NOT NULL CHECK (amount > 0),
    currency       char(3)       NOT NULL CHECK (currency ~ '^[A-Z]{3}$'),
    external_no    text          CHECK (external_no ~ '^[A-Za-z0-9_-]{1,64}$'),
    raw_callback   jsonb,                        -- 第三方原始报文，只存不查
    occurred_at    timestamptz   NOT NULL,       -- UTC 时间点
    created_at     timestamptz   NOT NULL DEFAULT now()
);
```

## 5. 约束才是领域模型：不变量放在哪一层

一条业务规则可以放在三层：领域对象（Kotlin 里）、应用服务（校验逻辑）、数据库（约束）。**只有第三层在并发下是可靠的**，因为前两层都是「先读后判」，中间有窗口。

```sql
-- 并发扣库存：应用层校验必然失守
-- 两个事务都读到 stock = 1，都判断通过，都写入
UPDATE skus SET stock = stock - 1 WHERE id = 1;   -- 结果是 -1

-- 库约束兜底：即使应用层判断错了，也写不进去
ALTER TABLE skus ADD CONSTRAINT skus_stock_non_negative CHECK (stock >= 0);
```

三层各该放什么：

| 层 | 该放什么 | 不该放什么 |
|---|---|---|
| 领域对象 | 类型层面的不变量（金额不能为负的 `Money` 值对象）、状态迁移合法性 | 依赖外部数据的校验（库存够不够） |
| 应用服务 | 跨聚合的规则、需要查其它表/外部服务的判断、给用户的友好错误 | 唯一性（改成库约束 + 捕获冲突）、并发相关判断 |
| 数据库 | 唯一性、非空、范围（`>= 0`）、列间一致（`refunded <= paid`）、状态取值集合、外键 | 需要复杂业务知识的规则（会变成触发器地狱） |

**唯一索引是"最后一道门"，同时是实现幂等的首选手段。** 「同一用户对同一订单只能有一条未支付支付单」写成部分唯一索引，比任何 if 判断都可靠：

```sql
CREATE UNIQUE INDEX payments_one_pending_per_order
    ON payments (order_id) WHERE status = 'PENDING';
```

**外键到底用不用**，是个真实的取舍而不是教条：

- 用外键的收益：引用完整性由库保证；级联删除可以声明；`EXPLAIN` 里 join 的基数估算更准。
- 用外键的代价：每次插入子表要对父表行加 `KEY SHARE` 锁，这在**父表有高频删除/更新**时会造成锁等待；分库分表后外键物理上不可能。
- 现实选择：**单体 + 单库阶段大量使用外键**（收益远大于代价）；跨服务边界一定不用（数据所有权不在一处）；超高写入的日志类表可以不用（但要在应用层补一致性校验和定期对账）。

**约束一定要留名字。** `CONSTRAINT orders_refund_le_paid CHECK (...)` 而不是匿名的 `CHECK (...)`——匿名约束在报错时只给你 `orders_check1`，而具名约束能直接告诉你违反了哪条业务规则，也方便后续 `DROP CONSTRAINT` 精确定位。

## 6. 软删除的四个代价

`deleted_at` 加不加，看起来是个人偏好，实际会连锁影响唯一约束、索引体积、每一条查询和合规流程。

**代价一：唯一约束直接失效。** 用户注销后 `deleted_at` 置位，邮箱仍占着唯一索引，该邮箱永远无法再注册——这是软删除最经典的线上事故。解法是部分唯一索引：

```sql
-- 只对"活着"的行做唯一约束
DROP INDEX IF EXISTS users_email_key;
CREATE UNIQUE INDEX users_email_alive
    ON users (lower(email)) WHERE deleted_at IS NULL;
```

注意这里同时用 `lower(email)` 做了规范化——邮箱大小写不敏感是业务事实，靠应用层每次 `toLowerCase()` 迟早会漏。

**代价二：每一条查询都要带过滤条件，漏一处就是 bug。** 而且是静默的 bug：漏掉 `deleted_at IS NULL` 的查询不会报错，只会给用户看到已删除的数据。缓解手段有三种，按可靠性排序：一是用视图封装（`v_users AS SELECT * FROM users WHERE deleted_at IS NULL`，写入走原表）；二是 ORM 层全局过滤器（Hibernate 的 `@SQLRestriction` / `@Filter`，但对原生 SQL 无效）；三是靠 code review——最不可靠。

**代价三：索引膨胀与查询计划退化。** 一张 1000 万行、其中 900 万行是软删除的表，索引里 90% 的条目永远用不上，`EXPLAIN` 的基数估算也会偏。定期物理归档是必要的，否则"软删除"最终会变成"表只增不减"。

**代价四：真正的删除需求仍然存在。** 合规上的「被遗忘权」要求物理删除，软删除只是拖后了这件事。所以更完整的方案是：软删除（业务可恢复）+ 归档表（冷数据搬走）+ 审计日志（记录谁删了什么）。三者的分工是——软删除给业务留撤销窗口，归档解决体积，审计解决追责。

**替代方案**：如果删除是「状态」而不是「删除」（订单被取消、任务被终止），那它本来就该是状态机里的一种状态，用 `status = 'CANCELLED'` 表达，比 `deleted_at` 语义准确得多。软删除真正适用的场景只有一类：**用户主动删除、且业务需要「误删可恢复」窗口**。

## 7. 关系建模：一对多、多对多、树形

**一对多**的外键永远放在「多」的那一侧，方向不能反（反了就是数组字段，违反第一范式，且无法索引、无法约束）。`order_items.order_id` 指向 `orders.id` 是标准形态。

**多对多**必须用连接表，连接表的主键有两种选法：

| 选法 | 适用 | 代价 |
|---|---|---|
| `PRIMARY KEY (a_id, b_id)` | 关系本身无属性、且不需要被单独引用 | 无代理 id，删除/更新要走复合条件 |
| 代理 id + `UNIQUE (a_id, b_id)` | 关系有属性（加入时间、角色、排序）、或要被外键引用 | 多一个索引，但引用方便 |

关系上有属性时（如 `user_roles` 带 `granted_at`、`granted_by`），连接表就是一张正经的实体表，别硬塞进联合主键。

**树形结构有四种做法**，代价差异极大，选错会在递归查询上撞墙：

| 方案 | 结构 | 查子树 | 查祖先 | 移动子树 | 适合 |
|---|---|---|---|---|---|
| 邻接表 | `parent_id` | 递归 CTE | 递归 CTE | 改一行 | 深度小、读多写少、PG 有递归 CTE |
| 路径枚举 | `path = '/1/5/12/'` | `path LIKE '/1/5/%'` | 字符串拆分 | 重写整棵子树的 path | 读极多、树几乎不变 |
| 嵌套集 | `lft` / `rgt` | `lft BETWEEN a AND b`（无递归） | `lft < a AND rgt > b` | 重算大量节点 | 只读目录（如分类树） |
| 闭包表 | 独立的 `(ancestor, descendant, depth)` 表 | 一次 join | 一次 join | 插入 O(深度) | 深度大、读写都频繁、需要任意层级统计 |

默认选邻接表——PG 的递归 CTE 写起来干净，且它在深度不大时性能完全够：

```sql
WITH RECURSIVE subtree AS (
    SELECT id, parent_id, name, 1 AS depth
    FROM categories WHERE id = 5
    UNION ALL
    SELECT c.id, c.parent_id, c.name, s.depth + 1
    FROM categories c JOIN subtree s ON c.parent_id = s.id
)
SELECT * FROM subtree ORDER BY depth, id;
```

**递归 CTE 的两个必须项**：一是加深度上限（`WHERE s.depth < 10`）防脏数据造成的无限递归；二是给 `parent_id` 建索引（否则每一层都是全表扫描）。若树的深度可能超过几十层、或需要频繁查「某节点的全部祖先」，闭包表是唯一不会退化的方案。

**别用 JSONB 数组存一对多关系**（如 `order.product_ids: [1,2,3]`）。它一次性丢掉了外键约束、join 能力、按商品反查订单的能力，以及元素级的更新能力——这类"省一张表"的设计，通常在第二个需求就要求你写迁移脚本把它拆开。

## 8. 值对象与聚合怎么落表

领域模型和表结构不是一一对应关系。一个值对象（`Address`、`Money`、`DateRange`）落表有四种方式，各有适用面：

```kotlin
// 领域层：值对象自带不变量
@JvmInline
value class Money private constructor(val cents: Long) {
    companion object {
        fun of(cents: Long): Money {
            require(cents >= 0) { "金额不能为负" }
            return Money(cents)
        }
    }
    operator fun plus(other: Money) = Money(cents + other.cents)
}
```

| 落表方式 | 例子 | 何时用 |
|---|---|---|
| 内联成多列 | `receiver_name` / `receiver_phone` / `receiver_detail` | 值对象字段少、不需要独立查询、生命周期与宿主一致 |
| 拆成独立表 | `order_addresses`（带版本） | 需要保留历史、需要被其它表引用 |
| JSONB 单列 | `shipping_address jsonb` | 结构确实会变、只整体读写、不按子字段过滤 |
| 共享字典表 | `address_id` 指向地址簿 | 值对象被多处复用、且需要统一维护 |

**聚合边界决定事务边界**。一个聚合内的所有表，改动应该在同一个事务里完成；跨聚合的修改只能靠事件与补偿。这直接约束了建表方式：如果你把 `order` 和 `order_items` 放在两个"服务"里，那么「订单总额必须等于明细之和」这条不变量就再也没有地方保证了。**建表之前先想清楚哪些数据必须一起改**——这比任何范式都重要。

**不可变快照 vs 可更新引用**是另一个关键选择。订单里的商品名、单价必须是快照（`sku_name`、`unit_price` 直接存在 `order_items` 里），因为「当时买的是什么、多少钱」是历史事实；而 `sku_id` 是指向当前商品的引用。**混淆这两者会造成两类事故**：用 join 取当前价导致历史订单金额变化；或者把快照当引用，改了商品名却不知道历史订单也该跟着改。

## 9. 反范式：什么时候该冗余

「第三范式」是默认起点，但有三类冗余是**必要的**，而且必须能回答「谁是源、怎么同步、不一致能忍多久」：

**一、历史快照**。订单明细里的商品名与单价、发票上的公司抬头、审批流里的审批人姓名。这类冗余不是"重复存储"，而是**捕获时间点的事实**——源数据后来会变，而历史不该变。这类字段永不回填、永不同步。

**二、聚合缓存**。`orders.total_amount` 是 `order_items` 之和，`orders.refunded_amount` 是 `refunds` 之和。冗余的理由是查询性能（列表页不可能每次都聚合明细）。同步方式有三种：

```sql
-- 方式一：同一事务内应用层维护（最简单，也最容易漏）
UPDATE orders SET total_amount = (
    SELECT COALESCE(sum(unit_price * quantity), 0)
    FROM order_items WHERE order_id = $1
) WHERE id = $1;

-- 方式二：触发器保证（不会漏，但把逻辑藏进了数据库）
CREATE OR REPLACE FUNCTION sync_order_total() RETURNS trigger AS $$
BEGIN
    UPDATE orders SET total_amount = (
        SELECT COALESCE(sum(unit_price * quantity), 0)
        FROM order_items WHERE order_id = COALESCE(NEW.order_id, OLD.order_id)
    ) WHERE id = COALESCE(NEW.order_id, OLD.order_id);
    RETURN NULL;
END $$ LANGUAGE plpgsql;

CREATE TRIGGER order_items_total AFTER INSERT OR UPDATE OR DELETE
    ON order_items FOR EACH ROW EXECUTE FUNCTION sync_order_total();
```

方式二有个明显的代价：批量插入 100 行明细会触发 100 次全表聚合，性能会崩。真实项目里通常用「应用层维护 + 每日对账」：对账任务按天扫出 `total_amount != sum(detail)` 的订单并告警修复。**对账是冗余字段的必要配套**，没有对账的冗余等于埋雷。

**三、跨边界只读副本**。微服务里订单服务冗余一份 `user_nickname` 用于列表展示，避免每次调用用户服务。这类冗余的规则是：**只读、单向同步、允许短暂不一致、禁止反向写回**。一旦它变成双向的，就等于把两个服务的写模型耦合在了一起。

**什么不该冗余**：可由 join 廉价得到的字段（用户邮箱）、会频繁变更且要求强一致的字段（库存数量）、以及"为了少写一个 join"而冗余的字段——后者是最常见的过度优化，代价是永久的一致性维护负担。

## 10. 建模验收清单

建完表，逐条过一遍。任何一条答不上来，都值得回头改：

- [ ] 每条业务不变量，都能指出它由哪一层（库约束 / 应用 / 领域对象）保证，且并发场景下仍然成立
- [ ] 所有唯一性都有对应的唯一索引（含软删除场景的部分唯一索引）
- [ ] 金额列是 `numeric`，且有 `currency` 列或明确的单币种约定
- [ ] 所有时间列是 `timestamptz`，代码里没有裸 `LocalDateTime` 入库
- [ ] 状态列是单列 + `CHECK`，没有用多个 boolean 表达互斥状态
- [ ] 每个会被 `WHERE` / `ORDER BY` 的列，都能说出它命中哪个索引（或明确接受全表扫描）
- [ ] 多对多关系用的是连接表，没有用 JSONB 数组存 id 列表
- [ ] 历史快照字段（价格、名称、地址）与引用字段（id）区分清楚，没有混用
- [ ] 每个冗余字段都有对账或同步机制，不是"到时候再说"
- [ ] 主键选型能说清理由（是否对外暴露、写入顺序性、是否需客户端生成）
- [ ] 所有约束都有名字（出问题时能一眼定位违反哪条业务规则）
- [ ] 表能回答「加一个什么样的需求会逼我改结构」，改的时候要不要停机

## 11. 自测

1. 一张表用 UUIDv4 做主键，写入 200 万行后索引比同数据的 `bigint` 主键大 35%。除了「16 字节 vs 8 字节」，还有什么原因？怎么验证？
2. 需求说「订单支持部分退款」，你在 `orders` 上加 `refunded_amount` 列。这个设计什么时候会不够用？请给出一个必须改成子表的场景。
3. `timestamp` 与 `timestamptz` 在「开发机 CST、容器 UTC」的环境下，分别会发生什么？为什么说「时区只活在展示层」？
4. 用户注销后邮箱无法重新注册。这是哪一层的问题？给出 SQL 修法，并说明为什么应用层判断解决不了。
5. 你有三个布尔列 `is_paid`、`is_shipped`、`is_refunded`。请说明它能表示多少种状态、其中多少种非法，以及改成单列状态后旧数据的迁移顺序。
6. 一张 1000 万行的表里 900 万行已软删除。写出三条受影响的查询类型，并给出一套「软删除 + 归档 + 审计」的分工方案。
