## 阶段目标

1. 说出 HikariCP 每个关键参数的作用，并根据「QPS × 平均持有时间」估算池大小，解释为什么池不是越大越好。

4. 用两个会话实测四种隔离级别的差异，解释 PG 的 MVCC 快照如何避免脏读、以及「可重复读」下仍可能出现的写偏差。
5. 解释 JPA 的脏检查、一级缓存、`flush` 时机，能定位并修复 N+1。
6. 设计一次零停机迁移：加列 → 双写 → 回填 → 切换读 → 删旧列，每步的兼容性与回滚点。
7. 在 JPA / MyBatis / `JdbcClient` 之间做选型，并说明理由能落到「团队维护成本」而不是「我喜欢」。

## 知识点地图

### 1. 连接池（02 册）

- **池大小的本质**：数据库能同时高效处理的活跃连接数远小于「应用线程数」。经验起点是 `CPU 核数 × 2 + 有效磁盘数`，再按实测调；**调大池通常只是把排队从应用挪到了数据库**。
- **`connectionTimeout` 是等连接的时间**，不是查询时间；「池满」时报的是它。`maxLifetime` 要小于数据库侧的连接空闲超时，否则会拿到已被服务端关闭的连接。
- **泄漏排查**：`leakDetectionThreshold` 打开后看日志里的获取堆栈；`HikariPool ... - Connection is not available` 出现前，通常已经有长时间未归还的连接。

### 2. SQL 与索引（03 册）

- **读计划先看三件事**：走了哪个索引（或全表扫描）、预估行数与实际行数差多少（统计信息是否过期）、有没有 `Sort`/`Hash` 落到磁盘。
- **索引失效的常见写法**：列上做函数/运算、隐式类型转换、前导通配 `LIKE '%x'`、`OR` 混合不同索引列、复合索引不满足最左前缀、`!=`/`NOT IN` 的选择性、`ORDER BY` 与索引顺序不一致。
- **覆盖索引**能消除回表，但会增加写放大与索引体积——索引是「用写换读」的交易，不是免费的。

### 3. 事务与隔离级别（04 册）

- **PG 的 MVCC**：读不阻塞写、写不阻塞读，快照在语句或事务开始时确定。`READ COMMITTED` 每条语句一个新快照，`REPEATABLE READ` 整个事务一个快照。
- **幻读与间隙锁**：MySQL InnoDB 在 RR 下用间隙锁防幻读，PG 用 SSI（可串行化快照隔离）在 `SERIALIZABLE` 下检测冲突并让事务回滚。**两个数据库的「RR」语义并不相同**，跨库迁移必踩。
- **死锁分析**：拿到两份事务的加锁顺序，倒推「谁先锁了 A 又等 B」；解法通常是统一加锁顺序、缩短事务、或改用乐观锁。

### 4. 持久化选型（05、06 册）

- **JPA 的收益**：对象图映射、脏检查自动生成 UPDATE、跨库方言。**代价**：SQL 不可见、批量能力弱、复杂查询要靠 JPQL/Criteria 写得更难读。
- **MyBatis 的收益**：SQL 完全可控、复杂报表友好。**代价**：映射维护成本、动态 SQL 可读性。**`JdbcClient`**（Spring 6.1+）适合少量高频、手写 SQL 的场景。
- **N+1 的三种修法**：`JOIN FETCH`/`EntityGraph`（一次查完，注意去重与分页冲突）、`@BatchSize`（批量补查）、投影 DTO（只取需要的列）。**先数 SQL 条数再优化**。
- **批量**：`saveAll` 不等于批量插入（默认逐条），要开 `hibernate.jdbc.batch_size` 与 `order_inserts`；大事务分批提交。
- **实体别用 `data class`**：`equals`/`hashCode` 基于全部字段会让 Set/缓存行为异常，`copy` 会造出游离对象。

### 5. Schema 演进（07 册）

- **兼容顺序**：加列（可空或带默认）→ 双写 → 回填 → 切读 → 删旧列。每一步都要求「旧版本代码仍能跑」，这样回滚才有意义。
- **改类型/加约束要在大表上评估锁**：PG 的 `ADD COLUMN ... DEFAULT` 在 11+ 是元数据操作，但 `ALTER TYPE` 会重写表；MySQL 的 `ALGORITHM=INPLACE` 并非万能。
- **Flyway 纪律**：脚本一旦合入主分支就不可修改，只能新增；失败迁移要有手工修复文档。
