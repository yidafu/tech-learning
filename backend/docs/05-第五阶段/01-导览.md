# 第五阶段导览：数据层——建模、SQL、连接池与持久化

> [返回：后端开发学习大纲](../后端开发学习大纲.md)
> 本文是第五阶段的入口。后端事故的高发区：表结构从第一天就埋错了约束、连接池打满、慢查询拖垮数据库、ORM 偷偷发了两百条 SQL。本阶段的要求是**能设计出"约束替你把住关"的表、能看懂执行计划、能证明隔离级别、能数清 SQL 条数**。

**建议时长**：2 周。数据库知识不要指望「看一遍记住」，全部结论都要求在你自己的 PG 实例上复现一遍。

## 阶段目标

1. 说出一张表的主键为什么选 `bigint`/UUIDv7/雪花，并用索引体积与写入顺序性解释代价，而不是「大家都这么用」。
2. 列出金额、时间、枚举、JSONB、文本长度这五类字段的选型铁律，并说出各自选错的线上后果。
3. 给出一条业务不变量，说明它该由库约束、应用服务还是领域对象保证，以及为什么并发下只有库约束可靠。
4. 说出 HikariCP 每个关键参数的作用，并根据「QPS × 平均持有时间」估算池大小，解释为什么池不是越大越好。
5. 独立读懂 `EXPLAIN ANALYZE` 输出：扫描方式、预估行数 vs 实际行数、循环次数、排序与临时文件。
6. 列出至少八种让索引失效的写法，并能在自己的表上验证。
7. 用两个会话实测四种隔离级别的差异，解释 PG 的 MVCC 快照如何避免脏读、以及「可重复读」下仍可能出现的写偏差。
8. 解释 JPA 的脏检查、一级缓存、`flush` 时机，能定位并修复 N+1。
9. 设计一次零停机迁移：加列 → 双写 → 回填 → 切换读 → 删旧列，每步的兼容性与回滚点。
10. 在 JPA / MyBatis / `JdbcClient` 之间做选型，并说明理由能落到「团队维护成本」而不是「我喜欢」。

## 知识点地图

### 1. 数据建模（03 册）

- **判据不是范式，是三件事**：哪条不变量必须由库保证、主要查询能否走索引、加一个字段要不要改结构。「按页面建表」把成本推给未来，「按查询建表」把成本推给扩展性，「按领域建表」把成本推给当下的设计时间——选哪个取决于这张表要活多久、变更频率多高。
- **主键是三重取舍**：存储顺序性、对外可猜测性、生成位置。随机 UUID 会让 B-tree 叶子页密度掉到 60%~70%（顺序主键约 90%），代价是索引体积与随机写 IO；UUIDv7 用时间前缀同时拿到了「不可猜」和「顺序写」。
- **类型铁律**：金额 `numeric` 不用浮点；时间 `timestamptz` 不用 `timestamp`（时区只活在展示层）；状态用单列 + `CHECK` 而非多个 boolean（n 个布尔有 2^n 组合、大部分非法）；JSONB 只给「结构不确定且不按子字段查询」的字段；`varchar(n)` 的 n 是约束不是性能。
- **约束才是领域模型**：应用层校验在并发下必然失守（读-改-写窗口），唯一索引既是兜底也是幂等的实现手段；列间一致性（`refunded <= paid`）必须落成 `CHECK`；约束一律具名。
- **软删除的四个代价**：唯一约束失效（用部分唯一索引修）、每条查询都要带过滤（漏一处就是静默 bug）、索引膨胀、真正的物理删除需求仍在。
- **树形四种做法**：邻接表（默认，递归 CTE）、路径枚举（读极多）、嵌套集（只读目录）、闭包表（深度大且读写都频繁）。递归 CTE 必须配深度上限与 `parent_id` 索引。
- **领域模型 ≠ 表结构**：值对象可内联成多列、拆表、JSONB 或共享字典；**聚合边界决定事务边界**，把「必须一起改」的数据拆到两个服务，不变量就再也没地方保证。
- **冗余的三类合理场景**：历史快照（永不回填）、聚合缓存（必须配对账）、跨边界只读副本（单向、禁反向写）。

### 2. 连接池（02 册）

- **池大小的本质**：数据库能同时高效处理的活跃连接数远小于「应用线程数」。经验起点是 `CPU 核数 × 2 + 有效磁盘数`，再按实测调；**调大池通常只是把排队从应用挪到了数据库**。
- **`connectionTimeout` 是等连接的时间**，不是查询时间；「池满」时报的是它。`maxLifetime` 要小于数据库侧的连接空闲超时，否则会拿到已被服务端关闭的连接。
- **泄漏排查**：`leakDetectionThreshold` 打开后看日志里的获取堆栈；`HikariPool ... - Connection is not available` 出现前，通常已经有长时间未归还的连接。

### 3. SQL 与索引（04 册）

- **读计划先看三件事**：走了哪个索引（或全表扫描）、预估行数与实际行数差多少（统计信息是否过期）、有没有 `Sort`/`Hash` 落到磁盘。
- **索引失效的常见写法**：列上做函数/运算、隐式类型转换、前导通配 `LIKE '%x'`、`OR` 混合不同索引列、复合索引不满足最左前缀、`!=`/`NOT IN` 的选择性、`ORDER BY` 与索引顺序不一致。
- **覆盖索引**能消除回表，但会增加写放大与索引体积——索引是「用写换读」的交易，不是免费的。

### 4. 事务与隔离级别（05 册）

- **PG 的 MVCC**：读不阻塞写、写不阻塞读，快照在语句或事务开始时确定。`READ COMMITTED` 每条语句一个新快照，`REPEATABLE READ` 整个事务一个快照。
- **幻读与间隙锁**：MySQL InnoDB 在 RR 下用间隙锁防幻读，PG 用 SSI（可串行化快照隔离）在 `SERIALIZABLE` 下检测冲突并让事务回滚。**两个数据库的「RR」语义并不相同**，跨库迁移必踩。
- **死锁分析**：拿到两份事务的加锁顺序，倒推「谁先锁了 A 又等 B」；解法通常是统一加锁顺序、缩短事务、或改用乐观锁。

### 5. 持久化选型（06、07 册）

- **JPA 的收益**：对象图映射、脏检查自动生成 UPDATE、跨库方言。**代价**：SQL 不可见、批量能力弱、复杂查询要靠 JPQL/Criteria 写得更难读。
- **MyBatis 的收益**：SQL 完全可控、复杂报表友好。**代价**：映射维护成本、动态 SQL 可读性。**`JdbcClient`**（Spring 6.1+）适合少量高频、手写 SQL 的场景。
- **N+1 的三种修法**：`JOIN FETCH`/`EntityGraph`（一次查完，注意去重与分页冲突）、`@BatchSize`（批量补查）、投影 DTO（只取需要的列）。**先数 SQL 条数再优化**。
- **批量**：`saveAll` 不等于批量插入（默认逐条），要开 `hibernate.jdbc.batch_size` 与 `order_inserts`；大事务分批提交。
- **实体别用 `data class`**：`equals`/`hashCode` 基于全部字段会让 Set/缓存行为异常，`copy` 会造出游离对象。

### 6. Schema 演进（08 册）

- **兼容顺序**：加列（可空或带默认）→ 双写 → 回填 → 切读 → 删旧列。每一步都要求「旧版本代码仍能跑」，这样回滚才有意义。
- **改类型/加约束要在大表上评估锁**：PG 的 `ADD COLUMN ... DEFAULT` 在 11+ 是元数据操作，但 `ALTER TYPE` 会重写表；MySQL 的 `ALGORITHM=INPLACE` 并非万能。
- **Flyway 纪律**：脚本一旦合入主分支就不可修改，只能新增；失败迁移要有手工修复文档。

## 阶段实践

在自己的表上做四个实验，把数字记进账本：

1. 为毕业项目设计一版表结构（订单/短链/预约任选），逐条写下「这条约束为什么必须在库里」，再用并发脚本试着绕过它；
2. 造 100 万行数据，用「函数包裹列」和「前导通配」各写一条查询，对比执行计划与耗时；
3. 用两个 psql 会话实测 `READ COMMITTED` 与 `REPEATABLE READ` 下的不可重复读；
4. 用 JPA 查一个「订单 + 明细」列表，打开 SQL 日志数条数，改成 `EntityGraph` 后再数一次。
