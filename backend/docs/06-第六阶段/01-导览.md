# 第六阶段导览：事务、锁与一致性

> [返回：后端开发学习大纲](../后端开发学习大纲.md)
> 本文是第六阶段的入口。`@Transactional` 是被误用最多的 Spring 注解：加上了不等于有事务，传播用错等于没事务，异常被吞等于白做。本阶段先把失效现场穷尽，再往跨服务一致性上走。

## 知识点地图

### 1. 传播行为与失效现场（02 册）

- **最常用的三个**：`REQUIRED`（默认，有则加入、无则新建）、`REQUIRES_NEW`（挂起外层、独立提交，用于「日志必须落库」）、`NESTED`（保存点，回滚不影响外层，仅 JDBC 支持）。其余四个（`SUPPORTS`、`NOT_SUPPORTED`、`MANDATORY`、`NEVER`）多数是「明确表达意图」而非实际使用。
- **六种失效现场**：同类自调用（绕代理）、方法非 `public`、异常被 `catch` 未重抛、抛的是受检异常且未配 `rollbackFor`、类未被 Spring 管理（`new` 出来的）、多线程/异步里调用（事务绑定线程）。
- **只读事务的意义**：`readOnly=true` 让 Hibernate 跳过脏检查、部分驱动走只读连接——这是性能优化，不是安全保证。

### 2. 事务边界（03 册）

- **边界应该包住「一组必须同时成立的数据变更」**，而不是「一个 Service 方法」。边界过大导致长事务（锁持有久、连接占用久、回滚代价大）。
- **事务内禁止的操作**：远程调用、发消息、写文件、读大结果集。远程慢 → 连接被占；远程失败 → 本地白回滚；消息发出后回滚 → 数据不一致。
- **正确姿势**：事务内只改库，事务提交后（`TransactionSynchronization#afterCommit` 或事件监听 `@TransactionalEventListener`）再发消息/调下游。注意「提交后发消息」仍有失败可能，所以配 Outbox 或重试。
- **事务与重试**：重试必须放在事务外层，否则重试的是「同一个已标记回滚的事务」，必然失败。

### 3. 锁（04 册）

- **乐观锁**：读时拿 version，写时 `WHERE version = ?`，影响行数为 0 就重试或报冲突。适合冲突率低的场景，冲突率高时重试风暴。
- **悲观锁**：`SELECT ... FOR UPDATE` 持锁到事务结束。适合「一定要成功且冲突频繁」的场景，代价是吞吐与死锁风险。
- **唯一索引是最后一道防线**：所有「防重复」逻辑都应有唯一约束兜底，因为应用层判断和插入之间永远有窗口。
- **热点行**：同一行被高频更新时，任何锁都会变成串行点；解法是拆分计数行、异步合并更新、或用队列削峰。

### 4. 幂等（05 册）

- **重复请求的六个来源**：用户重复点击、网关超时重试、客户端重试、消息重复投递、定时任务多实例、回滚重放。
- **幂等键设计**：由客户端生成（如 UUID）并随请求发送，或用「业务唯一标识 + 操作类型」拼装；服务端存「键 → 处理结果」，用唯一索引保证并发同键只有一个成功。
- **三种实现层次**：DB 唯一约束（最可靠）→ 去重表/Redis `SETNX`（需要过期与结果存储）→ 状态机约束（`WHERE status = 'PENDING'`，天然幂等且能防非法流转）。

### 5. 跨服务一致性（06 册）

- **Outbox（本地消息表）**：业务变更与「待发消息」在同一事务写入，独立投递器扫表发送并标记，实现「至少一次」。消费侧必须幂等。
- **Saga**：把长事务拆成多个本地事务 + 补偿动作。编排式（一个协调者）比协同式（各服务自发）好排查；补偿必须幂等，且要考虑「补偿也失败」的人工兜底与对账。
- **TCC**：Try 预留、Confirm 确认、Cancel 释放。成本最高——要求每个参与方实现三个接口且都幂等，只在「资金/库存」这类强一致场景值得。
- **分布式锁**：只解决「互斥」，不解决「一致性」。Redlock 的争议在于时钟漂移下的安全性；工程上更常见的是「Redis 锁 + 数据库唯一约束兜底 + 对账」。
