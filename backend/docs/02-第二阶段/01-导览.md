# 第二阶段导览：Kotlin 服务端工程化

> [返回：后端开发学习大纲](../后端开发学习大纲.md)
> 本文是第二阶段的入口。Kotlin 在服务端不是「Java 加语法糖」——它的类型系统能替你挡掉一类 bug，但它的语法糖也能让代码变得没人敢改。本阶段的目标是划出这条线。

**建议时长**：1.5 周。语言特性本身不难，难的是「什么时候不该用」。

## 分册计划

| 分册 | 内容要点 |

| 03-类型系统进阶 | `value class` 零开销包装、`sealed` + 穷尽 `when`、`inline` 与契约、泛型变型 |
| 04-扩展-委托与DSL的边界 | 扩展函数的静态解析、`by lazy`/`observable`、类型安全 DSL、DSL 滥用的代价 |
| 05-协程基础 | `suspend` 本质、结构化并发、取消传播、异常处理、与线程池的关系 |

## 阶段目标

1. 用类型把「非法状态」变成不可编译：金额、ID、状态机都用值类或密封类表达，而不是 `String` + `Long`。
2. 解释 `sealed interface` + 穷尽 `when` 怎么替代 `if (status == 3)` 这类散落判断，并在新增分支时让编译器报错。
3. 说清扩展函数为什么「不能多态」，以及它在 Spring 里作为工具方法的合理边界。
4. 写出一个正确的 `suspend` 函数，讲清它的编译产物（状态机 + Continuation）以及为什么不能在 `suspend` 里做阻塞 IO。
5. 解释 Spring 为什么要给 Kotlin 类加 `allopen`/`noarg` 插件，不加会发生什么（`@Configuration` 类被 final 挡住、JPA 实体无默认构造）。
6. 用 version catalog 统一依赖版本，并说出构建缓存命中的三个前提。
7. 用 detekt 规则把团队的 Kotlin 规约固化进 CI。

## 知识点地图

### 1. 用类型表达约束（02、03 册）

- **裸类型的代价**：`fun transfer(from: String, to: String, amount: Long)` 三个参数可以任意互换而不报错。换成 `AccountId`、`Money` 值类后，编译器第一次成了队友。
- **`value class` 的关键性质**：只有单个属性、编译后大多擦除为底层类型，因此没有装箱开销——这是它能用在热路径上的原因，但也不能有多个属性、不能当 `data class` 用。
- **密封类做状态机**：`sealed interface OrderState` 的每个实现携带自己的数据（已支付带 `paidAt`，已取消带 `reason`），`when` 分支穷尽，新增状态时所有未处理处直接编译失败。
- **`copy` 的陷阱**：`data class` 的 `copy` 是浅拷贝，内部可变集合还是同一个引用；DTO 里出现 `MutableList` 基本等于埋雷。

### 2. 语法糖的边界（04 册）

- **扩展函数是静态解析**：它编译成静态方法，第一个参数是接收者，因此不参与多态、不能被覆写、在 Java 侧看起来像普通静态工具方法。适合做「给已有类型加只读便利方法」，不适合做业务抽象。
- **委托属性**：`by lazy` 适合重量级单例初始化；`Delegates.observable` 在配置类里很顺手，但在领域对象里往往意味着「悄悄藏了副作用」。
- **类型安全 DSL**：Gradle Kotlin DSL、Spring 的 `router { }`、Security 的 `http { }` 都是靠「接收者 + `@DslMarker`」实现的。写 DSL 的门槛不高，**读得懂的门槛很高**——团队里没有共识就不要造。

### 3. 协程（05 册）

- **`suspend` 不是线程切换**：它只是把函数编译成可挂起的状态机；真正切线程的是 `Dispatcher`。在 `Dispatchers.IO` 上跑 CPU 密集任务和在主线程跑一样糟。
- **结构化并发**：`coroutineScope` 保证父协程不会在子协程未完成时结束，任一子协程失败会取消兄弟协程——这是「不会泄漏线程」的根据。
- **取消是协作式的**：阻塞调用（JDBC、`Thread.sleep`）不会响应取消，必须靠超时或不阻塞的 API；`withTimeout` 对阻塞代码无效。

### 4. Spring 的接缝（06 册）

- **为什么需要 `allopen`**：Kotlin 类默认 final，而 Spring 的 CGLIB 代理、`@Configuration` 的增强都要求可继承。`kotlin-spring` 插件按注解自动 open，别手工一个个加 `open`。
- **`noarg` 与 JPA**：JPA 要求实体有无参构造，`kotlin-jpa` 插件自动生成；但**不要给实体用 `data class`**——`equals`/`hashCode` 基于全部字段、`copy` 会产生游离对象，两者都会让 Hibernate 的脏检查出错。
- **平台类型**：调用 Java 方法拿到的是 `String!`，Kotlin 不检查可空性。在边界处（第三方 SDK）要显式声明类型，别让 `!` 一路传进业务层。

### 5. 构建（07 册）

- **version catalog**（`libs.versions.toml`）把版本收在一处，多模块共享；配合 Boot 的 BOM，绝大多数依赖不必写版本。
- **构建缓存的三个前提**：任务输入可声明、输出可复现（无时间戳）、不读环境中的隐式状态。命中率低通常是因为代码里读了 `LocalDateTime.now()` 或随机数。
- **convention plugin** 比 `buildSrc` 更适合多模块：可发布、可版本化、IDE 支持更好。

## 阶段实践

把第一阶段骨架里「String 满天飞」的接口重构一遍：

1. 金额 → `value class Money(val cents: Long)`，账号 → `value class AccountId(val value: UUID)`；
2. 订单状态 → `sealed interface`，所有 `when` 改为穷尽；
3. 加 detekt + ktlint 到 CI，规则集写进仓库；
4. 记录重构前后「编译期能发现的错误类型」清单——这是本阶段唯一值得量化的产出。

## 自测

1. `value class` 编译后是什么？为什么它不能有两个属性？
2. 扩展函数为什么无法实现多态？它和成员函数在解析时机上有什么不同？
3. 一个 `suspend` 函数里调用了 `Thread.sleep(1000)`，`withTimeout(500)` 能中断它吗？为什么？
4. 为什么 JPA 实体不能用 `data class`？至少说出两个理由。
5. 不加 `allopen` 插件时，`@Configuration` 类会发生什么？
6. 你的构建缓存命中率只有 30%，列出三个排查方向。
