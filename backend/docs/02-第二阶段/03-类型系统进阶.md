# 03. 类型系统进阶

> [← 第二阶段导览](01-导览.md) · 上一册把「空」和「可变」赶出了类型；这一册让类型多背两个责任：**表达单位与身份**（`value class`，运行期零开销），以及**把非法分支穷尽**（`sealed` + 穷尽 `when`，新增一种状态时编译器替你列出所有要改的地方）。

## 1. `value class`：擦除之后还剩什么

`value class` 只有一个属性，编译器把它擦除成那个属性的类型。`AccountId(val value: String)` 在字节码里就是一个 `String`，不是「包着 String 的对象」。

```kotlin
@JvmInline
value class AccountId(val value: String) {
    init { require(value.isNotBlank()) { "账号不能为空" } }
    fun masked(): String = value.take(2) + "****"
}

// 编译后大致等价于：
// final class AccountId {
//     static String constructor-impl(String value) { ...require...; return value; }
//     static String masked-impl(String value) { ... }
//     static String toString-impl(String value) { ... }
// }
```

三个细节决定了它能不能用在热路径上：

1. **字段被擦除**：方法签名里的 `AccountId` 变成 `String`，没有对象头、没有额外指针、没有一次分配；
2. **方法名被 mangle**：`masked-impl`、`getValue-<hash>` 这类后缀（具体形式随版本与签名变化）是 JVM 上避免与底层类型方法签名冲突的手段。优点是安全，缺点是**反射按名字找方法的框架会全部失手**；
3. **装箱是按需发生的**：只有擦除表达不了的时候才 `box-impl` 成对象。

第二点是本册最容易踩的坑：Spring 的 `@PathVariable`、Bean Validation、Jackson、Hibernate 全靠反射拿方法或构造器，遇到 mangle 后的名字就报「找不到属性」或「没有可用构造器」——错误信息里看不出跟 `value class` 有关。

**为什么只允许一个属性**：擦除后必须有一种明确的底层表示。两个属性就没法选「擦成谁」，`equals` 语义也会变成「按哪个字段比」的争论。单属性把「包装」限制成「同一份数据的类型化视图」，语义才干净。

### 1.1 什么时候会装箱

| 场景 | 是否装箱 | 原因 |
|---|---|---|
| `fun f(id: AccountId)` 直接传参 | 否 | 签名擦除为底层类型 |
| `val id: AccountId?` | 是 | null 需要与「有值」区分，底层类型表达不了 |
| `List<AccountId>` / `Map<K, AccountId>` | 是 | 泛型参数必须是引用类型 |
| `Array<AccountId>` | 是 | 数组元素是对象引用 |
| 把 `AccountId` 赋给 `Any` 或某个接口 | 是 | 需要对象身份 |
| `inline` 函数的泛型参数（`T` 被推断为 `AccountId`） | 是 | 泛型参数擦除为 `Object`，Kotlin 不做单态化 |
| `equals` / `hashCode` / `toString` 的调用 | 视情况 | 编译器可能生成 `box-impl` 再调 |

结论：**「零开销」是有条件的**。值类当参数、当局部变量、当不可空字段是零开销；一旦可空、进集合、进泛型，就和普通包装类一样。别拿「value class 无开销」去解释一段把 `List<AccountId>` 当主数据结构的代码。

## 2. `value class` 与框架：三处必踩的冲突

### 2.1 JPA / Hibernate

实体是反射驱动的：它需要一个可调用的无参构造、需要按名字找 getter/setter、需要知道属性的 Java 类型。`value class` 三样都不给。表现为启动期 `Could not determine recommended JdbcType` 或运行期「找不到属性 `accountId`」。

三个稳妥方案，按推荐度排序：

| 方案 | 做法 | 代价 |
|---|---|---|
| 实体存底层类型（推荐） | 实体字段 `val accountId: String`，Repository 边界 `AccountId(entity.accountId)` | 转换点集中，领域层仍是值对象 |
| `AttributeConverter` | `@Converter` 转 `AccountId <-> String`，属性上 `@Convert` | 需要显式标注；`autoApply` 受泛型擦除影响，未必生效 |
| `@Embeddable` 普通类 | 用普通类（非 value class）做可嵌入 ID | 有对象分配，失去零开销 |

第一种在工程上最稳：**值对象属于领域层，实体属于持久化层，两者在仓储边界转换**。这跟「DTO 不直接当实体」是同一条边界纪律。

### 2.2 Jackson 3

默认把 `AccountId` 当一个普通对象，序列化成 `{"value":"acc-1"}`。要让它在 JSON 里就是一个字符串：

```kotlin
@JvmInline
value class AccountId(val value: String) {
    @get:JsonValue
    val raw: String get() = value
}
```

`@get:JsonValue` 告诉 Jackson 用这个属性作为整个值的表示。反序列化方向还需要一个能接收单参数的构造入口，Jackson 3 对 Kotlin 值类的支持依赖 `jackson-module-kotlin` 的版本，最保险的是配一个 `ValueInstantiator` 或自定义 `Deserializer`。**接口契约里出现值类时，先写一个序列化往返测试**，比读文档快。

### 2.3 Spring MVC 与校验

`@PathVariable id: AccountId` 需要 `Converter<String, AccountId>`；`@Valid` 对值类字段上的约束注解不会自动生效，因为约束通常写在底层类型上。两个做法：注册全局 `Converter`/`Formatter`，以及在控制器边界就用 DTO（里面是裸类型 + 校验注解），进服务层再转值对象。**校验留在边界，值对象负责不变量**，两边不重叠。

## 3. `sealed`：把「新增一种状态」变成编译错误

```kotlin
sealed interface PaymentState {
    data object Pending : PaymentState
    data class Paid(val paidAt: Instant, val transactionId: String) : PaymentState
    data class Failed(val reason: String, val retryable: Boolean) : PaymentState
    data class Refunded(val refundedAt: Instant, val amount: Money) : PaymentState
}

fun PaymentState.describe(): String = when (this) {
    PaymentState.Pending -> "待支付"
    is PaymentState.Paid -> "已支付于 $paidAt，流水 $transactionId"
    is PaymentState.Failed -> if (retryable) "可重试失败：$reason" else "终态失败：$reason"
    is PaymentState.Refunded -> "已退款 $amount"
}
```

从 Kotlin 1.5 起，`sealed` 的子类型必须与声明**同模块同包**（不再要求同文件）；子类型可以散在多个文件里，但仍然锁在一个模块内。字节码层面 sealed class 编译成「构造器私有的抽象类」，新版本在 JVM 17+ 目标下还会写出 `PermittedSubclasses` 属性，与 Java 的 sealed 对齐——但 Kotlin 的约束更严（同包同模块），比 Java 的 `permits` 更难被外部扩展。

**为什么它比 `enum` 强**：枚举的每个常量共享同一组字段，`Paid` 的 `paidAt` 和 `Failed` 的 `reason` 只能都塞进一个大对象、大部分为 null。`sealed` 的每个子类型携带自己的数据，`when` 分支里 `is Paid` 之后直接访问 `paidAt`，不需要判空也不需要强转。

**为什么它比「`status: Int` + 散落 if」强**：穷尽 `when` 在表达式位置必须覆盖全部子类型，Kotlin 1.7 起连语句位置的非穷尽 `when` 也是错误。新增 `PaymentState.ChargedBack` 时，所有没处理它的 `when` 立刻编译失败——**「新增状态要改哪些地方」从靠人 review 变成编译器列清单**。

四条纪律，否则这套机制会失效：

1. **不要写 `else`**。一个 `else` 就把穷尽性检查关掉了，新增分支时它静默吞掉。用 `is` 分支列全；
2. **不要在 `when` 里写副作用**。穷尽 `when` 的价值是「映射表」，一旦掺入更新数据库、发消息，它就不再可穷尽地被测试；
3. **不要把 sealed 层级当公共 API 发布**。新增子类型对已编译的调用方是二进制不兼容——老的 `when` 编译时是全的，运行时遇到新类型会抛 `NoWhenBranchMatchedException`；
4. **层级要浅**。两三层足够；嵌套密封类配 `@DslMarker` 之外的场景，读起来会迅速失控。

## 4. `inline` 与契约：让编译器承认「这个函数返回就代表非空」

`inline` 的第一个作用是消除 lambda 的对象分配与调用开销，第二个作用常常被忽略：**它让编译器在调用点看得见函数体**，于是契约（contract）能影响类型收窄。

```kotlin
@OptIn(ExperimentalContracts::class)
inline fun isValid(input: String?): Boolean {
    contract { returns() implies (input != null) }
    return input != null && input.isNotBlank()
}

fun handle(raw: String?) {
    if (!isValid(raw)) return
    println(raw.length)   // 编译通过：契约告诉编译器「返回 true 则 raw 非空」
}
```

这里必须用 `inline`：契约要求编译器在调用点看到函数体。注意契约写的是「返回 true 意味着 `input != null`」——它是在**给调用方补充编译器推不出来的信息**，而不是替代函数里的判空。如果把返回类型写成非空（比如 `orThrow(): T`），契约就是多余的：返回类型本身已经保证了非空。

契约必须写在函数体第一行，且目前能表达的很少：`returns() implies (条件)`、`returnsNotNull()`、`callsInPlace(block, EXACTLY_ONCE)`。它表达不了「抛什么异常」「参数之间的大小关系」，所以别指望用它替代运行时校验。

**代价与边界**：

- 字节码膨胀：`inline` 在每个调用点展开函数体。一个 30 行的 `inline` 函数被调 200 次，方法体积会明显变大，JIT 反而更难优化；
- 不能内联虚调用：`open`/接口方法即使标 `inline` 也只会在编译期被当作普通调用（编译器会给警告）；
- `public inline` 不能访问 `private` 成员，除非给成员加 `@PublishedApi internal`——这是 API 设计上的实质约束；
- 调试体验变差：栈里是调用者的行号，断点会落在展开后的位置；
- 高阶函数加 `crossinline`/`noinline` 之后，语义开始需要查文档才能确认，团队里能读懂的人会骤减。

判断标准：**只在「库代码 + 高频 + 需要非局部返回或契约」三者同时成立时用 `inline`**。业务代码里为了「省一个 lambda 对象」而 `inline`，收益远小于可读性损失。

## 5. 泛型变型：`in`/`out` 与 Java 通配符的对应

Kotlin 把变型写在**声明处**，Java 写在**使用处**。两者描述的是同一件事：`List<String>` 能不能当 `List<Any>` 用。

```kotlin
interface Producer<out T> { fun produce(): T }      // 只产出 → 协变，≈ ? extends T
interface Consumer<in T> { fun consume(t: T) }      // 只消费 → 逆变，≈ ? super T

fun copyInto(from: List<Number>, to: MutableList<in Number>) {
    from.forEach { to.add(it) }
}

val strings: List<String> = listOf("a")
val anys: List<Any> = strings          // 协变：List<out E> 声明处已标
// val mutable: MutableList<Any> = mutableListOf<String>()  // 不变，编译错误
```

| Kotlin | Java 等价 | 方向 | 直觉 |
|---|---|---|---|
| `List<out T>` | `List<? extends T>` | 协变 | 只能读出来，读出的是 `T` 或子类 |
| `Comparator<in T>` | `Comparator<? super T>` | 逆变 | 只能喂进去，喂 `T` 或父类都行 |
| `MutableList<T>` | `List<T>` | 不变 | 又读又写，两个方向都不安全 |
| `List<*>`（星投影） | `List<?>` | — | 只能读成 `Any?`，不能写 |
| `List<Any?>` | `List<Object>` | 不变 | 明确装的是任意可空值，与星投影不同 |

PECS 口诀在这里依然适用：**Producer Extends, Consumer Super**——只读的用 `out`（生产者），只写的用 `in`（消费者），又读又写就别变型。

两个容易忽略的点：

- **`List` 的 `contains` 用了 `@UnsafeVariance`**：`List<out E>` 里 `contains(element: E)` 把 `E` 放在参数位置，本来违反协变规则，标准库用 `@UnsafeVariance` 显式压掉检查——因为 `contains` 只做相等比较，不写入。你自己写这类方法时要能说清「为什么这里不安全但仍正确」，而不是随手抄注解；
- **星投影不等于 `Any?`**：`List<*>` 你读出来是 `Any?`，但你不知道元素类型；`List<Any?>` 明确声明了元素是任意可空值。前者表达「我不关心/不知道」，后者表达「我知道它是任意类型」。

## 6. 把错误模型写成 `sealed interface`

这是本册最实用的一节：错误分类散落在 `if (code == 4001)` 里，是服务端最难维护的代码之一。换成 sealed 之后，**新增一种错误，所有映射点编译失败**。

```kotlin
sealed interface DomainError {
    val code: String

    data class NotFound(val resource: String, val id: String) : DomainError {
        override val code = "RESOURCE_NOT_FOUND"
    }
    data class Validation(val field: String, val reason: String) : DomainError {
        override val code = "VALIDATION_FAILED"
    }
    data class Conflict(val resource: String, val currentState: String) : DomainError {
        override val code = "STATE_CONFLICT"
    }
    data class Upstream(val service: String, val retryable: Boolean) : DomainError {
        override val code = "UPSTREAM_FAILED"
    }
    data object Forbidden : DomainError {
        override val code = "FORBIDDEN"
    }
}

fun DomainError.toStatus(): Int = when (this) {
    is DomainError.NotFound -> 404
    is DomainError.Validation -> 422
    is DomainError.Conflict -> 409
    is DomainError.Upstream -> if (retryable) 503 else 502
    DomainError.Forbidden -> 403
}
```

| 子类型 | HTTP | 该不该让客户端重试 | 备注 |
|---|---|---|---|
| `NotFound` | 404 | 否 | 也可能是越权，注意别泄露资源存在性 |
| `Validation` | 422（或 400） | 否 | 字段级信息放 `errors[]`，别只给一句话 |
| `Conflict` | 409 | 否（改状态后重发） | 乐观锁失败、状态机非法迁移 |
| `Upstream`（可重试） | 503 + `Retry-After` | 是 | 下游超时/过载 |
| `Upstream`（不可重试） | 502 | 否 | 下游返回了非法响应 |
| `Forbidden` | 403 | 否 | 已认证但无权限；未认证是 401，不属于领域错误 |

**为什么用 sealed 而不是枚举 + 消息**：枚举区分不了「哪个字段校验失败」，只能再挂一个 `Map<String, String>`；sealed 让每种错误携带恰好它需要的数据，`when` 里直接 `is Validation` 拿到 `field`，不需要 `as` 也不需要判空。

**为什么映射函数要写成一个 `when`**：HTTP 状态码是接口契约的一部分，必须集中。散在各个 `@ExceptionHandler` 里，新增错误时总有一处忘改，客户端就会收到 500——而 500 在监控里是「服务端故障」，会误导排障方向。

三个坑：

1. **别把 `Throwable` 塞进错误模型**。`data class Upstream(val cause: Throwable)` 一旦被序列化（日志、消息体、错误响应）就会拖出整条栈甚至循环引用。内部错误与线上错误要分开：领域层留 `cause`，出网关前映射成 `ProblemDetail`；
2. **不要把所有错误塞进一个 sealed 接口**。20 个子类型时 `when` 就不可读了，按边界分层（领域错误、鉴权错误、基础设施错误各一个）比一层到底好；
3. **要跨模块共享，就把整个层级搬进共享模块**。子类型必须与接口同模块同包，所以正确做法是「接口 + 全部子类型」一起放进一个共享模块的同一个包里，而不是每个服务各写一份——后者会让 `when` 的穷尽性在跨服务时立刻失效。
