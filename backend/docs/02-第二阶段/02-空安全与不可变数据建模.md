# 02. 空安全与不可变数据建模

> [← 第二阶段导览](01-导览.md) · Kotlin 的空安全不是「多了个问号」，而是把可空性写进类型；但这份保证在 Java 边界、`!!`、`data class` 的浅拷贝和只读集合接口上各有缺口，本册把四个缺口逐个堵上，最后用一次「裸 `String` 换值对象」的重构收口。

## 1. 可空性是类型的一部分，不是注解

Java 的 `@Nullable` 是给 IDE 和静态分析工具看的，`javac` 不会因为你把 null 传给非空参数而报错。Kotlin 把可空性做成了类型系统的一等公民：`String` 与 `String?` 是两个不同的类型，前者是后者的子类型，反向赋值需要显式检查。这个差别带来的不是「少写几个判空」，而是**编译通过的含义变了**——从「语法正确」变成「在这条路径上，null 进不来」。

编译器在三个位置下手：

1. 赋值与传参处检查：把 `String?` 传给 `String` 参数直接编译失败；
2. `if (x != null)` 之后做 smart cast，把 `x` 的类型在流敏感分析里收窄为 `String`；
3. 在 public 函数入口插入 `Intrinsics.checkNotNullParameter`，字节码里给参数挂 `@NotNull`，让 Java 调用方也被运行时兜住。

```kotlin
data class User(val id: Long, val nickname: String?)

fun greet(user: User): String =
    if (user.nickname != null) {
        "hi, ${user.nickname.uppercase()}"   // smart cast：这里 nickname 是 String
    } else {
        "hi, anonymous"
    }
```

**为什么值得当真**：`Intrinsics.checkNotNullParameter` 抛的是 `NullPointerException`，且消息里带参数名（`Parameter specified as non-null is null: method ...`）。它把「业务层深处某个字段是 null」变成「边界处第一个参数就是 null」，定位时间从小时级降到分钟级。

**坑在于表达「没有值」的方式太多**。同一个「查不到用户」，有人返回 `null`，有人抛异常，有人返回空对象，有人返回 `Result`。调用方只能猜：

| 表达方式 | 语义 | 适合 | 不适合 |
|---|---|---|---|
| `T?` | 值可能不存在，是正常分支 | 查询单个可缺省资源 | 需要携带「为什么没有」时 |
| `Result<T>` / `Either` | 失败是值，带原因 | 可预期的业务失败 | 失败种类多时类型会爆炸 |
| `sealed interface` 结果 | 每种失败一个子类型 | 需要穷尽处理的错误模型（03 册） | 只有成功/失败两态的小函数 |
| 抛异常 | 意外，调用方不该继续 | 编程错误、基础设施故障 | 正常的「查不到」 |

规矩只有一条：**一个模块内对同一类「没有」只用一种表达**，并在 KDoc 里写清。混用是空安全在团队层面失效的头号原因——编译器挡得住类型，挡不住语义分歧。

## 2. 平台类型：Java 把空指针送进业务层的那道门

调用没有可空注解的 Java 方法时，Kotlin 看到的是**平台类型**（flexible type），IDE 里显示为 `String!`。它的行为很别扭：既能赋给 `String`，也能赋给 `String?`，两边都不检查。

```kotlin
// Java 侧：public static String findName(long id)   // 文档说「可能返回 null」，但没注解
val name: String = LegacyUserApi.findName(1)  // 编译通过，编译器没插检查
println(name.length)                          // NPE，栈顶就停在这一行业务代码
```

**为什么危险**：NPE 的栈帧落在业务层，不在边界。排查时人会反复怀疑自己的判空逻辑写错了，而真正的问题是「以为这个方法不会返回 null」。更糟的是它会在 `data class` 构造器里爆发——异常指向构造器，而脏数据来自三层之外的 SDK。

切断这道门有四招，按成本从低到高：

1. **边界适配层**：所有第三方 SDK 只在一个文件里被调用，返回值显式标注 `String?`，或立刻 `requireNotNull(...) { "..." }` 转成带上下文的异常；
2. **`Objects.requireNonNull(x, "userName from LegacyApi")`**：让失败发生在边界那一帧，栈里能看见是哪个调用点；
3. **给依赖加 JSpecify 注解**：包级 `@NullMarked` 加逐点 `@Nullable`，K2 编译器能识别并把平台类型收窄成有契约的类型，`String!` 退化成 `String` 或 `String?`；
4. **测试用 null 喂边界**：多数人只测 happy path，于是平台类型的第一个受害者永远是生产环境。

| Java 侧声明 | Kotlin 看到的类型 | 编译期检查 | 建议动作 |
|---|---|---|---|
| `String`（无注解） | `String!` | 无 | 适配层显式标注 + 边界断言 |
| `@Nullable String` | `String?` | 有 | 直接按可空处理 |
| `@NotNull String` | `String` | 有 | 信任，但仍建议测一次 |
| `Optional<String>` | `Optional<String>` | 有 | 在边界转成 `String?`，别把 Optional 传进业务层 |
| `@NullMarked` 包下的 `String` | `String` | 有 | 可信契约，可去掉冗余判空 |

最后一行是本册最省的收益：给一个老 SDK 加 `package-info.java` 里的 `@NullMarked`，一次改动换来整个包在 Kotlin 侧的类型收窄，比在每个调用点写 `?:` 便宜得多。

## 3. `data class` 做 DTO：收益是真的

`data class` 自动生成 `equals`/`hashCode`/`toString`/`copy`/`componentN`。对 DTO 来说这五件全是净收益：

- `equals` 一致，测试里可以直接断言整个对象，不用逐字段比；
- `toString` 可读，日志和失败信息里能看见内容而不是 `com.example.Order@1b6d`；
- `copy` 让「基于旧值造变体」变成一行，测试夹具和事件改写都靠它；
- 与 Jackson 3 的 Kotlin 模块配合良好：缺字段用默认值、非空字段缺失直接报错（06 册）。

**为什么 DTO 适合而实体不适合**：DTO 是**值语义**——两个字段相同的 DTO 就是同一个值，没有身份、没有生命周期、不会被代理。JPA 实体反过来：它有身份（主键）、有状态（脏检查）、有代理（懒加载子类）。`data class` 假设的东西，实体一条都不满足。06 册会展开「实体为什么不能用 `data class`」，这里先记住结论。

与 Java `record` 的差别值得说清，因为很多人以为二者等价：

| 能力 | Kotlin `data class` | Java `record` |
|---|---|---|
| 值相等 | 自动 | 自动 |
| 复制变体 | `copy(...)` | 无，手写构造 |
| 可变属性 | 允许（危险） | 不允许（全 final） |
| 解构 | `componentN` | 无（访问器按名） |
| 附加属性 | 可有 `val`/`var` 与 `init` | 只能有静态成员与紧凑构造器 |
| 数组字段相等 | 引用比较（坑） | 引用比较（同一个坑） |

`copy` 是 Kotlin 独有的便利，也是本册第一个坑的来源。

## 4. `data class` 的三个坑

### 4.1 坑一：`copy` 是浅拷贝

```kotlin
data class OrderDraft(val id: String, val items: MutableList<String>)

val a = OrderDraft("o-1", mutableListOf("book"))
val b = a.copy(id = "o-2")
b.items.add("pen")

println(a.items)  // [book, pen] —— a 被改了，尽管它是 val
```

`copy` 生成的是「新对象 + 字段引用逐个复制」，`items` 两个对象指向同一个 `ArrayList`。`val` 只保证引用不变，不保证被引用对象不变。

**修法不是「小心一点」，而是让类型不给机会**：

1. DTO 里禁止 `MutableList`/`MutableMap`/`Array`，统一 `List`/`Map`；构造时 `items.toList()` 复制一份；
2. 需要「改一处」时用不可变复制：`a.copy(items = a.items + "pen")`，语义清晰且不共享；
3. 嵌套结构要真不可变，必须每一层都不可变——`copy` 只复制最外层，嵌套对象仍然共享；
4. 数组是特例：`data class` 的 `equals` 对数组做引用比较（`Array.equals` 就是 identity），要么换成 `List`，要么手写 `equals` 用 `contentEquals`。这一条每年都能在 code review 里抓到几次。

### 4.2 坑二：`equals` 基于全部字段

对 DTO 这是想要的，对「有身份的对象」是错的。

- 两个 `User` 的 id 相同、昵称不同，按业务它们是同一个用户，`data class` 判不等——放进 `Set` 就成了两个元素；
- 反过来，A 模块的 `Money(100, "CNY")` 指「100 分」，B 模块同样的 `Money(100, "CNY")` 指「100 元」，`equals` 判等而语义差 100 倍——类型没编码单位，`equals` 再准也没用，这是裸类型的锅（第 7 节的值对象能治）；
- 对象放进 `HashSet`/`HashMap` 后再改字段，`hashCode` 变了，元素「消失」——这是所有可变键的通用问题，但 `var` 字段让它更容易发生；
- 与 JPA 代理：`data class` 的 `equals` 会读取全部字段，代理上读字段先触发初始化，session 已关闭就抛 `LazyInitializationException`；而代理与实体的相等语义本来由 Hibernate 拦截，和「按字段比较」的假设直接冲突。

规矩一句话：**`data class` 只用于不可变值对象；有身份、有生命周期、会被代理的对象，手写 `equals`。**

### 4.3 坑三：`componentN` 按位置绑定，破坏兼容

```kotlin
data class CreateUserCommand(val name: String, val email: String)

// 三个月后，为了多租户在中间插了一个字段
data class CreateUserCommand(val name: String, val tenantId: String, val email: String)

val (name, email) = cmd   // 编译通过，email 实际拿到的是 tenantId
```

这是最阴的一个：`copy(id = ...)` 用具名参数，改名会编译错；解构按 `component1()`/`component2()` 的**位置**绑定，插字段不会报错，只会静默错位。类型还都是 `String` 时，编译器连类型不匹配都发现不了。

规矩：

- 解构只用于私有/局部的小结构（`Map.Entry`、`Pair`、循环里的临时值），**不要跨模块解构公共 DTO**；
- 公共 DTO 加字段加在末尾，且消费方用具名访问；
- 需要长期演进的契约对象，宁可用显式属性访问器，也不要用解构换那点简洁。

## 5. 不可变集合：`List` 只是「只读接口」

`kotlin.collections.List` 没有 `add`/`remove`，所以看起来不可变。但它只是个接口：底层完全可以是一个 `ArrayList`。Kotlin 的只读接口是**编译期的「不给你改」**，不是运行时的「改不了」。

```kotlin
val readOnly: List<String> = mutableListOf("a")   // 只读接口，底层可变
val snapshot: List<String> = readOnly.toList()    // 复制一份，与上游脱钩
val guarded: List<String> = java.util.Collections.unmodifiableList(readOnly) // 运行时禁写
```

| 写法 | 底层可变 | 能挡住谁 | 代价 | 语义 |
|---|---|---|---|---|
| `listOf(a, b)` | 定长（Java 侧仍可 `set`） | Kotlin 与 Java 的增删 | 无 | 只读接口 + 定长实现 |
| `mutableListOf()` 赋给 `List` | 是 | 只有 Kotlin 调用方 | 无 | 只读视图，随时会被别人改 |
| `toList()` | 否 | 所有人 | O(n) 浅复制 | 快照，与上游脱钩 |
| `Collections.unmodifiableList` | 是（原表还能改） | 所有人（写操作抛 UOE） | 每次读一层转发 | 包装视图，上游改动会透出 |
| `List.copyOf(list)` | 否 | 所有人 | O(n) + null 检查 | 真不可变快照（推荐对外返回） |

三个容易混的点：

1. **`toList()` 是复制，`asList`/直接赋值是视图**。前者防「上游后来改了」，后者只防「下游现在改」。要哪个取决于你是不是把集合交给了别人。
2. **`Collections.unmodifiableList` 与 `toList()` 不等价**：前者是包装，原始 list 变化会透出来；后者是快照。对外暴露内部集合时，要的是快照，不是包装。
3. **Java 侧没有只读接口**。Kotlin 的 `List` 编译成 `java.util.List`，Java 代码照样能 `add`；连 `listOf` 也只是定长实现，Java 侧 `set` 仍然能写。跨语言边界时，只读接口零强制力，必须 `List.copyOf` 或 `unmodifiableList` 兜底。

**深不可变是递归的**：`List<MutableList<T>>` 再只读也没用，元素还能改。真要做到「传出去就安全」，每一层都得是不可变类型——这也是为什么第 7 节要用值对象，而不只是把 `var` 改成 `val`。

## 6. 用 `init` + `require`/`check` 把不变量钉在构造期

```kotlin
data class DateRange(val from: LocalDate, val to: LocalDate) {
    init {
        require(!to.isBefore(from)) { "to($to) 不能早于 from($from)" }
    }
}

class Order private constructor(
    val id: OrderId,
    val lines: List<OrderLine>,
) {
    companion object {
        fun of(id: OrderId, lines: List<OrderLine>) = Order(id, lines.toList())
    }

    init {
        require(lines.isNotEmpty()) { "订单至少要有一行" }
        check(lines.sumOf { it.amount.cents } > 0) { "订单总额必须为正" }
    }
}
```

`require` 抛 `IllegalArgumentException`，语义是「调用方给的参数非法」；`check` 抛 `IllegalStateException`，语义是「对象自身状态非法」。`assert` 只在 `-ea` 下生效，绝不能用于业务校验——生产环境大概率没开。

**为什么值得**：非法状态在构造期就构造不出来，下游所有方法都不必再防御。它把「校验散落在 N 个调用点」收敛成「1 个构造器」，这是本册性价比最高的一条规矩。

四个坑：

- `init` 与属性初始化按**声明顺序**执行，`init` 里引用后面声明的属性会拿到默认值（或未初始化）。把校验放在所有属性之后。
- `copy()` 会重新走构造器与 `init`，这是好事——但 Jackson 反序列化可能绕过构造器，除非挂上 Kotlin 模块（06 册）。绕过就意味着校验被跳过，脏数据进内存。
- `init` 里不要做 IO、查库、读配置。构造器应该纯内存、快、可重复；需要外部数据才能校验的不变量，属于领域服务，不属于构造器。
- 抛出的异常要能被映射成 4xx 而不是 500。`IllegalArgumentException` 落到 `@ControllerAdvice` 上应该是 400，第四阶段的错误模型会接住它。

## 7. 一次重构：`String` 参数换成值对象

重构前——三个参数可以任意互换，编译器全程沉默：

```kotlin
fun transfer(from: String, to: String, amount: Long) { /* ... */ }

transfer("acc-1", "acc-2", 100)   // 哪个是 from、哪个是 to？编译器不管
transfer("acc-1", "acc-2", 10000) // 分还是元？没人知道
transfer("acc-1", "acc-1", -5)    // 自己转自己、负数金额，全都放行
```

重构后——用 `value class` 把单位和身份编进类型（`value class` 的编译产物与映射细节在 03 册）：

```kotlin
@JvmInline
value class AccountId(val value: String) {
    init { require(value.isNotBlank()) { "账号不能为空" } }
}

@JvmInline
value class Money(val cents: Long) {
    init { require(cents >= 0) { "金额不能为负：$cents" } }
    operator fun plus(other: Money) = Money(cents + other.cents)
}

fun transfer(from: AccountId, to: AccountId, amount: Money) { /* ... */ }

val a = AccountId("acc-1")
val b = AccountId("acc-2")
transfer(b, a, Money(100))          // 编译通过，语义明确
// transfer(a, b, 100L)             // 编译错误：Long 不是 Money
// transfer(a, a, Money(-1))        // 编译通过，构造期抛 IllegalArgumentException
```

| 错误类型 | 重构前 | 重构后 |
|---|---|---|
| 把 `orderId` 传给 `accountId` | 编译通过 | 编译错误（类型不同） |
| 传了「元」而不是「分」 | 编译通过，金额放大 100 倍 | 必须显式 `Money(...)`，单位在类型名里 |
| 负数金额 | 编译通过 | 构造期抛异常，栈指向构造点 |
| 空账号 | 运行到 SQL 才报错 | 构造期抛异常 |
| 日志里看到 `"acc-1"` 不知是什么 | 无上下文 | `AccountId(value=acc-1)` |
| 两个 `AccountId` 参数顺序写反 | 编译通过 | **仍然编译通过** |

最后一行要诚实：**值对象挡的是「跨类型混淆」，不是「同类型顺序」**。`from` 和 `to` 都是 `AccountId`，写反了编译器照样放行。这类错误只能靠具名参数调用，或者把参数收成一个 `TransferCommand(from, to, amount)` 对象——如果 `from`/`to` 真的那么容易被搞混，就该给它们不同的类型（`DebitAccount`/`CreditAccount`），而不是指望值对象顺手解决一切。

**代价要提前算**：

- 序列化：Jackson 把 `value class` 当普通对象，需要 `@get:JsonValue` 或自定义序列化器，否则 JSON 里会多一层 `{"value": "acc-1"}`；
- 持久化：Hibernate 不认识 `value class`，实体里通常仍存底层类型，在 Repository 边界转换；
- 转换点成本：与遗留接口、消息体、缓存 key 交互时都要显式 `.value`；
- 别过度：只有「同构裸类型出现两个以上参数」或「有单位/格式语义」时才包装。给每个 `String` 都建一个类，只会让代码多一层噪音。

`value class` 在运行期擦除成底层类型，所以这层类型安全基本不收运行时税——这正是它比普通包装类更适合热路径的原因。
