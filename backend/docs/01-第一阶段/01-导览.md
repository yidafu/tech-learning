# 第一阶段导览：后端全景与工程地基

> [返回：后端开发学习大纲](../后端开发学习大纲.md)
> 本文是第一阶段的入口：阶段目标、分册计划、知识点地图、实践任务与自测。建议开阶段时读一遍定计划，收阶段时再读一遍查漏。

**建议时长**：1 周（每天 1~2 小时）。本阶段不钻任何一层细节，只做四件事：把十五站主时间线装进脑子、把技术基线钉死、搭出一个能长期用的骨架工程、装好度量工具。

## 阶段目标

学完本阶段，你应该能不查资料做到这些事：

1. 画出十五站主时间线，说清每一站跑在哪个线程上（容器线程 / 业务线程 / 连接池线程 / IO 线程）。
2. 说出本地、同机房、跨机房三种场景下各段的耗时量级，并判断哪些段受网络 RTT 支配、哪些受计算与 IO 支配。
3. 解释 Spring Boot 4 相对 3.5 的五个关键差异，并知道自己项目该钉在哪个版本线上。
4. 从零搭出一个多模块工程骨架，说明「为什么这个依赖只能被这个模块引用」。
5. 用 JFR 录一段压测期间的执行，在火焰图上指出占比最高的三个方法。
6. 说出 JMH 至少三个容易把结论测反的坑（预热、死代码消除、常量折叠）。

## 知识点地图

### 1. 十五站与账本思维（02 册）

- **为什么先建账本**：后端调优最常见的错误是「凭感觉猜瓶颈」——看到慢就加缓存、看到 CPU 高就加核。账本把一次请求拆成十五段，每段有名字、有量级、有归属线程，后续每个阶段都是在给其中某几站做精修，精修完回来核账看整体数字怎么变。
- **三套量级表**：本地（无网络、单机 DB）几乎全是计算与 IO 时间；同机房（RTT ~0.5ms）连接建立几乎可忽略；跨机房（RTT ~30ms）时下游调用次数直接决定总耗时。**同一次改动在不同部署形态下结论可能相反**，所以账本必须分场景记。
- **必须标注的阻塞点**：数据库等待、Redis 等待、下游 HTTP 等待、锁等待、GC 停顿。这五类都不吃 CPU，只看 CPU 使用率永远找不到它们。

### 2. 技术基线与环境（03 册）

- **版本不是细节**：Boot 4 把 starter 拆细、Jackson 换成 3.x、tracing 自动配置独立成模块，照抄 3.x 教程会踩一串「代码能编译、行为不对」的坑。
- **本地环境要可复现**：PG、Redis、Kafka 用 Compose 起，版本号写死在文件里；不要用「我机器上那套」，否则阶段七的压测数据没法对比。
- **JDK 25 的意义**：虚拟线程与结构化并发在阶段八会成为主力工具，现在就把运行时选对，避免后面改一行代码要重跑全站实验。

### 3. 工程骨架（04 册）

- **单体优先**：先做模块化单体（模块之间只通过接口与事件通信），只有在「团队规模 × 变更频率」撑不住时才拆服务（第十一阶段）。骨架就要为这种演进留出边界。
- **依赖方向单一**：`api → service → repository`，反向依赖一律靠接口或事件；基础设施代码（DB、MQ 客户端）不许漏到 controller 层。
- **三类对象别混**：DTO（对外契约，可演进）、领域对象（业务不变量）、实体（持久化映射）。混用是后期「改个字段炸一片」的根因。

### 4. 度量工具（05 册）

- **JFR 优于采样 profiler 的场合**：低开销、可长时间开、能同时看到 GC、线程、锁、IO。看火焰图先看「宽而平」的部分，再看具体方法。
- **JMH 的坑**：不预热就测会把 JIT 编译时间算进去；返回值不消费会被死代码消除；常量折叠会让「优化前」看起来和「优化后」一样快。
- **Actuator 先开 `health`、`metrics`、`prometheus`**，其余端点默认关闭——第十阶段会讲怎么在生产里安全地开。

## 阶段实践

跑通骨架服务，给十五站各埋一个计时点（用 Micrometer `Timer` 或简单的 `System.nanoTime()` 汇总），压一轮固定 QPS，产出第一版账本：每站 P50/P99 + 归属线程 + 是否阻塞。这份账本会在后面每个阶段被引用。

## 自测

1. 一个接口 P99 是 800ms，CPU 使用率 15%，最可能是哪几站的问题？你会先看什么数据？
2. 为什么跨机房部署时「多调用一次下游」的代价远大于同机房？
3. 你的项目现在用的是 Boot 3.5，要升到 4.x，列出至少五项必须改的地方。
4. JMH 测出来「优化后慢了 5%」，可能是什么原因导致的假结论？
5. 一个 Controller 直接注入了 Repository，为什么这是骨架层面的设计问题？
