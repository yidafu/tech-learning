# 06. 服务发现与配置中心

> [← 第十一阶段导览](01-导览.md) · 注册中心和配置中心都是强依赖：引入前先问「平台能不能替你做」；引入之后，它们挂掉的那十分钟会发生什么，取决于客户端缓存——这个隐性 SLA 要主动设计，而不是碰运气。

## 1. 三条路线对比

服务实例的地址会随扩缩容、重启、滚动更新不断变化，调用方需要一张「谁在运行」的活名单。三条获取路线：

| 维度 | Eureka | Consul | K8s Service + DNS |
|---|---|---|---|
| 定位 | Spring 生态的注册中心 | 通用服务网格/注册中心，不限语言 | 平台内置，无需额外组件 |
| CAP 取向 | **AP 优先**：自我保护模式，网络分区时宁可提供过期名单也不清空 | CP 倾向：Raft 强一致；健康检查可挂脚本/TTL | 平台侧保证，节点级分流 |
| 健康检查 | 客户端心跳上报 | 服务端主动探测（HTTP/TCP/脚本） | kubelet 探针（readiness/liveness） |
| 配置能力 | 无 | 顺带 KV 存储，可当配置中心 | ConfigMap/Secret + 外部配置系统 |
| 运维成本 | 单独部署一套（还要考虑高可用） | 单独部署一套，通用性好 | 零——平台已经跑着了 |
| 适用 | 无 K8s 的传统部署、纯 Spring 站点 | 混合语言、VM 与容器混合 | 已上 K8s 的一切 |

三条路线的差异表面在功能，实质在**「这个事实由谁维护」**：Eureka/Consul 自己维护一份实例名单，K8s 的名单就是 Deployment 的期望副本数与探针结果——事实只有一份，不会漂移。

## 2. 已经有 K8s，就别再引注册中心

这条论证值得展开，因为「在 K8s 里再装一套 Eureka」是非常常见的多余动作：

1. **同一事实两处记录**。K8s 的 Service 已经维护了「哪些 Pod 活着、流量怎么分」，注册中心又维护一份。两份名单靠应用自身的心跳对齐，漂移后（应用注册失败、Pod 已死但没反注册）排查成本远高于收益。
2. **双份健康检查互相打架**。readiness 说 Pod 未就绪，Eureka 心跳还在报 UP——流量到底该不该进？答案是流量路径与探针路径分离，两边结论不一致时，排障先变成考古。
3. **多一个要维护的高可用组件**。注册中心本身要 3 节点集群、要升级、要监控——为一个「平台已经解决」的问题新增的运维面。
4. **生命周期割裂**。K8s 的滚动更新天然保证「新 Pod 就绪才切流量、旧 Pod 排空后才退出」；绕过平台走注册中心反注册，排空时序要自己重新实现一遍（第十阶段 07 册的优雅停机在平台里是免费的）。

例外情况确实存在：**跨集群/混合部署**（部分服务在 K8s 外的虚拟机上）、或服务网格要跨平台统一寻址——此时注册中心才重新有意义。判据一句话：**服务发现的事实源跟着部署平台走，别再造一个平行的事实源**。

## 3. 客户端本地缓存：注册中心的隐性 SLA

注册中心挂了会怎样？答案不是「全站挂了」，而是一个取决于配置的窗口。推演一下宕机 10 分钟：

| 时间线 | 发生什么 | 决定因素 |
|---|---|---|
| 第 0~1 分钟 | 已建立的调用不受影响（连接已建立，不看名单） | — |
| 第 1~10 分钟 | 客户端继续用**本地缓存的实例名单**调用；新实例注册不上（扩容无效）、实例下线感知不到（流量继续打进已死实例） | 客户端缓存 TTL、名单刷新间隔 |
| 心跳停止一侧 | 服务端（若恢复）会因心跳缺失剔除实例；但服务端挂着，剔除根本不发生 | 心跳间隔、剔除超时 |
| 第 10 分钟后恢复 | 缓存刷新，名单回正 | 恢复后的风暴（所有客户端同时拉名单） |

所以系统的真实可用性不是「注册中心的可用性」，而是「**注册中心不可用时，客户端缓存还能撑多久、撑得对不对**」——这是一个隐性 SLA，要显式设计三件事：

1. **缓存 TTL 与刷新间隔**：Eureka 客户端默认 30s 拉取注册表，Consul 可配查询间隔；间隔越短故障窗口越小，但注册中心压力越大。10 分钟宕机 + 30s 刷新，期间名单是过期的——**扩缩容和故障摘除在这十分钟里全部失效**。
2. **客户端侧的失败摘除**：名单里有个实例已经死了，调用持续报错——负载均衡器要有「连续失败摘除」（熔断器对实例级的保护，第八阶段 06 册），不能迷信名单的正确性。
3. **启动时的降级策略**：注册中心挂了，新启动的实例拉不到名单。可配「失败不阻塞启动，先起来等服务恢复」，还是「阻塞启动保证名单正确」——按业务容忍度选。

对照表（第 6 节）把「注册中心不可用时各行为」钉死，这张表应该出现在每个服务的运维手册里。

## 4. 配置中心：能力与代价

配置中心解决的是「同一份配置散落 N 个实例、改一次发一次版」的问题。三个核心能力：

- **集中管理**：一份配置一个来源，环境差异（dev/staging/prod）按 profile 分层，密钥外置（第十阶段 06 册的分层原则在多服务下的延伸）；
- **动态刷新**：改配置不用重启——`@RefreshScope` 的 Bean 在刷新事件后重建，适合限流阈值、开关、降级名单这类「变了就要立刻生效」的值；
- **灰度配置**：按实例标签推送（先推一台验证，再全量）——配置的发布策略与服务发布共用一套心智。

代价要摆上桌面：**配置中心成为新的强依赖**。它挂了，服务还能不能启动、还能不能改配置？答案是靠本地兜底：`application.yml` 里保留一份完整的兜底配置，配置中心的值是**覆盖**而不是**唯一来源**——配置中心不可用时，服务按兜底配置正常启动，只是拿不到最新值。没有兜底配置的团队，在配置中心抖动时会得到一批起不来的实例，故障从「改不了配置」升级成「起不来服务」。

动态刷新还有一个语义陷阱：`@RefreshScope` 重建的是 Bean，**不是所有组件都走这条路**——连接池大小这类「已创建的资源」刷新不了（要重启），只对「每次使用时读取的值」有效。把「哪些配置能热更」列成清单，比把所有配置塞进刷新范围更务实。

```kotlin
// 可热更配置的标准写法：RefreshScope 代理 + 每次调用读最新值
@RefreshScope
@Component
class RateLimitRules(
    // 本地兜底默认值写在代码里：配置中心不可用时，这个 Bean 仍能用默认值构造
    @Value("\${limit.order-per-user:100}")
    private val defaultPerUser: Int,
) {
    // 每次调用读字段（代理重建后是新值），而不是在 Bean 初始化时缓存
    fun perUserLimit(): Int = currentRules().perUser ?: defaultPerUser

    // 不能热更的配置（连接池、线程池大小）不要放进 RefreshScope——
    // 刷新只会重建这个 Bean，HikariCP 的池子还是旧的，给人「已生效」的假象
}
```

## 5. 配置变更是一类发布风险

改配置 = 改行为，但不走代码评审与流水线——这是配置变更危险的根源。纪律四条：

1. **评审**：配置变更走与代码相同的评审流程（PR 改配置文件、或配置中心的变更记录可审计），禁止单人直改生产配置；
2. **灰度**：先推一台实例，观察指标（错误率、P99、连接数）无异常再全量——限流阈值从 1000 改成 50 这种手滑，灰度能在影响一台时拦住；
3. **可回滚**：保留历史版本，一键回退；回退速度要与发布回滚同级看待；
4. **变更后观察**：每次配置变更后盯 5~10 分钟关键指标。配置变更引发的事故特点是「改完立刻起效但没人盯着」——盯住了就是小事故，没盯住就是凌晨被告警叫醒。

## 6. 配置代码

Eureka/Consul 客户端的典型配置（二选一，取决于部署平台）：

```yaml
# 方案 A：无 K8s，走 Eureka——客户端缓存参数就是第 3 节的隐性 SLA
eureka:
  client:
    service-url:
      default-zone: http://eureka-1:8761/eureka,http://eureka-2:8761/eureka
    fetch-registry: true
    registry-fetch-interval-seconds: 30   # 名单刷新间隔：故障窗口的直接决定因素
  instance:
    lease-renewal-interval-in-seconds: 10 # 心跳间隔
    lease-expiration-duration-in-seconds: 30
    prefer-ip-address: true

# 方案 B：无 K8s，走 Consul——注册与配置二合一
spring:
  cloud:
    consul:
      host: consul-1
      port: 8500
      discovery:
        health-check-interval: 10s
        health-check-path: /actuator/health
      config:
        enabled: true
        fail-fast: false   # 配置中心不可用不阻塞启动——本地兜底配置顶上
```

K8s 原生方案：不装注册中心，Service + readiness 就是服务发现（第 2 节的论证在此落地）：

```yaml
# 调用方视角：目标就是 DNS 名字 inventory-service，没有注册中心参与
apiVersion: v1
kind: Service
metadata:
  name: inventory-service
spec:
  selector:
    app: inventory          # 流量只进 readiness 通过的 Pod
  ports:
    - port: 80
      targetPort: 8080
---
apiVersion: apps/v1
kind: Deployment
metadata:
  name: inventory
spec:
  template:
    spec:
      containers:
        - name: inventory
          image: registry.example.com/inventory:1.4.2
          readinessProbe:            # 就绪判定：失败即从 Service 名单摘除
            httpGet:
              path: /actuator/health/readiness
              port: 8080
            periodSeconds: 5
          lifecycle:
            preStop:                 # 滚动更新时排空在途请求（第十阶段 07 册）
              exec:
                command: ["sh", "-c", "sleep 10"]
```

客户端代码侧只需要两件事：把下游地址写成服务名/DNS 名（交给负载均衡解析），以及为「名单过期」做实例级摘除：

```kotlin
// 本地缓存名单 + 实例级失败摘除：注册中心挂掉时的最后防线
@Component
class ResilientInvoker(
    private val balancer: LoadBalancerClient,   // 依赖抽象，Eureka/Consul/K8s 可替换
) {
    private val failures = ConcurrentHashMap<String, AtomicInteger>()

    fun <T> invoke(service: String, action: (URI) -> T): T {
        val uri = balancer.choose(service) ?: throw ServiceUnavailable(service)
        val key = uri.host
        if ((failures[key]?.get() ?: 0) >= 3) throw InstanceRemoved(key)  // 连续失败摘除
        return try {
            val result = action(uri)
            failures.remove(key)
            result
        } catch (e: Exception) {
            failures.computeIfAbsent(key) { AtomicInteger() }.incrementAndGet()
            throw e
        }
    }
}
```

## 7. 注册中心不可用时的行为对照表

| 场景 | Eureka/Consul 路线 | K8s Service 路线 |
|---|---|---|
| 控制组件宕机 10 分钟 | 已运行实例：靠本地缓存名单继续调用（窗口 = 刷新间隔） | Service 由 kube-proxy 维护在每节点，**控制面短暂不可用不影响存量转发** |
| 期间扩容 | 新实例注册不上，扩容无效 | Deployment 副本数改了但控制面不可用时同样延迟生效 |
| 期间实例崩溃 | 名单不更新，流量继续打进死实例，靠客户端失败摘除兜底 | kubelet 本地探针继续工作，Pod 摘除**不依赖控制面** |
| 新实例冷启动 | 拉不到名单（可配不阻塞启动） | Service 解析不依赖控制面（节点级 DNS 缓存 + iptables/IPVS 规则） |
| 恢复后 | 全量客户端同时拉名单，注意风暴 | 无额外动作 |

对照表的结论与第 2 节互证：K8s 路线把「控制面挂掉」的影响面压到最小（数据面自治），自建注册中心路线则把宝押在客户端缓存 TTL 上——两条路线的运维哲学不同，但**「客户端不迷信名单」这条纪律相同**。

## 8. 自测

1. 三条服务发现路线的差异实质是什么（「事实由谁维护」）？Eureka 的自我保护模式在 CAP 上选择了什么、代价是什么？
2. 「在 K8s 里再装一套 Eureka」会造成哪两类事实漂移？什么情况下注册中心重新有意义？
3. 注册中心宕机 10 分钟，系统还能调用吗？取决于哪两个配置项？这十分钟里哪些能力失效？
