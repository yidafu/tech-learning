# 第十一阶段导览：微服务与大型应用

> [返回：后端开发学习大纲](../后端开发学习大纲.md)
> 本文是第十一阶段的入口。单服务的天花板来自「团队规模 × 变更频率」，不是「QPS 不够」。本阶段先讲**该不该拆**，再讲拆完必须付的五笔账：边界、通信、数据、治理、可观测性。

**建议时长**：2.5 周。这是全站最「贵」的阶段——概念不多，但每一个决定的代价都很大。

## 阶段目标

1. 用「团队数 / 发布频率 / 故障域 / 数据耦合」四个维度判断一个系统该停在哪种形态，并能给出反例（哪些情况绝不该拆）。
2. 用限界上下文划出服务边界，说清「一服务一库」之后跨服务查询、报表、事务分别怎么办。
3. 为一次跨服务调用选择同步还是异步，并算出超时预算与重试放大。
4. 配置 Spring Cloud Gateway 完成路由、鉴权前置、限流，并说出「网关不该做的事」（业务编排、复杂聚合）。
5. 说清三种服务发现路线的差异（Eureka/Consul/K8s Service），以及注册中心不可用时系统会怎样。
6. 用 Outbox + 消息实现一个可靠的跨服务流程，说明对账与人工兜底放在哪里。
7. 让一条请求在三个服务之间串起完整 trace，并配置基于 SLO 的告警。
8. 设计一次灰度发布：谁先进、怎么切流、回滚条件是什么。

## 知识点地图

### 1. 该不该拆（02 册）

- **三种形态的成本曲线**：单体（开发快、部署简单、故障域整体）→ 模块化单体（模块间走接口/事件，可独立演进，仍单进程）→ 微服务（独立部署、独立扩缩，代价是分布式一切）。
- **拆分的真实动因**：多团队并行开发互相阻塞、某些模块的伸缩需求差异巨大、合规要求隔离、发布节奏必须解耦。**「代码太乱」不是理由**——那是模块化没做好。
- **拆错的典型症状**：一个业务变更要改五个服务、跨服务事务满天飞、联调环境永远起不来、链路排查要拉四个人。
- **绞杀者模式**：从单体边缘切一小块出来做服务，网关按路径分流，稳定后继续切。**先切读、后切写；先切无状态、后切有状态**。

### 2. 边界与数据（03 册）

- **限界上下文**是「语言一致 + 模型自洽」的边界：同一个「商品」在订单域和库存域含义不同，就该是两个模型。
- **一服务一库**是微服务的地基：共享数据库等于共享事务与共享 schema，等于拆不开。
- **跨服务查询的四种解法**：API 组合（BFF 聚合）、数据冗余（本地存快照）、事件驱动的读模型（CQRS）、报表走数仓。**没有「跨库 JOIN」这个选项**。
- **聚合根**决定事务边界：一次事务只改一个聚合，跨聚合靠事件最终一致。

### 3. 通信（04 册）

| 场景 | 首选 | 理由 |
|---|---|---|
| 查询、强实时 | 同步 HTTP（`RestClient`/`HTTP Service Clients`） | 简单、可观测、易调试 |
| 内部高频、强类型 | gRPC | 二进制、流式、代码生成 |
| 状态变更通知、长流程 | 消息（Kafka/RabbitMQ） | 解耦、削峰、可重放 |
| 需要返回值的长流程 | 同步受理 + 异步回调/轮询 | 避免长连接与超时嵌套 |

- **Feign 的定位**：OpenFeign 已进入维护状态，官方建议新项目评估 Spring 的 HTTP Service Clients（声明式接口 + `@HttpExchange`）。迁移成本主要在注解与错误处理。
- **超时预算逐层递减**：入口 500ms → 服务 A 调 B 给 200ms → B 调 C 给 100ms。**任何一层超时大于上游，就等于没有超时**。
- **同步调用链的深度上限**：超过三层就要考虑改成异步或聚合，否则可用性是各层可用性相乘（3 个 99.9% 串起来是 99.7%）。

### 4. 网关与 BFF（05 册）

- **网关职责**：路由、鉴权前置（验 token 后透传身份）、限流、灰度分流、协议转换、统一错误体。**不该做**：业务编排、跨服务多次聚合、状态存储。
- **BFF** 是「为某类客户端定制的后端」，解决「移动端要 3 个接口、Web 要 1 个」的问题。BFF 可以聚合，但不该持有业务规则。
- **Gateway 5** 同时提供 WebFlux 与 Web MVC 形态，选型要看团队栈与是否已有响应式依赖；过滤器链的顺序直接决定鉴权与限流谁先生效。

### 5. 发现与配置（06 册）

- **三条路线**：Eureka（Spring 生态、AP 优先）、Consul（通用、带健康检查与 KV）、K8s Service + DNS（无需额外组件、依托平台）。**已经有 K8s 就别再引一套注册中心**。
- **注册中心挂了会怎样**：客户端通常有本地缓存，短期可继续调用；但新实例注册不上、下线感知延迟，要评估「缓存 TTL」这个隐性 SLA。
- **配置中心**：集中管理 + 动态刷新 + 灰度配置。代价是多一个强依赖（必须在本地留兜底配置），以及「配置变更」成为一类新的发布风险。

### 6. 分布式事务（07 册）

- **优先避免分布式事务**：把「必须同时成功」的操作收进同一个服务（改边界），或用「先受理、后异步完成」的业务设计（订单先创建为待确认）。
- **Outbox + 消息**覆盖 80% 场景：本地事务写业务表 + 消息表，投递器发出，消费侧幂等。
- **编排式 Saga**：协调者持有状态机，每步有补偿；适合跨 3+ 服务的长流程。协同式（各服务听事件自行决定）在服务多时难以排查。
- **Seata**：AT 模式对业务侵入小但依赖全局锁与回滚日志，性能与运维成本要评估；TCC 适合资金类。**任何方案都要有对账**——最终一致性系统的最后一道防线是「定期核对 + 人工修复工单」。

### 7. 观测与治理（08 册）

- **trace 串联的三个条件**：统一 traceId 传播（HTTP header / 消息 header）、统一采样策略、统一后端。跨团队时最容易在「消息 header 没带上」断掉。
- **SLO 而不是「都告警」**：每个服务定 1~2 个关键 SLO（可用性、P99），告警基于错误预算消耗速率，避免告警疲劳。
- **契约治理**：接口变更走契约测试 + 版本策略 + 废弃公告期；服务依赖拓扑要能自动生成，否则没人知道改这个接口会炸谁。

### 8. 大型应用工程化（09 册）

- **本地联调**：Compose 起依赖中间件 + Testcontainers 起「别人的服务」，或统一的 dev 环境命名空间；**不要指望每个开发都能本地起全栈**。
- **灰度**：按流量比例/用户标签/请求头分流；灰度必须有明确的「进入条件、观察指标、回滚阈值」。
- **容量**：按「峰值 QPS × 单请求资源占用」估算，再做压测验证；扩容要考虑冷启动与预热（连接池、JIT、本地缓存）。
- **发布顺序**：数据库变更先行且向后兼容 → 服务先扩后缩 → 消费者先升级（兼容新消息）→ 生产者最后切。

## 阶段实践

把第十阶段的服务拆成三个服务（订单、库存、通知）：

1. 用网关统一入口，鉴权在网关做，身份透传；
2. 订单 → 库存走同步（含超时与熔断），订单 → 通知走消息（Outbox）；
3. 用 Compose/K8s 起全套，验证一条请求的 trace 能串起三个服务；
4. 做一次灰度：旧版本 90% / 新版本 10%，人为让新版本错误率升高，验证自动回滚。

## 自测

1. 一个 5 人团队、日均发布 1 次、单体 30 万行，该拆微服务吗？给出判断理由。
2. 「一服务一库」之后，运营需要一个跨服务的订单+物流列表，你有哪四种方案？
3. 入口超时 800ms，服务 A 调 B 设了 1s，会发生什么？
4. 注册中心宕机 10 分钟，系统还能正常调用吗？取决于哪些配置？
5. 网关里做「订单 + 用户 + 库存」三次聚合，问题在哪？
6. 消息 header 里没带 traceId，链路会怎样？怎么系统性避免？
7. 灰度 10% 时发现新版本 P99 翻倍，回滚的正确顺序是什么？
