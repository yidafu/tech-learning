# 08. 多服务可观测性与契约治理

> [← 第十一阶段导览](01-导览.md) · 单服务的可观测是第十阶段的事；服务一多，观测的敌人变成「断链」，治理的敌人变成「没人知道改这个接口会炸谁」。这一册讲三件事：trace 怎么不断、SLO 怎么告警、契约怎么演进。

## 1. 跨服务 trace 串联的三个条件

一条请求穿过网关 → 订单 → 库存 → 消息 → 通知，要能在链路后端还原成同一棵调用树，三个条件缺一不可：

| 条件 | 内容 | 不满足的表现 |
|---|---|---|
| 统一传播 | 每一跳都接续 W3C `traceparent` 头——HTTP 请求头、**消息 header**、线程/协程切换的上下文传递（第十阶段 02 册） | 链路断成三截，各自有各自的 traceId |
| 统一采样 | 全链路同一套采样策略（全量或按比例，头部采样决定） | 订单 100% 采样、库存 1% 采样——上游请求的 trace 下游查不到 |
| 统一后端 | 全部服务把 span 发到同一个后端（Jaeger/Tempo/商业 APM） | 各服务各存各的，跨服务排障要登录多套系统 |

最常见的断裂点是**消息 header 没带 traceId**：HTTP 调用的传播 Micrometer Tracing（OTel）自动做，而消息路径要生产者把上下文写进 Kafka header、消费者读出来续上——框架只对部分框架集成自动支持，自写的生产消费代码经常漏掉这一跳。第二个高频断裂点是异步边界：线程池切换丢 MDC、协程切调度器丢 context——第十阶段 02、04 册讲过的上下文传递问题，在跨服务语境下后果从「日志缺 id」升级成「链路断掉」。

一次排障的推导链能说明串联的价值：入口 traceId → 网关 span → 订单 span → **Kafka 消息（同一 traceId）** → 通知 span。断在中间任何一环，「通知为什么没发出去」就要在两个服务的日志里靠时间戳猜。

## 2. 服务级 SLO 与错误预算告警

每个服务定 1~2 个关键 SLO，不要多：

| SLO 类型 | 形式 | 示例 |
|---|---|---|
| 可用性 | 成功请求数 / 总请求数（5xx 算失败，4xx 不算） | 30 天内 ≥ 99.9% |
| 延迟 | P99 < 某阈值（与超时预算对齐，04 册） | 99% 的请求 < 300ms |

「每个 SLO 配一个告警阈值」的老做法会制造告警疲劳：阈值定松了永远不响，定紧了天天半夜响。正确做法是**基于错误预算的消耗速率**：

- 错误预算 = 1 − SLO。99.9% 的可用性意味着 30 天里有 0.1% 的请求额度（约 43 分钟的全量错误）；
- 告警看**燃烧率**（burn rate）：当前错误速率是预算匀速消耗速率的多少倍。多窗口组合防误报——「1 小时窗口燃烧率 > 14 倍 **且** 5 分钟窗口 > 14 倍」触发 page（真事故的形状是急且持续）；「6 小时 > 6 倍」触发 ticket（慢性消耗）；
- 预算烧完（30 天额度用尽）的动作是**冻结非修复类发布**——这是错误预算比 SLA 承诺先进的地方：它把「该不该继续加功能」变成了一个数字决策。

告警疲劳的真实代价不是「烦」，是**可靠性纪律的瓦解**：值班者连续被假警报叫醒几次之后，会开始忽略告警——然后真事故的 page 也被当成假警报划掉。所以告警规则的数量预算要和 SLO 一样克制：**一个服务的 page 类告警不超过两条**，其余一律降级为 ticket 或面板展示。「这个异常值得配告警吗」的判断标准只有一个：收到它的人此刻需要做什么动作。没有对应动作的告警，是发给日志的不是发给人的。

服务间的 SLO 还要分层：链路 SLO 由各层 SLO 相乘约束（04 册的乘法），所以下游服务比上游要有更紧的 SLO——上游 99.9% 的预算里，要给下游留出它自己的 0.1%。

## 3. 依赖拓扑自动生成

「谁调用谁」必须自动生成，不能手维护——手维护的文档必然过期。两个来源：

1. **trace 数据**：span 带服务名与对端服务名，聚合出服务依赖图。这是最准确的来源（反映了真实流量），还能标出调用频率与错误率；
2. **网关/入口日志**：至少覆盖「外部 → 服务」这一跳。

拓扑图的三个用途：改接口前先查「改这个方法会炸谁」（契约治理的前置输入）；容量评估时识别扇出最大的服务（04 册的可用性乘法发生在扇出中心）；故障演练时确定爆炸半径。一条纪律：**新增服务间依赖要走评审**——拓扑图让依赖变更可见，但拦住坏依赖的还是评审（比如「通知服务依赖订单库的直连」这种应该被 03 册的数据所有权纪律拦住的边）。

## 4. 契约治理：接口变更的流程

多服务下接口变更的危险在于：生产者改完自己发布成功，消费者在某个未知的时刻炸掉。治理三件套：

**契约测试**。消费者驱动的契约（Pact）或契约先行（Spring Cloud Contract，第十阶段 03 册的落地方法）：消费者声明自己依赖的字段与行为，生产者 CI 跑契约测试——破坏契约的 PR 直接构建失败。它解决的是「生产者不知道消费者用哪些字段」这个信息差。

**版本策略**。非破坏变更（加可空字段、加端点）不升版本直接发；破坏变更（删字段、改类型、改语义）升版本——URL 路径（`/v2/orders`）或媒体类型参数，与消费方约定一种并坚持（第四阶段 08 册的版本化基础）。

**废弃公告期**。删除旧版本前走完整流程：公告（至少一个迭代周期）→ 旧版本响应加 `Deprecation` 与 `Sunset` 头（标准做法，客户端可自动发现）→ 监控旧版本流量下降曲线 → **流量归零才下线**。跳过公告期直接删，等价于对未知数量的消费方做随机故障注入。

公告期里最容易被低估的环节是**盯流量曲线**：公告发出去不等于消费方看到了，更不等于他们改完了——有的消费方是外部门的季度项目，有的是三行没人认领的定时任务。流量曲线归零之前，「还有谁在调我」这个问题只有监控能回答；这就是第 3 节依赖拓扑必须自动生成的另一个原因——人工统计调用方的时间点恰好是项目最忙的时候。

破坏性变更的协调流程一句话版：**先加新的（双版本共存）→ 消费者迁完（拓扑图确认流量归零）→ 再删旧的**。禁止「原地改语义」。

## 5. API 版本化的灰度共存

多服务下版本发布经常与灰度绑定：v2 逻辑先在 10% 流量上验证。三种共存形态：

| 形态 | 做法 | 适用 |
|---|---|---|
| 同实例双版本 | 一个服务同时跑 v1/v2 路由，代码里并行实现 | 版本差异小、过渡期短 |
| 双实例组 | v2 部署独立实例组，网关按权重切（09 册的切流） | 版本差异大、要独立回滚 |
| 按头路由 | 网关按 `X-Api-Version` 头分流，客户端控制版本 | 客户端成熟、能显式带版本 |

判据是**回滚粒度**：要「v2 有问题秒回 v1」就上双实例组；只是平滑迁移代码就同实例双版本。无论哪种，双版本的**观察期指标要分开统计**——合在一起看，v2 的劣化会被 v1 的流量稀释掉。

## 6. 消息 header 带 traceId：生产者与消费者

把第 1 节的第一条件落成代码。生产者发出消息时把当前上下文的 traceId 写进 header；消费者读出并续上：

```kotlin
@Component
class TracedOrderEventProducer(
    private val kafkaTemplate: KafkaTemplate<String, String>,
) {

    fun send(event: OrderEvent) {
        val record = ProducerRecord("ORDER_EVENTS", event.orderId.toString(), event.toJson())

        // 把当前（HTTP 请求触发的）trace 上下文写进消息 header——
        // W3C traceparent 格式：version-traceId-spanId-flags
        currentTraceContext()?.let { tp ->
            record.headers().add("traceparent", tp.toByteArray())
        }
        record.headers().add("schema-version", "2".toByteArray())

        kafkaTemplate.send(record)
    }

    private fun currentTraceContext(): String? =
        TraceContext.current()?.let { "${it.version}-${it.traceId}-${it.spanId}-${it.flags}" }
}
```

```kotlin
@Component
class TracedOrderEventConsumer(
    private val handler: OrderCreatedHandler,
) {

    @KafkaListener(topics = ["ORDER_EVENTS"], groupId = "notification-service")
    fun on(record: ConsumerRecord<String, String>) {
        // 消费者续上 trace：从 header 读出 traceparent，作为本跳的父 span——
        // 这一段跳过，链路就断在消息这一跳（第 1 节的第一断裂点）
        val parent = record.headers().lastHeader("traceparent")?.value()?.decodeToString()

        withTraceContext(parent) {
            handler.on(record)
        }
    }

    // 框架集成（如带 instrumentation 的 listener 容器）会自动做这一步；
    // 自写消费路径必须手动续——这就是断裂点的由来
    private inline fun <T> withTraceContext(parent: String?, block: () -> T): T =
        TraceScope(parent).use { block() }
}
```

工程化的建议：把「写 header / 读 header」封装成公司级的生产消费基类或库，而不是要求每个开发者记得——**断裂点的系统性消除靠基础设施，不靠自觉**。验证方法：本地起三个服务加 Kafka，发一条消息，在链路后端确认同一 traceId 贯穿五跳（本阶段阶段实践的第 3 步）。

## 7. 三个服务的 SLO 与告警规则示例

把第 2 节的框架落成一张真实形状的配置表（入口网关 → 订单 → 库存链路）：

| 服务 | SLO | 错误预算（30 天） | 告警规则 | 动作 |
|---|---|---|---|---|
| 订单服务 | 可用性 99.9%；P99 < 400ms | 0.1%（约 43 分钟全量错误） | 1h & 5m 燃烧率 > 14 → page；6h > 6 → ticket | page：值班响应；预算烧尽：冻结发布 |
| 库存服务 | 可用性 99.95%（上游留预算）；P99 < 150ms | 0.05% | 同上，阈值更紧 | 下游比上游紧：订单的 99.9% 要容纳库存的抖动 |
| 通知服务 | 可用性 99.5%（可容忍短暂延迟）；P99 < 2s | 0.5% | 6h > 6 → ticket（不 page：非实时业务） | 异步业务降级告警级别，保护值班注意力 |

这张表体现的三个原则：SLO 数量克制（每服务不超过 2 个）；下游比上游紧（可用性乘法）；告警级别与业务实时性对齐（通知服务不配 page——半夜叫醒人修「短信晚到」是告警疲劳的直接来源）。

## 8. 自测

1. trace 串联的三个条件各管什么？为什么消息 header 是最常见的断裂点？系统性消除靠什么？
2. 99.9% 可用性的错误预算是多少？「1h & 5m 双窗口燃烧率 > 14」这种组合为什么能防误报？
3. 为什么下游服务的 SLO 要比上游更紧？写出可用性乘法对 SLO 分配的约束式。
4. 废弃公告期的四步是什么？「先加新的、迁完再删旧的」为什么禁止「原地改语义」？
5. API 版本灰度共存的三种形态怎么选？双版本观察期的指标为什么要分开统计？
6. 依赖拓扑的两个数据来源哪个更准？拓扑图在契约治理里的前置用途是什么？
