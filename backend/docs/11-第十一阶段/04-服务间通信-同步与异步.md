# 04. 服务间通信：同步与异步

> [← 第十一阶段导览](01-导览.md) · 同步简单，但把可用性变成乘法；异步解耦，但要付幂等与顺序的账。先按场景选型，再算超时预算，最后把契约与可重试性钉死。

## 1. 选型表：四个场景，四个答案

服务间通信没有「最好的方式」，只有按场景匹配的方式。四个典型场景先给结论：

| 场景 | 首选 | 理由 |
|---|---|---|
| 查询、强实时（页面要立刻渲染） | 同步 HTTP（`RestClient` / HTTP Service Clients） | 简单、可观测、易调试；调用方拿到返回值才能继续 |
| 内部高频、强类型、低延迟 | gRPC | 二进制序列化小且快、接口代码生成、支持流式 |
| 状态变更通知、长流程解耦 | 消息（Kafka / RabbitMQ） | 解耦、削峰、可重放；发送方不关心谁消费 |
| 需要返回值的长流程 | 同步受理 + 异步回调/轮询 | 避免长连接与超时嵌套，见第 5 节 |

两条贯穿的选择原则：

1. **同步调用把两个服务的可用性绑死**——下游挂，上游跟着挂（第 3 节的乘法）。所以默认倾向异步：能用「通知 + 最终一致」的业务，就不该用同步 RPC 硬撑实时性。
2. **消息与 RPC 不是竞争关系**：一次下单流程可以同时有「订单→库存」的同步扣减（必须立刻知道成败）和「订单→通知」的消息（发短信不必实时）。按每一跳的业务语义分别选型，而不是全系统统一一种。

## 2. Spring 侧的三种客户端

| 客户端 | 形态 | 适用 |
|---|---|---|
| `RestClient` | 命令式同步，Boot 4 的默认同步 HTTP 客户端 | 一次性调用、动态 URL、脚本式请求 |
| HTTP Service Clients | 声明式：接口 + `@HttpExchange` 注解 | 固定下游、要契约化与 mock 测试 |
| gRPC | 接口由 proto 生成 | 内部高频、强类型、需要流式 |

三者可以按服务分别选用：对外的 HTTP 服务用 `RestClient` 或声明式客户端，内部高频链路用 gRPC。OpenFeign 的定位要明确：**已进入 feature-complete 维护状态**，不再加新特性——存量可以继续用，新项目优先 Spring 自家的 HTTP Service Clients（同一作者脉络的声明式方案）。迁移成本主要在注解映射（`@FeignClient`/`@PathVariable` → `@HttpExchange`/`@PathVariable`）与错误处理代码，业务逻辑不动；没有收益的存量迁移可以不做。

声明式客户端的写法：

```kotlin
// 接口即契约：参数与返回类型是编译期检查的，测试时可以直接 mock 这个接口
interface InventoryClient {

    @GetExchange("/api/stock/{sku}")
    fun getStock(@PathVariable sku: String): StockView

    @PostExchange("/api/stock/{sku}/reserve")
    fun reserve(@PathVariable sku: String, @RequestBody cmd: ReserveCmd): ReserveResult
}

data class StockView(val sku: String, val available: Int)
data class ReserveCmd(val orderId: String, val qty: Int)

@Configuration
class HttpClientsConfig {

    @Bean
    fun inventoryClient(builder: RestClient.Builder): InventoryClient =
        HttpServiceProxyFactory
            .builderFor(RestClientAdapter.create(
                // baseUrl 指向下游服务；服务发现场景由负载均衡的 builder 提供
                builder.baseUrl("http://inventory-service").build()
            ))
            .build()
            .createClient(InventoryClient::class.java)
}
```

注意超时和重试不要散落在每个调用点：统一在 `ClientHttpRequestFactorySettings`（连接/读超时）和弹性层（Resilience4j，第八阶段 06 册）配置，声明式接口只声明「调谁、调什么」。

## 3. 超时预算：自顶向下分配

超时是同步通信里唯一必答题。规则是**自顶向下分配预算**：入口定了整个请求的时限，每一层只允许花掉预算的一部分。

```text
入口网关 500ms
  └─ 服务 A 的接口预算 400ms
       └─ A 调 B 分配 200ms
            └─ B 调 C 分配 100ms
```

三条硬规则：

1. **下游超时 ≥ 上游超时，等于没有超时**。入口 800ms，A 调 B 设 1s：B 永远不会被自己的超时保护——上游 800ms 时已经掐断并进入失败路径，而 B 的线程还在继续执行那个注定没人收货的请求，白白消耗下游容量。每一层的超时必须**严格小于**上游，差值留给自身处理（序列化、业务逻辑、写库）。
2. **预算按 P99 分配，不按平均值**。下游 P99 是 80ms，你给它 100ms 意味着 1% 的请求超时——如果这个失败率不可接受，预算和下游容量都要加，而不是把超时调大把问题藏到上游。
3. **连接超时与读超时分开**。连接超时短（百毫秒级，发现「连不上」要快），读超时按预算给（等「响应」）。混用一个值会让你既探不动死节点、又等不住慢响应。

超时之外还有重试的放大问题：超时 200ms × 重试 3 次 = 800ms，把上游的预算烧穿。重试次数要算进预算（第八阶段 06 册的指数退避与重试预算），不是配了就算。

## 4. 同步调用链的深度上限

同步链每加深一层，可用性做一次乘法：链路可用性 = 各层可用性之积。

| 链路深度 | 各层 99.9% | 链路可用性 | 每月不可用 |
|---|---|---|---|
| 1 层 | 99.9% | 99.9% | 43 分钟 |
| 2 层 | 99.9% | 99.8% | 86 分钟 |
| 3 层 | 99.9% | 99.7% | 2.2 小时 |

3 个 99.9% 的服务串起来，链路只有 99.7%——比任何一层都差，且每加一层继续往下掉。这给出工程上限：**同步调用链控制在三层以内**。超过三条路可走：

- **改异步**：把「必须立刻知道结果」改成「受理 + 通知」（第 5 节），链路变成发布者与订阅者，不再乘法；
- **聚合并行走 BFF**：网关/BFF 并行调三个服务再拼装——并行化救的是**延迟**（不再串行叠加），但可用性仍是三者的乘积，所以聚合层必须配降级（一个服务挂了，页面局部降级而不是整体 500）；
- **冗余或收敛边界**：高频共存的两个能力（订单和它的支付状态），第二册的边界标准提示它们可能该在一个服务里。

排障时的对应习惯：看到跨三层的同步链，先问「中间这层拿返回值做了什么不可替代的事」——很多中间层只是转发，删掉转发层等于白拿 99.8% 的可用性。

## 5. 消息通信的事件设计

消息把「实时绑定」换成「最终一致」，换来三个能力（削峰、重放、解耦），也换来三条设计纪律：

**事件要带幂等键。** 投递语义是至少一次（第六阶段 06 册的 Outbox 契约），消费必然重复。事件头里必须有唯一 `eventId`，加上业务幂等键（如 `orderId + eventType`）——消费侧去重表只认这个键，不认「消息内容长得像不像」。

**Schema 只加不改。** 消费者升级永远滞后于生产者：新字段必须有默认值或可空；不改字段类型、不改字段名、不删字段（废弃标注后下下个版本再删）；消费端对未知字段宽容（反序列化忽略）。破坏性演进等于让所有消费方同时升级——多服务下做不到。

**header 是基础设施信息的位置。** traceId、 causationId（哪个事件触发了本事件）、schema 版本进 header，不进 payload——业务字段和基础设施信息的演进节奏不同，混在一起会让每条业务变更都变成消费方破坏性变更。traceId 的完整讨论见 [08 册](08-多服务可观测性与契约治理.md)。

## 6. 同步受理 + 异步完成

长流程（下单后要风控、扣库存、结算、发货）的正确接口形态：**同步只做「受理」，返回 202 和追踪凭据；真正完成靠异步，结果通过查询或回调获取**。这避免了「HTTP 连接挂着等五分钟」与「超时预算层层嵌套」两个死局。

```kotlin
@RestController
class OrderController(private val orders: OrderService) {

    // 受理：只做参数校验 + 建单（PENDING）+ 发布事件，几十毫秒内返回
    @PostMapping("/api/orders")
    fun place(@Valid @RequestBody cmd: PlaceOrderCmd, request: HttpServletRequest): ResponseEntity<Accepted> {
        val orderId = orders.accept(cmd)
        // Location 指向结果查询接口，客户端轮询；202 语义 = 已受理、未完成
        return ResponseEntity
            .accepted()
            .location(URI.create("/api/orders/${orderId.value}"))
            .body(Accepted(orderId.value, status = "PENDING"))
    }

    // 轮询端点：客户端用同一个 orderId 问进度，直到状态离开 PENDING
    @GetMapping("/api/orders/{id}")
    fun status(@PathVariable id: UUID): ResponseEntity<OrderStatusView> {
        val view = orders.statusOf(OrderId(id))
        return when (view.phase) {
            Phase.PENDING -> ResponseEntity.accepted().body(view)
            else -> ResponseEntity.ok(view)
        }
    }
}

@Service
class OrderService(private val repo: OrderRepository, private val events: ApplicationEventPublisher) {

    fun accept(cmd: PlaceOrderCmd): OrderId {
        val order = Order.pending(cmd)
        repo.save(order)                       // 本地事务保证受理落地
        events.publishEvent(order.toAcceptedEvent())  // 之后的一切异步推进
        return order.id
    }
}
```

设计要点三条：受理接口必须是**幂等**的（客户端超时重试带同一个幂等键，第四阶段 03 册的 Idempotency-Key 纪律），否则受理重试制造重复订单；202 的语义要说给客户端——已受理不等于成功，客户端按 `Location` 轮询或提供回调地址；PENDING 是业务状态机的一部分（第六阶段 06 册的语义锁），中间态必须可见、可查、可人工推进。
