# 02. 测试金字塔与切片测试

> [← 第十阶段导览](01-导览.md) · 测试的价值不在覆盖率数字，而在「你改坏一行代码后多久知道、知道得多准」。金字塔管的是**比例与预算**，切片测试管的是**反馈的精度**——把 Spring 的启动面缩到刚好覆盖被测的那一层。

## 1. 金字塔的现代修正版

经典金字塔是 70/20/10（单测/服务测试/UI 测试）。放到 Spring Boot 项目里，它需要一次修正：**中间层要按「加载了哪些 Bean」来切，而不是按「测了哪些类」来切**。

| 层次 | 比例（按数量） | 单例耗时 | 总量预算 | 失败时告诉你什么 |
|---|---|---|---|---|
| 纯单测（无 Spring） | 60%~70% | 1~20ms | < 20s | 哪个分支、哪个入参 |
| 切片测试（`@WebMvcTest` 等） | 20%~30% | 200~800ms | < 60s | 哪一层的契约破了（状态码/JSON/SQL） |
| 集成测试（Testcontainers） | 5%~10% | 2~10s | < 10min | 真组件交互是否成立 |
| 端到端（真部署 + 真依赖） | < 2% | 30s~分钟 | nightly | 整条链路是否通 |

比例背后的两个约束：

1. **反馈时间决定测试是否被运行**。本地 `./gradlew test` 超过 2 分钟，开发者就开始「先 push 再说」；CI 超过 15 分钟，就会有人开始重跑而不是看失败原因。测试腐烂从来不是技术问题，是等待时间问题。
2. **失败定位成本决定修 bug 的成本**。一个 `@SpringBootTest` 挂掉，错误信息是「expected 200 but was 500」，你要翻三层日志才知道是校验、事务还是 SQL。切片测试把「哪一层」直接写在了注解上。

**为什么比例会失衡**：写全量集成测试最省脑子——不用想依赖边界，直接 `@SpringBootTest` 一把梭。代价是把「设计问题」推迟成了「CI 问题」：当你的 Service 有 8 个依赖、其中 5 个是静态调用时，你只能靠起整个容器来测它。**写不出单测，往往是设计在报警**。

**坑**：把覆盖率当目标。getter、`data class` 的 `copy`、Spring 配置类能轻松把行覆盖率刷到 85%，而真正会出错的「金额四舍五入」「幂等键复用」「并发扣减」一行没测。覆盖率是**发现漏测**的探针，不是验收指标。

## 2. 切片测试到底加载了什么

切片（slice）的本质是：**只装一条竖切面——一组固定的自动配置，加上类型过滤器把其他层的组件挡在扫描之外**。Boot 用 `@TypeExcludeFilters` 实现后半句，所以你在 `@WebMvcTest` 里注入 `OrderService` 会直接失败——这不是 bug，是设计。

| 注解 | 装配 | 不装配 | 能测 | 测不了 |
|---|---|---|---|---|
| `@WebMvcTest` | `@Controller`、`@ControllerAdvice`、`WebMvcConfigurer`、`Filter`、`HandlerInterceptor`、Jackson、`MockMvc` | `@Service`、`@Repository`、`DataSource`、事务、真实端口 | 路由映射、参数绑定、Bean Validation、序列化形态、异常 → `ProblemDetail`、状态码、`Content-Type` | 事务边界、SQL、真实网络行为、安全策略（只会生效默认安全配置，需自己导入 `SecurityFilterChain`） |
| `@DataJpaTest` | `DataSource`、`EntityManager`、`JpaRepository`、Flyway/Liquibase（若在类路径） | `@Service`、Web 层、`MockMvc` | 实体映射、派生查询与 JPQL、约束与级联、`@Version` 行为 | Controller 契约、序列化、跨层编排 |
| `@JsonTest` | `JsonMapper`（Jackson 3）、你声明的 `@JsonComponent` | Web 层、Service、DB | 字段名、`null` 与默认值、日期与数值格式、多态、枚举 | 其余一切 |

四个容易踩的默认行为：

- `@DataJpaTest` **默认把数据源替换成嵌入式库**。你要连真 PG，必须加 `@AutoConfigureTestDatabase(replace = AutoConfigureTestDatabase.Replace.NONE)`，否则测试跑在 H2 上，而 H2 不认识 PG 的 `jsonb`、部分索引、`ON CONFLICT` 语义——测试全绿，上线就炸。
- `@DataJpaTest` 默认给每个测试方法套一个事务并回滚。这既是优点（自动隔离）也是陷阱（见 03 册：它掩盖了「事务提交后才生效」的一类 bug）。
- 类路径上有 Spring Security 时，`@WebMvcTest` 会装配**默认安全配置**，于是所有请求都返回 401。要么导入一个测试用的 `SecurityFilterChain`，要么 `@AutoConfigureMockMvc(addFilters = false)`——这个坑几乎每个项目都会踩一次。

**`@JsonTest` 为什么值得单独存在**：接口契约的破坏性变更，一大半发生在序列化层——字段改名、`null` 变成字符串 `"null"`、`Long` 超过 JS 安全整数、时间从 ISO 变成时间戳。这些在 `@WebMvcTest` 里也能测，但 `@JsonTest` 快 5 倍、失败信息直接指到那个 DTO。

## 3. Boot 4 的三个迁移点

Boot 4 把「隐式提供」改成了「显式声明」，测试代码受影响的正好是三处：

| 3.x 写法 | 4.x 写法 | 不迁移的症状 |
|---|---|---|
| `@MockBean` | `@MockitoBean` | 编译不过（注解已删除，不是废弃） |
| `@SpyBean` | `@MockitoSpyBean` | 同上 |
| `@SpringBootTest` 自动有 `MockMvc` | 需要 `@AutoConfigureMockMvc` | `MockMvc` 注入为 `null`，NPE 打在 `@BeforeEach` |
| `@SpringBootTest(webEnvironment=RANDOM_PORT)` 自动有 `TestRestTemplate` | 自己声明 `TestRestTemplate`/`RestClient` Bean，或用 `RestTestClient` | 注入失败或 NPE |

`@MockitoBean` 不只是改名。它来自 Spring TestContext 的 **Bean Override** 机制（`org.springframework.test.context.bean.override.mockito`），和 `@MockBean` 的差别在于：

- 覆盖发生在 **Bean 定义阶段**，而不是启动后替换单例，所以依赖它的 Bean 拿到的一定是 mock；
- 默认在**测试类级别**生效，测试方法之间自动重置（stubbing 不残留到下一个方法）；
- 类型不匹配时直接报错，而不是像 `@MockBean` 那样「按类型找不到就新建一个」。

**为什么 Boot 4 要砍掉自动配置 `MockMvc`**：模块化之后，`spring-boot-test-autoconfigure` 不再默认假设你要测 Web。隐式装配的代价是「一个纯 Service 测试也会加载 MVC 基础设施」，而收益只是少写一行注解。

**坑**：迁移时最容易漏的是 `@WebMvcTest` 里注入 `MockMvc` 的写法没变、但 `@SpringBootTest` 的变体没加注解——报错在 `lateinit property mockMvc has not been initialized`，这个信息完全不指向根因。迁移时先把所有 `@SpringBootTest` 搜一遍。

## 4. 一段切片测试与一段纯单测的对照

同一个「下单」用例，两层各测什么：

```kotlin
@WebMvcTest(OrderController::class)
class OrderControllerTest {

    @Autowired lateinit var mockMvc: MockMvc

    @MockitoBean lateinit var orderService: OrderService

    @Test
    fun `quantity below one is rejected before reaching the domain`() {
        mockMvc.post("/api/orders") {
            contentType = MediaType.APPLICATION_JSON
            content = """{"sku":"A-1","quantity":0}"""
        }.andExpect {
            status { isBadRequest() }
            jsonPath("$.type") { value("https://errors.example.com/validation") }
            jsonPath("$.errors[0].field") { value("quantity") }
        }
        // 这一行才是切片测试的价值：证明非法请求根本没进领域层
        verifyNoInteractions(orderService)
    }

    @Test
    fun `insufficient stock maps to 409 with problem detail`() {
        given(orderService.place(any())).willThrow(OutOfStockException("A-1"))

        mockMvc.post("/api/orders") {
            contentType = MediaType.APPLICATION_JSON
            content = """{"sku":"A-1","quantity":1}"""
        }.andExpect {
            status { isConflict() }
            jsonPath("$.title") { value("out_of_stock") }
            header { string("Content-Type", containsString("application/problem+json")) }
        }
    }
}
```

它只花 300ms 左右，因为它只启动了 MVC 基础设施。注意它**测不到**：库存扣减是不是在事务里、`@Version` 有没有生效、`OutOfStockException` 抛出后事务有没有回滚——这些是下一层的事。

```kotlin
class OrderPricingTest {

    private val clock = Clock.fixed(Instant.parse("2026-11-15T10:00:00Z"), ZoneOffset.UTC)
    private val orders = InMemoryOrderRepository()          // 手写 fake，不用 mock
    private val service = OrderService(orders, clock, CouponPolicy())

    @Test
    fun `a coupon can only be applied once per customer per day`() {
        val customer = CustomerId("c-1")
        service.place(OrderMother.pending(customer, total = Money.of("100.00", "CNY"), coupon = "SAVE10"))
        service.place(OrderMother.pending(customer, total = Money.of("100.00", "CNY"), coupon = "SAVE10"))

        val discountOnSecond = orders.all().last().discount
        assertThat(discountOnSecond)
            .describedAs("同一天第二次使用同一张券，折扣必须为 0（优惠券规则是业务底线）")
            .isEqualTo(Money.ZERO)
    }
}
```

两段的差别就是金字塔的差别：上面问「契约对不对」，下面问「规则对不对」。**规则用 fake 测，契约用切片测，中间不要混**。用 mock 测规则会得到一堆 `verify(repo).save(any())`，它证明的是「你按你写的方式调用了自己」，不是「规则正确」。

**取舍**：手写 fake 比 mock 多花 20 分钟，但它能在整个测试类里复用、能模拟「重复插入报唯一键冲突」这类真实行为，而且读代码的人不用在脑子里重构 mock 的返回序列。依赖超过 3 个时再考虑 mock——那通常说明该拆类了。

## 5. 测试数据的可读性

测试代码的读者是「三个月后排查失败的人」，他的问题是：**这个测试到底在断言哪几个字段？** 满屏 12 个参数的对象构造会把答案埋掉。

```kotlin
object OrderMother {

    fun pending(
        customer: CustomerId = CustomerId("c-default"),
        total: Money = Money.of("100.00", "CNY"),
        coupon: String? = null,
        items: List<OrderItem> = listOf(OrderItem("A-1", 1, Money.of("100.00", "CNY"))),
    ) = Order(
        id = OrderId("o-1"),            // 固定值：失败信息可读、可 grep
        customerId = customer,
        total = total,
        couponCode = coupon,
        items = items,
        status = OrderStatus.PENDING,
        createdAt = Instant.parse("2026-11-15T10:00:00Z"),
    )
}
```

三条规约：

1. **默认值要有意义**：默认值构成「一个合法的普通订单」，测试里只写它关心的那两三个参数，读者一眼看到变量。
2. **随机值要可控**：`UUID.randomUUID()` 会让失败信息不可复现、日志无法 grep。要么固定，要么从注入的 `IdGenerator` 拿。
3. **时间必须注入**：`Clock` 而不是 `Instant.now()`。否则「跨天优惠券失效」这类测试会在半夜随机挂，成为 CI 里的幽灵。

**坑**：Object Mother 用久了会长成一个巨型工厂（`anyOrder()` 带 20 个开关）。控制方式是「一个场景一个方法」——`pending()`、`paid()`、`shippedWithRefund()`，而不是 `anyOrder(status = ..., refunded = ..., coupon = ...)`。名字即场景，读测试的人不用拼装。

## 6. 一个测试只断言一个行为

「一个行为」不等于「一个 `assert`」。判据是：**当第一个断言失败时，后面的断言是否还有诊断价值**。

```kotlin
// 一个行为：下单成功后的四个可观察结果，属于同一件事
@Test
fun `placing an order returns 201 with location and persists a pending order`() {
    val response = client.post("/api/orders", body = """{"sku":"A-1","quantity":2}""")

    assertThat(response.statusCode).`as`("创建应返回 201").isEqualTo(HttpStatus.CREATED)
    assertThat(response.headers.getFirst("Location")).`as`("必须给出新资源地址").isNotNull()
    assertThat(response.body).`as`("返回体只含 id 与 status").containsOnlyKeys("id", "status")
    assertThat(orders.count()).`as`("必须落库一条 PENDING 订单").isEqualTo(1)
}
```

这四条断言描述的是「一次成功的创建」这一件事，任何一条挂了都指向同一个修复方向，可以放在一起。而下面这种就要拆：

```kotlin
@Test
fun `order api behaves correctly`() {          // 反例：三件事挤在一起
    assertThat(post(validBody).statusCode).isEqualTo(201)
    assertThat(post(invalidBody).statusCode).isEqualTo(400)   // 第二个行为
    assertThat(get("/api/orders/o-1").statusCode).isEqualTo(200)  // 第三个行为
}
```

第一个失败会掩盖后两个，你修完跑一遍又挂，一轮 CI 只推进一格。

**失败信息的设计**：断言要回答三个问题——期望什么、实际什么、为什么这个期望重要。

| 写法 | 失败时看到 | 问题 |
|---|---|---|
| `assertTrue(list.size == 3)` | `expected true but was false` | 完全无信息 |
| `assertEquals(3, list.size)` | `expected 3 but was 2` | 有数字，无原因 |
| `assertThat(list).hasSize(3)` | 打印整个集合 | 好，但没说业务含义 |
| `assertThat(list).describedAs("扣减后只剩两条流水，重复请求不应产生第三条").hasSize(3)` | 业务原因 + 实际内容 | 最佳 |

## 7. 测试执行时间治理

Spring 测试慢在两处：**上下文启动**和**上下文重建**。前者靠切片解决，后者靠纪律解决。

```kotlin
// build.gradle.kts
val integrationTest by tasks.registering(Test::class) {
    description = "需要 Docker 的集成测试"
    testClassesDirs = sourceSets["integrationTest"].output.classesDirs
    classpath = sourceSets["integrationTest"].runtimeClasspath
    useJUnitPlatform()
    maxParallelForks = 1          // Testcontainers 抢端口，别并发抢容器
    timeout.set(Duration.ofMinutes(15))
}

tasks.test {
    useJUnitPlatform()
    maxParallelForks = (Runtime.getRuntime().availableProcessors() / 2).coerceAtLeast(1)
    exclude("**/*IT.class")       // 单测 task 里绝不能混进集成测试
}
```

四条治理手段，按收益排序：

1. **切 task 分层执行**：`test` 只跑单测与切片（本地每次保存都能跑），`integrationTest` 在 PR 阶段跑。混在一起的结果是「本地太慢不跑，CI 太慢被跳过」。
2. **并行**：JUnit 5 的 `junit.jupiter.execution.parallel.enabled=true` 对纯单测收益最大；Spring 测试并行时要小心 `@DirtiesContext` 与静态可变状态。
3. **别滥用 `@DirtiesContext`**：它会把整个上下文丢掉重建，一次 1~3 秒。它经常被用来掩盖「上一个测试改了共享状态」——真正的修法是把状态收进测试自己创建的 fixture，或者把可变依赖换成 `@MockitoBean`（每个方法后自动重置）。
4. **盯住 context cache 的 key**：Spring 按「配置组合」缓存上下文。你在 A 类用 `@MockitoBean` 换掉 `OrderService`、B 类不换，就是两个上下文、两次启动。测试类之间的注解差异越大，缓存命中率越低。

| 症状 | 原因 | 处理 |
|---|---|---|
| 单个测试类 30s+ | 用了 `@SpringBootTest` 但只测一个 Controller | 换 `@WebMvcTest` |
| 测试数增加但时间线性涨 | 每个类一个上下文（注解组合各不相同） | 统一注解组合，提高缓存命中 |
| 偶发失败、重跑就好 | 共享静态状态、`Instant.now()`、端口冲突 | 注入 `Clock`、清静态状态、改用随机端口 |
| 加一个测试慢 2s | `@DirtiesContext` | 找它想掩盖的状态污染 |
| `test` task 里有 Docker 依赖 | 包名/后缀没隔离 | 用 source set 或 `exclude` 切干净 |

## 8. 自测

1. 一个 Service 有 6 个依赖，你写不出单测只能起全量容器——这更像是测试问题还是设计问题？给出两种改法。
2. `@WebMvcTest` 里注入 `OrderService` 失败，报「No qualifying bean」。为什么这是预期行为？要测 Controller 与 Service 的协作该换哪个注解？
3. `@DataJpaTest` 在 PG 上测一条带 `jsonb` 列的查询，测试全绿但线上报类型错误，最可能漏了哪个注解？
4. `@MockitoBean` 相比 `@MockBean` 在「依赖它的 Bean 拿到的是不是 mock」这件事上，为什么更可靠？
5. 下面这条断言失败时你会得到什么信息，怎么改：`assertTrue(order.items.size == 2)`。
6. 团队 CI 里 `test` task 要跑 8 分钟，报告显示 12 个 `@SpringBootTest` 类合计占 6 分钟。列出三个按收益排序的改法。
