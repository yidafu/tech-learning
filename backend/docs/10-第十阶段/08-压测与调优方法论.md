# 08. 压测与调优方法论

> [← 第十阶段导览](01-导览.md) · 压测不是「把 QPS 打上去看看能扛多少」，而是一次**带假设的实验**：先定目标，再固定变量，再按固定顺序排除，每一轮只改一处并留下数字。没有方法论的压测，产出的是一张好看的图和一个错误的结论。

## 1. 先定目标，再开压

压测报告里最没用的一句话是「系统能扛 800 QPS」。扛得住什么？P99 多少？错误率多少？数据有多少行？没有这四个约束，数字没有意义。

| 目标项 | 怎么定 | 例子 |
|---|---|---|
| 目标 QPS | 线上峰值 × 1.5~2（留突发余量） | 峰值 600 → 目标 1000 |
| 可接受 P99 | 由 SLA 倒推，不是「越低越好」 | 接口 SLA 200ms → 目标 P99 ≤ 150ms |
| 错误率上限 | 通常 0.1%，资金类要 0 | `rate < 0.001`，5xx 一律视为失败 |
| 数据规模 | 与线上同量级，否则索引与执行计划都不真实 | 订单表 500 万行、单用户 200 单 |
| 场景比例 | 按真实流量分布，不是只压一个接口 | 读:写 = 9:1，热门 SKU 占 60% |
| 资源上限 | 明确「跑在几核几 G 上」 | 4C8G × 2 实例 |

**为什么数据规模必须写进目标**：1000 行的表全表扫也只要 1ms，500 万行的表缺索引就是 800ms。用空库压出来的 P99 是假的，而且假得很危险——它让你以为「不需要加索引」。

**为什么 P99 而不是平均值**：平均值会把 1% 的 3 秒请求摊薄成 30ms 的「提升」。用户感知的是尾部，SLA 罚的也是尾部。

**取舍**：目标定太高（比如 P99 ≤ 50ms）会逼你做过早优化，把系统改成缓存满天飞的样子，一致性成本远超收益。目标应该来自「业务能不能接受」，而不是「隔壁团队做到了多少」。

## 2. 工具与场景设计

| 工具 | 语言/模型 | 强项 | 弱项 | 适合 |
|---|---|---|---|---|
| `wrk` | C，多线程 + epoll | 单机吞吐极高、开销极小 | 脚本能力弱（Lua）、报告粗糙 | 摸单接口吞吐上限、验证「机器能打多快」 |
| `Gatling` | Scala DSL，JVM | 场景表达力强、HTML 报告好 | 压测机自身吃 JVM 资源，高并发时互相干扰 | 复杂业务链路、需要可读报告 |
| `k6` | Go + JS 脚本 | 单机性能好、脚本灵活、原生 Prometheus/阈值 | 复杂协议支持一般 | 现代默认选择，CI 里跑回归压测 |

不管用哪个，四个设计约束：

1. **压测机不能成为瓶颈**。开压前先看压测机的 CPU、网络、`TIME_WAIT` 数量。单台 k6 打简单 GET 大概能到几万 RPS；一旦你要打 5 万 QPS，压测机先趴下，你测到的是它的上限。判断方法：同时压两个目标实例，看总 QPS 是否线性增长。
2. **warmup 必须单独一段**。JIT 需要几万次调用才编译到最优，连接池要扩到稳态，缓存要热。丢掉前 30~60 秒的数据，否则 P99 里混着「编译期」的假慢。
3. **采样时长 ≥ 3 分钟**。GC、定时任务、日志滚动都是分钟级的周期现象，30 秒的样本可能刚好躲过一次 Full GC。
4. **场景比例要真**。只压一个「按 ID 查订单」的接口，会得到一条漂亮曲线和一个错误结论——线上的慢是慢在「列表页 + 聚合 + 排序」。

```javascript
// k6: 稳态 + 阶梯加压，带阈值断言
import http from 'k6/http';
import { check } from 'k6';

export const options = {
  scenarios: {
    steady: {
      executor: 'ramping-arrival-rate',
      startRate: 50, timeUnit: '1s',
      preAllocatedVUs: 200, maxVUs: 1200,
      stages: [
        { target: 200, duration: '1m' },   // 爬坡（含 warmup）
        { target: 200, duration: '5m' },   // 稳态观察
        { target: 1000, duration: '3m' },  // 找拐点
      ],
    },
  },
  thresholds: {
    http_req_failed: ['rate<0.001'],
    http_req_duration: ['p(99)<150'],
  },
};

export default function () {
  const res = http.get(`${__ENV.BASE}/api/orders/o-1`, {
    headers: { 'Accept': 'application/json' },
  });
  check(res, { 'status is 200': (r) => r.status === 200 });
}
```

`ramping-arrival-rate` 而不是 `constant-vus`：前者控制「每秒发起多少请求」，后者控制「多少并发」。压测要的是「在 200 QPS 下系统表现如何」，用并发数控制会得到「并发 100 时 QPS 恰好 180」这种无法解释的结果。

**压测环境与生产环境的四个差异**，每一个都会让数字失真：

| 差异 | 失真方向 | 处理 |
|---|---|---|
| 只压 1 个实例（或压全集群） | 单实例看上限，全集群看总和；混着看会掩盖单实例的串行点 | 先单实例压到拐点，再全集群验证线性度 |
| 数据量小（空库或 1 万行） | 索引与执行计划都不真实，测出来偏快 | 灌到线上同量级（500 万行），并按真实热点分布 |
| 网络同机房、无跨区调用 | 忽略了 RTT，测出来偏快 | 至少把跨区依赖的 RTT 用 Toxiproxy 加上（04 册） |
| 依赖被桩替换 | 下游的慢与错被隐藏，测出来偏快 | 压测的目标链路要用真下游，或在桩里注入真实 P99 |

## 3. 瓶颈定位的固定顺序

顺序的价值在于**排除法**。每一层都会伪装成上一层的症状：GC 频繁会让 CPU 变高，连接池等待会让 CPU 看起来很闲，数据库锁等待会让连接池耗尽。所以按「最便宜、最能证伪」的顺序走：

| # | 层 | 看什么数据 | 工具 | 判定信号 |
|---|---|---|---|---|
| 1 | CPU | 使用率、每核分布、上下文切换 | `top -H`、火焰图 | 单核打满 = 有串行点；整体 90%+ = 算不过来 |
| 2 | GC | 停顿时间、频率、分配速率、晋升量 | `jvm.gc.pause`、JFR、GC 日志 | 停顿 > 50ms 或占比 > 5% |
| 3 | 连接池 | `pending`、`active`、获取连接耗时 | `hikaricp.connections.*` | `pending > 0` 持续出现 |
| 4 | 数据库 | 慢查询、`pg_stat_activity` 等待事件、锁 | `pg_stat_statements`、`EXPLAIN ANALYZE` | DB CPU 高 / 大量 `Lock` 等待 |
| 5 | 应用锁与串行点 | `BLOCKED` 线程数、锁竞争火焰 | 线程 dump、`asprof -e lock` | CPU 不高但吞吐上不去 |

**第 1 步为什么要区分「CPU 型」与「等待型」**：CPU 打满说明算力不够，方向是减少计算（缓存、批量化、少拷贝）；CPU 只有 40% 却 P99 很高，说明线程在等（下游、锁、连接），方向完全不同。搞错这一步，后续全白做。

**第 2 步为什么在连接池之前**：GC 停顿会让所有请求同时变慢，包括那些根本不碰数据库的请求。如果先怀疑连接池，你会看到 `pending` 也确实 > 0——因为 GC 期间没人释放连接。顺序反了，就会去调大池子，而真正的问题在堆上。

**第 5 步为什么放最后**：应用锁最难看见。它表现为「CPU 利用率上不去、QPS 上不去、延迟随并发线性上涨」，三种工具都不直接指向它，只有线程 dump 里一串 `BLOCKED` 才露馅。

## 4. 一次完整案例：200 QPS P99 800ms → 1000 QPS P99 150ms

基线：4C8G × 2 实例，PG 17（4C16G），订单表 500 万行。目标：1000 QPS、P99 ≤ 150ms、错误率 < 0.1%。

**R0 基线（固定 200 QPS）**：P99 820ms，CPU 35%，GC 占比 1.8%，`hikaricp.connections.pending` 峰值 0，**DB CPU 92%**，每请求 **41 条 SQL**。

第一个判断：CPU 不高、DB 打满、单请求 41 条 SQL——这是典型的 N+1，不是 CPU 问题。

**R1 只改一件事：把 N+1 改成批量查询。**

```kotlin
// 反例：1 次订单查询 + 40 次明细查询
fun load(id: OrderId): OrderView {
    val order = orderRepository.findById(id).orElseThrow()
    val items = order.itemIds.map { itemRepository.findById(it).orElseThrow() }  // 40 条
    return OrderView(order, items)
}

// 正解：一次 IN 查询 + 内存拼装
fun load(id: OrderId): OrderView {
    val order = orderRepository.findById(id).orElseThrow()
    val items = itemRepository.findAllById(order.itemIds)   // 1 条
        .associateBy { it.id }
    return OrderView(order, order.itemIds.map { items.getValue(it) })
}
```

结果：41 条 → 3 条 SQL，P99 **820 → 240ms**，DB CPU **92% → 45%**，CPU 35% → 33%。

**R2 只改一件事：连接池 10 → 30**（此时 `pending` 峰值出现 12，说明有请求在等连接）。

P99 **240 → 180ms**，`pending` 归零，DB CPU 48%。注意：**池不是越大越好**，30 是「DB 侧还能承受」的上限；盲目调到 100 会把 PG 的 CPU 打到 100%，延迟反而更差。

**R3 只改一件事：去掉全局锁。**

```kotlin
// 反例：所有请求串行经过一把锁，8 核也只能用一个核
private val lock = Any()
private var totalCreated = 0L

fun onCreated() = synchronized(lock) { totalCreated++ }

// 正解：无锁累计 + 定期快照
private val totalCreated = LongAdder()

fun onCreated() { totalCreated.increment() }
```

结果：P99 **180 → 150ms**，CPU 从 33% 涨到 41%（终于用上多核了），DB 不变。**目标 A 达成：200 QPS、P99 150ms。**

**R4 加 QPS 到 500**：P99 220ms，GC 占比升到 8%，CPU 62%。火焰图显示 `Jackson` 序列化与 `byte[]` 拷贝占 30%。改动：把「先序列化成 String 再写 byte[]」改为直接流式写。

结果：P99 **220 → 130ms**，GC 8% → 4%，CPU 62% → 70%。

**R5 加到 1000 QPS**：P99 150ms，CPU 78%，DB CPU 65%，2 个实例各扛 500 QPS。

| 轮次 | 改动 | 压测 QPS | P99 | CPU | GC | DB CPU |
|---|---|---|---|---|---|---|
| R0 | 基线 | 200 | 820ms | 35% | 1.8% | 92% |
| R1 | N+1 → 批量 | 200 | 240ms | 33% | 1.5% | 45% |
| R2 | 池 10 → 30 | 200 | 180ms | 33% | 1.5% | 48% |
| R3 | 去全局锁 | 200 | 150ms | 41% | 1.6% | 48% |
| R4 | 序列化零拷贝 | 500 | 130ms | 70% | 4% | 60% |
| R5 | 加实例/加负载 | 1000 | 150ms | 78% | 4.5% | 65% |

**这张表的读法**：每一行只与上一行差一个变量，所以「P99 降了 580ms」可以归因到那一处改动。这就是「每轮只改一个变量」的全部意义——否则你永远在猜是哪一处生效了。

### 4.5 从压测数字到容量规划

调优的终点不是「P99 150ms」，而是「我需要几个副本、几个数据库连接」。算法只有三步：

```text
1. 单实例安全 QPS = P99 达标时的 QPS × 0.7        （留 30% 余量，覆盖 GC 与突发）
2. 副本数 = ceil(峰值 QPS / 单实例安全 QPS)
3. 校验故障域：挂掉一个副本后，剩余容量是否仍 ≥ 峰值
```

代入本例：单实例 500 QPS 时 P99 150ms → 安全值 350；峰值 1000 → `ceil(1000/350) = 3` 个副本。但第 3 步不过：3 副本挂 1 个，剩 2 × 350 = 700 < 1000，发布或故障时必然过载。所以要么 4 副本（1400 余量），要么接受「故障时降级」。**这一步经常被跳过，然后故障当天才发现「设计上就扛不住」。**

连接池要跟着副本数一起算：每副本 30 连接 × 4 副本 = 120，PG 的 `max_connections` 是 200，留 80 给运维连接与批处理——刚好够，但再加一个服务就不够了。**池大小从来不是单实例的事**，它是「实例数 × 每实例池」的总账。


## 5. 火焰图的读法

```bash
# JFR：低开销（~1%），适合生产与长时间录制
java -XX:StartFlightRecording=settings=profile,filename=/tmp/app.jfr,duration=120s -jar app.jar
jfr view hot-methods /tmp/app.jfr
jfr view gc-pauses /tmp/app.jfr

# async-profiler：采样更密，锁与分配有专门模式
asprof -e cpu -d 60 -f /tmp/cpu.html <pid>
asprof -e lock -d 60 -f /tmp/lock.html <pid>
asprof -e alloc -d 60 -f /tmp/alloc.html <pid>
```

读法四条：

1. **横轴是样本占比，不是时间**。一帧越宽，说明采样落在它上面的次数越多。
2. **找「宽而平」的顶部帧**：叶子帧（self time）宽，说明时间花在它自己身上（比如 `memcpy`、`String.format`、正则回溯）。这种帧最容易优化。
3. **找「多分支共享的底部帧」**：如果 `ObjectMapper.writeValue` 下面所有分支都很宽，说明瓶颈是整体序列化，不是某个具体类型。
4. **颜色没有语义**（async-profiler 的配色只是视觉区分）。别从颜色推断 Java/Kernel。

**坑**：`-e cpu` 只采样「running」状态，线程在等锁、等 IO 时不算 CPU。所以「CPU 火焰图看不出热点，但 P99 很高」是正常的——此时要换 `-e lock` 或 `-e wall`，wall 模式按墙钟采样，能看见阻塞。

## 6. 调优报告的结构

一份能被别人复用的报告，结构固定为五段：

| 段落 | 内容 | 反例 |
|---|---|---|
| 假设 | 你怀疑瓶颈在哪，为什么 | 「系统有性能问题」 |
| 方法 | 压测场景、数据规模、每轮改了什么 | 「做了优化」 |
| 数字 | 每轮的 QPS/P99/错误率/资源 | 「性能提升明显」 |
| 结论 | 哪处改动贡献了多少，还有多少余量 | 「优化完成」 |
| 遗留风险 | 没解决的、下次会先炸的 | 省略 |

**遗留风险这一段最有价值**，因为它决定了下一次故障的形状。本例的遗留风险应该写：

- DB CPU 65%，单实例上限约 600 QPS；再扩容要先评估 PG 的写放大。
- 池 30 是按 1000 QPS 调的，若 P99 上涨到 300ms，池会再次成为瓶颈（并发 = QPS × 时延）。
- 未压测「缓存失效」场景（Redis 整体不可用时回源会把 DB 打穿）。

最后一条带出一个公式，值得单独记：**连接池需要的并发 ≈ QPS × 单请求持有连接的时间**。200 QPS × 5ms = 1；1000 QPS × 30ms = 30。P99 一涨，池就不够——所以调池大小必须和延迟目标一起定。

## 7. 「指标异常 → 下一步查什么」

| 观察到的 | 最可能的方向 | 下一步 |
|---|---|---|
| CPU 95%、QPS 上不去 | 计算密集或串行点 | 火焰图看热点；`top -H` 看是否单核打满 |
| CPU 40%、P99 高 | 等待型（IO/锁/池） | 看 `pending`、下游耗时、`-e wall` |
| GC 停顿 200ms+ | 堆过大或晋升过快 | 看分配速率与老年代曲线；考虑分代/区域大小 |
| GC 占比 10%+ 但停顿不大 | 分配率过高 | `-e alloc` 找分配热点，减少临时对象 |
| `hikaricp.connections.pending > 0` | 池小或连接被长事务占住 | 先看连接持有时间分布，再决定加池还是拆事务 |
| DB CPU 90% | 慢查询/缺索引/N+1 | `pg_stat_statements` 按总耗时排序，`EXPLAIN ANALYZE` 验证 |
| 线程大量 `BLOCKED` | 应用锁争用 | `-e lock`，找锁对象与持有者 |
| QPS 不涨、延迟线性涨 | 队列或串行点 | 看线程池 `queued`、Tomcat `busy` 线程数 |
| 错误率突增伴随超时 | 下游或资源耗尽 | 看 `http.client.requests` 的 P99 与 `executor.active` |

## 8. 自测

1. 为什么「能扛 800 QPS」这个结论没有意义？补上哪四个约束才有意义？
2. 压测机自己成了瓶颈时，症状是什么？怎么用一次实验确认？
3. CPU 只有 40% 而 P99 很高，你要查的三样东西是什么？为什么先不看 GC？
4. 为什么连接池大小必须和 P99 一起定？给出「1000 QPS × 30ms」下的估算。
5. 火焰图上 `-e cpu` 看不出热点，但接口很慢。可能是什么原因？换哪个采样模式？
6. 一轮调优把 P99 从 800ms 降到 240ms，但同时改了三处。这份报告缺了什么，导致结论不可信？
