# 05. 可观测性落地：指标、日志与链路

> [← 第十阶段导览](01-导览.md) · 三类信号不是「都装上就安心」，而是**三种不同的提问方式**：指标问「有没有问题」（便宜、可聚合、可告警），日志问「问题是什么」（有上下文、贵），链路问「问题在哪一跳」（跨服务、有采样）。本册只讲在 Spring Boot 里怎么接、怎么配、哪里会断——原理体系归可观测性站。

## 1. 三类信号的分工与成本

| 维度 | 指标 Metrics | 日志 Logs | 链路 Traces |
|---|---|---|---|
| 数据结构 | 时间序列（名字 + 标签 + 值） | 离散事件文本 | 树状 span |
| 成本 | 极低（每分钟一个点） | 高（每请求几 KB，还要存储与索引） | 中（按采样率线性） |
| 能否聚合 | 原生支持 | 只能靠日志系统 | 只能聚合「按服务/操作」的统计 |
| 典型问题 | 「错误率涨了吗」「P99 多少」 | 「这个订单为什么失败」 | 「慢在 DB 还是下游」 |
| 保留期 | 数月~数年（降采样） | 7~30 天 | 数天~数周 |
| 采样 | 不需要 | 全量或按级别 | 必须（1%~10%） |
| 判定「出问题」 | 是，唯一适合告警的 | 可做异常计数，噪声大 | 否 |

**为什么顺序是「指标 → 链路 → 日志」**：指标秒级返回，用标签圈定「哪个接口、什么状态码、什么时候开始」；链路把范围缩到「哪一跳」；日志用 `traceId` 取出那一跳的完整上下文。反过来先翻日志，等于在几个 GB 文本里做全文搜索，还得先猜关键词。

**成本纪律**：日志最贵。一个 1000 QPS 的服务，每请求打 2KB 日志 = 每天 170GB。「日志要有用」不是审美问题，是账单问题。

「先看哪个信号」要练成条件反射：

| 症状 | 先看（圈定范围） | 再看（拿细节） |
|---|---|---|
| 错误率上涨 | 指标：按 `uri`/`status` 拆分，找到接口与起始时间 | 链路：失败 span 停在哪一跳；日志：按 `traceId` 取现场 |
| P99 涨但错误率正常 | 指标：`http.client.requests` 各下游的分位对比 | 链路：慢在哪个 span；日志：该跳的耗时上下文 |
| 单个用户投诉 | 日志：按 `userId`/`traceId` 检索 | 链路：完整链路；指标：确认是否已成整体异常 |
| 消息积压、消费停止 | 指标：lag 与 `executor.queued` | 日志：消费异常与再均衡记录 |

## 2. 指标：命名与低基数

Micrometer 的命名规约：**小写点分，`<系统>.<对象>.<动作>`，单位只放在后缀（`_seconds` / `_bytes`），不要塞进名字**。Micrometer 会按后端做转换：Prometheus 把 `http.server.requests` 转成 `http_server_requests_seconds`，并自动加 `_total` 计数后缀、`_bucket` 直方图后缀。

Boot 自动提供的核心指标（先知道有什么，再决定加什么）：

| 指标 | 类型 | 关键标签 | 用来回答 |
|---|---|---|---|
| `http.server.requests` | timer | `method`、`uri`、`status`、`outcome`、`exception` | 流量、错误率、延迟分位 |
| `http.client.requests` | timer | `client.name`、`uri`、`status` | 下游依赖的健康与耗时 |
| `jvm.gc.pause` | timer | `cause`、`action` | GC 是否在拖延迟 |
| `jvm.memory.used` | gauge | `area`、`id` | 是否泄漏、是否接近上限 |
| `hikaricp.connections.pending` | gauge | `pool` | 拿不到连接（池满的第一信号） |
| `executor.active` / `executor.queued` | gauge | `name` | 线程池是否堆积 |
| `spring.data.repository.invocations` | timer | `repository`、`method` | 哪类查询慢 |

**低基数是硬约束，不是建议**：时序库为每个「标签组合」维护一条独立的时间线。`uri=/orders/12345` 有 10 万个取值就是 10 万条时间线，一个月后你的 Prometheus 因为 OOM 挂掉，而监控系统本身挂掉意味着你连「为什么挂」都看不到。

| 标签 | 可以放 | 绝对不能放 |
|---|---|---|
| `uri` | 路由模板 `/orders/{id}` | 原始路径 `/orders/8f3a...` |
| `status` | `200`、`500` | 完整响应体 |
| `user` | —（不要有） | `userId`、`email`、手机号 |
| `error` | 异常类名（有限集合） | 异常 message（含变量） |
| `tenant` | 只有租户数 < 50 时才考虑 | 每用户一个租户 |

需要按用户维度排查时，正确工具是**日志与链路**（它们有 `traceId` 可以精确检索），不是指标。指标回答的是「整体有没有异常」，不是「张三遇到了什么」。

**坑**：`@Timed` 默认用「类名.方法名」做指标名、不支持动态标签，容易造出几百个只出现一次的指标；需要标签时用 `MeterRegistry` 手工建，或改用 `@Observed` + `Observation`（同一套 API 同时产出指标与 span）。

## 3. 业务指标怎么埋

技术指标（HTTP、GC、连接池）告诉你「服务累不累」，业务指标告诉你「生意有没有异常」。一个只监控 CPU 的团队，会在「支付成功率从 99% 掉到 40%」时毫无察觉——因为 CPU 很闲。

三种仪器选型：

| 仪器 | 语义 | 例子 | 别用来做 |
|---|---|---|---|
| `Counter` | 只增的累计量 | 创建订单数、失败数、重放命中数 | 任何会减少的量（用 gauge） |
| `Timer` | 次数 + 耗时分布 | 支付校验耗时、下游调用耗时 | 非时间量 |
| `DistributionSummary` | 次数 + 数值分布 | 订单金额、响应体大小、批量条数 | 时间（用 Timer） |
| `Gauge` | 瞬时值（回调式） | 队列积压、缓存条目数 | 累计量 |

```kotlin
@Component
class OrderMetrics(registry: MeterRegistry) {

    private val created: Counter = Counter.builder("orders.created")
        .description("成功创建的订单数")
        .register(registry)

    // 金额分布：业务侧最需要的「分位」不是 P99 耗时，而是「大额订单占比」
    private val amount: DistributionSummary = DistributionSummary.builder("orders.amount")
        .baseUnit("yuan")
        .publishPercentileHistogram()
        .serviceLevelObjectives(100.0, 500.0, 2_000.0, 10_000.0)
        .register(registry)

    fun onCreated(money: Money) {
        created.increment()
        amount.record(money.toYuan())
    }

    // 标签值来自枚举，基数天然有限；绝不能把异常 message 拼进标签
    fun onRejected(reason: RejectReason) {
        registry.counter("orders.rejected", "reason", reason.name).increment()
    }
}
```

**为什么用直方图而不是客户端算分位**：`publishPercentileHistogram()` 让客户端吐出桶（bucket），Prometheus 用 `histogram_quantile()` 在**查询时**聚合出跨实例的 P99。如果客户端直接上报 `p99=120ms`，你只能对 10 个实例的 p99 求平均——数学上毫无意义（P99 不可平均）。这是「指标落地」里最常见的错误。

```yaml
management:
  metrics:
    distribution:
      percentiles-histogram:
        http.server.requests: true
      slo:
        http.server.requests: 50ms,200ms,500ms,1s
```

`slo` 那一行生成 `_bucket{le="0.5"}` 这类精确边界，让你能直接写「500ms 内完成的比例」这个 SLO 查询，而不是被默认桶边界（1ms/10ms/100ms/1s）坑到算不出 500ms。

**取舍**：直方图不是免费的——默认 70 多个桶 × 每个标签组合，时间线数量翻几十倍。做法是只给**关键接口**开直方图（用 `management.metrics.distribution.percentiles-histogram.http.server.requests` 全局开会很贵，可以按 meter 名单独配），其余接口只要 count/sum/max。

## 4. 结构化日志

JSON 日志的唯一目的是「可被机器按字段检索」。Boot 4 内置支持，不用引入 logstash encoder：

```yaml
logging:
  structured:
    format:
      console: ecs          # 也可用 logstash / gelf
  level:
    root: INFO
    com.example.order: INFO
```

输出里固定带上的字段（缺一个，排障时就少一条线索）：

| 字段 | 谁填 | 用途 |
|---|---|---|
| `traceId` / `spanId` | Micrometer Tracing 自动注入 MDC | 从链路跳到日志的唯一钥匙 |
| `tenantId` | 你的过滤器（从 token/header 解析） | 多租户隔离排查 |
| `userId` | 你的过滤器（脱敏后的内部 ID） | 「这个用户报错了」时唯一能用的检索键 |
| `event` | 手写（`order.created`） | 让日志可被聚合，而不是纯文本 |
| `durationMs` | 手写 | 慢请求的现场证据 |

**级别纪律**（比格式更重要）：

- `ERROR` 只用于「需要人介入」的事：资金不一致、数据丢失、外部依赖持续失败。**每个 ERROR 都应该有对应的告警或工单**，否则它就是个噪音。
- `WARN` 用于「自动恢复了，但值得看一眼」：重试成功、降级兜底命中、幂等重放。
- `INFO` 用于状态变迁：订单创建、支付成功。一条业务事件一条日志，不要在一个请求里打 20 条「进入方法 A/B/C」。
- `DEBUG` 用于开发期；生产打开前先想清楚它的量。

**三条禁令**：

1. **不要打全量请求/响应体**。里面有手机号、身份证、token、Cookie。真需要时打「字段名 + 长度 + hash」，或走脱敏采样。
2. **不要在循环里打日志**。批量处理 1000 条，日志量是 1000 倍，而且第一条之后的都没人看。
3. **不要用字符串拼接**。用参数化（`log.info("order created id={}", id)`），否则未开启的级别也在做拼接与 `toString()`——这是常见的「日志拖慢接口」原因。

**坑**：MDC 是 ThreadLocal，**异步一交给别的线程就丢**。这不是配置问题，是模型问题（见 §6）。

## 5. 链路：Boot 4 的模块拆分与 OTel 接入

Boot 4 把 tracing 自动配置从核心拆成了独立模块，这件事必须说清，因为 3.x 的依赖写法在 4.x 会静默少一半功能：

| 模块 | 内容 | 作用 |
|---|---|---|
| `spring-boot-micrometer-tracing` | 抽象层自动配置（`Tracer`、`Observation` 集成、采样） | 必须有，其他模块依赖它 |
| `spring-boot-micrometer-tracing-brave` | Brave 桥接 + Zipkin 上报 | 老系统/已有 Zipkin 时选它 |
| `spring-boot-micrometer-tracing-otel` | OpenTelemetry 桥接 + OTLP 上报 | 新系统默认选它 |

桥接实现**只能选一个**（`micrometer-tracing-bridge-brave` 与 `micrometer-tracing-bridge-otel` 同时存在会启动失败），上报器可以多个。最小接入：

```yaml
management:
  tracing:
    sampling:
      probability: 0.1          # 生产 10%，压测/排障时临时调 1.0
  otlp:
    tracing:
      endpoint: http://otel-collector:4318/v1/traces
  # 给所有 observation 加公共低基数标签（会同时进指标与 span）
  observations:
    key-values:
      service: order-service
```

`management.tracing.sampling.probability` 是**入口采样**：父级已采样的请求必然采样（保证一条链路完整），所以 10% 的入口采样得到的是完整的 10% 请求，不是断断续续的碎片链路。

**为什么一定要接 OTLP 而不是直接写 Zipkin**：OTLP 是出口标准，collector 负责采样二次处理、扇出到多个后端、脱敏。应用只认一个出口，换后端不用改代码。

**坑**：采样率与「错误必采」的冲突。10% 采样下，一个 500 错误有 90% 概率没有被记录——而错误恰恰是最需要看的那条。解法是「尾部采样」（在 collector 里配：错误/慢请求全留），不是把应用采样率调到 100%。

## 6. 五个链路断裂点

链路断裂的本质只有一个：**上下文存在 ThreadLocal 里，而工作换了线程**。Micrometer 的 `Observation` 上下文不会自动跨线程，必须显式传播。

| 断裂点 | 症状 | 传播写法 |
|---|---|---|
| 线程池提交 | 子线程的日志没有 `traceId`，链路里多出一棵新树 | 给 `ThreadPoolTaskExecutor` 配 `TaskDecorator`（`ContextSnapshot.captureAll()`） |
| `@Async` | 同上，且更难发现（注解看不见线程池） | 给 `@Async` 用的那个 executor 配同一个 decorator |
| 消息生产 | 消费端的链路是独立树，与生产端无关 | 开 `spring.kafka.template.observation-enabled`，让 traceparent 进 header |
| 消息消费 | 消费端日志缺 `traceId` | 开 `spring.kafka.listener.observation-enabled`，从 header 提取父上下文 |
| `CompletableFuture` | `supplyAsync` 后链路断 | `ContextSnapshot.wrap()` 包住 supplier，或用 `ContextExecutorService` |
| 协程调度 | `withContext(Dispatchers.IO)` 后 MDC 与 span 都丢 | `MDCContext()` 保日志字段；协程边界用 `ContextSnapshot` 或手写 `Observation` |

```kotlin
@Configuration
class AsyncConfig {

    // 关键：一个 decorator 同时传播 MDC（日志字段）与 Observation（trace/span）
    @Bean
    fun mdcAndTracePropagatingDecorator() = TaskDecorator { runnable ->
        val snapshot = ContextSnapshot.captureAll()      // 捕获当前线程的全部 ThreadLocal
        Runnable {
            val scope = snapshot.setThreadLocals()       // 子线程安装上下文
            try {
                runnable.run()
            } finally {
                scope.close()                            // 必须还原，否则线程复用时串上下文
            }
        }
    }

    @Bean("orderExecutor")
    fun orderExecutor(decorator: TaskDecorator): ThreadPoolTaskExecutor =
        ThreadPoolTaskExecutor().apply {
            corePoolSize = 8
            maxPoolSize = 32
            queueCapacity = 500
            setTaskDecorator(decorator)
            setThreadNamePrefix("order-")
        }
}
```

消息侧不需要写代码，但必须开开关——**默认是关的**，这是「装了链路却看不到消息环节」的首要原因：

```yaml
spring:
  kafka:
    template:
      observation-enabled: true     # 生产：把 traceparent 写进 record header
    listener:
      observation-enabled: true     # 消费：从 header 提取父上下文，续上同一条链路
```

协程侧的两个坑要分开处理：

```kotlin
suspend fun enrich(orderId: String): EnrichedOrder = withContext(Dispatchers.IO + MDCContext()) {
    // MDCContext() 只还原 MDC（traceId 能出现在日志里），
    // 但 Observation 的 ThreadLocal 仍需要 ContextSnapshot 或手工建 span
    log.info("enriching order id={}", orderId)     // 这里有 traceId 了
    repository.load(orderId)
}
```

`MDCContext()` 让日志看起来正常了，链路却可能还是断的——**日志有 traceId ≠ 链路接上了**。验证方法是看链路后端里这条 span 的 parent 是不是 HTTP 入口那个 span。

**取舍**：`ContextSnapshot.captureAll()` 每次提交要复制若干 ThreadLocal，通常纳秒级；executor 每秒提交百万任务时值得单独压测一次。

## 7. Actuator 端点安全

Actuator 是「把内部状态暴露出 HTTP」——它的每一个端点都是一个潜在的信息泄露或 RCE 面。`/actuator/env` 能读到配置（含密钥）、`/actuator/heapdump` 能下载整个堆（含内存里的凭据）、`/actuator/shutdown`（若开启）能停服务。

四条措施，缺一不可：

```yaml
management:
  server:
    port: 8081                  # 管理端口与业务端口分离：不经过公网入口
  endpoints:
    access:
      default: none             # 默认全部关闭，只显式开口
    web:
      exposure:
        include: health,prometheus
  endpoint:
    health:
      access: read-only
      probes:
        enabled: true           # 暴露 /health/liveness 与 /health/readiness
      show-details: when-authorized
    prometheus:
      access: read-only
```

| 措施 | 防什么 | 漏掉的后果 |
|---|---|---|
| 独立管理端口 | 公网/网关误转发 | `/actuator/env` 直接可达，密钥泄露 |
| `access.default: none` + 白名单 | 新版本新增端点自动暴露 | 升级 Boot 后突然多出可写端点 |
| `prometheus` 只读 | 抓取方被篡改 | 指标可被伪造，告警失真 |
| 管理端口的网络策略 | 集群内横向扫描 | 内部攻击者拿到堆转储 |

**为什么 `show-details: when-authorized` 而不是 `always`**：`/actuator/health` 的 details 里有数据库地址、磁盘路径、连接池状态。`always` 等于给攻击者一份基础设施清单。

**坑**：探针端点必须走管理端口，反向代理若只转发业务端口，K8s 的 readinessProbe 打到 8080 的 `/actuator/health/readiness` 上就是 404，Pod 永远不 ready。这不是探针配置错，是端口没对齐（详见 07 册）。

## 8. 自测

1. 一个接口 P99 从 80ms 涨到 900ms，CPU 与 GC 都正常。按「指标 → 链路 → 日志」的顺序，你分别查什么？
2. 为什么「每个实例上报自己的 P99，然后取平均」是错的？正确做法需要打开哪个开关？
3. 有人把 `http.server.requests` 的 `uri` 标签设成 `request.requestURI`。一周后监控系统 OOM，解释因果链。
4. 一条业务日志里有 `traceId`，但链路后端里对应的 span 是独立的一棵树。最可能断在哪？怎么验证？
5. `spring.kafka.listener.observation-enabled` 忘了开，症状是什么？为什么生产端的 header 已经写了 traceparent 也没用？
6. 生产环境 `/actuator/env` 返回 200，你现在要做的三件事按什么顺序？
