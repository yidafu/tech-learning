# 第十阶段导览：质量、可观测性与单服务生产化

> [返回：后端开发学习大纲](../后端开发学习大纲.md)
> 本文是第十阶段的入口，也是单服务部分的收官。测试决定你敢不敢改，可观测性决定出事后能不能定位，交付与压测决定它能不能扛住第一个流量高峰。

**建议时长**：2 周。本阶段的验收标准是「敢把这个服务交给别人值班」。

## 分册计划

| 分册 | 内容要点 |
|---|---|
| 02-测试金字塔与切片测试 | 纯单测、`@WebMvcTest`/`@DataJpaTest`、`@MockitoBean` 迁移、测试数据可读性 |
| 03-Testcontainers与契约测试 | 真数据库集成测试、容器复用、消费者驱动契约、测试执行时间治理 |
| 04-并发-幂等与故障注入测试 | 并发一致性测试、幂等重放、故障注入（延迟/异常/断连） |
| 05-可观测性落地-指标-日志与链路 | Micrometer 指标命名、结构化日志、OTel 串联异步与消息、Actuator 端点安全 |
| 06-配置分层与密钥外置 | 多环境配置、动态刷新、配置即代码、密钥不进仓库 |
| 07-交付-分层镜像-探针与优雅停机 | 分层 Dockerfile、容器内 JVM 参数、readiness/liveness、优雅停机完整时序 |
| 08-压测与调优方法论 | 压测工具与场景设计、瓶颈定位顺序、一次完整调优报告 |

## 阶段目标

1. 设计一套「快、稳、覆盖关键路径」的测试集：单测秒级、切片测试十秒级、集成测试分钟级，且不在 CI 里随机失败。
2. 说清 `@MockitoBean` 与 `@MockBean` 的迁移差异，以及 `@SpringBootTest` 在 Boot 4 里不再自动提供 `MockMvc` 后该怎么写。
3. 用 Testcontainers 起真 PG/Redis/Kafka，并解决容器启动慢与数据隔离问题。
4. 定义一组有用的指标（不是只加 `@Timed`）：请求量、错误率、延迟分位、依赖健康、业务事件。
5. 让一条请求的 traceId 贯穿 HTTP → 线程池 → 消息 → 消费 → 下游调用，并说清哪些环节最容易断。
6. 写出生产可用的 Dockerfile 与部署参数，说明 readiness/liveness/startup 三种探针的区别与配错后果。
7. 按「CPU → GC → 连接池 → 数据库 → 锁」的顺序定位瓶颈，并产出一份有前后对比数字的调优报告。

## 知识点地图

### 1. 测试（02~04 册）

- **切片测试的价值**：`@WebMvcTest` 只起 Web 层、`@DataJpaTest` 只起 JPA + 内存库，速度快、失败定位准。全量 `@SpringBootTest` 只用于「跨层链路 + 需要真容器」的少数场景。
- **Boot 4 的迁移点**：`@MockBean`/`@SpyBean` 移除 → `@MockitoBean`/`@MockitoSpyBean`；`@SpringBootTest` 不再自动配置 `MockMvc`，要加 `@AutoConfigureMockMvc`。
- **Testcontainers 的三个坑**：容器启动拖慢 CI（用单例容器 + 复用）、测试间数据污染（每测试事务回滚或清表）、Kafka 这类组件就绪判断（等真实健康而不是 `sleep`）。
- **契约测试**：消费者定义期望 → 生产者验证，能在不联调的情况下发现「字段改名/必填变了」这类破坏性变更。
- **并发与幂等测试**：用 `CountDownLatch`/`ExecutorService` 制造真并发；幂等测试要真的把同一请求发两次并断言副作用只有一次。

### 2. 可观测性（05 册）

- **三类信号的分工**：指标回答「有没有问题」（聚合、便宜、可告警），日志回答「问题是什么」（上下文、贵），链路回答「问题在哪一跳」（跨服务、有采样）。
- **指标命名**：`http_server_requests_seconds` 用标签区分 `uri`/`status`/`method`；**不要把用户 ID、订单号放进标签**——高基数会打爆时序库。
- **日志**：结构化（JSON）+ 固定字段（`traceId`、`spanId`、`tenantId`、`userId`）+ 分级合理；日志里不要打全量请求体（脱敏与体积）。
- **链路断裂点**：线程池提交、`@Async`、消息生产/消费、`CompletableFuture`、协程调度——每一处都要显式传播上下文，否则 trace 在这里断掉。
- **Actuator 安全**：只暴露必要端点，管理端口与业务端口分离，`prometheus` 端点做访问控制。

### 3. 配置（06 册）

- **分层**：`application.yml`（通用）→ `application-<profile>.yml`（环境差异）→ 环境变量（部署注入）→ 配置中心（动态）。**优先级从低到高**，冲突时要能说清谁赢。
- **动态刷新**：`@ConfigurationProperties` + `@RefreshScope` 的代价是「刷新时 Bean 重建」，有状态 Bean 别刷。
- **配置即代码**：配置进 git、走评审、可回滚；密钥走密钥管理，不进 git（含历史提交）。

### 4. 交付（07 册）

- **分层镜像**：依赖层与业务层分离，命中缓存后镜像 push 从分钟级降到秒级；基础镜像用 `-jre`/`-runtime` 变体。
- **容器内 JVM**：`-XX:MaxRAMPercentage=75` 而不是写死 `-Xmx`；容器内存 = 堆 + 元空间 + 直接内存 + 线程栈，算漏了就会被 OOMKilled。
- **探针**：startup 决定「启动慢要不要被杀」，readiness 决定「要不要接流量」，liveness 决定「要不要重启」。**liveness 里不要检查下游依赖**——下游抖动会让所有实例一起重启。
- **优雅停机**：先摘 readiness（停止接新流量）→ 等在途请求完成 → 关闭连接池/消费者 → 退出。`preStop` + `terminationGracePeriodSeconds` 要配套。

### 5. 压测与调优（08 册）

- **压测先定目标**：目标 QPS、可接受 P99、错误率上限、数据规模。没有目标的压测只会得到一张好看的图。
- **定位顺序**：CPU（线程栈/火焰图）→ GC（停顿与分配率）→ 连接池（等待时间）→ 数据库（慢查询/锁）→ 应用锁与串行点。**顺序错了会在错误的地方优化半天**。
- **报告结构**：改动假设 → 实验方法 → 数字对比（QPS/P99/资源）→ 结论与遗留风险。

## 阶段实践

给服务补齐「可交付」的最小集合：

1. 测试：单测 + Web/Data 切片 + 一个 Testcontainers 集成测试 + 一个越权回归测试；
2. 可观测：核心指标 + 结构化日志 + 一条贯穿异步的 trace；
3. 交付：分层 Dockerfile + 健康探针 + 优雅停机验证（滚动更新时零 5xx）；
4. 压测：找到拐点，按顺序定位一处瓶颈并优化，写调优报告。

## 自测

1. 为什么 liveness 探针里不能检查数据库连接？
2. Boot 4 里 `@SpringBootTest` 写 MockMvc 测试要补哪个注解？
3. 一个指标的标签里放了 `orderId`，会发生什么？
4. 滚动更新时出现少量 502，最可能是哪个环节的顺序错了？
5. `-Xmx` 设为容器内存的 90% 有什么风险？
6. 压测到 500 QPS 时 P99 突然从 80ms 跳到 2s，你的排查顺序是什么？
