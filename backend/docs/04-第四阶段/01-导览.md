# 第四阶段导览：Web 层与接口契约

> [返回：后端开发学习大纲](../后端开发学习大纲.md)
> 本文是第四阶段的入口。核心不是「怎么写 `@GetMapping`」，而是分发链路、错误模型、序列化行为与接口契约——这四项决定一个 API 是能被别人长期依赖，还是上线三天就得改。

**建议时长**：2 周。本阶段输出物是一份能贴进团队 wiki 的《接口契约规范》。

## 阶段目标

1. 说清一个请求从 TCP 进来到进入 Controller 方法，中间经过哪些组件、按什么顺序、各自能拿到什么上下文。
2. 判断一段横切逻辑（鉴权、日志、幂等、限流）该放 Filter、Interceptor 还是 AOP，并说明理由。
3. 写出一个分层的统一错误响应：业务异常、校验异常、框架异常、未知异常各自映射到什么状态码与错误体。
4. 说清 Jackson 3 与 2 的差异（坐标、`JsonMapper`、属性前缀），并解释为什么「自定义了 `ObjectMapper` 却不生效」。
5. 设计一套可长期演进的接口：资源命名、分页方式、幂等键、版本化策略、错误码命名。
6. 用 OpenAPI 契约先行的方式定义接口，并用契约测试保证实现与文档不漂移。
7. 说清「没有 `web.xml` 时 `DispatcherServlet` 是被谁注册的」，并把注解从类上到路由表的过程还原出来（09 册）。

## 知识点地图

### 1. 容器与线程模型（02 册）

- **Tomcat NIO 的两级结构**：`acceptor` 接连接、`poller` 管事件、业务线程池执行 `service()`。`maxThreads` 是**业务线程**上限，不是并发连接上限。
- **排队发生在哪**：线程池满后请求进 `acceptCount` 队列，队列满才开始拒绝——所以「超时」有两种：排队超时与处理超时，现象完全不同。
- **虚拟线程执行器**：Boot 4 里可让 Tomcat 用虚拟线程执行请求，阻塞式代码的并发能力大幅提升，但**下游资源的连接池上限**会成为新瓶颈（第八阶段展开）。

### 2. 三类拦截机制（03 册）

| 机制 | 作用位置 | 能拿到什么 | 典型用途 |
|---|---|---|---|
| Filter | Servlet 容器层，最外层 | `ServletRequest`，拿不到 handler 方法 | 编码、CORS、请求体大小限制、安全过滤链 |
| Interceptor | DispatcherServlet 内、handler 选定后 | `HandlerMethod`、路径变量 | 登录态校验、权限注解、请求日志 |
| AOP | Bean 方法调用层 | 方法参数、返回值、异常 | 事务、指标埋点、幂等、缓存 |

- **顺序**：Filter → Interceptor（preHandle）→ AOP → 方法 → AOP → Interceptor（postHandle / afterCompletion）→ Filter 返回。
- **选型口诀**：需要「整个请求」或「响应体流」用 Filter；需要「知道调的是哪个方法」用 Interceptor/AOP；需要「事务边界内」只能用 AOP。

### 3. 分发与参数解析（04 册）

- `DispatcherServlet` 的九步：找 handler → 找 `HandlerAdapter` → 应用 preHandle → 参数解析 → 调用 → 返回值处理 → postHandle → 异常处理 → 渲染/写回。
- **`HandlerMethodArgumentResolver` 是最实用的扩展点**：把「从 token 解析出当前用户」「从 header 解析租户」这类逻辑收进注解 + 解析器，比在每个方法里重复 `@RequestHeader` 干净得多。
- **类型转换**：`@DateTimeFormat`/`Converter`/`Formatter` 的优先级，以及为什么「前端传空串」会变成 `null` 或 400。

### 4. 校验（05 册）

- **分组校验**解决「新增和修改校验规则不同」；`@GroupSequence` 解决「先校验基础字段再校验依赖字段」。
- **Kotlin 特有坑**：非空类型 + `@field:NotNull` 的组合、`data class` 默认值让「字段缺失」和「字段为 null」不可区分、`@Valid` 必须标在字段/参数上而非类型上。
- **自定义约束**要能被 `@Validated` 与 `@Valid` 同时触发，并考虑国际化消息。

### 5. 错误模型（06 册）

- **RFC 9457 `ProblemDetail`** 是标准错误体：`type`（问题类型 URI）、`title`、`status`、`detail`、`instance`，可扩展业务字段（`code`、`traceId`、`errors[]`）。
- **分层映射**：校验失败 → 400 + 字段级 `errors`；认证失败 → 401；权限不足 → 403；资源不存在 → 404；业务规则冲突 → 409/422；限流 → 429；未知异常 → 500 且**不暴露堆栈**。
- **错误码体系**：`域-模块-序号`（如 `ORDER-PAY-0012`），与 HTTP 状态码解耦，前端按 code 分支、按 status 兜底。

### 6. 序列化（07 册）

- **Jackson 3 换坐标**：`com.fasterxml.jackson` → `tools.jackson`（`jackson-annotations` 保留原坐标）；自定义要走 `JsonMapper`，配置 `ObjectMapper` 不再替换默认 mapper——这是升级时最容易「无声改变响应形状」的地方。
- **Kotlin 模块**必须注册，否则默认值与可空性判断会出错；`null` 是否输出、`FAIL_ON_UNKNOWN_PROPERTIES` 是否关闭，都要在契约里写死。
- **精度与时间**：`BigDecimal` 别被序列化成科学计数法；时间统一 ISO-8601 带时区，别用 `long` 时间戳混着来。

### 7. 契约（08 册）

- **资源语义**：名词复数、层级不超过两级、状态变更用子资源动作（`POST /orders/{id}/cancel`）而不是 `PUT status`。
- **分页**：列表接口默认游标分页（`cursor` + `limit` + `nextCursor`），`offset` 只用于后台报表类场景。
- **幂等**：写接口接受 `Idempotency-Key`，服务端存「键 → 结果」，重复请求直接返回首次结果（第六阶段实现）。
- **版本化**：优先「兼容式演进」（加字段、加可选参数），必须破坏时用 Boot 4 的 API versioning 明确标注，并与废弃策略一起写进契约。

### 8. 注解装配（09 册·补充）

- **注解版 MVC 是两块砖**：IoC 容器把 `@Controller` 造成 Bean（`@Controller` 是 `@Component` 的特化，所以靠扫描而非 `@RequestMapping` 成立），`RequestMappingHandlerMapping` 再读 Bean 上的注解建路由表。`initHandlerMappings` 查的是 `getBeansOfType(HandlerMapping)`——**路由表来自容器**，容器没装好就是「全 404 且启动无报错」。
- **分水岭不是「新」而是「元数据源换了」**：XML 与注解最终产出同一张 `BeanDefinition` 表与同一张 `RequestMappingInfo` 表，所以两边的问题形状一一对应（`<mvc:annotation-driven>` ↔ `@EnableWebMvc`，`<bean>` ↔ `@Bean`）。
- **没有 `web.xml` 也能注册 `DispatcherServlet`**：Servlet 3.0 的 `ServletContainerInitializer` SPI → `SpringServletContainerInitializer` → `WebApplicationInitializer.onStartup` → `addServlet(...).addMapping("/")`；Boot 侧等价物是 `DispatcherServletRegistrationBean`。
- **注解版是「启动期建表、运行期查表」**：`RequestMappingHandlerMapping` 初始化时做五件事（遍历 bean → `isHandler` → 选方法 → 合并类级/方法级注解 → 注册并查冲突），运行期 `getHandler` 只是一次 `PathPattern` 查表。

## 阶段实践

给同一个资源写两版接口并做对比：

2. v2：`ProblemDetail` 错误体 + DTO 校验 + 游标分页 + `Idempotency-Key` + OpenAPI 文档 + 契约测试；
