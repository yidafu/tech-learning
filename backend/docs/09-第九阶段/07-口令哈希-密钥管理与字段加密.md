# 07. 口令哈希、密钥管理与字段加密

> [← 第九阶段导览](01-导览.md) · 口令要用「故意很慢」的算法，密钥要从代码里彻底消失，字段加密只给真正敏感的那几列。三件事的共同点是：做错了不会有任何报错，只会在某次数据库泄露时一次性结算。

## 1. 口令哈希的三条硬规矩

口令不能加密（加密可逆，密钥泄露即全泄），只能哈希。而「能存口令的哈希」必须同时满足三条：

1. **慢且可调**。慢是目的，不是副作用——它把「离线暴力破解」的成本从秒级抬到年级。
2. **每用户唯一盐**。盐随哈希一起存，防彩虹表，也防「两个用户口令相同则哈希相同」。
3. **不可逆、无捷径**。不能用可并行化的快速哈希，也不能有已知的代数弱点。

为什么 SHA-256 不行：它的设计目标是快。一块消费级 GPU 每秒能算几十亿次 SHA-256，一个 8 位口令的整个空间在小时级内被穷举完。加盐只解决「彩虹表」和「撞库可见同口令」，**不解决单条口令的离线爆破**——盐是公开的，攻击者对每条记录照样能逐个猜。

「自己加固定盐」错在两处：盐一旦全局固定，等于没有盐（彩虹表针对这个盐重建一次即可复用全部记录）；而把盐写在代码里，和把盐写进数据库没有区别。正确做法是让算法自己生成随机盐并编码进结果字符串。

| 算法 | 抗 GPU | 内存硬 | 可调参数 | 结论 |
|---|---|---|---|---|
| MD5 / SHA-1 / SHA-256 | 无 | 无 | 无 | 禁止用于口令 |
| bcrypt | 中 | 否（约 4KB） | cost 4~31 | 可用，最成熟 |
| scrypt | 强 | 是 | N/r/p | 可用，参数易配错 |
| Argon2id | 强 | 是 | 内存/迭代/并行 | 首选 |

**坑**：bcrypt 只处理口令的前 72 字节，超出部分要么被静默截断（不同口令可能同哈希），要么被新版本直接拒绝。无论哪种，都要在接口入口限制口令长度上限，并明确告知用户。

顺带把口令策略说清楚，因为它经常被做过：强制「大小写 + 数字 + 符号 + 90 天更换」的结果是用户写 `Password1!` 然后贴在显示器上。现行建议（NIST 800-63B 一脉）是**长度优先**：最少 8 位、建议 12 位以上、允许任意字符与空格、不做组合复杂度强制、不强制定期更换（除非有泄露证据）、拿口令去比对已泄露口令库。这些规则不会让哈希更安全，但会显著降低「弱口令」这个更大的风险源。

## 2. BCrypt 成本因子与 Argon2id 参数

BCrypt 的 `cost` 每加 1，计算量翻倍。业界常用的 10~12 是「登录可接受延迟」与「破解成本」的折中，但它必须**在你的机器上量出来**，不能照抄。

实测口径（比数字本身重要）：

1. 用生产同规格的 CPU、同一个 JVM、同样的容器限额；
2. 先跑 200 次预热让 JIT 编译稳定，再串行测 1000 次；
3. 记录 P50 与 P99，不要用平均值（GC 与调度抖动会让均值失真）；
4. 换算成容量：`单核可支撑 QPS ≈ 1000 / P99 毫秒`。

| cost | 单次耗时量级（现代服务器单核） | 单核 QPS 上限 | 适用 |
|---|---|---|---|
| 10 | 50~80ms | ~15 | 低配机器 / 高登录量 |
| 11 | 100~160ms | ~7 | 通用 |
| 12 | 200~320ms | ~3 | 安全优先，需配限流 |

**成本因子调高的真实代价不是「慢一点」**：`cost=12` 时单核只能扛 3 次/秒，100 QPS 的登录峰值需要 30 多核。更麻烦的是**攻击者可以用错误口令消耗你的 CPU**——每次尝试都要算 300ms。所以提高 cost 必须同时给登录接口做限流与账号锁定，否则你就是自己的 DoS 放大器。

配套的三条措施，缺一条都会让上面的容量账失效：按 IP 与按账号双维度限流（只按 IP 挡不住分布式撞库）、失败次数递增延迟（第 5 次错误后延迟 2 秒）、把「哈希计算」放进独立的有限并发池（否则登录洪峰会把业务线程池一起拖垮，第 08 阶段的池隔离在这里复用）。

Argon2id 是当前推荐，三个参数分别控制「内存占用、时间、并行度」：

| 参数 | 含义 | OWASP 建议 | Spring 默认（`defaultsForSpringSecurity_v5_8`） |
|---|---|---|---|
| memory | 内存开销（KiB） | 19456（19 MiB） | 16384（16 MiB） |
| iterations | 迭代次数 | 2 | 2 |
| parallelism | 并行度 | 1 | 1 |
| salt / hash 长度 | 字节 | 16 / 32 | 16 / 32 |

内存硬的好处是**削平 GPU 优势**：每个并行猜测都要占 19 MiB，显卡的显存装不下几千路并发。代价是服务端也要为每次登录付出同样的内存——并发登录高时这是实打实的内存压力，需要按「并发登录数 × 19MiB」估算。

```kotlin
@Bean
fun passwordEncoder(): PasswordEncoder =
    DelegatingPasswordEncoder(
        "argon2",                                   // 新口令用 argon2 编码
        mapOf(
            "argon2" to Argon2PasswordEncoder.defaultsForSpringSecurity_v5_8(),
            "bcrypt" to BCryptPasswordEncoder(12),
        ),
    )
```

## 3. `DelegatingPasswordEncoder` 与平滑迁移

存储格式是 `{算法id}密文`，例如 `{bcrypt}$2a$12$...`。验签时按前缀选算法，于是「换算法」变成「新口令用新算法，旧口令登录时顺手升级」。

```kotlin
@Service
class PasswordUpgradeService(
    private val users: UserRepository,
    private val encoder: PasswordEncoder,
) : UserDetailsPasswordService {

    // DaoAuthenticationProvider 在 encoder.upgradeEncoding() 为 true 时自动调用
    override fun updatePassword(user: UserDetails, newPassword: String): UserDetails {
        val encoded = encoder.encode(newPassword)
        users.updatePasswordHash(user.username, encoded)
        return user.withPassword(encoded)
    }
}
```

迁移分三步走，每一步都可回滚：

| 阶段 | 动作 | 观察什么 |
|---|---|---|
| 1 | 引入 delegating encoder，旧哈希加 `{bcrypt}` 前缀（或配 `setDefaultPasswordEncoderForMatches`） | 登录成功率不掉 |
| 2 | 登录成功时自动重编码为目标算法 | 库里 `{argon2}` 占比逐日上升 |
| 3 | 移除旧算法与默认回退 | 旧前缀数量归零，再删分支 |

三个坑：

- **`setDefaultPasswordEncoderForMatches` 必须指向老算法**。它是「没有前缀的历史数据用什么验」，指错方向会导致老用户全部登录失败。
- **`PasswordEncoderFactories.createDelegatingPasswordEncoder()` 内置了 `noop`**。这意味着能写数据库的人可以把口令改成 `{noop}明文`，然后直接登录。生产环境请自己构造 map，不要带 `noop`。
- **迁移完成要删掉回退分支**。留着 `setDefaultPasswordEncoderForMatches(bcrypt)` 而不监控，等于永久保留一个弱算法入口。

## 4. 密钥的三级演进与轮换

密钥管理有三个成熟度级别，绝大多数事故停在第一级：

| 级别 | 形态 | 泄露面 | 轮换成本 | 审计 |
|---|---|---|---|---|
| 0 | 代码/`application.yml` 字面量 | 仓库、镜像、CI 日志、离职人员 | 改代码 + 重新发布 | 无 |
| 1 | 环境变量 / 挂载文件 | 进程环境、`/actuator/env`、崩溃转储 | 重启或滚动发布 | 无 |
| 2 | Vault / KMS / 云密钥服务 | 仅运行时内存 | 动态租期，自动 | 有（谁在何时取过哪把钥） |

**级别 1 不是终点**：环境变量的价值是「不进仓库」，但它会出现在 `docker inspect`、K8s 的 Pod spec、进程的 `/proc/<pid>/environ`、以及某些 APM 的启动参数采集里。它也没有「谁读过」的记录——出事时无法回答「这把钥被哪些服务拿过」。

**级别 2 的关键不是「存到别处」，是信封加密**：KMS/Vault 里放主密钥（永不出服务），应用启动时用主密钥解出一个数据密钥（DEK），真正的加解密用 DEK。主密钥不落地、DEK 有租期、每次取用都有审计。代价是冷启动多一次往返，且密钥服务不可用时应用起不来——这比「静默用一份过期的本地密钥继续跑」要好。

**历史提交里的密钥按已泄露处理**。密钥只要进过 git 历史——哪怕后来的 commit 把它删了——就视为泄露：它存在于每一次 clone、每一份 fork、每一个 CI 缓存里。处理顺序不能反：**先轮换**，让旧钥作废，这一步不依赖任何清理；再从代码与配置里移除字面量；最后用 gitleaks / trufflehog 这类工具扫全量历史并接入 CI，防止新密钥再次入仓。改写历史（`git filter-repo`）只对本仓库和刚 clone 的副本有意义，挡不住早已散出去的 fork 与备份——「先改历史再轮换」是典型的时间倒错，轮换永远排第一。

**轮换必须能双钥并行**。做法是给每把钥一个 `kid`，密文里带 `kid` 前缀：

- 加密只用 `active` 钥；
- 解密接受 `active` + 所有 `retired` 钥；
- 轮换顺序：先下发新钥（仍用旧钥加密）→ 切 `active` 指向新钥 → 观察一个完整周期 → 再删旧钥。

对 token 这类短期凭证，旧钥的保留时间必须 ≥ token 最大有效期，否则轮换瞬间所有在线用户被踢。

```kotlin
@ConfigurationProperties("app.crypto")
data class CryptoProperties(
    val activeKeyId: String,
    val keys: Map<String, String>,
) {
    init {
        // 启动即校验：缺钥、短钥都直接让应用起不来，而不是等到第一次加密
        require(keys.containsKey(activeKeyId)) { "active key '$activeKeyId' not configured" }
        keys.forEach { (id, value) ->
            require(value.length >= 32) { "key '$id' must be at least 32 chars" }
        }
    }
}
```

**为什么必须 fail-fast**：密钥缺失时的默认行为是「第一次加密时抛 NPE」，此时应用已经接流量、健康检查已通过、告警还没配。结果是「服务活着，但所有写入失败」。把校验放进配置绑定的 `init`，问题就在启动阶段暴露，滚动发布直接卡住。

## 5. 字段加密：确定性还是随机 IV

先明确一点：**只加密真正敏感的字段**。证件号、银行卡号、银行账户、病历摘要值得加密；姓名、地址这类需要模糊搜索的字段加密后会让所有查询失效，收益远小于代价。

| 方案 | 密文特点 | 可等值查询 | 泄露什么 |
|---|---|---|---|
| 随机 IV（AES-GCM） | 同一明文每次不同 | 否 | 仅长度 |
| 确定性加密（固定 IV / SIV） | 同一明文每次相同 | 是 | **相等性**：相同值的记录可被关联 |
| 随机 IV + blind index | 密文随机 + 额外索引列 | 是（走索引列） | 索引列同样泄露相等性 |

确定性加密的「相等性泄露」不是理论问题：攻击者拿到库后，能看出「这 500 个用户是同一个身份证号」，也能对低熵字段（如性别、生日组合）做频率分析。所以只在业务确实需要等值查询（如「按卡号查订单」）时才用，且优先选「随机 IV + blind index（`HMAC(key, 明文)`）」，把泄露局限在一列。

**范围查询基本无解**。除非引入可搜索加密或分桶（把金额按区间存成固定值），否则「查询金额在 1000~2000 之间的订单」在加密列上做不了。这属于设计阶段就要接受的限制，不是实现细节。

```kotlin
@Component
@Converter
class EncryptedStringConverter(
    private val crypto: FieldCrypto,
) : AttributeConverter<String, String> {

    // 输出格式：kid:base64(iv):base64(ciphertext)
    override fun convertToDatabaseColumn(attribute: String?): String? =
        attribute?.let(crypto::encrypt)

    override fun convertToEntityAttribute(dbData: String?): String? =
        dbData?.let(crypto::decrypt)
}
```

`FieldCrypto` 的骨架值得写出来，因为「AES-GCM 用错」比「用错算法」更常见：

```kotlin
@Component
class FieldCrypto(
    private val props: CryptoProperties,
    private val random: SecureRandom = SecureRandom(),
) {
    fun encrypt(plain: String): String {
        val iv = ByteArray(12).also(random::nextBytes)          // 每次都要新 IV
        val cipher = Cipher.getInstance("AES/GCM/NoPadding")
        cipher.init(ENCRYPT_MODE, keyFor(props.activeKeyId), GCMParameterSpec(128, iv))
        val ct = cipher.doFinal(plain.toByteArray(UTF_8))
        return "${props.activeKeyId}:${b64(iv)}:${b64(ct)}"
    }

    fun decrypt(payload: String): String {
        val (kid, iv, ct) = payload.split(':')
        val cipher = Cipher.getInstance("AES/GCM/NoPadding")
        cipher.init(DECRYPT_MODE, keyFor(kid), GCMParameterSpec(128, b64d(iv)))
        return String(cipher.doFinal(b64d(ct)), UTF_8)          // 篡改会抛 AEADBadTagException
    }

    private fun keyFor(kid: String): SecretKey =
        props.keys[kid]?.let { SecretKeySpec(b64d(it), "AES") }
            ?: throw UnknownKeyId(kid)                          // 未知 kid 必须报错，不能回退
}
```

三个细节：IV 绝不复用（GCM 下复用 IV 会直接泄露明文异或值，是致命错误）；`AEADBadTagException` 不能被吞成「返回空字符串」，那等于把篡改当正常；未知 `kid` 必须报错，回退到「随便挑一把钥试」等于放弃完整性。

**坑**：JPA 的 `AttributeConverter` 由 Hibernate 实例化，需要让 Hibernate 的 `SpringBeanContainer` 帮你注入依赖——把 Converter 声明为 Spring Bean（`@Component` + `@Converter`）即可，Spring Boot 默认已启用该容器。

**还有一件容易漏的事：AAD**。AES-GCM 支持附加认证数据，应该把「这张密文属于哪一行哪一列」（如 `orders:id_card:42`）绑进去。否则攻击者能把 A 用户的密文原样复制到 B 用户的行里——数据库层面完全合法，解密也成功，只是数据错了位。这类篡改不会报错，只会让业务数据悄悄串号。

四个代价，必须在设计时想清楚：

- **唯一约束失效**。随机 IV 下同一证件号两次写入密文不同，`unique` 索引形同虚设。要唯一就加 blind index 列并对其建唯一索引。
- **模糊查询失效**。`like '%1234'` 查不了，需要额外存「后四位」这种低敏列（PCI 也允许存后四位）。
- **排序、聚合、外键全部失效**。加密列不能 `order by`，不能做 `group by`。
- **密钥轮换要重刷历史数据**。旧 `kid` 必须一直保留到全量重加密完成，否则老数据解不开。

## 6. 展示层与日志脱敏

字段加密解决「库被拖走」，脱敏解决「人不该看见」。两者不能互替：

| 级别 | 例子 | 存储 | 展示 | 日志 |
|---|---|---|---|---|
| L1 公开 | 商品名、门店地址 | 明文 | 原样 | 可记 |
| L2 内部 | 手机号、邮箱 | 明文 + 访问控制 | 部分脱敏 `138****1234` | 不记 |
| L3 敏感 | 身份证、银行卡 | 加密 + blind index | 强脱敏 `**** **** **** 1234` | 禁止 |
| L4 凭证 | 口令、密钥、token | 单向哈希 / KMS | 永不展示 | 永不记录 |

**脱敏在 DTO 层做，不在实体层**。实体上的字段一旦脱敏，业务逻辑拿到的就是脏数据（对账、退款、风控全错）。正确做法是实体保持原值，出站时按调用方权限决定脱敏级别——同一个字段，客服看到后四位，风控看到全量。

**Kotlin 特有的坑**：`data class` 自动生成的 `toString()` 会把所有字段打出来。一个 `data class User(val idCard: String, val phone: String)` 被日志框架打印一次，就是一次数据泄露。三件事要做：给敏感字段加 `@ToString.Exclude`（Lombok 风格，Kotlin 里需手写 `toString`）、在日志配置里对这些字段做正则替换、禁止 `log.info("req={}", request)` 这种整对象打印。

**日志脱敏要放在采集端**：应用层替换只管自己写的日志，框架、驱动、APM agent 打的日志绕不过去。真正的兜底是在日志采集侧（Filebeat/Fluent Bit）加规则，并把「日志里出现身份证格式」做成告警——发现一次就修一次，而不是配一次就当解决了。

## 7. 自测

1. 加盐能防住彩虹表，为什么防不住「针对单条记录的离线爆破」？口令哈希的「慢」是防什么的？
2. `cost` 从 10 调到 12，单次耗时与单核 QPS 各变化多少？为什么提高 cost 会放大 DoS 风险？
3. Argon2id 的 memory 参数为什么能削弱 GPU 的破解优势？它对服务端内存的影响怎么估算？
4. `PasswordEncoderFactories.createDelegatingPasswordEncoder()` 内置了 `noop`，这会带来什么攻击路径？生产环境该怎么构造？
5. 随机 IV 加密为什么让唯一约束失效？要在加密列上做等值查询，有哪两种工程方案、各自泄露什么？
6. 密钥轮换时，旧钥为什么不能立刻删除？删除时机由什么决定？
