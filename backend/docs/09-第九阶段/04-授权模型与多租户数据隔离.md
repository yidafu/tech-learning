# 04. 授权模型与多租户数据隔离

> [← 第九阶段导览](01-导览.md) · 「登录了」和「有权限」是两件事，「有权限」和「这条数据是你的」是第三件事。越权事故几乎全出在第三层——URL 规则永远管不到「这条订单属于谁」，只能靠数据访问层的强制条件。

## 1. RBAC 的三层建模与它的失效边界

标准 RBAC 是三层：用户 → 角色 → 权限。权限用「资源:动作」表达（`order:read`、`order:refund`），角色是权限的集合，用户挂角色。

| 表 | 关键列 | 为什么要单独存 |
|---|---|---|
| `users` | `id` | — |
| `roles` | `id`, `code` | 角色是岗位，随组织结构变 |
| `permissions` | `id`, `code` | 权限是能力，相对稳定 |
| `user_roles` | `user_id`, `role_id` | 多对多 |
| `role_permissions` | `role_id`, `permission_id` | 多对多 |

**为什么不做两层（用户直接挂权限）**：人数一多就爆炸——100 个客服每人 20 条权限记录，改一条规则要动 100 行，且没人说得清「谁有这个权限」。角色是这层间接性买来的可运维性。

**为什么也不做四层（角色继承）**：继承让「这个用户到底有什么权限」需要递归计算，缓存失效、环路检测、审计解释全都变复杂。多数系统的角色不超过 20 个，继承带来的收益抵不过排查成本。

RBAC 的失效边界有两条，都很清晰：

1. **权限依赖资源属性时**。规则是「只能看本部门的订单」，RBAC 只能靠造角色解决：每个部门一个 `dept_x_viewer`。N 个部门 × M 个动作，角色数随维度乘积增长，最终没人敢删任何一个角色。
2. **权限是行级而非功能级时**。`order:read` 这个权限无法表达「读自己的那 3 条」。RBAC 判断的是「能不能调用这个功能」，不是「能操作哪些数据」。

**坑**：很多系统号称做了 RBAC，实际只做到「角色 → 菜单」，接口上仍是 `anyRequest().authenticated()`。这等于把第二层（功能权限）也交给了前端——隐藏菜单不叫鉴权。

## 2. ABAC 与策略表达式

当权限依赖资源属性（归属、部门、状态、金额）时，判权函数就变成 `f(subject, resource, action)`。Spring 里的载体是方法级 SpEL：

```kotlin
@Service
class OrderService(
    private val orders: OrderRepository,
    private val evaluator: OrderPermissionEvaluator,
) {
    // hasPermission 会路由到 PermissionEvaluator
    @PreAuthorize("hasPermission(#id, 'Order', 'read')")
    fun detail(id: Long): OrderView =
        orders.findById(id).map(OrderView::from).orElseThrow { OrderNotFound(id) }

    // 简单规则直接写表达式：只能改自己的草稿
    @PreAuthorize("#form.ownerId == authentication.principal.userId")
    fun updateDraft(form: OrderForm) { /* ... */ }
}
```

`hasPermission(...)` 由 `PermissionEvaluator` 实现，把「订单归属」这类知识放到一个可单测的类里：

```kotlin
@Component
class OrderPermissionEvaluator(private val orders: OrderRepository) : PermissionEvaluator {

    override fun hasPermission(
        authentication: Authentication?,
        targetId: Any?,
        targetType: String,
        permission: Any?,
    ): Boolean {
        val principal = authentication?.principal as? JwtPrincipal ?: return false
        if (targetType != "Order" || targetId !is Long) return false
        val order = orders.findById(targetId).orElse(null) ?: return false

        if (order.tenantId != principal.tenantId) return false          // 租户硬隔离
        return when (permission) {
            "read" -> order.ownerId == principal.userId || principal.hasRole("OPS")
            "refund" -> order.status == OrderStatus.PAID && principal.hasRole("FINANCE")
            else -> false
        }
    }

    override fun hasPermission(
        authentication: Authentication?,
        targetDomainObject: Any?,
        permission: Any?,
    ): Boolean = hasPermission(authentication, (targetDomainObject as? Order)?.id, "Order", permission)
}
```

**为什么要有单独的 `PermissionEvaluator` 而不是把 SpEL 写长**：表达式字符串没有编译期检查，写错只会在运行时变成 500 或 403；而且 `@orderRepo.findById(#id)` 这种在 SpEL 里调 bean 的写法，每次求值都发一次 SQL，`@PreAuthorize` 与业务查询叠加成两次往返。

**取舍**：SpEL 适合「一两个字段的比较」（归属、状态、租户），超过三个条件就该下沉到 evaluator 或领域服务。判断标准：这个规则能不能被一条单元测试直接覆盖。

## 3. IDOR：`GET /orders/{id}` 的完整案例

一个「看起来没问题」的实现：

```kotlin
// 漏洞版：只校验了「已登录」
@GetMapping("/orders/{id}")
fun detail(@PathVariable id: Long): OrderView =
    orderRepository.findById(id).map(OrderView::from).orElseThrow { OrderNotFound(id) }
```

配合 `anyRequest().authenticated()`，这个接口在安全扫描里是「通过」的：未登录返回 401，登录返回 200。但攻击者拿自己的 token 遍历 `id`，能读到所有人的订单——这就是 IDOR（不安全的直接对象引用），也是真实事故里出现频率最高的一类漏洞。订单号自增时，脚本几分钟就能把全量数据拉走。

三种修法，差别不在「能不能修好这个接口」，而在「下一个接口还会不会犯」：

| 修法 | 做法 | 漏掉新接口时 | 能否静态检查 | 存在性泄露 |
|---|---|---|---|---|
| A 补 if | Controller 里 `if (order.ownerId != me) throw` | 新接口照旧裸奔 | 否 | 403 泄露 id 存在 |
| B 方法级 | `@PostAuthorize("returnObject.ownerId == principal.userId")` | 忘加注解即裸奔 | 部分（可扫描注解覆盖） | 403 |
| C 数据访问层 | 只提供 `findByIdAndOwnerId(id, ownerId)` | 编译期就没有裸查方法 | 是 | 404 |

C 是唯一「结构性正确」的修法：

```kotlin
interface OrderRepository : JpaRepository<Order, Long> {
    // 唯一的按 id 查询入口：归属条件在方法名里，JPQL 由框架生成
    fun findByIdAndOwnerId(id: Long, ownerId: Long): Order?

    // 列表同理，绝不暴露 findAll()
    fun findByOwnerId(ownerId: Long, pageable: Pageable): Page<Order>
}
```

Controller 里把当前用户从 `Authentication` 取出，传给仓储：

```kotlin
@GetMapping("/orders/{id}")
fun detail(@AuthenticationPrincipal principal: JwtPrincipal, @PathVariable id: Long): OrderView =
    orderRepository.findByIdAndOwnerId(id, principal.userId)
        ?.let(OrderView::from)
        ?: throw OrderNotFound(id)          // 404，不区分「不存在」与「不是你的」
```

**为什么返回 404 而不是 403**：403 等于告诉攻击者「这个 id 存在，只是不属于你」。有 403/404 的差异，攻击者就能先枚举出系统中所有有效 id，再针对性地找别的漏洞。404 把「不存在」和「无权」合并成同一个响应，这是防枚举的标准做法。

**为什么「先查后判」不如「带条件查」**：前者把归属判断放在 Java 层，两次操作之间订单可能被转移（TOCTOU）；后者把条件下推到 SQL，一次查询就定了结果。副作用是 `@PostAuthorize` 也不如 C——它在数据已经读出之后才判，对象已在内存里，日志和异常里都可能带出去。

**坑**：修了主接口不等于修完。导出、报表、消息补偿、内部管理后台往往各自有一条 `findById`，这些旁路才是越权的重灾区。所以「禁止裸查」必须靠规约检查（见第 5 节），不能靠人。

**顺带说清 id 形态的取舍**：把自增 id 换成 UUID 或雪花 id，只是让「遍历」变贵，不是修复。攻击者拿到一个合法 id 后，仍然可以拿它去试别的接口、别的租户；而且 UUID 换来了索引膨胀与可读性下降。**id 不可猜测属于纵深防御，归属校验才是修复**。把这两件事混为一谈，就会出现「换成 UUID 之后就不做归属校验了」的荒唐结果。

## 4. 多租户的四种隔离

| 方案 | 隔离强度 | 单租户增量成本 | 漏条件的后果 | 迁移与运维 |
|---|---|---|---|---|
| 按行 `tenant_id` | 弱 | 几乎为零 | **静默跨租户泄露** | 一次 DDL 全租户生效 |
| 按 schema | 中 | 中（每租户一套表） | 报错或读到默认 schema | N 次迁移，靠 `search_path` 切换 |
| 按库 | 强 | 高（每租户连接池） | 连不上（失败响亮） | 备份/恢复按库 |
| 按实例 | 最强 | 最高 | 物理隔离 | 成本随租户线性增长 |

这张表最重要的不是「强度递增」，而是**失败模式的方向**：越往右，配置错了越容易「响」（连不上、表不存在、报错）；最左边那一列，配置错了是**静默的**——SQL 执行成功、HTTP 返回 200、只是数据是别人的。这就是按行方案必须配三道兜底的原因。

**为什么大多数 SaaS 仍选按行**：一个 5000 租户的系统，按 schema 意味着 5000 套表 × 每次迁移 5000 次 DDL，按库意味着 5000 个连接池。成本不在存储，在运维。所以现实是「按行 + 兜底」，只有强合规要求的租户才单独上实例。

**坑**：按 schema 方案里，连接池复用会串 schema。用 `SET search_path` 而不在归还连接时重置，下一个拿到该连接的租户就查到了别人的表——这类事故排查起来极其困难，因为代码完全正确。

## 5. 按行方案的三道兜底

### 第一道：Hibernate 层自动加条件

```kotlin
@Entity
@Table(name = "orders")
@FilterDef(
    name = "tenantFilter",
    defaultCondition = "tenant_id = :tenantId",
    autoEnabled = true,                                  // 不必每个 Session 手动 enableFilter
    applyToLoadByKey = true,                             // 主键 find 也过滤，见下方坑
    parameters = [ParamDef(name = "tenantId", type = String::class)],
)
@Filter(name = "tenantFilter")
class Order(
    @Id
    val id: Long = 0,

    @TenantId                                             // Hibernate 自动填充 + 自动过滤
    @Column(name = "tenant_id", nullable = false, updatable = false)
    val tenantId: String,

    @Column(name = "owner_id", nullable = false)
    val ownerId: Long,

    @Enumerated(EnumType.STRING)
    val status: OrderStatus,
)
```

`@TenantId` 需要配 `CurrentTenantIdentifierResolver`（从 `TenantContext` 或 `SecurityContext` 取值），由它决定当前会话的租户标识，Hibernate 负责在 insert 时填值、在查询时拼条件。`@Filter` 是更通用的那一层：还能顺带处理软删、状态可见性。

**坑**：`@Filter` 默认**不作用于按主键加载**——`find(id)` 和 `@ManyToOne` 的关联抓取都不过滤。不写 `applyToLoadByKey = true`，就等于「列表查不出来，`findById` 一查一个准」，而这恰恰是最常见的越权入口。

**局限**：原生 SQL、`@Query(nativeQuery = true)`、`JdbcClient`、报表工具全部绕过这两者——它们拼的是手写 SQL，Hibernate 管不着。所以第一道只能算「默认安全」，不是「绝对安全」。

### 第二道：Repository 只暴露带条件的入口

```kotlin
@NoRepositoryBean
interface TenantAwareRepository<T : Any, ID : Any> : JpaRepository<T, ID> {
    fun findByIdAndTenantId(id: ID, tenantId: String): T?
}

// 业务仓储继承它，并且不额外声明 findById 之类的裸方法
interface OrderRepository : TenantAwareRepository<Order, Long> {
    fun findByTenantIdAndOwnerId(tenantId: String, ownerId: Long): List<Order>
}
```

再配一条 ArchUnit 规则，禁止业务代码直接调用 `findById`/`findAll`：

```kotlin
@ArchTest
val noBareLookup: ArchRule = noClasses()
    .should().callMethod(JpaRepository::class.java, "findById", Any::class.java)
    .because("按 id 裸查绕过租户隔离，请用 findByIdAndTenantId")
```

这条规则的价值在于**它会在 CI 里失败**。前两道兜底的区别是：第一道防「忘了写 where」，第二道防「有人新写了裸查方法」。

### 第三道：数据库 RLS

```sql
ALTER TABLE orders ENABLE ROW LEVEL SECURITY;
ALTER TABLE orders FORCE ROW LEVEL SECURITY;

CREATE POLICY tenant_isolation ON orders
  USING (tenant_id = current_setting('app.tenant_id', true));
```

配合每个事务开头的 `SET LOCAL app.tenant_id = '...'`（`LOCAL` 保证事务结束即失效，不会污染复用的连接）。这一道是唯一能挡住「应用层全部出错」的：即使有人连错库、写错 SQL、用了原生查询，数据库仍然只返回本租户的行。

**代价**：所有访问都必须经过设置了 `app.tenant_id` 的连接，后台运维、数据修复、跨租户统计都要显式提权（单独角色 + `BYPASSRLS`）。漏设参数的后果是**返回空集**而不是报错——这点比静默泄露好，但仍然要靠监控发现「数据突然全是 0 条」。

## 6. 越权回归测试怎么写

越权修复必须配一条会失败的测试，否则下次重构就回来了。三个断言缺一不可：**跨用户 404、跨租户 404、列表不含他人数据**。

```kotlin
@SpringBootTest
@AutoConfigureMockMvc
class OrderIsolationTest @Autowired constructor(
    private val mockMvc: MockMvc,
    private val tokens: TestTokens,
    private val orders: OrderRepository,
) {
    @Test
    fun `A 用户读 B 用户的订单返回 404 而不是 403`() {
        val orderOfB = orders.save(anOrder(tenantId = "t1", ownerId = tokens.userBId))

        mockMvc.get("/api/orders/${orderOfB.id}") {
            header(HttpHeaders.AUTHORIZATION, "Bearer ${tokens.forUserA()}")
        }.andExpect {
            status { isNotFound() }                    // 不是 403，避免存在性泄露
        }
    }

    @Test
    fun `跨租户访问即使 ownerId 相同也必须 404`() {
        val otherTenant = orders.save(anOrder(tenantId = "t2", ownerId = tokens.userAId))

        mockMvc.get("/api/orders/${otherTenant.id}") {
            header(HttpHeaders.AUTHORIZATION, "Bearer ${tokens.forUserA()}")
        }.andExpect { status { isNotFound() } }
    }

    @Test
    fun `列表接口不得返回他人订单`() {
        val orderOfB = orders.save(anOrder(tenantId = "t1", ownerId = tokens.userBId))

        mockMvc.get("/api/orders") {
            header(HttpHeaders.AUTHORIZATION, "Bearer ${tokens.forUserA()}")
        }.andExpect {
            status { isOk() }
            jsonPath("$.content[*].id") { value(not(hasItem(orderOfB.id))) }
        }
    }
}
```

**第二个用例是最容易被漏掉的**：`ownerId` 相同、租户不同，说明测试真的走到了租户条件，而不是只走了归属条件。只写第一个用例的系统，往往在「同一用户跨租户」时仍然泄露。

**为什么断言 404 而不是「非 200」**：`isNotFound()` 把「不要泄露存在性」这个决定也钉进了测试。如果哪天有人把 404 改成 403，测试会红，评审时就能讨论。

**坑**：`@SpringBootTest` 不起事务时，测试数据会留在库里污染其它用例；起事务又可能让 RLS 的 `SET LOCAL` 行为与生产不一致。多数团队的做法是每个用例独立租户 id（如 `t-${UUID}`），从数据层面隔离而不是靠回滚。

**怎么知道测试覆盖够了**：手工为每个接口写三条用例，迟早会漏。可行的做法是拿接口清单做参数化——把 `GET /orders/{id}`、`PATCH /orders/{id}`、`GET /orders/{id}/items` 这些「带资源 id 的路径」抽成表，用「A 的 token + B 的资源」逐条跑，断言非 2xx。新增接口时 CI 会提示这条表没有对应条目，比靠评审盯更可靠。

**取舍**：这类测试会显著变慢（每条都要准备两个租户的数据），所以放在独立的测试任务里，随 PR 跑而不是随单测跑。

## 7. 自测

1. RBAC 在什么情况下必然退化成「角色爆炸」？给出一个具体的维度组合。
2. `@PostAuthorize` 与「数据访问层带条件查询」都能拦住越权，前者多出哪两个风险？
