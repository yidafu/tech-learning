# 08. 审计、依赖漏洞与安全响应头

> [← 第九阶段导览](01-导览.md) · 前面六册讲「怎么防」，这一册讲「防不住之后怎么回答问题」：谁在什么时候动了哪条数据、这次泄露涉及哪些记录、这个漏洞到底可不可达。安全能力的终点不是拦截率，是**可追溯**。

## 1. 审计日志该记什么

一条审计事件的最小字段集是五个，缺一个就无法回答关键问题：

| 字段 | 内容 | 缺了会怎样 |
|---|---|---|
| who | 用户 id、租户、客户端 id、来源 IP | 只能知道「有人删了」，不知道是谁 |
| when | 带时区的时间戳（UTC 存储） | 跨时区对账对不上 |
| what | 资源类型 + **资源 id** | 回答不了「涉及哪些记录」 |
| action | 动作（`order.refund`、`user.export`） | 无法按操作类型检索 |
| result | 成功/失败/被拒绝 + 拒绝原因 | 分不清「尝试过」与「做成了」 |

再加两个关联字段：`traceId`（串到业务日志与链路）与 `requestId`（幂等/重试场景去重）。**敏感字段记「已变更」而不是 before/after 原文**——审计日志本身不能变成第二份泄露源。

**为什么不能和业务日志混在一起**，有四条硬理由：

1. **生命周期不同**。业务日志通常保留 7~30 天且可采样；审计要按合规保留 6 个月到数年，且一条都不能丢。
2. **可变性不同**。`log.info` 的级别在生产环境可能被调到 WARN，一行代码就让它静默消失；审计不能依赖运行时可调的开关。
3. **权限不同**。能读业务日志的人很多，能改审计的人必须没有——写审计的服务账号不应该有 `UPDATE`/`DELETE` 权限。
4. **检索方式不同**。业务日志按关键词搜，审计要按「用户 × 时间 × 资源」做结构化查询。

**坑**：把审计写成「业务方法里加一行 `log.info`」，是最常见的伪实现。它满足了「有记录」，但在事故复盘时会发现：日志被轮转删了、级别被调过、字段是拼给人看的字符串、查不出某个用户三个月前的操作。

## 2. 不可篡改：追加写、哈希链、外送

三层机制，成本递增，防的威胁不同：

| 机制 | 防什么 | 实现 | 局限 |
|---|---|---|---|
| 追加写 | 应用侧误删/误改 | 表只授 `INSERT`；或写只追加的流（Kafka topic + 归档） | 有 DBA 权限的人仍可改 |
| 哈希链 | 悄悄篡改单条记录 | 每条含 `prevHash`，`hash = SHA256(prevHash + 规范化内容)` | 整段删除后链仍「自洽」 |
| 外送 | 内部人删库/删账号 | 异步推到独立账号的 WORM 存储或第三方 | 有延迟，需对账 |

```kotlin
@Service
class AuditChain(private val repo: AuditRepository, private val signer: AuditSigner) {

    // 串行化写入：链不能分叉，用行锁或单分区保证顺序
    @Transactional
    fun append(event: AuditEvent): AuditRecord {
        val prev = repo.lockLastHash() ?: GENESIS
        val body = event.canonicalJson()                 // 字段顺序固定，否则哈希不可复现
        val hash = sha256(prev + body)
        return repo.save(
            AuditRecord(
                prevHash = prev,
                body = body,
                hash = hash,
                signature = signer.sign(hash),            // 防「重算整条链」
                occurredAt = event.occurredAt,
            )
        )
    }
}
```

**为什么需要签名**：只有哈希链时，能改数据库的人可以「改一条，然后把后面所有记录的 hash 全部重算」——链依然自洽。加上用外部密钥签名（第 06 册的 KMS），没有那把钥就重算不出合法签名，篡改必然留下痕迹。

**验收方法**：写一个离线校验任务，从链头开始逐条重算，任一条不匹配就报出「第一条断链的位置」。这个任务要定期跑，因为「链断了但没人知道」等于没有链。

**坑**：审计写入如果和业务在同一个事务里，业务回滚会把审计也回滚掉——「操作失败」这件事本身是需要记录的。正确做法是把「尝试」与「结果」分开记，或用 outbox 保证「业务提交则审计必达」。

事件发布是把「尝试」与「结果」拆开的常用姿势：业务事务里只发事件，由监听器在提交或回滚后落库，业务回滚不再连带吞掉审计。

```kotlin
@Target(AnnotationTarget.FUNCTION)
@Retention(AnnotationRetention.RUNTIME)
annotation class Audited(val action: String)

@Aspect
@Component
class AuditAspect(private val events: ApplicationEventPublisher) {

    @Around("@annotation(audited)")
    fun around(pjp: ProceedingJoinPoint, audited: Audited): Any? {
        val base = AuditEvent(
            action = audited.action,
            target = pjp.args.firstOrNull()?.toString() ?: "n/a",
            occurredAt = Instant.now(),
        )
        return try {
            pjp.proceed().also { events.publishEvent(base.copy(result = "SUCCESS")) }
        } catch (e: Throwable) {
            events.publishEvent(base.copy(result = "FAILED:${e.javaClass.simpleName}"))
            throw e
        }
    }
}

@Component
class AuditEventListener(private val chain: AuditChain) {

    // 提交成功记 SUCCESS；回滚也要记——「尝试过」本身就是审计事实
    @TransactionalEventListener(phase = TransactionPhase.AFTER_COMMIT)
    fun onSuccess(event: AuditEvent) = chain.append(event)

    @TransactionalEventListener(phase = TransactionPhase.AFTER_ROLLBACK)
    fun onRollback(event: AuditEvent) = chain.append(event.copy(result = "ROLLBACK"))
}
```

两个监听器对应事务的两个终态，保证无论提交还是回滚都有一条审计落地；`chain.append` 自带独立事务，与业务事务解耦。两个注意点：事件必须在事务内发布，否则 `@TransactionalEventListener` 默认直接丢弃（加 `fallbackExecution = true` 可兜底非事务方法，但会失去「回滚也要记」的语义）；监听器里的写入晚于业务提交，进程恰在两者之间崩溃会丢一条记录——这正是 outbox 兜底的场景，重要性高的审计走 outbox，一般的走事件。

## 3. `traceId` 与「泄露范围」这个验收问题

审计日志的价值不在于「有」，在于能回答一个具体问题：**这次数据泄露，涉及哪些记录？**

要回答它，审计里必须能反查出三样东西：时间窗内的所有读操作、每次读操作的资源 id 范围、以及发起者的身份。所以：

- 单条查询记 `resourceType + resourceId`；
- 列表/导出记「查询条件 + 返回条数 + 首末 id」，只记「导出了订单列表」等于没记；
- 分页遍历要能把同一 `traceId` 下的多页拼成一次操作；
- 内部服务调用要透传 `traceId`，否则链路在服务边界断掉。

`traceId` 的来源是 Micrometer Tracing（或 OTel）写进 MDC 的那个值，审计事件与业务日志共用它。这样事故复盘时的路径是：告警 → 某个 `traceId` → 该 trace 下的全部审计事件与日志 → 涉及的资源 id 清单。

**坑**：异步线程池与消息消费默认丢失 MDC。审计切面如果在异步方法上执行，`traceId` 会是 `null`——除非用了 `TaskDecorator`（第 08 阶段 02 册）或把 `traceId` 显式放进事件体。

**顺带一个合规收益**：同一套按用户检索的能力，正好是「数据主体访问请求」（用户要求导出/删除自己的数据）需要的。审计设计得好，合规功能几乎是免费的。

## 4. 依赖漏洞扫描：可达漏洞与噪音

SCA（软件组成分析）工具能列出「你依赖的库里有哪些已知 CVE」，但它不知道你的代码有没有真的调用那段受影响的方法。Java 生态缺少成熟的可达性分析，于是现实是「一堆高危，没人看得完」。

分流是唯一出路：

| 噪音类型 | 识别方式 | 处理 |
|---|---|---|
| 只在测试/编译期依赖 | 看 `testRuntimeClasspath` / `compileOnly` | 降级为非阻断 |
| 传递引入但未使用 | `dependencyInsight --dependency X` 看引入路径 | 排除（`exclude`）或接受 |
| 受影响功能未被调用 | 人工确认调用点 + 版本范围 | 记录结论与依据，设复核日期 |
| 版本范围误报 | 核对 CVE 的 affected versions 与你的实际版本 | 标注误报，附证据 |
| 确实可达且可利用 | 有调用路径、有入口 | **阻断发布** |

**门禁策略要分层，不能一刀切**：`CVSS >= 7` 且属于运行时依赖 → 阻断合并；`CVSS 4~7` → 记录并在一个迭代内处理；其余 → 报告不阻断。要求「全绿才能合并」的结果一定是有人加一句 `ignoreFailures = true`，从此整条门禁失效。

**工程落点**：CI 里生成 SBOM（CycloneDX 插件）+ 扫描（Trivy / osv-scanner / Dependency-Check 任一），把 SBOM 作为发布产物存档。SBOM 的价值在事后——某个组件爆出新 CVE 时，你能在十分钟内回答「我们哪些镜像受影响」，而不是靠人肉翻 `build.gradle`。

## 5. 升级验证：`spring-boot-properties-migrator` 之外

升级依赖处理漏洞时，最大的风险不是「升不上去」，是「升上去了但行为变了」。`spring-boot-properties-migrator` 只解决配置键重命名，其余一概不管。

按这个顺序验证，能把大部分坑挡在灰度之前：

1. **读 release notes 的升级段落**，尤其是「默认值变更」「移除的 API」「行为修正」三节。
2. **全量测试**，包括集成测试与契约测试；单测通过不代表序列化格式没变。
3. **启动冒烟**：`/actuator/health`、`/actuator/info`、关键 endpoint 各打一次，确认自动配置没有因为版本变化而失效。
4. **重点核对三类行为**：序列化（Jackson 3 换坐标后 `ObjectMapper` → `JsonMapper`，日期与多态默认值都变过）、安全默认值（Security 6→7 的 DSL 与 CSRF 掩码）、SQL 生成（Hibernate 升级后 `@Filter`、抓取策略、`order by` 拼接都可能变）。
5. **依赖冲突**：`./gradlew dependencyInsight --dependency <lib>` 确认仲裁后的实际版本，别只看声明。
6. **灰度与指标**：错误率、P99、GC、连接池等待，任一项异常就回滚。

**坑**：安全补丁常常是「小版本升级」，而小版本里也可能带默认行为变化。把「补丁版本可以无脑升」写进规范，是给自己埋雷。正确表述是「补丁版本优先升，但仍要跑完整验证流水线」。

## 6. 错误信息：不泄露，但要能追

生产环境的错误响应只该包含三样东西：**稳定的错误码**、**给人看的简短说明**、**`traceId`**。不该包含堆栈、SQL、类名、内部主机名、依赖版本。

```kotlin
@RestControllerAdvice
class ApiExceptionHandler {

    @ExceptionHandler(Exception::class)
    fun handle(e: Exception, request: HttpServletRequest): ProblemDetail {
        val traceId = MDC.get("traceId") ?: "unknown"
        // 堆栈只进日志，并且带上 traceId 以便关联
        log.error("unhandled error traceId={} path={}", traceId, request.requestURI, e)

        return ProblemDetail.forStatus(HttpStatus.INTERNAL_SERVER_ERROR).apply {
            title = "Internal Server Error"
            detail = "请求处理失败，请稍后重试并提供 traceId"
            setProperty("traceId", traceId)
        }
    }
}
```

四条纪律：

- **认证失败不要区分原因**。「用户不存在」与「密码错误」返回同一个响应，否则就是账号枚举接口。
- **不要把 `e.message` 直接返回**。JDBC 异常的消息里常有表名、列名、甚至 SQL 片段；`NullPointerException` 的消息在新版 JDK 里会带详细的变量信息。
- **`server.error.include-stacktrace=never`、`include-message=never`** 要显式写进生产配置，别依赖默认值——它随版本变过。
- **`traceId` 必须打进日志**，否则用户报障时拿着一个随机字符串，你在日志里搜不到。

**取舍**：内部服务之间可以返回更详细的错误（便于排查），但要在网关统一裁剪。判断标准是「这个响应会不会到达最终用户或第三方」。

## 7. 安全响应头与 TLS 清单

响应头的逐项作用在第 05 册第 8 节，这里只列「上线前必须确认存在」的清单；TLS 侧则常被忽略，因为它在反向代理/负载均衡上，不在应用代码里。

| 项 | 目标值 | 检查点 |
|---|---|---|
| HSTS | `max-age>=31536000; includeSubDomains` | 只在 HTTPS 响应上，先小后大 |
| CSP | 无 `unsafe-inline`，`object-src 'none'` | 先 `Report-Only` 收集 |
| `X-Content-Type-Options` | `nosniff` | 全站，含静态资源 |
| `Referrer-Policy` | `strict-origin-when-cross-origin` 或更严 | 避免 URL 参数外泄 |
| 防点击劫持 | `frame-ancestors 'none'` | 与 `X-Frame-Options` 不冲突 |
| `Permissions-Policy` | 按需关闭摄像头/定位/麦克风 | 别全关，会误伤业务 |
| TLS 版本 | 仅 1.2 / 1.3 | 关掉 1.0/1.1 与 SSLv3 |
| 套件 | 仅 AEAD（GCM/ChaCha20） | 禁用 CBC 与 RSA 密钥交换 |
| 证书 | 链完整、自动续期 | **到期前 30 天告警** |
| 内部调用 | 服务间 TLS 或 mTLS | 内网不等于可信 |

**坑**：证书过期是最高频的「低级」线上事故，且几乎总是因为「续期是自动的，所以没人监控」。自动续期失败（DNS 挑战失败、ACME 限流、权限变更）不会有任何提示，直到浏览器弹出警告。监控必须盯「剩余有效期」这个指标，而不是盯续期任务的成功率。

## 8. 上线前安全检查清单

| # | 检查项 | 通过标准 |
|---|---|---|
| 1 | 认证 | 所有非公开路径要求认证；无「忘记加注解」的接口（有清单比对） |
| 2 | 授权 | 带资源 id 的接口全部走归属校验；越权回归测试在 CI 里 |
| 3 | 租户 | 按行隔离有三道兜底；原生 SQL 已审计 |
| 4 | 会话/令牌 | `aud`/`iss`/`exp`/算法逐项校验；刷新令牌一次性且能检测重放 |
| 5 | 口令 | 使用 bcrypt(cost>=10) 或 Argon2id；无 `{noop}`；有登录限流 |
| 6 | 密钥 | 代码与配置中无字面量；来自 KMS/Vault；启动时 fail-fast |
| 7 | 敏感字段 | 分级明确；L3 以上加密；日志与 DTO 已脱敏 |
| 8 | 注入 | 全部参数化；排序/列名白名单；无字符串拼接 SQL |
| 9 | 出站请求 | URL 白名单 + 私网拦截 + 禁重定向 |
| 10 | 上传下载 | 服务端生成文件名；`Path.startsWith` 校验；目录不可执行 |
| 11 | 错误响应 | 无堆栈/SQL；带 `traceId`；认证失败不区分原因 |
| 12 | 审计 | 五要素齐全；只追加；有链校验任务与外部留存 |
| 13 | 依赖 | SCA 进 CI；高危可达项已处理；SBOM 已归档 |
| 14 | 传输 | TLS 1.2+、强套件、证书有效期监控 |
| 15 | 响应头 | HSTS/CSP/nosniff/Referrer-Policy 全站生效 |

这张清单的用法不是「上线前打勾一次」，而是**逐项落到自动化**：能写成测试的写成测试（1、2、3、11），能写成 CI 检查的写成检查（8、13），剩下的才靠人工确认。

## 9. 自测

1. 审计事件的五个必填字段是什么？缺 `result` 会带来什么具体问题？
2. 为什么审计不能复用业务日志？给出四条理由，并说明「级别被调高」为什么会毁掉审计。
3. 只有哈希链、没有签名时，攻击者怎么让篡改「看不出来」？签名补上了哪一环？
4. 面对「这次泄露涉及哪些记录」这个问题，审计里必须记什么？为什么只记「查询了订单列表」不够？
5. SCA 报告里 20 个高危，你怎么在半天内分出哪些必须修？给出三步分流法。
6. 为什么证书自动续期了还要监控？该监控哪个指标？
