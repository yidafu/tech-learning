# 第九阶段导览：安全与鉴权

> [返回：后端开发学习大纲](../后端开发学习大纲.md)
> 本文是第九阶段的入口。安全不是「加个 filter」。本阶段沿「认证 → 权限模型 → 授权落地与数据隔离 → 输入输出 → 密钥」五层推进，重点是**越权**和**密钥**这两类真实事故——它们不出现在扫描报告里，却出现在事故复盘里。

**建议时长**：1.5 周。要求至少完成一次真实的越权打通与修复。

| 03-会话-JWT与OAuth2-OIDC | 有状态 vs 无状态、JWT 吊销/续期/存储的真实代价、OIDC 登录、资源服务器 |

| 05-授权落地与多租户数据隔离 | 方法级安全（`PermissionEvaluator`）、IDOR 越权案例、租户隔离的四种实现 |

## 阶段目标

1. 画出 Spring Security 过滤器链中一次请求的完整时序，指出认证、授权、异常处理各发生在哪个过滤器。
2. 说清会话与 JWT 的取舍：JWT 为什么「难以吊销」，以及业界常见的三种补救方案与各自代价。
3. 区分「未认证」「未授权」「越权访问他人资源」三类问题，并给出各自的防御层。
4. 把权限拆成「功能 / 数据范围 / 资源状态」三个维度，并解释「给每个部门建一个角色」为什么必然导致角色爆炸。
5. 设计多租户隔离方案（按行/按 schema/按库），说清每种方案在「漏加 where 条件」时的后果。
6. 说出至少六种 Web 攻击在 Spring 侧的防线，以及 Spring Security 默认替你做了什么、没做什么。
7. 正确使用口令哈希（BCrypt/Argon2 参数怎么选），并把密钥从代码与配置中彻底移出。
8. 建立审计日志与依赖漏洞扫描的最小闭环。

## 知识点地图

### 1. 过滤器链（02 册）

- **顺序即安全**：`SecurityContextHolderFilter` 建立上下文 → 认证过滤器（表单/Bearer/自定义）→ `AuthorizationFilter` 判权 → 异常转换（`ExceptionTranslationFilter` 把认证异常转成 401/403）。**自定义过滤器插错位置，会导致「登录了但拿不到用户」或「匿名能过鉴权」**。
- **`SecurityFilterChain` vs `WebSecurityCustomizer`**：后者让路径完全绕过安全链（连安全头都没有），只适合静态资源，别用来「图方便放行接口」。
- **方法级安全**（`@PreAuthorize`）作用在代理层，与 URL 级规则是两道独立的门；两道都配时以更严格者为准，且要意识到自调用会绕过方法级安全。

### 2. 认证（03 册）

- **会话**：服务端存状态，可随时踢人；水平扩展需共享存储（Redis session）或粘性会话。
- **JWT**：无状态、可跨服务验签，但**签发即生效、到期才失效**。三种补救：短有效期 + 刷新令牌、维护吊销名单（等于又有状态）、按版本号失效（用户表存 `tokenVersion`）。
- **OIDC**：授权码 + PKCE 是标准姿势；后端服务作为「资源服务器」只验 token，不参与登录流程；`aud`/`iss`/`exp`/签名算法必须逐项校验，**不能接受 `alg: none` 或任意算法**。

### 3. 权限模型（04 册）

- **三个维度分开承载**：功能 → 角色挂权限点；数据范围 → 数据权限（`ALL`/`DEPT_SUBTREE`/`SELF`/`EXPLICIT`）；资源状态 → 策略或领域判断。把数据维度塞进角色，角色数就是「部门 × 动作 × 数据档」的乘积，最后没人敢删任何一个。
- **RBAC 家族停在 RBAC0 的代价**：RBAC1 解决角色重复（父子继承，必须防环），RBAC2 的互斥角色（制单/审核不能同一人）与基数约束几乎没人实现——职责分离于是只能靠制度，而制度在赶工时最先被绕过。
- **权限点对齐业务能力，不对齐 UI**：`order:refund` 是能力，按钮是 UI；权限点稳定、页面声明依赖，才不会被一次改版拖垮。
- **权限缓存的失效用版本号**：改权限只 bump `auth:ver:{uid}`，比批量删 key 稳；把权限塞进 JWT 则等于把「立即收回」换成「等 token 过期」。
- **ABAC 与 ReBAC 的边界**：规则多到业务方要自己改 → 上策略引擎；授权本质是关系（文档共享、组织树）→ ReBAC；单据类业务上 ReBAC 是过度设计。

### 4. 授权与隔离（05 册）

- **IDOR 是最高频的真实漏洞**：`GET /orders/{id}` 只校验了「已登录」，没校验「这个订单是不是你的」。修复必须落到数据访问层（`WHERE user_id = :currentUser`），而不是在 Controller 里补个 if。
- **方法级安全**：`@PreAuthorize` 与 `PermissionEvaluator` 用来承载「依赖资源属性」的规则；表达式超过三个条件就该下沉到可单测的类里。
- **多租户四种隔离**：按行（`tenant_id`，最省成本、最怕漏条件）→ 按 schema → 按库 → 按实例。越往右隔离越强、成本越高。**按行方案必须有「框架级兜底」**（如 Hibernate filter 或 Repository 基类强制加条件），不能靠人记得写。

### 5. 攻击面（06 册）

| 攻击 | Spring 侧防线 |
|---|---|
| CSRF | 会话模式下默认开启；纯 Bearer token 的无状态 API 可关闭并说明理由 |
| XSS | 输出编码、`Content-Security-Policy`、富文本白名单清洗 |
| SQL/JPQL 注入 | 参数化查询；拼接 `ORDER BY` 字段时必须白名单 |
| SSRF | 出站 URL 白名单、禁止内网地址段、独立出口代理 |
| 反序列化 | 不用 Java 原生序列化、Jackson 关闭默认类型信息 |
| 路径穿越 | 上传/下载路径规范化后校验前缀，不信任客户端文件名 |

### 6. 密钥（07 册）

- **口令哈希**：BCrypt（成本因子 10~12）或 Argon2id；**永不使用 MD5/SHA 系列**，也不要在哈希前自己加固定盐。
- **密钥外置**：环境变量只是最低要求，生产应用 Vault/KMS/云密钥服务；密钥要能轮换，代码里不该出现任何密钥字面量（含测试）。
- **字段加密**：只加密真正敏感的字段（证件号、卡号），并接受「加密后无法模糊查询」的代价；展示层做脱敏。

### 7. 运维侧（08 册）

- **审计日志**：谁、什么时候、对什么资源做了什么、结果如何。要能回答「这次数据泄露涉及哪些记录」。
- **SCA**：依赖漏洞扫描进 CI，但要区分「可达漏洞」与「仅在测试依赖里」，否则会被噪音淹没。
- **错误信息**：生产环境不返回堆栈与 SQL；但要有 `traceId` 让排查能对上日志。

## 阶段实践

1. 给一个后台设计权限模型：按「功能 / 数据范围 / 资源状态」三分法列出角色清单（压到 20 个以内）与每类数据范围，写清哪条规则交给代码判断；
2. 在自己的服务上构造越权：用 A 用户 token 读 B 用户订单，确认能打通；
3. 修复：数据访问层强制归属条件 + 方法级权限 + 审计日志；
4. 补回归测试（越权用例必须变成自动化测试）；
5. 扫描一遍依赖漏洞，处理至少一个高危项并记录升级影响。

## 自测

1. 自定义 JWT 认证过滤器插在 `UsernamePasswordAuthenticationFilter` 之前还是之后？位置错了会怎样？
2. JWT 被盗后如何让它立刻失效？三种方案各自的代价是什么？
3. 「只能看本部门订单」这条规则如果做成角色，角色数会怎么增长？该拆成哪三个维度分别承载？
4. `@PreAuthorize` 加在 Service 上，Controller 里同类调用会绕过吗？为什么？
5. 按行隔离的多租户系统，怎么防止「某个新接口忘了加 tenant_id」？
6. 一个上传接口只校验了扩展名，可能被怎么利用？
7. 为什么 BCrypt 比 SHA-256 更适合存口令？成本因子调高有什么代价？
