# 第八阶段导览：并发模型深潜

> [返回：后端开发学习大纲](../后端开发学习大纲.md)
> 本文是第八阶段的入口。同一个接口，用平台线程池写、虚拟线程写、响应式写，吞吐与故障模式完全不同。本阶段要求你能说出「这个接口该用哪种模型，为什么」，并用压测数据证明。

**建议时长**：2 周。核心实验是「同一接口三种实现 + 同一压测脚本」。

## 阶段目标

1. 用「到达率 × 平均处理时间」估算需要的并发度，并解释为什么 `maxThreads` 调大常常只是把问题挪到下游。
2. 说清虚拟线程的成本模型，指出 `synchronized` 块、`ThreadLocal`、native 调用分别带来什么问题。
3. 划出协程的 `suspend` 边界：哪些层应该是 suspend 的，哪些层不该。
4. 解释 Reactor 的背压语义，说出 `flatMap` 与 `concatMap` 在并发与顺序上的差别，以及 WebFlux 在什么情况下反而更慢。
5. 设计一套超时预算：入口超时 < 各下游超时之和，重试次数与超时联动，熔断阈值怎么定。
6. 用压测数据说明三种模型在同一接口上的差异，并给出选型结论。
7. 解释线程池「池隔离」的意义：一个慢下游如何拖垮整个应用，隔离如何止血。

## 知识点地图

### 1. 线程池（02 册）

- **参数组合的真实后果**：核心线程满 → 进队列（队列满了才扩容到 `max`）→ 拒绝。所以「有界大队列」会让 `max` 永远用不上，「小队列 + 大 max」才会真的扩容。
- **拒绝策略**：`AbortPolicy`（抛异常，让上游感知）通常是对的；`CallerRunsPolicy` 会把压力反弹给调用线程（可能是容器线程），要清楚代价。
- **池隔离**：按依赖分池（DB 池、缓存池、下游 A 池、下游 B 池），一个依赖抖动不会耗尽所有线程。代价是线程总数上升、需要统一监控。
- **上下文传递**：`ThreadLocal`（含 MDC/TraceId）不跨线程；必须显式传递或使用可传播的包装（`TaskDecorator`、协程上下文、Reactor Context）。

### 2. 虚拟线程（03 册）

- **优势**：阻塞式代码也能获得高并发，代码可读性远好于响应式；创建成本低，不需要池化（池化虚拟线程反而有害）。
- **pinning 的两种来源**：`synchronized` 块内阻塞（JDK 24 起已大幅缓解，但仍要看版本）、native 方法/JNI 阻塞。pinning 会让载体线程被占住，并发能力退化到平台线程水平。
- **`ThreadLocal` 的代价**：虚拟线程数量巨大时，每个线程的 ThreadLocalMap 都是内存开销；高并发场景优先显式传参。
- **不适合的场景**：CPU 密集型任务（虚拟线程不增加算力）、需要精细线程控制的场景。

### 3. 协程（04 册）

- **`suspend` 边界**：Controller/Service 层可以是 suspend；Repository 层如果是阻塞 JDBC，就应该在 `Dispatchers.IO` 上执行并明确标注，而不是伪装成 suspend。
- **自定义 Dispatcher**：给「慢 IO」和「CPU 计算」分不同调度器，避免相互挤占。
- **取消与超时**：`withTimeout` 只对可挂起代码有效；对阻塞调用要用可中断的 API 或外部超时。

### 4. 响应式（05 册）

- **心智模型**：`Mono`/`Flux` 是「数据流 + 完成/错误信号」，`subscribe` 才真正执行；操作符是「声明」。写 WebFlux 最常见的 bug 是「忘记订阅」或「在流里做阻塞调用」。
- **背压**：下游声明需求，上游按需生产。`onBackpressureBuffer/Drop/Latest` 是策略而非万能药；真正的解法是端到端支持背压（HTTP/2、Reactive 驱动）。
- **WebFlux 什么时候更慢**：依赖全阻塞（JDBC、同步 SDK）时，WebFlux 只是把阻塞搬到了事件循环线程上，吞吐反而下降；团队不熟悉操作符时，排查成本也会显著上升。

### 5. 弹性（06 册）

- **超时预算**：入口 500ms，则两个串行下游各 200ms、留 100ms 余量；**下游超时必须小于上游**，否则上游先超时，下游还在白干活。
- **重试放大**：三层各重试 3 次 = 最多 27 倍流量打到最底层。重试必须配合熔断、退避与「只重试幂等操作」。
- **熔断与舱壁**：熔断解决「快速失败」，舱壁（bulkhead）解决「资源隔离」；限流解决「入口过载」。三者位置不同，别混用。
- **限流算法**：令牌桶（允许突发）、漏桶（恒定速率）、滑动窗口（精确统计）、并发信号量（控制同时在途数）。对外 API 用令牌桶 + 并发限制组合更实用。

## 阶段实践

实现同一个「聚合三个下游」的接口三遍：

1. 平台线程池 + `CompletableFuture`；
2. 虚拟线程（每请求一虚拟线程，内部阻塞调用）；
3. WebFlux + `WebClient`（或协程 + `awaitAll`）。

同一压测脚本、同一组下游延迟（50ms/100ms/故障 10%），记录吞吐、P99、内存、故障时的表现（是否雪崩、是否快速失败），写进对比报告。
