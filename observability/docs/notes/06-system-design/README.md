## 建议学习顺序

1. 学完阶段 0–5 后，把本阶段当**收官复盘**读：每篇都会把前面某个组件的"用法"翻转成"为什么这样设计、还能怎么设计"。
2. 顺序：总体设计 → 服务端 SDK → RUM SDK → 接入管道 → 存储 → 查询与告警（与数据流向一致：采集 → 管道 → 存储 → 查询）。
3. 读法建议：每篇先看决策表和"常见坑"，能对上自己的经验再回头看机制细节；面试冲刺只看各篇"面试题小结"。

## 贯穿全系列的三条设计公理

- **永不伤害宿主/业务**：SDK 有界队列自损，网关过载拒绝（429）推回退避——数据完整性永远让位于业务存活；
- **按访问模式设计存储**：metrics 窗口聚合、logs 标签过滤+内容扫描、traces ID 点查——三种访问模式决定三副引擎，统一的是 trace_id 关联而非存储；
- **成本是第一等设计约束**：采样率、降采样、保留策略、预聚合四个阀门必须租户级可配，容量表（不是架构图）是设计的第一张表。

## 阶段导读：为什么要有这个阶段

前六个阶段你都是**用户**：用 Prometheus 写查询、配 Loki 管道、接 OTel SDK。本阶段切换到**设计者**视角：如果这些工具都不存在，让你从零造一个 mini 可观测平台，每一层该怎么设计、为什么是这个设计而不是别的？这一视角切换的价值是双重的——日常层面，懂设计的使用者能判断"这条查询为什么慢、该动哪一层"而不是只会调参数；求职与晋升层面，"设计一个可观测系统"正是该方向系统设计面与架构评审的核心考题，而考官想听的恰恰是本阶段这套"从需求反推、逐层决策、对照开源"的思路。

本阶段的方法论固定为三步，六篇笔记全部遵循：

1. **从排障工作流反推需求**：不从"我要存三种数据"出发，而从"值班工程师处理一次告警的每一步需要什么能力"出发——这是 architecture-overview 的第一章，也是整个系列的锚点；
2. **容量先行**：一条算例走完三种信号的量级估算（写入速率、存储增长、查询压力），容量表是设计的第一张表，拓扑、介质、预算全由它决定；
3. **逐层决策 + 对照开源**：服务端 SDK、RUM SDK、接入管道、存储后端、查询与告警五篇，每篇先给最小可用骨架与决策表，再对照 OTel / Prometheus / Mimir / Loki / Tempo 的工业级做法——你既能看懂开源为什么这样设计，也能判断自己的场景该抄哪一处、改哪一处。

贯穿全系列的三条设计公理（永不伤害宿主、按访问模式设计存储、成本是第一等约束）不是凭空提出的，它们分别对应前六个阶段的真实痛点：SDK 有界队列自损对应"埋点拖垮业务"的案例，"三副引擎"对应阶段 2 的存储选型，成本四阀门（采样率、降采样、保留策略、预聚合）对应阶段 5 的全部主题。**本阶段不引入任何新工具**——它需要的所有前置都在前面，这也是它适合当收官复盘的原因。

## 常见误区与正解

- **误区一："设计可观测系统，先把三种数据的存储引擎定下来。"**
  为什么错：存储选型由访问模式决定——指标是按时间窗聚合、日志是标签过滤后扫内容、trace 是按 ID 点查；跳过访问模式直接选引擎，容易选出一个"什么都能存、什么都查不快"的通用库。
  正解：先写排障工作流与查询模式清单，再让三种访问模式各自选引擎；统一的只有 trace_id 关联，不是存储。
- **误区二："用一个大而全的数据库统一存三种信号，架构更简单。"**
  为什么错：三种信号的写入吞吐、压缩特征、查询语义、保留策略完全不同；单一引擎要么为日志牺牲指标查询性能，要么为指标浪费日志存储成本。
  正解：接受"三副引擎 + 统一查询面"的形态——Grafana 的统一是查询面统一，不是存储统一。
- **误区三："SDK 直写存储，省掉接入层，少一个组件。"**
  为什么错：脱敏、配额、协议适配、尾部采样、多后端分发全都没有落脚点；SDK 直写还要求每个客户端都懂每种后端的写入语义，客户端复杂度爆炸。
  正解：保留接入管道（agent / gateway 两级拓扑），把"脏活"全部收进管道，SDK 只管产出。
- **误区四："过载时排队，尽量不丢数据。"**
  为什么错：排队会把延迟与内存压力转嫁给 SDK 与宿主业务——可观测数据把业务打挂，是最不可接受的故障形态。
  正解：拒绝优先于排队：网关 429 推回退避，SDK 有界队列自损；数据完整性永远让位于业务存活。
- **误区五："容量等上线后压测再估，架构评审不用算数。"**
  为什么错：容量决定拓扑（单机还是分片）、存储介质与预算，是设计的第一张表；上线后才发现量级差一个数量级，等于重做架构。
  正解：用 architecture-overview 的算例先估出写入速率、存储增长、查询压力三个数，再谈选型与评审。

## 一页速记：三条公理与六层决策

公理三句，任何设计讨论先对齐它们：

1. 永不伤害宿主与业务——网关过载拒绝（429）推回退避，SDK 有界队列自损；
2. 按访问模式设计存储——三副引擎各管一类查询，统一的是 trace_id 关联；
3. 成本是第一等约束——采样、降采样、保留、预聚合四个阀门必须租户级可配。

决策六问，覆盖六篇笔记的主线：需求从哪反推（排障工作流）？量级多大（容量表）？SDK 怎么做到不伤宿主（控制反转与队列策略）？管道拒谁保谁（拒绝优先于排队）？每类数据用什么引擎（访问模式定引擎）？查询怎么快、告警怎么收敛（拆分缓存与状态机）？

自测方式很简单：六问每问能在白板上写出三行有取舍的回答，就具备参加架构评审的入场水平；写不出的那一问，对应的那篇笔记就是你的复习范围。
