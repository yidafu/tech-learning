# 第三阶段导览：建立连接——DNS、TCP/UDP、ICMP 与 TLS

> [返回：浏览器与网络原理学习大纲](../浏览器与网络原理学习大纲.md)
> 本文是第三阶段的入口。这一阶段覆盖主时间线的 ③④⑤ 三步：域名变成 IP（DNS）、建立管道——可靠的 TCP 与轻量的 UDP，外加网络层的报信协议 ICMP、把管道升级成加密信道（TLS）。

**建议时长**：1.5 周（含抓包实验）。弱网下这三步能吃掉首屏时间的一半以上；它们也是「为什么 CDN、连接复用、0-RTT 这些优化有效」的物理基础。这一阶段的特点是：**每个包都看得见**——我们会真的抓包逐个看。

## 阶段目标

学完本阶段，你应该能不查资料做到这些事：

1. 画出 DNS 从浏览器到权威服务器的完整查询路径，说清递归查询与迭代查询的区别，以及 TTL、负缓存各缓住了什么。
2. 解释为什么「第一次访问慢、第二次快」——把浏览器 DNS 缓存、OS 缓存、resolver 缓存各层的 TTL 对上号。
3. 画出三次握手的时序图（SYN → SYN+ACK → ACK），说出每一步之后双方的 TCP 状态（CLOSED → SYN_SENT → …），并解释为什么不是两次握手。
4. 说出 TLS 1.2（2-RTT）与 TLS 1.3（1-RTT）握手的差异，解释 0-RTT 为什么快、为什么有重放风险、哪些请求敢用 0-RTT。
5. 解释证书链验证：浏览器拿到一张证书后如何一级级验到根 CA，中间证书缺失为什么会失败。
6. 在 Wireshark 里过滤出一次完整握手的所有包，给每个包写一行注释。

## 知识点地图

### 1. DNS（02 册）

- **查询路径**：浏览器缓存 → OS 缓存（macOS `/etc/resolver`、Windows ipconfig displaydns）→ 本地 resolver（运营商或 8.8.8.8 等）→ 根 → TLD（.com）→ 权威。resolver 与权威之间是迭代查询，客户端与 resolver 之间是递归查询。
- **两个容易被忽视的缓存**：负缓存（查不到也缓存一段时间，NXDOMAIN 拖累重试）与浏览器自己的连接池复用（DNS 没查但连接还在，根本不用查）。
- **CDN 调度**：同一域名解析出的 IP 随地理位置变化（GSLB），resolver 位置 ≈ 用户位置（EDNS Client Subnet 把客户端网段带给权威），这就是「DNS 也是负载均衡」的含义。
- **DoH/DoT**：明文 DNS 会被中间设备窥探/劫持，加密 DNS（HTTPS 上的 DNS / TLS 上的 DNS）正在变成浏览器默认。

### 2. TCP（03 册）

- **三次握手**：SYN（客户端 SYN_SENT）→ SYN+ACK（服务端 SYN_RCVD）→ ACK（双方 ESTABLISHED）。两次握手的问题在于旧重复 SYN 会让服务端误建半连接。
- **握手=1 个 RTT 纯开销**：数据一个字节没传，弱网 4G 下这一个 RTT 就是 ~100ms——这是后面「连接复用」「0-RTT」「TLS1.3 握手合并」所有优化的靶子。
- **握手只是开始**：慢启动意味着连接刚建立时吞吐起不来（cwnd 从 10 个 MSS 起步），首屏这种「短连接突发传输」的形态对拥塞控制最不友好。
- **SYN cookie**：半连接队列被 SYN 洪水打满时的防御：把状态编码进 SYN+ACK 的序列号，不占队列。

### 3. UDP 与 ICMP（04 册）

- **UDP 是「无连接」的极简信封**：8 字节头（源/目的端口/长度/校验和），无握手、无重传、无拥塞控制——可靠性、顺序、限速的决定权全部交还应用。
- **报文有边界**：一次 send = 一个完整报文——与 TCP 字节流的应用写法差异的根源。
- **谁在用 UDP**：DNS（一问一答，丢了重问比维护连接便宜）、QUIC/h3（在用户态重造可靠传输）、WebRTC（实时性优先，丢帧比重传好）。
- **UDP 与 IP 分片**：报文超 MTU 由 IP 分片，任何一片丢失整个报文作废——应用层把报文限制在单 MTU 内是纪律（DNS resolver 载荷 1232 的算术来历）。
- **ICMP 是网络层的报信协议**：没有端口、不承载数据；类型 3（不可达）/11（超时）是排障高频；ping（Echo 8/0↔0/0）与 traceroute（TTL 递增逼出逐跳回音）是它的两张王牌；PMTUD（类型 3/4）失效造成「小包通、大包卡」的黑洞故障。

### 4. TLS（05 册）

- **握手做什么**：协商密码套件、验证证书链、交换密钥材料、派生对称会话密钥。1.2 要 2-RTT，1.3 把它压到 1-RTT 且握手密钥与应用数据密钥分离。
- **证书链**：叶子证书 → 中间 CA → 根 CA，逐级验签 + 有效期 + 域名匹配 + 吊销状态（OCSP/OCSP 装订——为什么「装订」比实时查询快）。
- **SNI 与 ECH**：ClientHello 明文带了要访问的域名（SNI），中间设备看得见；ECH（Encrypted Client Hello）把 SNI 加密，是「加密到什么程度」的边界问题。
- **会话恢复与 0-RTT**：session ticket / PSK 让「见过面的双方」跳过大部分握手；1.3 的 0-RTT 允许第一个包就带数据，但该数据可被重放——所以只用于幂等请求。
- **ALPN**：TLS 握手里顺带协商应用层协议——h2/h3 的开关就在这里，第四阶段的协议升级全靠它搭便车。

## 实践任务

1. `dig +trace example.com` 看一次完整的迭代查询路径；再查两次，对照缓存命中时路径怎么缩短。
2. 用 Wireshark 抓自己本地站点的握手：过滤 `tcp.port == 端口`，标注 SYN/SYN+ACK/ACK 与 ClientHello/ServerHello/Finished（06 册有逐步指引）。
3. 用 `openssl s_client -connect 主机:443 -showcerts` 打出完整证书链，数一数链上有几张证书、根在哪。
4. 在 Network 面板里找一个 HTTPS 站点的连接建立段，读出 DNS/Connect/SSL 各花了几毫秒（`Timing` 标签）。

## 自测题

1. 递归查询和迭代查询的区别是什么？为什么 resolver 到权威之间用迭代？（提示：根服务器扛不扛得住全世界的递归）
2. TTL=300 的记录在 OS 缓存过期后，下一次查询一定到得了权威服务器吗？中间还有哪些层可能给出答案？
3. 三次握手里第三次 ACK 丢了会怎样？双方各是什么状态？这个连接后续还能建立成功吗？
4. 为什么 TLS 1.3 能把握手从 2-RTT 压到 1-RTT？压掉的这一个 RTT 里原来在传什么？
5. 0-RTT 数据被重放会造成什么实际危害？举一个「绝不能放在 0-RTT 里」的请求例子。
6. 服务器只配置了叶子证书和私钥、没配中间证书，浏览器会怎么失败？curl 和浏览器行为一样吗？（提示：AIA chasing）
7. `Connection: keep-alive` 复用的是哪几步？（把 ③④⑤ 想成一个整体再回答）HTTP/3 复用的又是什么？
8. dns-prefetch 和 preconnect 分别替你提前做了哪几步？各自的收益上限是多少毫秒（按 RTT 估）？
9. 一个页面同时要连 30 个不同域名，HTTP/1.1 时代和 HTTP/3 时代的连接数与握手次数会有什么数量级差异？
10. 抓包时你能看到 TLS 之后的 HTTP 头吗？为什么看不到？加密的具体是从哪一层开始、用什么密钥？
