# 实践：用抓包工具拆一次真实握手

> [← 第三阶段导览](01-导览.md) · 本阶段收束实验。前四册讲了 DNS/TCP/UDP+ICMP/TLS 的理论时序，这一册把它们全部落到 Wireshark 的包上：每一个握手包亲手标注一遍，并把包序列与 DevTools 的 Timing 段一一对上。做完本册，第三阶段才算闭环。

**产出物**：`labs/handshake-截图/` 下的一组标注截图 + `labs/handshake-复测表.md`（模板见 §8.5）。

## 1. 环境准备

1. **安装 Wireshark**（官网 dmg，装完重启让抓包驱动生效）。
2. **选接口**：Wireshark 首页选活动网卡（无线上网选 Wi-Fi 接口）；抓回环流量（本地站点）选 **Loopback: lo0**。
3. **降噪**：
   - 用 Chrome 隐身窗（排除扩展的请求）；
   - 关掉会自动联网的应用（网盘/聊天/邮件）；
   - 优先抓**本地回环站点**的握手——背景流量为零，包序列最干净。
4. **起一个本地站点**：

   ```bash
   # 明文 HTTP（实验一/五用）
   python3 -m http.server 8080 --directory 你的站点目录
   # HTTPS（实验三用）：任选一种最快路径
   caddy file-server --listen :8443 --tls    # 自签证书一步到位
   # 或 mkcert 生成可信自签证书后挂给任意本地 server
   mkcert -install && mkcert localhost
   ```

没有 HTTPS 环境也能完成 §2/§3/§6/§8 四个实验，§4/§5 用真实站点。

## 1.5 Wireshark 速查：本册要用的过滤器与操作

| 目的 | 显示过滤器/操作 |
|---|---|
| 只看某条 TCP 连接 | `tcp.port == 8080` |
| 只看握手包 | `tcp.flags.syn == 1 or tcp.flags.fin == 1` |
| 只看 DNS | `udp.port == 53` |
| 只看 TLS 握手 | `tls.handshake.type`（1=ClientHello, 2=ServerHello, 11=Certificate…） |
| 只看 ICMP | `icmp`（ping 用 `icmp.type == 8 or icmp.type == 0`） |
| 明文 HTTP | `http.request or http.response` |
| TCP 异常（重传/复位） | `tcp.analysis.flags`（重传/乱序/丢包全部高亮） |
| 抓回环 | 接口选 Loopback: lo0（macOS） |

包详情展开的标准路径（记这个顺序，每个实验都用得上）：

```text
Frame 层        → 抓取时间戳、长度（对账 Timing 的原始依据）
Ethernet/IP 层  → IP 地址（本回环实验里都是 127.0.0.1）
TCP/UDP 层      → 端口、seq/ack、标志位、窗口、Options（MSS/WS/SACK）；UDP 只有 8 字节头
ICMP/TLS/HTTP 层 → 报信包、握手消息或明文报文（按实验对象不同）
```

读包纪律：**先看 Wireshark 自动标注的 Info 列（Summary），再展开层细节**——Summary 已经把 SYN/ACK/挥手/重传都标注好了，别一上来就扎进十六进制。

## 2. 实验一：TCP 三次握手（对照 03 册）

**过滤器**：`tcp.port == 8080`（换成你的本地端口）。

动作与标注清单：

1. 浏览器第一次访问本地站点，Wireshark 停止抓取；
2. 找到包 1/2/3：`[SYN]`（seq=x）→ `[SYN, ACK]`（seq=y, ack=x+1）→ `[ACK]`（ack=y+1）；
3. 逐包核对：包 1 的 seq 与包 2 的 ack 差 1（**SYN 消耗一个序号**——03 册原话落地）；
4. 展开包 1 的 Options 区，找出 **MSS、Window Scale、SACK permitted**——握手协商选项的实物（对照 03 册 §9 的字段树）；
5. 截图，把上述标注写在图上或 `labs` 笔记里。

你在 Wireshark 里看到的包列表大致长这样（字段值示意）：

```text
No.  Time     Source          Destination     Info
1    0.000    127.0.0.1:54321 127.0.0.1:8080  54321 → 8080 [SYN] Seq=0 Win=65535 Len=0 MSS=1460 ...
2    0.00004  127.0.0.1:8080  127.0.0.1:54321 8080 → 54321 [SYN, ACK] Seq=0 Ack=1 ...
3    0.00007  127.0.0.1:54321 127.0.0.1:8080  54321 → 8080 [ACK] Seq=1 Ack=1 ...
```

**进阶**：再访问第二次（不同连接），对比两条握手的 ISN 随机性（每次连接初始序号不同）。

## 3. 实验二：DNS 查询（对照 02 册）

**过滤器**：`udp.port == 53`。

1. 清缓存（`chrome://net-internals/#dns` → Clear host cache；macOS 再 `sudo killall -HUP mDNSResponder`）；
2. 访问一个**从未访问过**的域名，抓 UDP 53 的查询与应答；
3. 展开应答包的 Answers 区：找出 A 记录、TTL 数值，若有 CNAME 记下链；展开 Header 区对照 02 册 §2.5 的字段表（QR/RD/RA/RCODE）；
4. 对比实验：同一域名查第二次——包数与耗时变化（缓存命中时**根本没有 53 端口的包**，这本身就是结论）；
5. 若浏览器开了 DoH（安全 DNS）：重复抓取，UDP 53 消失、流量走 443——02 册 §6 的现象实证。

## 4. 实验三：TLS 1.3 握手（对照 05 册）

**过滤器**：`tcp.port == 443`（抓真实站点）或本地 TLS 端口。

1. 清浏览器连接（重启隐身窗，确保不走会话恢复）；
2. 抓一次完整 HTTPS 连接建立；
3. 找到 ClientHello 包，展开 TLS 层：
   - **Server Name** 扩展里的域名（SNI 明文可见——05 册 §10 的现场）；
   - **ALPN** 扩展（05 册 §11 的实物：h2/http/1.1 的协商）；
   - 密码套件列表、**key_share** 扩展（1.3 的密钥材料前置）；
4. 找 ServerHello 包，确认之后紧跟的加密包（EncryptedExtensions/Certificate/CertificateVerify/Finished 都已加密——包名在 Wireshark 里显示为 Application Data，内容不可读）；
5. 数一数：ClientHello → ServerHello+加密块 → 客户端 Finished，两个飞行包完成握手；
6. 若能抓到一台 TLS 1.2 的站点（老服务），对比包数与明文的 Certificate 包——两个版本的差异一眼见分晓（对照 05 册 §13.5 全项对照表）。

## 5. 实验四：解密自己的 HTTPS 流量（SSLKEYLOGFILE）

ECDHE 前向保密下 Wireshark 解不开 1.3 流量——但浏览器支持导出密钥日志，仅限**本机调试**场景：

```bash
# macOS / Linux：让浏览器带密钥日志启动（先完全退出 Chrome）
SSLKEYLOGFILE=~/tls-keys.log open -na "Google Chrome"
# Windows(PowerShell)：
# $env:SSLKEYLOGFILE='C:\temp\tls-keys.log'; & "chrome.exe"
```

然后 Wireshark → Settings → Protocols → **TLS** → (Pre)-Master-Secret log filename 填 `~/tls-keys.log` → 重新抓取访问。效果：TLS 层之下多出解密出的 **HTTP/2** 层，能看到请求头明文。

**三条纪律**：

1. 密钥日志文件等于全部会话密钥，只在本地调试用、用完删；
2. 绝不用于解密他人流量（也解不开，密钥只在双方内存里）；
3. 它解的是 TLS，**QUIC（h3）流量在 Wireshark 里的解密配置不同**（第四阶段再补）。

### 5.5 解密成功后看什么：一个请求的解密实景

密钥日志配好后，Wireshark 的包详情里会多出两层——解密后的 TLS 与 HTTP/2。展开一个真实请求帧的形态（字段示意）：

```text
Hypertext Transfer Protocol 2
  Stream: HEADERS (1), Stream ID: 1
    :method: GET
    :authority: example.com          ← h2 伪头部（第四阶段 03 册的主角）
    :scheme: https
    :path: /
    user-agent: Mozilla/5.0 ...
    accept: text/html,...
Secure Sockets Layer
  TLSv1.3 Record Layer: Application Data
    Opaque Type: 23 (Application Data)   ← 不配密钥日志时你只能看到这一行
```

三层对照是本实验的验收点：**最外层是密文记录（不配日志时的全部所见）→ 解密出 TLS 记录 → 再解出 HTTP/2 帧**。顺带确认两件事：

1. 解密后能看到请求头全貌（含 Cookie）——§5 纪律「密钥日志等于全部会话密钥」的直观证据；
2. 一个 Application Data 包里可以装多个 h2 帧——「包」与「报文」不是一比一，第四阶段讲分帧后这个感觉会越来越重要。

## 6. 实验五：HTTP/1.1 明文现场（第四阶段预告）

找一个仍支持 http 的站点或本地明文服务，过滤器 `http.request`：

1. 直接看到请求行（`GET / HTTP/1.1`）与全部请求头——第四阶段 02 册的报文结构实物；
2. 看 Host 头、Cookie 明文（为什么明文 http 上 Cookie 是裸奔）、Connection: keep-alive；
3. 对照：同一服务器换成 https 后这些内容全部隐入加密层——「加密的是 TLS 记录层，不是 URL 本身」（域名与 IP 在 SNI/DNS/TCP 层仍然可见，呼应 05 册 §10）。

## 7. 对账：包序列 ↔ DevTools Timing

完成上述实验后，把两边对上——这是本册的验收核心：

| DevTools Timing 段 | 抓包里的包序列 |
|---|---|
| DNS Lookup | UDP 53 的查询+应答（或 DoH 的 HTTPS 流量） |
| Initial connection | SYN → SYN+ACK → ACK |
| SSL | ClientHello → …→ 双方 Finished |
| Request sent | 客户端第一个带应用数据的包（明文可见 GET 行；密文时看 TLS 记录类型） |
| Waiting (TTFB) | 请求发出 → 服务器响应首字节包 |
| Content Download | 后续数据包流 |

### 7.5 实验六：复用连接 vs 新建连接（03 册核心结论的包级证明）

同一站点连续两次导航，抓包对比两次「第一次字节」的出发位置：

| | 第一次导航 | 第二次导航 |
|---|---|---|
| SYN 三元组 | 有 | **无**（复用连接） |
| ClientHello | 有 | 无 |
| DNS | 有（若冷） | 无 |
| 从输入到 GET 行 | 握手全链之后 | **立即** |

操作：抓包开起来 → 导航到站点（冷）→ 回首页 → 再点同一链接 → 停止抓包 → 对比两条流。**第二次导航的请求行直接出现在既有连接的数据流里**——这就是「复用让 ③④⑤ 归零」的包级证据，也是本阶段所有理论的一个闭环实验。

## 8. 实验七：ICMP 三连（对照 04 册）

**过滤器**：`icmp`。

1. **ping 拆包**：`ping example.com` 期间抓包，找 `Echo Request (type=8)` 与 `Echo Reply (type=0)` 的包对，读出 RTT 与 ttl——04 册 §8 的现场；
2. **traceroute 拆包**：`traceroute example.com` 期间抓包，观察 **TTL 递增的探测包**与各跳回的 `Time Exceeded (type=11)`——「故意把 TTL 设成 N 来逼出第 N 跳」的机制实证；Linux 版末尾的 `Port Unreachable (type=3, code=3)` 是 UDP 探测包被目的主机拒收的收尾（04 册 §8 的两种收尾形态）；
3. **端口不可达对照**：对本机一个没有服务监听的 UDP 端口发消息（`nc -u localhost 9999`），抓 ICMP 3/3 回音——「UDP 端口没开」的标准报信，与 TCP 的 RST 对照。

### 8.7 对账差异排查

两边数字对不上时，按这张表找原因——**对不上才是常态，解释清差异才是本事**：

| 差异现象 | 最可能原因 |
|---|---|
| DevTools 有 DNS 段，抓包里没有 UDP 53 | 走了 DoH（流量在 443 上）；或 OS 缓存命中（根本没出网） |
| 抓包有完整握手，DevTools 的 Timing 没有 DNS/Connect/SSL | 这条连接是复用的（DevTools 只给「这次请求」的增量段） |

**Q：一次抓包实验的最小记录单元是什么？**
四件套：过滤器表达式、包列表截图（含序号）、关键包的字段树展开截图、一句话结论（与理论预期的差异及原因）。少了截图，结论无法回溯；少了差异记录，实验退化为「看了一遍」——本册 §6.5 的记录表就是这四件套的表格化。

### 9.5 抓包三大陷阱（新手必然踩）

| 陷阱 | 现象 | 解法 |
|---|---|---|
| **代理劫持** | 挂了系统代理/抓包工具（如 Charles）时，Wireshark 看到的是「本机 → 代理」的连接，不是到真实服务器 | 抓包前关掉所有代理，或明确抓「到代理的这段」 |
| **回环不走网卡** | 访问本机站点，Wi-Fi 接口上一个包都没有 | 本机互访走 Loopback 接口——切接口不是没抓到 |
| **HTTPS 全是密文以为抓坏了** | TLS 流量下看不到任何 HTTP 字样 | 正常！前向保密的设计行为——解密走 §5 的密钥日志 |

加上一条经验：**每次实验只改变一个变量**（清不清缓存、换不换协议版本），否则包序列的差异无法归因——这是所有网络实验的第一纪律。

## 10.5 常见问答

**Q：Wireshark 和 DevTools Network 面板有什么区别？都用学吗？**
层次不同。DevTools 看到的是「应用视角」——连接已建好、解密后的请求/响应；Wireshark 看到「包视角」——三次握手、TLS 握手、重传这些被 DevTools 抽象掉的细节。学链路用包视角验证协议行为，做日常开发用 DevTools。第三阶段必须用 Wireshark，第四阶段起 DevTools 为主。

**Q：为什么 Timing 段加起来不等于总耗时？**
分段之间有空隙（内核与用户态交接、浏览器内部处理），且 Queueing/Stalled 的边界是人为定义。对账时允许 ±10% 的误差，抓大放小。

**Q：企业内网抓不到预期的包？**
先查是不是走了公司代理（§9.5 陷阱一）——Wireshark 看到的是到代理的连接，SNI/目标 IP 都是代理的。这类环境做本册实验建议用手机热点。

**Q：实验做完了，抓包能力在日常开发里怎么用？**
三个高频场景：①「偶发慢」定位——看是握手慢（DNS/TCP/TLS 段长）还是传输慢（重传/ZeroWindow）；②新协议验证——站点开 h2/h3 后抓包确认协商结果与帧的形态；③证书行为排查——SNI、链完整性、装订。日常不必常开，**「DevTools 解释不了的时候」才是 Wireshark 上场的时候**。

**Q：抓包文件太大跑不动怎么办？**
抓之前就用捕获过滤器（Capture Filter，如 `host example.com`）收窄，而不是抓完再过滤——显示过滤器不减少内存占用。已有的大文件用 File → Export Specified Packets 切出关心的会话留档。这是「抓包十分钟、分析一小时」的标准预防针。

**Q：为什么我抓到的包里 seq 从 0 开始？说好的 ISN 随机化呢？**
Wireshark 默认显示**相对序号**（把真实 ISN 归一化为 0，方便人读）；勾选 Edit → Preferences → Protocols → TCP 的 "Absolute sequence numbers" 才显示真实值。03 册 §9 字段树里 `Sequence Number: 0` 与 `Sequence Number (raw): 283746112` 并排出现，就是这个归一化在起作用——「随机化」没消失，只是被 Wireshark 折叠了。

**Q：Wireshark 显示的 Time 列比 DevTools Timing 的同名段短/长，哪个准？**
都准，口径不同：Wireshark 是包到达内核的绝对时刻，DevTools 是浏览器应用层的事件时刻——中间隔着解密、协议处理、事件派发。对账时用「同一起点归零 + 只比差值」的规则（§8.7 排查表的原则），不要逐段硬对齐。
