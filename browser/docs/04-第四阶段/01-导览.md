## 阶段目标

学完本阶段，你应该能不查资料做到这些事：

1. 手写一个合法的 HTTP/1.1 请求报文和响应报文（起始行、头、空行、体），说清每一行是给谁看的。
2. 解释队头阻塞在三个层面各是什么：HTTP/1.1 的应用层阻塞、HTTP/2 的 TCP 层阻塞、HTTP/3 如何用独立流解决。
3. 说出 HTTP/2 一个连接上 stream / message / frame 的层级关系，以及优先级依赖树怎么影响帧的发送顺序。
4. 解释为什么浏览器有 6 个 HTTP/1.1 连接限制，而 HTTP/2 时代域名分片（sharding）反而变成反模式。
5. 说出 HTTP/3 的三个核心卖点（握手合并、连接迁移、无 TCP 层队头阻塞）各自的原理，以及为什么连接迁移在 WiFi→5G 切换时有效。
6. 看到一组响应头，能说出：这段内容是怎么协商出来的（Accept*）、这发请求带没带凭证（Cookie 属性）、这个 304 是靠哪个验证器换来的。

## 知识点地图

### 1. HTTP/1.1（02 册）

- **报文是纯文本**：起始行 + CRLF 头 + 空行 + 可选体。头重复、大小写、空格容忍度——文本协议的历史包袱。
- **连接管理**：短连接 → keep-alive（复用，串行）→ 管线化（并行发送，但响应必须按序回 → 实际没人敢用 → 废弃）。
- **6 连接限制的由来**：浏览器对同 host 并发 TCP 的上限。它催生了域名分片、雪碧图、内联——又全被 HTTP/2 反向淘汰。
- **幂等性**：GET/PUT/DELETE 幂等、POST 不幂等——幂等性决定了自动重试敢不敢发，也决定了 0-RTT 敢不敢带。

### 2. HTTP/2（03 册）

- **分帧**：报文被切成带 stream ID 的二进制帧交错传输；一个连接上 N 条流并行，响应顺序不再绑定发送顺序。
- **优先级**：依赖树（浏览器声明「CSS 比图片重要」），服务端按树调度帧——理想丰满，实现参差，后来被 RFC 9218 的优先级信号取代。
- **HPACK**：头压缩（静态表 + 动态表 + Huffman），HTTP 头从每次几 KB 压到几十字节；动态表依赖包序 → 头部也怕丢包。
- **TCP 队头阻塞**：一个包丢了，内核层面所有流的数据都得等重传——应用层解复用了，传输层还是一个字节流。这是 HTTP/3 存在的核心理由。

### 3. HTTP/3 与 QUIC（04 册）

- **QUIC = UDP 上的可靠多路传输**：每个流独立丢包恢复，一个流丢包不再阻塞别的流。
- **握手合并**：传输握手与 TLS 握手叠在一起，首次连接 1-RTT、恢复连接 0-RTT——第三阶段的 TCP+TLS 两段被合成一段。
- **连接迁移**：连接身份是 Connection ID 而非「四元组」，换网络（IP 变了）连接不断——视频通话与长下载的救星。
- **发现与降级**：`Alt-Svc` 头 / HTTPS DNS 记录告诉浏览器「这里支持 h3」，浏览器先 h1/h2 连上再试升级；失败回退。

### 4. 请求语义（05 册）

- **内容协商**：Accept / Accept-Encoding / Accept-Language 与服务端 Vary 的配合——Vary 头错一个字，缓存体系就乱一套。
- **Cookie 属性全解**：Domain/Path/Expires/Secure/HttpOnly/SameSite（Strict/Lax/None）/Partitioned（CHIPS）——每个属性都在回答「这个 Cookie 在什么边界内可见」。
- **条件请求**：If-None-Match/ETag（强/弱验证器）与 If-Modified-Since/Last-Modified 两套体系，304 的经济学（省了体，省不了 RTT）。
- **Range**：断点续传与视频拖动的基础；配合 206/416 与 `Accept-Ranges`。

## 实践任务

1. `curl -v --http1.1` 与 `curl -v --http2` 各请求一次目标站点，对比响应头与连接行为。
2. 在 Network 面板把 Protocol 列打开，数一数目标站点的 h1/h2/h3 分布；找到那个还在用 h1 的第三方请求。
3. 用 `curl -H "Accept-Encoding: gzip" -I` 与不带该头各请求一次，对比 Content-Encoding 与体积。
4. 手写一个带 `If-None-Match` 的 curl 请求，复现 304；故意改错 ETag，观察 200。
5. DevTools 里对一个请求右键 Copy as cURL，分析它带了哪些 Cookie、哪些头是浏览器自动加的。

## 自测题

1. HTTP/1.1 管线化为什么失败了？它和 HTTP/2 多路复用「看起来都解决了串行等待」，本质差异在哪？
2. 一个页面引用了 20 个同域名小文件，h1（6 连接）与 h2（1 连接）下各自的请求排队形态是什么样的？画出瀑布图对比。
3. 为什么 HTTP/2 时代「域名分片」从优化变成反模式？写出两个原因。
4. TCP 队头阻塞的一个丢包为什么能拖住所有 HTTP/2 流？QUIC 是在哪一层做了「分流的丢包恢复」？
5. QUIC 的连接迁移为什么可能？迁移后 NAT 重绑定失败会怎样？
6. `Vary: User-Agent` 会让 CDN 缓存发生什么？为什么这行头在移动时代几乎不可用？
7. SameSite=Lax 的 Cookie 在跨站 `<img>`、顶级 GET 导航、顶级 POST 表单三种场景下分别发不发？
8. 强 ETag 和弱 ETag（W/）的区别是什么？静态资源该用哪个？
9. 304 响应省了什么、没省什么？如果 RTT 是 100ms，304 比直接 200+小文件还慢吗？
10. CORS 预检（OPTIONS）在本阶段的协议视角下是什么？为什么「带自定义头的跨站请求」会先飞一个 OPTIONS？（攻防细节详见 security 站，这里只需说清链路位置）
