# HTTP/2：分帧、多路复用与优先级

> [← 第四阶段导览](01-导览.md) · 时间线 ⑥。h1 的病根是「一根连接一次一个请求」；h2 的药方是把报文打碎成带编号的二进制帧，在同一根 TCP 连接上交错传输。这一册讲分帧与多路复用怎么落地、HPACK 怎么把头开销砍掉一个量级、优先级机制为什么陨落、以及 h2 没解决的那一半——TCP 层队头阻塞（把 h3 请出场的伏笔）。

## 1. 演进史：从 SPDY 到 h2——用实测数据赢下的一次换代

h2 不是 IETF 凭空设计的，它是 Google SPDY 的标准化后代。这条演进线值得完整记一遍——「性能优化 → 实测数据 → 标准化」的完整闭环，是协议演进里少有的快节奏案例：

| 年份 | 事件 | 关键点 |
|---|---|---|
| 2009 | Google 发布 **SPDY**（发音 "speedy"） | 立项目标直白：**把页面加载时间砍一半**。作者 Mike Belshe（后来又主导了 QUIC 立项）；核心三板斧：二进制分帧复用、头压缩、优先级——今天 h2 的三大支柱此时已成形 |
| 2009-2012 | SPDY 在 Chrome 部署，Twitter/GitHub 等跟进 | **实测数据**说话：Google 公布 SPDY 比 HTTP/1.1 加载快 11%~64%（页面复杂度越高收益越大）——「下一代该往哪走」第一次有了大规模生产环境的证据 |
| 2012 | IETF 成立 **httpbis** 工作组，宣布以 SPDY 为起点制定 HTTP/2 | 标准化的起点是「已被验证的实现」而非白纸——与 h3（先有 gQUIC 再有标准）同一模式 |
| 2012-2014 | 规范化中的关键修改：**NPN → ALPN**；头压缩从 SPDY 的 gzip 改为 **HPACK** | NPN（Next Protocol Negotiation，SPDY 用的协商机制）被更严格的 ALPN 取代（§1.5）；CRIME 攻击证明「对头用通用压缩」是安全事故源，SPDY 的 gzip 头压缩被专门设计的 HPACK 替换（§4 的历史包袱正是从这里背进来的） |
| 2015.5 | **RFC 7540**（h2）+ **RFC 7541**（HPACK）发布 | h2 正式定稿；同月 Firefox/Chrome/Nginx 支持上线——规范与部署几乎同步 |
| 2022 | **RFC 9113** 发布（h2 的勘误与整合版） | 其中最重要的是**正式废弃 PRIORITY 帧**——§6 优先级陨落的规范层句号 |

三个对工程的启示：

1. **「先跑起来再标准化」**：SPDY→h2 与 gQUIC→QUIC（§下一册）都是「生产环境实测数据先赢，标准随后追认」——这也是 Google 系协议能在十年里连赢两代的方法论；
2. **「安全的教训内建进规范」**：CRIME 逼出了 HPACK，安装痛（中间盒）逼出了 ALPN——每一代协议的安全与兼容设计，都写在上一代的伤疤清单里；
3. **「换代不换语义」**：SPDY 从 1.0 起就明确「不改方法/状态码/头语义，只改传输表示」——这是 h2 部署能平滑推进的根因（对比：改语义的换代几乎都死在兼容上）。

### 1.5 谈判出 h2：ALPN

h2 只在 TLS 上跑（浏览器的 h2c——明文 h2——从不支持）。协商发生在 TLS 握手里，就是第三阶段 ClientHello 里那个没展开的 **ALPN** 扩展：

h2 只在 TLS 上跑（浏览器的 h2c——明文 h2——从不支持）。协商发生在 TLS 握手里，就是第三阶段 ClientHello 里那个没展开的 **ALPN** 扩展：

```text
ClientHello
  extension: application_layer_protocol_negotiation
    ALPN protocol: h2            ← 「我会说 h2」
    ALPN protocol: http/1.1      ← 兜底
ServerHello
  ALPN protocol: h2              ← 「就 h2」→ 这条连接从此是 h2
```

没有额外出轨——协议升级搭了 TLS 握手的便车，一次往返定终身。观测点：DevTools 的 Protocol 列、Wireshark 里 ClientHello 的 ALPN 区（衔接第三阶段抓包实验）、`curl -sI -w '%{http_version}\n'`。

ALPN 列表的顺序有讲究：浏览器把最优先的协议排前面，服务器**必须选列表里它支持的第一个**——顺序错误会导致「双方明明都支持 h2 却落在 h1」。CDN/网关配置里「h2 没开但也不报错」的哑故障，ALPN 列表是第一个检查点。

## 2. 二进制分帧：三层概念体系

h2 把「报文」这个单体概念拆成三层，全站最需要记的名词体系：

```text
连接（connection）           1 条 TCP
 └─ 流（stream）            N 条，双向虚拟通道，各有 ID
     └─ 消息（message）      一个完整请求或响应（头帧 + 体帧序列）
         └─ 帧（frame）      最小传输单位，二进制，可交错
```

帧的通用头只有 9 字节：

| 字段 | 大小 | 作用 |
|---|---|---|
| Length | 3 字节 | 帧载荷长度（上限由 SETTINGS_MAX_FRAME_SIZE 定，默认 16KB） |
| Type | 1 字节 | 帧类型 |
| Flags | 1 字节 | 类型专属标志（如 END_STREAM） |
| R + Stream Identifier | 4 字节 | 流 ID（最高位保留）+1 位保留位 |

必须认识的帧类型：

| 类型 | 作用 | 类比 h1 |
|---|---|---|
| HEADERS | 头块（HPACK 压缩后） | 请求/响应头 |
| DATA | 体数据 | 体 |
| SETTINGS | 连接参数协商 | （无对应） |
| WINDOW_UPDATE | 流控窗口增量 | TCP 窗口（但按流/按连接两级） |
| PING | 连接活性探测 | keepalive（应用层版） |
| RST_STREAM | 紧急掐掉一条流 | （无对应——h1 只能掐连接） |
| GOAWAY | 「我要关连接了，流 N 以后别发了」 | Connection: close |

RST_STREAM 是革命性能力：h1 里取消一个下载只能断整条连接（殃及其他请求），h2 里掐流不伤连接——SPA 取消未完成路由请求就是靠它。

流 ID 的奇偶规则：客户端发起的流用奇数，服务端发起（Server Push 用）用偶数——从帧头就能看出「谁发起的」，抓包时一眼分类。

## 3. 多路复用：交错传输与「认领」

同一根连接上两条流的帧交错飞行（ASCII 示意，真实是二进制）：

```text
时间 →
客户端: [HEADERS A] [HEADERS B] [DATA A1] [DATA B1] [DATA A2] ...
服务端: [HEADERS A'] [DATA B'1] [DATA A'1] [DATA B'2] [DATA A'2] ...
         ↑ B 的响应先好先走——顺序不再绑定请求顺序
```

每一帧头里的 Stream ID 就是「认领凭据」：接收端按 ID 把交错的帧流重组回各自的消息。**这就是管线化失败的约束被拔掉的瞬间**——响应顺序彻底自由，慢接口 A 再也堵不住别人。

量化对照（20 个同域名小请求，每个 10ms 服务耗时，RTT 50ms）：

| 模式 | 总耗时量级 | 瓶颈 |
|---|---|---|
| h1 + 6 连接 | ~4 批串行 ≈ 数百 ms | 6 连接内仍串行 + 每条连接爬坡 |
| h2 单连接 | ~1 批并行 ≈ 一两个 RTT | 只剩拥塞窗口和服务器处理 |
| h1 串行单连接 | ~20 × (10+50+50)ms | 全是队头阻塞 |

h1 时代那批「绕限制」的手法（分片/雪碧图/合并）在 h2 下集体反模式的原因也在这里：并发不再靠连接数，靠流。

### 3.5 一个真实帧序列的逐帧解读（解密实景）

接第三阶段 SSLKEYLOGFILE 实验：解密后的一个 h2 请求-响应往返，逐帧读（字段示意）：

```text
→ HEADERS(stream=1, END_HEADERS)     请求头：:method GET :path /（HPACK 后 ~40B）
→ DATA(stream=1, END_STREAM, len=0)  GET 无体——空 DATA 帧带 END_STREAM 表示「我说完了」
← SETTINGS                            连接参数先行（有时在请求前）
← HEADERS(stream=1)                   响应头：:status 200 + content-type...
← DATA(stream=1, len=14000)           响应体第一帧
← DATA(stream=1, len=..., END_STREAM) 响应体最后一帧——END_STREAM = 消息完结
```

四个读帧要点：

1. **END_STREAM 是消息边界**——它落在哪一帧，那条消息就到哪结束；没有它浏览器会一直等；
2. **同一 stream ID 串联起一次完整对话**——请求与响应共用 ID 1；
3. 帧长度 ≠ TCP 包长度：一个 14000B 的 DATA 帧会被 TCP 拆成 ~10 个段发出去——「帧是应用概念、包是传输概念」，两者不是一比一；
4. 交错发生时按 stream ID 分拣——这就是 Wireshark 里「看着乱糟糟」的 h2 流量，重组后「各回各家」。

### 3.7 流的状态机：一条流的一生

每条流在双端各有一份状态机（RFC 7540 §5.1），抓包排障时对着它定位「流卡在哪一步」：

```text
           ┌────────┐  发/收 HEADERS   ┌────────┐  发/收 END_STREAM   ┌──────────────┐
           │  idle  │ ───────────────► │  open  │ ──────────────────► │ half-closed  │
           └────────┘                  └────────┘                     └──────────────┘
             （未启用）                  （双向可传）                      （一端已发完 END_STREAM，
      保留流（PUSH_PROMISE 用）              │                                   对端还能回）
                                            │ RST_STREAM
                                            ▼
                                        ┌────────┐
                                        │ closed │  （对端任何时刻可被 RST 掐断）
                                        └────────┘
```

四个工程要点：

| 点 | 说明 |
|---|---|
| **END_STREAM = 消息终点** | 它落在哪一帧，那条流就进入 half-closed——「我说完了」的唯一协议表达；没有它，对端会永远等下去（排障时「响应 hang 住」先查末帧有没有 END_STREAM） |
| **half-closed(remote/local)** | half-closed(local)=本端已发完可收；half-closed(remote)=对端已发完可发——抓包里判断「谁先说完」的依据 |
| **RST_STREAM 任意时刻可达** | 从 open 直接跳 closed——「取消请求」的协议实体（§2 的 SPA 路由切换场景）；服务器也可以用它拒绝流（如收到禁用的头） |
| **流 ID 不可复用** | 一条连接上流 ID 严格递增、用完不回收——长连接上 ID 单调增长是正常的；GOAWAY 里带的「last stream ID」划分「处理完/没接」的分界（连接迁移与重试的判据） |

## 4. HPACK：头压缩怎么砍掉一个量级

上一册算过：h1 下 30 个请求的重复头 ≈ 15~24KB。HPACK 的三板斧：

| 机制 | 做法 | 例 |
|---|---|---|
| **静态表** | 61 个高频头预置在规范里，直接用索引号 | `:method: GET` = 索引 2，2 字节搞定 |
| **动态表** | 连接级共享的「最近用过的头」FIFO 表，后随请求复用 | 第一个请求发了 800B 的 Cookie/UA 头，之后同值请求只发「索引 62」 |
| **Huffman 编码** | 字符串值再压一道 | 约再省 10~25% |

实测量级：典型浏览器请求头 ~800B → 复用后 **几十字节**；页面级总头开销从 20KB 量级降到 KB 以内。

**动态表的代价**：它是连接级共享状态、按序解码——头块之间产生了顺序依赖，丢一个包，后面所有流的头都解不开（头部的「队头阻塞」）。以及历史安全事件 HPACK bomb（解压放大攻击）催生了实现层的解压内存上限——攻防归 `security/` 站，这里记一句：**共享状态换压缩率，代价是新的故障与攻击面**。h3 的 QPACK 会针对「丢包堵头」专门重设计（04 册）。

动态表还有个容易被忽略的运维含义：**它让连接有了「记忆」**——HPACK 表随连接建立而积累。负载均衡如果把同一客户端的请求散到不同连接，动态表反复重建、压缩率反复退化；会话粘性（第五阶段 03 册的算法）在 h2 下多了一条存在理由。

## 5. 流控：两层 WINDOW_UPDATE

TCP 流控管的是整条连接，h2 需要更细的粒度——**流级流控**，否则一条超大下载流会吃光整条连接的接收窗口，其他流饿死：

```text
TCP 接收窗口（内核，管整条连接）
 └─ h2 流级窗口（应用，默认每流 65535B，SETTINGS 可调）
     └─ h2 连接级窗口（应用，管所有流总和）
```

机制与 TCP 同构：接收方发 WINDOW_UPDATE 帧宣布「我消费掉了 N 字节，窗口+ N」。**调小每流窗口 = 精准的下载限速**（不用断连接）；窗口调 0 = 这条流暂停。抓包/调试时看到大量 WINDOW_UPDATE 是正常背景音，看到窗口常年贴着 0 才是接收端堵住的信号——与 TCP ZeroWindow 的诊断逻辑一致，只是发生在应用层。

### 5.5 流控调参实战与「缓冲放大」

流控参数的三个工程场景：

| 场景 | 调什么 | 效果 |
|---|---|---|
| 限速某条大下载 | 调小该流窗口 | 精准限速不断连接 |
| 高带宽长肥管道 | 调大流窗口（大于 BDP） | 否则管道填不满——TCP 窗口够大也没用，被应用层卡住 |
| 大量并发小流 | 平衡流窗口与连接窗口 | 流窗口过大 = 单流挤占他人；过小 = 每条流都要频繁 WINDOW_UPDATE |

**缓冲放大（bufferbloat）的 h2 版**：接收端应用消费慢时，流控窗口把发送方「止住」，但 TLS/TCP 缓冲里已堆的数据照样占着延迟——「流控正常但延迟高」的经典组合。诊断思路与 TCP bufferbloat 一致：先看窗口有没有贴 0（流控生效），再看 RTT 是否随传输量增长（缓冲堆积）。

## 6. 优先级：依赖树、陨落与 RFC 9218

h2 规范里浏览器可以声明一棵**依赖树**：「CSS 是根、图片挂在 CSS 之下、各带 1~256 权重」——服务端按树调度帧的发送顺序，理想中关键资源先到。

```text
根（权重 256）
 ├─ style.css（关键资源先传）
 ├─ app.js（权重 200）
 └─ img × 10（权重 100，慢慢挤）
```

理想丰满，现实三连击：

1. **实现参差**：各家服务器/CDN 对依赖树的理解与实现差异巨大，同一棵树在不同源上调度完全不同；
2. **浏览器放弃发送**：Chrome 实测发现发出去的优先级信息收益不稳、还占用带宽，干脆停止发送依赖树——规范机制实际死亡；
3. **替代者登场**：RFC 9218 可扩展优先级——一个 `Priority` 头/ trailer，两个字段：

| 字段 | 取值 | 含义 |
|---|---|---|
| urgency | 0~7（0 最高） | 「这活多急」 |
| incremental | true/false | true = 增量有用（视频流边到边看）；false = 整体才有用（JS） |

工程口径：优先级的「声明权」正在从传输规范转向浏览器调度 + 页面用 `fetchpriority`/preload hint（第六阶段）表达——**h2 规范里的依赖树知道即可，别基于它做设计**。

## 7. Server Push 的兴衰

Push：服务器「猜你要什么」，趁响应还没发完就把 CSS/JS 用 PUSH_PROMISE 推下来。设计动机很好——消灭「HTML 到了才发现要 CSS」的那一个 RTT。

死亡原因：

| 病 | 说明 |
|---|---|
| 推了缓存里已有的 | 服务器不知道你浏览器有什么——命中判断只有客户端能做，结果大量重复传输 |
| 与 preload 抢带宽 | 推的优先级生硬，常常挤占真正关键的资源 |
| 单连接下放大 | 全部挤在一条 h2 连接上，错误优先级的代价更高 |

Chrome 2022 年移除支持。替代品 **103 Early Hints**：不推内容，只提前推「加载提示」（该预连哪些域、该 preload 哪些文件）——把「猜」限制在提示层，决策权留给浏览器。第五阶段 02 册展开。

### 7.5 Push 失败的深层原理：缓存知情权的单向性

Push 之死值得提炼成一条架构原则：**「服务器猜客户端缓存」这个方向永远是错的**——缓存状态（memory/disk/SW/Cache API 各层）只有客户端自己知道，且随时间变化。同类错误反复出现：

| 反模式 | 同一错误的现代翻版 |
|---|---|
| Server Push 推已有资源 | 忽略用户缓存状态预取全部图片 |
| 服务端「猜」设备能力下发高清图 | 不看 Client Hints 就下发 |

正解方向一致：**把决策所需的信息传过去（Client Hints、缓存探测 API），或把决策权留给拥有信息的一方（客户端 preload、103 提示）**。「信息不对称决定架构方向」——这个原则在第五阶段 CDN 的缓存键、第九阶段的指标采集里还会反复出现。

## 8. TCP 层队头阻塞：h2 没解决的那一半

多路复用把应用层解耦了，但底下还是一条 TCP 字节流：

```text
流 A: ▓▓▓░ [丢包!] ▓▓▓▓▓   ← 只属于流 A 的包丢了
TCP:  ────────────────────  传输层不认识流——它只能停下等重传
流 B: ▓▓▓▓▓▓ ✋ 全部冻结    ← 无辜的 B 陪绑
流 C: ▓▓▓▓▓▓ ✋ 全部冻结
```

**TCP 不认识流**：重传机制按字节序工作，中间一个洞就堵住整条管道——所有流的帧都在洞后面排着。这把 h1/h2 的丢包敏感性翻转了：

| 网络状况 | 谁更快 |
|---|---|
| 低丢包（正常家宽/办公网） | **h2**（单连接爬一次坡 + HPACK 红利） |
| 高丢包（弱网/差 WiFi） | h1 多连接可能反超（一条连接丢包只堵自己那 1/6） |

已有多份研究给出「丢包率 1~2% 量级时 h2 优势消失甚至反超」的曲线。结论不是「回退 h1」，是「问题在 TCP，不在复用」——把可靠多路复用做到 TCP 底下去，这就是下一册的 QUIC。

## 9. h2 的报文语义微调

头字段规则变了，写服务端/网关配置时用得上：

| 变化 | h1 | h2 |
|---|---|---|
| 头名 | 大小写不敏感 | **强制小写** |
| Host 头 | 必带 | 被 `:authority` 伪头部取代 |
| Connection / Transfer-Encoding | 合法 | **禁用**（连接语义被流替代） |
| 起始行 | 文本两行 | 伪头部 `:method` `:scheme` `:authority` `:path` |

「伪头部」是以 `:` 开头的特殊字段，必须在普通头之前。上一阶段 SSLKEYLOGFILE 实验解密出的 `:method: GET / :authority: example.com` 就是它们的真身。

连接生命周期：SETTINGS 先行协商（帧大小上限、初始流控窗口、头表大小），结束时 GOAWAY 优雅告别（告诉对端「流 N 之前的都处理了，之后的请重连」）——比 TCP FIN 多一层应用语义。

### 9.5 h2 上线的连接前提检查清单

站点开 h2 前过一遍（每一项都是真实踩过的坑）：

| # | 检查 | 不合格的后果 |
|---|---|---|
| 1 | TLS 证书与 ALPN 配置支持 h2 | 客户端全部回退 h1（Protocol 列验证） |
| 2 | 网关/反代的 h2 模块开启（Nginx `http2 on`） | 同上 |
| 3 | 头大小限制 ≥ 大 Cookie 场景（http2_max_field_size 类） | 大头请求被拒（连接级错误，比 h1 更狠） |
| 4 | 移除 h1 时代的域名分片 | HPACK 动态表被拆散，压缩率退化 |
| 5 | 服务端并发流数设置（SETTINGS_MAX_CONCURRENT_STREAMS） | 过小 = 退化为「另一种串行」 |
| 6 | 中间盒对长连接的空闲超时 | h2 单连接被掐 = 全部请求重连 |

## 10. 实验

1. **Protocol 分布普查**：DevTools 打开 Protocol 列，统计你的站点 + 三个常用站的 h2/h3/h1 分布；找出 h1 域名（§ 上一册的练习深化）。
2. **HPACK 效果实测**：SSLKEYLOGFILE + Wireshark 解密自己的 h2 流量，对比第一个请求与后续请求的 HEADERS 帧长度（动态表生效的前后差异）。
3. **RST_STREAM 观测**：在 SPA 站点快速切换路由打断进行中的 XHR，抓包（或 Wireshark 解密）找 RST_STREAM 帧——「取消请求」的协议实体。
4. **队头阻塞模拟**：`netem`（Linux `tc netem` 或 macOS dnctl/pfctl）注入 1% 丢包，分别对 h1 与 h2 站点测加载时间，复现 §8 的翻转曲线。
5. **优先级观察**：对同一页面分别在 DevTools Network 面板按优先级排序（高/中/低列），对照 Critical CSS/JS 与图片的位置——浏览器调度视角的优先级（比传输层的依赖树活得久）。

## 11. 常见误区

1. **「h2 = 更快的 h1，啥也不用改」**：默认收益来自复用与 HPACK，但 h1 时代的反模式（分片/合并）不清理会倒扣分——迁移 h2 的正确姿势是「开协议 + 拆掉旧优化」。
2. **「多路复用解决了队头阻塞」**：只解决了**应用层**那一半；TCP 层的队头阻塞原样保留（§8），弱网下甚至放大——「问题转移」不等于「问题消失」。
3. **「优先级依赖树是产品该依赖的机制」**：浏览器已弃发、服务端实现参差——按 RFC 9218 与 fetchpriority/preload 的现代体系理解（第六阶段）。
4. **「Server Push 失败 = 提前加载资源这个思路失败」**：失败的是「服务器推内容」；「提前给提示」的思路活在 103 Early Hints 与 preload 里。
5. **「HPACK 只是压缩算法」**：它是**有状态的共享表**——这解释了头部的顺序依赖、连接亲和性（连接断了表就没了）、以及为什么 h3 要重做它。
6. **「流控窗口就是 TCP 窗口」**：两层独立机制各管各的；h2 流级窗口调小会直接限速该流，与内核 TCP 参数无关。

### 11.5 常见问答

**Q：h2 下还要不要合并请求/内联资源？**
细粒度反而更优：单请求不再昂贵（无队头等待），拆开有独立缓存收益。「合并」只在一种情况下仍有价值——HTTP 缓存与压缩的效率（少量大文件 vs 大量小文件的 CPU/元数据开销），量级差异通常不大，别为它牺牲缓存粒度。

**Q：为什么我开了 h2，Network 面板还能看到请求排队？**
队列的原因变了：不再是「6 连接用完」，而是「并发流数上限（SETTINGS_MAX_CONCURRENT_STREAMS）」或「优先级低的让路」。看 Queueing 段是否集中在高优先级资源之后——h2 的排队是调度问题，不是连接数问题。

**Q：单连接是不是单点故障？连接断了是不是全页面请求都要重发？**
是的，这是 h2 的结构性格局（GOAWAY/连接异常时全部流终止）。浏览器的补偿：自动重建连接并重发未完成的请求（幂等的安全重发）。权衡上「一条热连接的日常收益」远大于「偶发断连的重连成本」，弱网下另有 h3 接手。

**Q：h2 下 «Keep-Alive 头» 还有用吗？**
没有意义——连接持久是 h2 的内置属性，Keep-Alive/Connection 系头被规范整体禁用（§9 的语义微调表）。配置里还留着这些头的，多半是 h1 时代的遗产，清理即可。

**Q：怎么从外部判断服务端并发流数上限是多少？**
看排队形态：单页面请求 30 个资源，若前 N 个并行、其余整齐排队，N 就是上限（常见值 100~128）。curl 单连接并发打 200 个请求数「同时 flying」的峰值是更直接的量法——它是网关/CDN 的 SETTINGS 协商值，各家不同。
