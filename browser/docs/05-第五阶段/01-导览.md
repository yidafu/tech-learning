## 阶段目标

学完本阶段，你应该能不查资料做到这些事：

1. 描述一个请求从 CDN 边缘到源站的完整路径，说出「缓存命中」与「回源」两种路径各自经过哪些环节。
2. 解释缓存键（cache key）的构成，说出为什么 `Vary` 头、查询参数、Cookie 都会影响命中率。
3. 说清 TTFB 的构成：DNS/连接（已在前段算过账）之外，边缘排队 + 回源 RTT + 服务端计算 + 首字节回程，并给出各自的典型量级。
4. 解释流式 SSR 为什么能把 TTFB 和 FCP 都提前：分块发送、浏览器边收边解析，与 Content-Length 不可知之间的关系。
5. 给出 gzip / brotli / zstd 三者在压缩率与 CPU 成本上的取舍，知道什么内容该什么级别、什么内容根本不该压。
6. 看到一堆 3xx 能报出每种的语义（301/302/303/307/308）与「永久性 + 方法保持」两个维度，并说出重定向链对加载时间的乘法效应。

## 知识点地图

### 1. CDN（02 册）

- **边缘与回源**：边缘节点命中直接返回（几毫秒）；未命中回源（一次额外 RTT + 源站计算）。命中率是 CDN 的生命线。
- **缓存键**：默认 = host + path + 少数头；`Vary`、Cookie、查询串的排序都会改变键——「同一个 URL 两种人看到不同内容」的缓存事故多源于此。
- **stale-while-revalidate / stale-if-error**：先给旧的、后台刷新——用一点新鲜度换大量 TTFB。
- **103 Early Hints**：源站趁生成 HTML 的空档先把「该加载哪些 CSS/JS」推给浏览器（经 CDN 转发），把第六阶段的资源调度提前启动。

### 2. 负载均衡与网关（03 册）

- **L4 vs L7**：四层按连接转发（看不见 URL），七层按内容路由（能按 path/header 分流、能做 TLS 终止）。TLS 终止在哪一层，决定了日志里看到的明文与证书归属。
- **Nginx 事件驱动**：一个 worker 进程 + epoll 扛几万并发连接——与「一连接一线程」模型的对照，是理解「为什么反代这么便宜」的钥匙。
- **限流熔断在浏览器侧的样子**：429（带 Retry-After）、503（带 Retry-After）——网关层的拒绝会以什么姿态出现在 Network 面板。

### 3. 服务端生成与流式（04 册）

- **模板渲染**：传统 SSR 是「全部拼好再发」——TTFB = 计算完成时间；数据库慢 200ms，浏览器就白等 200ms。
- **流式 SSR**：骨架先发、数据到了再 flush，配合浏览器「边收边解析」（第七阶段会讲），TTFB 与 FCP 同时受益。
- **状态注入**：`window.__INITIAL_STATE__` 的序列化位置与 XSS 边界（`</script>` 转义）——一段「既是数据又是代码」的特殊内容。

### 4. 压缩与回程（05 册）

- **压缩的经济学**：brotli 静态资源压缩率最高（但编码耗时大、适合预压）、gzip 动态响应的默认选择、zstd 两者平衡的新贵；二进制格式（图片/视频/wasm）再压一遍几乎白费 CPU。
- **分块**：Content-Length 已知 → 一次交付；未知/流式 → `Transfer-Encoding: chunked`，每块自描述长度。这是流式 SSR 的传输基础。
- **连接复用**：keep-alive 连接池——下一阶段（浏览器侧）与这一段（服务端 keepalive timeout）是同一根连接的两端，超时参数对不上会出现诡异的 ERR_CONNECTION_RESET。

## 实践任务

1. `curl -sD - -o /dev/null` 目标站点，读完整响应头：找出 CDN 供应商（Via/X-Cache/CF-Cache-Status）、缓存状态、压缩方式、有没有 Early Hints。
2. 同一 URL 查询两次，对比 `X-Cache: MISS/HIT`，估算回源与边缘命中的 TTFB 差。
3. 用 `curl --compressed -w '%{size_download} %{time_starttransfer} %{time_total}'` 对比 gzip 开关下的体积与 TTFB。
4. 找一个 SSR 站点，观察 Network 面板里 HTML 请求的 Content Download 是不是分成多段（流式分块的证据）。
5. 人为构造一条重定向链（301→302→200），量出每跳的额外 RTT。

## 自测题

1. CDN 边缘节点是怎么被选中的？这和第三阶段的哪个环节是同一件事？
2. `Vary: Accept-Encoding` 没配置时可能出什么缓存事故？（提示：代理把 gzip 版本发给了不支持的客户端）
3. TTFB 800ms，已知边缘排队 20ms、回源 RTT 100ms，剩下 600ms 多半花在哪？给出两个可能的构成与验证方法。
4. 流式 SSR 首块字节到了浏览器，但页面还是白的——可能卡在主时间线的哪一步？（预告：第七阶段的解析与第六阶段的调度）
5. 为什么对 already-compressed 的图片再开 gzip 纯属浪费？从 CPU 与体积两个角度说明。
6. Content-Length 和 chunked 能同时存在吗？为什么？HTTP/2 下「分块」这个概念还存在吗？
7. 301 和 308 的区别是什么？307 存在的意义是什么（302 有什么历史包袱）？
8. 重定向链 5 跳在弱网下的时间代价怎么估算？每跳会复用连接还是重新建连？（把第三阶段的知识串起来）
9. keep-alive 空闲连接被服务端 60 秒掐断，浏览器第 61 秒用它发请求会看到什么错误？为什么 Network 面板显示的是「失败」而重试后成功？
10. 网关返回 503 + `Retry-After: 30`，浏览器会自动等 30 秒重试吗？前端要不要自己写重试逻辑？
