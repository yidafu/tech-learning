# DevTools 深潜：Performance 全轨道解剖

> [← 第十阶段导览](01-导览.md) · 全链路收束。前九个阶段的知识分散在 17 步时间线上，本册把它们装进同一个工具：Performance 面板的每条轨道，都是某几个阶段的「可视化出口」——Network 轨道收拢第二至五阶段的连接与协议知识，Main 轨道收拢第七阶段的解析编译执行，Compositor/Raster/GPU 轨道收拢第八阶段的渲染管线，Timings 与交互轨道收拢第九阶段的指标。学完本册，一段 trace 不再是一团彩色方块，而是整条链路账本的展开图。

**产出物**：`labs/perf-轨道速查表.md`（§3 的轨道分工表亲手填一遍）+ 目标站点的一段完整 trace 文件（后续 05 册毕业项目的原始凭证）。

## 1. 收束地图：每条轨道背后是哪些阶段

先立总纲。一条 trace 从上到下摆着七八条轨道，每条轨道回答一个不同的问题——**问错了轨道，答案必然是错的**：

| 轨道 | 回答的问题 | 收拢的前九阶段知识 | 对应时间线段 |
|---|---|---|---|
| Timings | 首屏锚点在哪（FP/FCP/LCP/DCL） | 第九阶段指标原理 | ⑯ |
| Frames | 哪一帧掉了、这帧的 16.6ms 花在哪 | 第八阶段 06/07 册（合成与帧预算） | ⑮⑰ |
| Interactions / Experience | 交互慢在哪一段、位移发生在哪 | 第九阶段 03/05 册 | ⑰ |
| Main（主线程） | 主线程在烧什么：解析/样式/脚本/布局 | 第七阶段 03~07 册、第八阶段 03 册 | ⑪~⑮ |
| Network | 谁来得晚、谁阻塞了谁、优先级排队 | 第二~五阶段（连接、协议、服务端） | ③~⑧ |
| Compositor / Raster | 合成线程与光栅线程接住了什么 | 第八阶段 05/06 册（栅格化与合成） | ⑮ |
| GPU | 位图上传与合成是否成为瓶颈 | 第八阶段 06 册（GPU 进程协作） | ⑮ |

与 [第一阶段 04-度量基础](../01-第一阶段/04-度量基础-Network与Performance面板入门.md) 的关系：那一册教你「面板怎么开、怎么录一次」；本册教你「录到的每一块怎么读、读出什么结论」。前者是仪表盘，本册是读仪表盘。

## 2. 录制纪律：先固定变量，再谈结论

trace 是实验数据，实验数据的第一美德是**可控可复现**。[第一阶段 02 册](../01-第一阶段/02-从URL到首屏全景时间线与耗时账本.md)立的三纪律（固定环境、记原始凭证、写差异原因）在这里全部落地：

### 2.1 录制设置四件套

| 设置 | 怎么做 | 为什么 |
|---|---|---|
| 隐身窗 | 新开隐身窗口录制 | 排除扩展注入的脚本与请求——它们会污染 Main 与 Network 轨道 |
| Disable cache | Network 面板勾选 Disable cache（录制期间保持打开） | 量「冷启动」口径；不勾则每次录到的缓存状态不同 |
| CPU/网络节流 | Performance 设置里固定 CPU 4x + Fast 4G（内置档位约下行 1.6Mbps、RTT 150ms） | 对齐第一阶段账本的弱网口径；开发机 RTT<1ms 会把网络问题全部藏起来 |
| 保存 trace | 录完 Save profile 存 `labs/`，文件名带日期与环境 | 复测对比的原始凭证；trace 文件可以重新导入分析 |

### 2.2 三种录制方式与适用场景

| 方式 | 操作 | 用途 |
|---|---|---|
| 重新加载并录制 | 点录制图标 → 立即刷新页面 → 加载完停止 | 首屏加载全景（毕业项目基线用这个） |
| Start profiling and reload | 面板内直接选该入口 | 精确从导航起点开始，不漏 ①② |
| 空录 + 手动操作 | 开始录制后自己点击/滚动 | 交互段问题（INP、掉帧、布局抖动） |

一条铁律：**每次录制只改一个变量**（换页面不改节流、改节流不换缓存状态），否则前后两段 trace 无法归因——与第三阶段抓包实验的纪律同源。

## 3. 一条 trace 的地图：从上到下先扫一遍

拿到 trace 别急着放大。先通读一遍全景，回答三个宏观问题：

1. **总时长多少？** Timings 轨道的 LCP 竖线在哪、离右边界多远；
2. **时间花在哪类活动？** Main 轨道按颜色粗分（黄=脚本、紫=渲染、绿=绘制，详见 §6）；
3. **网络和计算谁在拖尾？** Network 轨道最后一条请求的结束时间 vs Main 轨道最后一块的结束时间。

然后按下表逐轨道细读。这个顺序本身就是排查树：**先锚点（Timings）→ 再资源（Network）→ 再计算（Main）→ 再帧（Frames/Compositor）**。

| 步 | 看哪 | 回答什么 | 看不到东西说明什么 |
|---|---|---|---|
| 1 | Timings | DCL/FCP/LCP 三个锚点的相对位置 | LCP 比 FCP 晚很多 → 大候选晚到（图/字体） |
| 2 | Network | 请求瀑布、排队段、谁最后完成 | 请求早就结束但页面没画 → 问题在计算侧 |
| 3 | Main | 主线程被什么占满、长任务在哪 | Main 空闲但页面卡 → 看合成线程/GPU |
| 4 | Frames | 掉哪几帧、每帧时长 | —— |
| 5 | Compositor/Raster/GPU | 主线程之外谁在忙 | 都空闲但掉帧 → 查显存/层（Layers 面板） |

## 4. Timings 轨道：首屏锚点与指标标记

Timings（部分版本叫 Overview/Timings）用竖线标出四个关键锚点：

| 标记 | 语义 | 晚了的典型原因 | 精修分册 |
|---|---|---|---|
| DCL（DOMContentLoaded） | DOM 解析完 + defer 脚本执行完 | 同步脚本阻塞解析（⑪）、HTML 太大 | 第七阶段 03 册（HTML 解析器） |
| FP/FCP | 首帧/首次内容绘制 | 渲染阻塞 CSS（⑫）、关键路径长 | 第九阶段 02 册（关键渲染路径） |
| LCP | 最大内容元素上屏 | LCP 候选晚到、被更大的候选刷新 | 第九阶段 03 册（指标深潜） |
| FCP→LCP 间隙 | 主体内容比首帧晚多少 | 字体 FOIT、图片解码、懒加载误伤 LCP | 第九阶段 04 册（优化手法） |

三个读法要点：

1. **LCP 竖线可能移动**：候选元素逐帧更新（更大的新候选出现就替换），trace 里有时能看到两次 LCP 标记——第二次才是最终值，第一次是「被刷掉的候选」；
2. **DCL ≠ 首屏**：DCL 只代表 DOM 与 defer 脚本就绪，首屏还要等 ⑭⑮ 跑完；DCL 早而 FCP 晚 → 查 CSS 与首帧渲染；
3. **与 Network 面板对账**：HTML 主文档 Timing 标签里的各段（③~⑧）应能与 trace 的 Network 轨道、Main 轨道的 Parse HTML 对上——对不上的差异就是信息（第三阶段 06 册 §8.7 的对账纪律在这里同样适用）。

## 5. Network 轨道：请求瀑布与优先级

### 5.1 读什么

| 观察 | 结论方向 |
|---|---|
| 请求条之间的空隙（左边不出头） | 排队等待——优先级低或被连接数限制卡住 |
| 请求条前段的浅色/深色分段 | 等待响应 vs 下载；精确分段回 Network 面板看 Timing 标签 |
| 请求条的着色深浅 | 按优先级着色（深=高优先级，浅=低）；hover 看具体 priority |
| 某资源的开始时间晚于 HTML 解析开始很久 | 没被 preload scanner 提前发现（动态注入/JS 拼的 URL） |
| 同域请求大量串行 | h1 六连接限制或优先级排队 |
| 关键 CSS/JS 的结束时间 | 渲染阻塞资源到齐的时间点 ≈ 首帧的下界 |

### 5.2 与 Network 面板的分工

| | Performance 的 Network 轨道 | Network 面板 |
|---|---|---|
| 时间轴 | 与渲染/主线程**同轴对齐**——能看出「请求到达时主线程在干什么」 | 独立时间轴 |
| Timing 明细 | 无逐段展开 | 每请求 Timing 标签（③~⑧ 逐段） |
| Initiator | 无 | Initiator 列 + 链条（§11 的主角） |
| 用途 | 归因「网络与计算的关系」 | 归因「单个请求内部」 |

两处结合才是完整读法：**Network 轨道回答「资源晚到时页面在干嘛」，Network 面板回答「这个资源为什么晚到」**。

## 6. Main 轨道与火焰图：颜色语义与三读法

主线程轨道是 trace 的心脏。它是一张倒置的调用栈图：**x 轴是时间，y 轴是栈深度，每个色块的宽度是耗时，上层块被下层块调用**。

### 6.1 颜色语义表

| 颜色 | 活动 | 对应的常见块 | 收拢的阶段知识 |
|---|---|---|---|
| 黄 | 脚本 | Script（编译+执行）、各种函数块 | 第七阶段 06 册（V8 执行模型） |
| 紫 | 渲染 | Recalculate Style、Layout、Update Layer Tree | 第七阶段 05 册、第八阶段 03 册 |
| 绿 | 绘制 | PrePaint、Paint、Composite Layers | 第八阶段 05 册 |
| 灰/棕 | 其他 | Parse HTML、GC Event、Compile | 第七阶段 03 册、V8 |
| 白（空） | 空闲 | —— | 有预算没花完，还是该忙没忙，要结合帧判断 |

（具体色调随版本微调，以 DevTools 图例为准；重要的是**四类活动的相对位置**。）

### 6.2 三条读法纪律

1. **宽度 = 耗时，与缩放无关**：同一函数在两条不同长度的 trace 里宽度占比不同，绝对毫秒数才是可比的；
2. **堆叠 = 调用关系，自上而下是「被谁调用」**：想知道一个块「为什么被执行」，沿它**下方**的块读；想知道「它做了什么」，沿**上方**读；
3. **先找宽而低的块（自耗时大），再顺藤摸瓜**：瓶颈通常不是最顶层的入口函数，而是它子树里某个自耗时长、且出现次数多的块。

### 6.3 一个文字化的火焰图

```text
时间 →
Main 轨道（自上而下 = 调用层级，宽度 = 耗时）
┌────────────────────────────────────────────────┐
│ onload handler                          （入口）│
│   ├─ initPage                    （子树总耗时大）│
│   │    ├─ JSON.parse  │││││││  （自耗时累积大）│
│   │    ├─ renderList        （子树总耗时大）    │
│   │    │    ├─ buildRow ││ ││ ││ （被反复调用）│
│   │    │    └─ getStyle │  │  │  （每次读几何）│
│   │    └─ bindEvents │││                        │
└────────────────────────────────────────────────┘
```

读法示范：`renderList` 宽 → 点它看 Bottom-Up，发现 `getStyle` 聚合耗时最大 → getStyle 是几何读取，每次都触发强制同步布局（第八阶段 03 册的 layout thrashing 现场）→ 修复方向是批量读写。这一套「宽块 → Bottom-Up → 归因」的动线会在[本阶段 04 册](04-案例复盘集-渲染类.md)的案例一里完整走一遍。

## 7. Call Tree 与 Bottom-Up：两个视角一张账

点 Main 轨道里任意块（或框选一段区间），底部面板给出三个标签：Summary、Bottom-Up、Call Tree。后两个是归因的左膀右臂：

### 7.1 定义与操作

| | Call Tree（自顶向下） | Bottom-Up（自底向上） |
|---|---|---|
| 视角 | 从根出发的调用树，按 Total Time 排序 | 把每个函数的全部**自耗时**聚合后排序，展开看「谁调用了我」 |
| 排序字段 | Total Time（该函数 + 其子树） | Self Time（仅该函数自身，不含子树） |
| 回答的问题 | 「最贵的**路径**是哪条」 | 「最贵的**函数**是哪个、它被谁反复调用」 |
| 操作 | 点火焰图块 → Call Tree 标签 | 同一入口 → Bottom-Up 标签 |
| 降噪 | Group by Activity / Category 合并同类 | 同左 |

两个时间的定义必须分清：**Self Time = 函数体自身耗时（不含子调用）；Total Time = 自身 + 全部子树**。递归/高频调用的函数 Self Time 被聚合放大；入口函数 Total Time 天然巨大但没有信息量。

### 7.2 适用场景

| 场景 | 用哪个 | 为什么 |
|---|---|---|
| 「这段脚本为什么跑了 800ms」——想知道执行路径 | Call Tree | 沿最贵路径逐层下钻，路径本身就是因果链 |
| 「页面整体卡，不知道哪个函数是元凶」 | Bottom-Up | 不需要知道路径，只需要知道谁消耗最多 |
| 怀疑某工具函数被滥用（如频繁几何读取、频繁 JSON 解析） | Bottom-Up | 聚合视角立刻暴露「单次便宜 × 万次调用」型问题 |
| 向他人解释问题 | Call Tree | 树形路径可读性好，能讲成故事 |

### 7.3 两者结论相反的例子

构造一个场景（数字示意）：某列表页脚本总耗时 400ms。

- **Call Tree 说**：最贵路径是 `render → renderList → buildRow`（Total 360ms）——顺着这条路径看，每一步的 Self Time 都不大；
- **Bottom-Up 说**：最贵函数是 `JSON.parse`（聚合 Self 180ms，被 600 次调用）和 `getStyle`（聚合 Self 140ms，每次触发一次布局）。

结论相反的含义：Call Tree 告诉你「从哪条**路径**砍」（把 renderList 的渲染重构掉），Bottom-Up 告诉你「哪个**函数**被滥用」（缓存解析结果、批量读几何）。前者指向架构改法，后者指向调用纪律改法——**两者都看，修复方案才完整**。这正是[本阶段 04 册](04-案例复盘集-渲染类.md)案例一与案例三分别使用两个视角的原因。

## 8. 渲染各阶段在 trace 中的样子

第八阶段讲的管线五个阶段，在 Main 与相关线程轨道上有确切的事件名。**事件名 → 管线阶段**的对照是读渲染类 trace 的词汇表：

| trace 事件名 | 管线阶段 | 收拢的分册 | 出现得多的含义 |
|---|---|---|---|
| Recalculate Style | 样式计算（⑭） | 第七阶段 05 册（样式计算） | 选择器病态、DOM 过大、失效范围失控 |
| Layout | 布局 | [第八阶段 03 册](../08-第八阶段/03-布局-盒模型-格式化上下文与布局抖动.md) | 强制同步布局（锯齿状，见下）、视口尺寸变化 |
| Update Layer Tree | 分层更新 | [第八阶段 04 册](../08-第八阶段/04-分层-PaintLayer-合成层与层爆炸.md) | 层增删频繁、will-change 滥用 |
| PrePaint / Paint | 绘制指令记录 | [第八阶段 05 册](../08-第八阶段/05-绘制与栅格化-display list-瓦片与Skia.md) | 重绘范围大（改了共享祖先的属性） |
| Rasterize Paint（Raster 线程轨道） | 栅格化 | 第八阶段 05 册 | 大面积重绘、大图解码后重栅格 |
| Composite Layers（主线程）→ commit → 合成线程 draw | 合成 | [第八阶段 06 册](../08-第八阶段/06-合成-合成线程-GPU与vsync.md) | 层数多、合成提交重 |
| ImageDecode / Image Resize | 图片解码缩放 | 第八阶段 05 册 | LCP 大图没给尺寸、没压缩 |

### 8.1 失效传播的 trace 实证

[第八阶段 07 册](../08-第八阶段/07-一帧的完整生命周期-失效传播与帧预算.md)讲的失效粒度，在 trace 里的表现：

| 改动 | trace 里应出现 | 代价级别 |
|---|---|---|
| background-color | Recalculate Style → Paint（无 Layout） | 低 |
| width | Recalculate Style → Layout → Paint → 栅格 | 高 |
| transform | （无主线程渲染块）→ 合成线程 draw | 最低 |

用这个表反向诊断：**看到 Layout 出现在不该出现的交互里**（比如滚动、hover），就是布局抖动或宽失效的信号——[本阶段 04 册](04-案例复盘集-渲染类.md)案例一的判据。

### 8.2 强制同步布局的「锯齿」形态

布局抖动在 Main 轨道有唯一的视觉签名：黄色 Script 块与紫色 Layout 块高频交替：

```text
正常（一次批处理）：
  [Script………………] [Layout] [Script………………] [Layout]
抖动（读写交错，n 个列表项）：
  [S][L][S][L][S][L][S][L][S][L]   ← 每读一次几何就插一次 Layout
```

看到锯齿立刻点紫色小块 → Bottom-Up → 看「谁读了几何属性」——offsetTop/offsetHeight/getBoundingClientRect 是高频嫌疑犯。

## 9. Compositor、Raster 与 GPU 轨道：主线程之外的世界

第八阶段 06 册讲过：渲染进程里主线程不是唯一的干活者。这三条轨道是「主线程视角之外」的补充证据：

| 轨道 | 谁的活 | 忙 = 什么问题 | 与主线程的关系 |
|---|---|---|---|
| Compositor | 合成线程：合成帧组装、滚动、transform 动画 | 层太多、合成提交太重、滚动层处理 | 主线程卡死时它仍能滚动（合成器滚动） |
| Raster | 光栅线程：瓦片位图生成 | 大面积重绘后栅格排队、大图解码 | 主线程 Paint 出指令，它执行成位图 |
| GPU | GPU 进程：位图上传、合成执行 | 显存带宽、巨大层纹理 | 前两步的下游；它慢会拖垮所有帧 |

**掉帧排查的第二分叉**：Frames 轨道确认掉帧后，先看主线程那 16.6ms 里谁在忙——

- 主线程满（Script/Layout）→ 主线程问题，走 §6~§8 的动线；
- 主线程闲、Compositor/Raster/GPU 忙 → 合成侧问题：查层数量与显存（DevTools → More tools → Layers），[本阶段 04 册](04-案例复盘集-渲染类.md)案例二走的就是这条线。

## 10. Frames 轨道与帧预算

Frames 轨道每帧一条。读法：

1. **hover 帧条看时长**：60Hz 下 16.6ms 是预算线；120Hz 设备按 8.3ms 想（帧预算机制详见第八阶段 06 册）；
2. **红角标/红色帧 = 长帧**：这帧超预算了，用户感知为掉帧或卡顿；
3. **点帧条跳转**：DevTools 会选中该帧区间，Main/Compositor 轨道同步缩放——直接看这一帧里谁在干活；
4. **连续长帧 = 卡顿**，孤立长帧 = 单次尖峰。前者改调度（拆任务），后者改算法（单次耗时）。

第九阶段 05 册讲的「交互后重渲染」也在这里验证：点击 → Main 的 Script（处理）→ 渲染块（Style/Layout/Paint）→ 合成线程 draw → 下一个 Frames 条。整条链在 trace 上同轴可见，INP 的「呈现延迟」段就是从点击到下一帧上屏的距离。

## 11. Interactions 与 Experience 轨道：交互与位移的证据

### 11.1 Interactions 轨道（INP 主战场）

每次用户交互一条，条长 = 该交互的总耗时。新版 DevTools 直接在条内用三色分段呈现 INP 的三段构成（第九阶段 03 册）：

| 分段 | 语义 | 拉长的原因 |
|---|---|---|
| 输入延迟 | 事件派发前主线程被占用 | 长任务正好卡在点击前（→ [本阶段 04 册](04-案例复盘集-渲染类.md)案例三） |
| 处理时间 | 回调执行 | 回调里干重活、同步布局 |
| 呈现延迟 | 回调结束到下一帧上屏 | 回调触发了大范围 Layout/Paint（→ 案例一、四） |

配套用底部的 **Event Log** 标签：按时间列出所有事件（含派发时刻、处理时长、调用栈），是「这个交互里具体跑了什么」的明细账。

### 11.2 Experience 轨道（CLS 主战场）

布局位移以矩形区域标注在 Experience 轨道上（第九阶段 03 册的 Layout Shift Regions 可视化）。配合 Performance 设置里勾选 Layout Shift Regions，页面上还会高亮位移元素——「谁动了」与「何时动的」在时间轴上对齐，归因到具体资源（晚到的 banner、无尺寸的图）。

## 12. Event Initiator：请求归因的第一工具

「这个请求是谁引来的」——Network 面板的 Initiator 列与请求详情的 Initiator 标签给出链条。这是第三方脚本归因（[本阶段 03 册](03-案例复盘集-加载类.md)案例三）的核心武器。

### 12.1 Initiator 的取值

| 取值 | 含义 | 典型例子 |
|---|---|---|
| parser | HTML 解析器解析到该标签 | `<link>`/`<script src>` |
| script | 某脚本动态发起 | fetch/XHR/动态注入的 img |
| preload | preload scanner 提前发现 | head 里靠前的资源 |
| redirect | 由重定向引来 | 30x 跳转的后续请求 |
| other | 其他（如导航本身） | 主文档请求 |

### 12.2 归因动线

```text
Network 面板发现可疑请求（第三方域）
  → 看 Initiator 列的值
  → 点开请求详情的 Initiator 标签：完整链（A 引来 B、B 引来 C）
  → 链的根部 = 最初引入的脚本（通常是某个统计/营销 SDK）
  → 回 Performance 的 Main 轨道验证：该脚本执行段里是否有对应网络/长任务
```

第三阶段 06 册的抓包实验教你「包从哪来」，本节教你「请求从哪来」——两层归因互补：包视角看连接与握手，请求视角看代码与依赖。

## 13. Lighthouse 审计对应：审计项就是链路检查点

Lighthouse 的每个审计项，本质是对链路某一段的自动化检查。把审计项翻译回时间线段落，审计报告就从「分数」变成「账本检查单」：

| 审计项 | 检查的时间线段 | 对应面板/轨道 | 修复方向（精修分册） |
|---|---|---|---|
| Eliminate render-blocking resources | ⑫ CSS 阻塞 | Network + Main | 关键 CSS 内联、media 拆分（第九阶段 02 册） |
| Preload key requests / Preconnect | ③④⑤ 与 ⑪ 的提前量 | Network 瀑布 | 资源 hint（第六阶段 05 册） |
| Ensure text remains visible during webfont load | ⑫ 字体 FOIT | Network + Timings | font-display（第九阶段 02 册） |
| Reduce unused JavaScript / CSS | ⑬ 编译执行 | Coverage 面板 | 代码分割（第九阶段 04 册） |
| Defer offscreen images / Properly size images | ⑧ 回程 + ⑮ 解码 | Network + Main | 图片手法（第九阶段 04 册） |
| Serve images in next-gen formats / Efficiently encode | ⑧ 体积 | Network | 格式选择（第九阶段 04 册） |
| Avoid enormous network payloads | ⑧ 总体积 | Network | 预算与拆分 |
| Minimize main-thread work | ⑪~⑮ 汇总 | Main 轨道 | 分类别治理 |
| Avoid long main-thread tasks | ⑰ 长任务 | Main + Interactions | 拆分（本阶段 04 册案例三） |
| Total Blocking Time | ⑰ FCP 后长任务超额部分 | Main | 同上 |
| Largest Contentful Paint element | ⑯ LCP 归因 | Timings + Elements | LCP 专项（第九阶段 04 册） |
| Image elements have explicit width/height | CLS 预防 | Experience | 尺寸占位（第九阶段 03 册） |
| Avoid multiple page redirects | ②⑩ 重定向链 | Network 瀑布 | 重定向归一（本阶段 03 册案例四） |
| Enable text compression | ⑧ 压缩 | Network Size 列 | 压缩（第五阶段 05 册） |

两条边界要记牢：

1. **Lighthouse 是 lab 数据**：单次、模拟环境、无真实交互——它与真实用户数据（field/CrUX）的差距分析是[本阶段 05 册](05-毕业项目-全链路测量与优化报告.md)的必修题；大规模采集归 `observability/` 站；
2. **审计项是检查点不是处方**：它告诉你「哪段不达标」，怎么修要回到链路归因——直接照审计建议改而不知道为什么，常常按下葫芦浮起瓢。

## 14. 实验：六条动线各走一遍

参照第三阶段 06 册的实验纪律（一个变量、记录表、差异原因），对同一个目标站点完成：

1. **基线录制**：隐身窗 + 4x CPU + Fast 4G + Disable cache，重新加载录制，保存 trace 到 `labs/`；填一张 §3 的五步通读表；
2. **对账实验**：把 HTML 主文档 Network Timing 各段与 trace 的 Network/Main 轨道互相指认（③~⑧ 与 Parse HTML 的重叠关系）；
3. **火焰图下钻**：找 Main 轨道最宽的黄色块，Call Tree 与 Bottom-Up 各下一次，写下两者各自的结论与是否一致；
4. **失效传播实验**：给目标页某元素分别改 background-color 与 width（临时改），录两次 trace 对比渲染块的出现差异（§8.1 表的实证）；
5. **掉帧定位**：滚动目标页录制，Frames 轨道找长帧，判断是主线程忙还是合成侧忙（§9 的第二分叉）；
6. **Initiator 追踪**：找出目标页的某个第三方请求，画「谁引来谁」的链条图（§12.2 动线），标注链根。

| 实验 | 用的轨道/面板 | 关键观察 | 与预期差 | 差异原因 |
|---|---|---|---|---|
| 1 基线 | 全部 | LCP 竖线位置 | | |
| 2 对账 | Network 双处 | Timing 段 ↔ 轨道块 | | |
| 3 下钻 | Main + Bottom-Up | 最贵路径 vs 最贵函数 | | |
| 4 失效 | Main 渲染块 | Layout 出现与否 | | |

## 15. 常见误区

1. **「火焰图宽度大就是该优化的函数」**：入口函数天然宽；先看 Self Time/Total Time 的区分，再用 Bottom-Up 找聚合大头——把入口函数当瓶颈是火焰图第一误读。
2. **「trace 是绝对真相」**：录制本身有开销（instrumentation overhead），小函数会被放大；同一函数在带 Profiling 与不带 Profiling 的运行里耗时不同——结论看量级与相对关系，别抠单次毫秒。
3. **「本地录一次就能下结论」**：不节流的开发机 trace 会把网络段全部抹平；样本量只有一次时，抖动与缓存状态都可能让结论反转——固定节流 + 多次录制是底线。
4. **「Main 空闲 = 页面流畅」**：合成线程、Raster、GPU 任一忙不过来都会掉帧；主线程视角的盲区在 §9 的三条轨道上。
5. **「Lighthouse 分数 = 性能」**：分数是加权合成的 lab 单样本；TBT 权重高不代表你的页面问题在脚本上——审计要还原成链路检查点（§13）逐条归因。
6. **「Event Log 和 Interactions 轨道重复」**：轨道给「哪个交互总耗时超阈值」，Event Log 给「这交互里每个事件的明细时刻」——前者筛对象、后者做归因，是上下游不是二选一。
7. **「颜色是精确分类」**：色调随版本变化，且一个块内可能混合多种活动；以块名（Recalculate Style 等）为准，颜色只做快速粗筛。

## 16. 自测题

1. 默写 §1 的轨道分工表：Timings/Network/Main/Compositor/Frames 各回答什么问题？「请求晚到但页面早画」该先看哪条轨道？
2. 火焰图里「宽而高的块」与「宽而低的块」分别提示什么问题？为什么瓶颈常在后者？
3. Self Time 与 Total Time 的定义？一个入口函数 Total 800ms、Self 2ms，能说明什么、不能说明什么？
4. §7.3 的例子里，Call Tree 与 Bottom-Up 结论相反——各自的修复方向是什么？如果只允许做一个，你先做哪个？为什么？
5. 在 trace 里指出强制同步布局的视觉签名，并说出下一步操作（点什么块、看什么标签）。
6. 改 width 与改 transform，各自在 trace 里出现哪些渲染块？用第八阶段 07 册的失效传播解释差异。
7. Frames 轨道发现长帧后，怎么判断是主线程问题还是合成侧问题？两边各自的下一步是什么？
8. INP 三段在 Interactions 轨道里怎么对应到色段？「输入延迟长」优先查什么、「呈现延迟长」优先查什么？
9. Initiator 取值里 parser/script/preload 各是什么含义？「链根脚本」为什么常在第三方归因里成为收网点？
10. 把 Lighthouse 的「Eliminate render-blocking resources」还原成时间线段落归因：它检查 ⑪~⑮ 里的哪几段？为什么有时消除阻塞资源后 FCP 几乎不变？
11. 为什么说「Lighthouse 分数高不代表真实用户体验好」？给出至少两个结构性原因（lab vs field、单样本、无真实交互……）。
12. 录制四件套里，「Disable cache」什么时候该关掉（即允许缓存）？给出一个必须允许缓存的排查场景。

| # | 检查 | 工具/入口 | 异常指向 |
|---|---|---|---|
| 1 | 录制四件套齐了吗 | 隐身窗/Disable cache/节流/存 trace | 缺一项，前后对比就不可信 |
| 2 | 能五步通读一条 trace 吗 | §3 的顺序 | 卡在哪步 = 那条轨道没学会 |
