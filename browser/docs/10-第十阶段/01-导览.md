## 阶段目标

学完本阶段，你应该能不查资料做到这些事：

1. 面对一段 trace，说清每条轨道（Timings / Network / Frames / Main / Compositor / Raster / GPU）各自回答什么问题。
2. 用 call tree 定位「最贵的自顶向下路径」、用 bottom-up 定位「被谁反复调用」，说出两者的适用场景。
3. 给出「白屏超过 2 秒」的完整排查树：先看 Network（谁阻塞）→ 再看 Main（解析/执行卡在哪）→ 再看缓存判定。
4. 复盘 ETag 失效风暴：重新部署后 mtime 全变 → ETag 全变 → 全量 200 → 缓存失效雪崩，以及为什么内容哈希文件名 + immutable 能根治。
5. 独立完成毕业项目：从 17 步时间线账本出发，产出一份别人能照着做的优化报告。

## 知识点地图

### 1. DevTools 深潜（02 册）

- **轨道分工**：Network（谁来得晚）、Frames（哪帧掉了）、Main（主线程在烧什么）、Compositor（合成线程接住了什么）、GPU（位图上传与合成）。
- **火焰图读法**：宽度 = 耗时、堆叠 = 调用关系；自上而下是「谁调用谁」，找瓶颈先找「宽且低的格子」（自己耗时多）再找「宽且高的格子」（调用子树总耗时多）。
- **Event Initiator**：Network 面板里每个请求的发起者链——「这个请求是谁引来的」是归因第三方脚本的第一工具。

### 2. 案例复盘方法论（03、04 册）

- **统一模板**：现象（可量化）→ 假设（按时间线排序）→ 测量（哪个面板哪条轨道）→ 根因（哪一段账本出了问题）→ 修复（改了什么）→ 复测（指标前后对照）。
- **加载类四案**：阻塞资源树白屏、ETag 风暴、第三方脚本（它精确演示 Event Initiator 的用法）、重定向链（第三、五阶段知识串联）。
- **渲染类四案**：布局抖动（第八阶段）、层爆炸（第八阶段）、长任务（第七阶段事件循环）、INP 劣化（第九阶段指标三段拆解）。

### 3. 毕业项目（05 册）

- **交付物**：一份报告，包含 17 步时间线账本（优化前）、三个优化动作（各自归因到时间线段落）、指标前后对照（TTFB/FCP/LCP/CLS/INP）、复测账本与结论。
- **验收标准**：任何一段耗时都能说出「为什么」；任何优化都能说出「精修哪段、预期收益多少、实际收益多少、误差为什么」。

## 实践任务

1. 用 Event Initiator 追踪目标站点某个第三方脚本的请求链，画出「谁引来谁」的关系图。
2. 按第 03 册的模板，对目标站点做一次「白屏假设树」演练（哪怕它其实不白屏，练习走查流程）。
3. 毕业项目启动：确定对象站点、采集优化前的完整基线（账本 + 五指标）。
4. 完成三轮优化并复测，写出报告；按验收表自评。

## 自测题

1. call tree 和 bottom-up 各在什么场景下更有效？给一个「两者结论相反」的例子。
2. trace 里看到一帧 8.3ms 预算被 Main 线程的 Script 占了 12ms——下一帧会怎样？连续出现时的用户感知是什么？
3. 「白屏 2 秒」排查树的第一站为什么是 Network 面板而不是 Performance 面板？（提示：先区分「没到」还是「到了没画」）
4. ETag 失效风暴中，为什么 304 机制没有发挥作用？Last-Modified 验证器在这次事故里能救场吗？
5. 第三方脚本的「代价」除了它自己的下载执行，还可能包含哪些（提示：连接抢占、主线程长任务、LCP 候选变化）？
6. 毕业报告里的「误差为什么」一栏在检验什么能力？（提示：lab 数据与 field 数据、样本量、缓存状态）
7. 优化后本地测得 LCP 从 4.2s 降到 2.1s，但真实用户 CrUX 数据几乎没变——给出三种可能的解释。
8. 完成全站学习后回看第一阶段的 17 步账本：现在你能给每一段补上「典型慢的三个原因 + 对应面板」了吗？试写一遍。
