# 水合与下一代渲染架构

> [← 第九阶段导览](01-导览.md) · 时间线 ⑯⑰。SSR 解决了首屏 HTML 的传输（第五阶段 04 册），但交互前还有一笔账：框架 JS 要把整棵组件树**重跑一遍来「认领」服务端画好的 DOM**——这就是水合（hydration），也是「首屏快、交互卡」裂缝的根源。这一册给出水合的成本模型、从全量到选择性再到 islands 的谱系、RSC 与流式传输的平台机制（框架层实现归 `react/` 站），最后收在两个管线级新原语：View Transitions 与 content-visibility。

## 1. 水合的成本模型：为什么它贵

先把 SSR 时代页面加载的完整账摆出来：

```text
⑦⑧ 服务端渲染 HTML → 流回
⑯ 首帧上屏（HTML 直接渲染，快）
⑪ 下载框架 JS（bundle 常比 HTML 大一个量级）
⑬ 解析 + 执行框架 JS（⑬ 的账，量级常为数百 ms 到数秒）
⑭ 水合：重新执行组件树 → 构建内存中的虚拟树
⑮ 与服务端 DOM 逐节点比对「认领」→ 挂事件监听器、建状态
→ 此刻页面才「可交互」（视觉上早就「加载完」了）
```

水合贵在它**重复付费**：

| 已在服务端做过的事 | 水合时浏览器再做一遍 |
|---|---|
| 组件树渲染 | 组件函数重新执行（构建虚拟树） |
| 产出 HTML 结构 | 与现有 DOM 逐节点 reconcile |
| 事件绑定语义 | 真正挂上监听器 |
| 初始状态 | 状态重新初始化（通常从 HTML 里的序列化注入读回） |

这笔账的时间窗口正是 INP 的雷区：**水合没完成前点击页面，要么没反应，要么回调排队等水合**——上一册 §1 的输入延迟段被水合任务整体拉长。导览自测题第 7 题的粗账用这里的话说：页面 80% 区域无交互时，全量水合仍为那 20% 的交互区跑完了 100% 的组件树——浪费比例就是「无交互区域占比 × 水合成本」。

## 2. 谱系：从全量到「不水合」

四代方案各自砍掉成本模型的不同段：

```text
全量水合 ──→ 渐进水合 ──→ islands（部分水合）──→ 选择性水合 ──→ resumability
（最贵）      （按时间摊）     （按空间裁）          （按交互优先）     （不重跑，恢复现场）
```

### 2.1 全量水合（SSR + 单 bundle 的默认形态）

- 姿势：页面级 bundle，DOMContentLoaded 前后一次性水合整棵树。
- 省的：无——它是基线。
- 症状：小屏幕大页面（营销页 + 复杂导航）里，99% 静态内容陪跑水合。

### 2.2 渐进水合（progressive hydration）

- 姿势：按时间调度——不同组件分批水合（rAF/空闲期/定时器驱动）。
- 省的：把「一次大长任务」摊成多次小任务——主线程不再被一次性堵死（长任务纪律，上一册 §5）。
- 没省的：**总量没变**——还是要为整棵树跑 JS，只是摊薄了；静态部分依然陪跑。
- 分工提醒：调度实现是框架层机制（`react/` 站展开），本站只记平台语义「水合任务是普通 JS 任务，参与事件循环竞争」。

### 2.3 Islands（部分水合）：按空间裁

- 姿势（Astro/Marko 类）：页面默认是纯静态 HTML，只有被 `<Island>` 标记的交互岛各自独立水合（各自带自己的 JS）。
- 省的：静态区域的 JS 全免——「80% 无交互」的账直接砍掉 80%。
- 代价：岛间通信要过 DOM/事件（框架为此设计各自的机制，归框架站）；岛粒度太粗退化为全量、太细碎片化请求。
- 平台机制视角：每个岛是一个独立的「HTML + script」交付单元，水合时机由岛自己声明（idle/visible/交互时）——`requestIdleCallback`、`IntersectionObserver`、事件监听器是三档时机的平台原语。

三档时机到平台原语的映射（示意骨架）：

```js
// idle：主线程空了才水合（非关键岛）
requestIdleCallback(() => hydrateIsland(el));

// visible：滚到视口才水合（折叠线以下的岛）
const io = new IntersectionObserver((entries) => {
  if (entries.some(e => e.isIntersecting)) {
    hydrateIsland(el);
    io.disconnect();
  }
});
io.observe(el);

// interactive：用户碰到岛才水合（配合事件暂存回放，§2.4）
['pointerdown', 'focusin'].forEach(t =>
  el.addEventListener(t, () => hydrateIsland(el), { once: true })
);
```

### 2.4 选择性水合（React 18 语境）：按交互优先

- 姿势：流式 SSR + Suspense 边界 + **按用户交互优先水合**——用户点哪个岛，哪个岛优先水合；点得太早时，浏览器先以捕获阶段监听全局事件**把交互记账暂存**，等对应区域水合完再回放。
- 省的：不是总量，是**顺序**——用户正在等的区域插队，感知交互恢复时间（INP）缩短。
- 平台机制视角：捕获阶段全局监听 + 事件队列回放，是纯平台能力（事件模型，上一册 §4）；框架只是用它做优先级调度——实现归 `react/` 站。

### 2.5 Resumability：不水合，恢复现场

- 姿势（Qwik 类）：服务端把「组件树状态 + 监听器映射」序列化进 HTML，浏览器**不重新执行组件树**，交互发生时按需加载对应处理函数直接执行。
- 省的：整个「重执行」段——水合成本趋近于零，代价是序列化格式与生态约束。
- 平台视角：这是「状态注入」（第五阶段 04 册的 SSR 状态序列化）的极致化——把 JS 执行图的恢复也变成数据。

### 2.6 谱系总表（收束）

| 方案 | 砍哪段 | 保留什么成本 | 代表 |
|---|---|---|---|
| 全量 | 无（基线） | 全部 | 传统 SSR SPA |
| 渐进 | 总量不变，**时间分布**优化 | 静态区陪跑 | React 分批调度 |
| islands | **静态区全部 JS** | 岛内全量 | Astro/Marko |
| 选择性 | 水合**顺序**（交互优先） | 岛外仍有总量 | React 18 流式 SSR |
| resumability | **重执行段整体** | 序列化体积 | Qwik |

## 3. RSC 与流式：平台机制侧的账

React Server Components 把「组件在谁那边执行」变成了架构选择——**服务端组件的代码永不进入客户端 bundle**，只有客户端组件参与水合。本站只讲平台机制，组件模型与实现归 `react/` 站。

### 3.1 流式传输与渐进呈现

平台侧的关键机制是**流式响应 + 边界占位**：

```text
响应流：[头部 HTML 立即冲刷] → [Suspense 占位] → ……
        ↓ 时间推进
首帧：头部 + 各处骨架/占位（⑯ 提前）
后续：每块内容就绪后流式到达，运行时用脚本把占位替换成真内容
```

| 平台机制 | 作用 | 本站哪册讲过 |
|---|---|---|
| chunked 流式响应 | HTML 不必等全部生成 | 第五阶段 05 册 |
| 流式 SSR 冲刷时机 | TTFB 与首帧前移 | 第五阶段 04 册 |
| 占位替换脚本 | out-of-order 流式（后到的块插入前面已画的位置） | 本册 |
| 状态注入 script | 水合数据的载体 | 第五阶段 04 册 |

流式的指标红利与代价并存：FCP 显著提前（占位也是内容）；**LCP 可能被「更大内容后到」刷新**（上一册 §3 候选更新机制的直接后果）；占位与真内容尺寸不符时 CLS 爆发（上一册 §4.4 源头表）——流式不是免费午餐，占位尺寸纪律是准入条件。

### 3.2 平台侧对水合时代的支持清单

| 平台能力 | 支撑了什么 |
|---|---|
| `<script type="module">` + 模块图 | 岛级/边界级按需加载 |
| 事件捕获阶段全局监听 | 选择性水合的交互暂存 |
| `requestIdleCallback` / `scheduler.postTask` | 水合任务的优先级调度 |
| Stream API / ReadableStream | RSC 序列化数据的流式传输 |

## 4. View Transitions：跨视图状态过渡的平台原语

问题：SPA 里组件切换靠 CSS transition 拼动画（旧元素等新元素渲染好再淡出——状态衔接全靠手写）；MPA 之间更是白屏硬切。View Transitions API 把「新旧两个视觉状态之间」的过渡交给了浏览器。

### 4.1 机制

```js
document.startViewTransition(() => {
  // 回调里完成 DOM 的状态切换（同步改完）
  updateTheDOMSomehow();
});
```

浏览器做的事：**先给旧状态拍快照**（伪元素树 `::view-transition`，每个过渡元素一组快照），回调跑完给新状态拍快照，然后**用快照之间的 CSS 动画完成过渡**——动画期间页面被快照接管，旧 DOM 已切换，用户看到的是两张「照片」在动画。

```text
::view-transition                     ← 快照树根
  └─ ::view-transition-group(name)    ← 每个具名元素一组
       ├─ ::view-transition-old(name) ← 旧状态快照（静态图）
       └─ ::view-transition-new(name) ← 新状态快照（静态图/实时内容）
```

### 4.2 与 CSS transition 的本质区别（导览自测题 9）

| 维度 | CSS transition | View Transitions |
|---|---|---|
| 过渡对象 | 元素的**属性值**（同一元素连续变化） | **两个离散状态**的快照（DOM 可能整体换血） |
| 快照 | 无 | 旧/新状态各一帧图像 |
| 动画执行 | 常规 CSS 动画（可合成器接管） | 伪元素上的 CSS 动画——快照多为静态图，合成器友好 |
| DOM 切换时机 | 不切 | 动画开始前就切完，动画只是视觉戏法 |
| 跨文档 | 不适用 | `@view-transition` 声明可支持 MPA 导航（较新能力） |

工程价值：**「DOM 已经变了」与「用户看到的过渡」解耦**——状态切换的代码不用为动画让路（不用手写「先淡出再换内容再淡入」的状态机）。注意快照机制的边界：过渡期间旧内容是图（不可交互、文字不可选中）、超大页面快照内存成本、跨文档过渡的浏览器支持差异——装饰性过渡用 `view-transition-name` 精确圈定范围，别全页快照。

### 4.3 使用边界与退化行为

| 场景 | 行为 |
|---|---|
| 回调抛错 / DOM 更新失败 | 过渡中止，页面停留在新状态（回退为「硬切」）——功能不损坏，动画缺失 |
| 浏览器不支持 | `document.startViewTransition` 为 undefined——先能力检测再调用，不支持时直接执行回调 |
| 快照期间布局变化 | 快照是「照片」，不随内容变化——过渡里的动态内容建议标记 `view-transition-name` 之外或接受静态呈现 |
| 嵌套/并发调用 | 同一时刻只进行一个文档级过渡——并发触发会被排队或丢弃（实现细节，量级口径） |

```js
// 能力检测的标准姿势
if (document.startViewTransition) {
  document.startViewTransition(() => swapContent());
} else {
  swapContent();  // 老浏览器直接切换，无动画
}
```

## 5. content-visibility 与 contain：管线级裁剪

上一册 §6 说「改 body class = 全页失效」——长页面里这等于全页重算。渲染管线的裁剪原语让「视口外」免于参与：

### 5.1 content-visibility: auto

```css
.feed-item { content-visibility: auto; contain-intrinsic-size: 0 320px; }
```

| 维度 | 说明 |
|---|---|
| 做什么 | 视口外元素**跳过 Style/Layout/Paint**（⑭⑮ 对这些子树不执行）；进入视口才完整渲染 |
| 尺寸 | 跳过期间用 `contain-intrinsic-size` 的占位尺寸参与滚动条计算 |
| 收益 | 初始渲染与滚动的失效范围大幅缩小——长列表/长文档的 FCP 与滚动性能立竿见影（示例量级，以实测为准） |
| 代价 | scrollHeight/锚点基于估算尺寸——**滚动条抖动**、`scrollIntoView`/查找定位会强制渲染目标（浏览器为此做了强制渲染，正确性保住了但性能优惠在那一刻消失） |
| 隐患 | `contain-intrinsic-size` 估得越准抖动越小；动态内容配 `auto 320px` 保留「渲染过的真实尺寸」记忆 |

### 5.2 contain：失效隔离的五个刻度

`contain` 声明「这棵子树内部的变化不外溢」，让失效传播在边界停下（衔接第八阶段 07 册的失效传播）：

| 值 | 隔离内容 | 典型用途 |
|---|---|---|
| `layout` | 子树外不受内部布局影响 | 布局边界 |
| `paint` | 子孙绘制不外溢（兼作裁剪与 containing block） | 组件级绘制隔离 |
| `style` | 计数器/引号等样式作用域不外溢 | CSS 计数器隔离 |
| `size` | 尺寸不依赖内容（子树按声明尺寸计） | 需显式给尺寸 |
| `strict` | size+layout+paint | 全隔离（给固定尺寸容器） |
| `content` | layout+paint+style | 常用默认推荐 |

组合纪律：`content-visibility: auto` **隐含** layout/paint/style 包含（它就是 contain 的自动化包装）；给「渲染稳定的大组件」加 `contain: content` 是低成本高收益的失效卫生。

### 5.4 content-visibility 的适用与不适用

| 适用 | 不适用 / 慎用 |
|---|---|
| 长列表/信息流（视口外区块边界清晰） | 视口内首屏元素（看不出收益） |
| 长文档的章节块（配合 `contain-intrinsic-size` 估高） | 需要精确 `scrollHeight` 的交互（滚动条联动、进度计算） |
| 评论区/瀑布流的非首屏卡片 | 依赖祖先布局计算的元素（百分比高度链会断） |
| 与虚拟列表互补：简单场景用它省掉虚拟列表复杂度 | 锚点跳转/查找定位高频的场景（强制渲染抵消收益） |

最后一个提醒：`content-visibility` 改变的是「跳过时」的表现——DOM 结构、事件监听器、可访问性树的存在方式各浏览器实现细节有差异（示意口径），上生产前用真实交互路径（Tab 焦点遍历、屏幕阅读器、查找）回归一遍。

### 5.3 交互链路的收束

回到上一册 §6：交互后重渲染的成本 = 失效范围 × 管线阶段。本节原语给出了第三条优化轴：

```text
改属性通道（transform/opacity）  → 管线短（上一册）
缩小失效范围（scoped class）      → 范围小
contain/content-visibility       → 让「不相关区域」根本不参与
```

## 6. 实验

1. **水合成本可视化**：本地起一个 SSR demo（任意框架均可），Performance 录制加载——在首帧（⑯ 标记）之后找到水合长任务；用 4x CPU throttling 放大后观察「首帧完成但点击无响应」的窗口（对齐 INP 输入延迟段）。
2. **islands 对照**：同一页面做两版——全量水合 vs 只水合一个交互岛。对比 ⑬ 下载/执行量（Network+Performance）与水合任务时长（示例对比，量级自测）。
3. **选择性水合的交互暂存**：流式 SSR demo 里在水合完成前点击，观察点击是否被「暂存后回放」（框架 DevTools 或打断点验证捕获阶段监听器）——平台机制的实证。
4. **View Transitions 快照观察**：给两个状态的容器加 `view-transition-name: card`，DevTools Elements 面板在过渡期间展开 `::view-transition` 伪元素树，确认快照结构（§4.1 图）；再尝试过渡期间点击快照区域，验证「不可交互」。
5. **content-visibility 收益测量**：500 个卡片的长列表，开/关 `content-visibility: auto`（配 contain-intrinsic-size），对比 FCP、Layout 时长（Performance 面板）与滚动帧率（FPS meter）。
6. **contain-intrinsic-size 与滚动条抖动**：故意把估算高度写错（真实 500px 估 100px），观察滚动条跳动与跳转偏差——「估算尺寸纪律」的反面教材。
7. **contain 失效隔离验证**：`contain: content` 的大容器内高频改样式，对比容器外区域的 Style 计算时间（Performance 的 Recalculate Style 范围）。

## 7. 常见误区

1. **「SSR 了就快了」**：SSR 省的是首屏传输/渲染；交互就绪要等水合——「首屏快交互卡」正是 SSR 时代的典型裂缝。
2. **「渐进水合省了 JS」**：它只摊薄时间分布；静态区依然陪跑——省总量的是 islands/resumability，调顺序的是选择性水合，三件事别混。
3. **「RSC = 不水合」**：RSC 免掉的是**服务端组件的 JS 下发**；客户端组件照样水合——「水合消失」的说法属于 resumability 那一档。
4. **「流式 SSR 只有好处」**：占位尺寸不准 → CLS；后到的大内容 → LCP 被刷新（上一册候选机制）——流式要配套占位纪律。
5. **「View Transitions 是更高级的 CSS transition」**：本质不同——它过渡的是两个离散状态的快照，DOM 早已切换；动画期间内容不可交互。
6. **「content-visibility 随手加」**：scrollHeight/锚点/查找定位都受估算尺寸影响——配不准的 contain-intrinsic-size 反而制造滚动条抖动。
7. **「contain 是无害的属性」**：`size`/`strict` 让子树尺寸脱离内容——没给准尺寸直接塌陷或溢出；`paint` 会创建裁剪上下文，溢出可见性变化。

### 7.5 常见问答

**Q：怎么判断我的页面该上 islands 还是留在全量水合？**
量一个比值：**水合总时长 × （1 − 交互区域面积占比）**——这个「陪跑浪费」如果达到几百 ms 量级（4x CPU throttling 下肉眼可见点击延迟），islands 的改造收益就成立；反之页面本来就是「整页应用」，拆岛只会增加通信成本。判断依据来自实验 1 的水合任务测量，不是架构潮流。

**Q：选择性水合的「事件暂存」会不会丢事件？**
平台机制上是「捕获阶段全局监听 + 记账回放」——事件没有丢，只是延迟派发；但交互的**反馈**延迟了（INP 的输入延迟段被计入）。用户感知的是「点了但慢半拍」而非「点了没反应」——这也是它比「水合完成前完全无响应」的体验改善所在。极端场景（暂存期间页面切换）由框架层的清理逻辑负责，归 `react/` 站。

**Q：View Transitions 和 FLIP 手法（First-Last-Invert-Play）什么关系？**
FLIP 是手写快照过渡的原始模式（先记旧位置 → 改 DOM → 反向 transform → 播放动画）；View Transitions 把这套流程平台化——快照、逆变换、动画全由浏览器接管，还天然覆盖「元素消失/新增」这类 FLIP 难写的场景。理解了 FLIP，VT 的快照机制就是「浏览器替你做的 FLIP」。

**Q：content-visibility 能替代虚拟列表吗？**
场景决定：content-visibility 保留全部 DOM（内存里所有节点都在），只是跳过渲染——列表几百项时它是零成本的省事方案；上万项时 DOM 本身的内存与样式匹配成本压不住，虚拟列表（只挂载视口附近节点）仍是正确工具。两者可以叠加：虚拟列表的每个条目再加 content-visibility 处理渲染层。
