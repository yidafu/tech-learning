# 加载优化手法手册

> [← 第九阶段导览](01-导览.md) · 时间线 ⑪→⑯。前两册建立了诊断框架（CRP 三条件 + 指标计算原理），这一册开始给弹药：资源 hint 全用法、图片优化、代码分割与预取。每件手法都带三件套——**精修时间线哪一段、预期指标收益、什么时候变成陷阱**。手法会过时（参照第四阶段 6 连接军备竞赛的下场），但「归因 + 验证」的纪律不会。

## 1. 手法归因总表：先学对号入座

学手法的正确顺序：先知道它砍的是时间线哪一段，再看怎么用——「preconnect 该不该用在同源」这种争论，归因表一眼就终结：

| 手法 | 精修段落 | 主打指标 | 最常见误用 |
|---|---|---|---|
| dns-prefetch | ③ | FCP 微量 | 用它替代 preconnect |
| preconnect | ③④⑤ | FCP/LCP | 滥用（>4 个域） |
| preload | ⑪（资源发现提前） | LCP | 抢占关键资源带宽 |
| modulepreload | ⑬（提前编译） | FCP/LCP | 忘了它是「解析+编译」级 |
| prefetch（旧） | ⑪（未来导航） | 下一页 LCP | 当 preload 用 |
| Speculation Rules | ⑪~⑯（整页预渲染） | 下一页全指标 | 预渲染非幂等页面 |
| fetchpriority | ⑪（带宽分配） | LCP | 满页 high |
| 图片 lazy | ⑪（延后非首屏） | FCP/LCP（省带宽） | **lazy 在 LCP 图上** |
| srcset/sizes | ⑪（传输体积） | LCP | 只写 x 描述符不管视口 |
| aspect-ratio 占位 | ⑮→⑯（预留空间） | CLS | 占位尺寸 ≠ 真实尺寸 |
| 关键 CSS 内联 | ⑫ | FCP | 超体积预算（上一册） |
| 代码分割 | ⑬ | FCP/LCP/TBT | 分过头：请求瀑布化 |
| 路由预取 | ⑪（未来导航） | 下一页 FCP | 预取全部路由 |

下面逐类展开。

## 2. 资源 hint 全用法

### 2.1 dns-prefetch：最轻的 hint

```html
<link rel="dns-prefetch" href="https://stats.example.com">
```

| 维度 | 说明 |
|---|---|
| 做什么 | 后台提前解析 DNS（③） |
| 收益 | 省一次 DNS 往返（几十到几百 ms，弱网放大） |
| 陷阱 | 几乎没有——但收益也只有 DNS 段，别指望它替代 preconnect |
| 最佳位置 | 对**少量**第三方域兜底；通常与 preconnect 配对（preconnect 失败时 dns-prefetch 仍在） |

### 2.2 preconnect：建连全家桶

```html
<link rel="preconnect" href="https://fonts.gstatic.com" crossorigin>
```

| 维度 | 说明 |
|---|---|
| 做什么 | 提前完成 ③DNS + ④TCP + ⑤TLS 三段 |
| 收益 | 首个请求省 1~3 RTT（对照第四阶段的建连账） |
| 陷阱 1 | **闲置 10s 即关闭**（量级口径）——hint 太早发出，到用时连接已断，白付 TLS |
| 陷阱 2 | **滥用带宽/CPU**：每个 preconnect 付真实握手成本，>4 个域得不偿失 |
| 陷阱 3 | `crossorigin` 属性决定连接能否复用：字体/脚本等跨源资源**必须带**，漏写 = 建了两条不相关的连接 |

使用纪律：**只 preconnect 确定要用且马上要用的关键域**（字体 CDN、关键 API 域），数量控制在个位数。

### 2.3 preload：把「发现」提前到解析之前

```html
<link rel="preload" href="/hero.avif" as="image" fetchpriority="high">
<link rel="preload" href="/fonts/headline.woff2" as="font" type="font/woff2" crossorigin>
```

| 维度 | 说明 |
|---|---|
| 做什么 | 告诉浏览器「这个资源当前页面一定要」，提前高优先级拉取（⑪） |
| 何时该用 | 资源**藏在 CSS/JS 里**（CSS 背景图、@font-face）或**深度依赖**（bundle 后期才发现）导致发现太晚时 |
| 收益 | LCP 前移——LCP 相位的「加载延迟」段直接缩短（上一册 §3.4 相位分解） |
| 陷阱 1 | **双下载**：preload 的 URL 与实际使用不一致（哪怕参数差异）= 浏览器拉两次，Network 面板会出现重复条目与 console 警告 |
| 陷阱 2 | **抢占带宽**：preload 优先级默认很高，preload 错东西（如非首屏图）会把 LCP 图挤到后面 |
| 陷阱 3 | **违背 DRY**：preload 列表手工维护，URL 改版漏改 = 双下载静默发生 |

一个反直觉用法：**LCP 图如果就是 HTML 里的 `<img>`，别 preload**——HTML 里靠前位置的 img 本来就被 preload scanner 早早发现（第六阶段 05 册），再 preload 是冗余；该用 `fetchpriority="high"` 表达优先级（§2.6）。

### 2.4 modulepreload：ES 模块的深度版

```html
<link rel="modulepreload" href="/app/main.mjs">
```

比普通 preload 多做两步：下载后**递归解析模块图**并**编译**入缓存——⑬ 的编译成本也提前付了。用于「首屏主模块 + 其依赖图」的入口；陷阱与 preload 相同（URL 必须与 import 实际 URL 逐字一致）。

### 2.5 prefetch 与 Speculation Rules：面向下一次导航

```html
<!-- 旧 prefetch：低优先级拉资源，供未来使用 -->
<link rel="prefetch" href="/next-page.html">
```

```html
<!-- 现代 Speculation Rules：声明式预取/预渲染 -->
<script type="speculationrules">
{
  "prefetch": [{ "urls": ["/docs/"], "eagerness": "moderate" }],
  "prerender": [{ "urls": ["/docs/"], "eagerness": "moderate" }]
}
</script>
```

| 手段 | 粒度 | 收益 | 陷阱 |
|---|---|---|---|
| prefetch（旧） | 单资源 | 下一页的资源 ⑪ 免排队 | 误当 preload 用（优先级低、不渲染） |
| Speculation Rules prefetch | 整页响应 | 下一页 HTML 提前到手 | 服务端有副作用路由（登出等）不能预取 |
| Speculation Rules prerender | **整页预渲染** | 下一页 ⑪~⑯ 全部提前完成，点击近乎 0ms | 预渲染页面里 JS 立即执行（副作用放大）、带宽翻倍；需配合 eagerness 控制 |

eagerness 三档（Chrome 口径）：`conservative`（仅 hover 链接后）、`moderate`（悬停/预点击时）、`eager`（立即）。预渲染纪律：**只预渲染幂等的、高概率前往的页面**（文档下一页、列表详情），带副作用的操作 URL 一律排除。

### 2.6 fetchpriority：带宽分配的手术刀

```html
<img src="/hero.avif" fetchpriority="high">
<img src="/footer-logo.png" fetchpriority="low">
```

浏览器本就按资源类型/位置给默认优先级（第六阶段 05 册的优先级表）；`fetchpriority` 是**显式覆盖**——适合「HTML 位置无法表达重要性」的场景（模板渲染的 hero 图排在大量小图之后）。陷阱：满页 high = 没有人 high；先看默认优先级是否已经正确，再谈覆盖。

### 2.7 hint 使用速查（决策树）

```text
这个资源是当前页首屏必需、但发现晚（藏在 CSS/JS）？
  └─ 是 → preload + as 指明类型（字体记 crossorigin）
跨源连接会马上用到？
  └─ 是 → preconnect（≤4 个域，字体域记 crossorigin）
是下一次导航的整页？
  └─ 是 → Speculation Rules（prefetch/prerender + eagerness）
是 HTML 里靠前的 LCP 图？
  └─ 是 → 都不用，fetchpriority="high"
只是「可能用到的第三方域」兜底？
  └─ 是 → dns-prefetch（轻量兜底）
```

## 3. 图片优化：LCP 与 CLS 的主战场

### 3.1 loading="lazy"：救 FCP 的刀，别捅 LCP

```html
<img src="below-fold.avif" loading="lazy" alt="...">
```

原理：视口外图片不进入加载队列，滚动临近时（距离阈值触发，量级口径：快网数百像素到千像素级、慢网翻倍）才开始请求。收益：首屏带宽与并发全部让给关键资源。

**经典负优化**：把 `loading="lazy"` 加在 LCP 候选图上——首屏图反而被延后，LCP 直接劣化（上一册 §3.1 的候选规则决定了首屏大图几乎必是冠军）。纪律：**首屏图绝不含 lazy；lazy 只给首屏外**。

### 3.2 srcset/sizes：按设备发对的尺寸

```html
<img
  src="hero-800.avif"
  srcset="hero-400.avif 400w, hero-800.avif 800w, hero-1600.avif 1600w"
  sizes="(max-width: 600px) 100vw, 50vw"
  alt="...">
```

| 描述符 | 语义 | 适用 |
|---|---|---|
| `400w` + `sizes` | 按**视口宽度**选文件 | 响应式布局图片（主流） |
| `1x/2x` | 按 **DPR** 选文件 | 固定尺寸图片（图标类） |

`sizes` 告诉浏览器「这张图最终显示多宽」，浏览器综合视口宽 × DPR 选最接近的候选——发 2x 屏 4K 原图到 320px 宽的手机位，是最常见的流量浪费。陷阱：`sizes` 写错（与实际显示宽不符）= 选择偏差，Layout 稳定后可用 DevTools 检查实际加载了哪个候选。

### 3.3 aspect-ratio 与 width/height：CLS 的源头治理

```html
<img src="chart.avif" width="1200" height="600" alt="...">
```

```css
.hero-img { width: 100%; height: auto; aspect-ratio: 2 / 1; }
```

写上 `width/height` 属性（或 CSS `aspect-ratio`）后，浏览器**在图片加载前**就由 HTML 属性算出宽高比、预留正确空间——加载完成不再撑开文档（上一册 §4.4 的 CLS 源头治理）。陷阱：属性值与真实图片宽高比不符 = 预留错位（浏览器会按比例修正但布局抖动仍在）；构建管线应校验「属性宽高 = 图片元数据宽高」。

### 3.4 格式与压缩

| 格式 | 相对体积（量级口径） | 关键能力 | 兼容注意 |
|---|---|---|---|
| AVIF | 基准的 ~50% | 高压缩、支持动画/透明 | 较新浏览器；配 fallback |
| WebP | 基准的 ~70% | 广泛兼容 | 老 Safari 有坑 |
| JPEG（渐进式） | 基准 | 万无一失的兜底 | — |

工程姿势：`<picture>` 双源 + JPEG 兜底；服务端按 Accept 头直接协商也常见（第五阶段 05 册的压缩协商同款思路）。收益如实记：格式换代是**传输体积**段（⑪）的优化，LCP 收益取决于图片是否恰是候选。

### 3.5 LCP 图的完整处方（本节收束）

```html
<!-- 首屏 LCP 图：不 lazy + 尺寸占位 + 高优先级 + 右尺寸 -->
<img src="hero-800.avif"
     srcset="hero-400.avif 400w, hero-800.avif 800w"
     sizes="100vw"
     width="800" height="450"
     fetchpriority="high"
     alt="...">

<!-- 可选：CSS 背景图形式的 LCP 才需要 preload -->
<link rel="preload" as="image" href="hero-800.avif" fetchpriority="high">
```

## 4. 代码分割与预取

### 4.1 路由级分割：默认姿势

```js
// 路由懒加载：首屏只载当前路由的 chunk
const Page = React.lazy(() => import('./routes/Docs'));
```

收益：⑬ 的解析/编译/执行量按路由摊薄；FCP 与 TBT 双降。陷阱一览：

| 陷阱 | 现场 | 解法 |
|---|---|---|
| **分割过碎 → 请求瀑布** | 动态 import 嵌套（A 的 chunk 里再 import B）——发现 B 要等 A 下载执行完 | 路由入口模块收敛依赖图；模块预声明（下一小节） |
| 分割过粗 | 单 chunk 5MB | 评审路由/组件边界 |
| 共享依赖重复打包 | 多 chunk 各带一份库 | 构建器 splitChunks/vendor 拆分 |
| 懒加载延迟 | 点击后白等 chunk 下载 | 路由级预取（§4.2） |

### 4.2 预取未来 chunk：让分割不用付延迟

```js
// 用户悬停导航项时预取目标路由 chunk（依赖可见性/悬停信号）
navLink.addEventListener('pointerenter', () => {
  import(/* webpackPrefetch: true */ './routes/Docs');
});
```

或构建期静态声明关键路由的 `<link rel="prefetch">` / Speculation Rules。纪律：**预取「大概率前往」的路由**（列表→详情、文档下一页），预取全部路由 = 带宽浪费回潮（§1 表里的老毛病）。

### 4.3 首屏 bundle 的瘦身清单

| 手段 | 段落 | 备注 |
|---|---|---|
| Tree shaking 确认生效 | ⑬ | 构建产物里搜未用到的库代码 |
| 大依赖按需替换/移除 | ⑪⑬ | 日期库/工具库动辄几十 KB |
| polyfill 按目标浏览器发 | ⑪ | 现代浏览器别背 legacy 包 |
| 首屏不必要的 JS defer/延迟 | ⑬ | 分析脚本、聊天挂件（衔接上一册） |
| 第三方脚本审计 | ⑪⑬ | 每个 script 问「首屏需要吗」；第三方治理见第十阶段案例 |

## 6. 实验

1. **preconnect 收益量化**：本地起服务 + 用 tc/工具类模拟 100ms RTT（或 Network throttling），对比有/无 preconnect 时首个跨源资源的时间戳差值（示例量级，以实测为准）。
2. **preload 双下载复现**：preload 一个带查询参数差异的 URL（与 CSS 里实际引用不一致），观察 Network 面板重复条目与 console 警告——§2.3 陷阱 1 的现场。
3. **LCP 图 lazy 负优化**：给首屏大图加 `loading="lazy"`，Lighthouse 前后对比 LCP；移除后复测。
4. **srcset 实测**：DevTools 设备模拟切 DPR 1/2/3，观察实际加载的候选文件；故意把 sizes 写错（50vw 实占 100vw），验证选择偏差。
5. **aspect-ratio 修 CLS**：无尺寸图片页 vs width/height 属性页，用 Layout Shift Regions（上一册实验）对比位移区域是否消失。
6. **Speculation Rules 预渲染**：本地站配置 prerender 下一页，点击链接观察导航近乎瞬时（DevTools Performance 里无网络段）；再给预渲染页加副作用脚本（发请求），观察副作用在预渲染期即发生——陷阱实证。
7. **代码分割瀑布诊断**：故意做「chunk A 内再 import chunk B」的嵌套懒加载，Network 面板观察 B 的请求起点晚于 A 的执行——瀑布现场；再用构建器预声明消除。
8. **优先级观察**：Network 面板开 Priority 列（右键列头），记录同页 img/字体/脚本/预加载的默认优先级，再试 fetchpriority 覆盖——衔接第六阶段 05 册的优先级表。

## 7. 常见误区

1. **「hint 越多越快」**：每个 hint 有真实成本（握手、带宽、双下载）——hint 是手术刀不是维生素，滥用者把带宽让给了不重要的资源。
2. **「preload 万金油」**：HTML 里靠前的 img 本就被扫描器早发现，preload 冗余；URL 不一致直接双下载——先确认「发现晚」这个前提成立。
3. **「全站图片 lazy 是最佳实践」**：LCP 候选图 lazy 是教科书级负优化——lazy 的收益对象是首屏外。
4. **「上了 AVIF/WebP 就完事」**：体积优化 ≠ 发现/优先级优化；LCP 相位四段（上一册 §3.4）各有各的病，格式只治加载时长一段。
5. **「代码分割越细越好」**：过碎引发请求瀑布与并行度下降（h2 多路复用也救不了「依赖发现必须等执行」）——分割粒度跟着路由边界走。
6. **「prefetch 当前页资源」**：prefetch 面向未来导航；当前页用 preload——两者优先级、语义、时机全不同。
7. **「预渲染随便开」**：预渲染页里的 JS 立刻执行，副作用（埋点/请求/状态写入）提前发生——幂等纪律是预渲染的准入条件。

| 5 | 路由 chunk 无嵌套瀑布？ | Network 面板 chunk 串行度 | 动态 import 嵌套 = 分割返工 |
| 6 | 响应式图片 sizes 与显示宽一致？ | 设备模拟实测候选 | 选择偏差 = 白下载 |
| 7 | 预渲染页面副作用审计过？ | Speculation Rules + 代码 review | 埋点/请求在预渲染期提前跑 = 数据污染 |
| 8 | 每个手法改完复测过指标？ | Lighthouse + Performance 前后对照 | 无对照数据 = 手法没被验证 |
