## 阶段目标

学完本阶段，你应该能不查资料做到这些事：

1. 精确说出关键渲染路径：CSSOM 就绪 + DOM 就绪 + 同步 JS 执行完 → 首次渲染，并解释「CSS 在前 JS 在后」「关键 CSS 内联」为什么成立。
2. 说出 LCP 的候选元素集合（img、背景图、文本块、视频首帧……）与自动剔除规则（用户交互后停止、不可见元素不算），以及为什么 2.5s 是「好」的阈值。
3. 计算 CLS：给定三次位移的距离分数与影响分数，算出 session window 下的总分。
4. 拆解 INP 的三段延迟（输入延迟：主线程忙 → 处理：回调执行 → 呈现延迟：下一帧渲染），并给出每段的定位方法。
5. 说出滚动事件为什么默认可能阻塞合成器滚动、`passive: true` 改变了什么、`touch-action` 与 overscroll 的分工。
6. 解释水合为什么贵（重执行一遍 JS 来「认领」已有 DOM）、部分水合/选择性水合分别在省哪一段。

## 知识点地图

### 1. 首屏与 CRP（02 册）

- **首次渲染的前置条件**：DOM（至少视口内）+ CSSOM（视口内生效样式）+ 阻塞 JS 执行完毕。三者谁晚到谁说了算——这就是「首屏优化 = 缩短三者关键路径」。
- **白屏解剖**：CSS 阻塞渲染（防 FOUC）+ 同步 JS 阻塞解析 + 字体 FOIT，三类阻塞的时序叠加是白屏的经典构成。
- **字体**：FOIT（不可见期）/FOT（后备字体闪替）与 `font-display: swap/optional/fallback` 的取舍——`optional` 甚至可能整次访问都不用自定义字体。

### 2. 指标原理（03 册）

- **LCP**：候选元素在渲染中逐帧更新（更大的新候选出现就替换），直到首次用户输入后停止上报——所以 LCP 可以被「一张更晚出现的大图」刷新。
- **CLS**：每次位移 = 影响分数（视口内受影响面积占比）× 距离分数（位移距离/视口尺寸），session window（5s 窗口、1s 间隙）取最大值——「累计」其实是「最糟窗口」。
- **INP**：取页面生命周期内所有交互的第 ~98 百分位（每次交互=输入延迟+处理时间+呈现延迟），长任务与渲染阻塞直接体现在前两段。
- **web-vitals 库**：用 PerformanceObserver + 各指标规范实现纯前端测量——它是把「指标定义」变成「代码」的参考实现。

### 3. 优化手法与交互（04、05 册）

- **手法归因表**：每个手法都标注精修哪段（preconnect→③④⑤、preload→⑪、关键 CSS 内联→⑫、content-visibility→⑮…）——学手法先学归因。
- **图片**：lazy（注意别 lazy 到 LCP 候选上）、srcset（按 DPR/视口选格式）、aspect-ratio（从源头消灭 CLS）、AVIF/WebP。
- **输入链路**：合成器先接住输入（滚动/手势不需要 JS）→ hit test 找到目标 → 事件路由到主线程 → 回调执行 → 重渲染。passive listener 把「事件处理可能阻止滚动」的承诺提前给出，合成器不必等主线程。

### 4. 水合与新架构（06 册）

- **水合的成本模型**：SSR 给了 HTML（省了渲染），但交互前必须把框架 JS 全跑一遍「认领」DOM——全量水合是最贵的摊销方式。
- **谱系**：部分水合（islands，只水合交互岛）→ 选择性水合（React 18，按交互优先级排队）→ RSC（服务端组件不进客户端 bundle）。
- **管线级新原语**：`content-visibility: auto`（视口外跳过布局绘制）、`contain`（失效隔离）、View Transitions（跨视图状态过渡，浏览器接管动画帧）。

## 实践任务

1. 给目标站点接入 web-vitals，把 LCP/CLS/INP 上报到 console，收集 20 次弱网样本。
2. 找出目标站点 LCP 元素（Performance 面板 LCP 标记 + Elements 面板对应节点），检查它有没有被 lazy、有没有 preload。
3. 人为制造一次 CLS（图片无尺寸 + 晚到的 banner），用 Layout Shift Regions 高亮验证，再用 aspect-ratio 修复。
4. 写一个长任务（>100ms）卡主线程，测 INP 劣化；用 `scheduler.postTask` 拆分后复测。
5. 打开 chrome://flags 的平均帧率监控（或 FPS meter），对比 content-visibility 开关前后的滚动帧率。

## 自测题

1. 「CSS 放 head、JS 放 body 尾」这条老经验在 CRP 模型下的精确解释是什么？什么情况下「JS 放尾部」依然拖慢首屏？
2. LCP 候选元素在什么时候不再更新？为什么 LCP 有时比 FCP 还早？
3. 一次位移影响视口 50% 面积、移动 20% 视口高度，这次位移的 CLS 分数是多少？如果 4 秒后又发生一次同样位移，总分怎么算？
4. INP 的「输入延迟」段变长，通常说明主线程在干什么？给出两种定位方法。
5. passive: true 的 scroll 监听器里调用 preventDefault() 会发生什么？为什么？
6. `loading="lazy"` 用在 LCP 候选图上为什么是负优化？浏览器 lazy 加载的距离阈值大概是什么量级？
7. 全量水合、部分水合、选择性水合三者各自省掉了哪一段成本？用一个「页面 80% 区域无交互」的场景算一笔粗账。
8. content-visibility: auto 让浏览器跳过视口外元素的哪些管线阶段？它会不会影响 scrollHeight/锚点定位？
9. View Transitions API 的动画帧由谁驱动？它和 CSS transition 的执行位置有什么本质区别？
10. 把本阶段手法填进时间线账本：为 ⑯（首帧上屏）提速的三板斧分别精修哪几段？为什么「减少关键资源数量」比「压缩单个资源」常常更有效？
