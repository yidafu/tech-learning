# 性能指标深潜：FCP / LCP / CLS / INP 测量原理

> [← 第九阶段导览](01-导览.md) · 时间线 ⑯⑰。上一册把首屏的阻塞源讲透了，这一册回答更难的问题：**浏览器到底是怎么算出这些数字的**。LCP 的候选元素会逐帧更新、CLS 的「累计」其实是最糟窗口、INP 把一次交互拆成三段延迟——不懂计算原理，优化就是在给一个不理解的公式做题。本册只讲单用户视角的度量原理；RUM 与线上大规模采集的口径归 `observability/` 站。

## 1. 指标全景：为什么是这四个

Core Web Vitals 的入选逻辑不是「哪个指标好算」，而是各覆盖一类用户感知：

| 指标 | 感知问题 | 时间线锚点 | 「好」阈值（p75 口径） |
|---|---|---|---|
| **FCP** | 页面开始有内容了吗 | ⑯ 首帧 | ≤ 1.8s |
| **LCP** | 主内容出来了吗 | ⑯ 首屏 | ≤ 2.5s（劣化 > 4.0s） |
| **CLS** | 页面稳不稳（会不会误点） | ⑯ 后持续 | ≤ 0.1（劣化 > 0.25） |
| **INP** | 交互跟手吗 | ⑰ 持续交互 | ≤ 200ms（劣化 > 500ms） |

阈值来源是公开的口径（Google 基于用户行为研究选取的分位线），不是随缘数字；报告中统一取页面访问的 **p75** 再看分布——均值会被少数极快/极慢样本掩盖。两个体系别混：**实验室数据**（Lighthouse/本地录 Performance，确定性可复现）与**真实用户数据**（CrUX/RUM，反映真实分布）——本册讲的计算原理两者通用，但数值解读要区分场景。

### 1.5 先立规矩：什么算「渲染」

所有绘制类指标共享一套判定底座：

| 判定 | 规则 |
|---|---|
| 有内容（contentful） | 文本、图像（含背景图）、SVG、非空白 canvas |
| 不算内容 | 空白区域、纯背景色、不可见元素（`opacity: 0`、`display: none`、`visibility: hidden`） |
| 首帧即内容 | FCP = 第一次「有内容」的绘制 |

这套判定直接解释了上一册的 FOIT 盲区：不可见文本「绘制了」但用户看不见——绘制类指标与人类感知之间天然存在裂缝，指标组合的意义就在互相补盲。

## 2. FCP：最简单的起点

FCP 的定义朴素：导航开始后，首次绘制出任何「有内容」内容的时刻。

```js
new PerformanceObserver((list) => {
  for (const e of list.getEntries()) console.log('FCP:', e.startTime);
}).observe({ type: 'paint', buffered: true });
```

测量要点：

- `buffered: true` 把观察者注册前已发生的历史条目补发——**所有指标测量的第一课**：脚本晚于首帧运行（分析工具、延迟注入）时照样能拿到数据。
- FCP 只报告一次；`first-paint`（FP，任何绘制）与 FCP 的差值 = 「画了东西但还没画内容」的时段。
- FCP 对「内容多少」不敏感——一整个空白骨架屏 + 一行 loading 文字也能拿下漂亮 FCP。所以它只配当起点，LCP 才是主内容指标。

## 3. LCP：候选元素的游戏规则

LCP（Largest Contentful Paint）不是「最大的图片加载完」，它是一场**逐帧进行的选美**：

1. 渲染管线每画一帧，检查这一帧里有没有新的「LCP 候选元素」；
2. 候选的**有效面积**（与视口求交的部分）若大于当前冠军，则**替换冠军**并更新 LCP 时刻；
3. 直到**停止条件**触发，最后那个冠军的绘制时刻就是 LCP。

### 3.1 候选元素集合（规范定义，非穷举感觉）

| 元素类型 | 说明 |
|---|---|
| `<img>` | 含内联 srcset/sizes 的选择结果 |
| SVG 内的 `<image>` | — |
| `<video>` | 有 poster 时算 poster 图；无 poster 的首帧呈现也算 |
| `background-image: url(...)` 的元素 | CSS 背景图（注意：不是渐变） |
| 包含**文本节点**的块级元素 | 或其行内子元素含文本——整块文本算一个候选 |

### 3.2 剔除与特殊规则（高频考点）

| 规则 | 后果 |
|---|---|
| 不可见元素（`opacity: 0` 等）不算候选 | `opacity: 0` 藏首屏图骗不了 LCP；但注意它也让你测不出问题 |
| 有效面积 = 与视口的交集 | 视口外的那部分面积不计入——长图只有首屏部分参与排名 |
| **元素从 DOM 移除，冠军不撤** | 先画的大图后被 JS 删掉，LCP 照旧成立 |
| 网络图逐字节到达时，面积按已到达字节的呈现进度计 | 一张渐进加载的大图可能在加载中途才「长得够大」成为冠军——LCP 被晚到的图刷新是正常机制 |
| `display: none`→显示的切换会产生新候选 | 延迟显示的首屏内容照样参与选美 |

### 3.3 停止条件（LCP 什么时候封盘）

| 触发 | 行为 |
|---|---|
| **首次真实用户交互**（click / tap / keydown 等；**滚动不算**） | 立即停止候选更新，上报当时的 LCP |
| 页面转入后台（标签页隐藏/最小化） | 上报当时的最终值 |
| 页面卸载 | 上报最终值 |

「滚动不算」是个反直觉但讲得通的设计：滚动不改变用户对主内容的预期，用户可能只是路过；而点击/按键意味着用户开始「用」页面了。这也给了性能优化一个提醒：**页面加载后 2 秒才出现的超大 hero 图依然会刷新 LCP**——别以为用户没交互就封盘了。

### 3.4 测量代码与 Performance 面板对照

```js
new PerformanceObserver((list) => {
  const entries = list.getEntries();
  const last = entries[entries.length - 1];
  // LCP 是逐条更新的：last 就是当前冠军
  console.log('LCP:', last.startTime, '元素:', last.element, '面积:', last.size);
}).observe({ type: 'largest-contentful-paint', buffered: true });
```

DevTools 对应物：

| 工具位置 | 能看到什么 |
|---|---|
| Performance 面板 → Timings 轨道 | `LCP` 标记（最终冠军的时刻） |
| Performance Insights（Chrome） | LCP 相位分解：TTFB / 加载延迟 / 加载时长 / 渲染延迟 |
| Elements 面板 | 配合 `entry.element` 定位冠军节点 |

LCP 相位分解是归因的入口（量级示意，以实测为准）：**TTFB 长 → 服务端/网络问题（第五阶段）；加载延迟长 → 资源发现晚了（preload/优先级，下一册）；加载时长长 → 体积/压缩；渲染延迟长 → 主线程被占（阻塞脚本/CSS）**。

## 4. CLS：一次位移的分数与 session window

### 4.1 单次位移的分数

每次「意外的布局位移」产生一个分数：

```text
位移分数 = 影响分数（impact fraction） × 距离分数（distance fraction）
影响分数 = （受影响区域并集面积） / 视口面积
距离分数 = （最大位移距离） / 视口最大维度（宽高中较大者）
两个分数都封顶 1.0
```

算例（导览自测题第 3 题的答案底稿）：一次位移影响视口 50% 面积、内容移动 20% 视口高度：

```text
影响分数 0.5 × 距离分数 0.2 = 本次位移 0.10 —— 正好踩在「好」的边界上
```

### 4.2 哪些位移不算数（剔除规则）

| 剔除规则 | 理由 |
|---|---|
| **用户输入后 500ms 内的位移**（点击/按键；滚动不算输入） | 用户主动引发的展开/收起不该记过 |
| **transform 引起的移动**（translate 动画等） | transform 动画不触发布局——浏览器刻意把动画通道设计成免罚 |
| 在视口外发生的位移 | 用户看不见的位移不扣分 |

「transform 免罚」是性能纪律的经济学：把位移动画全部改写为 transform，既是渲染性能优化（第八阶段合成器动画），也是 CLS 优化——一箭双雕。

### 4.3 Session Window：「累计」的真相

页面整个生命周期里位移可能发生几十次，如果简单累加，一个长滚动页面随便就爆表。规范的处理是 **session window（会话窗口）**：

```text
窗口开启：发生第一次位移
窗口延续：相邻位移间隔 ≤ 1s，且窗口总时长 ≤ 5s
窗口关闭：间隔超 1s 或总时长超 5s
CLS 最终值 = 所有窗口各自总分的最大值
```

```text
时间轴：  位移A(0.04) ─ 0.3s ─ 位移B(0.03) ─ 0.3s ─ 位移C(0.02) │……4s 静默……│ 位移D(0.08)
          └────────── 窗口1：总 0.09 ──────────┘              └─ 窗口2：0.08 ─┘
CLS = max(0.09, 0.08) = 0.09        ← 不是累加 0.17！
```

「累计」实为「最糟 5 秒」——这个设计回答了导览自测题第 3 题：4 秒后再次位移时，第一窗口（≤5s 且间隔 ≤1s）若已闭合则分窗取最大，未闭合（间隔 4s > 1s 必然闭合）则分窗。工程含义：**把几次小位移集中在一个 5 秒窗口里爆发，比分散开来伤害大**——分散修复位移时，先修同窗口内的那一簇。

### 4.4 CLS 的高发源头与测量

| 源头 | 机制 | 修复指针 |
|---|---|---|
| 无尺寸图片 | 加载后撑开下方内容 | `width/height` 属性或 `aspect-ratio`（第 04 册） |
| 广告/嵌入第三方 | 晚到且尺寸未知 | 预留容器固定尺寸 |
| 字体闪替（FOUT） | 后备字体度量 ≠ 真字体 | size-adjust 度量覆盖（上一册 §5） |
| 动态插入内容 | 在已有内容上方插入 | 插到下方或预留占位 |
| 无骨架尺寸的骨架屏 | 占位 ≠ 真实内容 | 骨架按最终尺寸建模 |

测量工具：

```js
let clsValue = 0, session = {value: 0, first: 0, last: 0};
new PerformanceObserver((list) => {
  for (const e of list.getEntries()) {
    if (!e.hadRecentInput) {           // 500ms 输入窗口内的位移剔除
      // （示意：完整实现需按 session window 规则累加，web-vitals 库已实现）
      clsValue += e.value;
    }
  }
}).observe({ type: 'layout-shift', buffered: true });
```

DevTools：Performance 面板勾选 **Layout Shift Regions**（Rendering 面板），复现一次位移，蓝色高亮区就是影响区域——与 §4.1 的「影响分数」直接对上；`layout-shift` 条目的 `sources` 给出肇事元素。

## 5. INP：一次交互的三段延迟

INP（Interaction to Next Paint）在 2024 年 3 月正式接替 FID（First Input Delay），理由：FID 只测**第一次**交互的**输入延迟**段——既不看后续交互，也不管回调执行与渲染呈现，是个偏乐观的下限指标。INP 的测量对象与口径：

- 对象：页面生命周期内**所有合格交互**（点击/点按/键盘；滚动与悬停不计）；
- 单次交互的时长：从**首个输入事件**到**交互引发的视觉更新下一帧绘制**完成；
- 每次页面访问取所有交互中**约第 98 百分位**（实现上常取最差一次交互）——站点层面的 p75 再聚合。

### 5.1 三段构成（INP 的解剖图）

```text
│←──── 输入延迟 ────→│←── 处理时间 ──→│←──── 呈现延迟 ────→│
│ 输入事件发生         │ 事件回调执行    │ 回调结束 → 下一帧绘制 │
│ 等主线程空出来       │（可能多个监听器）│ style/layout/paint    │
└──────────────── INP = 三段之和 ─────────────────────────┘
```

| 段 | 变长的典型原因 | 定位方法 |
|---|---|---|
| **输入延迟** | 主线程忙：长任务占道、其他回调排队 | Performance 面板看输入标记前的任务；长任务检测（`PerformanceObserver` longtask） |
| **处理时间** | 回调本身慢：同步计算、大循环、强制同步布局 | Performance 面板交互轨道展开事件；Event Log 看各监听器耗时 |
| **呈现延迟** | 回调后渲染工作重：大面积失效、布局抖动、样式计算范围大 | 看回调结束到帧绘制之间的 Style/Layout 火焰；`getBoundingClientRect` 读写交错是常客 |

三段各自独立归因是 INP 优于 FID 的本质：它逼你回答「这次交互到底慢在哪一段」，而不是给一个说不清的总数。

### 5.2 Event Timing API：INP 的数据源

```js
new PerformanceObserver((list) => {
  for (const e of list.getEntries()) {
    // 每个事件条目自带三段的时间戳
    console.log({
      interactionId: e.interactionId,   // 同一交互的多个事件共享此 ID（点击=pointerdown+up+click 合并为一次交互）
      inputDelay: e.processingStart - e.startTime,
      processing: e.processingEnd - e.processingStart,
      // 呈现延迟 = 下一帧绘制时刻 - processingEnd（帧时刻需另取 frame 条目）
    });
  }
}).observe({ type: 'event', buffered: true, durationThreshold: 16 });
```

细节：`durationThreshold: 16` 只上报超过一帧（约 16.7ms）的事件；「一次交互」由 `interactionId` 归并——INP 的口径是**交互**粒度而非事件粒度。

### 5.3 TBT 与 TTI：两个退场的辅助指标

| 指标 | 定义 | 现状 |
|---|---|---|
| **TBT** | FCP 到 TTI 之间，主线程阻塞超 50ms 的任务的「超出部分」总和 | 实验室指标保留（Lighthouse 用它近似 INP 风险），现场不再上报 |
| **TTI** | 主线程安静（5s 无长任务）且网络安静后的时刻 | 已从 Lighthouse 评分退役——定义过于间接、数值飘忽 |

TBT 的「50ms 以上算阻塞」源自任务切片纪律（单任务预算一帧）；它与 INP 的相关性是「风险指示」而非「保证」——TBT 低 INP 仍可能差（呈现延迟段不在 TBT 口径内）。

### 5.4 FID 与 INP 的口径对照（兴衰的完整账）

把退役指标放进同一张表，能看清 INP 为什么立得住：

| 维度 | FID（已退役） | INP（现行） |
|---|---|---|
| 交互范围 | 只有**第一次**输入 | 全生命周期所有交互 |
| 测量段 | 输入延迟 + 首个回调起点前的等待（不含回调执行完与渲染） | 输入延迟 + 处理时间 + 呈现延迟（到下一帧绘制） |
| 回归场景 | 回调慢/渲染慢**测不到**——FID 绿色但页面点不动 | 全口径捕获 |
| 兴衰原因 | 2018 年引入时「能测」优先，后来被证明是下限偏乐观的代理 | 2024-03 正式接棒 |

一句话：**FID 是「页面接住输入有多快」，INP 是「页面消化并呈现这次交互有多快」**——后者才是用户说的「跟手」。

## 6. web-vitals 库：规范的参考实现

指标定义 → 可运行代码之间的翻译由 Google 的 web-vitals 库完成，它的架构值得读（也是自研埋点的底稿）：

| 指标 | 数据源（PerformanceObserver 类型） | 库内计算 |
|---|---|---|
| FCP | `paint` | 取 first-contentful-paint 条目 |
| LCP | `largest-contentful-paint` | 跟踪最新冠军，交互/隐藏时封盘 |
| CLS | `layout-shift` | 按 hadRecentInput 剔除 + session window 累加 |
| INP | `event`（+ frame） | 按 interactionId 归并取最差交互，三段求和 |

三个工程要点：`buffered: true` 补历史（§2）；**上报时机**选 `visibilitychange` 隐藏时（指标可能仍在演化，页面隐藏才算终值）；attribution 扩展版（`onLCP` 的 attribution 对象）直接给出元素/加载阶段等归因字段。RUM 平台的大规模采集与分位聚合归 `observability/` 站，本册止步于单页测量。

## 7. 实验

1. **LCP 选美观赛**：页面先渲染一段文本（冠军），2s 后插入一张更大的首屏图——用 PerformanceObserver 观察冠军更替与 `entry.size` 变化；再在图到达后点击页面，观察封盘后不再更新。
2. **剔除规则实证**：给首屏图设 `opacity: 0`，确认 LCP 不再以它为候选（换次大候选）；移除 opacity 恢复。再验证「移除冠军节点 LCP 不撤」。
3. **CLS 手工计算**：构造无尺寸图片（视口 800×600，加载后撑开 50% 面积、下移 120px），先手算预期分数（0.5 × 120/600 = 0.10），再对照 Performance 面板 Layout Shift Regions 与 `layout-shift` 条目值。
4. **session window 实证**：两个位移间隔设 4s（分窗）与 0.8s（同窗）各跑一次，对比脚本输出的总分差异——「最糟窗口」语义的实证。
5. **INP 三段定位**：页面放一个 200ms 长任务 + 一个 100ms 的点击回调 + 回调内强制同步布局。录 Performance，对照三段构成图逐段指认；再用 `scheduler.postTask` 拆任务复测。
6. **滚动不算交互**：LCP 封盘实验里改用滚动触发——确认 LCP 仍在更新，点击才封盘。
7. **Lighthouse 交叉验证**：跑一次 Lighthouse，对照 FCP/LCP/CLS/TBT 数值与本册脚本输出（实验室口径 vs API 原始条目）。

## 8. 常见误区

1. **「LCP = 最大图片加载完」**：候选可以是文本块；网络图按到达字节渐进参与选美；元素删除不撤冠军——「图片」只是最常见的候选，不是定义。
2. **「CLS 是全生命周期累加」**：session window 下是「最糟 5 秒窗口」的分数——分散的小位移可能比集中的大位移总分更低。
3. **「用户滚动会封 LCP」**：滚动不算停止条件；click/tap/keydown 才算。
4. **「INP 只测回调执行」**：三段口径——输入延迟（等主线程）与呈现延迟（下一帧渲染）各占一段，只优化回调常治不好 INP。
5. **「动画导致 CLS」**：transform 动画免罚——布局属性（width/top）动画才触发位移扣分；这是改写动画的强动机。
6. **「TBT 好 INP 就好」**：TBT 只覆盖主线程阻塞风险，呈现延迟段不在其口径内；两者是相关非等价。
7. **「实验室分数等于线上表现」**：Lighthouse 是确定性单样本；线上看 p75 分布——机器/网络/用户行为差异让两套数据各管一段。

### 8.5 常见问答

**Q：为什么我的站点 LCP 在本地跑很快、CrUX 里很慢？**
三个口径差：①本地是实验室环境（快网/真机模拟、无并发），现场是真实用户分布（弱网、低端机占比可观）；②本地样本 1 次，现场 p75——你被分位线以上的一半用户「代表」；③本地跑分前常有缓存，现场用户大量冷启动。定位口径差异是优化前的第一课：先用现场数据的 p75 找最差群体（设备×网络维度），再回实验室复现那个群体的环境。

**Q：LCP 里 `entry.element` 是 `null` 是怎么回事？**
常见两种：①页面已转入后台/卸载，元素引用被释放；②脚本跨安全上下文（不同源 iframe 注入）无法拿到元素引用。前者换 buffered 前的实时 observer，后者查注入环境。另外注意 `entry.url` 对图片候选会给出图片 URL——元素拿不到时它是归因的备用线索。

**Q：CLS 很小但用户抱怨页面「跳」，是什么情况？**
查三处：①被 500ms 输入窗口豁免的位移（用户自己点击引发的展开不扣分，但视觉上确实在跳）；②`transform` 移动免罚（视觉在动但指标看不见）；③发生频率——session window 只计最糟 5 秒，分散的多次小跳不累加，但体感是「一直在跳」。指标的「最糟窗口」口径与用户的「全程感受」口径不同——这就是指标之外还要录屏走查的原因。

**Q：INP 的 200ms 是「每个交互都要达标」吗？**
不是——口径是每次页面访问取约第 98 百分位（实现上常取最差一次交互），站点层面再看 p75。所以「最差的 2% 交互」可以豁免；但反过来说，**只要你页面每次访问几乎都有一两个糟糕交互，p75 就会暴露它**——INP 对「偶发但普遍」的卡顿特别敏感，这也是它比均值类指标诚实的原因。
