# 从 URL 到首屏：全景时间线与耗时账本

> [← 第一阶段导览](01-导览.md) · 本册是全站的「总纲册」：后面 40 多册讲的每一段机制，都挂在这条 17 步主线上。
> 学法建议：本册第一遍只求「每一步知道发生了什么、谁干的、大概多久」；每个阶段学完回来重读对应小节并核账——同一小节，第一阶段读是简介，第三阶段读应该能讲出 RTT 和握手细节。

## 1. 为什么先建账本

「页面慢」是前端最模糊的描述，也是最多优化返工的源头——凭感觉优化的人，通常精修了时间线上最显眼的一段，而瓶颈其实在另一段。

一个真实形态的例子：某页面 TTFB 800ms，团队花两周把 SSR 计算从 600ms 压到 200ms，线上 LCP 却只降了 80ms。复盘发现弱网下真正的大头是：

- 连接建立（DNS + TCP + TLS）合计 ~400ms，SSR 根本不在主要矛盾上；
- HTML 下载后的关键 CSS 串行加载又吃掉 ~300ms；
- SSR 的 400ms 优化只占总时间线的一小段。

这些工作不是白做，但它证明了：**没有账本，优化的投入产出比是随机的**。

账本思维三个动作：

1. **拆段**：把「打开页面」拆成 17 步，每步有名字、有归属进程、有测量手段；
2. **记账**：对目标页面量出每段的毫秒数（第一版账本）；
3. **核账**：每次学完一个阶段、每次做完一个优化，重测一遍，看哪些段变了、哪些没变、为什么。

配套的三个纪律（贯穿全站）：

- **固定环境**：CPU 节流、网络节流、缓存状态不固定，前后对比就是编故事；
- **记原始凭证**：trace 文件与截图存 `labs/`，账本数字必须能回溯；
- **写差异原因**：复测时数字对不上，必须写「为什么」——这是最值钱的学习材料。

## 2. 17 步主时间线

```mermaid

  A[① 输入 URL] --> B[② 导航决策]
  B --> C[③ DNS]
  C --> D[④ TCP 握手]
  D --> E[⑤ TLS 握手]
  E --> F[⑥ 发送请求]
  F --> G[⑦ 服务端处理]
  G --> H[⑧ 响应回程]
  H --> I[⑨ 网络进程接收]
  I --> J[⑩ commit +<br>渲染进程就位]
  J --> K[⑪ HTML→DOM]
  K --> L[⑫ CSS→CSSOM]

  N --> O[⑮ 布局→分层→绘制<br>→栅格化→合成]
```

### 2.1 归属进程总表

先建立「归属进程」的总表——它决定了「慢了找谁」（进程架构详见下一册）：

| 步骤 | 归属 | 进程/场所 | 慢了先怀疑 |
|---|---|---|---|
| ① 输入 URL | 浏览器 UI | Browser 进程（UI 线程） | 几乎不慢；地址栏建议请求可抢连接 |
| ② 导航决策 | 浏览器内部 | Browser 进程 + SW 线程 | 捷径没命中（缓存配置错） |
| ③ DNS | 操作系统网络栈 | 本机缓存 → resolver → DNS 服务器 | 冷缓存、resolver 慢 |
| ④⑤ 连接建立 | 操作系统网络栈 | 内核 TCP/IP + TLS 库 | RTT 大、TLS 版本老 |
| ⑥ 发送请求 | 网络 | Network 进程 | 巨型 Cookie、拥塞窗口起步 |
| ⑦ 服务端处理 | **服务器** | CDN / 负载均衡 / 应用服务 | 未命中缓存回源、SSR 计算 |
| ⑧ 响应回程 | 网络 + 服务器 | 分块/压缩流回 | 体积、带宽 |
| ⑨ 接收 | 浏览器 | Network 进程 | 几乎不慢 |
| ⑩ commit | 浏览器 | Browser 进程 → 渲染进程 | 重定向链、进程冷启动（已预热） |
| ⑪~⑭ 解析构建 | 浏览器 | 渲染进程主线程 | HTML 体积、同步脚本、选择器 |
| ⑮ 渲染管线 | 浏览器 | 主线程 + 合成线程 + GPU 进程 | 节点数、层数、图片解码 |
| ⑯⑰ 上屏与交互 | 浏览器 + 屏幕 | 全链路结果 | 上面所有段的总和 |

### 2.2 谁支配谁：RTT 与计算的两分法

17 步的耗时来源只有两类：

- **RTT 支配段**（③~⑧）：每来一回网络都是 1 个 RTT。弱网 RTT≈100ms 时，这些段是「毫秒级 × RTT 个数」的结构——**减次数**比减单次耗时有效；
- **计算支配段**（⑪~⑮）：发生在本机 CPU。弱网本地同价——**减工作量**（体积/节点数/脚本量）才有效。

每个优化手法都应能回答「我在优化哪一类」：preconnect 减 RTT 次数、代码分割减计算量。两手都要，但要知道此刻的主矛盾在哪边。

## 3. 逐段走读

以下每段都是简介版（指向精修它的分册），每段固定四问：发生了什么 / 谁干的 / 典型耗时 / 哪里会出病。

### ① 输入 URL

**发生了什么**：地址栏接收输入，立即开始「这串字符是什么」的判定（URL？搜索词？书签匹配？），同时给出候选建议。此时尚无导航行为。

**谁干的**：Browser 进程 UI 线程，纯本地，几毫秒。

**哪里会出病**：几乎不慢，但地址栏建议体系（历史、书签、**搜索建议的网络请求**）可能已经悄悄发出第一批请求——它们与正式导航共享连接池与 DNS 缓存。

**怎么量**：几乎不需要量；排查「为什么没发请求」时先确认分类结果（地址栏下拉第一项是「搜索」还是 URL）。

→ 精修分册：[第二阶段 02-URL语法解析与地址栏决策](../02-第二阶段/02-URL语法解析与地址栏决策.md)

### ② 导航决策

**发生了什么**：回车按下，浏览器按顺序查四条「不发网络请求」的捷径：**BFCache → Service Worker → 内存缓存 → 磁盘缓存**；若都没有，检查 HSTS（http 是否强制升 https）、决定渲染进程策略。

**谁干的**：Browser 进程导航控制器；SW 命中时在 SW 线程。

**典型耗时**：决策本身 <5ms；**捷径命中则 ③~⑧ 全部消失**——全链路最便宜的加速。

**哪里会出病**：该命中的缓存没命中（响应头配置错）、BFCache 被第三方埋点的 `unload` 挡掉。

→ 精修分册：[第二阶段 03-导航决策链](../02-第二阶段/03-导航决策链-HSTS-ServiceWorker-缓存与BFCache.md)、[04-导航执行](../02-第二阶段/04-导航执行-跨进程流转与commit.md)

### ③ DNS 解析

**发生了什么**：把域名变成 IP。完整路径：浏览器缓存 → OS 缓存 → 本地 resolver（递归）→ 根 → TLD → 权威（迭代）。

**谁干的**：操作系统网络栈 + 本地 resolver。

**典型耗时**：缓存全空时弱网下几百毫秒级的大头；命中时趋近于零。**复用已有连接时此步完全跳过**——「为什么二次访问快」的第一层原因。

**哪里会出病**：CNAME 链串长、负缓存（NXDOMAIN 被缓存）、改记录后多层缓存延迟生效。

→ 精修分册：[第三阶段 02-DNS解析全链路](../03-第三阶段/02-DNS解析全链路.md)

### ④ TCP 握手

**发生了什么**：SYN → SYN+ACK → ACK 三次握手建立可靠管道，同时协商 MSS/窗口缩放/SACK 等选项。

**谁干的**：内核 TCP 栈，两端各一次状态迁移。

**典型耗时**：**一个完整 RTT 纯开销**，期间没有应用数据传输。弱网 ~100ms。TFO 可在这一步捎带数据但普及有限；HTTP/3 干脆把 ④⑤ 合并（见下）。

**哪里会出病**：半连接队列满（SYN 洪水防护态）、中间设备掐长连接。

→ 精修分册：[第三阶段 03-TCP](../03-第三阶段/03-TCP-三次握手与传输控制.md)

### ⑤ TLS 握手

**发生了什么**：协商密码套件、验证证书链、交换密钥材料。

**谁干的**：两端 TLS 库 + CA 信任链。

**典型耗时**：TLS 1.2 额外 2 个 RTT；**TLS 1.3 压到 1 个 RTT**；会话恢复（PSK）+ 0-RTT 可接近零额外开销。QUIC 把 ④⑤ 两步合并成 1 个 RTT。

**哪里会出病**：证书链缺中间证书、吊销查询慢、SNI 被中间设备干预。

→ 精修分册：[第三阶段 05-TLS](../03-第三阶段/05-TLS-从明文到加密信道.md)

### ⑥ 发送 HTTP 请求

**发生了什么**：请求报文（含 Cookie）写入连接，按**优先级**排队（CSS/JS 高、图片低）。

**谁干的**：Network 进程。

**典型耗时**：发送本身趋近于零；但受**拥塞控制初始窗口**影响——新连接 cwnd 小，大请求头（巨型 Cookie！）可能要多个包才能发完。

**哪里会出病**：h1 的 6 连接限制导致排队（Queueing 段长）、请求头超大。

→ 精修分册：[第四阶段导览](../04-第四阶段/01-导览.md)、[第六阶段 05-子资源调度](../06-第六阶段/05-子资源调度-预解析扫描器-优先级与资源hint.md)

### ⑦ 服务端处理

**发生了什么**：请求被 CDN 边缘命中（几毫秒）或回源穿过负载均衡 → 网关 → 应用服务 → 数据库，SSR 渲染出 HTML。

**谁干的**：**服务器**（本站唯一一段「不在你电脑上」的时间）。

**典型耗时**：10ms（静态命中）到数秒（复杂 SSR）——TTFB 最大的可变项。103 Early Hints 让服务端「边算边预告」关键资源。

**哪里会出病**：CDN 缓存键设计错导致命中率低、回源链长、数据库慢查询。

→ 精修分册：[第五阶段导览](../05-第五阶段/01-导览.md)

### ⑧ 响应回程

**发生了什么**：HTML 字节沿连接流回。压缩（gzip/brotli）在这里生效；流式 SSR 在这里**分块**下发。

**谁干的**：服务器 → 网络 → Network 进程。

**典型耗时**：体积/带宽 + RTT。**关键认知**：⑧ 和 ⑪ 是**重叠**的——浏览器边收边解析，Network 面板的蓝色 Download 段与 Performance 面板的 Parse HTML 段在时间轴上并排。

**哪里会出病**：没压缩、体积失控。

→ 精修分册：[第五阶段 05-响应回程-压缩-分块与连接复用](../05-第五阶段/05-响应回程-压缩-分块与连接复用.md)

### ⑨ 网络进程接收

**发生了什么**：检查 MIME（嗅探或信头）、跑跨域读阻断（CORB/ORB）、按响应类型决定交给谁——HTML 导航响应交给渲染进程。

**谁干的**：Network 进程。

**典型耗时**：<10ms。

**哪里会出病**：MIME 配错 + nosniff 触发拦截（页面直接废）、跨域资源被 ORB 剥掉 body。

→ 精修分册：[第六阶段 02-接收流水线](../06-第六阶段/02-网络进程接收流水线.md)、[03-HTTP缓存体系](../06-第六阶段/03-HTTP缓存体系全解.md)

### ⑩ commit + 渲染进程就位

**发生了什么**：响应头到达，Browser 进程选定渲染进程（复用或新建——Chrome 会**提前预热**进程），把导航「提交」给它。URL 栏更新、旧页面开始卸载、渲染进程准备接收数据流。

**谁干的**：Browser 进程 → 渲染进程。

**典型耗时**：进程已预热则 <10ms。

**哪里会出病**：重定向链（每跳一次 commit 未遂）、unload 里的同步逻辑拖慢卸载。

→ 精修分册：[第二阶段 04-导航执行](../02-第二阶段/04-导航执行-跨进程流转与commit.md)

### ⑪ HTML → DOM

**发生了什么**：渲染进程主线程把字节流**解码**（字节→字符，编码判定链）、喂给 HTML 解析器（分词 + 树构建），DOM 边收边长。**preload scanner** 与主解析器并行，把「还没解析到」的 CSS/JS/图片**提前预约下载**。

**谁干的**：渲染进程主线程（解析）+ Network 进程（并行下载）。

**典型耗时**：5~50ms（与 ⑧ 并行推进）。

**哪里会出病**：同步 `<script>` 把主解析器暂停（下载不停）、编码判定错（整页乱码）。

→ 精修分册：[第七阶段 03-HTML解析器](../07-第七阶段/03-HTML解析器-状态机-容错与DOM构建.md)、[第六阶段 05-预解析扫描器](../06-第六阶段/05-子资源调度-预解析扫描器-优先级与资源hint.md)

### ⑫ CSS → CSSOM

**发生了什么**：CSS 文件解析成 CSSOM。head 里的 CSS 是**渲染阻塞**的：CSSOM 没好，⑯ 不允许发生（防无样式闪烁）。

**谁干的**：渲染进程主线程。

**典型耗时**：解析本身 1~10ms；但「等 CSS 文件到」可能是 1 个 RTT/文件。

**哪里会出病**：`@import` 串行链、字体 FOIT、media 写错导致全量阻塞。

→ 精修分册：[第七阶段 04-CSS解析与CSSOM](../07-第七阶段/04-CSS解析与CSSOM.md)、第九阶段 02-关键渲染路径（待写）

### ⑬ JS 编译与执行

**发生了什么**：JS 文件下载完 → V8 编译（惰性：先字节码，热点再优化）→ 执行。同步脚本在此**阻塞 DOM 构建**；defer 排队到 DOM 就绪后；module 有依赖图。

**谁干的**：渲染进程主线程（V8），下载在 Network 进程已完成。

**典型耗时**：重前端应用常是几百毫秒级——它晚到一秒，可交互就晚一秒。

**哪里会出病**：巨型 bundle、长任务、同步第三方脚本。

→ 精修分册：[第七阶段 06-V8](../07-第七阶段/06-V8执行模型-从源码到优化机器码.md)、[07-事件循环](../07-第七阶段/07-事件循环与任务调度-渲染在哪里发生.md)

### ⑭ Style 计算

**发生了什么**：DOM × CSSOM → 每个节点的 ComputedStyle：选择器匹配（右到左）、级联裁决、继承填充。

**谁干的**：渲染进程主线程。

**典型耗时**：1~10ms（有规则分桶、祖先过滤器、样式共享等工程优化兜底）。

**哪里会出病**：病态选择器、超大规模 DOM、强制同步布局的第一现场。

→ 精修分册：[第七阶段 05-样式计算](../07-第七阶段/05-样式计算-级联-匹配与ComputedStyle.md)

### ⑮ 渲染管线

**发生了什么**：ComputedStyle → 布局（盒与几何）→ 分层与绘制指令（display list）→ 栅格化（指令→瓦片位图）→ 合成（位图拼装成帧）→ 提交 GPU 上屏。

**谁干的**：渲染进程主线程（布局/绘制记录）+ 合成线程（合成）+ Raster 线程 + GPU 进程。

**典型耗时**：5~50ms（首遍）；受 vsync 节拍（16.6ms 预算）约束。

**哪里会出病**：强制同步布局、层爆炸、大图解码。

→ 精修分册：[第八阶段导览](../08-第八阶段/01-导览.md)

### ⑯ 首帧上屏

**发生了什么**：管线第一遍跑完、合成帧上屏的瞬间是 FCP；最大内容元素（LCP 候选）上屏是 LCP。

**谁干的**：全链路结果。

**怎么想**：指标是**结果**，账本 ①~⑮ 是**原因**——优化指标 = 优化它上游的某几段。

→ 精修分册：第九阶段 03-指标深潜（待写）

### ⑰ 持续交互

**发生了什么**：用户点击/滚动 → 合成器先接住输入（滚动不需要主线程）→ hit test → 事件路由到主线程 → 回调执行 → 改了什么就重跑 ⑭/⑮ 的对应部分（失效传播）→ 下一帧。

**谁干的**：合成线程（输入预接 + 滚动）→ 主线程（回调）→ 再回合成线程。

**典型耗时**：单帧预算 16.6ms（60Hz）/ 8.3ms（120Hz）。

**哪里会出病**：长任务、布局抖动、滚动阻塞事件。

→ 精修分册：第九阶段 05-输入事件链路（待写）

## 4. 耗时量级表：两套环境

> 下表是**量级参考**（典型值），不是保证值。你的账本必须自己量——量法见第 5 节。带宽按 4G ≈ 10Mbps / RTT ≈ 100ms 估。

| # | 阶段 | 本地回环（RTT<1ms） | 4G 弱网（RTT≈100ms） | 主要变量 | 怎么量 |
|---|---|---|---|---|---|
| ①② | 输入+导航决策 | <5ms | <5ms（决策本身） | BFCache/SW 命中则后面全消 | Performance 面板起点 |
| ③ | DNS | <1ms | 50~300ms（冷）/ 0（热） | 缓存层级、resolver | Network Timing 段 |
| ④ | TCP 握手 | <1ms | ≈1 RTT（~100ms） | RTT、TFO | Network Timing 段 |
| ⑤ | TLS 握手 | <2ms | 1~2 RTT（100~200ms）/ 0（0-RTT） | 版本、会话恢复 | Network Timing 段 |
| ⑥ | 发送请求 | ~0 | 0~1 RTT（大头 Cookie） | 请求头体积、拥塞窗口 | 极少单独可见 |
| ⑦ | 服务端处理 | 5~600ms | 同左（不含网络） | CDN 命中/回源、SSR 计算 | TTFB 减去连接段 |
| ⑧ | HTML 回程 | ~0 | 50~200ms（20~50KB HTML） | 体积、带宽、压缩 | Content Download 段 |
| ⑨⑩ | 接收+commit | <5ms | <10ms | 进程复用与否 | 几乎不可见 |
| ⑪ | HTML→DOM | 5~50ms | 同左（与⑧并行） | HTML 体积、脚本阻塞 | Main 轨道 Parse HTML |
| ⑫ | CSS→CSSOM | 1~10ms | 1 个 RTT/文件（若未预载） | 文件数、@import、阻塞规则 | Recalculate Style 前 |
| ⑬ | JS 编译执行 | 50~500ms+ | 同左 + 下载 RTT | bundle 体积、同步/defer | Main 轨道 Script 段 |
| ⑭ | Style 计算 | 1~10ms | 同左 | 节点数、选择器病态度 | Recalculate Style 段 |
| ⑮ | 渲染管线首遍 | 5~50ms | 同左 | 节点数、层数、图片解码 | Layout/Paint/Raster 段 |
| ⑯ | 首帧上屏 | ≈1 帧（16.6ms） | 同左（但受 vsync 对齐） | 上面所有段的总和 | FCP/LCP 标记 |
| ⑰ | 交互响应 | 视实现 | 视实现 | 长任务、失效范围 | INP / Events 轨道 |

### 4.1 读表三结论（背下来）

1. **弱网的大头在网络段（③~⑧）**：连接建立 ≈300ms + TTFB 数百 ms——preconnect / CDN / 缓存 / 0-RTT 这些「网络手法」在弱网收益最大；
2. **本地的大头在计算段（⑬⑪⑮）**：JS 执行和渲染管线——代码分割 / 懒加载 / 减少失效这些「主线程手法」在重应用上收益最大；
3. **优化前先问环境**：同一个手法在两套环境下的收益可以差一个数量级。你的用户在哪种环境？答案在真实用户数据里（field 数据，第九阶段衔接）。

### 4.2 一份样例账本（Fast 4G 节流，虚构但量级真实）

给一个「SSR 商城首页」量出来的账本长这样（下一册教你量的方法）：

| 段 | 实测 | 归因备注 |
|---|---|---|
| ③ DNS | 180ms | 全冷；主域 + 2 个第三方域各查一次 |
| ④ TCP | 110ms | ≈1 RTT |
| ⑤ TLS | 105ms | TLS 1.3（1 RTT），无会话恢复 |
| ⑦ 服务端 | 420ms | CDN MISS 回源 + SSR 计算 |
| ⑧ HTML 回程 | 90ms | 45KB 压缩后 |
| ⑬ JS 执行 | 610ms | 主 bundle 380KB（未分割） |
| ⑮ 渲染管线 | 45ms | 图片解码占一半 |
| **LCP** | **1.62s** | 首图晚于文字（未 preload） |

一眼可见的三个候选刀口：DNS（180ms，可 preconnect）、JS 执行（610ms，可分割/延迟）、LCP 图（可 preload）——**先量后刀，刀刀有据**。

### 5.2 操作流程（固定套路，别每次即兴）

1. DevTools → Network + Performance 同时开，Network 勾 Disable cache（冷启动量测时）；
2. Performance 设置里固定 CPU 4x slowdown + Fast 4G（除非量本地环境）；
3. 刷新录制一次完整加载，先看 Timings 轨道的 DCL/FCP/LCP 三个竖线，再看 Main 轨道从左到右的分段；
4. Network 面板点开 HTML 主文档，把 Timing 标签的各段抄进账本——这就是 ③~⑧ 的实测值；
5. 保存 trace 文件到 `labs/`（文件名带日期与环境），这是你复测对比的原始凭证。

每学完一个阶段，重测一次目标页面，并在账本备注里写「本阶段学到的东西解释了哪一段」：

## 6. 常见误区

1. **「Network 面板的瀑布就是加载」**：瀑布只覆盖网络段。⑪~⑯ 的计算在 Performance 面板里——只看 Network 会把「HTML 早就到了但白屏两秒」的页面判成「网络没问题」。
2. **拿本地环境断言线上性能**：本地 RTT<1ms，网络段趋近零，怎么优化 TTFB 都「没收益」。开发机结论必须用节流复测。
3. **平均值陷阱**：TTFB 平均 300ms 可能是 90% 请求 100ms + 10% 请求 2s——分位数（p75/p95）才是用户感知（第九阶段展开）。
4. **把「压缩后体积」当「传输耗时」**：弱网下传输时间 = 体积/带宽，但首字节前还有连接与排队——体积优化救不了 TTFB。
5. **忽视 ② 的短路效应**：量出来的「二次访问 200ms」多半是缓存捷径命中，和首访 2s 根本不是同一本账——对比实验必须固定缓存状态。
6. **账本只记一次**：不同网络环境、不同缓存状态下的账本是**不同的本子**；混用一本账得出的结论必然打架。

## 7. 自测题

1. 默写 17 步主时间线，并给每步标注归属进程。
