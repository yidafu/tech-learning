# 布局：盒模型、格式化上下文与布局抖动

> [← 第八阶段导览](01-导览.md) · 时间线 ⑮。LayoutObject 树搭好了（02 册），这一册讲几何怎么算出来：盒模型与 containing block 是计算的地基，BFC/IFC 是块级与行内布局的规则手册，Flex/Grid 是现代主力算法的骨架。最后落到本阶段最著名的性能病灶——**layout thrashing（布局抖动）**：读-写交错的 JS 怎么把布局引擎按在地上摩擦，以及三种标准治理手段。

## 1. 布局做什么：输入、输出与 containing block

布局是自上而下的递归几何计算：

```text
输入：盒子的 ComputedStyle（07 阶段 05 册产出）
      + containing block（由谁、按哪个盒提供可用空间）
输出：fragment 树（02 册）——每个盒的位置与尺寸
```

**containing block（包含块）**决定「我的尺寸百分比相对谁、我的 absolute 定位相对谁」——它由 `position` 决定，规则全表：

| 元素的 position | containing block 是 |
|---|---|
| static / relative / sticky | 最近的**块容器**祖先的内容盒 |
| absolute | 最近的 **positioned**（非 static）祖先的 padding 盒 |
| fixed | 视口（viewport）——**除非**某个祖先有 transform/perspective/filter/will-change:transform/backdrop-filter/contain:paint，则改为该祖先 |
| （浮动元素内容） | 浮动元素自身的内容盒 |

fixed 那一行的例外是高频坑：**给祖先加 transform，里面的 position:fixed 元素立刻改认新爹**——「弹层fixed定位怎么突然跟着滚动跑了」的经典病根。sticky 介于两者之间：相对最近滚动祖先（scrollport）吸附。

### 1.5 盒模型与 box-sizing

| box-sizing | width 指的是 | 实际占宽公式 |
|---|---|---|
| content-box（默认） | 内容宽 | width + padding + border（+ margin 占位） |
| border-box | 边框盒宽 | padding/border 向内吃，width 是总宽 |

布局引擎内始终按 content-box 的思路算（先求 content 尺寸），box-sizing 只是样式层的「口径」声明。工程约定几乎一致：全局 `* { box-sizing: border-box }`——尺寸直觉与代码一致，代价是覆盖原生组件默认值时要留意。

盒子从外到内的五个区（margin/border/padding/content）里，布局阶段关心**前四个的几何**，绘制阶段关心边框/背景/阴影怎么画（05 册）。

## 2. 盒的生成：display 决定参与哪套规则

`display` 是双关键字属性（outer: 参与外部排布的方式；inner: 内部用什么格式化上下文）：

| display | 盒类型 | 参与 | 自己是 FC 吗 |
|---|---|---|---|
| block | 块级盒 | 外部 BFC 的成员 | 是（块容器，建 BFC 当条件满足，§3） |
| inline | 行内盒 | 外部 IFC 的成员 | 否（不建 BFC） |
| inline-block | 行内级块容器 | 外部 IFC 成员、内部 BFC | 是（内部建 BFC） |
| flex / inline-flex | 弹性容器 | 外部 BFC/IFC 成员 | 是（建 **FFC**） |
| grid / inline-grid | 网格容器 | 同上 | 是（建 **GFC**） |
| table 系 | 表格盒族 | 表格布局 | 是（匿名盒修补，02 册） |
| flow-root | 块级 | 外部 BFC 成员 | **是（显式建 BFC）** |

「flex/grid 的子项 margin 不合并」「overflow:hidden 管不住 flex 容器的溢出」这类诡异现象，答案都在「它是什么盒、属于谁的 FC、自己建了什么 FC」这条链上。

## 3. BFC：块级格式化上下文

BFC 是一块「独立王国」：内部按块级规则排布，且与外部的排布互相隔离。**创建条件**（工程归纳表，`display:flow-root` 是显式创建的现代正解）：

| # | 创建者 | 例 |
|---|---|---|
| 1 | 根元素 | `<html>` |
| 2 | 浮动元素 | `float: left/right` |
| 3 | 绝对定位元素 | `position: absolute/fixed` |
| 4 | 非块盒的块容器 | `inline-block`、`table-cell`、`table-caption` |
| 5 | overflow 非 visible 的块盒 | `overflow: hidden/scroll/auto` |
| 6 | **display: flow-root** | 显式创建，无副作用 |
| 7 | 弹性/网格容器的**子项** | flex/grid item 天然独立 FC |
| 8 | contain 特定值 | `contain: layout/content/paint` |
| 9 | 多列容器与其内部 | columns |

**BFC 的布局规则**（经典四条，逐条配工程场景）：

| # | 规则 | 工程场景 |
|---|---|---|
| 1 | 内部的盒垂直方向依次排列，同一 BFC 内相邻块盒的 margin 合并 | §3.5 全解 |
| 2 | BFC 区域**不与浮动重叠** | 经典两栏布局：主栏建 BFC 后不再绕排文字 |
| 3 | 计算 BFC 高度时，**内部浮动子元素参与** | 现代清浮动：flow-root 替代 clearfix hack |
| 4 | BFC 是隔离容器：内外互不影响（子元素的浮动/边距不外泄） | 防止子树布局扰动外部 |

注意第 2 条的精确语义：**是 BFC 的区域不与浮动重叠，不是「子元素不绕排」**——BFC 根元素自身右移避开浮动，其内部的行内内容（文字）依然绕排。两栏布局「主栏 `overflow:hidden` 后文字不绕排了」的真正机制：主栏整体让位给浮动了。想不绕排、还不想 overflow:hidden 的裁剪副作用？`display:flow-root` 或干脆 Grid/Flex。

### 3.5 margin 合并全解

块方向上，相邻的垂直 margin 会「叠」成一个——**只在同一个 BFC 内的块级盒之间发生**。三个发生场景：

| 场景 | 例 | 结果 |
|---|---|---|
| 相邻兄弟之间 | A 的 margin-bottom 20px + B 的 margin-top 30px | 间距 = **30px**（取大者） |
| 父块与第一个/最后一个子块之间 | 父无 border/padding/行内内容/BFC 隔离时 | **子 margin「穿透」到父外面**（最反直觉） |
| 空块盒自身 | 高度为 0 的块，上 margin 20 下 margin 30 | 自身上下合并为一个 30px |

负值算法：正负相加取和；都是负数取绝对值最大者。混合时取「最大正值 + 最小负值」之和。

**「穿透」案例与两种修复**：

```html
<style>
  .outer { background: #eee; }
  /* .inner 的 margin-top: 40px 会顶穿 .outer —— .outer 被「顶」着往下挪 40px，
     且 .outer 内部看，子元素仍贴着顶 */
</style>
<div class="outer">
  <div class="inner">margin-top: 40px</div>
</div>
```

```text
修复 A：给 .outer 加 display:flow-root   —— 建 BFC，隔离成立，40px 收进父内
修复 B：给 .outer 加 padding-top: 1px（或 border-top） —— 有物理隔离，父子 margin 不再相邻
```

**不合并**的完整排除表（每个条件都值得记，反着用就是「想合并时的检查单」）：

| 不合并条件 | 例 |
|---|---|
| 任何一方是 BFC 的「成员之外」 | float、absolute/fixed、inline-block |
| flex/grid 容器的子项之间 | **flex/grid 永不合并 margin** |
| 父子之间隔着 border/padding/行内内容 | §3.5 修复 B |
| 隔着 BFC 边界（flow-root 等） | §3.5 修复 A |
| 水平方向 | 块方向（垂直）才合并，IFC 不合并 |
| clear 的元素 | 与下一个元素的 margin 被压制 |

## 4. IFC：行内格式化上下文

行内布局是「一条条行盒（line box）」的堆叠，四个核心概念：

| 概念 | 是什么 |
|---|---|
| 行盒 | 一行内容的容器：横向铺开、纵向按对齐规则定高 |
| strut | 每个行盒自带的「隐形基准行内盒」——即使整行是 img，也有 strut 决定基线与最小行高 |
| 基线（baseline） | 对齐的原点：文本以字体基线为准，**替换元素（img）以自身下 margin 边为准**，inline-block 无内容时取 margin-box 底边 |
| vertical-align | 行内盒相对行盒基线/行高的对齐方式（top/bottom/middle/baseline/sub/super/长度） |

**经典案例：img 底部多出的几像素空隙**。机制：img 是替换元素，默认 `vertical-align: baseline`，把自己下边缘对齐到行盒基线；基线下方还有 strut 的下行区（descender）——空隙就是 descender 区。三种修复任选：

```css
img { vertical-align: top; }    /* 或 middle/bottom：脱离基线对齐 */
img { display: block; }         /* 退出 IFC，参与块排布 */
父 { line-height: 0; }          /* 把 strut 压扁 */
```

行高的继承陷阱顺带记一笔：line-height 是**可继承**属性且常写无单位数字（因子继承）——「父 16px 字号写 line-height:1.5，子 32px 字号行高应为 48px；写成 24px 则子行高恒 24px 挤压文字」。写无单位是硬约定。

## 5. Flex 与 Grid：算法概览

现代布局两大主力，各记「算法骨架」而不是属性手册。

### 5.1 Flex：两阶段求解

```text
阶段一：收集 flex line（行/列收集，wrap 与否决定几条线）
阶段一：确定各 item 的 flex base size（flex-basis 起步）
阶段二：弹性长度求解——剩余空间按 grow 分 / 超出空间按 shrink 收
        （求解时受 min/max-width 钳制，钳制失败会再分配一轮）
最后：  主轴对齐（justify-content）→ 交叉轴对齐（align-items/self/content）
```

必记的陷阱：**flex item 的自动最小尺寸（min-width/height: auto）**——默认最小尺寸 = min-content，内容再长也收缩不下去。「flex 子项被长文本撑爆、overflow:hidden 也没用」的标准修复：

```css
.item { min-width: 0; }   /* 放开自动最小尺寸，配合 overflow:hidden/ellipsis 生效 */
```

### 5.2 Grid：轨道尺寸求解

| 步骤 | 在做什么 |
|---|---|
| 放置 | 按文档序/显式坐标放 item，auto-placement 补位 |
| 轨道基尺寸 | minmax(min, max) 的 min/max 各自求解（auto = min-content/max-content 参与） |
| fr 分配 | 剩余空间按 fr 比例分，跨轨道 item 的影响先算（span 大的先撑） |
| 对齐 | justify/align-content/items/self |

Grid 的成本敏感点：**跨行/跨列的 item 与大量 auto/min-content 尺寸**会让轨道求解变成多轮迭代（示意）；auto-placement 在大网格上也有可感知成本。性能纪律：显式坐标 > auto 放置；固定轨道 > 全 auto 轨道（固定值可直接查表，免求解）。

### 5.3 各布局方式的成本量级（示意归纳，非实测承诺）

| 方式 | 布局成本特征 | 备注 |
|---|---|---|
| 块流（block） | 最便宜：单遍自上而下 | 默认首选 |
| IFC 行内 | 中等：与文本量线性相关 | 字体度量是大头 |
| Flex | 中等：两阶段 + 钳制重解 | NG 后与旧实现比显著变好（量级示意） |
| Grid | 中偏高：轨道求解可迭代 | 跨项/auto 尺寸多时上升 |
| Table 系 | 高：匿名盒修补 + 双遍 | 非表格数据别用 |

与 `gui/` 站的对照：自绘框架的布局器同样面临「两遍求解、钳制重解」的问题，浏览器把这套算法做成了规范化的工业实现——框架侧的布局约束系统（如 Flutter 的 constraint 下行/size 上行）是同一思想的另一种表达。

## 6. 脏标记、局部布局与强制同步布局

改了一个节点的样式，**不是全页重排**：

```text
改某节点盒模型属性
  → 该节点记「脏」（self-dirty / children-dirty）
  → 脏位沿祖先传播到「布局根」（通常是不被外部约束的最近子树根）
  → 下一次统一布局：只从布局根重算子树，未脏子树沿用旧 fragment（02 册 LayoutNG）
```

看起来很美好，直到 JS 在中间插了一脚。**强制同步布局（forced synchronous layout）**的机制：

```text
正常时序：JS 全跑完 → 渲染阶段统一算布局（一次）
强制时序：JS 读几何 API → 发现布局脏 → 「现在就算」→ 返回值
```

会触发强制布局的读 API 清单（写代码时对照自查）：

| 家族 | API |
|---|---|
| offset | offsetTop / offsetLeft / offsetWidth / offsetHeight / offsetParent |
| client | clientTop / clientLeft / clientWidth / clientHeight |
| scroll | scrollTop / scrollLeft / scrollWidth / scrollHeight |
| 几何 | **getBoundingClientRect()** / getClientRects() |
| 样式 | getComputedStyle() 的部分属性（padding/margin/width 等布局值） |
| 其他 | scrollIntoView / focus（可能滚动）/ window.scrollX 等滚动量 |

### 6.5 layout thrashing：读-写交错的循环

```js
// 反面教材：每轮循环「读 → 改」，读被迫清上一轮的写 → 每轮一次强制布局
items.forEach(el => {
  const top = el.offsetTop;        // 强制布局（上一轮的写入还没结算）
  el.style.top = top + dy + 'px';  // 记布局脏
});
// N 个元素 = N 次强制布局 —— trace 上的紫色 Layout 锯齿
```

Performance 面板的指纹：**Main 轨道一个 Task 里 Script 与紫色 Layout 交替出现锯齿**；Bottom-Up 视图按 Self Time 排序能看到 Layout 被反复调用。现代 DevTools 的 Performance 面板还会把这类调用标记为 forced reflow（Issue 提示）。

**三种治理手段**（导览阶段目标里的「三板斧」）：

| 手段 | 做法 | 原理 |
|---|---|---|
| **批量读写分离** | 先循环读全部 → 再循环写全部 | 布局只在读批末尾强制一次（N 次 → 1 次） |
| **transform 替代几何属性** | 动画/位移用 transform，别用 top/left/width | transform 不进布局（07 册分诊表），直接降级失效类型 |
| **contain 隔离** | `contain: layout/paint/content` 标注自包含子树 | 布局根上移受阻 → 失效范围被钉死在容器内（09 阶段 06 册与 content-visibility 配套） |

框架级方案：FastDOM 类库（把读写排进两个队列，rAF 结算）、rAF 批处理（所有 DOM 写集中在同一帧回调）。本质都是同一个原则：**读与写的时间上分离**，让引擎有机会把多次布局合并成一次。

## 7. 实验

1. **thrashing 复现与修复对比**：写 200 个列表项的 §6.5 反面教材，Performance 录制点击按钮后 1 秒，数 Main 轨道里 Layout 块的个数；改造成「先读后写」两段式再录——Layout 块应从 N 个变 1 个（量级示意，以你的机器为准）。
2. **margin 合并三场景复现**：兄弟合并（取大者）、父子穿透（§3.5 代码）、空块盒自并——各写一个最小 demo，用 DevTools 盒模型面板读 margin 实际生效值。
3. **flow-root 修复对照**：给穿透案例父级加 `display:flow-root`，对比修复前后 `getBoundingClientRect().top`；再加 `overflow:hidden` 版本对比——若子元素有溢出内容，两者的差异立刻可见（hidden 裁剪、flow-root 不裁剪）。
4. **flex 最小尺寸陷阱**：flex 容器里放超长英文串子项，观察收缩失败；加 `min-width:0` 后对比。再试 `overflow:hidden` 单独加与不加 min-width:0 的差别（不放开最小尺寸时 hidden 也无效——因为最小尺寸钳制在先）。
5. **img 底部空隙**：图片容器包一层 div 观察底部空隙，依次试 `vertical-align:top`、`display:block`、父级 `line-height:0` 三种修复，理解各自走的机制（§4）。
6. **containing block 陷阱**：外层 `position:fixed` 全屏弹层内放一个 `position:fixed` 的关闭按钮，给外层加 `transform: translateZ(0)`——按钮的定位基准从视口变成外层，滚动页面对比两者的行为。
7. **line-height 继承对比**：父级 16px 字号分别写 `line-height:1.5` 与 `line-height:24px`，子级 32px 字号的行高一个 48px、一个恒 24px——无单位与带单位继承的差异一眼可见（§4 末段机制的对照实验）。

## 8. 常见误区

1. **「margin 合并是浏览器的 bug」**：规范行为（CSS2.2 §8.3.1），语义是「段落间距取大不叠加」。不想要就改格式化上下文（flow-root/flex/grid 子项天然不合并），而不是逐处 margin 拆东墙。
2. **「overflow:hidden 能清浮动、能包住一切」**：hidden 建 BFC 是真的，但它同时是裁剪器与滚动容器语义的近亲——副作用是溢出内容被裁、且在部分场景阻止 sticky 生效。现代清浮动用 flow-root。
3. **「BFC 是万能药」**：BFC 只管块级排布的四条规则；flex 布局问题、层叠问题、绘制问题分别归 FFC、stacking context（04 册）、PaintLayer——先问「这是哪一层的问题」，再找哪把钥匙。
4. **「布局 = 全页重排」**：脏标记 + 布局根让重排通常是子树级；只有布局根一路脏到根（如改根字号、媒体查询）才接近全量。thrashing 的代价不在于「全页」，在于**每帧 N 次**。
5. **「getComputedStyle 返回实时计算值，随时读都便宜」**：它保证返回「最新」值——布局脏时最新值需要先强制布局。读样式不贵，读**布局类**样式才贵。
6. **「用 top/left 动画只是慢一点」**：不是慢一点，是失效类型高一级：每帧 layout + paint（07 册分诊表），对比 transform 的 composite-only，是跨量级的差。
7. **「加了 contain:layout 就不会再抖」**：contain 钉住的是失效**范围**；thrashing 的主病灶是**频率**（每轮读写各一次）。两者配合用，但治理频率（批量读写）永远是第一步。
8. **「flex 布局总是比 float 快」**：没有免费的午餐——flex 的两阶段求解 + min/max 钳制在深嵌套下的成本可观（量级示意）。性能上真正的分界线是「失效范围与频率」，不是「用哪种布局」。

### 8.5 常见问答

**Q：requestAnimationFrame 里改样式，同一帧会布局几次？**
一次。rAF 回调跑完才进入渲染阶段（style → layout → paint），回调里不管读写怎么交错，布局都在回调**结束后**统一结算——除非回调中途读了几何 API。所以「把写挪进 rAF」只解决「多帧多次」的问题，「一帧内读-写交错」仍要在回调里手动批量分离。

**Q：改字号、改窗口大小这类「全量布局」能避免吗？**
触发范围由「改的东西影响谁」决定，不太能避免，但可以**限流**：resize 事件节流、根字号改动合并到低频路径、媒体查询断点减少。另外 CSS `size` containment 与 content-visibility（09 阶段 06 册）能把「外部尺寸变化」对子树的影响隔离——全量变局部的最后一块拼图。

**Q：怎么快速判断一段代码的布局是「全页」还是「子树」？**
Performance 里放大 Layout 事件看详情：布局对象数量级与页面总盒数对比即可判断。经验法则：改的是盒模型/字号等「几何输入」→ 看它沿树向上的约束关系；只改颜色/背景/阴影 → 根本不进布局（07 册分诊表）。
