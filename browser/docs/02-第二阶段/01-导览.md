## 阶段目标

学完本阶段，你应该能不查资料做到这些事：

1. 给出 URL 的完整结构（scheme://host:port/path?query#fragment），说清每段的编码规则与规范化动作（大写化 host、去默认端口、路径点号消解）。
2. 解释浏览器如何判断地址栏输入是「URL 还是搜索词」（有无 scheme、有无空格、有无点号、内建列表）。
3. 列出「命中即不发网络请求」的四条捷径，并说出各自的判定顺序：BFCache、Service Worker、HTTP 内存缓存、磁盘缓存。
4. 说出至少五个 BFCache 的「拦路虎」（unload/beforeunload 监听、Cache-Control: no-store、WebSocket 未关、opener 引用等），以及为什么它们会挡住 BFCache。
5. 描述一次导航在进程间的完整流转，并解释「commit」为什么发生在响应头到达而不是响应体下载完成。
6. 解释 OOPIF：为什么跨站 iframe 必须独立进程，它给 hit test、滚动、合成各带来什么影响。

## 知识点地图

### 1. URL 解析（02 册）

- **URL 不是字符串是结构**：解析产物是一组字段（scheme、host、port、path、query、fragment），各字段有各自的字符集与编码规则；「输入 `标.例` 会被当成什么」取决于每家浏览器的判定启发式。
- **Punycode 与同形异义字攻击**：`中文.com` 在网络上传输的是 `xn--...`；URL 显示端的防钓鱼策略（显示 punycode 还是Unicode）是安全与可用性的折中。
- **规范化**：`HTTP://EXAMPLE.com:443/a/../b` → `https://example.com/b`，每一步发生在哪一层（地址栏补全 / 导航时 / 请求时）。

### 2. 导航决策链（03 册）

- **决策顺序**（命中即停）：BFCache →（无缓存可复用时）Service Worker `fetch` 事件 → 内存缓存 → 磁盘缓存 → 真正的网络请求。
- **HSTS**：一次 `Strict-Transport-Security` 响应头会把「该域强制 https」写进本地列表（还有一份全浏览器共享的 preload 列表），之后 http:// 请求在发出去之前就被本地 307 重定向。
- **BFCache 拦路虎为什么存在**：unload 里可能有关闭连接/清状态的代码、opener 引用可能被页面改动、no-store 意味着「恢复的页面可能与服务器状态不一致」——每一条都是「恢复后的页面可能说谎」，浏览器宁可不缓存。

### 3. 导航执行与 commit（04 册）

- **三段式流转**：UI 进程（用户输入）→ Browser 进程（导航发起）→ Network 进程（真实请求）→ 响应头到达 → Browser 进程决定渲染进程（复用或新建）→ **commit**（渲染进程开始接收数据）→ 响应体流式交付。
- **commit 的意义**：在 commit 之前浏览器还在「旧页面」上；commit 之后 URL 栏更新、旧页面卸载开始。这就是为什么慢服务器的白屏期其实是「旧页面还在 + 等响应头」。
- **进程复用规则**：same-site 导航倾向复用渲染进程，跨站必须新建——这既是 site isolation 的要求，也解释了为什么有些跳转明显比别的跳转「顿一下」。

### 4. 站点隔离与 OOPIF（05 册）

- **frame tree**：页面是主 frame + N 个子 frame 的树；site isolation 后，树上的每个节点可能住在不同进程里。
- **OOPIF（out-of-process iframe）**：跨站 iframe 独立进程后，主页面与 iframe 之间的每次交互（事件路由、滚动嵌套、hit test）都变成跨进程通信——这是很多「iframe 里滚动卡」问题的根源。

## 实践任务

1. 在地址栏分别输入 `localhost`、`localhost:3000`、`hello world`、`a.b`、`1+1`，观察哪些被当 URL、哪些被当搜索，对照 02 册的判定规则。
2. 构造一个命中 BFCache 的场景（跳走 → 后退）与一个被 `Cache-Control: no-store` 挡掉的场景，用 Network 面板对比：前者零请求、后者重新请求。
3. 给页面加 `unload` 监听，用 Chrome DevTools 的 Back/forward cache 面板看它怎么被挡。
4. 写一个页面嵌跨站 iframe（比如 youtube embed），在 `chrome://process-internals/` 找到它的独立进程；再观察主页面滚动时 iframe 的表现。

## 自测题

1. `example.com:443/path` 和 `https://example.com/path` 在浏览器眼里是同一个 URL 吗？规范化发生在哪一步？
2. 为什么 `<meta charset>` 必须写在前 1024 字节内才能生效——这个问题和本阶段的哪个环节有关？（本阶段先留个钩子，第七阶段揭晓）
3. 用户在 http:// 版本的站点上点了一个链接，但站点发过 HSTS 头，请求最终以什么协议发出？这个重定向会出现在 Network 面板里吗？
4. Service Worker 的 scope 是 `/app/`，导航到 `/app/page2` 会命中 SW 吗？导航到 `/` 呢？
5. `beforeunload` 和 `unload` 都会挡 BFCache，但为什么 Safari 后来对 beforeunload 的处理和 Chrome 不一样了？
6. 「响应头到达才 commit」对用户体验意味着什么？如果 TTFB 是 3 秒，这 3 秒里用户看到的是什么？地址栏是什么状态？
7. 同一个站点的两个标签页会共享渲染进程吗？为什么「共享进程」在 site isolation 时代被大幅收紧了？
8. 跨站 iframe 里的一个按钮被点击，事件从合成器到 iframe 的处理函数之间要跨几次进程边界？
9. 为什么 BFCache 恢复的页面不会触发 load 事件，而会触发 pageshow？
10. 回顾第一阶段的时间线账本：本阶段的四册分别精修了账本的哪几段？如果 BFCache 命中，整本账本还剩几段？
