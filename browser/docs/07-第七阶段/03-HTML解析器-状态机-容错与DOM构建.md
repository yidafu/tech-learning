# HTML 解析器：状态机、容错与 DOM 构建

> [← 第七阶段导览](01-导览.md) · 时间线 ⑪。上一册把字节变成字符流，这一册看字符流怎么变成 DOM 树。HTML 解析是全站「解析与构建」阶段的第一主角：它是一个**双层结构**——分词状态机吐 token、树构建器把 token 装进树——而且它的每一处「容错」都是 WHATWG 规范白纸黑字规定的确定性算法，不是浏览器随手补救。读完这一册，「这段烂 HTML 各浏览器解析出什么」对你不再是玄学。

## 1. 总览：双层结构与「规范即容错」

HTML 解析器（HTML Standard 的 parsing 算法）由两个交替工作的部件组成：

```text
字符流 ──► 分词器（tokenizer，一台状态机）── token ──► 树构建器（tree construction）
   ▲                                                            │
   └────────── 树构建器可以「喂回」字符（如 script 内容的重新分词）◄─┘
```

| 部件 | 职责 | 关键机制 |
|---|---|---|
| 分词器 | 字符 → token（开始标签/结束标签/文本/注释/DOCTYPE） | 状态机 + 当前标签的临时缓冲 |
| 树构建器 | token → DOM 节点 → 挂树 | 插入模式（insertion mode）+ 开放元素栈 |

为什么容错必须写进规范？历史原因：浏览器大战年代各家对烂 HTML 的补救各自为政，网页依赖这些补救后，**补救行为本身成了兼容性需求**。WHATWG 的做法是把全部补救标准化——`<b><i></b></i>` 最终 DOM 长什么样、`<table>` 缺 `<tbody>` 补不补，各浏览器**必然一致**。这就是「规范即容错」：容错不是「尽量兜住」，是确定性算法。

## 2. 分词状态机走读

分词器是一台显式状态机，规范里定义了几十个小状态。主干一条线：

```text
Data 状态（普通文本）
  │ 遇到 <
  ▼
Tag open ──字母──► Tag name ──空白──► Before attribute name ─┐
  │                            │                             │ 属性名/=/值循环
  │ ! → Markup declaration     └─/ → Self-closing start tag  │
  │    (注释/DOCTYPE/CDATA)      （仅 void 元素与外SVG/MathML有意义）│
  ▼                                                          ▼
注释状态 / DOCTYPE 状态                        After attribute name → Before attr value
                                                          → 属性值（单引/双引/无引）
                                                          → … → Data（标签结束回到起点）
```

工程上最该记住的几条规则：

| 规则 | 内容 | 出错表现 |
|---|---|---|
| 文本里的 `<` | 后面不跟字母/`!`/`/`/`?` 时，`<` 当普通文本 | `a<b 和 c>d` 里 `<` 进入文本 |
| `</ >` 非法结束标签 | `</ p>`（带空格）不是合法闭合——按「bogus comment」处理成注释 | 意外整段消失 |
| 属性值的引号 | 引号内 `<>` 都不算标签边界 | `<div title="a > b">` 合法 |
| 自闭合斜杠 | HTML 语法里 `<span/>` 的 `/` 被忽略，仍是开始标签 | 「为什么我自闭合了还嵌套」 |
| 大小写 | 标签名/属性名 ASCII 大小写不敏感，统一小写进 DOM | `tagName` 返回大写、属性全小写 |
| DOCTYPE 缺失 | 不报错照常解析，但 quirks 模式生效（盒模型/行高全套老行为） | 布局「差之毫厘」的经典来源 |

`&` 实体不在这台状态机里展开——它是**树构建/字符引用状态**的事（`&#x4E2D;`、`&amp;` 的展开表在规范字符引用一节），这也是「`&` 后面不跟实体名时按字面输出」的原因。

## 3. 三类特殊文本状态：script、textarea 与「假标签」

普通状态之外，进入特定元素后分词器切换到专门的文本状态——**在这些状态里，`<div>` 不再是标签，只是字符**：

| 元素 | 状态类型 | 里面写 `<div>` 会怎样 |
|---|---|---|
| `<script>` / `<style>` | RAWTEXT / script data | 全部当文本；结束只认 `</script>`/`</style>` |
| `<textarea>` / `<title>` | RCDATA | 同上，且支持字符引用展开 |
| `<xmp>` / `<iframe>` / `<noembed>` | RAWTEXT（历史遗留） | 同 script 系 |

script data 状态有一段著名的历史补丁：**`<!--` 与 `<script` 的嵌套转义**。老页面在 `<script>` 里写 `<!--` 包住代码，规范只好让 script data 状态带一层「转义深度」计数——`<!--` 进 1、`-->` 出 1，深度非零时 `</script>` 的判定规则变化。它存在的唯一理由是兼容 1995 年的写法。由此产生的实际铁律：**JS 字符串里绝不能裸写 `</script>`**（会终结脚本），要写 `<\/script>`：

```html
<script>
  const s = "</script>";   // 错：分词器在这里真的结束 script——JS 都没解析，字符串字面量救不了你
  const t = "<\/script>";  // 对：/ 不改变 JS 字符串的值，但骗过了 HTML 分词器
</script>
```

「HTML 分词先于 JS 解析」的层级关系在这两行里暴露无遗——分词器不知道字符串是什么，它只认 `</script>` 这几个字符。

## 4. 树构建：插入模式与开放元素栈

树构建器维护两样核心状态：

- **开放元素栈**（stack of open elements）：从 `html` 到当前节点的路径；结束标签要在栈里找到匹配元素，途中弹出的所有元素都被隐式闭合。
- **插入模式**（insertion mode）：当前 token 应按哪套规则处理——`before html`、`in head`、`in body`、`in table`、`in select`……几十个模式各自带处理表。

一次简单解析的走查：

```text
输入：<div><p>hello</div>

token 序列         动作                          开放元素栈
"div" 开始标签     创建 div，入栈                 [html, body, div]
"p"   开始标签     创建 p，入栈                   [html, body, div, p]
"hello" 文本       挂到当前节点（栈顶 p）          同上
"/div" 结束标签    栈里找 div：p 不是 div → 弹出 p（隐式闭合）；找到 div → 弹出 div
                                                 [html, body]
EOF               退出所有模式
```

`<p>` 没写 `</p>` 也得到了正确结构——「结束标签弹出途中一切元素」这条通用规则就是最常见的容错之一。而更精细的「哪些标签能自动闭合谁」由**元素自身的闭合规则**规定（§5 的表）。

### 4.5 一次带容错的完整 token 表

把容错规则「跑」一遍——输入 `<ul><li>a<li>b</ul><table>text<tr><td>c` 的解析走查（容错全开）：

| token | 树构建动作 | 关键规则 |
|---|---|---|
| `<ul>` 开始 | 创建 ul 入栈 | — |
| `<li>` 开始 | 创建 li 入栈 | — |
| `a` 文本 | 挂到 li | — |
| `<li>` 开始 | **先弹出栈顶 li**，再创建新 li 入栈 | li 的同类闭合规则 |
| `b` 文本 | 挂到新 li | — |
| `</ul>` 结束 | 弹出两个 li + ul | 途中隐式闭合 |
| `<table>` 开始 | 创建 table 入栈，插入模式切 in table | — |
| `text` 文本 | **寄养**到 table 之前 | foster parenting（§4.8） |
| `<tr>` 开始 | **先插入 tbody**，tr 挂进 tbody | in table 模式强制 tbody 中介 |
| `<td>` 开始 | 创建 td 入栈 | — |
| `c` 文本 | 挂到 td | — |
| EOF | 逐层退出，闭合全部 | EOF 处理 |

最终 DOM：

```text
body
├─ ul
│  ├─ li "a"
│  └─ li "b"
├─ "text"          ← 寄养的文本，不在 table 里
└─ table
   └─ tbody        ← 规范补的
      └─ tr
         └─ td "c"
```

### 4.8 foster parenting：文本闯进表格怎么办

树构建最「反直觉」的规则：只允许特定内容（`caption`/`col`/`tbody` 等）出现在 `<table>` 直接子级。解析时若文本或普通元素在 table 模式下出现，**移出表格**插到 table 之前——这就是 foster parenting（寄养）：

```html
<table><span>x</span><tr><td>cell</td></tr></table>
```

```text
DOM 结果：                  span 不在 table 里！
<body>
  ├─ span "x"    ← 被寄养到 table 之前
  └─ table
      └─ tbody  ← 规范自动补的
          └─ tr
              └─ td "cell"
```

为什么这么设计？table 的子节点语义是封闭集合，寄养是「不破坏表格语义前提下保留内容」的唯一确定解。它也是布局疑难杂症的常客——CSS 选择器 `.table > span` 永远匹配不到寄养的节点。

## 5. 著名容错规则速查表

把这些规则当「规范 API」记——它们是确定行为，不是运气：

| 输入 | 规范规定的 DOM 结果 | 规则名/机制 |
|---|---|---|
| `<table><tr><td>x</td></tr></table>` | 自动补 `<tbody>` 包住 tr | in table 模式要求 tbody 中介 |
| `<p>one<p>two` | 两个并列 p（第二个 p 开始时自动闭合前一个） | p 的闭合规则 |
| `<li>a<li>b` | 两个并列 li | 同类闭合规则（li/option 等同族） |
| `<b>1<i>2</b>3</i>` | `<b>1<i>2</i></b><i>3</i>` | **adoption agency algorithm**（格式元素的错误嵌套修复） |
| `<b><p>x</b>y</p>` | b 包到 p 里，y 在 p 内且包 `<b>` | adoption agency + 重构活动格式元素 |
| `<html>`/`<head>`/`<body>` 缺失 | 全部自动补出 | 三个隐式节点的强制存在 |
| `<head>` 里写 `<div>` | div 被挪进 body | in head 模式遇到非 head 内容 → 切 in body |
| `</br>` | 当作 `<br>` | 特例表 |
| 表格里的裸文本/`<span>` | 寄养到 table 之前 | foster parenting（§4.8） |
| `<colgroup>` 提前关闭等 | 一组专属闭合序列 | 各容器专属规则 |
| `<select>` 里混入非法元素 | 丢弃 token（select 的子节点是封闭集合） | in select 模式专用表 |
| `<form>` 嵌套 `<form>` | 第二个 form 被忽略 | form 指针机制（同一时刻至多一个开放表单） |

adoption agency 值得多看一眼，它是全规范最复杂的单个算法（`<b><i></b></i>` 是它的教科书用例）：

```text
<b>1 <i>2 </b>3 </i> 4
解析结果：
<b>1 <i>2</i></b><i> 3</i> 4
         ↑ b 提前关闭时，i 被从 b 里「搬出来」单独重开，让后续文本保持斜体
```

设计意图：保持**格式元素（b/i/u…）的视觉连续性**与**树的良构性**兼得——直接闭 b 会丢掉 3 的斜体，直接不闭会产出非法嵌套。规范选择了「拆开重排」的中间路线。

## 6. `<script>` 与解析暂停：解析器视角的脚本阻塞

第六阶段从加载模型讲过同步脚本的阻塞语义，这里是它的解析器内部视角：

```text
树构建器收到 <script> 开始 token
  → 若无 async/defer/module：暂停解析（进入 script parsing 状态）
  → 等脚本资源取回 + 执行完毕
  → 执行期间脚本可以 document.write（往解析器输入流里插内容！）
  → 脚本结束后，树构建器从暂停点继续
```

三个要点把两册串起来：

1. **阻塞的是「树构建」**，不是分词——`</script>` 之后的 token 要等脚本结束才会被处理，因为脚本可能改写输入流（`document.write`）或改 DOM。
2. **脚本能做的一切 DOM 操作都看到「半个 DOM」**——同步脚本执行时，它后面的节点还不存在。这是「脚本放 body 底部 / defer」的根本原因（[第六阶段 06 册](../06-第六阶段/06-脚本加载模型-阻塞-defer-async与module.md)的时序图）。
3. **`document.write` 是毒药**的机理：它把内容插进解析器**当前输入位置**，网络慢时甚至要「 reopening the input stream」重开解析——打断流式管线、触发整段重新解析，现代浏览器在慢连接上直接拒绝执行 write 注入的脚本。规范与工程共识一致：别用。

### 6.5 解析、脚本与 DOMContentLoaded 的时序关系

把「解析完」与「DOMContentLoaded」的关系用解析器语言说清（完整时序图在第六阶段 06 册）：

| 事件 | 解析器语言翻译 |
|---|---|
| `DOMContentLoaded` | 树构建器处理完 EOF token——「主文档解析完毕」的时刻 |
| 同步脚本 | 把 EOF 的到达时间往后推（解析暂停） |
| `defer` 脚本 | 在 EOF 之后、DOMContentLoaded 之前按序执行 |
| `async` 脚本 | 与解析完全解耦，谁先到谁先执行 |
| 样式表 | 不推迟解析与 DOMContentLoaded 本身（但会推迟其上的脚本执行，见[第七阶段 04 册](04-CSS解析与CSSOM.md)） |

由此得到一个实用的排障视角：「DOMContentLoaded 迟到」时，先看 trace 里 EOF 被什么拖住——同步脚本链是第一嫌疑人。

## 7. meta charset 位置之谜（真解析视角收尾）

上一册从 prescan 角度讲过 1024 字节，这里补上真解析视角，两半合起来才是完整答案：

| 视角 | 发生时间 | meta 在 1024 内 | meta 在 1024 外 |
|---|---|---|---|
| prescan（上册 §3） | 正式解析**前**，字节级侦察 | 命中，按正确编码启动 | 看不见 |
| 真解析（本册） | 逐 token 构建 DOM | （已被 prescan 解决） | 解析到 meta 才发现——若编码不同触发 change the encoding，重解码已收到的流 |

还有一个容易被问倒的细节：**为什么 meta charset 自身不受「head 之外会被挪进 body」规则影响**？因为规范为 meta charset 设了特例——即使它出现在 body 位置，编码判定同样认账（只要解析器还在受编码影响的阶段）。但工程上别依赖特例：prescan 只看前 1024 字节，特例救不了 1024 之外的那个。

## 8. 流式解析与 preload scanner 的分工

字节一到就喂解析器——HTML 解析是流式的，网络层与解析层不停接力：

```text
网络块 ① 到达 → 喂分词器 → 构建到 <link>（CSS）/ <img>
网络块 ② 到达 → 继续构建……
```

**preload scanner** 是挂在解析器旁边的旁路扫描器：主解析器被同步脚本卡住时，它继续往前扫「还没真正解析到」的 `<link>`/`<script src>`/`<img>`，把资源请求**提前预约**给网络栈。分工表：

| 参与者 | 看什么 | 不受什么影响 |
|---|---|---|
| 主解析器 | 逐 token 构建 DOM；遇同步脚本暂停 | — |
| preload scanner | 资源 URL 扫描与下载预约 | 同步脚本阻塞（它不暂停）、JS 执行 |

为什么 waterfall 里常见「脚本还没执行，它后面的图片已经开始下载」——那就是 preload scanner 干的（[第六阶段 05 册](../06-第六阶段/05-子资源调度-预解析扫描器-优先级与资源hint.md)有完整优先级表）。「下载提前、执行仍阻塞」两层分离，是理解脚本优化收益的基础。

### 8.5 解析是分块任务：主线程让出点

流式解析的另一个细节：解析器不会一口气吃到 EOF——网络块之间、以及周期性的让出点上，解析工作作为**一个或多个任务**插回事件循环（下一册 07 的主角）。两个可观察的后果：

| 后果 | 机制 |
|---|---|
| trace 里 Parse HTML 常被切成多段 | 每段对应一次「网络块到达/任务调度」的解析任务 |
| 「解析期间页面可交互」的错觉 | 各段之间的空档里，已构建的 DOM 已可被脚本/渲染触碰 |

## 9. 实验

1. **trace 定位 Parse HTML**：Performance 面板录制一次页面加载，Main 轨道找 `Parse HTML` 绿色块；放大看它被同步脚本切成几段——每段之间夹着脚本执行块，这就是 §6 的可视化。
2. **容错规则实测**：把 §5 表里的输入逐个贴进空页面，console 里 `document.body.innerHTML` 看规范化结果；重点复现 `<b><i>2</b>` 的 adoption agency 产物。
3. **token 表手推验证**：拿 §4.5 的输入自己手推一遍 token 表，再贴进页面核对最终 DOM——「手推 → 验证」是吃透容错规则的最快路径。
4. **foster parenting 现场**：构造 `<table><span>x</span></table>`，Elements 面板看 span 被挪到 table 外；再试给 span 写 `.table>span` 选择器——匹配失败即寄养的副作用。
5. **`</script>` 分词实验**：写一段含 `"</script>"` 字符串的脚本，观察脚本被腰斩；换成 `<\/script>` 修复。
6. **preload scanner 观察**：写一个 head 里同步脚本 + body 里 20 张图的页面（图片服务加 2s 延迟），Network 面板对照「图片请求发起时间」与「脚本执行完成时间」——请求早于执行即 preload scanner 的贡献。
7. **性能面板里的解析成本**：生成一个 1MB 量级的单文件 HTML（脚本生成几千个元素），对比整体 Parse HTML 时长与逐块到达形态（示意量级，机器不同差异大）。

## 10. 常见误区

1. **「浏览器会修复我的烂 HTML，所以无所谓」**：修复是确定性算法，但修复结果未必是你想要的（寄养、自动闭合、adoption agency 都会改变选择器命中与布局）；「能渲染」和「按我写的结构渲染」是两回事。
2. **「`<span/>` 自闭合了」**：HTML 语法里斜杠被忽略，span 仍是开始标签；真正的 void 元素只有 `<br>` `<img>` `<input>` 等固定名单。混淆它会造成神秘嵌套。
3. **「`document.write` 只是老派写法」**：它直接操纵解析器输入流，在动态注入/慢网络下引发重解析甚至被浏览器拒绝；动态内容一律 `createElement`/`innerHTML`。
4. **「解析器被脚本阻塞时整条流水线全停」**：停的是主解析与 DOM 构建；preload scanner 与网络下载照跑——「阻塞脚本」与「阻塞下载」要分开评价。
5. **「HTML 容错=宽容」**：恰恰相反，规范对错误输入的规定比合法输入更细——每类错误输入都有唯一确定的输出，这是跨浏览器一致的根基。
6. **「textarea 里的 HTML 会被解析」**：RCDATA 状态里全是文本；把模板塞 textarea/模板标签里「存 HTML」要分清 `innerHTML` 取值时机。
7. **「没有 DOCTYPE 只是少一行」**：缺它进 quirks 模式，盒模型/行高等整套老行为生效——「各浏览器布局不一样」的经典来源之一。

## 11. 自测题
