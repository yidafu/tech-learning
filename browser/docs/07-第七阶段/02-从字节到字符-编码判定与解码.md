# 从字节到字符：编码判定与解码

> [← 第七阶段导览](01-导览.md) · 时间线 ⑪ 的第 0 步。网络进程交付过来的不是「HTML」，是一串**字节**。HTML 解析器要处理字符串，中间必须先过一道「这些字节按什么编码读」的判定——猜错了，后面整棵 DOM 里的中文全是乱码。这一册把判定链（BOM→HTTP 头→meta 前 1024 字节→默认）逐级拆开，说清「1024 字节」这个神秘数字的来历，最后把乱码按成因分好类——每类乱码的修复位置完全不同。

## 1. 总账：为什么编码判定是解析的第 0 步

渲染进程拿到响应体，主线程准备开始时间线 ⑪「HTML→DOM」。但解析器的输入是 Unicode 字符串，网络的输出是字节序列，中间横着一道翻译：

```text
网络字节流  3C 21 44 4F 43 54 59 50 45 ...   ← 没有编码信息的原始字节
      │
      ▼  ① 编码判定（本册主角）
      │
字符流     "<!DOCTYPE ..."                    ← 解析器真正要的东西
      │
      ▼  ② HTML 解析（下一册）
      │
DOM 树
```

三句话立住本册的框架：

| 断言 | 含义 |
|---|---|
| 判定必须**先于**解析 | 解析器「边解析边找 charset」是不可能的——找 meta 本身就需要先解码 |
| 判定是**猜**，不是读 | 字节流自带编码信息的只有 BOM；其余全是启发式推断，规范明文允许浏览器「猜错后改判」 |
| 判定依据来自**四个层级** | BOM → HTTP 头 → meta → 默认值，优先级固定，出处是 WHATWG Encoding Standard 与 HTML Standard 的 encoding sniffing 算法 |

`document.characterSet` 就是判定结果的只读视图——本册所有实验都以它为裁判。

## 2. 判定链全表：四级优先级

HTML 规范的「determine the encoding」流程，按顺序尝试，命中即停：

| 优先级 | 判定源 | 依据什么 | 命中条件 | 猜错的典型 |
|---|---|---|---|---|
| ① | **BOM**（字节顺序标记） | 流开头 `EF BB BF`（UTF-8）/ `FF FE`（UTF-16LE）/ `FE FF`（UTF-16BE） | 存在即终判，**无视其他一切声明** | 文件被编辑器「顺手」加 BOM |
| ② | **HTTP `Content-Type` 头** | `Content-Type: text/html; charset=utf-8` 的 charset 参数 | 头里带了 charset | 头与文件实际编码不一致 |
| ③ | **`<meta>` 前 1024 字节** | `<meta charset="...">` 或 `<meta http-equiv="Content-Type" ...>` | 在流**前 1024 字节**内能扫到 | meta 写在 1024 字节之外（§4） |
| ④ | **默认编码** | 本地化设置推断（历史上 zh 环境多为 GBK/GBK18030，现代浏览器趋于 UTF-8；跨浏览器不保证一致） | 前三级全空 | 页面没声明任何编码且非 UTF-8 |

三个细则容易踩：

1. **BOM 是绝对优先**。UTF-8 文件带了 BOM、HTTP 头却说 GBK——浏览器听 BOM 的。反过来这也解释了「为什么声明没错却乱码」的一类悬案：编辑器保存时自动加 BOM 或转了码。
2. **BOM 会从流里剥掉**。UTF-8 BOM 只用于判定，判定完 `EF BB BF` 三个字节不进入解析器——所以你在 `document.documentElement` 上游永远看不到它。
3. **四级之外的兜底**：跨文档继承（`window.open`/iframe 某些场景沿用父文档编码）与用户手动切换（浏览器菜单「以 XX 编码重新加载」， 现代 Chrome 已收窄此能力）都存在，但都不是站点的可靠出路——**别依赖兜底，把 ①~③ 自己写全**。

### 2.5 一页正反例速查

```html
<!-- 反例：什么都没写。判定走到 ④ 默认值，跨浏览器结果不一致 -->
<html><head><title>中文</title></head>...

<!-- 反例：meta 写了，但 HTTP 头也带了 charset 且两者冲突 → 头赢（②>③） -->
<!-- HTTP: Content-Type: text/html; charset=gbk -->
<meta charset="utf-8">

<!-- 正例：头没带 charset（或带的就是它），meta 在 1024 字节内、与文件实际一致 -->
<meta charset="utf-8">
```

工程铁律：**HTTP 头与 meta 至少写一处，两处都写时必须一致**。只写 meta 时，它还兼任「被另存为本地文件后打开」场景的编码来源（那时没有 HTTP 头了）。

## 3. 1024 字节之谜：侦察窗口与 prescan

为什么 meta 必须在前 1024 字节？直接原因写在规范里：浏览器在正式解析前，会对**流的前 1024 字节**做一次「prescan a byte stream to determine its encoding」（预扫描）——用一套只认 ASCII 结构的轻量状态机找 meta 标签，找到就取它的 charset。

为什么是「预扫描」而不是「直接解析到 meta 再说」？因为先有鸡还是先有蛋：

```text
解析需要字符流 → 字符流需要编码 → 编码线索（meta）藏在字节流里
      ↑_____________________________|
```

解开死结的办法就是 prescan：它**不解码**，只在字节层面认 ASCII 子集——`<`、字母、引号、`>` 这些在 UTF-8 与 GBK 里字节表示都相同的字符。标签名、属性名全是 ASCII，所以「找 `<meta charset=...>`」不需要正确解码全文。前 1024 字节就是给这道侦察程序的预算。

| 问题 | 答案 |
|---|---|
| 为什么是 1024 不是 100？ | head 里的 title、viewport、icon 等 meta 常占几十到几百字节；1024 字节是「正常 head 都能覆盖」的工程余量（规范定值） |
| meta 写在 1024 字节外会怎样？ | prescan 看不见 → 判定落到 ④ 默认编码 → 解析照常进行；**若**解析中途真的解析到那个 meta 且编码与当前不同，走 §5 的「编码变更」补救——代价是可能整页重解码 |
| prescan 会误报吗？ | 会。注释里、字符串里的「假 meta」若落进前 1024 字节同样生效——它不是真解析 |

这就是导览里那条自测题的答案：meta 写在第 3000 字节，判定走默认编码；解析推进到那里时规范允许「change the encoding」——用新编码从头再来一遍（§5）。

### 3.5 prescan 的识别规则细节

prescan 不是「正则找 meta」，它有一套防御性规则，理解它们能解释线上几种诡异现象：

| prescan 规则 | 内容 | 对应的诡异现象 |
|---|---|---|
| 只认 ASCII 标签结构 | `<meta` 与 `charset=` 必须以 ASCII 字节出现 | 属性值里混入多字节后位置计算仍按字节——「meta 在第 900 个**字符**处」可能已超 1024 **字节** |
| 属性名大小写不敏感 | `CHARSET`/`Charset` 同样命中 | 无 |
| 引号容错 | 单引/双引/无引三种属性值形态都认 | 无 |
| 顺序无关 | `charset` 在 `content` 里的位置不影响命中 | 无 |
| 碰到非法序列 | 停止 prescan（安全放弃） | 二进制 payload 开头的页面可能「丢了 meta」 |

「字符数 ≠ 字节数」这一行值得单独画重点：中文注释里塞 meta 前，1024 字节可能只等于三四百个汉字——多字节编码下这个预算比直觉更紧。

## 4. UTF-8 解码与 U+FFFD：非法字节怎么处理

判定出编码后，字节流按 WHATWG Encoding Standard 的解码算法变成字符流。以 UTF-8 为例，两个工程上必须知道的细节：

**变长编码结构**：UTF-8 用首字节前缀标识长度，1~4 字节表达全部 Unicode：

| 码点范围 | 字节数 | 首字节形态 | 例子（「中」= U+4E2D） |
|---|---|---|---|
| U+0000~007F | 1 | `0xxxxxxx` | `41` = A |
| U+0080~07FF | 2 | `110xxxxx 10xxxxxx` | é = `C3 A9` |
| U+0800~FFFF | 3 | `1110xxxx 10xxxxxx 10xxxxxx` | 中 = `E4 B8 AD` |
| U+10000+ | 4 | `11110xxx 10xxxxxx ×3` | emoji = `F0 9F 98 80` |

**非法序列 → U+FFFD**（REPLACEMENT CHARACTER，就是那个黑色的菱形问号）：续字节缺失、首字节非法、序列超长……一律按规范的错误处理规则产出 U+FFFD 并继续。两个推论：

1. **看到 U+FFFD 说明字节在半路就坏了**——不是显示问题，是解码问题；而「能解码出别的汉字但不是该有的字」说明是判定错了编码（§6 的分类依据正是这个区别）。
2. **解码是流式的、有状态的**：多字节序列可能跨网络分块边界（上一册的字节分块 arrives），解码器必须把半截序列攒着等下一块——浏览器内部如此，你自己写流处理时也得如此。

GBK/GB18030 一类多字节编码没有「前缀自校验」这种好性质——这就是为什么误把 UTF-8 当 GBK 读，会解出一堆「看起来合法但毫无意义」的汉字（锟斤拷的来历之一），而反向误读更容易撞出 U+FFFD。

### 4.5 UTF-16 与 JS 字符串：另一层编码

页面编码（UTF-8）与 JS 内部字符串编码（UTF-16）是两回事，混为一谈会出经典 bug：

| 层 | 编码 | 谁负责 |
|---|---|---|
| 网络到解析器 | 页面判定编码（多为 UTF-8） | 本册判定链 |
| JS 运行时字符串 | UTF-16 码元序列（历史遗产） | 引擎内部（V8 还有单字节字符串优化） |

```js
'中'.length            // 1：U+4E2D 在 BMP 内，一个 UTF-16 码元
'𝄞'.length            // 2：U+1D11E 需要**代理对**（两个码元）
'𝄞'.codePointAt(0)    // 119070：按码点读
'𝄞'.charAt(0)         // 乱码感：读到半个代理对
[...'𝄞'].length       // 1：展开运算符按码点迭代
```

| 操作 | 按 UTF-16 码元 | 按 Unicode 码点 |
|---|---|---|
| `.length` / `charAt` / `charCodeAt` / `slice` | 是 | — |
| `for...of` / 展开 / `codePointAt` | — | 是 |

emoji 时代「字符串被腰斩出乱码」的新形态就是**代理对被从中间截断**——E 类乱码（§6）的 Unicode 版本。处理用户输入/切片时用码点安全 API，不是性能洁癖，是正确性要求。

## 5. 编码变更：解析中途改主意

规范允许解析过程中更换编码，触发条件主要是两个：

```text
① prescan 没找到、真解析却解析到了 1024 字节外的 meta charset
   → 若与当前编码不同 → change the encoding
② <pre> 前出现 BOM 才被处理等边角情况（罕见）
```

「change the encoding」的代价要记清：**新编码重解码整个已收到的流，已构建的 DOM 推翻重建**。更糟的是如果新编码是多字节、旧字节边界对不上，规范甚至规定可能需要等更多字节到达才能重新开始——网络窗口里表现为一次明显的解析重启。

这给出 meta charset 「必须尽早」的完整答案（导览知识点地图第 1 条的展开）：

| meta 位置 | 判定路径 | 代价 |
|---|---|---|
| 前 1024 字节内 | prescan 命中，一次解码 | 零额外代价 |
| 1024 字节外 | 先按默认编解码 + 解析，命中 meta 后 change the encoding | 重解码 + 可能重解析；默认猜错则先渲染出一屏乱码再自愈 |
| 根本没写 | 默认编码到底 | 错了就错到底 |

顺带一提 `<script>` 偷运 charset 的历史：老代码里 `<script charset="gbk">` 曾用于引入不同编码的外部脚本，HTML5 已废弃该属性——外部脚本的编码同样遵循本册判定链（HTTP 头优先，meta 兜不了忙），所以**多编码站点迁移 UTF-8 时，老 JS 文件是重灾区**。

## 6. 乱码成因分类：每类的症状与修复位置

把乱码当病看，先分型再开药。五大类：

| 类型 | 成因 | 典型症状 | 修复位置 |
|---|---|---|---|
| A. 声明与实际不符 | meta/HTTP 头写 GBK，文件实际是 UTF-8（或反之） | 固定的、可复现的错字（如「æµ‹è¯•」是 UTF-8 被当 Latin-1 读） | 改声明，或统一文件编码——**对齐两者** |
| B. 声明缺失 + 默认猜错 | 前三级全空，默认编码与实际不符 | 本地正常、部署到服务器就乱（服务器环境 locale 改变默认值） | 补 meta + 补 HTTP 头 |
| C. 双重编码 | 文本被「按错误编码解码后又存成字节」两轮以上 | 「锟斤拷」「æ¸¬è©¦」叠加态；修声明无效 | 数据已损坏，从源头重新导出——**声明救不了** |
| D. 传输层转码 | 中间件/代理/网关擅自转码或截断多字节 | 同一文件不同环境结果不同；curl 直连正常、过网关就乱 | 查链路上的中间层，声明只能配合 |
| E. 半截截断 | 多字节序列被按字节截断（日志切割、substring） | 每隔固定长度出现一个 U+FFFD | 按**字符**不按字节切，修复在处理代码 |

「锟斤拷」的完整链条值得一讲，它是 C 类的标本：UTF-8 解码失败产出 U+FFFD（`EF BF BD`）→ 某层把 U+FFFD 按 GBK 重新编码成 `EF BF BD EF BF BD` → 再按 GBK 解码回来就是「锟斤拷」——两个 U+FFFD 恰好凑出三个常见汉字。所以见到「锟斤拷」不是巧合，是「U+FFFD 被二次编码」的指纹。

### 6.5 分诊树：从症状到修复的决策路径

```text
页面乱码？
 ├─ 错字固定、可复现（同一处永远同一批错字）？
 │    ├─ 是 → A 类。核对：curl -i 看 HTTP charset + 看文件真实编码
 │    │       修复：对齐声明与实际（改头或转码重存）
 │    └─ 环境相关（本地好、线上乱 / 换浏览器不一样）？
 │         → B/D 类。先查三级声明是否齐全（B），再查中间层（D）
 ├─ 黑色菱形 U+FFFD？
 │    → 字节已坏：C（历史双重编码）或 E（截断）。
 │      声明修复无效，回溯数据导出/处理链路
 └─ 代理对腰斩（emoji 后半截乱）？
      → §4.5：按码点处理的代码修复
```

每类「能修的位置」不同是分型的全部意义：A/B 修**声明**，C 修**数据源**，D 修**链路**，E 修**处理代码**——拿声明去救 C 类是线上常见的无效修复。

## 7. 外部资源的编码：CSS `@charset` 与脚本继承

判定链不止管 HTML 一份文档，外部资源各有自己的编码判定入口：

| 资源 | 判定方式 | 备注 |
|---|---|---|
| CSS 文件 | HTTP 头 charset > `@charset "utf-8";`（必须是文件**最前面**，前面不许有任何字符，含 BOM 争议区） > 引入它的文档编码 > 默认 | `@charset` 位置苛刻：必须是第一条语句，字符级精确 |
| JS 外部脚本 | HTTP 头 charset > （HTML5 已废弃 script charset 属性）> 沿用引用它的文档编码 > 默认 | 「老 GBK 脚本 + 新 UTF-8 页面」的乱码重灾区 |
| XHR/fetch 文本 | 按 Content-Type 头 / `TextDecoder` 显式指定 | API 层面把判定权交给你的代码 |

CSS 的 `@charset` 写法与位置（错一个字符就整个失效）：

```css
@charset "UTF-8";        /* 必须第一条、无前导空白、双引号、分号结尾 */
```

工程结论统一成一句：**外部资源一律在 HTTP 头声明编码**——它是唯一同时被 HTML/CSS/JS 判定链最高优先级尊重的位置。

## 8. 实验

1. **裁判工具就位**：任意页面 console 里 `document.characterSet`（注意是这个属性名，老 API `charset` 已废弃）；Network 面板点开文档请求 → Headers 看 `Content-Type`——判定链 ②③④ 的原料全部可视化。
2. **判定链优先级实测**：本地起 `python3 -m http.server`，写四个 HTML 变体——无声明 / 仅 meta / 仅 HTTP 头（用一个小脚本塞头）/ 头与 meta 冲突——分别访问读 characterSet，对照 §2 表格逐级验证。
3. **1024 字节边界复现**：用脚本生成一个 head 前塞 1100 字节注释、meta charset 写在其后的页面；观察是否触发编码变更（若与默认一致则无感——把 meta 故意写成与内容不同的编码看乱码）。
4. **U+FFFD 制造现场**：用 Python 把一个含中文的 UTF-8 字符串拦腰截断中间字节，再正常解码输出——观察 U+FFFD 出现的位置（§4 推论 1 的实证）。
5. **代理对截断实验**：JS 里对含 emoji 字符串做 `slice(0, n)` 多次，观察乱码；换成码点安全写法 `[...str].slice(0,n).join('')` 对照（§4.5）。
6. **CSS `@charset` 位置敏感性**：构造 `@charset` 前多一个空行/空格/注释的三个 CSS，写中文类名或中文内容（加 `content`），观察解码结果差异。
7. **乱码分诊演练**：故意构造 A/C 两类乱码页面各一个，练习 §6.5 分诊树；把修复过程记进 `labs/`。

```bash
# 实验辅助：看一个文件的真实字节与 BOM
python3 - <<'PY'
data = open('demo.html','rb').read()
print(data[:16])            # 首字节：EF BB BF 开头即 UTF-8 BOM
print(len(data))            # 文件总字节数（注意与字符数区分）
PY
```

## 9. 常见误区

1. **「浏览器会解析 HTML 找 charset」**：正式解析以编码为前提；找到 meta 的是 prescan（字节级侦察）或 change-the-encoding 补救，两条路完全不同——混淆它们就解释不了 1024 字节规则。
2. **「meta charset 写在哪都行」**：写在哪都能被「真解析」扫到，但只有前 1024 字节内的才被 prescan 看见；超界的靠补救机制兜底，多付一次重解码。
3. **「乱码 = 加个 meta charset 就好」**：C/E 类乱码数据本身已损坏，任何声明都无效；分型（§6）是修复的前置步骤。
4. **「BOM 是坏东西，一律去掉」**：BOM 对判定链是最高优先级的可靠信号；要不要去是工程偏好（JSON 禁 BOM、部分工具链嫌它），但「BOM 导致乱码」多数其实是 BOM 与声明冲突的场景，先对齐再谈去留。
5. **「HTTP 头和 meta 各写各的没关系」**：冲突时头赢（②>③），meta 形同虚设——CDN/框架注入的默认头常常是冲突源头，排查时两头都要看。
6. **「UTF-8 下 1 个字符 = 1 个字节」**：ASCII 部分是，中文 3 字节、emoji 4 字节；按字节截断/计数是 E 类乱码的直接来源。
7. **「页面是 UTF-8，JS 字符串也是 UTF-8」**：JS 运行时字符串是 UTF-16 码元（§4.5）；`.length`/`slice` 都按码元算——emoji/生僻字处理必须走码点 API。
8. **「`@charset` 写了就行」**：它必须是文件第一条语句且写法精确；位置/引号错一个字符整条失效——不如把 CSS 编码也交 HTTP 头管。

## 10. 常见问答

**Q：现在还用得着关心 GBK 吗？全站 UTF-8 不就完了？**
站点自己确实应该全 UTF-8（统一是消灭 A/C 类乱码的根本手段），但「关心 GBK」的两个真实场景仍在：对接老系统/老数据（GBK 库、GBK 导出文件）时的转码正确性；以及理解历史乱码数据（用户资料里的锟斤拷）是修不回来的——知道哪些数据值得抢救、哪些只能重新采集。

**Q：meta charset 和 meta http-equiv 两种写法有区别吗？**
判定语义等价（prescan 都认）；`<meta charset="...">` 是 HTML5 的简写形态，`http-equiv="Content-Type"` 是兼容老写法。现代页面用前者，不必再写后者。

**Q：为什么我的中文文件名/路径请求也乱码？**
那是 URL 百分号编码问题（URL 编码按 UTF-8 序列化），与文档编码判定是两套机制；服务端解码方式不一致时会看到「%E4%B8%AD」或其错误还原——归 URL/网络层话题，本册只标记分界。

**Q：能在 JS 里「修正」页面编码吗？**
不能，也永远别试。脚本运行时页面早已按判定编码解码完毕，字符串已是 Unicode——「读出来再转」救不了文档流本身；唯一的修法是在判定链上游修（声明/头/文件编码），让浏览器**第一次**就解码正确。这条边界同时给出 AJAX 场景的正解：拉到旧编码文本时在 `TextDecoder` 层显式指定旧编码做「字节→字符」的干净转换，而不是对已解码字符串做二次折腾。

**Q：浏览器「用错误编码渲染了整页但中文都正常」可能吗？**
可能。ASCII 范围内 UTF-8 与 GBK 完全同构——英文页面判错编码可能毫无症状；症状只在第一个非 ASCII 字符出现。这解释了「国际化后突然爆乱码」的常见时间线：英文版埋的雷，上了中文才炸。

**Q：自己处理字节流时（fetch/流式解析），怎么复用浏览器这套判定？**
`TextDecoder` 就是 WHATWG Encoding Standard 的可编程接口：`new TextDecoder('utf-8')` 默认带 U+FFFD 错误处理与跨块状态保持，`fatal: true` 可把「非法序列」改成抛错（校验场景用），`ignoreBOM: true` 控制是否吞 BOM。浏览器内核的判定链是它的超集——自己写时不必重建判定链，把输入按 §2 判定好、解码交给 `TextDecoder`。
