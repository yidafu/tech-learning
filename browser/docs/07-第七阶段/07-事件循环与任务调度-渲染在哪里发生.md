# 事件循环与任务调度：渲染在哪里发生

> [← 第七阶段导览](01-导览.md) · 时间线 ⑪⑫⑬⑭ 的总装车间。前三册的解析、样式计算、脚本执行全是「事件循环里的任务」——这一册把总装图补上：主线程这个单线程队列到底按什么规则出队？宏任务与微任务的边界在哪？**rAF 回调站在循环的哪个确切位置？渲染为什么不是每轮循环都发生？**读完这册，「我这段代码什么时候执行、渲染排在它前面还是后面」就不再是背口诀，而是能从机制推出来。

## 1. 总账：主线程是一个「跑任务 + 择机渲染」的循环

事件循环（event loop）不是浏览器独有的发明（Node 也有），但**浏览器的事件循环定义里有「渲染」这一步**——这是它与 Node 版本最大的分野，也是本册标题「渲染在哪里发生」的答案所在：

```text
while (true) {
  task = 任一任务队列里取最旧的一个      ← 宏任务：脚本、事件回调、定时器……
  执行完它（run to completion）
  清空整个微任务队列                    ← promise/queueMicrotask/MutationObserver
  if (该渲染了) {
    执行「更新渲染」步骤：rAF 回调 → Style → Layout → 合成提交   ← ★ 本册主角
  }
  if (没有活干了) 挂起（或跑 idle 回调）  ← requestIdleCallback（§6）
}
```

| 要点 | 内容 |
|---|---|
| 单线程 | 一个 renderer 进程一个主线程，DOM/CSSOM/JS 全在它身上 |
| run to completion | 一个宏任务跑到底，中途不切别的任务——这是「长任务卡界面」的机制根源 |
| 渲染是「择机」 | 不是每轮循环都渲染；由 vsync 节拍与页面状态决定（§4） |

**任务队列的真相**：规范说「取任一队列最旧任务」，但实现里**不止一条队列**——不同 task source（定时器/用户输入/网络回调/解析任务……）各有队列，浏览器按内部策略挑（用户输入通常优先）。这解释了「忙时点击响应为什么仍可能插队」：输入队列的优先级高于定时器队列。本阶段各册的任务都认得出来源：[03 册](03-HTML解析器-状态机-容错与DOM构建.md)的解析任务、本册的定时器/事件回调、网络回调来自网络栈。

**Worker 是另一个循环**：每个 Worker（Dedicated/Shared/Service）有**自己独立的事件循环**——没有 DOM、没有 rAF、微任务机制照有。Service Worker 的 install/activate/waiting 状态机（[第六阶段 04 册](../06-第六阶段/04-ServiceWorker-生命周期与拦截时序.md)）就是跑在它自己的循环里。**「把活搬去 Worker」能搬走计算，搬不走 DOM**——主线程独占 DOM 是本册全部问题的出发点。

## 2. 一次循环的完整步骤表

把循环拆成规范粒度（HTML Standard 的 event loop processing model 精简版），每行都值得认领：

| 步骤 | 内容 | 对应 trace/现象 |
|---|---|---|
| ① 取宏任务 | 从任务队列取最旧任务（不同源的任务队列有优先策略，实现自由） | Main 轨道一个新任务块 |
| ② 执行到底 | 同步代码跑完，中途的 setTimeout/事件回调只是**入队** | 任务块内的函数调用树 |
| ③ 微任务检查点 | 执行栈一空 → 清空**整个**微任务队列（新产生的微任务也在本轮清掉） | trace 中不单独命名，夹在任务末尾 |
| ④ 该渲染吗 | vsync 临近 + 页面可见 + 有更新 → 进入渲染步骤；否则回 ① | 高刷屏 rAF 密度变化 |
| ⑤ rAF 回调 | 按注册顺序跑全部 `requestAnimationFrame` 回调 | trace 的 Animation Frame 任务块 |
| ⑥ Style/Layout/Paint | 失效部分重算样式、布局、产绘制提交给合成器 | `Recalculate Style`/`Layout`/`Paint` 块 |
| ⑦ 回到 ① | 下一轮循环 | — |

两个高频追问现在有了机制答案：

- **「rAF 在微任务之前还是之后？」**——在之后。微任务检查点（③）每轮循环必跑，rAF 只在「决定渲染」的轮次跑（⑤）。但注意细则：**rAF 回调执行过程中新入队的微任务，会在该 rAF 回调一结束就被清空**（每个回调边界都有微任务检查点）——「rAF 里 await 了一下」不会把渲染推迟到下一帧。
- **「rAF 里改 DOM，同帧布局算几次？」**——rAF 是渲染步骤的第一步，Style/Layout 排在它后面：rAF 里的 DOM 修改在**同一帧的 ⑥ 被统一计算**，正常情况下只算一次；把布局相关的读（offsetHeight）插进 rAF 才会把 ⑥ 切成多段（§6 的读写纪律）。

### 2.5 微任务检查点的嵌套细则

「执行栈一空就清微任务」的精确版比「宏任务结束后」更细——**每个回调边界都算一次栈空**：

```js
// 嵌套回调场景
setTimeout(() => {
  Promise.resolve().then(() => console.log('microtask A'));
  setTimeout(() => console.log('macrotask C'), 0);
  console.log('macrotask B 的同步尾');
}, 0);

// 输出顺序：B 的同步尾 → A → C
// A 在「B 结束后的检查点」清掉，不用等 C——微任务永远插在紧邻的下一个回调之前
```

| 场景 | 检查点时机 |
|---|---|
| 普通宏任务结束 | 任务末尾清空（③） |
| 微任务自身结束 | 继续清（队列没空就接着清，同一轮） |
| rAF / 事件监听器等**每个回调**结束 | 该回调末尾清一次 |
| `new Promise` 执行器、resolve 回调 | 视作同步代码，无独立检查点 |

结论一句话：**微任务的粒度是「栈空」，不是「任务结束」**——回调链越长，插入的检查点越多，但规则不变。

## 3. 宏任务与微任务：两层队列的完整规则

| 维度 | 宏任务（task） | 微任务（microtask） |
|---|---|---|
| 成员 | 整段脚本、事件回调、`setTimeout`/`setInterval` 到期、I/O 回调、MessageChannel | `Promise.then/catch/finally`、`queueMicrotask`、`MutationObserver`、`await` 的续体 |

MutationObserver 的位置值得单独点名：它是**微任务**——一次回调里改 100 个节点，100 处变更合并成**一次**微任务回调（批量交付），这使它比「监听后同步处理」和「轮询 DOM」都便宜。但它的微任务身份也意味着：在微任务风暴里它同样被饿着——「MutationObserver 一定及时」不成立。
| 出队粒度 | 每轮循环**一个** | 每个检查点**清空整个队列**（含新产生的） |
| 什么时候插入 | 按各自的调度时机 | 同步代码一结束就有机会 |
| 谁能插队渲染 | — | 微任务永远在「渲染决策」**之前**清空 |

「为什么 microtask 一定在下一个宏任务之前清空」（导览自测题第 8 题）：微任务的语义是「**当前执行栈一结束就跑**的逻辑延续」——promise 链把异步代码写成「看起来同步」的依赖全押在它身上。若微任务能被下一个宏任务（比如一次点击）插队，promise 续体就要和用户事件抢序，语义崩塌。所以规范把清空点钉死在「每次栈空」。

微任务无限自生的后果同样由机制给出：**清空循环永不退出**——渲染永远到不了（④ 永远轮不到），页面冻结但**不是死循环报错**，是「安静地再也不渲染」。`while(true) Promise.resolve().then(()=>queueMicrotask(...))` 就是这条的标本。

`setTimeout(fn, 0)` 的两个细则顺带钉死：

| 细则 | 内容 |
|---|---|
| 嵌套下限 | 嵌套超过 5 层后最小间隔钳到 4ms（HTML 规范明文） |
| 「0ms」语义 | 「最早下一轮宏任务」，不是「立刻」——中间隔着微任务清空与可能的本轮渲染 |
| `setInterval` 的堆积语义 | 处理器耗时超过间隔时，后续到期回调**可连续执行**（不合并）——密集 interval 是长任务配方 |

「要一个不被 4ms 钳制的宏任务」的工程工具是 `MessageChannel`——它的消息回调走任务队列但不走定时器，`postMessage` 到自己的 port 即得一个「下一轮宏任务、无 4ms 税」的原语（一些调度库的底层积木）。

## 4. 渲染决策：rAF 的确切位置与「不是每轮都渲染」

「该渲染吗」的真实判定，关键参与者是 **vsync**（垂直同步信号）：

```text
渲染步骤由「渲染机会（rendering opportunities）」驱动：
  页面可见（background 标签页 rAF 冻结）
  + 屏幕刷新节拍临近（vsync，通常 60Hz/120Hz，示意）
  + 有东西要更新（样式脏/布局脏/rAF 已注册……）
  三者齐 → 本轮循环执行渲染步骤
```

| 推论 | 机制出处 |
|---|---|
| rAF 每秒至多随刷新率触发 | 渲染机会由 vsync 对齐；60Hz 屏 ≈ 每 16.6ms 一个机会 |
| 后台标签页 rAF 停、定时器降频 | 页面可见性是渲染机会的硬前提 |
| 「一帧内多次 rAF 注册只跑一轮」 | 渲染步骤把**已注册的全部回调**按序跑完 |
| 主线程忙 ≠ 渲染必延后合成 | 滚动等部分工作在合成线程，见[第八阶段 06 册](../08-第八阶段/06-合成-合成线程-GPU与vsync.md) |

把渲染步骤内部的顺序再钉一遍（§2 步骤⑤⑥的展开，也是导览目标 7 的标准答案）：**rAF 回调 → 样式计算 → 布局 → 生成绘制指令 → 提交合成**。「rAF = 绘制之前」的说法是粗略版，精确版是「rAF 是渲染步骤的第一个动作，它内部对 DOM/样式的改动会被同帧的后续步骤吸收」。

多显示器/高刷的补充：同一页面的 rAF 频率跟随**所在屏幕**的刷新率（拖到 120Hz 屏上 rAF 间隔减半，示意）——「rAF 是 60Hz 专属」的老说法过时了；对齐的是 vsync，不是某个固定数字。

## 5. 完整走查：一段代码的输出顺序

把三节知识压进一道题（导览实践任务第 5 题的完整版）：

```js
console.log('1: 同步');
setTimeout(() => console.log('4: 宏任务'), 0);
Promise.resolve().then(() => console.log('3: 微任务'));
requestAnimationFrame(() => console.log('5: rAF（若本轮渲染）'));
console.log('2: 同步末尾');
```

| 顺序 | 输出 | 机制 |
|---|---|---|
| 同步 | 1、2 | run to completion |
| 微任务清空 | 3 | 栈一空即清微任务（步骤③） |
| 宏任务 | 4 | 下一轮循环才轮到它（步骤①） |
| rAF | 5 | **与 4 的相对顺序不保证**——取决于 vsync 何时到：本轮渲染先来则 5 在 4 前；vsync 晚于下一轮宏任务则 4 在 5 前 |

最后一行是这道题的真正考点：宏任务与 rAF **不在同一个队列、不受同一个规则排序**——「setTimeout 和 rAF 谁先」的正确答案永远是「看 vsync，不背顺序」。想在下一帧渲染**前**做视觉相关工作，唯一可靠工具是 rAF 本身。

### 5.5 进阶走查：await 与 rAF 的组合

把 async/await 加进题目（检查「微任务粒度=栈空」是否真懂）：

```js
async function run() {
  console.log('a');
  await Promise.resolve();          // 续体进微任务
  console.log('b');
  requestAnimationFrame(() => console.log('c: rAF'));
}
run();
setTimeout(() => console.log('d: 宏任务'), 0);
```

| 输出 | 机制 |
|---|---|
| a | 同步段 |
| b | await 续体在首个检查点清掉 |
| c 与 d 相对顺序不保证 | 与 §5 同理：rAF 看 vsync，宏任务看队列 |

关键点：`await` 之后注册 rAF 的**时机**（在微任务里）不影响它归属哪一轮渲染——rAF 注册进的是「下一次渲染步骤」，不是「当前执行栈」。理解到这层，async/await 与渲染的交织就不再神秘。

## 6. 长任务与 yield 模式

**长任务（long task）**的判定：主线程上连续占用超过 **50ms** 的任务（Long Tasks API，`performance.getEntriesByType('longtask')` 可查）。50 这个数字的含义：交互响应预算（用户输入到视觉反馈 ≤100ms 的量级感）减去渲染开销后的任务上限——单任务超它，本轮输入就要等到下下个机会。

| 工具 | 定位 | 机制 |
|---|---|---|
| `scheduler.postTask(priority)` | 把活交给调度器并声明优先级 | 任务入队 + 优先级排序（Scheduler API） |
| `scheduler.yield()` | 长任务中途让出主线程，**续体以用户可见优先级续跑**，且在「可能的中断点」前保持顺序 | 返回 promise，微任务式续体 |
| `setTimeout(fn,0)` | 传统让出 | 宏任务尾队 + 4ms 钳制；让出后渲染有机会插入 |
| `MessageChannel` | 不想等 4ms 又要「宏任务」语义 | 新任务不走定时器钳制 |
| `isInputPending()` | 长任务里轮询「有输入吗」 | 有输入则先 yield 处理输入 |

`postTask` 的三档优先级与「意外后果」对照：

| priority | 给谁用 | 风险 |
|---|---|---|
| `user-blocking` | 输入响应、即将可见的更新 | 滥用 = 优先级通胀，人人都 blocking 等于没人 blocking |
| `user-visible` | 默认档，普通 UI 更新 | — |
| `background` | 埋点、预取、日志 | 与用户抢带宽/缓存的活放这里 |

yield 模式骨架（长任务切块的标准写法）：

```js
async function processChunked(items) {
  let start = performance.now();
  for (let i = 0; i < items.length; i++) {
    process(items[i]);
    if (performance.now() - start > 20 && i < items.length - 1) {  // 攒 ~20ms（示意阈值）
      await scheduler.yield?.() ?? new Promise(r => setTimeout(r, 0));  // 让出：渲染/输入插队
      start = performance.now();
    }
  }
}
```

`requestIdleCallback` 补一笔（导览自测题第 10 题）：它的回调在「渲染机会用尽、还有空闲」时才可能跑，且 `timeout` 参数到点前**没有任何执行保证**——空闲是低优先级资源，绝不能放关键路径；它与长任务的关系是「长任务挤占空闲 → idle 回调更饿」。真正的交互保命手段是本节的 yield/切块，不是祈祷空闲。

## 7. 实验

1. **输出顺序走查**：跑 §5 的五段代码 10 次（页面与 console），记录 4 与 5 的相对顺序波动——实证「宏任务与 rAF 不受同一规则排序」。
2. **嵌套检查点验证**：跑 §2.5 的示例，核对「B → A → C」；再在事件监听器里放 promise 续体，观察「回调一结束就清」的行为。
3. **微任务冻结复现**：跑一个「微任务无限自生」的循环，Performance 面板观察任务块连续、渲染步骤消失的形态；几秒后终止。
4. **rAF 的 vsync 对齐**：在 `rAF` 回调里 `performance.now()` 记录时间戳序列，算相邻间隔分布（60Hz 屏 ≈ 16.6ms，示意；拖窗口跨屏看变化）；同页面在后台标签对比 rAF 停摆。
5. **长任务识别**：构造一个 100ms 的同步循环，Performance 面板看任务块右上角红色三角（长任务标记）；`performance.getEntriesByType('longtask')` 读取同一条记录。
6. **yield 前后对照**：100ms 任务 vs 切成 5 段 yield 的同任务，Performance 面板对比渲染步骤是否能插入任务之间——「主线程呼吸感」的 trace 证据。
7. **MessageChannel vs setTimeout 计时**：两种「下一轮宏任务」原语各跑 1000 次记录间隔分布——对比 4ms 钳制的有无（示意量级）。
8. **同帧布局次数**：rAF 回调里改 DOM（无布局读）→ trace 中 Layout 一段；再插入 offsetHeight 读 → Layout 被切成多段（[05 册](05-样式计算-级联-匹配与ComputedStyle.md)强制布局的循环视角闭环）。
9. **interval 堆积复现**：`setInterval(fn, 100)` 里放一个 250ms 的处理器，Performance 面板观察回调背靠背连发的形态（§3 的堆积语义实证）；换成 rAF 版本对照。
10. **任务来源识别**：同一页面混用定时器/事件/MessageChannel 各触发一次，trace 里对照三者的任务块起点——「多队列按源调度」的可见证据。

## 8. 常见误区

1. **「setTimeout(fn,0) 是微任务」**：它是宏任务；「0ms」也要等当前微任务清空 + 本轮宏任务让位——await（微任务）比它快一个量级的场景比比皆是。
2. **「rAF 是更快的 setTimeout」**：rAF 是渲染步骤的入口，与 vsync 对齐、页面不可见即停；把它当定时器用（做逻辑运算）语义就错了——它的合同是「下一帧绘制前」。
3. **「事件循环每转一圈渲染一次」**：渲染是「择机」的（vsync + 可见 + 有更新）；后台标签页转圈不停但渲染为零。
4. **「微任务队列是『某个队列』之一」**：每个事件循环只有一层微任务队列，且清空规则是「清到空」——它与宏任务队列不是平级兄弟，是每轮循环间的强制插曲。
5. **「async/await 会切换线程」**：await 只是把续体排进微任务队列；主线程还是那一个，「异步」 ≠ 「并行」。
6. **「requestIdleCallback 保证执行」**：空闲回调零保证（timeout 只是最后期限）；关键路径放 idle 回调 = 把功能交给运气。
7. **「Worker 能帮 DOM 活减负」**：Worker 是独立事件循环但无 DOM；能搬走的只有纯计算——与 DOM 相关的活只能在主线程排队（或用 OffscreenCanvas 这类特例通道）。
8. **「postTask 的 user-blocking 想用就用」**：优先级是相对稀缺资源，全员最高 = 退化为 FIFO；滥用还会让真正的输入响应失去插队优势。

## 9. 常见问答

**Q：为什么有时 setTimeout(fn,0) 的回调看起来「立刻」就跑了？**
本轮没有其他宏任务、vsync 未到、微任务清空完成——下一轮循环马上取它。「0ms」的期望距离只是「一个循环圈」，机器空载时这个圈是微秒级；忙时才是真正的等待。这和「定时器精度」是两回事：精度下限（4ms 钳制）与队列等待时间叠加。

**Q：微任务和 rAF 的执行顺序能保证吗？**
「已入队的微任务」一定先于「本轮渲染的 rAF」（检查点在渲染决策之前）；「rAF 回调里新排的微任务」在该 rAF 回调结束的检查点跑（§2.5），早于同帧 Style/Layout。所以「rAF 前的微任务、rAF 中的微任务」两个位置都有确定答案，不确定的只有「宏任务 vs rAF」（§5）。

**Q：怎么让一段代码「保证在下一帧渲染前跑」？**
rAF。任何宏任务工具（setTimeout/MessageChannel/postTask）都只保证「下一轮循环」，不保证「下一帧前」——循环与帧不是一回事（§4）。反过来「渲染后再跑」用 rAF 套 rAF。

**Q：`setInterval(fn, 100)` 的处理器要跑 250ms 时会发生什么？**
每次到期都独立入队一个宏任务——处理器还没跑完的到期不会被「跳过合并」，积压的回调会在后续循环里**背靠背连发**（间隔语义名存实亡）。这就是「动效用 interval 写着写着掉帧」的机制根源，也是「定时驱动渲染请用 rAF」的第三条论据（前两条：vsync 对齐与不可见暂停）。

**Q：长任务切多少合适？**
20~50ms 一块是常见工程区间（示意）：小于 20ms 让出开销占比升高，大于 50ms 就成了 long task 本身。以「trace 里任务块不再带红色三角、输入延迟不超预算」为验收，不迷信单一数字。

**Q：为什么有时改了样式，rAF 回调里读到的还是旧值？**
正常情况下不会——rAF 在渲染步骤开头，Style 排在它后面，rAF 里改样式同帧就生效。能出现「旧值」的场景是读法问题：在 rAF **之前**的宏任务里改样式又立刻 `getComputedStyle` 读，此时样式虽已重算，但若读的是布局相关值且读得早，可能触发强制布局（[05 册](05-样式计算-级联-匹配与ComputedStyle.md) §6）而非拿到「未来」的值。判定口诀：改与读之间隔了几个「栈空检查点」，值就是几个检查点之后的版本。
