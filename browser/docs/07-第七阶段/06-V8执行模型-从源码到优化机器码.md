# V8 执行模型：从源码到优化机器码

> [← 第七阶段导览](01-导览.md) · 时间线 ⑬。解析器把 `<script>` 内容交给执行引擎，主线程时间线的第三段开始：JS 怎么从源码变成跑得飞快的机器码。这一册只讲 **V8 特有的执行模型**——四层编译流水线、内联缓存、隐藏类、去优化。词法/语法/AST/IR/GC 这些通用编译与运行时理论不在这里重复造轮子（详读 `compiler/` 站），本册聚焦「V8 为什么这样设计、你的代码怎么喂它才不挨打」。

## 1. 总账：一段代码的完整旅程

```text
源码（HTML 分词器吐出的脚本文本）
   │
   ▼
词法/语法分析 → AST          ← 通用理论见 compiler/ 站（一句话指针）
   │
   ▼
Ignition 字节码（解释执行）   ← 惰性编译：函数体先只记「没编译」
   │  热点被命中、反馈向量攒类型信息
   ▼
Sparkplug 基线编译（快出机器码，不做优化）
   │  仍然热
   ▼
Maglev 中层优化（轻量推测优化，快出成品）
   │  非常热
   ▼
Turbofan 深度优化（推测优化 + 内联 + 指令调度，最慢出成品、跑得最快）
   │
   └─ 假设被打破 → 去优化 → 回 Ignition 字节码（§7）
```

| 层 | 产物 | 出手速度 | 运行速度 | 角色一句话 |
|---|---|---|---|---|
| Ignition | 字节码 | 最快 | 最慢 | 全量兜底 + 类型反馈收集 |
| Sparkplug | 基线机器码 | 快 | 略快于解释 | 省去解释开销的「直译版」 |
| Maglev | 中层优化码 | 中 | 快 | 早期热点受益，轻量推测 |
| Turbofan | 优化机器码 | 最慢 | 最快 | 深度优化 + 激进内联 |

时间线 ⑬ 在 trace 里的名字：主线程上的 `Compile`/`v8.compile` 块与执行帧（函数名直接可见）；后台的 script streaming 见 §6。

「为什么中间要垫两层」是流水线的核心问题，答案是一对矛盾：**优化编译器出手慢**（做内联/寄存器分配/指令调度都要时间），**热点等不了**。四层就是按「出手时间换运行速度」的连续谱——每一层都为「还不够热到值得进下一层」的代码兜底。中短期运行的页面（一次性脚本、事件驱动的 UI 代码）大量函数终身停在 Ignition/Sparkplug——**不是所有代码都值得优化，这正是分层的意义**。

tier-up 的触发器是「热度」的两种计数（阈值是内部策略，量级示意）：

| 触发器 | 含义 | 观察方式 |
|---|---|---|
| 调用/执行计数 | 函数被调用或字节码循环执行的次数过阈值 | `--trace-opt` 的 marking 输出 |
| 循环回边（配合 OSR） | 长循环中途直接升级（§6 的 OSR） | benchmark 循环中途变快 |
| 反馈质量 | 反馈槽里有「可假设」的证据才值得深优化 | 纯多态/超多态的函数升了也快不起来 |

第三行常被忽略：**热度只是门票，反馈质量才是优化的原料**——超多态的热函数「够热但没得优化」，升层后收益有限。这也解释了为什么「形状稳定」比「多跑」更重要。

## 2. 惰性编译与 script streaming

两个「不白白编译」的机制先立住：

**惰性编译（lazy compilation）**：函数体默认**不立即编译**——预解析器只检查语法合法性，函数体等首次调用才真编译。收益：一屏页面里从未执行的函数零编译成本。代价与细节：

| 细节 | 内容 |
|---|---|
| 立即编译的例外 | 顶层代码、`new Function`/eval、被强制 eager 的内部函数（如 IIFE 包裹） |
| 惰性的代价 | 首次调用多一次「现编译」延迟——微秒级，绝大多数场景可忽略 |
| 立即调用包一层括号的历史 | `(function(){...})()` 曾被预解析器当 eager 处理，现代 V8 已能自动识别 |

**script streaming**：大脚本**边下载边在后台线程预解析**（UTF-16/UTF-8 双形态的现代实现是后台线程直接产 AST 级产物），主线程拿到时编译大头已完成——与[第六阶段 06 册](../06-第六阶段/06-脚本加载模型-阻塞-defer-async与module.md)的加载模型衔接：`defer`/`async` 脚本下载期越长，streaming 省得越多；`<script async>` + 缓存命中的小脚本反而可能用不上（流都没开始）。观察形态：Performance 面板里 `v8.compile` 出现在**后台线程轨道**而非 Main。

### 2.5 优化也是后台做的：并发编译

不止 streaming 在后台——**Turbofan/Maglev 的优化编译本身也放在后台线程**做（concurrent compilation），主线程只做：决定优化（tier-up 判定）、安装成品（把函数入口切到优化码）。对 trace 的解读：

| 现象 | 机制 |
|---|---|
| 主线程几乎看不到 Turbofan 编译大块 | 编译在后台线程轨道（trace 里 v8 相关后台任务） |
| 「函数突然变快」的时刻 | 安装点的入口切换，瞬间完成 |
| 前几十次循环仍慢 | tier-up 有延迟——微基准要「先热身再计时」的机制原因 |

微基准的「warm-up」纪律直接由此而来：**先跑几千次等优化装好，再开始计时**——否则测的是 Ignition/Maglev 而不是你以为的 Turbofan。

## 3. Ignition：字节码与反馈向量

Ignition 是寄存器式字节码解释器。看一段代码的字节码（Node 环境）：

```bash
node --print-bytecode -e 'function add(a,b){return a+b}; add(1,2)'
```

```text
LdaSmi [1]        ← 小整数立即数进累加器
Star0             ← 存进寄存器 r0
Ldar a1           …
Add a1, [0]       ← 加法；[0] 是反馈槽编号！
Return
```

重点不在指令集，在 **`[0]` 这个反馈槽（feedback slot）**：每个字节码操作关联一个槽，运行时把「见到的操作数类型、调用目标、属性访问的形状」记录进去——**类型反馈就存在这里**。加法槽看到的全是 Smi（小整数）→ 优化器才敢生成整数加法机器码；槽里混进字符串 → 只能生成「运行时再判断」的慢路径。

| 概念 | 存在哪 | 谁消费 |
|---|---|---|
| 类型反馈 | 反馈向量（每函数一份，槽对应操作） | Maglev/Turbofan（决定敢生成什么假设） |
| IC 状态 | 同一个槽里（§4） | 属性访问/调用的快速路径 |

「先跑一万次攒证据，再按证据编译」——这就是分层设计的信息论基础：**解释层是优化层的传感器**。

反馈向量的生命周期也值得知道：首次调用时分配（与函数绑定，不是与调用点全局共享）、随函数对象存活、在函数被优化/去优化的循环中**内容持续累积**——去优化不丢反馈（那正是「再优化时敢更准」的依据），只有函数被回收才随之回收。这也回答「为什么多态槽回不去单态」：反馈记录的是**历史**，历史里见过的形状不会忘。

## 4. 内联缓存：属性访问为什么能快过字典查询

IC（Inline Cache）回答的问题：`obj.x` 每次都要查吗？不用——**把上次查询的结果缓存在这条指令旁边**：

| IC 状态 | 含义 | 访问路径 |
|---|---|---|
| monomorphic（单态） | 槽里只见过 1 种形状 | 形状校验 1 次 → **直接偏移量读取**（最快路径） |
| polymorphic（多态） | 见过 2~4 种形状 | 逐项比对（上限量级 4，示意） |
| megamorphic（超多态） | 超过上限 | 查全局运行时表（最慢的「快路径」） |

超多态的全局表在 V8 里有个专有名字——**megamorphic stub cache**（全局桩缓存，按「形状+名字」的哈希查找）：它仍比「每次完整查哈希表」快（命中过就记住），但已丧失「按槽定形状」的确定性。多态槽与全局缓存的关系：**槽是本地的快路径，缓存是全世界的慢路径**——IC 的全部意义就是让热点访问留在前者。

```js
// 单态的喂法：所有对象同一形状
function getX(o) { return o.x; }
getX({x:1,y:2}); getX({x:3,y:4});   // 同形状 → monomorphic

// 多态的喂法：
getX({x:1,y:2}); getX({y:2,x:1});   // 属性顺序不同 → 形状不同（§5）→ polymorphic
```

工程口径：**热点函数的参数形状保持单一**；框架/通用库里的「任意形状」函数天然多态，这没关系——多态是现实，超多态才是信号。用 `%DebugPrint`/`--trace-ic`（Node 调试参数）可观测 IC 状态迁移。

### 4.5 调用点 IC：函数调用也有缓存

属性访问之外的另一类 IC——**调用点反馈**（call feedback）：调用指令的槽里记「这个位置历史上调用过哪些函数」。Turbofan 的内联决策直接读它：

| 槽里记的 | 优化器敢做的 |
|---|---|
| 永远是同一个函数 | **内联**该函数体（§6 收益之王） |
| 固定两三个函数 | 内联 + 分发（按被调者分派，体量可控） |
| 千变万化 | 放弃内联，留间接调用 |

「热点回调被传成不同函数」是 megamorphic 调用点的常见来源——事件处理器的统一分发器、数组方法的回调形态等。与前节同一条纪律：**同一调用点尽量喂同一形状**。

## 5. 隐藏类：JS 对象的「形状」

JS 对象语义是哈希表，但 V8 给每个对象挂一个 **隐藏类（hidden class / Map）**描述它的布局：有哪些属性、按什么偏移量存。相同创建顺序的对象共享同一隐藏类——属性访问从「查哈希」变成「形状校验 + 定长偏移读取」，与 IC 配合后接近结构体字段访问。

**形状迁移（transition）链**——按顺序加属性会沿链滑向新形状：

```js
const a = {}; a.x = 1; a.y = 2;   // 形状 M0 → M1 → M2
const b = {}; b.y = 2; b.x = 1;   // y 先加 → 另一条迁移链！与 a 不同形状
```

破坏形状稳定的三件套：

| 行为 | 后果 | 规避 |
|---|---|---|
| 乱序添加属性 | 同构对象落入不同隐藏类，IC 升多态 | 构造函数里**固定顺序**初始化全部字段 |
| `delete obj.x` | 该对象转入**字典模式**（慢属性，退回哈希查找） | 用 `undefined`/`null` 占位替代删除 |
| 字面量键值动态拼装 | 每个对象可能独立形状 | 统一构造路径 |
| 以不同形态反复赋值同一属性（number ↔ object） | 属性表示在 Smi/Double/Tagged 间迁移，形状震荡 | 初始化时给「终态类型」的值 |

数组同理：`arr[10000]=1` 会让引擎考虑字典/稀疏形态；`hole`（稀疏空洞）也有专门的慢路径。一句话纪律：**同构对象用同构代码造**——class 与固定形状工厂函数不是美学，是给 IC 和 Turbofan 发的「形状稳定承诺书」。

### 5.5 快属性与慢属性：对象内部的两套账

隐藏类之下，属性存储本身还分两档，读 V8 文章/调内存快照时会遇到：

| 形态 | 存储 | 访问速度 | 何时出现 |
|---|---|---|---|
| 快属性（in-object + 快哈希） | 对象内联槽 / 描述符数组 | 偏移量直读 | 常规对象 |
| 字典模式（慢属性） | 哈希表 | 查表 | 大量动态增删、`delete` 后 |

触发慢化的常见操作：`delete`、超量属性（阈值级，示意）、`Object.defineProperty` 配置非默认描述符的批量操作。内存快照工具里看到「dictionary_properties」就是它——**能改回快形态吗？**新造对象比「拯救」老对象便宜，重构构造路径是正解。

再补一块与形状相邻的机制：**闭包变量与上下文分配**。被内层函数捕获的变量不能留在栈帧里，V8 把它们装箱进**堆上的 Context 对象**——每次访问多一层间接。「把大循环变量包进回调」的隐性成本常在这：捕获的变量越多、越大（数组/大对象），装箱与回收的面就越大。对策朴素有效：**闭包只捕获真正需要的最小变量集**（用局部变量收窄，别把整个作用域顺手捕获）。

## 6. Turbofan：推测优化与内联

Turbofan 的核心手段是**推测优化（speculative optimization）**：把反馈向量里攒的假设直接「焊」进机器码——

| 反馈证据 | 焊进的假设 | 假设打破时 |
|---|---|---|
| 加法槽全是 Smi | 整数加法（溢出检查仍保留） | 去优化 |
| 属性访问单态 | 形状校验 + 偏移读取 | 校验失败 → 去优化 |
| 函数每次都接收「某形状」 | 内联化（函数体展开进调用方） | 被调对象形状变 → 去优化 |

**内联（inlining）**是优化收益之王：消除调用开销只是零头，真正价值是让被调函数体进入调用方的优化上下文——后续所有优化（逃逸分析、常量传播、死代码消除）获得更大的作用范围。内联决策依据反馈 + 体量启发式（超大函数不内联）。

「类型反馈在哪里记录了假设」（导览自测题第 7 题答案）：**Ignition 的反馈向量**——数字调用一万次时槽里记满 Smi/数字态，Turbofan 按此假设编译；第 10001 次传字符串，运行时的假设检查（守卫）失败，进入 §7。

还有一个精细机制值得知道：**OSR（On-Stack Replacement）**——一个正在执行中的长循环不需要等函数退出才能享受优化：解释器发现循环热到阈值，可以把「栈上正在跑的这一帧」原地换到优化码里继续。这就是「写个百万次循环 benchmark，中途它自己变快」的机制。代价是 OSR 编译的函数多数是一次性场景，未必值得长期优化。

## 7. 去优化：优化是假设，不是承诺

**Deoptimization** = 假设被打破时，把执行现场从优化机器码搬回 Ignition 字节码，从对应位置继续——语义永远正确，速度回到起点附近。

| 类型 | 时机 | 例子 |
|---|---|---|
| **eager deopt**（急切） | 守卫当场失败 | 给单态假设的函数传了新形状/新类型 |
| **lazy deopt**（惰性） | 优化码依赖的对象在执行中被外部改变（如被回调改了原型） | 优化码运行中假设失效，回到入口重走 |

去优化不是失败，是**分层设计的正常运转**——但同一函数反复「优化→去优化→再优化」的**去优化循环**（deopt loop）是真实存在的性能事故：观察手段与治理：

```bash
node --trace-opt --trace-deopt demo.js
# [marking] optimizing hot function ...   ← 升层
# [bailout] reason: wrong ...            ← 去优化及原因
```

| 信号 | 含义 | 治理 |
|---|---|---|
| 同一函数反复 bailout | 调用方形状/类型不稳定 | 统一构造路径（§5） |
| bailout reason: wrong map / wrong instance type | 隐藏类假设被打破 | 检查 delete/乱序属性 |
| try/catch 包裹热路径（老引擎代价比现在小） | 优化窗口受限 | 热路径内避免大块 try |
| `arguments`/`delete`/eval 等解优化特征 | 优化器放弃假设 | 重构掉 |

把话说全：**V8 的快不是「JS 被编译了」，是「你写出了可以被假设的代码」**——去优化机制就是这半句话的反面。

## 8. GC 与 DOM 边界（两句话带过）

按分工边界各记一句指针，不展开：

- **GC（分代/增量/并发回收）**：通用垃圾回收理论在 `compiler/` 站；本册要记的只有一条工程含义——**大规模对象分配的暂停会以「微停顿」形态出现在主线程 trace 上**，分配热点（每帧 new 大量对象）是主线程抖动的隐性来源。
- **DOM 对象与 JS 对象的互操作**：DOM 不是普通 JS 对象（各自独立的世界，靠绑定层翻译），跨边界调用的成本独立于本册的 IC/优化体系——「为什么 wrapper 对象访问比纯 JS 对象慢」的答案在那条边界上。

## 9. 实验

1. **字节码肉眼可读**：`node --print-bytecode --print-bytecode-filter=add -e 'function add(a,b){return a+b}; for(let i=0;i<10;i++) add(i,i)'`——找到 Add 指令与反馈槽编号（§3）。
2. **四层流水线观测**：`node --trace-opt --trace-deopt` 跑一个 1 万次循环的热函数，观察「解释 → Sparkplug/Maglev → Turbofan」的升层标记（Node 版本不同层数标记不同，示意）。
3. **去优化复现**：热函数先吃一万次 `{x:1}` 再吃一次 `{y:1}`，看 `--trace-deopt` 输出的 bailout reason；把两次调用改成同序属性，确认不再 bailout。
4. **IC 状态迁移**：`--trace-ic` 观察 `getX` 从 mono → poly → mega 的迁移线，对照 §4 状态表。
5. **优化状态探针**：`--allow-natives-syntax` 下用 `%GetOptimizationStatus(fn)`（位掩码）在循环前后各读一次，验证升级与打回（导览实践任务第 4 题的标准做法）。
6. **OSR 观测**：单函数内写一个 500 万次的长循环，`--trace-opt` 看中途的 OSR 标记（§6）。
7. **Performance 面板对照**：录一次真实页面加载，Main 轨道找 Compile 块与函数执行帧；再对比「脚本 streaming 出现在后台轨道」的页面（大脚本 + 慢网络模拟）。
8. **微基准 warm-up 对照**：同一基准，「不热身直接计时」与「先跑 1 万次再计时」两组数字对比——体会 §2.5 的 tier-up 延迟（数字是示意的，结论看相对差）。

## 10. 常见误区

1. **「V8 会把所有代码都优化成机器码」**：优化按热点逐函数、按反馈证据做；冷代码一辈子待在 Ignition——「没被调用的函数被优化了」不存在。
2. **「优化后会一直快」**：优化是**假设**，去优化随时可能发生；假设被打破回到字节码是设计内行为，不是 bug。
3. **「delete 和乱序属性只是风格问题」**：它们破坏隐藏类同构，直接推高 IC 多态度与去优化率——是性能问题。
4. **「加了 try/catch / 用了 eval 就一定不优化」**：现代 V8 的限制已大幅放宽；真实纪律是「热路径里少放**阻碍假设**的结构」，而不是教条回避。
5. **「类型反馈存在 AST 里」**：存在运行时函数级**反馈向量**里，槽与字节码指令对应——这也是「解释层是传感器」说法的出处。
6. **「microbenchmark 里快 10% 的写法线上也快」**：分层引擎的收益高度依赖真实调用形态（形状稳定性、热点密度）；基准结论必须带「同形状、够热」的前提，且 warm-up 要做够（§2.5）。
7. **「async/await 会让优化失效」**：await 是语法糖（promise 续体 + 状态机），优化器照常处理；真正的干扰源仍是形状/类型不稳定，不是 async 本身。

## 11. 常见问答

**Q：四个编译层是规范吗？其他引擎（SpiderMonkey/JavaScriptCore）一样吗？**
不是规范，是 V8 的实现架构（且层名/层数随版本在变）。其他引擎也有自己的分层（JSC 有四五个 tier），思想同构——「解释攒反馈 → 多级优化 → 去优化兜底」是所有现代 JS 引擎的通用骨架，只是名字与层数不同。

**Q：TypeScript 的类型对 V8 有帮助吗？**
运行时没有——TS 类型编译后即消失，V8 只认反馈向量里攒的运行时事实。TS 的收益是编译期正确性与人；「写了 TS 所以更快」是把两套系统混为一谈。

**Q：怎么知道线上代码是否被去优化了？**
生产环境开 `--trace-deopt` 不现实（Node 才有）；浏览器侧的信号是 Performance 面板中「同一函数耗时突然变慢数倍」+ 本地用相同调用形态复现 `--trace-deopt`——「本地按线上形态喂参数」是去优化排查的核心方法论。

**Q：既然优化这么条件苛刻，认真写「优化友好」代码值得吗？**
值得，但分寸在「形状稳定、避免 delete、热点参数同构」这几条低成本纪律上；超过这个粒度（手写 monomorphic 分发、规避多态）通常得不偿失——引擎优化是给「正常写的好代码」的奖励，不是给自己的写法上枷锁的理由。

**Q：数组也是对象，数组操作的形状纪律是什么？**
数组在 V8 里有自己的「元素种类（elements kind）」谱系：packed SMI → packed double → packed element → 对应的 holey 版本，每往「泛化」走一步，读写路径的优化余地就小一分。`arr[0]=1.5` 把 SMI 数组降级为 double 数组、稀疏写入把 packed 降级为 holey——降级容易升回难。纪律：**数组只装一类东西、不留空洞、用 push 顺序填充**，`for` 正序遍历优于 `for...in`（后者按属性语义遍历，天然慢路径）。

**Q：`Object.freeze` / `Object.seal` 对优化有什么影响？**
冻结后的对象形状固定不可再迁移，属性访问本可走最快路径；但引擎对冻结对象的某些操作（如以它为原型、或对它的写入探测）要走特殊分支——结论是「冻结只为了不可变性语义才用」，把它当优化手段属于过度设计。
