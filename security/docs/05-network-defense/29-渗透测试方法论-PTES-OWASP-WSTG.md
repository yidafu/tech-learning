## 0. 开篇：定义、红线与"和黑客的区别"

**渗透测试（Penetration Testing / Pentest）**是在**获得授权的前提下**，由专业人员在约定范围（Scope）内模拟真实攻击者手法，评估目标系统安全性的工程活动。它的产出不是"打穿了"，而是一份能驱动修复的**报告**。

红线重申（本工作区一以贯之）：
- **书面授权是前提**：授权书（Authorization Letter / Rules of Engagement）先行，无授权的"测试"就是攻击，是犯罪。
- **Scope（范围）与 ROE（Rules of Engagement，交战规则）**：明确允许测试的域名、IP、网段、时间段、方式（是否允许 DoS、社会工程、物理闯入、生产数据访问）。**范围外一概不碰**。
- **越界的后果**：法律上（中国《刑法》第 285/286 条、他国 CFAA 等）是刑事责任；职业上是行业性禁入。
- 与"黑客"的区别一句话：**渗透测试是带着甲方授权、时间盒与报告义务的攻击仿真；黑客不受 scope、时间与伦理约束**。我们学习攻击技术是为了防御（offensive-informed defense）。

## 1. 标准体系对比：为什么需要方法论

没有方法论的测试 = 凭感觉乱测 = 漏洞靠运气。方法论保证**覆盖率可评估、过程可复现、质量可审计**。四大标准定位：

| 标准 | 全称 | 定位与侧重 | 适用 |
| --- | --- | --- | --- |
| **PTES** | Penetration Testing Execution Standard | 渗透测试**全流程**七阶段骨架，从前期交互到报告，阶段产出物明确 | 通用渗透项目流程管理 |
| **OWASP WSTG** | Web Security Testing Guide | **Web 应用**测试清单：10+ 大类、数百个带编号的测试项，每项给怎么做 | Web 应用测试覆盖度基线 |
| **OSSTMM** | Open Source Security Testing Methodology Manual | 学术化、量化（RAV 分值）、强调可测量的运营安全测试 | 深度安全评估/研究 |
| **NIST SP 800-115** | Technical Guide to Information Security Testing and Assessment | 美国官方指南：规划-执行-后置三段式，强调管理与合规衔接 | 合规驱动的测试（金融/政府） |

实践建议：**流程骨架用 PTES，Web 覆盖用 WSTG 打勾，报告结构参考 NIST 800-115 附录**——三者互补不互斥。

## 2. PTES 七阶段详解

```text
1 前期交互 → 2 情报收集 → 3 威胁建模 → 4 漏洞分析 → 5 漏洞利用 → 6 后渗透 → 7 报告
   (约定)      (侦察)       (怎么打)      (哪里弱)      (打进去)      (影响证明)   (交付价值)
```

### 阶段 1：前期交互（Pre-engagement Interactions）

- **目标**：把"做什么、不做什么、怎么算完成"写死在纸面上。
- **活动清单**：签署授权书与 NDA；确定测试类型（黑盒/灰盒/白盒——Blackbox 无信息、Greybox 部分信息如账号、Whitebox 给源码/架构）；界定 Scope（域名/IP/应用/账号集）；制定 ROE（禁止手法、时间窗、应急联系人、数据处置约定）；谈定测试环境（生产 or 镜像）、出口 IP 申报（避免被甲方封禁/误伤）；交付物与复测条款；保险与法律责任划分。
- **产出物**：授权书、SOW（Statement of Work，工作说明书）、ROE 文档、测试计划与时间表。

### 阶段 2：情报收集（Intelligence Gathering）

- **目标**：建立目标的技术与业务画像，攻击面越大情报越多。
- **活动清单**：被动信息收集（whois、DNS、证书透明度、搜索引擎、GitHub 泄露、招聘信息推断技术栈）；主动探测（端口扫描 nmap、目录爆破、指纹识别、WAF 识别——见笔记 25）；业务逻辑了解（注册流程、角色体系）。
- **产出物**：资产清单（域名/子域/IP/端口/服务/技术栈）、组织信息图、潜在攻击面列表。
- **红线**：被动情报收集也涉及个人信息（员工邮箱、组织架构），按最小必要原则，不落敏感非必要数据。

### 阶段 3：威胁建模（Threat Modeling）

- **目标**：回答"谁会以什么路径打这个系统"，据此排测试优先级。
- **活动清单**：结合 STRIDE 等方法识别高价值资产（数据库、支付、认证）；画出数据流与信任边界（DFD）；枚举最可能的攻击路径（如"外网后台弱口令 → 越权 → 内网"）；与甲方确认最关心的威胁场景。
- **产出物**：威胁建模图、攻击路径假设列表、测试优先级矩阵。

### 阶段 4：漏洞分析（Vulnerability Analysis）

- **目标**：把"开放的攻击面"变成"具体可利用的弱点清单"。
- **活动清单**：自动化扫描（漏扫器、nmap NSE vuln 类脚本）打初筛；**人工验证**每一处可疑发现（自动化结果必须人工确认，误报直接写进报告是职业事故）；按威胁建模的路径定向手工测试（逻辑漏洞扫描器发现不了）。
- **产出物**：经验证的漏洞列表（含位置、条件、证据截图）、误报剔除记录。

### 阶段 5：漏洞利用（Exploitation）

- **目标**：证明漏洞**真实可利用**并控制影响范围。
- **活动清单**：编写/调整 PoC（Proof of Concept，概念验证）；最小破坏利用（选无害 payload，如 `sleep 5` 证明命令执行而不是反弹 shell）；记录每一步（命令、时间、屏幕录像）以便复现与复原；失败也要记录（证明尝试过，评估防护有效性）。
- **产出物**：利用记录（步骤+时间戳+截图/录像）、获得的访问级别说明。

### 阶段 6：后渗透（Post-Exploitation）

- **目标**：评估**真实业务影响**（一个 shell 值多少风险？），而非"炫技横向"。
- **活动清单**：本机信息收集与权限提升（Privilege Escalation）；按 ROE 决定是否横向移动（很多 ROE 禁止）；目标数据**存活性证明**（prove，不是 steal：列出数据条数/表结构/截图打码样本，**不下载真实用户数据**）；建立与清除测试痕迹（安装的文件、账号、计划任务全部记录并在结束时移除）；持续性仅在被明确授权时验证。
- **产出物**：影响评估（可达数据/系统清单）、痕迹清理清单、清理完成确认。

### 阶段 7：报告（Reporting）

- **目标**：把技术发现转化为甲方**能执行、能排期、能验证**的修复行动。详见 §6/§7。
- **产出物**：执行摘要 + 技术报告 + 复测说明（报告是渗透测试**唯一可交付的价值载体**）。

## 3. OWASP WSTG 结构详解

WSTG 把 Web 测试组织为类别化、带唯一编号的测试项（如 `WSTG-INFO-02`），编号可在报告与 checklist 中直接引用。分类结构（v4.2）与重点测试项：

### 3.1 分类总览与重点项

| WSTG 类别 | 编号前缀 | 关注点 | 挑选的重点测试项（编号 + 一句话要点） |
| --- | --- | --- | --- |
| 信息收集 | `WSTG-INFO` | 表面侦察 | INFO-01 搜索引擎与缓存发现被索引的敏感页；**INFO-02 枚举 Web 服务器指纹（版本/框架）**；INFO-05 review 注释与源码中泄露的路径、密钥、后端逻辑 |
| 配置与部署管理 | `WSTG-CONF` | 配置失误 | **CONF-05 管理接口枚举**（/admin、/manager）；CONF-04 旧备份与未引用文件（.bak、.git）；CONF-11 云存储权限错配 |
| 身份认证 | `WSTG-ATHN` | 登录体系 | **ATHN-02 默认凭据测试**；ATHN-03 弱锁定机制（可被爆破吗）；ATHN-04 绕过认证方案（空口令/认证逻辑绕过）；ATHN-09 弱密码修改/重置功能（找回流程绕过） |
| 会话管理 | `WSTG-SESS` | 会话安全 | **SESS-01 会话管理方案（含会话 ID 熵不足/可预测）**；**SESS-02 Cookie 属性（HttpOnly/Secure/SameSite）**；SESS-03 会话固定（登录后未换 token）；SESS-05 CSRF；SESS-06 注销后旧会话是否真正失效 |
| 授权 | `WSTG-ATHZ` | 越权 | **ATHZ-01 目录遍历（路径穿越/文件包含）**；**ATHZ-02 绕过授权方案**；ATHZ-03 权限提升（垂直越权——普通用户触达管理功能）；ATHZ-04 不安全的直接对象引用（IDOR——改 id 水平越权） |
| 数据校验（输入校验） | `WSTG-INPV` | 注入类 | **INPV-01 反射型 XSS**；**INPV-02 存储型 XSS**；**INPV-05 SQL 注入**（05.1–05.8 子项）；INPV-11 代码注入（11.1 LFI / 11.2 RFI）；INPV-12 命令注入；INPV-18 SSTI；INPV-19 SSRF（文件上传类测试归业务逻辑：BUSL-08/09） |
| 错误处理 | `WSTG-ERRH` | 信息泄露 | **ERRH-01 错误信息中泄露栈/SQL/路径（调试模式未关）**；ERRH-02 堆栈跟踪利用 |
| 密码学 | `WSTG-CRYP` | 算法与传输 | **CRYP-01 弱传输层安全（弱 TLS 版本/套件、证书校验缺失）**；CRYP-02 padding oracle；CRYP-03 未加密信道传输敏感信息（HTTP 明文登录）；CRYP-04 弱算法（MD5/RC4） |
| 业务逻辑 | `WSTG-BUSL` | 逻辑缺陷 | **BUSL-01 业务数据校验（负数数量、超限金额）**；BUSL-04 过程时序（竞态条件、并发薅羊毛）；BUSL-06 工作流绕过（跳步支付）；BUSL-08/09 上传意外文件类型/上传恶意文件（webshell） |
| 客户端测试 | `WSTG-CLNT` | 浏览器端 | **CLNT-01 DOM XSS**；CLNT-07 跨域策略（CORS 误配——反射 Origin + credentials）；CLNT-11 Web Messaging（postMessage 来源校验） |
| API 测试（v4.2 新增） | `WSTG-APIS` | API 专项 | APIS-01 GraphQL（内省暴露）；REST 权限与批量赋值（v4.2 无专项编号，仅留描述） |
| （另附）综述导读 | 无编号 | 架构/技术 | 测试指南开篇的架构审阅与技术错配内容（不参与 WSTG 编号体系） |

> 使用方式：把 WSTG 编号体系作为**覆盖度基线**——报告附"WSTG 覆盖矩阵"（哪些项测了、哪些不适用及原因），可审计且显专业。

## 4. 信息收集方法论

### 4.1 被动收集（不触碰目标服务器）

| 手段 | 工具/入口 | 说明 |
| --- | --- | --- |
| whois | `whois example.com` | 注册人、NS、到期时间（社工与子域线索） |
| **证书透明度（CT, Certificate Transparency）** | `https://crt.sh/?q=%25.example.com` | 历史签发证书暴露隐藏子域——被动首选 |
| DNS 记录 | `dig any example.com`、`dig axfr @ns.example.com example.com`（区域传送误配） | MX/TXT/SPF/区域传送 |
| **Google Hacking（Google Dorks）** | 见下方语法表 | 搜索引擎索引的敏感内容 |
| 代码仓库泄露 | GitHub/GitLab 搜索（企业域名、AK/SK、password） | truffleHog/gitleaks 半自动化 |
| 网络空间测绘 | FOFA/Shodan/Hunter（企业自有资产查询） | 资产与暴露面盘点（企业自查同样用） |
| 子域枚举 | subfinder、amass、`crt.sh`、DNS 字典爆破 | 见下"工具思路" |

**Google Hacking 语法表**：

| 语法 | 作用 | 示例 |
| --- | --- | --- |
| `site:` | 限定站点 | `site:example.com admin` |
| `inurl:` | URL 含关键词 | `inurl:admin login` |
| `intitle:` | 标题含关键词 | `intitle:"index of" backup` |
| `filetype:` / `ext:` | 文件类型 | `site:example.com filetype:sql` |
| `cache:` | 缓存快照（**已失效**：Google 2024 年起已移除该操作符，仅旧资料中可见） | `cache:example.com/old-page`（不再可用） |
| 组合 | - | `site:example.com (ext:bkf \| ext:sql \| ext:log)` |

**子域枚举工具思路**：证书透明度（crt.sh API）→ 被动 DNS 数据库（amass passive）→ 主动字典爆破（subfinder -d domain + 字典）→ DNS 解析存活验证 → 存活子域进端口/目录阶段。工具不重要，**数据源叠加**才有效。

### 4.2 主动收集（触碰目标，授权范围内）

```bash
# 环境：Kali/Ubuntu + 已授权目标。仅限本地靶场或书面授权环境。
# 端口与服务
sudo nmap -sS -sV -sC -p- -T4 target.example.com        # 见笔记 25
# 目录与文件爆破
ffuf -w /usr/share/wordlists/dirb/common.txt -u https://target/FUZZ \
     -mc 200,301,302,403 -recursion -recursion-depth 2 -t 40
dirsearch -u https://target -e php,asp,jsp,html,js -x 404,403
# 指纹识别
whatweb https://target           # 框架/CMS/中间件
# WAF 识别
wafw00f https://target
```

ffuf 要点：`FUZZ` 占位符、`-mc` 过滤响应码（403/200 之外常是噪声）、注意用 `-fs`/`-fl` 按大小/长度去噪声、速率 `-t`/`-rate` 别打挂目标。

## 5. 漏洞验证原则与利用、后渗透

### 5.1 验证原则（"证明影响，而非制造破坏"）

1. **最小化影响（safe exploitation）**：能 `sleep 5` 证明命令执行就不用反弹 shell；能读一条自建测试记录证明 SQL 注入就不 `--dump` 全库；
2. **数据处理纪律**：**不下载真实用户数据**。需要证明数据可达时：统计条数、字段结构、打码截图，测试完成后销毁临时数据；
3. **停止条件（stop conditions）**：达到预授权访问级别即停（如"获得应用层管理员即停，不做内网"）；触发甲方监控/造成性能劣化即停并通报；发现非 Scope 内系统被波及（如利用链跳到第三方）立即停止并报告；
4. **全记录**：每步命令与时间戳（配合屏幕录像），既为复现，也为"事后审计我做了什么"自证清白。

### 5.2 利用与后渗透简述（概述性，细节在后续 Pwn/Web 笔记）

**权限提升（Privilege Escalation）思路清单**（Linux）：
- 内核漏洞（脏牛 DirtyCow、DirtyPipe 等版本匹配）；
- SUID/SGID 二进制滥用（`find / -perm -4000 -type f 2>/dev/null`）；
- sudo 规则误配（`sudo -l`：NOPASSWD 的意外命令、GTFOBins 利用）；
- 可写定时任务/服务单元、cron 路径劫持；
- 明文凭据与历史（配置文件、`~/.bash_history`）、PATH 劫持。

（Windows 提权：服务路径未加引号、AlwaysInstallElevated、令牌伪造/土豆系列、Unquoted Service Path——大纲第 4/7 阶段展开。）

**横向移动一句话**：在已控主机上利用有效凭据（mimikatz 提取/票据传递）经 SMB/WinRM/RDP 扩散到同域其他主机，检验内网分区与监控的有效性——是否执行取决于 ROE。

**跳板与痕迹**：以受控主机为代理（pivoting/chisel/ssh -D）访问隔离网段；**痕迹管理双面性**：渗透测试中所有"清理痕迹"必须记录在案并在项目结束时确认恢复原状；防御视角的"痕迹"就是日志（笔记 28），你在靶场删日志的同时要理解哪些日志删不掉（远端转发）。

## 7. 报告撰写详解

### 7.1 结构模板

1. **执行摘要（Executive Summary）**——面向管理层：业务语言、无技术术语。内容：测试范围与方法一段话、总体安全状况定性、**最重要的 3-5 个发现及业务风险**、修复优先级路线图（速赢→中期→长期）。
2. **风险评级矩阵**——严重度分布（危急/高/中/低数量）、风险矩阵图（可能性 × 影响）。
3. **漏洞详情**——逐漏洞：标题（含资产）；风险等级与 **CVSS**（联动见下）；**复现步骤**（精确到可直接照做的命令/请求）；证据（截图打码、PoC 代码）；风险描述（攻击者能做什么、业务影响）；**修复建议**（分层：立即缓解 + 根本修复 + 纵深防御）。
4. **复测说明**——已修复项验证结果、未修复项的遗留风险与豁免理由。
5. **附录**——测试覆盖矩阵（WSTG 打勾表）、工具清单、原始数据、术语表、ROE 摘要。

**CVSS 联动**：以 CVSS（Common Vulnerability Scoring System，通用漏洞评分系统）v3.1 基础分（0-10：Critical≥9.0 / High≥7.0 / Medium≥4.0 / Low≥0.1）为起点，再按**业务上下文调整**（同样的漏洞在支付系统与宣传页权重不同）。报告里写清"基础分 + 环境调整理由"，避免"拍脑袋定级"。

### 7.2 优秀报告的 8 个特征

1. **可复现**：任一工程师按步骤能独立重现；
2. **可执行**：每条发现都有明确、分层、可排期的修复建议；
3. **分级合理**：业务上下文驱动，不夸大不隐瞒；
4. **证据充分**：截图/PoC/请求响应完整且脱敏；
5. **结构分层**：管理层摘要与技术细节分离，各取所需；
6. **正向语言**：报告写"如何修好"而非"你们多烂"；
7. **覆盖透明**：明确测了什么、没测什么、为什么；
8. **合规可审计**：编号、时间戳、版本修订记录齐全。

## 8. 法律与合规要点

- **授权书/SOW 关键条款**：双方主体与签署人；测试范围（资产清单附录）；允许与禁止的技术手段；测试时间窗与变更通知；数据处理与保密（NDA）；事故响应联动（打挂了先叫谁）；责任限制与保险；交付物清单与验收标准；复测条款；争议解决与适用法律。
- **个人数据保护（PIPL，《个人信息保护法》）边界**：测试中获得个人信息属"最小必要"用途，**不得留存、不得导出原始数据**（只做可达性证明）；靶场/镜像环境优先；涉及人脸/证件等敏感个人信息时建议在脱敏数据集上测试；报告本身也要脱敏。
- **跨境**：数据出境与境外测试工具回传（部分云漏扫/众测平台）需评估数据出境合规；跨境攻击性测试涉及双重违法风险。
- **漏洞披露政策（Vulnerability Disclosure Policy）**：企业应公开接收渠道（security.txt、邮箱）、响应 SLA 与致谢/奖励规则；发现方应遵循**负责任披露（Responsible Disclosure）**：先报告、给修复窗口（如 90 天）、不公开利用细节直至修复——这是"白帽子"的法律与道义安全区。

## 9. 全流程微案例：对 DVWA 靶场走一遍方法论

> 目的：把 PTES 七阶段从"概念"变成"肌肉记忆"。**仅限本地靶场**（Docker 本地运行的 DVWA，`http://127.0.0.1:8080`），实验记录建议归档到 `labs/` 目录。

### 9.1 阶段 1：前期交互（模拟）

自己扮演双方，填一张最小 ROE 表：

| 条款 | 内容 |
| --- | --- |
| 范围 | `127.0.0.1:8080` 单一 Web 应用（DVWA latest，默认密码已改） |
| 类型 | 灰盒（持有一个低权限普通账号） |
| 禁止 | 不做 DoS、不触碰宿主机其他端口、不利用容器逃逸 |
| 时间盒 | 2 小时（防止无休止深挖） |
| 停止条件 | 获得 OS 命令执行即停（证明影响已足够） |

### 9.2 阶段 2：情报收集

```bash
# 主动探测（目标是自己本机容器，属授权范围）
sudo nmap -sV -sC -p 8080 127.0.0.1        # 服务版本 → 笔记 25
whatweb http://127.0.0.1:8080              # 指纹：PHP/XD
curl -s http://127.0.0.1:8080/robots.txt   # 敏感路径
# 浏览器人工观察：登录页、注册功能、页面底部的 "DVWA" 版本提示
```

产出：资产卡一张（技术栈 PHP+MySQL，单入口登录，存在 /vulnerabilities/ 目录结构——DVWA 的菜单即功能清单，真实项目等价物是目录爆破与 JS 分析）。

### 9.3 阶段 3：威胁建模

高价值资产 = 数据库（用户表）与会话；信任边界 = 登录认证；攻击路径假设（按优先级）：
1. 未授权访问弱模块（低安全级别下命令执行模块直接可用）；
2. 认证后注入类（SQLi → 拖库）；
3. 会话/CSRF（cookie 属性与 token 机制）。

### 9.4 阶段 4：漏洞分析（抽样两项，对应 checklist）

- 打勾 checklist 第 14 项（Cookie 属性）：DevTools 看 `PHPSESSID` 是否缺 HttpOnly/Secure；
- 打勾第 22 项（SQL 注入）：在 SQLi 模块提交 `1'`，观察报错即 ERRH-01 与 INPV-05 双命中。

### 9.5 阶段 5：漏洞利用（最小破坏）

```bash
# 命令执行模块（低安全级别）：用无害 payload 证明影响，不反弹 shell
127.0.0.1; id            # → uid=33(www-data) 证明当前应用身份
127.0.0.1; sleep 3       # → 响应延迟 3 秒，证明真实执行
# SQL 注入（配合 Burp，笔记 17）：只证明结构可达，不导出用户真实数据
1' UNION SELECT table_name, table_schema FROM information_schema.tables-- 
```

### 9.6 阶段 6：后渗透（点到为止）

```bash
127.0.0.1; cat /etc/passwd | head -3      # 证明文件系统可读（影响面）
127.0.0.1; ls -la /var/www/html           # 定位 web 根，评估持久化可行性（不实际落盘）
```

按 ROE 停止条件结束：已证明"应用层 RCE + www-data 权限 + 数据库可达"，足够写高危/危急定级；不做提权与横向。

### 9.7 阶段 7：报告（节选）

按 §7.3 模板产出：
- 执行摘要一句版："测试环境存在未授权命令执行与 SQL 注入，攻击者可以完全控制应用并以数据库读取权限获取全部业务数据；根因为安全级别配置与未参数化查询。"
- VULN-001：DVWA Command Injection（危急，CVSS 9.8——网络可达、低复杂度、无权限要求）+ 复现步骤 + 修复建议（白名单输入校验、`escapeshellarg`、禁用危险函数、纵深：容器只读根文件系统）。
- 覆盖矩阵：§6 checklist 30 项中"适用 12 项，已测 12 项，其余不适用（靶场无注册/短信等）"。

**复盘提问**：哪一步如果在真实项目会失败？（提示：无授权、无时间盒、未控制影响——方法论的价值就是把"会做"与"做得对"分开。）

## 10. 常见坑汇总

1. **没有书面授权就开扫**：口头许可不算数；邮件确认也弱于正式授权文件。
2. **Scope 理解错位**：测了"看起来是对方"的资产（CDN、第三方 SaaS）；范围以书面清单为准，模糊处书面澄清。
3. **自动扫完直接写报告**：漏扫器误报不人工验证 = 报告失格；逻辑漏洞漏测 = 覆盖率造假。
4. **证明破坏而非影响**：真的 `--dump` 用户表、真删库验证注入 = 违反数据处理纪律。
5. **报告只堆技术**：管理层看不懂、无法排期，修复推动不了——报告价值等于零。
6. **复现步骤写不清**：换个人按步骤复现失败，可信度崩塌。
7. **时间盒失控**：无休止深挖单点（rabbit hole），牺牲整体覆盖度；按时间盒+优先级止损。
8. **痕迹未清理**：测试账号、上传文件、计划任务留在生产，成为新风险且违反合同。
9. **CVSS 死板套用**：不看环境（资产暴露面、补偿控制）直接抄基础分，导致定级失真。
10. **保密意识松懈**：报告含真实数据未脱敏、通过个人网盘传输——二次泄露事故。
