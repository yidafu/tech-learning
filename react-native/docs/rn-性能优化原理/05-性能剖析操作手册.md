# 性能剖析操作手册：从现象到函数

> 01 篇给了三步法与工具矩阵，回答的是"看什么"；本篇补"**怎么做**"：Android 系统级 trace 怎么采、采到怎么读，Hermes 采样 profile 怎么采、怎么读，React Profiler 夹在中间怎么把"JS 忙"翻译成"哪个组件"。最后给两条完整的收敛路径（滑动掉帧、启动慢），把 01 篇的流程落成可以逐条勾掉的操作。**再次声明：本篇所有"读法示意"都是构造的说明性描述，不是任何真实应用的采集结果**——真实数字永远来自你自己的设备。

## 0. 采集前的四条纪律

1. **用 release（或至少 profileable/debuggable 的非 dev）构建**。dev 构建有类型检查、告警、未压缩代码与调试链路开销（模块八 04、模块九 01 都说过：dev 的性能结论不可信）。Android 上 dev 菜单、FPS 悬浮窗本身就有污染；
2. **场景脚本化**：采集前写清楚操作序列（进入哪个页、滑几下、停在哪），保证前后两次采集可比；
3. **短窗口采集**：trace 抓 5–10 秒、只覆盖目标场景。窗口越长，文件越大、信噪比越差；
4. **多采几轮**：单次 trace 有调度噪声，至少 3 轮看模式是否复现——**复现的模式才是问题，偶发的毛刺可能只是背景噪声**。

## 1. Android 系统级 trace：Perfetto

### 1.1 为什么是它、两条采集路径

`systrace` 命令行工具已从 Android platform-tools 移除，系统级 trace 的标准工具是 **Perfetto**（官方文档也以 Android Studio Profiler + Perfetto 为推荐路径）。两条等价路径：

- **图形路径**：Android Studio → Profiler → "Capture System Activities"（即 System Trace），录制完可在 Studio 里直接看，或导出 `.perfetto-trace` 文件拖到 [ui.perfetto.dev](https://ui.perfetto.dev)；
- **命令路径**（适合脚本化、CI、无 Studio 环境）：写一份 trace 配置，`adb` 推给设备上的 `perfetto` 服务：

```text
# trace_config.txt —— 采集 RN 掉帧问题的常用配置（示意，字段含义见下）
buffers { size_kb: 65536 fill_policy: DISCARD }
data_sources {
  config {
    name: "linux.ftrace"
    ftrace_config {
      ftrace_events: "sched_switch"
      ftrace_events: "sched_wakeup"
      atrace_categories: "sched"    # 调度：线程运行/阻塞
      atrace_categories: "gfx"      # 图形：vsync、RenderThread、帧
      atrace_categories: "view"     # 视图系统：measure/layout/draw
      atrace_categories: "freq"     # CPU 频率（判读"忙"时是否降频）
    }
  }
}
duration_ms: 10000
```

```bash
adb push trace_config.txt /data/local/tmp/
adb shell perfetto --txt -c /data/local/tmp/trace_config.txt \
  -o /data/misc/perfetto-traces/rn_trace
adb pull /data/misc/perfetto-traces/rn_trace .   # 拖进 ui.perfetto.dev 打开
```

配置的含义：`sched` 给出**每个线程何时在跑**（这是三色归因的基础），`gfx/view` 给出**帧与绘制分段**，`freq` 防止误判——线程"慢"可能只是 CPU 降频（大核没上频）而不是代码问题。

### 1.2 怎么读：先找线程，再找帧，再找段

打开 trace 后按三步走。

**第一步：认线程泳道。** RN App 的关键线程命名（因 RN 版本与架构形态而异，以实际 trace 为准）：

| 泳道 | 是谁 | 归因角色（01 篇三色） |
|------|------|---------------------|
| 主线程（通常显示为包名，可能被内核 15 字符上限截断） | Android UI 线程：measure/layout/draw 调度、原生视图操作 | UI 线程色 |
| `mqt_js` 或类似命名 | JS 线程：Hermes 跑 JS、reconciler；**新架构下 commit（含 Yoga 布局）也发生在这条线程的调用栈里** | JS 色（含"布局"的一部分） |
| `mqt_native_modules` 或类似命名 | 原生模块线程：模块方法执行 | 模块侧原生成本 |
| `RenderThread` | 渲染线程：DrawFrame、GPU 提交 | GPU/绘制色 |

**第二步：找帧边界。** Perfetto UI 开启 vsync 高亮后，帧边界呈斑马纹（60Hz 下相邻边界约 16.7ms）。**工作段跨越边界 = 掉帧**：看哪条线程的活跃段压过了边界，三色归因在这一步完成。

**第三步：看段的内容。** 点开超时段，读它内部的 atrace 切片名（示意，非真实采集）：

```text
（示意）JS 线程上一个 28ms 的活跃段，内部切片自上而下：
  runApplication / BatchedBridge.executeJSCall
    ├── ReactNativeJS: render PageList
    ├── NativeModules 模块调用（跨到 mqt_native_modules 的弧线）
    └── ……
（示意）UI 线程上一个 25ms 的活跃段：
  doFrame
    ├── traversal: measure / layout（深嵌套视图的征兆）
    └── draw / ViewRootImpl（新增视图挂载的征兆）
```

判读口诀：

- JS 段超时 → 问题收敛到 JS（进第 2 节）；
- UI 段超时且内部是 measure/layout → 视图层级问题（扁平化、定高，模块九 02）；
- UI 段超时且内部是 draw/挂载 → 原生渲染重（图片解码、过度重绘，模块九 01 的暗坑表）；
- RenderThread 段超时 → GPU 压力（层、阴影、过度绘制）；
- **跨线程弧线**（slice 上的箭头）标出因果链：UI 段的忙常常是"JS 决定新建视图"的结果——不要只治表象。

### 1.3 iOS 侧的等价物

Instruments（Time Profiler 找 CPU 热点、Hangs 诊断主线程卡顿、Animations 看帧）+ 与 Android 同一套 Hermes profile（第 2 节）。思路完全同构：**先定线程，再定段，再进 JS**。

## 2. Hermes 采样 profile：函数级归因

### 2.1 机制：采的是什么

Hermes 内置**采样式** CPU profiler：引擎周期性地记录 JS 调用栈快照（而非埋点计时），导出为 Chrome 兼容的 `.cpuprofile`。两个推论要记住：

- **采样式天然有偏差**：极短但高频的函数可能被低估或漏采，长函数会被准确命中——看分布模式，不要把 12.3ms 之类的小数当精确值；
- **只看得到 JS 栈**：GC、原生代码内部、线程切换造成的时间不在 JS 函数的账户里——**"JS 栈上没有大户但 JS 线程很忙"时，嫌疑转向 GC（模块三 03）与原生模块调用（模块四）**，回 trace 侧找旁证。

### 2.2 采集路径

**路径 A（经典流程，随 RN 版本有差异，以所用版本文档为准）**：dev 菜单 → "Enable Sampling Profiler" → 执行场景 → 停止；trace 文件可用 CLI 拉取并转换成 Chrome 可打开的格式（如 `npx react-native profile-hermes <文件路径>` 一类命令），在 Chrome DevTools 的 JavaScript Profiler 面板查看。

**路径 B（集成的 Performance 面板，较新的 RN 版本提供）**：React Native DevTools（0.76+ 默认调试前端，模块十 04）在较新版本中集成了 Performance 面板——打开 DevTools 的 Performance 标签 → Record → 执行场景 → Stop，得到分层视图：

- **Scheduler 轨道**：React 调度器的更新分相位展示（Update/Render/Commit 等，并发优先级分道）；
- **Components**：组件级火焰图（render/effects/mount 分色）；
- **Thread**：JS 函数火焰图（React 内部默认折叠）。

早期版本里该面板可能需要 Settings → Experiments 手动开启。**用哪条路径取决于你的 RN 版本，但读法一致**（下一节）。

### 2.3 怎么读：self 与 total 的分工

火焰图/表格两个读法：

- **先按 self（自身耗时）排序找叶子**：self 大 = 这个函数自己算得久（排序、JSON、正则、同步循环……），是最直接的优化对象；
- **再看 total（含子调用）找结构**：total 大而 self 小 = 它调用的子树重——沿树往下钻，直到找到 self 大的那层；
- **宽而平的火焰** = 一层调了很多小函数（考虑批量/缓存）；**窄而深的火焰** = 递归或长链路（考虑短路/记忆化）；
- minify 后的函数名是压缩名，需要 sourcemap 符号化才可读（模块九 04 的符号化同一套基建）。

读法示意（构造的说明性 profile，非真实采集）：

```text
（示意）按 self 排序的前三行：
  a.js:112    self 38%   ← 命中：纯计算热点
  b.js:45     self 21%
  gc / 未归因  self 15%  ← GC 占比高：查对象分配率（模块九 04）
（示意）total 视角：PageList.render total 70%、self 3%
  → 沿子树下钻：RowItem.render total 55%，其中 Date 格式化占大头
  → 处方方向：行级 memo + 日期格式化缓存（模块九 03）
```

## 3. React Profiler：把"JS 忙"翻译成"哪个组件"

trace 告诉你 JS 线程忙，profile 告诉你哪个函数热，**两者之间还差一层：这次渲染为什么发生、波及了哪些组件**——这正是 React DevTools Profiler（连接方式见模块十 04）的位置。

操作：打开 Profiler → 点录制 → 在设备上执行场景 → 停止。读法：

1. **commit 时间轴**：每次 commit 一根柱子，柱高≈本次提交耗时。对照操作时间点，看哪些 commit 是"预期外的"（用户只点了一下，却出现一串 commit——级联更新的征兆）；
2. **火焰图**：看哪些组件参与了本次 commit（render 了）。**理想状态：一次状态更新的 commit 只包含状态真正变化的子树**；
3. **渲染原因**：较新的 DevTools 在 commit 详情里给出每个组件"为什么渲染"（props/state/context 变化）——直接指向模块九 03 的处方表：引用相等性、状态放置、context 粒度；
4. **"Highlight updates"**（不录制时的实时模式）：快速肉眼确认 re-render 范围，适合第一轮侦查。

注意 Profiler 的时序是 dev 环境的：**用它定性（谁渲染了、为什么），不用它定量（耗时几毫秒）**——定量交给 release 上的 trace/profile。

## 4. 收敛路径 A：滑动掉帧（完整走一遍）

把 01 篇的流程实例化成 checklist（可对照勾选）：

```text
1. 采集：release 构建 + Perfetto 10s，脚本化"进入商品流，匀速滑动"
2. 三色归因（第 1.2 节）：
   [ ] JS 段超时？→ 3
   [ ] UI 段 measure/layout 超时？→ 视图层处方（扁平化/定高，模块九 02）
   [ ] UI 段 draw/挂载超时？→ 图片/重绘处方（模块九 01 暗坑表）
   [ ] RenderThread 超时？→ GPU 处方（层/阴影）
3. React Profiler 定组件（第 3 节）：
   [ ] 滑动中出现了哪些 commit？波及组件是哪些？
   [ ] 渲染原因：内联 props？context？状态放置过高？
4. Hermes profile 定函数（第 2 节）：
   [ ] self 大户是业务函数还是工具函数？
   [ ] GC 占比高不高（分配率问题）？
5. 处方 → 复测：只改一处，回 1 再采一轮
   [ ] 帧模式改善？归因段瘦身？——没有改善就回滚改动，回 3 重查
```

常见漏网（01 篇列过，归因时再核对）：context 值未 memo（Profiler 的"渲染原因"会显示 context 变化）；列表 item 不定高（Yoga 缓存失效，trace 上表现为 layout 段反复出现）；onScroll 高频 setState（trace 上 JS 段随滚动持续高密度活跃）。

## 5. 收敛路径 B：启动慢

启动的采集组合是"打点 + trace"，不是 profile（采样窗口很难对齐）：

1. **打点分段**：两端各有启动性能标记（Android ReactMarker / iOS 的性能日志，模块二 01/02 的链路节点），再加上业务侧 TTI 打点（首屏可交互）。得到"时间花在哪一段"的第一手数据；
2. **trace 覆盖冷启动**：Perfetto 从进程创建录到首帧（窗口放宽到 30s 级）；
3. 按段归因（示意结构，非真实数据）：

| 段超时 | 典型成因 | 处方落点 |
|--------|---------|---------|
| 进程→Application 完成 | so 初始化、第三方 SDK 同步 init | 推迟非必需 init |
| → bundle 加载完成 | 包体过大、读取慢 | 模块八 04：字节码/构成分析/拆包 |
| → runApplication | evaluate 全量模块执行 | inline requires、依赖治理（模块八 04） |
| → 首帧 | 首屏组件重、同步数据拉取 | 模块九 03：首屏拆分、骨架屏、数据并行 |

4. 复测用同一打点口径，对比同一段的缩减。

## 6. 工具矩阵（本篇操作版）

| 层 | 工具 | 操作入口 | 输出物 |
|----|------|---------|--------|
| 线程/帧 | Perfetto（Android）/ Instruments（iOS） | Studio Profiler 或 `adb shell perfetto`；Instruments | trace：线程泳道 + 帧边界 |
| 组件 | React DevTools Profiler | `npx react-devtools` 或 RN DevTools | commit 时序 + 火焰图 + 渲染原因 |
| 函数 | Hermes Sampling Profiler | dev 菜单 + CLI 转换，或 RN DevTools Performance 面板 | `.cpuprofile` / 分层火焰图 |
| 内存 | 平台内存工具 + JS heap（模块九 04） | Studio Profiler / Instruments / CDP | 内存曲线与快照 |

三级放大、不要跳步（01 篇）：**trace 没归因到线程之前，不打开 Profiler；Profiler 没圈定组件之前，不采 profile**——顺序反了就是大海捞针。

## 小结

- 采集纪律四条：release 构建、场景脚本化、短窗口、多轮复现——没有这四条，后面的读法都是噪声上的精读；
- Perfetto 三步读法：认线程泳道（mqt_js / mqt_native_modules / RenderThread / 主线程）→ 找帧边界（跨界即掉帧）→ 读段内切片定性质；跨线程弧线给出因果链；
- Hermes 采样 profile 只看 JS 栈：self 找叶子热点、total 钻结构、GC 与原生时间是盲区要回 trace 找旁证；React Profiler 管"为什么渲染"（定性不定量）；
- 两条收敛路径（掉帧、启动）都已 checklist 化——性能工作的产出应当是"复现的模式 + 处方 + 复测对照"，而不是一次性的灵光；
- RN DevTools 的集成 Performance 面板是新趋势：三层视图（Scheduler/Components/Thread）正对应本篇的三级放大。
