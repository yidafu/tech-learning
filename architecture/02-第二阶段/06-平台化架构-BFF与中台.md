## 5.1 BFF（Backend for Frontend）

**概念**：为**每一种前端体验**配一个专属的后端聚合层，由对应的端团队拥有（SoundCloud 团队 2015 年提出）。微服务化之后它解决两类新问题：

1. **聚合问题**：一个页面的数据散在 N 个服务里，客户端要么串行调 N 个接口（延迟叠加、可用性相乘，见 2 节自测 3），要么让网关代劳——但网关一旦承担聚合编排，就滑向“上帝层”（见 2.2）；
2. **差异问题**：小程序要轻、运营后台要全、配送员端要位置与路线。一个“通用 API”被迫长成大而全的 DTO：每个端为自己用不到的字段付流量，更危险的是为不该看到的字段埋雷。

❌ **反例：一个“通用”聚合接口喂所有端**

```kotlin
// "通用"订单详情：一个 DTO 同时服务 C 端小程序、配送员端、运营后台
data class UniversalOrderDetail(
    val orderId: OrderId,
    val status: String,
    val courierPhone: String?,           // 只有配送员端需要；C 端每次白白传输 null
    val internalCostPrice: BigDecimal,   // 财务域的成本价——跟着"通用模型"泄漏给 C 端！
)
// 接着"如果是小程序就删掉 route 字段"的 if 分支开始滋生——上帝层 2.0 的起点
```

问题：C 端为不用的字段付流量与序列化开销；`internalCostPrice` 这类财务域字段顺着重用的链路泄漏给不该见的端——**通用 DTO 是数据泄漏的温床**；任一下游字段变更，三个端全部回归测试；“按端裁剪”的 if-else 在聚合层越长越多。

✅ **修正：每端一个 BFF，各自裁出窄类型**

```kotlin
// C 端 BFF 只依赖订单客户端——想泄漏成本价，类型上就不可能
data class CustomerOrderCard(val orderId: OrderId, val status: String)

// 配送员端 BFF：只聚合配送员要用的最小字段
data class CourierTaskCard(val taskId: TaskId, val window: String,
    val community: String, val receivable: BigDecimal)   // 空桶应收

class CendBff(private val orders: OrderClient) {
    fun card(orderId: OrderId): CustomerOrderCard =
        orders.detail(orderId).let { CustomerOrderCard(it.id, it.status) }
}

class CourierBff(private val delivery: DeliveryClient) {
    fun todayBoard(courierId: CourierId): List<CourierTaskCard> =
        delivery.tasks(courierId).map {
            CourierTaskCard(it.id, it.window, it.community, it.receivable)
        }
}
```

聚合往往还要**并行**调下游（三个下游各 200ms：串行 600ms，并行约 200ms），协程写法：

```kotlin
suspend fun todayBoard(courierId: CourierId): BoardResponse = coroutineScope {
    val tasks = async { delivery.todayTasks(courierId) }
    val route  = async { delivery.routeOf(courierId) }
    BoardResponse(route.await(),
        tasks.await().map { TaskCard(it.id, it.window, it.community, it.receivable) })
}
```

**网关 vs BFF 的职责边界**：

| | API 网关 | BFF |
|---|---|---|
| 关注点 | 横切技术关注点 | 纵向体验关注点 |
| 职责 | 路由、鉴权、限流、协议转换 | 聚合、裁剪、端适配、体验编排 |
| 归属团队 | 平台团队 | 对应端的前端/端团队 |
| 数量 | 通常一个 | 每端一个 |
| 业务规则 | 不应有 | 允许“体验编排”，领域规则仍须下沉 |

边界判据：**换一种表达方式的需求放 BFF，换一种业务事实的需求下沉到领域服务。**“空桶应收怎么算”是费率政策（业务规则）→ 归押金/营销服务；BFF 只拼装展示。BFF 里重算价格是经典事故源——政策一变，各端算出的价格不一致。

### 三类职责判据表：一件需求，先问“它因什么而变”

上面的边界判据把“网关 / BFF / 领域服务”三层定了个方向，但落到日常评审桌上还不够用——真实的争议需求往往两头都沾。这里给出一张更完整的判据表，判据的核心不是“这个需求听起来像谁的事”，而是**它因什么而变**：因端而变 → BFF；因业务事实而变 → 领域服务；因流量与安全而变 → 网关。变化原因放错层，腐化只是时间问题。

| 职责 | 判据（变化原因） | 典型工作 | 正例（到家平台） | 反例（错放在哪层） |
|---|---|---|---|---|
| 聚合与裁剪 → **BFF** | 因端而变：换一个端，取哪些数、怎么展示就不同 | 并行取数、字段裁剪与窄 DTO、展示编排、兜底文案 | 小程序下单页一次请求聚合商品+库存+配送时效；库存域宕机展示“库存未知”而不是白屏 | 把“满 3 桶减 5 元”的促销计算写进 C 端 BFF——活动口径一改，三端的 BFF 各改一遍，还因各自理解出现细微差别 |
| 业务规则 → **领域服务** | 因业务事实而变：换任何端，规则的结果都一样 | 价格与押金计算、库存可售判定、风控、状态机流转 | “空桶应收多少”由押金域按费率政策算好，BFF 拿现成数字展示 | BFF 里重算价格：政策一变，各端展示价与下单实际成交价不一致——经典资损事故源 |
| 策略控制 → **网关** | 因流量与安全而变：对所有端的所有流量一视同仁 | 限流、鉴权、灰度分流、协议转换、审计埋点 | 小程序渠道设独立的限流阈值；JWT 在网关校验一次，后端只做最小复核 | 把“会员才可见某 SKU”写成网关插件——业务判断进了策略层，网关成了隐形业务决策者，且不在任何业务回归测试的覆盖范围里 |

评审时用**三问**逐条过：

1. 换一个端，结果会不一样吗？——会 → BFF（且只是**取数与展示**层面不一样）。
2. 换一个营销活动、换一版政策，结果会不一样吗？——会 → 领域服务。
3. 它跟“是谁在访问”有关、而跟“访问什么”无关吗？——是 → 网关。

有一个高频陷阱要单独点破：**“按端返回不同结果”不等于“这是端差异”**。“会员价只在 APP 端生效”听起来像端适配，实质是**定价策略**（因营销政策而变）——正解是领域服务按渠道与身份出价，BFF 与网关都不参与计算、只透传结果。端差异必须止步于“取哪些数、怎么展示”，绝不能延伸到“算出什么值”。判据表的这三行合起来，其实就是主笔记 2.2“网关只做策略不做业务”那句话的全集展开。

### 可运行示例：小程序下单页 BFF——并行聚合 + 降级裁剪

判据表第一行“聚合裁剪归 BFF”的工程落地，就是下面这个桶装水小程序的下单页：一次请求要拿到**商品域**（标题与价格）、**库存域**（余量）、**配送时效域**（送达时间窗）三个域的数据。三域并行取数；并按“关键依赖 vs 非关键依赖”预设降级策略——**商品域宕机就整页失败（fail fast：不存在没有商品的下单页），库存与时效宕机则只裁剪对应板块**：库存展示为“库存未知：可正常下单，若缺货自动全额退款”，而不是让用户面对一个白屏。

（示例为免第三方依赖，用 JDK `CompletableFuture` 表达并行聚合；生产中 Kotlin 常用协程 `coroutineScope + async`，结构与上文片段完全同构。）

```kotlin
import java.util.concurrent.CompletableFuture
import java.util.concurrent.TimeUnit

// ============ 下游三域（模拟微服务客户端） ============

/** 商品域：页面主数据 */
data class ProductInfo(val skuId: String, val title: String, val priceFen: Long)

/** 库存域读结果：两种形态——正常给数，降级给"未知" */
sealed interface StockView {
    data class Available(val remain: Int) : StockView
    data class Unknown(val reason: String) : StockView   // 降级态：不阻塞页面，只换文案
}

/** 配送时效域 */
data class DeliveryEta(val community: String, val slotText: String)

class ProductClient {
    fun detail(skuId: String): ProductInfo {
        Thread.sleep(150)                       // 模拟 RPC 耗时
        return ProductInfo(skuId, "农夫山泉 19L 桶装水（会员价）", 2390)
    }
}

/** 库存域客户端：本次演示向它注入故障 */
class InventoryClient(private val fail: Boolean) {
    fun remainOf(skuId: String): Int {
        Thread.sleep(120)
        if (fail) throw IllegalStateException("inventory rpc timeout: sku=$skuId")
        return 36
    }
}

class DeliveryClient {
    fun etaOf(community: String): DeliveryEta {
        Thread.sleep(130)
        return DeliveryEta(community, "今日 18:00-20:00")
    }
}

// ============ BFF：小程序下单页聚合器 ============

/** 下单页窄模型：只裁出小程序这一屏要用的字段，多余字段在类型上就不存在 */
data class OrderPageData(
    val title: String,
    val priceText: String,
    val stockText: String,
    val etaText: String,
    val degradedDomains: List<String>,   // 本次请求降级了哪些域——打日志/上报，可观测
)

class MiniProgramOrderPageBff(
    private val products: ProductClient,
    private val inventory: InventoryClient,
    private val delivery: DeliveryClient,
    private val timeoutMs: Long = 800,
) {
    /** 单域降级包装：超时/异常 → 记账 + 兜底值。生产中对应熔断 + 兜底文案 */
    private inline fun <T> degrade(
        domain: String,
        degraded: MutableList<String>,
        fallback: () -> T,
        call: () -> T,
    ): T = try {
        call()
    } catch (e: Exception) {
        degraded += domain
        println("  [BFF] $domain 降级：${e.cause ?: e}")
        fallback()
    }

    fun loadPage(skuId: String, community: String): OrderPageData {
        val t0 = System.currentTimeMillis()
        val degraded = mutableListOf<String>()

        // 三域并行取数（JDK CompletableFuture；等价的协程写法 coroutineScope+async 见上文片段）
        val productF = CompletableFuture.supplyAsync { products.detail(skuId) }
        val stockF   = CompletableFuture.supplyAsync { inventory.remainOf(skuId) }
        val etaF     = CompletableFuture.supplyAsync { delivery.etaOf(community) }

        // 关键依赖：商品域挂了 -> 整页失败（fail fast），不存在"没有商品的下单页"
        val product = productF.get(timeoutMs, TimeUnit.MILLISECONDS)

        // 非关键依赖：库存/时效挂了 -> 降级裁剪，页面照常出
        val stock = degrade("库存", degraded,
            fallback = { StockView.Unknown("库存暂时查询不到") },
        ) { StockView.Available(stockF.get(timeoutMs, TimeUnit.MILLISECONDS)) }

        val eta = degrade("配送时效", degraded,
            fallback = { DeliveryEta(community, "配送时效暂不可用") },
        ) { etaF.get(timeoutMs, TimeUnit.MILLISECONDS) }

        println("  [BFF] 三域并行聚合耗时 ${System.currentTimeMillis() - t0} ms" +
            if (degraded.isEmpty()) "" else "（降级域：$degraded）")

        return OrderPageData(
            title = product.title,
            // 仅做展示格式化；价格数值本身来自商品域——BFF 不算价，只搬运
            priceText = "¥" + (product.priceFen / 100) + "." +
                (product.priceFen % 100).toString().padStart(2, '0'),
            stockText = when (stock) {
                is StockView.Available -> "有货，剩余 ${stock.remain} 桶"
                is StockView.Unknown -> "库存未知：可正常下单，若缺货自动全额退款"
                // 兜底承诺的兑现（缺货退款）是订单域的业务规则；BFF 只负责把承诺展示出来
            },
            etaText = eta.slotText,
            degradedDomains = degraded.toList(),
        )
    }
}

fun main() {
    println("== 场景一：三域全部正常 ==")
    val healthy = MiniProgramOrderPageBff(ProductClient(), InventoryClient(fail = false), DeliveryClient())
    println(healthy.loadPage("sku-water-19l", "幸福小区"))

    println()
    println("== 场景二：库存域故障 -> 降级裁剪，整页不失败 ==")
    val degraded = MiniProgramOrderPageBff(ProductClient(), InventoryClient(fail = true), DeliveryClient())
    println(degraded.loadPage("sku-water-19l", "幸福小区"))
}
```

实测输出（kotlinc 2.2.20 编译运行；耗时数字随机器浮动）：

```text

== 场景二：库存域故障 -> 降级裁剪，整页不失败 ==
```

五个工程要点，每一条都对应判据表的一行：

1. **并行聚合是 BFF 的存在理由之一**：三域各 120~150ms，串行约 400ms，并行后整页约 170ms。可用性上同样成立：若三个下游各自 99.9% 可用且互相独立，串行调用的页面可用性按乘法掉到约 99.7%（每年多出约 26 小时不可用），“并行 + 按域降级”能把它救回来——降级把“三域同时在线”这个前提从可用性公式里拿掉了。
2. **降级是按域预设的策略，不是临场发挥**：`degrade` 包装器统一了“超时 → 记账 → 兜底值”三件事；哪些域可降、降到什么文案，是评审时定好的产品决策，写进代码里的每一行 fallback 都应该能在评审记录里找到出处。
3. **兜底文案里藏着业务承诺**：“缺货自动全额退款”这句话的**兑现**是订单域的规则（下单后缺货 → 全额退款，见第三阶段分布式事务），BFF 只负责展示文案。这就是“聚合裁剪归 BFF”的精确边界——**承诺的展示在 BFF，承诺的兑现下沉领域**。
4. **降级可观测**：`degradedDomains` 随响应返回并上报，可观测性大屏上“库存降级率”突增，就是库存域故障的最早告警——先于用户投诉，这正是主笔记 2.2 服务治理里“降级要有开关也要有仪表”的意思。
5. **BFF 只做读聚合，不做写编排**：下单页“点一次按钮由 BFF 依次调订单、库存、支付”是反模式——跨域写的一致性归领域服务与事件编排（`OrderPlaced` 之后各订阅者各干各的，见[事件驱动架构](04-事件驱动架构.md)）；BFF 若编排写事务，就从“聚合层”变成“分布式事务协调者”，重试、补偿、幂等全套复杂度一层不少地搬到最靠近前端的地方，还要面对“第二步失败第一步已生效”的悬置状态。读可以拼，写必须归位。

对照反例：把上面场景交给网关做——网关插件里写“取三个域、拼一个响应、库存宕机给默认值”，路由引擎从此背上了页面编排；下一个端（配送员端）需要类似聚合时，要么复制插件，要么插件里长出 `if (channel == ...)`。上帝层网关就是这样长成的（呼应 2.2 的反例）。

### BFF 数量演进：单 BFF → 按端多 BFF → 自助式 BFF / GraphQL

“每端一个 BFF”是终态而不是起点。BFF 的数量应该跟着**团队结构的分裂压力**走，而不是跟着端数走——这是康威定律（见[康威定律补充](../01-第一阶段/05-康威定律-补充.md)）的正向应用：让接口结构镜像真实的协作关系。

| 阶段 | BFF 拓扑 | 适用团队规模 | 进入下一阶段的信号 | 这一阶段的典型事故 |
|---|---|---|---|---|
| 0 无 BFF | 客户端直连网关 / 网关薄聚合 | 单端或两端、1~2 个全栈团队 | 页面开始“一次点调 N 个接口”，首屏延迟叠加、可用性相乘 | 聚合逻辑塞进网关，网关开始长业务 |
| 1 单 BFF | 一个聚合服务服务所有端 | 2~3 个端、一个前后端团队 | 代码里出现 `if (clientType == ...)`；各端互相等排期 | 单 BFF 变“上帝层 2.0”：任何端的需求都排队，改一处全端回归 |
| 2 按端多 BFF | 每端一个（experience API），页面 + BFF 同一团队竖切 | 3~5 个端、端团队各自独立 | 新端接入时，下游客户端封装、错误码映射等样板在多个 BFF 里复制粘贴 | 公共逻辑（鉴权透传、埋点规范）漂移出 N 份不一致的版本 |
| 3 自助式 BFF / GraphQL | 平台团队维护 BFF 框架与下游客户端库，端团队自助写查询 / schema | 端 ≥5、端团队工程能力强、GraphQL 治理三件套跟得上 | —— | 治理缺位：恶意复杂查询打穿下游、schema 无版本纪律、N+1 取数拖垮域服务 |

三条纪律贯穿所有阶段：

1. **拆分时机看排队，不看端数**：不是“端多了就拆”，而是“各端团队开始互相等排期”那一刻——组织排队是拓扑错误的最早信号，比代码里的 if 分支出现得更早。
2. **公共逻辑下沉为库，不下沉为服务**：多 BFF 之后，鉴权上下文解析、错误码映射、埋点规范沉淀成各 BFF 共用的公共库（代码复用，无运行时集中点），而不是再立一个“BFF 平台服务”——那等于把排队问题换了个地方重演。
3. **每一步可回滚**：单 BFF 拆成按端多 BFF 时，网关按渠道把流量在旧单 BFF 与新端 BFF 之间灰度切换，随时切回（渐进迁移与可逆性，同主笔记 2.5 的手法在前端侧的应用）。

GraphQL 作为阶段 3 的载体值得单独一提：它把“字段裁剪”从 BFF 团队手里交还给端自己——端自定义查询 = 端自己写裁剪，“BFF 该有几个”的问题于是消解为“一个 GraphQL 网关 + 每域一个 resolver”。但灵活性是用治理面换的：**查询复杂度限制**（防止一条查询拖垮下游）、**持久化查询**（APP 内置白名单查询，不允许运行时任意拼）、**DataLoader 批量取数**（解 N+1）三件事没做，GraphQL 的灵活性会以打穿下游的方式原样还回来。治理没预算的团队，停在阶段 2 反而是更优解。

**多租户视角的一段补充**：如果这套端服务的是 SaaS 产品（工单中心卖给几十家企业的画像），BFF 还要多背一条纪律——**租户上下文只透传、不翻译**：BFF 从令牌解析出租户 ID 后原样传给每个下游，聚合层不缓存、不改写租户数据；隔离与配额的执行点仍在网关与数据面服务（策略由控制平面下发，控制面/数据面分离的心智模型），BFF 不做“这个租户能不能用这个功能”的判断。否则 BFF 就成了第二个需要审计隔离逻辑的地方——串租户事故最喜欢藏身之处。

### 上帝层网关 / BFF 腐化：五个信号与减脂三步

主笔记 2.2 已把“上帝层网关”列为微服务最常见的腐化。定义落到日常评审还是抽象，五个信号更好用——**出现任意两个，就该给这一层减脂**：

1. **业务分叉滋生**：BFF / 网关代码里出现 `if (clientType == ...)` 或 `if (activityId in ...)` 之类的**计算**分支（价格、优惠、资格判断），而不只是取数分支。信号强度最高的一个，出现即处理。
2. **绕过领域服务取数**：BFF 直连数据库、直读别的服务的从库——聚合层拿到了数据所有权，契约约束从此对它失效（数据所有权纪律见 2.1 / 2.3）。
3. **反向协同发布**：改一个 BFF 需要与多个下游服务约同一天发版——说明 BFF 依赖了下游**未契约化的内部行为**，而不是版本化契约（契约纪律见 2.6）。
4. **体积与页面数严重失衡**：一个 BFF 的接口数、代码量远超它所服务的端的页面复杂度；改一行展示文案需要全量回归。
5. **无主逻辑**：review 时问“这段为什么在 BFF”，没人答得上来——逻辑沉淀已经失控，只是还没爆炸。

减脂三步（顺序有讲究，每步独立可回滚）：

1. **逻辑下沉**：把业务计算搬回领域服务——先在领域服务开新接口，BFF 改读新接口，观察一个周期后删掉旧实现（绞杀者式迁移，同主笔记 2.5 四步法）。回滚点：BFF 切回旧本地实现。
2. **契约收紧**：对端返回收窄为窄 DTO（多余字段在类型上删除，而不是标 `@Deprecated`）；对下游只依赖版本化契约、禁直连库；BFF 与下游之间补消费者驱动契约测试（见主笔记 2.6）。回滚点：新旧 DTO 字段并存期。
3. **只留编排**：最终验收标准一句话——**删掉任何一个领域服务，BFF 必须要么编译报错、要么走显式降级路径，绝不能自己默默补一段业务逻辑**。做到这一条，“上帝层”这顶帽子就摘了；做不到，说明还有第 4、第 5 条信号没清干净。

**权衡**：换来端差异化、窄接口、团队自治（端团队拥有“页面 + BFF”整条竖切，接口对齐沟通边界——康威定律的又一次显形）；付出层数 +1（每请求多一跳，但并行聚合通常净赚）、公共逻辑重复（要沉淀 BFF 公共库）、职责漂移风险（BFF 长出业务就成上帝层 2.0，用上面的判据守住）。变体：**GraphQL 天然适合做 BFF**（端自定义查询 = 端自己写裁剪）；**微前端 + BFF** 把竖切推到前端侧，是微服务思想在前端的对偶。

## 5.2 中台架构

**概念**：把多条业务线**真共享**的能力沉淀为可复用的平台层，前台保持轻薄、快速试错——2015 年阿里提出“大中台、小前台”（借鉴 Supercell 小团队 + 公共游戏组件的组织方式），2021 年后多家大厂陆续“拆中台”。三种形态：

| 形态 | 沉淀什么 | 到家平台对应 | 深入分册 |
|---|---|---|---|
| 业务中台 | 共享的**领域能力**（用户/支付/营销/调度） | 支付中台、调度中台 | DDD 战略设计（[第四阶段](../04-第四阶段/01-架构方法论.md)） |
| 数据中台 | 统一的数据采集—加工—服务 | 三条线共用的经营报表与用户画像 | 数据架构（[第三阶段](../03-第三阶段/01-分布式系统核心技术.md)） |
| 技术中台 | 基础设施（微服务框架/MQ/K8s/监控） | 就是本阶段与第三、五阶段讲的那些基础设施 | [第三阶段](../03-第三阶段/01-分布式系统核心技术.md)、[第五阶段](../05-第五阶段/01-工程化与运维视角.md) |

**关键认知**：中台不是一种新的部署或代码风格，而是**微服务 + DDD + 平台化组织**在多业务线公司里的组织级组合。本阶段其他风格回答“一个系统怎么组织”，中台回答“**一个公司的一批系统怎么组织**”——所以判断能不能中台化的标尺，仍然是限界上下文：**共享的是同一个领域，还是只是同名概念？**

主线延伸：桶装水公司长成“到家服务平台”，三条业务线：桶装水商城、家电清洗、家政保洁。共享的：用户与地址、支付与结算、营销与优惠券、上门调度（送水排线与保洁排班同构）。各自独有的：商品域、服务流程域、押金（桶装水独有）。

❌ **反例 1：“同名即同域”的通用订单中台**

```kotlin
// 想用一套"通用订单"模型同时承载 买水、家电清洗、保洁 三条线
data class UniversalOrder(
    val orderId: OrderId,
    val userId: UserId,
    val items: List<ItemDto>,            // 买水是 SKU+桶数，保洁是服务+时长——语义已经对不上
    val depositBuckets: Int? = null,     // 桶装水私有字段挤进"通用"模型
    val cleanerSkillLevel: Int? = null,  // 家政私有字段
)

fun feeOf(o: UniversalOrder): String = when {        // 每条线的特殊性 = 一个分支
    o.depositBuckets != null -> "买水：水费 + 押金"
    o.cleanerSkillLevel != null -> "保洁：按技能等级计价"
    else -> "兜底：谁知道这是哪条业务的订单"
}
```

问题：三条线的“订单”根本不是同一个限界上下文（送水没有“排班”，保洁没有“楼层费”——语言都不一致，见 2.1 拆分依据第一行）；通用模型靠可空字段 + `when` 分支吸收差异，**每接一条新业务线就长一截**；所有线的需求都排队等中台团队排期——中台成为全局瓶颈；康威定律：这个中台必然长成横跨所有业务线的巨大沟通枢纽。

✅ **修正：中台沉淀“语义一致”的能力，前台保留自己的领域编排**（本例已实际编译运行验证）

```kotlin
// 支付中台：收钱、退款、对账在三条线语义一致——真共享的领域能力
interface PaymentPlatform {
    fun charge(request: ChargeRequest): PaymentReceipt   // 版本化契约 + SLA
}

// 前台一：桶装水——自己的订单领域 + 押金语义，前台不是"薄 UI"
class WaterOrderService(private val payment: PaymentPlatform) {
    data class WaterOrder(val no: String, val sku: String, val buckets: Int) {
        val amount get() = buckets * 15
    }
    fun place(sku: String, buckets: Int): PaymentReceipt {
        val order = WaterOrder("W-2026-001", sku, buckets)
        return payment.charge(ChargeRequest(order.no,
            BigDecimal(order.amount + buckets * DEPOSIT_PER_BUCKET)))   // 含押金：前台自己懂
    }
}

// 前台二：家政保洁——同一个支付中台，完全不同的订单领域
class CleaningOrderService(private val payment: PaymentPlatform) {
    data class CleaningOrder(val no: String, val service: String, val hours: Int) {
        val amount get() = hours * 60
    }
    fun place(service: String, hours: Int): PaymentReceipt {
        val order = CleaningOrder("C-2026-001", service, hours)
        return payment.charge(ChargeRequest(order.no, BigDecimal(order.amount))) // 按小时计费，无押金
    }
}
```

运行两个前台：同一个支付中台，一笔收款含押金 40 元、一笔按小时计费无押金——**能力复用，语义各归其位**。判据一句话：**多条业务线在这个能力上的语义一致吗？**支付（收/退/对账）一致 → 中台；订单（各线模型完全不同）→ 留在各自前台。中台吸收合理差异用**扩展点（SPI）**而不是 if-else（如支付中台的“分润规则”由接入方注册自己的实现）。

（上例连同分润 SPI 的完整可运行版已在 kotlinc 2.2.20 下编译运行验证：桶装水下单一笔收款 **70 元**（水费 2×15=30 + 押金 2×20=40）、保洁按小时一笔 **180 元**；两条线各自注册分润规则后，同一笔 100 元分别分润为 `{平台=100}` 与 `{平台=60.0, 配送员=40.0}`——中台核心零改动，差异全部由扩展点吸收。）

### 能力沉淀判据四问：四问全过才沉

“多条业务线语义一致吗”是方向判据，落到立项评审还需要四道可操作的问句——**四问全过才沉；任何一问不过，就用 5.3 的轻量路线过渡，而不是硬沉**：

1. **多线复用吗？**——现在有几条线在用？未来半年有几条**已立项**的线明确要用？“以后可能有”不算数。少于 2 个真实消费方，沉淀的契约成本就没有分摊者（YAGNI 的组织级版本）。
2. **语义稳定吗？**——这个能力在不同业务线下是不是同一个含义、且核心语义很少变？支付（收/退/对账）十年不变 → 过；“订单”三条线三种含义 → 第一问就过不去。语义还在漂移的能力一旦沉淀，之后每次漂移都是 N 方参与的契约变更。
3. **规模效益吗？**——各线自建 N 份的总成本，对比“平台一份 + 定制成本 + 排队成本”孰低？给个现实校准：平台团队不足 3 人却要服务 5 条线，排队成本大概率吞掉全部复用收益——规模效益不只看能力的重复度，也看平台团队的承载力。
4. **可标准化接口吗？**——能力能否用“稳定契约 + SLA + 扩展点”表达？必须深入各线内部细节才能接入的（比如“调度”要听懂每条线自己的排班语言），说明抽象还没长成，先别沉。

四问对照到家平台三条线逐能力过一遍：

| 能力 | 问1 多线复用 | 问2 语义稳定 | 问3 规模效益 | 问4 可标准化 | 结论 |
|---|---|---|---|---|---|
| 支付与结算 | 3/3 条线 | 收退对账语义一致 | 各自对接支付渠道成本高 | 契约 + 分润 SPI 成熟 | **沉** |
| 用户与地址 | 3/3 条线 | 一致 | 三套账号体系合并成本极高 | 契约稳定 | **沉** |
| 上门调度 | 送水排线 + 保洁排班同构 | “按地理与时间窗排人排车”一致 | 排线算法自研成本高 | 需按线扩展班次语义，SPI 可表达 | **沉（带扩展点）** |
| 订单域 | 每线模型完全不同 | 不一致 | 无 | 不可标准化 | **不沉，留前台** |
| 桶押金 | 仅桶装水一条线 | —— | 无规模效益 | —— | **不沉** |

注意“沉（带扩展点）”这一档：上门调度过了四问，但问 4 是勉强过——线间差异（班次、时段、技能标签）用 SPI 由接入方注册自己的语义来吸收，而不是往通用模型里塞可空字段。这与上面修正版代码里 `PaymentPlatform` 加分润规则是同一手法：**扩展点开在“接入方确实各不相同”的位置，契约冻结在“大家确实相同”的位置**——扩展点开错位置（把私有语义开成公共 SPI）同样会腐化，只是速度慢一点。

❌ **反例 2：前台薄成“纯 UI”**。若前台没有自己的领域与编排，做个“会员日买三送一”都要中台排期改价格引擎、等一个月——“小前台”的“小”应指**边界小而完整**（接口 + 数据 + 团队三位一体，同 2.1 微服务的“微”），不是能力被抽干。

**权衡与退潮教训**：中台买的是**复用 + 新业务线启动速度**，付的是**约束（契约）、排队（需求瓶颈）、定制成本（扩展点）**，还要配套组织机制（中台团队与业务团队的双向契约）。2021 年后多家公司退潮，正是权衡的另一面显现：业务差异大、创新求快时，中台从加速器变瓶颈；业务同质性高（连锁复制同一模式）时依然有效。**中台是组织决策，不是技术升级**——没有真实的多业务线复用诉求，单业务线上中台等于自缚手脚（对照 2.3 的审判：单业务线的桶装水商城，结论同样是模块化单体）。国际上的对应争论：数据侧的 Data Mesh（数据所有权下放业务域）vs 中心化数据平台，是同一场“集中复用 vs 域自治”权衡的两种答案。

**中台退潮解剖：四个病根的症状、根因与解药**

上文“权衡与退潮教训”把退潮归因于权衡的另一面显现；落到解剖台上，真实的失败模式收敛为四类。逐类对号的用处在于：**你的中台若有其中一类症状，解药是具体的，不必整体推翻**——反过来，四类症状齐了，救活的成本多半高于重来。

| 病根 | 典型症状 | 根因 | 解药 |
|---|---|---|---|
| **抽象错层** | 通用模型塞满可空字段与 `when` 分支，每接一条线长一截；“同名即同域” | 把同名概念当同一领域沉淀（语义不一致硬抽象），错把“全公司词汇表”当“限界上下文” | 回到限界上下文判据（DDD 战略设计，[第四阶段](../04-第四阶段/01-架构方法论.md)展开）：只沉语义一致能力；已错的把私有线逐步绞杀回前台（主笔记 2.5 手法） |
| **组织错配** | 业务需求排队一个月起步；业务团队绕开中台私建影子服务 | 中台团队按“复用率/调用量”考核而非业务价值；没有需求分级与双向契约机制 | 双向契约（业务方提优先级、中台承诺 SLA 与排期透明）、业务方驻场共建；组织机制不肯改就拆——中台是组织决策，技术补救无效 |
| **契约僵化** | 接新业务线要改中台核心模型；中台升级全线被迫跟进回归 | 契约冻结在第一版认知上，缺扩展点、缺多版本共存 | 扩展点（SPI）吸收合理差异、契约版本化并保留新旧版本并存期、向后兼容纪律（见主笔记 2.6） |
| **过度平台化** | 只有一条线用的能力也“先平台化”；平台团队臃肿，业务小团队处处交“平台税” | 把中台当技术升级立项、为平台而平台；没有消费方也要“先建生态” | 四问逐能力复审，砍掉单线能力；确立“先有 ≥2 个真实消费方，再有平台”的立项铁律 |

四类病根里，**抽象错层**与**契约僵化**是技术问题，可以修；**组织错配**与**过度平台化**是决策问题，只能改组织或者撤销。判别你遇到的是哪一类，决定你的动作是“改代码”还是“拆组织”——拿错药方的改造，是中台项目里最常见的二次浪费。

**平台工程 vs 中台：国际话术与国内话术的异同**

2020 年代国际上兴起的 Platform Engineering（平台工程）常被拿来与“中台”互译。两者确实同源——都是“把共性能力平台化，让业务团队专注差异”，技术中台那一层几乎可以无损互换。但有三处实质差异，翻译时最容易丢：

1. **自服务是第一原则**：平台工程的核心交付物是 IDP（Internal Developer Platform，内部开发者平台）——业务团队**自助**取用环境、流水线、脚手架与可观测性基线，平台团队做的是产品化入口（控制台 / CLI / 模板市场），而不是“提需求 → 排期 → 等交付”。国内中台高潮期最大的痛点“排队”，在平台工程话语里恰恰是被点名消灭的对象——**排队存在，就说明它还不是平台，只是外包队**。
2. **范围收缩在技术侧**：平台工程明确只做技术基础设施（CI/CD、K8s、可观测性、安全基线），**不做业务语义层**——没有“业务中台”这个对应物。业务能力的复用由领域团队之间以共享库、内部开源、能力市场的方式自组织（正是 5.3 的三条轻量路线）。
3. **组织假设不同**：中台预设“中心化平台团队沉淀能力给前台用”的强中心结构，平台团队可以很大；平台工程预设“平台即产品，业务团队是客户”的服务关系，平台团队规模被刻意限制（维持不了一个产品团队规模的平台，就做不成 IDP）。

一句话对齐：**技术侧复用走“自服务平台”已是共识；分歧在业务侧复用**——国内中台把业务能力也收进中心平台（于是“排队”结构性出现，退潮时最先被拆的也是业务中台），平台工程不碰业务语义。所以“中台退潮之后，国际上大家在做什么”的答案是：技术中台以平台工程 / IDP 的形态活得更好，业务复用改走轻量路线。评估你的组织时，与其争论“要不要中台”，不如拆成两问：技术侧要不要自服务平台（几乎总答“要”）；业务侧哪些能力过了四问（通常很少）。

## 5.3 平台化的替代路线：共享库、自服务基础设施、内部开源

四问设了一道高门槛，多数能力过不了——这是常态，不是失败。过不了四问 ≠ 各线重复造轮子：中间还有三条轻量路线。它们与重中台的差别在两处结构特征：**有没有运行时集中点**（库没有、服务有）与**所有权在谁**（owner 团队还是中央平台团队）。

| 路线 | 沉淀什么 | 运行时集中点 | 排队风险 | 版本漂移风险 | 适用判据 |
|---|---|---|---|---|---|
| **共享库** | 纯逻辑与抽象：钱/时间/幂等组件、协议编解码、时间窗计算 | 无（编译进各服务） | 低（无中央需求队列） | 高：多语言多版本并存，升级靠推动 | 逻辑与运行时数据无关、变更不频繁、消费方技术栈同构 |
| **自服务基础设施** | 技术侧共性：脚手架、流水线、可观测性基线（即 IDP 的正域） | 有，但只碰技术语义 | 低（自助取用，不排期） | 低（平台统一版本节奏） | 技术侧共性几乎全适用（对照[第五阶段](../05-第五阶段/01-工程化与运维视角.md)） |
| **内部开源（inner source）** | 单 owner 团队维护、多团队消费的能力：排线算法、规则引擎 | 可有可无（库或服务皆可） | 中（owner 团队评审带宽是瓶颈） | 中（版本发布纪律像开源项目） | 有明确 owner 团队、演进快、消费方愿意提 PR 而不是提需求 |
| **重中台** | 四问全过的领域能力：支付、账号 | 有（中央服务集群） | 高（无自服务机制时要排队） | 低（契约统一） | 四问全过，且组织配套（双向契约、考核）跟得上 |

三条轻量路线不互斥，而且常常是重中台的**前置台阶**——以到家平台的“上门调度”为例走一遍谱系：

1. **共享库先行**：桶装水排线与家电清洗预约都要“上门时间窗计算”，先沉淀成公共库——两处调用、无运行时集中点、零排队。这一步的成本几乎只有抽库的工时。
2. **升格为内部开源服务**：家政保洁接入后，“时间窗”开始需要**统一的调度状态**（跨线看师傅与车辆的全局占用），库的形式不够了——由最懂它的团队（桶装水配送域）负责，以内部开源方式提供服务，消费方提 PR 扩展各自的班次语义，契约用版本发布管理。所有权没有离开最懂的团队，治理像开源项目一样轻量。
3. **四问全过才升重中台**：只有当第四条、第五条线接入、跨线算力复用与全局调度的规模效益真正显现时，才立项“调度中台”——此刻它有 3 个真实消费方垫底，不是赌未来。

这条渐进谱系最大的优点是**每一步可逆**：库废弃了删依赖即可；inner source 项目停滞了，消费方锁住旧版本继续用；都不像拆中台那样伤筋动骨。把“要不要平台化”从二选一改写成“**现在走到谱系哪一档**”，是本节给你的最后一个判据——它和“要不要微服务”的正确问法“先模块化单体、按扩展差异渐进拆”（见 2.3 与 2.5）是同一个思维动作。

三条轻量路线也各有自己的偷懒用法，提前点名：

- **共享库做成“common 万能筐”**：什么都往一个 `common` 库里塞，任何一处改动全公司重新编译发版——这是进程内版的“上帝层”。共享库同样要按领域切分、语义化版本管理，“是库”不是免检金牌。
- **内部开源没有维护激励**：owner 团队的 PR 评审不进绩效、不算工作量，半年后项目烂尾、消费方被迫各自 fork——inner source 是治理机制不是口号，维护者的投入要被组织看见。
- **自服务平台做成“工单系统”**：号称 IDP，取个测试环境还要提单等审批——排队没有消失，只是换了界面。回到平台工程第一原则：自助是第一原则，做不到自助就不叫平台。

场景对照收尾：到家平台三条线的现实选择大概率是——支付与账号直接用成熟自建或采购的能力平台（技术侧，自服务基础设施路线）；调度走“共享库 → 内部开源服务”两步；订单与押金永远留在各自前台（押金是桶装水的身份标识，把它抽象进“通用订单”等于把业务抽象没了）。**轻路线是默认，重中台是例外**——这与本阶段反复出现的“模块化单体是多数系统的最优解”是同一句话的两个声部：**为真实的复用买单，不为想象中的复用付税。**

**本节自测（BFF 与中台）**
1. 用“换表达方式 vs 换业务事实”判据给下列需求定位到网关 / BFF / 领域服务：请求聚合、限流、把美元价格换算成本地货币展示、会员折扣价计算。
2. “空桶应收怎么算”放 BFF 还是领域服务？如果放错了，会出什么事故？
3. 通用订单中台反例错在哪一步——是“做中台”错，还是“把语义不一致的能力硬沉淀”错？由此说说什么能力适合中台化。
4. 你的公司里有没有“事实上的中台”（被多条业务线共用的服务）？它有没有版本化契约、SLA、扩展点？哪一条最欠缺，后果是什么？
5. 用“变化原因三问”给下列需求定位到网关 / BFF / 领域服务，并写出每项的“变化原因”：(a) 小程序把商品价格从“分”格式化成“¥xx.xx”展示；(b) 满减促销的金额计算；(c) 开放平台按第三方应用维度限流；(d) 配送员端把今日任务与路线拼成一次请求；(e) “会员价仅在 APP 端生效”。哪一项最容易放错层？
6. 你的到家平台已有 4 个端，各端团队开始互相等 BFF 排期，小程序团队抱怨配送员端的改动拖累自己。按“数量演进”该走到哪一阶段？拆分时配套要做哪两件事，防止公共逻辑漂移出 N 份不一致的版本？
7. “上门时间窗计算”目前两条线在用、演进很快、有明确的 owner 团队——按 5.3 的判据选共享库 / 内部开源 / 重中台，并说明理由；如果半年后第三条线接入、且开始需要跨线的全局调度状态，你的决策怎么变？
