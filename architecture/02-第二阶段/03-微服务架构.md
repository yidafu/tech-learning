## 2. 微服务架构

（主线继续：为演示完整演进，本节让桶装水真的微服务化；“该不该”的审判放在 2.3。）

### 2.1 服务拆分的依据与常见误区

**概念**：微服务是一组围绕业务能力构建、可独立部署、去中心化管理数据的小型服务。“微”不是指代码行数少，而是指**边界小而完整**（接口 + 数据 + 团队三位一体）。

拆分依据（按优先级排序，以桶装水为例）：

| 依据 | 说明 | 桶装水示例 |
|---|---|---|
| 限界上下文（DDD） | 同一个词在边界内外含义不同，语言一致处即边界 | “商品”在商城域是 SKU，在配送域是“送水任务上的桶数与楼层” |
| 数据所有权 | 谁写谁拥有，一表一主 | 库存表只有商品与库存服务可写 |
| 变化原因/频率 | 因同种原因变化的东西放一起 | 排线算法天天实验调参、交易流程相对稳定，分开 |
| 团队拓扑（康威定律） | 服务边界对齐团队沟通边界，见[第一阶段](../01-第一阶段/01-架构思维与设计基础.md) | 交易团队 vs 配送团队 |
| 扩展性差异 | 资源画像差异大的分开 | 排线是 CPU 密集的算法问题；商品浏览是读多写少的 IO 问题 |

上表回答“按什么切”，实践中还有四种常用**拆分坐标**回答“第一刀落在哪里”。四种坐标各有适用面，也各有典型误用：

| 拆分坐标 | 切法 | 桶装水示例 | 误用反例 |
|---|---|---|---|
| 按业务能力 | 一个服务对应一项对外的业务能力（能向业务方说清楚“它负责什么生意”） | 订单、配送、押金各自成服务 | 把“数据存储”当成业务能力，拆出“数据库服务”——那是技术资源不是业务能力，一切业务改动都要路过它 |
| 按子域（DDD） | 区分核心域/支撑域/通用域，核心域独立成服务重点投入 | 周期购订阅是核心域（差异化竞争所在），短信通知是通用域（买现成服务即可） | 把支撑域当核心域过度投入：给“短信通知”配一个专职团队和维护一套自研模板引擎 |
| 按变化频率 | 变化节奏差异大的分开，稳的少动、动的快跑 | 排线算法天天调参（周级甚至日级发版） vs 交易主流程季度级稳定 | 反向误用：把“最近都改得多”的几个不相干模块捆成一个“高频变更服务”——变化**原因**不同的东西捆在一起，照样互相牵连；该按原因聚，不是按次数聚 |
| 按团队拓扑 | 服务边界对齐团队沟通边界，一个服务一个明确 owner | 交易团队 owns 交易服务，配送团队 owns 配送服务 | 团队只有 4 个人却按拓扑拆出 6 个服务——每人 owns 1.5 个服务，oncall 与 code review 直接失控（康威定律反向适用：边界超过团队容量就是灾难） |

四种坐标经常给出不一致的答案。组合使用的判据：**业务能力/子域定“切什么”（大块的边界），变化频率与团队拓扑定“切多细”（要不要再一分为二），扩展性画像（资源差异）定“是否值得物理隔离”**。四者冲突时以子域边界为底——子域错了，后面全部跟着错；子域对了，其余三个坐标只是在正确边界上做微调。

两个典型的拆分判断：

- **配送排线先拆**：车辆路径规划是独立算法问题（挑战 5）。耦在交易里，意味着排线算法每次实验性改动都要重发整个交易系统；拆出去后可独立扩容 CPU、独立灰度算法版本，排线 OOM 也不拖垮下单。
- **周期购订阅其次**：它是“定时触发的订单”（挑战 2），调度可靠性、错过补偿、暂停/换地址等生命周期与即时交易的变化节奏不同步，适合独立演进。

❌ **常见误区与修正对照**：

| 误区 | 后果 | 修正 |
|---|---|---|
| 按技术层拆（“数据库服务”“工具服务”） | 一个业务改动横跨全部服务，即“分布式单体” | 按业务能力垂直拆 |
| 一上来拆 20 个服务 | 运维与联调成本陡增 | 从 3~5 个粗粒度服务起步（monolith first） |
| 多个服务共享一个数据库 | 隐式耦合，改 schema 互相殃及 | 每服务私有库，跨服务走 API 或事件 |
| 同步调用链过长 | A→B→C，可用性相乘下降 | 非关键路径异步化（异步化展开见主笔记第 3 节） |
| 把“能拆”当“该拆” | 白付分布式代价，无任何收益 | 先问：团队规模？独立扩展需求？独立部署价值？ |

> **常见追问**：分布式单体是为了提高吞吐率吗？——不是。分布式单体不是设计目标，而是拆分失败的意外产物。拆服务的真实动机是独立部署、独立扩展、故障隔离、团队自治，吞吐最多对应“独立扩展”一条。分布式单体反而连吞吐都救不了：同步调用链每跳多一次序列化 + 网络往返（进程内调用纳秒~微秒级，网络跳毫秒级），延迟叠加；共享数据库没拆，瓶颈原封不动；链路可用性相乘，高峰期更脆。真要吞吐，单体先有招——缓存、读写分离、无状态多实例水平扩容（桶装水商品读洪峰即如此，见 2.3）；确有资源画像差异（如排线 CPU 密集）才按“扩展性差异”拆出边界清晰的微服务。

✅ 按业务拆分后（示意：交易、商品与库存、支付、配送、押金五个服务起步），交易服务只做编排、不实现别人领域的细节：

```kotlin
class PlaceOrderHandler(
    private val inventory: InventoryClient,   // 远程客户端：商品与库存服务
    private val payment: PaymentClient,       // 远程客户端：支付服务
    private val events: EventPublisher,
) {
    fun handle(cmd: PlaceOrderCommand): OrderId {
        val order = Order.draft(cmd)
        inventory.reserve(order.id, order.lines)
        payment.charge(order)                  // 失败必须走补偿，不能让订单悬空
        events.publish(OrderEvent.OrderPlaced(order.id, order.lines, Instant.now()))
        return order.id
    }
}
```

**演进前后对比**——解决了：独立部署（排线算法每天可发版）、独立扩展（大促时只扩商品读服务）、故障隔离（排线宕机不耽误下单）。付出了：下单原子性没了（本地事务 → Saga/最终一致，见[第三阶段](../03-第三阶段/01-分布式系统核心技术.md)）；“我的订单”页要聚合四个服务；一次排查跨多条日志。这就是用复杂度换伸缩性。

**拆分粒度的量化自检**：边界划得对不对，不能靠感觉吵，拿数据说话。三个指标，各带达标线：

| 指标 | 口径 | 达标线 | 超标含义 |
|---|---|---|---|
| 需求跨服务数 | 抽样最近 20~30 个已完成需求，统计平均需要改动几个服务 | ≤ 1.5（多数需求在单个服务内闭环） | > 2.5：需求与边界不对齐，切分坐标选错了 |
| 同步调用深度 | 网关入口到最深的同步下游的跳数（P99 口径） | ≤ 3 跳 | 每深一跳可用性相乘、延迟相加；超标链路要么异步化要么合并服务 |
| 发布联动率 | 一个月内“必须同时发布 ≥2 个服务才算完成”的发布占比 | < 20% | > 40%：独立部署已名存实亡，是最直接的分布式单体信号 |

桶装水的抽样演示：抽 20 个需求——“改运费计算”动 1 个服务、“周期购换地址”动 1 个、“下单送券”跨订单 + 营销 2 个、“订单详情页加展示字段”跨订单 + BFF 2 个……平均 1.4，健康。如果“下单送券”这类需求每次都要五个服务陪跑，说明营销的边界切错了位置（券的资格判定应该在营销服务内闭环，而不是散在各处）。

使用节奏的判据：**需求跨服务数**成本最低，每个迭代回顾顺手抽一次；三项全量体检放季度架构评审。连续两个周期超标才动手重组边界——单周期的毛刺可能只是需求样本偏，别被个别需求带偏了全局。

### 2.2 服务通信、API 网关、服务治理

| 维度 | 同步（REST / gRPC） | 异步（消息 / 事件） |
|---|---|---|
| 耦合 | 调用方要知道对方的地址与契约 | 只依赖事件契约 |
| 可用性 | 被调宕机则调用方受牵连（需熔断） | 中间件存活即可继续 |
| 结果反馈 | 立即拿到（支付扣款必须） | 最终一致（生成配送任务可以等） |
| 流量模型 | 点对点放大 caller 的压力 | 削峰、缓冲、一对多广播 |

原则：**需要立即结果的用同步（扣款、锁库存），能容忍延迟的用异步（排线、押金记账、营销发券）**。

原则落到具体链路时，用四维判据逐项过一遍，比“凭感觉选”可靠：

| 判据 | 倾向同步 | 倾向异步 |
|---|---|---|
| 一致性要求 | 强一致、当下必须生效（锁库存防超卖、扣款防重复消费） | 最终一致可容忍（押金记账、积分、发券） |
| 时延敏感 | 用户在等结果（下单必须立刻知道成没成） | 用户不等（配送任务生成、报表、对账） |
| 故障传播 | 下游宕机必须让用户感知失败（宁可下单失败也不能白扣款） | 下游宕机不能拖累主流程（发券宕机不影响下单） |
| 背压能力 | 洪峰只能靠限流硬扛（同步链路没有缓冲） | 洪峰可入队削峰（消息队列天然提供背压缓冲） |

判定顺序建议：**先问一致性**（资金、库存类几乎注定同步），**再问时延**，**再看故障传播方向**（谁宕机不能拖累谁），**最后看流量形态**。桶装水下单链路的完整判定：锁库存 = 同步（一致性）；支付 = 同步（一致性 + 时延）；生成配送任务 = 异步（时延）；发券 = 异步（故障传播方向：营销宕机不得拖累交易）；押金记账 = 异步（押金生命周期长，秒级延迟无感）；排线 = 异步（背压 + 时延，且算法耗时波动大）。秒杀场景把这组判据推到极端：只有“排队受理”是同步的，其余全部异步化削峰——因为瞬时流量下任何同步长链都是灾难。

❌ **反例：无超时、无熔断的同步调用**

```kotlin
class PaymentClient(private val rest: RestTemplate) {
    fun charge(order: Order): Receipt =
        rest.postForObject("/payments", PayRequest(order.id, order.total), Receipt::class.java)!!
    // 没有超时：支付服务一次 GC 停顿 30s，交易服务的线程池被拖干，整个商城没人能下单
}
```

✅ **修正：显式超时 + 熔断 + 降级**

```kotlin
class PaymentClient(private val web: WebClient) {
    // 显式超时，快速失败，把故障控制在局部；外层再套 Resilience4j 熔断器
    suspend fun charge(order: Order): Receipt = withTimeout(2.seconds) {
        web.post().uri("/payments")
            .bodyValue(PayRequest(order.id, order.total))
            .retrieve()
            .awaitBody<Receipt>()
    }
    // 熔断打开后的降级：订单标记 PENDING_PAYMENT，交给补偿任务重试，而不是无限等待
}
```

**API 网关**的职责：统一入口的路由、鉴权、限流、协议转换、响应聚合。桶装水的入口画像：C 端小程序/APP（商品、下单、订阅管理）、配送员端 APP（任务与路线）、运营后台——三类端走同一网关，但鉴权方式（用户 token vs 员工账号）与限流策略各不相同；`GET /order-detail` 由网关聚合订单 + 商品 + 配送任务 + 押金状态四个服务。注意网关最容易被腐化成“上帝层”：**业务规则不应写进网关**；聚合逻辑变复杂时下沉到 BFF（如“配送员端 BFF”专门聚合路线 + 任务 + 客户地址 + 空桶应收；模式展开见主笔记 5.1）。

“这段逻辑放网关、BFF 还是领域服务？”用三条判据做归属判定：

1. **与具体端无关的横切策略**（鉴权、限流、审计、路由、协议转换）→ 网关。特征：换一个端它依然成立。
2. **因端而异的聚合/裁剪/编排**（同一份数据，不同端要不同形状）→ BFF。特征：只为某一类调用方服务，端变了它就变了。
3. **领域业务规则**（价格怎么算、订单状态怎么流转、券的资格怎么判）→ 只能住在领域服务里。特征：跟“谁在调”完全无关。

反过来还有第四种去向要警惕——**哪儿都不该放**：把满减规则、状态机这类业务逻辑塞进网关或 BFF，只是把上帝层从网关搬到了 BFF，腐化换了个地址而已。桶装水判定练习：第三方开放平台的签名验签 → 网关（横切策略）；配送员端聚合“路线 + 任务 + 客户地址 + 空桶应收” → 配送员 BFF（因端而异的编排）；满 3 桶减 5 元 → 订单/营销服务（领域规则）；C 端按用户维度限流、运营后台按账号限流 → 网关（横切策略）；订单 15 分钟未支付自动取消 → 订单服务（领域规则，跟端无关）。多租户 SaaS 里同一结构换个名字：控制面定义配额策略，网关在数据面第一线执行——“策略与执行分离”是同一件事。

**服务治理**清单：注册发现（K8s Service / Nacos / Consul，排线服务多实例按 CPU 弹性伸缩）、配置中心、熔断降级与舱壁隔离、链路追踪（traceId 贯穿“下单 → 支付 → 排线”全链）、集中日志与指标。治理细节（一致性、可观测性）在[第三阶段](../03-第三阶段/01-分布式系统核心技术.md)展开。

其中**服务注册发现**有两种基本模式，故障面完全不同：

| 模式 | 做法 | 代表 | 优点 | 故障面 |
|---|---|---|---|---|
| 客户端发现 | 调用方查询注册表拿实例列表，自己做负载均衡、自己剔除坏实例 | Eureka + Ribbon、gRPC 客户端均衡 | 少一跳网络；可按调用方定制均衡策略（就近、灰度加权） | 每个语言栈都要实现一遍发现逻辑（多语言团队成本翻倍）；客户端缓存过期会把请求打到已下线实例；调用方代码变复杂 |
| 服务端发现 | 调用方只请求一个稳定的 VIP/域名，中间层负责查表并路由到具体实例 | K8s Service、云负载均衡、Nginx | 调用方零心智，发现逻辑集中在基础设施层 | 中间层自身是新的故障面与延迟加成；均衡策略受限于中间层支持的算法 |

两种模式共同的兜底问题是：**注册中心自己宕机怎么办？**答案不是“多部署几台注册中心”就算完——已拉取的实例列表要在调用方本地缓存并继续使用（宁可路由到少量过期实例，不能全站瘫痪）；已建立的长连接不因注册中心抖动而中断；注册中心恢复后再收敛列表。判据：纯 K8s 内部通信直接用 Service（服务端发现已内置，不必再引注册中心）；跨集群、多语言异构、或需要调用方维度精细流量策略（如按机房就近、按灰度标记路由）才引入客户端发现或 service mesh。MES 是个现成的反面约束：车间边缘网关调用厂内排程服务，车间网络抖动频繁、不允许依赖厂外注册中心——边缘侧用“本地静态实例表 + 主动健康探测”的轻量服务端发现，断网时本地自治、恢复后回连（与 MES 的边缘自治原则一致）。

### 2.3 微服务的代价：什么时候不该用微服务

| 代价 | 具体表现 | 桶装水场景 |
|---|---|---|
| 分布式事务 | 下单成功但扣库存失败，需要 Saga/补偿 | 付了钱没扣水 = 超卖事故 |
| 网络不可靠 | 超时后“到底成没成功？” | 支付超时后盲目重试 = 重复扣款，必须幂等 |
| 测试复杂 | 无法在一个进程内跑完用例 | “下单送水”一个用例要起 4 个服务，需要契约测试 |
| 运维成本 × N | N 套 CI/CD、监控、告警、oncall | 3 人团队维护 20 个服务 = 灾难 |
| 读一致性 | 不再有一致性读 | 下单成功后立刻查“我的订单”可能查不到 |
| 排查难度 | 一个请求跨 6 个服务 | 没有 traceId 就是盲人摸象 |

**不该用的信号**（满足越多越不该上）：团队小于 10 人；领域还在剧烈变化（边界认知不清，拆了必返工）；没有独立扩展需求；缺乏 CI/CD 与监控基础设施；动机只是“大厂都在用”。

信号清单回答“该不该拆”；如果你已经拆了，还需要一张清单回答“**拆成了微服务，还是拆成了分布式单体**”。十条自检，每条配一句可执行的诊断方法：

1. **服务名里没有业务词**（“数据中台服务”“公共工具服务”）——诊断：把服务名念给业务方听，对方听不出它在负责什么业务，就是按技术层拆的。
2. **多个服务写同一张表**——诊断：数一遍核心表的写权限数据库账号，归属超过 1 个服务即中招。
3. **一个需求平均跨 ≥3 个服务**——诊断：抽最近 20 个已完成需求，数代码变更涉及的服务数（对应 2.1 的量化自检）。
4. **发布必须成串联动**——诊断：看发布系统里“关联发布/合并发布”标记的占比，超过四成即中招。
5. **同步调用链超过 3 跳**——诊断：打开链路追踪的拓扑视图，找最深的一条同步路径。
6. **改一次接口要拉所有消费方排期同步发版**——诊断：翻最近一次接口变更的沟通记录，数协调了多少个团队、等了多久才集齐。
7. **存在 common-domain / common-entity 共享领域模型库**——诊断：全局搜 common 包名，看被几个服务的构建文件引用（2.6 会讲这是最隐蔽的一条）。
8. **一次上线只构建出一个大产物**——诊断：看 CI 产物列表，如果所有服务永远同版本号同车发布，“独立部署”从来没成立过。
9. **测试必须起全链路环境才能跑**——诊断：统计被“集成环境宕机”阻塞的用例比例，超过一半即中招。
10. **一个需求的代码评审要跨 3 个团队的 owner**——诊断：看最近一次大需求的 PR 分布，数涉及的 code owner 数量。

判读方式：**0~2 条**——边界基本健康，保持观察；**3~5 条**——正在滑向分布式单体，优先修第 2 条（数据所有权）与第 6 条（契约纪律），这两条是病根；**≥6 条**——已经是分布式单体，别急着“更微服务”，先按 2.5 的渐进路子合拢或重切。注意这十条的病根几乎都不在“服务数量”上，而在**数据、契约、部署独立性**三件事上——多拆几个服务治不了它们，只会加重。

**主线审判：桶装水商城该不该上微服务？** 设定现实画像：一个 10 人上下的团队、日订单几万、读多写少。逐条对照信号——团队规模贴线；领域边界经模块化单体已趋稳定；独立扩展需求真实存在的只有两处：商品读洪峰（先上缓存 + 读写分离即可解决大半，见[第三阶段](../03-第三阶段/01-分布式系统核心技术.md)）与排线算法的 CPU。合理结论是“**模块化单体为主 + 至多拆一个排线服务**”，而非全面微服务化。这也说明：本节演示的“五服务架构”是教学推演，真实决策永远从代价清单出发，而不是从模式出发。

经验法则（Sam Newman《Monolith to Microservices》）：**先单体（最好是模块化单体），确有需要时用“绞杀者”模式渐进拆出第一个服务**——选扩展性差异最大的部分（如排线算法、图片处理），而不是订单核心链路（绞杀四步展开见 2.5）。

### 2.4 历史对照：SOA（面向服务的架构）

**概念**：SOA 比微服务早十年（2000 年代主流）：把系统能力封装为可复用的“服务”，通过**企业服务总线（ESB，Enterprise Service Bus）**统一接入——报文转换、协议适配、路由、流程编排、集中治理都长在总线上。典型形态：各业务系统（含大量遗留系统）把功能发布成 Web Service（SOAP/WSDL），总线负责让异构系统互相说得上话。

同一个“服务化”方向，两个时代给出的答案：

| 维度 | SOA | 微服务 |
|---|---|---|
| 核心动机 | **集成**：让异构老系统互通复用 | **交付**：让小团队独立开发、独立部署 |
| 服务粒度 | 粗（按系统/大块能力） | 细（按业务能力与限界上下文，见 2.1） |
| 中介 | ESB：转换/编排/路由全做（智能总线） | 网关只做横切策略 + MQ 只搬字节（哑管道） |
| 治理 | 中心化（总线团队、全局标准） | 去中心化（谁建设谁运营） |
| 数据 | 常共享库、共享大模型 | 每服务私有库（见 2.3 代价表） |

❌ **反例：智能总线、哑端点**

```kotlin
// 所有转换与编排逻辑长在 ESB 里：每对接一个系统，总线就长一对转换器
class OrderEsb {
    fun route(msg: Map<String, Any?>, target: String): Any? = when (target) {
        "billing"   -> toBillingFormat(msg)      // 财务系统要的报文
        "logistics" -> toLogisticsFormat(msg)    // 物流系统要的报文
        "erp"       -> toErpFormat(msg)          // ERP 要的报文
        else -> msg
    }
    // "下单→扣款→通知仓储"的流程编排也在这里：ESB = 全局单点 + 全公司需求瓶颈
}
```

病根与网关腐化、BFF 职责漂移（见 2.2、主笔记 5.1）是同一个：**中介层吞了业务逻辑**。业务规则散落进总线，服务本身越来越“薄”；改一个编排步骤要总线团队发版；总线成为全公司的性能与可用性单点。

✅ **微服务的修正**：逻辑收回服务内部（“智能端点”），中介退化成哑管道——API 网关只做路由/鉴权/限流等横切策略（见 2.2），系统间搬运交给消息队列（见主笔记 3.1）。对照记忆：**ESB 之于 SOA ≈ 上帝层网关之于微服务**——都是中介腐化，解毒剂都是“策略与业务分离”。

### 2.5 渐进拆分：绞杀者模式与数据拆分

（2.3 的审判结论是“模块化单体为主 + 至多拆一个排线服务”；本节讲“真要拆时，怎么拆才稳妥”。）

**绞杀者模式（Strangler Fig）**：不做一次性重写，而是在旧系统前面立一个**分流入口**，让新服务一点点接管流量，旧系统被逐步“绞杀”到只剩壳，最后删除。Martin Fowler 2004 年命名，灵感来自绞杀榕：缠着宿主树生长，宿主枯死后自己长成独立的新树。前置条件只有一个：入口处有能拦截请求的分流点（网关或门面层）；没有统一入口的遗留系统要先补门面，否则绞杀无从下手。

四步循环（以“拆出排线服务”为例）：

1. **立分流入口**：网关把“生成排线”请求按规则路由到新旧两条路径，初期 100% 走旧模块——新服务没接管任何真实流量，只是先“挂上去”。
2. **影子对拍**：放量前先跑影子流量——同一批历史配送工单同时发旧模块与新服务，**只比对不生效**；比对口径：排线方案差异（路线、装载、时间窗）、耗时、约束违反数。差异清单收敛（或逐条确认“新逻辑才是对的”）后才放量。这一步把“行为对等”从切换夜的赌局变成可量化验收的日常检查。
3. **灰度切流 + 预设回滚条件**：小比例放量（如 5%），错误率 / P99 时延超阈值**自动全量回退旧路径**。桶装水按**配送站维度**切最自然——排线按站点出结果，一个站的流量要么全新要么全旧，不会出现同一站两套排线互相踩。
4. **收尾**：流量 100% 后旧模块**冻结**（只修 bug 不加功能）→ 观察一个完整业务周期（月结、一次大促）→ 删除旧代码与表。删代码之前，旧路径始终是回滚保险，不能提前拆。

❌ **反例：大爆炸重写（Big Bang Rewrite）**

> 新排线服务“功能写完了”，选个周末停旧上新。上线当天客诉激增：山顶配送没人接单、暴雨加时规则没了、婚庆大单（一次 200 桶）排不进去——旧单体里沉淀着五年攒下的 17 条热修补丁规则，重写团队只对着文档实现了 9 条。

一次性重写的死穴：旧系统的真实行为散落在历次热修里，没有完整文档，“功能对等”永远在切换日被发现不对等。绞杀者的影子对拍正是针对这一点——拿真实历史流量逼出新旧行为的全部差异。

**数据拆分才是硬骨头**：代码好搬，数据难拆。拆服务必须配套拆数据，否则 2.1 误区表里“共享数据库”的耦合原封不动。三阶段路径：

| 阶段 | 形态 | 得到 | 还欠什么 |
|---|---|---|---|
| ① 共库不同 schema | 同一库实例按 schema 划账 | 归属清晰了一半 | 资源/锁仍竞争，改表结构仍要协调 |
| ② 逻辑私有 | 权限隔离：每个服务只有自己 schema 的读写权限 | 直连别人表在权限层就报错，耦合**显性化** | 仍是物理共库，容量与故障域没分开 |
| ③ 物理独立 | 独立库实例 | 独立扩容、独立备份、故障隔离 | 跨库 join 没了、事务没了（见[第三阶段](../03-第三阶段/01-分布式系统核心技术.md)第 4 节） |

迁移的顺序原则：**先断别人对我表的直连，再断我对别人表的直连，最后才搬库**——直连不断就搬库，切换瞬间全线报错。同步过渡期：旧表写完同步写新库（或发事件），加一条对账任务核对差异；落地机制（本地消息表）在[第三阶段](../03-第三阶段/01-分布式系统核心技术.md) 4.5 展开。

**跨服务查询的三种替代**（共库 join 没了之后，“我的订单”页要显示配送状态怎么办）：

| 方案 | 做法 | 取舍 | 适用 |
|---|---|---|---|
| API 组合 | 展示时逐个调订单、配送、押金服务再拼装 | 强新鲜；链路长、可用性受牵连、往返多 | 管理后台等低频页 |
| 事件复制本地读 | 订单服务订阅配送任务事件，在本地维护只读状态字段，读自己的库 | 读快读稳；最终一致（秒级延迟），要建副本 | C 端高频页 |
| 报表另建 | 跨全业务的统计对账走独立报表库（ETL / CDC 定期拉数） | 不占交易链路；数据非实时 | 月度对账、经营报表 |

> 第二行“事件复制本地读”就是主笔记 3.2 CQRS 读侧的最小形态——微服务的跨服务查询问题在这里自然接轨 CQRS。

**拆错了可以合回来**：粒度校准不是单向门。合并信号：两个服务永远同发同部署；边界内高频互调（成对出现的秒级往返）；一个需求总是同时改两个代码库。处理：先合库共事务过渡，再合代码。《Monolith to Microservices》专门有“合并”一章——敢拆也敢合，才是把粒度当权衡，而不是信仰。

**最小可运行示例：路由门面 + 新旧实现对拍**。把四步循环的前三步浓缩成一个可跑的门面：旧实现与新实现并存，门面按流量比例把订单路由到新实现，被选中的订单同时用旧实现做影子对拍——结果不一致就告警并回退用旧结果，不一致率超阈值则自动全量回滚。完整代码（含 `main`，已实际编译运行验证，kotlinc 2.2.20）：

```kotlin
// StranglerFacadeDemo.kt —— 绞杀者迁移最小实现：路由门面 + 新旧实现对拍 + 告警回退 + 自动回滚
//
// 场景：桶装水商城把"配送排线"从单体模块拆成独立服务。
//       旧实现沉淀着五年热修规则；新服务第一版漏了"婚庆大单加派专车"规则。
//       门面按流量比例放量：被选中的订单走新实现，同时用旧实现影子对拍，
//       不一致就告警并回退用旧结果；不一致率超阈值 → 自动全量回滚旧路径。
//
// 运行：kotlinc StranglerFacadeDemo.kt -include-runtime -d strangler-facade.jar && java -jar strangler-facade.jar

import kotlin.random.Random

data class DeliveryOrder(val id: String, val buckets: Int, val wedding: Boolean, val mountain: Boolean)
data class RoutePlan(val routes: Int, val etaMinutes: Int) {
    override fun toString(): String = "路线${routes}条/ETA${etaMinutes}分"
}

// ---------- 旧实现：单体里的排线模块，五年热修规则全在里面 ----------
object LegacyRouter {
    fun route(o: DeliveryOrder): RoutePlan {
        var routes = if (o.buckets <= 60) 1 else (o.buckets + 59) / 60
        var eta = 90
        if (o.mountain) eta += 60                 // 热修：山顶站加时
        if (o.wedding) { routes += 1; eta += 30 } // 热修：婚庆大单加派专车
        return RoutePlan(routes, eta)
    }
}

// ---------- 新服务的两个版本：v1 漏了婚庆规则（重写团队只对着文档实现了一半），v2 补齐 ----------
fun newRouterV1(o: DeliveryOrder): RoutePlan {
    var routes = if (o.buckets <= 60) 1 else (o.buckets + 59) / 60
    var eta = 90
    if (o.mountain) eta += 60                     // 山顶规则有，婚庆规则漏了
    return RoutePlan(routes, eta)
}
fun newRouterV2(o: DeliveryOrder): RoutePlan = LegacyRouter.route(o) // 修复后行为对等（示意）

// ---------- 路由门面：按流量比例切流 + 影子对拍 + 不一致告警回退 + 超阈值自动回滚 ----------
class StranglerFacade(
    private val newRouter: (DeliveryOrder) -> RoutePlan,
    private val mismatchThreshold: Double = 0.05,   // 对拍不一致率阈值
) {
    private val rnd = Random(42)                    // 固定种子，输出可复现
    var newTrafficPercent = 0                       // 当前对新实现的放量比例
    var rolledBack = false
        private set
    var rollbackReason: String? = null
        private set
    var sampled = 0                                 // 对拍样本数
        private set
    var mismatched = 0                              // 不一致数
        private set

    fun handle(o: DeliveryOrder): RoutePlan {
        if (rolledBack) return LegacyRouter.route(o)   // 已回滚：全量走旧，不再对拍
        val toNew = rnd.nextInt(100) < newTrafficPercent
        val oldPlan = LegacyRouter.route(o)
        if (!toNew) return oldPlan                    // 走旧的：正常服务，不对拍
        val newPlan = newRouter(o)
        sampled++
        return if (newPlan == oldPlan) {
            newPlan                                   // 对拍一致：新结果生效
        } else {
            mismatched++
            println("[告警] ${o.id} 新旧排线不一致（旧=$oldPlan 新=$newPlan）——本次回退用旧结果")
            val rate = mismatched.toDouble() / sampled
            if (rate > mismatchThreshold) {
                rolledBack = true
                rollbackReason = "对拍不一致率 ${"%.0f".format(rate * 100)}%（$mismatched/$sampled）超过阈值 $mismatchThreshold，自动全量回滚旧路径"
                println("[回滚] $rollbackReason")
            }
            oldPlan                                   // 不一致：本次用旧结果，宁可保守
        }
    }
    fun summary(): String = "放量=$newTrafficPercent%，对拍样本 $sampled，不一致 $mismatched，已回滚=$rolledBack"
}

fun main() {
    // 一批历史配送工单（确定性生成）
    val orders = List(60) { i ->
        val r = Random(i)
        DeliveryOrder(
            id = "D-${i + 1}",
            buckets = 20 + r.nextInt(180),
            wedding = r.nextInt(10) < 2,   // 两成是婚庆大单
            mountain = r.nextInt(10) < 1,  // 一成走山顶站
        )
    }

    println("== 第 1 步：立分流入口，放量 0%（新服务挂上去，不接管任何流量）==")
    val facadeV1 = StranglerFacade(newRouter = ::newRouterV1)
    orders.forEach { facadeV1.handle(it) }
    println(facadeV1.summary())

    println()
    println("== 第 2 步：灰度放量 30%，新实现 v1 漏了婚庆规则 → 对拍告警 → 自动回滚 ==")
    facadeV1.newTrafficPercent = 30
    orders.forEach { facadeV1.handle(it) }
    println(facadeV1.summary())
    println("回滚原因：${facadeV1.rollbackReason}")

    println()
    println("== 第 3 步：修复后的 v2 重新放量 100%，对拍全程一致 → 旧实现冻结待删 ==")
    val facadeV2 = StranglerFacade(newRouter = ::newRouterV2)
    facadeV2.newTrafficPercent = 100
    orders.forEach { facadeV2.handle(it) }
    println(facadeV2.summary())
    println("收尾：流量 100% 且对拍一致 → 旧模块冻结（只修 bug）→ 观察一个完整业务周期 → 删代码与表")
}
```

三步输出正是绞杀四步的缩影：第 1 步新服务挂上去零接管（分流入口立起，回滚保险最厚）；第 2 步 D-35 是一张婚庆大单，新实现漏了“加派专车”规则，影子对拍当场抓住——**这正是大爆炸重写在切换夜才能发现的问题，在放量期第 9 个样本就被逮住了**，且该单已按旧结果履约，用户无感；不一致率 11% 超过 5% 阈值，自动回滚，不需要人守夜；第 3 步修复后重新放量，60 个样本全程一致才敢谈删除旧代码。

几个工程判据把示例推到真实场景：

- **按维度切流优于按比例切流**：本例为最小化用了随机比例；真实排线场景应按配送站维度切（2.5 第 3 步的理由）——同一实体的重复请求必须稳定走同一路径，否则同一站两套排线互相踩。有自然维度（站点、租户、仓库）时按维度切，没有自然维度才按比例随机。
- **回退的触发源不止一种**：本例用“对拍不一致率”；生产上通常三条并行——对拍不一致率（行为不等）、新服务错误率（实现坏了）、新服务 P99 时延（性能劣化）。任一超阈值都回滚，且回滚开关必须不依赖新服务本身存活（否则新服务宕机连回滚都执行不了）。
- **对拍有成本，放量后要采样**：影子对拍意味着双份计算。放量初期样本少可全量对拍；比例放大后对拍按比例采样（如 10%），但婚庆大单这类**低频高危样本要列入强制对拍名单**——它们恰恰是热修规则聚集地。
- **对拍不写生产数据**：影子流量只读真实输入、比对输出，新实现的落库、发消息动作在影子模式下必须短路，否则“对拍”本身就在污染生产。

（完整可运行版：[03a-示例-microservices/StranglerRouting.kt](03a-示例-microservices/StranglerRouting.kt)——影子对拍、按站灰度与错误率自动回滚；[03a-示例-microservices/QueryFromJoinToApi.kt](03a-示例-microservices/QueryFromJoinToApi.kt)——join → API 组合 → 事件复制三阶段的延迟与耦合对比。均已实际编译运行验证。）

### 2.6 契约管理与向后兼容：独立部署的前提

**概念**：微服务“可独立部署”成立的前提是——**我改自己，不会弄坏别人**。承载这个承诺的就是服务契约：接口的报文结构 + 字段语义 + 错误码承诺。没有兼容纪律，每次改接口都得拉着所有消费方同步发版，“独立部署”名存实亡——这是分布式单体最容易忽视的一种成因（另两类：按技术层拆、共享数据库，见 2.1、2.5）。

生产端纪律（向后兼容规则清单）：

- **只加不改不删**：新增字段一律可选；旧字段含义永不漂移（`amountFen` 永远是“分”；含税不含税，二选一后不再动）。
- **取值域只扩不缩**：订单状态新增 `PARTIAL_DELIVERED` 可以；把 `DELIVERED` 改名或重定义不行。
- **错误码只增不改**：消费方对未知错误码按“未知失败”兜底。
- **要减先弃用**：标记 deprecated → 兼容窗口内新旧并存（双字段或双版本路由）→ 消费方全部迁完 → 删除。

消费端纪律——**宽容读者（Tolerant Reader）**：反序列化只提取自己关心的字段，忽略未知字段；但必填字段缺失时**显式失败**，不悄悄拿默认值硬撑。反模式是严格解析：遇到未知字段就抛异常——等于宣告“生产端永远不许动报文”，把对方锁死。

❌ **反例：两类契约破坏**

```kotlin
// 生产端：price 改名 unitPrice，且单位从"分"悄悄改成"元"
// 消费端 A（严格解析器）：字段对不上直接抛异常 → 下单全线报错，【loudly 坏】
// 消费端 B（宽容读者但无语义断言）：读不到 price，静默取 0 → 钱算错一百倍，【softly 坏】
```

两类破坏里最贵的是第二种：**静默语义漂移**——解析不报错、账算错一个数量级，等对账发现已损失一个账期。所以宽容读者必须配合契约测试的语义断言：**“宽容”只针对结构，绝不针对语义**。

✅ **修正：结构宽容 + 语义卡口**

```kotlin
data class PriceView(val amountFen: Long) {
    companion object {
        fun from(msg: Map<String, Any?>): PriceView {
            val raw = msg["amountFen"] ?: msg["price"]     // 新旧字段名都认——兼容期并存
                ?: throw IllegalStateException("契约破坏：amountFen 缺失，拒绝静默兜底")
            return PriceView((raw as Number).toLong())     // 语义承诺：单位永远是"分"
        }
    }
}
// 生产端契约测试（跑在 CI）：断言报文含 amountFen 且单位为分——"改单位"这类变更在这里被卡住
```

**消费者驱动契约（Consumer-Driven Contracts）**：契约不由生产端单方面定——**谁消费，谁提交一份“我依赖哪些字段、断言什么语义”的契约**；生产端每次改接口，先在 CI 里跑全部消费方的契约测试，全绿才能发布（Pact 是这类工具的代表）。契约测试 ≠ 集成测试：它只验证“承诺”本身，不需要把服务真的拉起来——正面回应 2.3 代价表的“测试复杂”：把“起 4 个服务的集成用例”大幅压缩为“每个服务对着契约文件跑单测”。

**最小可运行示例：契约用例集 + 提供方验证**。两个消费方各提交一份契约（依赖哪些字段、断言什么语义），提供方每次构建先跑全部契约：合规报文全绿放行；破坏性变更让测试变红、发布被卡。完整代码（含 `main`，已实际编译运行验证，kotlinc 2.2.20）：

```kotlin
// ContractTestDemo.kt —— 消费者驱动契约最小演示：契约用例集 + 提供方验证，破坏契约时测试红
//
// 场景：商品服务（提供方）发布价格报文，订单服务与对账服务（消费方）各自提交契约——
//       "我依赖哪些字段、断言什么语义"。提供方每次构建先跑全部消费方契约：
//       合规报文全绿才能发布；有人把 amountFen（分）改成 unitPrice（元），CI 变红卡住发布。
//
// 运行：kotlinc ContractTestDemo.kt -include-runtime -d contract-test.jar && java -jar contract-test.jar

// ---------- 提供方：商品价格报文（兼容期内新旧字段名并存） ----------
typealias Payload = Map<String, Any?>

data class PricePayload(val itemId: String, val qty: Int, val amountFen: Long) {
    // 契约承诺：amountFen 永远是"分"，只加不改不删
    fun toPayload(): Payload =
        mapOf("itemId" to itemId, "qty" to qty, "amountFen" to amountFen, "currency" to "FEN")
}

// ---------- 消费方契约：字段存在性 + 语义断言（各自仓库维护，提交给提供方 CI） ----------
data class Expectation(val field: String, val check: (Any?) -> String?)   // 返回 null = 通过，非 null = 失败原因
data class ConsumerContract(val consumer: String, val expectations: List<Expectation>)

val orderServiceContract = ConsumerContract(
    "订单服务",
    listOf(
        Expectation("itemId") { v -> if (v is String && v.isNotEmpty()) null else "itemId 必须是非空字符串" },
        Expectation("amountFen") { v ->
            when {
                v == null -> "承诺字段 amountFen 缺失（宽容读者容忍新增字段，不容忍承诺字段消失）"
                v !is Long -> "amountFen 类型错误：期望 Long（分），实际 ${v::class.simpleName}"
                v <= 0L -> "语义断言失败：amountFen=$v 必须为正数，单位承诺是分"
                else -> null
            }
        },
    ),
)

val reconciliationContract = ConsumerContract(
    "对账服务",
    listOf(
        Expectation("itemId") { v -> if (v is String) null else "itemId 缺失" },
        Expectation("qty") { v -> if (v is Int && v > 0) null else "qty 必须是正整数" },
    ),
)

// ---------- 提供方验证：发布前必须全部契约绿 ----------
data class VerifyResult(val consumer: String, val failures: List<String>) {
    val pass: Boolean get() = failures.isEmpty()
}

fun verify(payload: Payload, contracts: List<ConsumerContract>): List<VerifyResult> =
    contracts.map { c ->
        val fails = c.expectations.mapNotNull { (field, check) ->
            check(payload[field])?.let { reason -> "[$field] $reason" }
        }
        VerifyResult(c.consumer, fails)
    }

fun report(results: List<VerifyResult>) {
    var allGreen = true
    for (r in results) {
        val mark = if (r.pass) "【绿】" else "【红】"
        println("$mark ${r.consumer}：${if (r.pass) "全部断言通过" else r.failures.joinToString("; ")}")
        if (!r.pass) allGreen = false
    }
    println(if (allGreen) "=> 契约验证通过，允许发布" else "=> 契约验证失败，发布被 CI 卡住")
}

fun main() {
    println("== 场景一：合规报文（amountFen=1200，单位分）跑全部消费方契约 ==")
    val compliant = PricePayload("SKU-01", qty = 2, amountFen = 1200L).toPayload()
    report(verify(compliant, listOf(orderServiceContract, reconciliationContract)))

    println()
    println("== 场景二：有人把 amountFen 改名 unitPrice 且单位改成元（破坏性变更）==")
    val breaking: Payload = mapOf("itemId" to "SKU-01", "qty" to 2, "unitPrice" to 1.2, "currency" to "YUAN")
    report(verify(breaking, listOf(orderServiceContract, reconciliationContract)))

    println()
    println("== 场景三：兼容演化——只加可选字段 salePrice=999（分），不删不改 ==")
    val additive = compliant + ("salePrice" to 999L)
    report(verify(additive, listOf(orderServiceContract, reconciliationContract)))
}
```

```text
【绿】 订单服务：全部断言通过

=> 契约验证通过，允许发布

```

三个场景各说一件事。场景一：**契约全绿是发布的前置门禁**，不是事后通知。场景二最有教学价值——同样的破坏性报文，订单服务的契约红了（它承诺依赖 `amountFen`），对账服务的契约仍然绿（它只依赖 `itemId` 和 `qty`）：**契约只约束各自消费方声明过的依赖**，所以提供方从红绿分布里立刻知道“这次破坏伤及谁、伤在哪”，而不是等订单服务上线后出事再回溯；同时“改单位”这种 2.6 开头说的最贵静默漂移，在这里被语义断言拦在 CI 里，而不是等月底对账发现账错一个数量级。场景三：**只加可选字段**的兼容演化全绿——这正是向后兼容规则清单第一条想要的效果：提供方保留演化的自由，消费方不被打扰。

与真实工具的对应关系（片段示意，Pact 的契约文件是消费方期望的 JSON 化，不需要跑服务即可验证）：

```json
{
  "consumer": { "name": "order-service" },
  "provider": { "name": "product-service" },
  "interactions": [
    {
      "uponReceiving": "一个商品价格查询",
      "withRequest": { "method": "GET", "path": "/prices/SKU-01" },
      "willRespondWith": {
        "status": 200,
        "body": { "itemId": "SKU-01", "amountFen": 1200 }
      }
    }
  ],
  "metadata": { "pactSpecification": { "version": "2.0.0" } }
}
```

工程判据：**稳定的消费方达到 2 个以上才值得建契约体系**——只有一个消费方时，一条集成测试就够，契约基建是纯开销；消费方一多，“提供方改接口 → 拉所有消费方联调”的协调成本指数上升，契约测试把这场联调压缩成提供方 CI 里的一次本地验证。同时要认清契约测试**卡得住什么、放走什么**：它卡得住“承诺字段消失/语义漂移”（结构 + 语义断言），放得走“未承诺字段的新增与内部实现重构”——后者正是留给提供方的演化自由，与消费端的宽容读者严丝合缝地配合。反过来，契约测试替代不了集成测试：跨服务的时序问题（超时、重试、乱序）、消息中间件的真实行为、部署环境的差异，都在契约的视野之外——两者是互补的卡口，不是替代关系。

**共享库的边界**：可以共享的只有两类——

1. **与业务无关的基础设施**：日志格式、traceId 透传、重试工具（各自独立发版，多版本并存）；
2. **契约本身**：薄的 DTO / schema / proto 文件，作为接口定义发布给消费方。

不能共享的是**领域模型**。把 `User`、`Order` 实体抽成 common-domain-lib 让所有服务引用，看似“避免重复定义”，实则把 2.1 辛苦划出的边界重新焊死：商城域的“订单”（价格、支付状态）和配送域的“订单”（桶数、楼层、时间窗）本来就应该是两个类。领域不共享、重复定义是**特性**不是缺陷——重复正是解耦的代价与凭证。共享领域库是最隐蔽的一种分布式单体成因，且它常常打着“代码复用”的旗号出现。

## 微服务成熟度自评表

拆分、数据、治理、可观测、组织五个维度，各分三级。先说用法：**这张表是能力坐标，不是进化目标——级高不等于好，匹配团队才好**。3 人团队硬冲 L3 是给自己买刑具，200 人平台停在 L1 是给自己埋雷；评分目的是找短板，不是刷分。建议半年一评，每次只挑“与当前痛点最相关的 1~2 个维度”做提升。

| 维度 | L1 起步 | L2 规范 | L3 成熟 |
|---|---|---|---|
| 拆分 | 拆了服务但边界靠感觉，从没跑过 2.1 的量化自检 | 三项粒度指标（需求跨服务数/同步深度/发布联动率）定期体检，边界与需求对齐 | 粒度可逆：敢拆也敢合（2.5 合并信号例行巡检），粒度跟随组织与负载调整 |
| 数据 | 逻辑共库，schema 归属含糊，改表要开会 | 每服务私有库，跨服务只走 API/事件，数据所有权一表一主 | 拆库有全套配套：对账任务、事件复制读模型、数据迁移演练过、有回滚剧本 |
| 治理 | 调用无超时，故障靠人工重启 | 超时/熔断/降级全覆盖，注册发现有本地缓存兜底 | 治理策略集中下发、可灰度；故障注入（chaos）例行化，回滚开关演练过 |
| 可观测 | 各服务各看各的日志，排障靠猜 | traceId 全链贯穿，核心指标有告警，能定位到服务 | SLO 驱动：错误预算、依赖拓扑自动发现、慢查询可归因到具体服务与版本 |
| 组织 | 一人守一串服务，oncall 无边界 | 服务与团队一一对应，谁建设谁运营 | “你建你跑”制度化：独立部署率、需求跨服务数纳入团队健康度指标 |

桶装水 10 人团队的合理定位：拆分 L1→L2（刚跑起量化自检）、数据 L1（还是逻辑共库）、治理 L2（超时熔断齐了）、可观测 L1→L2（traceId 已贯穿）、组织 L1（还在贴线）——总分不高，但每一格都匹配现状，这就是好的评分。对照 2.3 的审判结论：“模块化单体为主 + 至多拆一个排线服务”的团队，成熟度停在 L1~L2 恰恰是**正确**的；等团队过 30 人、排线算法团队独立成组，拆分维度的目标才会自然上移。

最后提醒一条跳级禁令：**任何维度跳级都会出问题**。没有 L2 治理就直接冲 L3 拆分，等于把故障面切成 N 份却不给灭火器；没有 L2 数据就谈 L3 可观测，traceId 串得再好也查不清共库表谁改的。补短板的顺序通常应是：治理与可观测先行（L2），数据跟上（L2），拆分与组织最后到位（L2→L3）。
