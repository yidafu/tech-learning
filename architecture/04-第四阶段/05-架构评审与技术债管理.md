# 架构评审与技术债管理
> [返回：软件架构学习大纲](../软件架构学习大纲.md)

> 本节是第四阶段“架构方法论”的收尾分册。前三册讲了怎么表达决策（[C4 与 ADR](02-架构设计与表达-C4视图与ADR.md)）、怎么划边界（[DDD](03-领域驱动设计-DDD.md)）、怎么让系统在约束下持续演进（[适应度函数与绞杀者](04-演进式架构-适应度函数与绞杀者.md)）；这一册回答三个更现实的问题：**评审怎么把个人判断变成组织记忆，技术债怎么像金融债一样记账和偿还，治理怎么让约定真正“长牙”**。三件事合起来，就是架构师的日常运维工作——前几册是“设计方法论”，本册是“使设计持续成立的方法论”。

## 1. 架构评审：把决策变成组织记忆

先纠正一个流行误解：架构评审的目的不是“挑错”，也不是“领导把关”。评审的本质是三件事：

1. **把隐性判断显性化**：陈述者为了过评审，必须把“我为什么这么设计”说清楚——很多设计者在准备材料时自己发现了问题，这是评审最大的收益，发生在会前而不是会上；
2. **把个人判断变成组织判断**：一个模块的边界如果只存在于设计者脑子里，他离职边界就消失了；评审通过 + ADR 落笔，边界才进入组织记忆；
3. **把分歧当场解决或显式挂起**：两个团队对接口归属各执一词，不评审就会各做各的，上线那天用生产事故对齐。

反过来说，如果一场评审既不产生新信息、不沉淀记录、不解决分歧，它就只剩一个功能——免责签字。这样的评审不如不开。

### 1.1 评审什么、不评审什么

评审是昂贵的（五六个人一小时 ≈ 大半个人日），所以第一个问题不是“怎么评”，而是“什么配得上评审”。判据只有三条，而且都可以归结为一个问题：**这个决策做错了，回头改的代价是线性的还是指数的？**

| 判据 | 典型对象 | 是否进架构评审 | 理由 |
|---|---|---|---|
| 跨模块契约 | 服务间接口、事件 schema、共享表结构、SDK 发布 | 评审 | 契约的修改成本随消费方数量增长，改错是指数代价 |
| 不可逆 / 单向门决策 | 拆服务、选数据库/中间件、引入新框架、数据格式定版 | 评审 | 第一阶段讲过的“单向门”：回头走要推倒重来，必须多方共识 |
| 质量属性达标签门 | 性能场景验收、可用性预案、容量推演 | 评审（发布前） | 带数字的场景卡必须有人核验（呼应[章节1 质量属性六要素](../01-第一阶段/04-架构质量属性.md)） |
| 有预案的可逆决策 | 函数抽取、模块内部重构、可一键回退的参数调整 | 不评审 | 走正常代码评审即可；错了改回来是线性代价 |
| 局部实现细节 | 私有方法命名、循环写法、日志措辞 | 不评审 | 属于代码评审范畴，抬进架构评审是浪费 |
| 未定版的技术尝试 | spike 验证性代码、技术预研原型 | 不评审 | 原型的使命就是被丢弃，评它是给垃圾镀金 |

三句话总结这张表：**契约、单向门、带数字的验收，评审；其余交给代码评审和自动化检查**。还有一条隐藏判据——评审频率是架构健康的信号：如果一个团队每周要开三次架构评审，说明要么契约定义得太多（该收权），要么没有自动化检查（该建门禁，见第 3 节），评审被当成了人工 CI。

评审有三种形态，时机、对象、产物各不相同，别混成一种会：

| 形态 | 时机 | 对象 | 时长 | 产物 |
|---|---|---|---|---|
| 设计评审 | 编码开始前 | C4 图 + 关键决策点 + 质量属性场景卡 | 60~90 分钟 | 评审结论 + ADR 草案（或修订） |
| 代码级架构走查 | 首个垂直切片合并前 | 真实代码的分层与依赖方向（不是逐行读代码，是核对“图与代码是否一致”） | 45~60 分钟 | 架构符合性清单 + 待立项的适应度函数 |
| 发布前检门 | 上线前 | 场景验证结果（压测报告、演练记录）+ 回滚预案 | 30 分钟 | 检门记录：通过 / 有条件通过 / 打回 |

三种形态不是三次独立会议，而是一条**证据链的接力**：设计评审产出的 C4 图与 ADR，是走查时核对“图与代码是否一致”的基准——没有基准的走查只能凭感觉；走查产出的架构符合性清单与适应度函数立项，是检门时要逐条复核的输入——没有清单的检门只能重新争论。上一环节的产物是下一环节的依据，这是三者必须分开开会的原因：把三件事压缩成一场两小时的会，每一件都做不实。对小型变更，三种形态可以合并降级（设计评审并入走查、检门由 CI 门禁自动完成），但降级的依据是变更影响面小，而不是“没时间”。

❌ 反例：桶装水商城早期把“配送排线独立服务”的设计评审排在了上线前夜。评审全票通过、通过率 100%——因为那时代码都写完了，任何打回都等于返工，评审唯一的功能是让架构师在责任书上签字。
✅ 修正：设计评审必须发生在写第一行生产代码之前；走查发生在第一个切片合并前；检门只核验“说过的做到了”，不重新讨论设计。三种形态各守各的时间点，错后一步，评审就从“防风险”退化成“背书”。

### 1.2 评审会怎么开

评审会的质量在会前就决定了大半。分三段说。

**会前：材料清单，缺材料不开会。** 四样：

1. **C4 图一页**：L1/L2 级别（系统上下文 + 容器），用高亮标出本次变更涉及的部分（画法见 [02 分册 1.1](02-架构设计与表达-C4视图与ADR.md)）；
2. **关键决策点 3~5 个**：每个列出备选方案与取舍理由，最好的载体就是 ADR 草案——评审会不是让与会者从零理解设计，而是让他们挑战已经写下来的判断；
3. **质量属性场景卡**：只放本次变更承诺的场景，每张必须带数字（P99、错误率、恢复时限），不带数字的场景卡退回重写；
4. **“不做什么”清单**：本次变更明确不解决的问题——没有这张清单，评审会必然膨胀成对整个系统的批斗会。

与会人数也有判据：**能对决策点投出有效票的最小集合**——决策的受影响方、有否决权的相关方（如安全、法务、上游团队），再加一名与本案无关的“外行”挑战者（专职提傻问题，防集体盲区）。人多了变务虚大会，人少了变橡皮图章；十人上下的评审会，通常意味着材料已经写得太薄，靠与会人数在兜底。

**会中：三个角色 + 一条铁律。** 角色三件套：

- **引导者**：控制节奏、分配发言，**不裁决设计对错**。架构师可以当评审者，但别默认当裁判——既当运动员又当裁判的评审，产出的是服从而不是共识；
- **记录者**：现场记下每条分歧与结论，散会前当众复述一遍“今天定了什么、挂起了什么”。这个角色必须存在且与陈述者不是同一人；
- **陈述者**：讲清“问题—方案—代价”，特别是代价。只讲好处的评审陈述等于广告。

铁律是**“先对齐问题，再争论方案”**：会议前 10 分钟只允许讨论“要解决什么问题、约束是什么”，禁止进入方案比较。这不是形式主义——大量评审争吵的根源是各方在解不同的问题，方案之争只是症状。

> 桶装水商城的真实一幕：配送排线评审会上，第五分钟就有人开吵“通知订单该用 Kafka 还是 RocketMQ”。引导者打断：先确认问题——是“排线结果如何通知订单域”（消息选型问题），还是“排线计算本身如何与交易解耦”（事件边界问题）？对齐后发现两拨人争的根本不是同一层的事：前者是事件驱动的选型细节（第三阶段内容），后者才是本次评审的核心决策。议题回到正轨。

另外两条操作性纪律：每个决策点 **15 分钟时间盒**，谈不完的转线下另约（会上硬磨是磨不出共识的，只会磨出怨气）；结论只有三种——**通过 / 有条件通过（条件 = 登记技术债或补 ADR，见第 2、3 节）/ 打回**。“原则上通过、细节再看看”不是结论，是把评审成本转嫁给会后的灰色状态。

**会后：记录是评审的交付物。** 三件事，24 小时内完成：评审记录发相关方；通过的决策补完 ADR（三条纪律——一决策一文件、状态显式、负向后果必须写——见 [02 分册 1.3](02-架构设计与表达-C4视图与ADR.md)）；“有条件通过”的条件进入技术债登记簿或任务看板，**不允许只留在会议纪要的措辞里**。检验标准很简单：半年后新人不翻聊天记录，就能回答“当时为什么这么定、有哪些未了条件”。

评审记录的最小模板（记录者现场填，散会前当众复述）：

```text
# 评审记录：配送排线独立服务（2026-10-20）
结论：有条件通过（条件见末条，未了条件计入登记簿/看板）
决策点逐条：
  D1 排线计算与交易解耦方式 → 事件驱动，消费 OrderPaid ｜ 无挂起
  D2 排线结果回供订单的通道 → 开放主机服务查询接口 ｜ 挂起：分页语义定义（张三，两周）
转债清单：TD-021 接口文档补齐（负责人、触发条件、期限）
转 ADR 清单：ADR-007 草案按本次结论修订后归档
```

模板的五栏（结论 / 决策点 / 挂起项 / 转债 / 转 ADR）缺一不可——特别是“转债清单”栏：评审是发现债的第一现场，这一栏空着的评审记录，往往意味着发现被当场放走了。

四例评审反模式，各配症状与解法：

| 反模式 | 症状 | 根因 | 解法 |
|---|---|---|---|
| 走过场签字会 | 近三个月通过率 100%，评审意见全是错别字级别 | 评审开得太晚或太浅，无人真读材料 | 抽样复盘评审记录；通过率连续 > 90% 就前移评审时机、砍掉例行评审 |
| 审美大战 | 为命名和代码风格吵 40 分钟，真正的问题没时间谈 | 把代码评审的议题抬进了架构评审 | 风格问题交给规范文档与格式化工具（CI 自动改），架构评审只裁“架构可见”的分歧 |
| 权威一言堂 | 最资深的人发言后全场安静，结论 = 他的第一直觉 | 服从权威压过了技术论证 | 引导者强制发言顺序：先请资历最浅者；重大分歧改为会前书面背对背打分，会上只谈分歧点 |
| 无记录评审 | 结论散落在聊天记录，三个月后无人能复述 | 没人把记录当交付物 | 立纪律：无 ADR / 无记录的评审视为未发生；记录者角色强制设岗 |

### 1.3 评审 Checklist 示例：配送排线独立服务

把 1.1 的判据和 1.2 的流程落到一张能直接用的清单上。背景取自 [02 分册 ADR-007](02-架构设计与表达-C4视图与ADR.md)：桶装水商城把配送排线从单体拆为独立服务。评审这 10 条，每条都有**检查项 + 通过判据 + 不通过的处置**——处置分三档：**阻塞**（不解决不上线）、**转债**（登记进技术债登记簿、带触发条件后放行）、**备忘**（记入 ADR 复查点即可）。

| # | 类别 | 检查项 | 通过判据 | 不通过的处置 |
|---|---|---|---|---|
| 1 | 边界 | 地图 / 距离矩阵等外部依赖是否收敛在配送服务内部 | 商城与订单服务代码中搜索不到任何地图 API 直接调用，全部经配送服务开放主机接口 | 阻塞：收敛后再上会（这是拆分动机本身，退让等于没拆） |
| 2 | 边界 | 订单域与配送域是否只通过事件和公开接口交互 | 无点对点直读对方数据库表、无引用对方内部类；依赖方向与 C4 图一致 | 阻塞 + 转债：当场改，遗留部分登记债并立适应度函数守门（呼应 [04 分册](04-演进式架构-适应度函数与绞杀者.md)） |
| 3 | 边界 | 配送服务“明确不做什么”是否写清 | README 三行摘要含职责、依赖、不做什么（如：不做运费计价、不改订单状态） | 备忘：补入 README，进下次走查核对 |
| 4 | 契约 | OrderPaid 事件 schema 是否版本化且向后兼容 | 只增不删字段；消费侧按 Tolerant Reader 处理未知字段；schema 文件进仓库受版本控制 | 阻塞：契约未定版不允许消费方开工 |
| 5 | 契约 | 排线结果查询接口的幂等与分页语义是否写清 | 接口文档含幂等键、重试语义、分页游标定义；重复查询结果一致 | 转债：接口文档任务进看板，两周内补齐 |
| 6 | 一致性 | 配送任务生成失败（消费侧异常）的补偿路径是否存在 | 消息重试 + 死信队列 + 人工兜底操作清单三者齐备，兜底清单有演练记录 | 阻塞：缺死信或兜底清单不上线（订单支付成功但配送任务丢失是资金级事故） |
| 7 | 一致性 | 订单状态与配送状态是否有日终对账 | 对账任务覆盖“已支付未排线”“已排线未送达超时”两类差异，差异触发告警 | 转债：对账任务排期 ≤ 1 个迭代 |
| 8 | 可观测 | 链路 ID 是否跨服务透传 | 任选一笔订单，能在 tracing 系统串出“下单 → 支付 → 排线”完整链路 | 阻塞：埋点不齐不上线（微服务排障没有 trace 是盲人摸象，见章节5 可观测性） |
| 9 | 可观测 | 排线积压是否有监控与告警阈值 | “未排线任务数”“积压时长”两项指标入看板，积压 > 30 分钟告警值班 | 转债：指标任务排期，上线首周人工巡检顶替 |
| 10 | 回滚 + 容量 | 新链路能否一键切回单体路径；早高峰批量排线的容量水位是否推演过 | 功能开关已演练切换；压测报告给出排线服务容量水位与降级策略（高峰降级为“延迟送达容忍”） | 转债：压测与演练给出截止日，检门时复核 |

这张清单的用法是**按条给结论**，而不是按次给总分：10 条里 8 条通过、2 条转债，只要转债条目带触发条件和期限，就是一次合格的评审——追求“10 条全绿才放行”的团队，最后学会的是怎么把问题藏起来不写进清单。

## 2. 技术债：像管理金融债一样管理

“技术债”这个词被严重滥用了：有人把所有自己不喜欢的代码都叫技术债，于是这个词失去了管理意义。先把类别理清，再谈记账和偿还。

### 2.1 准确的类比与常见的误用

Ward Cunningham 提出这个类比时，说的场景是：**为了当期交付更快，故意选择一条不够优雅但能跑通的路**——此后每次在这段代码上做变更，都要多付一部分额外成本。这个类比的三个要点，恰好是“什么算债”的判别标准：

1. **借的时候知道**：有意识地选择了捷径（而不是单纯能力不足写出的烂代码）；
2. **换来了当期速度**：这笔“借款”当时是有回报的（赶上了发布窗口）；
3. **此后持续计息**：利息可以观察、可以估算——这是它区别于“烂代码”的关键。

❌ 反例（误用）：“这个模块写得真烂，全是技术债。”——如果说不清利息是多少、什么时候借的、还清要多少本金，它就不是一笔债，而是一段需要重新认识的代码。泛化的“技术债”没法排优先级，也就没法管理。
✅ 修正：用三条判据重新表述——“押金计算在三个地方各有一份实现（位置具体），是 2025 年 11 月赶水站开城时故意抄近路欠下的（借款时间与动机），导致此后每次调费率都要改三处、每月约 3 人日额外成本（利息可估）。”——这才是一笔能进登记簿的债。

Martin Fowler 的四象限把“怎么欠的”拆成两个维度：**是否故意（知道 / 不知道）× 是否谨慎（有纪律 / 无纪律）**：

| | 鲁莽（无纪律） | 谨慎（有纪律） |
|---|---|---|
| **故意** | “没时间设计接口了，订单服务直接查配送的表。”——知道是债，赌没人来收 | “上线日期不能动，先双写旧表，登记债，下季度专项还。”——知道是债，有偿还计划 |
| **无意** | “什么是分层？”——不知道自己欠了债，连登记都做不到 | “给每个模块都加了抽象层，事后发现九成抽象从未被第二个实现复用。”——事后复盘才意识到当初可以更简单 |

这四格里，**故意·谨慎**是健康的（权衡后的负债经营，本节全部管理手段服务的就是它）；**故意·鲁莽**常见于救火期，管理目标是“欠可以，必须登记”；**无意·鲁莽**最危险——当事人不知道这是债，评审和走查是发现它的主要手段；**无意·谨慎**是过度设计，偿还方式往往是做减法（删抽象层），而不是加代码。

**利息怎么观察。** 金融债的利息写在合同上，技术债的利息藏在四个可观测指标里：

| 指标 | 观察方法 | 利息信号 |
|---|---|---|
| 变更热点 | 把近 6 个月 git 提交按文件 / 目录聚合，排序取前 10 | 热点文件与债项位置重合：同一段代码被反复“修补”，修补本身就是利息支出 |
| 同需求耗时对比 | 同类需求在本模块与干净模块的实际人日对比 | 差值就是利息：押金模块改一个费率 3 人日，商品模块改一个价格 0.5 人日 |
| 全量测试运行时长 | CI 测试耗时趋势 | 月增长率 > 10% 说明测试套件在被债务拖累（冗余用例、脆弱用例、慢依赖） |
| 发布耗时 | 从代码完成到生产可用的小时数趋势 | 上线要人工协调的环节越多，通常说明债越重（配置散落、环境不可复制） |

利息的单位统一折算成**人日**，后面登记簿和优先级排序才能可加、可比。

还要把债的两类持有成本分开记账：**利息是确定性的慢损耗**（每天都在付，表现为变慢），**风险是小概率的大损失**（平时不付，爆一次付一大笔）。二者必须分列而不是笼统写个“影响”，因为应对手段不同：重构同时降低两者；而护栏手段——监控、对账、降级预案——主要压低风险（降低爆炸半径、缩短恢复时间），对利息几乎无用。老优惠券引擎“只还利息”策略的本质，就是用廉价的护栏把风险钉住、容忍利息，直到模块退役。登记簿里风险写成“年故障概率 × 爆炸半径”两个因子而不是一个数，正是为了逼登记人分别回答“它多容易炸”和“炸了多疼”，这两个问题的答案来源完全不同（前者看历史变更频率与告警记录，后者看下游依赖与资金/客诉敏感度）。

### 2.2 技术债登记簿

和金融债一样，管理债的第一步是记账。登记簿不需要重型系统，一个共享表格甚至一个 markdown 文件都行，**关键是字段齐全、人人可看、有维护纪律**。

| 字段 | 说明 | 纪律 |
|---|---|---|
| 编号 | TD-001 递增 | 引用靠编号，别靠标题 |
| 标题 | 一句话说清欠了什么 | 能让没参与的人看懂 |
| 位置 | 模块 / 类 / 文件 | 必须具体到能搜索；“大概在订单那边”等于没登记 |
| 类型 | Fowler 四象限 | 区分“故意·谨慎”与“无意·鲁莽”，前者是决策、后者是事故 |
| 利息 | 每月拖慢的人日 | 必须有依据（变更热点、耗时对比），哪怕粗估；不写利息的债无法排优先级 |
| 本金 | 一次性还清（重构）所需人日 | 可由当事人 + 一位旁观者共同估 |
| 风险 | 年故障概率 × 爆炸半径（故障恢复 + 业务损失折算人日） | 风险是利息之外的第二类持有成本：有的债平时不拖速度，但炸一次很痛 |
| 偿还策略 | 立即还 / 分期还 / 只还利息 / 违约核销 | 见 2.3 |
| 触发条件 | 什么信号出现就必须升级偿还 | **必备字段**。没有触发条件的债会永远“再等等” |
| 负责人、登记日期 | 记账的基本元数据 | 每次评审 / 巡检复核更新 |

登记簿的维护节奏比字段本身更容易失守，两条纪律：每条债有显式**状态机**——登记中 → 偿还中 → 已偿还 / 已核销，状态不流动的债项超过一个季度，就在季度复审时强制处理（还、拆小、或明确“只还利息”）；整本登记簿**每季度走查一次**，配合触发条件的兑现情况重排优先级——利息、本金、风险三个数都是估计值，半年不复核的估计值和编造没有区别。登记簿烂掉的最典型症状是“只进不出”：债项只增不减、状态永远停在“登记中”，团队很快就会发现记了也没人看，登记纪律随之瓦解。

下面是本节的核心示例：**登记簿的最小领域模型 + 偿还优先级排序**（Kotlin，完整可运行，已用 kotlinc 2.2.20 编译运行验证）。排序逻辑设计成金融上的“回本速度”：

> 优先级分 = 年化持有成本 ÷ 本金 =（月利息 × 12 + 年故障概率 × 爆炸半径）÷ 重构人日
>
> 含义：**每投入 1 人日还这笔债，一年能省回多少人日**——回本最快的先还。

```kotlin
// TechDebt.kt —— 技术债登记簿：最小领域模型 + 偿还优先级排序
// 编译运行：kotlinc TechDebt.kt -include-runtime -d techdebt.jar && java -jar techdebt.jar

/** 债是怎么欠下的：Fowler 四象限 */
enum class DebtNature(val label: String) {
    DELIBERATE_RECKLESS("故意·鲁莽"),
    DELIBERATE_PRUDENT("故意·谨慎"),
    INADVERTENT_RECKLESS("无意·鲁莽"),
    INADVERTENT_PRUDENT("无意·谨慎"),
}

/** 偿还策略四选一 */
enum class RepayStrategy(val label: String) {
    PAY_NOW("立即还"),
    PAY_IN_INSTALLMENTS("分期还"),
    PAY_INTEREST_ONLY("只还利息（加护栏不重构）"),
    DEFAULT_WRITE_OFF("违约核销（删除）"),
}

/**
 * 一条技术债。金额类字段单位统一为"人日"：
 * - interestPerMonth 利息 = 该债每月额外拖慢团队的人日；
 * - principalCost    本金 = 一次性还清（重构）所需人日；
 * - 风险 = 年故障概率 × 爆炸半径（故障恢复 + 业务损失折算人日）。
 */
data class DebtItem(
    val id: String,
    val title: String,
    val location: String,
    val nature: DebtNature,
    val interestPerMonth: Double,
    val principalCost: Double,
    val failureProbPerYear: Double,
    val blastRadiusDays: Double,
    val repayStrategy: RepayStrategy,
    val trigger: String,
) {
    /** 风险期望成本（人日/年）= 年故障概率 × 爆炸半径 */
    val annualRiskCost: Double get() = failureProbPerYear * blastRadiusDays

    /** 年化持有成本 = 年利息 + 年风险期望损失 */
    val annualCarryingCost: Double get() = interestPerMonth * 12 + annualRiskCost

    /** 优先级分 = 年化持有成本 / 本金：每投入 1 人日还债，一年能省回多少人日 */
    val priorityScore: Double
        get() = annualCarryingCost / if (principalCost <= 0.0) 1.0 else principalCost

    /** 回本期（年）= 本金 / 年化持有成本 */
    val paybackYears: Double
        get() = principalCost / if (annualCarryingCost <= 0.0) Double.MAX_VALUE else annualCarryingCost
}
```

（`main` 中构造 6 条债项——押金规则散落三处、周期购扫表缺索引、老优惠券引擎、排线算法复制变体、工单状态机 if-else、废弃短信通道——按优先级降序输出偿还队列、核销队列与偿还能力面板。完整源码与运行输出见本节末尾附录。）

### 2.3 偿还策略四选一

每笔债进入偿还队列后，先选策略。四选一的判据表：

| 策略 | 适用场景 | 判据 | 桶装水商城示例 |
|---|---|---|---|
| **立即还** | 利息高、本金小 | 优先级分高且回本期 < 0.5 年；或债在核心交易链路 | TD-002 扫表缺索引：本金 2 人日，一次迭代顺手还清 |
| **分期还** | 本金大、可拆分、每期结束系统可用 | 重构能切成互不依赖的阶段，每阶段独立验收 | TD-001 押金三处：第一期统一下单侧、第二期退桶侧、第三期对账侧改读统一策略 |
| **只还利息不还本金** | 本金大、业务价值在衰减（模块将退役） | 回本期 > 模块剩余生命周期；加护栏（监控、对账、测试）把风险钉住 | TD-003 老优惠券引擎：补监控与手工对账，等下线，不重构 |
| **违约不还（核销）** | 代码不再被使用 | 无调用方、无数据依赖 | TD-006 废弃短信通道：直接删除。**最便宜的偿还是删除**——债的另一种结局是“债权人消失” |

两种常见误区。其一，“只还利息”被滥用成“永远不还”——判据很清楚：它只适用于业务价值衰减中的模块，且必须有触发条件（TD-003 的触发条件是“旧活动复活或占比回升 > 15%”，一旦触发就要重新选择策略）。其二，“分期还”被做成“无限期还”——分期必须写在登记簿里（每期范围与验收标准），否则不是分期，是拖延。

**重构预算制度化**：策略定了，钱（人日）从哪来？两种模式：

| 模式 | 做法 | 适用团队 | 风险 |
|---|---|---|---|
| **固定比例预算**（如每迭代 20% 还债） | 每个迭代排期时固定划出两成人日给登记簿队列 | 债多而散、产品方信任工程团队自律 | 赶工期时最容易被挪用——挪用一次，“预算”就退化成“建议” |
| **债务驱动专项** | 从登记簿挑高息债立专项，明确范围与验收 | 高息债集中（押金三处这种）、需要向管理层要资源的场合 | 日常新债无人管：专项还旧债的同时，新债照常积累 |

成熟团队通常混合使用：日常 20% 预算滚动偿还小额债，每季度看一次登记簿，若**月利息合计超过团队产能的 15%**（示例输出里是 47.5%，远超），就立专项集中还队首的大额债。判据背后的直觉：利息支出吃掉近半产能的团队，任何功能排期都已经是债的奴仆——先把产能赎回来再谈迭代效率。

金融类比里还有一样东西技术债同样逃不掉：**复利**。没人偿还的债不是线性变贵，而是指数变贵——每层新的补丁都叠在旧捷径上，本金本身会膨胀：复制出的第二份押金实现（本金 12 人日）拖着不还，半年后会有人为了绕开它的 bug 再包一层适配（本金涨到 18 人日），而试图动它的人要先读懂三层历史包袱，重构报价继续上调。判据：**季度复审时某债项的本金估算上调超过 50%，视为复利已启动**，该债项在队列里自动前置——登记簿排序公式算的是“现在的回本速度”，而复利意味着它未来的分数只会更高，晚还不如早还。

### 2.4 预防新债的四道闸

偿还旧债的同时必须阻止新债加速流入，否则登记簿永远还不完。四道闸，分别对应本阶段四个分册的能力：

| 闸 | 做法 | 防的是哪类债 | 出处 |
|---|---|---|---|
| **ADR 记录妥协与触发条件** | 决策时把已知妥协写进 ADR 负向后果栏，并设复查点；复查点就是这笔债的“到期日” | 故意·谨慎型债失控：借款时说好的“下季度还”没人记得 | [02 分册 1.3](02-架构设计与表达-C4视图与ADR.md) |
| **适应度函数守门** | 把“不得出现第二份押金计算实现”这类约束写成 CI 断言，违规提交直接红 | 无意·鲁莽型债：新人在不知情的情况下复制旧模式 | [04 分册 3.2](04-演进式架构-适应度函数与绞杀者.md) |
| **评审清单** | 把反复出现的债升级为 checklist 条目（如 1.3 清单的第 2 条就是从历史债项提炼的） | 同一个坑进第二次：评审时人记不住所有历史教训，清单记得住 | 本册 1.3 |
| **“债要登记才准欠”纪律** | 允许欠债，但必须当场进登记簿并写触发条件；巡检发现未登记的债，升级为阻塞项 | 隐性债：最大的债是账外的债 | 本册 + 第 3 节治理 |

四道闸的共同逻辑：**让“欠债”这个动作从无意识变有意识、从口头变留痕、从留痕变有价**。预防的性价比远高于偿还——押金三处这笔债，如果在第一份复制实现合入前有一条适应度函数拦一下，12 人日本金和 40 人日风险敞口就都不存在了；一道 CI 断言的编写成本是半天。

## 3. 架构治理：让约定长牙

评审和登记簿是“事件驱动”的——靠一次次会议和记账运转。治理是“常驻机制”：**在没有评审会的每一个普通日子里，替你盯着约定的人**。

### 3.1 治理 vs 管理之辨

先辨词。**管理**是盯着人：架构师看代码、拉群里提醒“这个别直接依赖数据库”、逐个团队反复强调分层。**治理**是设计规则：把约定变成自动检查 + 例外流程，让系统自己守规矩。区分二者的试金石是扩展性——**管理的成本随服务数量线性增长，治理的成本接近固定**。一个人盯十个人的团队叫管理，盯一百个人的团队叫心力交瘁；而一套 CI 门禁盯十个人和一百个人，成本几乎一样。

❌ 反例（管理式治理）：某平台团队二十个微服务，架构师坚持每笔 PR 亲自过目“有没有破坏分层”。头三个月有效；半年后 PR 积压、团队开始绕过他走自己的仓库，分层反而加速崩坏——单点人工检查挡不住规模，还会制造对立。
✅ 修正：把分层规则写成适应度函数进 CI（治理），架构师只处理门禁报出的例外申请（例外流程）。人从“守门员”退到“规则制定者 + 例外裁判”。

治理分三个层次，逐层递进，**跳层是空转**：

| 层次 | 内容 | 判据 |
|---|---|---|
| 一、约定成文 | 分层规则、依赖方向、命名、契约规范写成文档（ADR + README + 统一词表） | 新成员不问人就能找到规则全文；找不到的约定等于不存在 |
| 二、检查自动化 | 每条**可判定的**约定配自动检查，进 CI 或定时巡检 | 违规的提交会红，而不是靠评审或人举报逮住 |
| 三、例外显式化 | 每条规则配豁免流程：谁能批、批什么条件、有效期多久 | 每条豁免有期限与补偿；见 3.3 |

第三层是“长牙”的关键：**约定没有后果就不是约定，是建议**。后果不需要严刑峻法，三个就够——CI 红、发布被拦、违规债强制登记升级。没有这三颗牙，前两层写得再漂亮也只是装饰品。

治理机制本身也需要被度量——门禁没人管也会腐烂。三个指标按月看：**门禁误报率**（拦截后被复审推翻的比例，持续高于两成说明规则定错该修规则）；**豁免存量与月增**（3.3 详述，腐化的先行指标）；**违规平均滞留时长**（从 CI 变红到修复或豁免的天数——红了没人理的 CI 只剩噪音）。一条总判据：**团队对门禁的第一反应是“又拦住一个”而不是“又烦人一次”**——前者说明门禁在产生价值，后者说明门禁已经退化成流程税，该做一次规则体检了。

还有一条诚实的边界：治理只能覆盖**可判定**的约定。“依赖方向不得反向”“接口必须版本化”可以判定；“设计要优雅”“抽象要恰当”不可判定。试图把不可判定的约定也交给机器管的团队，最后得到的是一批没有意义的 lint 规则；这类判断仍然属于评审（第 1 节）和走查的领域。

### 3.2 治理工具箱

按“约定作用的层次”分三类，每类给判据和一个工具示例（均为片段级示意，未随本节编译运行）：

**静态检查——看代码里的结构。** 判据：一条架构约束如果能在测试里断言，就不允许只存在于文档里（02 分册“可发现性”手段三的同款原则）。工具示例：ArchUnit 断言依赖方向。

```kotlin
// 片段：押金领域层纯净性门禁（ArchUnit，deposit-service CI 中的架构测试节选）
// 约定：押金领域层不得依赖基础设施（框架、数据库、HTTP），也不得被上层反向渗透
archRule(
    noClasses().that().resideInAPackage("..deposit.domain..")
        .should().dependOnClassesThat().resideInAnyPackage(
            "..deposit.infrastructure..", "org.springframework..", "java.net..")
).check(importedClasses)
```

这条断言守住的正是 [DDD 分册 2.7](03-领域驱动设计-DDD.md) 的仓储依赖方向纪律：接口在领域层、实现在基础设施层——规则写在 DDD 教材里十年了，没牙的团队照样写出 `DepositRepositoryImpl` 被领域服务直接 new 的代码。

不是每个仓库都值得上 ArchUnit，最简形态的静态检查一个脚本就能起步——把“禁止反向依赖”写成 import 白名单：

```bash
# 片段：模块间 import 白名单检查（订单模块仓库的 CI 步骤节选，示意）
# 约定：订单域不得 import 配送域内部包（内部实现可以自由重构的前提是没人盯它）
violations=$(grep -rn "import .*\.delivery\.internal\." --include="*.kt" order-domain/ || true)
if [ -n "$violations" ]; then
  echo "架构违规：订单域引用了配送域内部实现，请改走公开接口"; echo "$violations"; exit 1
fi
```

起步用脚本、成熟后迁 ArchUnit，判据不变：**规则要么可自动判定并进 CI，要么明确承认它只归评审管**——最糟的状态是写在规范文档里、无人检查也无人承认没人检查。

**CI 门禁——看变更是否越过底线。** 判据：门禁失败只有两条出路——修复或走豁免（3.3），不存在“先上线再说”。

```yaml
# 片段：delivery-service 流水线门禁节选（示意）
quality_gates:
  - test_coverage: { incremental_min: 0.6 }        # 增量覆盖率 >= 60%
  - arch_fitness: { suite: "arch-tests" }          # 适应度函数套件全绿
  - perf_baseline:                                  # 关键接口 P99 劣化超 10% 拦截
      endpoints: ["route:query", "order:create"]
      max_regression_pct: 10
```

性能基线门禁是三个里最容易被省略、事后又最想不起来加的：没有基线，“这次发布把下单 P99 拖慢了 40%”只能靠用户投诉发现。

**运行时巡检——看活着的系统是否仍然符合约定。** 判据：巡检发现的问题必须回流登记簿（或开豁免），形成“发现 → 记账 → 偿还”闭环，否则巡检沦为月报装饰。

```yaml
# 片段：押金对账差异告警规则（监控告警配置节选，示意）
alert: deposit_recon_mismatch
expr: deposit_recon_diff_count{job="recon-daily"} > 3
for: 0m
labels: { severity: warning, owner: deposit-team }
annotations:
  summary: "押金日终对账差异超 3 单 —— 可能触发 TD-001 触发条件，复核登记簿"
```

注意这条告警的注解直接引用了登记簿编号——巡检与登记簿是同一本账的两面：告警是“债的触发条件正在兑现”的探测器。三类工具再各配一行判据总表：

| 类别 | 一行判据 | 工具示例 |
|---|---|---|
| 静态检查 | 约束可断言就不许只写文档 | ArchUnit、detekt（命名）、import 白名单（分层） |
| CI 门禁 | 门禁失败只有修复或豁免两条路 | 覆盖率卡点、性能基线、适应度函数套件 |
| 运行时巡检 | 巡检发现必须回流登记簿 | 接口契约 diff（OpenAPI 变更比对）、容量水位周报、对账差异告警 |

### 3.3 例外与豁免

任何规则都会遇到例外，治理的水平体现在**例外是不是被显式管理**。豁免单五个字段：**范围**（豁免哪条规则、哪个模块）、**期限**（到期自动失效，规则恢复全效）、**替代补偿**（额外测试、监控、对账——补偿豁免带来的风险敞口）、**到期复审人**、**理由**。

一条铁律：**没有期限的豁免等于废除规则**。“本次先这样”的豁免没有到期日，三个月后它就是既成事实，规则名存实亡。第二条判据：**豁免单数量趋势是架构腐化的先行指标**——某条规则的豁免单月增超过 5 条，说明规则本身可能定错了（该修规则而不是继续发豁免），或团队遇到了规则没覆盖的真实约束（该升级为架构议题）。

❌ 反例（架构师踩刹车而不是修路）：工单中心接入新告警渠道（IoT 设备告警直连），按约定必须走防腐层适配器。架构师坚持每笔直连需求人工审批并逐笔拒绝，理由是“保护内核”。三个月后：团队开了一个影子仓库绕过审批，直连代码照样上线，架构师直到一次 IoT 告警风暴压垮内核才知道影子仓库的存在——**人工刹车挡不住需求，只会把变更赶到视野之外**。
✅ 修正（修路）：第一，发带期限的豁免——允许“临时直连”，豁免单必须带 30 天期限 + 契约测试作为补偿，到期自动恢复拦截；第二，把高频例外变成路的一部分——观察三个月后发现 IoT 渠道直连是稳定需求，于是把它做成官方适配器（六边形架构的端口实现，见 [章节2 六边形/洋葱/整洁](../02-第二阶段/05-其他重要架构风格.md)）入库，从此该场景不再需要豁免。架构师的价值从“批条子”变成“把反复出现的例外沉淀为新规则”，这正是绞杀者模式里“逐步替代旧路径”思想在治理层面的投影（[04 分册 3.3](04-演进式架构-适应度函数与绞杀者.md)）。

一张真实的豁免单长什么样（五字段齐全，可直接抄作模板）：

| 字段 | 内容 |
|---|---|
| 范围 | 豁免工单中心“渠道消息必经防腐层”规则；限 IoT 告警渠道的 `iot-alert-bridge` 模块，其余渠道不适用 |
| 期限 | 2026-11-01 起 30 天，到期自动失效、拦截恢复，不自动续期 |
| 替代补偿 | 该模块独立线程池 + 熔断（IoT 告警风暴不波及内核）；契约测试覆盖直连字段；纳入日终对账 |
| 到期复审人 | 平台架构组（复审结论二选一：转正为官方适配器立项，或恢复拦截并出整改排期） |
| 理由 | IoT 渠道首批设备两周内上线，防腐层适配器排期在下一季度；先通业务，后修路 |

这张单子的关键设计在“复审结论二选一”：豁免到期后不允许“再续 30 天”这种无限拖延，要么把例外转正为新规则（说明原约定有缺口），要么回到拦截（说明例外确属权宜）——两条路都通向“规则恢复效力”，唯独“继续豁免”不通。

## 4. 把三件事串起来：一次真实的架构治理闭环

最后用桶装水商城把评审、登记簿、治理、ADR 串成一个完整故事。主角是本文反复出现的那笔债：**押金计算规则散落三处**。

**第一步：评审发现（第 1 节的机制在干活）。** “配送排线独立服务”的代码级架构走查上，评审者核对依赖方向时顺藤摸到一处异常：`RefundService#refundDeposit` 里内联着一份押金费率计算，与 `OrderService#chargeDeposit` 的实现**瓶损起扣阈值不一致**（一处 3 只起扣、一处 2 只起扣）。追查下去，月底对账任务 `ReconJob` 里还有第三份。评审者当场做了正确的分类：这不是本次评审范围（排线），不扩会；但“一致性”属于跨模块契约问题，不能放任——结论记为**有条件通过**：排线上线不受影响，押金问题当场登记。

> 走查记录片段：
> - 发现：押金费率计算存在 3 份实现，瓶损起扣阈值不一致（3 只 / 2 只 / 3 只）
> - 定性：跨模块一致性缺陷 + 历史欠账，非本次变更引入
> - 处置：转技术债登记簿（TD-001），本次评审结论 = 有条件通过

**第二步：登记（第 2 节的机制在干活）。** 债项 TD-001 进登记簿，就是 2.2 示例里的那条：利息 3 人日/月（每次调费率改三处 + 处理对账差异）、本金 12 人日、风险 0.6 × 40 人日、触发条件“月度对账差异 > 3 单或费率再调整”。登记动作本身带来第一个收益：**三处阈值不一致被确认为已发生的故障**（对账上月的差异单正是它），债从“隐患”变成了“事故待修”，优先级进一步坐实。

**第三步：治理 + 排期（第 3 节的机制在干活）。** 两手并行：

- **先守门，止住新增**：写一条适应度函数进 CI——除 `deposit.domain.DepositPolicy` 外，任何类不得出现押金费率字面量（扫描常量与魔法数）。这道闸挡住的是“还债期间又有人抄出第四份实现”的可能，成本半天；
- **再排期，偿还存量**：登记簿队列里 TD-001 优先级分 5.0、排第三，但触发条件已经兑现（对账差异超 3 单），按登记簿纪律触发即升级——与队首的 TD-002 一并纳入下迭代。偿还采用**分期**：第一期抽 `DepositPolicy` 统一下单侧、第二期退桶侧、第三期对账任务改读统一策略，每期独立验收（对账差异单逐期清零）。

**第四步：ADR 落笔（呼应 [02 分册](02-架构设计与表达-C4视图与ADR.md)）。** 重构完成后，把最终方案固化为决策记录（编号顺接 [02 分册](02-架构设计与表达-C4视图与ADR.md) 的 ADR-008）：

```markdown
# ADR-009：押金费率计算收敛到 DepositPolicy 单一策略对象

- 状态：已接受（2026-03-10）

## 背景
押金计算（含瓶损起扣阈值）散落在下单、退桶、对账三处，各自实现且阈值不一致，
已造成对账差异与错扣客诉（TD-001）。每次费率调整需同步修改三处，月均利息 3 人日。

## 决策
在押金领域层建立 DepositPolicy 策略对象作为费率规则的唯一来源；费率参数版本化存表，
下单侧按订单时点取版本快照；退桶与对账一律读 DepositPolicy。CI 以适应度函数守门：
费率字面量只允许出现在 DepositPolicy 及费率表加载器中。

## 备选方案（为什么不是别的）
规则引擎外置（费率规则仅十余条，引擎运维成本大于收益，否决）；
配置中心下发（费率需按订单时点回溯，实时下发无法满足对账口径，否决）。

## 后果
- 正向：费率调整只改一处；对账与退桶口径天然一致；适应度函数防止回潮
- 负向：费率表迁移需一次性数据订正脚本（已执行并双人复核）；费率版本表增加一次查询
- 复查点：若费率规则复杂化到分支组合 > 20 条，重新评估规则引擎（复查点即债的到期日）
```

**闭环判据。** 一个月后核对三件事：登记簿 TD-001 状态改为**已偿还**，其利息从面板消失（月利息占比 47.5% → 32.5%）；走查记录里那条发现升级为 1.3 评审清单的新条目——“金额类规则是否单一来源”（第 3 道闸：同一个坑不进第二次）；押金对账告警连续 30 天零触发（运行时巡检确认债真的还清了，而不是只改了代码）。评审发现、登记定价、守门偿还、决策留痕——四步各自是机制，合起来是**一笔债从欠下到消失的完整生命周期**，也把第四阶段四个分册的方法论咬合成了一个整体（参看 [04 分册末尾“三节如何互相咬合”](04-演进式架构-适应度函数与绞杀者.md)）。

闭环本身也要接受度量，两个指标按季度回看：**处置周期**（从发现到登记的天数、从登记到开始偿还的天数——押金这笔债从走查发现到进下迭代排期是一周，超过一个月说明登记簿没有接住评审的输出）；**复发率**（同一位置六个月内再次出现同类债的次数——押金还清半年后又有人抄出第四份实现，说明适应度函数的断言写漏了或者根本没跑）。复发是最诚实的失败信号：它直接证伪“已偿还”的结论，必须回头检查守门的那道闸是形同虚设还是规则本身写窄了。

            repayStrategy = RepayStrategy.DEFAULT_WRITE_OFF, // 最便宜的偿还是删除
            trigger = "",
        ),
    )

    fun f(d: Double) = String.format("%.1f", d)

    println("== 技术债登记簿（共 ${ledger.size} 条）==")
    println("优先级分 = 年化持有成本 / 本金 =（月利息 × 12 + 年故障概率 × 爆炸半径）/ 重构人日")
    println("含义：每投入 1 人日还这笔债，一年能省回多少人日 —— 回本最快的先还。")
    println()

    val repayQueue = ledger
        .filter { it.repayStrategy != RepayStrategy.DEFAULT_WRITE_OFF }
        .sortedByDescending { it.priorityScore }

    println("── 偿还队列（按优先级分降序）──")
    repayQueue.forEachIndexed { i, d ->
        println("${i + 1}. [${d.id}] ${d.title}")
        println("   位置：${d.location}")
        println("   类型：${d.nature.label}    策略：${d.repayStrategy.label}")
        println(
            "   利息 ${f(d.interestPerMonth)} 人日/月   本金 ${f(d.principalCost)} 人日   " +
                "风险 ${f(d.failureProbPerYear)} × ${f(d.blastRadiusDays)} = ${f(d.annualRiskCost)} 人日/年"
        )
        println(
            "   年化持有成本 ${f(d.annualCarryingCost)} 人日   优先级分 ${f(d.priorityScore)}   " +
                "回本期 ${f(d.paybackYears)} 年"
        )
        println("   触发条件：${d.trigger.ifBlank { "（缺失——登记质量问题）" }}")
        println()
    }

    val defaulted = ledger.filter { it.repayStrategy == RepayStrategy.DEFAULT_WRITE_OFF }
    if (defaulted.isNotEmpty()) {
        println("── 核销队列（不再偿还，直接删除）──")
        defaulted.forEach { println("[${it.id}] ${it.title} → 删除 ${it.location}") }
        println()
    }

    val monthlyInterest = repayQueue.sumOf { it.interestPerMonth }
    val monthlyCapacity = 20.0   // 团队月产能（人日）
    val ratio = monthlyInterest / monthlyCapacity
    println("── 偿还能力面板 ──")
    println("登记簿月利息合计：${f(monthlyInterest)} 人日/月，占团队产能 ${f(ratio * 100)}%")
    println("判据：月利息 > 产能 15% 时，除日常 20% 预算外必须立债务偿还专项。")
    val top = repayQueue.firstOrNull()?.id ?: "无"
    println(
        if (ratio > 0.15) "当前结论：超过阈值 → 立专项，队首 [$top] 纳入下迭代。"
        else "当前结论：未超阈值 → 日常 20% 预算滚动偿还即可。"
    )
}

## 全节小结

三件事各有一句本质、一个最小启动动作：

| 机制 | 本质 | 最小启动动作（本周就能做） |
|---|---|---|
| 架构评审 | 把个人判断变成组织记忆 | 给下次评审补一份“检查项 + 通过判据 + 处置”清单 |
| 技术债管理 | 把妥协变成可算账、可排期的负债 | 建一张最简登记簿，先登记手上最痛的那笔债并写触发条件 |
| 架构治理 | 把约定变成自动执行、例外显式的规则 | 把最常被违反的一条约定改成 CI 断言 |

三者层层递进：评审在**事件发生时**守住质量并发现债，登记簿让债**在事件之间**持续可见、可定价、可排期，治理让约定**在没有人在场的每个提交里**自动生效。它们共同的底层能力，正是本阶段前三个分册训练的东西：把判断写成 ADR（02 分册）、把边界划清并守住（03 分册）、把约束变成可执行的适应度函数（04 分册）。架构师的价值不在于每次都亲自到场，而在于**人不在场时，规则仍在执行**。
