## 1. DDD：领域驱动设计（Eric Evans，2003）

### 起源

**谁与何时**：Eric Evans，2003 年。**在哪**：Addison-Wesley 出版的《Domain-Driven Design: Tackling Complexity in the Heart of Software》（中译《领域驱动设计：软件核心复杂性应对之道》）。封面深蓝，社区通称**蓝皮书**。Evans 不是书斋学者：他是领域咨询公司 Domain Language 创始人，这套方法从 1980 年代末到 1990 年代一连串 Smalltalk、C++ 企业项目的实战中沉淀而来——蓝皮书是十年咨询经验的结集，不是先有理论再找案例。

**时代背景**：三点叠加决定了这本书为什么出现在 2003 年。①**工具吃掉了全部注意力**：那是 J2EE / EJB 重型容器当道的年代，团队把精力耗在中间件、部署描述符和框架配置上，而软件真正的复杂度——业务领域本身——反而无人照看。②**敏捷正在抬头**：Kent Beck 的《解析极限编程》（1999）与敏捷宣言（2001）之后，迭代节奏需要一种“模型可以持续深化而不是一次冻结”的设计方法，DDD 的知识消化（knowledge crunching）与迭代天然契合。③**模式词汇刚刚备齐**：Fowler 的《企业应用架构模式》（2002）刚把战术层模式词汇整理完，蓝皮书补上了“统一语言与边界”这半张图。

**出版十年后才大热——方法论传播史上的著名慢热案例**。蓝皮书出版后数年销量平平，Evans 一度以为它会被遗忘。转机在 2008 年前后：InfoQ（2006 年创立）的演讲与文章、DDD 邮件列表与 QCon 会议接力，社区先“重新发现”了它；2014~2015 年微服务兴起，“限界上下文 ≈ 服务边界”的等式让**战略设计**重新走红——距出版已过十年。慢热的成因：蓝皮书出版在博客时代前夜，靠的是纸书与口碑的慢传播；它等来了属于自己的时代（微服务把“边界”变成头号问题），而不是自己制造了时代。

**两个续作补齐落地链**：Vaughn Vernon 的《Implementing Domain-Driven Design》（2013，封面红色，**红皮书**，Evans 作序）把蓝皮书的思想翻译成可执行的代码纪律（聚合的实现守则、限界上下文的代码结构、与六边形架构的对接）；Alberto Brandolini 约 2013 年提出**事件风暴**（EventStorming）——这套方法在他的博客与工作坊中成形，他自述受 2010 年《Gamestorming》（Dave Gray 等）与事件驱动思维启发，用领域事件便利贴做快速、跨职能的知识消化，把传统需求分析的几个月压缩到几天；2016 年以 Leanpub 电子书《EventStorming: What's beyond?》系统化。红皮书回答“代码怎么写”，事件风暴回答“知识从哪来”，蓝皮书的骨架至此完整。

### 核心要点

- **复杂度在领域，不在技术**：框架与中间件的问题是“有界的、有人解决的”，业务复杂度才是“无边界的、只能由你自己承担的”——所以设计精力的主战场应该移到领域。
- **战略设计先于战术设计**：统一语言（Ubiquitous Language）、限界上下文（Bounded Context）、上下文映射（Context Map）——先划对边界，再谈类怎么写；边界划错，战术层写得再漂亮也是精装修危房。
- **模型即语言**：模型不是 UML 图册，而是开发团队与领域专家共同使用、随对话演进的工作语言；“同一个词在两个上下文里意思不同”是发现边界的信号。
- **聚合是一致性边界**：一个事务只改一个聚合，跨聚合走领域事件的最终一致——这条纪律同时是并发的护城河与微服务拆分的接缝。
- **通用性有边界**：DDD 的投入产出在领域复杂度三档里只在“复杂档”为正，对简单 CRUD 域套用 DDD 是负收益（判据见正文 03 分册 2.1）。

### 使用场景

**最对的场景**：领域规则复杂、术语繁多且持续变化的业务系统——本工作区主线桶装水商城（商品 / 订单 / 周期购订阅 / 配送 / 押金，“桶”一词跨上下文含义漂移）与工单中心（创建 / 分派 / 流转 / SLA / 关单的状态机域）都是标准画像；事件风暴则适合**跨职能专家都在场、需要在一两天内对齐业务全貌**的启动阶段。

**典型误用**：①把 DDD 当作“高级分包规范”——只学战术设计，处处套用实体 / 聚合 / 仓储，边界照旧一团糟（“用 DDD 的词汇写贫血分层”）；②把事件风暴当作画图仪式——贴满便利贴却没有产出统一语言与边界结论；Brandolini 反复强调 **It's not about the sticky notes**：产出物是共识不是墙面；③在低代码 / 配置化平台上强行套用 DDD——DDD 的通用性有边界，把业务规则强行塞入元数据引擎的反例详见正文 03 分册 2.8。

### 示例

- 正文分册：[领域驱动设计-DDD](03-领域驱动设计-DDD.md)——2.1 投入产出判据、2.2 统一语言与限界上下文、2.3 上下文映射、2.5 聚合一致性边界（含“支付成功激活押金单”完整 Kotlin 守卫示例）、2.6 贫血 vs 充血、2.8 低代码反例、2.9 五步落地路线图。
- 红皮书与六边形的接线：本档案第 8 节 + [02-第二阶段/05-其他重要架构风格](../02-第二阶段/05-其他重要架构风格.md) 4.2（洋葱架构正是把六边形 DDD 化的那一步）；工作区 ADR 对战略模式的真实消费见 [ADR-008](02a-示例-adr/008-subscription-delayed-message.md)（“开放主机服务 / 客户-供应商协议”即上下文映射模式）。

## 2. 4+1 视图模型（Philippe Kruchten，1995）

### 起源

**谁与何时**：Philippe Kruchten，1995 年。**在哪**：IEEE Software 杂志论文《The 4+1 View Model of Architecture》（第 12 卷第 6 期，1995 年 11 月）——这是本档案八件“原始出处”里唯一的学术期刊论文。Kruchten 当时的身份是 Rational 公司 RUP（Rational Unified Process）的负责人；此前在 Alcatel 做过大型电信与实时系统架构，长期一线画图、交图、被图背叛。

**时代背景**：论文要解决的是一个反复上演的失败——**“一张架构图讨好所有人”**。他观察到架构师常用一张图应付所有受众：给最终用户看，用户关心的是“我的业务功能在哪”，图里却是进程与队列；给开发经理看，经理关心模块划分与人力分工，图里却是部署节点；给运维看，运维关心物理拓扑，图里却是类。论文的处方：与其追求“最终架构图”，不如承认**架构 = 一组视图**，每个视图服务一类关注点，再用第五个视图把它们钉在一起。

**“4+1”的具体构成**：逻辑视图（Logical，功能如何分解，服务最终用户）、进程视图（Process，并发 / 通信 / 性能 / 可用性，服务系统集成视角）、开发视图（Development，模块 / 目录 / 依赖，服务程序员与配置管理）、物理视图（Physical，进程到处理器的映射，服务运维）。**“+1”是场景视图（Scenarios，用例实例）**——它不是第五个并列的视图，而是穿过其余四视图的针脚：用关键用例在四个视图上各走一遍，检验架构能否讲通一个真实的执行故事。这个“用场景串视图”的思路后来无处不在：微服务时代的调用链追踪、事件风暴里的“热点事件走读”、C4 的动态图都是它的后代。

**后续演化**：4+1 被吸收进 RUP，成为“以架构为中心”过程的标准表达；Kruchten 后来多次提醒：**视图是给不同受众的，不是架构本身**，不要把“画满五张图”当作绩效。微服务与云时代四视图热度不均：开发视图让位给仓库 / 服务拓扑，物理视图变成部署拓扑主角，场景视图仍是集成验证的第一工具。

### 核心要点

- **架构没有“唯一正确的图”**：不同的受众与关注点对应不同的视图，一张图容纳所有关注点，等于对所有人失焦。
- **四视图各管一类问题**：功能（逻辑）/ 运行时并发与性能（进程）/ 代码组织（开发）/ 部署映射（物理）——四个问题各有自己的受众。
- **“+1”是粘合剂**：场景不是第五张并列的图，而是检验四视图是否自洽的针脚。
- **视图是表达不是架构**：删掉五张图，架构还在；视图的价值在于“让某一类读者回答某一类问题”。

### 使用场景

**最对的场景**：多受众的架构沟通——评审会上有业务、开发、运维同席时，用它做**覆盖性检查**：“这个问题该由哪个视图回答？那个视图画了吗？”它是一张检查清单（哪类问题无人能答），而不是一套必画的五张图。

**典型误用**：①把 4+1 当作“画五张图的任务清单”来追进度——图虽画齐，却没有一张对准真实受众的问题；②在十人小项目上强行画满五张图——视图数量应随受众数量而定；③把 4+1 当作画图语法来用——它只回答“要哪几类视图”，不回答“图里画什么符号”，符号层另有工具（UML、C4）。

### 示例

- 正文分册：[架构设计与表达-C4视图与ADR](02-架构设计与表达-C4视图与ADR.md) 1.2——4+1 定义、与现代工件（服务拓扑 / 部署图 / 调用链）的映射、与 C4 的分工对照；1.1 末尾的“验收三个动作”本质上是“每类受众一个视图”的 Kruchten 式落地。

## 3. ADR：架构决策记录（Michael Nygard，2007）

### 起源

**谁与何时**：Michael T. Nygard，2007 年 11 月 15 日。**在哪**：一篇博文《Documenting Architecture Decisions》，发表在他的个人博客上，后由 Cognitect 博客转载——今天的常见引用即这份转载。一篇博客文章成为一类文档的起源，这本身是“博客时代方法论生产方式”的标本（对比 DDD 慢热的十年，见第 10 节）。Nygard 不是文档专家而是生产事故专家：同年出版的《Release It!》（Pragmatic Bookshelf，2007）教企业软件如何在生产环境中存活——他深知“决策的理由没有留下”在事故复盘时代价有多大。

**时代背景**：2007 年正值敏捷主流化，架构决策从“前期一次大设计（BDUF）”变成“迭代中连续的小决策”，但文档实践未能跟上：架构文档还是陈年 PPT 与方框箭头图——**只有“是什么”，没有“为什么”**；于是同一个团队隔几个月就要把同样的争论重演一遍（当时的结论没有留下来），新人只能靠梳理代码反推设计意图。Nygard 的处方朴素到极致：每个决策写一页短文，固定五段——**标题（Title）、状态（Status）、背景（Context）、决策（Decision）、后果（Consequences）**。放进代码仓库、随代码版本化、编号连续。他特别强调 Consequences 要诚实写**负向后果**。

**为什么是这五段**：Context 记录“当时的约束条件”（这是决策的保鲜膜，一年后约束变了，就知道该复查决策）；Decision 只写结论一句话；Consequences 让反对者在决策时就把代价摆上桌面。Status 字段则给了决策**生命周期**：proposed → accepted → superseded（被取代）——被取代的 ADR 不删，保留“决策变迁史”。

**后续演化**：社区把它工程化：Nat Pryce 的 adr-tools 等命令行工具让创建 ADR 只需一条命令；2017 年前后，德国斯图加特大学软件工程研究组在 GitHub 发起 **MADR**（Markdown Any Decision Records，adr/madr 仓库），把五段式扩展成结构化 Markdown 模板（增加 Deciders、Date、决策驱动因素、被考虑的备选方案与利弊表）；中文社区常见的“背景 / 决策 / 备选方案 / 后果”四段式则是五段式的本地化变体。

### 核心要点

- **架构的沉淀物不是图，而是决策及其理由**：图会过期，“为什么当时这么做”才是长期资产（这正是正文 02 分册的定义句）。
- **一页、一段、一决策**：ADR 之所以能成为日常习惯，靠的是足够小——半小时能写完、一页纸能装下。
- **Context 是保鲜膜，Status 是生命周期**：约束条件记录得越清楚，一年后越能判断“决策是否仍然成立”；被取代不等于错误。
- **Consequences 必须写负向**：只写好处的 ADR 是宣传稿，不是决策记录；ADR 贴着代码仓库存放，随代码评审与版本化。

### 使用场景

**最对的场景**：**做了就难回头、且理由容易遗忘的决策**——选型、边界（拆不拆服务）、模式（同步还是事件驱动）、取舍（一致性换延迟）。判据一句话：**一年后有人问“当时为什么这么定”，而你需要三句话以上才能讲清的，都值得一条 ADR**。

**典型误用**：①写成会议纪要——ADR 记一个决策，不记一场讨论的发言顺序；②没有 Consequences 或 Consequences 只写好处——反对者指出的代价没有被记录，复查时无从对照；③被取代后直接删除旧 ADR——丢掉了“前提变了所以决策跟着变”的变迁史；④只有“接受”没有“否决”——被否决的备选方案（以及否决理由）同样是资产，否则半年后有人会真诚地重提你否决过的方案。

### 示例（真实样本：工作区 ADR 目录）

本工作区 `02a-示例-adr/` 目录的三条真实 ADR 恰好覆盖生命周期三阶段（模板与反模式展开见 02 分册 1.3）：

- [02a-示例-adr/003-old-adr.md](02a-示例-adr/003-old-adr.md)：**状态字段的教科书演示**——“状态：被 ADR-007 取代（2026-10-20）”；其收尾句“被取代不等于错误：当时的前提变了，决策就该跟着变”即 Nygard 设计 Status 的用意。
- [02a-示例-adr/007-delivery-routing-as-service.md](02a-示例-adr/007-delivery-routing-as-service.md)：**完整决策的样本**——五段之外增加了“备选方案（为什么不是别的）”与“复查点”（给出重新评估的触发条件：QPS 下降一个量级、团队缩减至两三人时考虑合并回单体）——复查点是对 Nygard 模板最有价值的社区扩展。
- [02a-示例-adr/008-subscription-delayed-message.md](02a-示例-adr/008-subscription-delayed-message.md)：**捕捉推理而非结论的样本**——周期购下期订单生成选“调度扫表”而非“MQ 延迟消息”，它把否决理由写得十分清楚（长延迟可靠性、退订无法撤回、“复杂度并未消失，只是挪了位置”），半年后若有人提议“换成延迟消息”，这条 ADR 便能直接回应。
- 模板、生命周期与反模式展开：[02 分册 1.3](02-架构设计与表达-C4视图与ADR.md)；治理闭环里 ADR 如何被复查：[05 分册](05-架构评审与技术债管理.md) 第 4 节。

## 4. 技术债（Ward Cunningham，1992）

### 起源

**谁与何时**：Ward Cunningham，1992 年。**在哪**：OOPSLA'92 大会（温哥华）的经验报告《The WyCash Portfolio Management System》，次年刊于 ACM SIGPLAN OOPS Messenger 第 4 卷第 2 期——形式上是一份“经验报告”（experience report），讲的是一个资产管理系统的 Smalltalk 实践，技术债的复利比喻只是其中的论证片段，却成了整份报告流传最广的遗产。Cunningham 是软件行业的传奇人物：CRC 卡片（与 Kent Beck 合作）、Fit 测试框架，以及 1995 年发明的 **Wiki**（c2.com 的 WikiWikiWeb，“波特兰模式仓库”）——第一个用户可编辑的网站。他惯于发明“用浅白语言讲清工程问题”的工具，技术债比喻和 Wiki 出自同一种品味。

**时代背景**：1992 年，面向对象刚刚进入企业，“先快速交付再重构”的敏捷思想还在胎动（敏捷宣言要到 2001 年）。Cunningham 面对的听众是**非技术的管理层**：他们听到“代码需要重构”就理解为“你们没写好”，于是拒绝给重构排期。他需要一个管理层能立刻理解的框架，于是借来了金融概念：**借债**。借钱能让你今天买得起本来买不起的东西（快速交付）；利息是未来的每次变更都要多付的成本（债没还清前，改动一直更贵）；**还本**就是重构；**只付利息不还本**，利息滚入本金（复利）；**破产**就是系统彻底无法修改。在这个框架下，“为了赶上期限先欠一笔债”是理性的经营决策，“一直不还”无异于自毁——管理层懂金融，于是第一次理解了重构。

**他本人后来的澄清（比喻的边界）**：2009 年 Agile 大会的一段著名短视频（“Ward Explains Debt Metaphor”）里，Cunningham 专门出面纠偏——太多人把比喻用偏了：**技术债专指“知道自己在借、评估过怎么还”的主动权衡**——“我借这笔钱时，我想过怎么还”；而没做过任何评估、不打算还、纯粹写出来的烂代码，**不配称为技术债**——那不是融资，是乱花钱。这就是“**债 ≠ 烂代码**”的原始出处：债有四个要件（有意、有记录、有利率意识、有偿还计划），烂代码一个都不占。把烂代码一概称作技术债，等于取消比喻的区分度。

**后续演化**：Martin Fowler 2009 年在 bliki 上写了《TechnicalDebt》与“技术债四象限”（**是否故意 × 是否谨慎**）：故意且谨慎（真债）、故意但鲁莽（“没时间做设计”）、无意但谨慎、无意且鲁莽——Cunningham 的原教旨定义对应第一格；管理含义：真债进登记簿排期偿还，伪债是能力 / 流程问题，登记簿解决不了它（四象限完整展开与 Kotlin 示例见 05 分册 2.1）。

### 核心要点

- **债是主动权衡，不是质量差**：四个要件——有意选择、记录在案、对利率（额外变更成本）有意识、有偿还计划。
- **复利是危险的来源**：利息滚入本金，未偿债务越多，每迭代被利息吃掉的开发量越大——见下方 DebtInterest.kt 的量化演示。
- **比喻的对象是管理层**：它的发明是为了让非技术决策者理解重构的经济学，而不是供工程师互相贴标签的工具。
- **破产是真实终点**：复利曲线的尽头是“每个小改动都贵到无人敢做”——技术破产不写在财务报表上，写在团队离职率上。

### 使用场景

**最对的场景**：迭代节奏下的**容量预算讨论**——把“偿还技术债的迭代占比”当成理财问题与产品侧谈判（每迭代固定 20%？还是按利率排序偿还？），而不是当成工程侧的道德控诉。真实画像：桶装水商城“排线与下单耦合”债（ADR-003 时代），利率极高（每次算法迭代都连带回归下单链路），最终由 [ADR-007](02a-示例-adr/007-delivery-routing-as-service.md) 一次性清偿——**拆服务本身就是一次大额还债**。

**典型误用**：①“债 = 烂代码”的混同——见上文 Cunningham 的四要件，误读的后果是登记簿里塞满无法定价、只凭主观感受登记的条目；②只记新债不还旧债——登记簿变成忏悔录；③把低利率的债当危机——有些债利率极低（即将下线的模块里的一段复制粘贴），提前偿还反而是浪费；④绕开债务表欠债——没有 ADR / 登记簿记录的“临时方案”，是利率最不可控的暗债。

### 示例（含可运行 Kotlin 复利模拟）

正文分册：[架构评审与技术债管理](05-架构评审与技术债管理.md) 2.1“准确的类比与常见的误用”（含 Cunningham 原始场景与 Fowler 四象限）、2.2 技术债登记簿（字段设计与 Kotlin 示例）、2.3 偿还策略四选一、2.4 预防新债的四道闸。本节补充一个正文没有的视角：**把复利模拟出来**。下面的 `DebtInterest.kt` 模拟两条曲线——存量债 20、每迭代新增债 10、利率 8%/迭代（债对后续变更的拖累系数）：

```kotlin
/**
 * DebtInterest.kt —— 技术债复利模拟
 * 对应 Cunningham 1992 的金融比喻：每迭代都会新增债务，
 * 未偿余额还要按"利率"滚利息；对比"从不还债"与"每迭代偿还 20%"两条曲线。
 */
fun main() {
    val iterations = 24        // 模拟迭代数（约一年的双周迭代）
    val initialDebt = 20.0     // 存量技术债（历史欠账）
    val newDebtPerIter = 10.0  // 每迭代新增债务（赶工欠下的）
    val interestRate = 0.08    // 每迭代"利率"：债对后续变更的拖累系数
    val repayRatio = 0.20      // 策略二：每迭代偿还余额的 20%

    class Ledger {
        var balance = initialDebt
        var interestAccrued = 0.0   // 累计利息（被债额外吃掉的开发量）
        var repaid = 0.0            // 累计已偿还
        fun step(repayRatio: Double?) {
            val interest = balance * interestRate
            interestAccrued += interest
            balance += interest + newDebtPerIter   // 计息 -> 滚入本金 -> 再欠新债
            if (repayRatio != null) {
                val pay = balance * repayRatio
                balance -= pay
                repaid += pay
            }
        }
    }

    // 中日韩字符按 2 列宽补齐，让中英文混排表格对齐
    fun pad(s: String, width: Int): String {
        val w = s.sumOf { if (it.code > 0x2E80) 2 else 1 }
        return s + " ".repeat(maxOf(0, width - w))
    }

    val never = Ledger()    // 策略一：从不还债
    val repay20 = Ledger()  // 策略二：每迭代偿还 20%

    println("技术债复利模拟：存量债=$initialDebt 每迭代新增=$newDebtPerIter " +
        "利率=${"%.0f".format(interestRate * 100)}%/迭代 共 $iterations 个迭代")
    println()
    println(pad("迭代", 5) + pad("从不还债余额", 13) + pad("累计利息", 11) +
        pad("偿还20%余额", 13) + pad("累计已还", 10) + "  债务规模(每█≈25)")
    repeat(iterations + 1) { i ->
        if (i > 0) { never.step(null); repay20.step(repayRatio) }
        val bar = "█".repeat(minOf(34, (never.balance / 25).toInt()))
        println(pad("$i", 5) + pad("%.1f".format(never.balance), 13) +
            pad("%.1f".format(never.interestAccrued), 11) +
            pad("%.1f".format(repay20.balance), 13) +
            pad("%.1f".format(repay20.repaid), 10) + "  " + bar)
    }
    println()
    // 稳态推导：b* = (1-r)·(1+i)·b* + (1-r)·新债  =>  b* = (1-r)·新债 / (1-(1-r)(1+i))
    val steady = (1 - repayRatio) * newDebtPerIter / (1 - (1 - repayRatio) * (1 + interestRate))
    println("结论：从不还债 -> 余额 %.1f，累计利息 %.1f：指数增长，无稳态".format(never.balance, never.interestAccrued))
    println("      每迭代还 20%% -> 余额 %.1f，累计利息 %.1f，累计已还 %.1f：收敛到稳态 %.1f（债被驯服，但不清零）"
        .format(repay20.balance, repay20.interestAccrued, repay20.repaid, steady))
}
```

编译运行（无第三方依赖；kotlinc 2.2.20）：

```bash

# （把上面源码存为 DebtInterest.kt）
kotlinc DebtInterest.kt -include-runtime -d app.jar && java -jar app.jar
```

## 5. C4 模型（Simon Brown，2014~2018）

### 起源

**谁与何时**：Simon Brown。**在哪**：这个概念的“原始出处”不是一篇论文，而是一段培训实践 + 一个名字。可考的脉络是：C4 的四层抽象（Context / Container / Component / Code）诞生于 Brown **2006~2011 年**做全球架构培训时的材料——他在课上反复发现同一件事：学员被要求画架构图，交上来的常常是“两个箱子和一条没有定义的箭头”；他于是把“画图前先问这张图给谁看、回答哪层问题”整理成四层抽象。**2014 年前后**，他开始以“C4”之名在会议上演讲（Context、Containers、Components、Code 四个 C）；2016 年，Leanpub 电子书《Software Architecture for Developers, Volume 2》把方法系统成文；2018 年 **c4model.com 官网上线** +《Visualising Software Architecture with the C4 Model》出版，“定名”完成——思想酝酿于 2006~2011 的培训教室，名字与传播定型于 2014~2018。

**时代背景**：Brown 的动机是反抗**两个极端**。一端是 **UML 太重**：他常年在培训现场提问“谁能画出标准的 UML 2.x 图？”，几乎无人举手——一个无人会用的记法，无论多“标准”，实际表达力都是零。另一端是**白板太轻**：非正式的方框箭头图没有任何定义——箭头是调用还是依赖还是数据流？箱子是服务还是模块还是数据库？读者只能自行猜测。中间缺一个“记法极简但每个元素有定义”的层。C4 的答案分为两半：**抽象层**（人 / 软件系统 / 容器 / 组件 + 代码，四级缩放，像地图一样从国界缩放到街区）与**“一图一答”纪律**（每张图回答一个明确的问题，配图例，标题写明问题本身）。Brown 还写了 Structurizr（2014~2015，“diagrams as code”，代码定义模型再生成图）证明它可以工具化，回击“图一定会过期”的宿命论。

**后续演化**：C4 与 4+1、arc42 的关系被问得最多——按 Brown 本人的说法：C4 是**抽象层次**（abstractions）不是记法（notation），可以用 UML 符号画 C4 的容器图；C4 的 L1/L2 大体对应 4+1 的“给业务方的视图”，但没有进程 / 物理视图的强划分，部署图按需另画。如今 C4 已是事实上的架构图入门标准，“先问给谁看、回答什么问题”取代了“用 UML 还是白板”成为第一问。

### 核心要点

- **像地图一样分级缩放**：L1 上下文、L2 容器、L3 组件、L4 代码——每张图只回答一个层级的问题，避免“一张巨图塞进所有细节”。
- **Container 不是 Docker 容器**：指“一个独立运行单元”（应用、SPA、数据库、消息中间件各算一个）——这是第一大误读点。
- **一图一答 + 图例**：标题写清楚这张图回答什么问题；箭头与箱子的含义必须能从图例读到，否则读者只能猜谜。
- **C4 是抽象层不是记法**：用任何符号绘制都可以，只要箱子的“层级”一致；**价值在 1~3 层**，L4 交给 IDE。

### 使用场景

**最对的场景**：需要**快速对齐结构认知**的场合——新人入职（用 L2 在五分钟内找到“押金退费在哪个模块”）、跨团队评审（L1 界定系统边界）、给业务方讲“我们和支付渠道是什么关系”（L1）。本工作区 02 分册用桶装水商城的 L1（用户 / 配送员 / 商城 / 支付 / 短信 / 地图）做过完整演示。

**典型误用**：①一张图混四个层级（类名、Pod 副本数、外部系统与模块框挤在同一张图里）——读者被迫同时回答四个层级的问题，这正是 C4 要消灭的“巨图病”；②只有图例没有受众——画图前答不出“给谁看、回答什么问题”的图，画得再标准也是装饰。

## 6. 架构适应度函数（Ford / Parsons / Kua，2017）

### 起源

**谁与何时**：Neal Ford、Rebecca Parsons、Patrick Kua——三位 ThoughtWorks 成员（Ford 是资深架构师 / 演讲者，Parsons 是公司 CTO，Kua 是顾问、后任澳大利亚 Tyro 支付 CTO）。**在哪**：O'Reilly 书《Building Evolutionary Architectures: Support Constant Change》，**第一版 2017 年**；**第二版 2022 年**，Patrick Kua 退出，由 Pramod Sadalage（ThoughtWorks 顾问、《NoSQL Distilled》合著者）接替。因此引用这本书需要注明版本：第一版的“作者四人组”到第二版换了一个人——这种人事细节在二手资料中常被误传。

**时代背景**：书要回答的问题是“**架构怎么支持持续的变化**”。2017 年的工程语境：微服务把“变更”变成高频日常，CI/CD 管道成了标配——每个提交都会自动执行一套客观检验。作者们借来一个旧词：**fitness function 来自演化计算 / 遗传算法**——适应度函数给每个候选解打分、决定谁进入下一代；算法不需要理解“为什么”，只需要反复执行打分与选择。映射到架构：**架构目标不该靠评审会的记忆与自觉来守护，而该变成“客观的、可自动执行的检验”**——单元测试、ArchUnit 的分层规则、性能基准、安全扫描、甚至“每个服务必须有 README”的脚本检查，都是适应度函数。书里的定义句：适应度函数是**“检验架构离目标有多近的任何客观机制”**。没有 CI/CD 时代的“每次变更自动执行检验”这个底座，这套方法论便无处安放——它是管道时代的产物，就像 ADR 是博客时代的产物。

**后续演化**：第一版给出的分类（原子 vs 整体、触发式 vs 持续式、静态 vs 动态）在社区迅速与 ArchUnit、NetArchTest 等工具合流；第二版（2022）扩充机制清单与案例，更明确地把适应度函数与“增量变更”三前提（可度量、可自动化验证、可回滚）绑定。

### 核心要点

- **定义**：检验架构离目标有多近的任何客观机制——从单元测试到性能基准到架构规则扫描。
- **名字来自遗传算法**：打分不由人临时判断，而是预先定义、反复自动执行。
- **多个函数构成组合**：真实架构有多个相互竞争的目标（性能 vs 可测试性 vs 安全），适应度函数清单表达的是“追求什么、以什么为界”。
- **依赖三个前提**：可度量（目标能写成断言）、可自动化验证（有管道执行）、可回滚（函数检查不通过时能回退）——三个前提缺一，“演进式”就退化为“失控式”。

### 使用场景

**最对的场景**：**边界与质量的日常守门**——把“领域层不许依赖框架注解”写成 CI 门禁（本工作区 04 分册已给出相应的最小 Kotlin 示例）、把“下单 P99 < 300ms”做成性能基准、把“每个服务暴露的接口数”做成监控告警。凡是“评审会上反复口头强调”的架构约定，都应追问一句：能否变成一条适应度函数？

**典型误用**：①只写代码维度——性能、安全、可观测都不是静态分析能覆盖的，清单失衡会让“全绿”给出虚假安全感；②函数集合从不演化——业务目标变了（从快变稳），函数清单仍停在旧目标上，守门员守着废弃的球门；③把适应度函数当作 KPI 考核个人——它会立刻从“引导演化的打分器”异化为“被优化的指标”，Goodhart 定律在架构领域同样生效。

### 示例

- 正文分册：[演进式架构-适应度函数与绞杀者](04-演进式架构-适应度函数与绞杀者.md)——3.1 演进式 vs 计划式、3.2 适应度函数分类 + **最小可运行示例（“领域层纯净性”变成一条 CI 门禁）** + 反模式、3.3 绞杀者模式与迁移顺序。
- 与第六阶段“秒杀 / 限时抢购”场景的接线：限流 / 熔断指标可反向写成性能类适应度函数——运行时自我保护，演进时守门，同一指标的两种身份。

## 7. Team Topologies（Skelton & Pais，2019）

### 起源

**谁与何时**：Matthew Skelton 与 Manuel Pais，2019 年。**在哪**：IT Revolution 出版社的同名书《Team Topologies: Organizing Business and Technology Teams for Fast Flow》（2019 年 9 月）——出版商即 Gene Kim 的 IT Revolution（《凤凰项目》的出版方），它是 DevOps“流”思想的组织学收官之作。两位作者的背景值得了解：Skelton 是英国 Conflux 咨询公司创始人，更早以 **DevOps Topologies**（devopstopologies.com，收录几十种团队交互的组织模式与反模式）闻名——Team Topologies 的“团队类型 × 交互模式”正是把这些观察提炼成正式模型；Pais 是常驻里斯本的独立 DevOps 顾问、DevOps Lisbon 聚会的联合组织者。**Skelton 的另一身份（DevOps Topologies 作者）解释了本书为何遍布组织拓扑图。**

**时代背景**：三股潮流的汇合。①**康威定律复兴**：微服务时代“组织结构长进代码结构”已是普遍的切身体会，“逆康威”（按目标架构调整组织）开始被讨论，但缺少一套“编排组织”的操作词汇；②**DevOps 度量成熟**：《Accelerate》（Forsgren 等，2018）用调研数据证明了组织设计与交付绩效的相关性；③**认知科学入场**：核心概念“团队认知负荷”（team cognitive load）借自认知心理学（Sweller 的认知负荷理论）——一个团队能同时照料的领域复杂度有硬上限。Team Topologies 给出的答案是一套排版规则：**四类团队**（业务流 stream-aligned、平台 platform、赋能 enabling、复杂子系统 complicated-subsystem）× **三种交互模式**（协作 collaboration、X-as-a-Service 服务化、促进 facilitating）。本档案按分工**不重写**这套内容（它属于康威定律的展开，见下方链接），只补一句定位：**康威定律（1967）是物理定律，逆康威是工程策略，Team Topologies 就是施工手册**。

**后续演化**：出版后迅速成为组织设计通用语言（“我们是 platform 团队，对你们是 as-a-service”开始出现在日常对话）；官网与社区 meetup 持续扩展案例库；“Team API”（团队对外暴露的文档、代码、协作方式的接口面）被微服务治理大量借用。

### 核心要点

- **团队是架构的一等公民**：组织设计就是架构设计的一部分，“先定架构再配人”与“先定团队再生长架构”是同一个决定的两面。
- **四类团队 × 三种交互**：类型管“这个团队为什么存在”，交互管“团队之间怎么打交道”——协作、服务化、促进三种模式各有成本结构。
- **认知负荷是划界判据**：一个团队照料的域太宽，边界再清晰也会崩塌——这是“拆不拆服务”之外“拆不拆团队”的量化视角。
- **交互模式随成熟度演化**：协作（贵、快、适合探路）→ 服务化（便宜、可扩展、适合成熟能力）——不是静态标签。

### 使用场景

**最对的场景**：**组织与架构长期相互掣肘**的组织——按功能分层组队（前端组 / 后端组 / DBA 组）却要做业务流演进（每个需求横切五个团队）、或微服务数量暴增但平台团队缺位（每个服务团队都在重造部署轮子）。本工作区康威定律补充笔记用桶装水商城“按层分 vs 按业务流分”的 8 人团队案例推演过完整逻辑。

**典型误用**：①只改组织图不改配套——招聘画像、绩效指标、汇报线不动，三个月后组织在旧惯性下回弹；②把“平台团队”当作“工具组”——平台团队的产品（内部服务）必须有 Team API、有路线图、按产品运营，否则退化成接单的支撑组；③随处增设“赋能团队”——enabling 是有任期的教练（教会即撤），长期驻场的 enabling 会变成最贵的执行者。

### 示例

- 正文简述：[康威定律-补充](../01-第一阶段/05-康威定律-补充.md)（第 5 节“逆康威定律”+“Team Topologies：逆康威的排版工具”——四类团队、三种交互、与逆康威五步的配合已有完整展开，本档案不重写）。
- 与第四阶段的接线：适应度函数守代码边界（本档案第 6 节），Team Topologies 守组织边界——一个管“结构如何生长”，一个管“由谁来生长”。

## 8. 六边形架构起源考（Alistair Cockburn，2005）——短小节

### 起源

**谁与何时**：Alistair Cockburn，2005 年 4 月。**在哪**：他个人网站上的文章《Hexagonal Architecture》，正式别名 **Ports and Adapters**（端口与适配器）——这个别名才是本名，“六边形”只是画法。Cockburn 是敏捷运动元老（敏捷宣言签署者之一、Crystal 方法族作者）。**思想酝酿自 1990 年代前后的 Objective-C 项目**：应用要同时支持多种 UI 与多种存储，把“UI 在最上、数据库在最下”的三层图画法改成“应用在中间、四周全是可插拔端口”，替换问题就自然消失。2005 年他把酝酿十几年的想法写成文章。

**为什么画成六边形**：没有玄学——他自己解释，矩形画图时端口无处安放，六边形边多、写得下端口名字，还不像矩形那样暗示“上下层”。**“六”这个数字没有任何含义**，五边形、八边形均可；这是“表达形式反客为主”的经典案例：名字比思想好记，流传下来的是六边形。

**原文的两个要点**：①**对称性**——驱动侧（调用应用的 UI / 测试 / 消息）与被驱动侧（应用调用的数据库 / 通知）地位对等，任何一边都可替换；这是对“三层架构把 UI 供在最上面”的正面抗议。②**测试是第一个驱动适配器**——测试与生产 UI 通过同一个端口驱动应用，这是“可测试性是架构属性”的早期表达。

### 核心要点与示例（短小节，只做原文考）

- 2005 年 4 月，Cockburn 个人网站，《Hexagonal Architecture》（Ports and Adapters）。
- 思想酝酿自 1990 年代前后的 Objective-C 项目（多 UI 多存储替换的真实痛点）。
- “六”无含义，Ports and Adapters 才是本名；驱动侧 / 被驱动侧对称是核心主张。
- 后续三次命名（2005 六边形 → 2008 洋葱 → 2012 整洁）的完整演进脉络、共同内核（依赖规则）与六维对比表，正文已有，链接：[02-第二阶段/05-其他重要架构风格](../02-第二阶段/05-其他重要架构风格.md) 4.2。
- 与 DDD 的合流发生在红皮书（Vernon 2013，本档案第 1 节）：聚合住在六边形内核里——今天说“DDD 落地架构”，多半指这一合流的结果。

## 10. 为什么这些方法论在 2003~2019 集中涌现

八件概念里除技术债（1992）与 4+1（1995）两件前奏，其余六件全部落在 2003~2019——不是巧合，是**四个条件**同时成熟的结果。

**条件一：软件从“写的时代”进入“改的时代”。** 互联网应用取代套装软件成为主战场，软件从“交付即结束”变成“上线即开始”——交付日只占系统生命周期的一两个百分点，剩下 98% 都是变更。长期主义方法论只有在“改的时代”才有需求侧：技术债管理的是变更成本，ADR 记录的是连续小决策的理由，DDD 守的是模型在连续变更中不腐烂，演进式架构把“架构支持持续变化”写进书名。**这批方法论共同的隐藏主语都是“下一次变更”。**

**条件二：敏捷与迭代把架构工作打碎成日常。** 敏捷（2001~）把“前期一次大设计”变成“迭代中连续小决策”，但决策的**配套件**要几年后才补齐：小决策需要轻量记录（ADR，2007）、欠债需要登记簿与偿还排期（Cunningham 的比喻生长出管理形态）、质量约定需要自动守门（适应度函数，2017，等 CI/CD 成标配）。滞后规律：**管理形态总比实践形态晚好几年**，方法论文献是在为“已经开始做的事”补账。

**条件三：传播基础设施的换代。** 个人博客（2004~）、InfoQ（2006）、QCon（2007）、Leanpub（2010）与 YouTube——方法论的生产与分发成本骤降。对照组就在上表中：DDD 出版于 2003 年，博客时代前夜，靠纸书与口碑慢传播，等了十年才大热；C4 诞生在 2016~2018 的博客与会议视频时代，几年就普及。**同一个行业，传播基础设施把“思想变成方法论”的周期从十年压缩到两三年**——这也是本档案坚持给“原始出处”的原因：传播越快，二手转述越多，年份人名漂移越严重（把事件风暴归到 Evans 名下、把第二版作者变更误作四人不变）。

**条件四：云与微服务把“边界与组织”推上主桌。** 2010~2015 年微服务兴起，头号问题从“类怎么写”变成“边界在哪、谁 owns 什么”——旧概念重新走红（DDD 战略设计、康威定律 1967 年的论文被重读），新概念收官（Team Topologies 把康威定律变成可操作的排版规则；适应度函数给“多目标漂移”装上守门员）。**终点站 Team Topologies 与起点站 DDD 恰好呼应：一个划业务边界，一个划组织边界，微服务同时需要两者。**

还有一条贯穿的暗线：这八件方法论**没有一件产自学院**，作者全部是一线顾问与工程师（Evans、Nygard、Brown、Cockburn、Skelton 都是培训师 / 咨询师出身），过半直接出自“教学需求”（C4 出自培训材料、事件风暴出自工作坊）。这提示我们读方法论的方式：**它们是可复制的教学产品，不是真理**——每件都有明确反抗的对象（一张图讨好所有人、UML 太重、只记图不记为什么、债被当成烂代码）与失效的边界（小项目、简单域、单一受众）。用之前先问它在反抗什么；超过它的反抗对象继续用，方法论就会变成新的形式主义。
