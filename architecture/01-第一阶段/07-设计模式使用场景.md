## 0. 症状反查表：从问题找模式

拿不准时先查这张表，从“你现在的痛点”反查，再跳到对应小节确认边界：

| 你遇到的症状 | 先考虑 |
|---|---|
| 同一套按类型分支的 if/else 散落多处 | 策略（换算法）、工厂方法（换创建） |
| 类名里出现两个维度的拼接（SmsOrderShippedNotifier） | 桥接 |
| 构造参数太多，调用处全是 null, null | 建造者（Kotlin 用具名参数） |
| 想复用老代码但接口对不上 / 不敢动 | 适配器 |
| 想给对象加日志、重试、指标等可组合能力 | 装饰器 |
| 访问前要插权限 / 缓存 / 懒加载 / 远程调用 | 代理 |
| 子系统步骤一大串，调用方只想调一个入口 | 外观 |
| 树形结构，叶子和容器想统一处理 | 组合 |
| 对象数百万个，内存成了主要矛盾 | 享元 |
| 一件事发生后多方各自响应、还会增加下游 | 观察者 |
| 请求要过一串可插拔、可排序的规则 | 责任链 |
| 操作要支持撤销 / 排队 / 审计 / 重放 | 命令（记动作）、备忘录（记状态） |
| 同一调用在不同状态下行为不同、when 分支失控 | 状态 |
| 多个组件两两互调织成网 | 中介者 |
| 业务方要自己配置规则表达式 | 解释器（用现成引擎） |
| 流程骨架固定、只允许各步骤实现不同 | 模板方法 |
| 一组对象必须配套创建、整体切换 | 抽象工厂 |
| 构造昂贵、要按模板批量复制近似对象 | 原型 |
| 进程内真正全局唯一 | 单例 |
| 要遍历特殊结构（游标/树）或懒拉取 | 迭代器 |
| 元素族稳定、操作（报表/导出）不断增加 | 访问者 |

### 0.1 症状现场：把表格放回真实项目

表格是干条目，这一节把每行症状放回真实场景——当时的痛是什么、最后是什么模式接住的。读的时候建议先盖住箭头右侧，自己先答一遍；答错了比答不出来更值得记住，因为那是“差点用错模式”的现场。

- **工单中心分派策略**（→ 策略，3.1）：分派逻辑最初写在 `Dispatcher.assign()` 里，先按技能组、再按负载、再按优先级，三层 if/else 嵌套。上线三个月，产品要求“大促期间优先级权重翻倍”，改动点散落在三处分支，漏改一处就是线上事故。把每种分派算法抽成 `DispatchStrategy`，配置切换——分派器一行没动。判据补一句：如果“负载”和“优先级”只是同一个算法里的参数差异，那就传参，别上升成两个策略类。
- **桶装水押金状态机**（→ 状态，3.9）：押金从“支付押金→桶在手→回收验收→退押金/扣损”一路流转，`DepositService` 里 `when(status)` 出现在扣款、退桶、对账三个方法里，各自判的还不一致——“已验收能不能退押金”三个地方三个答案。把每个状态的行为收进状态对象、把“哪些转移合法”收进唯一入口，三个方法只剩一个问题：当前状态是什么。
- **MES 多设备协议接入**（→ 适配器，2.1）：车间里 Modbus、OPC UA、厂商私有串口协议并存，采集内核不想被任何一种协议绑架。每种协议写一个适配器，把各家报文翻译成统一的 `DeviceReading`，内核只认识统一模型——新协议进来就是新增一个适配器文件。这正是六边形架构里“被驱动侧适配器”的最小形态。
- **低代码公式引擎**（→ 解释器，3.11）：实施人员要在表单里配“当购买数量 > 0 且已有投诉时显示售后段”，不能每次都改代码。把条件定义成 `Gt/And/Or/Not` 的小表达式对象树，运行时对着上下文求值——业务方在界面上拖拽生成的正是这棵树。注意别用的信号：真要自己写分词器和语法分析器时，先想想 SpEL/Aviator/QLExpress 这类现成引擎。
- **API 网关鉴权链**（→ 责任链，3.4）：每个请求要过 认证→验签→限流→路由 四关，任一关可以拦截（401/429 直接返回）或放行。安全规则还在不停增减——上周加了设备指纹校验，这周要求开放平台单独验 AppKey。每关一个 Handler，可插拔、可排序、可按路由分组，比一个 800 行的 `handleGateway()` 方法好改得多。
- **订单超时关单**（→ 命令 + 延迟触发，3.5）：“15 分钟未支付自动关单”不是一次方法调用——它要被创建后等 15 分钟才执行、要留操作痕迹、失败要能重试、关单本身要幂等。把“关单”包装成命令对象投进延迟消息/时间轮，到期取出来执行并落审计。命令模式的本质是“把动作变成数据”：凡是动作要排队、延迟、留痕、重放的场景，先想到它。
- **报表导出多格式**（→ 模板方法 3.2 + 工厂方法 1.1）：运营后台的报表要同时导出 Excel、CSV、PDF，三种格式的“取数”完全一样、“写文件”完全不同，下季度还要加 Markdown。模板方法定骨架（校验→取数→渲染→上传），工厂方法按用户选的格式造对应的渲染器——一个管“步骤怎么走”，一个管“零件谁来做”。
- **订单通知的渠道矩阵**（→ 桥接，2.5）：通知中心有 发货/退款/账单 三类消息，要发到 短信/APP 推送/企业钉钉 三个渠道，难道写九个 `SmsOrderShippedNotifier`？把消息类型和发送渠道拆成两个独立变化的维度，各写三个、运行时装配——3+3 替代 3×3。
- **下单后的连锁反应**（→ 观察者，3.3）：下单成功后要加积分、发券、通知仓配、风控审计，今天四个下游，明天产品说再加“会员成长值”。订单服务发布一个“订单已支付”事件，下游各自订阅——发布方不该认识响应方，否则每加一个下游都要改一次下单主流程。
- **套装的“部分-整体”**（→ 组合，2.6）：桶装水商城有单品，也有“家庭装 = 12 桶水 + 1 个压水器”，套装还能套套装，结算要对任意层级算总价、算件数。让叶子和容器实现同一个 `PricedNode` 接口，结算逻辑对树递归，不区分拿到的是单品还是套装。
- **大促页面的商品卡片**（→ 享元，2.7）：活动页要渲染上万张商品卡片，每张都 new 一个含商品详情的完整对象，堆内存直接报警。商品名称、图片、价格这类内部状态全局共享一份不可变对象，卡片只存自己的位置、样式编号等外部状态——万级对象压缩到千级。
- **审批驳回要能反悔**（→ 备忘录，3.8）：工单中心的主管想在驳回后“回到我上次处理前的样子”，但不能把工单内部字段全暴露给界面层。驳回前快照、撤销时恢复，快照对象对外不透明。和命令的区别一句话：命令记“做了什么动作”，备忘录记“当时是什么状态”。
- **配送排线的多方牵制**（→ 中介者，3.7）：排一个配送波次，司机要看车辆、车辆要看电量、订单要看时段窗口、时段又要看司机负荷，两两互调之后没人敢动任何一个类。引入排线调度中心作为中介者，四方都只和它说话。但要警惕：规则再涨下去，中介者自己会膨胀成上帝类——那时该考虑规则引擎或独立排线服务。
- **多租户整套换云 SDK**（→ 抽象工厂，1.2）：SaaS 化的工单中心要支持“存储、缓存、消息”按租户部署到不同云上。三样东西必须配套（A 云的存储不能配 B 云的队列），抽一个 `CloudComponentFactory`，族内成员一起换。如果三样东西其实各自独立选型，那就退化成三个工厂方法。
- **工单列表的深度分页**（→ 迭代器，3.6）：几十万在途工单不可能一次载入内存，而调用方只想要 `for (ticket in ticketStore)`。给存储实现一个按游标懒拉取的迭代器，调用方代码和遍历普通集合毫无区别——数据在磁盘还是内存，遍历的人不关心。
- **报表引擎的多种口径**（→ 访问者，3.10）：单据结构（表头/明细/审核记录）三年没变过，但财务口径、运营口径、税务口径的统计报表一年加好几个。元素族稳定、操作频繁增加——访问者的教科书场景。反过来，如果节点类型还会增（明天加一种“赠品行”），每加一个类型要改所有访问者，就别用。
- **网关路由配置对象**（→ 建造者，1.4）：一条路由规则带 30 多个可选参数（超时、重试、熔断阈值、灰度权重……），调用处全是 `null, null, null`。Java 里用 Builder 分步收集 + 末端统一校验；Kotlin 里先试具名参数 + 默认值，够用就不必写 Builder 类。
- **监控埋点不敢改老类**（→ 装饰器，2.2）：库存查询是核心链路，想在它外面套一层耗时指标和失败重试，又不敢动原实现。写一个 `MeteredStockQuery` 包住原接口，同型签名、内部计数再转发——原类零改动，指标可拆可换。
- **报表中心的大文件**（→ 代理，2.3）：月账单导出动辄几百 MB，不能点开列表就加载。给导出对象挂一个代理，首次真正下载、之后走缓存，并顺手做权限校验——调用方完全无感。和装饰器的分工：这些控制是调用方“不应感知”的，一旦要用户自己选“要不要套这层”，就回到装饰器。
- **下单门面**（→ 外观，2.4）：新来的同事想下一个测试单，却发现要按顺序调 库存→订单→支付→物流 四个服务、还要自己处理中间失败。给一条“一键下单”的门面方法，把编排顺序收进去——门面方法的纪律是只做编排不做规则，一旦开始长业务判断，它就在腐化成上帝类。
- **进程内配置注册表**（→ 单例，1.3）：运行参数、功能开关这类真正的进程级共享状态，用 `object` 注册表没问题。反例是把“订单服务”注册成单例——分布式部署下每个进程各有一个实例，“业务唯一”必须靠数据库唯一键或分布式锁，单例模式管不到那一层。

## 1. 创建型：对象怎么“造”

### 1.1 工厂方法（[P01](07a-示例-patterns/P01_Factory.kt)）

- **用它的信号**：按条件决定“造什么”的 when/if 散落在多个调用点；创建逻辑本身复杂（要读配置、要初始化）；调用方只该说“给我一个能干 X 的”，不该知道具体类。
- **别用的信号**：只有一个实现且可预见不变——直接 new/构造；为了“显得规范”给所有类都配工厂（纯仪式感）。
- **现实中的它**：`Calendar.getInstance()`、Spring `FactoryBean`、各类 `Creator`/`Loader`；接新支付渠道/新存储后端时。

### 1.2 抽象工厂（[P11](07a-示例-patterns/P11_AbstractFactory.kt)）

- **用它的信号**：一组对象必须**配套**出现（同族），且族会**整体切换**——换数据库方言、换物流服务商、换云厂商 SDK、换 UI 主题。
- **别用的信号**：族成员经常增减（每加一个成员就要改工厂接口）；其实只需要造“一个”对象（用工厂方法）。
- **现实中的它**：JDBC `Connection`（一个连接造出一族 Statement/MetaData）、换主题的 UI 组件集、多租户按渠道整套替换实现。

### 1.3 单例（[P02](07a-示例-patterns/P02_Singleton.kt)）

- **用它的信号**：真正的进程级唯一 + 无状态或线程安全——全局配置、常量池、注册表。
- **别用的信号**：只是为了“到处方便拿到”而全局化（那是伪装的全局变量，依赖不可见、单测不可替）；它是需要被注入替换的“依赖”（用 DI）；**以为单例=业务唯一**——分布式多实例部署下每个进程各有一个，业务唯一要靠数据库唯一键/分布式锁。
- **现实中的它**：Kotlin `object`、Spring 默认单例 Bean、`Runtime.getRuntime()`。

### 1.4 建造者（[P03](07a-示例-patterns/P03_Builder.kt)）

- **用它的信号**：4 个以上可选参数或重叠构造器；构造要**分步收集 + 最后统一校验**（跨字段规则）；要链式配置复杂对象。
- **别用的信号**：Kotlin 里具名参数 + 默认值已经够用却硬写 Builder 类；参数就两三个。
- **现实中的它**：OkHttp `OkHttpClient.Builder`、ProtoBuf `Message.Builder`；Kotlin 首选具名参数，Builder 留给“逐步收集、末端校验”和 Java 互操作。

### 1.5 原型（[P12](07a-示例-patterns/P12_Prototype.kt)）

- **用它的信号**：构造昂贵（解析大配置、加载模型）且要批量“近似副本”；以调好的模板为基准各自微调（活动页模板、报表模板）。
- **别用的信号**：对象小而构造便宜（直接 new）；嵌套可变字段没处理浅拷贝——克隆体会互相污染。
- **现实中的它**：Kotlin `data class.copy()`（语言内置）、游戏怪物模板批量生成、`Object.clone()`。

## 2. 结构型：东西怎么“组装”

### 2.1 适配器（[P04](07a-示例-patterns/P04_Adapter.kt)）

- **用它的信号**：想复用已有实现但接口不匹配；新老系统共存、老接口不能动也不敢动；第三方 SDK 接口不合新系统口味。
- **别用的信号**：能改源码且改动便宜（直接改更干净）；系统从零开始时预设大量“转换层”（过度设计）。
- **现实中的它**：`InputStreamReader`（字节流→字符流）、Spring MVC `HandlerAdapter`、DDD 防腐层的最小形态。

### 2.2 装饰器（[P05](07a-示例-patterns/P05_Decorator.kt)）

- **用它的信号**：多个**正交**能力（日志×重试×指标×缓存）要按需自由组合；不想改原类还想叠功能；用继承会组合爆炸。
- **别用的信号**：只有一个增强且不会变（直接写进去）；套娃超过三四层——调用栈难调试，该考虑责任链或中间件管线。
- **现实中的它**：Java IO 流 `BufferedReader(Reader)`、OkHttp Interceptor、Spring AOP（`@Transactional`/`@Cacheable` 就是运行时动态装饰）。

### 2.3 代理（[P06](07a-示例-patterns/P06_Proxy.kt)）

- **用它的信号**：调用方**不应感知**的控制层——权限校验、懒加载、缓存、远程调用、审计埋点。
- **别用的信号**：增强是要调用方知情、自由选择叠加的（那是装饰器）。
- **现实中的它**：gRPC/Dubbo 生成的本地桩 stub、Spring `@Lazy`/AOP 代理、Kotlin `by lazy`（本质懒加载代理）。

### 2.4 外观（[P15](07a-示例-patterns/P15_Facade.kt)）

- **用它的信号**：调用方被迫理解子系统的编排顺序；子系统复杂但常用入口其实就一两个；想给复杂库一个顺手 API。
- **别用的信号**：子系统本来简单（一层空转）；外观方法开始长业务规则、在多个外观方法间复制流程——它在腐化成上帝类。
- **现实中的它**：分层架构里每层的门面 Service、SLF4J、SDK 的 `XxxClient`。

### 2.5 桥接（[P13](07a-示例-patterns/P13_Bridge.kt)）

- **用它的信号**：两个维度**各自独立变化**，组合起来类爆炸（类型×渠道、平台×渲染器）；类名出现两维度拼接。
- **别用的信号**：其中一个维度实际不变化——不需要桥，一个抽象就够。
- **现实中的它**：JDBC（API 抽象 × 各家驱动实现）、日志门面×实现、消息类型×发送渠道。

### 2.6 组合（[P14](07a-示例-patterns/P14_Composite.kt)）

- **用它的信号**：天然的“部分-整体”层次（菜单、目录、套装、组织架构）；调用方想无差别处理叶子和容器。
- **别用的信号**：结构实际是扁平的；容器与叶子行为差异巨大——硬统一接口会出现大量“不支持此操作”的别扭实现。
- **现实中的它**：文件系统 File/Directory、前端组件树、订单履约包、AST（解释器/访问者的结构基础）。

### 2.7 享元（[P16](07a-示例-patterns/P16_Flyweight.kt)）

- **用它的信号**：海量细粒度对象（数十万以上）成为内存瓶颈，且大部分内部状态可共享、可做到不可变。
- **别用的信号**：对象量万级以下（收益小于复杂度）；共享部分做不到不可变——一处修改全局污染。
- **现实中的它**：`Integer.valueOf` 缓存、字符串常量池、Netty 池化 ByteBuf；大促页面上万商品卡片共享商品元信息。

## 3. 行为型：之间怎么“协作”

### 3.1 策略（[P07](07a-示例-patterns/P07_Strategy.kt)）

- **用它的信号**：同一动作存在一族可替换算法（计价、路由、排序、风控规则），靠类型分支切换；算法要**运行期热切换**（促销季换优惠）。
- **别用的信号**：分支间差异只是**参数**不同（传参就行，别上升成类）；只有一两种算法且长期稳定。
- **现实中的它**：`Comparator` 传给 `sort()`（函数即策略）、Spring `AuthenticationProvider` 链、促销引擎、Kotlin 高阶函数。

### 3.2 模板方法（[P08](07a-示例-patterns/P08_TemplateMethod.kt)）

- **用它的信号**：流程**骨架固定且顺序必须受保护**（校验必须先于执行），各步骤实现各异；做框架钩子给业务填空。
- **别用的信号**：步骤顺序本身需要运行时调整（用函数组合/责任链）；继承层次已深，再套一层更难懂。
- **现实中的它**：`JdbcTemplate`、JUnit 生命周期方法、Spring `refresh()`、各类 export/import 流程骨架。

### 3.3 观察者（[P09](07a-示例-patterns/P09_Observer.kt)）

- **用它的信号**：一件事发生后多方各自响应，发布方不该认识响应方；下游会**持续增加**（今天库存积分、明天优惠券）。
- **别用的信号**：只有固定一个下游（直接调用更清晰）；需要同步拿到处理**结果**（那是调用，不是通知）。
- **现实中的它**：Spring `ApplicationEvent`、MQ 发布订阅（跨进程放大版）、GUI 事件、下单后的一切“后续动作”。

### 3.4 责任链（[P10](07a-示例-patterns/P10_ChainOfResponsibility.kt)）

- **用它的信号**：请求要过一串**可插拔、可排序**的处理步骤，任一步可拦截或放行；规则集会增减（风控规则、网关过滤器）。
- **别用的信号**：步骤固定且少（直接顺序调用）；需要**每一步都执行**且流经数据被逐级加工——那是管道（Pipeline/Stream），不是责任链。
- **现实中的它**：Servlet Filter、Spring Interceptor、Netty Pipeline、API 网关 鉴权→限流→日志→路由、OkHttp Interceptor（责任链+装饰器双重身份）。

### 3.5 命令（[P17](07a-示例-patterns/P17_Command.kt)）

- **用它的信号**：请求需要**排队 / 延迟执行 / 撤销 / 重放 / 审计**；调用方与执行方解耦（任务队列、操作历史）。
- **别用的信号**：调用即执行、永远不需要撤销和记录——直接方法调用，别包装。
- **现实中的它**：`Runnable` 进线程池、编辑器 undo/redo、MQ 任务消息体、CQRS 的 Command、操作审计日志。

### 3.6 迭代器（[P18](07a-示例-patterns/P18_Iterator.kt)）

- **用它的信号**：聚合内部结构特殊（游标分页、树、图）或要**惰性遍历**避免一次性载入；想给“不是集合的东西”一个 for 接口。
- **别用的信号**：普通集合（语言已内置）；数据量小、全量载入毫无压力。
- **现实中的它**：Kotlin for-in / `Sequence`、数据库游标、深度分页滚动拉取、树的先序遍历器。

### 3.7 中介者（[P19](07a-示例-patterns/P19_Mediator.kt)）

- **用它的信号**：N 个组件两两互调成**网状**（N² 依赖）；联动规则要集中管理；各组件想独立复用/测试。
- **别用的信号**：组件就两三个（直连更清楚）；中介者自己长成上帝类——该按流程拆分或上规则引擎/工作流。
- **现实中的它**：调度中心 vs 各执行器、页面组件间事件总线、聊天室、下单流程编排器。

### 3.8 备忘录（[P20](07a-示例-patterns/P20_Memento.kt)）

- **用它的信号**：需要“恢复到之前状态”（撤销、回滚、草稿版本切换）且不能暴露对象内部结构；状态较小、快照频率可控。
- **别用的信号**：状态巨大且快照频繁（内存耗尽——改用命令的逆操作或增量记录）；快照会被外部随意修改（破坏封装）。
- **现实中的它**：编辑器撤销栈、游戏存档、工作流驳回回到上一节点、订单状态机回滚。

### 3.9 状态（[P21](07a-示例-patterns/P21_State.kt)）

- **用它的信号**：对象行为随状态剧变，`when(status)` 分支在**多个方法里重复出现**；状态数会增长；要防护非法转换。
- **别用的信号**：状态就两三个且转换极简（if/布尔够）；“状态”只是数据没有行为差异（用枚举存值即可）。
- **现实中的它**：订单/工单/审批流、TCP 连接状态机、游戏角色状态、Spring StateMachine。

### 3.10 访问者（[P22](07a-示例-patterns/P22_Visitor.kt)）

- **用它的信号**：**元素族稳定、操作频繁增加**——报表、导出、静态检查规则不断新增，但元素类型（如 AST 节点）不再变。
- **别用的信号**：元素类型还会增（每加一个要改所有访问者）；Kotlin 里 `when + sealed` 三五行能解决的场景。
- **现实中的它**：编译器/注解处理器的 AST 遍历、ASM 字节码访问、报表引擎对固定单据结构的多种口径统计。

### 3.11 解释器（[P23](07a-示例-patterns/P23_Interpreter.kt)）

- **用它的信号**：**业务方要自己写规则/表达式**（风控公式、营销条件、审批条件），且同一表达式要对海量数据反复求值。
- **别用的信号**：规则种类少、由开发改代码就行；打算手写完整分词/语法解析——用现成引擎（SpEL/Aviator/QLExpress/Drools）。
- **现实中的它**：规则中心、营销平台条件配置、审批流分支表达式、SQL/正则引擎的内核。

## 模式组合实战三例：单模式为什么常常不够

单个模式只解决**一个维度**的问题；真实系统的痛点往往同时来自两三个维度。下面三个例子都取自本文出现过的场景（API 网关、低代码表单、订单审批），代码均为完整可运行的 Kotlin（kotlinc 2.2.20 编译运行验证），可直接对照运行输出读。

### 组合一：API 网关插件链（责任链 × 策略）

**症状**：请求要按序穿过 认证→限流→路由，任一关可拦截；限流算法还会**整体切换**——大促前把固定窗口换成令牌桶。

**结构**：责任链负责“顺序、拦截、可插拔”；策略负责“这一关内部的算法可替换”。`RateLimitHandler` 是链上的一环，`RateLimitStrategy` 是它内部可注入的策略——两个模式在同一个对象里各管一刀。

```kotlin
/* 例1：API 网关插件链 —— 责任链定"顺序与拦截"，策略定"算法可替换" */
class Request(val path: String, val user: String, val token: String)
class Response(var status: Int = 200, var body: String = "")

interface GatewayHandler {
    fun handle(req: Request, res: Response, next: () -> Unit)
}

class AuthHandler(private val validTokens: Set<String>) : GatewayHandler {
    override fun handle(req: Request, res: Response, next: () -> Unit) {
        if (req.token !in validTokens) { res.status = 401; res.body = "未认证"; return }
        next()
    }
}

/* 策略接口：限流算法一族，运行期可整体替换 */
interface RateLimitStrategy {
    fun allow(key: String, nowMs: Long): Boolean
    val desc: String
}

class FixedWindowStrategy(private val limit: Int, private val windowMs: Long) : RateLimitStrategy {
    private data class Win(var start: Long, var count: Int)
    private val wins = mutableMapOf<String, Win>()
    override fun allow(key: String, nowMs: Long): Boolean {
        val w = wins.getOrPut(key) { Win(nowMs, 0) }
        if (nowMs - w.start >= windowMs) { w.start = nowMs; w.count = 0 }
        return if (w.count < limit) { w.count++; true } else false
    }
    override val desc get() = "固定窗口 $limit 次/${windowMs / 1000}s"
}

class TokenBucketStrategy(private val capacity: Int, private val refillPerSec: Double) : RateLimitStrategy {
    private data class Bucket(var tokens: Double, var last: Long)
    private val buckets = mutableMapOf<String, Bucket>()
    override fun allow(key: String, nowMs: Long): Boolean {
        val b = buckets.getOrPut(key) { Bucket(capacity.toDouble(), nowMs) }
        b.tokens = minOf(capacity.toDouble(), b.tokens + (nowMs - b.last) / 1000.0 * refillPerSec)
        b.last = nowMs
        return if (b.tokens >= 1.0) { b.tokens -= 1.0; true } else false
    }
    override val desc get() = "令牌桶 容量$capacity 速率$refillPerSec/s"
}

class RateLimitHandler(private val strategy: RateLimitStrategy) : GatewayHandler {
    override fun handle(req: Request, res: Response, next: () -> Unit) {
        if (!strategy.allow(req.user, System.currentTimeMillis())) {
            res.status = 429; res.body = "触发限流（${strategy.desc}）"; return
        }
        next()
    }
}

class RouteHandler(private val backend: String) : GatewayHandler {
    override fun handle(req: Request, res: Response, next: () -> Unit) {
        res.body = "已路由到 $backend 处理 ${req.path}"
    }
}

/* 组链：把 N 个 handler 编成一条按序执行的链 */
fun buildChain(vararg handlers: GatewayHandler): (Request, Response) -> Unit {
    fun call(i: Int, req: Request, res: Response) {
        if (i == handlers.size) return
        handlers[i].handle(req, res) { call(i + 1, req, res) }
    }
    return { req, res -> call(0, req, res) }
}

fun main() {
    val chain = buildChain(
        AuthHandler(setOf("tok-a")),
        RateLimitHandler(FixedWindowStrategy(limit = 2, windowMs = 60_000)),
        RouteHandler("order-service")
    )
    repeat(3) { i ->
        val res = Response()
        chain(Request("/orders", "u1", "tok-a"), res)
        println("第${i + 1}次请求: ${res.status} ${res.body}")
    }
    /* 换策略：链与 handler 零改动，只换注入的策略对象 */
    val chain2 = buildChain(
        AuthHandler(setOf("tok-a")),
        RateLimitHandler(TokenBucketStrategy(capacity = 10, refillPerSec = 0.001)),
        RouteHandler("order-service")
    )
    val res = Response()
    chain2(Request("/orders", "u2", "tok-a"), res)
    println("换令牌桶后: ${res.status} ${res.body}")
}
```

运行输出（前两次放行，第三次被固定窗口拦下；换令牌桶后正常放行）：

```text
第1次请求: 200 已路由到 order-service 处理 /orders
第2次请求: 200 已路由到 order-service 处理 /orders
第3次请求: 429 触发限流（固定窗口 2 次/60s）
换令牌桶后: 200 已路由到 order-service 处理 /orders
```

**为什么单模式不够**：只有责任链没有策略——限流算法切换要改 Handler 内部的 if/else，链的结构保住了、开闭原则照样被破坏；只有策略没有责任链——策略算出“放不放行”之后，没人负责把请求继续往下传，也没人在它之前先拦一道。判据：当你在责任链的某个 Handler 里又开始写 `if (algo == "fixedWindow")` 时，就是该往这一环里注入策略的信号；反过来，当“哪些步骤、什么顺序”也成了变化点，就该把散落的策略调用编成链。

### 组合二：低代码表单引擎（组合 × 解释器 × 访问者）

**症状**：表单 Schema 天然是一棵树（Section 套 Field，来自实施人员的拖拽配置）；字段可见性由实施人员配置的**表达式**决定（“买了桶才显示押金段”）；对同一棵树还要不断加新操作——渲染、审计、统计——而不想每次都改节点类。

**结构**：组合定义“树怎么存”，解释器定义“规则怎么算”，访问者定义“对树的新操作怎么加”。三个模式分别对应树的三种变化方向。

```kotlin
/* 例2：低代码表单引擎 —— 组合存"树"、解释器算"规则"、访问者加"新操作" */

/* ---------- 解释器：可见性表达式，由实施人员拖拽配置生成 ---------- */
interface Expr { fun eval(ctx: Map<String, Int>): Boolean }

data class Gt(val fieldId: String, val threshold: Int) : Expr {
    override fun eval(ctx: Map<String, Int>) = (ctx[fieldId] ?: 0) > threshold
}
data class And(val a: Expr, val b: Expr) : Expr {
    override fun eval(ctx: Map<String, Int>) = a.eval(ctx) && b.eval(ctx)
}
data class Not(val inner: Expr) : Expr {
    override fun eval(ctx: Map<String, Int>) = !inner.eval(ctx)
}
data class Or(val a: Expr, val b: Expr) : Expr {
    override fun eval(ctx: Map<String, Int>) = a.eval(ctx) || b.eval(ctx)
}

/* ---------- 组合：表单 Schema 是一棵"部分-整体"树 ---------- */
sealed interface FormNode { val id: String; fun <R> accept(v: FormVisitor<R>): R }

data class Field(
    override val id: String, val label: String, val required: Boolean = false
) : FormNode {
    override fun <R> accept(v: FormVisitor<R>): R = v.visitField(this)
}

data class Section(
    override val id: String, val title: String,
    val children: List<FormNode>, val visibleWhen: Expr? = null
) : FormNode {
    override fun <R> accept(v: FormVisitor<R>): R = v.visitSection(this)
}

/* ---------- 访问者：对同一棵树加新操作，节点类零改动 ---------- */
interface FormVisitor<R> {
    fun visitField(f: Field): R
    fun visitSection(s: Section): R
}

/* 访问者之一：按运行时上下文渲染（跳过不可见 Section） */
class RenderVisitor(private val ctx: Map<String, Int>) : FormVisitor<String> {
    override fun visitField(f: Field) =
        "  - ${f.label}${if (f.required) "（必填）" else ""}\n"
    override fun visitSection(s: Section): String {
        if (s.visibleWhen?.eval(ctx) == false) return ""
        return "## ${s.title}\n" + s.children.joinToString("") { it.accept(this) }
    }
}

/* 访问者之二：审计——收集全部必填字段（导出验收清单用） */
class RequiredCollector : FormVisitor<List<String>> {
    private val acc = mutableListOf<String>()
    override fun visitField(f: Field): List<String> {
        if (f.required) acc += f.label
        return acc
    }
    override fun visitSection(s: Section): List<String> {
        s.children.forEach { it.accept(this) }
        return acc
    }
}

/* 访问者之三：统计节点数（Schema 复杂度审计） */
class NodeCounter : FormVisitor<Int> {
    override fun visitField(f: Field) = 1
    override fun visitSection(s: Section) = 1 + s.children.sumOf { it.accept(this) }
}

fun main() {
    /* 桶装水商城"押金购水单"：押金段只在买了桶时出现 */
    val form = Section("root", "押金购水单", listOf(
        Section("buy", "购买信息", listOf(
            Field("qty", "购买数量", required = true),
            Field("addr", "配送地址", required = true)
        )),
        Section("deposit", "押金信息", listOf(
            Field("depositFee", "押金金额", required = true),
            Field("bucketNo", "水桶编号", required = true)
        ), visibleWhen = Gt("qty", 0)),
        Section("aftercare", "售后信息", listOf(
            Field("servicePhone", "客服电话")
        ), visibleWhen = Or(Not(Gt("qty", 0)), Gt("complaintCount", 0)))
    ))

    println("== 买 3 桶时的表单 ==")
    println(form.accept(RenderVisitor(mapOf("qty" to 3))))
    println("== 买 0 桶（纯退桶）时的表单 ==")
    println(form.accept(RenderVisitor(mapOf("qty" to 0))))
    println("必填字段: ${form.accept(RequiredCollector())}")
    println("Schema 节点总数: ${form.accept(NodeCounter())}")
}
```

运行输出（买 3 桶时押金段出现；纯退桶时押金段隐藏、售后段出现）：

```text
== 买 3 桶时的表单 ==
## 押金购水单
## 购买信息
  - 购买数量（必填）
  - 配送地址（必填）
## 押金信息
  - 押金金额（必填）
  - 水桶编号（必填）

== 买 0 桶（纯退桶）时的表单 ==
## 押金购水单
## 购买信息
  - 购买数量（必填）
  - 配送地址（必填）
## 售后信息
  - 客服电话

必填字段: [购买数量, 配送地址, 押金金额, 水桶编号]
Schema 节点总数: 9
```

**为什么单模式不够**：只有组合没有解释器——可见性规则只能硬编码在 Section 里，实施人员没法配置；只有解释器没有组合——表达式没有可作用的求值对象，规则配了也挂不到树上；没有访问者——每加一个“导出/统计/校验”操作都要去改 Field 和 Section 两个类。还有一个容易忽视的细节藏在输出里：`RequiredCollector` 把隐藏的押金段必填字段也收集了——访问者遍历的是**静态结构**，与运行时可见性无关；如果业务要“按可见性收集”，那是另一个访问者（或把上下文传进去），不要指望改节点类解决。

### 组合三：订单审批流（状态 × 观察者 × 命令/备忘录）

**症状**：审批单在 草稿→待审批→已通过/已驳回 之间流转，非法转移必须被拦；状态一变，SLA 计时、通知中心都要跟着动；“通过”点错了要能撤销，且每次操作要留审计。

**结构**：状态管“当前状态下什么是合法的”；观察者管“变化之后谁知道”；命令 + 备忘录管“动作留痕与反悔”。三者在一个方法里交接班。

```kotlin
/* 例3：订单审批流 —— 状态管"规则"、观察者管"广播"、命令+备忘录管"撤销与审计" */

/* ---------- 状态：每个状态自己声明允许去哪，非法转移在唯一入口被拦 ---------- */
sealed class DocState(val name: String) {
    abstract fun allowedNext(): List<String>
    object Draft    : DocState("草稿")   { override fun allowedNext() = listOf("待审批") }
    object Pending  : DocState("待审批") { override fun allowedNext() = listOf("已通过", "已驳回") }
    object Approved : DocState("已通过") { override fun allowedNext() = emptyList<String>() }
    object Rejected : DocState("已驳回") { override fun allowedNext() = listOf("待审批") }
}

/* ---------- 观察者：状态一变，发布方不知道也不关心谁在听 ---------- */
interface StateListener { fun onStateChanged(doc: ApprovalDoc, from: String, to: String) }

class SlaTimer : StateListener {
    override fun onStateChanged(doc: ApprovalDoc, from: String, to: String) {
        if (to == "待审批") println("  [SLA计时] 审批计时开始（${doc.id}）")
        if (from == "待审批") println("  [SLA计时] 审批计时结束（${doc.id}）")
    }
}

class Notifier : StateListener {
    override fun onStateChanged(doc: ApprovalDoc, from: String, to: String) {
        if (to == "已驳回") println("  [通知] 已短信告知提交人：${doc.id} 被驳回")
    }
}

class ApprovalDoc(val id: String) {
    var state: DocState = DocState.Draft
    var assignee: String = "-"
    private val listeners = mutableListOf<StateListener>()
    fun subscribe(l: StateListener) { listeners += l }

    fun transition(to: DocState) {
        require(to.name in state.allowedNext()) { "非法转移: ${state.name} -> ${to.name}" }
        val from = state
        state = to
        listeners.forEach { it.onStateChanged(this, from.name, to.name) }
    }

    /* ---------- 备忘录：快照不暴露内部结构 ---------- */
    data class Memento(val state: DocState, val assignee: String)
    fun snapshot() = Memento(state, assignee)
    fun restore(m: Memento) { state = m.state; assignee = m.assignee }
}

/* ---------- 命令：动作可执行、可撤销、可留痕 ---------- */
interface Command { fun execute(); fun undo() }

class TransitionCommand(
    private val doc: ApprovalDoc, private val to: DocState, private val assignee: String? = null
) : Command {
    private var memento: ApprovalDoc.Memento? = null
    override fun execute() {
        memento = doc.snapshot()
        if (assignee != null) doc.assignee = assignee
        doc.transition(to)
        println("  [审计] ${doc.id}: ${memento!!.state.name} -> ${doc.state.name}（操作人 $assignee）")
    }
    override fun undo() {
        memento?.let { doc.restore(it); println("  [审计] ${doc.id}: 撤销，恢复到 ${doc.state.name}") }
    }
}

/* 审批历史栈：重放/回退都靠它 */
class ApprovalSession(private val doc: ApprovalDoc) {
    private val history = mutableListOf<Command>()
    init {
        doc.subscribe(SlaTimer()); doc.subscribe(Notifier())
    }
    fun doIt(c: Command) { c.execute(); history += c }
    fun undoLast() { history.removeLastOrNull()?.undo() }
}

fun main() {
    val doc = ApprovalDoc("PO-2026-0301")
    val session = ApprovalSession(doc)

    session.doIt(TransitionCommand(doc, DocState.Pending, assignee = "王经理"))   // 提交送审
    session.doIt(TransitionCommand(doc, DocState.Approved, assignee = "王经理")) // 通过
    println("当前状态: ${doc.state.name}")
    session.undoLast()                                                          // 撤销"通过"
    println("撤销后状态: ${doc.state.name}")
    session.doIt(TransitionCommand(doc, DocState.Rejected, assignee = "王经理")) // 改为驳回
    println("最终状态: ${doc.state.name}")

    try { session.doIt(TransitionCommand(doc, DocState.Draft)) }                // 非法转移演示：已驳回不能直接退回草稿
    catch (e: IllegalArgumentException) { println("  [拦截] ${e.message}") }
}
```

运行输出（注意观察者行先于审计行——广播发生在 `transition()` 内部、状态变化的那一刻）：

```text
  [SLA计时] 审批计时开始（PO-2026-0301）
  [审计] PO-2026-0301: 草稿 -> 待审批（操作人 王经理）
  [SLA计时] 审批计时结束（PO-2026-0301）
  [审计] PO-2026-0301: 待审批 -> 已通过（操作人 王经理）
当前状态: 已通过
  [审计] PO-2026-0301: 撤销，恢复到 待审批
撤销后状态: 待审批
  [SLA计时] 审批计时结束（PO-2026-0301）
  [通知] 已短信告知提交人：PO-2026-0301 被驳回
  [审计] PO-2026-0301: 待审批 -> 已驳回（操作人 王经理）
最终状态: 已驳回
  [拦截] 非法转移: 已驳回 -> 草稿
```

**为什么单模式不够**：只有状态没有观察者——SLA 计时和通知只能塞进每个 `transition` 调用点，漏一处就漏一次计时；只有命令没有状态——撤销功能有了，但“已通过不能撤销重走、已驳回只能重新送审”这些规则没有集中入口，散在每个命令里互相打架；没有备忘录——命令撤销只能写“逆操作”，而 approve 的逆操作是什么？重新置回待审批？assignee 恢复成谁？动作的逆不好写时，恢复快照更稳。

还要留心组合自身的代价，输出里就藏着一处：`undo()` 走 `restore()` 恢复快照，**绕过了 `transition()` 这个唯一入口**，所以撤销后观察者全部失聪——SLA 计时没有重新开始。实际系统里要么让恢复也走状态机入口，要么在恢复后手动广播；“恢复算不算一次状态变化”必须在设计时回答，不能留给运行时。

### 组合的使用判据

- 先问“这个痛点到底来自**几个维度**”：一个维度一个模式。网关的两个维度是“顺序可插拔”与“算法可替换”，所以是两个模式。
- 模式之间要有**明确的交接点**（例1 的交接点是 `RateLimitHandler` 内部；例3 的交接点是 `transition()`），交接点说不清楚，说明还没想清楚要怎么组合。
- 如果凑齐三个模式才能跑通第一个需求，往往不是模式选错了，而是需求还没落地（见下一节反模式）。

---

## 4. 三条使用纪律（比记住 23 个模式更重要）

1. **先有痛点，再上模式**：模式是给“重复出现的痛点”起的标准名字。没有痛点就套模式，是为用而用——复杂度白付。
2. **重构到模式，而非预先设计**：第一次写直白实现，等变化的信号真实出现（第二个、第三个变体来了）再重构到模式。YAGNI 在模式上同样适用。
3. **一个坑一次只填一个模式**：同时引三个模式的提交没法 review 也没法回退；先解决主要矛盾的那个。

## 5. 反模式：模式强迫症（三个症状与戒断判据）

纪律说的是“别忘记”，这一节说的是“上瘾之后长什么样”。模式强迫症（Pattern fever）是把“用上模式”本身当目标，而不是把“解决真实变化”当目标。三种典型症状，一次比一次隐蔽：

**症状一：面试式设计。** 写代码前先想“这里能用上哪个设计模式”，评审的夸奖词是“这里抽象得真好”，而不是“这接住了哪个真实变化”。特征：模式数量超过痛点数量；几乎每个类都配了“接口 + 唯一实现”；新人的第一个 PR 就在给只有一个实现的接口配齐整套依赖注入。这种代码不是坏在错，而是坏在**每一层都要穿过去才能读懂一句业务**。

**症状二：为想象中的扩展性预建抽象。** 需求文档里没有的“将来可能”，都会变成今天的类层次：“以后可能换算法”→先抽策略接口；“以后可能换数据库”→先上抽象工厂；“以后可能加校验”→先搭责任链。每层抽象都是要还的债——阅读成本、测试成本，以及最贵的一种：它会把第二个真实变体**框死在你今天想象的形状里**。真实案例：只有一个支付渠道时就建好“策略接口 + 工厂 + 注册中心”三层，半年后第二个渠道来了，接口却按渠道 A 的参数设计，照样要动接口——预建抽象没有消灭变化，只是把变化推迟并加了利息。

**症状三：把“用了模式”当质量证明。** 评审时说“这里用了策略模式，所以没问题”。模式名只能解释代码的**形状**，不能论证代码的**正确性**：策略里的算法照样可以算错，单例照样会在并发下失效，责任链照样能把顺序排反。质量证明来自测试、来自对真实变化的覆盖，不来自名词。

**戒断判据**（与第 4 节三条纪律一脉相承）：

1. **先有真实变化，再上模式**——第一次写直白实现；第二个变体出现在需求里、而不是出现在想象里时，才重构。
2. **两处重复才抽象**——一处代码哪怕再丑，它只在一个地方疼；为“看着会重复”的代码付抽象税，是最亏的交易。
3. **“删掉会怎样”反向检验**——把刚加的抽象删掉，如果代码没变难懂、没变难改，它本来就不该存在。
4. **模式名只出现在解释里，不出现在论证里**——PR 描述里写“用责任链组织过滤器”是解释结构，没问题；写“因为用了责任链所以可靠”是论证错误。

最后一条自检：翻翻最近三个月的提交记录，找“引入模式”的提交，逐个问“它要接住的第二个变体来了吗”。多数答案是没有——这不是说模式错了，是说节奏错了：模式是重构的目标，不是起点。
