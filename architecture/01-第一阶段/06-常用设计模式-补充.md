## 0. 读前须知：Kotlin 让很多模式“变轻”

GoF 的 23 个模式成书于 1994 年（C++/Smalltalk 时代），很多模式是在**给语言缺少的特性打补丁**。Kotlin 的语言特性直接吸收了一部分：

| 模式 | GoF 时代的写法 | Kotlin 惯用替代 |
|---|---|---|
| 单例 | 手写双重检查锁 | `object` / `by lazy` |
| 建造者 | 手写 Builder 类 | 具名参数 + 默认值 |
| 策略 | 定义接口 + 实现类 | `fun interface` + lambda |
| 责任链 | Handler 抽象类 + next 指针 | 函数列表 + `firstNotNullOfOrNull` |
| 装饰器 | 装饰器基类转发全部方法 | 接口委托 `by` |
| 迭代器 | 手写 hasNext/next | 语言内置 for-in / `Sequence` |
| 访问者 | 双分派 visit 重载 | `when` + sealed 模式匹配（见第 22 节选型） |

所以学模式的正确做法：**先学“意图”，再看语言给了什么更轻的落地方式**。面试问“策略模式”答“传一个函数”不算错，但要知道背后隔离的意图是什么。

另外记住主笔记 2.3 的提醒：模式的价值在于**给解法起标准名字、让团队沟通高效**，不是为用而用。判断标准始终是：它是否让“变化的影响范围局部化”（呼应 2.1 SOLID 的共同目标）。

本节靠后还有进阶版：[Kotlin 让模式变轻（进阶）](#kotlin-让模式变轻进阶四种完整-gof-结构的轻量替代)，把 sealed/函数类型/委托/copy 四种替代展开成代码，并划清“什么时候仍值得用完整 GoF 结构”的边界。

## 1. 工厂方法（Factory Method）｜创建型

> 📂 可运行代码：[07a-示例-patterns/P01_Factory.kt](07a-示例-patterns/P01_Factory.kt)（收银台按渠道创建支付客户端）

**意图**：把“创建哪个对象”的决定收拢到一处，调用方只面向接口，不关心具体类怎么 new。

**订单场景**：支付网关按渠道（支付宝/微信/银联）创建支付客户端。

**反例**：业务代码里到处写 `if (channel == "ALIPAY") AlipayClient() else WeChatPayClient()`——新增渠道要在所有调用点改一遍，漏一处就是线上事故。

```kotlin
interface PaymentClient {
    fun pay(orderId: String, amountCents: Long): String
}

class AlipayClient : PaymentClient {
    override fun pay(orderId: String, amountCents: Long) = "【支付宝】订单 $orderId 支付完成"
}

// 简单工厂：创建逻辑收拢到一处
object PaymentClientFactory {
    fun create(channel: String): PaymentClient = when (channel) {
        "ALIPAY" -> AlipayClient()
        "WECHAT" -> WeChatPayClient()
        else -> throw IllegalArgumentException("不支持的支付渠道: $channel")
    }
}
```

**OCP 升级：注册表式工厂**。上面的 `when` 版新增渠道仍要改工厂本身；注册表版把“新增”变成“注册”，工厂代码完全不动：

```kotlin
object PaymentClientRegistry {
    private val creators = mutableMapOf<String, () -> PaymentClient>()
    fun register(channel: String, creator: () -> PaymentClient) { creators[channel] = creator }
    fun create(channel: String): PaymentClient =
        creators[channel]?.invoke() ?: throw IllegalArgumentException("不支持的支付渠道: $channel")
}

// 接入银联：只写实现类 + 一行注册，零修改老代码
PaymentClientRegistry.register("UNIONPAY") { UnionPayClient() }
```

**Kotlin 要点**：简单场景 `when` 工厂够了；要满足开闭原则用注册表（`Map<String, () -> T>`）；还可以用 `companion operator fun invoke` 让 `PaymentClient("ALIPAY")` 这种写法等价于工厂。

**常见误用：为每个类都配一个工厂**。看到“工厂好”就给每个类发一个 `XxxFactory`，工厂里只有一行 `new`，简单问题被包出三层间接。判据：**创建逻辑是否存在“变化轴”**——渠道会增加（上注册表）、实现可替换（多环境/测试桩）、构造昂贵需要装配（依赖多、要缓存）才值得收口；一个稳定的 `AlipayClient()` 直接 new 就好。过度抽象的代价是真实的：新人找“对象在哪创建的”要多跳两层，工厂本身却从不变化。

## 2. 单例（Singleton）｜创建型

> 📂 可运行代码：[07a-示例-patterns/P02_Singleton.kt](07a-示例-patterns/P02_Singleton.kt)（配置一次加载全局使用 + 风控引擎懒加载）

**意图**：进程内全局唯一实例。

**订单场景**：配置中心客户端、初始化昂贵的规则引擎。

**反例**（Java 时代）：手写双重检查锁（DCL），`volatile` 忘写就是并发 bug；更隐蔽的代价是——单例是**伪装的全局变量**，依赖它的代码看不出依赖关系，单元测试无法替换实现（mock 不了），这直接违反 DIP。

```kotlin
// object = 饿汉式线程安全单例，JVM 类加载机制保证唯一性
object AppConfig {
    val paymentTimeoutMs: Long = 3_000
    val defaultCurrency: String = "CNY"
}

// 懒加载单例：首次访问才初始化，lazy 默认线程安全
class RiskEngine {
    init { println("[初始化] RiskEngine 加载规则模型（模拟耗时操作）") }
    fun score(userId: String): Int = (userId.hashCode() % 100 + 100) % 100
}
val riskEngine: RiskEngine by lazy { RiskEngine() }
```

**Kotlin 要点**：`object` 一行即可完成；懒加载用 `by lazy`。**但先问该不该单例**：如果这个对象是一个“依赖”，更好的做法是依赖注入（构造函数传入），把“唯一”交给容器或调用方去保证，而不是对象自己锁死自己。

**常见误用：全局状态与测试污染**。单例互相持有、还携带可变状态之后：单元测试无法替换实现，用例之间状态串场——第一个用例改了配置，第二个用例莫名其妙失败，测试只能串行跑甚至随机失败。判据：**它是否真的必须全局唯一**——进程级资源（连接池、配置缓存、线程池）是；业务服务（`OrderService`）不是，交给 DI 容器管理生命周期即可。`object` 装不可变常量没问题，装可变状态前先三思：任何“单例里的 `var`”都是全局变量。

## 3. 建造者（Builder）｜创建型

> 📂 可运行代码：[07a-示例-patterns/P03_Builder.kt](07a-示例-patterns/P03_Builder.kt)（后台订单筛选：具名参数 vs 分步收集的 Builder）

**意图**：可选参数很多时，安全、可读地构造对象。

**订单场景**：订单查询对象，6 个参数里 4 个可选。

**反例**（Java 时代）：重叠构造器——`new OrderQuery(42)`、`new OrderQuery(42, "PAID")`、`new OrderQuery(42, "PAID", null, null, 2, 50)`……参数一多，调用处的 `null, null` 谁也读不懂，相邻同类型参数传反了编译器也不报错。

```kotlin
// Kotlin 惯用写法：具名参数 + 默认值，直接消灭 Java 式 Builder
data class OrderQuery(
    val userId: Long? = null,
    val status: String? = null,
    val minAmountCents: Long? = null,
    val maxAmountCents: Long? = null,
    val page: Int = 1,
    val pageSize: Int = 20,
)

// 用起来：只写关心的字段，顺序无关，可读性拉满
val query = OrderQuery(userId = 42, status = "PAID", page = 2, pageSize = 50)
```

**Kotlin 要点**：90% 的 Builder 被具名参数 + 默认值取代；需要“分步收集、最后统一校验”时（比如从表单逐项填充），用 `apply { }` 块在不可变对象之外解决，或仍然写 Builder。与 Java 库互操作（OkHttp、ProtoBuf）时仍会见到 Builder，认得出来即可。

**常见误用：参数不到 4 个也上建造者**。3 个参数的请求对象也写一个 Builder，多出一个类和一层间接，读代码的人要先跳进 Builder 才知道能填什么、填了什么。判据：**可选参数 ≥ 4，或需要“分步收集 + 最后统一校验”** 才值得；Kotlin 下具名参数 + 默认值覆盖大半需求，`apply { }` 覆盖大部分“分步填充”。判据的另一面：参数会持续增加的对外 SDK/网关请求对象，提前上 Builder 反而是合理投资——按“调用方的数量”决定，不按参数数量一刀切。

## 4. 适配器（Adapter）｜结构型

> 📂 可运行代码：[07a-示例-patterns/P04_Adapter.kt](07a-示例-patterns/P04_Adapter.kt)（老库存系统包装成新接口，防腐层最小形态）

**意图**：接口不匹配时做转换，让不兼容的类合作；不改动任何一方。

**订单场景**：新系统想要干净的库存接口，但老系统接口形状完全不同且不能改。

```kotlin
// 新系统想要的目标接口
interface InventoryPort {
    fun reserve(itemId: String, quantity: Int): Boolean
}

// 老系统：命名风格、参数类型、返回值全不一样
class LegacyInventorySystem {
    fun chk_resv(skuId: Int, cnt: Int): Int {  // 0=成功 1=库存不足 2=系统错误
        return 0
    }
}

// 适配器：把老接口"翻译"成新接口
class LegacyInventoryAdapter(private val legacy: LegacyInventorySystem) : InventoryPort {
    override fun reserve(itemId: String, quantity: Int): Boolean =
        legacy.chk_resv(itemId.toInt(), quantity) == 0
}
```

**关键点**：新代码从此只依赖 `InventoryPort`，老系统被隔离在适配器后面——这就是 DDD“防腐层”（第四阶段）在代码级的最小形态：**老系统的烂接口烂不到新代码身上**。

**Kotlin 要点**：接口委托 `by` 可以少写纯转发的代码。

**常见误用：三个“包一层”模式互相串门（意图混淆）**。适配器顺手加缓存、代理里塞业务判断、装饰器改了接口形状——三者结构相似，职责越界非常隐蔽。意图判据一句话：**形状不对找适配器（转接），想增强且调用方知情找装饰器，想控制且调用方无感找代理**。追问两个问题即可判定：接口同形吗？改的是“形状”还是“行为”？行为里是“叠加增强”（可多层）还是“限制控制”（通常一层）？适配器里夹带行为时拆成两层：适配器管转接，增强交给它外面的装饰器——防腐层不该长出新耦合。四组易混模式全表见下文[易混模式辨析](#易混模式辨析四组最容易张冠李戴的对)。

## 5. 装饰器（Decorator）｜结构型

> 📂 可运行代码：[07a-示例-patterns/P05_Decorator.kt](07a-示例-patterns/P05_Decorator.kt)（HTTP 客户端叠加日志/重试/指标，两种套法行为对比）

**意图**：不改原类、动态叠加能力；多个能力可自由组合。

**订单场景**：HTTP 客户端叠加日志、重试（能力正交：要不要日志 × 要不要重试，继承写法要 2² 个子类，装饰器只要 2 个装饰器）。

```kotlin
interface OrderHttpClient {
    fun post(path: String, body: String): String
}

// 会抖动的网络客户端：前 failTimes 次抛异常（演示用）
class FlakyOrderHttpClient(private val failTimes: Int) : OrderHttpClient { ... }

// 装饰器一：日志。接口委托 by 让装饰器只写差异部分
class LoggingClient(private val delegate: OrderHttpClient) : OrderHttpClient by delegate {
    override fun post(path: String, body: String): String {
        println("[日志] → POST $path")
        val resp = delegate.post(path, body)
        println("[日志] ← $resp")
        return resp
    }
}

// 装饰器二：重试
class RetryClient(
    private val delegate: OrderHttpClient,
    private val maxRetries: Int = 2,
) : OrderHttpClient by delegate {
    override fun post(path: String, body: String): String {
        var last: java.io.IOException? = null
        repeat(maxRetries + 1) {
            try {
                return delegate.post(path, body)
            } catch (e: java.io.IOException) {
                println("[重试] 第 ${it + 1} 次失败: ${e.message}")
                last = e
            }
        }
        throw last!!
    }
}

// 像套娃一样自由组合：重试(日志(抖动网络))
val http: OrderHttpClient = RetryClient(LoggingClient(FlakyOrderHttpClient(failTimes = 2)))
```

运行效果（节选）：日志先包住请求，重试在最外层兜住前两次抖动，第三次成功——**每个装饰器只做一件事，组合交给调用方**。

```text
[日志] → POST /orders
[重试] 第 1 次失败: 网络抖动 #1
[日志] → POST /orders
[重试] 第 2 次失败: 网络抖动 #2
[日志] → POST /orders
[日志] ← 200 OK（第 3 次调用成功）
```

**Kotlin 要点**：`: OrderHttpClient by delegate` 让未覆盖的方法自动转发，装饰器只写差异；这也是 OkHttp Interceptor 的原理（`chain.proceed` 就是链上的 delegate 调用）。

**常见误用：层数失控与语义破坏**。其一，层数失控：`重试(指标(日志(重试(日志(…)))))` 套五层后，异常栈没人读得懂，组合逻辑散落在每个装配点。判据：装饰器解决“正交能力的组合”，**同一能力被叠加两次以上就该合并成一个类或改成构造参数**。其二，破坏语义：“透明增强”是有前提的——重试装饰器默认套在非幂等调用上，会把一次下单重试成两次下单；缓存装饰器吞掉异常返回过期数据。判据：副作用型增强必须以幂等性为显式前提（下单接口的重试要带幂等键），不能“默认全包”。

## 6. 代理（Proxy）｜结构型

> 📂 可运行代码：[07a-示例-patterns/P06_Proxy.kt](07a-示例-patterns/P06_Proxy.kt)（库存 RPC 本地桩：先鉴权再转发，RPC stub 原型）

**意图**：**控制**对真实对象的访问（权限、懒加载、缓存、远程调用），调用方无感。

**订单场景**：库存服务是远程 RPC，本地给一个代理：先做权限检查，再转发给真实对象。

```kotlin
interface InventoryFacade {
    fun lockStock(orderId: String, sku: String, quantity: Int)
}

class RealInventoryFacade : InventoryFacade {
    override fun lockStock(orderId: String, sku: String, quantity: Int) {
        println("[远程调用] 库存服务锁定: orderId=$orderId sku=$sku x$quantity")
    }
}

// 保护代理：调用方以为在调真服务，实际上先过权限检查
class InventoryProxy(
    private val real: InventoryFacade = RealInventoryFacade(),
) : InventoryFacade by real {
    var currentUser: String = "system" // 演示用；真实项目从请求上下文取
    override fun lockStock(orderId: String, sku: String, quantity: Int) {
        check(currentUser in setOf("system", "ops", "admin")) { "用户 $currentUser 无权操作库存" }
        real.lockStock(orderId, sku, quantity)
    }
}
```

**装饰器 vs 代理**（结构一模一样，意图不同）：

- 装饰器：调用方**主动选择**叠加能力，包几层是调用方的事 → 日志、重试
- 代理：调用方**不知道有代理存在**，以为是真对象 → 权限、懒加载、RPC stub

**架构级伏笔**：RPC 框架（gRPC/Dubbo）生成的“本地桩 stub”就是远程代理的工业化版本——调用方 `inventoryFacade.lockStock(...)`，底下藏的是序列化 + 网络 + 重试 + 熔断。第三阶段远程通信会回到这里。

**常见误用：把业务逻辑写进代理**。保护代理尝到甜头后开始理解业务：“促销订单跳过库存检查”“白名单用户跳过限额”——代理从“控制访问”越权成第二套业务规则，和真正的业务服务形成双写，改一处漏一处。判据：**代理只做“控制”（鉴权、懒加载、远程转发、缓存），不做“决策”**；代理里出现业务分支，就是该下沉到服务的信号。另一个常见误判是“代理无成本”：远程代理每次调用都是一次网络往返，循环里调 N 次就是 N 次 RTT，批量化才是正解（第三阶段远程通信展开）。

## 7. 策略（Strategy）｜行为型

> 📂 可运行代码：[07a-示例-patterns/P07_Strategy.kt](07a-示例-patterns/P07_Strategy.kt)（促销季切换优惠策略，结算代码零改动）

**意图**：一族可替换的算法，运行时可切换；新增算法不改使用方。**这是 OCP 的标准落地做法**（呼应主笔记 2.1 的开闭原则反例与修正）。

**订单场景**：优惠计算——满减、折扣、N 元购，促销季来回换。

**反例**：`CheckoutService` 里 `if (type == FULL_REDUCTION) ... else if (type == VIP_RATE) ...`——每次大促加促销类型都要改结算核心类，改错一处全线故障。

```kotlin
// fun interface：单方法接口，可以用 lambda 直接创建
fun interface DiscountPolicy {
    fun discount(amountCents: Long): Long
}

class FullReductionPolicy(
    private val thresholdCents: Long,
    private val reduceCents: Long,
) : DiscountPolicy {
    override fun discount(amountCents: Long) =
        if (amountCents >= thresholdCents) amountCents - reduceCents else amountCents
}

// 结算服务只依赖抽象，换促销策略不改这里的代码
class CheckoutService(private val policy: DiscountPolicy) {
    fun payableCents(amountCents: Long): Long {
        val payable = policy.discount(amountCents)
        println("[结算] 原价 $amountCents → 应付 $payable")
        return payable
    }
}

// 复杂策略写成类；简单策略一个 lambda 就是策略
CheckoutService(FullReductionPolicy(thresholdCents = 100_00, reduceCents = 20_00)).payableCents(150_00)
CheckoutService(DiscountPolicy { it * 95 / 100 }).payableCents(150_00)  // VIP 95 折
```

**Kotlin 要点**：`fun interface` + lambda 是策略的“轻量形态”；当策略有多个方法或有状态时，回到普通 interface + 实现类。**从架构视角看，策略就是“把变化点抽成可插拔单元”——微服务的可插拔中间件、算法路由都是它的放大版**。

**常见误用：有状态的策略与失管的策略**。其一，把可变字段塞进策略对象（比如在策略里记“本单已优惠金额”），并发请求互相污染，而且只在压测时现身——**策略默认应当不可变，需要的状态由调用方在调用时传参**（把“订单上下文”作为 `discount` 的参数，而不是策略的字段）。其二，策略一多就失管：十几个实现散落各包，没人说得出全集，新人在角落又写了一个重复的。判据：用注册表/枚举收口（呼应第 1 节注册表工厂），让“有哪些策略”一眼可枚举；策略与渠道编码的映射关系放配置，别散在调用点。

配套反例已在本机编译运行验证（Kotlin 2.2.20），一行不改就能复现“第二单该减未减”：

```kotlin
// 反例：把"本单的决定"记进策略对象——策略被当单例复用后状态跨单泄漏
class LeakyDiscountPolicy {
    private var grantedToday = false // "今天是否已优惠过"本应存外部存储按天/按单判定

    fun discount(amountCents: Long): Long {
        if (!grantedToday && amountCents >= 100_00) {
            grantedToday = true // 副作用写在自己身上：第一单的决定，第二单被迫继承
            return amountCents - 20_00
        }
        return amountCents
    }
}

// 修正：策略纯函数化，状态由调用方按单持有/传递
class PureDiscountPolicy {
    fun discount(amountCents: Long): Pair<Long, Long> = // (应付, 本单已优惠)
        if (amountCents >= 100_00) (amountCents - 20_00) to 20_00 else amountCents to 0L
}

fun main() {
    val shared = LeakyDiscountPolicy() // 模拟 DI 容器里的单例策略 Bean
    println("[反例] 订单1 应付=${shared.discount(150_00)}")
    println("[反例] 订单2 应付=${shared.discount(150_00)}（本该同样减 2000，却被第一单的决定吞掉）")

    val pure = PureDiscountPolicy()
    val (p1, r1) = pure.discount(150_00)
    val (p2, r2) = pure.discount(150_00)
    println("[修正] 订单1 应付=$p1 本单优惠=$r1")
    println("[修正] 订单2 应付=$p2 本单优惠=$r2（纯函数策略，各单各算）")
}
```

实际运行输出（注意订单 2：15000 就是“该减未减”的脏结果）：

```text
[反例] 订单1 应付=13000
[反例] 订单2 应付=15000（本该同样减 2000，却被第一单的决定吞掉）
[修正] 订单1 应付=13000 本单优惠=2000
[修正] 订单2 应付=13000 本单优惠=2000（纯函数策略，各单各算）
```

## 8. 模板方法（Template Method）｜行为型

> 📂 可运行代码：[07a-示例-patterns/P08_TemplateMethod.kt](07a-示例-patterns/P08_TemplateMethod.kt)（订单导出流程：CSV/HTML 填空 + 钩子加审计）

**意图**：父类定死流程骨架，子类只填空位。适合“流程固定、步骤实现多变”的场景。

**订单场景**：订单导出流程固定为 校验权限 → 查询数据 → 格式化 → 记录完成，但 CSV/HTML/Excel 各步骤实现不同。

```kotlin
abstract class OrderExporter {
    // 模板方法：流程骨架用 final 锁死，子类只能填空位
    final fun export(orderId: String): String {
        checkPermission()               // 钩子：通用步骤给默认实现
        val rows = query(orderId)       // 空位：子类必须实现
        val content = format(rows)      // 空位：子类必须实现
        println("[导出] 完成 orderId=$orderId，格式=${this::class.simpleName}")
        return content
    }

    protected open fun checkPermission() {
        println("[导出] 校验导出权限（通用步骤）")
    }

    protected abstract fun query(orderId: String): List<String>
    protected abstract fun format(rows: List<String>): String
}

class CsvOrderExporter : OrderExporter() {
    override fun query(orderId: String) = listOf("order_id=$orderId", "status=PAID")
    override fun format(rows: List<String>) = rows.joinToString("\n")
}

class HtmlOrderExporter : OrderExporter() {
    override fun query(orderId: String) = listOf("order_id=$orderId", "status=PAID")
    override fun format(rows: List<String>) =
        "<table>\n" + rows.joinToString("\n") { "<tr><td>$it</td></tr>" } + "\n</table>"
}
```

**三层空位设计**：`final fun` 锁骨架 → `protected open`（钩子，有默认实现可不覆盖）→ `protected abstract`（纯空位，必须覆盖）。骨架被锁死意味着子类**不可能**把“校验”绕过去——这是模板方法相比“子类随便覆盖 public 方法”的安全优势。

**Kotlin 要点**：继承的替代方案是“把步骤当函数参数传入”（高阶函数），流程骨架就变成一个普通函数，继承层次消失——组合优于继承（呼应 2.1 LSP：少用继承来实现复用）。两种都要看得懂。

**常见误用：继承层次失控与钩子越权**。其一，`OrderExporter → CsvExporter → CsvExporterV2` 三代继承之后，“流程到底走到哪一步”要跨三个文件跳着看，模板方法的可读性红利耗尽。判据：**继承深于两层，就把步骤改成函数参数（组合）**——骨架退化为一个高阶函数，“继承”只剩“传参”。其二，子类覆盖钩子时顺手重排步骤、或在 `query()` 里提前 return 掉校验——违反 LSP，“骨架不可绕过”的承诺作废。判据：钩子只允许**填空**，不允许**改流程**；需要改流程，说明当初的骨架抽象选错了，改骨架而不是绕骨架。

## 9. 观察者（Observer）｜行为型

> 📂 可运行代码：[07a-示例-patterns/P09_Observer.kt](07a-示例-patterns/P09_Observer.kt)（下单事件通知多方，含“毒订阅方”异常隔离演示）

**意图**：状态变化时通知多方；发布方不认识订阅方，双方只认识事件。

**订单场景**：下单成功后，库存要扣减、积分要发放、消息要推送——下单逻辑不应该认识这三家。

**反例**：`OrderService.createOrder()` 里直接调用 `stockService.deduct()`、`pointService.add()`、`pushService.notify()`——每加一个下游，订单核心代码就改一次；下游宕机，下单也随之不可用。

```kotlin
data class OrderCreatedEvent(
    val orderId: String,
    val userId: String,
    val amountCents: Long,
)

class OrderEventBus {
    private val listeners = mutableListOf<(OrderCreatedEvent) -> Unit>()
    fun subscribe(listener: (OrderCreatedEvent) -> Unit) { listeners += listener }
    fun publish(event: OrderCreatedEvent) {
        println("[事件总线] 发布 $event")
        listeners.forEach { it(event) }
    }
}

// 下游各自订阅，订单代码完全不认识它们
val bus = OrderEventBus()
bus.subscribe { e -> println("[库存] 扣减库存: ${e.orderId}") }
bus.subscribe { e -> println("[积分] 给 ${e.userId} 发放积分") }
bus.subscribe { e -> println("[消息] 推送订单完成通知") }
bus.publish(OrderCreatedEvent("o_3001", "u_42", 15_800))
```

**Kotlin 要点**：lambda 列表就是最简观察者，不需要 `EventListener` 接口体系。

**架构级伏笔**（重点）：这个进程内实现有两个致命局限——**同步执行**（一个订阅方抛异常，后面的全不执行、甚至拖垮下单主流程）和**不跨进程**。把它放大并解决这两点，就是消息队列 + 事件驱动架构（第二阶段）：RocketMQ/Kafka 的发布订阅 = 观察者的分布式版，再加持久化、重试、削峰。**认出“代码级模式 → 架构级模式”的放大关系，是学模式的架构师视角**。

**常见误用：忘退订的内存泄漏与“先发布后订阅”的顺序坑**。其一，忘退订：长生命周期的发布方（全局事件总线）持有短生命周期对象（页面、临时弹窗、一次性任务）的订阅引用，订阅方早该回收却因被引用而泄漏——**订阅与退订必须成对出现**（`use { }` 或 try-finally 里成对注册注销，或用作用域感知的订阅 API、弱引用）。其二，顺序坑：发布发生在订阅完成之前（订阅在另一个线程还没注册完），下游永远收不到首条事件，且极难复现——**要么显式保证“先订阅后发布”（初始化顺序写进框架约定），要么改用“新订阅者先补拉当前状态、再收增量事件”的模型**。其三，同步链上的毒订阅方：任何一个订阅方抛异常会中断后续（P09 演示了隔离写法）——进程内总线至少要给每个回调套 try-catch。

## 10. 责任链（Chain of Responsibility）｜行为型

> 📂 可运行代码：[07a-示例-patterns/P10_ChainOfResponsibility.kt](07a-示例-patterns/P10_ChainOfResponsibility.kt)（下单风控：黑名单→限额→深夜大单，四单四种结局）

**意图**：请求沿处理者链传递，每个处理者要么处理、要么放行给下一个。

**订单场景**：下单风控——黑名单检查 → 单笔限额 → （将来继续加规则）→ 默认放行。

```kotlin
data class RiskOrder(val orderId: String, val userId: String, val amountCents: Long)

sealed interface RiskDecision {
    data class Reject(val reason: String) : RiskDecision
    data object Pass : RiskDecision
}

// 一条规则：返回 null 表示"放行，交给下一条"；返回 Reject 表示拦截
typealias RiskCheck = (RiskOrder) -> RiskDecision?

fun checkRisk(order: RiskOrder, checks: List<RiskCheck>): RiskDecision =
    checks.firstNotNullOfOrNull { it(order) } ?: RiskDecision.Pass

fun blacklistCheck(order: RiskOrder): RiskDecision? =
    if (order.userId == "u_777") RiskDecision.Reject("黑名单用户") else null

fun amountLimitCheck(order: RiskOrder): RiskDecision? =
    if (order.amountCents > 500_000_00) RiskDecision.Reject("单笔超过 5 万，转人工审核") else null

val pipeline = listOf(::blacklistCheck, ::amountLimitCheck)
// checkRisk(RiskOrder("o_4001", "u_777", 100_00), pipeline) → Reject(reason=黑名单用户)
// checkRisk(RiskOrder("o_4002", "u_42", 100_00), pipeline)  → Pass
```

**Kotlin 要点**：函数列表 + `firstNotNullOfOrNull`（取第一个非 null 结果）就是完整责任链；经典 OO 版（Handler 抽象类持 `next` 指针）在需要“链上后移/中断恢复”等复杂控制时才用。

**认出现实中的它**：Servlet Filter、Spring Interceptor、OkHttp Interceptor、Netty Pipeline——网关/中间件的横切能力（鉴权→限流→日志→路由）几乎都是责任链，因为“规则可插拔、顺序可编排”正是它的强项。

**常见误用：链顺序成为隐式契约**。“黑名单必须在限额之前”“鉴权必须在限流之后”只存在于某次 code review 的记忆里——新人调整 `listOf(::a, ::b)` 的顺序，拦截语义全变，而编译器和测试都不报警（比如限额放在鉴权后，未认证请求的恶意大单反而绕过检查）。工程判据：**链的顺序是契约，要落进测试**——写一条“顺序契约”用例，构造一个“只有顺序对了结果才对”的输入并断言结果；组装处集中声明链并注释每个位置“为什么在这”；链超过 5 节时按语义分段（如网关的 pre-auth / post-auth 两段），段内可自由调整，段间顺序受测试保护。

这条“顺序契约用例”长什么样？下面的完整示例（已编译运行验证）构造了一个**只有顺序对了结果才对**的输入——VIP 大单：免检在前放行、限额在前拦截：

```kotlin
data class RiskOrder(val userId: String, val amountCents: Long)

sealed interface RiskDecision {
    data class Reject(val reason: String) : RiskDecision
    data object Pass : RiskDecision
}

typealias RiskCheck = (RiskOrder) -> RiskDecision?

// 免检通道：VIP 直接放行（业务约定 VIP 不限额）
val vipFastPath: RiskCheck = { if (it.userId == "u_666") RiskDecision.Pass else null }

// 限额：单笔超 5 万转人工
val amountLimit: RiskCheck =
    { if (it.amountCents > 500_000_00) RiskDecision.Reject("单笔超 5 万，转人工") else null }

fun runChain(order: RiskOrder, chain: List<RiskCheck>): RiskDecision =
    chain.firstNotNullOfOrNull { it(order) } ?: RiskDecision.Pass

fun main() {
    val vipBigOrder = RiskOrder("u_666", 600_000_00)
    val byDesign = runChain(vipBigOrder, listOf(vipFastPath, amountLimit))
    val byLuck = runChain(vipBigOrder, listOf(amountLimit, vipFastPath))
    println("VIP 大单 600000 分：")
    println("  设计顺序 [免检, 限额] → $byDesign")
    println("  调换后   [限额, 免检] → $byLuck")
    check(byDesign == RiskDecision.Pass && byLuck is RiskDecision.Reject) {
        "顺序契约被破坏：同一输入、两种顺序、两种结果"
    }
    println("顺序契约断言成立：免检必须在限额前——这条规则已钉进 CI，而不是钉在某次 code review 的记忆里")
}
```

实际运行输出：

```text
VIP 大单 600000 分：
  设计顺序 [免检, 限额] → Pass
  调换后   [限额, 免检] → Reject(reason=单笔超 5 万，转人工)
顺序契约断言成立：免检必须在限额前——这条规则已钉进 CI，而不是钉在某次 code review 的记忆里
```

要点：契约测试的关键不是“跑一遍链”，而是**构造对顺序敏感的输入**（一个会被前序检查短路、且短路结果与后续检查相反的请求），再对两种顺序断言不同结果——谁动了组装顺序，CI 立刻红。

## 14. 组合（Composite）｜结构型

> 📂 可运行代码：[07a-示例-patterns/P14_Composite.kt](07a-示例-patterns/P14_Composite.kt)（套装嵌套装的订单计价，sealed 实现树）

**意图**：树形结构里，叶子与容器同一接口——调用方递归处理，无差别对待“一件商品”和“一个套装”。

**场景**：订单计价。订单行既可以是单品也可以是套装（套装里还能再嵌套装）；计价只有一行 `items.sumOf { it.totalCents() }`，嵌套多深都不用关心。

**要点**：现实对应——菜单、组织架构、文件系统、前端组件树。用 sealed 表达元素族还能获得编译器穷尽检查。它是解释器（第 23 节）AST 的结构基础。

**延伸：透明组合 vs 安全组合**。GoF 原书留了一个经典取舍没替你决定：树操作（`add`/`remove`）要不要放进公共接口？

- **透明组合**：`add` 在公共接口上，调用方对叶子和容器**无差别调用**——代价是单品被迫“假装支持”，只能抛异常或静默忽略，把“编译期就能发现的错误”推迟到运行期。
- **安全组合**：树操作只出现在容器类上——代价是调用方需要区分类型，但 Kotlin 的 sealed + when 把这个代价压到了编译期（漏分支编译器报错），安全版明显更划算。

完整示例（已编译运行验证，两种写法对照）：

```kotlin
// 写法一：透明组合——add() 进公共接口，单品被迫"假装支持"
interface TransparentComponent {
    fun totalCents(): Long
    fun add(child: TransparentComponent)
}

data class Sku(val name: String, val priceCents: Long, val qty: Int) : TransparentComponent {
    override fun totalCents() = priceCents * qty
    override fun add(child: TransparentComponent): Unit =
        throw UnsupportedOperationException("单品不能挂子节点") // 运行期才爆炸
}

class BundleT(val name: String) : TransparentComponent {
    private val children = mutableListOf<TransparentComponent>()
    override fun totalCents() = children.sumOf { it.totalCents() }
    override fun add(child: TransparentComponent) { children += child }
}

// 写法二：安全组合——树操作只出现在容器；sealed + when 把"区分类型"的代价压到编译期
sealed interface SafeComponent { fun totalCents(): Long }

data class SafeSku(val name: String, val priceCents: Long, val qty: Int) : SafeComponent {
    override fun totalCents() = priceCents * qty
}

class BundleSafe(val children: List<SafeComponent>) : SafeComponent {
    override fun totalCents() = children.sumOf { it.totalCents() }
}

fun familyPack(): SafeComponent =
    BundleSafe(
        listOf(
            SafeSku("桶装水", 1_500, 2),
            BundleSafe(listOf(SafeSku("饮水机", 29_900, 1))),
        )
    )

fun main() {
    val t = BundleT("家庭装")
    t.add(Sku("桶装水", 1_500, 2))
    val leaf: TransparentComponent = Sku("赠品券", 0, 1)
    // leaf.add(t)  // 编译放行、运行期才抛 UnsupportedOperationException——错误被推迟到线上
    println("[透明] 合计=${t.totalCents()}（add 的合法性只有运行期才知道）")

    val s = familyPack()
    println("[安全] 嵌套装合计=${s.totalCents()}（1500x2 + 29900x1 = 32900）")
}
```

实际运行输出：

```text
[透明] 合计=3000（add 的合法性只有运行期才知道）
[安全] 嵌套装合计=32900（1500x2 + 29900x1 = 32900）
```

判据：**没有动态改树需求的场景（计价、报表）一律安全组合**；透明组合只在“调用方真的无法区分叶子和容器、且树结构运行时可变”（如 GUI 组件树）才有理由——GoF 写透明版是因为 1994 年还没有模式匹配，今天不该照抄。

## 15. 外观（Facade）｜结构型

> 📂 可运行代码：[07a-示例-patterns/P15_Facade.kt](07a-示例-patterns/P15_Facade.kt)（placeOrder() 背后藏着六个子系统）

**意图**：给复杂子系统一个简单入口。**不是消灭子系统，而是把编排细节藏起来**。

**场景**：下单要协调 锁库存→计价→核券→风控→落库→发事件 六步；Controller 只调 `placeOrder()`，不知道六步的存在。

**要点**：最常用也最容易被忽略——分层架构里的门面服务（`OrderService`）、SDK 的 `XxxClient` 本质都是外观。与中介者（第 19 节）的区别：外观是**单向**简化入口（外面调里面），中介者是**双向**协调（同事之间互相通信）。腐化信号：外观方法越长越胖、流程在多个外观方法间复制。

## 16. 享元（Flyweight）｜结构型

> 📂 可运行代码：[07a-示例-patterns/P16_Flyweight.kt](07a-示例-patterns/P16_Flyweight.kt)（10 万订单行只建 1 万个商品元信息对象）

**意图**：共享细粒度对象省内存。**内部状态**（不变、可共享）放进享元；**外部状态**（多变）由调用方持有。

**场景**：订单列表页 10 万条订单行，商品元信息只有 1 万种——元信息做享元共享（池 + `getOrPut`），订单行只持有引用 + 数量/成交价。代码验证：10 万行只创建 1 万个对象。

**要点**：享元必须不可变——谁改共享对象，引用它的所有订单行同时被污染。现实对应：`Integer.valueOf` 缓存、字符串常量池、连接池。

## 17. 命令（Command）｜行为型

> 📂 可运行代码：[07a-示例-patterns/P17_Command.kt](07a-示例-patterns/P17_Command.kt)（运营改地址/调价，历史栈逐步撤销）

**意图**：把“请求”封装成对象。于是请求可以**排队、记录、撤销、重放、审计**。

**场景**：运营后台对订单的操作封装成命令，走统一历史栈执行，支持逐步撤销（`execute`/`undo` 成对，执行时记住撤销所需最小信息）。

**架构级伏笔**：命令对象 ≈ CQRS 里的 Command（表达意图）；执行历史 ≈ 事件溯源里的 Event（记录已发生的事）——两者都在第二阶段事件驱动架构展开。

## 18. 迭代器（Iterator）｜行为型

> 📂 可运行代码：[07a-示例-patterns/P18_Iterator.kt](07a-示例-patterns/P18_Iterator.kt)（对账任务用 for 扫完游标分页的订单库）

**意图**：不暴露聚合内部结构，按序遍历。现代语言已内置（Kotlin for-in 就是迭代器语法糖），日常无需手写；价值在**遍历策略自定义**：游标分页、懒拉取。

**场景**：对账任务全量扫描历史订单，存储只支持“给我下一页”——自定义迭代器把分页细节藏起来，调用方只写一个 for。

**要点**：Kotlin 里的亲戚是 `Sequence` / `sequence { }`（懒求值流）。值得手写的信号：聚合结构特殊（游标/树/图）、或要惰性求值避免一次性载入。

**常见误用：遍历中修改集合**。迭代器把“怎么遍历”藏了起来，但没把“集合还能不能改”藏起来——`MutableList` 的迭代器是 fail-fast（快速失败）设计：迭代器创建时记下集合的版本号（modCount），每次 `next()` 前对一遍账，发现被改就抛 `ConcurrentModificationException`：

```kotlin
// 片段（已编译验证；运行抛 java.util.ConcurrentModificationException）
val ids = mutableListOf(1, 2, 3)
for (id in ids) {
    if (id == 1) ids.remove(id) // 遍历中改结构 → 迭代器对账失败立刻抛异常
}
```

但 fail-fast 是**尽力而为**不是保证——本机验证过的一个细节：删掉的如果是**倒数第二个元素**，`hasNext()` 恰好返回 false，循环自然结束，不抛异常，最后一个元素被静默跳过（`listOf(1,2,3)` 边遍历边删 2，得到 `[1, 3]` 且无异常）。所以正确做法不是“赌它抛异常”，而是**根本别在遍历中改结构**：删除用 `ids.removeIf { ... }`（JDK 8+ 内部自己管理遍历与修改），或先收集待删项、遍历完再删；跨线程共享的集合则必须加同步或改用并发容器——fail-fast 只适合当 bug 的哨兵，不适合当并发策略。

## 19. 中介者（Mediator）｜行为型

> 📂 可运行代码：[07a-示例-patterns/P19_Mediator.kt](07a-示例-patterns/P19_Mediator.kt)（购物车↔库存↔促销↔积分，网状变星型）

**意图**：用一个中介对象封装一组对象的交互，**网状依赖变星型**。

**场景**：加购联动购物车、库存、促销、积分。互调会织成网；引入中介者后每个组件只认识中介：加购 → 中介问库存（不足则协调回滚购物车）→ 促销试算 → 积分预告。新增联动只改中介一处。

**代价**：中介者自己会越长越胖（“上帝类”）——规则继续膨胀的下一步是流程编排/规则引擎。与外观的区别见第 15 节：**外观单向简化入口，中介者双向协调**。

## 20. 备忘录（Memento）｜行为型

> 📂 可运行代码：[07a-示例-patterns/P20_Memento.kt](07a-示例-patterns/P20_Memento.kt)（订单状态流转前拍快照，误操作逐级回滚）

**意图**：不破坏封装的前提下捕获对象内部状态，用于稍后恢复——撤销/回滚的基础设施。

**场景**：订单状态每次流转前拍快照；误标发货后一键回滚到上一状态、再回滚到创建态。

**与命令（第 17 节）互补**：命令记“做了什么动作”（撤销靠逆操作重放）；备忘录记“当时长什么样”（恢复靠快照，不依赖动作语义）。纪律：快照只交还给原对象解释，管理者只存取——否则“回滚”变成“任意篡改历史”。

## 21. 状态（State）｜行为型

> 📂 可运行代码：[07a-示例-patterns/P21_State.kt](07a-示例-patterns/P21_State.kt)（订单状态机：每状态一个 object，非法操作自带拒绝理由）

**意图**：状态驱动行为——同一调用在不同状态下行为不同。把每个状态的行为收进各自的类，替代“每个方法里一个巨型 when(status)”的**分支地狱**。

**场景**：订单状态机。支付/发货/取消 × 待支付/已支付/已发货/已取消：反例是 12 个分支散落三个方法；状态模式下每个状态一个 object，合法转换和拒绝理由内聚在自己家里，新增状态（如“退货中”）不动老状态。

**与策略（第 7 节）的区别**：策略由调用方从外部挑一个注入；状态由对象自己随流转切换。Kotlin 轻量替代是 sealed + when，但“状态自身带行为”时 OO 版职责更清晰。

## 22. 访问者（Visitor）｜行为型

> 📂 可运行代码：[07a-示例-patterns/P22_Visitor.kt](07a-示例-patterns/P22_Visitor.kt)（同一棵订单树跑财务/运营/客服三种报表）

**意图**：不改动元素类的前提下，为一族元素添加新操作（双分派）。

**场景**：订单树（单品/套装/赠品，延续第 14 节的组合结构）上跑三种报表：财务算实收、运营算赠品成本、客服导明细——三种报表 = 三个访问者，元素类零改动；再加报表仍零改动。

**选型口诀**：**操作常增、元素稳定 → 访问者**（新操作 = 新类）；**元素常增、操作稳定 → when + sealed**（编译器强制补全所有分支）。Kotlin 里后者更惯用；访问者保留给元素族真正稳定的场景（编译器 AST、报表内核）。代价：加新元素类型要改所有访问者。

## 23. 解释器（Interpreter）｜行为型

> 📂 可运行代码：[07a-示例-patterns/P23_Interpreter.kt](07a-示例-patterns/P23_Interpreter.kt)（风控规则表达式：AST 构建 + 递归求值）

**意图**：为一门小语言定义文法（表达式树）和求值器。业务中最常见的落地是**规则引擎**。

**场景**：风控规则由运营配置成表达式（“黑名单，或（VIP 且单笔超 5 万）转人工”），系统解析成 AST（本例手写树 + 递归求值；字符串→AST 的 parser 省略），对每笔订单求值。

**现实忠告**：别为业务手写完整解释器（分词/语法分析是另一个量级的工程），用现成引擎（Aviator / QLExpress / SpEL / Drools）。结构上它 = 组合模式的树 + 每节点一个求值类；规则可序列化入库、可视化编辑、热更新——营销平台/规则中心的内核都是它，23 个模式里离“平台化”最近的一个。

## 易混模式辨析：四组最容易张冠李戴的对

前 10 节里反复出现“结构一样、意图不同”的兄弟模式——结构相似是它们最容易误导人的地方，因为 code review 时看不出毛病，要害全在**意图**上。这一节把最易混的四组放在一起，每组给一组**可操作的判据**。先给总表：

| 易混组 | 一句话判据 | 决定性问题 |
|---|---|---|
| 策略 vs 状态 vs 命令 | 可换的族 / 随内部状态自动迁移 / 需要排队撤销重放 | 谁决定切换？要不要留下历史？ |
| 装饰器 vs 代理 vs 适配器 | 增强 / 控制 / 转接 | 接口同形吗？调用方知情吗？行为是叠加还是限制？ |
| 外观 vs 中介者 | 一对多简化入口 vs 多对象互解耦 | 谁单向谁双向？子系统之间互相认识吗？ |
| 模板方法 vs 策略 | 继承骨架填空 vs 组合可换步骤 | 骨架要不要锁死？步骤切换的粒度要多细？ |

### 策略 vs 状态 vs 命令：可换的族 / 自动迁移 / 请求对象化

三者的方法签名可以长得一模一样（一个方法、可替换的实现），判据在三个问题上：

- **策略**：调用方从外部**挑一个**注入，选完不迁移；“用哪个”是别人的决定（促销活动配置决定用哪个优惠算法）。
- **状态**：对象自己随内部状态**自动迁移**，“下一个状态是什么”写在状态内部，非法转换自带拒绝理由。
- **命令**：重点是**把请求存成对象**——为了排队、撤销、重放、审计；“执行”只是它的副作用之一。

对照片段（已编译运行验证，输出见注释）：

```kotlin
// 片段
fun interface Pricing { fun price(cents: Long): Long }

sealed interface OrderSt {
    data object Unpaid : OrderSt
    data object Paid : OrderSt
    fun pay(): OrderSt = when (this) {      // 状态自己决定去向
        Unpaid -> Paid
        Paid -> error("已支付，不能重复支付")
    }
}

class OpHistory {                            // 动作入栈，撤销才有依据
    private val undoStack = mutableListOf<() -> Unit>()
    fun run(action: () -> Unit, undo: () -> Unit) { action(); undoStack += undo }
    fun undoLast() { undoStack.removeLastOrNull()?.invoke() }
}

val vip = Pricing { it * 95 / 100 }          // 策略：外部挑选，用完即弃
var st: OrderSt = OrderSt.Unpaid
st = st.pay()                                // 状态：Unpaid → Paid；再调 pay() 抛"已支付，不能重复支付"

val addr = mutableMapOf("o1" to "旧地址")
val hist = OpHistory()
hist.run({ addr["o1"] = "新地址" }, { addr["o1"] = "旧地址" })  // 命令：执行后 addr=新地址
hist.undoLast()                              // 撤销后 addr=旧地址
```

记忆钩子：**策略是菜单点菜（你选），状态是人生阶段（时间推着走），命令是签过字的单据（留档可追）**。

### 装饰器 vs 代理 vs 适配器：增强 / 控制 / 转接

三个模式都是“包一层”，判定只看两个问题：**接口同形吗？包的人想干什么？**

```kotlin
// 片段（已编译运行验证）：同一个 StockPort，三种意图
interface StockPort { fun lock(sku: String, n: Int): Boolean }

class LegacyStock {                                   // 老系统：接口形状不同
    fun chkResv(skuId: Int, cnt: Int): Int = 0
}
class LegacyStockAdapter(private val legacy: LegacyStock) : StockPort {
    override fun lock(sku: String, n: Int) = legacy.chkResv(sku.toInt(), n) == 0
}   // 适配器：形状不对 → 转接（出发点就是"接口不同"）

class LoggingStock(private val next: StockPort) : StockPort by next {
    override fun lock(sku: String, n: Int): Boolean =
        next.lock(sku, n).also { println("[日志] lock($sku,$n)=$it") }
}   // 装饰器：形状相同 → 增强（调用方知情、主动叠加、可多层）

class GuardedStock(private val real: StockPort) : StockPort {
    override fun lock(sku: String, n: Int): Boolean {
        check(n in 1..999) { "越界数量，拒绝转发" }      // 控制发生在转发之前
        return real.lock(sku, n)
    }
}   // 代理：形状相同 → 控制（调用方无感，以为就是真对象）
```

三个模式与第 4/5/6 节的正篇对照阅读；再补一个判据角度：**装饰器可以叠 N 层，代理通常只有一层**——需要叠两层“控制”时，第二层多半该是装饰器。

### 外观 vs 中介者：单向入口 vs 双向协调

两者都“让复杂变简单”，方向完全不同：

```kotlin
// 片段（已编译运行验证）
class StockSvc { fun lock(orderId: String) = println("[库存] 锁定 $orderId") }
class CouponSvc { fun use(orderId: String) = println("[券] 核销 $orderId") }
class PointSvc { fun preview(orderId: String) = println("[积分] 预告 $orderId") }

// 外观：单向。外面调里面变简单；子系统互不知情，也不回头找调用方
class CheckoutFacade(private val stock: StockSvc, private val coupon: CouponSvc) {
    fun place(orderId: String) { stock.lock(orderId); coupon.use(orderId) }
}

// 中介者：双向。同事互不认识，协调逻辑（含失败回滚）长在中介身上
class CartColleague { val items = mutableListOf<String>() }
class StockColleague(private val lockOk: Boolean) { fun lock(sku: String): Boolean = lockOk }
class CartMediator(
    private val cart: CartColleague,
    private val stock: StockColleague,
    private val points: PointSvc,
) {
    fun addToCart(sku: String) {
        cart.items += sku
        if (!stock.lock(sku)) {              // 库存不足 → 中介负责回滚购物车
            cart.items.remove(sku)
            println("[中介] 库存不足，回滚购物车")
            return
        }
        points.preview(sku)                  // 成功 → 中介继续协调积分预告
    }
}
```

判据：**只有“外面 → 里面”一个方向的编排，是外观；对象之间要互相反应（A 的结果决定 B 回滚还是 C 继续），才需要中介者**。误把外观当中介者用，会让所有子系统反过来依赖门面——单向依赖被改成环。架构对应：外观 ≈ BFF/聚合服务（第 2 阶段），中介者 ≈ 流程编排器/规则引擎。

### 模板方法 vs 策略：继承骨架 vs 组合步骤

“流程固定、步骤多变”既可以用继承实现（模板方法），也可以用组合实现（策略/高阶函数）：

```kotlin
// 片段（已编译运行验证）：同一骨架的两种组织法
abstract class ReportSkeleton {
    fun run(orderId: String): String = render(query(orderId))   // 骨架 final 锁死在父类
    protected abstract fun query(orderId: String): List<String>
    protected abstract fun render(rows: List<String>): String
}

// 同一骨架的组合版：步骤是参数，换步骤 = 传不同 lambda，继承层次消失
fun runReport(orderId: String, query: (String) -> List<String>, render: (List<String>) -> String): String =
    render(query(orderId))
```

判据：**骨架必须“不可绕过”且变体数量有限（CSV/HTML/Excel 数得过来）→ 模板方法；步骤需要运行时自由拼装、变体开放（策略来自配置/插件）→ 组合**。模板方法的安全优势（final 锁流程）与策略的灵活优势（不靠继承）不可兼得——选定前先问“骨架是资产还是临时的”。

## Kotlin 让模式变轻（进阶）：四种“完整 GoF 结构”的轻量替代

第 0 节给过速查表；这里挑四个最值得掌握的替代写法展开成代码，并回答同一个问题：**什么时候仍然值得用完整 GoF 结构？**

### 1. sealed class + when 替代状态模式（对应第 21 节）

```kotlin
// 片段（已编译运行验证）：桶装水订单状态机
sealed interface WaterOrderStatus {
    data object PendingPay : WaterOrderStatus
    data class Paid(val payNo: String) : WaterOrderStatus
    data object Delivering : WaterOrderStatus
    data object Done : WaterOrderStatus
    data object Cancelled : WaterOrderStatus
}

fun WaterOrderStatus.onPay(payNo: String): WaterOrderStatus = when (this) {
    WaterOrderStatus.PendingPay -> WaterOrderStatus.Paid(payNo)
    else -> error("状态 $this 下不能支付")
}

fun WaterOrderStatus.canCancel(): Boolean = when (this) {
    WaterOrderStatus.PendingPay, is WaterOrderStatus.Paid -> true
    WaterOrderStatus.Delivering, WaterOrderStatus.Done, WaterOrderStatus.Cancelled -> false
}
```

红利在**编译期穷尽检查**：新增状态（如“退货中”）时，所有没写 `else` 的 `when` 全部编译报错，替代了“状态模式下新增状态要人工找全所有分支”。**什么时候回到完整状态模式**：状态多（7 个以上）且每个状态携带大量行为、状态本身要被注入替换（测试桩）、或转换规则要运行时可配置（流程引擎）——sealed + when 把转换集中在一处，状态类模式把行为分散到各家，规模一大后者正交性占优。

### 2. 函数类型替代命令模式（对应第 17 节）

```kotlin
// 片段：lambda 版命令——几行就是"可撤销操作"
data class Command(val name: String, val execute: () -> Unit, val undo: () -> Unit)
val audit = mutableListOf<Command>()         // 只能活在内存里：函数没有"形状"可入库
```

`execute`/`undo` 两个 lambda 就是一条可撤销命令（完整历史栈演示见“易混模式辨析”的 `OpHistory`）。**什么时候回到完整命令模式**：函数**序列化不了**——审计要落库、重放要跨进程、命令要进 MQ 时，函数类型没有“形状”可存。判据一句话：**命令只在内存里活 → 函数；命令要“出进程”（入库、上网络、进消息队列）→ 对象**。CQRS 的 Command 是对象，正因为它要被序列化、被分发。

### 3. `by` 委托替代装饰器（对应第 5 节）

接口级委托已在第 5 节/P05 演示（`: OrderHttpClient by delegate` 只写差异方法）；委托思想还能下沉到**属性级**：

```kotlin
// 片段（已编译运行验证）：属性委托——装饰器思想下沉到字段级
import kotlin.properties.Delegates

class OrderFsm {
    var status: String by Delegates.observable("CREATED") { _, old, new ->
        println("[可观测属性] 状态 $old → $new")   // status 赋值时打印：CREATED → PAID
    }
}
```

一行就给字段装上“监听”，相当于字段级观察者 + 装饰器。`by lazy`（第 2 节）同理——懒加载代理的字段版。**什么时候回到完整装饰器类**：组合层次需要运行时动态决定（按配置包 N 层）、或装饰器要作为接口实现传给别的消费者——`observable` 只能监听字段，覆盖不了接口级组合。

### 4. data class + copy 替代原型（对应第 12 节）

```kotlin
// 片段（已编译运行验证）
data class CardTpl(val title: String, val priceCents: Long, val tags: List<String>)

val tpl = CardTpl("大促卡", 9_900, listOf("热销"))
val card = tpl.copy(title = "第二张卡")       // 只改关心的字段，其余照抄模板
// card.tags === tpl.tags → true：copy 是浅拷贝，引用字段仍共享（陷阱与修法见第 12 节）
```

`copy` + 具名参数让“以模板为基准微调”零仪式感，GoF 的 Prototype 在 Kotlin 业务代码里基本退役。**什么时候回到完整原型**：构造过程有副作用（连接、注册回调）、私有状态无法通过 copy 暴露、或需要“原型注册表”提供统一 clone 入口给不认识具体类型的框架代码。

**进阶四条的共性**：轻量替代赢在“少一层间接”，GoF 完整结构赢在“结构可以被序列化、注入、运行时编排”。判据始终是同一条：**变化发生在编译期（写代码时定）→ 语言特性够用；变化发生在运行期（配置/插件/网络另一端决定）→ 完整结构**。

## 附 A：模式与 SOLID 的对应

| 模式 | 落地的原则 | 一句话 |
|---|---|---|
| 工厂方法 | DIP + OCP | 调用方依赖抽象，创建收拢一处 |
| 策略 | OCP | 新增算法不改使用方 |
| 装饰器 | OCP + SRP | 每个能力一个类，自由组合 |
| 适配器 | DIP（防腐） | 依赖我的抽象，不依赖它的接口 |
| 模板方法 | DIP（好莱坞原则） | 别调用我们，我们会调用你 |
| 观察者 | 低耦合 | 发布方不认识订阅方 |
| 责任链 | SRP | 一条规则一个处理单元 |

好莱坞原则（Don't call us, we'll call you）是 DIP 的行为版：控制流由框架（父类/框架代码）持有，你只填空位——模板方法、观察者、依赖注入容器都是它的化身。

## 附 B：选型速查（23 模式全图）

- 对象怎么**造**：工厂方法（收拢“造什么”）/ 抽象工厂（造一族配套件）/ 建造者（参数太多）/ 原型（克隆模板或昂贵构造）/ 单例（全局唯一）
- **结构**怎么搭：适配器（接口转换）/ 装饰器（叠加能力）/ 代理（控制访问）/ 外观（复杂子系统简入口）/ 桥接（两个维度各自扩展）/ 组合（叶子与容器同一接口）/ 享元（共享不可变部分省内存）
- **行为**怎么协作：策略（换算法）/ 模板方法（定骨架）/ 观察者（通知多方）/ 责任链（依次过滤）/ 命令（请求对象化：排队/撤销/审计）/ 状态（状态驱动行为）/ 中介者（网状变星型）/ 备忘录（快照恢复）/ 迭代器（隐藏遍历细节）/ 访问者（元素稳定、操作常增）/ 解释器（小语言求值，规则引擎内核）

易混对辨析：装饰器 vs 代理（叠加能力 vs 控制访问）｜工厂方法 vs 抽象工厂（造一个 vs 造一族）｜外观 vs 中介者（单向入口 vs 双向协调）｜命令 vs 备忘录（记动作 vs 记状态）｜策略 vs 状态（外部注入 vs 自行流转）

### 23 模式 × 学习优先级（三档）

| 档位 | 模式 | 为什么是这一档 |
|---|---|---|
| 必须精通（10 个） | 工厂方法、单例、建造者、适配器、装饰器、代理、策略、模板方法、观察者、责任链 | 业务代码与主流框架（Spring/OkHttp/Servlet/网关）中出现频率最高；且是后续架构模式的代码级根——防腐层是适配器、事件驱动是观察者的分布式版、网关插件链是责任链、RPC 桩是代理。code review 与面试的高频区，误用代价也最大（见各节“常见误用”）。 |
| 会用即可（8 个） | 抽象工厂、外观、命令、状态、中介者、备忘录、迭代器、组合 | 场景特征明显：遇到“成套创建”想到抽象工厂、“树形结构”想到组合、“撤销/审计”想到命令，能认出、能查到正确用法即可。其中外观、状态、命令较常出现在业务代码，组合是树形结构与规则引擎 AST 的地基，值得略多投入。 |
| 知道就行（5 个） | 原型、桥接、享元、访问者、解释器 | 价值在“认出”不在“常写”：原型被 data class + copy 部分替代；桥接的“拆维度”思想比结构本身常用；享元下沉进了池化与缓存基础设施；访问者被 when + sealed 替代居多；解释器只在规则引擎/AST 内核出现（用现成引擎，不手写）。 |

给自己定档的自测方法：拿不准某模式属于哪档，问一句“**最近一年，我在业务代码或框架源码里见过它几次真实使用（不是教程里的例子）**”——零次的就别先背它的类图。

## 附 C：在主流框架里认模式，从代码级放大到架构级

学模式的第二重收益是**读懂框架**：框架源码几乎每页都有模式，认出它们，API 的“为什么这样设计”就自己浮现；第三重收益是**认出架构的根**：很多架构级模式不是新发明，而是某个代码级模式被放大到进程间。两张表各管一头。

### C.1 主流框架/组件里的模式（认出信号）

| 框架/组件 | 里面的模式 | 认出信号 |
|---|---|---|
| Spring 容器 | 单例（默认 singleton scope）、工厂（BeanFactory/FactoryBean）、模板方法（JdbcTemplate 的 callback 空位）、观察者（ApplicationEvent/EventListener）、代理（@Transactional/@Async 的动态代理）、策略（AuthenticationManager 的多 Provider） | `getBean` 拿到的类不是你写的类（被代理了）；模板类总是配一个回调参数；`@EventListener` 注解对 |
| OkHttp / Netty | 责任链（Interceptor / ChannelPipeline）、装饰器（client 层层包装）、享元（连接池、ByteBuf 池）、代理（连接复用） | `chain.proceed(request)` 一层层穿过；`pipeline.addLast(...)` |
| Servlet / API 网关 | 责任链（Filter/Interceptor 链）、外观（网关统一入口）、代理（反向代理）、策略（路由匹配） | 配置里声明的 filter 顺序；网关 route 配置 |
| Kafka / RocketMQ | 观察者的分布式放大（发布订阅）、命令（消息 = 可持久化的请求对象）、中介者（broker 居中，生产消费双方互不认识） | 双方只认识 topic，不认识彼此 |
| Kotlin 标准库 | 单例（object / by lazy）、迭代器（for-in / Sequence）、建造者（StringBuilder、apply{} DSL）、装饰器（只读 List 视图包装）、原型（data class copy） | 只读接口包住可变集合；`by` 委托关键字 |

使用判据补一句：**框架替你实现了模式，不代表你可以随便依赖它的实现细节**——比如依赖“Spring 默认单例”往 bean 里塞可变字段，就是把框架行为当成了自己的设计依据（呼应第 2 节单例误用）。

### C.2 代码级模式 → 架构级模式的放大对照

| 代码级模式 | 放大到架构级成为 | 放大时补了什么 |
|---|---|---|
| 观察者（第 9 节） | 事件驱动架构 / 消息队列 | 异步化、持久化、重试、削峰、消费组 |
| 责任链（第 10 节） | API 网关插件链 / 中间件管道 | 链的配置化编排、按路由装配 |
| 代理（第 6 节） | RPC stub / 反向代理 / 服务网格 sidecar | 序列化、负载均衡、熔断重试 |
| 适配器（第 4 节） | 防腐层 / 系统集成边界 | 领域模型与外部模型的翻译层 |
| 外观（第 15 节） | BFF / 聚合服务 | 面向前端体验的裁剪与编排 |
| 命令（第 17 节） | CQRS 的 Command / 事件溯源的 Event | 可序列化、可审计、可重放 |
| 组合 + 解释器（第 14/23 节） | 规则引擎 / 低代码平台内核 | 表达式入库、可视化编辑、热更新 |
| 策略（第 7 节） | 可插拔组件 / 灰度路由 | 按配置或按流量特征动态挑选 |
| 状态（第 21 节） | 工作流引擎 / 订单状态机服务化 | 转换规则外部化、多实例共享流转 |
| 模板方法（第 8 节） | 框架-回调约定（好莱坞原则工程化） | 控制反转从类级放大到框架级 |

这张表是“学模式的架构师视角”的收口：**架构设计很少从零发明机制，多数是把某个被验证过的代码级协作方式放大到进程、服务、组织的尺度，并补上分布式带来的缺失件**（持久化、重试、一致性）。反过来读也成立——当你在一个架构方案里看到“通知多方”，先问它是不是观察者的放大、放大时补了什么、有没有补全，往往比直接套名词更能发现设计漏洞。

10. sealed + when 已经能替代状态模式（见“Kotlin 让模式变轻”第 1 条），列出两个你仍会写“每状态一个 object”完整状态类的条件，并说明 sealed 版在什么规模下开始吃亏。

13. 从“23 模式 × 学习优先级”表里挑一个“知道就行”档的模式，说清它降档的理由，以及出现什么信号时你会把它升档（项目里真的要用它了）。

17. 在主流框架里认模式（附 C.1）：Spring 的 @Transactional 靠动态代理、JdbcTemplate 是模板方法、ApplicationEvent 是观察者——挑两个说明框架这样设计的意图；再各给一个“业务代码不该跟着框架这么用”的信号。
18. 代理和外观都“替你藏细节”：RPC 客户端 stub 藏序列化与网络往返，BFF 藏多服务编排——从“接口形状是否相同、调用方是否知情、藏的是控制还是编排”三个角度辨析两者；再判断：API 网关属于哪个，还是两者叠加？说出叠加的部分各是什么。
