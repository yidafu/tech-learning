## 1. 理论基础

### 1.1 CAP：被普遍误读的"三选二"

**概念定义**：CAP 描述分布式系统在**网络分区（Partition）**发生时的三个属性：

| 字母 | 含义 | 场景化例子 |
|---|---|---|
| C（一致性） | 所有节点同一时刻看到同一份数据 | 库存、账户余额的所有副本都认为 sku=1001 只剩 2 件 |
| A（可用性） | 每个请求都能在合理时间内得到非错误响应 | 设备上报、IM 发消息总有响应，而不是报错或无限挂起 |
| P（分区容忍） | 节点间网络断开时系统仍能工作 | 物联网接入网关与数据管道之间、两地 IM 机房之间网络断了 |

**常见误读**：❌ "CAP 就是三选二，我们的系统选 CA。"

**修正理解**：✅ P 不是可选项。只要数据分布在多台机器上，网络分区**迟早**发生：物联网平台百万设备分布各地，网关与后端、机房与机房之间的链路断开是常态而非意外；IM 两地机房之间的光缆被挖断也不是新闻；甚至一次长 GC 在效果上也像分区。真正的取舍只发生在**分区期间**：要么拒绝写入保 C（牺牲 A），要么继续接受写入保 A（两侧数据暂时不一致）；**没有分区时 C 和 A 可以同时拥有**——Brewer 本人在 2012 年专门撰文澄清过这一点。

分区真的发生时，两类业务的选法相反：

- **支付扣款（支付与清结算）选 C**：宁可让付款页报"系统繁忙"，也不能出现两份成功扣款。钱相关的数据通常倾向 CP。
- **设备数据上报（物联网平台）选 A**：接入层照常收数据，分区恢复后按事件时间去重、对账收敛。设备端本来就有弱网重传，"先收下来慢慢收敛"是常态，价值密度低的时序数据经得起秒级延迟。

⚠️ 再强调：不要给整个系统贴 CAP 标签。CAP 描述的是**单个数据副本组在一次分区中的行为**——同一个物联网平台里，指令下发模块可以是 CP（宁可不发，不能发错发重），时序数据模块可以是 AP。

**理论来源：从工程直觉到"定理"**。CAP 不是凭空掉下来的公理，它走过一条"实践总结 → 猜想 → 形式化证明 → 作者本人纠偏"的路：

| 时间 | 事件 | 一句话要点 |
|---|---|---|
| 1998~1999 | Brewer（UC Berkeley 教授、Inktomi 联合创始人）经营大规模集群服务时总结出这一权衡（与 Fox 合著 Harvest/Yield 论文） | 出身工程实践，最初是经验之谈 |
| 2000 | PODC（分布式计算原理大会）主题演讲 *Towards Robust Distributed Systems* | 正式以**猜想**形式提出"一致性、可用性、分区容忍不可兼得"，讲稿只有寥寥数页幻灯片 |
| 2002 | MIT 的 Gilbert & Lynch 发表 *Brewer's Conjecture and the Feasibility of Consistent, Available, Partition-Tolerant Web Services* | 把三个性质形式化，在**异步网络模型**下证明猜想成立；2010 年修订后重刊于 CACM，"CAP 定理"由此得名 |
| 2012 | Brewer 撰文 *CAP Twelve Years Later: How the "Rules" Have Changed* | 亲自纠偏："三选二"是误导，无分区时 C、A 可兼得；分区期间更好的策略是记录冲突、分区恢复后补偿收敛，而非简单弃 A |
| 2015 | Kleppmann 发表 *Please Stop Calling Databases CP or AP* | C、A 是**单个操作**的属性，给整个数据库贴 CP/AP 标签没有意义——正是上文"不要给系统贴标签"的理论依据 |

**形式化定义**（Gilbert & Lynch 的原始定义比日常口语严格，常见的坑都出在这里）：

| 字母 | 形式化定义 | 与日常口语的偏差 |
|---|---|---|
| C | **单对象**上的原子一致性（atomic，即线性一致）：所有读写表现得像按某个全局顺序逐个执行，且符合实时先后 | 日常说的"数据一致"常混入"多表/多对象事务一致"——CAP 不覆盖后者，那是分布式事务（第 4 节）的领地 |
| A | **完全可用**：到达任何非故障节点的请求**最终**得到非错误响应 | 定义只承诺"最终响应"，阻塞 30 秒再答也算 A；工程说的"高可用/低延迟"是更强的要求（于是有了下方的延迟维度扩展） |
| P | 网络可以任意丢消息、无限延迟（直到分区愈合） | 不是"容忍偶尔丢包"，而是假设节点间通信可能**任意长时间**中断——这正是"P 不可选"的原因：只能假设它会发生 |

**证明直觉**（异步模型，两个节点就够）：分区期间 G1 收到写请求、G2 收到读请求，两边无法通信。若 G2 必须立刻响应（保 A），它无法证明自己拿到的是最新值（弃 C）；若 G2 憋住不答、等分区恢复再对齐（保 C），请求就无限挂起（弃 A）。异步模型里节点分不清"对方宕机"和"链路断了"，这个二选一无处可逃；部分同步模型下结论稍弱：三者兼得的系统在分区愈合的收敛过程中，仍必然出现违反 C 或 A 的窗口。

**PACELC（2010，Abadi）：把 CAP 从"灾备时刻"扩展到"平时"**。CAP 只回答了分区那一小段时间的取舍；可系统 99.99% 的时间没有分区，平时的权衡是**延迟（Latency）vs 一致性（Consistency）**：

> 分区时（P）在 A/C 里二选一；无分区时（E）在延迟/一致性里二选一。

- **PC/EC**：分区时弃 A，平时同步复制保 C——etcd/ZooKeeper、支付收款主库（宁慢三分，不错一笔）。
- **PA/EL**：分区时弃 C，平时异步复制换低延迟——Dynamo、Cassandra 默认配置、Feed 计数、物联网时序、MES 看板聚合。
- 同一系统内混用是常态：支付与清结算里，收款流水 PC/EC，商户经营报表 PA/EL——取舍粒度仍然是"单个数据副本组"。

### 1.2 BASE：AP 路线的工程化契约

BASE 是对"分区期间选 A"的工程化补充（对 ACID 的妥协）：

| 字母 | 含义 | 场景化例子 |
|---|---|---|
| Basically Available（基本可用） | 损失部分可用性换生存：限流、降级、响应变慢 | 秒杀时下单排队、推荐位返回兜底商品；Feed 热搜降级为分钟级更新 |
| Soft state（软状态） | 允许存在中间状态 | 支付单停在"支付中"等渠道回调；分账单"分账处理中" |
| Eventually consistent（最终一致） | 停止写入后，经过一段时间副本收敛一致 | 支付成功几秒后，发货指令、分账、积分才陆续看到该事件；MES 看板聚合延迟秒级 |

**一句话关系**：CAP 是理论判断（分区时必弃其一），BASE 是选 A 之后的工程纪律（接受软状态，但必须保证收敛，且收敛过程要有对账与补偿，见 4.5）。

### 1.3 一致性模型：强一致 / 最终一致

**强一致（线性一致）**：任何读都能读到最近一次写的结果，系统表现得像只有一份数据。实现代价高：要么单点串行（单库事务），要么依赖共识算法（1.4）同步复制。
**最终一致**：停止写入后，经过一段时间所有副本收敛到相同状态；期间不同节点可能读到不同版本。

一致性不是二值，而是一个光谱：读己之写（自己写完自己一定能读到）、单调读（不会越读越旧）、因果一致（先问后答的顺序保留）……工程上常按"会话保证"逐条承诺，而非全有或全无。

两类业务的典型选型：

- **必须强一致**：支付扣款——同一笔交易绝不能出现两份成功；秒杀扣库存——不能超卖。
- **接受最终一致**：Feed 时间线——发帖后粉丝几秒内才刷到完全无妨；MES 生产看板——各工序报工聚合出"今日产量"，秒级延迟不影响决策。

**反例**：❌ 把整条链路做成同步强一致——桶装水商城下单：同步扣库存 → 同步核销优惠券 → 同步算配送线路 → 同步记押金 → 同步发短信，任何一环失败整体回滚。延迟逐级叠加，可用性相乘（4 个 99.9% 的服务串起来只剩约 99.6%），改一处通知逻辑要动下单代码。

**修正**：✅ 分层取舍——

| 环节 | 一致性要求 | 手段 |
|---|---|---|
| 支付扣款、余额/额度冻结 | 强一致（不能凭空扣钱、不能两份成功） | 数据库事务 / 共识 / TCC |
| 秒杀库存扣减 | 强一致（不能超卖） | Redis + Lua 原子预扣，DB 乐观锁兜底（3.1） |
| 订单/支付单状态流转 | 读己之写 + 最终一致 | 主从复制、状态机 + 消息驱动（4.5） |
| Feed 时间线、MES 看板、积分、通知 | 最终一致（秒级延迟可接受） | 本地消息表 + MQ |

### 1.4 共识算法：Raft 为主，了解 Paxos

**要解决的问题**：多个节点如何对"下一个值是什么"达成一致，且少数节点宕机、网络分区时不出错。这是实现强一致存储（如 etcd、TiKV）的底座。多数派是关键：**2f+1 个节点可容忍 f 个故障**，因为任意两个多数派必然相交，已提交的值不会丢。

**Paxos（了解细节，重点看它为什么"长这样"）**：经典共识算法，角色分为 Proposer（提案者）/ Acceptor（表决者）/ Learner（学习者），通过 **Prepare → Promise、Accept → Accepted** 两阶段对**单个值**（single decree）达成一致。完整可运行模拟见 [章节3/cap-algorithms/](cap-algorithms/)：

```kotlin
// —— 单个值的 Paxos 核心：每个 Acceptor 只记两样东西 ——
class Acceptor(val id: Int) {
    var promisedN = 0L                        // 已承诺的最大提案号：不再接受编号更小的提案
    var accepted: Pair<Long, String>? = null  // 已接受的最大编号提案 (n, value)

    fun prepare(n: Long): Boolean =           // Phase 1：Promise（承诺 + 带回已接受的旧值）
        if (n >= promisedN) { promisedN = n; true } else false

    fun accept(n: Long, value: String): Boolean =     // Phase 2：Accept
        if (n >= promisedN) { accepted = n to value; true } else false
}

// —— Proposer：二阶段的值不许自作主张 ——
fun propose(n: Long, selfValue: String, acceptors: List<Acceptor>): String? {
    val granted = acceptors.filter { it.prepare(n) }              // Phase 1 收 Promise
    if (granted.size <= acceptors.size / 2) return null           // 没拿到多数派承诺，换更高编号重试
    // ⚠️ 关键：只要任何一个 Promise 带回了已接受的旧值，就必须放弃自选值改用它
    val carried = granted.mapNotNull { it.accepted }.maxByOrNull { it.first }?.second
    val value = carried ?: selfValue
    val acks = granted.count { it.accept(n, value) }              // Phase 2 发 Accept
    return if (acks > acceptors.size / 2) value else null         // 多数派接受 → 值被"选定"
}
```

三条关键不变量（Paxos 的全部安全性都藏在这里）：

1. **提案号全局唯一且全序**（如"轮次计数 + 节点 ID"拼位），谁大谁说了算。
2. **Promise 是承诺**：Acceptor 承诺不再接受编号更小的提案，并**带回它已接受的最高编号值**——这保证已被多数派接受的值不会被后来者换掉。
3. **Proposer 必须沿用旧值**：二阶段提的值只能是 Promise 里编号最大的那个旧值；只有没人接受过值时才能用自选值。于是：一旦某值被多数派接受，之后所有提案提的都是同一个值，Learner 学到的值唯一。

**活锁**：两个 Proposer 交替抬高提案号——A 的 Accept 还没落地，B 的更高号 Prepare 已把 Acceptor 的承诺抢走，A 失败、加号重试、又抢走 B 的……理论上永远选不定。**工程解法就是 Multi-Paxos 的稳定 Leader**：选出一个 Leader 独占提案权后，后续提案省掉 Phase 1 只走 Phase 2（两阶段压成一阶段）。Raft 用选举一步到位实现了同样的事——**Prepare ≈ 选举**（"你日志比我新我就服你"）、**Accept ≈ 日志复制**；Paxos 对每个日志位独立跑一次共识，Raft 用"日志连续 + 只认最新 Leader"把它串成流水线，这就是"为可理解性设计"的落点。正确但极难理解、更难实现正确，于是有了 Raft。

**Raft 主流程**：把共识分解为三个子问题——Leader 选举、日志复制、安全性。所有写请求都经过 Leader。

```kotlin
// —— 选举：随机超时把"瓜分选票"的概率压到极低 ——
enum class Role { FOLLOWER, CANDIDATE, LEADER }

class RaftNode(val id: Int, val peers: List<RaftNode>) {
    var role = Role.FOLLOWER
    var currentTerm = 0          // 任期，单调递增，是 Raft 的"逻辑时钟"
    var votedFor: Int? = null    // 本任期投给谁（一任一票）
    var commitIndex = -1         // 已提交（已复制到多数派）的最高日志下标
    val log = mutableListOf<Pair<Int, String>>()   // (term, command)

    fun startElection() {                       // 选举超时（如 150~300ms 随机）未收到心跳
        role = Role.CANDIDATE
        currentTerm += 1
        votedFor = id                           // 先投自己
        val votes = peers.count { it.grantVote(currentTerm, id, log.lastIndex()) } + 1
        if (votes > peers.size / 2) role = Role.LEADER   // 拿到多数派即当选
    }
}

// —— 日志复制：一条"账户扣款"命令的旅程 ——
fun replicate(leader: RaftNode, command: String): Boolean {
    leader.log += leader.currentTerm to command                  // 1. Leader 先追加本地日志（未提交）
    val acks = leader.peers.count { it.appendEntries(leader) } + 1
    return if (acks > leader.peers.size / 2) {                   // 2. 并行发给 Follower，复制到多数派
        leader.commitIndex = leader.log.lastIndex()              // 3. 达到多数派才"提交"
        applyToStateMachine(command)                             // 4. 应用到状态机后才响应客户端
        true
    } else false
}
```

记住三条就够面试和设计用了：

1. **选举**：Follower 随机超时未收到心跳 → 升任 Candidate、term+1、拉票；多数派同意则成为 Leader；一任一票 + 随机超时避免选举活锁。
2. **复制**：命令先写 Leader 本地日志，AppendEntries 并行同步 Follower，**提交条件是复制到多数派**；Follower 日志与 Leader 冲突时被强制覆盖成 Leader 的（日志匹配特性）。
3. **安全**：选举时只有拥有"最新日志"的节点能赢（比较最后一条日志的 term 和 index），所以旧 Leader 脑裂成少数派时无法提交任何日志——已提交的数据绝不丢失。

**工程补丁（真实实现绕不开的四个细节）**：

1. **提交规则（"图 8 问题"）**：Leader 只能靠**当前任期**的日志推进 commitIndex——旧任期日志即使已复制到多数派，也不能直接判定已提交（它可能随新 Leader 当选被覆盖），只能夹在新日志里"搭车"提交。防止的事故：旧 Leader 脑裂期间把某条日志复制到了多数派但未响应客户端，新 Leader 上台把它覆盖掉——若按"复制到多数派即提交"就会丢掉一条"曾经算数"的日志。
2. **PreVote**：被网络隔离的 Follower 反复选举超时、term 疯涨，重新连上后用巨大的 term 把正常集群的 Leader 顶翻。PreVote 让节点先"试探拉票"（不涨 term），确认能联系上多数派才真正开始选举——把"隔离节点的歇斯底里"挡在门外。
3. **线性一致读**：读也走日志复制太贵。ReadIndex——Leader 先向多数派确认"我仍是 Leader"，再读本地状态机返回；Leader Lease——靠租约期内时钟上界保证身份有效，免确认直接读。读己之写也要走 ReadIndex（客户端的读可能落在已被替换的旧 Leader 上）。
4. **快照与成员变更**：日志不能无限增长，定期快照 + 丢弃已快照前缀；扩缩容改成员组要走两阶段联合一致（joint consensus），避免新旧配置两个"多数派"各选出一个 Leader。

一句话对照：ZooKeeper 的 ZAB 与 Raft 同属多数派共识家族（ZXID 的 epoch ≈ term）；etcd/Consul 用 Raft，TiKV 用 Multi-Raft（按 key range 切成多个 Raft 组并行）。

### 1.5 Quorum 与 NWR：CAP 的连续旋钮

共识算法（1.4）给的是"非黑即白"的强一致，但很多业务要的是**中间档位**：比最终一致更稳，又不想每次写都等多数派同步复制。Quorum 机制把 CAP 的二选一变成可调参数：

- **N**：每个数据的副本数；**W**：写成功要求至少确认的副本数；**R**：读成功要求至少响应的副本数。
- **强一致的充分条件：W + R > N**——写集合与读集合各自过半、必然相交，交集中的副本带着最新版本，读时取版本最高的那份。
- **W > N/2**：两次写的集合也必然相交，写冲突才有"先后"可言。

典型档位（Cassandra/Dynamo 风格，N=3）：

| 配置 | 行为 | CAP 位置 | 场景 |
|---|---|---|---|
| W=1, R=1 | 一个副本确认即成功，最快 | AP：分区两侧都能写读 | 物联网时序上报、Feed 计数 |
| W=2, R=2（QUORUM/QUORUM） | 读写都过半、集合必相交 | 偏 C：分区少数派侧写不进 | 商品库存、订单状态 |
| W=3（ALL） | 全部副本确认才成功 | CP 极端：任一副本失联即不可写 | 极少用——可用性太脆 |

**反例**：❌ "我们配了 QUORUM，所以系统强一致。"——Quorum 只是**副本数门槛**，一致性还取决于**谁接受写**：

- **单写者 + R+W>N**（所有写经同一个 Leader 串行定序）：可达线性一致。这正是共识算法的本质——**共识 = Quorum 复制 + 唯一 Leader + 日志定序**（对照 1.4 的 Raft）。
- **多写者**（Dynamo 风格，任意副本都能接受写）：R+W>N 只保证读到"最新已确认版本"，两个并发写仍可能在交集中留下分叉——需要冲突处理：向量时钟判定并发、last-write-wins 按时间戳粗暴取舍（可能丢写！）或 CRDT 合并（见 1.6）。

**分区期间**：W=N 的写在少数派侧凑不齐确认 → 拒绝写（弃 A 保 C）；W=1 则两侧照写，愈合后按版本合并收敛（弃 C 保 A）——CAP 的取舍在这里被调成了参数。完整可运行演示（含丢写场景）见 [章节3/cap-algorithms/](cap-algorithms/)。

### 1.6 Gossip 与 CRDT：AP 路线的收敛引擎

分区期间选 A（各写各的）只是第一步，BASE 真正的难点是 1.2 里那句"停止写入后副本收敛一致"**靠什么收敛**。AP 世界的两个答案：Gossip 负责"怎么把新值传开"，CRDT 负责"怎么把冲突合掉"。

**Gossip 协议**：每个节点周期性随机挑几个邻居交换信息，像传八卦一样把更新扩散到全集群。三种手段按可靠性/开销递进：

| 手段 | 做法 | 特点 |
|---|---|---|
| Direct mail（直接通知） | 写入时顺手把更新推给其他节点 | 一步到位，但丢一条就漏一洞，只配当加速器 |
| Anti-entropy（反熵） | 周期性两两比对版本、补齐差异；方向分 push / pull / push-pull | 最可靠，是收敛的兜底；push-pull 收敛最快 |
| Rumor mongering（谣言传播） | 新消息像热点谣言传几轮，"过了新鲜期"就不再主动发 | 给反熵省流量——热点消息不必每轮全量比对 |

**收敛速度**：push-pull 每轮让"知情 × 不知情"的配对双方都变为知情，知情数近乎翻倍，约 **O(log n)** 轮收敛——10 个节点三四轮，1000 个节点十轮上下。代价是没有一致性的时点保证：任意时刻读任意节点，可能读到几轮之前的旧值——这正是"最终一致"里"最终"二字的含义。

**现实应用**：Cassandra 的集群成员与故障检测（Phi Accrual 疑似度计分）、Consul/Serf 的 memberlist、Redis Cluster 的拓扑传播、Dynamo 的元数据同步，全是 Gossip；Eureka 的对等节点复制同理（呼应 5.4 注册中心的 AP 选型）。

**CRDT（Conflict-free Replicated Data Type，无冲突复制数据结构）**：Gossip 只负责"传"，两个副本各自改了同一份计数器怎么合？CRDT 把收敛性做进数据结构本身——只要 merge 满足**交换律、结合律、幂等**，无论消息乱序、重复、从哪个方向合，所有副本最终收敛到同一值，**不需要人工裁决冲突**：

```kotlin
// G-Counter：只增计数器。每个副本只改自己那一格，merge = 逐格取 max
class GCounter(val replicas: Int) {
    private val counts = LongArray(replicas)              // counts[i] = 副本 i 自己累加的量
    fun increment(replica: Int, by: Long = 1) { counts[replica] += by }   // 只写自己的格
    val value: Long get() = counts.sum()
    fun merge(other: GCounter) {                          // max：交换 + 结合 + 幂等
        for (i in 0 until replicas) counts[i] = maxOf(counts[i], other.counts[i])
    }
}
```

`max` 天然满足三条性质：`max(a,b)=max(b,a)`（交换）、`max(max(a,b),c)=max(a,max(b,c))`（结合）、`max(a,a)=a`（幂等）——乱序、重复收到同一次同步都无害。常用变体：PN-Counter（两个 G-Counter 相减，可增可减）、LWW-Register/Set（带时间戳取新）、OR-Set（增删无歧义的集合）；分布式计数、协作编辑、会话列表合并都在用。一句话对照：**物联网时序去重、支付对账（4.5）是应用层的收敛；CRDT 把同样的收敛下沉为数据结构的数学性质**。

## 2. 远程通信

### 2.1 REST vs gRPC vs 消息 + 物联网多协议接入

**内部服务间选型**（以桶装水商城拆出的微服务为例）先看这张表：

| 维度 | REST | gRPC | 消息（MQ） |
|---|---|---|---|
| 协议/格式 | HTTP/1.1 + JSON | HTTP/2 + Protobuf | AMQP/Kafka 私有协议 |
| 通信模式 | 请求-响应（同步） | 同步 + 四种流式 | 异步、单向 |
| 性能 | 文本序列化，体积大、较慢 | 二进制 + 多路复用，快 | 吞吐高，但有延迟 |
| 契约 | OpenAPI（弱约束） | .proto 强类型 IDL，代码生成 | 消息 schema（可选） |
| 耦合 | 调用方知道对方地址和接口 | 同左，但有版本化工具 | 生产者只发事件，不知道谁消费 |
| 典型场景 | 对外 API、BFF、低频管理接口 | 内部高频服务调用、跨语言 | 事件广播、削峰、异步解耦 |

**选型原则**（桶装水商城落地）：对外——小程序/H5 的商品、下单 API 用 REST（通用、可 curl 调试、网关生态友好）；内部——下单服务到库存服务的高频同步预扣用 gRPC（省流量、低延迟、.proto 契约清晰）；旁路——下单成功后通知配送排线、记押金流水、发短信，不需要立刻知道结果，一律上消息。

**反例**：❌ 下单成功后同步串起所有旁路：

```kotlin
// ❌ 同步长链：短信网关挂 30 秒，整个下单就挂 30 秒
fun placeOrder(cmd: PlaceOrderCmd) {
    orderRepo.create(cmd)
    inventoryClient.deduct(cmd.skuId, cmd.qty)
    couponClient.use(cmd.couponId)          // 每一步都是一次网络往返
    depositClient.record(cmd.userId, cmd.deposit)   // 押金流水也要此刻记完？
    smsClient.notify(cmd.userId)            // 短信网关一抖，用户下单失败
}
```

**修正**：✅ 交易核心同步（gRPC 调库存），旁路异步（发一条 `order.created` 事件，押金/排线/积分/短信各自订阅）：

```kotlin
// ✅ 核心同步、旁路异步：下单只依赖真正决定成败的两步
fun placeOrder(cmd: PlaceOrderCmd) {
    val orderId = orderRepo.create(cmd)                 // 本地事务：订单落库 + 消息出站记录（见 4.5）
    inventoryClient.deduct(cmd.skuId, cmd.qty)          // gRPC 同步：扣库存必须此刻有结论
    outbox.publish("order.created", OrderCreated(orderId, cmd.userId))
}   // 押金/排线/短信由各自消费者订阅 order 生命周期事件，失败重试互不影响下单
```

**外部设备接入：多协议适配层（物联网平台）**。平台面对的不只是自己的服务，还有百万台设备：水表走 MQTT、老款电表走厂商私有 TCP、低功耗传感器走 CoAP（UDP）、售水机走 HTTP——报文格式各异，且**明天还会接入新协议**。❌ 反例：把每种协议的解析逻辑写进接入网关主流程，每接一批新设备改一次网关代码、全量回归。✅ 修正：协议适配层 + 编解码器插件化——**开闭原则的硬件版**：

```kotlin
// ✅ 网关只认统一的内部模型；每种协议一个编解码器，新增协议 = 注册新插件，网关零改动
interface ProtocolCodec {
    val scheme: String                                        // "mqtt" / "coap" / "tcp-vendor-a" / "http"
    fun decode(raw: ByteArray, meta: ConnMeta): DeviceUplink // 各协议报文 → 统一上行模型
    fun encode(cmd: DownlinkCommand): ByteArray               // 统一下行指令 → 各协议报文
}

class ProtocolGateway {
    private val codecs = mutableMapOf<String, ProtocolCodec>()
    fun register(codec: ProtocolCodec) { codecs[codec.scheme] = codec }   // 新厂商协议即插即用

    fun onMessage(raw: ByteArray, meta: ConnMeta) {
        val codec = codecs[meta.scheme] ?: throw UnknownProtocolException(meta.scheme)
        pipeline.accept(codec.decode(raw, meta))
        // MQTT 的 JSON、私有 TCP 的二进制、CoAP 的 CBOR……到这一行全变成了同一种 DeviceUplink
    }
}
```

这与第二阶段六边形架构的防腐层是同一个思想：**把"协议差异"挡在核心之外**，核心只面对统一模型。指令下发同理（encode 反向走一遍）。

### 2.2 序列化协议

序列化决定了每一次跨进程调用的体积与耗时，是"看不见的性能"：

| 协议 | 格式 | 体积 | 速度 | Schema | 可读性 | 典型场景 |
|---|---|---|---|---|---|---|
| JSON | 文本 | 大 | 慢 | 弱（可配 JSON Schema） | 好 | REST、日志、配置 |
| Protobuf | 二进制 | 小（约为 JSON 的 1/3~1/5） | 快 | 强 IDL | 差 | gRPC、存储通信 |
| Avro | 二进制 | 小 | 快 | 强且"读写各自 schema" | 差 | Kafka、数据仓库 |

同一个平台两副面孔：

- **设备上行报文（IoT）**：一台设备秒级多条 × 百万台，一条水位读数的 JSON 约 120 字节，Protobuf/CBOR 紧凑二进制压到 20~40 字节——带宽与解析 CPU 同时降一个量级，弱网下还省电省流量。
- **工单/订单管理 API**：人来调试、跨团队协作、字段低频演化——JSON 可读可 curl，弱约束反而是优点。

**两条纪律**：

1. **兼容性演化**：Protobuf 加字段没问题，但**绝不能改字段编号、不能复用已删字段的编号**——老消费者会按编号把新数据读成完全错误的类型。JSON 加字段天然兼容，这是它在外部 API 上长盛不衰的原因。
2. **禁止 Java/Kotlin 原生序列化**（`Serializable`）：体积大、慢、跨语言失败，且反序列化漏洞是经典攻击面。

## 3. 数据架构

### 3.1 缓存体系：多级缓存、Redis、穿透 / 击穿 / 雪崩（秒杀 + 桶装水商城）

**多级缓存**（秒杀是教科书场景）：CDN/页面静态化（商品详情页提前渲染成静态 HTML 推到边缘节点，活动开始后大多数刷新根本到不了源站）→ 本地缓存（Caffeine，进程内零网络开销，放极热的秒杀活动信息，容忍秒级旧数据）→ Redis（集中式、容量大，放商品详情与库存计数）→ MySQL。桶装水商城则是典型**读多写少**：商品浏览量远大于下单量，读几乎全被缓存挡住，写（扣库存）走库。

**Cache-Aside 读写模式**（最常用）：读——先缓存、未命中查库并回填；写——**先更新库，再删除缓存**（不是更新缓存：并发写下更新缓存容易把旧值写回去，而删除让下次读触发回源，天然懒加载）。

**三大经典问题**，先分清现象再谈方案：

| 问题 | 触发条件 | 现象 |
|---|---|---|
| 穿透 | 请求的 key **根本不存在**（黄牛拿随机 skuId 试探） | 缓存永远无法命中，请求全部落到 DB |
| 击穿 | **单个热点 key 过期的瞬间**，海量并发同时回源 | 秒杀 sku 缓存过期 → DB 瞬间被该 key 的回源流量打挂 |
| 雪崩 | **大批 key 同时过期**，或 **Redis 整体宕机** | DB 被全面冲垮，故障面是全部 key |

**穿透：反例与修正**：

```kotlin
// ❌ 反例：不存在的 skuId 每次都穿到数据库
fun getSku(skuId: String): Sku? {
    redis.get("sku:$skuId")?.let { return deserialize(it) }
    return skuRepo.findById(skuId)     // 脚本拿 99999999 这类不存在的 id 高频请求 → 全部落库
}

// ✅ 修正：布隆过滤器前置挡"肯定不存在"，空值缓存挡"刚查过确实没有"
fun getSku(skuId: String): Sku? {
    if (!bloomFilter.mightContain(skuId)) return null      // 布隆说没有 → 一定没有，不用查库
    return when (val v = redis.get("sku:$skuId")) {
        NULL_SENTINEL -> null                               // 命中空值缓存，直接返回"不存在"
        null -> skuRepo.findById(skuId)?.also {
            redis.setex("sku:$skuId", 3600, serialize(it))
        } ?: redis.setex("sku:$skuId", 60, NULL_SENTINEL).let { null }   // 空值也要缓存，TTL 短
        else -> deserialize(v)
    }
}
```

**击穿：singleflight 互斥回源**（同一 key 只放一个请求去重建）：

```kotlin
// ✅ 热点 key 失效瞬间，只允许一个请求查库重建，其余等它写回后读缓存
fun getSeckillStock(skuId: String): Int {
    redis.get("stock:$skuId")?.let { return it.toInt() }
    return mutexGuard(key = "lock:stock:$skuId", waitMs = 200) {    // 拿到锁的少数人回源
        redis.get("stock:$skuId")?.toInt() ?: reloadAndCache(skuId) // 双重检查：等锁期间可能已被重建
    } ?: throw BusyException()                                      // 等锁超时：快速失败而非压垮 DB
}
```

更省心的替代：**逻辑过期**——key 不设 TTL，value 里带过期时间戳，读到过期就返回旧值并异步触发重建，业务永远不被回源阻塞。

**雪崩：组合拳**——TTL 加随机抖动错开过期时间、Redis 哨兵/集群保高可用、多级缓存（Redis 挂了还有本地缓存顶着）、回源路上加限流熔断兜底：

```kotlin
// ✅ 过期时间加随机抖动，避免同一批预热 key 在同一秒集体失效
redis.setex(key, 3600 + Random.nextInt(0, 600), value)
```

**秒杀防超卖：Redis + Lua 原子预扣**。库存扣减必须"读—判断—写"原子完成，先 GET 再 DECR 的两步写法在并发下必超卖：

```kotlin
// ❌ 反例：GET 与 DECR 之间有间隙，两个请求都读到"还剩 1 件"，各扣一次 → 超卖
// ✅ 修正：Lua 脚本在 Redis 内原子执行"判断 + 扣减"
val DEDUCT_LUA = """
    local stock = tonumber(redis.call('GET', KEYS[1]) or '-1')
    if stock < tonumber(ARGV[1]) then return -1 end      -- 不够：拒绝，不再碰库存
    return redis.call('DECRBY', KEYS[1], ARGV[1])        -- 够：一步扣掉
""".trimIndent()

fun preDeduct(skuId: String, qty: Int, reqId: String) {
    val left = redis.eval(DEDUCT_LUA, listOf("seckill:stock:$skuId"), listOf("$qty")) as Long
    if (left >= 0) {
        mq.send("seckill.deducted", Deducted(skuId, qty, reqId))   // 预扣成功 → MQ 异步落库建单（削峰）
    } else {
        throw SoldOutException(skuId)                              // 已抢完，快速失败
    }
}
// Redis 只是"预扣"：真实库存以 DB 为准，消费侧用乐观锁兜底，防 Redis 与 DB 漂移
```

**热点 key 拆分**：100 万请求打同一个 `seckill:stock:1001`，Redis 集群里这个 key 只能落在单个分片上。可把库存拆成 N 个子 key（`stock:1001:0` ~ `stock:1001:9`），请求随机路由到一个子 key 扣减、汇总校对——单分片压力除以 N。

### 3.2 读写分离、分库分表（Feed 流 + 桶装水订单）

**读写分离**：写走主库，读走从库，主从异步复制分担读压力。代价是**复制延迟**（毫秒到秒级）。

❌ 反例：用户刚发完帖立刻刷新个人主页，请求被路由到还没复制完的从库 → 帖子"消失" → 以为发布失败又发一遍。
✅ 修正：**读己之写**——写后若干秒内该用户的读强制走主库（网关按 userId 打标），或前端用写接口回带的快照渲染。

**分库分表**：Feed 流是天然推手——用户与发帖量持续增长，单库的时间线表迟早放不下；桶装水商城订单量从日均几千涨到几十万也是同一条路。垂直分库（按业务拆：内容库/关系库/互动库）+ 水平分片（按分片键把行散到多库多表）。核心决策是**分片键**：

```kotlin
// ✅ Feed 时间线、桶装水订单表都以 user_id 为分片键（"刷我的时间线/查我的订单"是最高频查询）
fun shardOf(userId: Long): Pair<String, String> {
    val db = "feed_db_${(userId % 4).toInt()}"             // 4 个库
    val table = "timeline_${((userId / 4) % 8).toInt()}"   // 每库 8 张表
    return db to table
}
```

❌ 反例：Feed 按 `post_id` 分片，用户刷自己时间线时没有 post_id，只能**全库全表扫描**。
✅ 修正：分片键与主查询维度一致（user_id）；post_id 里可嵌入 user_id 分片位（基因法）；运营/客服等次要维度另建异构索引，binlog 同步到 ES（3.3）。

**路由与扩容**：`userId % 4` 这种取模路由，4 库扩 8 库时几乎全部数据要迁移。常用解法是**预分片**——一开始就建 1024 个逻辑分片（哈希后对 1024 取模），映射到 4 个物理库；扩容时只改"逻辑分片 → 物理库"的映射，迁移量可控。桶装水商城订单涨 50 倍时走的正是这条路。

**连带问题**：跨分片无法用数据库自增主键 → 全局 ID 用雪花算法；跨分片事务 → 第 4 节；跨分片排序分页 → 游标翻页 + 各分片归并，深度翻页要限制。

### 3.3 NoSQL 选型：KV / 文档 / 列族 / 图 / 搜索引擎（IM + Feed）

| 类型 | 代表 | 数据模型 | 擅长 | 场景用法 | 不擅长 |
|---|---|---|---|---|---|
| KV | Redis | key-value | 极低延迟读写、丰富数据结构 | 秒杀预扣库存（3.1 的 Lua）、IM 在线状态/未读数、Feed 热榜缓存 | 复杂查询、大 value |
| 文档 | MongoDB | JSON 文档、schema 灵活 | 字段多变、嵌套结构 | Feed 帖子与评论（图文嵌套）、桶装水订单快照 | 多表关联、强事务 |
| 列族 | HBase / Cassandra | 宽表、按 rowkey | 海量写入、按主键点查/范围扫 | **IM 全量消息落档**（会话 ID+序号作 rowkey）、IoT 时序数据 | 二级查询、聚合分析 |
| 图 | Neo4j | 点和边 | 多跳关系查询 | 风控（同收货地址/同设备的欺诈团伙）、Feed 好友关系 | 大范围扫描 |
| 搜索 | Elasticsearch | 倒排索引 | 全文检索、多维过滤聚合 | 工单/订单/帖子搜索（通用能力），配合分库分表做异构索引 | 强一致、点查、计数 |

**IM 为什么选宽表/KV**：消息写入是持续高吞吐（百万在线 × 每秒多条），且读取模式极其固定——"按会话拉最近 N 条、按序号范围补拉"。rowkey = 会话 ID + 单调递增序号，天然按会话聚簇、天然有序，正是列族库的主场；热会话再叠一层 Redis。**Feed 时间线**读取也是"按用户拉取、按时间排序"，结构同构，可复用同一选型。

❌ 反例：用 ES 扣库存——ES 是**近实时**（refresh 前后读到的不一致），写入可见性有延迟，并发扣减必超卖。
✅ 修正：扣减只在强一致存储（MySQL 事务或 Redis+Lua），ES 只承担"搜"，通过 binlog/消息异构同步，接受秒级延迟。

### 3.4 动态字段存储：低代码平台的三方案（数据架构经典 trade-off）

低代码平台的表单由用户拖拽配置，字段集合随时变：今天报修单有"故障照片"，明天巡检单加"设备序列号"。工单中心"新增工单类型只配表单不改代码"，本质是同一个问题。**用户自定义字段怎么存**是必考的存储选型，三种方案各有明码标价的代价。

**方案 A：EAV 表**——一行存一个字段（`form_data(entity_id, field_code, value_str)`）：

```kotlin
// ❌ EAV：按自定义字段过滤要"行转列"，字段一多 SQL 膨胀、索引难命中
// SELECT entity_id FROM form_data WHERE field_code='priority' AND value_str='P0'
// INTERSECT
// SELECT entity_id FROM form_data WHERE field_code='device_line' AND value_str='A1'
// —— 查"紧急 + A1 产线"的工单：条件越多交集越多，且 value 全是字符串，类型与统计口径失控
fun findTickets(conds: Map<String, String>) = formDataTable.query(conds)  // 加字段零成本，但查询代价巨大
```

**方案 B：JSON 列**——一行一张表单，自定义字段收进 JSON：

```kotlin
data class Ticket(
    val id: Long,
    val typeId: Long,          // 工单类型 → 对应哪份表单 Schema
    val schemaVersion: Int,    // 历史单据按提交时的旧版 Schema 渲染与校验（版本化）
    val fields: String         // JSON：{"priority":"P0","device_line":"A1","photos":["url1"]}
)

// ✅ 高频过滤字段用"生成列 + 索引"提升为真正的索引列（MySQL 8 / PostgreSQL JSONB 均有等价能力）
// ALTER TABLE ticket ADD COLUMN priority VARCHAR(8)
//   GENERATED ALWAYS AS (fields->>'$.priority') STORED, ADD INDEX idx_priority(priority);
fun findP0Tickets(typeId: Long) =
    ticketRepo.where("type_id = ? AND priority = 'P0'", typeId)   // 走索引，而不是全表扫 JSON
```

**方案 C：动态建表**——每个表单 DDL 一张专表，字段即列。查询性能最好（原生列、原生索引、原生聚合），但代价沉重：改表单 = ALTER TABLE（DDL 审批、锁表风险）；表数量爆炸拖累连接池与元数据；跨表单聚合要 UNION 一堆结构各异的表；Schema 版本演进最痛。只适合字段集合稳定、数据量大的少数专有场景（如某大客户的定制工单类型）。

**三方案对比**（务必记住这张表）：

| 维度 | A：EAV 表 | B：JSON 列 + 生成列索引 | C：动态建表 |
|---|---|---|---|
| 加字段 / 写入灵活度 | 极高（插一行即可） | 高（新字段直接进 JSON） | 低（ALTER TABLE / DDL 治理） |
| 按自定义字段过滤 | 差（行转列、难索引） | 中（生成列索引覆盖高频字段） | 好（原生列与索引） |
| Schema 演进成本 | 低 | 低（老数据按 schemaVersion 兼容） | 高（历史表迁移） |
| 聚合统计 | 差（类型靠约定） | 中（类型来自 Schema 定义） | 好（SQL 原生） |
| 运维复杂度 | 低 | 低 | 高（表爆炸、DDL 风险） |
| 适用 | 字段极多但极少按字段查 | **大多数低代码平台的默认解** | 字段稳定 + 数据量大的专表场景 |

默认答案是 **B**：查询性能不足时，只把少数热点字段"提升"为生成列索引——性能问题局部治，不为个别字段付出全局 DDL 成本；C 留作逃生舱。这与第二阶段"元数据驱动 + 解释器模式"呼应：Schema 是解释执行的配置，存储方案要让配置演化足够便宜。

## 4. 分布式事务

> 本节全部围绕一笔交易展开：**用户付款 → 商户发货 → 平台/商户/配送员分账**——它跨支付渠道、订单、履约、分账多个系统，是分布式事务的完整舞台（场景文档指定）；**桶装水商城**的"下单-库存-支付"一致性做第二例子。

### 4.1 问题起源

支付、订单、商户、分账拆成独立服务/独立库后，**数据库本地事务的边界（单库）再也罩不住一次交易**：渠道扣款成功、订单落库成功、分账服务超时——三件事没有共同的事务管理器。分布式事务的所有方案，本质都是在回答：**要么牺牲性能换强一致，要么牺牲即时一致换性能，再用补偿把状态收敛回来**。桶装水商城同理：下单成功但扣库存失败、支付成功但押金没记——同一个问题的弱化版；周期购"定时触发的订单"还把可靠性问题拖到了时间维度（4.5）。

### 4.2 2PC（两阶段提交）

**机制**：协调者先向所有参与者发 Prepare（各自执行并**锁住资源**，投"能提交"票）；全部同意后再发 Commit，任一拒绝则 Abort。

**两大缺陷**：① **同步阻塞**——Prepare 之后到二阶段结束前，资源一直锁着，参与者全体干等协调者；落到支付上：渠道侧资金与平台侧订单双双锁死，谁也不敢动。② **协调者单点**——它在两阶段之间宕机，参与者就悬在锁定态。加上两轮网络往返，高并发主链路基本不用，多见于传统数据库间（XA）的低频强一致操作，如日终对账批处理、数据迁移。

### 4.3 TCC（Try-Confirm-Cancel）：余额冻结切片

把事务控制权上移到业务层，每个参与方实现三个接口：**Try 预留资源 → 全部成功则 Confirm 真正提交 → 任一失败则 Cancel 释放**。以支付为例：Try 冻结用户余额/渠道额度，Confirm 真正扣款记账，Cancel 解冻。锁的不是数据库行，而是业务语义上的"冻结"，性能远好于 2PC，代价是**侵入性极大**（每个参与方三接口 + 状态记录）。

```kotlin
interface BalanceTcc {
    fun tryFreeze(txId: String, accountId: String, amountCents: Long): Boolean // 冻结：可用 -amount，冻结 +amount
    fun confirm(txId: String)     // 确认扣款：冻结 -amount，已入账 +amount
    fun cancel(txId: String)      // 取消：解冻，可用 +amount
}

// 事务状态表是 TCC 的护栏：所有接口都先查它
class TccBalance(
    private val txRepo: TccTxRepository,
    private val accountRepo: AccountRepository,
) : BalanceTcc {
    override fun tryFreeze(txId: String, accountId: String, amountCents: Long): Boolean {
        if (txRepo.isTried(txId)) return true            // 幂等：框架可能重发 Try
        if (txRepo.isCancelled(txId)) return false       // 防悬挂：Cancel 已先到，拒绝迟到的 Try
        accountRepo.freeze(accountId, amountCents)
        txRepo.markTried(txId)
        return true
    }
    override fun cancel(txId: String) {
        val tx = txRepo.find(txId)
        when {
            tx == null -> txRepo.markCancelled(txId)     // 空回滚：Try 从未到达也要记录，用于挡悬挂
            tx.tried -> accountRepo.unfreeze(txId)       // 正常解冻（按 txId 找冻结记录，本身幂等）
        }
    }
    override fun confirm(txId: String) { /* 同理：先查幂等记录，再把冻结额转入已扣款 */ }
}
```

**三大坑**（面试高频，全部用"冻结余额"理解）：**幂等**（三个接口都可能被框架重试）；**空回滚**（Try 因网络丢包未到达，Cancel 先到——必须直接返回成功并留痕，否则框架会无限重试）；**悬挂**（Cancel 之后，被网络延迟的 Try 才到达并冻结了余额，从此没人释放——Try 前必须检查"已回滚"标记）。

### 4.4 Saga：扣款 → 发货 → 分账切片

把一次交易拆成若干**各自本地事务**的步骤，全部正向执行则成功；某步失败则**逆序执行补偿**。两种组织方式：**编排**（Orchestrator 集中状态机，流程清晰、易观测，如 Seata Saga、Temporal）与**协同**（事件驱动，服务各自订阅，松耦合但链路难追）。缺点：**没有隔离性**——中间状态对外可见。

```kotlin
class PayDeliverSplitSaga(
    private val channel: PaymentChannelService,   // 支付渠道：扣款 / 退款
    private val orderRepo: OrderRepository,
    private val fulfillment: FulfillmentService,  // 商户发货
    private val split: SplitService,              // 分账：平台/商户/配送员分成
    private val retryQueue: CompensationRetryQueue,
) {
    fun settle(cmd: SettleCmd) {
        val compensations = mutableListOf<suspend () -> Unit>()     // 已成功步骤的逆动作栈
        try {
            channel.charge(cmd.userId, cmd.amountCents, cmd.orderId)   // 步骤1：渠道扣款（本地事务）
            compensations += { channel.refund(cmd.orderId) }           // 补偿：原路退款
            orderRepo.markPaid(cmd.orderId)                            // 步骤2：订单支付成功
            compensations += { orderRepo.close(cmd.orderId, CLOSED) }
            fulfillment.dispatch(cmd.orderId, cmd.items)               // 步骤3：通知发货（本地事务）
            compensations += { fulfillment.cancelDispatch(cmd.orderId) }
            split.execute(cmd.orderId, cmd.splitPlan)                  // 步骤4：分账（本地事务）
            compensations += { split.reverse(cmd.orderId) }            // 补偿：分账冲正
        } catch (e: Exception) {
            compensations.reversed().forEach { undo ->               // 失败 → 逆序补偿
                runCatching(undo).onFailure { retryQueue.push(undo, it) }   // 补偿失败进重试表，最终必达
            }
        }
    }
}
```

隔离性缺失在支付业务里的样子：用户能看到"分账处理中"，某步失败后又变回"退款中"；日终对账必须能识别这些中间态。**补偿三纪律**：补偿必须幂等（会被重试）；补偿失败必须持久化重试直到成功；**不可补偿或难补偿的动作（真实打款、已分出的账）尽量排在 Saga 末尾**，让失败发生在还能挽回的阶段。

### 4.5 本地消息表 + 最终一致（支付系统的默认解）

**核心思想**：把"改业务数据"和"记一条待发消息"放进**同一个本地事务**（原子），再由后台任务把消息投到 MQ——绕开"数据库写成功但 MQ 发送失败"的经典裂缝，即事务性发件箱（Outbox）模式。

**渠道回调：状态机驱动的最终一致**。支付结果不是同步返回的，而是渠道异步通知到达；通知还会重复（渠道怕丢失会重发）。❌ 反例：回调来了就发货 → 渠道重发 30 次 → 发 30 次货。✅ 修正：状态机守卫 + Outbox，同一本地事务内原子完成：

```kotlin
// ① 回调处理：状态机守卫 + Outbox，并发/重复回调只有一个能生效
fun onChannelNotify(n: ChannelNotify) = transaction {
    val pay = payRepo.findByChannelOrderNo(n.channelOrderNo)
        ?: throw UnknownNotifyException(n)                     // 无法识别 → 进差错队列，绝不能丢
    if (!pay.canTransit(PAYING to PAID)) return@transaction    // 已支付/已关闭 → 重复回调，幂等返回成功让渠道停止重发
    payRepo.casUpdateStatus(pay.id, from = PAYING, to = PAID)  // 乐观锁式更新，并发回调只有一个成功
    outboxRepo.insert(Outbox("pay.succeeded", """{"payId":"${pay.id}","amount":${n.amountCents}}"""))
}
```

```kotlin
// ② 后台任务轮询（或订阅 binlog）投递 MQ，成功才标记
fun relayOutbox() {
    outboxRepo.findPending(limit = 100).forEach { msg ->
        mq.send(msg.topic, msg.payload, messageId = msg.id)
        outboxRepo.markDone(msg.id)
    }
}

// ③ 消费端幂等：MQ 是 at-least-once，重复投递是常态不是异常
// ❌ 反例：重复消费 → 重复发货、重复分账
// ✅ 修正：以 messageId（或业务唯一键）做幂等表
fun onPaySucceeded(msg: PaySucceededMsg) {
    if (!idempotentRepo.tryInsert(msg.messageId)) return   // 处理过，直接丢弃
    fulfillmentService.createShipment(msg.payId)
    splitService.schedule(msg.payId)
}
```

整条链路是：**本地事务 + Outbox + MQ 可靠投递 + 消费幂等 + 对账兜底**。对账是最后防线：日终拿渠道对账单与平台流水逐笔核对，长款/短款/重复支付自动分类、转人工处理。

**第二例子：桶装水商城**。下单-库存-支付走同一条路：下单本地事务写 Outbox → 库存/支付各自消费。周期购是"定时触发的订单"：订阅生效时投递一条**延迟消息**，到期触发"生成下一期订单"，消费端以 `订阅ID+期号` 幂等防重复生成；替代方案是任务表定时扫描——可控、易运维，但几十万订阅全量扫表有压力，与工单中心 SLA 超时检测（几十万在途工单）是同一道选型题（见自测）。

```kotlin
// 周期购：延迟消息到期触发续订，幂等键 = 订阅ID + 期号
fun onRenew(msg: RenewMsg) {
    if (!idempotentRepo.tryInsert("renew:${msg.subId}:${msg.cycleNo}")) return
    orderService.createCycleOrder(msg.subId, msg.cycleNo)
```

### 4.6 方案对比与选型（以收款/分账业务为例）

| 方案 | 一致性 | 侵入性 | 性能 | 开发量 | 收款/分账中的适用 |
|---|---|---|---|---|---|
| 2PC / XA | 强 | 低（数据库代劳） | 差（阻塞） | 小 | 日终对账、数据迁移等低频跨库强一致 |
| TCC | 准强（结果确定） | 高（每方三接口+状态表） | 中 | 大 | 资金短事务：余额/额度冻结 + 确认扣款 |
| Saga | 最终一致（补偿回滚） | 中 | 好 | 中 | 扣款→发货→分账的长流程跨系统编排 |
| 本地消息表 + MQ | 最终一致（正向重试） | 中 | 好 | 中 | 回调后通知发货、记账、开票等旁路 |

**选型顺序**：能合并到同库就别上分布式事务 → 短而关键的链路用 TCC → 长流程用 Saga → 旁路用消息最终一致。**先问能不能不一致，再选哪种一致**。

## 5. 高可用与稳定性

秒杀讲稳定性要从**容量推演**开始：预计 100 万人抢 1000 件，峰值 QPS 是平时的百倍——逐个环节问"能扛多少"：网关 10 万、下单服务 2 万、DB 写入 5 千；容量之外的流量，必须在离用户最近的地方挡掉或排起队来。本节另两个舞台：**MES**（产线 7×24 不能停）与**物联网平台**（写入型洪峰，与秒杀方向相反）。

### 5.1 限流

**四种算法**：固定窗口（临界处会出现双倍突刺）、滑动窗口（平滑计数）、漏桶（恒定速率流出，绝不突发）、令牌桶（匀速产令牌、允许攒令牌应付突发——互联网最常用）。

```kotlin
class TokenBucket(private val capacity: Int, private val refillPerSecond: Double) {
    private var tokens = capacity.toDouble()
    private var lastRefill = System.nanoTime()
    private val lock = ReentrantLock()

    fun tryAcquire(n: Int = 1): Boolean = lock.withLock {
        val now = System.nanoTime()
        tokens = min(capacity.toDouble(), tokens + (now - lastRefill) * 1e-9 * refillPerSecond)
        lastRefill = now
        if (tokens >= n) { tokens -= n; true } else false
    }
}

// ❌ 反例：秒杀开始，10 万 QPS 直击下单服务 → 线程池打满 → 连普通下单也不能用
// ✅ 修正：入口限流，超出容量的请求快速失败（生产中用 Redis+Lua 做集群级限流，或 Sentinel/Resilience4j）
val seckillBucket = TokenBucket(capacity = 2000, refillPerSecond = 1000.0)

fun seckill(skuId: String, userId: String): ApiResult =
    if (seckillBucket.tryAcquire()) ApiResult.ok(seckillService.place(skuId, userId))
    else ApiResult(429, "太火爆了，请稍后再试")     // 宁可拒绝，不可拖垮
```

**分层限流**：网关按总量粗限（保住机房带宽）、服务按接口细限（保住线程池）、再叠加用户维度限（防单用户脚本刷单）。

**写洪峰对照（物联网平台）**：秒杀超容量可以拒绝用户（429、排队页），设备数据却**拒绝不得**——水表一条读数丢了就永远丢了。写入型洪峰的"限流"是**排队与背压**：接入层照单全收 → 写进 MQ 削峰 → 消费者按下游能力匀速批量写入（隔离见 5.2）。一句话对照：**读洪峰在入口挡，写洪峰在管道排**。

### 5.2 熔断、降级、隔离

**熔断**：下游持续失败时直接"跳闸"，一段时间内不再发起真实调用、立刻走失败逻辑，避免线程全都阻塞在等超时上；窗口结束后放一个探测请求试探恢复。

```kotlin
enum class BreakerState { CLOSED, OPEN, HALF_OPEN }

class CircuitBreaker(private val failureThreshold: Int = 20, private val openMillis: Long = 10_000) {
    var state = BreakerState.CLOSED; private set
    private var failures = 0
    private var openedAt = 0L

    fun <T> call(block: () -> T, fallback: () -> T): T {
        if (state == BreakerState.OPEN) {
            if (System.currentTimeMillis() - openedAt < openMillis) return fallback()  // 跳闸中：快速失败
            state = BreakerState.HALF_OPEN                                            // 冷却结束：放行探测
        }
        return try {
            block().also { failures = 0; state = BreakerState.CLOSED }                // 探测成功：闭合
        } catch (e: Exception) {
            if (++failures >= failureThreshold || state == BreakerState.HALF_OPEN) {   // 探测失败：继续跳闸
                state = BreakerState.OPEN; openedAt = System.currentTimeMillis()
            }
            fallback()
        }
    }
}

// ✅ 推荐位是旁路：挂了不应该拖垮秒杀主链路
val recBreaker = CircuitBreaker(failureThreshold = 20, openMillis = 10_000)

fun seckillPage(skuId: String, userId: String): SeckillPage {
    val stock = stockService.get(skuId)                     // 主链路：库存与下单，必须成功
    val recs = recBreaker.call(
        block = { recommendService.forUser(userId, limit = 6) },
        fallback = { DEFAULT_RECOMMENDATIONS },             // 降级：运营配置的兜底商品
    )
    return SeckillPage(stock, recs)
}
```

**降级**是目的（有损服务），熔断是手段（快速失败给降级让路）。常见降级：兜底数据（默认推荐）、简化响应（不显示实时库存）、异步化（先落库后处理）、拒绝低优先级流量（保交易砍浏览）。MES 的工控版：产线 7×24 不能停——MES 与云端断网时，报工与设备采集在**边缘网关本地续采**，看板降级为"本地最近数据"（牺牲新鲜度保可用）；恢复后补传，靠上报幂等去重（与 IoT 弱网补传同一招）。

**隔离**（舱壁模式）：每个下游独立线程池/信号量配额，推荐服务再慢也只耗尽自己的池子，耗不尽主链路线程；部署层面同理——核心链路与非核心服务分开分组。IoT 的经典故障：❌ 一个慢消费者拖垮整条链路——告警消费者处理慢 → MQ 积压 → 背压向上传导 → 接入层写入受阻 → 全平台采集停摆。✅ 修正：按消费者分组隔离（独立 Topic/消费者组 + 各自配额），存储抖动只让自己的组排队；写洪峰系统的保命原则是"**入口不断、管道可涨、下游可慢**"。

### 5.3 超时与重试

**每个跨进程调用必须设超时**，且超时预算沿调用链**递减分配**：网关 3s → 交易服务 2s → 渠道支付 500ms，保证上游先于下游放弃，不留悬挂请求。
**重试三个前提**：① 被调操作**幂等**（渠道扣款接口没做幂等前，超时重试 = 重复扣款，资金事故）；② 判断下游是**暂时性故障**（超时、503 可重试；400、业务拒绝不重试）；③ **指数退避 + 上限**，否则重试风暴会把正在恢复的下游再次打挂。

```kotlin
// ❌ 反例：不设超时、固定间隔无脑重试 → 线程耗尽 + 重试流量放大
// ✅ 修正：指数退避 + 抖动 + 重试预算，耗尽后转异步补偿而非无限等
fun payWithRetry(orderId: String): PayResult {
    var backoff = 100L
    repeat(3) { attempt ->
        if (attempt > 0) {
            Thread.sleep(backoff + Random.nextLong(0, 50))   // 抖动错开同时重试的请求
            backoff *= 2                                      // 100ms → 200ms → 400ms
        }
        try { return paymentClient.charge(orderId, timeoutMs = 800) }   // 前提：charge 幂等
        catch (e: TimeoutException) { log.warn("pay attempt {} timeout", attempt) }
    }
    throw PayPendingException(orderId)    // 转入"支付中"+ 对账任务，而不是让用户干等
}
```

### 5.4 负载均衡与服务发现

**服务发现**：实例上下线动态，调用方不能写死地址。注册中心（Nacos / Consul / etcd / Eureka）三要素：服务注册（启动时上报）、健康检查（心跳失败摘除）、变更推送（订阅者拿到最新实例列表）。桶装水商城拆出的商品/订单/库存/配送服务全部注册进中心，大促前给下单服务扩容 10 个实例、宕机实例自动摘除；工单中心高峰前对分派服务做同样的事。

**负载均衡算法**：轮询、加权轮询（按机器配置分配）、最少连接（慢请求场景）、一致性哈希（同一请求方落到同一实例，配合本地缓存友好——IM 的连接路由正是用它：同一用户的长连接始终落在同一接入网关，Session 状态本地化）。实现位置：服务端 LB（Nginx/网关集中转发，简单但多一跳）与客户端 LB（消费端从注册中心拉列表本地直连，少一跳，gRPC 原生支持）。

**注册中心的 CAP 取舍**：etcd/Consul/ZooKeeper 基于 Raft/ZAB，是 **CP**——分区时少数派侧不可注册/查询，牺牲可用性；Eureka 是 **AP**——分区时各自可用，但可能返回已死实例（靠调用方超时+熔断兜底）。内网万级实例的大公司常自研 AP 系注册中心，呼应 1.1：**又是一次分区期间的 C/A 权衡**。

### 5.5 异地多活

**演进路径**：同城双活（两机房距离近、延迟 <2ms，可**同步**复制，故障秒级切换，但整体抗不了城市级灾难）→ 两地三中心（同城双活 + 异地灾备，异地**异步**复制，灾难时丢少量数据）→ **异地多活**（多地同时提供服务，城市级故障也能接管）。

**异地多活的核心是单元化（Set 化）**：按用户 ID 把流量和数据路由到固定单元，**每个用户的数据只在归属单元可写**，单元内读写封闭；跨单元之间做异步数据同步与对账。桶装水商城按城市单元化天然合适——配送本来就是地域业务：华南用户归属广州单元。

❌ 反例：北京、上海机房都部署全量服务，用户请求就近接入、数据两地双写——同一账户两地同时扣款，异步复制互相覆盖，余额两边各扣各的，资金错乱+对不平账。
✅ 修正：全局路由层（DNS/GSLB）按 userId 把该用户**始终**送进归属单元，只有归属单元可写；单元故障时先把该单元用户整体切到备份单元（等数据追平再切写）。衡量指标：RPO（能容忍丢多少数据）与 RTO（多久能恢复服务）。故障切换演练属于[第五阶段-工程化与运维视角](../章节5/01-第五阶段-工程化与运维视角.md)的混沌工程话题。
