## 1. 可观测性

### 1.1 概念：可观测性的三大支柱

**定义**：可观测性（Observability）指仅凭系统的外部输出，推断系统内部状态的能力。监控回答"它挂了"，可观测性回答"它为什么挂、挂在哪"。

| 支柱 | 回答的问题 | 数据形态 | 典型技术栈 | MES 例子 |
|---|---|---|---|---|
| 日志 Logging | 单个事件**发生了什么** | 离散事件（文本/JSON） | SLF4J + Logback → ELK / Loki | "3 号注塑机离线重连""报工被拒：批次已冻结"那一条条事件 |
| 指标 Metrics | 系统当前**整体状态如何** | 可聚合的时序数值 | Micrometer + Prometheus + Grafana | 采集入库延迟、每秒入库点数、断线设备数、产线节拍 |
| 链路追踪 Tracing | 一次数据流**经过了谁、卡在哪** | Span 组成的树 | OpenTelemetry + Jaeger / SkyWalking | 一条报工从扫码枪到看板走了 4 秒，卡在入库攒批 |

MES 的可观测性天然比普通业务系统苛刻：一台设备秒级多条数据、全厂成百上千台设备 7×24 不停上报，而产线不能停——指标体系设计得好不好，直接决定故障时"数据断没断、断在哪一层"能不能被立刻回答。三者协作的排障闭环（核心认知，不是三选一）：**指标发现异常（采集延迟 P99 突增告警）→ 追踪定位环节（打开一条慢 Trace）→ 日志查明原因（按 traceId 检索到具体事件）**。这套闭环与业务无关：桶装水商城下单慢、工单中心分派慢，用的是同一套动作。

### 1.2 日志：结构化、traceId 与海量设备日志的分级采样

- **结构化**：写成 key=value 或 JSON，机器可解析、可检索；不要拼接自然语言。
- **级别纪律**：ERROR = 需要人立刻处理（入库管道断开）；WARN = 已自动恢复但需关注（设备掉线后重连成功）；INFO = 关键业务动作（报工、指令下发、联锁拒绝）；DEBUG = 仅排查时开启。
- **traceId 传递**：入口生成全局唯一 traceId → 写入日志 MDC（Mapped Diagnostic Context），本请求内所有日志自动携带 → 跨服务时放入 HTTP 头（W3C `traceparent`）或 MQ 消息属性透传。

❌ 反例：字符串拼接、没有上下文、异常被吞：

```kotlin
fun reportWork(req: WorkReportRequest) {
    log.info("工号" + req.workerId + "报工了")   // 不可检索，缺工序/批次等关键业务参数
    mesClient.submit(req.toWorkRecord())          // 失败直接 500，事后查不到原因
    TODO()
}
```

✅ 修正：结构化字段 + MDC 中的 traceId + 分级记录 + 保留堆栈：

```kotlin
// 边缘网关入口过滤器统一生成 traceId 并放入 MDC，业务代码无感
class TraceIdFilter : OncePerRequestFilter() {
    override fun doFilterInternal(req: HttpServletRequest, res: HttpServletResponse, chain: FilterChain) {
        val traceId = req.getHeader("traceparent")?.split("-")?.getOrNull(1)  // 有上游就沿用
            ?: UUID.randomUUID().toString().replace("-", "")                  // 否则新生成
        MDC.putCloseable("traceId", traceId).use { chain.doFilter(req, res) }
    }
}

fun reportWork(req: WorkReportRequest) {
    log.info("work_report_received workerId={} operationId={} batchNo={}",
        req.workerId, req.operationId, req.batchNo)
    try {
        val record = workRecordRepository.save(req.toRecord())
        mqProducer.send("work.report", record)  // 客户端把 traceId 写入消息属性透传
        log.info("work_report_accepted recordId={} batchNo={}", record.id, record.batchNo)
    } catch (e: BatchFrozenException) {
        log.warn("work_report_rejected reason=batch_frozen batchNo={} operationId={}", req.batchNo, req.operationId)
        throw e
    } catch (e: Exception) {
        log.error("work_report_failed workerId={} operationId={}", req.workerId, req.operationId, e) // e 单独传参以打印堆栈
        throw e
    }
}
```

**海量设备日志的分级与采样**（MES 特有，普通订单系统没有的量级问题）：

- **原始采集数据不是日志**：温湿度、PLC 寄存器值这些数据点走时序数据库与指标。❌ 反例：`log.info("device data: $payload")` 每秒几万条，ELK 三天撑爆。✅ 修正：数据点入时序库，日志只记"事件"——设备上下线、阈值越限、指令执行结果。
- **风暴期采样聚合**：网关重启时上万台设备同时重连，逐条 INFO 就是日志洪水。✅ 按设备+事件类型在时间窗内聚合：`device_reconnect device=XXX count=37 in 60s` 聚成一条 WARN。
- **边缘侧预聚合**：能在边缘网关算成指标（计数、均值、最值）的先聚合成指标再上报，原始明细日志只在 DEBUG 排查窗口开启。

logback 用 `%X{traceId}` 取 MDC 值，输出形如 `12:00:01.123 INFO [abc123def...] ... - work_report_received workerId=42 operationId=OP-30 batchNo=B2026...`。跨服务不断链：HTTP 头、MQ 消息属性、甚至边缘网关自定义协议里预留的透传字段，都是 traceId 的载体。

### 1.3 指标：RED/USE 与 MES 指标体系

选型框架：服务/接口层用 **RED**（Rate 速率、Errors 错误率、Duration 耗时分布）；资源层用 **USE**（Utilization 使用率、Saturation 饱和度如队列堆积、Errors）。写入型管道还要盯**消费速率 vs 生产速率**——两者持续背离意味着堆积。

MES 采集链路的典型指标（命名与分层本身就是架构设计）：

| 指标 | 类型 | 回答的问题 |
|---|---|---|
| `collector_ingest_lag`（采集→入库延迟 P99） | Timer | 现场发生的事多久后能在系统里看到 |
| `collector_points_ingested_total`（每秒入库点数） | Counter | 管道吞吐是否在预期水位 |
| `devices_offline_total`（断线设备数，按车间/产线打标） | Gauge | 哪条产线的采集断了 |
| `mq_lag`（MQ 堆积） | Gauge | 消费端是否跟得上生产端 |
| `dashboard_query_duration`（看板查询 P99） | Timer | 聚合读路径是否健康 |

Kotlin（Micrometer）埋点示例：

```kotlin
@Component
class IngestMetrics(private val registry: MeterRegistry) {
    private val ingested = Counter.builder("collector_points_ingested_total")
        .tag("pipeline", "device-ingest")   // 标签只能用有限枚举值
        .register(registry)

    private val lag = Timer.builder("collector_ingest_lag")
        .publishPercentiles(0.5, 0.99)      // 直接发布 P50 / P99
        .register(registry)

    fun recordBatch(points: Int, lag: Duration) {
        ingested.increment(points.toDouble())
        lag.record(lag)
    }
}
```

❌ 反例：`tag("deviceId", deviceId)`——跨厂区几十万台设备就是几十万条时间序列，把 Prometheus 内存打爆。✅ 修正：指标标签只用低基数枚举（产线、车间、设备型号、版本号）；**设备维度的明细分析交给时序数据库**（TDengine/InfluxDB 的标签天生就是干这个的），两者分工而非替代。

- **P99 延迟**：99% 的数据点快于该值。产线看板场景"平均延迟 200ms"可能掩盖"1% 的批次要 4 秒"——平均数会撒谎，分位数才会说话。
- 实时看板是"高频写 + 聚合读"：写路径（入库速率）与读路径（看板查询 P99）分开盯；聚合读突然膨胀时优先怀疑是否直扫了明细表（读写分离与事件驱动的讨论见[第二阶段-经典架构模式](../章节2/01-第二阶段-经典架构模式.md)）。

### 1.4 链路追踪：一条报工的完整 Trace

- **Trace**：一次数据流的全链路视图，由全局唯一 traceId 标识。
- **Span**：链路中的一个操作（一次 HTTP 调用、一条 SQL、一次 MQ 收发），记录起止时间与父子关系，组成树。
- **传播**：跨进程靠 HTTP 头 `traceparent: 00-{traceId}-{spanId}-{flags}`、MQ 消息属性、或协议里预留的透传字段携带上下文。

```text
报工 Trace（总 4.2s, traceId=abc123）
├─ scanner.report 15ms           扫码枪 HTTP 上报
├─ edgegw.validate 30ms          边缘网关校验、本地缓冲
├─ mq.publish 12ms
├─ ingest.consume 3880ms         ← 慢点：消费端攒批，等满 3s 计时器才 flush
│  └─ tsdb.batch_insert 180ms    批量入库本身并不慢——慢在攒批策略，不是数据库
└─ dashboard.refresh 45ms        看板读的是物化聚合，未直扫明细
```

展开 Span 树的价值就在这里：一眼看出 4.2s 里有 3.7s 花在"等攒批"，而不是想当然地去优化数据库。Kotlin（OpenTelemetry）示例：给 MQ 消费建 Span，上下文从消息属性恢复：

```kotlin
fun onMessage(msg: Message) {
    // 上下文随消息属性传播：先恢复父上下文，traceId 才能接上扫码枪那一侧
    val parentCtx = propagator.extract(Context.current(), msg.properties) { props, key -> props[key] }
    val span = tracer.spanBuilder("ingest.consume")
        .setSpanKind(SpanKind.CONSUMER)
        .setParent(parentCtx)
        .startSpan()
    span.makeCurrent().use {
        try {
            buffer.add(msg.body)   // 攒批；flush 时再开 tsdb.batch_insert 子 Span
        } catch (e: Exception) {
            span.recordException(e)
            span.setStatus(StatusCode.ERROR)
            throw e
        } finally {
            span.end()
        }
    }
}
```

### 1.5 串联：一次产线看板延迟告警的排障闭环

traceId 如何串起三大支柱（面试高频）：扫码枪/网关入口生成 traceId 写入 MDC 与 `traceparent` → 沿途每个服务的每条日志都带 `[abc123]`（日志）→ 各服务持续上报采集延迟、吞吐、断线设备数（指标）→ 全链路 Span 树进入 Jaeger（追踪）。实际排障三步：Grafana 发现 `collector_ingest_lag` P99 从 800ms 涨到 4s → Jaeger 筛 duration>3s 的 Trace，定位卡在 `ingest.consume` 的攒批等待 → 拿 traceId 到 Loki 检索日志，结合配置变更记录发现有人把 flush 间隔从 500ms 改成了 3s。

### 本节自测

1. 三大支柱各自回答什么问题？"3 号产线看板比现场慢半分钟"，你按什么顺序用三支柱定位？
2. 设备原始采集数据为什么不该逐条打日志？它应该进哪里？设备重连风暴期的日志怎么治理？
3. traceId 从扫码枪到看板要经过哪几种传播载体？
4. 指标标签里放 deviceId 会导致什么后果？设备维度分析应该交给谁？
5. **你的 MES/工单中心现在能在一分钟内回答"哪个环节慢了吗"吗？缺的是指标、追踪，还是日志没串起来？**

## 2. 部署与发布策略

### 2.1 CI/CD：从提交到上线的主线

- **CI 持续集成**：每次提交自动构建 + 测试 + 打包制品（容器镜像），问题越早暴露修复成本越低。
- **CD 持续交付/部署**：制品沿流水线推进到预发、生产。交付 = 停在需人工批准的位置；部署 = 全自动直达生产。

核心原则：**一次构建，处处部署**——同一镜像贯穿所有环境，环境差异全部放配置，制品是不可变单元；给每个环境单独打包是流水线坏味道。镜像 tag 用 commit SHA（不可变、可追溯），不要用 latest。

GitHub Actions 示例（工单中心 ticket-center）：

```yaml
name: ticket-center
on:
  push:
    branches: [main]
jobs:
  build-and-deploy:
    runs-on: ubuntu-latest
    steps:
      - uses: actions/checkout@v4
      - uses: actions/setup-java@v4
        with: { distribution: temurin, java-version: 21 }
      - name: 单元测试与集成测试
        run: ./gradlew test
      - name: 构建并推送镜像（jib，无需 Docker 守护进程）
        run: ./gradlew jib --image=registry.example.com/ticket-center:${{ github.sha }}
      - name: 部署到预发（滚动更新）
        run: kubectl set image deploy/ticket-center app=registry.example.com/ticket-center:${{ github.sha }} -n staging
```

**配置即代码**：低代码平台的表单 Schema、流程定义也是"会出事故的变更"，同样应存 Git、走 PR 评审 → CI 校验（Schema 合法性、字段删除的向后兼容检查）→ 发布审批 → 灰度，与代码共用一条流水线。这是 2.3 主案例的前置认知：**配置的变更频率比代码更高，治理标准不应更低**。

### 2.2 蓝绿发布

两套**完整**环境：蓝 = 当前版本承接 100% 流量；绿 = 新版本部署完毕后，网关一键把流量整体从蓝切到绿。优点是切换与回滚都是秒级（切回蓝即可）；代价是双倍资源，且共享数据库时 schema 变更必须同时兼容两个版本。适合需要极快回滚的关键变更——例如桶装水商城大促前夜给支付服务换版本：出了问题秒级切回，不影响第二天开卖。

### 2.3 灰度 / 金丝雀发布

新版本先接一小部分**真实流量**（如 5%），观察核心指标无异常后逐步放量 5% → 25% → 50% → 100%；指标恶化立即回切。"金丝雀"取自矿工带金丝雀下井探毒气的典故——用小牺牲换大预警。

**主案例：低代码平台的搭建产物发布治理**。实施人员把报修表单里的"紧急程度"字段删了、审批流加了一级会签，点"保存"直接生效——麻烦立刻出现：300 张在途工单的渲染与校验还引用旧字段，流程卡死、报表报错，而且**没有旧版本可回滚**。搭建产物的发布治理需要四件套：

1. **Schema 版本化**：每次发布生成不可变版本（v12）。单据提交时绑定当前版本，历史单据永远按**提交时的版本**渲染与校验——删字段只影响新单，不炸旧单（与[第三阶段-动态字段存储](../章节3/01-第三阶段-分布式系统核心技术.md)中 Schema 演化的讨论呼应）。
2. **发布审批**：配置变更走 PR/审批流，谁改的、改了什么、何时生效全程留痕——配置即代码。
3. **配置灰度**：新版本 Schema 先对试点租户/车间生效：

```kotlin
// 表单 Schema 灰度：v13 先对试点租户生效，其余仍用 v12
fun resolveSchemaVersion(formId: FormId, tenantId: TenantId): SchemaVersion {
    val gray = grayReleaseRepository.find(formId) ?: return latestStable(formId)
    return if (gray.pilotTenants.contains(tenantId)) gray.candidateVersion else gray.stableVersion
}
```

4. **一键回滚**：灰度观察期发现问题，把 stable 指回 v12 即刻生效；因版本化，已按 v13 提交的少量单据仍按 v13 渲染，数据不损坏。

**传统应用发布对照**：桶装水商城支付服务 v2 重写了分账逻辑，按 userId 哈希把 5% 用户路由到 v2：

```kotlin
// 网关路由示意：同一用户始终落在同一版本，避免"忽新忽旧"造成体验割裂与数据错乱
fun routeVersion(userId: String): String =
    if (abs(userId.hashCode()) % 100 < 5) "v2-canary" else "v1-stable"
```

配套要求（两类发布通用）：指标带版本标签，在 Grafana 并排对比新旧版本的成功率、错误率、P99；数据兼容（v2 写入的新字段 v1 能忽略，回切后业务仍正确）；功能开关（Feature Flag）与灰度正交，把发布风险与功能风险分离。

### 2.4 滚动发布

逐台/逐批替换实例：旧实例摘除流量 → 更新镜像 → 就绪后挂回，循环至全部替换。资源最省（约 1 批冗余），但发布期间**新旧版本长期共存**，接口必须 N-1 兼容（v2 能处理 v1 写的数据，反之亦然）；回滚 = 反向再滚一轮，速度最慢。适合常规小改动——工单中心新增一个通知渠道这类低风险变更用滚动即可，不必动用蓝绿的双倍资源。

### 2.5 三种发布策略对比

| 维度 | 蓝绿 | 灰度 / 金丝雀 | 滚动 |
|---|---|---|---|
| 资源成本 | 高（双份完整环境） | 中（少量新实例） | 最低（约 1 批冗余） |
| 回滚速度 | 最快（秒级切回） | 快（流量/配置回切） | 慢（逐批反向再滚） |
| 发布风险 | 中：切换即全量，无渐进观察 | 最低：小流量试错 + 渐进放量 | 中：混合版本共存期长 |
| 流量粒度 | 0% / 100% | 任意比例，可按人群/租户/地域 | 逐实例 |
| 关键前提 | 环境一致性 + DB 双向兼容 | 版本路由 + 按版本对比指标 | 接口与数据 N-1 兼容 |
| 典型场景 | 大促前关键变更、要求秒级回滚 | 高风险大变更（低代码 Schema、分账逻辑） | 常规小改动 |

❌ 反例：周五下午实施人员直接在生产改报修表单、删字段保存即生效——在途工单渲染报错、流程卡死，且没有旧版本可回退。✅ 修正：Schema 版本化 + PR 审批 + 试点租户灰度 + 一键回滚（见 2.3）；配置"发布"到试点后先验证在途流程与新提交两条路径都正常，再全量。

## 3. 安全架构

### 3.1 认证 vs 授权

| 概念 | 回答的问题 | 支付与清结算例子 |
|---|---|---|
| 认证 Authentication | 你是谁？ | 支付渠道回调：渠道用约定签名证明"我是渠道官方"而非伪造者；商户登录商户平台 |
| 授权 Authorization | 你能做什么？ | 商户 A 只能查自己的交易与分账单；只有运营风控角色能发起退款 |

经典漏洞：只做认证不做授权——商户登录后枚举 settlementId 就能查到任意商户的分账单（水平越权）。任何查单接口都必须：

```kotlin
fun mySettlement(settlementId: SettlementId, currentMerchant: MerchantId): Settlement {
    val s = settlementRepository.find(settlementId) ?: throw NotFoundException()
    check(s.merchantId == currentMerchant) { "无权访问他人分账单" }  // ✅ 资源归属校验，服务端每次都做
    return s
}
```

### 3.2 OAuth2：四种授权模式与授权码 + PKCE

OAuth2 解决**委托授权**：用户让第三方应用有限度地访问自己在另一服务的资源，而不交出密码。典型场景：第三方开发的门店收银/对账 SaaS 要读商户在本平台的交易数据——商户授权它 `trade:read`，而不是把账号密码交给它。RFC 6749 的四种授权模式：

| 模式 | 适用客户端 | 现状 |
|---|---|---|
| 授权码 authorization_code | Web 服务端应用（能安全保存密钥） | 主流 |
| 隐式 implicit | 早期 SPA，token 直接放 URL 回传 | 已废弃（token 暴露在 URL 与浏览器历史） |
| 密码 password | 应用直接经手用户名密码 | 已废弃（应用不该接触密码） |
| 客户端凭证 client_credentials | 服务对服务，无用户参与 | 常用 |

**PKCE（Proof Key for Code Exchange）是授权码模式的扩展**，为"存不住密钥"的公共客户端（移动 App、SPA）设计，是当前新接入的推荐做法。流程：

```text
1. App 本地生成随机 code_verifier，计算 code_challenge = BASE64URL(SHA256(verifier))
2. App 拉起系统浏览器访问认证服务器：
   GET /authorize?client_id=merchant-app&redirect_uri=callback
       &code_challenge=xxx&code_challenge_method=S256&response_type=code&scope=trade:read settle:read
3. 用户在认证服务器登录并同意授权（密码只在认证服务器输入，App 碰不到）
4. 认证服务器携带一次性授权码 code 重定向回 redirect_uri
5. App 后台用 code + code_verifier 请求 /token
6. 认证服务器校验 SHA256(verifier) == 之前的 challenge，签发 access_token（含 refresh_token）
```

PKCE 的意义：即使第 4 步的授权码在重定向途中被劫持，攻击者没有 code_verifier 也换不到 token——等于给公共客户端补上了"一次性动态密钥"。服务间场景用 client_credentials：清结算服务以**自己的身份**（而非任何用户身份）申请 token 调用银行存管接口，这也是零信任中"服务身份"的落地（见 3.5）。

### 3.3 JWT：结构、签发、校验与常见误用

JWT（JSON Web Token）= `header.payload.signature` 三段 base64url 以 "." 连接：

```text
header     {"alg":"RS256","typ":"JWT"}                              声明签名算法
payload    {"sub":"M-1001","scope":"settle:read","exp":1760000000}  业务声明（任何人都能解码）
signature  RS256(base64(header).base64(payload), 私钥)               防篡改：改任何一个字符，验签失败
```

Kotlin 签发与校验（jjwt 0.12.x）：

```kotlin
fun issueAccessToken(merchantId: String): String {
    val now = Instant.now()
    return Jwts.builder()
        .subject(merchantId)
        .claim("scope", "trade:read settle:read")
        .issuedAt(Date.from(now))
        .expiration(Date.from(now.plus(15, ChronoUnit.MINUTES)))  // ✅ 短有效期
        .signWith(privateKey, Jwts.SIG.RS256)
        .compact()
}

fun verifyAccessToken(token: String): Claims =
    Jwts.parser()
        .verifyWith(publicKey)     // ✅ 服务端固定算法与密钥，绝不信任 header 里声明的 alg
        .build()
        .parseSignedClaims(token)  // 验签失败 / 已过期都会在此抛异常
        .payload
}
```

常见误用（每条都是真实事故来源）：

❌ 误用 1：把 JWT 当服务端会话，指望"商户点登出后 token 立即失效"。JWT 是自包含、无状态凭证，服务端不存储它，签发后到过期前天然有效；要即时失效只能短过期 + refresh token 轮换（登出作废 refresh，access 最多再活 15 分钟）或引入黑名单（重新变有状态）。强会话控制的系统用服务端会话更简单。
❌ 误用 2：不设 exp 或有效期一年，一旦泄露就是长期通行证——支付场景等于长期资金操作权限。✅ access token 15 分钟 + refresh token 数天、每次使用轮换且可吊销。
❌ 误用 3：payload 放卡号、持卡人手机号等敏感信息。payload 只是 base64，**任何人都能解码**——签名防篡改，不防阅读；只放 merchantId、scope 等非敏感声明（卡号怎么存见 3.4）。
❌ 误用 4：校验时信任 header 里的 alg。历史漏洞：把 alg 改成 none 或 HS256 制造算法混淆攻击。✅ 服务端写死算法与密钥（如上 verifyWith）。
❌ 误用 5：商户前端按 JWT 里的 scope 隐藏"退款"按钮就当作完成授权。前端控制只是体验，**每次请求服务端必须重新校验 scope 与资源归属**（见 3.1）。

### 3.4 敏感数据保护：卡号、密码与密钥管理

支付与清结算在"资金零差错"之外还有"敏感数据零泄露"，三样东西各有正确姿势：

| 对象 | 原则 | 落地 |
|---|---|---|
| 卡号 PAN | 传输加密 + 存储加密 + 展示脱敏 | TLS 之上，落库用 KMS 信封加密；页面与日志只出现 `6222********1234` |
| 密码 | 永不明文、永不可逆 | 只存加盐慢哈希（bcrypt/Argon2），登录时比对 |
| 密钥 | 密钥不出安全区 | 主密钥留在 KMS/HSM，应用只拿数据密钥的密文；定期轮换 |

❌ 反例：`log.info("pay cardNo={}", req.cardNo)`——卡号全文进了日志平台，所有能查日志的人都看得到，且日志保留期往往比业务库还长。✅ 修正：

```kotlin
object CardMask {
    fun mask(pan: String): String = pan.take(4) + "*".repeat(pan.length - 8) + pan.takeLast(4)
}

fun onPayCallback(cb: PayCallback) {
    log.info("pay_callback orderId={} amount={} card={}", cb.orderId, cb.amount, CardMask.mask(cb.cardNo))
}
```

合规是硬约束（PCI DSS 对卡数据、等保与审计要求）：谁能解密、谁查过敏感数据都要留审计日志。更进一步：大部分系统根本不该接触完整卡号——让支付渠道托管卡信息，自己只存渠道返回的 token/掩码，是更安全的架构选择。

### 3.5 零信任：从支付内网到工控 OT/IT 隔离

传统边界模型像城堡：守住防火墙，内网即信任区。后果是入侵者一旦进入内网（或内部人员作恶），服务之间彼此裸奔，横向移动畅通无阻。**零信任原则：Never trust, always verify——不因"来源在内网/本机房"就给予任何信任**：

| 要素 | 支付清结算落地 | 工控（MES/OT）落地 |
|---|---|---|
| 身份为王 | 服务间 mTLS 双向证书 / client_credentials 服务 token；回调验签 | 生产网内的系统与设备同样要身份，区域之间不存在"内网互信" |
| 最小权限 | 结算服务只能读写结算库，无权碰卡数据明文 | MES 只能"请求"设备动作，且只有授权工序的指令才被接受 |
| 持续校验 | token 短期有效、异常交易触发二次校验 | 每次指令下发都经现场安全联锁校验，昨天的授权不代表今天放行 |
| 默认拒绝 | 网关 + 服务双层鉴权，而不是只靠网关一道闸 | 生产网（OT）与管理网（IT）之间默认不通，数据经 DMZ/单向通道汇聚 |

**工控是零信任最有说服力的落地**，因为后果是物理性的：IT 系统被攻破丢的是数据，产线控制被攻破停的是生产、坏的是设备、伤的是人（震网 Stuxnet 经 U 盘进入"隔离"网络，物理摧毁了离心机——"内网就是安全"的假设被击碎）。两个专属设计：

- **OT/IT 隔离**：按 ISA-95/Purdue 分层，L1/L2 生产网与 L3/L4 管理网之间设 DMZ，数据上行走单向通道（网闸），指令下行走独立受控通道——MES 想发指令不能直连 PLC。
- **Fail-Safe 与控制权归属**：安全联锁做在现场 PLC，不在 MES——MES 下发的指令，现场校验联锁条件不满足就拒绝执行；急停等关键控制权永远归现场硬接线回路。MES 挂了，产线照转；MES 被攻破，最坏也只能"请求"，拦不住现场急停。

❌ 反例：图省事把 MES 服务器直接桥接办公网，"反正有防火墙"——办公网一台电脑被钓鱼后勒索软件横向移动进车间，停产一周。✅ 修正：DMZ + 单向数据通道 + 生产网白名单策略 + 指令通道独立鉴权与现场联锁。"从不信任、始终校验"在 OT 的含义是：**即使信任 MES，现场也要校验**。

## 4. 性能工程

### 4.1 容量规划：把业务目标翻译成资源数量

秒杀的容量推演永远从两个问题开始：**流量有多少？每个环节能扛多少？**——这也是所有系统容量规划的通用方法，秒杀只是把数字放大到无法糊弄。

**第 1 步 流量估算**（读、写分开算）。业务设定：晚 8 点开抢，60 万用户到场，库存 1000 件。

| 流量项 | 推演 | 结果 |
|---|---|---|
| 商品页读 | 60 万用户开抢前每 3 秒刷新一次详情页 | 600000 / 3 ≈ **20 万 QPS**（读） |
| 下单写 | 点击集中在开抢后 10 秒内（脉冲） | 600000 × 80% / 10 ≈ **4.8 万 QPS**（写） |
| 真实成交 | 库存只有 1000 件 | 支付仅 1000 笔/15 分钟，压力可忽略 |

**第 2 步 分层消化**（关键认知：20 万读 QPS 和 4.8 万写 QPS 绝不能原样打到应用层）：

| 环节 | 手段 | 到达下游的流量 |
|---|---|---|
| 商品页读 | 页面静态化 + CDN + 多级缓存，回源约 5% | 应用层约 1 万 QPS，DB 近乎 0 |
| 下单写 | 网关限流 + MQ 异步排队削峰（呼应[第三阶段-限流熔断](../章节3/01-第三阶段-分布式系统核心技术.md)） | 同步链路只做校验 + Redis 预扣；落库按 MQ 消费速率 2000/s 恒定 |
| 库存扣减 | Redis 原子扣减防超卖，DB 乐观锁兜底 | Redis 约 1 万 QPS，DB 最终 1000 次 |

**第 3 步 实例数**：同步下单链路（校验+预扣）承接 4.8 万 QPS，压测得出单实例在 P99 < 300ms 水位下稳定 2000 QPS（依赖 4.2）→ 48000 / 2000 = 24 → 加约 30% 冗余 ≈ **32 实例**（冗余不是给流量的，是给发布摘流量与单机故障的）。

**第 4 步 全链路核对**：应用够了 ≠ 系统够了。DB 连接数、Redis 分片与热点 key、MQ 堆积与消费速率、第三方（支付渠道限频 500 QPS 就得排队/合并）逐项核对——**容量遵循木桶效应，取决于最短的板**。

要点：**脉冲系数**是因为流量不匀速，开抢前 10 秒的瞬时 QPS 是分钟均值的数倍，按分钟均值规划必挂。容量规划与限流熔断是一对：规划是"算"出来的承诺，限流是"守"住的底线，超预期流量靠限流与降级兜底而不是无限扩容；秒杀完整拆解见[第六阶段-实战与案例分析](../章节6/01-第六阶段-实战与案例分析.md)。

**对照：物联网平台的写入型洪峰**。方向相反、方法相同——先算流量：100 万设备 × 每 10 秒上报 1 条 = **10 万条/秒**（入口写洪峰，持续而非脉冲）→ 接入网关无状态水平扩展 → MQ 削峰 → 消费端**批量聚合写入**：每批 500 条，10 万 / 500 = 200 批/秒，实测单消费者实例稳定扛 60 批/秒 → 4 个消费者实例 + 1 冗余。读洪峰拼缓存与静态化，写洪峰拼队列与批量化；容量指标从"每秒请求数"变成"每秒写入点数 + 批大小 + 堆积水位"。

### 4.2 压测：验证容量的唯一手段

| 类型 | 目的 | 场景举例 |
|---|---|---|
| 基准测试 | 摸清单实例容量 | 秒杀下单链路单实例水位 QPS；IoT 消费者单实例每秒批量入库点数 |
| 负载测试 | 验证预期流量达标 | 1.2 倍预估峰值持续 30 分钟，P99 与错误率不破线 |
| 压力测试 | 找极限与崩溃方式 | 持续加压直至错误率上升，看先打满的是 CPU、DB 连接还是 Kafka 堆积 |
| 稳定性测试 soak | 长跑暴露泄漏 | 中位流量跑 6~12 小时，观察内存/连接是否缓慢上涨——IoT 的长连接与攒批缓冲尤其需要 |
| 浪涌测试 | 瞬时洪峰恢复力 | 秒杀 0 → 4.8 万 QPS 瞬冲；IoT 断电恢复后百万设备重连补传的二次洪峰 |

Gatling（Kotlin DSL）秒杀压测脚本骨架：

```kotlin
val httpProtocol = http
    .baseUrl("https://staging.example.com")
    .header("X-Load-Test", "true")          // 压测标：全链路识别压测流量

val users = csv("users.csv").circular()      // 每个虚拟用户独立账号，避免缓存热点

val seckill = scenario("秒杀压测")
    .feed(users)
    .exec(http("商品页").get("/api/skus/1001")           // 读链路也要压：验证缓存命中与回源比例
        .check(status().`is`(200)))
    .pause(1)
    .exec(http("登录").post("/api/auth/token")
        .body(StringBody("""{"userId":"#{userId}"}""")).check(jmesPath("token").saveAs("tk")))
    .exec(http("下单").post("/api/seckill/orders")
        .header("Authorization", "Bearer #{tk}")
        .body(StringBody("""{"skuId":"1001","quantity":1}"""))
        .check(status().in(200, 429)))      // 429=限流排队，属预期行为，不算失败

setUp(seckill.injectOpen(rampUsersPerSec(500).to(48000).during(10.minutes))).protocols(httpProtocol)  // 阶梯加压复现脉冲
```

IoT 写洪峰的压测姿势（与秒杀对照）：

- **模拟连接而非真实设备**：百万设备不可能真开机，用分布式施压集群模拟 MQTT 长连接与上报节奏（每施压节点扛约 1 万连接）；压的不是 HTTP P99，而是**入口吞吐、MQ 堆积、消费端写入速率**三者是否匹配——生产速率持续大于消费速率，堆积就会无限增长，直到磁盘或延迟先崩（背压与流控见[第三阶段](../章节3/01-第三阶段-分布式系统核心技术.md)）。
- **容量测算闭环**：压出"单消费者实例 60 批/秒、批 500 条、P99 入库延迟 800ms"这样的水位数据，回填 4.1 的公式。

❌ 反例：直接压生产且不打标——压测订单混进真实经营报表；库存被压成负数；"下单成功"的短信真实发给了用户；IoT 压测数据触发真实告警、自动生成工单派给了现场。✅ 修正：

1. 压测流量全链路打标（`X-Load-Test: true`），数据写**影子表**或压测后按标记清理；
2. 旁路统计：经营报表与告警规则按标记剔除压测流量；
3. 第三方依赖（真实支付渠道、短信网关、银行接口）用挡板/mock，只压自己的链路；
4. 压测全程盯 RED/USE 指标（见 1.3），触达水位立即停止——目的是找瓶颈，不是打挂环境；
5. 结果沉淀为容量档案：单机容量回填 4.1 的规划公式，形成"规划 → 压测 → 修正"闭环。
