# 第二阶段：经典架构模式

> 所属学习计划：[软件架构学习大纲](../软件架构学习大纲.md)（建议时长 3~4 周）
> 本文件是第二阶段的详细学习笔记；大纲文件中只保留进度追踪。
> 示例取材：[示例项目场景](../示例项目场景.md)——主线：桶装水商城（单体→模块化→微服务→事件驱动演进）；工单中心、MES、IM、Feed 流、API 网关按小节切换。

本阶段的贯穿主线是一个**桶装水商城**：用户线上买水（单次购买或周期购订阅），配送员按线路送水，水桶收押金、空桶回收退押金，外加会员与优惠券。业务人人看得懂，但领域完整：商品与库存、订单、周期购订阅、支付、配送排线、押金管理、营销、用户八个模块，以及五条实打实的架构挑战：

1. **订单—库存—支付一致性**：下单成功但扣减失败怎么办；
2. **周期购是定时触发的订单**：调度可靠性与错过处理；
3. **押金有完整生命周期状态机**：支付押金→桶在手→回收验收→退押金/扣损；
4. **读多写少**：商品浏览量远大于下单量；
5. **配送排线是独立的算法问题**：不能和交易逻辑耦死。

我们会让这同一个系统先后"变成"分层单体、模块化单体、微服务、事件驱动系统，**每次改造都前后对比：解决了什么、付出了什么**。架构学习的核心不是记住名词，而是**权衡**：每种风格都是用一类复杂度去换另一类复杂度。工单中心、MES、IM、Feed 流等专题场景按小节切换取材（见各节开头的"场景切换"标记）。

## 1. 单体架构

单体（Monolith）：整个系统打包为**一个进程、一次部署**，所有功能编译进同一个制品（如一个 Spring Boot fat-jar）。这绝不等于"落后"——它是默认正确、应被优先考虑的选项。

### 1.1 分层架构（三层 / N 层）

**概念**：把系统按职责垂直切分为若干层，每层只与相邻层对话，依赖方向自上而下。经典三层（以桶装水商城"下单"为例）：

| 层 | 职责 | 桶装水中的例子 | 典型错误 |
|---|---|---|---|
| 表现层（接口层） | 协议转换、参数校验、鉴权 | `OrderController` 接收小程序/APP 的 HTTP/JSON | 写业务规则 |
| 业务逻辑层 | 用例编排、事务边界、领域规则 | `OrderService.create()` 校验库存、算押金、发起支付 | 直接写 SQL |
| 数据访问层 | 持久化细节 | `OrderRepository` 映射 ORM、生成 SQL | 把连接暴露给上层 |

N 层变体：再加缓存层（商品浏览读多写少，先查 Redis——深入在[第三阶段](../章节3/01-第三阶段-分布式系统核心技术.md)）、防腐层（隔离外部模型）、或把业务层细分为应用层与领域层（见 4.2 整洁架构）。

**为什么分层**：关注点分离是[第一阶段](../章节1/01-第一阶段-架构思维与设计基础.md)"可修改性"的具体手法——换数据库只动一层，小程序接口换 gRPC 只动一层。**代价**：一次业务修改要穿透多层；横切逻辑（事务、日志）天然跨层，分层挡不住它。对五条挑战的态度：分层只解决"代码放哪"，挑战 1（跨模块一致性）与挑战 5（排线独立演进）它完全无能为力——这正是后面几节的演进动机。

❌ **反例：越层调用 + 业务规则泄漏进 Controller**

```kotlin
@RestController
class OrderController(private val jdbc: JdbcTemplate) {
    @PostMapping("/orders")
    fun create(@RequestBody req: OrderRequest): ResponseEntity<String> {
        val stock = jdbc.queryForObject(
            "SELECT stock FROM product WHERE sku = ?", Int::class.java, req.sku)
        if (stock < req.quantity) throw IllegalStateException("库存不足")      // 业务规则泄漏到接口层
        val inHand = jdbc.queryForObject(
            "SELECT COUNT(*) FROM bucket_deposit WHERE user_id = ? AND status = 'IN_HAND'",
            Int::class.java, req.userId)
        if (inHand + req.quantity > 4) throw IllegalStateException("押金桶数超上限") // 押金规则也泄漏了
        jdbc.update("UPDATE product SET stock = stock - ? WHERE sku = ?", req.quantity, req.sku)
        jdbc.update("INSERT INTO orders(id, sku, qty) VALUES (?, ?, ?)",
            UUID.randomUUID(), req.sku, req.quantity)
        return ResponseEntity.ok("created")
    }
}
```

问题：换数据库要改"接口层"；将来配送员代客下单入口上线时，库存与押金校验被迫复制一份；规则无法被其他用例复用、无法单测；"押金上限 4 桶"这种会变的策略被焊死在 HTTP 代码里。

✅ **修正：各层各司其职，依赖自上而下**

```kotlin
// 表现层：只做协议转换，不含任何业务规则
@RestController
class OrderController(private val orderService: OrderService) {
    @PostMapping("/orders")
    fun create(@RequestBody req: OrderRequest): OrderResponse =
        orderService.create(req.toCommand()).toResponse()
}

// 业务逻辑层：编排用例、划定事务边界
@Service
class OrderService(
    private val orders: OrderRepository,
    private val products: ProductRepository,
    private val deposits: DepositRepository,
) {
    @Transactional
    fun create(cmd: CreateOrderCommand): Order {
        val product = products.find(cmd.sku) ?: throw ProductNotFoundException(cmd.sku)
        deposits.assertBucketQuota(cmd.userId, cmd.quantity)   // 押金上限：最懂押金的代码说了算
        return Order.place(product, cmd.quantity).also { orders.save(it) }
    }
}

// 领域对象：规则内聚在最懂它的地方
class Order private constructor(val id: OrderId, val lines: List<OrderLine>) {
    companion object {
        fun place(product: Product, qty: Int): Order {
            require(product.stock >= qty) { "库存不足: ${product.sku}" }
            return Order(OrderId.new(), listOf(OrderLine(product.sku, qty, product.price)))
        }
    }
}

// 数据访问层：持久化细节，上层只见接口
interface OrderRepository {
    fun save(order: Order)
    fun find(id: OrderId): Order?
}
```

分层的真正纪律不在"层数"，而在**依赖方向**与**每层的单一职责**。

### 1.2 模块化单体（Modular Monolith）

**概念**：保留单体的部署模型（一个进程），但按业务能力/限界上下文把代码切成高内聚模块，模块间只通过彼此的**公开接口**通信，各自拥有自己的数据表。它是单体与微服务之间的关键中间态：**微服务的设计纪律（边界、数据所有权）可以先在进程内练**，将来确有必要时按模块线拆出去。

**主线演进第 1 步：桶装水从"分层但耦合"到"模块化单体"。** 分层单体跑了一年后：八个模块共用一个库，订单代码随手 join 押金表，排线算法和促销计算混在同一个"业务逻辑层"里。模块化改造：商品与库存、订单、周期购订阅、支付、配送排线、押金管理、营销、用户各成一模块，模块内自己分层，模块间只见 API。

| 维度 | 传统单体 | 模块化单体 | 微服务 |
|---|---|---|---|
| 部署单元 | 1 个 | 1 个 | N 个 |
| 模块边界 | 包名约定（可被绕过） | 强制（编译期/测试保障） | 进程 + 网络边界 |
| 数据库 | 共享，随意跨表 | 每模块自己的 schema | 每服务自己的库 |
| 事务 | 本地事务 | 本地事务（跨模块仍要设计） | 分布式事务/最终一致 |
| 团队协作 | 无并行约束 | 可按模块分工 | 按服务 ownership |

**改造前后对比**——解决了：边界腐化被强制手段拦住；押金、排线、营销各自独立演进互不拖累；团队可按模块认领。付出了：跨模块不再是"一个事务全包"（下单要同时锁库存、记押金，现在要么接受进程内两段编排，要么引入进程内事件）；要养 ArchUnit 等守护纪律的工具；一笔数据修改从"改表"升级为"改 API + 版本协商"。

❌ **反例：模块间直接查对方的表（共享数据是最大耦合源）**

```kotlin
// 订单模块的代码直接读库存模块的表
class OrderService(private val jdbc: JdbcTemplate) {
    fun place(cmd: CreateOrderCommand) {
        val stock = jdbc.queryForObject(
            "SELECT stock FROM inventory_item WHERE sku = ?", Int::class.java, cmd.sku)
        // 库存模块一旦按仓库分表重构，订单模块跟着一起崩
    }
}
```

✅ **修正：跨模块只走对方公开的进程内 API**

```kotlin
// 库存模块对外唯一入口，库存表只有它自己能碰
interface InventoryApi {
    fun reserve(orderId: OrderId, lines: List<OrderLine>): Reservation
}

// 订单模块只依赖接口，感知不到表的存在
class OrderService(private val inventory: InventoryApi, private val orders: OrderRepository) {
    fun place(cmd: CreateOrderCommand): Order {
        val reservation = inventory.reserve(cmd.orderId, cmd.lines)
        return Order.confirmed(cmd.orderId, reservation).also { orders.save(it) }
    }
}
```

落地手段：Gradle 多模块用 `api`/`implementation` 分离依赖可见性、模块间走进程内事件总线、用 ArchUnit 规则测试守护边界（"订单模块不得 import 库存模块内部包"）。检验模块化单体是否合格的标尺：**随机挑两个模块，能否不改业务代码、只改通信方式就把它们拆成两个服务**。

**第二案例：工单中心的模块划分。** 工单中心（多渠道进单、自动分派、SLA 时限、关单回访）同样适合模块化单体，按"变化原因"切模块：

| 模块 | 职责 | 变化原因 |
|---|---|---|
| 工单管理 | 工单生命周期与状态机 | 流转规则随工单类型变化 |
| 分派调度 | 自动/手动分派策略 | 按技能组/负载/优先级频繁调整 |
| SLA 计时与催办 | 时限检测、超时升级 | SLA 策略相对稳定 |
| 工单类型与表单配置 | 元数据驱动的表单/流程 | 每新增类型都变（内嵌的低代码） |
| 通知 | 短信/APP/钉钉触达 | 渠道经常增减 |
| 统计报表 | 聚合分析 | 报表需求持续新增 |

这套边界里，"创建工单 + 首次分派 + 启动 SLA 计时"仍在同一进程内一个事务搞定——这正是模块化单体相对微服务的红利。它也是"**模块化单体够不够、要不要微服务**"的标准讨论素材：企业内部平台、团队十人上下、几十万在途工单——模块化单体大概率够用；真要拆，先拆的也是变化原因与流量画像都独立的统计报表和通知（见 2.1、2.3），而不是工单核心链路。

## 2. 微服务架构

（主线继续：为演示完整演进，本节让桶装水真的微服务化；"该不该"的审判放在 2.3。）

### 2.1 服务拆分的依据与常见误区

**概念**：微服务是一组围绕业务能力构建、可独立部署、去中心化管理数据的小型服务。"微"不是指代码行数少，而是指**边界小而完整**（接口 + 数据 + 团队三位一体）。

拆分依据（按优先级排序，以桶装水为例）：

| 依据 | 说明 | 桶装水示例 |
|---|---|---|
| 限界上下文（DDD） | 同一个词在边界内外含义不同，语言一致处即边界 | "商品"在商城域是 SKU，在配送域是"送水任务上的桶数与楼层" |
| 数据所有权 | 谁写谁拥有，一表一主 | 库存表只有商品与库存服务可写 |
| 变化原因/频率 | 因同种原因变化的东西放一起 | 排线算法天天实验调参、交易流程相对稳定，分开 |
| 团队拓扑（康威定律） | 服务边界对齐团队沟通边界，见[第一阶段](../章节1/01-第一阶段-架构思维与设计基础.md) | 交易团队 vs 配送团队 |
| 扩展性差异 | 资源画像差异大的分开 | 排线是 CPU 密集的算法问题；商品浏览是读多写少的 IO 问题 |

两个典型的拆分判断：

- **配送排线先拆**：车辆路径规划是独立算法问题（挑战 5）。耦在交易里，意味着排线算法每次实验性改动都要重发整个交易系统；拆出去后可独立扩容 CPU、独立灰度算法版本，排线 OOM 也不拖垮下单。
- **周期购订阅其次**：它是"定时触发的订单"（挑战 2），调度可靠性、错过补偿、暂停/换地址等生命周期与即时交易的变化节奏不同步，适合独立演进。

❌ **常见误区与修正对照**：

| 误区 | 后果 | 修正 |
|---|---|---|
| 按技术层拆（"数据库服务""工具服务"） | 一个业务改动横跨全部服务，即"分布式单体" | 按业务能力垂直拆 |
| 一上来拆 20 个服务 | 运维与联调成本爆炸 | 从 3~5 个粗粒度服务起步（monolith first） |
| 多个服务共享一个数据库 | 隐式耦合，改 schema 互相炸 | 每服务私有库，跨服务走 API 或事件 |
| 同步调用链过长 | A→B→C，可用性相乘下降 | 非关键路径异步化（见第 3 节） |
| 把"能拆"当"该拆" | 白付分布式代价，无任何收益 | 先问：团队规模？独立扩展需求？独立部署价值？ |

> **常见追问**：分布式单体是为了提高吞吐率吗？——不是。分布式单体不是设计目标，而是拆分失败的意外产物。拆服务的真实动机是独立部署、独立扩展、故障隔离、团队自治，吞吐最多对应"独立扩展"一条。分布式单体反而连吞吐都救不了：同步调用链每跳多一次序列化 + 网络往返（进程内调用纳秒~微秒级，网络跳毫秒级），延迟叠加；共享数据库没拆，瓶颈原封不动；链路可用性相乘，高峰期更脆。真要吞吐，单体先有招——缓存、读写分离、无状态多实例水平扩容（桶装水商品读洪峰即如此，见 2.3）；确有资源画像差异（如排线 CPU 密集）才按"扩展性差异"拆出边界清晰的微服务。

✅ 按业务拆分后（示意：交易、商品与库存、支付、配送、押金五个服务起步），交易服务只做编排、不实现别人领域的细节：

```kotlin
class PlaceOrderHandler(
    private val inventory: InventoryClient,   // 远程客户端：商品与库存服务
    private val payment: PaymentClient,       // 远程客户端：支付服务
    private val events: EventPublisher,
) {
    fun handle(cmd: PlaceOrderCommand): OrderId {
        val order = Order.draft(cmd)
        inventory.reserve(order.id, order.lines)
        payment.charge(order)                  // 失败必须走补偿，不能让订单悬空
        events.publish(OrderEvent.OrderPlaced(order.id, order.lines, Instant.now()))
        return order.id
    }
}
```

**演进前后对比**——解决了：独立部署（排线算法每天可发版）、独立扩展（大促时只扩商品读服务）、故障隔离（排线挂了不耽误下单）。付出了：下单原子性没了（本地事务 → Saga/最终一致，见[第三阶段](../章节3/01-第三阶段-分布式系统核心技术.md)）；"我的订单"页要聚合四个服务；一次排查跨多条日志。这就是用复杂度换伸缩性。

### 2.2 服务通信、API 网关、服务治理

| 维度 | 同步（REST / gRPC） | 异步（消息 / 事件） |
|---|---|---|
| 耦合 | 调用方要知道对方的地址与契约 | 只依赖事件契约 |
| 可用性 | 被调挂则调用方受牵连（需熔断） | 中间件存活即可继续 |
| 结果反馈 | 立即拿到（支付扣款必须） | 最终一致（生成配送任务可以等） |
| 流量模型 | 点对点放大 caller 的压力 | 削峰、缓冲、一对多广播 |

原则：**需要立即结果的用同步（扣款、锁库存），能容忍延迟的用异步（排线、押金记账、营销发券）**。

❌ **反例：无超时、无熔断的同步调用**

```kotlin
class PaymentClient(private val rest: RestTemplate) {
    fun charge(order: Order): Receipt =
        rest.postForObject("/payments", PayRequest(order.id, order.total), Receipt::class.java)!!
    // 没有超时：支付服务一次 GC 停顿 30s，交易服务的线程池被拖干，整个商城没人能下单
}
```

✅ **修正：显式超时 + 熔断 + 降级**

```kotlin
class PaymentClient(private val web: WebClient) {
    // 显式超时，快速失败，把故障控制在局部；外层再套 Resilience4j 熔断器
    suspend fun charge(order: Order): Receipt = withTimeout(2.seconds) {
        web.post().uri("/payments")
            .bodyValue(PayRequest(order.id, order.total))
            .retrieve()
            .awaitBody<Receipt>()
    }
    // 熔断打开后的降级：订单标记 PENDING_PAYMENT，交给补偿任务重试，而不是无限等待
}
```

**API 网关**的职责：统一入口的路由、鉴权、限流、协议转换、响应聚合。桶装水的入口画像：C 端小程序/APP（商品、下单、订阅管理）、配送员端 APP（任务与路线）、运营后台——三类端走同一网关，但鉴权方式（用户 token vs 员工账号）与限流策略各不相同；`GET /order-detail` 由网关聚合订单 + 商品 + 配送任务 + 押金状态四个服务。注意网关最容易被腐化成"上帝层"：**业务规则不应写进网关**；聚合逻辑变复杂时下沉到 BFF（如"配送员端 BFF"专门聚合路线 + 任务 + 客户地址 + 空桶应收；模式展开见 5.1）。

**服务治理**清单：注册发现（K8s Service / Nacos / Consul，排线服务多实例按 CPU 弹性伸缩）、配置中心、熔断降级与舱壁隔离、链路追踪（traceId 贯穿"下单 → 支付 → 排线"全链）、集中日志与指标。治理细节（一致性、可观测性）在[第三阶段](../章节3/01-第三阶段-分布式系统核心技术.md)展开。

### 2.3 微服务的代价：什么时候不该用微服务

| 代价 | 具体表现 | 桶装水场景 |
|---|---|---|
| 分布式事务 | 下单成功但扣库存失败，需要 Saga/补偿 | 付了钱没扣水 = 超卖事故 |
| 网络不可靠 | 超时后"到底成没成功？" | 支付超时后盲目重试 = 重复扣款，必须幂等 |
| 测试复杂 | 无法在一个进程内跑完用例 | "下单送水"一个用例要起 4 个服务，需要契约测试 |
| 运维成本 × N | N 套 CI/CD、监控、告警、oncall | 3 人团队维护 20 个服务 = 灾难 |
| 读一致性 | 不再有一致性读 | 下单成功后立刻查"我的订单"可能查不到 |
| 排查难度 | 一个请求跨 6 个服务 | 没有 traceId 就是盲人摸象 |

**不该用的信号**（满足越多越不该上）：团队小于 10 人；领域还在剧烈变化（边界认知不清，拆了必返工）；没有独立扩展需求；缺乏 CI/CD 与监控基础设施；动机只是"大厂都在用"。

**主线审判：桶装水商城该不该上微服务？** 设定现实画像：一个 10 人上下的团队、日订单几万、读多写少。逐条对照信号——团队规模贴线；领域边界经模块化单体已趋稳定；独立扩展需求真实存在的只有两处：商品读洪峰（先上缓存 + 读写分离即可解决大半，见[第三阶段](../章节3/01-第三阶段-分布式系统核心技术.md)）与排线算法的 CPU。合理结论是"**模块化单体为主 + 至多拆一个排线服务**"，而非全面微服务化。这也说明：本节演示的"五服务架构"是教学推演，真实决策永远从代价清单出发，而不是从模式出发。

经验法则（Sam Newman《Monolith to Microservices》）：**先单体（最好是模块化单体），确有需要时用"绞杀者"模式渐进拆出第一个服务**——选扩展性差异最大的部分（如排线算法、图片处理），而不是订单核心链路（绞杀四步展开见 2.5）。

### 2.4 历史对照：SOA（面向服务的架构）

**概念**：SOA 比微服务早十年（2000 年代主流）：把系统能力封装为可复用的"服务"，通过**企业服务总线（ESB，Enterprise Service Bus）**统一接入——报文转换、协议适配、路由、流程编排、集中治理都长在总线上。典型形态：各业务系统（含大量遗留系统）把功能发布成 Web Service（SOAP/WSDL），总线负责让异构系统互相说得上话。

同一个"服务化"方向，两个时代给出的答案：

| 维度 | SOA | 微服务 |
|---|---|---|
| 核心动机 | **集成**：让异构老系统互通复用 | **交付**：让小团队独立开发、独立部署 |
| 服务粒度 | 粗（按系统/大块能力） | 细（按业务能力与限界上下文，见 2.1） |
| 中介 | ESB：转换/编排/路由全做（智能总线） | 网关只做横切策略 + MQ 只搬字节（哑管道） |
| 治理 | 中心化（总线团队、全局标准） | 去中心化（谁建设谁运营） |
| 数据 | 常共享库、共享大模型 | 每服务私有库（见 2.3 代价表） |

❌ **反例：智能总线、哑端点**

```kotlin
// 所有转换与编排逻辑长在 ESB 里：每对接一个系统，总线就长一对转换器
class OrderEsb {
    fun route(msg: Map<String, Any?>, target: String): Any? = when (target) {
        "billing"   -> toBillingFormat(msg)      // 财务系统要的报文
        "logistics" -> toLogisticsFormat(msg)    // 物流系统要的报文
        "erp"       -> toErpFormat(msg)          // ERP 要的报文
        else -> msg
    }
    // "下单→扣款→通知仓储"的流程编排也在这里：ESB = 全局单点 + 全公司需求瓶颈
}
```

病根与网关腐化、BFF 职责漂移（见 2.2、5.1）是同一个：**中介层吞了业务逻辑**。业务规则散落进总线，服务本身越来越"薄"；改一个编排步骤要总线团队发版；总线成为全公司的性能与可用性单点。

✅ **微服务的修正**：逻辑收回服务内部（"智能端点"），中介退化成哑管道——API 网关只做路由/鉴权/限流等横切策略（见 2.2），系统间搬运交给消息队列（见 3.1）。对照记忆：**ESB 之于 SOA ≈ 上帝层网关之于微服务**——都是中介腐化，解毒剂都是"策略与业务分离"。

### 2.5 渐进拆分：绞杀者模式与数据拆分

（2.3 的审判结论是"模块化单体为主 + 至多拆一个排线服务"；本节讲"真要拆时，怎么拆才不翻车"。）

**绞杀者模式（Strangler Fig）**：不做一次性重写，而是在旧系统前面立一个**分流入口**，让新服务一点点接管流量，旧系统被逐步"绞杀"到只剩壳，最后删除。Martin Fowler 2004 年命名，灵感来自绞杀榕：缠着宿主树生长，宿主枯死后自己长成独立的新树。前置条件只有一个：入口处有能拦截请求的分流点（网关或门面层）；没有统一入口的遗留系统要先补门面，否则绞杀无从下手。

四步循环（以"拆出排线服务"为例）：

1. **立分流入口**：网关把"生成排线"请求按规则路由到新旧两条路径，初期 100% 走旧模块——新服务没接管任何真实流量，只是先"挂上去"。
2. **影子对拍**：放量前先跑影子流量——同一批历史配送工单同时发旧模块与新服务，**只比对不生效**；比对口径：排线方案差异（路线、装载、时间窗）、耗时、约束违反数。差异清单收敛（或逐条确认"新逻辑才是对的"）后才放量。这一步把"行为对等"从切换夜的赌局变成可量化验收的日常检查。
3. **灰度切流 + 预设回滚条件**：小比例放量（如 5%），错误率 / P99 时延超阈值**自动全量回退旧路径**。桶装水按**配送站维度**切最自然——排线按站点出结果，一个站的流量要么全新要么全旧，不会出现同一站两套排线互相踩。
4. **收尾**：流量 100% 后旧模块**冻结**（只修 bug 不加功能）→ 观察一个完整业务周期（月结、一次大促）→ 删除旧代码与表。删代码之前，旧路径始终是回滚保险，不能提前拆。

❌ **反例：大爆炸重写（Big Bang Rewrite）**

> 新排线服务"功能写完了"，选个周末停旧上新。上线当天客服炸锅：山顶配送没人接单、暴雨加时规则没了、婚庆大单（一次 200 桶）排不进去——旧单体里沉淀着五年攒下的 17 条热修补丁规则，重写团队只对着文档实现了 9 条。

一次性重写的死穴：旧系统的真实行为散落在历次热修里，没有完整文档，"功能对等"永远在切换日被发现不对等。绞杀者的影子对拍正是针对这一点——拿真实历史流量逼出新旧行为的全部差异。

**数据拆分才是硬骨头**：代码好搬，数据难拆。拆服务必须配套拆数据，否则 2.1 误区表里"共享数据库"的耦合原封不动。三阶段路径：

| 阶段 | 形态 | 得到 | 还欠什么 |
|---|---|---|---|
| ① 共库不同 schema | 同一库实例按 schema 划账 | 归属清晰了一半 | 资源/锁仍竞争，改表结构仍要协调 |
| ② 逻辑私有 | 权限隔离：每个服务只有自己 schema 的读写权限 | 直连别人表在权限层就报错，耦合**显性化** | 仍是物理共库，容量与故障域没分开 |
| ③ 物理独立 | 独立库实例 | 独立扩容、独立备份、故障隔离 | 跨库 join 没了、事务没了（见[第三阶段](../章节3/01-第三阶段-分布式系统核心技术.md)第 4 节） |

迁移的顺序原则：**先断别人对我表的直连，再断我对别人表的直连，最后才搬库**——直连不断就搬库，切换瞬间全家报错。同步过渡期：旧表写完同步写新库（或发事件），加一条对账任务核对差异；落地机制（本地消息表）在[第三阶段](../章节3/01-第三阶段-分布式系统核心技术.md) 4.5 展开。

**跨服务查询的三种替代**（共库 join 没了之后，"我的订单"页要显示配送状态怎么办）：

| 方案 | 做法 | 取舍 | 适用 |
|---|---|---|---|
| API 组合 | 展示时逐个调订单、配送、押金服务再拼装 | 强新鲜；链路长、可用性受牵连、往返多 | 管理后台等低频页 |
| 事件复制本地读 | 订单服务订阅配送任务事件，在本地维护只读状态字段，读自己的库 | 读快读稳；最终一致（秒级延迟），要建副本 | C 端高频页 |
| 报表另建 | 跨全业务的统计对账走独立报表库（ETL / CDC 定期拉数） | 不占交易链路；数据非实时 | 月度对账、经营报表 |

> 第三行"事件复制本地读"就是 3.2 CQRS 读侧的最小形态——微服务的跨服务查询问题在这里自然接轨 CQRS。

**拆错了可以合回来**：粒度校准不是单向门。合并信号：两个服务永远同发同部署；边界内高频互调（成对出现的秒级往返）；一个需求总是同时改两个代码库。处理：先合库共事务过渡，再合代码。《Monolith to Microservices》专门有"合并"一章——敢拆也敢合，才是把粒度当权衡，而不是信仰。

（完整可运行版：[microservices/StranglerRouting.kt](microservices/StranglerRouting.kt)——影子对拍、按站灰度与错误率自动回滚；[microservices/QueryFromJoinToApi.kt](microservices/QueryFromJoinToApi.kt)——join → API 组合 → 事件复制三阶段的延迟与耦合对比。均已实际编译运行验证。）

### 2.6 契约管理与向后兼容：独立部署的前提

**概念**：微服务"可独立部署"成立的前提是——**我改自己，不会弄坏别人**。承载这个承诺的就是服务契约：接口的报文结构 + 字段语义 + 错误码承诺。没有兼容纪律，每次改接口都得拉着所有消费方同步发版，"独立部署"名存实亡——这是分布式单体最容易忽视的一种成因（另两类：按技术层拆、共享数据库，见 2.1、2.5）。

生产端纪律（向后兼容规则清单）：

- **只加不改不删**：新增字段一律可选；旧字段含义永不漂移（`amountFen` 永远是"分"；含税不含税，二选一后不再动）。
- **取值域只扩不缩**：订单状态新增 `PARTIAL_DELIVERED` 可以；把 `DELIVERED` 改名或重定义不行。
- **错误码只增不改**：消费方对未知错误码按"未知失败"兜底。
- **要减先弃用**：标记 deprecated → 兼容窗口内新旧并存（双字段或双版本路由）→ 消费方全部迁完 → 删除。

消费端纪律——**宽容读者（Tolerant Reader）**：反序列化只提取自己关心的字段，忽略未知字段；但必填字段缺失时**显式失败**，不悄悄拿默认值硬撑。反模式是严格解析：遇到未知字段就抛异常——等于宣告"生产端永远不许动报文"，把对方锁死。

❌ **反例：两类契约破坏**

```kotlin
// 生产端：price 改名 unitPrice，且单位从"分"悄悄改成"元"
// 消费端 A（严格解析器）：字段对不上直接抛异常 → 下单全线报错，【loudly 坏】
// 消费端 B（宽容读者但无语义断言）：读不到 price，静默取 0 → 钱算错一百倍，【softly 坏】
```

两类破坏里最贵的是第二种：**静默语义漂移**——解析不报错、账算错一个数量级，等对账发现已损失一个账期。所以宽容读者必须配合契约测试的语义断言：**"宽容"只针对结构，绝不针对语义**。

✅ **修正：结构宽容 + 语义卡口**

```kotlin
data class PriceView(val amountFen: Long) {
    companion object {
        fun from(msg: Map<String, Any?>): PriceView {
            val raw = msg["amountFen"] ?: msg["price"]     // 新旧字段名都认——兼容期并存
                ?: throw IllegalStateException("契约破坏：amountFen 缺失，拒绝静默兜底")
            return PriceView((raw as Number).toLong())     // 语义承诺：单位永远是"分"
        }
    }
}
// 生产端契约测试（跑在 CI）：断言报文含 amountFen 且单位为分——"改单位"这类变更在这里被卡住
```

**消费者驱动契约（Consumer-Driven Contracts）**：契约不由生产端单方面定——**谁消费，谁提交一份"我依赖哪些字段、断言什么语义"的契约**；生产端每次改接口，先在 CI 里跑全部消费方的契约测试，全绿才能发布（Pact 是这类工具的代表）。契约测试 ≠ 集成测试：它只验证"承诺"本身，不需要把服务真的拉起来——正面回应 2.3 代价表的"测试复杂"：把"起 4 个服务的集成用例"大幅压缩为"每个服务对着契约文件跑单测"。

**共享库的边界**：可以共享的只有两类——

1. **与业务无关的基础设施**：日志格式、traceId 透传、重试工具（各自独立发版，多版本并存）；
2. **契约本身**：薄的 DTO / schema / proto 文件，作为接口定义发布给消费方。

不能共享的是**领域模型**。把 `User`、`Order` 实体抽成 common-domain-lib 让所有服务引用，看似"避免重复定义"，实则把 2.1 辛苦划出的边界重新焊死：商城域的"订单"（价格、支付状态）和配送域的"订单"（桶数、楼层、时间窗）本来就应该是两个类。领域不共享、重复定义是**特性**不是缺陷——重复正是解耦的代价与凭证。共享领域库是最隐蔽的一种分布式单体成因，且它常常打着"代码复用"的旗号出现。

（完整可运行版：[microservices/ContractEvolution.kt](microservices/ContractEvolution.kt)——三代报文在严格读者 / 宽容读者上的兼容矩阵，以及语义断言如何卡住"改单位"。已实际编译运行验证。）

## 3. 事件驱动架构

（场景切换：本节主线取 MES 与物联网平台，IM 辅助讲消息语义；桶装水主线在 3.1 末尾"订单事件驱动化"处收尾。）

### 3.1 发布订阅、消息队列

**概念**：组件之间通过**事件**（已发生的事实，用过去时态命名）间接通信：生产者只负责"宣布发生了什么"，不关心谁在听；消费者各自订阅、各自处理；消息队列（Broker）在中间承担路由、缓冲与持久化。

它买到三样东西：
- **解耦**：交易服务发布 `OrderPlaced`，库存/配送/押金/营销各订各的；新增一个"大数据分析"订阅者，交易服务零改动。
- **削峰**：物联网平台一台设备秒级多条上报、海量设备并发，同步逐条 INSERT 数据库必挂——上报先进队列，消费者按自己的节奏批量聚合写入；存储抖动时接入层照收不误（背压与流控在[第三阶段](../章节3/01-第三阶段-分布式系统核心技术.md)展开）。
- **交付语义**：主流是 at-least-once（至少一次）→ **消费者必须幂等**。IM 把这一点演到极致：消息必达靠 ACK + 重发，不重靠消息 ID 幂等去重——"至少一次 + 去重"逼近"恰好一次"；同一会话内还要不乱序（按会话分区串行消费）。

常见中间件速览（选型深入在[第三阶段](../章节3/01-第三阶段-分布式系统核心技术.md)）：

| | Kafka | RabbitMQ | 云托管（RocketMQ/SNS 等） |
|---|---|---|---|
| 模型 | 分布式日志，可重放 | 传统队列 + 交换机路由 | 免运维 |
| 顺序 | 分区内有序 | 队列内有序 | 依产品而异 |
| 回溯消费 | 支持（offset） | 不便 | 依产品而异 |
| 适合 | 高吞吐事件流（设备采集、MES 报工流） | 任务队列、低延迟路由 | 不想自建集群 |

❌ **反例：把命令当事件 + 胖事件 + 消费者改写别人的库**

```kotlin
// "事件"里带着命令口吻，还把整个订单实体连同内部字段都塞进去
data class DoReserveAndArrangeEvent(
    val command: String = "reserve_and_arrange_delivery",  // 这是指令，不是事实
    val order: OrderEntity,                                // 共享实体：改一个字段，所有消费者跟着改
)

class DeliveryConsumer(private val jdbc: JdbcTemplate) {
    fun onEvent(e: DoReserveAndArrangeEvent) {
        jdbc.update("UPDATE orders SET status = 'ARRANGED' WHERE id = ?",  // 消费者改写订单库！
            e.order.id.toString())
    }
}
```

问题：契约耦合（共享实体定义）、破坏数据所有权（消费者写订单表）、命令式命名让新增订阅者误解语义。

✅ **修正：过去时态事件 + 最小契约 + 幂等消费**

```kotlin
sealed interface OrderEvent {
    val orderId: OrderId
    val occurredAt: Instant
    data class OrderPlaced(
        override val orderId: OrderId,
        val lines: List<OrderLineDto>,      // 只带消费者需要的最小字段
        override val occurredAt: Instant,
        val version: Int = 1,               // 契约版本，演进时向后兼容
    ) : OrderEvent
}

class DeliveryConsumer(private val delivery: DeliveryService) {
    fun onEvent(e: OrderEvent.OrderPlaced) {
        if (delivery.alreadyHasTask(e.orderId)) return      // 幂等：at-least-once 的必配
        delivery.createTask(e.orderId, e.lines)             // 生成配送任务，进入排线
    }
}
```

**主线收尾：桶装水订单事件驱动化。** 微服务化后，交易服务若还要同步调用四个下游（订阅、配送、押金、营销），任何一家抖动都会拖垮下单。最后一步改造：下单成功只发布 `OrderPlaced`，其余各自订阅——

```
OrderPlaced ──▶ 周期购订阅：记录本期已送，计算下期触发时间
           ──▶ 配送：生成配送任务，进入排线
           ──▶ 押金：首单记账（押金应收 / 桶在手）
           ──▶ 营销：核销优惠券、累积会员积分
```

前后对比——解决了：下单可用性与下游解耦（押金服务挂了照样下单，记账滞后补上）；新增消费者零改造。付出了：最终一致（下单后数秒配送任务才生成）；排查从"一条堆栈"变成"一条消息链"；要防重复与乱序（幂等 + 版本号）。至此桶装水的演进闭环完成：**分层单体（起步）→ 模块化单体（纪律）→ 微服务（伸缩与隔离）→ 事件驱动（解耦与弹性）**，每一步都是一次明确的权衡。

**权衡**：事件驱动换来弹性与解耦，付出的是最终一致（下单后约百毫秒后续动作才发生）、排查链路变长（需要消息级追踪）、重复与乱序防御（幂等 + 版本号）。

### 3.2 事件溯源（Event Sourcing）与 CQRS

**场景切换：MES 批次追溯——事件溯源思想的最佳载体。** 制造现场要回答"这批产品用了哪几批料、经过哪些工序、谁在什么时间报的工"：投料、报工、质检本身就是一串不可变事实，批次谱系是一条天然的事件链。如果只存"当前状态表"（当前工序、当前用料），历史投料关系会被后续工序覆盖丢失，追溯无从谈起。

**事件溯源**：不存"当前状态"，只存**追加式（append-only）的事件序列**；状态 = 事件回放。批次的表从 `batch(step, material)` 变成 `batch_events(batch_id, seq, type, payload, at)`。

```kotlin
sealed interface BatchEvent {
    data class MaterialIssued(val batchId: BatchId, val stepId: StepId,
        val materialBatchId: BatchId, val qty: Int, val at: Instant) : BatchEvent
    data class OperationCompleted(val batchId: BatchId, val stepId: StepId,
        val outputQty: Int, val operator: String, val at: Instant) : BatchEvent
    data class QualityInspected(val batchId: BatchId, val passed: Boolean, val at: Instant) : BatchEvent
}

// 状态由事件折叠（fold）而来，"当前状态"只是缓存；追溯 = 沿事件链回放
fun rebuild(events: List<BatchEvent>): Batch = events.fold(Batch.initial()) { b, e -> b.apply(e) }

class Batch private constructor(
    val id: BatchId,
    val passedSteps: List<StepId>,        // 经过哪些工序
    val upstreamBatches: Set<BatchId>,    // 用了哪几批料——谱系由事件自然累积
) {
    fun apply(e: BatchEvent): Batch = when (e) {
        is BatchEvent.MaterialIssued    -> copy(upstreamBatches = upstreamBatches + e.materialBatchId)
        is BatchEvent.OperationCompleted -> copy(passedSteps = passedSteps + e.stepId)
        is BatchEvent.QualityInspected  -> this
    }
}
```

价值：完整审计与时间旅行（"这批为什么被判不合格？"回放即知）、天然产出事件流喂给分析与 CQRS。代价：查询难（"查所有待检批次"要全量回放）→ 必须配 CQRS；事件 schema 要版本化演进；学习与运维成本高。**适合资金、审计、批次追溯、复杂状态机领域（押金生命周期状态机同理）；不适合简单 CRUD。**

**CQRS**（命令查询职责分离）：MES 里两种读的负载完全不同——实时生产看板（高频写 + 聚合读）与月底报表（全量分析）不该压在同一个模型上。写模型（Batch 聚合 + 事件）与读模型（看板投影表、报表库）彻底分开，中间靠事件异步同步。

```kotlin
// 写侧：只接受命令、产出事件
class ReportWorkHandler(private val store: EventStore) {
    fun handle(cmd: ReportWorkCommand) {
        val batch = rebuild(store.eventsOf(cmd.batchId))
        store.append(cmd.batchId, batch.complete(cmd.stepId, cmd.outputQty, cmd.operator))
    }
}

// 读侧：投影器消费事件，维护一张查询友好的宽表
class DashboardProjection(private val dao: DashboardDao) {
    fun on(e: BatchEvent) = when (e) {
        is BatchEvent.OperationCompleted -> dao.addStepOutput(e.stepId, e.outputQty)
        else -> Unit
    }
}
// 看板查询变成一条 SQL：SELECT step_id, SUM(output_qty) FROM dashboard GROUP BY step_id
```

注意：CQRS 可独立于事件溯源使用（读写分模型、分库即可），两者常一起出现但**并不绑定**。读模型必然滞后（最终一致）——报工后看板晚几百毫秒无伤大雅；但"质检不通过就拦下流转"这类决策不能读投影，必须走写侧或同步校验。同一系统里，**容忍滞后的读交给投影，不容忍的读回到写侧**。

**把写侧做对：追加原子性与乐观并发控制。** 上文 `store.append` 看似只是"往列表加一条"，并发下却是正确性的命门。就用桶装水的**押金账户**（开头说过"押金生命周期状态机同理"，这里把它做出来）演示：一个用户一条事件流，不变式是**累计退桶数 ≤ 累计交桶数**。反例：两个"退 1 桶"请求同时到达，都读到"可用 1 桶"、都通过校验、都追加成功——用户退了没交过的桶，押金池透支。事件溯源里这类超卖/超退问题落在**追加**这一步，解法是把数据库乐观锁搬进事件库：**append 带上 expectedVersion（决策时看到的流长度），库端原子校验，不符即拒**；命令方收到冲突不是报错，而是"重读最新状态、重新校验、再追加"的信号。

✅ **修正：追加带版本校验 + 命令侧冲突重试**（完整可运行版：[es-cqrs/DepositWriteSide.kt](es-cqrs/DepositWriteSide.kt)，本例已实际编译运行验证）

```kotlin
fun append(userId: String, expectedVersion: Int, newEvents: List<DepositEvent>) {
    val s = streams.getOrPut(userId) { Stream() }
    if (s.events.size != expectedVersion) throw ConcurrencyException(expectedVersion, s.events.size)
    s.events += newEvents   // 校验与写入必须原子——生产中靠 UNIQUE(stream_id, version) 约束兜底
    ...
}

// 命令侧：冲突不是错误，是"重来"的信号
while (true) {
    val acc = store.load(userId)
    val ev = acc.refund(buckets, at)                  // 决策时点：聚合里校验不变式
    try { store.append(userId, acc.version, listOf(ev)); break }
    catch (e: ConcurrencyException) { /* 提交时点被拒 → 重读重判 */ }
}
```

demo 运行结果节选：交 2 桶退 1 桶后，两个并发"再退 1 桶"——A 提交成功；B 因版本不符被拒（`命令基于版本 2 决策，流已是版本 3`）；B 重读后发现可用已为 0，不变式把超退真正拦下。**校验写在聚合里（决策时点），原子性守在追加处（提交时点），两层合起来才封得住并发口子。**

**快照：事件流变长的止痛药。** 用户用三年，押金流几百条事件，每次 load 全量回放明显变慢。解法：每 N 条事件落一次**快照**（状态定格），load = 快照 + 增量事件。两条纪律：**快照是缓存不是事实**——丢了就从事件流重建，删了系统照样正确、只是变慢；**先追加后拍照**——同一聚合的追加与快照更新次序不能反。demo 里 `snapshotEvery = 4`（教学取小值，生产通常 100+ 条一拍），运行打印"事件流 6 条，快照版本 4——load 只回放其后 2 条增量"。

**事件 schema 演进：事件不可变，但业务会变。** 2024 年押金全站统一 50 元/桶，事件只记桶数；2025 年按桶型定价，单价必须进事件。❌ 反例：回头修改 v1 事件的字段含义、或给历史 payload 直接塞新字段——已存数据读出来对不上，旧账静默算错，审计直接失真（"时间旅行"旅行到假历史）。✅ 修正：**历史事件一条不改**，演进靠三招：① 新事件类型替代旧类型（写侧切换，老事件照存）；② **读时升级（upcasting）**——回放读出 v1，按"当时的业务事实"补齐新字段再进 fold；③ 事件带 schema 版本号，升级规则写成代码并配测试。押金定价演进的完整例：

```kotlin
// 读时升级（完整可运行版：[es-cqrs/DepositSchemaUpcast.kt](es-cqrs/DepositSchemaUpcast.kt)，本例已实际编译运行验证）
fun upcast(e: Any): DepositEvent = when (e) {
    is DepositPaidV1     -> DepositEvent.Paid(e.userId, e.bucketCount, unitCents = 5_000L)  // 2024 统一价 50 元/桶
    is DepositPaidV2     -> DepositEvent.Paid(e.userId, e.bucketCount, e.unitCents)
    is DepositRefundedV1 -> DepositEvent.Refunded(e.userId, e.bucketCount, e.refundCents)
    else -> throw IllegalArgumentException("未知事件形态：$e")
}
// 新旧事件同一条 fold 链回放：李四 2024 年交的桶按 50 元、2025 年按 80 元，余额分毫不差
```

**投影工程化：检查点、幂等与重建。** 上文的投影器是"收到事件就更新"的玩具版，工程化补三件事：① **检查点**——投影记录已消费到的全局序号，重启从检查点续跑而不是从头；② **幂等**——经消息队列至少一次送达（见 3.1），同一事件可能被消费多次，按全局序号/事件 ID 去重；③ **重建**——投影表被误删、口径要改、或想新增一个投影（报表库、搜索索引）？清空、检查点归零、从事件流全量重放即可。demo 的 `RefundStatsProjection` 演示了追赶 → 模拟误删 → 重建，前后统计一致。一句话：**读模型是可丢弃缓存，事件流才是唯一事实**——"状态 = 事件回放"在读侧的镜像。

**CQRS 渐进谱系：别一步到位。** CQRS 不是开关，是刻度盘。多数系统走到 L1/L2 就该停，L3 只属于写不变式复杂或确有审计追溯诉求的子域：

| 级别 | 形态 | 付出 | 适用信号 |
|---|---|---|---|
| L0 | 同一模型读写（默认） | 无 | 绝大多数 CRUD |
| L1 | 读写分模型、同库 | 两套映射代码 | 读写形状差异大（列表页 vs 表单） |
| L2 | 读写分库 | 最终一致 + 同步设施 | 读多写少、读写争抢（桶装水商品读洪峰，见 2.3） |
| L3 | 事件驱动投影（常配事件溯源） | 全套复杂度：投影运维、滞后处理 | 复杂写不变式 + 多种读形状（MES 看板/报表）、审计追溯刚需 |

配套一道必答题：**读自己写**。用户退桶后立刻刷"我的押金"页，投影还没同步——账面没变，用户以为失败再点一次。处置还是那条纪律的两端：写后立读的关键页面回写侧查（或等投影追上再返回），容忍滞后的读才交给投影。

❌ **反例：小团队一步登天。** 5 人团队、日订单几千的桶装水商城，一上来 Axon + 事件溯源 + CQRS 全家桶：本该一个方法解决的"改地址"变成命令、聚合、事件、upcaster、投影五件套——复杂度陡增（见阶段总结权衡表）而收益为零。
✅ **修正：从 L0/L1 起步，痛点真实出现再逐级升级；只有 MES 批次追溯、押金/资金这类子域才值得 L3。**

**选型与边界：事件存哪里、什么时候别用。** 事件存储三个候选：① **关系库单表**（`stream_id, version, type, payload, at`，`UNIQUE(stream_id, version)` 兜并发）——大多数场景的最优解，别嫌土；② 专用事件库（EventStoreDB、Axon Server）——按流读、订阅、投影开箱即用，代价是多一套基础设施；③ **Kafka 当事件存储？** 它确实 append-only，但按聚合随机读不友好（按分区扫，无法按 stream_id 点查）、也没有 per-stream 唯一约束兜并发追加。正确分工：**事件库存事实，Kafka 做投影分发管道**（事件库 → Kafka → 各投影消费）。最后一条边界辨析：**事件溯源 ≠ 审计日志 / binlog**——审计日志记录"存储层的行被改成了什么"（`UPDATE deposit SET balance = ...`），事件溯源记录"业务上发生了什么"（`DepositRefunded：退 1 桶`）；前者是技术产物，后者是领域语言（呼应本阶段自测第 4 题）。什么时候都别用：简单 CRUD、团队没踩过坑又没人力补课、读多写少无审计诉求——命中任意一条，上事件溯源就是自购复杂度。

### 3.3 事件的形态谱系：通知、携带状态转移与溯源

3.1 的反例治"胖事件"，但反向走极端——事件瘦到只剩一个 ID——同样有坑。把事件的"携带量"排成谱系，正好是 Martin Fowler 的三档分法：

| 形态 | 事件里带什么 | 消费者怎么拿数据 | 代价 |
|---|---|---|---|
| 事件通知（Event Notification） | 只带标识（`ticketId`） | 回查上游查询接口 | 回查风暴、读耦合、时点漂移 |
| 事件携带状态转移（ECST，Event-Carried State Transfer） | 各消费者决策所需的最小事实快照 | 直接用事件载荷，可物化本地副本 | 字段冗余，"最小"边界要守 |
| 事件溯源（Event Sourcing） | 事件即事实，状态 = 回放 | 重建 / 投影（见 3.2） | 全套复杂度（见 3.2 选型边界） |

❌ **反例：瘦事件的回查风暴。** 工单中心发布 `TicketResolved`（只带 ticketId），通知、看板、SLA 三个消费者各自回查工单查询接口：一次解决 = 3 次回查，订阅者翻倍回查翻倍；更要命的是**查询接口一挂，全体消费者瘫**——事件买到的时间解耦，被一次回查连本带利卖了回去（读依赖原地复活）。还有一个隐蔽坑：**时点漂移**——回查拿到的是"消费时点的当前状态"，不是"事发时点的事实"。工单解决后被运营改判分类，回查式看板把同一次解决先后计入两个分类，统计口径悄悄失真。

✅ **修正：ECST——事件携带事发时点的事实快照。** `TicketResolved` 带上 reporterId、解决时点的分类、解决时长：三个消费者零回查；看板还能把事件**物化成本地副本**（自己维护一张按分类计数的表），从此连读都不依赖工单服务——解耦从"时间、空间"扩展到"读"。demo 运行对照（完整可运行版：[event-driven/EventStyles.kt](event-driven/EventStyles.kt)，本例已实际编译运行验证）：风格 A 一次事件回查 3 次、工单改判后看板统计漂移（同一次解决先后计入「机械故障」「电气故障」）；风格 C 回查 0 次，本地副本 `{机械故障=1}` 不受改判污染。

**边界：ECST ≠ 胖事件。** 谱系两端是同一个坑的两副面孔——瘦事件把耦合藏在回查里，胖事件把耦合写进契约里（3.1 反例：整实体入事件，加一个字段全体消费者跟着改）。判据一句话：**字段进不进事件，看"有没有消费者要拿它做决定"，不看"实体里有没有"**；诊断日志、解决说明这类无人决策的字段一概不带。反向确认：如果消费者需要的本来就是**最新状态**（处理动作前先看工单此刻到哪一步），那是命令式的同步查询，本来就该走查询 API，而不是塞进事件。

**取舍**：通知买最小契约、留读耦合；ECST 用冗余买断读依赖；溯源把状态本身交给事件（复杂度见 3.2）。谱系逐级加码，按消费者数量与读隔离的真实需求停档——单一内部消费者，通知 + 回查完全够用。

### 3.4 补充场景：事件驱动还落在哪

前两节的主线（MES / 物联网 / 桶装水）之外，把大纲里的经典场景在事件驱动视角下过一遍——重点是识别共性信号，深入内容在各场景的主章节：

| 模式 | 场景（深入章节） | 事件驱动解决什么 | 付出的代价 / 注意点 |
|---|---|---|---|
| 削峰填谷 | 秒杀抢购（第三阶段缓存与限流） | 瞬时洪峰先入队，消费者按数据库能力匀速扣减建单 | 交互模式改变：用户看"排队中"而非即时结果；要积压监控与超时降级 |
| 扇出记账 | 支付与清结算（第三阶段分布式事务） | 支付成功事件扇出发货 / 记账 / 积分 / 分账，互不阻塞 | 双写裂缝要 Outbox 兜；日终对账不可省 |
| 延迟触发 | 桶装水周期购续订、工单 SLA 超时升级（第三阶段选型题） | "到期才发生"的事（下期订单、超时升级）交给延迟消息 | 与"任务表定时扫描"二选一；消费端按业务键幂等防重复触发 |
| 状态广播 | 工单流转、IM 在线状态 | 状态一次变更多方感知：IM 通知、看板、SLA 计时器各自订阅 | 即 3.3 的形态选择题：通知还是携带状态 |
| 计量事件流 | 多租户 SaaS 用量与配额（第三阶段限流） | API 调用 / 存储用量先记事件，异步聚合成计量，再出账计费 | 计费最终一致；配额硬拦截需同步判定，不能等异步聚合 |
| 采集管道 | 物联网上报、MES 报工流（3.1 已讲） | 上报先进队列，消费者按下游节奏批量写入 | 背压与流控（第三阶段） |

看点不是背表，是提炼**共性信号**——每行至少命中一条：**一个事实发生后有多方关注**（扇出）；**洪峰与处理速度不匹配**（削峰）；**动作要在未来某时点发生**（延迟）。命中任一信号，事件驱动进入候选；三条都不沾，老老实实请求-响应。再加第四条隐性信号：**上游不该知道下游的存在**（3.1 大数据订阅者零改造）——组织上要独立演进的边界之间，事件是默认语言。

### 3.5 优缺点与取舍：什么时候选事件驱动

**买到什么（优点）**：
- **解耦三件套**：时间解耦（下游挂了上游照发）、空间解耦（生产者不认识消费者）、读解耦（ECST 物化副本，3.3）。
- **弹性与故障隔离**：单个消费者故障不拖垮发布方与其他消费者，重试各自进行。
- **削峰填谷**：把瞬时洪峰摊平成下游可承受的匀速流量（3.1 物联网、3.4 秒杀）。
- **独立伸缩**：消费者各自按积压伸缩，互不绑架。
- **可演进**：新增行为 = 新增订阅者，老链路零改动。
- **审计与重放**：配合事件溯源得到时间旅行能力（3.2）。

**付出什么（缺点）**：
1. **最终一致成为默认**：用户可见滞后（下单后数秒配送任务才生成），关键页面要专门处理"读自己写"（3.2）。
2. **流程不可见**：一次业务动作散成一串异步消息，没有一处能看全链路——谁的锅、卡在哪，要靠消息级追踪与相关性 ID 才能回答（第五阶段可观测性）。
3. **重复与乱序防御**：at-least-once 下，幂等是每个消费者的入场费（3.1）。
4. **契约演进更难**：一个事件 N 个消费者，改字段 = 动 N 份契约——2.6 的兼容纪律在这里加倍适用。
5. **运维面变宽**：Broker 集群、积压监控、死信处理、消息留存，都是新增设施（第三阶段）。
6. **一致性裂缝**：DB 写成功而消息发丢的窗口，要靠 Outbox / 本地消息表补（第三阶段分布式事务）。

**两种拓扑：中介者（Mediator）与代理者（Broker）。** 事件流需要按流程推进（先扣款、再发货、再分账，某步失败要补偿）时有两种放法：**中介者拓扑**——中央编排器按流程依次触发并监听各步骤事件，流程集中可见、可控，代价是中心组件成为耦合点与单点；**代理者拓扑**——没有编排器，事件直接扇出、各消费者自行链式触发，极致松耦合、伸缩性好，代价是流程"只存在于各消费者的脑中"，出问题没人看得全。这与第三阶段 Saga 的编排 / 协同之辨同构（选型在那边展开）；经验法则：**流程要求可观测、可干预（支付清结算）偏中介者；纯事实广播（`OrderPlaced` 扇出）偏代理者。** 注意别与 4.5 的代理者模式混淆：那边讲的是"进程内对象间的消息中介"，这边讲的是"事件流要不要一个流程中枢"。

**同步还是事件？一道判定题。** 需要即时答复（下单当场返回订单号）或强一致决策（库存不足当场拒单）→ 同步调用；事实已定、多方关注、容忍秒级滞后 → 事件。真实系统常是两段拼装：**同步段守住"成不成"，事件段广播"成了之后"**——3.1 桶装水最后一步正是这个形态（下单事务同步完成，其余各自订阅 `OrderPlaced`）。

❌ **反例：万物皆事件。** 团队尝到甜头后走向极端：查询也改成"发查询请求事件、订阅查询结果事件"；单体内部两个模块的一次函数调用也要过 MQ；改个地址（本该一个方法）拆成命令、事件、投影三件套。延迟、幂等、排查三税全交，解耦收益为零——耦合本来就不存在，谈何消除。

✅ **修正：事件用在"事实发生后"的扇出点上；需要"回答"的地方保持请求-响应。** 起步姿势：核心链路同步 + 旁路事件化，随真实痛点（下游拖垮上游？新增关注方频繁改上游？洪峰打挂库？）逐段异步化——事件驱动是止痛药，先确诊再吃。

一句话接住 3.1 末尾的权衡：事件驱动用**最终一致、可观测性、契约纪律**换**解耦、弹性、削峰**——换不换取决于这三样付不付得起，而不是它流不流行。

## 4. 其他重要风格

### 4.1 管道-过滤器

（场景切换：Feed 流内容社区。）

**概念**：数据像水一样流经一串**过滤器**（独立的小处理步骤），由**管道**连接；每个过滤器不看全局，只做"输入 → 变换 → 输出"。Unix shell（`cat | grep | wc`）是鼻祖。

Feed 发布管道示例——一条帖子从发布到可见，流经审核与统计两级管道：

```kotlin
data class PostContext(val post: Post, val score: Int = 0, val blocked: Boolean = false)

// 每个过滤器只做一件事，可独立测试、自由重组
val machineReview: (PostContext) -> PostContext = { ctx ->      // 机审：涉政/色情识别
    ctx.copy(blocked = ctx.blocked || RiskModel.flag(ctx.post))
}
val quality: (PostContext) -> PostContext = { ctx ->            // 质量分：低质内容限流
    ctx.copy(score = ctx.score + QualityModel.score(ctx.post))
}
val hotSearchTap: (PostContext) -> PostContext = { ctx ->       // 旁路：热搜实时统计
    HotWordCounter.tap(ctx.post.text); ctx
}

// 管道 = 组合子；新增"地域合规过滤"只需再插入一个过滤器，其余代码零改动
fun publish(post: Post): PostContext =
    PostContext(post).let(machineReview).let(quality).let(hotSearchTap)
```

热搜榜是另一条流式管道：发帖/点击事件流 → 分词 → 计数 → 滑动窗口聚合 → 榜单更新，每个环节无状态、可并行、可分别扩容。

时间线生成则是一个点到为止的权衡预告：**写给所有人看（写扩散：发布时推到每个粉丝的时间线，读快写慢）还是读时聚合（读扩散：刷 Feed 时实时合并关注者的帖子，写快读慢）？大 V 百万粉丝把天平压向哪边？**这是"架构本质是权衡"的教科书案例，完整推演见[第六阶段](../章节6/01-第六阶段-实战与案例分析.md)的 Feed 流拆解。

适合流式/批量数据处理、编译器、规则链、推荐特征流水线。**不适合**需要全局事务、强交互（每步要看结果再决定走向）或有长生命周期状态的场景。权衡：换来可组合、可并行（无依赖的过滤器可并发执行），付出交互性差、错误处理要提前设计（异常如何沿管道传播）。

### 4.2 六边形架构（端口与适配器）、整洁架构、洋葱架构

（场景切换：工单中心——多渠道接入的标准案例。）

三者是同一思想的演进：**领域逻辑放中心，所有技术细节通过依赖倒置推到外圈，依赖方向永远指向内**。

| | 六边形（Cockburn, 2005） | 洋葱（Palermo, 2008） | 整洁（Martin, 2012） |
|---|---|---|---|
| 圈层语言 | 内核 + 端口 + 适配器 | Domain / Application / Infrastructure / UI | Entities / UseCases / Interface / Infra |
| 强调 | 对称性：左侧驱动适配器、右侧被驱动适配器 | 依赖规则 | 依赖规则 + 跨边界只传 DTO |

**演进脉络：同一个思想的三次命名。** 2005 年 Cockburn 提出"端口与适配器"，回答的问题是"**UI 和数据库凭什么站在架构图中央**"——他画成六边形（不是六层！）是为了表达"各边等价"：任何一条边都可以接一个驱动者，谁也不比谁特殊。2008 年 Palermo 的洋葱架构把它 DDD 化：画出同心圆、给内圈起名（Domain / Application），把"依赖只能向内"写成硬规则。2012 年 Martin 的博文《The Clean Architecture》把六边形、洋葱等图并列"收编"，统一成一套同心圆话术（2017 年成书《架构整洁之道》）。所以**三者不是三个候选选项，而是同一条依赖规则的三次命名**——先记共同内核：

```
传统 N 层（见 §1）：依赖自上而下        UI → 业务层 → 数据访问层 → 数据库
依赖规则（三者共同内核）：依赖永远向内    外圈(UI / DB / 框架) → 用例 → 领域
```

支点都是[第一阶段](../章节1/01-第一阶段-架构思维与设计基础.md)的依赖倒置：**接口（端口）由内核拥有，实现在外圈**——于是是"数据库适配我的领域"，而不是"领域迁就数据库"。

工单中心的接入画像：电话（呼叫中心话单转工单）、APP 用户自主提交、IoT 告警自动生成（售水机故障、水质异常）、外部系统转入（ERP/MES）——每个渠道报文格式各异，但工单内核必须稳定。

❌ **反例：渠道差异用 if-else 吞进领域层**

```kotlin
class TicketService {
    fun create(raw: Map<String, Any?>, channel: String): TicketId {
        val title: String; val reporter: String
        when (channel) {
            "PHONE" -> { title = raw["summary"].toString();    reporter = raw["callerPhone"].toString() }
            "APP"   -> { title = raw["subject"].toString();    reporter = "user:${raw["userId"]}" }
            "IOT"   -> { title = "设备告警:${raw["alarmCode"]}"; reporter = "device:${raw["deviceId"]}" }
            else -> throw IllegalArgumentException("未知渠道")
        }
        // 每接一个新渠道这里就长一个分支，报文解析把工单领域逻辑淹没
        // ...
    }
}
```

✅ **修正：每个渠道一个驱动侧适配器，报文 → 命令的翻译就是防腐层**

```kotlin
// 端口与用例：由领域层定义的统一入口，零渠道痕迹
class CreateTicketUseCase(
    private val tickets: TicketRepository,   // 被驱动侧端口：工单存储
    private val notifier: NotifierPort,      // 被驱动侧端口：通知
) {
    fun execute(cmd: CreateTicketCommand): TicketId {
        val ticket = Ticket.open(cmd)        // 领域只认识命令，不认识任何渠道报文
        tickets.save(ticket)
        notifier.notifyAssigned(ticket)
        return ticket.id
    }
}

// 驱动侧适配器：呼叫中心话单 → 领域命令（防腐层翻译在此发生）
class PhoneChannelAdapter(private val useCase: CreateTicketUseCase) {
    fun onCallFinished(report: TelephonyReport) = useCase.execute(
        CreateTicketCommand(source = Channel.PHONE, title = report.summary,
            reporter = report.callerPhone, attachments = listOf(report.recordingId)))
}

// 驱动侧适配器：IoT 告警报文 → 同一个命令
class IotAlarmAdapter(private val useCase: CreateTicketUseCase) {
    fun onAlarm(alarm: DeviceAlarm) = useCase.execute(
        CreateTicketCommand(source = Channel.IOT, title = "设备告警:${alarm.code}",
            reporter = "device:${alarm.deviceId}"))
}
```

新增"微信小程序"渠道 = 新写一个适配器，领域与其他适配器零改动（[第一阶段](../章节1/01-第一阶段-架构思维与设计基础.md)开闭原则的架构版）。被驱动侧同理：`NotifierPort` 的实现可以是短信适配器、钉钉适配器；工单存储可从 MySQL 换成 ES 而不触及用例。

❌ **反例：领域对象长满框架注解，依赖方向反了**

```kotlin
@Entity
@Table(name = "ticket")
data class Ticket(
    @Id @GeneratedValue val id: Long = 0,                          // 数据库身份污染领域身份
    @Column(name = "sla_deadline") val slaDeadline: Instant,
    @Transient val attachments: List<Attachment> = emptyList(),    // "不落库"要靠注解声明
)
// JPA 要求无参构造与可变字段，领域被迫放弃不可变性；单测要 mock 框架甚至起数据库
```

✅ **修正**：领域模型保持纯净（不可变、无注解），ORM 映射放进适配器（JPA POJO + 转换器或 MyBatis 映射），存储变化不触及领域。

**三者的细粒度对比**（同源，差异只在强调什么）：

| 维度 | 六边形 | 洋葱 | 整洁 |
|---|---|---|---|
| 出身动机 | 对称性：UI/测试/消息消费者是平等的驱动者 | 给 DDD 一个家：Domain 与 Application 分环 | 集大成 + 统一话术："框架是细节" |
| 内核内部结构 | **不规定**（内核内部自组织） | 规定两内环：Domain / Application | 规定两内环：Entities / Use Cases |
| 驱动侧的处理 | **显式**分左右两侧（驱动/被驱动） | 不区分，都在环上 | 不区分，统称 Interface Adapters |
| 跨边界传什么 | 命令/DTO（未特别强调） | DTO | 硬规定：**只传简单数据结构**，领域实体不许跨界 |
| 招牌卖点 | 可替换性与可测试性（测试即驱动侧适配器） | 依赖规则可视化 | 口号好记、传播力强 |
| 框架/DB 的地位 | 适配器，可整体替换 | Infrastructure 外环 | "细节"，采用哪个框架的决定推迟到最后 |

**同一件事的三种叫法**（第一列锚定 §1 已学的传统分层）：

| 实际角色 | 传统 N 层 | 六边形 | 洋葱 | 整洁 |
|---|---|---|---|---|
| 领域规则 | 业务层实体类 | 内核 | Domain 环 | Entities 环 |
| 用例编排 | 业务层 Service | 内核里的用例 | Application 环 | Use Case（Interactor） |
| 技术细节（DB/消息） | DAO / 消息客户端 | 被驱动侧适配器 | Infrastructure 环 | Frameworks & Drivers |
| 系统入口 | Controller / UI | 驱动侧适配器 | 最外环 | Interface Adapters（Controller） |
| 依赖方向 | 向下 | **向内** | 向内 | 向内 |

**落成代码几乎是同一份**——三个名字，一份代码，差异只在命名与强调（完整可运行版：[hex-onion-clean/HexOnionClean.kt](hex-onion-clean/HexOnionClean.kt)，已实际编译运行验证）。它额外演示两条这家族的通用红利：

1. **被驱动侧可替换**：`NotifierPort` 的短信实现换成钉钉实现，改的是装配、不是内核；
2. **测试就是又一个驱动侧适配器**：`FixedClock` + 内存库替身驱动同一个用例——不起 UI、不起数据库、不依赖真实时钟即可验证"关键工单 SLA = 2h"。"**时间也是外部细节**"这一点常被忽略：`ClockPort` 一旦倒置，SLA 这类时间规则立刻可测——传统分层里"取当前时间"散在业务代码中，恰恰最难测。

**使用场景与选型**：

- **先判断要不要用这一家族**（判据三者共享）：复杂领域、规则密集（工单状态机、押金生命周期），或技术细节预计会换（通知渠道、数据库、接入渠道持续增加）。简单 CRUD、薄领域（报表、配置管理）、原型期——分层就够，强行倒置只是交样板代码税。
- **三选一：按"哪面墙最痛"选话术**：
  - **集成与渠道密集** → 六边形话术最贴切（驱动/被驱动两侧、适配器即防腐层）：工单中心的多渠道接入、MES 的 PLC/SCADA/ERP 对接、支付通道对接，本质都是"**两侧适配器在变、内核不动**"。
  - **领域深、走 DDD** → 洋葱/整洁更顺手：Application 与 Domain 两环的分界，正好承接 DDD 应用服务与领域服务之分（桶装水的押金、周期购规则适合住进 Domain 环；战略设计见[第四阶段](../章节4/01-第四阶段-架构方法论.md)）。
  - **要统一团队认知** → 整洁的口号传播力最强："数据库不是架构、Web 不是架构、框架是细节"——评审、新人培训时最能防"框架绑架"。
- **混用是常态**：Martin 的博文本身就收录了六边形与洋葱的图；实践中常见"整洁的分层 + 六边形的左右两侧话术"。**坚持一套话术 > 纠结哪个正宗**——文档与评审里术语统一的价值，远大于站队。
- **渐进落地**：不必起步就用。从分层开始，痛点出现（渠道越接越多、单测被迫起数据库、领域模型长满注解）再把端口倒置出来——六边形常常是**重构目标**而非起步姿势，与 2.5 绞杀者"可逆、渐进"是同一哲学。

### 4.3 Serverless

**概念**：应用逻辑交给托管运行时按需执行（FaaS，云函数），状态与通用能力用托管服务（BaaS：对象存储、托管数据库、消息、鉴权）。部署粒度从"一个服务"细化到"一个函数"，按调用量计费。

```kotlin
// IoT 数据采集的轻量函数：设备上报经接入网关触发，无需维护常驻服务器
class TelemetryIngestHandler(
    private val tsdb: TimeSeriesStore,   // BaaS：托管时序库
    private val alarms: AlarmBus,        // BaaS：托管消息
) {
    fun handle(request: HttpRequest): HttpResponse {
        val payload = DeviceCodec.decode(request.body)
            ?: return HttpResponse.badRequest()
        if (tsdb.alreadyIngested(payload.deviceId, payload.eventTime))
            return HttpResponse.ok()                    // 幂等：设备弱网重传是常态
        tsdb.writeBatch(payload.toPoints())             // 批量落库
        if (payload.outOfRange()) alarms.publish(payload.toAlarm())
        return HttpResponse.ok()
    }
}
```

适合：流量极端不均（秒杀、大促）、事件触发的粘合逻辑（回调、定时对账、图片处理）、无运维能力的小团队。代价：**冷启动延迟**（首请求慢数百毫秒到秒级）、厂商锁定（触发器与 SDK 不通用）、不适合长任务与有状态长连接（MQTT 接入这类长连接仍需常驻集群，见[第三阶段](../章节3/01-第三阶段-分布式系统核心技术.md)）、本地调试麻烦；持续高流量下按调用计费**反而更贵**。

### 4.4 主从模式（Master-Slave）

**概念**：节点分成两类角色——**主**（Master/Leader/Primary）：接收写入、分解或分发任务、持有权威状态；**从**（Slave/Replica/Follower/Worker）：执行任务或维护副本，服从主的调度。工程里到处都是它的两个子型：

| 子型 | 主做什么 | 从做什么 | 例子 |
|---|---|---|---|
| 主从复制（primary-replica） | 接收写、向从推送变更 | 只读副本，扛读流量 | MySQL 主从 + 读写分离（接住桶装水"读多写少"的挑战 4，深入见[第三阶段](../章节3/01-第三阶段-分布式系统核心技术.md)）、Redis 主从、Kafka 分区 Leader/Follower |
| 主从任务分发（master-worker） | 切分任务、调度、汇聚结果 | 领任务干活，水平加机器 | K8s 控制面与 kubelet、Spark driver/executor、MES 里 Modbus 主站轮询 PLC 从站采集报工数据 |

（术语注：社区已改用 leader/follower、primary/replica、main 等叫法，结构不变，本文保留"主从"作模式名。）它的对偶是**对等/无主（P2P，leaderless）**：没有主，所有副本地位相同，靠协议仲裁（Cassandra 的 quorum 读写、Git 的多远端同步）——省掉选主，代价是每笔写都要协商（CAP 与共识见[第三阶段](../章节3/01-第三阶段-分布式系统核心技术.md)）。

主从买到三样：**读扩展**（写一份读 N 份）、**并行**（worker 越多吞吐越大）、**容灾**（主挂了提升从上位）。代价集中在两处：**复制滞后**（从库晚几百毫秒——"支付成功页立刻查积分"这类读不能走从库，判据同 3.2"容忍滞后的读交给投影/副本"）与**选主**（主挂了谁说了算？）。

❌ **反例："ping 不通对端就当主"——脑裂（split-brain）**（本例已实际编译运行验证）

```kotlin
class NaiveNode(private val id: String, private val peerReachable: Boolean) {
    var writes = 0
    fun tick() {
        if (!peerReachable) applyWrite()   // 探测不到对端 = "对端死了，我该当主"
    }
    private fun applyWrite() { writes++ }
}
```

网络分区时 A、B 互相探测不通——**两边同时晋升为主、同时收写**：库存一边扣了、一边没扣，网络恢复后数据已经分叉。这就是脑裂，主从模式最著名的事故形态。

✅ **修正：租约 + 多数派仲裁——同一时刻至多一个主**

```kotlin
// 仲裁组 3 票：必须拿到超过半数选票才能当主；分区后只有看得见多数派的一方当选
class QuorumStore(private val voters: Int) {
    var holder: String? = null
    fun elect(candidate: String, votes: Set<String>): Boolean =
        (votes.size > voters / 2).also { if (it) holder = candidate }
}

class LeaseNode(private val id: String, private val quorum: QuorumStore) {
    var isLeader = false
    var writes = 0
    fun tryPromote(visible: Set<String>) { isLeader = quorum.elect(id, visible) }
    fun tick() { if (isLeader) writes++ }
}
```

分区后 n1 仍看得见 3 个节点 → 多数派同意，当选；n2 只看得见自己 → 1 票不足多数，拒绝晋升。**单一写者**由此保住。Redis 哨兵、etcd 租约、Raft 选主全是这个结构的工程化（租约带 TTL 到期重选、仲裁组取奇数个节点，Raft 细节见[第三阶段](../章节3/01-第三阶段-分布式系统核心技术.md)）。顺带一提：2.2 治理清单里的注册中心、K8s 的控制面都是主从结构——**控制面（主）管调度，数据面（从）干活**。

### 4.5 代理者模式（Broker）

**概念**：POSA 里最古老的分布式模式之一（1996）：**调用方与服务之间插一个中介**，中介负责请求转发、结果回传、服务注册与**位置透明**——调用方不需要知道服务在哪台机器上。二十多年过去，中介演化出三个化身，你天天在用：

| 化身 | 中介承担什么 | 例子 |
|---|---|---|
| RPC Broker | 注册中心、地址解析、负载均衡 | Dubbo/Eureka、Nacos、Consul（见 2.2 服务发现） |
| 消息 Broker | 存转消息、路由、削峰、投递语义 | RabbitMQ、Kafka（见 3.1 发布订阅） |
| 边缘 Broker | 统一入口的路由与策略 | API 网关、服务网格 sidecar（见 2.2） |

❌ **反例：点对点直连成网**

```kotlin
class PaymentService {
    // 每个服务硬编码所有依赖的地址：N 个服务 = N(N-1) 条依赖
    private val inventory = HttpClient("http://10.2.3.4:8080")
    private val points    = HttpClient("http://10.2.3.7:9090")
    // 库存服务迁移机房 / 扩容加副本 / 换端口：全公司跟着改配置、发版
}
```

✅ **修正：调用方只认服务名，地址交给 Broker 解析**（本例已实际编译运行验证，运行时 3 次调用被随机摊到两个副本上）

```kotlin
class Registry {                       // Broker 的最小化身：注册与发现
    private val services = mutableMapOf<String, MutableList<Instance>>()
    fun register(name: String, instance: Instance) {
        services.getOrPut(name) { mutableListOf() }.add(instance)
    }
    fun resolve(name: String): Instance =
        services.getValue(name).random()      // 随机挑一个 = 最朴素的负载均衡
}

class BrokerClient(private val registry: Registry, private val name: String) {
    fun call(path: String): String {
        val t = registry.resolve(name)        // 调用时才解析：扩容、迁移对调用方透明
        return "$name@${t.host}:${t.port}$path"
    }
}
```

事后给 inventory-service 加第二个副本，调用方一行不改——`resolve` 自动把流量摊过去。两个化身解耦的深度不同：**RPC Broker 解的是位置耦合**（它在哪里），**消息 Broker 解的是时间与语义耦合**（我根本不关心谁在听、什么时候处理，见 3.1）。

**Broker 的代价**（两条都要盯住）：中介自身成为可用性与性能的关键路径——注册中心要集群化、消息 Broker 要副本与持久化；**中介膨胀**——往 Broker 里塞业务逻辑，它就长成 SOA 的 ESB（见 2.4）。"网关只做策略、消息队列只搬字节"这条纪律，对三个化身一视同仁。

### 4.6 微内核架构（插件化）

（场景切换：低代码开发平台——表单/流程/页面拖拽搭建、元数据驱动运行，是微内核最典型的现代样本；工单中心渠道接入、API 网关插件链同款结构。）

**概念**：内核只保留最稳定、最小的公共能力——**扩展点契约、插件注册与发现、生命周期管理、插件间通信**；业务能力全部做成插件，运行时装配。语出操作系统（微内核 OS vs 宏内核），工程里的实现谱系：Eclipse/OSGi、IDEA 与 VS Code 的插件、Chrome 扩展、K8s 的 CRI/CNI/CSI 与 admission webhook、API 网关的插件链（见 2.2）。教义一句话：**内核提供机制，插件提供策略。**

与已学知识的接线：它是[第一阶段](../章节1/01-第一阶段-架构思维与设计基础.md)开闭原则的**架构级落地**（新增能力 = 加插件，内核零改动）；进程内插件 ≈ 策略/责任链（章节1 设计模式），**架构级插件**（独立开发、独立发布、故障隔离）才是风格层面的东西；与 4.2 六边形的分工——六边形管**依赖方向**（技术细节推外圈），微内核管**能力本身外置**（内核 + 扩展点 + 插件注册）；FaaS（4.3）可以看作插件的极致形态——连运行时都托管了。

❌ **反例：活动规则焊死在结算内核里**（桶装水营销，本例已实际编译运行验证）

```kotlin
class MonolithicCheckout {
    fun settle(cart: CartContext): CartContext {
        var c = cart
        if (c.amount >= 200) c = c.copy(amount = c.amount - 30)         // 满减
        if ("VIP" in c.tags) c = c.copy(amount = c.amount * 90 / 100)   // 会员九折
        // 每上一个新活动就改内核、全量回归；活动下线就删代码
        return c
    }
}
```

✅ **修正：内核只管注册与调度，规则全是插件**

```kotlin
interface PromotionPlugin {                     // 扩展点契约：全系统最贵的接口
    val id: String
    fun applicable(cart: CartContext): Boolean
    fun apply(cart: CartContext): CartContext
}

class PromotionEngine {                         // 内核：机制，不含任何营销规则
    private val plugins = linkedMapOf<String, PromotionPlugin>()
    fun register(p: PromotionPlugin) { plugins[p.id] = p }
    fun settle(cart: CartContext): CartContext =
        plugins.values.filter { it.applicable(cart) }.fold(cart) { c, p -> p.apply(c) }
}

class FullReduction(private val threshold: Int, private val off: Int) : PromotionPlugin {
    override val id = "full-reduction"
    override fun applicable(cart: CartContext) = cart.amount >= threshold
    override fun apply(cart: CartContext) = cart.copy(amount = cart.amount - off)
}

class VipDiscount(private val percentOff: Int) : PromotionPlugin {
    override val id = "vip-discount"
    override fun applicable(cart: CartContext) = "VIP" in cart.tags
    override fun apply(cart: CartContext) = cart.copy(amount = cart.amount * (100 - percentOff) / 100)
}
```

运行验证：两种写法对同一购物车算出相同金额（满 200 减 30、会员再九折：260→230→207）；随后热插一个"满 3 件立减 20"的双十一插件，**内核与既有插件一行不改**，金额变为 187。对照低代码平台读这个结构：元数据引擎与渲染器是内核，表单组件、连接器、自定义函数全是插件；工单中心同理，渠道适配器（电话/APP/IoT）天然是插件——4.2 的六边形接口 `CreateTicketCommand` 就是它的扩展点契约。

**三条纪律**：
1. **内核必须薄且稳定**：扩展点契约是全系统最贵的接口——改一次契约，全体插件跟着返工。宁可加新扩展点，不动旧契约（契约版本化演进，同 3.1 事件的 `version` 字段）。
2. **插件之间不许互相 import**：插件协作只通过内核提供的事件/消息总线，否则插件网状依赖，卸载或升级一个就炸一片。
3. **插件的独立程度决定收益**：进程内插件换来编译期解耦与并行开发（本例）；进程外插件（网关、K8s admission webhook、OSGi）再换来故障隔离与热插拔，付出序列化成本与运维复杂度。

**权衡**：买到扩展性、并行开发、按需装配（按需安装插件，缩小体积与安全面）、隔离；付出契约冻结（扩展点设计是最大难点，一次设计定生死）、版本矩阵（插件 × 内核兼容性管理）、性能间接层（注册与查表）、生态治理（插件质量参差，需要审核与沙箱）。

## 5. 平台化架构：BFF 与中台

（场景切换：桶装水公司长大成"到家服务平台"——三条业务线 + 三类端，是 BFF 与中台的自然土壤。）

前面四节的风格回答的都是"**后端内部怎么组织**"；本节的两个模式回答另外两个维度的问题：**BFF** 管"多个前端如何面对微服务集群"，**中台** 管"多条业务线如何共享能力"。两者是同一思路在不同维度的表达——**把共性沉淀成平台，把差异留给边缘**；也共享同一条主线命题：**复用不是免费的，买复用，付的是约束与排队。**

### 5.1 BFF（Backend for Frontend）

**概念**：为**每一种前端体验**配一个专属的后端聚合层，由对应的端团队拥有（SoundCloud 团队 2015 年提出）。微服务化之后它解决两类新问题：

1. **聚合问题**：一个页面的数据散在 N 个服务里，客户端要么串行调 N 个接口（延迟叠加、可用性相乘，见 2 节自测 3），要么让网关代劳——但网关一旦承担聚合编排，就滑向"上帝层"（见 2.2）；
2. **差异问题**：小程序要轻、运营后台要全、配送员端要位置与路线。一个"通用 API"被迫长成大而全的 DTO：每个端为自己用不到的字段付流量，更危险的是为不该看到的字段埋雷。

❌ **反例：一个"通用"聚合接口喂所有端**

```kotlin
// "通用"订单详情：一个 DTO 同时服务 C 端小程序、配送员端、运营后台
data class UniversalOrderDetail(
    val orderId: OrderId,
    val status: String,
    val courierPhone: String?,           // 只有配送员端需要；C 端每次白白传输 null
    val internalCostPrice: BigDecimal,   // 财务域的成本价——跟着"通用模型"泄漏给 C 端！
)
// 接着"如果是小程序就删掉 route 字段"的 if 分支开始滋生——上帝层 2.0 的起点
```

问题：C 端为不用的字段付流量与序列化开销；`internalCostPrice` 这类财务域字段顺着重用的链路泄漏给不该见的端——**通用 DTO 是数据泄漏的温床**；任一下游字段变更，四个端全部回归测试；"按端裁剪"的 if-else 在聚合层越长越多。

✅ **修正：每端一个 BFF，各自裁出窄类型**

```kotlin
// C 端 BFF 只依赖订单客户端——想泄漏成本价，类型上就不可能
data class CustomerOrderCard(val orderId: OrderId, val status: String)

// 配送员端 BFF：只聚合配送员要用的最小字段
data class CourierTaskCard(val taskId: TaskId, val window: String,
    val community: String, val receivable: BigDecimal)   // 空桶应收

class CendBff(private val orders: OrderClient) {
    fun card(orderId: OrderId): CustomerOrderCard =
        orders.detail(orderId).let { CustomerOrderCard(it.id, it.status) }
}

class CourierBff(private val delivery: DeliveryClient) {
    fun todayBoard(courierId: CourierId): List<CourierTaskCard> =
        delivery.tasks(courierId).map {
            CourierTaskCard(it.id, it.window, it.community, it.receivable)
        }
}
```

聚合往往还要**并行**调下游（三个下游各 200ms：串行 600ms，并行约 200ms），协程写法：

```kotlin
suspend fun todayBoard(courierId: CourierId): BoardResponse = coroutineScope {
    val tasks = async { delivery.todayTasks(courierId) }
    val route  = async { delivery.routeOf(courierId) }
    BoardResponse(route.await(),
        tasks.await().map { TaskCard(it.id, it.window, it.community, it.receivable) })
}
```

**网关 vs BFF 的职责边界**：

| | API 网关 | BFF |
|---|---|---|
| 关注点 | 横切技术关注点 | 纵向体验关注点 |
| 职责 | 路由、鉴权、限流、协议转换 | 聚合、裁剪、端适配、体验编排 |
| 归属团队 | 平台团队 | 对应端的前端/端团队 |
| 数量 | 通常一个 | 每端一个 |
| 业务规则 | 不应有 | 允许"体验编排"，领域规则仍须下沉 |

边界判据：**换一种表达方式的需求放 BFF，换一种业务事实的需求下沉到领域服务。**"空桶应收怎么算"是费率政策（业务规则）→ 归押金/营销服务；BFF 只拼装展示。BFF 里重算价格是经典事故源——政策一变，各端算出的价格不一致。

**权衡**：换来端差异化、窄接口、团队自治（端团队 owns"页面 + BFF"整条竖切，接口对齐沟通边界——康威定律的又一次显形）；付出层数 +1（每请求多一跳，但并行聚合通常净赚）、公共逻辑重复（要沉淀 BFF 公共库）、职责漂移风险（BFF 长出业务就成上帝层 2.0，用上面的判据守住）。变体：**GraphQL 天然适合做 BFF**（端自定义查询 = 端自己写裁剪）；**微前端 + BFF** 把竖切推到前端侧，是微服务思想在前端的对偶。

### 5.2 中台架构

**概念**：把多条业务线**真共享**的能力沉淀为可复用的平台层，前台保持轻薄、快速试错——2015 年阿里提出"大中台、小前台"（借鉴 Supercell 小团队 + 公共游戏组件的组织方式），2021 年后多家大厂陆续"拆中台"。三种形态：

| 形态 | 沉淀什么 | 到家平台对应 | 深入章节 |
|---|---|---|---|
| 业务中台 | 共享的**领域能力**（用户/支付/营销/调度） | 支付中台、调度中台 | DDD 战略设计（[第四阶段](../章节4/01-第四阶段-架构方法论.md)） |
| 数据中台 | 统一的数据采集—加工—服务 | 三条线共用的经营报表与用户画像 | 数据架构（[第三阶段](../章节3/01-第三阶段-分布式系统核心技术.md)） |
| 技术中台 | 基础设施（微服务框架/MQ/K8s/监控） | 就是本章与三、五章讲的那些基础设施 | [第三阶段](../章节3/01-第三阶段-分布式系统核心技术.md)、[第五阶段](../章节5/01-第五阶段-工程化与运维视角.md) |

**关键认知**：中台不是一种新的部署或代码风格，而是**微服务 + DDD + 平台化组织**在多业务线公司里的组织级组合。本章其他风格回答"一个系统怎么组织"，中台回答"**一个公司的一批系统怎么组织**"——所以判断能不能中台化的标尺，仍然是限界上下文：**共享的是同一个领域，还是只是同名概念？**

主线延伸：桶装水公司长成"到家服务平台"，三条业务线：桶装水商城、家电清洗、家政保洁。共享的：用户与地址、支付与结算、营销与优惠券、上门调度（送水排线与保洁排班同构）。各自独有的：商品域、服务流程域、押金（桶装水独有）。

❌ **反例 1："同名即同域"的通用订单中台**

```kotlin
// 想用一套"通用订单"模型同时承载 买水、家电清洗、保洁 三条线
data class UniversalOrder(
    val orderId: OrderId,
    val userId: UserId,
    val items: List<ItemDto>,            // 买水是 SKU+桶数，保洁是服务+时长——语义已经对不上
    val depositBuckets: Int? = null,     // 桶装水私有字段挤进"通用"模型
    val cleanerSkillLevel: Int? = null,  // 家政私有字段
)

fun feeOf(o: UniversalOrder): String = when {        // 每条线的特殊性 = 一个分支
    o.depositBuckets != null -> "买水：水费 + 押金"
    o.cleanerSkillLevel != null -> "保洁：按技能等级计价"
    else -> "兜底：谁知道这是哪条业务的订单"
}
```

问题：三条线的"订单"根本不是同一个限界上下文（送水没有"排班"，保洁没有"楼层费"——语言都不一致，见 2.1 拆分依据第一行）；通用模型靠可空字段 + `when` 分支吸收差异，**每接一条新业务线就长一截**；所有线的需求都排队等中台团队排期——中台成为全局瓶颈；康威定律：这个中台必然长成横跨所有业务线的巨大沟通枢纽。

✅ **修正：中台沉淀"语义一致"的能力，前台保留自己的领域编排**（本例已实际编译运行验证）

```kotlin
// 支付中台：收钱、退款、对账在三条线语义一致——真共享的领域能力
interface PaymentPlatform {
    fun charge(request: ChargeRequest): PaymentReceipt   // 版本化契约 + SLA
}

// 前台一：桶装水——自己的订单领域 + 押金语义，前台不是"薄 UI"
class WaterOrderService(private val payment: PaymentPlatform) {
    data class WaterOrder(val no: String, val sku: String, val buckets: Int) {
        val amount get() = buckets * 15
    }
    fun place(sku: String, buckets: Int): PaymentReceipt {
        val order = WaterOrder("W-2026-001", sku, buckets)
        return payment.charge(ChargeRequest(order.no,
            BigDecimal(order.amount + buckets * DEPOSIT_PER_BUCKET)))   // 含押金：前台自己懂
    }
}

// 前台二：家政保洁——同一个支付中台，完全不同的订单领域
class CleaningOrderService(private val payment: PaymentPlatform) {
    data class CleaningOrder(val no: String, val service: String, val hours: Int) {
        val amount get() = hours * 60
    }
    fun place(service: String, hours: Int): PaymentReceipt {
        val order = CleaningOrder("C-2026-001", service, hours)
        return payment.charge(ChargeRequest(order.no, BigDecimal(order.amount))) // 按小时计费，无押金
    }
}
```

运行两个前台：同一个支付中台，一笔收款含押金 40 元、一笔按小时计费无押金——**能力复用，语义各归其位**。判据一句话：**多条业务线在这个能力上的语义一致吗？**支付（收/退/对账）一致 → 中台；订单（各线模型完全不同）→ 留在各自前台。中台吸收合理差异用**扩展点（SPI）**而不是 if-else（如支付中台的"分润规则"由接入方注册自己的实现）。

❌ **反例 2：前台薄成"纯 UI"**。若前台没有自己的领域与编排，做个"会员日买三送一"都要中台排期改价格引擎、等一个月——"小前台"的"小"应指**边界小而完整**（接口 + 数据 + 团队三位一体，同 2.1 微服务的"微"），不是能力被抽干。

**权衡与退潮教训**：中台买的是**复用 + 新业务线启动速度**，付的是**约束（契约）、排队（需求瓶颈）、定制成本（扩展点）**，还要配套组织机制（中台团队与业务团队的双向契约）。2021 年后多家公司退潮，正是权衡的另一面显现：业务差异大、创新求快时，中台从加速器变瓶颈；业务同质性高（连锁复制同一模式）时依然有效。**中台是组织决策，不是技术升级**——没有真实的多业务线复用诉求，单业务线上中台等于自缚手脚（对照 2.3 的审判：单业务线的桶装水商城，结论同样是模块化单体）。国际上的对应争论：数据侧的 Data Mesh（数据所有权下放业务域）vs 中心化数据平台，是同一场"集中复用 vs 域自治"权衡的两种答案。

**本节自测（BFF 与中台）**
1. 用"换表达方式 vs 换业务事实"判据给下列需求定位到网关 / BFF / 领域服务：请求聚合、限流、把美元价格换算成本地货币展示、会员折扣价计算。
2. "空桶应收怎么算"放 BFF 还是领域服务？如果放错了，会出什么事故？
3. 通用订单中台反例错在哪一步——是"做中台"错，还是"把语义不一致的能力硬沉淀"错？由此说说什么能力适合中台化。
4. 你的公司里有没有"事实上的中台"（被多条业务线共用的服务）？它有没有版本化契约、SLA、扩展点？哪一条最欠缺，后果是什么？

## 阶段总结：一张权衡地图

| 风格 | 换来了什么 | 付出了什么 | 演进主线上的落点 |
|---|---|---|---|
| 分层单体 | 简单、本地事务、好调试 | 整体扩展、易腐化 | 桶装水起步形态：八模块一进程一库 |
| 模块化单体 | 边界纪律 + 单体简单性 | 需要强制手段与团队自律 | 桶装水成长期最优解；工单中心同款 |
| 微服务 | 独立部署/扩展、组织伸缩 | 分布式的一切代价 | 只拆排线、订阅等扩展差异大的服务 |
| 事件驱动 | 解耦、削峰、弹性 | 最终一致、排查变难 | OrderPlaced 一事四订阅，收尾主线 |
| 事件溯源 + CQRS | 审计、时间旅行 | 复杂度陡增 | MES 批次追溯与生产看板 |
| 管道-过滤器 | 可组合、可并行 | 交互性差 | Feed 审核管道与热搜统计 |
| 六边形/整洁/洋葱 | 领域防腐、可测试 | 样板代码 | 工单中心多渠道接入的内核组织 |
| Serverless | 免运维、极致弹性 | 锁定、冷启动、成本 | IoT 采集函数、回调与定时任务 |
| BFF | 端差异化聚合、前后端团队自治 | 层数 +1、公共逻辑重复、职责漂移风险 | 网关只做策略，三类端各一个 BFF |
| 中台 | 能力复用、新业务线启动快 | 约束（契约）、排队（需求瓶颈）、定制成本 | 单业务线不需要；语义一致才沉淀 |
| SOA（ESB） | 异构系统互通、集中管控 | 智能总线成瓶颈与单点 | 历史教训：中介只做策略不做业务 |
| 主从 | 读扩展、并行、容灾切换 | 复制滞后、选主与脑裂 | 商品读主从；K8s 控制面/数据面同构 |
| Broker | 位置透明、解耦 | 中介要高可用、忌膨胀成 ESB | 注册中心、消息队列、网关与 sidecar |
| 微内核/插件化 | 扩展点稳定、能力热插拔、并行开发 | 契约冻结、版本矩阵、插件协作绕远 | 低代码引擎、工单渠道、网关插件链 |

真实系统是**风格的组合**。桶装水商城走完全程后的合理终态，很可能不是"全微服务"，而是：**模块化单体（交易域内部用六边形组织）+ 少量微服务（配送排线，必要时再加商品读服务）+ 事件驱动（OrderPlaced 后置动作）+ Serverless（夜间对账、大促预热函数）+ 网关与各端 BFF 收口三类入口**。架构师的功夫在于为**每个子域单独**选风格，而不是让全公司只有一种风格。
