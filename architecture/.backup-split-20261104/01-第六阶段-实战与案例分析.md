## 1. 典型场景拆解

### 1.1 秒杀

**场景定义**：限量商品定点开抢，瞬时流量百倍于日常，硬约束是**绝不超卖**（通用例子：1 万件手机 12:00 开抢）。**核心挑战**：① 瞬时读洪峰（1k → 100w+ QPS）；② 强一致的库存约束；③ 脚本、黄牛、重放攻击。

**总体架构**：漏斗逐层拦截，让越少的请求触达越贵的资源。

```
用户 → CDN(静态页/JS) → 网关(黑名单/限流/答题) → 秒杀服务 → Redis(Lua 原子预扣)
                                                          │ 中签者
                                                          ▼
                                                        MQ(削峰排队) → 订单服务(落库) → 支付(见 1.5)
漏斗示意：1000w 请求 → 100w 过网关 → 10w 过预扣 → 1w 下单 = 库存 1w
```

**关键设计点**：

1. **动静分离 + 多级缓存**：详情页/按钮全静态化上 CDN，未命中的走"本地缓存 → Redis"多级缓存；网关做令牌桶限流、黑名单、答题打散峰值。权衡：误伤真人 vs 系统存活——秒杀永远选后者（第一阶段：可用性优先级排序）。
2. **Redis 预扣库存（Lua 原子）+ DB 乐观锁兜底**："GET 再 DECR"两步并发下会扣成负数；数据库行锁洪峰下必死。Lua 把"查 + 扣 + 记已购"合成一个原子操作；落库时数据库再用乐观锁兜最后一道：`UPDATE stock SET n = n - ? WHERE id = ? AND n >= ?`——即便 Redis 与 DB 短暂不一致，超卖也被这道闸拦住。
3. **MQ 削峰排队**：预扣成功 ≠ 下单成功，订单服务按自身能力消费落库。用户此刻应看到"排队中"而非"已抢到"——把最终一致性如实表达给用户。
4. **防重复下单与防黄牛**：同一用户限购 → 预扣时记已购集合；网络重试 → requestId 幂等；防黄牛是军备竞赛——设备指纹、答题、黑名单、收货地址风控，目标是抬高作弊成本而非根绝。
5. **热点 key 拆分**：所有请求打同一个库存 key，而单 key 只能落在一个 Redis 分片（单分片约 10w QPS 上限）。做法：库存分桶 `seckill:stock:{itemId}:{0..N}`，请求随机路由到一桶扣减，桶不足再向其他桶"借"；活动信息等读热点配本地缓存。
6. **对账与回补**：Redis 扣成功但 MQ 丢消息/落库失败 → 定时对账 + 超时未支付释放库存回补，形成闭环。

```kotlin
val deductLua = """
    local stock = tonumber(redis.call('GET', KEYS[1]) or '-1')
    if stock < 0 then return -1 end                 -- 活动未初始化
    if stock < tonumber(ARGV[1]) then return 0 end  -- 库存不足
    redis.call('DECRBY', KEYS[1], ARGV[1])
    redis.call('SADD', KEYS[2], ARGV[2])            -- 已购集合：一人一单
    return 1
""".trimIndent()

// Lua 原子执行"查+扣+记已购"（第三阶段：原子操作）；返回 1 即中签，发 MQ 异步建单
val won = redis.eval(deductLua,
    keys = listOf("seckill:stock:$itemId", "seckill:bought:$itemId"),
    args = listOf("1", userId.toString())) as Long == 1L
```

**常见错误**：

- ❌ 直接 `UPDATE stock SET n = n - 1`：行锁串行化，数据库被打死。
  ✅ 预热进 Redis，Lua 预扣，MQ 异步落库，DB 只承受"中签流量"。
- ❌ 全部请求挤同一个库存 key：单分片 CPU/带宽先于库存挂掉。
  ✅ 分桶拆 key + 不足借调。
- ❌ 预扣成功就展示"已抢到"：MQ 积压或消费失败时客诉爆炸。
  ✅ 展示"排队中"，订单落库后推送真实结果。
- ❌ 以为前端按钮置灰就挡住了重复提交。
  ✅ 服务端幂等是唯一防线（第三阶段：永远不信任客户端）。

**回指**：[第三阶段](../章节3/01-第三阶段-分布式系统核心技术.md)（缓存、Lua 原子性、MQ 削峰、限流、幂等）、[第一阶段](../章节1/01-第一阶段-架构思维与设计基础.md)（质量属性优先级）、[第五阶段](../章节5/01-第五阶段-工程化与运维视角.md)（压测与预案）。

### 1.2 电商交易（桶装水商城·主线收官）

**场景定义**：桶装水商城——C 端用户单次购买或周期购订阅（每周/每月自动送），水站与配送员按线路配送，水桶收押金、空桶回收退押金。它自[第二阶段](../章节2/01-第二阶段-经典架构模式.md)起就是贯穿主线，这里做收官拆解：长流程横跨订单、库存、支付、押金、配送。**核心挑战**：① 订单—库存—支付三者的一致性；② 周期购是"定时触发的订单"；③ 押金有完整生命周期状态机；④ 读多写少；⑤ 配送排线是独立的算法问题。

**总体架构**（从单体分层一路演进至今的形态）：

```
用户/APP → 网关 ─┬→ 商品服务（读多写少：多级缓存 + 读写分离）
                 ├→ 周期购服务（任务表 + 延迟消息，到点生成订单 → 走同一条下单链路）
                 └→ 订单服务（本地事务：orders + outbox 表）─事件→ 库存服务（预占/释放）
                                                      ├→ 支付（见 1.5）→ 押金（状态机）
                                                      └→ 配送服务（排线算法，独立边界）
订单状态机：CREATED → PAID → SHIPPED → COMPLETED；各状态可按规则 → CLOSED / REFUNDING
押金状态机：PAY_DEPOSIT(支付押金) → BUCKET_IN_HAND(桶在手) → RECEIVED(回收验收)
            → REFUNDED(退押金) / DEDUCTED(验收扣损)
```

**关键设计点**：

1. **显式状态机，订单与押金各一条**：所有迁移集中校验，非法迁移拒绝。押金生命周期"支付押金→桶在手→回收验收→退押金/扣损"，验收结论（完好/破损/丢失）决定终态分支；退押金是资金操作：退款单号幂等、独立状态机、进对账（复用 1.5 套路）。❌ 用 `isPaid`、`isRefunded` 布尔字段拼状态——组合爆炸且必有矛盾态。
2. **一致性选型分级**：跨服务不强求原子——收单幂等（见下）+ 订单与下游走 Outbox 本地消息表（订单与"订单已创建"事件同库同事务写入，relay 投递 MQ）+ 长流程用 Saga：编排（中心协调器发命令收补偿，流程清晰、有中心依赖）vs 协同（各服务订阅事件自行补偿，松耦合、流程散落难排查）——钱相关的长流程通常选编排。❌ 把 2PC/XA 当默认选项：吞吐崩、耦合紧、可用性差。
3. **周期购 = 定时触发的订单**：与"超时关单"是同一类问题，通用三方案——定时扫表（简单、延迟高）/ 延迟消息（精准、依赖 MQ）/ 时间轮（海量任务、实现复杂），按订单量与精度选；更关键的是**错过处理**：调度服务宕机后重启，任务表按 `next_run_at` 把到期任务全部补跑，补跑靠 `(subscription_id, period_no)` 唯一约束幂等——"不漏送、不重送"。❌ 内存队列调度：重启即丢、即重。
4. **读多写少**：商品/水站浏览量远大于下单量——多级缓存扛读 + 读写分离；订单表按 `user_id` 分片（最高频查询是"查我的订单"，第三阶段：分片键随最高频查询选），一年以上归档冷存。
5. **配送排线独立成服务**：排线是算法重、迭代快的问题（路径优化、片区划分），与交易逻辑耦死会互相拖累——一次排线慢查询拖垮下单。独立服务只订阅"订单已支付"事件产出配送任务，失败可重放、不影响交易主链路。服务边界按"变化速率不同"切（第二阶段拆分依据）。

```kotlin
// 幂等收单：幂等键 = requestId。重试方要的是"上次的结果"，不是报错
fun createOrder(requestId: String, cmd: CreateOrderCmd): OrderResult {
    orderResultRepo.find(requestId)?.let { return it }        // 1. 先查结果表
    return try {
        tx {
            val order = orderRepo.insert(Order.from(cmd))
            outboxRepo.insert(OutboxEvent("OrderCreated", order.id))  // 同库同事务
            OrderResult.success(order)
        }
    } catch (e: DuplicateKeyException) {                      // 2. 唯一约束兜底并发
        orderResultRepo.find(requestId)!!
    }
}
```

**常见错误**：

- ❌ 超时关单与支付回调并发无保护：单已关、钱才到。
  ✅ 状态迁移用 CAS（乐观锁）串行化；"已关闭却收到支付成功"走自动退款分支。
- ❌ 周期购补跑不幂等：宕机恢复后同一期送了两次。
  ✅ `(subscription_id, period_no)` 唯一约束，补跑天然去重。
- ❌ 排线算法与订单服务同进程同库：算法一慢，下单跟着超时。
  ✅ 独立服务 + 事件驱动，慢不传染。
- ❌ 各服务直接订阅订单事件、各自猜语义。
  ✅ 事件 schema 显式契约 + 版本化（第二阶段：事件演进）。

**演进复盘（全工作区主线收束）**：这条业务从第二阶段一路演进而来，每一步都是"当时的最大痛点 vs 引入的新复杂度"的权衡：

| 演进步骤（出处） | 解决了什么 | 付出了什么 |
|---|---|---|
| 单体分层（第二阶段） | 职责清晰、小团队快速交付 | 模块边界靠自觉，发布互相牵连 |
| 模块化单体（第二阶段） | 强制模块边界，仍是一个部署单元 | 同库跨模块查询偶有越界 |
| DDD 划限界上下文（第四阶段） | 交易/库存/押金/配送语言统一、边界明确 | 建模范式的学习与维护成本 |
| 微服务拆分（第二/三阶段） | 按负载独立伸缩（商品读、交易写）、独立发布 | 分布式税：事务、测试、运维全变难 |
| 事件驱动化（第二/三阶段） | Outbox + Saga 保一致，排线等下游彻底解耦 | 最终一致、排查复杂，靠可观测性（第五阶段）续命 |

没有终点态，只有"当前最合适的形态"——这正是[第四阶段演进式架构](../章节4/01-第四阶段-架构方法论.md)的结论。

### 1.3 Feed 流

**场景定义**：内容社区首页（微博/Twitter 同构）——"我关注的作者发了什么"按时间/算法排序聚合给每个人。**核心挑战**：① 读写比例极端（100:1 以上：刷 Feed 是读、发帖是写）；② 时效性 vs 存储成本；③ **大 V 问题**（一条内容扇出到上亿收件箱）；④ 排序不止时间序；⑤ 数据量增长后单库放不下。

**总体架构**：推模式（写扩散）与拉模式（读扩散）各有死穴，主流是**推拉结合**：

```
发布：作者 → 内容库(全量永久存档)
         ├─ 普通作者 → 写扩散：推到粉丝收件箱(Redis ZSet，只存最近 N 条)
         └─ 大V(粉丝>阈值) → 不扩散，落库即返回
读取：用户收件箱(推来的) + 在线拉取"我关注的大V"最新内容(拉) → 按时间归并 → 游标分页
```

| 方案 | 写成本 | 读成本 | 适合 |
|---|---|---|---|
| 写扩散（推） | O(粉丝数)，大 V 爆炸 | O(1) 收件箱直读 | 普通作者、活跃用户 |
| 读扩散（拉） | O(1) 只落库 | O(关注数) 在线聚合 | 大 V、非活跃用户 |

**关键设计点**：

1. **收件箱只是索引不是存储**：截断最近约 4000 条，翻更早的页回内容库按关注关系拉——存储成本与读延迟的折中。
2. **推拉边界动态化**：静态按粉丝数切仍有坑（中 V 粉丝多但多为僵尸粉），应只推"近期活跃"粉丝（活跃度靠离线画像）。
3. **游标分页**：offset 深翻页性能崩且数据漂移；游标带 `(score, id)` 双字段避免同分抖动。
4. **删除/编辑一致性**：不做物理扇出删除，逻辑删除标记 + 读取时过滤。
5. **发布与扩散解耦**：先落内容库（成功即成功），扩散异步、失败可重放——核心链路最短化（第二阶段）。
6. **分库分表按用户 ID 路由**：收件箱与关注关系按 `user_id` 分片——最高频查询是"刷我的收件箱"，路由键随它选（第三阶段：分片键一旦定了极难改，扩容走翻倍迁移）；内容库按 `post_id` 分片，另建作者维度冗余索引。
7. **热搜是流式计算**：点赞/转发/搜索词是持续事件流 → 流式引擎滚动窗口聚合 + HyperLogLog/布隆过滤器去重，榜单结果落缓存供读。特征是"算的是数据流，不是请求流"（第二阶段：管道-过滤器）。
8. **审核与推荐管道**：发布先异步过机审再进扩散；推荐内容在读取管道中插入——发布→审核→扩散→读取，每段可替换、可加节点（管道模式的自然演示）。

```kotlin
suspend fun publish(post: Post) {
    postStore.save(post)                              // 第一步永远是落内容库
    if (userRepo.find(post.authorId).followerCount > BIG_V) return  // 大V不扩散
    fanService.activeFollowers(post.authorId)         // 只推活跃粉丝，省扇出写入
        .forEach { fanId -> redis.zAddTrim("feed:inbox:$fanId", post.publishAt, post.id, 4000) }
}

suspend fun readFeed(userId: Long, cursor: Cursor?): List<Post> {
    val pushed = redis.zRevRange("feed:inbox:$userId", cursor, limit = pageSize)
    val bigV = postStore.latest(followService.followingBigVs(userId), before = cursor)
    return mergeByTimeDesc(pushed, bigV).take(pageSize)  // 推 + 拉 在线归并
}
```

**常见错误**：

- ❌ 全量写扩散不分大 V：一条内容扇出上亿写，缓存集群被打爆。
  ✅ 大 V 走拉，读时合并。
- ❌ 收件箱无限增长。
  ✅ 截断 + 内容库兜底。
- ❌ offset 深分页。
  ✅ 游标分页。

**回指**：[第三阶段](../章节3/01-第三阶段-分布式系统核心技术.md)（缓存、分库分表与用户路由、热点）、[第二阶段](../章节2/01-第二阶段-经典架构模式.md)（事件扇出、读写分离/CQRS、管道-过滤器）。

### 1.4 IM（即时通讯）

**场景定义**：聊天 App 的单聊/群聊消息系统，难点全在"连接"与"可靠投递"。**核心挑战**：① 海量长连接的接入与路由（用户连在哪台机器）；② 可靠投递：不丢、不重、**会话内有序**；③ 离线消息与多端同步；④ 接入节点伸缩/发布时的连接迁移。

**总体架构**：

```
客户端A ⇄ 接入层(长连接网关集群) ⇄ 逻辑层(消息/会话/seq分配/关系链) ⇄ 存储层(消息/离线/已读)
              路由表(Redis): userId → 接入节点Id        （逻辑层无状态，可任意扩缩）
```

**关键设计点**：

1. **接入层与逻辑层分离**：接入层只管连接与转发，连接信息进路由表，节点挂了重连任意节点即恢复；逻辑层无状态可水平扩（第二阶段分层）——这也是第五阶段滚动发布的前提。
2. **消息双 ID**：客户端 `clientMsgId`（UUID）做发送方去重（幂等）；服务端按**会话维度**分配严格递增 `seq`。❌ 全局唯一 ID 或时间戳保序：全局有序 ≠ 会话有序，时钟漂移不可用。
3. **投递协议：先落库再推送 + ACK**：落库成功才推送；接收端超时未 ACK 定期重推；接收端按 seq/clientMsgId 去重（重推必然重复）。
4. **丢消息检测**：收到 seq=101 而上一条是 99 → 主动拉取 100。seq 连续性是免费的完整性校验。
5. **推拉结合的投递模型**：在线推、离线拉——离线不写扩散到每个离线者收件箱，上线后按会话拉最近 N 条；多端各记各的 `syncVersion` 增量同步。
6. **存储选型：KV NoSQL + 群聊扩散**：消息写多读少、按会话聚簇 → LSM 树的 KV NoSQL（HBase/Cassandra 类）扛高吞吐写，Redis 只做路由表/收件箱等热数据；群聊是小号版 Feed——小群写扩散（推到每个成员会话）、超大群读扩散（成员拉取），与 1.3 大 V 问题同构。

```kotlin
data class ChatMessage(
    val conversationId: Long,
    val seq: Long,            // 服务端按会话分配，严格递增
    val clientMsgId: String,  // 客户端生成，用于发送方去重（幂等）
    val content: String,
)

fun deliver(msg: ChatMessage): Ack {
    if (messageRepo.existsByClientMsgId(msg.clientMsgId)) return Ack.DUPLICATED
    val seq = seqAllocator.next(msg.conversationId)      // 会话维度集中分配保证有序
    messageRepo.save(msg.copy(seq = seq))
    val session = connRouter.lookup(msg.receiverId)       // 路由表: userId -> 接入节点
    session?.push(msg) ?: offlineStore.markNew(msg.receiverId)  // 不在线转离线
    return Ack.OK
}
```

**常见错误**：

- ❌ 先推送后落库：落库失败消息就永久丢了。
  ✅ 先存储后推送，ACK + 重推 + 去重三件套。
- ❌ 在线推送失败无限重试占住资源。
  ✅ 有限次重试后转离线，端上主动拉。
- ❌ 已读回执、消息状态直接改消息本体。
  ✅ 回执是独立的"会话状态"，与消息内容分离（状态机思想，同 1.2）。

**回指**：[第三阶段](../章节3/01-第三阶段-分布式系统核心技术.md)（幂等、有序性、NoSQL 选型、路由协调）、[第二阶段](../章节2/01-第二阶段-经典架构模式.md)（分层、事件驱动）、[第五阶段](../章节5/01-第五阶段-工程化与运维视角.md)（无状态化让发布与伸缩成为常规操作）。

### 1.5 支付

**场景定义**：用户对 1.2 桶装水商城创建的订单发起支付，对接微信/支付宝渠道，款项还要在平台、水站、配送员之间分账。钱的系统，错误容忍度为零。**核心挑战**：① 不丢钱、不多扣、不错账；② 渠道是异步世界（回调可能延迟、重复、乱序甚至伪造）；③ 对账与差错处理；④ 分账动账顺序；⑤ 安全合规。

**总体架构**：

```
订单系统 → 收单服务(幂等/风控/参数校验) → 渠道网关(多渠道适配器: 微信/支付宝/银联)
                ↑ 异步回调(验签→幂等→主动查询→状态机推进) ←─┘
                ↓ 事件
          对账系统(每日渠道对账单 vs 内部流水) + 退款/分账/差错处理
```

**关键设计点**：

1. **多渠道收单 + 幂等**：各渠道接口、回调、对账单格式各异 → 渠道网关用适配器统一抽象，新渠道只加适配器（开闭原则）；收单以商户单号 `outTradeNo` 唯一约束，重复提交返回同一张支付单而非新建。
2. **回调处理铁律**：验签 → 幂等检查 → **不信回调信查询** → 状态机 CAS 推进 → 应答 SUCCESS。为什么必须查：回调可能伪造、重复、乱序（先到"失败"回调、钱实际成功），渠道查询接口才是权威事实源（第三阶段：跨系统一致性最终靠查询收口）。
3. **掉单治理**：回调丢失 = 用户付了钱、系统没记账。兜底：创建支付单后注册定时任务轮询渠道，查询结果与回调走同一条状态机路径。
4. **对账三步**：渠道对账单 vs 支付流水 vs 订单，日切核对；差错分类——**长款**（渠道有我无，多收了）/ **短款**（我有渠道无，疑掉单）/ 状态不一致——能自动的自动，其余转人工处理流程。对账是支付系统的最终裁判。
5. **分账"先收后分"**：买家付款先进平台中间户，确认收货/签收后再触发向水站与配送员分账；分账指令以分账单号幂等，并纳入日终对账。❌ 边收边分：买家退款时钱已分出去，账轧不平。
6. **金额用分为单位的 Long**。❌ `Double`：0.1 + 0.2 ≠ 0.3 在钱上就是事故。
7. **退款与正向对称**：退款单号幂等、独立状态机、独立对账——很多人只把正向做扎实，退款线全是洞。
8. **敏感数据与合规**：卡号/身份信息加密存储（密钥走 KMS，不写死在配置里）、全链路日志脱敏（打印明文卡号即事故）、最小化收集与留存期限（第五阶段：安全架构与合规）。

```kotlin
// 渠道异步通知：验签 → 幂等 → 主动查询 → 状态机推进，必须快速应答
fun onPayNotify(notify: PayNotify): String {
    if (!signVerifier.verify(notify)) return "FAIL"             // 1. 验签防伪造
    val payment = paymentRepo.findByOutTradeNo(notify.outTradeNo) ?: return "FAIL"
    if (payment.status == PaymentStatus.PAID) return "SUCCESS"  // 2. 幂等：已处理直接应答
    if (payGateway.query(notify.outTradeNo)?.status != RemoteStatus.PAID) return "FAIL"
    payStateMachine.fire(payment, PayEvent.PAY_SUCCESS)         // 3. 不信通知，查渠道核实
    return "SUCCESS"                                            // 4. CAS 推进；履约走事件异步
}
```

**常见错误**：

- ❌ 回调里同步做发货、发短信等重逻辑：处理慢导致渠道认为失败而疯狂重试。
  ✅ 回调只推状态机并快速应答，后续动作事件驱动异步化（第二阶段）。
- ❌ 回调金额不校验。
  ✅ 金额、币种、商户号逐项与本地支付单核对。
- ❌ 只依赖回调不做主动查询。
  ✅ 查询轮询兜底掉单——异步世界的真理：通知会丢，查询不会。

**回指**：[第三阶段](../章节3/01-第三阶段-分布式系统核心技术.md)（幂等、最终一致、以查询收口）、[第二阶段](../章节2/01-第二阶段-经典架构模式.md)（状态机 + 事件驱动、适配器）、[第五阶段](../章节5/01-第五阶段-工程化与运维视角.md)（安全架构：加密、脱敏、合规）、[第一阶段](../章节1/01-第一阶段-架构思维与设计基础.md)（安全性质量属性）。

### 1.6 搜索

**场景定义**：内容社区的标配读侧——帖子与商品的搜索：关键词 + 类目/标签 + 属性 + 价格区间组合查询，按相关性排序。**核心挑战**：① 多条件全文匹配，B+ 树/哈希都无法高效支持 → 需要**倒排索引**（词 → 文档列表）；② 主库与索引的最终一致；③ 相关性排序；④ 索引体积与更新频率的平衡。

**总体架构**：

```
MySQL(内容/商品库) --binlog/CDC--> MQ --> 索引构建器(Projector) --> ES 集群(倒排索引，分片+副本)
在线查询：网关 → 搜索服务 → 查询理解(分词/纠错/同义词) → 召回(ES) → 排序(粗排/精排/重排) → 结果
```

**关键设计点**：

1. **为什么不用主库 LIKE**：`LIKE '%手机%'` 全表扫描，组合过滤没有高效索引形态。搜索本质是**为查询专门建模的读模型**（第二阶段 CQRS：命令侧主库、查询侧索引）。
2. **同步链路 binlog → MQ → 索引**：与主库解耦、可重放、可重建（第三阶段最终一致）。权衡：秒级延迟，内容/商品搜索可接受。❌ 业务代码双写 DB 和 ES：两步写无一致性保障，除非走 Outbox。
3. **Update 回查主库**：binlog 行镜像可能缺字段 → 按 id 回查再 upsert，保证文档完整。
4. **分片与副本**：按内容 id 分片、副本扩读；超大创作者/卖家单独处理防热点（第三阶段）。
5. **索引蓝绿切换**：结构变更/数据修复时"建新索引 → 重放/全量导入 → 双读校验 → 切别名 → 删旧"，期间不中断——第五阶段蓝绿思想平移到数据资产。

```kotlin
// 索引投影器：单一事实源是主库，索引只是投影
class ProductIndexProjector(private val index: SearchIndex, private val repo: ProductRepo) {
    fun on(evt: BinlogEvent) = when (evt) {
        is Insert -> index.upsert(evt.toDoc())
        is Update -> index.upsert(repo.reloadAsDoc(evt.id))  // 行镜像不全，回查主库
        is Delete -> index.remove(evt.id)
    }
}
```

**常见错误**：

- ❌ 搜索接口直查主库 `LIKE`。
  ✅ 独立搜索引擎 + CDC 索引管道。
- ❌ 直接删索引重建（期间搜索 404）。
  ✅ 别名切换的蓝绿重建。
- ❌ 排序只有文本匹配度：搜"桶装水"排出一堆水桶收纳架。
  ✅ 相关性 = 文本相关 × 销量/质量分等业务信号组合。

**回指**：[第二阶段](../章节2/01-第二阶段-经典架构模式.md)（事件驱动、CQRS）、[第三阶段](../章节3/01-第三阶段-分布式系统核心技术.md)（分片、最终一致）、[第五阶段](../章节5/01-第五阶段-工程化与运维视角.md)（蓝绿切换思想迁移）。

### 1.7 物联网数据采集平台（写入型洪峰）

**场景定义**（补充场景）：售水机、智能水表、传感器等海量设备经 MQTT/TCP/CoAP/HTTP 持续上报；平台负责接入认证、解析入库、规则告警、指令下发与 OTA，规模从数万台到百万台。**核心挑战**：① 百万级长连接接入的水平扩展；② **写入型洪峰**——与秒杀的读洪峰方向相反；③ 多协议多版本接入；④ 设备不可靠（弱网断连、重复上报、乱序）；⑤ 数据体量大但价值密度低；⑥ 指令下发的可达性；⑦ 一个慢消费者拖垮整条链路（背压）。

**总体架构**：

```
设备(MQTT/TCP/CoAP) → 接入网关集群(负载均衡 + 连接路由表) → 协议解析(编解码插件)
   → MQ(削峰/缓冲/背压) → 流式管道(清洗/去重/开窗) → 时序库(热数据)
                                                └→ 降采样归档 → 对象存储(冷数据)
   规则引擎(订阅管道) → 告警 → 工单中心          指令下发 ← 设备影子(离线指令不丢)
```

**读洪峰 vs 写洪峰**（与 1.1 秒杀对照，方向相反的两类系统）：

| | 秒杀（读洪峰） | IoT（写洪峰） |
|---|---|---|
| 压力方向 | 百万人反复读同一处 | 百万设备持续写 |
| 第一道防线 | CDN/多级缓存扛读 | 网关只收不解，MQ 做缓冲 |
| 削峰手段 | Redis 预扣筛掉失败者 | MQ 攒批 + 消费者聚合入库 |
| 可否丢弃 | 请求可丢（用户重试即可） | 分级：遥测 QoS0 可丢，计费/控制不可丢 |

**关键设计点**：

1. **接入网关水平扩展**：难在"连接本身就是状态"。做法与 IM 接入层同构（对照 1.4）：四层负载均衡 + 路由表（deviceId → 接入节点），节点宕机设备重连任意节点即恢复。
2. **写入洪峰靠管道**：逐条 INSERT 必挂——MQ 削峰，消费者攒批聚合写时序库，按（设备, 时间）分区；洪峰存进队列，落库速率由消费者自己控制。
3. **多协议插件化**：报文格式各异且会新增协议 → 编解码器做成插件，新协议不改核心（开闭原则的硬件版；MES 的 Modbus/OPC UA 驱动接入同构）。
4. **设备不可靠的对策**：重复上报 →（deviceId, 上报序号）幂等去重；乱序/迟到 → 按**事件时间**（设备端时间戳）开窗而非处理时间，迟到数据走侧输出流补算（第三阶段：幂等与乱序处理）。
5. **冷热分层降采样**：近期明细进时序库，历史数据降采样（秒级 → 分钟级聚合）后归档对象存储——"近期要查、历史舍不得删"的存储对策（第三阶段：NoSQL/时序选型）。
6. **指令下发与设备影子**：设备离线时指令不能丢——先写影子（desired 期望态），设备上线对比 desired/reported 补下发；MQTT QoS 按业务分级（遥测 QoS0 可丢、计费 QoS1、控制 QoS1 + 应用层 ACK）。
7. **背压与流控**：存储抖动时接入层继续狂收会内存爆炸，全拒收又丢数据 → MQ 天然缓冲 + 消费 lag 监控 + 分级丢弃（低价值遥测先丢），把故障隔离在管道内消化。

```kotlin
// 设备影子：desired = 平台期望态，reported = 设备上报态，version 做乐观锁
data class DeviceShadow(
    val deviceId: String,
    val desired: Map<String, Any?>?,   // 下发"远程关阀"指令写这里
    val reported: Map<String, Any?>?,  // 设备最新上报态
    val version: Long,                 // 并发下发/上报不互相覆盖
)

fun applyCommand(shadow: DeviceShadow, cmd: Command): DeviceShadow {
    val next = shadow.copy(
        desired = cmd.patch,                      // 覆盖式更新期望态
        version = shadow.version + 1,
    )
    shadowStore.save(next)                        // 设备离线也没关系：先落影子
    if (gateway.isOnline(cmd.deviceId)) gateway.push(cmd.deviceId, cmd)  // 在线顺手推
    return next
}

// 设备上线：对比 desired 与 reported，把差异补下发——离线指令不丢的关键
fun onDeviceOnline(evt: DeviceOnline) {
    val s = shadowStore.find(evt.deviceId) ?: return
    val delta = shadowStore.diff(s.desired, s.reported) ?: return
    gateway.push(evt.deviceId, delta)
}
```

**常见错误**：

- ❌ 每条上报一次 HTTP 请求直写数据库。
  ✅ 长连接接入 + MQ 削峰 + 批量聚合入库。
- ❌ 按到达时间（处理时间）开窗统计，网络抖动让统计失真。
  ✅ 事件时间开窗，迟到数据侧输出补算。
- ❌ 指令只做在线推送，设备离线即丢。
  ✅ 设备影子 + 上线对比补发。
- ❌ 慢消费者靠接入层内存无限堆积硬扛。
  ✅ MQ 缓冲 + lag 告警 + 分级丢弃。

**与你的真实项目联动**：① 桶装水商城的售水机/智能水表就是典型接入设备——水表读数驱动周期购自动续订与结算，售水机缺水/故障上报经规则引擎自动生成工单中心的维修工单（事件驱动 + 1.2 的幂等收单防重复工单）；② MES 的设备采集本质上是 IoT 在工厂内的一个特例：协议换成 OPC UA/Modbus、实时性与 OT/IT 隔离要求更高，但"接入—管道—存储—指令"的骨架完全同构（详见[示例项目场景](../示例项目场景.md)的分工说明）。

### 1.8 低代码开发平台（元数据驱动）

**场景定义**（补充场景）：业务/实施人员通过拖拽配置而非编码搭建应用：表单（字段、校验、联动）、流程（审批、分支、会签）、页面（列表、报表、大屏）、数据建模；运行时引擎解释执行元数据。典型产物：OA 审批、报修登记、巡检打卡——工单中心"新增工单类型只配表单不改代码"的能力，本质就是内嵌的低代码。**核心挑战**：① 一切皆元数据；② 用户自定义字段怎么存；③ Schema 版本演化；④ 流程引擎通用性陷阱；⑤ 解释执行性能；⑥ 字段/行级权限；⑦ 配置发布治理；⑧ 逃生舱。

**总体架构**：

```
设计期：表单/流程/页面设计器 → 元数据仓库(Schema + 版本) → 发布(灰度/回滚)
运行期：请求 → 表单/流程/页面引擎(解释执行，读编译缓存的 Schema)
                      ├→ 数据引擎(自定义字段: EAV / JSON 列 / 动态建表)
                      ├→ 权限引擎(字段可见 / 行级范围，随配置联动)
                      └→ 脚本/插件扩展点(逃生舱)
```

**关键设计点**：

1. **元数据解释执行 vs 代码生成**：解释执行——即时生效、可灰度回滚、平台控制力强，代价是性能；代码生成——性能好、产物可脱离平台，代价是失去运行时控制与统一治理。多数平台选"解释 + 热点编译缓存"（解释器模式，第一阶段）。
2. **自定义字段存储三方案**：EAV（最灵活，多表 JOIN 查询爆炸）、JSON 列（折中，MySQL/PG 的 JSON 索引能力决定上限）、动态建表（查询最好，DDL 治理是噩梦）——按查询需求选型，数据架构的经典 trade-off（第三阶段）。
3. **Schema 版本化向后兼容**：历史单据必须按**提交时的旧版结构**渲染与校验——单据钉住 schemaVersion，旧版 Schema 只追加不修改（事件溯源的"不可变历史"思想，第二阶段）。
4. **流程引擎通用性陷阱**：分支/并行/会签/撤回/加签越做越像通用 BPM，复杂度失控。YAGNI：明确平台边界——配置覆盖 80% 常见流程，剩下的交给逃生舱（第四阶段：通用性的代价）。
5. **解释执行性能**：Schema 解析结果编译缓存（解析一次、渲染 N 次），高频页面预渲染；性能预算反过来限制元数据模型能做多复杂。
6. **权限与元数据联动**：字段可见性、行级数据范围是配置的一部分，由权限引擎在渲染管道统一执行，不散落在各组件（管道-过滤器）。
7. **配置即代码**：改表单直接生效会击穿在途流程——配置变更走版本化 + 灰度 + 回滚（第五阶段发布治理平移到配置资产）。
8. **逃生舱设计**：复杂业务逻辑不硬塞进配置，留脚本/插件扩展点——平台管骨架，代码管例外（开闭原则与平台边界）。

```kotlin
// Schema 解释执行：单据钉住提交时的 Schema 版本，历史单据永远按旧版渲染与校验
data class BizOrder(
    val id: Long,
    val data: Map<String, Any?>,
    val schemaRef: SchemaRef,   // 指向具体版本，而非"当前版"
)

class FormEngine(private val schemaCache: SchemaCache, private val bizRepo: BizOrderRepo) {
    fun render(order: BizOrder): RenderedForm {
        val schema = schemaCache.compiled(order.schemaRef)          // 编译缓存：解析一次，渲染 N 次
        return RenderedForm(schema.fields.map { it.render(order.data[it.name]) })
    }

    fun submit(draft: Draft, ref: SchemaRef): BizOrder {
        schemaCache.compiled(ref).validate(draft.data)              // 解释执行校验规则（解释器模式）
        return bizRepo.save(BizOrder(data = draft.data, schemaRef = ref))  // 写入即钉住版本
    }
}
```

**常见错误**：

- ❌ Schema 只有一份"当前版"：改字段后历史单据渲染错乱、已提交数据校验不过。
  ✅ 版本化 + 单据钉住提交时版本。
- ❌ 把 ERP 级复杂逻辑硬塞进流程配置，配置图变成没人敢动的天书。
  ✅ 逃生舱：配置管流程骨架，复杂逻辑走代码/脚本。
- ❌ 自定义字段无脑 EAV，列表页一条 SQL 打出几十个 JOIN。
  ✅ 按查询模式在 EAV/JSON/动态建表中选型。

**回指**：[第一阶段](../章节1/01-第一阶段-架构思维与设计基础.md)（解释器/组合模式、开闭、YAGNI）、[第二阶段](../章节2/01-第二阶段-经典架构模式.md)（管道-过滤器、事件溯源思想）、[第三阶段](../章节3/01-第三阶段-分布式系统核心技术.md)（动态字段存储选型）、[第四阶段](../章节4/01-第四阶段-架构方法论.md)（DDD 通用性边界：什么不该做成平台）、[第五阶段](../章节5/01-第五阶段-工程化与运维视角.md)（配置灰度与回滚）。

## 2. 知名架构演进案例

以下基于公开分享/公开资料整理演进脉络与可迁移教训，不涉及未公开的内部细节。

### 2.1 Netflix：从单体到微服务与混沌工程

**演进脉络**：

- 2008 年数据库损坏的严重故障（公开披露的起点事件），促使其放弃"垂直伸缩的单体 + 集中式数据库"，转向 AWS 云与水平拆分；此后按[第二阶段绞杀者模式](../章节2/01-第二阶段-经典架构模式.md)渐进迁移，直至全部工作量上云。
- 拆分的首要驱动力（公开表述）是**独立部署速度**：小团队每天多次发布而不必全体排队；故障隔离与弹性伸缩是随附收益——本质是组织交付问题（第一阶段康威定律：系统结构追随组织结构）。
- 开源 OSS 是演进的副产品：Eureka（服务发现）、Hystrix（熔断）、Zuul（网关）、Ribbon（负载均衡）——第三阶段服务治理的工业源头。
- 混沌工程：从 Chaos Monkey（随机杀生产实例）到 Chaos Kong（下线整个可用区），把"实例随时会挂"从假设变成持续验证的实验——用工程手段替代祈祷。

**可迁移教训**：

1. 微服务首先是组织与交付问题的解：独立交付的收益 > 分布式复杂性代价时才值得（第一阶段：先算账再拆）。
2. 韧性不是架构图画出来的，是持续故障演练出来的（第五阶段：没演练过的预案等于不存在）。
3. 大迁移靠渐进绞杀 + 双跑对账，不靠"停服重写"——重写是风险最高的选项。

❌ 常见误读："Netflix 全上微服务，所以我们也要拆。"
✅ 若瓶颈不在多团队独立交付，微服务只会让你把第三阶段的分布式税全部交一遍。

### 2.2 阿里巴巴：双 11 与单元化异地多活

**演进脉络**：

- **去 IOE**（IBM 小型机/Oracle/EMC → 通用服务器 + MySQL 分库分表 + 自研中间件）：用第三阶段的数据分片、读写分离换掉集中式数据库的垂直扩展路线。
- **双 11 洪峰倒逼**：MQ 削峰填谷、多级限流、热点缓存、全链路压测成为常态——从"大促前人肉扩容"进化为"容量是架构属性"。
- **单元化（Set 化）**：按买家 ID 把流量与数据分片到多个单元，每个单元内交易闭环；机房故障时把该单元流量切到其他单元 → **异地多活**。与"两地三中心"（主生产 + 备用闲置）不同，单元化的多个机房平时同时在生产服役，RTO 从小时级灾备切换缩短到分钟级流量调度。
- **开源反哺**：RocketMQ、Sentinel（限流熔断）、Seata（分布式事务 TCC/Saga 的工业实现）都长自这些场景。

**可迁移教训**：

1. 洪峰容量买不完，分片闭环才能横向扩 + 快速切流——RTO 由架构决定，不由运维手速决定（第三阶段：故障转移）。
2. 大促可靠性 = 平时架构 × 预案 × 演练，临场加机器救不了设计缺陷（第五阶段）。
3. 分片路由键（买家 ID）一旦定下极难更改，要按最高优先级的查询模式选——分片键设计接近"一锤子买卖"。

### 2.3 字节跳动：抖音与推荐基础设施

**公开分享要点**：

- **推荐数据管道**：客户端埋点 → 上报网关 → 实时流 + 离线批处理双链路 → 特征与样本 → 索引；在线侧是"召回 → 粗排 → 精排 → 重排"的分层漏斗。服务链路与数据链路同等重要。
- **A/B 实验文化**：任何推荐策略、UI 改动先分流实验、看指标置信度再全量——实验平台（流量分层、指标体系）成为架构一级公民，而非运营工具。
- **海量微服务与自研中间件**：内部 RPC、服务发现、KV/图存储支撑高吞吐读写；短视频分发对 CDN 与边缘节点要求极高。
- **研发效率基础设施**：服务模板化、代码生成、内部平台把最佳实践固化进脚手架，小团队快速开出标准化服务。

**可迁移教训**：

1. 架构师要为"数据侧"建模：离线/实时双管道（Lambda 形态）与在线服务共同构成系统全貌，只画服务框图是不完整的。
2. 把[第五阶段的灰度发布](../章节5/01-第五阶段-工程化与运维视角.md)推到极致：每个改动都是实验，用数据决策代替会议室争论。
3. 推荐场景的权衡主线是**延迟预算**：几百毫秒跑完整个漏斗，性能预算反过来决定每层算法复杂度上限（第一阶段：性能属性驱动设计）。

## 3. 进阶选修：AI 应用架构

AI 应用没有推翻前面的知识，而是把它们放进一组新约束：**延迟秒级、输出不确定、成本按 token 计费、失败模式是"一本正经地胡说"而非报错**。三个子方向层层递进：LLM 应用（直接调模型）→ RAG（外挂知识）→ Agent（自己干活）。

### 3.1 LLM 应用架构

**场景**：业务系统集成大模型，如"AI 生成商品标题""智能客服首答"。**核心挑战**：① 延迟高且方差大（首 token 秒级）；② 成本与调用量成正比；③ 输出不确定；④ 模型迭代快，必须保留供应商可替换性。

**总体架构**：

```
客户端 → 应用服务 → LLM 网关(路由/限流/缓存/成本核算/审计) → 模型服务(自建 or 供应商 API)
                     ↑ Prompt 管理(模板/版本/灰度)      ↑ 缓存(精确 + 语义)
```

**关键设计点**：

1. **LLM 网关是必备组件**：统一鉴权、限流、多模型路由、成本核算、内容审计——就是第三阶段"网关 + 熔断降级"的 AI 翻版，供应商在网关后面可随时替换。
2. **流式输出**：逐 token 返回（SSE），首 token 时间（TTFT）决定体验；总延迟秒级可接受，"干等完整答案"不可接受。
3. **降级链**：主模型超时/限流 → 小模型（裁剪上下文）→ 缓存/规则兜底。AI 同样必须设计降级，"模型挂了业务就挂"是设计失败。
4. **Prompt 即代码**：模板版本化、灰度、可回滚——把 Prompt 变更当成第五阶段的发布对待，而非改配置随手上线。
5. **成本控制**：精确缓存（同问直返）、上下文裁剪（历史摘要化）、简单请求分流小模型。

```kotlin
// LLM 网关：缓存 → 主模型 → 超时降级小模型（第三阶段：超时/降级/缓存的 AI 变体）
class RoutingLlmGateway(
    private val primary: LlmClient,
    private val fallback: LlmClient,
    private val cache: PromptCache,
) : LlmGateway {
    override suspend fun stream(prompt: PromptContext): Flow<Chunk> {
        cache.exactHit(prompt.signature())?.let { return it.text.chunkedFlow() }  // 1. 缓存直返
        val buffer = StringBuilder()
        val flow = withTimeoutOrNull(8.seconds) { primary.stream(prompt) }
            ?: return fallback.stream(prompt.trimmed())   // 2. 超时降级：小模型+裁剪上下文
        return flow.onEach { buffer.append(it.text) }
            .onCompletion { cache.put(prompt.signature(), buffer.toString()) }   // 3. 回填缓存
    }
}
```

**常见错误**：

- ❌ 业务代码直连某家模型 SDK 写死在服务里。
  ✅ 网关 + 适配层，供应商可替换。
- ❌ 等完整回答再一次性返回。
  ✅ 流式，首 token 优先。
- ❌ Prompt 改动不经测试直接上线（改一个词可能让其他 case 全崩）。
  ✅ 评测集回归 + 灰度（第五阶段）。

**回指**：[第三阶段](../章节3/01-第三阶段-分布式系统核心技术.md)（超时、降级、限流、缓存）、[第五阶段](../章节5/01-第五阶段-工程化与运维视角.md)（灰度与发布治理）、[第一阶段](../章节1/01-第一阶段-架构思维与设计基础.md)（成本也是质量属性）。

### 3.2 RAG（检索增强生成）

**场景**：企业知识问答（如客服知识库）：私有数据训练不进模型、模型知识有截止日期、直接让它答会幻觉。

**总体架构**：

```
离线管道：文档 → 解析/清洗 → 切分(Chunk) → Embedding → 向量库 (+ 关键词倒排索引)
在线链路：query → 改写/扩展 → 混合检索(向量+关键词) → 重排(Rerank) → 组装上下文 → LLM → 带引用的回答
```

**关键设计点**：

1. **离线管道决定上限，在线链路决定下限**：切分策略（按结构/语义边界、带 overlap）对召回质量影响最大；检索与重排决定"找到了能否排上来"。
2. **混合检索**：向量管"语义相近"（怎么退货 ≈ 如何退款），关键词（BM25）管"专有名词/型号精确匹配"（错误码、SKU 编号）——只用向量是最常见翻车点。
3. **重排**：召回 100 条，轻量 rerank 精排取 top 5 进上下文——上下文是稀缺预算，塞得多又贵又稀释注意力。
4. **引用与拒答**：回答标注来源；检索置信度低时明确答"知识库中没有"——**拒答路径是抑制幻觉的架构手段**，不是提示词技巧。
5. **增量更新复用事件驱动**：文档变更事件 → 只重建该文档向量（第二阶段思路平移到向量库）。
6. **评估先行**：建评测集（召回率、忠实度、答案质量）——没有评测的 RAG 调参是玄学（第五阶段：可观测与回归测试思想）。

**常见错误**：

- ❌ 把整篇文档塞进 Prompt。
  ✅ 切分 + 检索 + 重排，控制在预算内。
- ❌ 只做向量检索，型号/编号查不到。
  ✅ 混合检索。
- ❌ 无引用无拒答，用户无从校验。
  ✅ 结构化引用 + 显式拒答分支。

### 3.3 Agent 系统

**场景定义**：给 LLM 一个目标、一组工具和一个循环：**感知 → 规划 → 调用工具 → 观察结果 → 再规划**，直到产出最终答案（例子：自动排查工单中心的客服工单——查订单 → 查物流 → 判定责任方 → 生成回复草稿）。

**总体架构**：

```
用户目标 → Agent Runtime(循环控制/预算/护栏) ⇄ LLM(规划与决策)
                  │ 工具调用
                  ├→ 工具注册表(检索/DB/API/子Agent)
                  ├→ 记忆(短期:轨迹上下文 / 长期:外部存储+检索)
                  └→ 人工介入点(HITL): 高危操作前暂停确认
```

**关键设计点**：

1. **预算控制是生命线**：最大步数、总 token、总时长、单工具超时——Agent 最大的风险是循环失控烧钱（第三阶段：超时与配额思想）。
2. **工具契约**：工具必须**幂等**（Agent 天然会重试）、入参 schema 强校验、错误信息写成"LLM 能读懂的提示"——与 1.5 支付回调"幂等 + 可理解应答"同款要求。
3. **权限最小化 + HITL**：只读工具自动执行；写操作、花钱操作默认人工确认后放行。
4. **轨迹可观测**：每步决策、工具出入参全落 trace，可回放审计——第五阶段可观测的单位从"一次请求"细化到"一步决策"。
5. **记忆分层**：短期 = 本轮上下文窗口（会溢出，定期摘要压缩）；长期 = 外部存储 + 检索（复用 RAG）。

```kotlin
class Agent(private val llm: LlmGateway, private val tools: ToolRegistry,
            private val memory: AgentMemory) {
    suspend fun run(goal: String): AgentResult {
        repeat(MAX_STEPS) {                          // 预算1：步数上限，防循环失控
            when (val d = llm.decide(goal, memory, tools.descriptions())) {
                is FinalAnswer -> return AgentResult.Done(d.answer)
                is ToolCall -> {
                    val result = withTimeoutOrNull(tools[d.name].timeout) {
                        tools[d.name].invoke(d.args)  // 工具必须幂等：Agent 会重试
                    } ?: ToolResult.error("tool timeout, try another way")
                    memory.observe(d, result)        // 轨迹：可回放、可审计
                }
                is NeedHuman -> return AgentResult.Escalated(d.question)  // HITL：高危暂停
            }
        }
        return AgentResult.BudgetExceeded            // 止损退出，而不是永远跑下去
    }
}
```

**常见错误**：

- ❌ 给 Agent 无限循环 + 一把生产库写权限的扳手。
  ✅ 步数/token/时长预算 + 最小权限 + 高危操作 HITL。
- ❌ 工具失败就盲目重试，不管副作用。
  ✅ 幂等键 + 可重试/不可重试错误分类（第三阶段原样适用）。
- ❌ 只评估最终答案，中间步骤黑盒。
  ✅ 全链路 trace + 分步评估。
