# 第一阶段：架构思维与设计基础

> 所属学习计划：[软件架构学习大纲](../软件架构学习大纲.md)（建议时长 2~3 周）
> 本文件是第一阶段的详细学习笔记；大纲文件中只保留进度追踪。
> 示例取材：[示例项目场景](../示例项目场景.md)——本阶段以订单系统（通用）为主，穿插工单中心、低代码平台、MES 工控等专题场景。

## 1. 认识软件架构 ✅

### 1.1 什么是软件架构

定义：**对系统高层结构做出的、影响全局且难以轻易更改的设计决策**。回答三个问题：

1. 系统由什么组成——模块/服务/组件怎么划分
2. 部分之间如何交互——谁调用谁、数据怎么流动、同步还是异步
3. 为什么这样划分——背后的约束与取舍

第三个问题最容易被忽略，但恰恰是架构的核心：**框图谁都会画，理由才见功力**。

#### 1.1.1 案例（MES 工控）：ISA-95/Purdue 分层——"为什么这样划分"的工业版答案

工厂信息系统按 ISA-95/Purdue 参考模型天然分五层：

```text
L4  ERP        —— 经营计划（天/周级）
L3  MES        —— 生产执行（分钟/秒级协同）
L2  SCADA/HMI  —— 监控与操作（秒级）
L1  PLC/DCS    —— 实时控制（毫秒级、确定性）
L0  传感器/设备
```

为什么温度控制回路放在 L1 的 PLC 而不是 L3 的 MES？因为控制回路要求毫秒级**确定性**响应，多绕一次网络往返就超时；"这单活排给哪条产线"以分钟计，归 MES；"下周产能怎么分配"以天/周计，归 ERP。**时间尺度与可靠性要求决定某段逻辑放在哪一层**——每一层的存在都对应一类不同的响应时间与故障容忍要求，而不是层数越多越专业。第二阶段的分层架构沿用的正是这个思路，只是划分依据换成了职责与变化方向。

### 1.2 架构 vs 详细设计 vs 代码

| 层级 | 关注什么 | 例子 |
|---|---|---|
| 架构 | 系统/模块级结构、技术选型 | 订单和支付拆成两个服务，用消息队列解耦 |
| 详细设计 | 模块内部的类、函数、数据结构 | 订单模块里设计 OrderService 和状态机 |
| 代码 | 具体实现 | 写出状态机的逻辑 |

分界线是**改动成本**：牵动全局的决策是架构级（换数据库、改服务边界），只影响局部的是设计级（重命名函数）。判断法："这个决定做错了以后，回头改的代价有多大？"

康威定律：系统结构会映射组织的沟通结构——所以架构决策不能只看技术，还要看团队怎么协作。扩展阅读：[康威定律-补充](05-康威定律-补充.md)（机制、逆康威定律与三条实践启示）。

### 1.3 架构师的角色

先破两个误解：

- 误解一：架构师 = 画框图的。实际上画图只是输出形式，核心工作是权衡与守护。
- 误解二：架构师 = 最资深程序员的自动升级。资历不自动带来架构能力。

关键观念：**架构师是角色，不是职位**。在模块内决定怎么分层、依赖朝哪个方向，就是在做架构决策。

#### 1.3.1 职责全景：架构师到底做什么

按软件生命周期看，架构师的工作远不止画图：

**1. 需求阶段——翻译与识别**
- 识别质量属性需求：业务方说"系统要稳"，架构师要追问成可验证指标（可用性几个 9？故障容忍多久？）
- 收集真实约束：预算、团队技能、上线期限、合规要求、遗留系统——架构永远在约束下做，不在真空中

**2. 设计阶段——结构与契约**
- 划分模块/服务边界，定义接口契约和数据流向
- 技术选型：自建 / 开源 / 采购 / 云服务的权衡，重点不是"哪个最好"而是"哪个的代价我们承受得起"
- 产出可沟通的方案：C4 图、ADR（架构决策记录），让方案能被评审、被挑战

**3. 实施阶段——守护边界**
- Review 代码与设计是否偏离架构（依赖方向有没有被破坏、边界有没有被绕过）
- 处理例外的艺术：deadline 压力下允许破例，但破例必须记录、必须有偿还计划——否则例外会变成新常态

**4. 交付运维阶段——闭环反馈**
- 参与上线方案（灰度、回滚）、容量规划
- 参与故障复盘，把线上教训反哺到架构演进——架构不是交付那天就完成了，而是持续演进的

**5. 沟通协调——横向与纵向**
- 向上：向管理层解释技术投资与风险，用业务语言而不是技术名词
- 横向：对齐有依赖关系的团队，处理跨团队的接口争议
- 向下：让团队理解架构意图，而不是只发号施令

#### 1.3.2 现实中的架构师分类

"架构师"是一族角色，按关注层次从高到低：

| 角色 | 关注范围 | 典型问题 |
|---|---|---|
| 企业架构师（EA） | 公司级业务-技术战略对齐 | 哪些系统该合并、该淘汰 |
| 解决方案架构师 | 一个项目/交付的端到端方案 | 这个需求用哪些系统怎么组合实现 |
| 应用/软件架构师 | 单个系统内部结构 | 订单系统怎么分层、怎么拆模块 |
| 基础设施/云架构师 | 平台、网络、部署拓扑 | 多活怎么部署、容量怎么规划 |
| 数据架构师 | 数据模型、数据流、治理 | 主数据在哪、数仓怎么分层 |
| 安全架构师 | 认证授权体系、威胁建模 | 零信任怎么落地 |

小公司一个人兼任多种，大公司有架构委员会做集体决策。关键是识别：**当前问题属于哪一层，就借用哪一层的视角**。

#### 1.3.3 能力模型展开

三件套"技术深度 + 业务理解 + 沟通影响力"展开看：

- **技术深度（T 的竖）**：至少在一个领域足够深，深到能识别别人看不见的风险和成本；没有深度的广度是浮浅的
- **技术广度（T 的横）**：知道解决方案全景图和各自的代价，选型时才有"菜单"可选
- **业务/领域理解**：能跟业务方用领域语言对话，能判断"这个需求会不会变"——很多取舍依赖对业务演进的预判
- **沟通表达**：写方案（结构化、有权衡、有结论）、讲权衡（讲清"为什么"比讲清"是什么"更难）
- **影响力**：架构师往往没有人事指挥权，推动靠让人信服的判断力和靠谱的历史决策记录
- **决策力**：信息不完备时敢拍板，并为后果负责

常用的成长描述：**会设计模块 → 会设计系统 → 会设计演进路径**——第三步最难，它要求理解组织、成本和时间。

#### 1.3.4 架构师如何做决策

**1. 区分可逆与不可逆决策（单向门 vs 双向门）**
换数据库、改服务边界这类"单向门"几乎不可逆，要慢、充分论证；换缓存库、改内部实现这类"双向门"可以回退，要快、错了再改。常见错误是对两类决策用同一种速度——要么什么都慢，要么什么都轻率。

**2. 记录决策理由（ADR）**
"为什么当时这么选"比"选了什么"更重要。没有记录，半年后要么重新吵一遍，要么有人悄悄"优化"掉一个当初有充分理由的决策。背景-决策-理由-后果，一页以内。

**3. 与其预测未来，不如保持可演进**
架构师无法预测业务三年后的样子，可靠的替代是：确定不变的领域核心做稳，不确定的部分留松（可替换的边界、防腐层）。演进能力 > 预测能力。

#### 1.3.5 常见失败形态（反模式）

| 反模式 | 症状 | 后果 |
|---|---|---|
| PPT 架构师 | 方案精美但不落地，不考虑团队能力和交付成本 | 纸上架构，落地变形 |
| 简历驱动开发（RDD） | 为个人简历引入新技术 | 系统为技术买单，团队为学习成本买单 |
| 架构独裁者 | 不听反馈，方案不容挑战 | 决策质量差，团队阳奉阴违 |
| 事必躬亲 | 把架构当唯一正确答案，事事插手 | 团队失去自主性，架构师成为瓶颈 |
| 脱离代码 | 不再看代码，判断全凭印象 | 选型和评估失真，失去团队信任 |
| 过度设计 / 设计不足 | 为想象的需求过度抽象；或对已知变化毫无预留 | 前者复杂度失控，后者快速腐化 |

#### 1.3.6 架构师与团队的关系

- **架构是团队共识，不是个人作品**：架构师提方案 + 讲清权衡 → 团队评审挑战 → 共同承诺。强推的架构一定会被悄悄绕过。
- **保持写代码**：至少写原型、核心模块或坚持 code review——手离开代码，判断就会失真。
- **传导架构思维**：review 时讲为什么（而不只是改什么），架构思维才能在团队里规模化，架构师才不必成为单点。

#### 1.3.7 成长路径参考

1. **先深后广**：先在一个领域做深（能负责复杂模块端到端设计），再横向扩展
2. **主动跨模块**：争取跨模块/跨团队的 design 任务，练全局视角
3. **写方案并接受挑战**：把每个技术方案当架构练习——有背景、有选项对比、有结论，主动找人 review
4. **复盘大决策**：半年一年后回看当时的选型对不对、错在哪——最便宜的"实战课"
5. **读案例**：DDIA、凤凰架构、大厂架构分享，积累"别人的权衡"

本节自测：

1. 你身边最接近架构师角色的人，五类职责（需求翻译/结构设计/守护边界/运维闭环/沟通协调）各占多少？
2. 你最近参与的一个技术决策，是单向门还是双向门？处理速度匹配吗？
3. 六种反模式里，你最可能滑向哪一种？预警信号是什么？

### 1.4 架构的本质是权衡

没有银弹（Fred Brooks）：任何方案都是在解决一部分问题的同时制造另一些问题。判断架构好坏的标准：**是否解决了当时的主要矛盾、代价是否被清醒地接受**——而不是用了多新的技术。

#### 1.4.1 为什么权衡不可避免

三个根源决定了"全都要"不存在：

1. **质量属性天然冲突**：性能与可维护性、一致性与可用性、安全与开发效率——优化其中一个往往要在另一个上付费。这是结构性的，不是技术不够好。
2. **资源永远有限**：时间、人力、预算约束下，做 A 就少做 B；"小孩子才全都要"在架构上的版本是"什么都想要的系统通常什么都不行"。
3. **本质复杂性无法消除**（Brooks《没有银弹》）：软件的复杂性来自问题域本身，工具和框架只能搬走偶然复杂性，业务本身的复杂你得原样接住。

所以架构工作的正确姿势不是寻找"最优解"，而是**在冲突的属性间分配预算**。

#### 1.4.2 常见权衡对清单

| 权衡对 | 一边 | 另一边 | 典型问题 |
|---|---|---|---|
| 一致性 vs 可用性 | 故障时拒绝请求保数据正确 | 继续服务接受暂时不一致 | 转账 vs Feed 流点赞数 |
| 性能 vs 可维护性 | 绕过分层、缓存套缓存 | 清晰分层、留出演进空间 | 快一时，坑后人 |
| 简单 vs 灵活 | 单体、模块化单体 | 微服务、插件化 | 团队 5 人时灵活性的代价付不起 |
| 自建 vs 复用 | 控制力、深度定制 | 开源/云服务快速起效 | 自建的消息队列谁来值班？ |
| 交付速度 vs 质量债 | 先上线再还债 | 打好基础再上线 | 债要记在案，不是不存在 |
| 同步 vs 异步 | 调用直观、强一致 | 削峰、解耦、延迟低 | 下单扣库存可以异步吗？ |
| 数据反范式化 vs 一致性 | 冗余字段免 join、读快 | 多处更新、可能不一致 | 订单里冗余商品名，改名怎么办？ |
| 冗余 vs 成本 | 多副本、多活高可用 | 机器与运维成本 | 99.99% 比 99.9% 贵一个数量级 |
| 共享 vs 复制 | 共享库一处修改 | 复制代码各自独立演进 | 共享库会成为发布瓶颈 |

记法：**每一行右边都不是"错"，只是"另一头"**——判断依据永远是当前场景哪个代价更能承受。

#### 1.4.3 做权衡的五步方法

1. **先定主要矛盾**：问"什么会先杀死这个系统/项目"——是性能？交付速度？还是没人能看懂代码？主要矛盾决定资源往哪倾斜。
2. **列出至少两个候选方案**：只有一个选项就不存在决策，只有服从。
3. **显式写出每个方案的收益与代价**：代价不只是钱，还有复杂度、对团队技能的要求、运维负担、**退出成本**（将来想换掉它有多痛）。
4. **评估可逆性**：结合 1.3.4 的单向门/双向门——不可逆的决策值得慢，可逆的决策值得快。
5. **记录结论（ADR）**：写下当时的场景、选项和理由，半年后它是对是错都能复盘。

一个关键纪律：**权衡要落在数字和场景上，不能停在形容词上**。"要支撑高并发"不是需求，"大促峰值 5 万 QPS、可容忍 1 分钟降级"才是——前者没法权衡，后者才能。

#### 1.4.4 权衡是动态的：时间维度

今天的正确决策，明天可能就是错的——因为业务规模、团队、约束都变了：

- 典型演进路径：几乎所有大厂都从单体开始（Amazon、Netflix、淘宝），等到单体真的成为主要矛盾才拆服务——**不是他们一开始不知道微服务，而是早期用不上那份灵活性，付不起那份复杂度**
- 存储演进同理：SQLite/单库 MySQL → 读写分离 → 分库分表，每一步都是在"数据量成为主要矛盾"时才发生
- 所以比"一次做对"更重要的是**保持可调整的能力**：把不确定的部分留松、用防腐层隔离可能替换的依赖、把大决策拆成一串双向门小决策

推论：评估一个架构要问"它给下一步演进留路了吗"，而不只问"它现在对不对"。

#### 1.4.5 权衡的错误姿态

| 错误姿态 | 症状 | 解药 |
|---|---|---|
| 假权衡 | 为不存在的需求付出真实代价（日活 1 万按亿级流量设计） | 回到数字和场景 |
| 隐式权衡 | 没意识到在权衡：照搬大厂方案 | 大厂方案解决的是大厂的矛盾，先问自己的矛盾是什么 |
| 只报喜不报忧 | 方案只列收益不列代价 | 每个方案强制写"我们付出的代价是" |
| 二极管思维 | 要么单体要么微服务，非黑即白 | 多数权衡存在中间态（模块化单体、混合部署） |
| 分析瘫痪 | 怕做错决定，永远在调研 | 区分可逆性，双向门决策先动起来 |

#### 1.4.6 练习与自测

练一个可复用的权衡记录表（以后做技术方案直接套）：

```text
决策：<一句话>
场景与主要矛盾：<数字和场景，如峰值 5 万 QPS、团队 6 人>
候选方案 A / B / C：<每个的收益、代价、退出成本>
可逆性：<单向门 / 双向门>
结论与理由：<选了什么，为什么，接受了什么代价>
复查点：<什么信号出现时重新评估这个决策>
```

自测：

1. 你的系统最近一次大的技术选型，显式列出代价了吗？代价里包含退出成本吗？
2. 在 1.4.2 的清单里，你的系统当前每一行站在哪一头？是有意识选的还是默认滑过去的？
3. 你的系统当前的主要矛盾是什么？半年前是同一个吗？——如果变了，架构跟上没有？

## 2. 代码级设计能力 ✅

架构的最小单元是代码结构；代码级的坏设计会不断累积，最终变成一团泥球的架构（Big Ball of Mud）。本节是架构思维在最小尺度上的训练。

### 2.1 SOLID 五大原则（贯穿例子：订单系统）

- **S 单一职责（SRP）**：一个类/模块只有一个变化原因。反例：OrderService 同时算价格、写数据库、发邮件——三个变化方向堆进一个类。修正：拆成 OrderService + OrderRepository + NotificationService。判据是"有几个外部原因会迫使它修改"，不是"做了几件事"。
- **O 开闭（OCP）**：对扩展开放、对修改关闭。反例：支付逻辑写成 if/else，每接一种新支付都要改老函数。修正：定义 PaymentMethod 抽象，每种支付一个实现（策略模式）。本质：**用抽象隔离预判到的变化**；但与 YAGNI 平衡——不为所有想象中的变化留扩展点。
- **L 里氏替换（LSP）**：子类必须能无感替换父类且程序行为仍正确。经典反例：正方形继承长方形（setWidth 会影响 getHeight）；业务反例："不可退款订单"子类把 refund() 抛异常，逼所有调用方加 instanceof。继承必须表达**行为兼容的 is-a**，不为蹭代码复用而继承。
- **I 接口隔离（ISP）**：调用方不应被迫依赖它用不到的方法。反例：巨大的 PaymentService 接口包含支付/退款/对账/结算，收银台只需要支付却面对全部。修正：按使用者拆接口。SRP 按"变化原因"划分，ISP 按"依赖面"划分，目标都是缩小依赖范围。
- **D 依赖倒置（DIP）**：高层模块不依赖低层模块，两者都依赖抽象。反例：OrderService 内部直接 new MySQLOrderRepository。修正：依赖 OrderRepository 接口，具体实现由外部注入。**DIP 是六边形架构、整洁架构的理论基石**——那两种模式就是把它应用到系统层面。

总记：S/I 管边界划分，O/L 管扩展方式，D 管依赖方向；五条共同目标只有一个——**让变化的影响范围局部化**。

#### 2.1.1 场景案例（工单中心）：if-else 如何腐烂，OCP + 策略如何止血

工单中心的流转规则随工单类型变化：投诉单要先绑定责任组，报修单要先生成上门任务，催办规则、SLA 时限也各不相同。最初几乎所有团队都会写成这样：

```kotlin
// ❌ 反例：流转规则硬编码，每加一种类型就再摞一层 else——
// 三个月后 300 行 if-else：没人敢动、改一处崩三处、新人不敢上线
fun transfer(ticket: Ticket, action: Action): Status {
    if (ticket.type == TicketType.COMPLAINT) {
        if (ticket.status == Status.PENDING && action == Action.START) return Status.BINDING // 投诉单先绑责任组
        if (ticket.status == Status.BINDING && action == Action.ASSIGN) return Status.PROCESSING
    } else if (ticket.type == TicketType.REPAIR) {
        if (ticket.status == Status.PENDING && action == Action.START) return Status.VISITING // 报修单直接生成上门
        // ……每个类型、每个状态对都是一段新分支
    }
    throw IllegalStateException("不支持的操作")
}
```

烂掉的不是写代码的人，而是**把"随类型变化的东西"写死在"不随类型变化的流程"里**——这正是 OCP 要隔离的变化。修正：把"下一步去哪"抽象为一族策略，按类型各自实现：

```kotlin
// ✅ 修正：一族 TransferPolicy——新增工单类型只加一个实现，不改已有代码（OCP + 策略模式）
interface TransferPolicy {
    fun supports(type: TicketType): Boolean
    fun next(current: Status, action: Action): Status
}

class ComplaintTransferPolicy : TransferPolicy {
    override fun supports(type: TicketType) = type == TicketType.COMPLAINT
    override fun next(current: Status, action: Action): Status = when (current to action) {
        Status.PENDING to Action.START -> Status.BINDING      // 投诉单先绑责任组
        Status.BINDING to Action.ASSIGN -> Status.PROCESSING
        else -> throw IllegalStateException("投诉单不支持 $action")
    }
}

class TransferService(private val policies: List<TransferPolicy>) {
    fun transfer(ticket: Ticket, action: Action): Status =
        policies.first { it.supports(ticket.type) }.next(ticket.status, action)
}
```

同一张药方还治"分派规则频繁调整"：按技能组、按负载、按优先级的分派逻辑若硬编码，每两周调整一次就要改代码发版；把规则做成**配置/规则引擎**（数据而非代码），新规则上线不动代码——"用抽象隔离变化"从类级别放大到系统级别，这正是第二阶段模块划分要接着讲的话题。

### 2.2 高内聚低耦合与朴素原则

- 高内聚：模块内部的东西在业务上是一件事；低耦合：模块之间只通过窄接口往来。实用判据：两个模块总是必须一起改，说明它们其实是同一个模块，边界画错了。
- 关注点分离：业务逻辑与技术细节（日志、事务、鉴权、重试）分开——这也是"分层"的理论来源。
- DRY：消除的是**知识的重复**（同一件事的定义出现在多处），不是文本重复；两个恰好长得一样的代码不一定该合并，过度 DRY 会把不相关的东西错误耦合。
- KISS：能用简单方案就不用聪明方案。
- YAGNI：不为想象中的未来需求写代码；它的放大版就是架构上"提前设计 vs 演进式等待"的取舍。

### 2.3 常用设计模式（每类挑高频）

设计模式 = 给常见解法起的**标准名字**，价值在于沟通；不要为用而用。现代语言特性让很多模式变轻（策略 ≈ 传一个函数）。

| 类别 | 模式 | 一句话 | 业务例子 |
|---|---|---|---|
| 创建型 | 工厂方法 | "造什么"的决定收拢到一处 | 按渠道创建支付客户端 |
| | 单例 | 全局唯一实例（注意并发安全） | 配置中心客户端 |
| | 建造者 | 多参数对象分步构造 | 含 10+ 可选参数的查询对象 |
| 结构型 | 适配器 | 接口不匹配时做转换 | 老系统接口包装成新接口 |
| | 装饰器 | 不改原类、叠加能力 | HTTP 客户端叠加重试、日志 |
| | 代理 | 控制访问，持有真实对象 | RPC 客户端的本地桩（stub） |
| 行为型 | 策略 | 一族可替换算法 | 多种优惠计算方式 |
| | 模板方法 | 父类定骨架，子类填空位 | 导出流程：校验→查询→格式化 |
| | 观察者 | 状态变化通知多方 | 下单后通知库存、积分、消息 |
| | 责任链 | 请求沿链传递，各自处理或放行 | 风控规则、过滤器链 |

装饰器 vs 代理：装饰器**叠加职责**（调用方知情），代理**控制访问**（调用方不知情）。模式与 SOLID 的关系：模式是原则的落地姿势（策略模式 = OCP 的具体应用）。

GoF 全部 23 个设计模式的逐一详解（前 10 个高频精讲、后 13 个补全；意图、订单系统贯穿的 Kotlin 可运行示例、反例与 Kotlin 惯用写法）已拆到单独文件：[常用设计模式-补充](06-常用设计模式-补充.md)，配套可运行代码在 [patterns/](patterns/) 目录——一个模式一个 .kt 文件（P01~P23），每份围绕一个具体业务场景、带独立 main 可单独运行；什么时候该用哪个模式，另有一份症状反查速查：[设计模式使用场景](07-设计模式使用场景.md)。

#### 2.3.1 场景案例（低代码平台）：解释器 + 组合的天然舞台

低代码平台里，表单设计器产出的不是代码而是**元数据 Schema**（字段、校验、联动规则），流程设计器产出节点/分支/会签的流程定义；运行时引擎对这份"数据"解释执行——一门小语言加一个解释器（解释器模式），而表单与流程天然是树形结构（组合模式）。工单中心"新增工单类型只配表单、不改代码"的能力，本质就是内嵌的低代码：

```kotlin
// 流程定义 = 元数据（组合成树）；interpret = 解释器（对元数据求值）
sealed interface FlowNode {
    data class Task(val role: String) : FlowNode
    data class Condition(val expr: String, val yes: FlowNode, val no: FlowNode) : FlowNode
}

fun interpret(node: FlowNode, ctx: TicketContext) = when (node) {
    is FlowNode.Task -> ctx.assign(node.role)
    is FlowNode.Condition ->
        if (ctx.eval(node.expr)) interpret(node.yes, ctx) else interpret(node.no, ctx)
}
```

代价也要看见：解释执行慢于生成代码、Schema 要做版本演化（历史单据按提交时的旧版结构渲染）、流程引擎很容易越做越像通用 BPM 而复杂度失控——通用性的代价，第四阶段 DDD 处回头细算。

### 2.4 怎么练

- 找当前项目里最"胖"的类/服务，数它有几个变化原因，说出拆分方案。
- Code review 时练习用术语描述问题："这个类不满足 SRP""这里违反了 DIP"。

## 3. 架构质量属性

### 3.1 功能需求 vs 质量属性

功能需求回答"系统能做什么"，质量属性回答"系统做得怎么样"。**任何功能都能在任何架构上实现，但性能、可用性这些属性由架构决定**——这就是架构工作主要围绕质量属性展开的原因。

一个直观对比：两家电商的功能清单可以一模一样（浏览、下单、支付、退款），但一个大促扛得住、一个日常高峰就崩——功能相同、架构不同，差别全在质量属性。**功能决定系统能不能上线，质量属性决定系统能不能活下来。**

#### 3.1.1 运行期属性与开发期属性

按"谁在什么时间感知到它"分两类：

| 类别 | 属性 | 谁最关心 |
|---|---|---|
| 运行期 | 性能、可用性、可靠性、安全性、可扩展性、易用性 | 用户、业务方、运维 |
| 开发期 | 可维护性、可测试性、可移植性、可复用性 | 开发团队 |

两个推论：

- 运行期属性的失误**上线即爆**；开发期属性的失误**温水煮青蛙**——后者更容易被忽视，因为故障复盘不会写"根因是可维护性差"，但大量事故的远因正是代码腐化。
- 两类属性天然冲突：为极致性能写的代码（绕过分层、缓存套缓存）几乎总在牺牲可维护性，见 3.4。

反例（订单系统）：立项文档只有功能清单加"高性能、高可用"两个形容词——结果缓存策略没有依据（不知道目标延迟）、压测没有通过标准（不知道多少 QPS 算过关）、故障没有判定依据（不知道这算不算事故）。修正：每个属性都落成 3.3 的可验证场景。

### 3.2 核心属性逐一展开

#### 3.2.1 性能：延迟、吞吐、并发

度量三件套：

- **延迟**：一个请求花多久。必须看分位数 P50/P95/P99——**平均值会骗人**：100 个请求里 99 个 10ms、1 个 2s，平均约 30ms 看着很好，但那个 2s 的用户已经流失；而落在 P99 长尾里的往往恰是订单量最大、数据最多的重度用户。
- **吞吐量**：每秒处理多少请求（QPS/TPS）。
- **并发数**：同时在处理的请求数。三者由利特尔法则相连（见下第 4 点）——延迟和吞吐不是两个独立指标，优化一个常牵动另一个。

**1. 延迟的分位数：为什么长尾这么长**

分位数的读法：P50 = 一半请求比它快（中位数）；P95 = 95% 的请求比它快；P99 大致就是每 100 个请求里最慢那一个的量级。**分位数选多严苛，取决于一次糟糕体验的代价**：日均一亿次请求的系统，哪怕只有 P999 越线，也是每天十万次糟糕体验；而内部报表系统看 P95 就够了。

延迟分布是**长尾**而非正态：GC 停顿、缓存未命中、锁竞争、慢 SQL、重试风暴、个别大账户的超大数据量……每个小概率因素都在分布右端堆出肥尾。两个实践推论：

- 反例（订单系统）：监控大盘只展示"平均响应时间 45ms"，一切看似正常；实际 P99 已到 3s，而落在长尾里的恰是订单最多的大买家，客诉不断。修正：大盘直接展示 P95/P99 分位数 + 错误率，平均值只作参考。
- **分位数不可再平均**：把一小时里上千个小窗口的 P99 平均成"小时级 P99"，毛刺会被抹平——要看分位数就看小窗口原始值，不要看聚合平均值。

**2. 延迟测在哪一端：服务端耗时 ≠ 用户体验**

服务端日志记录的是"处理耗时"；用户感受到的是端到端耗时 = 网络 + 排队（网关、线程池、连接池）+ 处理 + 失败重试。反例：服务端 P99 = 120ms，客户端实测 P99 = 800ms——差距在网关排队和连接池等待上，服务端自己看不见。修正：关键链路在客户端/网关埋点真实体验（RUM）；APM 只能回答"服务端尽力了吗"，回答不了"用户爽了吗"。

**3. 吞吐量：QPS、TPS 与峰值/均值**

- **QPS vs TPS**：QPS 按请求数、TPS 按事务数——一次"下单事务"包含查库存、算价、创建订单、扣款多个请求。压测前先对齐口径，两者混用是沟通事故的常客。
- **单位随层级变化**：应用层 QPS → 数据库层 QPS/IOPS → 缓存层命中 QPS → 网络 MB/s → 消息队列条/秒。容量推算要逐层换算，别拿应用层 QPS 直接去套数据库的极限值。
- **峰值与均值**：容量按峰值设计（再乘安全系数），成本却按均值发生——电商大促的峰均比可达 10 倍以上，这正是弹性伸缩存在的理由（呼应 3.2.4 的弹性）。
- **场景（秒杀）**：平时 500 QPS 的商品页，活动开始瞬间冲到 5 万 QPS——瞬时百倍流量、库存却只有 1000 件。峰均比上百倍时"按峰值常备资源"成本无法承受，于是有缓存预热、MQ 异步下单、限流排队这些削峰手段（第三阶段逐一拆解）；容量推演永远从"流量有多少、每个环节能扛多少"开始。
- **吞吐-延迟曲线与膝点**：负载上升，延迟先缓升；越过某个利用率（经验上约 70%~80%）后排队急剧膨胀、延迟雪崩。**系统的"最大可用吞吐"不是被压垮前的极限值，而是延迟仍达标时的最大吞吐**——所以吞吐必须和延迟一起报告（见第 6 点）。

**4. 并发与容量估算：利特尔法则实战**

利特尔法则：**并发数 = 吞吐 × 平均延迟**。一条公式把"要加多少机器"从拍脑袋变成算术（订单系统示例）：

> 大促峰值 5 万 QPS、目标平均延迟 100ms → 系统需同时处理 5 万 × 0.1s = 5000 个请求；单实例健康并发约 500 → 至少 10 个实例；再按膝点纪律留 30% 余量 → 部署 14 个。

配套认知：**在线用户数 ≠ 并发请求数**——10 万用户同时在线，按人均操作频率折算出的并发请求数可能只有几千，容量规划算的是后者。

**5. 资源层指标：别只盯着接口（USE 方法）**

USE 方法（Brendan Gregg）：对每一层资源都问三件事——**利用率**（U，忙的占比）、**饱和度**（S，排队/堆积程度）、**错误**（E，出错计数）。

| 资源 | 利用率 | 饱和度（排队信号） | 错误 |
|---|---|---|---|
| CPU | CPU 使用率 | load 相对核数、运行队列 | — |
| 内存 | 已用比例 | swap、GC 频率 | OOM kill |
| 磁盘 | iostat util% | iowait、队列深度 | IO 错误 |
| 网络 | 带宽占比 | 重传率、丢包 | 超时 |
| 线程池/连接池 | 池使用率 | 等待队列、拒绝数 | 获取超时 |
| 数据库 | 活跃连接占比 | 慢查询数、锁等待 | 死锁 |
| 缓存 | — | 热 key、大 key | 命中率下降、穿透 |
| 消息队列 | 消费速率 | **堆积量（lag）** | 消费失败 |

两条经验：接口延迟飙升时**先看饱和度列**——排队是延迟的头号来源（CPU 才 60% 但线程池排队 200 个，慢在排队不在计算）；MQ 堆积是最直白的饱和度信号，堆积 = 消费速率跟不上生产速率。JVM/Kotlin 补充：GC 暂停是 P999 毛刺的常客，长尾突刺先翻 GC 日志。

**6. 指标要组合看：压测结论三件套**

单个数字都会骗人：只报 QPS 不报延迟（那是崩溃边缘的吞吐）、只报延迟不报错误率（超时被记成"慢"而不是"错"）。合格的结论 = **吞吐 + 延迟分位数 + 错误率三者同时达标**：

> "下单接口在 5 万 QPS 负载下，P99 < 500ms、错误率 < 0.1%" ✓——能当验收标准
> "单机压到了 8000 QPS" ✗——延迟多少？错了多少？都不知道

常见手段：缓存、异步（非核心链路外移）、分片、池化、预计算——注意它们各自作用于三件套的哪一项（缓存降延迟、异步提吞吐、分片扩并发上限），详见 3.4 战术表。

经典反例——列表接口循环查库（N+1）：

```kotlin
// 反例：1 次查列表 + N 次查用户；一页 50 条就是 51 次 DB 往返
fun listOrders(userId: Long): List<OrderVO> =
    orderRepo.findByUserId(userId).map { order ->
        OrderVO(order, userRepo.findById(order.buyerId))   // 循环内单条查询
    }

// 修正：批量查询 + 内存组装，固定 2 次往返
fun listOrders(userId: Long): List<OrderVO> {
    val orders = orderRepo.findByUserId(userId)
    val users = userRepo.findByIds(orders.map { it.buyerId }.toSet()).associateBy { it.id }
    return orders.map { order -> OrderVO(order, users.getValue(order.buyerId)) }
}
```

N+1 的教训：架构没坏、选型没错，坏在**数据访问模式**——性能优化的一大半是在"减少往返、减少重复计算"，而不是换更贵的中间件。

#### 3.2.2 可用性：几个 9 的真实含义

定义：系统**能对外提供服务的时间占比**。SLA 用"几个 9"表达，换算成停机时间才有体感：

| SLA | 年停机 | 月停机 | 达到它大致需要 |
|---|---|---|---|
| 99% | 3.65 天 | 7.2 小时 | 单实例 + 快速重启 |
| 99.9% | 8.8 小时 | 43 分钟 | 冗余部署 + 监控告警 |
| 99.99% | 53 分钟 | 4.3 分钟 | 多可用区 + 自动切换 |
| 99.999% | 5.3 分钟 | 26 秒 | 多活 + 全自动容灾 |

关键规律：**每多一个 9，成本大约上一个数量级**，而业务感知未必同步提升——所以 SLA 要按链路分层定（下单 99.99%、推荐 99.9%、报表 99%），一刀切要么浪费要么欠账。

**场景（MES）**：产线 7×24 连续生产，MES 宕机不等于马上停产，但数据不能永久丢——于是有"断网时边缘网关本地续采、恢复后补传"与"降级为手工扫码报工"这类战术。把 SLA 翻译成钱才有讨论基础：99.9%（月停 43 分钟）对离散加工车间可能可接受，对连续产线却意味着整线在制品报废——同一张 SLA 表，贴上业务场景才能裁决。

公式视角：可用性 = MTBF / (MTBF + MTTR)，于是有两条路——**少出事**（提高 MTBF：冗余、隔离）和**快恢复**（降低 MTTR：监控、自动切换、演练）。多数团队过度盯着前者，其实后者的性价比常常更高。

反例（订单系统）：库存读 Redis 单实例，Redis 一挂全站不能下单——典型的单点故障（SPOF）。修正：哨兵/集群 + 本地缓存兜底 + 降级走数据库扣减（慢但可用）。

补充一个反直觉事实：**可用性的最大敌人往往不是机器挂掉而是变更**——业界统计多数线上故障由发布和配置变更引发，所以灰度、回滚本身就是可用性战术（第五阶段展开）。

#### 3.2.3 可靠性与容错：在线 ≠ 正确

与可用性的区分：**可用性说"在不在服务"，可靠性说"服务的结果对不对"**——系统可以 99.99% 在线，但每千单错一单：在线而不可靠。

容错设计的标准问题："下游坏了、网络抖了、消息重复了，我会怎样？"

经典反例——支付回调不幂等，网络重试导致重复发货：

```kotlin
// 反例：来一次处理一次，消息重试 → 用户收到两次发货
fun onPaymentCallback(cb: PaymentCallback) {
    orderService.markPaid(cb.orderId)
    warehouseService.ship(cb.orderId)
}

// 修正：幂等键 + 处理记录，重复消息直接跳过（markIfAbsent：首次标记返回 true）
fun onPaymentCallback(cb: PaymentCallback) {
    if (!dedupStore.markIfAbsent("pay-cb:${cb.orderId}:${cb.eventId}")) return
    orderService.markPaid(cb.orderId)
    warehouseService.ship(cb.orderId)
}
```

消息语义三档：至多一次（可能丢）、至少一次（可能重）、恰好一次（昂贵的幻觉）。工程通行解是**至少一次投递 + 消费端幂等**，因为网络重试无法根除（第三阶段展开）。

#### 3.2.4 可扩展性：加机器能不能顶住

定义：**负载增加时，通过加资源维持指标的能力**。两个方向：垂直扩展（换更强的机器，简单但有天花板、成本陡增）与水平扩展（加更多机器，天花板高但要求架构配合）。水平扩展的前提是**应用无状态**——任何请求打到任何实例都能处理。

反例（订单系统）——登录态存在实例本地内存：

```kotlin
// 反例：会话在实例内存里，负载均衡一换机器用户就"被登出"；
// 扩容前要预热，缩容丢会话——本地状态挡住了水平扩展
object LocalSession {
    val sessions = ConcurrentHashMap<String, Session>()
}

// 修正：状态外置到 Redis，实例本身无状态，扩缩容只是加减副本
class SessionService(private val redis: RedisClient) {
    fun get(token: String): Session? = redis.get("session:$token")
}
```

区分两个词：**扩展性**（加机器能不能顶住）与**弹性**（流量来了能否自动扩、走了能否自动缩），云原生时代两者都要。

完整的扩展链条：接入层（负载均衡）→ 应用层（无状态 + 自动扩缩容）→ 数据层（读写分离、分库分表）。**应用层最好扩，数据层最难扩**——规模够大之后，扩展瓶颈几乎总落在数据层（第三阶段展开）。

**场景（物联网平台）**：接入设备从数万台长到百万台，连接数与上报量近似线性增长——典型的**写洪峰**扩展问题（与秒杀的读洪峰方向相反）：逐条 INSERT 必挂，要靠无状态接入网关水平扩 + 消息队列削峰 + 消费端批量聚合写入。可扩展性设计的第一问永远是"哪个维度在涨"（用户数、数据量还是流量），沿真正在涨的维度扩。

**为什么加机器不总是线性扩展：Amdahl 定律与 USL**

水平扩展的理想图景是 N 台机器 N 倍吞吐，现实有两层折扣，各有一条定律管着：

- **Amdahl 定律——串行部分封顶**。任何链路总有绕不开的串行段：单一热点行、全局锁、必须落到同一个库的写入。设串行比例为 S，N 台机器的加速上限是 1/S——串行 15% 的系统理论上限只有约 6.7 倍，加到 200 台也只是逼近它。推论：**加机器之前先看串行比例**，S 不动，机器堆上去只是让排队更整齐。
- **USL（Universal Scalability Law）——争用与协调吃掉收益**。Gunther 在 Amdahl 之上再加两项随集群规模增长的开销：**α 争用**（节点抢共享资源：同一个库、同一把分布式锁）与 **β 协调**（节点间为保持一致付出的通信：分布式事务、复制、共识）。β 项随节点数**平方**增长，所以扩展曲线**先升后降**——过了峰值点再加机器，吞吐不涨反跌。

Kotlin 推演（数字先于机器回答"扩容划算吗"）：

```kotlin
// Amdahl：串行比例 S 无法被并行化，加速比 = 1 / (S + (1-S)/N)，上限 1/S
fun amdahl(serial: Double, nodes: Int): Double =
    1.0 / (serial + (1 - serial) / nodes)

// USL：N 台机器相对 1 台的吞吐倍数 = N / (1 + α(N-1) + βN(N-1))
// α 争用：节点抢同一共享资源（同一个库、同一把锁）的开销
// β 协调：节点间为保持一致付出的通信（分布式事务、复制、共识），随 N² 增长
fun usl(alpha: Double, beta: Double, nodes: Int): Double =
    nodes / (1 + alpha * (nodes - 1) + beta * nodes * (nodes - 1))

fun main() {
    println("Amdahl（串行 15%）：")
    for (n in listOf(2, 10, 20)) {
        println("  $n 台 = ${"%.1f".format(amdahl(0.15, n))} 倍（上限 ${"%.1f".format(1 / 0.15)} 倍）")
    }
    println("USL（α=0.05，β=0.002）：")
    for (n in listOf(8, 16, 22, 32)) {
        println("  $n 台 = ${"%.1f".format(usl(0.05, 0.002, n))} 倍")
    }
}
```

运行结果：Amdahl 上限 6.7 倍，2→20 台只从 1.7 涨到 5.2；USL（α=0.05，β=0.002）峰值在 22 台附近的 7.4 倍，**16→32 台机器翻倍、吞吐反而从 7.2 掉到 7.1**——β 项超过线性收益的拐点真实存在。

反例（订单系统）：下单链路 85% 已并行化，剩下 15% 必须写同一个数据库——Amdahl 上限 6.7 倍，扩到 20 台已接近打满。此时把它拆成 5 个微服务：若服务仍然共库，S 一点没降（上限纹丝不动），反而每笔订单多了几次跨服务调用、多了一次分布式事务——β 变大，实际吞吐可能比拆前还低。**拆了服务没拆数据 = 只付 USL 的成本、不拿 Amdahl 的收益**，这正是第二阶段要展开的"分布式单体"。

**场景（工单中心/MES）**：评估"某模块拆出去能不能换来吞吐"，别看代码量看数据——① 这段逻辑访问共享资源（S 与 α）的占比多少？② 拆出去之后，跨服务调用与一致性保障（β）新增多少？两个问题算完，多数内部系统的答案是"读写分离比拆微服务便宜且有效"。

三句话收束：加机器前先算 S；优化优先削 S 与 α（3.4 战术表里的读写分离、缓存、异步都在削它们）；β 是微服务最容易低估的暗账——协调成本随规模平方涨。

#### 3.2.5 可维护性：长期成本的大头

定义：改动的难易。业界经验：开发只占软件生命周期成本的 20%~40%，其余全是维护（改需求、修缺陷、升级依赖）——**为"好改"投入的钱回报期最长**。

比"代码干净"更可操作的判据：

- **波及范围**：改一条价格规则要动几个模块、发几个服务？
- **新人上手时间**：新人多久敢独立改核心模块？
- **可逆性**：这次改动错了，回滚多容易？

反例（订单系统）：价格计算散落在下单、退款、后台改价、导出报表四处，规则一变四处改、四处测、四处祈祷。修正：收敛为独立的 PricingService，其余位置只调用——这就是高内聚低耦合（呼应 2.2）。

**场景（工单中心）**：流转与分派规则随工单类型不断变化（见 2.1.1）——硬编码时代每新增一种类型都要改代码、发版、回归；收敛为策略实现 + 配置之后，"新增一种工单类型只改 1 个模块、0 行核心代码、预计 2 人日"就成了可验收的可维护性场景，而不是"代码要写干净"的愿望。

#### 3.2.6 可测试性：难测 ≈ 耦合重

定义：**在受控条件下低成本验证行为的能力**，三个条件：能隔离依赖、能控制输入、能观测输出。

可测试性差几乎总是设计问题的信号灯：内部 `new` 出真实依赖（直连数据库、Kafka）的类没法单测，本质是违反了 DIP（呼应 2.1）——依赖接口并由外部注入，测试时注入假实现即可。**测试不只是质量保障，更是设计质量的反馈环**：一段代码难测，先别抱怨测试框架，先看它的耦合。

#### 3.2.7 安全性：CIA 与越权

三要素 CIA：**机密性**（不给看的不给看）、**完整性**（不给改的不给改）、**可用性**（攻击打不瘫服务——与 3.2.2 在 DDoS 防护上汇合）。

基础区分：**认证（你是谁）≠ 授权（你能干什么）**，混淆两者是高频漏洞来源。

经典反例——订单接口水平越权（IDOR）：

```kotlin
// 反例：自增 ID + 不校验归属者，攻击者遍历 id 即可拉走全站订单
fun getOrder(orderId: Long): Order = orderRepo.findById(orderId)

// 修正：查询永远限定当前用户；对外标识改用不可预测的订单号
fun getOrder(userId: Long, orderId: Long): Order =
    orderRepo.findByIdAndOwnerId(orderId, userId) ?: throw NotFoundException()
```

IDOR 是真实事故里最高频的漏洞类型之一——**功能测试全绿也照样越权**，因为它不是功能缺陷而是属性缺陷，这正是"质量属性需要专门的场景来验收"的例证。

架构视角两条：安全要**左移**（设计期做威胁建模，而不是上线前靠渗透测试兜底）；**纵深防御**（网关鉴权 + 服务间校验 + 数据层权限各守一道）优于单点设防。

#### 3.2.8 可观测性：出事后多快能定位

定义：**仅凭外部输出就能推断系统内部状态的能力**。三支柱：日志（这次请求发生了什么）、指标（系统整体怎么样）、链路追踪（一个请求经过了谁、各花多久）。

反例（订单系统）："下单慢"排查三天，手段是在代码里到处加日志、重启、复现。修正：traceId 全链路贯穿、关键接口延迟分位数埋点、异常分级告警——排查从"三天加日志"变成"打开面板看链路"。

终极判据：**遇到一个没预料到的故障，多久能定位？**（第五阶段展开）

### 3.3 把属性变成可验证的场景

抽象目标（"系统要快、要稳"）无法指导设计。质量属性场景 = **刺激 + 环境 + 响应**：

> 例 1：订单查询接口在高峰时段（环境）收到请求（刺激），99% 在 200ms 内返回（响应）。
> 例 2：单机房故障（刺激）发生时（环境），核心服务 1 分钟内恢复（响应）。

SEI 的完整版是六要素：刺激源（谁发起）、刺激（什么事件）、制品（作用在哪部分）、环境（什么条件）、响应（系统做什么）、响应度量（用数字衡量）。日常用三要素够用，关键是**响应必须带数字**——没有数字的场景仍然无法验收。

场景化的三大检验：

1. **可验收**：能直接变成压测通过标准（"99% < 200ms"就是压测报告的及格线）
2. **可权衡**：冲突时能拿来排序（"宁可 P99 500ms 也要强一致"能写成场景，"要快要稳"不能）
3. **可追溯**：评审时每条场景都能指出由哪个战术支撑（见 3.4）

反模式对照——把 SLA 写成形容词：

| 形容词版（不可验收） | 场景版（可验收） |
|---|---|
| 系统要快 | 下单接口日常 P99 < 300ms，大促 P99 < 1s |
| 系统要稳 | 任一可用区故障，核心链路 1 分钟内恢复且不丢单 |
| 数据要安全 | 所有订单接口校验归属者；身份证号落库加密 |
| 要好维护 | 新增一种优惠类型只改 Pricing 模块，预计 2 人日 |

最后一行示范了**可修改性场景**：变更刺激（加一种优惠）在开发期（环境）到来，只波及 1 个模块（响应）、2 人日（度量）——场景不只用来描述运行期属性。

### 3.4 冲突与战术

典型冲突：

- 性能 vs 可维护性（为快绕过分层、缓存套缓存——快一时，坑后人）
- 可用性 vs 一致性（CAP，第三阶段展开：转账宁拒服务，Feed 点赞数容忍短暂不一致）
- 安全 vs 开发效率与性能（加密、鉴权链路都有开销——不能砍，但可分层设防）
- 延迟 vs 一致性（强一致意味着同步等待确认——"读到自己刚下的订单"是有代价的）
- 可扩展性 vs 简单性（无状态、分片都有架构成本——日活 1 万的系统不必预付）

给冲突贴上场景（同一对冲突，场景不同裁决完全不同）：MES 设备采集直写数据库最简单，但一台设备秒级多条的高频上报会把库写挂——批量聚合写入复杂一点，换回产线 7×24 的可用性（简单性 vs 可用性）；物联网平台百万台设备必须无状态接入 + MQ 削峰，而几万在途工单的工单中心连读写分离都用不上——为不存在的规模预付复杂度，就是 1.4.5 的假权衡（可扩展性 vs 简单性）。

架构战术 = 针对某个质量属性的成套原子手段：

| 属性 | 主要战术 | 战术的代价 |
|---|---|---|
| 性能 | 缓存、异步、分片、池化、预计算 | 缓存一致性、异步难调试、分片复杂度 |
| 可用性 | 冗余、心跳检测、故障转移、超时重试、降级、限流、多活 | 资源翻倍、运维复杂、数据同步 |
| 可靠性 | 幂等、重试、事务、对账、死信队列 | 开发量、延迟 |
| 可扩展性 | 无状态化、读写分离、分库分表 | 数据层改造大、约束多 |
| 可维护性 | 高内聚低耦合、清晰分层、模块化、ADR | 短期交付略慢 |
| 可测试性 | 依赖注入、接口抽象 | 前期设计约束 |
| 安全 | 认证授权、加密、最小权限、纵深防御、审计 | 性能与效率开销 |
| 可观测性 | 结构化日志、指标、链路追踪、告警 | 约 1%~5% 的性能与存储开销 |

两个要点：

1. **右列"代价"才是决策依据**——没有免费的战术，只有还没付账的战术。
2. **战术组合打包成架构模式**：冗余 + 心跳 + 故障转移 → 主备/集群；缓存 + 读写分离 → 读扩展。模式是为某组属性优先级预打包的战术组合——所以**先定属性优先级、再选模式**，顺序反了就是在照抄别人的答案。

不同系统的属性优先级（以及由此推出的架构倾向）：

| 系统类型 | 属性前三 | 架构倾向 |
|---|---|---|
| 支付/交易 | 一致性、安全、可用性 | 同步强一致、对账兜底、宁慢不错 |
| Feed 流 | 可用性、吞吐、成本 | 最终一致、重度缓存、冗余读 |
| 实时游戏 | 延迟、可用性、扩展性 | 状态在内存/就近节点、同区部署 |
| 报表/数仓 | 成本、口径正确、吞吐 | 离线批处理、T+1、廉价存储 |
| 内部后台 | 可维护性、安全 | 单体/模块化单体、权限做好 |

实践要点：接到需求先问"这个系统**最重要的质量属性是什么、目标值多少**"。主要矛盾不同，架构完全不同——交易系统优先一致性，Feed 流优先可用性。

### 3.5 怎么定优先级：场景投票

"哪个属性最重要"不能靠拍脑袋（每个干系人都会说自己那栏最重要）。轻量流程（简化自 SEI 的 ATAM 架构评估法）：

1. **收集**：各干系人（业务、开发、运维）每人写几条质量属性场景，凑 20~30 条
2. **投票**：按重要度投票，选出前 5~10 条
3. **定序**：前几条场景所属的属性即优先级序——之后所有属性冲突按它裁决
4. **留档**：结论写进 ADR（背景、排序、被牺牲的属性及理由）

反例：跳过排序直接选型——"我们要用微服务，因为大厂都用"。大厂微服务解决的是大厂的矛盾（几十个团队的协作与发布效率），你的矛盾可能只是数据库连接数不够，一次读写分离就够了。这是 1.4.5 "隐式权衡"在质量属性上的重现。

本节自测：

1. 结合你熟悉的 MES：把"产线 7×24 不能停"翻译成"刺激 + 环境 + 响应"场景（断网、宕机、发布变更各写一条），响应带数字了吗？
2. 工单中心的 SLA 该定几个 9？先把催办/关单链路与统计报表链路分开各定一个，再各自换算成年停机时间——与"全系统一刀切一个数"相比差在哪？
3. 最近一次性能优化，盯的是平均值还是 P99？优化前后各是多少？
4. 用利特尔法则估算你的系统容量：峰值 QPS × 目标延迟 = 需要的并发数，再除以单实例健康并发 = 实例数——算出来和当前实际部署差多少？
5. 你的系统里有单点吗？它挂了会发生什么？恢复是自动的还是靠人爬起来处理？
6. 明天流量涨 10 倍，哪一层先崩？——那层就是当前扩展性的短板。
7. 3.4 的五行系统类型表里，你的系统最像哪一行？现有架构与那一行的"架构倾向"匹配吗？
8. 用 Amdahl 定律给你的核心链路算笔账：必须串行访问同一共享资源（单库写入、全局锁、单点服务）的步骤占比约多少？由此算出的扩展上限是几倍？当前实例数离上限多远，继续加机器还划算吗？如果打算拆微服务，拆的是 S 与 α，还是只新增了 β？

## 第一阶段自测

1. 你当前项目里，哪一次改动是架构级的？哪一次只是设计级？判断依据？
2. 你的系统当前最主要的矛盾是什么？做了哪些权衡？
3. 项目里最"胖"的类违反 SRP 吗？它有几个变化原因？怎么拆？
4. 你的系统最核心的质量属性是什么？写成"刺激 + 环境 + 响应"的场景是什么样？
5. 回看 2.1.1 的工单中心案例：你们项目最近一次"新增一种类型/规则"的改动，是加配置、加一个策略实现，还是又摞了一层 if-else？下一次新增预计要付几天成本？
6. 若由你为桶装水商城设计押金生命周期（支付押金→桶在手→回收验收→退押金/扣损），你会建状态机还是写 if-else？判断依据与 2.1 的哪条原则相关？
