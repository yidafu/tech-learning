## 3. 安全架构

可观测性回答“出了事能不能看见”，部署发布回答“改坏了能不能回去”，安全架构回答的问题是：**能不能把“不该发生的事”挡在门外，并且在事后证明谁做了什么**。它常被当成“上线前加个登录”的功能项，但从架构视角看，安全是贯穿所有质量属性的一条横切约束：

- **与性能互斥又共生的经典权衡**：TLS 握手、验签、慢哈希都耗 CPU——支付系统登录用 bcrypt 故意慢（防暴力破解），代价是登录接口吞吐骤降，于是要配套限流与预热（见 [章节3/06-高可用与稳定性-限流熔断与多活.md](../章节3/06-高可用与稳定性-限流熔断与多活.md)）。
- **与可观测性共享基础设施但目标不同**：审计日志、访问日志都是日志（见 [02-可观测性-日志指标与链路追踪.md](02-可观测性-日志指标与链路追踪.md)），但审计日志有合规保留期与防篡改要求，不能和普通应用日志混在同一个可随意删除的存储里。
- **失败模型不同**：性能问题的失败是“慢”，安全问题的失败是“静默的”——数据被拖走了系统还在正常运行，用户与监控系统毫无感知。这决定了安全架构的评审不能靠“跑一遍看结果”，必须靠清单、threat model 与演练。

本文按“先分清两件事（3.1 认证/授权）→ 标准化协议（3.2 OAuth2、3.3 JWT）→ 数据本身（3.4 敏感数据）→ 网络假设推倒重来（3.5 零信任）”的顺序展开，最后给一份可执行的安全架构 Checklist。

### 3.1 认证 vs 授权

| 概念 | 回答的问题 | 支付与清结算例子 |
|---|---|---|
| 认证 Authentication | 你是谁？ | 支付渠道回调：渠道用约定签名证明“我是渠道官方”而非伪造者；商户登录商户平台 |
| 授权 Authorization | 你能做什么？ | 商户 A 只能查自己的交易与分账单；只有运营风控角色能发起退款 |

经典漏洞：只做认证不做授权——商户登录后枚举 settlementId 就能查到任意商户的分账单（水平越权）。任何查单接口都必须：

```kotlin
fun mySettlement(settlementId: SettlementId, currentMerchant: MerchantId): Settlement {
    val s = settlementRepository.find(settlementId) ?: throw NotFoundException()
    check(s.merchantId == currentMerchant) { "无权访问他人分账单" }  // ✅ 资源归属校验，服务端每次都做
    return s
}
```

这段代码有两个细节值得放大：一是 `find` 之后**先比归属再返回**，比对不通过时统一抛 `NotFoundException` 还是 `ForbiddenException` 是一个权衡——返回 404 不向攻击者透露“这个 ID 存在但我无权看”，比明确返回 403 更保守；二是校验发生在服务端业务逻辑里，而不是网关或前端——网关只能做粗粒度的“这个 token 能不能调这个路径”，资源归属这种细粒度判断只有业务层有数据。

#### AAA 三件套：认证、授权、审计

工程上把访问控制整理成 **AAA**（Authentication 认证、Authorization 授权、Accounting/Audit 审计）三件套，比只谈前两者更完整：

| 环节 | 回答的问题 | 没有它会怎样 | 支付清结算例子 |
|---|---|---|---|
| 认证 | 你是谁？ | 任何人可以冒充任何人 | 伪造渠道回调，凭空造一笔“已支付” |
| 授权 | 你能做什么？ | 合法用户可以越界操作 | 商户 A 查商户 B 的分账单（上文水平越权） |
| 审计 | 你做了什么？ | 出事后无法取证、无法收敛权限 | 有人凌晨批量导出了 10 万条交易明细，但查不到是谁、用哪个账号、从哪个 IP |

三者的关系是**层层依赖 + 闭环反馈**：认证是授权的前提（没验明身份，授权无从谈起）；授权是认证的价值兑现（只认人不管权限，认证只是门禁贴纸）；审计则同时是兜底与校准器——

- **兜底**：授权规则总有漏网之鱼（新接口忘了挂权限、规则配错），审计记录保证漏过去的操作至少**留痕可查**。安全架构的铁律之一：**假设任何一道闸都可能失效，审计是最后一道**。
- **校准**：审计数据反过来修正授权——统计发现某个角色 90% 的人从未用过某权限，就是权限收敛的依据。“先审计观察、再收紧授权”是比凭主观判断改权限表安全得多的工作方式。

审计在多租户 SaaS 控制平面里是合规硬要求（见 [示例项目场景.md](../示例项目场景.md) 场景十二）：租户开通/冻结、套餐变更、管理员改配置这类**特权操作**，必须记录“谁、何时、对哪个租户、做了什么、结果如何”，且审计日志独立存储、追加写（append-only）、保留期比普通日志长（常见 180 天以上），运维不能随手清。❌ 反例：某团队把审计日志和应用日志写进同一个 ES 索引、统一 30 天滚动删除——等监管来查半年前的操作记录，什么都没有。✅ 修正：审计走独立管道独立存储，写权限只归审计服务，应用服务只可追加不可删改。

工程判据：评审任何一个“能改数据”的接口，依次问三句——**谁在调用（认证）？它被允许吗（授权）？操作记下来了吗（审计）？**三问都答得上才算过。

#### 认证强度：按操作风险分层

AAA 的“认证”一环自身还要再分层——认证不是“过一次登录就完事”，**强度必须与被保护操作的风险匹配**：

| 强度 | 因素构成 | 适用 | 本工作区例子 |
|---|---|---|---|
| 单因素 | 口令 | 低风险只读 | 商户平台查昨日交易流水 |
| MFA 双因素 | 口令 + OTP/推送确认 | 改配置、动资金 | 商户修改收款结算账户、运营发起大额退款，强制二次确认 |
| 证书/硬因素 | 私钥证书、硬件密钥 | 机器身份与最高风险操作 | 渠道回调验签、内部服务 mTLS、财务人员 UKey 签批 |
| 生物特征 | 指纹/人脸 | 本地解锁便捷场景 | 只用于“解锁本机 App”，不做远程认证主因素 |

生物特征那行有独立的道理：它是**不可重置的凭证**——口令泄露可以改密码，指纹泄露一辈子只有十枚。所以生物特征适合本地比对（数据不出设备），远程认证永远以口令 + MFA 或证书为主因素。

工程判据：接口按 3.4 的数据分级映射认证强度——读公开/读内部可用单因素，改敏感、动机密与资金类操作一律 MFA；机器与机器之间（渠道回调、服务互调）只认签名与证书，不存在“回调还要输密码”。

#### RBAC vs ABAC：权限模型的分水岭

授权模型里最常被拿出来对比的是两派：

- **RBAC（Role-Based Access Control，基于角色）**：权限绑定在角色上，人通过被授予角色获得权限。商户平台里“运营、风控、财务、商户管理员”就是四个角色。
- **ABAC（Attribute-Based Access Control，基于属性）**：授权判定不查“你是什么角色”，而是**当场计算一条策略**——主体的属性（部门、租户、职级）、资源的属性（归属商户、金额、数据级别）、环境属性（时间、来源 IP、是否工作时间）共同决定放行与否。上文 `mySettlement` 里的 `s.merchantId == currentMerchant`，本质上就是一条最小的 ABAC 规则（主体属性 = 当前商户，资源属性 = 分账单归属商户）。

| 维度 | RBAC | ABAC |
|---|---|---|
| 判定依据 | 你持有哪个角色 | 主体/资源/环境的属性组合是否满足策略 |
| 判定时机 | 授予角色时已大体确定 | 每次访问动态计算 |
| 粒度 | 角色 → 权限集合，较粗 | 可细到单条记录的单个属性 |
| 心智负担 | 直观，“给张三挂运营角色”人人能懂 | 需要设计属性模型与策略语言，门槛高 |
| 适应性 | 维度一多就爆炸（见下） | 天然适配多维交叉 |
| 典型失败模式 | 角色爆炸 | 策略不可读、属性源头不可信 |

**RBAC 的经典失败是角色爆炸**：权限需求一旦按多个独立维度交叉，角色数量就以乘积增长。桶装水商城的管理后台就有这个苗头——需要区分“华东区/华南区”（地域维度）、“直营/加盟”（渠道维度）、“客服/配送调度/财务”（职能维度）、“只读/可操作”（操作维度）。RBAC 硬扛的结果是 `华东直营配送调度可写`、`华南加盟客服只读`……理论组合 2×2×3×2 = 24 个角色，每新增一个维度，角色数按其基数成倍增长；最后没人说得清某个人该挂哪些角色，权限治理失控。

ABAC 用属性判据化解：不建 24 个角色，而是四条属性规则——`region == 主体.region`、`channel == 主体.channel`、`职能 ∈ 主体.duties`、`操作 ∈ 资源.allowedOps`。新增维度是加一条属性，不是翻倍建角色。示意片段：

```kotlin
// 片段：ABAC 思想的最小示意（真实系统会把策略外置成可配置规则）
data class Subject(val region: String, val channel: String, val duties: Set<String>)
data class Resource(val region: String, val channel: String, val allowedOps: Set<String>)

fun authorize(subject: Subject, resource: Resource, op: String): Boolean =
    subject.region == resource.region &&                 // 地域属性匹配
    subject.channel == resource.channel &&               // 渠道属性匹配
    op in resource.allowedOps &&                         // 资源允许该操作
    subject.duties.contains("delivery_dispatch")         // 主体具备该职能
```

那**多租户 SaaS 到底用哪个？**成熟答案是**分层混用，而不是二选一**：

- **控制平面用 RBAC**：租户管理员、运营、财务、客服这类角色数量有限、稳定，RBAC 直观可控；硬上 ABAC 反而让管理员配不明白。
- **数据平面与配额用 ABAC**：“租户 A 的用户只能读租户 A 的数据”本质是属性判定（token 里的 tenantId vs 资源的 tenantId）；“这个租户能开多少门店、能配多少 QPS”由套餐属性决定，也是属性判定。
- 两者交界处有一条铁律：**RBAC 的角色授权范围本身受 ABAC 的租户边界约束**——即使你在租户 A 里是管理员（RBAC 最高角色），你的所有授权在策略引擎里还要先过“你的 tenantId == 资源的 tenantId”（ABAC）这一关。角色再大，也大不过租户边界。

工程判据：维度 ≤ 2 且角色 ≤ 20 个，用 RBAC；维度开始交叉增长或出现“按数据归属/套餐属性动态判定”的需求，引入 ABAC；两者并存时明确写下“哪个判定先发生”（租户边界判定永远先于角色判定）。

### 3.2 OAuth2：四种授权模式与授权码 + PKCE

OAuth2 解决**委托授权**：用户让第三方应用有限度地访问自己在另一服务的资源，而不交出密码。典型场景：第三方开发的门店收银/对账 SaaS 要读商户在本平台的交易数据——商户授权它 `trade:read`，而不是把账号密码交给它。RFC 6749 的四种授权模式：

| 模式 | 适用客户端 | 现状 |
|---|---|---|
| 授权码 authorization_code | Web 服务端应用（能安全保存密钥） | 主流 |
| 隐式 implicit | 早期 SPA，token 直接放 URL 回传 | 已废弃（token 暴露在 URL 与浏览器历史） |
| 密码 password | 应用直接经手用户名密码 | 已废弃（应用不该接触密码） |
| 客户端凭证 client_credentials | 服务对服务，无用户参与 | 常用 |

**PKCE（Proof Key for Code Exchange）是授权码模式的扩展**，为“存不住密钥”的公共客户端（移动 App、SPA）设计，是当前新接入的推荐做法。流程：

```text
1. App 本地生成随机 code_verifier，计算 code_challenge = BASE64URL(SHA256(verifier))
2. App 拉起系统浏览器访问认证服务器：
   GET /authorize?client_id=merchant-app&redirect_uri=callback
       &code_challenge=xxx&code_challenge_method=S256&response_type=code&scope=trade:read settle:read
3. 用户在认证服务器登录并同意授权（密码只在认证服务器输入，App 碰不到）
4. 认证服务器携带一次性授权码 code 重定向回 redirect_uri
5. App 后台用 code + code_verifier 请求 /token
6. 认证服务器校验 SHA256(verifier) == 之前的 challenge，签发 access_token（含 refresh_token）
```

PKCE 的意义：即使第 4 步的授权码在重定向途中被劫持，攻击者没有 code_verifier 也换不到 token——等于给公共客户端补上了“一次性动态密钥”。服务间场景用 client_credentials：清结算服务以**自己的身份**（而非任何用户身份）申请 token 调用银行存管接口，这也是零信任中“服务身份”的落地（见 3.5）。

#### 四种模式现在到底怎么选：给谁用、为什么

RFC 6749 的表格回答“协议里有什么”，工程选型要回答“2026 年的今天，谁该用哪个”。一句话结论：**有用户参与的场景收敛到“授权码 + PKCE”，纯机器场景用 client_credentials，输入受限设备用 device_code，隐式和密码模式不再新接入**。

| 模式 | 给谁用 | 为什么 |
|---|---|---|
| authorization_code + PKCE | 一切有用户参与的接入：Web 服务端应用、移动 App、SPA、桌面端 | 密钥/verifier 不经过前端可窃取面；code 一次性且经后端交换；Web 服务端加 client_secret、公共客户端加 PKCE，两者统一为一条路径，降低认证服务器实现复杂度 |
| client_credentials | 服务对服务：清结算服务调银行存管、定时对账任务、内部微服务互调、开放平台的商户系统对接 | 无用户参与，token 即服务身份；配合 scope 控制该服务能调什么——零信任里“服务身份”的标准载体 |
| device_code | 输入受限设备：水站门口的取水大屏、工控车间的 HMI 触摸屏、智能电视 | 设备上没法输密码也没法弹浏览器，改由用户在手机上输入设备码完成授权，设备轮询拿 token |
| implicit / password | 不再用于任何新接入 | implicit 的 token 走 URL 前端回传且无 refresh，泄露面大；password 让第三方应用经手密码，密码一旦泄露波及用户在该平台的所有服务——这两种模式的场景分别被“授权码+PKCE”与“client_credentials/token 交换”完全替代 |

桶装水商城对照着记：用户在微信小程序里登录（微信侧认证，商城拿到身份）是 OIDC 的活（下文）；小程序后端调商城 API 用授权码+PKCE；水站大屏“扫码登录”用 device_code；商城的结算服务调支付网关用 client_credentials。

#### OAuth2 是授权框架，不是认证协议——以及 OIDC 补了什么

这是被误解最多的一点，值得单独掰开。**OAuth2 回答的问题是“这个应用能代表用户做哪些事”（授权），它从不回答“这个用户是谁”（认证）。**

❌ 反例：某团队拿 access_token 当登录态——用户侧登录成功后直接把 access_token 存起来当“已登录”凭证。问题有三：其一，access_token 里通常没有稳定的用户标识（client_credentials 的 token 甚至不对应任何用户）；其二，token 的受众是资源服务器，认证服务器无法在“登录”语义上声明“这个人是谁、给哪个应用看”；其三，不同用户、不同应用的 token 在结构上难以区分，伪造与混淆风险高。本质是拿授权凭证干了认证的活，语义错位。

✅ 修正：需要“登录”语义时用 **OIDC（OpenID Connect）**——它在 OAuth2 之上补了一层认证协议：

- 签发时多返回一个 **id_token**：一个标准 JWT，`iss`（谁签发的）、`sub`（这个用户的唯一标识）、`aud`（给哪个应用看的）等声明，应用**验签后**从中得到“认证服务器确认：这个人是谁”。认证语义由 `nonce`（防重放）与 `aud` 校验保证。
- 提供 UserInfo 端点与 Discovery 文档（`/.well-known/openid-configuration`），客户端不用硬编码各端点。

一句话分工：**OAuth2 管“能做什么”，OIDC 管“你是谁”；登录用 OIDC，登录之后代表用户调 API 用 OAuth2 授权**。API 网关是这套协议在架构上的收口处（见 [示例项目场景.md](../示例项目场景.md) 场景十一）：网关在入口统一完成 OIDC 校验与 OAuth2 token 验签（认证卸载），把解析出的用户/服务身份、scope 注入请求头传给下游服务——下游服务只信网关注入的身份头，同时自己做细粒度授权（3.1 的资源归属校验），这就是“网关管粗、服务管细”的双层鉴权。

#### 补充判据：回调验签与 OAuth2 的边界

开放对接还有一条不走 OAuth2 的路线：**AppKey + HMAC 请求签名**——接入方与平台共享 AppSecret，每次请求把方法、路径、参数、时间戳按约定规则串接后计算 HMAC 附在请求头，平台用同一密钥重算比对，时间戳 + nonce 缓存防重放。支付渠道回调验签正是这条路线（3.1 表里的“渠道用约定签名证明我是渠道官方”）。两者怎么选，判据一条就够：**有没有“用户授权第三方应用”这个语义**——

- 有（第三方收银 SaaS 代表商户读交易数据）：走 OAuth2/OIDC，授权范围、用户同意页、token 时效都是为这个语义服务的。
- 没有（平台↔渠道、平台↔商户系统的纯机器对接）：签名验签足够，硬套 OAuth2 反而平添 token 管理与刷新的复杂度。
- 两者不互斥且常并用：token 证明“调用方是谁、被授权什么范围”，请求签名额外证明“这条报文在途中未被篡改且不可重放”——资金类回调通常两者都要。

### 3.3 JWT：结构、签发、校验与常见误用

JWT（JSON Web Token）= `header.payload.signature` 三段 base64url 以 “.” 连接：

```text
header     {"alg":"RS256","typ":"JWT"}                              声明签名算法
payload    {"sub":"M-1001","scope":"settle:read","exp":1760000000}  业务声明（任何人都能解码）
signature  RS256(base64(header).base64(payload), 私钥)               防篡改：改任何一个字符，验签失败
```

Kotlin 签发与校验（jjwt 0.12.x）：

```kotlin
fun issueAccessToken(merchantId: String): String {
    val now = Instant.now()
    return Jwts.builder()
        .subject(merchantId)
        .claim("scope", "trade:read settle:read")
        .issuedAt(Date.from(now))
        .expiration(Date.from(now.plus(15, ChronoUnit.MINUTES)))  // ✅ 短有效期
        .signWith(privateKey, Jwts.SIG.RS256)
        .compact()
}

fun verifyAccessToken(token: String): Claims =
    Jwts.parser()
        .verifyWith(publicKey)     // ✅ 服务端固定算法与密钥，绝不信任 header 里声明的 alg
        .build()
        .parseSignedClaims(token)  // 验签失败 / 已过期都会在此抛异常
        .payload
}
```

常见误用（每条都是真实事故来源）：

❌ 误用 1：把 JWT 当服务端会话，指望“商户点登出后 token 立即失效”。JWT 是自包含、无状态凭证，服务端不存储它，签发后到过期前天然有效；要即时失效只能短过期 + refresh token 轮换（登出作废 refresh，access 最多再活 15 分钟）或引入黑名单（重新变有状态）。强会话控制的系统用服务端会话更简单。
❌ 误用 2：不设 exp 或有效期一年，一旦泄露就是长期通行证——支付场景等于长期资金操作权限。✅ access token 15 分钟 + refresh token 数天、每次使用轮换且可吊销。
❌ 误用 3：payload 放卡号、持卡人手机号等敏感信息。payload 只是 base64，**任何人都能解码**——签名防篡改，不防阅读；只放 merchantId、scope 等非敏感声明（卡号怎么存见 3.4）。
❌ 误用 4：校验时信任 header 里的 alg。历史漏洞：把 alg 改成 none 或 HS256 制造算法混淆攻击。✅ 服务端写死算法与密钥（如上 verifyWith）。
❌ 误用 5：商户前端按 JWT 里的 scope 隐藏“退款”按钮就当作完成授权。前端控制只是体验，**每次请求服务端必须重新校验 scope 与资源归属**（见 3.1）。

#### 手写最小 HS256：把签发与校验拆开看

库帮你做的事值得亲手做一遍——拆开后你会看到 JWT 的全部安全性只来自三行逻辑：**用只有签发方知道的密钥对前两段重算 HMAC，比对第三段，再查 exp**。下面这个完整示例只用 JVM 标准库（`javax.crypto` 的 HMAC 与 JDK 的 Base64Url），不引任何第三方依赖，带 main，可直接运行：

```kotlin
import java.nio.charset.StandardCharsets
import java.security.MessageDigest
import java.util.Base64
import javax.crypto.Mac
import javax.crypto.spec.SecretKeySpec

// ---------- 最小工具：Base64Url 与 HMAC-SHA256（全部 JVM 标准库，无第三方依赖） ----------

/** RFC 4648 Base64Url，无填充——JWT 三段的标准编码 */
fun b64Url(bytes: ByteArray): String =
    Base64.getUrlEncoder().withoutPadding().encodeToString(bytes)

fun hmacSha256(secret: ByteArray, data: ByteArray): ByteArray {
    val mac = Mac.getInstance("HmacSHA256")
    mac.init(SecretKeySpec(secret, "HmacSHA256"))
    return mac.doFinal(data)
}

// ---------- 手写最小 HS256 签发与校验 ----------

object MiniJwt {

    /**
     * 签发：signingInput = b64url(header) + "." + b64url(payload)
     * 签名 = HMAC-SHA256(secret, signingInput)，再 Base64Url 编码为第三段。
     * payloadJson 需是非空 JSON 对象（演示用，exp 由本函数统一追加）。
     */
    fun issue(payloadJson: String, secret: ByteArray, nowEpochSec: Long, ttlSec: Long): String {
        val header = """{"alg":"HS256","typ":"JWT"}"""
        val withExp = payloadJson.trim().removeSuffix("}") + ",\"exp\":${nowEpochSec + ttlSec}}"
        val signingInput = b64Url(header.toByteArray(StandardCharsets.UTF_8)) + "." +
                b64Url(withExp.toByteArray(StandardCharsets.UTF_8))
        val signature = hmacSha256(secret, signingInput.toByteArray(StandardCharsets.UTF_8))
        return signingInput + "." + b64Url(signature)
    }

    /** 校验结果显式建模，不抛异常：调用方按结果分支，而不是靠 try/catch 控制流程 */
    sealed class VerifyResult {
        data class Ok(val payloadJson: String) : VerifyResult()
        data class BadSignature(val detail: String) : VerifyResult()
        data class Expired(val exp: Long, val now: Long) : VerifyResult()
        data class Malformed(val detail: String) : VerifyResult()
    }

    fun verify(token: String, secret: ByteArray, nowEpochSec: Long): VerifyResult {
        val parts = token.split(".")
        if (parts.size != 3) return VerifyResult.Malformed("段数=${parts.size}，JWT 应为 3 段")

        // alg 固定写死 HS256：绝不信任 token 自己声明的算法（防 alg=none / RS256→HS256 混淆攻击）
        val headerJson = String(Base64.getUrlDecoder().decode(parts[0]), StandardCharsets.UTF_8)
        if (!headerJson.contains("\"alg\":\"HS256\"")) return VerifyResult.Malformed("alg 不是 HS256，直接拒绝")

        // 用相同签名输入重算 HMAC，与第三段比对（MessageDigest.isEqual 是常量时间比较，防时序侧信道）
        val signingInput = parts[0] + "." + parts[1]
        val expected = hmacSha256(secret, signingInput.toByteArray(StandardCharsets.UTF_8))
        val actual = try {
            Base64.getUrlDecoder().decode(parts[2])
        } catch (e: IllegalArgumentException) {
            return VerifyResult.Malformed("signature 段不是合法 base64url")
        }
        if (!MessageDigest.isEqual(expected, actual)) {
            return VerifyResult.BadSignature("签名不匹配：payload 或密钥与签发时不一致")
        }

        // 验签通过后才开始信 payload：解析 exp 做时效校验
        val payloadJson = String(Base64.getUrlDecoder().decode(parts[1]), StandardCharsets.UTF_8)
        val exp = Regex("\"exp\"\\s*:\\s*(-?\\d+)").find(payloadJson)?.groupValues?.get(1)?.toLong()
            ?: return VerifyResult.Malformed("payload 缺少 exp 声明")
        return if (nowEpochSec >= exp) VerifyResult.Expired(exp, nowEpochSec)
        else VerifyResult.Ok(payloadJson)
    }
}

fun main() {
    // 生产环境密钥应从 KMS/配置中心注入，绝不硬编码入库；此处为演示
    val secret = "demo-secret-store-in-kms-rotate-quarterly".toByteArray(StandardCharsets.UTF_8)
    val now = 1_760_000_000L

    // 1) 正常签发 + 校验：15 分钟有效期（支付类 access token 推荐时长）
    val token = MiniJwt.issue("""{"sub":"M-1001","scope":"settle:read"}""", secret, now, ttlSec = 900)
    println("[1] 签发 token = $token")
    println("[1] 一分钟后校验 = ${MiniJwt.verify(token, secret, now + 60)}")

    // 2) 篡改 payload：攻击者把 scope 从 settle:read 改成 settle:write 后重放
    val parts = token.split(".")
    val forgedPayload = b64Url("""{"sub":"M-1001","scope":"settle:write"}""".toByteArray(StandardCharsets.UTF_8))
    val forged = parts[0] + "." + forgedPayload + "." + parts[2]   // 签名保持原样
    println("[2] 篡改后的 token = $forged")
    println("[2] 校验结果 = ${MiniJwt.verify(forged, secret, now + 60)}")

    // 3) 过期 token：TTL=900 秒，901 秒后再用
    println("[3] 901 秒后校验 = ${MiniJwt.verify(token, secret, now + 901)}")
}
```

对着输出与代码，四个此前容易被一笔带过的点现在可以落实：

1. **验签先于解码 payload 信任**：注意 `[2]` 里攻击者根本没有密钥，只是把 payload 段换掉、签名段原样带上——HMAC 对新签名输入算出的值与旧签名不一致，`BadSignature`。这也再次印证误用 3：签名能挡住篡改，但 `[1]` 里任何人把 payload 段随手 base64 解码就能读，挡不住偷看。
2. **alg 写死而非读取**：`verify` 开头就检查 header 必须是 HS256——示例里“写死”是显式的 if，生产库（如上方 jjwt 的 `verifyWith`）是把算法与密钥绑死在 parser 构造期。若反过来“读 header 里的 alg 再选验证方式”，攻击者把 alg 改成 `none` 去掉签名段，或用公钥当 HMAC 密钥发起算法混淆，都能绕过验签。
3. **常量时间比较**：比对签名用 `MessageDigest.isEqual` 而不是 `==`。逐字符比较的 `==` 会在第一个不同字符处提前返回，攻击者可通过测量响应时间逐位猜签名；常量时间比较无论差在哪都耗同样时长，堵死这条时序侧信道。
4. **校验结果显式建模**：`VerifyResult` 用 sealed class 区分四种失败，而不是让异常穿透——认证是每个请求都要走的路径，把失败类型做成类型，调用方（网关过滤器、服务鉴权切面）才能针对“过期就去 refresh”“签名错就拉黑告警”分别处理，也方便把失败原因打进安全指标（认证失败率突增 = 可能有人在撞库，接 [02-可观测性-日志指标与链路追踪.md](02-可观测性-日志指标与链路追踪.md) 的告警）。

工程判据：HS256（对称）适合签发方与校验方是同一信任域（内部微服务共用一个认证中心）；多方校验、签发方唯一时（开放平台给第三方签发）用 RS256/ES256（非对称），校验方只持公钥，公钥泄露不影响签发能力。无论哪种，“算法写死在验证端、密钥不落代码库”两条不变。

### 3.4 敏感数据保护：卡号、密码与密钥管理

支付与清结算在“资金零差错”之外还有“敏感数据零泄露”，三样东西各有正确做法：

| 对象 | 原则 | 落地 |
|---|---|---|
| 卡号 PAN | 传输加密 + 存储加密 + 展示脱敏 | TLS 之上，落库用 KMS 信封加密；页面与日志只出现 `6222********1234` |
| 密码 | 永不明文、永不可逆 | 只存加盐慢哈希（bcrypt/Argon2），登录时比对 |
| 密钥 | 密钥不出安全区 | 主密钥留在 KMS/HSM，应用只拿数据密钥的密文；定期轮换 |

❌ 反例：`log.info("pay cardNo={}", req.cardNo)`——卡号全文进了日志平台，所有能查日志的人都看得到，且日志保留期往往比业务库还长。✅ 修正：

```kotlin
object CardMask {
    fun mask(pan: String): String = pan.take(4) + "*".repeat(pan.length - 8) + pan.takeLast(4)
}

fun onPayCallback(cb: PayCallback) {
    log.info("pay_callback orderId={} amount={} card={}", cb.orderId, cb.amount, CardMask.mask(cb.cardNo))
}
```

合规是硬约束（PCI DSS 对卡数据、等保与审计要求）：谁能解密、谁查过敏感数据都要留审计日志。更进一步：大部分系统根本不该接触完整卡号——让支付渠道托管卡信息，自己只存渠道返回的 token/掩码，是更安全的架构选择。

“更安全的架构选择”值得展开一句：不存完整卡号不只是少一张加密表，而是**消灭了一整类风险**——不需要解密能力的系统，攻击者拿到库也拿不到卡号；不需要接触卡数据的系统，连 PCI DSS 合规范围都缩小了。安全设计里“不接触”永远优于“接触了但保护得很好”。

#### 密码存储的完整示例：PBKDF2（JVM 标准库可运行）

上表说密码“只存加盐慢哈希（bcrypt/Argon2）”，两者都是第三方库；JVM 标准库自带的 **PBKDF2**（`SecretKeyFactory` + `PBEKeySpec`）是零依赖场景下的合规替代——同为 OWASP 认可的慢哈希，代价是迭代次数要给足。桶装水商城的会员账号体系若不想引依赖，就用它。完整示例演示三件事：同一密码两次哈希结果不同（随机盐生效）、正确密码通过、错误密码拒绝（kotlinc 2.2.20 编译运行，输出附后）：

```kotlin
import java.security.MessageDigest
import java.security.SecureRandom
import java.util.Base64
import javax.crypto.SecretKeyFactory
import javax.crypto.spec.PBEKeySpec

/** 存库格式：alg$iterations$salt$hash——迭代次数随存，轮换时老记录可识别 */
fun hashPassword(password: CharArray): String {
    val salt = ByteArray(16).also { SecureRandom().nextBytes(it) }
    val iterations = 600_000   // OWASP 对 PBKDF2-HmacSHA256 的现行建议（演示同值）
    val spec = PBEKeySpec(password, salt, iterations, 256)
    val hash = SecretKeyFactory.getInstance("PBKDF2WithHmacSHA256").generateSecret(spec).encoded
    spec.clearPassword()
    val b64 = Base64.getEncoder()
    return "pbkdf2_sha256$$iterations$${b64.encodeToString(salt)}$${b64.encodeToString(hash)}"
}

fun verifyPassword(password: CharArray, stored: String): Boolean {
    val p = stored.split("$")
    if (p.size != 4 || p[0] != "pbkdf2_sha256") return false
    val iterations = p[1].toInt()
    val salt = Base64.getDecoder().decode(p[2])
    val expected = Base64.getDecoder().decode(p[3])
    val spec = PBEKeySpec(password, salt, iterations, expected.size * 8)
    val actual = SecretKeyFactory.getInstance("PBKDF2WithHmacSHA256").generateSecret(spec).encoded
    spec.clearPassword()
    return MessageDigest.isEqual(expected, actual)   // 常量时间比较，理由同 JWT 验签
}

fun main() {
    // 1) 同一密码两次哈希：盐不同 → 结果完全不同，彩虹表失效
    val h1 = hashPassword("Shop@2026".toCharArray())
    val h2 = hashPassword("Shop@2026".toCharArray())
    println("[1] 第一次哈希 = $h1")
    println("[1] 第二次哈希 = $h2")
    println("[1] 两次结果相同吗 = ${h1 == h2}")

    // 2) 登录比对：正确密码通过，错误密码拒绝
    println("[2] 正确密码校验 = ${verifyPassword("Shop@2026".toCharArray(), h1)}")
    println("[2] 错误密码校验 = ${verifyPassword("shop@2026".toCharArray(), h1)}")
}
```

```text
[1] 第一次哈希 = pbkdf2_sha256$600000$GkGVXU2xTiWMwBxXNskyHQ==$lwjrdlcii0odFc7rQ1E7D1pxr6dNWX5s1U/pGUFKnB4=
[1] 第二次哈希 = pbkdf2_sha256$600000$1E52eymqbyZiKYUkyLDWUQ==$/1SETFY+x6bUPoQeZaBQaazwVJf0g7kJAXH17iTuANQ=
[1] 两次结果相同吗 = false
[2] 正确密码校验 = true
[2] 错误密码校验 = false
```

对着输出讲四点：其一，**同密码两次哈希不同**——16 字节随机盐让每条记录都要单独暴力破解，预计算彩虹表整体失效，这就是“加盐”的全部意义；盐不是秘密，明文随哈希一起存。其二，**存库格式自带算法与迭代次数**（`pbkdf2_sha256$600000$salt$hash`），未来提高迭代次数或换算法时老记录可识别，可在用户下次登录时透明重哈希、平滑轮换。其三，**慢是特性不是缺陷**——60 万次迭代让单次验证耗时约百毫秒量级，用户无感，但攻击者离线暴力猜测的成本被放大同样倍数；也因此登录接口必须配套限流，防止攻击者用你的慢哈希接口在线撞库打穿可用性（限流见 [章节3/06-高可用与稳定性-限流熔断与多活.md](../章节3/06-高可用与稳定性-限流熔断与多活.md)）。其四，比对仍用常量时间 `MessageDigest.isEqual`，与 3.3 验签同一条侧信道教训。

工程判据：有条件优先 bcrypt/Argon2（对 GPU/ASIC 暴力更不友好），零依赖场景用 PBKDF2 且迭代次数对标 OWASP 现行建议；密码哈希存在“敏感”级字段（3.4 分级表），任何日志与异常里绝不出现密码原文与哈希值。

#### 数据分级：先分清“多敏感”，再谈“怎么保护”

上面三行表回答的是“卡号/密码/密钥怎么办”，架构层面还需要一张**全量数据的分级表**——不分级，“保护敏感数据”就是一句没法执行的空话（不知道哪些字段算敏感，日志脱敏、加密存储都会漏）。通用分四级，每级在四个环节的处理要求：

| 级别 | 典型例子（本工作区场景） | 传输 | 存储 | 展示 | 日志 |
|---|---|---|---|---|---|
| 公开 | 商品价格页、门店营业时间、公开 API 文档 | HTTPS（完整性） | 无特殊要求 | 无限制 | 无需脱敏 |
| 内部 | 订单状态、配送线路、报工记录、内部接口文档 | 强制 TLS | 普通库，访问走鉴权 | 登录后可见 | 可原样记录，但禁止外部输出 |
| 敏感 | 卡号 PAN、手机号、家庭地址、密码哈希、商户结算费率 | 强制 TLS + 字段级加密通道 | KMS 信封加密或独立加密表，密钥分离 | 强制脱敏（6+4、手机号 3+4） | **禁止原样出现**，输出前统一脱敏 |
| 机密 | 清结算对账原始凭证、KMS 主密钥材料、全量用户导出文件、多租户平台的跨租户数据 | TLS + 专用通道（机密数据不过共享网关） | HSM/KMS 托管，访问需双人授权+审计 | 原则上不在界面展示 | **绝对禁止**出现，连掩码形态也尽量不落日志 |

两个容易判错的例子：**密码哈希是敏感级而非公开级**——哈希虽不可逆，但拖库后可离线暴力碰撞（这就是为什么必须加盐慢哈希，让每次碰撞成本高到不可行）；**商户结算费率是敏感级**——它对内是财务数据、对外是商业机密，泄露给竞争对手等于把谈判底牌亮出去。

分级表落地的三个判据：其一，**分级进 ADR 与评审**——新表新接口评审时逐字段标级（ADR 写法见 [章节4/02-架构设计与表达-C4视图与ADR.md](../章节4/02-架构设计与表达-C4视图与ADR.md)），没有标级字段的表不允许上线；其二，**处理逻辑跟级别走而不是跟人走**——日志脱敏、加密、展示权限都按“字段级别”在公共组件里实现，不依赖每个开发者记得“这个字段敏感”；其三，**级别就高不就低**——一个字段聚合了敏感信息（如订单收货人 = 姓名+手机号+地址），整条按敏感级处理。

#### 日志脱敏：正反片段（6+4 打码）

上方 `CardMask.mask` 是 4+4 保留（前 4 后 4）。展示与日志场景更常按 **PCI DSS 的“最多显示前 6 后 4”**执行——前 6 位是卡 BIN（发卡行与卡种信息，风控要用），后 4 位够用户辨认“是哪张卡”，中间全掩。片段：

```kotlin
// 片段：6+4 打码与常见字段脱敏（真实项目放进公共日志组件，配单测锁定行为）
fun maskPan(pan: String): String =
    if (pan.length < 10) "*".repeat(pan.length)          // 长度异常宁可不显示，不能拼出泄露
    else pan.take(6) + "*".repeat(pan.length - 10) + pan.takeLast(4)
// "6222600212345678" -> "622260******5678"

fun maskPhone(phone: String): String =
    if (phone.length != 11) "*".repeat(phone.length)
    else phone.take(3) + "****" + phone.takeLast(4)
// "13812345678" -> "138****5678"
```

对应正例与它的三个细节：

```kotlin
// 片段：结构化日志只输出掩码字段，原始值不出函数边界
fun onPayCallback(cb: PayCallback) {
    log.info(
        "pay_callback orderId={} amount={} card={} phone={}",
        cb.orderId, cb.amount, maskPan(cb.cardNo), maskPhone(cb.phone)   // 脱敏发生在拼日志参数处
    )
}
```

细节一：**脱敏点在“构造日志参数”处**，即原始值离开业务函数之前就变掩码——不要指望日志框架的 pattern 或后续清洗，“先写出去再清洗”意味着原始值已经过了网络与队列，泄露已经发生。细节二：**脱敏函数集中一处并配单测**，分散在各业务代码里的脱敏等于没有脱敏（总有人忘）；公共组件 + 单测（断言输出绝不含完整 PAN）才能守住。细节三：**泄露路径不止 `log.info`**——异常消息里把整个请求对象 toString（堆栈进日志）、HTTP access log 记录 query string（token/手机号常在 URL 参数里）、链路追踪的 span attribute 记录请求体（见 02-可观测性），三条路都要过同一套脱敏组件。

❌ 反例（真实多见）：`catch (e: Exception) { log.error("支付失败 req={}", req, e) }`——`req` 的 toString 把卡号、手机号全文带进了错误日志，而错误日志恰恰是排查时被最多人搜索的。✅ 修正：异常日志只打 `req` 的白名单字段（orderId、渠道流水号），或为请求对象实现“脱敏 toString”。

#### 多租户 SaaS：隔离即最大的授权

多租户 SaaS 把 3.1 的授权问题升级成体系问题：**几十家企业的数据放在同一套系统里，租户边界是所有授权里优先级最高的那条**。按泄露半径从小到大，三种隔离形态：

- **独立库/独立 schema**：租户数据物理/逻辑分离，越界需要跨库连接，泄露半径最小，成本最高——大客户与强合规行业租户用。
- **共享库分 schema / 行级隔离（租户 ID 列）**：最常见形态，所有查询必须带 `tenant_id` 过滤。它的风险不在设计而在**遗漏**——一条忘加租户过滤的 SQL 就是全部租户数据的泄露口。✅ 工程做法是行级隔离不靠自觉：ORM/数据访问层统一注入租户条件（从 token 的 tenantId 来，不从请求参数来——参数可伪造），再加 **CI 里的跨租户测试用例**（用租户 A 的 token 访问租户 B 的资源，断言 403/404）作为回归门禁。
- **计算层隔离**：租户身份不只过滤数据，还决定“能不能调这个接口”（套餐属性、配额，见 3.1 ABAC）——控制平面把租户策略下发到 API 网关，数据面第一线执行。

审计独立于此之上：跨租户的每一次敏感数据访问（运维查数、客服查询用户资料）都留“谁、哪个租户、查了什么、为什么”，审计日志本身独立存储、只追加写、设长保留期（见文末 Checklist 第 5 条）。

### 3.5 零信任：从支付内网到工控 OT/IT 隔离

传统边界模型像城堡：守住防火墙，内网即信任区。后果是入侵者一旦进入内网（或内部人员作恶），服务之间彼此无防护，横向移动畅通无阻。**零信任原则：Never trust, always verify——不因“来源在内网/本机房”就给予任何信任**：

| 要素 | 支付清结算落地 | 工控（MES/OT）落地 |
|---|---|---|
| 身份为王 | 服务间 mTLS 双向证书 / client_credentials 服务 token；回调验签 | 生产网内的系统与设备同样要身份，区域之间不存在“内网互信” |
| 最小权限 | 结算服务只能读写结算库，无权碰卡数据明文 | MES 只能“请求”设备动作，且只有授权工序的指令才被接受 |
| 持续校验 | token 短期有效、异常交易触发二次校验 | 每次指令下发都经现场安全联锁校验，昨天的授权不代表今天放行 |
| 默认拒绝 | 网关 + 服务双层鉴权，而不是只靠网关一道闸 | 生产网（OT）与管理网（IT）之间默认不通，数据经 DMZ/单向通道汇聚 |

**工控是零信任最有说服力的落地**，因为后果是物理性的：IT 系统被攻破丢的是数据，产线控制被攻破停的是生产、坏的是设备、伤的是人（震网 Stuxnet 经 U 盘进入“隔离”网络，物理摧毁了离心机——“内网就是安全”的假设被击碎）。两个专属设计：

- **OT/IT 隔离**：按 ISA-95/Purdue 分层，L1/L2 生产网与 L3/L4 管理网之间设 DMZ，数据上行走单向通道（网闸），指令下行走独立受控通道——MES 想发指令不能直连 PLC。
- **Fail-Safe 与控制权归属**：安全联锁做在现场 PLC，不在 MES——MES 下发的指令，现场校验联锁条件不满足就拒绝执行；急停等关键控制权永远归现场硬接线回路。MES 宕机，产线照转；MES 被攻破，最坏也只能“请求”，拦不住现场急停。

❌ 反例：图省事把 MES 服务器直接桥接办公网，“反正有防火墙”——办公网一台电脑被钓鱼后勒索软件横向移动进车间，停产一周。✅ 修正：DMZ + 单向数据通道 + 生产网白名单策略 + 指令通道独立鉴权与现场联锁。“从不信任、始终校验”在 OT 的含义是：**即使信任 MES，现场也要校验**。

#### 一个入口被攻破之后：横向移动 vs 止步

“内网不等于可信”用一条攻击路径推演最有感觉。设攻击者通过钓鱼拿下**一个**入口——清结算公司办公网里一台开发机：

- **传统边界模型下的连锁**：开发机在内网 → 内网互信，可以随意扫端口 → 扫到结算服务有个“健康检查接口”顺手返回了全量商户列表，还发现服务间调用**不带任何鉴权**（“反正内网”）→ 攻击者以开发机为跳板直接调内部接口，拉取分账数据 → 再往里走，发现数据库对内网段开着默认端口，用配置文件里明文躺着的连接串直连拖库。每一跳都成立，因为**每一跳的信任都来自“你在内网”**这一个事实。防御者事后复盘，看到的只有一次登录告警——攻击像水一样流过了所有没有闸门的地方。
- **微隔离下的止步**：同样的入口被拿下，攻击者从开发机发起的第一个内部请求就撞墙——内部服务间调用要求 mTLS 双向证书，开发机只有“办公终端”身份证书，不在结算服务的调用方白名单里，默认拒绝；尝试用泄露的连接串连数据库，数据库侧校验的是**工作负载身份**（来自结算服务的证书）而非 IP 网段，同样拒绝。攻击者止步在第一跳，防御者从认证失败指标突增（3.3 的 `VerifyResult` 失败计数接到告警）**实时看到**有人在内网试探。

两相对比，零信任改变的不是“入口守得更好”，而是**把一次成功入侵的爆炸半径从“全网”压到“一台机器”**。这就是为什么零信任常被概括为：假定边界已经被攻穿（breach assumption），安全设计的目标是让攻击者每前进一米都要重新攻破一次。

工程判据：拿一张内部服务调用清单问自己——**每一跳调用，调用方是谁、凭什么放行、拒绝有没有被记录？**任何一跳答不出“调用方是谁”（即所谓“内网无防护”），就是横向移动的潜在通路。这条判据在微服务里对应服务网格/服务间 mTLS 与鉴权中间件，在 API 网关场景对应“网关管粗、服务管细”的双层鉴权（3.2）。

#### 零信任的落地三阶段

零信任不是买一个产品，是按三阶段递进的改造路线。每阶段一个中心、一条可验收判据：

**阶段一：身份为中心（先让一切调用“有名字”）。**给人、服务、设备三类主体建立统一身份：人走 SSO + MFA（重要操作二次校验），服务走 mTLS 双向证书或 client_credentials 服务 token（3.2），设备发身份证书。这一阶段**不改网络拓扑，只补身份**——先把全公司“谁在调谁”从黑盒变成账本。支付清结算系统的切入点通常是渠道回调验签与内部服务互调的 token 化；MES 的切入点是 SCADA/边缘网关与 MES 之间先建证书身份。
判据：**任何服务间调用都能说出调用方身份**；认证失败有指标有告警；存在匿名内网调用的清单且逐月收敛趋零。

**阶段二：设备健康（把“合法身份”升级为“健康且合法的身份”）。**有名字不等于没被攻破——被钓鱼的开发机一样有合法证书。此阶段把设备状态纳入信任评估：终端准入（MDM/EDR 在线、补丁基线达标、磁盘加密开启）不满足就降权或隔离；工控环境对应工控机白名单、移动介质管控（震网走的就是 U 盘，U 盘管控是 OT 侧必答题）、操作站专机专用。
判据：**不健康设备拿不到全量权限**（降级或踢出）；设备健康数据有采集、有审计；介质管控有技术手段而非仅制度。

**阶段三：微隔离（默认拒绝落到每两条服务之间）。**身份与健康都有了，最后把网络策略从“网段互信”改成“按身份放行”：每个服务声明“我需要和谁通信”，其余默认拒绝——云上对应安全组/NetworkPolicy 以服务身份（而非 IP 段）表达策略，数据中心内对应分布式防火墙，OT 环境对应 Purdue 分层 + DMZ + 单向网闸（上文 OT/IT 隔离即是微隔离的工业版，只是策略粒度更粗、审批更严）。
判据：**任意两个服务默认不通**；策略以身份而非 IP 表达；做一次“拔掉某服务的网络策略”演练能被告警捕获。

三阶段是递进而非并列：没有身份（一），健康无从绑定（二）；没有身份与健康，微隔离的策略会退化成 IP 白名单——防得住扫描器，防不住拿到合法主机的攻击者。多数团队的顺序是先在办公网/管理网走完一、二阶段，再啃生产网微隔离；OT 生产网通常停在三阶段的粗粒度版（区域隔离）就已是业界良好实践，不必为了“彻底零信任”把产线联锁改得无法运维。

### 安全架构 Checklist

十条可执行判据，评审与自查直接对着勾：

1. **传输加密**：所有外部入口与内部服务间通信强制 TLS/mTLS，包括内网——能扫到明文端口即不通过。
2. **存储加密**：敏感/机密级字段落库前经 KMS 信封加密，数据密文与密钥分离存储，数据库导出文件不携带解密能力。
3. **密钥轮换**：每类密钥有明确轮换周期与轮换演练记录，轮换不中断业务；密钥疑似泄露时能在约定时限（如 1 小时）内完成吊销与换发。
4. **最小权限**：每个服务与角色有可枚举的权限清单并与“业务必需”对账，默认拒绝、按需申请，权限收敛有审计数据支撑。
5. **审计留痕**：敏感数据访问与特权操作全部进入独立、追加写、长保留期的审计日志（谁、何时、对什么、做了什么、结果），应用侧无删除权限。
6. **依赖漏洞扫描**：CI 集成依赖与镜像漏洞扫描，高危（CVE High/Critical）不进生产，修复时限写入团队 SLA。
7. **敏感日志脱敏**：应用日志、异常消息、access log、链路 attribute 四条输出路径共用同一套脱敏组件，并有单测断言输出绝不含完整 PAN/手机号。
8. **接口鉴权默认拒绝**：新接口不写鉴权代码即不可访问；每个读/改数据的接口在服务端做资源归属校验（3.1 的模式），网关只算第一道不算唯一一道。
9. **租户隔离验证**：跨租户访问用例（A 租户 token 访问 B 租户资源必须 403/404）进入 CI 回归，数据访问层统一注入租户条件且来源为 token 而非请求参数。
10. **安全演练**：至少每半年一次入侵路径演练（红蓝对抗或桌面推演，含“入口被攻破后横向移动”剧本）与安全事件应急回滚演练，演练产出的缺口进入整改清单跟踪闭环。
