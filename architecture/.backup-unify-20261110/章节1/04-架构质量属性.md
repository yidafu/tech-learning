## 3. 架构质量属性

### 3.1 功能需求 vs 质量属性

功能需求回答“系统能做什么”，质量属性回答“系统做得怎么样”。**任何功能都能在任何架构上实现，但性能、可用性这些属性由架构决定**——这就是架构工作主要围绕质量属性展开的原因。

一个直观对比：两家电商的功能清单可以一模一样（浏览、下单、支付、退款），但一个大促扛得住、一个日常高峰就崩溃——功能相同、架构不同，差别全在质量属性。**功能决定系统能不能上线，质量属性决定系统能不能活下来。**

#### 3.1.1 运行期属性与开发期属性

按“谁在什么时间感知到它”分两类：

| 类别 | 属性 | 谁最关心 |
|---|---|---|
| 运行期 | 性能、可用性、可靠性、安全性、可扩展性、易用性 | 用户、业务方、运维 |
| 开发期 | 可维护性、可测试性、可移植性、可复用性 | 开发团队 |

两个推论：

- 运行期属性的失误**上线即爆**；开发期属性的失误**温水煮青蛙**——后者更容易被忽视，因为故障复盘不会写“根因是可维护性差”，但大量事故的远因正是代码腐化。
- 两类属性天然冲突：为极致性能写的代码（绕过分层、缓存套缓存）几乎总在牺牲可维护性，见 3.4。

反例（订单系统）：立项文档只有功能清单加“高性能、高可用”两个形容词——结果缓存策略没有依据（不知道目标延迟）、压测没有通过标准（不知道多少 QPS 算过关）、故障没有判定依据（不知道这算不算事故）。修正：每个属性都落成 3.3 的可验证场景。

### 3.2 核心属性逐一展开

八个属性不需要平均用力。性能、可用性、可靠性、可扩展性是**运行期的四大件**，每个都给出度量方式、反例与工程判据；可维护性与可测试性是**开发期的地基**，决定前四个能不能持续达标；安全与可观测性分别是**边界与后视镜**。读法建议：先通读 3.1 建立“属性决定架构”的视角，再按当前项目最痛的属性精读对应小节，最后用 3.3 的场景卡模板把所学落成自己系统的验收标准。

#### 3.2.1 性能：延迟、吞吐、并发

度量三件套：

- **延迟**：一个请求花多久。必须看分位数 P50/P95/P99——**平均值会骗人**：100 个请求里 99 个 10ms、1 个 2s，平均约 30ms 看着很好，但那个 2s 的用户已经流失；而落在 P99 长尾里的往往恰是订单量最大、数据最多的重度用户。
- **吞吐量**：每秒处理多少请求（QPS/TPS）。
- **并发数**：同时在处理的请求数。三者由利特尔法则相连（见下第 4 点）——延迟和吞吐不是两个独立指标，优化一个常牵动另一个。

**1. 延迟的分位数：为什么长尾这么长**

分位数的读法：P50 = 一半请求比它快（中位数）；P95 = 95% 的请求比它快；P99 大致就是每 100 个请求里最慢那一个的量级。**分位数选多严苛，取决于一次糟糕体验的代价**：日均一亿次请求的系统，哪怕只有 P999 越线，也是每天十万次糟糕体验；而内部报表系统看 P95 就够了。

延迟分布是**长尾**而非正态：GC 停顿、缓存未命中、锁竞争、慢 SQL、重试风暴、个别大账户的超大数据量……每个小概率因素都在分布右端堆出肥尾。两个实践推论：

- 反例（订单系统）：监控大盘只展示“平均响应时间 45ms”，一切看似正常；实际 P99 已到 3s，而落在长尾里的恰是订单最多的大买家，客诉不断。修正：大盘直接展示 P95/P99 分位数 + 错误率，平均值只作参考。
- **分位数不可再平均**：把一小时里上千个小窗口的 P99 平均成“小时级 P99”，毛刺会被抹平——要看分位数就看小窗口原始值，不要看聚合平均值。

**2. 延迟测在哪一端：服务端耗时 ≠ 用户体验**

服务端日志记录的是“处理耗时”；用户感受到的是端到端耗时 = 网络 + 排队（网关、线程池、连接池）+ 处理 + 失败重试。反例：服务端 P99 = 120ms，客户端实测 P99 = 800ms——差距在网关排队和连接池等待上，服务端自己看不见。修正：关键链路在客户端/网关埋点真实体验（RUM）；APM 只能回答“服务端尽力了吗”，回答不了“用户体验好不好”。

**3. 吞吐量：QPS、TPS 与峰值/均值**

- **QPS vs TPS**：QPS 按请求数、TPS 按事务数——一次“下单事务”包含查库存、算价、创建订单、扣款多个请求。压测前先对齐口径，两者混用是沟通事故的常客。
- **单位随层级变化**：应用层 QPS → 数据库层 QPS/IOPS → 缓存层命中 QPS → 网络 MB/s → 消息队列条/秒。容量推算要逐层换算，别拿应用层 QPS 直接去套数据库的极限值。
- **峰值与均值**：容量按峰值设计（再乘安全系数），成本却按均值发生——电商大促的峰均比可达 10 倍以上，这正是弹性伸缩存在的理由（呼应 3.2.4 的弹性）。
- **场景（秒杀）**：平时 500 QPS 的商品页，活动开始瞬间冲到 5 万 QPS——瞬时百倍流量、库存却只有 1000 件。峰均比上百倍时“按峰值常备资源”成本无法承受，于是有缓存预热、MQ 异步下单、限流排队这些削峰手段（第三阶段逐一拆解）；容量推演永远从“流量有多少、每个环节能扛多少”开始。
- **吞吐-延迟曲线与膝点**：负载上升，延迟先缓升；越过某个利用率（经验上约 70%~80%）后排队急剧膨胀、延迟雪崩。**系统的“最大可用吞吐”不是被压垮前的极限值，而是延迟仍达标时的最大吞吐**——所以吞吐必须和延迟一起报告（见第 6 点）。

**4. 并发与容量估算：利特尔法则实战**

利特尔法则：**并发数 = 吞吐 × 平均延迟**。一条公式把“要加多少机器”从主观拍板变成算术（订单系统示例）：

> 大促峰值 5 万 QPS、目标平均延迟 100ms → 系统需同时处理 5 万 × 0.1s = 5000 个请求；单实例健康并发约 500 → 至少 10 个实例；再按膝点纪律留 30% 余量 → 部署 14 个。

配套认知：**在线用户数 ≠ 并发请求数**——10 万用户同时在线，按人均操作频率折算出的并发请求数可能只有几千，容量规划算的是后者。

**5. 资源层指标：别只盯着接口（USE 方法）**

USE 方法（Brendan Gregg）：对每一层资源都问三件事——**利用率**（U，忙的占比）、**饱和度**（S，排队/堆积程度）、**错误**（E，出错计数）。

| 资源 | 利用率 | 饱和度（排队信号） | 错误 |
|---|---|---|---|
| CPU | CPU 使用率 | load 相对核数、运行队列 | — |
| 内存 | 已用比例 | swap、GC 频率 | OOM kill |
| 磁盘 | iostat util% | iowait、队列深度 | IO 错误 |
| 网络 | 带宽占比 | 重传率、丢包 | 超时 |
| 线程池/连接池 | 池使用率 | 等待队列、拒绝数 | 获取超时 |
| 数据库 | 活跃连接占比 | 慢查询数、锁等待 | 死锁 |
| 缓存 | — | 热 key、大 key | 命中率下降、穿透 |
| 消息队列 | 消费速率 | **堆积量（lag）** | 消费失败 |

两条经验：接口延迟飙升时**先看饱和度列**——排队是延迟的头号来源（CPU 才 60% 但线程池排队 200 个，慢在排队不在计算）；MQ 堆积是最直白的饱和度信号，堆积 = 消费速率跟不上生产速率。JVM/Kotlin 补充：GC 暂停是 P999 毛刺的常客，长尾突刺先翻 GC 日志。

**6. 指标要组合看：压测结论三件套**

单个数字都会骗人：只报 QPS 不报延迟（那是崩溃边缘的吞吐）、只报延迟不报错误率（超时被记成“慢”而不是“错”）。合格的结论 = **吞吐 + 延迟分位数 + 错误率三者同时达标**：

> “下单接口在 5 万 QPS 负载下，P99 < 500ms、错误率 < 0.1%” ✓——能当验收标准
> “单机压到了 8000 QPS” ✗——延迟多少？错了多少？都不知道

常见手段：缓存、异步（非核心链路外移）、分片、池化、预计算——注意它们各自作用于三件套的哪一项（缓存降延迟、异步提吞吐、分片扩并发上限），详见 3.4 战术表。

经典反例——列表接口循环查库（N+1）：

```kotlin
// 反例：1 次查列表 + N 次查用户；一页 50 条就是 51 次 DB 往返
fun listOrders(userId: Long): List<OrderVO> =
    orderRepo.findByUserId(userId).map { order ->
        OrderVO(order, userRepo.findById(order.buyerId))   // 循环内单条查询
    }

// 修正：批量查询 + 内存组装，固定 2 次往返
fun listOrders(userId: Long): List<OrderVO> {
    val orders = orderRepo.findByUserId(userId)
    val users = userRepo.findByIds(orders.map { it.buyerId }.toSet()).associateBy { it.id }
    return orders.map { order -> OrderVO(order, users.getValue(order.buyerId)) }
}
```

N+1 的教训：架构没坏、选型没错，坏在**数据访问模式**——性能优化的一大半是在“减少往返、减少重复计算”，而不是换更贵的中间件。

**7. 尾延迟放大：扇出如何把服务的 P99 变成用户的 P82**

第 1 点说的是单个接口的长尾，这里再补充一个更隐蔽的：**接口都达标，页面照样慢**。如今一个页面、一次交易要串并联打 N 个下游调用（商品页 = 商品 + 库存 + 价格 + 促销 + 推荐 + 用户……），只要有一个慢，整页就慢。各调用独立（近似成立）时：

> **整页慢的概率 = 1 − (1 − q)ⁿ**，q 为单调用“慢”的概率，n 为扇出数

把数字代进去看衰减有多快（Kotlin 完整算例，可编译运行）：

```kotlin
// 算例一：扇出调用下的尾延迟放大
// 一个页面要调用 n 个下游，每个调用"慢"的概率为 q，
// 只要有一个慢、整个页面就慢：P(页面慢) = 1 - (1 - q)^n
fun pageSlowProb(q: Double, n: Int): Double = 1 - Math.pow(1 - q, n.toDouble())

// 反解：页面慢概率要压到 target 以内，单调用慢概率最多允许多少
fun requiredPerCallQ(n: Int, target: Double): Double = 1 - Math.pow(1 - target, 1.0 / n)

// 算例二：利用率与排队延迟（M/M/1 近似，服务时间归一化为 1）
// 平均等待 Wq = ρ/(1-ρ)，平均逗留 W = 1/(1-ρ)——ρ 越过 0.7~0.8 后 Wq 陡增
fun main() {
    println("== 扇出 20 个调用时，页面慢的概率 ==")
    for (q in listOf(0.001, 0.005, 0.01, 0.02)) {
        println("单调用慢概率 ${"%.1f".format(q * 100)}% → 页面至少一个慢：${"%.1f".format(pageSlowProb(q, 20) * 100)}%")
    }
    println()
    println("== 页面慢概率压到 1% 以内（n=20）==")
    println("单调用慢概率必须 ≤ ${"%.3f".format(requiredPerCallQ(20, 0.01) * 100)}%（约等于把单调用从 P99 提到 P999.5）")
    println()
    println("== 利用率 ρ 与排队延迟（服务时间=1 个单位）==")
    println("ρ     | 平均等待 Wq | 平均逗留 W | Wq 相对 ρ=0.5 的倍数")
    val base = 0.5 / (1 - 0.5)
    for (rho in listOf(0.5, 0.6, 0.7, 0.8, 0.85, 0.9, 0.95)) {
        val wq = rho / (1 - rho)
        val w = 1 / (1 - rho)
        println("${"%.2f".format(rho)}  | ${"%6.2f".format(wq)}      | ${"%6.2f".format(w)}    | ${"%.1f".format(wq / base)}x")
    }
}
```

实际运行输出（kotlinc 2.2.20）：

```text
== 扇出 20 个调用时，页面慢的概率 ==
单调用慢概率 0.1% → 页面至少一个慢：2.0%
单调用慢概率 0.5% → 页面至少一个慢：9.5%
单调用慢概率 1.0% → 页面至少一个慢：18.2%
单调用慢概率 2.0% → 页面至少一个慢：33.2%

== 页面慢概率压到 1% 以内（n=20）==
单调用慢概率必须 ≤ 0.050%（约等于把单调用从 P99 提到 P999.5）
```

读法：扇出 20 个调用、单调用 P99（1% 慢）时，**整页慢的概率是 18.2%**——单服务的 P99 到了用户手里只剩 P82；q = 2% 时更是 33.2%，三分之一的请求慢，而每个服务自己的 P99 大盘都“完全正常”。反方向解更触目惊心：要把整页慢概率压回 1%，扇出 20 时单调用慢概率必须 ≤ 0.05%，即**每个下游都做到 P999.5**。三个工程推论：

- **扇出本身就是延迟预算的消耗大户**：能合并的调用合并（BFF/聚合接口）、能并行的别串行（并行扇出的整页延迟 ≈ 最慢一路，而非求和）、能砍掉的下游砍掉——扇出从 20 降到 8，对尾延迟的贡献往往超过把某个调用提速一倍。
- 微服务拆分要付的隐形成本在这里：单体里一次函数调用变成跨服务调用后，扇出翻倍、尾延迟按指数规律放大——这就是 3.2.4 的 β 协调成本的延迟版，也是第二阶段“分布式单体”（见 [章节2/01-第二阶段-经典架构模式.md](../章节2/01-第二阶段-经典架构模式.md)）在性能维度的症状。
- 监控要按“页面/链路”维度看 P99，只看单服务 P99 会永远活在“都达标”的错觉里。

**8. 排队论直觉：利用率过了 70%，延迟不是线性涨而是雪崩**

第 3 点“膝点”背后是排队论（M/M/1 模型的结论就够用）：平均等待时间 ≈ 服务时间 × ρ/(1−ρ)，分母的 1−ρ 意味着**越接近满载，等待发散得越快**。上面同一个程序的后半段打印出这张表（服务时间归一化为 1）：

| 利用率 ρ | 平均等待 Wq | 相对 ρ=0.5 的倍数 |
|---|---|---|
| 0.50 | 1.00 | 1.0x |
| 0.60 | 1.50 | 1.5x |
| 0.70 | 2.33 | 2.3x |
| 0.80 | 4.00 | 4.0x |
| 0.85 | 5.67 | 5.7x |
| 0.90 | 9.00 | 9.0x |
| 0.95 | 19.00 | 19.0x |

读法：利用率从 50% 提到 90%，容量只多榨了 80%，**平均等待却涨 9 倍**；从 90% 到 95%，等待再翻一倍。这就是“膝点纪律”的数学来源，三条推论：

- **容量规划的工作点必须钉在 ρ ≤ 0.7~0.8**。压测报告里的“极限吞吐”取在 ρ > 0.9 处就是自欺——真实流量的抖动（峰均比、突发、GC 停顿、慢查询）会把工作点瞬间推过 1，队列爆炸、延迟雪崩。第 4 点利特尔法则“留 30% 余量”是同一件事的另一种说法。
- **水位告警别设在 90%**——看到 90% 的延迟告警时已经在悬崖边；要看排队信号（线程池等待队列、连接池等待、MQ lag，即第 5 点的饱和度列）在 60%~70% 就出手扩容或限流。
- **场景（秒杀）**：限流的本质就是主动把 ρ 钉在膝点以下——与其让全部请求一起变慢集体雪崩，不如让一部分请求快速失败（“排队人数过多请稍后再试”），其余的稳定服务（第三阶段限流熔断展开，见 [章节3/01-第三阶段-分布式系统核心技术.md](../章节3/01-第三阶段-分布式系统核心技术.md)）。
- **容量评审三连问**：评审“这系统能不能扛住 X QPS”时，固定追问——目标延迟分位数是多少？该负载下核心资源（线程池、连接池、数据库 CPU）的利用率预计多少？超出容量后限流从哪一层开始？三问答不上来，“能扛住”的结论就不成立——这是把排队论变成评审清单的用法。

#### 3.2.2 可用性：几个 9 的真实含义

定义：系统**能对外提供服务的时间占比**。SLA 用“几个 9”表达，换算成停机时间才有体感：

| SLA | 年停机 | 月停机 | 达到它大致需要 |
|---|---|---|---|
| 99% | 3.65 天 | 7.2 小时 | 单实例 + 快速重启 |
| 99.9% | 8.8 小时 | 43 分钟 | 冗余部署 + 监控告警 |
| 99.99% | 53 分钟 | 4.3 分钟 | 多可用区 + 自动切换 |
| 99.999% | 5.3 分钟 | 26 秒 | 多活 + 全自动容灾 |

关键规律：**每多一个 9，成本大约上一个数量级**，而业务感知未必同步提升——所以 SLA 要按链路分层定（下单 99.99%、推荐 99.9%、报表 99%），一刀切要么浪费要么欠账。

**场景（MES）**：产线 7×24 连续生产，MES 宕机不等于马上停产，但数据不能永久丢——于是有“断网时边缘网关本地续采、恢复后补传”与“降级为手工扫码报工”这类战术。把 SLA 翻译成钱才有讨论基础：99.9%（月停 43 分钟）对离散加工车间可能可接受，对连续产线却意味着整线在制品报废——同一张 SLA 表，贴上业务场景才能裁决。

公式视角：可用性 = MTBF / (MTBF + MTTR)，于是有两条路——**少出事**（提高 MTBF：冗余、隔离）和**快恢复**（降低 MTTR：监控、自动切换、演练）。多数团队过度盯着前者，其实后者的性价比常常更高。

把这条公式算成账（Kotlin 完整算例，可编译运行）：

```kotlin
// 错误预算与 MTBF/MTTR 推演
// 错误预算 = 1 - SLO，换算成自然月（按 30 天）的不可用分钟数
fun budgetMinutesPerMonth(slo: Double): Double = 30.0 * 24 * 60 * (1 - slo)

// 可用性 = MTBF / (MTBF + MTTR)
fun availability(mtbfHours: Double, mttrHours: Double): Double =
    mtbfHours / (mtbfHours + mttrHours)

// 反解一：MTBF 固定时，达到目标可用性 A 允许的最大 MTTR
fun requiredMttr(mtbfHours: Double, target: Double): Double =
    mtbfHours * (1 - target) / target

// 反解二：MTTR 固定时，达到目标可用性 A 需要的最小 MTBF
fun requiredMtbf(mttrHours: Double, target: Double): Double =
    mttrHours * target / (1 - target)

fun main() {
    println("== 错误预算：不同 SLO 的月度不可用额度（按 30 天）==")
    for (slo in listOf(0.99, 0.999, 0.9999)) {
        println("SLO ${"%.2f".format(slo * 100)}% → 月预算 ${"%.1f".format(budgetMinutesPerMonth(slo))} 分钟")
    }
    println()
    println("== MTBF/MTTR 与可用性 ==")
    println("MTBF=720h（约每月一次故障）、MTTR=1h → 可用性 ${"%.3f".format(availability(720.0, 1.0) * 100)}%")
    println("同样 MTBF=720h，要到 99.99% → MTTR 必须压到 ${"%.1f".format(requiredMttr(720.0, 0.9999) * 60)} 分钟")
    println("同样 MTTR=1h，要到 99.99% → MTBF 必须拉到 ${"%.0f".format(requiredMtbf(1.0, 0.9999))} 小时（约 ${"%.0f".format(requiredMtbf(1.0, 0.9999) / 24)} 天一次故障都不能有）")
}
```

实际运行输出（kotlinc 2.2.20）：

```text

SLO 99.00% → 月预算 432.0 分钟
SLO 99.90% → 月预算 43.2 分钟
SLO 99.99% → 月预算 4.3 分钟

== MTBF/MTTR 与可用性 ==
MTBF=720h（约每月一次故障）、MTTR=1h → 可用性 99.861%
同样 MTBF=720h，要到 99.99% → MTTR 必须压到 4.3 分钟
同样 MTTR=1h，要到 99.99% → MTBF 必须拉到 9999 小时（约 417 天一次故障都不能有）
```

两个读数：月均出一次故障、人工修一小时（MTBF=720h、MTTR=1h）的团队，可用性上限就是 99.861%，**根本够不到 99.9%**；而要摸 99.99%，走“少出事”这条路意味着 417 天不能出任何一次故障——不现实，所以高 SLA 必然压在“快恢复”这条路上（MTTR 压到 4.3 分钟以内，靠人工做不到，只能靠自动化）。

**错误预算：把“能停机多久”当成钱来花**

99.9% 的另一面：一个月 43200 分钟 × 0.1% ≈ **43.2 分钟**——这就是本月全部的“出错额度”，术语叫错误预算（Error Budget，SRE 方法论的核心概念）。它最大的价值是把 SLA 从“考核指标”翻转成“花钱策略”：

- **预算充足**（本月还没怎么出错）→ 大胆发布、做有风险的重构和实验：出问题烧掉几分钟预算，换来交付速度，划算。
- **预算告急**（已烧掉大半）→ 冻结高风险变更，把余下预算全部投给稳定性：补监控、修自动化、做演练，等预算回正再恢复发布节奏。

还有一个容易漏掉的关键认知：**预算烧的不只是宕机**。SLO 若定义为“99.9% 的请求在 300ms 内成功返回”，那么每一次超时、每一段延迟雪崩、每一批失败重试都在烧同一个池子——“没宕机但慢了半小时”和“宕机半小时”在预算眼里是同一件事。这比“停机分钟数”更贴近用户真实感受，也是错误预算比传统 uptime 统计更高级的地方。

它回答了“发布节奏 vs 稳定性”这个永远吵不完的问题：**不是站队，而是看余额**。开发说“要快速迭代”、运维说“要稳字当头”，双方从立场之争变成预算分配问题——这正是它比“可用性要高”这类口号先进的地方。与上文“最大敌人是变更”连起来读：变更风险不是不敢碰，而是有额度地碰。这套机制怎么落地成 SLO 看板与发布门禁，第五阶段展开（见 [章节5/01-第五阶段-工程化与运维视角.md](../章节5/01-第五阶段-工程化与运维视角.md)）。

拿桶装水商城记一周账（示例）：月初定 SLO 99.9%，预算 43.2 分钟。第一周：周二发布优惠券模块，灰度中配置错误使下单失败率飙升，3 分钟后回滚——烧 3 分钟；周四低峰做主备切换演练，切换耗时 4 分钟（演练消耗真实可用性，同样记账）——烧 4 分钟，余额 36.2 分钟。第二周原计划排着两件事：大改配送排线算法（高风险）与给库存服务补熔断（低风险、高收益）。余额充足，两件都做，但排线算法必须金丝雀发布、一键回滚预案先行。假如第一周就烧掉了 35 分钟呢？排线算法推迟到下月，先上熔断，并把预算花在复盘“为什么那次故障 3 分钟才发现”上——**预算思维不是保守，而是让“冒险”变成可记账、可决策的资源**。

**MTTR 的解剖与四个杠杆**

MTTR 不是一段时间，是三段之和：**发现**（从故障发生到有人知道）→ **定位**（知道哪坏了、为什么）→ **恢复**（修好或切走）。缩短 MTTR 的四个杠杆，逐一对应到手段与出处：

| 杠杆 | 压缩哪段 | 手段 | 呼应 |
|---|---|---|---|
| 发现 | 故障发生 → 告警响 | 错误率/延迟分位数突增告警（别只盯机器指标）、分级通知值班 | 3.2.8 可观测性 |
| 定位 | 告警响 → 找到根因 | traceId 全链路、依赖拓扑图、仪表盘、“最近变更”清单 | 3.2.8 |
| 恢复 | 根因明确 → 止血 | 一键回滚、自动故障转移、预案脚本化（人工操作按分钟计价） | 下文 SPOF 反例 |
| 预防 | 让前三段更快更稳 | 故障演练（混沌工程）、预案定期演练、值班手册沉淀 | 3.2.3 恢复演练 |

注意“预防”压的不是故障次数（那是 MTBF 的事），而是**让前三段在被真实故障考验之前就演练过**——演练过预案的定位用分钟计，没演练过的用小时计。四个杠杆怎么排优先级？先量出三段各自的耗时占比：发现 2 分钟、定位 40 分钟、恢复 10 分钟，就先把钱花在定位（可观测性）上——数据说了算。

反例（订单系统）：库存读 Redis 单实例，Redis 一旦宕机全站不能下单——典型的单点故障（SPOF）。修正：哨兵/集群 + 本地缓存兜底 + 降级走数据库扣减（慢但可用）。

**可用性是链路属性，不是单点属性**。串联链路的整体可用性 ≈ 各环节可用性之积：下单要过的 5 个环节各自 99.9%，链路整体只剩 0.999⁵ ≈ 99.5%——月停机 3.6 小时，比任何一个环节都差。想抬上去只有两招：把薄弱环节做冗余（两个 99.9% 的实例并联，可用性 = 1 − 0.001² ≈ 99.9999%，冗余的收益是指数级的）；或者砍环节（链路越短越稳，这正是“不必要的微服务拆分损害可用性”的算术依据）。所以给下单链路定 99.99% 时，问的从来不是“哪个系统能达到”，而是“每一环都得比它高，谁还不够”。

补充一个反直觉事实：**可用性的最大敌人往往不是机器宕机而是变更**——业界统计多数线上故障由发布和配置变更引发，所以灰度、回滚本身就是可用性战术（第五阶段展开）。

#### 3.2.3 可靠性与容错：在线 ≠ 正确

与可用性的区分：**可用性说“在不在服务”，可靠性说“服务的结果对不对”**——系统可以 99.99% 在线，但每千单错一单：在线而不可靠。

容错设计的标准问题：“下游坏了、网络抖了、消息重复了，我会怎样？”

经典反例——支付回调不幂等，网络重试导致重复发货：

```kotlin
// 反例：来一次处理一次，消息重试 → 用户收到两次发货
fun onPaymentCallback(cb: PaymentCallback) {
    orderService.markPaid(cb.orderId)
    warehouseService.ship(cb.orderId)
}

// 修正：幂等键 + 处理记录，重复消息直接跳过（markIfAbsent：首次标记返回 true）
fun onPaymentCallback(cb: PaymentCallback) {
    if (!dedupStore.markIfAbsent("pay-cb:${cb.orderId}:${cb.eventId}")) return
    orderService.markPaid(cb.orderId)
    warehouseService.ship(cb.orderId)
}
```

消息语义三档：至多一次（可能丢）、至少一次（可能重）、恰好一次（昂贵的幻觉）。工程通行解是**至少一次投递 + 消费端幂等**，因为网络重试无法根除（第三阶段展开）。

**服务可用 ≠ 数据正确：活着但算错了，往往更糟**

“在线 ≠ 正确”再往前推一步：可用性事故是**明痛**——用户立刻发现打不开、报障、修复、复盘，痛完就过去；数据错误是**暗伤**——系统一直在线、一直出错，发现得越晚污染越广，修完服务还得花几倍精力善后“这段时间产生的错单”。而且两者的度量方式天差地别：可用性有 SLA 看板盯着，数据正确性没有看板就会一直错下去。

反例（桶装水商城）：押金服务 99.99% 在线，但空桶回收验收后，一条重复的消息把“已回收”的桶又写回“在用户手中”，退押金时按未回收扣了 20 元/桶。系统活得好好的，账错了；用户不会报障“系统宕机”，只会说“你们乱扣钱”——客诉、退一赔一、客服成本、口碑损失加起来，比宕机 5 分钟贵得多，而且“平台算错钱”的信任损伤不可逆。修正分三层：状态变更幂等 + 版本号乐观锁（防消息重放导致状态回退）；每日报账（系统押金台账 vs 仓库空桶盘点数）自动对账，差异进差错处理流程；对账告警与可用性告警同级对待（对账与差错处理的完整展开在第三阶段支付与清结算部分）。

工程判据：定义可用性目标时，同步追问两句——“系统一直在线但数据错了，**多久能发现**？”（靠对账、校验和、抽样核验）“发现了，**多久能纠正、能不能自动纠正**？”（靠差错流程、补偿事务、修数工具）。**可用性 SLA 保护“服务在不在”，对账体系保护“数据对不对”——两笔独立预算，不能互相抵充。**

对账的时机分三档，按“错误的扩散速度”选：**实时对账**（交易与台账双写后即时核对，最贵最快，只给押金、资金这类错一笔就赔的钱账用）；**日终对账**（批处理核对全量，行业标配，能兜住绝大多数状态回退与重复消息）；**抽样核验**（人工抽查，给低频低价值数据兜底）。反例就是上面押金的教训：押金账本该日终对账，实际连对账任务都没有，错误漂了半个月才被客诉暴露——发现成本全转嫁给了用户。

**没演练过恢复的备份，等于没有备份**

备份是可靠性战术里最容易被高估的一个：备份任务全绿 ≠ 灾难时能恢复。常见失败情形：备份文件早已损坏无人知晓；恢复脚本依赖某个只有离职同事知道的路径和口令；备份格式对不上升级后的新版本应用；备份 2 小时、恢复 20 小时，RTO 彻底超标。检验标准只有一条：**定期真刀真枪把备份恢复成一套能跑的系统**。恢复演练清单四条：

1. **定期在隔离环境完整拉起**（至少每季度一次）：“备份任务跑成功”不算数，“恢复出来的系统登录可用、数据对得上”才算数——恢复演练用的是“从备份倒推”的路径，与备份完全不同，不练就不会。
2. **度量 RTO 与 RPO**：RTO（多久恢复服务）、RPO（丢多少数据）是演练测出来的，不是文档写出来的；测出来要跟 3.3 场景卡的响应度量对表，超了就是短板。
3. **演练不只练数据库恢复**：降级开关、主备切换、MQ 堆积回放都要按剧本走一遍——故障切换这种“一生只触发几次”的代码路径，没演练过的切换瞬间经常爆出新故障。
4. **演练后 24 小时内复盘改预案**：演练发现的每个问题都是一次免费的事故预演；不复盘的演练只是表演。

#### 3.2.4 可扩展性：加机器能不能顶住

定义：**负载增加时，通过加资源维持指标的能力**。两个方向：垂直扩展（换更强的机器，简单但有上限、成本陡增）与水平扩展（加更多机器，上限高但要求架构配合）。水平扩展的前提是**应用无状态**——任何请求打到任何实例都能处理。

反例（订单系统）——登录态存在实例本地内存：

```kotlin
// 反例：会话在实例内存里，负载均衡一换机器用户就"被登出"；
// 扩容前要预热，缩容丢会话——本地状态挡住了水平扩展
object LocalSession {
    val sessions = ConcurrentHashMap<String, Session>()
}

// 修正：状态外置到 Redis，实例本身无状态，扩缩容只是加减副本
class SessionService(private val redis: RedisClient) {
    fun get(token: String): Session? = redis.get("session:$token")
}
```

区分两个词：**扩展性**（加机器能不能顶住）与**弹性**（流量来了能否自动扩、走了能否自动缩），云原生时代两者都要。

完整的扩展链条：接入层（负载均衡）→ 应用层（无状态 + 自动扩缩容）→ 数据层（读写分离、分库分表）。**应用层最好扩，数据层最难扩**——规模够大之后，扩展瓶颈几乎总落在数据层（第三阶段展开）。

**场景（物联网平台）**：接入设备从数万台长到百万台，连接数与上报量近似线性增长——典型的**写洪峰**扩展问题（与秒杀的读洪峰方向相反）：逐条 INSERT 无法支撑，要靠无状态接入网关水平扩 + 消息队列削峰 + 消费端批量聚合写入。可扩展性设计的第一问永远是“哪个维度在涨”（用户数、数据量还是流量），沿真正在涨的维度扩。

**为什么加机器不总是线性扩展：Amdahl 定律与 USL**

水平扩展的理想图景是 N 台机器 N 倍吞吐，现实有两层折扣，各有一条定律管着：

- **Amdahl 定律——串行部分封顶**。任何链路总有绕不开的串行段：单一热点行、全局锁、必须落到同一个库的写入。设串行比例为 S，N 台机器的加速上限是 1/S——串行 15% 的系统理论上限只有约 6.7 倍，加到 200 台也只是逼近它。推论：**加机器之前先看串行比例**，S 不动，机器堆上去只是让排队更整齐。
- **USL（Universal Scalability Law）——争用与协调吃掉收益**。Gunther 在 Amdahl 之上再加两项随集群规模增长的开销：**α 争用**（节点抢共享资源：同一个库、同一把分布式锁）与 **β 协调**（节点间为保持一致付出的通信：分布式事务、复制、共识）。β 项随节点数**平方**增长，所以扩展曲线**先升后降**——过了峰值点再加机器，吞吐不涨反跌。

Kotlin 推演（数字先于机器回答“扩容划算吗”）：

```kotlin
// Amdahl：串行比例 S 无法被并行化，加速比 = 1 / (S + (1-S)/N)，上限 1/S
fun amdahl(serial: Double, nodes: Int): Double =
    1.0 / (serial + (1 - serial) / nodes)

// USL：N 台机器相对 1 台的吞吐倍数 = N / (1 + α(N-1) + βN(N-1))
// α 争用：节点抢同一共享资源（同一个库、同一把锁）的开销
// β 协调：节点间为保持一致付出的通信（分布式事务、复制、共识），随 N² 增长
fun usl(alpha: Double, beta: Double, nodes: Int): Double =
    nodes / (1 + alpha * (nodes - 1) + beta * nodes * (nodes - 1))

fun main() {
    println("Amdahl（串行 15%）：")
    for (n in listOf(2, 10, 20)) {
        println("  $n 台 = ${"%.1f".format(amdahl(0.15, n))} 倍（上限 ${"%.1f".format(1 / 0.15)} 倍）")
    }
    println("USL（α=0.05，β=0.002）：")
    for (n in listOf(8, 16, 22, 32)) {
        println("  $n 台 = ${"%.1f".format(usl(0.05, 0.002, n))} 倍")
    }
}
```

运行结果：Amdahl 上限 6.7 倍，2→20 台只从 1.7 涨到 5.2；USL（α=0.05，β=0.002）峰值在 22 台附近的 7.4 倍，**16→32 台机器翻倍、吞吐反而从 7.2 掉到 7.1**——β 项超过线性收益的拐点真实存在。

反例（订单系统）：下单链路 85% 已并行化，剩下 15% 必须写同一个数据库——Amdahl 上限 6.7 倍，扩到 20 台已接近打满。此时把它拆成 5 个微服务：若服务仍然共库，S 一点没降（上限纹丝不动），反而每笔订单多了几次跨服务调用、多了一次分布式事务——β 变大，实际吞吐可能比拆前还低。**拆了服务没拆数据 = 只付 USL 的成本、不拿 Amdahl 的收益**，这正是第二阶段要展开的“分布式单体”。

**场景（工单中心/MES）**：评估“某模块拆出去能不能换来吞吐”，别看代码量看数据——① 这段逻辑访问共享资源（S 与 α）的占比多少？② 拆出去之后，跨服务调用与一致性保障（β）新增多少？两个问题算完，多数内部系统的答案是“读写分离比拆微服务便宜且有效”。

三句话收束：加机器前先算 S；优化优先削 S 与 α（3.4 战术表里的读写分离、缓存、异步都在削它们）；β 是微服务最容易低估的暗账——协调成本随规模平方涨。

#### 3.2.5 可维护性：长期成本的大头

定义：改动的难易。业界经验：开发只占软件生命周期成本的 20%~40%，其余全是维护（改需求、修缺陷、升级依赖）——**为“好改”投入的钱回报期最长**。

比“代码干净”更可操作的判据：

- **波及范围**：改一条价格规则要动几个模块、发几个服务？
- **新人上手时间**：新人多久敢独立改核心模块？
- **可逆性**：这次改动错了，回滚多容易？

反例（订单系统）：价格计算散落在下单、退款、后台改价、导出报表四处，规则一变四处改、四处测、四处祈祷。修正：收敛为独立的 PricingService，其余位置只调用——这就是高内聚低耦合（呼应 2.2）。

**场景（工单中心）**：流转与分派规则随工单类型不断变化（见 2.1.1）——硬编码时代每新增一种类型都要改代码、发版、回归；收敛为策略实现 + 配置之后，“新增一种工单类型只改 1 个模块、0 行核心代码、预计 2 人日”就成了可验收的可维护性场景，而不是“代码要写干净”的愿望。

#### 3.2.6 可测试性：难测 ≈ 耦合重

定义：**在受控条件下低成本验证行为的能力**，三个条件：能隔离依赖、能控制输入、能观测输出。

可测试性差几乎总是设计问题的信号灯：内部 `new` 出真实依赖（直连数据库、Kafka）的类没法单测，本质是违反了 DIP（呼应 2.1）——依赖接口并由外部注入，测试时注入假实现即可。**测试不只是质量保障，更是设计质量的反馈环**：一段代码难测，先别抱怨测试框架，先看它的耦合。

可测试性落到工程组织上，就是**测试金字塔**：底层单元测试（数量最多、跑得最快、依赖全隔离，占大头）→ 中层集成/接口测试（验证模块协作与真实依赖的组装）→ 顶层端到端测试（少而慢、只保关键链路）。可测试性好的架构让重心稳在金字塔底部——依赖可注入，绝大多数逻辑在单元层就被秒级验证；耦合重的系统则恰恰相反，逻辑只能靠昂贵的端到端测试兜底，形成“冰淇淋筒”倒金字塔——测试又慢又脆，还经常“全绿着放事故上线”。记住因果关系：**金字塔是结果，依赖方向才是原因**——先有 DIP 与接口抽象（2.1），才养得起健康的金字塔；测试策略与 CI 流水线如何组织，第五阶段展开。评审代码时可用两个问题快速自检：① 把这个类放进单元测试，需要连真实数据库或消息队列吗？（需要 = 耦合红灯）② 想测“库存不足时下单被拒”，能在测试里把库存固定成 0 吗？（不能 = 输入不可控）。两问全过，可测试性基本合格。

#### 3.2.7 安全性：CIA 与越权

三要素 CIA：**机密性**（不给看的不给看）、**完整性**（不给改的不给改）、**可用性**（攻击打不瘫服务——与 3.2.2 在 DDoS 防护上汇合）。

基础区分：**认证（你是谁）≠ 授权（你能干什么）**，混淆两者是高频漏洞来源。

经典反例——订单接口水平越权（IDOR）：

```kotlin
// 反例：自增 ID + 不校验归属者，攻击者遍历 id 即可拉走全站订单
fun getOrder(orderId: Long): Order = orderRepo.findById(orderId)

// 修正：查询永远限定当前用户；对外标识改用不可预测的订单号
fun getOrder(userId: Long, orderId: Long): Order =
    orderRepo.findByIdAndOwnerId(orderId, userId) ?: throw NotFoundException()
```

IDOR 是真实事故里最高频的漏洞类型之一——**功能测试全绿也照样越权**，因为它不是功能缺陷而是属性缺陷，这正是“质量属性需要专门的场景来验收”的例证。

架构视角两条：安全要**左移**（设计期做威胁建模，而不是上线前靠渗透测试兜底）；**纵深防御**（网关鉴权 + 服务间校验 + 数据层权限各守一道）优于单点设防。

#### 3.2.8 可观测性：出事后多快能定位

定义：**仅凭外部输出就能推断系统内部状态的能力**。三支柱：日志（这次请求发生了什么）、指标（系统整体怎么样）、链路追踪（一个请求经过了谁、各花多久）。

反例（订单系统）：“下单慢”排查三天，手段是在代码里到处加日志、重启、复现。修正：traceId 全链路贯穿、关键接口延迟分位数埋点、异常分级告警——排查从“三天加日志”变成“打开面板看链路”。

终极判据：**遇到一个没预料到的故障，多久能定位？**（第五阶段展开）

往前一步就是 SRE 的度量体系，先埋个伏笔：**SLI**（Service Level Indicator，指标本身——如“下单接口 P99 延迟”“错误率”）、**SLO**（Service Level Objective，内部目标——如“99.9% 的下单请求 P99 < 300ms”）、**SLA**（Service Level Agreement，对外承诺，违约要赔付）。三者是同心圆：SLA 是对外的底线，内部 SLO 应当**比 SLA 更严**（留出缓冲，别把承诺踩在及格线上），SLI 是 SLO 的数据来源；而 SLO 的反面就是 3.2.2 的错误预算（1 − SLO）——SLI/SLO 是“可观测性”与“可用性管理”的汇合点。SLI 怎么选、SLO 怎么定、预算怎么算，第五阶段（工程化与运维视角）展开。

### 3.3 把属性变成可验证的场景

抽象目标（“系统要快、要稳”）无法指导设计。质量属性场景 = **刺激 + 环境 + 响应**：

> 例 1：订单查询接口在高峰时段（环境）收到请求（刺激），99% 在 200ms 内返回（响应）。
> 例 2：单机房故障（刺激）发生时（环境），核心服务 1 分钟内恢复（响应）。

SEI 的完整版是六要素：刺激源（谁发起）、刺激（什么事件）、制品（作用在哪部分）、环境（什么条件）、响应（系统做什么）、响应度量（用数字衡量）。日常用三要素够用，关键是**响应必须带数字**——没有数字的场景仍然无法验收。

六要素当作逐项追问的模板用（右列以桶装水商城随手填几个例子示范“追问到位”长什么样）：

| 要素 | 追问 | 桶装水商城填法示例 |
|---|---|---|
| 刺激源 | 谁发起的？人还是系统？ | C 端用户、配送员 APP、周期购调度器、数据库主库 |
| 刺激 | 发生了什么事件？ | 下单请求、主库宕机、重复的退款回调、周末浏览高峰 |
| 环境 | 事件发生时处于什么条件？ | 晚 19 点下单高峰、活动进行中、正常运维、发布窗口 |
| 制品 | 作用在系统哪一部分？ | 下单链路、押金账户、商品详情接口、整个商城 |
| 响应 | 系统做什么？ | 切备库并降级、幂等拦截、缓存命中返回、告警值班 |
| 响应度量 | 怎么算达标？（必须带数字） | ≤ 5 分钟恢复、零丢单、P99 < 200ms、错误率 < 0.1% |

使用时机：日常内部沟通用三要素（刺激 + 环境 + 响应）就够；但**对外承诺、验收合同、故障演练剧本必须六要素全填**——“刺激源”和“制品”两格最容易暴露没想清楚的问题（到底谁触发的？到底作用在哪个环节？），填不出来就退回去重新讨论。

两张完整场景卡（桶装水商城，一张可用性、一张性能）。注意每格都是具体名词和数字——写不到这个精度，就说明还没想清楚：

**场景卡 A（可用性）：晚高峰主库故障**

| 要素 | 内容 |
|---|---|
| 刺激源 | 订单数据库主库（基础设施故障） |
| 刺激 | 晚 19:00 送水下单高峰，订单库主库宕机 |
| 环境 | 晚高峰约 2000 QPS 下单与查询混跑，周期购定时任务同时在执行 |
| 制品 | 下单链路：订单服务、库存扣减、支付回调 |
| 响应 | 哨兵 30 秒内完成主备切换；切换期间下单入口自动降级为“排队缓收”（订单先落消息队列，恢复后重放）；已支付订单不丢单、不重复发货；自动告警通知值班 |
| 响应度量 | 不可用时间 ≤ 5 分钟；订单零丢失、零重复发货；切换后下单 P99 < 1s；降级期间接收的订单在恢复后 10 分钟内全部补齐状态 |

**场景卡 B（性能）：周末商品详情页浏览高峰**

| 要素 | 内容 |
|---|---|
| 刺激源 | C 端用户（App/小程序浏览水站与商品） |
| 刺激 | 周六上午浏览高峰，商品详情接口 3000 QPS（日常约 500） |
| 环境 | 读多写少的日常峰值（非大促）、缓存已预热、配送排线等非核心链路正常 |
| 制品 | 商品详情接口（聚合商品主数据 + 门店可售库存 + 水站信息） |
| 响应 | 本地缓存 → Redis → 数据库逐级回源；库存可售数走短 TTL 缓存、容忍秒级误差；未命中只回源商品主数据 |
| 响应度量 | P99 < 200ms、错误率 < 0.1%、缓存命中率 ≥ 95%、回源后该接口数据库 QPS ≤ 300 |

这两张卡稍加改写就是压测预案和故障演练剧本——这正是下文“三大检验”第一条的意思。写卡时三个常见毛病，对照自查：**响应不带数字**（“快速恢复”不是度量，“≤ 5 分钟”才是）；**环境不写清**（同一个超时刺激，大促中和凌晨里的正确响应完全不同，环境含糊的卡变不成剧本）；**制品范围过大**（“整个系统 P99 < 200ms”注定失败，范围要缩到“下单链路”“商品详情接口”这一级）。

场景化的三大检验：

1. **可验收**：能直接变成压测通过标准（“99% < 200ms”就是压测报告的及格线）
2. **可权衡**：冲突时能拿来排序（“宁可 P99 500ms 也要强一致”能写成场景，“要快要稳”不能）
3. **可追溯**：评审时每条场景都能指出由哪个战术支撑（见 3.4）

反模式对照——把 SLA 写成形容词：

| 形容词版（不可验收） | 场景版（可验收） |
|---|---|
| 系统要快 | 下单接口日常 P99 < 300ms，大促 P99 < 1s |
| 系统要稳 | 任一可用区故障，核心链路 1 分钟内恢复且不丢单 |
| 数据要安全 | 所有订单接口校验归属者；身份证号落库加密 |
| 要好维护 | 新增一种优惠类型只改 Pricing 模块，预计 2 人日 |

最后一行示范了**可修改性场景**：变更刺激（加一种优惠）在开发期（环境）到来，只波及 1 个模块（响应）、2 人日（度量）——场景不只用来描述运行期属性。

### 3.4 冲突与战术

典型冲突：

- 性能 vs 可维护性（为快绕过分层、缓存套缓存——快一时，贻害后人）
- 可用性 vs 一致性（CAP，第三阶段展开：转账宁拒服务，Feed 点赞数容忍短暂不一致）
- 安全 vs 开发效率与性能（加密、鉴权链路都有开销——不能砍，但可分层设防）
- 延迟 vs 一致性（强一致意味着同步等待确认——“读到自己刚下的订单”是有代价的）
- 可扩展性 vs 简单性（无状态、分片都有架构成本——日活 1 万的系统不必预付）

给冲突贴上场景（同一对冲突，场景不同裁决完全不同）：MES 设备采集直写数据库最简单，但一台设备秒级多条的高频上报会把库写垮——批量聚合写入复杂一点，换回产线 7×24 的可用性（简单性 vs 可用性）；物联网平台百万台设备必须无状态接入 + MQ 削峰，而几万在途工单的工单中心连读写分离都用不上——为不存在的规模预付复杂度，就是 1.4.5 的假权衡（可扩展性 vs 简单性）。

冲突真出现时，裁决走三步，不由声量大小决定：① 把两边诉求各自还原成 3.3 的场景卡（带数字）；② 查 3.5 场景投票定下的优先级序，谁的场景靠前谁赢；③ 赢的怎么落地、输的被牺牲到什么程度，一并写进 ADR 留痕。三步走完，多数“性能还是可维护”的争论会自动收敛——因为写成场景之后，往往发现两边根本不在一个时间尺度上，可以都要。

架构战术 = 针对某个质量属性的成套原子手段：

| 属性 | 主要战术 | 战术的代价 |
|---|---|---|
| 性能 | 缓存、异步、分片、池化、预计算 | 缓存一致性、异步难调试、分片复杂度 |
| 可用性 | 冗余、心跳检测、故障转移、超时重试、降级、限流、多活 | 资源翻倍、运维复杂、数据同步 |
| 可靠性 | 幂等、重试、事务、对账、死信队列 | 开发量、延迟 |
| 可扩展性 | 无状态化、读写分离、分库分表 | 数据层改造大、约束多 |
| 可维护性 | 高内聚低耦合、清晰分层、模块化、ADR | 短期交付略慢 |
| 可测试性 | 依赖注入、接口抽象 | 前期设计约束 |
| 安全 | 认证授权、加密、最小权限、纵深防御、审计 | 性能与效率开销 |
| 可观测性 | 结构化日志、指标、链路追踪、告警 | 约 1%~5% 的性能与存储开销 |

两个要点：

1. **右列“代价”才是决策依据**——没有免费的战术，只有还没付账的战术。
2. **战术组合打包成架构模式**：冗余 + 心跳 + 故障转移 → 主备/集群；缓存 + 读写分离 → 读扩展。模式是为某组属性优先级预打包的战术组合——所以**先定属性优先级、再选模式**，顺序反了就是在照抄别人的答案。

把上表“性能、可用性”两行摊开成可执行的清单，并标注每一件武器在后续哪个阶段展开——本阶段不必记住全部战术，只需要知道**有哪些牌、在哪一章学怎么打**（性能与可用性战术大部分在 [第三阶段：分布式系统核心技术](../章节3/01-第三阶段-分布式系统核心技术.md) 展开，异步与事件外移在 [第二阶段：经典架构模式](../章节2/01-第二阶段-经典架构模式.md)，灰度与可观测体系在 [第五阶段：工程化与运维视角](../章节5/01-第五阶段-工程化与运维视角.md)）：

性能战术清单（对照 3.2.1 压测三件套，每条注明主要作用于哪一项）：

| # | 战术 | 作用于 | 一句话原理 | 主要代价 | 后续展开 |
|---|---|---|---|---|---|
| 1 | 多级缓存 | 降延迟 | 把答案放到离请求更近的地方，用一致性问题换时间 | 失效、穿透、一致性维护 | 第三阶段缓存体系 |
| 2 | 异步化（MQ 外移非核心链路） | 提吞吐 | 把“必须现在做完”改成“最终做完” | 调试难、最终一致 | 第二阶段事件驱动；第三阶段 MQ 削峰 |
| 3 | 数据分片（分库分表） | 扩并发上限 | 把一份大负担拆成 N 份小负担 | 跨片查询/事务、扩容迁移 | 第三阶段数据架构 |
| 4 | 读写分离 | 提吞吐 | 读副本分担主库读压力 | 主从延迟 | 第三阶段数据架构 |
| 5 | 池化（连接池/线程池） | 降延迟 | 复用昂贵的建连与创建开销 | 配置不当反成排队瓶颈 | USE 表的饱和度列盯它 |
| 6 | 批量合并（治 N+1） | 降延迟 | 少往返、一次取一批 | 单批过大反而更慢 | 本节 3.2.1 已演示 |
| 7 | 预计算（物化/离线聚合） | 降延迟 | 提前把要算的算好，查询时只查不算 | 存储换时间、时效性下降 | 第三阶段缓存体系 |
| 8 | 精简协议与序列化 | 降延迟提吞吐 | 少传字节、少做编解码 | 可读性差、CPU 换带宽 | 第二阶段微服务通信 |

可用性战术清单（对照 3.2.2 的 MTBF/MTTR，每条注明主要挡什么）：

| # | 战术 | 挡什么 | 一句话原理 | 主要代价 | 后续展开 |
|---|---|---|---|---|---|
| 1 | 冗余（主备/集群/多副本） | 单点故障 | 备份的东西随时能顶上 | 资源翻倍、数据同步 | 第三阶段高可用 |
| 2 | 心跳与健康检测 | 故障发现慢 | 先知道它死了，才谈得上换它 | 误判风险 | 第三阶段高可用 |
| 3 | 故障转移（failover） | 恢复慢 | 死了自动换备件，不等人 | 脑裂、切换丢数据窗口 | 第三阶段高可用 |
| 4 | 超时与重试（指数退避） | 偶发抖动 | 别为一个慢调用无限等下去 | 重试风暴（重试要算进容量） | 第三阶段分布式 |
| 5 | 降级与熔断 | 资源不足/级联故障 | 砍非核心保核心；下游坏了就别再打它 | 体验损失、开关治理 | 第三阶段限流熔断降级 |
| 6 | 限流与削峰 | 流量超容量 | 超出容量的请求排队或快速失败 | 拒绝率、排队体验 | 第三阶段限流（配合 3.2.1 第 8 点） |
| 7 | 灰度发布与快速回滚 | 变更引发故障 | 变更闯的祸，用变更的手段救回来 | 发布节奏变慢 | 第五阶段发布与运维 |
| 8 | 多活容灾（同城双活/异地多活） | 机房级灾难 | 任何一家机房宕机，业务都能继续 | 数据同步与冲突、成本上一个数量级 | 第三阶段容灾 |

读表方式：这两张表与 3.3 的场景卡是配套的——每条场景卡都要能圈出支撑它的两三条战术（可追溯检验）；反过来，每条战术也要能指出它为哪张场景卡付账，否则就是为战术而战术。

不同系统的属性优先级（以及由此推出的架构倾向）：

| 系统类型 | 属性前三 | 架构倾向 |
|---|---|---|
| 支付/交易 | 一致性、安全、可用性 | 同步强一致、对账兜底、宁慢不错 |
| Feed 流 | 可用性、吞吐、成本 | 最终一致、重度缓存、冗余读 |
| 实时游戏 | 延迟、可用性、扩展性 | 状态在内存/就近节点、同区部署 |
| 报表/数仓 | 成本、口径正确、吞吐 | 离线批处理、T+1、廉价存储 |
| 内部后台 | 可维护性、安全 | 单体/模块化单体、权限做好 |

实践要点：接到需求先问“这个系统**最重要的质量属性是什么、目标值多少**”。主要矛盾不同，架构完全不同——交易系统优先一致性，Feed 流优先可用性。

### 3.5 怎么定优先级：场景投票

“哪个属性最重要”不能靠主观判断（每个干系人都会说自己那栏最重要）。轻量流程（简化自 SEI 的 ATAM 架构评估法）：

1. **收集**：各干系人（业务、开发、运维）每人写几条质量属性场景，凑 20~30 条
2. **投票**：按重要度投票，选出前 5~10 条
3. **定序**：前几条场景所属的属性即优先级序——之后所有属性冲突按它裁决
4. **留档**：结论写进 ADR（背景、排序、被牺牲的属性及理由）

反例：跳过排序直接选型——“我们要用微服务，因为大厂都用”。大厂微服务解决的是大厂的矛盾（几十个团队的协作与发布效率），你的矛盾可能只是数据库连接数不够，一次读写分离就够了。这是 1.4.5 “隐式权衡”在质量属性上的重现。

本节自测：

1. 结合你熟悉的 MES：把“产线 7×24 不能停”翻译成“刺激 + 环境 + 响应”场景（断网、宕机、发布变更各写一条），响应带数字了吗？
2. 工单中心的 SLA 该定几个 9？先把催办/关单链路与统计报表链路分开各定一个，再各自换算成年停机时间——与“全系统一刀切一个数”相比差在哪？
3. 最近一次性能优化，盯的是平均值还是 P99？优化前后各是多少？
4. 用利特尔法则估算你的系统容量：峰值 QPS × 目标延迟 = 需要的并发数，再除以单实例健康并发 = 实例数——算出来和当前实际部署差多少？
5. 你的系统里有单点吗？它宕机后会发生什么？恢复是自动的还是依赖人工处置？
6. 明天流量涨 10 倍，哪一层先崩溃？——那层就是当前扩展性的短板。
7. 3.4 的五行系统类型表里，你的系统最像哪一行？现有架构与那一行的“架构倾向”匹配吗？
8. 用 Amdahl 定律给你的核心链路算笔账：必须串行访问同一共享资源（单库写入、全局锁、单点服务）的步骤占比约多少？由此算出的扩展上限是几倍？当前实例数离上限多远，继续加机器还划算吗？如果打算拆微服务，拆的是 S 与 α，还是只新增了 β？
9. （属性判据）下面三句话各违反了本节哪条判据？分别改正：①“把 12 个 5 分钟窗口的 P99 平均，得到小时级 P99 是 80ms，很稳”；②“单机压测到了 8000 QPS，所以容量达标”；③“我们全系统统一 99.99% 可用性”。
10. （属性判据）数一数你的系统首页（或任一核心列表页）从网关到存储一共扇出几个下游调用 n，用“整页慢概率 = 1 − (1−q)ⁿ”算两笔账：单调用 P99（q=1%）时整页慢概率多少？要让整页慢概率 ≤ 1%，单调用要做到哪个分位数？你的监控是按单服务看的还是按整页/链路看的？
11. （场景卡开放题）用六要素（刺激源/刺激/环境/制品/响应/响应度量）给桶装水商城“押金算错”写一张可靠性场景卡：刺激选“重复的回收验收消息把桶状态写回未回收”，响应度量要覆盖“多久发现、多久纠正”两件事。
12. （场景卡开放题）用六要素给你自己的系统写一张性能场景卡：响应度量必须同时含延迟分位数与错误率，并在卡末列出支撑这张卡的至少两条战术（从 3.4 的清单里选）。
13. （权衡题）你的 SLO 是 99.9%（月错误预算 43.2 分钟），本月已因一次故障烧掉 30 分钟；本周还有两个大发布和一个限流改造要上线。用错误预算思维给出这三件事的排序与发布方式（要不要灰度、要不要推迟），并说明为什么“一律全停”和“照常发布”都不对。
14. （权衡题）列表接口治 N+1 后 P99 从 900ms 降到 120ms，但组装代码复杂了三倍、多维护一条批量查询 SQL。给出“值得改”与“不值得改”的判据各两条（提示：该接口在什么链路上、流量占比多少、改动是否可逆、900ms 慢在哪一段）。
