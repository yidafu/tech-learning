## 阶段总结：一张权衡地图

| 风格 | 换来了什么 | 付出了什么 | 演进主线上的落点 |
|---|---|---|---|
| 分层单体 | 简单、本地事务、好调试 | 整体扩展、易腐化 | 桶装水起步形态：八模块一进程一库 |
| 模块化单体 | 边界纪律 + 单体简单性 | 需要强制手段与团队自律 | 桶装水成长期最优解；工单中心同款 |
| 微服务 | 独立部署/扩展、组织伸缩 | 分布式的一切代价 | 只拆排线、订阅等扩展差异大的服务 |
| 事件驱动 | 解耦、削峰、弹性 | 最终一致、排查变难 | OrderPlaced 一事四订阅，收尾主线 |
| 事件溯源 + CQRS | 审计、时间旅行 | 复杂度陡增 | MES 批次追溯与生产看板 |
| 管道-过滤器 | 可组合、可并行 | 交互性差 | Feed 审核管道与热搜统计 |
| 六边形/整洁/洋葱 | 领域防腐、可测试 | 样板代码 | 工单中心多渠道接入的内核组织 |
| Serverless | 免运维、极致弹性 | 锁定、冷启动、成本 | IoT 采集函数、回调与定时任务 |
| BFF | 端差异化聚合、前后端团队自治 | 层数 +1、公共逻辑重复、职责漂移风险 | 网关只做策略，三类端各一个 BFF |
| 中台 | 能力复用、新业务线启动快 | 约束（契约）、排队（需求瓶颈）、定制成本 | 单业务线不需要；语义一致才沉淀 |
| SOA（ESB） | 异构系统互通、集中管控 | 智能总线成瓶颈与单点 | 历史教训：中介只做策略不做业务 |
| 主从 | 读扩展、并行、容灾切换 | 复制滞后、选主与脑裂 | 商品读主从；K8s 控制面/数据面同构 |
| Broker | 位置透明、解耦 | 中介要高可用、忌膨胀成 ESB | 注册中心、消息队列、网关与 sidecar |
| 微内核/插件化 | 扩展点稳定、能力热插拔、并行开发 | 契约冻结、版本矩阵、插件协作绕远 | 低代码引擎、工单渠道、网关插件链 |

真实系统是**风格的组合**。桶装水商城走完全程后的合理终态，很可能不是“全微服务”，而是：**模块化单体（交易域内部用六边形组织）+ 少量微服务（配送排线，必要时再加商品读服务）+ 事件驱动（OrderPlaced 后置动作）+ Serverless（夜间对账、大促预热函数）+ 网关与各端 BFF 收口三类入口**。架构师的功夫在于为**每个子域单独**选风格，而不是让全公司只有一种风格。

## 第二阶段自测

1. 同一个桶装水商城在 3 人 / 30 人 / 300 人团队三种规模下，你会分别推荐什么架构组合？说明每个选择的主导权衡。
2. “我们拆了微服务，但每次发版要 6 个服务一起上线”——诊断这个系统的病灶，给出渐进式治疗方案。
3. 桶装水下单主链路中：锁库存（不能超卖）、支付扣款（必须立即知道结果）、生成配送任务与押金记账（可延迟）三类步骤，分别选什么通信与一致性方案？说明理由。
4. MES 批次追溯用事件溯源，与“用数据库 binlog 做审计”相比本质优势是什么？什么时候 binlog 审计就够用了？
5. 为什么“依赖方向指向领域”（六边形/整洁）与“数据所有权独立”（模块化单体/微服务）是同一条纪律在进程内与进程间的两种表达？
6. 为工单中心画一张端口与适配器示意图：标出四个驱动侧适配器（电话/APP/IoT/外部系统）与两个被驱动侧适配器（存储/通知），并说明防腐层放在哪里。
7. 同一个“订单”一词：通用订单中台想把桶装水、家电清洗、家政保洁的订单统一建模，错在哪里？用它反推：支付、营销、配送调度三条能力该不该中台化，判据分别是什么？
