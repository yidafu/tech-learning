## 2. 部署与发布策略

部署（deployment）与发布（release）是两个经常被混用、但必须分开的词：**部署是把制品装到服务器上的技术动作；发布是让用户真正用上新功能的业务动作**。CI/CD 解决“变更如何安全地走到生产”，蓝绿、灰度、滚动解决“到了生产之后如何放出来”。所有策略背后都在回答同一个问题：**新版本出问题时，把损失控制到多小、用多快止损**。这一节就沿着这个问题展开：先用 2.1 把“上”的路修好（流水线、门禁、回滚），再用 2.2~2.4 比较“放”的三种做法，2.5 给出选型与数据库变更的联合视角，2.6 补上功能维度的最后一层保险。

本节的三个主角场景各有分工：**桶装水商城**演示传统应用的版本发布（支付服务灰度、订单表兼容迁移）；**低代码平台**演示配置产物（表单 Schema、流程定义）的发布治理——配置也是“会出事故的变更”；**MES** 展示发布窗口受限系统的策略选择（产线白天不能停，窗口与预案怎么定），收尾的附录预案模板就用它填写。工单中心则在定时任务、SLA 扫描这些点上补充真实的滚动发布坑。

### 2.1 CI/CD：从提交到上线的主线

- **CI 持续集成**：每次提交自动构建 + 测试 + 打包制品（容器镜像），问题越早暴露修复成本越低。
- **CD 持续交付/部署**：制品沿流水线推进到预发、生产。交付 = 停在需人工批准的位置；部署 = 全自动直达生产。

核心原则：**一次构建，处处部署**——同一镜像贯穿所有环境，环境差异全部放配置，制品是不可变单元；给每个环境单独打包是流水线坏味道。镜像 tag 用 commit SHA（不可变、可追溯），不要用 latest。

GitHub Actions 示例（工单中心 ticket-center）：

```yaml
name: ticket-center
on:
  push:
    branches: [main]
jobs:
  build-and-deploy:
    runs-on: ubuntu-latest
    steps:
      - uses: actions/checkout@v4
      - uses: actions/setup-java@v4
        with: { distribution: temurin, java-version: 21 }
      - name: 单元测试与集成测试
        run: ./gradlew test
      - name: 构建并推送镜像（jib，无需 Docker 守护进程）
        run: ./gradlew jib --image=registry.example.com/ticket-center:${{ github.sha }}
      - name: 部署到预发（滚动更新）
        run: kubectl set image deploy/ticket-center app=registry.example.com/ticket-center:${{ github.sha }} -n staging
```

**配置即代码**：低代码平台的表单 Schema、流程定义也是“会出事故的变更”，同样应存 Git、走 PR 评审 → CI 校验（Schema 合法性、字段删除的向后兼容检查）→ 发布审批 → 灰度，与代码共用一条流水线。这是 2.3 主案例的前置认知：**配置的变更频率比代码更高，治理标准不应更低**。

“配置即代码”落到工单中心同理：分派规则、SLA 阈值这类规则配置改起来比代码还频繁、错了直接影响派单与催办，同样要进 Git、过门禁、可回滚。让“改配置”绕过流水线直改生产库，等于给生产开了一条没有门禁的旁路——配置变更的频率更高，恰恰说明它更需要这条流水线，而不是更不需要。

#### 2.1.1 流水线各级门禁：每一道闸拦什么

CI/CD 不是“自动把代码搬到生产”的传送带，而是一串**带门禁（quality gate）的关卡**：每一级只放行达到判据的制品，未达标就拦下。门禁的价值不在“多”，而在“不可绕过”——所有应急通道（管理员直接合并、跳过测试的临时参数）都会在半年后变成事故入口。紧急修复的正规做法是独立的 hotfix 流水线：**门禁一级不少，只是审批提速、发布强制走灰度**。

门禁按“越便宜的地方越早拦”排序，因为缺陷被发现的阶段越晚，修复成本越高——这是数量级意义上的差距：提交时发现问题，改几分钟就能重跑；到了生产才发现，是排查加发布加数据修复，外加资损与用户信任。

| 门禁 | 检查什么 | 通过判据 | 失败处置 |
|---|---|---|---|
| 编译构建 | 代码能否构建成制品 | 构建成功，产物 tag = commit SHA | 直接终止并通知提交者，分钟级修复 |
| 单元测试 | 模块内逻辑正确性 | 全绿；核心模块覆盖率不低于基线（如 70%） | 阻断合并；“红了先修红”，禁止跳过测试赶发布 |
| 静态检查 | 代码规范、坏味道、依赖漏洞 | 无新增高危告警 | 高危阻断；低危登记进技术债看板，不阻塞发布 |
| 契约测试 | 接口变更是否向后兼容 | 所有消费者契约用例通过 | 阻断，按兼容规则改造接口后再提（兼容纪律见[第二阶段-微服务架构](../02-第二阶段/03-微服务架构.md) 2.6） |
| 集成测试 | 跨模块/跨服务关键链路 | 关键链路用例通过 | 阻断；先分清是代码坏了还是环境漂了——环境问题同样要修，不能用一句“环境原因”放过 |
| 安全扫描 | 镜像 CVE、密钥泄露、敏感配置 | 无高危 CVE，无明文密钥 | 阻断；升级依赖或轮换密钥后重扫 |
| 部署前检查 | 配置 diff、DB 迁移脚本、人工审批 | 配置 diff 有人确认，迁移脚本通过向后兼容检查（见 2.1.3），负责人批准 | 挂起等待批准——这正是“持续交付”停在人工批准位的含义 |

注意最后一行：部署前检查是唯一“靠人”的门禁，它的产物是两份被评审过的 diff——配置改了什么、库要怎么改。审批人看的不是“代码写得好不好”（那是前六道闸的事），而是“这次变更的爆炸半径有多大、回滚方案成立吗”。

门禁失败本身也要有纪律：主分支红了，“谁红谁修”——红灯责任人 30 分钟内开始修复，修复期间冻结其他合并，防止红灯叠红灯把根因埋掉。CI 的全部价值都建立在“主干永远可发布”这个不变量上；破坏它一次，之后每次发布都建立在存疑的基线上。

流水线健不健康，最后要落到四个可度量的指标上（业界通称 DORA 四指标）：**部署频率**（发布越频繁、单次变更越小，单次风险越低）、**变更前置时间**（从 commit 到生产的时长，衡量流水线整体速度）、**变更失败率**（多大比例的发布触发了回滚或紧急修复，衡量门禁有效性）、**服务恢复时长**（出事后多久止损，衡量回滚与预案能力）。这四个数比“流水线配了多少 stage”诚实得多：门禁越有效，变更失败率越低，团队才敢提高部署频率，进入“小步快跑”的正循环；反过来，部署频率低、单次变更巨大，正是大多数“发版如渡劫”团队的病根。按能力分级的话可以粗略分四档：L0 手工部署（登录服务器拷包重启，全靠人盯）；L1 脚本化（部署动作脚本能一键执行，但没有自动触发）；L2 自动流水线（提交触发构建测试，人工点按钮部署，本文的 GitHub Actions 示例在此档）；L3 全自动 + 智能放量（流水线直达生产，灰度自动升量、越界自动回退——2.3.3 的控制器属于这一档的零件）。团队位置不同，该补的短板不同：L0 → L1 的收益最大（先消灭手工操作的随意性），L2 → L3 的前提是可观测性已经跟上（没有按版本的指标，全自动放量等于闭眼开车）。

#### 2.1.2 构建一次、处处部署

上面“一次构建，处处部署”值得单独拆开讲，因为它是流水线里被违反最多的一条。合规做法是**同一制品多环境晋级**：镜像在 CI 只构建一次（tag = commit SHA），从测试 → 预发 → 生产的每一步只是“同一个 tag 部署到下一个目标”，环境差异全部通过环境变量、配置中心、启动参数注入。

❌ 反例（各环境重新构建）：三个环境跑三次构建，打包时分别注入各环境的数据库地址。第二次生产构建时上游依赖恰好发了新版本，两个产物连依赖树都不一样——于是“我测过的包”和“线上出问题的包”不是同一个包，排查先花半天排除环境差异，最后发现根因是依赖变更。这类事故的病根永远在流水线而不在代码：**重新构建让“测试通过”这个结论失去了证据效力**。

✅ 修正判据：全流程只允许存在一个制品；想验证“生产配置对不对”，用同一镜像在预发注入生产配置跑冒烟，而不是重新构建一个“生产版镜像”。镜像 tag 全程 = commit SHA，从 tag 就能反查出代码、流水线日志、部署记录，这是事后追溯的全部基础。

配套的还有两件小事。**制品保留策略**：制品库保留最近 N 个可部署版本（比如 20 个），更早的清理——回滚的前提是“旧制品还在、还能跑”，别等事故时才发现要回滚的镜像已经被清掉了。**分支策略与流水线的关系**：流水线配好之后，最拖效率的往往是长命分支——在分支上憋三周再合回主干，等于把集成推迟到最后一刻，与持续集成的精神正好相反。主流做法是主干开发 + 短命分支（寿命不超过两三天）：没做完的功能用特性开关藏起来（见 2.6），代码先合进主干持续集成。分支管理、特性开关与流水线，三者是一套配合动作，拆开用哪个都缺一块。线上紧急修复同理：从出问题的 commit 拉出短命修复分支，改完走同一条流水线（门禁不少、发布走灰度），而不是有人绕过流水线直接登录生产改文件——后者改完没人说得清线上跑的是什么。

#### 2.1.3 回滚是一级公民

发布方案的第一页应该写“怎么退”，而不是“怎么上”。回滚要当成日常能力来维护，而不是事故时才第一次打开的文档：

- **回滚演练纳入日常**：预发环境每月做一次“部署新版本 → 回滚 → 再部署”演练，验证三件事：回滚按钮真的好用、回滚耗时有数、回滚后的数据状态符合预期。只在事故现场第一次执行回滚，等于排雷。
- **代码回滚通常是容易的**：镜像按 SHA 留存，一条 `kubectl rollout undo` 十秒完成。真正难的是**数据库变更与代码回滚互相锁死**。
- ❌ 反例（回滚通道被自己堵死）：v2 上线时迁移脚本把 `orders.legacy_discount` 列删了；一周后发现 v2 分账逻辑有 bug，需要回滚到 v1——v1 的代码还在往那一列 INSERT，每笔下单直接报错；被删的列和数据只能靠备份恢复，回滚升级成数据事故。代码 10 秒能回、数据库回不去，等于没有回滚。
- ✅ 解决方案：**向后兼容迁移三阶段（expand → migrate → contract）**，纪律是“兼容的加法先改库，收缩的减法先改代码；每一批库变更必须让上一个版本也能跑”：

```sql
-- 阶段一 Expand（扩：只做加法，新旧代码都能跑）——片段示意
ALTER TABLE orders ADD COLUMN expect_time TIME NULL;      -- 加可空列，旧代码无感知
CREATE TABLE order_paid_event ( id BIGINT PRIMARY KEY );  -- 或加新表/新索引

-- 阶段二 Migrate（迁：新代码双写或回填，期间随时可整体回滚）
UPDATE orders SET expect_time = SUBTIME(pay_time, '02:00:00') WHERE expect_time IS NULL;

-- 阶段三 Contract（缩：所有旧版本实例下线且观察期结束后才做减法）
ALTER TABLE orders MODIFY COLUMN expect_time TIME NOT NULL;
-- 删列永远是最后一步：先发"不再读写 legacy_discount"的代码，观察一个版本周期，再执行
-- ALTER TABLE orders DROP COLUMN legacy_discount;
```

（SQL 为片段示意，桶装水商城订单表加“期望送达时间”的真实节奏。）有了这个纪律，回滚代码到 v1 之后：v1 忽略新列照常工作，v2 已经写进新列的数据留在那里不丢；bug 修好再上 v2，数据无缝接上。**库变更永远向后兼容一步**，就是给回滚留门。

顺手把“回滚”分出三个层次，预案里三类都要有动作：**代码回滚**（切回旧镜像或旧版本流量，最常用）、**配置回滚**（配置中心一键回退上一版——很多“代码事故”其实是配置事故，配置回滚比代码回滚快一个数量级）、**数据回滚**（最难也最不该走到的一层：靠上面的兼容纪律避免，真发生时是备份恢复 + 数据订正，属于事故级操作）。用得越顺的层次越靠前：成熟团队日常止损九成靠配置回滚和关开关，代码回滚是第二道防线，数据回滚一年遇不到一次。

### 2.2 蓝绿发布

两套**完整**环境：蓝 = 当前版本承接 100% 流量；绿 = 新版本部署完毕后，网关一键把流量整体从蓝切到绿。优点是切换与回滚都是秒级（切回蓝即可）；代价是双倍资源，且共享数据库时 schema 变更必须同时兼容两个版本。适合需要极快回滚的关键变更——例如桶装水商城大促前夜给支付服务换版本：出了问题秒级切回，不影响第二天开卖。

#### 2.2.1 蓝绿的三个隐藏成本

“两套环境”本身不贵，贵的是三件常被低估的事：

1. **数据库不跟着蓝绿一起切**。蓝绿切的是应用层流量，schema 是共享的——绿版本跑过的迁移脚本，蓝版本也必须能跑。所以蓝绿“秒级回滚”隐含一个硬前提：**schema 变更同时兼容两个版本**（回到 2.1.3 的三阶段迁移）。谁在绿环境跑了一个破坏性 DDL，蓝环境的回滚按钮就废了。
2. **长连接不会跟着流量切**。Web 请求切流是瞬时的，但 IM 接入层、MES 边缘网关这类长连接服务，存量连接还挂在蓝上——“切换完成”之后蓝环境可能还承载着一半用户。要配连接排空：先摘注册与切流，再等存量连接自然断开或主动迁移，蓝环境连接数归零才算切完，下线动作放到最后。

顺带说一句“一键切流”的实现位置：常见做法有三层——负载均衡/网关层把后端分组从蓝换成绿（最常用，秒级生效且可回退）；服务注册与发现层让新实例上线、旧实例摘除；DNS 层切（生效慢，受 TTL 拖累，只适合粗粒度切换）。回滚按钮挂在网关层最可靠：DNS 回切可能要等 TTL 过期，事故时等不起。
3. **双倍资源平时闲置**。缓解办法是让绿环境平时也有活干：发布窗口外用作压测环境，或做新旧版本对拍（同一请求双跑比对输出），只在发布前把绿环境拉到与蓝同规格。

MES 的排程服务是蓝绿的典型适用场景：产线流量没法按“用户”灰度——车间就那几条产线，让半条产线跑新版本反而造成新旧排程数据混跑；而产线白天不能停、夜里换版本后留给观察的时间有限。蓝绿“整体切 + 秒级切回”恰好匹配这种**流量不可分、止损要快**的约束。它的夜间窗口操作顺序也值得抄一遍：22:00 确认晚班收工、在途工序已报完 → 绿环境部署并跑冒烟（含用蓝镜像起冒烟实例的回滚验证）→ 网关切流 → 观察 30 分钟（报工采集、排程计算、下发延迟三项指标）→ 达标则保留蓝环境热备 24 小时后销毁，越界则秒级切回。每一步都写进附录的发布预案，照单执行。

蓝绿还有两个变体值得知道。**影子发布（对拍 / dark launch）**：新版本接一份复制的真实请求，返回结果不给用户、只与旧版本输出比对——支付与清结算的账务服务大改版前常这么跑一周，差异清单就是最真实的回归测试；MES 的新排程算法也可以影子跑（算出来只进报表、不进产线）。影子发布抓不到缓存命中率、数据量增长这类“真流量才有的问题”，所以它适合验证正确性，不能替代真流量灰度。**分批蓝绿**：资源不够双倍时，按批次先扩绿再缩蓝，介于蓝绿与滚动之间——代价是失去“整体一键切回”，回滚也变成反向分批，速度向滚动看齐。选变体时先想清楚为了省那点资源放弃了什么。

❌ 反例：绿环境部署时，运维“顺手”执行了包含 DROP COLUMN 的清理脚本；切流后发现新版本分账出错，按预案切回蓝——蓝的代码读不到被删的列，**回滚动作本身制造了第二个事故**。✅ 修正：绿环境的一切 DB 操作同样走 2.1.3 三阶段；切换检查单里固定加一条——用蓝的镜像 + 新 schema 起一个冒烟实例，验证“切回去也能活”，才允许切流。

### 2.3 灰度 / 金丝雀发布

新版本先接一小部分**真实流量**（如 5%），观察核心指标无异常后逐步放量 5% → 25% → 50% → 100%；指标恶化立即回切。“金丝雀”取自矿工带金丝雀下井探毒气的典故——用小牺牲换大预警。

**主案例：低代码平台的搭建产物发布治理**。实施人员把报修表单里的“紧急程度”字段删了、审批流加了一级会签，点“保存”直接生效——麻烦立刻出现：300 张在途工单的渲染与校验还引用旧字段，流程卡死、报表报错，而且**没有旧版本可回滚**。搭建产物的发布治理需要四件套：

1. **Schema 版本化**：每次发布生成不可变版本（v12）。单据提交时绑定当前版本，历史单据永远按**提交时的版本**渲染与校验——删字段只影响新单，不影响旧单（与[第三阶段-动态字段存储](../03-第三阶段/01-分布式系统核心技术.md)中 Schema 演化的讨论呼应）。
2. **发布审批**：配置变更走 PR/审批流，谁改的、改了什么、何时生效全程留痕——配置即代码。
3. **配置灰度**：新版本 Schema 先对试点租户/车间生效：

```kotlin
// 表单 Schema 灰度：v13 先对试点租户生效，其余仍用 v12
fun resolveSchemaVersion(formId: FormId, tenantId: TenantId): SchemaVersion {
    val gray = grayReleaseRepository.find(formId) ?: return latestStable(formId)
    return if (gray.pilotTenants.contains(tenantId)) gray.candidateVersion else gray.stableVersion
}
```

4. **一键回滚**：灰度观察期发现问题，把 stable 指回 v12 即刻生效；因版本化，已按 v13 提交的少量单据仍按 v13 渲染，数据不损坏。

**传统应用发布对照**：桶装水商城支付服务 v2 重写了分账逻辑，按 userId 哈希把 5% 用户路由到 v2：

```kotlin
// 网关路由示意：同一用户始终落在同一版本，避免"忽新忽旧"造成体验割裂与数据错乱
fun routeVersion(userId: String): String =
    if (abs(userId.hashCode()) % 100 < 5) "v2-canary" else "v1-stable"
```

配套要求（两类发布通用）：指标带版本标签，在 Grafana 并排对比新旧版本的成功率、错误率、P99；数据兼容（v2 写入的新字段 v1 能忽略，回切后业务仍正确）；功能开关（Feature Flag）与灰度正交，把发布风险与功能风险分离。

#### 2.3.1 放量阶梯怎么设计

“5% → 25% → 50% → 100%”不是固定咒语，四个参数都要按业务定：

- **初始比例**：目标是“能观察、出不了事故”。支付服务从 1% 起步；低代码配置灰度先给 1 个试点租户。
- **每档停留时长**：由业务的自然周期决定。支付要覆盖一个完整的支付高峰（比如午高峰两小时）；配置灰度要覆盖“在途流程走完一圈”的时间。停留 10 分钟只能抓住部署类故障（起不来、连不上库），抓不住业务逻辑 bug——业务 bug 需要真实用户走出完整路径才暴露。
- **档间距**：不能 1% 直接跳 100%。内存泄漏、缓存击穿、连接池耗尽这类问题**随流量比例放大**，小流量完全暴露不出来；跳档等于放弃观察，直接拿全量用户赌。
- **人工批准点**：自动放量到 50% 为止是常见的分界——小比例交给控制器，50% → 100% 这一步人工确认后再放。理由：50% 已经“一半用户在新版本上”，此时最大的剩余风险不再是技术指标能反映的（比如业务规则理解错误），值得人看一眼再走最后一步。

先把“灰度”这个词分清三个层次，很多争论其实是层次错位：**实例级灰度**（传统应用按实例比例分流，5% 实例接 5% 流量，管的是代码版本的部署风险——下面传统对照里的支付服务）、**人群级灰度**（按 userId/租户/地域圈定人群，同一用户始终同一版本，管的是功能与业务风险）、**配置级灰度**（低代码 Schema、规则参数对试点租户生效，放出来的甚至不是代码——主案例的四件套）。三个层次可以叠加：SaaS 平台做实例级金丝雀 + 租户级配置灰度时，观察面板要分别按 version 和 tenant 标签拆开，混在一起互相污染。共享的骨架是同一套“放量 — 观察 — 回退”，变的只是放量对象。

#### 2.3.2 指标对比的两个陷阱

陷阱一：**只看大盘绝对值**。全站成功率 99.8% 看着健康，拆开版本一看：v1 是 99.95%，v2 只有 99.3%——v2 的问题被大盘平均掩盖了。所以原文强调“指标带版本标签、并排对比”，实操标准再加一条：**新版本与旧版本同期对比，允许的劣化幅度事先约定**（例如成功率差距不超过 0.1 个百分点、P99 劣化不超过 10%），而不是和某个全局阈值比。指标怎么按版本打标与聚合，见[可观测性分册](02-可观测性-日志指标与链路追踪.md)。

陷阱二：**小流量档位的统计噪声**。系统每分钟 2 万笔请求时，1% 档每分钟能积累 200 个样本，错误率有统计意义；每分钟只有 20 笔请求的小系统，1% 档 10 分钟才 2 个样本，一个偶发错误就是 50% 错误率——按阈值自动回退会误报，不报又会漏。修正：**设保底样本数**，样本不足时延长停留观察，既不放量、也不触发回退判定。

顺带澄清一个常见误区：金丝雀环境必须接**真实流量**，并且与生产环境同构（同规格的机器、同配置的依赖、同一份数据库）。用“测试流量打到隔离的金丝雀环境”测十遍，也替代不了 5% 真实用户半小时——真实流量的价值恰恰在于它带着你预料不到的参数、并发时序和数据分布，这正是金丝雀存在的意义。

#### 2.3.3 自动放量控制器：一个可运行的模拟

把上面的规则拼起来，就是灰度控制器的核心逻辑：尾号分桶路由 + 按档观测 + 达标升量 / 越界回退 + 决策留痕。下面是完整可运行的 Kotlin 模拟（真实系统中“读指标”换成按 version 标签查 PromQL，“决策日志”写入审计存储供复盘）：

```kotlin
// 金丝雀自动放量模拟：按用户尾号分桶 → 观察 P99 与错误率 → 达标升量 / 越界回退
// 决策全程输出"决策日志"，等价于生产上灰度控制器的审计记录

data class StageMetrics(val p99Millis: Double, val errorRate: Double, val samples: Int)

// 模拟监控系统：真实实现读 PromQL（按 version 标签聚合，见第 5 章可观测性笔记）
class MetricProbe(private val baselineP99: Double = 120.0) {
    fun probe(percent: Int, scenario: String): StageMetrics = when (scenario) {
        // 健康发布：随比例增大，负载上升带来轻微劣化，但都在阈值内
        "healthy" -> StageMetrics(
            p99Millis = baselineP99 * (1 + percent / 400.0),
            errorRate = 0.001 + percent * 0.00001,
            samples = percent * 4000
        )
        // 带病发布：1%、5% 时问题被基线噪声掩盖，放大到 25% 才显形
        "degrading" -> if (percent >= 25) StageMetrics(baselineP99 * 3.4, 0.041, percent * 4000)
                       else StageMetrics(baselineP99 * 1.15, 0.002, percent * 4000)
        else -> error("unknown scenario: $scenario")
    }
}

data class Thresholds(val p99MaxMillis: Double, val errorRateMax: Double)

class CanaryController(
    private val thresholds: Thresholds,
    private val probe: MetricProbe,
    private val dwellMinutes: Int = 10   // 每档停留观察时长
) {
    private fun log(msg: String) = println("[决策日志] $msg")

    fun rollout(scenario: String): Int {
        var percent = 1
        val ladder = listOf(5, 25, 100)
        log("发布开始：初始比例 ${percent}%（尾号 < $percent 的用户路由到新版本）")
        for (next in ladder) {
            Thread.sleep(20) // 模拟每档停留观察 dwellMinutes，演示中压缩为 20ms
            val m = probe.probe(percent, scenario)
            val p99Ok = m.p99Millis <= thresholds.p99MaxMillis
            val errOk = m.errorRate <= thresholds.errorRateMax
            if (!p99Ok || !errOk) {
                log("比例 ${percent}% 观测越界：P99=${"%.0f".format(m.p99Millis)}ms" +
                    "（阈值 ${thresholds.p99MaxMillis.toInt()}ms），" +
                    "错误率=${"%.2f".format(m.errorRate * 100)}%（阈值 ${thresholds.errorRateMax * 100}%）")
                log("触发自动回退：新版本比例归零，旧版本恢复 100%；决策与指标快照已存档供复盘")
                return 0
            }
            log("比例 ${percent}% 观测达标（样本 ${m.samples}）：P99=${"%.0f".format(m.p99Millis)}ms，" +
                "错误率=${"%.3f".format(m.errorRate * 100)}% → 停留 ${dwellMinutes} 分钟后放量到 ${next}%")
            percent = next
        }
        log("全量 100% 完成：旧版本下线，按版本区分的路由规则与本次灰度的指标面板一并归档")
        return 100
    }
}

fun main() {
    val thresholds = Thresholds(p99MaxMillis = 300.0, errorRateMax = 0.01)
    println("== 场景 A：健康发布，一路放量到全量 ==")
    CanaryController(thresholds, MetricProbe()).rollout("healthy")
    println()
    println("== 场景 B：带病发布，25% 档错误率越界自动回退 ==")
    CanaryController(thresholds, MetricProbe()).rollout("degrading")
}
```

场景 B 有两点值得回味。其一，1% 和 5% 档指标都在阈值内，问题到 25% 才显形——这正是“档间距不能跳”的实验证据：小流量挡不住随比例放大的问题，所以每一档都是真的在观察，不是走形式。其二，从越界到自动回退是秒级，凌晨三点的事故不等人响应。

把模拟换成真实系统，控制器要接上三个零件：**版本路由**（网关按规则把流量分到新旧版本，支持运行时改比例，不需要重新部署）；**按版本聚合的指标查询**（PromQL 里 `sum(rate(http_requests_total{version="v2"}))` 这类按 version 标签拆开的查询，面板与阈值判定共用同一套查询）；**决策执行与留痕**（改路由比例的动作本身要走审批日志——能自动放量就能自动误放量，控制器权限要收敛、动作要留痕）。三个零件齐了，上面 30 行控制器代码才能落地；缺任何一个，就退回“人工看面板 + 手动改路由”的半自动灰度，照样可用，只是凌晨的响应速度退回人工水平。

工程判据：**部署健康**（实例就绪率、启动失败）与**技术指标**（错误率、P99）适合交给控制器自动判、自动回退；**业务深水区**（资金差错、错发消息、审批流卡死）控制器看不见，靠对账、告警与人工兜底。不要指望灰度控制器抓住所有问题——它的职责是把“明显坏的”挡在小流量阶段。

灰度期间值守的观察清单按顺序过四样：一看技术指标（错误率、P99 与旧版本对比）；二看业务指标（支付成功率、下单量、订阅续费——业务指标要单独设阈值，技术全绿但支付成功率跌了 2 个百分点就是大事）；三扫错误日志的新增模式（error 日志按 version 拆分后看有没有新指纹，很多 bug 先在日志里露头、几小时后才变成错误率）；四收用户反馈（试点人群的客服工单量、内部试用群的反馈）。上面示例里的决策日志在复盘时价值最大：它记录了“每个比例上停留多久、看到什么数、做了什么决定”——出事后能回答“为什么 25% 没拦住”，下一次调阈值、调阶梯才有依据，而不是凭记忆吵。

配置级灰度的观察项和传统应用不同，别照抄 P99 那套：低代码平台灰度新版本 Schema，看的是**在途流程卡滞数**（引用已删字段的老单据还剩多少没走完）、**新版本单据提交成功率**、**渲染报错数**——主案例里那 300 张在途工单，就是“在途流程卡滞数”这个指标要抓的东西。传统应用抓部署故障，配置灰度抓“新旧数据共存期”的兼容问题，观察面板的字段设计要跟着变。

最后一个提醒：灰度不是免死金牌，**发布窗口和值守纪律不能因为“有灰度”就放松**。凌晨发布 + 值守人到家就睡，等于 1% 的用户陪跑——灰度拦得住技术指标恶化，拦不住“凌晨三点没人看面板”。放量时段必须落在值守人在岗的时间段内，这是 2.3 和附录预案的交汇点。

### 2.4 滚动发布

逐台/逐批替换实例：旧实例摘除流量 → 更新镜像 → 就绪后挂回，循环至全部替换。资源最省（约 1 批冗余），但发布期间**新旧版本长期共存**，接口必须 N-1 兼容（v2 能处理 v1 写的数据，反之亦然）；回滚 = 反向再滚一轮，速度最慢。适合常规小改动——工单中心新增一个通知渠道这类低风险变更用滚动即可，不必动用蓝绿的双倍资源。

#### 2.4.1 滚动的节奏参数与两个坑

Kubernetes 里滚动的快慢由两个参数决定：`maxSurge`（允许超出期望副本数的新实例数，决定并行部署多少台）、`maxUnavailable`（允许同时不可用的旧实例数，决定滚动期间的容量下限）。默认 25%/25% 的含义是：一次替换四分之一的实例，期间集群容量不低于 75%。调大 `maxSurge` 发布更快但更费资源，调大 `maxUnavailable` 更省资源但容量下降——滚动发布的“资源最省”从来不是免费的，是在速度与容量之间调出来的。

**坑一：就绪探针决定“什么时候挂回流量”。** 就绪探针要检查“真能处理请求”：依赖的数据库连上了、缓存预热完成、线程池就绪。❌ 反例：探针只查进程活着（甚至没配探针），新实例一起来就接流量，冷缓存的头几百个请求 P99 打到 5 秒；滚动 20 台就制造了 20 波慢请求，大盘 P99 呈锯齿状却查不到单点故障。✅ 修正：就绪探针包含依赖检查，或实例启动后先预热再挂流量。启动特别慢的实例（比如要预热大缓存）再加启动探针，给足启动窗口，避免慢启动实例被存活探针误杀、陷入“起 → 被杀 → 再起”的循环。

**坑二：回滚 = 反向再滚一轮。** 100 台滚到 60 台发现 bug，回滚意味着剩下 40 台停滚回退、已滚的 60 台换回旧版本——共 200 台次实例操作，全程持续不可用风险。这就是“滚动只适合低风险常规变更”的量化原因：灰度方案同样的场景只动 5 台。滚动省资源的前提是“变更足够小、大概率不用回滚”；把高风险变更放上滚动发布，省下的资源远不够赔回滚时间。摘流量这一步也别省：旧实例先从注册中心/负载均衡摘除、处理完存量请求再杀进程，否则滚动期就是一波可预期的报错。

还有一类服务在滚动期有独特的坑：**内嵌定时任务的服务**。工单中心的 SLA 超时扫描是每 5 分钟扫一遍在途工单的定时任务，滚动发布的那 10 分钟里新旧实例都在跑——同一批超时工单被扫出两次，催办消息重复发送，用户收到两条“您的工单即将超时”。滚动本身没错，错在任务没为“多实例并存”设计。✅ 修正：定时任务加分布式锁（同一轮只有一个实例执行），或按分片扫描（实例各自负责 instanceId % N 号分片），滚动与灰度期间新旧实例各扫各的；更彻底的做法是把任务外置成独立调度（任务表 + 调度器），应用实例退化为无状态纯执行者，怎么滚都不重复。判据：代码里凡有定时任务注解，发布预案里就要回答一句“滚动期任务会不会双跑”。

最后厘清一个容易混淆的边界：Kubernetes 的滚动更新天然是“分批替换实例”，看起来像灰度，但**金丝雀与滚动的本质区别在切流依据**——滚动按实例数推进（一批替换 25% 的实例，流量随实例数被动移动），金丝雀按流量比例主动控制（5% 的流量精确导到新版本，其余锁定旧版本，且可按人群圈定）。前者回答“什么时候换完”，后者回答“给新版本多少流量、给谁”。没有服务网格或网关权重路由的集群，能做好滚动，做不了真正的金丝雀——这直接影响 2.5.1 第 4 问对团队工具水位的判断。

### 2.5 三种发布策略对比

| 维度 | 蓝绿 | 灰度 / 金丝雀 | 滚动 |
|---|---|---|---|
| 资源成本 | 高（双份完整环境） | 中（少量新实例） | 最低（约 1 批冗余） |
| 回滚速度 | 最快（秒级切回） | 快（流量/配置回切） | 慢（逐批反向再滚） |
| 发布风险 | 中：切换即全量，无渐进观察 | 最低：小流量试错 + 渐进放量 | 中：混合版本共存期长 |
| 流量粒度 | 0% / 100% | 任意比例，可按人群/租户/地域 | 逐实例 |
| 关键前提 | 环境一致性 + DB 双向兼容 | 版本路由 + 按版本对比指标 | 接口与数据 N-1 兼容 |
| 典型场景 | 大促前关键变更、要求秒级回滚 | 高风险大变更（低代码 Schema、分账逻辑） | 常规小改动 |

❌ 反例：周五下午实施人员直接在生产改报修表单、删字段保存即生效——在途工单渲染报错、流程卡死，且没有旧版本可回退。✅ 修正：Schema 版本化 + PR 审批 + 试点租户灰度 + 一键回滚（见 2.3）；配置“发布”到试点后先验证在途流程与新提交两条路径都正常，再全量。

#### 2.5.1 选型决策树：四问定策略

按顺序问四个问题，答案会收敛到一个默认策略：

1. **回滚速度要求多快？** 需要“秒级止损”（大促前夜的关键变更、产线夜间窗口）→ 蓝绿或灰度；“分钟级可接受”（常规业务改动）→ 滚动就够。
2. **停机容忍是多少？** 窗口内允许短暂抖动、容量允许暂时下降 → 三者皆可；完全不能停且**流量无法按人群切分**（产线设备流、车间就几条产线）→ 蓝绿整体切——灰度的“按用户分桶”在这里没有抓手。
3. **状态服务占比高不高？** 无状态为主 → 三者都可用，默认灰度；长连接、本地缓存等有状态实例多 → 优先蓝绿（整体切换语义清晰），或者先把状态外置（会话进 Redis、缓存集中化）再谈渐进式发布。
4. **团队规模与自动化水位？** 小团队、没有按版本聚合指标的看板 → 滚动 + 2.1 的完整门禁（**没有版本对比指标的灰度是盲灰**，升量靠感觉等于没灰度）；有可观测性与发布系统 → 灰度为主，蓝绿只留给关键变更。

注意四问的顺序就是优先级：止损速度 > 停机容忍 > 状态约束 > 工具水位。多数团队问完第 1、2 问就有了答案；第 4 问只决定“能不能用好”，不改变“该用哪种”。同一个系统里通常混用：常规改动走滚动，高风险大变更走灰度，大促前夜的关键服务用蓝绿——按变更的风险等级选策略，而不是全公司一刀切。

拿两个场景把四问走一遍。**桶装水支付服务大促前夜换分账版本**：回滚要求秒级（第 1 问命中）→ 停机零容忍（第 2 问）→ 支付服务无状态（第 3 问）→ 有指标平台（第 4 问）→ 默认灰度（人群级，按 userId 哈希），若团队对版本路由的稳定性没把握则退而求其次选蓝绿。**MES 排程服务夜间换版本**：产线流量按人群切没有抓手（第 2 问的例外分支直接命中）→ 蓝绿整体切，配上附录预案的窗口与值守。同一套四问，两个场景收敛到不同答案，这就是决策树而不是对照表的意义。

#### 2.5.2 发布策略 × 数据库变更：联合矩阵

发布策略只解决了“代码怎么放”，事故复盘里一半的麻烦来自“代码怎么放”和“库怎么改”没对齐。把两个维度放进同一张表：

| 数据库变更 \ 发布策略 | 滚动 | 蓝绿 | 灰度 / 金丝雀 |
|---|---|---|---|
| 兼容性变更（加可空列、加表、加索引） | 直接发布，迁移脚本先于代码执行 | 直接发布 | 直接发布 |
| 破坏性变更（删列、改类型、收紧约束） | **禁止单步执行**：必须 expand-contract 三阶段（见 2.1.3），代码先全量、库后收缩 | 同左；且回切要求蓝绿双向读写兼容 | 同左；灰度期新旧版本**同时写库**，双向兼容是硬前提 |

三条纪律贯穿全表：**加法先改库、减法先改代码**——expand 的迁移脚本先跑，新代码上线时列已就位，contract 必须等不再读写旧结构的代码全量上线；**每一批库变更必须让上一个版本也能跑**——这是滚动与灰度共存期、蓝绿回切路的共同前提；**迁移脚本纳入流水线门禁**（2.1.1 表的部署前检查行），禁止人工在生产库手敲 DDL。对照示例：桶装水订单表加 `expect_time`（2.1.3 的三阶段示例）属于兼容性变更，三种策略随便挑；但如果当时一步到位 `ADD COLUMN ... NOT NULL` 再删旧列，就落进矩阵右下的禁止格——灰度期旧版本实例 INSERT 不带新列直接报错，5% 的用户下不了单，而此时回滚也救不了已经被收紧约束的表。

表格里“关键前提”一行也别当成摆设，每一项都要有验证动作：环境一致性 → 用同一镜像在预发起冒烟验证配置注入；DB 双向兼容 → 用旧版本镜像 + 新 schema 起冒烟实例（2.2 反例的检查单项）；N-1 兼容 → 混跑环境里新旧版本互跑关键用例；版本路由 → 灰度开始前先验证“同一用户始终落在同一版本”（用测试账号连打十次请求看路由结果）。前提没验证过的策略，出问题时的表现恰恰是前提失效：回滚切回去起不来、共存期数据互相读不懂。

最后补一句组合用法：策略不是互斥选项。常见组合是“**灰度 + 蓝绿**”——金丝雀实例单独成一组，观察达标后把金丝雀组扩到全量（等价于蓝绿的整体切换，但切换前已经有真实流量验证过）；“**滚动 + 开关**”也常见（代码滚动全量、功能由开关控制放量）。选型决策树给的是**默认值**，预案里完全可以写成“滚动部署 + 功能开关放量”这样的组合表达式——按变更的风险画像挑零件，而不是背一个标准答案。

### 2.6 特性开关与金丝雀的组合

2.3 配套要求里提过一句“功能开关（Feature Flag）与灰度正交，把发布风险与功能风险分离”，这里展开成完整的组合打法。核心是把两类风险分给两个机制：

| | 特性开关 | 金丝雀 / 灰度 |
|---|---|---|
| 灰度对象 | 功能 × 人群 | 实例 × 流量比例 |
| 管什么风险 | **功能风险**：功能逻辑对不对、该不该给用户 | **部署风险**：这批实例上的代码跑不跑得动 |
| 验证手段 | 业务指标（转化率、下单成功率）与人工验收 | 技术指标（错误率、P99、资源占用） |
| 回滚动作 | 关开关，秒级生效，不动代码 | 流量切回旧版本 |
| 典型失效模式 | 开关越积越多没人清 | 小流量暴露不了放大性问题 |

**组合做法**：新功能的代码藏在开关后面（开关 = 0%）随版本正常走灰度发布——此时金丝雀只验证“部署无害”；部署健康后，功能节奏完全由开关控制：内部员工 → 5% 用户 → 全量。此后功能出问题，关开关即回滚，不需要任何一次“重新发布”。桶装水商城的周期购改版就是这么走的：v2 代码先全量部署但开关关闭，金丝雀确认部署健康，再按开关对 5% 用户放量，观察订阅续费率两周后全量，最后删开关删分支收尾。人群圈定方式也顺手统一：开关按 userId 哈希分桶（上面片段），金丝雀按版本路由分桶，两套分桶用同一个哈希函数，用户在两条灰度线上的位置才能对得上——否则排查“某个用户为什么看到新功能”时要分别查两套规则。

```kotlin
// 片段：特性开关——代码已全量部署，功能按开关比例独立放量
import kotlin.math.abs
import java.time.LocalDate

object FeatureFlags {
    // percent: 0 = 全关，100 = 全量；cleanupDate = 预期清理日期；owner = 开关归谁还
    private data class Flag(val percent: Int, val cleanupDate: LocalDate, val owner: String)
    private val flags = mutableMapOf<String, Flag>()

    fun register(name: String, percent: Int, cleanupDate: LocalDate, owner: String) {
        flags[name] = Flag(percent, cleanupDate, owner)
    }

    fun isEnabled(name: String, userId: String): Boolean {
        val f = flags[name] ?: return false
        return abs(userId.hashCode()) % 100 < f.percent
    }
}
```

**清理纪律：开关也是技术债。** 开关是所有技术债里最容易“只借不还”的一种——它不像烂代码那样天天硌手，条件分支静悄悄增殖。❌ 反例：某系统周期购改版开关 `periodic_v2` 上线后一直没清，两年后代码里 47 处 `if (periodic_v2)`：新人不敢关（不知道关了会不会坏）、测试要跑两套组合（N 个开关的组合数指数爆炸）、代码评审时谁也说不清哪个分支还有人在用——最后专门立个项目清开关，花费超过当年功能本身的开发量。✅ 修正：开关创建即登记 `owner + 清理日期`（上面代码里那两个字段就是为此存在的），到期未清自动挂进技术债看板，双月清点一次；全量稳定一个版本周期后，“删开关删分支”是该功能收尾任务的一部分。债务的记账与偿还方法见[第四阶段-架构评审与技术债管理](../04-第四阶段/05-架构评审与技术债管理.md)——**半年不清理的开关和没还的贷款一样是真实负债**，利息是每次读代码、跑测试、做评审多付的那一份。

补一个类型谱系，避免“所有开关都必须清”被教条化：**发布开关**（本文讨论的，功能上线后必须清，寿命以周计）；**运维开关 / kill switch**（一键降级关闭某个重依赖功能，比如大促时关掉积分抵扣——它是降级预案的一部分，长期保留、也要登记 owner，但治理方式不是删，而是每季度在预发按一次确认“真要用时敢按”）；**实验开关**（A/B 实验用，实验结束即清，结论归档到实验平台）。三类都要登记，只有发布开关与实验开关有“到期必删”的硬约束——kill switch 的债不是分支增殖，而是“从没演练过”。开关的存放位置也有谱系：最简单是代码里的 if 分支（上面片段的做法，实现零依赖但开关值更新要发版，所以实际会把比例放进配置中心动态读取）；更彻底是放到网关/路由层（开关变成路由规则，代码里完全没有分支，清理时删规则即可）。位置越靠外，“清开关”的改动越小，这是低代码平台把配置灰度做成发布规则而不是代码分支的同一个思路。别忘了审计：谁在什么时候把哪个开关调到多少，要进操作日志（低代码平台的配置灰度同理，见主案例的发布审批留痕），开关改错人和改错比例，都是能直接造成事故的变更。

最后把整节串成一条线：一次变更从 commit 进入流水线（2.1），过七道门禁、带着 commit SHA 的镜像晋级各环境；到生产后按风险选策略放出来（2.2~2.4）——常规改动滚动、高风险变更灰度、关键变更蓝绿，功能节奏另有开关控制（2.6）；数据库变更永远向后兼容一步（2.1.3、2.5.2），保证任何一种策略的回滚路都通；全程有预案（见本节末尾附录）、有决策日志、有按版本对比的指标。发布能力成熟与否，不看用了多高级的策略，看四个数：**部署频率高不高、单次变更大不大、变更失败率低不低、恢复得快不快**——这四个数字背后，就是本节的全部机制。

### 附录：发布预案模板与 MES 填写示例

发布预案是发布策略的“作战卡”：写下来、评审过、演练过，事故时照着执行而不是临场发挥。10 行模板：

```markdown
## 发布预案：<变更名称>
- **发布范围**：服务/模块、目标版本（commit SHA）、涉及环境
- **发布窗口**：日期 + 时间段（避开业务高峰/产线生产时段）
- **发布策略**：滚动 / 蓝绿 / 灰度（放量阶梯与每档停留时长）
- **前置门禁**：必须完成的测试与审批（含 DB 迁移脚本兼容性评审）
- **特性开关**：随本次发布的功能开关及初始状态
- **观测指标**：成功率、P99、错误率、关键业务指标及各自阈值
- **回滚条件**：触发即回滚的量化条件（谁观测、持续多久、什么数值）
- **回滚动作**：具体操作、预计耗时、执行人
- **值守安排**：观察时段的值守人与升级路径（找不到人升级找谁）
- **沟通渠道**：发布通告、进展播报、事故同步分别在哪个群/频道
```

MES 场景填好的示例（产线白天不能停，发布窗口与策略怎么定）：

```markdown
## 发布预案：MES 工序排程服务 v2026.11（SHA 3f9c2ab）
- **发布范围**：mes-scheduler 服务，仅生产环境；边缘网关上报协议无变更（契约测试已通过）
- **发布窗口**：周六 22:00–24:00（晚班收工后、周日夜班开工前；白班/晚班生产时段禁止发布）
- **发布策略**：蓝绿——网关整体切流，蓝环境热备保留 24 小时后销毁（产线流量无法按人群灰度）
- **前置门禁**：契约测试通过；DB 迁移为纯加列（Expand，见 2.1.3）；设备科与生产调度科会签
- **特性开关**：新排程算法 `scheduler_v2` 初始 0%（代码先上，算法观察一周后按车间放量）
- **观测指标**：报工采集成功率 ≥ 99.9%、排程计算 P99 ≤ 2s、工单下发延迟 ≤ 30s
- **回滚条件**：采集成功率 < 99% 持续 3 分钟，或任一产线报工中断——值守运维直接执行，不请示
- **回滚动作**：网关一键切回蓝（< 10s，已演练）；切回后按 2.1.3 三阶段确认旧版本可读写新列
- **值守安排**：周六 22:00–24:00 平台组 2 人 + MES 业务 1 人驻群；升级路径：值班运维 → 架构师 → CTO
- **沟通渠道**：#mes-release 群进展播报；切流前 15 分钟在车间看板与班组长群通告
```

两处细节最能体现“预案”和“文档”的区别：其一，回滚条件带数值、带持续时长、带“不请示”授权——事故现场没有时间讨论该不该回滚；其二，蓝环境保留 24 小时而不是切流成功立即销毁——周日夜班开工后若暴露问题，还有一条不必重启产线的退路。把这两条抄进任何系统的预案，都成立。

预案的维护节奏也和普通文档不同：每次发布前 10 分钟过一遍（变更范围、窗口、值守人是否成立）；每次实际回滚之后修订一次（把演练值换成真实值）；每季度挑一个真实发布做一次“照预案执行”的演练。预案过期的信号很明确：上面写的值守人已经转岗、指标阈值和当前系统容量差了一个量级——这两个信号一出现就该重写，而不是等下次事故时发现“预案里的人已经不在这家公司了”。
