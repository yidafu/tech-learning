# 技术工具档案：网关与服务网格

> [返回：软件架构学习大纲](../软件架构学习大纲.md)

> 本分册是“技术工具档案”系列的**网关与服务网格篇**（系列前作：[消息队列](../03-第三阶段/07-技术工具档案-消息队列.md)、[缓存](../03-第三阶段/08-技术工具档案-缓存.md)、[协调与注册中心](../03-第三阶段/09-技术工具档案-协调与注册中心.md)）。按流量方向分两大部分：**第一部分讲南北向流量（客户端↔集群之间）的四个 API 网关**——Nginx、Envoy、Kong、APISIX；**第二部分讲东西向流量（服务↔服务之间）的服务网格**——Istio、Linkerd 两位主角，eBPF/Cilium 一笔带过。每个工具固定四段式——**概况**（出身档案：作者/公司、年份与背景、归属、一句话定位）、**解决了什么问题**（出现前的痛，用场景故事讲）、**如何解决**（核心机制：进程/线程模型、配置模型、插件或过滤器架构，讲清设计动机）、**对比同类**（逐维度对比 + 何时选它）。贯穿全篇的心智模型只有一组词：**控制面与数据面分离**——“配置怎么下发、路由怎么热更新”比单机 QPS 更能区分这几代网关。主线可运行示例 `MiniGatewayChain.kt`（Kotlin 单文件、无第三方依赖）模拟“路由匹配 + 插件责任链短路 + 配置热生效”，与第五阶段 [01-工程化与运维视角.md](01-工程化与运维视角.md) 的工程化视角衔接；场景取材见 [示例项目场景/00-导览.md](../示例项目场景/00-导览.md)（API 网关、多租户 SaaS 控制平面、桶装水商城主线、物联网数据采集）。

## 0. 先看全景：南北向、东西向，与“控制面/数据面”

数据中心的经典拓扑图里，机架顶部的交换机画在图纸上下两端，流量从“北面”进来、穿过服务器、从“南面”出去；而机架**之间**的横向流量是平的，像地图上的东西方向。于是有了这对行话：

- **南北向流量**：客户端/合作伙伴 → 集群的入口流量。特征：身份是**外面的**（用户、第三方应用）、入口收敛（一扇城门）、失败半径极大（城门失守则全站无法进入）。
- **东西向流量**：集群内部服务↔服务的调用。特征：身份是**里面的**（服务自己）、数量比南北向大一个量级、拓扑随部署与弹性伸缩随时变化。

管这两类流量的工具形态相似（都是“代理”），但**该管的事完全不同**——这是本篇结尾 §9 的主题，先按下不表。全篇的时间线：

| 年份 | 事件 | 解决的当务之急 |
| --- | --- | --- |
| 2002~2004 | Igor Sysoev 为俄罗斯门户 Rambler 写出 Nginx（2004-10 首次公开发布） | C10K：单机承载一万并发连接 |
| 2011 | 章亦春（agentzh）开源 OpenResty（Nginx + LuaJIT 打包发行） | 让“改配置要 reload”的 Nginx 得以运行可编程逻辑 |
| 2015 | Mashape 开源 Kong（基于 OpenResty） | API 经济：认证/限流/计量做成插件 |
| 2016 | Lyft 开源 Envoy（9 月）；Buoyant 开源 Linkerd v1（业界第一个服务网格，“service mesh”一词由此普及） | 微服务的动态配置与原生观测；治理从业务库下沉 |
| 2017-05 | Google/IBM/Lyft 联合发布 Istio 0.1（数据面用 Envoy） | 服务间流量、安全、策略一站式下沉 |
| 2017-12 | Buoyant 另起 Conduit（Rust 数据面），后并回成为 Linkerd 2.0 | 给“太重”的 JVM 网格做减法 |
| 2018 | Istio 1.0（7 月）；Envoy 从 CNCF 毕业（11 月，继 Kubernetes、Prometheus 之后第三个） | 网格走向生产；数据面标准化 |
| 2019 | 支流科技开源 APISIX（6 月），10 月进入 Apache 孵化器 | 云原生动态网关：etcd 驱动全热更新 |
| 2020 | Istio 1.5（3 月）把控制面五组件合并为 istiod；APISIX 7 月毕业成 Apache 顶级项目 | 给控制面做减法；国产网关治理成熟 |
| 2021 | Linkerd 7 月从 CNCF 毕业（第一个毕业的服务网格） | 极简网格路线得到验证 |
| 2022~2023 | Istio 加入 CNCF（2022-09 孵化、2023-07 毕业）；Cilium（eBPF）2023-10 从 CNCF 毕业 | 网格整体成熟；无 sidecar 路线登场 |

读这张表的正确方法：**两代减法**。第一代是“配置怎么从文件变成数据”（OpenResty 的 Lua → Kong 的 Admin API → Envoy 的 xDS → APISIX 的 etcd watch）；第二代是“控制面怎么从众多组件收敛为一个整体”（Istio 五组件 → istiod；每 Pod sidecar → 节点级/内核级）。所谓**控制面（control plane）**是“决定流量怎么走的大脑”：存配置、做翻译、发证书；**数据面（data plane）**是“真正扛流量的手”：匹配路由、执行插件链、转发字节。这对词是 [../02-第二阶段/06-平台化架构-BFF与中台.md](../02-第二阶段/06-平台化架构-BFF与中台.md) 里“策略由控制平面下发、数据面执行”心智模型的工具版，也是本篇示例 `MiniGatewayChain.kt` 要演示的唯一一件事。

## 第一部分：南北向流量——API 网关四工具

网关是流量的城门：TLS 终止、对外认证、限流配额、路由分发。它**该管什么、不该管什么**（不聚合业务、不长业务逻辑），[../02-第二阶段/06-平台化架构-BFF与中台.md](../02-第二阶段/06-平台化架构-BFF与中台.md) 的“网关 vs BFF 职责边界”已给出判据，本篇专心讲工具本身。

### 1. Nginx：C10K 时代的事件驱动之王

#### 1.1 概况：出身档案

- **作者**：Igor Sysoev（俄罗斯）。2002 年起为俄罗斯门户网站 **Rambler**（rambler.ru）开发——门户的并发连接数远超当时主流 Web 服务器的承受能力；**2004 年 10 月首次公开发布**，BSD-2 许可，C 语言。
- **归属**：2011 年 Sysoev 联合创办 Nginx Inc.（商业版 Nginx Plus 提供管理 API 等增强）；**2019 年 3 月被 F5 以约 6.7 亿美元收购**。开源版至今仍是全球部署量最大的入口服务器之一。
- **生态延伸**：**OpenResty**（2011 年，章亦春/agentzh）把 LuaJIT 与 lua-nginx-module 打包成 Nginx 发行版，让 Nginx 从“配置驱动的代理”长成“可编程平台”——后来出场的 Kong 与 APISIX 全都站在它肩上。
- **一句话定位**：**事件驱动的高性能 Web 服务器 / 反向代理**。

#### 1.2 解决了什么问题：出现前的痛

痛点叫 **C10K**（得名于 1999 年 Dan Kegel 的著名文章《The C10K problem》）：一台服务器同时支撑一万个并发连接。当时的绝对主流 Apache 默认 **prefork MPM**——每个连接占一个进程（worker MPM 也只是换成每连接一线程），“连接↔进程/线程”绑死的模型把并发上限焊死在内存与上下文切换上：一万个连接就是一万个进程，光是内核调度开销就能把 CPU 耗尽，更不用说内存。

场景故事：把时间线拨回那个年代——桶装水商城的“前身”图片站用 Apache 支撑商品图与活动页，促销日并发连接升至三四千时，8GB 内存见底、CPU 大半耗在上下文切换，应用进程反而拿不到 CPU；运维的唯一手段是加机器。换 Nginx 之后：单 worker 稳定承载数万连接，每连接内存开销以 KB 计，同样的机器多承载了一个数量级。另一个附带收益：Nginx 挡在应用前面做反向代理后，应用宕机时返回的是网关的 502/503 页面，而不是让用户的 TCP 连接连握手都无法完成——**入口的可靠性第一次和应用解耦**。

#### 1.3 如何解决：核心机制拆解

**① master + 多 worker 进程模型**。master 进程不处理请求，只负责读配置、绑定端口、监控并拉起 worker；worker 数通常等于 CPU 核数，各自独立 accept 连接并处理（惊群问题用 accept_mutex/内核 SO_REUSEPORT 处理）。设计动机有两层：**无锁**——worker 之间不共享内存、无需加锁，事件循环里没有等待；**故障隔离**——一个 worker 崩溃只影响它名下的连接，master 立即补一个新 worker，进程边界成了天然的舱壁。

**② epoll/kqueue 事件驱动 + 非阻塞 IO**。每个 worker 是一个单线程事件循环：把所有连接的 socket 注册到 epoll（Linux 2.6）/kqueue（BSD）上，谁可读可写就处理谁，IO 全程非阻塞。这从根本上推翻了“每连接一个执行流”的假设——**并发数不再与执行流数量绑定**，一个 worker 管理数万连接是常态。这是 Nginx 对 C10K 的正面回答。

**③ 配置模型：声明式文件 + reload**。`nginx.conf` 按 http → server → location 三层组织，路由匹配用前缀 + 正则。改配置后 `nginx -s reload`：master 重读配置、平滑拉起新 worker、旧 worker 处理完存量连接后退出——**配置热更新的雏形**。但要看清它的粒度：这是“整个 worker 世代更替”，且没有任何管理 API，改路由必须登录机器改文件。这个“文件 + reload”的配置模型，正是后来 Envoy 的 xDS 流、Kong/APISIX 的 Admin API 要革命的对象——记住这个伏笔。

**④ 附带的整套组件**：反向代理与负载均衡（轮询/加权/最少连接/ip_hash）、静态文件、缓存、TLS 终止，让它成为“入口”的同义词。

**反例与修正**：

- 反例一：在 Nginx 上跑重的动态逻辑（早期确有团队这样做）。worker 的事件循环一旦被阻塞调用卡住，它名下**所有**连接一起卡死——事件驱动模型的死穴。修正：动态逻辑放应用服务，Nginx 只做代理；用 OpenResty 也必须严守“只用非阻塞 API”的纪律。
- 反例二：强行把 Nginx 当作 API 网关使用。路由变更 = 修改几千行 conf + reload，配置评审形同虚设，无人再敢变更。修正：路由/插件高频变更的 API 治理场景，换 Kong/APISIX（管理 API + 热更新）或 Envoy（xDS），Nginx 退回“静态入口、TLS、负载均衡”的本位——四层七层的基准件。

#### 1.4 对比同类：何时选它

| 维度 | Nginx | Apache httpd |
| --- | --- | --- |
| 并发模型 | master + worker，每 worker 单线程 epoll | prefork（每连接一进程）/ worker / event MPM（2.4 起有事件模型，但生态默认与历史包袱仍在） |
| 每连接开销 | KB 级 | 进程/线程级（event MPM 有改善） |
| 配置 | 声明式 conf + reload | 声明式 conf + reload |
| 动态性 | 无管理 API（Plus 商业版补齐一部分） | 同样没有 |
| 强项 | 高并发代理/静态资源/内存效率 | 动态模块生态、`.htaccess` 目录级配置（同时也是性能与安全负担） |

**何时选 Nginx**：入口的静态资源、TLS 卸载、四层/七层负载均衡——它仍是这类需求的默认答案；需要在其上做 API 治理时，选长在它之上的 OpenResty 系（Kong/APISIX），而不是继续堆砌 conf。

### 2. Envoy：为云原生而生的现代数据面

#### 2.1 概况：出身档案

- **作者**：Matt Klein（曾在 AWS/Twitter 任职，2015 年加入 **Lyft**），在 Lyft 内部孵化，**2016 年 9 月开源**；C++ 编写。
- **背景**：Lyft 正从单体拆微服务，语言栈混杂（PHP/Python 等），网络功能散落在各语言的库里。
- **归属**：CNCF——2017 年加入，**2018 年 11 月毕业，是继 Kubernetes、Prometheus 之后第三个从 CNCF 毕业的项目**。
- **一句话定位**：**为云原生环境设计的现代数据面代理**——把网络功能做成“进程外”统一能力的数据面底座，也是 Istio 的数据面。

#### 2.2 解决了什么问题：出现前的痛

**痛点一：库模式的升级地狱**（与 [../02-第二阶段/03-微服务架构.md](../02-第二阶段/03-微服务架构.md) 的服务间通信治理一节同源）。微服务的重试、超时、熔断、客户端负载均衡，最早都做成各语言的库：Java 有自己的生态、Go 有自己的、Python 又一套。后果：同一策略三个语言三份实现、行为不一致（超时语义、重试风暴的边界条件都不一样）；库升级要改业务依赖、全量构建、全量重启——**平台能力被焊死在业务发版节奏里**。

**痛点二：传统代理跟不上动态环境**。Nginx/HAProxy 的配置是静态文件，改路由要 reload；没有服务发现集成（上游实例增删靠人改配置）；可观测靠访问日志外挂，没有指标与链路的原生输出。

场景故事：Lyft 拆出几十个服务后，一次“把下游超时从 1s 调到 500ms”的策略变更，要跨 3 个语言栈改库、发版 40 个服务、协调两周窗口；而服务发现还停留在每周人工更新配置文件的年代。Matt Klein 的答案：这些能力不应驻留在应用里，也不应靠文件分发——应该有一个**独立的、所有服务共用的代理进程**，配置用**API 动态下发**。

#### 2.3 如何解决：核心机制拆解

**① xDS 动态配置 API 族——“配置热更新不用重启”的根基**。Envoy 把配置拆成五类资源，每类一个 Discovery Service：

| API | 管 | 类比 Nginx 的概念 |
| --- | --- | --- |
| LDS（Listener） | 监听器：开哪些端口、什么协议 | `server { listen ... }` |
| RDS（Route） | 路由规则：什么请求去哪 | `location` 匹配 |
| CDS（Cluster） | 集群定义：上游有哪些逻辑分组 | `upstream` 块 |
| EDS（Endpoint） | 集群成员：具体实例 IP/端口列表 | `server` 条目（自动版） |
| SDS（Secret） | 证书与密钥 | ssl_certificate（自动轮转版） |

控制面通过 gRPC 双向流订阅推送，Envoy 用版本号应答（ACK/NACK）。设计动机：把配置从“文件”变成“**流**”——增量推送、不重启进程、不中断长连接即可更换路由/证书/上游实例列表。**xDS 后来成为数据面控制协议的事实标准**，这是 Envoy 对行业最大的贡献：控制面（Istio、Gloo、Kuma、自研）与数据面（Envoy）可以来自不同团队。bootstrap 静态配置只写一件事：控制面在哪。

**② 过滤器链架构**。三层可编程：网络过滤器（TCP 层：代理、限速、TLS 检测）→ HTTP 连接管理器 → HTTP 过滤器（路由、重试、熔断、故障注入、外部鉴权 ext_authz……）。这正是 [../02-第二阶段/05-其他重要架构风格.md](../02-第二阶段/05-其他重要架构风格.md) 4.6 微内核那句教义的代理版：**内核（Envoy）提供机制（过滤器链），配置提供策略（插什么、什么顺序）**。

**③ 原生可观测三件套**：指标（`/stats` 端点直接输出 Prometheus 格式）、访问日志（文件或 gRPC 流式上报）、分布式追踪（原生传播 b3/traceparent 头并对接上报后端）。设计哲学：**可观测是数据面的第一公民**，不是事后外挂——这也是它作为“服务网格数据面”的资格证（观测能力见 [02-可观测性-日志指标与链路追踪.md](02-可观测性-日志指标与链路追踪.md)）。

**④ 非阻塞 IO + worker 线程模型**：事件驱动与 Nginx 同宗，但用多线程共享内存（连接池、路由表进程内共享），线程数可独立于核数配置。

**反例与修正**：反例——“Envoy 很强所以我们自研控制面”。从零对接 xDS 要处理状态机、版本协商、防抖，小团队极易做出一个半成品控制面。修正：用现成控制面（Istio、Gloo、Kuma）或直接选控制面内置的 Kong/APISIX；Envoy 的正确定位是“数据面专家”，控制面交给其他组件。

#### 2.4 对比同类：何时选它

| 维度 | Envoy | Nginx | HAProxy |
| --- | --- | --- | --- |
| 定位 | 云原生数据面（南北向/东西向通吃） | 入口 Web 服务器/反代 | 老牌四层/七层负载均衡 |
| 配置模型 | xDS 流式订阅，全动态，不重启 | 文件 + reload | 文件 + reload（也有 runtime API 但有限） |
| 可观测 | 指标/日志/链路原生三件套 | 日志为主，指标靠模块/外挂 | 统计页面 + 日志 |
| 扩展 | 过滤器 + Lua + Wasm | 模块编译进二进制；OpenResty 生态 | Lua（有限） |
| 服务发现 | EDS 原生集成 | 需外部脚本/商业版 | 需外部脚本 |

**何时选 Envoy**：需要 sidecar 数据面（Istio 家族）、要自建带动态配置与原生观测的代理层、或想要“数据面标准化 + 控制面自选”的架构；纯静态入口场景，Nginx 更轻。

### 3. Kong：插件式 API 网关的开创者

#### 3.1 概况：出身档案

- **出身**：**Mashape**——一家做 API 市场起家的公司（把第三方 API 汇聚到一个市场出售调用）。做市场必然要替入驻 API 做“门前治理”，2015 年把这套治理层以 **Kong** 之名开源；**2017 年 10 月公司整体更名为 Kong Inc.**（现 Kong），同时发布商业版 Kong Enterprise。名称由来：Mash-**ape** → “King” Kong（金刚）。
- **底座**：**OpenResty**（Nginx + LuaJIT）——Kong 不是从零写的代理，而是站在 Nginx 的事件驱动内核上，用 Lua 长出了一个 API 治理层。
- **商业化版图**：开源网关（Apache-2.0，部分高级插件与控制平面在商业版）+ Kong Konnect（SaaS 控制平面）+ Kuma（2019 年开源的轻量服务网格，数据面用 Envoy——与本篇第二部分遥相呼应）+ Insomnia（API 调试工具）。
- **一句话定位**：**插件式开源 API 网关**——核心极小、一切功能皆插件，围绕 API 全生命周期治理。

#### 3.2 解决了什么问题：出现前的痛

2014~2015 年的 **API 经济**：越来越多公司把能力包装成 API 对外开放（地图、支付、翻译……）。开放 API 的“门前需求”高度一致：API Key/JWT 认证、按调用方限流、调用量计量与计费、监控、CORS——但当时每家公司都把这些写在自己的应用代码里，重复实现、水平参差，而且**一旦换语言就重来**。Mashape 自己运营 API 市场，这个痛点每天咬它一口。

若用 Nginx 直接承担：路由即 conf、逻辑即 Lua 脚本、没有管理 API、没有插件生命周期管理——运维一个“API 平台”像运维大量祖传脚本。

场景故事：桶装水商城做开放平台，给便利店和企业客户开放“周期购下单 API”：每个调用方一个 API Key、按调用方独立限流（便利店 A 每分钟 60 次、企业 B 每分钟 600 次）、月底按调用量出账单。这些能力如果写进订单服务，业务代码里会混杂大量带“平台味”的 if 判断；装进网关插件，业务服务一行不改。

#### 3.3 如何解决：核心机制拆解

**① 插件式架构：一切功能皆插件**。核心只做路由、负载均衡、连接管理；认证（key-auth/jwt/hmac）、限流（rate-limiting，本地/集群/Redis 三档）、CORS、请求改写、prometheus 指标……全是插件。插件是 Lua 模块，声明生命周期钩子（access、header_filter、body_filter、log 阶段），挂载在 OpenResty 的请求处理阶段上——本质是一条**进程内责任链**（即本篇示例 `MiniGatewayChain.kt` 的形态）。插件可以按**全局/服务/路由/消费者（consumer）**四级粒度启用——“consumer”（API 调用方）是一等公民，这是 API 网关区别于通用代理的分水岭：通用代理问“这个请求去哪”，API 网关还问“**是谁在调、配额多少**”。

**② 配置模型：DB 与 DB-less 两种部署模式**。

- **DB 模式**：路由、服务、消费者、插件配置存 PostgreSQL/MySQL，网关提供 RESTful **Admin API** 读写，变更对数据面毫秒级生效（数据面内存里有配置缓存，只在变更链路上访问数据库）。API 平台形态的默认选择——消费者的增删改是运营日常。
- **DB-less 模式**：整份配置是一份声明式 YAML，整体下发整体替换，网关不连数据库。动机：GitOps（配置进 Git、走评审、流水线发布，呼应 [03-部署与发布策略-CICD与灰度.md](03-部署与发布策略-CICD与灰度.md) 的“配置也是会出事故的变更”）、少一个有状态组件；代价是变更是“换整份快照”，不适合消费者高频增删的场景。

**反例与修正**：DB 模式的关系库是配置链路的单点——DB 抖动时网关扩容启动（要全量拉配置）与变更都被牵连，而且多了一套数据库的运维。修正：数据面读的是内存缓存、数据库只服务变更链路，因此把 DB 当“配置的 Git”对待（备份、延迟监控）；或者直接采用 DB-less + 声明式流水线，把状态交给 Git。

#### 3.4 对比同类：何时选它

与同门的 APISIX 逐维度对比放在 §5 总表，这里给定位级判据。**何时选 Kong**：以 REST API 对外/对内开放为业务形态（开放平台、API 市场、合作伙伴集成），需要消费者管理、计量计费、成熟插件市场与企业支持；团队接受 OpenResty 技术栈。**何时不选**：只是给 Web 入口做个 TLS + 负载均衡——那是 Nginx 的职责，用 Kong 无异于杀鸡用牛刀。

### 4. APISIX：etcd 驱动的国产动态网关

#### 4.1 概况：出身档案

- **出身**：**支流科技**（ZhiLiu Tech），**2019 年 6 月 6 日开源**；**2019 年 10 月进入 Apache 孵化器，2020 年 7 月 15 日毕业成为 Apache 顶级项目**——从孵化到毕业约 9 个月，是 Apache 历史上最快的毕业项目之一。
- **底座**：与 Kong 同宗——OpenResty（Nginx + LuaJIT）；但**控制面存储换成了 etcd**。
- **归属**：Apache 软件基金会（Apache-2.0，基金会治理）；商业化由 APISIX 核心团队创办的 API7 承接。国产开源代表作（Apache 顶级项目里的中国项目名片之一）。
- **一句话定位**：**云原生动态 API 网关**——路由、上游、插件全部实时热更新，主打动态性与性能。

#### 4.2 解决了什么问题：出现前的痛

APISIX 问世时，Kong 已经很有名。它对标的是两个具体痛点：

**痛点一：配置存储与分发链路**。Kong DB 模式依赖关系库存配置、网关节点轮询/事件同步——变更生效有延迟、数据库是必选的重组件（DB-less 又牺牲了细粒度动态性）。而云原生时代的期望是：配置即数据、推送应达毫秒级、控制面自身就应是高可用集群。

**痛点二：路由匹配的性能与表达力**。radixtree（基数树）路由让 host + path + method + 优先级的多维匹配做到 O(路径长度)，官方基准下单核 QPS 领先同栈方案——对“网关扛在业务最前面”的场景，路由匹配就是热路径。

场景故事：物联网平台（[示例项目场景/00-导览.md](../示例项目场景/00-导览.md) 的物联网画像）接入几十类设备，每类设备一个主题前缀、一套插件组合（协议转换、限流、黑名单），设备类型还在持续新增——意味着**路由和插件每周都在增删**。用“改配置 + reload”的网关，每次变更都是一次心跳加速；用 etcd watch 推送的网关，变更就是一次 API 调用。

#### 4.3 如何解决：核心机制拆解

**① etcd 作为控制面存储——全热更新的地基**。Admin API 把路由/上游/插件配置写进 etcd；所有网关节点 watch etcd 的配置目录，任何增删改**即时推送到全部节点**，路由与插件全部毫秒级生效、无需 reload。这里和 [../03-第三阶段/09-技术工具档案-协调与注册中心.md](../03-第三阶段/09-技术工具档案-协调与注册中心.md) 的 etcd 档案正好接上：etcd 的**watch 机制**（一条 watch 流、事件续传）提供“订阅变更”，**全局单调递增的 revision** 提供版本与一致性——APISIX 只是把这两个原语用在了“网关配置分发”上。附带收益：etcd 天然三副本/五副本集群，控制面存储自带高可用，不用再给网关配一个数据库。

**② radixtree 路由**：把 host、path 前缀、方法、优先级合并进基数树匹配，长前缀共享路径节点——既快，又让“一条 `/orders/express` 高优先级规则压过 `/orders`”这类表达成为配置而不用重启（本篇示例的路由优先级就是它的极简版）。

**③ 插件生态的三条路径**：Lua 插件（同 Kong 的主路径）+ **ext-plugin**（plugin-runner 外置进程，用 Go/Java/Python 写插件跑在网关进程外，通过本地 RPC 通信——修正“必须会 Lua 才能写插件”的门槛）+ Wasm 支持。

**④ 全热更新**：伏笔回收——Nginx 时代“改路由要 reload、换证书要 reload”，APISIX 的答案是“**没有一种变更需要 reload**”：路由、上游、插件、证书全部 etcd 推送生效。

**反例与修正**：etcd 成为网关的命门——**etcd 抖动 = 配置不同步/新节点起不来**。反例：有团队索性把 etcd 当业务库使用（写入大对象、高频写入），etcd 的写延迟与磁盘压力骤增，网关配置推送随之波动。修正：etcd 只存“小而关键”的配置数据（这正是 etcd 档案里讲的容量纪律）、独立小集群部署、把 etcd 的延迟与领导切换纳入网关的告警面——**管好了 etcd 才管得好 APISIX**。

#### 4.4 对比同类：何时选它

| 维度 | APISIX | Kong |
| --- | --- | --- |
| 配置存储 | etcd（watch 推送） | PostgreSQL/MySQL（DB）或声明式 YAML（DB-less） |
| 生效机制 | 全热更新，无 reload | Admin API 生效（DB）/整体替换（DB-less） |
| 路由引擎 | radixtree（多维 + 优先级） | 传统匹配（后续版本也引入了表达式路由） |
| 插件语言 | Lua + ext-plugin（Go/Java/Python）+ Wasm | Lua（商业版另有插件） |
| 治理归属 | Apache 基金会（社区驱动） | Kong Inc. 主导 |
| 商业化 | API7 | Kong Enterprise / Konnect |

**何时选 APISIX**：路由与插件变更频繁的云原生环境、对“配置即数据 + watch 推送”有执念、已有 etcd 运维能力、看重中文社区与国产生态。**何时选 Kong**：更需要成熟的消费者体系、企业插件与企业支持。两者同为 OpenResty 系，迁移成本主要在插件与配置模型，不在底座。

## 第二部分：东西向流量——服务网格

南北向的城门修好了，城里的问题才显出来：几十上百个服务互相调用，调用方是谁、是否加密、超时重试由谁管、灰度流量切向哪里——这些**东西向治理**问题，第一代的答案写在每个语言的库里（Envoy 一节的痛点一），第二代的答案就是**服务网格（service mesh）**：把治理能力从业务进程里抽出，移入与业务容器同 Pod 的代理进程（**sidecar**，边车），由控制面统一指挥。数据面 = Envoy（Istio）或 linkerd2-proxy（Linkerd）；控制面 = istiod / linkerd 控制器。**控制面/数据面分离在东西向的翻版**——概念与 [../02-第二阶段/03-微服务架构.md](../02-第二阶段/03-微服务架构.md) 的“库模式 vs 边车模式”一一对应，这里只讲落地工具。

### 6. Istio：功能最全也最重的重量级冠军

#### 6.1 概况：出身档案

- **出身**：**Google、IBM、Lyft 三家联合**，2017 年 5 月发布 0.1；数据面直接采用 Lyft 刚开源一年的 Envoy——“Google/IBM 出控制面经验，Lyft 出数据面”的联姻。
- **里程碑**：2018 年 7 月 1.0 GA；**2020 年 3 月 1.5 把控制面多组件合并为单进程 istiod**；2022 年 9 月加入 CNCF（孵化），2023 年 7 月从 CNCF 毕业。
- **一句话定位**：**功能最全的服务网格**——流量管理、安全（mTLS/授权策略）、可观测一站式，Kubernetes 时代的“整套网格组件”。

#### 6.2 解决了什么问题：出现前的痛

**痛点一：治理能力的多语言重复**。Envoy 一节讲过的库模式之痛，在容器编排时代被放大：几十个服务、三五个语言栈，每个栈一套熔断/重试/追踪库，平台团队想统一调整一项超时策略，就等于一次全站发版。

**痛点二：内网明文——“内网可信”假设失效**。容器环境里，一台被攻破的 Pod 面对的是同网段内明文暴露的服务间调用：抓包即拿到调用内容，伪装即可横向移动。这正是 [04-安全架构-认证授权与零信任.md](04-安全架构-认证授权与零信任.md) 3.5 节零信任要推倒的假设——服务之间也要**身份 + 加密**，而给每个服务手工配证书、轮转证书、下发 ACL 是不现实的人力黑洞。

**痛点三：灰度发布的流量切分缺执行层**。[03-部署与发布策略-CICD与灰度.md](03-部署与发布策略-CICD与灰度.md) 2.3.3 的自动放量控制器（CanaryController）决定“切多少流量给新版本”，但“把 5% 的请求真的路由到 v2”需要有人执行——网格就是那个执行层。

场景故事：桶装水商城微服务化后 20 个服务（Kotlin + Go + Python），安全审计要求“全链路服务间加密 + 按比例灰度”。给三个语言栈分别接 TLS 库、证书管理、流量染色？业务团队必然强烈抵触。引入 Istio 后：业务代码零改动，mTLS 与切流都是平台配置。

#### 6.3 如何解决：核心机制拆解

**① Sidecar 注入：治理下沉的物理实现**。Kubernetes 的 mutating webhook 检查 namespace 标签，自动向 Pod 注入 Envoy 容器 + init 容器；init 容器把 Pod 的 iptables 改掉，出入流量**透明劫持**给 Envoy——业务进程以为自己在直连，实际全部经过边车。这就是“下沉”两个字落到操作系统层面的样子：不改代码、不换 SDK，劫持即可见、即可管。

**② 架构演化：从“五角大楼”到 istiod**。早期控制面有五个独立组件：Pilot（流量管理，把规则翻译成 xDS 下发）、Citadel（CA，签发证书）、Galley（配置校验）、Sidecar Injector（注入）、Mixer（遥测与策略检查）——社区戏称这套多组件架构为 Pentagon（五角大楼）。痛点非常现实：五套部署、五份依赖、五处排障，升级像搬家。**2020 年 3 月 1.5 版本合并为单二进制 istiod**，同时弃用 Mixer（遥测改由 Envoy 直接产生上报，随后版本彻底移除）。这是“给控制面做减法”的教科书案例——功能不收，组件收敛。

**③ mTLS 零信任**。服务身份用 SPIFFE URI（`spiffe://cluster.local/ns/<namespace>/sa/<serviceaccount>`）标识；istiod 是根 CA，为每个服务身份自动签发与轮转证书；PeerAuthentication 控制是否加密，AuthorizationPolicy 声明“谁能调谁”。零信任的“身份为王”（见 [04-安全架构-认证授权与零信任.md](04-安全架构-认证授权与零信任.md)）从原则变成两条 YAML。

**④ 流量切分与灰度**。VirtualService 声明路由（按权重切流、按 header/mirror 分流），DestinationRule 定义版本 subsets 与连接池/异常点检测。与 [03-部署与发布策略-CICD与灰度.md](03-部署与发布策略-CICD与灰度.md) 的联动：放量控制器读 [02-可观测性-日志指标与链路追踪.md](02-可观测性-日志指标与链路追踪.md) 的按版本指标 → 达标就改 VirtualService 权重 → istiod 翻译成 xDS → Envoy 执行。“决策在控制器、执行在网格”——控制面/数据面分离在灰度链路上的完整闭环（该控制器示例此处不重写）。

**⑤ “功能全但重”：复杂度使团队望而却步的历程与官方瘦身**。CRD 众多（VirtualService/DestinationRule/PeerAuthentication/AuthorizationPolicy……）、版本升级常遇典型陷阱、每 Pod 一个 Envoy 的资源开销（内存几十 MB 起）与升级摩擦（sidecar 升级要滚动全部业务 Pod）。社区出现大量“引入 Istio 后又退出”的案例——不是它不好，而是**它的功能全 = 它的认知与运维成本高**。官方的回应就是持续瘦身：组件合并（istiod）、默认安装精简、2022 年公布的 ambient 模式（节点级 ztunnel 代理 + 按需 waypoint，去掉每 Pod sidecar）。选型启示在下一段。

#### 6.4 对比同类：Istio vs Linkerd 主表

| 维度 | Istio | Linkerd |
| --- | --- | --- |
| 出身 | 2017-05，Google/IBM/Lyft | 2016，Buoyant（Twitter Finagle 系）；2.0 系 2017-12 起 |
| 数据面 | Envoy（C++，通用代理） | linkerd2-proxy（Rust，专用微代理） |
| 功能广度 | 整套组件：流量管理/mTLS/授权/策略/多集群 | 最小集：mTLS/可靠性/黄金指标 |
| 资源开销 | 高（sidecar + 控制面都重） | 低（proxy 内存 MB 级） |
| 学习曲线 | 陡（CRD 家族庞大） | 缓（默认值即生产可用） |
| 扩展性 | Envoy 过滤器/Wasm，扩展点丰富 | 代理基本不可插拔（可预测性优先） |
| 治理归属 | CNCF 毕业（2023-07） | CNCF 毕业（2021-07，第一个毕业的网格） |
| 适合谁 | 大规模多团队、强合规、细粒度流量需求 | 小团队、K8s 原生、要快、稳、简 |

**何时选 Istio**：服务规模大、需要细粒度流量切分与授权策略、有强制加密合规、有专职平台团队消化它的复杂度。

### 7. Linkerd：极简哲学的轻量级冠军

#### 7.1 概况：出身档案

- **出身**：**Buoyant** 公司，创始人 William Morgan、Oliver Gould 都出自 **Twitter 的 Finagle 系**（Finagle 正是“第一代服务网格”——装在进程里的那代）。**2016 年开源 Linkerd，是业界第一个服务网格，“service mesh”这个词就是 Linkerd 团队普及的**；2017 年 1 月进入 CNCF（首批项目之一）。
- **v1 的失败教训**：v1 用 Scala 写在 JVM 上（Finagle 内核），志在做“通用 RPC 路由器”。**2017 年 12 月另起 Conduit 项目**：数据面用 Rust 从零写了专用微代理 linkerd2-proxy，控制面用 Go；2018 年并回主线成为 **Linkerd 2.0**。**2021 年 7 月 28 日从 CNCF 毕业——第一个毕业的服务网格**。
- **一句话定位**：**最轻、最简的服务网格**——只做最必要的事。

#### 7.2 解决了什么问题：出现前的痛

v1 的失败本身就是最好的教材：JVM sidecar 每实例几百 MB 内存、启动要几十秒、GC 停顿抖动延迟——**用“通用平台的重量”换“什么都想做”，结果连最基本的服务网格场景都负担不起**；同时它与非 JVM 生态的互操作始终存在障碍。修正：不要通用，要专用——**网格场景真正需要的东西其实很少**：mTLS、重试/超时、黄金指标、注入。Linkerd 2.0 的立项书就是 v1 的检讨书。

另一个痛点是 Istio 留下的空白：大量团队看了网格的价签望而却步，但他们的真实需求只是“内网加密 + 统一超时重试 + 调用指标”这个最小集——没有人愿意为用不上的 80% 功能付出 100% 的复杂度。

#### 7.3 如何解决：核心机制拆解

**① linkerd2-proxy：为网格从零写的 Rust 微代理**。不是把通用代理裁剪，而是只实现网格需要的功能（HTTP/1、H2、gRPC 代理 + mTLS + 指标上报）。Rust 无 GC、内存安全，代理内存占用 MB 级（官方口径 10MB 上下——对比 Envoy sidecar 常见几十 MB 起）；代价是**代理不可插拔**——没有 Envoy 那样的过滤器生态，扩展性让位于可预测性。这是“极简哲学”在数据面上的物化：小而确定，胜过大而灵活。

**② 极简哲学的四个体现**：安装一条命令，默认值即生产可用（自动 mTLS 开箱即起）；配置直接用 Kubernetes 原生资源/注解，不另立庞大的 CRD 家族；重试等行为通过 ServiceProfile 显式声明（不暗中自动重试——隐式重试是事故温床）；内置 dashboard 与 CLI，黄金指标（成功率/请求量/P99）零配置可见（可观测性的接法见 [02-可观测性-日志指标与链路追踪.md](02-可观测性-日志指标与链路追踪.md)）。

**③ 功能取舍**：流量切分走 HTTPRoute/注解路线、表达力不如 VirtualService 的“权重 + header + 镜像”组合拳；故障注入等高级流量能力长期缺席。**取舍即立场**：这些能力不是做不到，是“大多数团队用不上、用上的团队常常用错”。

**反例与修正**：反向偏差也要防——选了 Linkerd 之后又逐步需要 Envoy 级的复杂流量编排（按 header 组合切流、外部鉴权过滤器、自定义 Wasm），于是开始在业务代码里打补丁。这是**选型错位**，不是工具缺陷：引入网格前先列必需能力清单（§10 的三问），清单里有“细粒度流量编排”就直接选 Istio，不应归咎于轻量网格。

#### 7.4 对比同类：资源开销与何时选它

Buoyant 官方多次发布基准，口径是 Linkerd 的每代理内存占用与 P99 延迟增量显著低于 Istio。工程判据：**官方基准只用来缩小候选，最终以自己的镜像、自己的流量形态压测为准**（方法论见 [05-性能工程-容量规划与压测.md](05-性能工程-容量规划与压测.md)）——网格的开销与你的请求大小、TLS 会话复用率强相关，别人的基准回答不了你的问题。

**何时选 Linkerd**：Kubernetes 原生环境、团队没有专职平台人手、需求收敛在 mTLS/可靠性/可观测、要“装完就能用”。**何时不选**：需要 Istio 级流量编排、多集群、复杂授权模型时。

### 8. 一笔带过：eBPF 系（Cilium）——无 Sidecar 的下一代尝试

Sidecar 模式有固有代价：每 Pod 一个代理，资源开销随 Pod 数线性放大；代理升级要滚动全部业务 Pod；iptables 劫持让排障链路多绕一层。**eBPF 路线**把包处理与策略执行下沉到 Linux 内核：代表是 **Cilium**（eBPF 驱动的网络/安全/观测整套组件，2021 年 10 月入 CNCF 孵化、2023 年 10 月毕业）——网络策略与可观测在内核层完成，L7 场景仍借助节点级 Envoy；Istio 的 ambient 模式（节点级 ztunnel）也是同一方向：**把代理从“每 Pod”移向“每节点/内核”**。代价是内核版本要求、eBPF 编程门槛、排障离应用更远。判据：这是值得跟踪的下一代尝试，但它同样要过 §10 的三问——“新”不是选型理由，痛点才是。

## 9. 边界判据：南北向 vs 东西向，谁该管什么

两个方向的工具形态相似（都是代理），把职责放错位置是最高频的架构错误。先给对照表：

| | 南北向（入口网关） | 东西向（服务网格） |
| --- | --- | --- |
| 流量形态 | 客户端/合作伙伴 → 集群；面向域名与 API | 服务 ↔ 服务；拓扑随部署与弹性随时变 |
| 认证对象 | 外部身份：用户 token、API Key、消费者（consumer） | 服务身份：SPIFFE/mTLS 证书 |
| 典型问题 | 谁能进来、进来多少、路由到哪、TLS/审计 | 谁能调谁、怎么加密、调用怎么观测、流量怎么切 |
| 典型组件 | Nginx / Envoy / Kong / APISIX | Istio / Linkerd（+ Cilium） |
| 变更节奏 | 路由/插件随 API 发布变更（天级） | 策略随部署与弹性伸缩变化（分钟级） |
| 失败形态 | 宕机 = 全站不可访问（显性、剧烈） | 宕机 = 服务间通信异常（隐蔽、形似“网络玄学”） |

**南北向该管**：TLS 终止、对外认证（API Key/OIDC）、粗粒度限流与配额（按调用方）、路由分发、WAF/边缘缓存、API 生命周期治理（Kong/APISIX 的主场）。**不该管**：业务聚合与裁剪（BFF 的职责——[../02-第二阶段/06-平台化架构-BFF与中台.md](../02-第二阶段/06-平台化架构-BFF与中台.md) 的“网关 vs BFF 职责边界”与“变化原因三问”是完整判据）、服务间治理（网格的职责）、业务规则。

**东西向该管**：服务间 mTLS 与服务身份、重试/超时/熔断的统一基线、服务级可观测（调用拓扑、黄金指标）、灰度切分的执行。**不该管**：对外 API 管理（网关的职责）、业务校验规则、端到端的业务编排。

**两个高频反例**：

- 反例一：**网关插件里长业务**。“会员才可见某 SKU”写进网关插件——策略层做了业务决策，且不在任何业务回归测试覆盖内；插件越写越多，网关长成隐形单体（上帝层网关的腐化信号，见 [../02-第二阶段/06-平台化架构-BFF与中台.md](../02-第二阶段/06-平台化架构-BFF与中台.md)）。修正：网关只问“是谁、多少、去哪”，不问“值不值、该不该（业务上）”。
- 反例二：**把入口限流策略照搬进服务间**。入口按“每秒 1000 次”限流，被原样配到服务间调用上——大促时内部扇出调用先于入口达到上限，触发级联熔断，故障后果比不限流更严重。修正：东西向的容量治理以“入口配额 × 内部扇出系数”推导，且优先用重试预算与并发限制（并发上限）而非硬 QPS。

一句话判据：**先分方向，再分层次**——方向错了（网关承担了网格的职责、网格承担了网关的职责），层次再对也无济于事。

## 10. 是否引入网格：小团队先问三个问题

先讲一个冷静的反例：一家只有五个服务的创业公司，听说“大厂都用 Istio”，于是引入了。半年后：一半工程人力耗在网格版本升级与“为什么这个调用 503”的排障上；一次 sidecar 版本升级引发全站间歇 502，回滚用了三天；而他们最初的真实诉求，只是“想看到服务间的调用指标”。**网格解决的是你还没有的问题**——这是本节的核心句。

引入网格前先问三个问题：

1. **痛点真的是东西向治理吗？** 服务数不足 10 个、语言单一、没有强制的加密合规——库模式（如各语言的 resilience 库）+ 网关日志多半已经够用；连服务调用拓扑图都画不出来的团队，先补 [02-可观测性-日志指标与链路追踪.md](02-可观测性-日志指标与链路追踪.md)，观测是一切治理的前置。mTLS 合规需求是唯一“绕不开网格”的硬理由。
2. **谁来长期运维？** 网格是“买了要养”的平台组件：升级窗口、版本兼容、排障要懂 Envoy/xDS 的人、值班响应。没有这样的人，选 Linkerd/Kuma 级别的轻量方案，或暂缓。
3. **是否已在 Kubernetes 上标准化？** 虚机混部、非 K8s 调度的环境里，sidecar 注入与流量劫持会变成泥潭；eBPF/ambient 路线对基础设施版本还有要求。基础设施未收敛之前引入网格，是在流沙上盖楼。

替代路径的梯度（每升一级的触发条件）：什么都不做（网关日志 + APM）→ 库模式（服务数增长、仍单语言）→ 轻量网格 Linkerd/Kuma（多语言、要 mTLS、无平台团队）→ 全功能 Istio（多团队、强合规、细粒度流量编排）。**每一级的成本都翻倍不止，而收益取决于你的规模能否承接。**

## 11. 可运行示例：MiniGatewayChain.kt——控制面/数据面分离的最小网关

先与两个既有示例辨析（它们与本例是三个正交切面）：

- [../06-第六阶段/11-AI应用架构.md](../06-第六阶段/11-AI应用架构.md) 的 `GatewayRouting.kt`：LLM 网关的**降级容灾路由**——多模型端点按递减预算逐级降级、缓存命中直返。聚焦“选哪个上游兜底”，没有插件链，也没有配置热更新。
- [../02-第二阶段/05-其他重要架构风格.md](../02-第二阶段/05-其他重要架构风格.md) 4.6 的解码插件容器（`DecoderPlugin` + ServiceLoader）：**插件的发现与注册**视角——内核不认识任何插件、运行时扫描装配。聚焦“插件从哪来”，不是“请求按什么顺序过链”。
- **本例聚焦第三块**：请求按序过责任链（限流 → 认证 → 转发，可短路拒绝）+ 路由按 host/path 前缀/优先级匹配 + **控制面配置版本变更后数据面路由热生效**——即本文反复出现的那对词：控制面与数据面分离。

```kotlin
// MiniGatewayChain.kt —— 通用 API 网关最小模拟：路由匹配 + 插件责任链 + 控制面配置热更新
// 单文件、无第三方依赖。核心是"控制面 vs 数据面"分离：
//   控制面只生产配置（真实世界：istiod 的 xDS 下发 / APISIX 写 etcd / Kong Admin API）
//   数据面只消费配置并执行转发（真实世界：Envoy / OpenResty worker）
// 编译：kotlinc MiniGatewayChain.kt -include-runtime -d app.jar
// 运行：java -jar app.jar

// ========== 数据面：请求 / 响应模型 ==========

data class HttpRequest(
    val method: String = "GET",
    val host: String,
    val path: String,
    val headers: Map<String, String> = emptyMap(),
) {
    val token: String? get() = headers["Authorization"]
}

data class HttpResponse(val status: Int, val body: String) {
    override fun toString(): String = "$status $body"
}

// ========== 控制面：配置模型（对应 xDS 的路由资源 / APISIX 存进 etcd 的 Route） ==========

/** 路由规则：host 精确匹配（"*" 通配）+ path 前缀 + 优先级（大者胜出） */
data class RouteRule(
    val id: String,
    val host: String,
    val pathPrefix: String,
    val priority: Int,
    val upstream: String,
)

/** 一份网关配置快照：version 单调递增（对应 xDS 的 version_info / etcd 的全局 revision） */
data class GatewayConfig(
    val version: Int,
    val routes: List<RouteRule>,
    val rateLimitPerMinute: Int,
) {
    /** 路由匹配：先按 (host, path 前缀) 过滤候选，再取优先级最高的一条 */
    fun match(host: String, path: String): RouteRule? =
        routes.asSequence()
            .filter { (it.host == "*" || it.host == host) && path.startsWith(it.pathPrefix) }
            .maxByOrNull { it.priority }
}

// ========== 数据面：插件责任链 ==========

class RequestContext(val config: GatewayConfig, val matchedRule: RouteRule) {
    val chainTrace = mutableListOf<String>()
}

/** 责任链判定：放行，或直接应答（拒绝/转发） */
sealed interface ChainResult {
    data object Continue : ChainResult
    data class Respond(val resp: HttpResponse) : ChainResult
}

/** 插件契约：访问顺序即策略顺序——本例固定为 限流 -> 认证 -> 转发 */
interface GatewayPlugin {
    val name: String
    fun handle(req: HttpRequest, ctx: RequestContext): ChainResult
}

/** 插件 1：固定窗口限流（按路由计数；演示版窗口不过期，聚焦链式短路行为） */
class RateLimitPlugin : GatewayPlugin {
    override val name = "RateLimit"
    private val used = mutableMapOf<String, Int>()
    override fun handle(req: HttpRequest, ctx: RequestContext): ChainResult {
        val n = used.getOrDefault(ctx.matchedRule.id, 0)
        if (n >= ctx.config.rateLimitPerMinute) {
            return ChainResult.Respond(
                HttpResponse(429, "Too Many Requests (route=${ctx.matchedRule.id}, limit=${ctx.config.rateLimitPerMinute})")
            )
        }
        used[ctx.matchedRule.id] = n + 1
        return ChainResult.Continue
    }
}

/** 插件 2：认证（Bearer 校验；publicPrefixes 之下的路径免认证——对应"按路由启用插件"的配置模型） */
class AuthPlugin(private val publicPrefixes: Set<String> = emptySet()) : GatewayPlugin {
    override val name = "Auth"
    override fun handle(req: HttpRequest, ctx: RequestContext): ChainResult {
        if (publicPrefixes.any { req.path.startsWith(it) }) return ChainResult.Continue // 公共路径：跳过
        val token = req.token
            ?: return ChainResult.Respond(HttpResponse(401, "Unauthorized: missing Authorization header"))
        if (token != "Bearer sk-watermall-2026") {
            return ChainResult.Respond(HttpResponse(401, "Unauthorized: bad token"))
        }
        return ChainResult.Continue
    }
}

/** 插件 3：转发（stub——真实网关在这里做反向代理与负载均衡，这里只回显命中的上游） */
class ForwardPlugin : GatewayPlugin {
    override val name = "Forward"
    override fun handle(req: HttpRequest, ctx: RequestContext): ChainResult =
        ChainResult.Respond(HttpResponse(200, "OK from upstream=${ctx.matchedRule.upstream}"))
}

// ========== 控制面 vs 数据面 ==========

/** 控制面：只负责"生产"配置（真实世界：istiod / Kong Admin API / APISIX Admin API 写 etcd） */
class ControlPlane {
    private var version = 0
    fun publish(routes: List<RouteRule>, rateLimitPerMinute: Int): GatewayConfig =
        GatewayConfig(++version, routes, rateLimitPerMinute).also {
            println("[控制面] 发布配置 v${it.version}：${it.routes.size} 条路由，限流阈值 ${it.rateLimitPerMinute} 次/分钟")
        }
}

/** 数据面：只负责"消费"配置并执行请求（真实世界：Envoy / OpenResty worker；热更新对应 xDS gRPC 流 / etcd watch） */
class DataPlane(initialConfig: GatewayConfig) {
    @Volatile private var config: GatewayConfig = initialConfig
    private val chain = listOf(
        RateLimitPlugin(),
        AuthPlugin(publicPrefixes = setOf("/static")),
        ForwardPlugin(),
    )

    /** 控制面下发新配置：不重启、不断流——原子替换配置快照即"热生效" */
    fun onConfigPushed(newConfig: GatewayConfig) {
        config = newConfig
    }

    fun serve(req: HttpRequest) {
        val cfg = config
        val rule = cfg.match(req.host, req.path)
        if (rule == null) {
            println("[数据面 v${cfg.version}] ${req.method} ${req.host}${req.path} -> 404 No Route | 责任链未启动")
            return
        }
        val ctx = RequestContext(cfg, rule)
        for ((idx, plugin) in chain.withIndex()) {
            ctx.chainTrace += plugin.name
            when (val result = plugin.handle(req, ctx)) {
                is ChainResult.Respond -> {
                    val tag = if (idx == chain.lastIndex) "转发完成" else "短路拒绝"
                    println(
                        "[数据面 v${cfg.version}] ${req.method} ${req.host}${req.path} -> ${result.resp}" +
                            " | 命中=${rule.id}(优先级${rule.priority}) 链=${ctx.chainTrace.joinToString(" -> ")} [$tag]"
                    )
                    return
                }
                ChainResult.Continue -> Unit
            }
        }
    }
}

// ========== 演示 ==========

fun main() {
    val cp = ControlPlane()
    val v1 = cp.publish(
        routes = listOf(
            RouteRule("orders", "api.watermall.com", "/orders", priority = 1, upstream = "order-service-v1"),
            RouteRule("static", "*", "/static", priority = 0, upstream = "cdn-origin"),
        ),
        rateLimitPerMinute = 3,
    )
    val dp = DataPlane(v1)

    println()
    println("== 阶段一：v1 配置下的常规流量（含 401 / 404 / 429 三种拒绝） ==")
    val ok = mapOf("Authorization" to "Bearer sk-watermall-2026")
    dp.serve(HttpRequest(host = "api.watermall.com", path = "/orders/123", headers = ok))
    dp.serve(HttpRequest(host = "api.watermall.com", path = "/orders/456"))              // 无令牌 -> 401
    dp.serve(HttpRequest(host = "unknown.example.com", path = "/health"))                // 无路由 -> 404
    dp.serve(HttpRequest(host = "mall.watermall.com", path = "/static/logo.png"))        // 通配 host + 免认证
    dp.serve(HttpRequest(host = "api.watermall.com", path = "/orders/789", headers = ok)) // 第 3 个名额 -> 200
    dp.serve(HttpRequest(host = "api.watermall.com", path = "/orders/000", headers = ok)) // 名额耗尽 -> 429

    println()
    println("== 阶段二：控制面发布 v2（orders 换上游 + 新增 express 高优先级路由 + 限流扩容），数据面热生效 ==")
    val v2 = cp.publish(
        routes = listOf(
            RouteRule("orders", "api.watermall.com", "/orders", priority = 1, upstream = "order-service-v2"),
            RouteRule("express", "api.watermall.com", "/orders/express", priority = 10, upstream = "express-service"),
            RouteRule("static", "*", "/static", priority = 0, upstream = "cdn-origin"),
        ),
        rateLimitPerMinute = 10,
    )
    dp.onConfigPushed(v2) // 对应 xDS / etcd watch 的"配置推送"：数据面不重启
    dp.serve(HttpRequest(host = "api.watermall.com", path = "/orders/999", headers = ok))
    dp.serve(HttpRequest(host = "api.watermall.com", path = "/orders/express/9", headers = ok)) // 双路由命中，优先级 10 胜出

    println()
    println("== 两个观察点 ==")
    println("1) 阶段一第 2 条 401 也消耗了一个限流名额——限流排在认证之前，链序本身就是策略；")
```

```
2) v2 发布后 orders 的限流计数没有清零——控制面只下发无状态配置，数据面本地状态（计数器/连接表）跨版本延续，真实网关滚动升级同理。
```

三个解读点：

1. **路由匹配**：`match()` 先按 host（通配或精确）+ path 前缀过滤，再取优先级最高者——阶段二的 `/orders/express/9` 同时命中 `orders`（优先级 1）与 `express`（优先级 10），高优先级胜出；这正是 APISIX radixtree 多维匹配与 Nginx location 优先级语义的最小化实现。
2. **责任链短路**：404 在链启动前返回（路由是链的前置）；429 在 RateLimit 处短路（链 = `[RateLimit]`）；401 在 Auth 处短路（链 = `[RateLimit -> Auth]`）；200 走完全链由 Forward 终结。插件顺序 = 策略：限流排在认证前，所以无令牌的请求也要消耗限流名额——先挡量、再验身，这是入口网关的常规队形（东西向恰好相反：先验服务身份再谈配额）。
3. **热更新的本质**：`@Volatile` 替换一份**不可变配置快照**（`GatewayConfig` 是只读 data class，version 单调递增）——真实世界对应 xDS 的 version_info、etcd 的 revision；控制面 `publish` 生产、数据面 `onConfigPushed` 消费，两边除这个方法调用外零耦合（真实世界是 gRPC 流/watch，跨进程）。以及那个容易被忽略的细节：**限流计数器不随配置版本清零**——控制面配置是无状态下发的，数据面的本地状态（计数器、连接表、缓存）跨版本延续，滚动升级的网关节点之间状态也各自独立——这也是为什么集群级限流必须外置存储（Redis/etcd），进程内计数器天生只代表“自己这个节点”。
