## 0. 容器前史：chroot 到 LXC，内核沉淀三十年的手艺

先澄清一个常见误解：容器不是 2013 年发明的。Linux 容器 = **namespaces（隔离视图：看见什么）+ cgroups（资源限额：能用多少）+ union FS（分层镜像：怎么打包）**，这三样内核能力是三十多年里逐步积累出来的：

| 年份 | 里程碑 | 做了什么 |
| --- | --- | --- |
| 1979 | **chroot** 随 Version 7 Unix 出现（通常归于 Bill Joy） | 第一个“隔离视图”：把进程的根目录换到子树里，进程以为整个世界就是 `/` 之下——“chroot 监狱”。初衷很朴素：隔离构建环境，以免编译产物互相污染 |
| 2000 | **FreeBSD jail**（Poul-Henning Kamp 主导） | 在 chroot 上补了进程隔离与网络隔离：每个“监狱”是一台虚拟的小机器，共享托管服务商（一台物理机卖几十个客户）第一次有了安全的隔离边界 |
| 2004 | **Solaris Zones**（随 Solaris 10） | 第一个接近现代容器的完整实现：一个内核、多个“区”，各区有独立主机名、IP、用户体系，开销远小于虚拟机——Sun 已经把“容器”的形态做对了，可惜绑在 Solaris 上 |
| 2006~2007 | **cgroups**：Google 工程师 Paul Menage 与 Rohit Seth 提出补丁、随后合入 Linux 主线（2.6.24） | 补上“资源限额”这半边：CPU、内存、IO 可以按进程组计量与限制。Google 内部跑着百万级服务器，没有 cgroups 之前靠用户态限流——这个补丁是把 Google 的生产经验写进内核 |
| 2008 | **LXC**（Linux Containers，IBM 工程师主导） | 第一次把 namespaces + cgroups 组装成“开箱即用的容器”：`lxc-create`、`lxc-start`，能跑完整系统。但用起来像“轻量虚拟机”而非“应用打包格式” |
| 2004~2013 | **namespaces 分批成熟** | mount ns（2004）→ UTS/IPC（2006~2008）→ PID ns（2008）→ network ns（2009）→ user ns（2013 年才真正可用）。凑齐之前，“容器”始终残缺不全 |

解读这张表的正确方式：**到 2008 年，Linux 内核已经具备容器需要的一切原料**，Google 内部（Borg 系统）用这套原料跑了多年的全球数据中心。缺的不是技术，是两样东西：**一个好用的打包格式**（应用 + 依赖 + 运行环境一起交付）和**一个标准的分发渠道**（像 `apt install` 一样找到、拉取、运行）。这就是 Docker 登场的故事——它站在 LXC 肩上，赢的却是另外两件事。

顺带把“容器 vs 虚拟机”这张经典对比图钉在墙上：虚拟机虚拟的是**硬件**（Hypervisor 之上各自一个完整内核，隔离强、启动分钟级、GB 级开销）；容器隔离的是**视图与配额**（各容器共享同一个内核，启动秒级、MB 级开销）。代价是隔离边界弱一档——共享内核意味着内核漏洞的逃逸面更大，所以“多租户强隔离”场景（卖主机的云厂商）至今仍是虚拟机打底、容器跑在虚机里的分层结构（[示例项目场景/00-导览.md](../示例项目场景/00-导览.md) 物联网场景里“边缘节点上虚机 + 容器混部”是同一逻辑）。

## 1. Docker 档案：赢了标准，输了公司

### 1.1 概况：出身档案

- **作者**：Solomon Hykes，法国工程师。容器不是他的发明，但“让容器好用”是他的功劳。
- **年份与背景**：Docker 前身是 **dotCloud**——2008 年成立的 PaaS 公司（和 Heroku 同赛道），内部用 LXC 跑用户的几十种语言应用多年，沉淀了一整套封装与分发工具。**2013 年 3 月，Hykes 在 PyCon 的 lightning talk 上现场演示 Docker：一条命令构建、一条命令运行、五秒内启动一个隔离的应用环境**——对比当时虚拟机的分钟级启动，现场引起轰动，视频传遍技术圈。dotCloud 随即把 Docker 以 Apache 2.0 开源，同年更名 **Docker Inc.**。
- **归属与后续**：2015 年联合各大厂成立 **OCI（Open Container Initiative）** 开放容器标准，并把核心运行时 libcontainer 捐出成为 **runC**、镜像格式捐作 OCI image spec 的基础；2015 年底把容器管理拆出 **containerd**，2017 年捐给 CNCF（2019 年毕业）。商业侧一路收缩：dotCloud 的 PaaS 业务 2016 年卖掉，**2019 年 11 月企业级产品线（Docker EE）整体卖给 Mirantis**，公司转型聚焦开发者桌面（Docker Desktop 与 Docker Hub 订阅）。
- **一句话定位**：**把“应用 + 依赖”打成分层镜像、一次构建处处运行的开发者工具与分发平台**。

### 1.2 解决了什么问题：出现前的痛

痛点是那句**“在我机器上是好的”**。桶装水商城的经典事故现场：开发在自己 Mac 上用 Homebrew 装了 JDK 17、PostgreSQL 15、Redis 7，本地运行一切正常；测试环境是 Ubuntu 20.04 + OpenJDK 11 + 自编译 Redis；生产是 CentOS 7 + 运维三年前编译的各色组件。同一个 jar 包，三个环境三套依赖矩阵，每次发版都是一次“环境考古”。之前的解法各有残缺：

- **虚拟机镜像**：能打包整个环境，但一个镜像几个 GB、启动几分钟，没有团队会为每个应用构建一个虚机；
- **配置管理**（Puppet/Chef/Ansible）：管理的是“机器怎么配置”，收敛慢、有漂移（drift：改了配置忘了提交，机器和代码库渐行渐远）；
- **LXC**：技术上能隔离，但它是“系统容器”——使用者必须先想清楚 rootfs 从哪来、依赖怎么装，本质还是在“装机器”。

而微服务化（[../02-第二阶段/03-微服务架构.md](../02-第二阶段/03-微服务架构.md)）把这个痛放大了一个量级：单体时代一年考古一次环境，18 个微服务就是 18 份依赖矩阵 × N 个环境。**微服务必须有标准化的部署载体，否则“拆服务”只会把环境问题乘以服务数**——容器就是这个载体。

Docker 的回答：`Dockerfile` 十几行声明“应用 + 依赖 + 运行方式”，`docker build` 产出一个不可变镜像，dev/staging/prod 跑的是**同一个镜像**，差异只通过环境变量注入（正是 [07-核心概念档案-云原生DevOps与SRE.md](07-核心概念档案-云原生DevOps与SRE.md) 里 12-Factor 第 III 条“配置存在环境中”的镜像版；CI 怎么构建镜像见 [03-部署与发布策略-CICD与灰度.md](03-部署与发布策略-CICD与灰度.md) 用 jib 打镜像的那段）。MES 边缘网关是另一面的受益者：网关要装进车间那台 2C/4G 的工控机，以前是运维带着 U 盘去现场装 JDK、配 systemd、改防火墙；容器化之后——厂商在办公室把网关连同 OPC UA 驱动一起打成镜像，现场 `docker run` 一条命令，升级即换镜像，回滚即换回旧 tag。

### 1.3 如何解决：核心机制拆解

**① 镜像分层（union FS / overlay2）**。Dockerfile 的每条指令（FROM、COPY、RUN……）生成一个**只读层**，多层叠加出一个统一的根文件系统视图；容器运行时在上面再加一个**可写层**（写时复制：改文件先拷到可写层）。设计动机有三层：**复用**——`FROM eclipse-temurin:17` 这层全网只存一份，10 个 Kotlin 服务共享；**缓存**——指令没变、输入没变，构建时这层直接命中缓存，把“改一行代码重新构建镜像”从几分钟缩短到几秒（这也是 Dockerfile 要把变化少的层放前面、`COPY 源码` 放最后的原因）；**增量分发**——拉镜像只传本地缺的层。“一次构建处处运行”的本质就是：**不可变的分层制品 + 内容寻址**（层 ID 由内容哈希得出，天然防篡改、可去重）。

**② 容器 = 隔离的进程，不是小虚机**。`docker run` 做的事情：用 namespaces 给进程造一套“假象”（独立的 PID 空间——它以为自己是 1 号进程；独立的网络栈、挂载点、用户视图），用 cgroups 圈住它的资源配额。所以容器里跑的**就是一个普通 Linux 进程**，没有 guest 内核、没有开机过程——这就是秒级启动与 MB 级开销的来源。反例视角：把容器当虚机用（进容器手改配置、容器里跑 systemd、数据写容器内）就会把这些好处全部抵消——容器是**一次性**的，实例终止即换新，状态必须外置。

**③ 分发体验：Docker Hub**。这是 Docker 真正的杀手锏——技术上 LXC 也能隔离，但 `docker pull redis:7` 三秒后即可运行一个 Redis，这种“注册中心 + 命令行 + 版本 tag”的体验让镜像成了新的软件分发单位。类比：cgroups/namespaces 是“压缩算法”，Docker Hub 是“应用商店”——**决定普及的从来是后者**。内部私有 registry（Harbor 等）沿用同一协议，企业内的制品库、CI 产物、漏洞扫描全部构建在这个生态之上。

**④ 标准化：OCI 与 containerd 的拆分**。2014~2015 年容器 runtime 大战一触即发（CoreOS 自推 appc/rkt 标准与 Docker 对峙），社区最怕的是“镜像格式分裂”。2015 年 6 月 Docker 联合 CoreOS、Google、RedHat、Microsoft 等成立 **OCI**，定义了两份任何人都能实现的规范——**runtime spec**（容器生命周期：create/start/kill 怎么表现）与 **image spec**（镜像格式）。Docker 捐出 libcontainer 作为参考实现 **runC**，又把管理容器的中间层 **containerd** 拆出来捐给 CNCF。从此“任何人生产的 OCI 镜像 + 任何 OCI 运行时”可以互相替换——今天的 K8s 集群里已经找不到“Docker”，但跑的全是 Docker 定下的标准。**注意这个格局的含义：容器生态的底层（runC/containerd/镜像格式）是彻底开放的商品，没有任何厂商能靠它收租**——这正是后文“Docker 公司兴衰”的伏笔。

**⑤ 一段公司史，一个教训**。Docker Inc. 的融资与估值一度冲上十亿美元级，但它的商业产品（Docker EE、云服务）始终没能把“标准制定者”的地位变现：runtime 与镜像被 OCI 公有化，编排战场又输给 Kubernetes（见 §4），2019 年只能把企业业务卖给 Mirantis。留下的复盘金句是**“赢了标准、输了公司”**——Docker 赢得了整个行业（今天一切云原生都以 OCI 镜像为交付单位），但开放标准没法独家收费，赢家是生态里的用户与云厂商。对照记忆：与它同期的 RedHat 靠“开源 + 企业订阅服务”最终成为 IBM 的收购对象；标准本身不赚钱，**围绕标准的服务与平台才赚钱**——这个判据后面 §5 还要用一次。

### 1.4 对比同类：容器运行时的层次表

“容器运行时”常被混用，其实是一条分层链路。K8s 节点上：kubelet → **CRI**（Container Runtime Interface，K8s 1.5 引入的插件接口）→ 高层运行时（拉镜像、管容器生命周期）→ **runC**（OCI 低层运行时，真正调 namespaces/cgroups 起进程的地方）→ Linux 内核。三个常见名词在这条链上的定位：

| 维度 | Docker Engine（dockerd） | containerd | CRI-O |
| --- | --- | --- | --- |
| **出身** | Docker 公司，2013 | 从 Docker 拆出，2015 年底发布、2017 年捐 CNCF、2019 年毕业 | RedHat 牵头的社区项目，2016 年起 |
| **定位** | 完整开发者体验：build（BuildKit）+ run + volume + network + API | 工业级“容器监督者”：只管镜像与容器生命周期，不管 build | 专为 K8s 而生的最小 CRI 实现：kubelet 需要什么就实现什么，其余一概不做 |
| **谁在用** | 开发机、CI 构建机（Docker Desktop / docker CLI） | Docker Engine 内嵌着它；绝大多数 K8s 节点的默认运行时 | OpenShift 的默认运行时 |
| **内置关系** | dockerd 内部就调用 containerd + runC | 下调 runC | 下调 runC |
| **何时选它** | 交互式开发、本地联调、构建镜像 | 节点级运行时的事实标准（托管 K8s 默认） | 想要 K8s 节点更精简、路径更短（无 Docker 血统包袱） |

两笔历史账帮助这张表定型：其一，K8s 早期通过 “dockershim” 兼容层调用 Docker，**2022 年 K8s 1.24 正式移除 dockershim**——当时社区一度恐慌“Docker 不能用了”，实际上毫无影响：镜像格式早已是 OCI 标准，K8s 直接对接 containerd/CRI-O 即可，`docker build` 出的镜像照常可运行。其二，开发机上 Docker Desktop 仍是事实标准（Podman 作为无守护进程/免 root 的替代品，在 Linux 圈有一席之地）。**何时选谁的一句话结论：开发机用 Docker（体验最全），K8s 节点交给 containerd（默认即正确），CRI-O 留给追求极简或有 RedHat 背景的场景。**

## 2. Kubernetes 档案：Borg 血统的分布式操作系统

### 2.1 概况：出身档案

- **作者**：Google 的 Joe Beda、Brendan Burns、Craig McLuckie（+Tim Hockin 等核心），Go 语言编写。名字取希腊语“舵手”（κυβερνήτης），K 与 s 之间 8 个字母故缩写 K8s。
- **年份与背景**：**2014 年 6 月公开**（Google I/O 上首秀），**2015 年 7 月发布 1.0 并捐赠给当天成立的 CNCF**（云原生计算基金会，Linux 基金会旗下；K8s 是其第一个项目、2018 年第一个毕业项目）。血统可以直接引用论文：**《Large-scale cluster management at Google with Borg》（Verma 等，EuroSys 2015）**——Google 内部集群系统 Borg 从 2003 年前后运行至今（论文时点已十五年），调度着全球百万级机器上的海量作业。K8s 不是 Borg 的开源版（代码重写、模型简化），但**设计基因全部来自 Borg/Omega**：声明式 API、标签体系、调度与资源模型。
- **归属**：CNCF 托管的开放社区项目，无单一厂商控制（Google/RedHat/Microsoft/华为等共同贡献）——这与 Docker 公司单打独斗形成对照，也是它赢下编排大战的组织原因。
- **一句话定位**：**把数据中心当一台计算机的分布式操作系统——你声明期望状态，它持续把实际状态调成期望状态**。

### 2.2 解决了什么问题：出现前的痛

Docker 解决了“打包”，下一站的痛是**“几十个镜像放到哪里、坏了谁管、怎么升级”**——编排（orchestration）。桶装水商城拆成 18 个微服务后的日常：

- **放哪**：18 个服务、峰值差 20 倍（秒杀服务大促要 20 副本，平时 2 个），手工指定机器 = 画一张谁也看不懂的 Excel；机器宕机后哪些容器要迁移，靠人工巡检。
- **坏了谁管**：进程崩溃要重启、机器要下线维护、发布要一台台滚动替换——运维写了几百行 shell 脚本，脚本本身成了最危险的系统。
- **找得到吗**：容器重启后 IP 会变，服务发现、负载均衡、健康检查全要自己做（[../03-第三阶段/09-技术工具档案-协调与注册中心.md](../03-第三阶段/09-技术工具档案-协调与注册中心.md) 讲的 ZooKeeper/etcd 就是在补这个洞）。
- **怎么升级**：18 个服务互相依赖，发布顺序、失败回滚、灰度比例——[03-部署与发布策略-CICD与灰度.md](03-部署与发布策略-CICD与灰度.md) 的滚动/金丝雀要有基础设施层面的载体才能落地。

Puppet 式工具（Ansible 等）管的是“机器”，而容器时代的管理单位变成了“服务副本”——需要一个新的、以服务为中心的控制层。2014~2015 年这个位置上挤着 Mesos、Swarm、Nomad、K8s 四位选手，最终 K8s 胜出（§4 复盘原因）。

### 2.3 如何解决：核心机制拆解

**① 声明式 API + 控制器调谐循环（reconciliation loop）——整个 K8s 的心脏**。不是下达“在 node-a 上启动容器 X”的命令（命令式），而是提交一份期望：“deployment：order-api，期望 3 副本，镜像 v2”。控制器持续执行同一个循环：**观察实际状态（现在 2 副本）→ 对比期望（3）→ 施动作（再启 1 个）→ 回到观察**。威力在于**收敛性**：任何偏离（Pod 终止、机器宕机、人工误删）都会被循环自动纠正回期望——“自愈”不是监控告警后人来修，而是控制回路天生如此。这套思想在 [../02-第二阶段/05-其他重要架构风格.md](../02-第二阶段/05-其他重要架构风格.md) 微内核视角下还有一种妙解：**K8s 本体是个小内核（apiserver + etcd + controller-manager + scheduler + kubelet），一切具体能力（网络、存储、DNS、数据库运维）都是“插件”**——扩展性正是靠下一个机制实现的。

**② Pod：为什么原子单位是 Pod 而不是容器**。K8s 刻意不直接调度容器，而是调度 **Pod**——一组共享网络与存储 namespace 的容器（同 Pod 容器同 IP、可通过 localhost 互访、共生死同调度）。为什么：其一，**多容器协作是真实需求**——业务容器 + 日志收集 sidecar + Envoy 代理（[08-技术工具档案-网关与服务网格.md](08-技术工具档案-网关与服务网格.md) 的 sidecar 模式），它们必须绑定部署、同生共死；其二，**调度需要一个“打包定价”的原子**——调度器按 Pod 的总请求资源一次决策，不能出现“代理容器放上了、业务容器没地方”的不完整状态；其三，Linux 容器之间默认并不共享网络，Pod 用一个暂停容器（pause 容器）先占住 network namespace，其余容器加进来共享——这是 Borg “alloc” 设计的直系后代。记住一句判据：**“一起调度、共享生命周期”的放一个 Pod；只是“互相调用”的分开成多个 Pod**——前者是打包关系，后者是网络关系。

**③ Deployment / ReplicaSet：滚动更新的载体（链接不重写）**。Deployment 管 ReplicaSet，ReplicaSet 保证副本数；改镜像 tag 触发滚动更新：新 RS 逐个扩、旧 RS 逐个缩，`maxSurge`/`maxUnavailable` 控制节奏。**滚动与金丝雀的完整机制、参数权衡与“能不能做真灰度”的判断，[03-部署与发布策略-CICD与灰度.md](03-部署与发布策略-CICD与灰度.md) 已详细拆解**，此处只补一句档案视角：Deployment 的本质是把“发布”也变成了一个可调谐的期望状态——发布中途出问题，回滚就是把期望指回旧版本，循环自动收敛。

**④ Service / Ingress：稳定的服务发现**。Pod 会终止也会漂移，Service 提供一个稳定的虚拟 IP + DNS 名（`order-api.default.svc.cluster.local`），后端由标签选择器动态圈定，kube-proxy 把流量分发到健康端点。这直接消灭了“容器时代自建注册中心”的需求——**K8s 内置了服务发现**（CoreDNS + Service），只有跨集群、跨语言、带健康探测增强的场景才需要额外的注册方案（对照 [../03-第三阶段/09-技术工具档案-协调与注册中心.md](../03-第三阶段/09-技术工具档案-协调与注册中心.md)）。Ingress/Gateway API 再往上补 L7：按域名路由、TLS 终止，正好接上 [08-技术工具档案-网关与服务网格.md](08-技术工具档案-网关与服务网格.md) 的南北向流量入口。而这一切的底座是：**K8s 集群的全部状态（Pod、Service、配置……）都存在 etcd 里**，apiserver 是唯一读写方，各控制器靠 etcd 的 watch 机制感知变化——etcd 抖动 = 整个控制面失明，这就是协调与注册中心档案里“etcd 容量与延迟纪律”在 K8s 上的分量。

**⑤ Scheduler：两阶段调度（过滤 + 打分）**。待调度的 Pod 进入队列，调度器对每个 Pod 走两步：**过滤（Predicates）**淘汰硬约束不满足的节点（资源不够、nodeSelector/亲和不匹配、污点不容忍）；**打分（Priorities）**对幸存者逐一评分取最高——默认策略包括“最少已分配优先”（往空的放，均衡负载）、资源均衡度（避免 CPU 满、内存空）、镜像本地性（已拉过镜像的节点加分）等。全集群无节点可放则 Pod 保持 **Pending** 排队；若该 Pod 优先级足够高，还可触发**抢占（Preemption）**：驱逐某些低优先级 Pod 腾出位置。MES 边缘部署立刻用得上这套语言：边缘节点打上 `edge=true` 标签，边缘网关 Pod 用 nodeSelector 锁定到边缘节点，再配污点（taint）与容忍（toleration）把普通服务挡在边缘节点外——**调度约束就是“部署拓扑”的声明式表达**。§7 的 `MiniScheduler.kt` 把这两阶段 + 抢占完整模拟了一遍。

**⑥ HPA：自动扩缩容**。Horizontal Pod Autoscaler 采样指标（默认 CPU 利用率相对 request 的比值），按公式 `期望副本 = ceil(当前副本 × 当前指标 / 目标指标)` 伸缩，并有默认 5 分钟的缩容稳定窗防抖。潮汐流量（桶装水商城早高峰订水、MES 白夜班采集量差三倍）从此无需人工值守调整副本数。注意 HPA 依赖**每个 Pod 都声明了 requests**——没有 request 就没有“利用率”的分母，这是后文反例“无防护容器”的病根之一。

**⑦ CRD + Operator：把运维知识编码成软件**。CRD（Custom Resource Definition）让用户在 apiserver 里注册自己的资源类型（比如 `MySQLCluster`），Kubernetes 就像对待原生对象一样存储、校验、watch 它；**Operator = CRD + 专用控制器**，把某类有状态系统的运维经验（备份、故障转移、版本升级）写成调谐循环代码。etcd Operator、Prometheus Operator 是教科书案例。这是“K8s 生态爆炸”的关键所在：**平台提供扩展点，而不是预判所有需求**——微内核架构（[../02-第二阶段/05-其他重要架构风格.md](../02-第二阶段/05-其他重要架构风格.md) 4.6）的分布式版。

### 2.4 对比同类：编排器对比表（K8s / Nomad / Swarm）

| 维度 | Kubernetes | Nomad | Docker Swarm |
| --- | --- | --- | --- |
| **出身 / 年份** | Google，2014 公布、2015 捐 CNCF | HashiCorp，2015 | Docker 公司，2016 随 Docker 1.12 内置（SwarmKit） |
| **学习曲线** | 陡：API 对象几十种，YAML、RBAC、网络与存储都要学 | 平缓：单二进制、一份 HCL job 文件、文档一页起步 | 最平：会 docker 命令就会 swarm，概念只多了 service/node |
| **调度能力** | 最强：两阶段调度、亲和/反亲和、污点容忍、拓扑扩散、抢占、调度框架可插拔 | 强：bin-packing、亲和、污点（fingerprint + constraint 模型），细节少于 K8s | 基础：约束过滤 + 简单打分，抢占/高级亲和长期缺失 |
| **生态** | 压倒性：CNCF 整套组件、Helm、Operator 市场、各大云托管 | HashiCorp 栈内闭环（Consul/Vault 联动顺畅），栈外偏少 | 停滞：厂商与社区 2017 年后转向 K8s |
| **多运行时** | 容器为主（CRI 理论上不限） | 亮点：原生进程、Java（JVM）、QEMU 虚拟机、容器并列一等公民 | 仅 Docker 容器 |
| **社区规模** | 云原生事实标准，招聘市场硬通货 | 小而稳定 | 明显萎缩，存量维护 |
| **适合谁** | 服务多、要弹性、要平台化；或直接用云托管 | 已采用 HashiCorp 整套组件、认为 K8s 过重、有非容器负载 | 仅需三五台机器快速起步且不考虑长期 |

**何时选 K8s**：服务数量到几十个以上、有潮汐弹性需求、需要统一的多环境交付（dev/staging/prod 用同一套 YAML + 不同 values）、团队有（或打算建）平台/SRE 角色。规模不到时优先“云托管 K8s”而非自建——判据展开见 §5。

## 3. Nomad 档案：HashiCorp 的简单哲学

### 3.1 概况：出身档案

- **作者**：HashiCorp（Mitchell Hashimoto 与 Armon Dadgar 创立），与 Consul（2014）、Terraform（2014）、Vault（2015）同门——这家公司的产品线是一个完整的“基础设施工作流”矩阵。
- **年份与背景**：**2015 年 9 月正式发布**（HashiConf 上宣布）。定位从一开始就克制：编排器里做“够用且极简”的那一个。
- **归属**：HashiCorp（2023 年许可证改 BSL，见下；2024 年 IBM 宣布收购 HashiCorp，2025 年完成交割）。
- **一句话定位**：**单二进制、开箱即用的多工作负载调度器**。

### 3.2 解决了什么问题

K8s 的痛点就是 Nomad 的空间：想容器化部署，但**不想为一个编排器引入一整套分布式系统**。工单中心团队的典型处境：6 个后端、2 个前端、一个批处理，三台 8C16G 的服务器；要的是“把服务铺上去、宕机自动拉起、发版不停机”，而不是先学懂 apiserver/etcd/CNI/CSI/RBAC 一整套词汇表。K8s 答卷的问题是“如何管理五千个节点的数据中心”，这份卷子对三台机器的团队是纯负担——**平台税超过了平台收益**。Nomad 的答卷只回答“中小规模的调度如何最省心”。

### 3.3 如何解决：核心机制

**① 单二进制、零外部依赖**。一个 `nomad` 二进制既是客户端也是服务端（`-dev` 一条命令即可启动全功能环境），状态复制用内嵌 Raft，不需要外置 etcd、不需要单独装调度器组件。对照 K8s 的“五组件起步”（apiserver/etcd/scheduler/controller-manager/kubelet + CNI + CoreDNS……），运维面从十几个 moving parts 缩到一两个。这与它同门兄弟的设计一致性极高——Consul 用一个二进制解决注册发现、Vault 用一个二进制解决密钥管理，**HashiCorp 的产品哲学就是“每个工具只做一件事，但单独可用”**。

**② 编排不止容器**。Nomad 的 task driver 体系里，Docker 容器、**原生进程（fork/exec 隔离）**、**JVM（直启 Jar，不必打镜像）**、QEMU 虚拟机是并列的一等公民。这个设计击中一批真实场景：MES 车间那台跑着十年前上位机程序的机器，不可能容器化，但可以用 Nomad 统一纳管（进程驱动 + 健康检查 + 声明式 job 文件）；批处理的 Java 任务直接跑 jar，省去为一次性任务打包镜像的额外开销。**“容器是工作负载的一种，而不是唯一一种”**——这个视角 K8s 生态很晚才补上（K8s 里至今默认一切皆容器）。

**③ 调度模型同源不同复杂度**。Nomad 同样是“声明 job → 调度器两阶段（约束过滤 + bin-packing 打分）→ 客户端执行 + 健康守护”，因为这套模型本来就从 Google 一脉相承（HashiCorp 团队公开承认参考了 Borg 论文）。差别在广度：没有 CRD、没有 Operator、调度策略选项更少——**砍掉的是表达力，换来的是可理解性**。十人团队里每个人都能读完一份 Nomad job 文件；一份等价的 K8s 部署（Deployment + Service + Ingress + HPA + RBAC + Helm chart）没有专人维护就会熵增。

**④ 2023 年 BSL 风波（档案里必须记的一课）**。2023 年 8 月 HashiCorp 宣布全线产品从 MPL 改为 **BSL（Business Source License）**：源码仍可见，但“与 HashiCorp 竞争的用途”四年内禁止生产使用。导火索是某云厂商基于 Terraform 提供商业托管服务却不回馈社区，但改许可证直接动摇了社区信任：Terraform 社区当即分叉出 OpenTofu（转入 Linux 基金会）、Vault 分叉出 OpenBao；Nomad 没有等量级的分叉，但“开源 → 改限制性许可”这一步让不少企业在选型时把“许可证可持续性”列为正式评估项。对工具档案系列的读者，这一课的判据是：**选基础设施要看三重风险——技术风险（会不会死）、商业风险（会不会被锁）、治理风险（许可证会不会变）**，2023 年之前业界大多只看前两个。

### 3.4 对比同类与何时选它

对照 §2.4 的编排器对比表。**何时选 Nomad**：团队已在 HashiCorp 栈内（Consul 做发现、Vault 管密钥、Terraform 管基础设施，Nomad 是拼图的最后一块）；工作负载里有非容器部分（老进程、JVM 任务、虚拟机）；机器规模在几台到几百台；没有专职平台团队但想声明式管理部署。**何时不选**：需要云厂商托管（三大云的托管编排全是 K8s）、需要 Operator 生态（数据库/中间件的运维自动化）、招聘与内部转岗要靠 K8s 技能流通——这些场景下 Nomad 的“简单”无济于事。

## 4. Docker Swarm 档案：上手最容易的失败者

### 4.1 概况：出身档案

- **作者**：Docker 公司。两代形态：2015 年 11 月独立工具 Swarm（beta），**2016 年 Docker 1.12 把 SwarmKit 直接内置进 Docker 引擎**——`docker swarm init` 一条命令，任何装了 Docker 的机器当场变成编排集群。
- **归属**：随 Docker 引擎一同发行；Docker 企业资产 2019 年卖身 Mirantis 后，Mirantis 承诺继续支持 Swarm 数年，此后进入维护状态。
- **一句话定位**：**零学习成本的内置编排器——“会 docker 就会编排”**。

### 4.2 解决了什么问题（以及那份漂亮的答卷）

2015~2016 年的痛点真实存在：容器技术大热，但“多机编排”门槛极高（当时 K8s 1.x 安装以“地狱难度”闻名，kubeadm 还没发布）。Swarm 的答卷在工程上非常漂亮：**零新增概念、零安装**——`docker service create --replicas 3 --name order-api xxx` 直接可用；声明式 service 模型、内置路由网格（routing mesh，任意节点都能把请求转给服务副本）、集群节点间自动 TLS、滚动更新与回滚参数一个不少。三台机器起步的小团队（比如桶装水商城初期），从单机 compose 迁到 Swarm 几乎是零成本平滑升级（compose 文件稍加修改就能 `docker stack deploy`）。**就“上手成本/功能比”而言，Swarm 至今没有被超越**。

### 4.3 为什么输：一个生态战的标本

但编排器的胜负手不在上手成本。复盘 2016~2017 年的窗口期：Google 把 K8s 捐给 CNCF 后，RedHat、Microsoft、IBM、AWS 全部押注 K8s（Azure AKS、AWS EKS 相继上线）——**云厂商要的是一个不受任何一家控制的中立标准**，K8s 的中立治理正中下怀，Swarm 是 Docker 公司的私有资产，战略上先天出局。生态随之雪崩：Helm 图表、Operator、监控方案、招聘简历全部涌向 K8s；2017 年 DockerCon 上 Docker 自己宣布支持 K8s，等于举旗投降。之后 `docker swarm` 关键词的搜索与招聘份额逐年萎缩到边缘水平。三条教训值得写进档案：

1. **平台类产品的胜负在生态，不在易用性**。易用性决定试用转化率，生态决定迁移成本——用户押注的是“三年后招得到人、找得到图表、云厂商托管”这些外部性，Swarm 三项皆输。
2. **“既是裁判又是选手”的结构性劣势**。Docker 公司既控制容器运行时（Docker Engine）又下场做编排，所有云厂商都警惕把编排层也交给它；K8s 捐给基金会后“Docker 贡献运行时、社区贡献编排、厂商贡献托管”各归各位。
3. **窗口期不等人**。编排大战 2017 年就分出了胜负，此后“再简单”也换不回沉没的生态投入——选基础设施时，**押注趋势比押注当下体验更重要**（这和 §1.5“赢了标准输了公司”是同一枚硬币的两面：Docker 在标准层赢在开放，在编排层输在封闭）。

### 4.4 对比同类与何时选它

对照 §2.4 的表。**今天何时还选 Swarm**：个人实验、边缘极小集群、存量系统维护、或某些内网环境“只允许装 Docker、不允许引入其他组件”的硬约束。除此之外，新项目在 2026 年的今天再选 Swarm，等于主动加入一个收缩中的社区——它作为“反面教材”的价值大于作为生产选型的价值。

## 5. 综合选型判据：什么团队、什么规模，该不该上 K8s

把四份档案收敛成一张决策地图。核心问题只有一个：**“平台税”能否被“平台收益”覆盖？**

**反例开场：为三个服务上 K8s**。桶装水商城初创期：5 人团队（3 后端 1 前端 1 兼职运维）、3 个服务、两台 4C8G 云主机。若坚持自建 K8s：三个 master 高可用 + etcd 备份 + CNI 选型 + 存储类 + RBAC + 证书轮换 + 版本升级（每年至少两次小版本升级，每次都是一次小型项目）——这套平台的维护成本约等于 0.5~1 个全职工程师，而它管理的负载是 3 个服务。**平台税 >> 平台收益**。此时正确答案在下面的阶梯第 0~1 级。

**部署复杂度的阶梯（从轻到重）**：

| 阶梯 | 方案 | 什么时候它是对的 |
| --- | --- | --- |
| 0 | 单机 `docker compose` | 开发联调、演示环境、初创期（服务 < 5、单机放得下、可容忍单机重启） |
| 1 | 多机 compose / Nomad / K3s（轻量 K8s 发行版） | 几台机器、无专职运维、要声明式与自愈但不要完整 K8s 的运维面；MES 车间边缘节点常选 K3s 或 Nomad（小足迹、可离线自治） |
| 2 | **云托管 K8s**（EKS/GKE/ACK 等） | 几十服务、多环境、要弹性伸缩——**控制面由云厂商运维，使用者只管节点池与工作负载**；这是 10~200 人技术公司的事实标准选项 |
| 3 | **Serverless 容器**（AWS Fargate、Cloud Run、阿里云 SAE/ECI） | 连节点都不想管理：按副本付费、缩容到零、突发流量（秒杀活动页）极合适；代价是冷启动、计费模型与厂商深度绑定 |
| 4 | 自建 K8s + 平台工程 | 大规模（数百节点以上）、强合规（数据不能出机房）、多租户内部平台——此时才值得组建专职平台团队，并把 K8s 封装成内部 PaaS（[07-核心概念档案-云原生DevOps与SRE.md](07-核心概念档案-云原生DevOps与SRE.md) 的平台工程一节） |

**四条硬判据**（满足越多，越该往阶梯高处走）：

1. **服务数量与变更频率**：服务 > 15 个、每天发布 > 3 次——手工/compose 的协调成本开始指数上升。
2. **弹性诉求**：流量潮汐差 3 倍以上、或需要“缩容到零”节约成本——HPA/Serverless 容器的收益可直接折算为成本节省。
3. **团队结构**：有（或计划有）平台/SRE 编制；若没有，托管优先、Serverless 其次、自建则近乎预定了一场事故。
4. **多环境一致性**：dev/staging/prod 要同一镜像同一套 YAML 走完——K8s 的声明式清单 + GitOps 是目前最成熟的载体（与 [03-部署与发布策略-CICD与灰度.md](03-部署与发布策略-CICD与灰度.md) 的发布流水线直接衔接）。

**三条反向判据**（命中任何一条，暂缓引入 K8s）：三个月内没有人力接管平台运维；负载里有大量无法容器化的老系统且没有混合编排方案；团队连 Dockerfile/镜像分层尚未掌握（地基没打好，上编排只会把混乱放大到分布式规模）。

MES 场景的专属判据补丁：**边缘与中心分治**——车间边缘节点（2C/4G 工控机、断网要自治）用 K3s/KubeEdge 或 Nomad 小足迹部署，中心机房用托管 K8s 统一管控下发；不要试图用一个跨厂区 WAN 的大集群覆盖边缘（etcd 跨 WAN 的延迟会拖垮控制面）。边缘网关镜像里带上全部协议驱动（OPC UA/Modbus），现场升级即换镜像、断网时本地缓存续传——这套“边缘自治”要求见 [示例项目场景/00-导览.md](../示例项目场景/00-导览.md) 的工控扩展场景。

## 6. 反例与修正

**反例一：容器当虚机用**。进了容器 `vim` 改配置、应用日志写容器文件系统、数据存容器里、一个容器跑五年不重建。修正：容器是**一次性的**——配置进环境变量/配置中心、日志打到 stdout（[02-可观测性-日志指标与链路追踪.md](02-可观测性-日志指标与链路追踪.md) 的采集前提）、状态进数据库/对象存储；任何“容器内手工修改”都会在下一次滚动更新时蒸发，这正是 12-Factor“易处置性”的含义（[07-核心概念档案-云原生DevOps与SRE.md](07-核心概念档案-云原生DevOps与SRE.md)）。

**反例二：“容器化了 = 云原生了”**。把 1.8GB 的 jar 连同整个 JDK+调试工具塞进一个巨型镜像，构建 20 分钟、启动 8 分钟，只是“用容器跑出了虚机的体验”。修正：多阶段构建（构建层与运行层分离）、Jib/Spring Boot 分层 jar 直接产出瘦镜像、基础镜像选 alpine/slim 变体、镜像里只留运行必需品——目标是**镜像体积以百 MB 计、启动以秒计**，否则 HPA 的弹性扩容会被启动时间严重拖累。

**反例三：裸容器（不设 requests/limits 与优先级）**。“反正是我自己的集群，资源先到先得”。后果：某个服务内存泄漏把节点拖垮，kubelet 无差别驱逐（看不到请求量就没法优雅排序），雪崩连锁。修正：**每个 Pod 必须声明 requests/limits + PriorityClass**——requests 是调度器两阶段调度的输入、HPA 的分母，limits 是单容器的资源围栏，优先级决定抢占时谁牺牲（§7 示例的 report-batch 就是“可牺牲批任务”的正确做法）。

**反例四：把 K8s 当应用服务器**。一个 Deployment 跑巨型单体、hostPath 直挂宿主机目录、Ingress 后面只有一个副本还不开健康探针。修正：K8s 的全部收益（滚动、自愈、弹性）都建立在“负载是无状态副本”的前提上——先按 [../02-第二阶段/03-微服务架构.md](../02-第二阶段/03-微服务架构.md) 的思路拆出可独立伸缩的模块，再享受编排红利；把单体强行搬上 K8s 只是换了一种方式支付服务器账单。

**反例五：边缘直接套大集群**。见 §5 的 MES 判据补丁：跨 WAN 的单一大集群 + 边缘弱网 = 控制面失联时车间停摆。修正：边缘自治分治（每厂区一个轻量控制面，中心只做镜像与配置下发），断网时本地照常生产、恢复后补传。

## 7. 可运行示例：MiniScheduler.kt——两阶段调度 + 抢占 + HPA

示例模拟 K8s 的三件事：**两阶段调度**（过滤 Filter → 打分 Score，“放置后已分配比”最小者优先）、**优先级抢占**（高优先级 Pod 可以驱逐低优先级 Pod 腾位）、**HPA 副本扩缩**（按负载折算期望副本数，增删 Pod 并触发新调度）。集群模型刻意贴合正文场景：node-a/node-b 是机房主机，edge-01 是带 `edge=true` 标签的车间边缘节点（MES 边缘网关专用）；负载则是桶装水商城的日常服务 + 秒杀大促。

```kotlin
// MiniScheduler.kt —— Kubernetes 调度器最小模拟
// 三件事：两阶段调度（过滤 -> 打分）、优先级抢占（Preemption）、HPA 副本扩缩
// 单文件、无第三方依赖。资源单位：CPU 毫核（m）、内存 MB。
// 编译：kotlinc MiniScheduler.kt -include-runtime -d app.jar
// 运行：java -jar app.jar

import kotlin.math.ceil

/** 资源向量：cpu 毫核，mem 兆字节 */
data class Res(val cpu: Int, val mem: Int) {
    operator fun plus(o: Res) = Res(cpu + o.cpu, mem + o.mem)
    operator fun minus(o: Res) = Res(cpu - o.cpu, mem - o.mem)
    fun fitsIn(cap: Res) = cpu <= cap.cpu && mem <= cap.mem   // 能否放进容量 cap
    override fun toString() = "${cpu}m/${mem}MB"
}

/** Pod：调度原子单位。priority 对应 K8s PriorityClass，nodeSelector 是硬约束 */
class Pod(
    val name: String,
    val req: Res,
    val priority: Int,
    val nodeSelector: Map<String, String> = emptyMap()
) {
    var node: String? = null
    var running = false
}

/** Node：容量 + 标签 + 已放置的 Pod */
class Node(
    val name: String,
    val capacity: Res,
    val labels: Map<String, String> = emptyMap()
) {
    val pods = mutableListOf<Pod>()
    fun requested() = pods.fold(Res(0, 0)) { acc, p -> acc + p.req }   // 已分配量（按 requests 累加）
    fun free() = capacity - requested()
    /** 已分配比 =(CPU 已用比 + 内存已用比)/2；extra 模拟"再放一个 Pod 之后" */
    fun usageRatio(extra: Res = Res(0, 0)): Double {
        val r = requested() + extra
        return (r.cpu.toDouble() / capacity.cpu + r.mem.toDouble() / capacity.mem) / 2.0
    }
}

/** 集群 + 调度器（kube-scheduler 的简化合体） */
class Cluster(val nodes: List<Node>) {
    fun node(name: String) = nodes.first { it.name == name }
    private fun pct(d: Double) = "%.0f".format(d * 100) + "%"

    // 阶段一：过滤（Predicates）——淘汰不满足硬约束（资源、nodeSelector）的节点
    fun filter(pod: Pod): Pair<List<Node>, List<String>> {
        val pass = mutableListOf<Node>()
        val why = mutableListOf<String>()
        for (n in nodes) {
            val labelBad = pod.nodeSelector.entries.firstOrNull { n.labels[it.key] != it.value }
            when {
                labelBad != null -> why.add("[过滤淘汰] ${n.name}：nodeSelector 不满足（要 ${labelBad.key}=${labelBad.value}）")
                !pod.req.fitsIn(n.free()) -> why.add("[过滤淘汰] ${n.name}：资源不足（剩 ${n.free()}，要 ${pod.req}）")
                else -> pass.add(n)
            }
        }
        return pass to why
    }

    // 阶段二：打分（Priorities）——放置后已分配比最小者胜（LeastRequested 思路：往最空的节点放）
    fun trySchedule(pod: Pod): Boolean {
        println("── 调度 ${pod.name}（请求 ${pod.req}，优先级 ${pod.priority}）")
        val (pass, why) = filter(pod)
        why.forEach { println("   $it") }
        if (pass.isEmpty()) {
            println("   [打分] 无节点通过过滤，进入抢占（Preemption）评估")
            return preempt(pod)
        }
        println("   [打分] 候选：" + pass.joinToString("、") { "${it.name}（放置后已分配比 ${pct(it.usageRatio(pod.req))}）" })
        val best = pass.minByOrNull { it.usageRatio(pod.req) }!!
        bind(pod, best.name)
        return true
    }

    // 抢占：在标签匹配的节点上，驱逐"优先级更低"的 Pod，直到腾出的资源够用
    fun preempt(pod: Pod): Boolean {
        for (n in nodes) {
            if (pod.nodeSelector.any { (k, v) -> n.labels[k] != v }) continue
            val victims = n.pods.filter { it.priority < pod.priority }.sortedBy { it.priority }
            var freed = Res(0, 0)
            val chosen = mutableListOf<Pod>()
            for (v in victims) {
                if (pod.req.fitsIn(n.free() + freed)) break
                chosen.add(v); freed += v.req
            }
            if (!pod.req.fitsIn(n.free() + freed)) continue
            for (v in chosen) {
                n.pods.remove(v); v.running = false; v.node = null
                println("   [驱逐] ${n.name} 上的 ${v.name}（优先级 ${v.priority}）被 ${pod.name}（优先级 ${pod.priority}）挤出，回到 Pending")
            }
            bind(pod, n.name)
            return true
        }
        println("   [结果] ${pod.name} 抢占也无果，保持 Pending —— 真实 K8s 里它会留在调度队列等待")
        return false
    }

    private fun bind(pod: Pod, nodeName: String) {
        val n = node(nodeName)
        n.pods.add(pod)
        pod.node = nodeName; pod.running = true
        println("   [绑定] ${pod.name} → $nodeName（该节点已分配比 ${pct(n.usageRatio())}，剩余 ${n.free()}）")
    }

    fun dump() {
        println("── 集群终态")
        for (n in nodes) {
            println("   ${n.name}：容量 ${n.capacity}，已分配 ${n.requested()}（${pct(n.usageRatio())}），标签 ${n.labels}")
            n.pods.forEach { println("      · ${it.name}（${it.req}，优先级 ${it.priority}）") }
        }
    }
}

/** HPA 模拟：期望副本 = ceil(负载 / 单副本目标承载)，夹在 [min, max]，再增删 Pod 并触发调度 */
class Hpa(
    private val cluster: Cluster,
    private val app: String,
    private val podReq: Res,
    private val priority: Int,
    private val rpsPerReplica: Int,
    private val min: Int,
    private val max: Int
) {
    private val live = mutableListOf<Pod>()
    private var seq = 0
    private fun running() = live.count { it.running }

    fun tick(loadRps: Int) {
        val raw = ceil(loadRps.toDouble() / rpsPerReplica).toInt()
        val desired = raw.coerceIn(min, max)
        println("── HPA[$app] 负载 ${loadRps} rps ÷ 单副本目标 ${rpsPerReplica} rps = $raw → 限制在 [$min, $max] → 期望 $desired 副本（当前 ${running()}）")
        while (running() < desired) {
            val pod = Pod("$app-${"%02d".format(++seq)}", podReq, priority)
            live.add(pod)
            if (!cluster.trySchedule(pod)) break   // 集群放不下就停（真实 K8s 里新 Pod 停在 Pending）
        }
        while (running() > desired) {
            val victim = live.last { it.running }
            cluster.node(victim.node!!).pods.remove(victim)
            victim.running = false
            println("   [缩容] 删除 ${victim.name}（释放 ${victim.req}），剩 ${running()} 个副本")
        }
    }
}

fun main() {
    println("== MiniScheduler：两阶段调度 + 优先级抢占 + HPA 扩缩模拟 ==\n")
    val cluster = Cluster(
        listOf(
            Node("node-a", Res(4000, 8192)),                          // 机房主机 4C/8G
            Node("node-b", Res(4000, 8192)),                          // 机房主机 4C/8G
            Node("edge-01", Res(2000, 4096), mapOf("edge" to "true")) // 车间边缘节点 2C/4G
        )
    )
    println("节点：node-a(4C/8G)、node-b(4C/8G)、edge-01(2C/4G, 标签 edge=true —— MES 边缘网关专用)\n")

    println("【第 1 步】桶装水商城 + MES 的日常负载逐个入队：")
    val pods = listOf(
        Pod("order-api-01", Res(1000, 1536), 10),                        // 订单服务
        Pod("order-api-02", Res(1000, 1536), 10),
        Pod("stock-api-01", Res(600, 1024), 10),                         // 库存服务
        Pod("dispatch-01", Res(400, 768), 10),                           // 配送排线
        Pod("report-batch-01", Res(1500, 2048), 1),                      // 低优先级：月末报表批处理
        Pod("report-batch-02", Res(1500, 2048), 1),
        Pod("mes-edge-gw-01", Res(800, 1024), 20, mapOf("edge" to "true")), // MES 边缘网关，只能上边缘节点
        Pod("monitor-agent-01", Res(200, 256), 50)                       // 监控 Agent，最高优先级
    )
    pods.forEach { cluster.trySchedule(it) }

    println("\n【第 2 步】MES 加开第二个边缘网关副本（高优先级 + nodeSelector=edge），把 stock-api-01 从边缘节点挤走：")
    cluster.trySchedule(Pod("mes-edge-gw-02", Res(800, 1024), 20, mapOf("edge" to "true")))
    println("—— 被驱逐的 stock-api-01 重新入队：")
    cluster.trySchedule(pods[2])   // 只能回机房节点

    println("\n【第 3 步】秒杀大促：HPA 按负载扩缩 seckill-api（单副本目标 250 rps，副本范围 2~5）：")
    val hpa = Hpa(cluster, "seckill-api", Res(800, 1024), 10, 250, 2, 5)
    hpa.tick(150)    // 平日
    hpa.tick(900)    // 大促洪峰
    hpa.tick(100)    // 洪峰回落

    println()
    cluster.dump()
}
```

五个解读点：

1. **两阶段的分工**：过滤处理**硬约束**（资源不够、nodeSelector 不匹配——直接淘汰，没有商量余地），打分处理**软偏好**（三个节点都能放，选放置后最空的那个）。`mes-edge-gw-01` 的调度轨迹展示了 nodeSelector：机房两台主机再空也与它无关。而打分用“放置后已分配比最小”，正是 K8s 默认的 LeastRequestedPriority 思路——注意它看的是**按 requests 累加的分配量**，不是实际用量：调度决策必须基于声明值，真实用量是事后才知道的。
2. **Pending 是答案而不是故障**：第 3 步大促扩容时，`seckill-api-02` 与 `seckill-api-04` 先后无节点通过过滤——三台节点都腾不出 800m 整块，调度器不硬塞、不超卖，转入抢占评估；被驱逐的 `report-batch-01/02` 优先级垫底、无更低的可抢，只能留在队列里（本模拟到此为止——真实 K8s 中 Job/Deployment 控制器会持续重建它们，洪峰过后资源宽裕即可归位）。反直觉但正确：**拒绝调度比错误调度便宜得多**（超卖导致的节点内存不足驱逐是不可控雪崩，Pending 是可控排队）。
3. **抢占 = 优先级的兑现**：第 2 步是完整的一次——`mes-edge-gw-02`（优先级 20 + nodeSelector=edge）在过滤阶段机房两台被标签淘汰、edge-01 剩 600m 不够 800m，无节点通过、进入抢占评估；调度器在标签匹配的 edge-01 上找到优先级更低的 `stock-api-01`（10），驱逐它、安放前者。这就是 PriorityClass 存在的意义：**资源不够时，决定谁留下来的是声明的优先级，而不是先来后到**。被驱逐的 stock-api-01 重新入队、落到 node-b——抢占不销毁工作，只是把它挪走。
4. **HPA 公式与缩容节奏**：`期望副本 = ceil(负载 ÷ 单副本目标承载)` 是 K8s HPA（`desiredReplicas = ceil(当前副本 × 当前指标 ÷ 目标指标)`）的等价简化；`coerceIn(min, max)` 对应 minReplicas/maxReplicas。注意第 3 步里洪峰 900 rps 折算出 4 副本（900/250=3.6 向上取整），回落到 100 rps 时副本缩回 2——真实 HPA 还有一段默认 5 分钟的缩容稳定窗防抖动，扩容则是即刻的：**快扩慢缩**是弹性策略的通用准则。
5. **一个留下的隐患（正文 taint 的活教材）**：回看第 1 步——普通业务 `stock-api-01` 被“放置后最空”的打分放到了 edge-01（28% 低于两台机房的 36%）。本例只用了 nodeSelector（“必须去哪”），没有实现污点 taint（“谁都不许来，除非声明容忍”），于是边缘节点在资源宽裕时照样会被普通业务占据，直到第 2 步更高优先级的 MES 网关把它驱逐——靠优先级“事后纠偏”而不是从入口禁止。真实 K8s 给边缘节点加 `edge=true:NoSchedule` 污点后，stock-api 这种普通 Pod 在过滤阶段就进不了 edge-01——**“拉”与“推”两个方向的约束要同时用，部署拓扑才锁得住**。
