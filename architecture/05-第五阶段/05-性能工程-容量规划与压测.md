## 4. 性能工程

性能工程由三件事组成一个闭环：**容量规划**把业务目标“算”成资源数量；**压测**把算出来的承诺“验”成实测水位；**性能定位**在承诺失守时把问题“修”回水位之内。三件事漏一件的下场各有不同：只算不验，规划数字只是主观估算；只验不算，压测结果没有回填到下次规划，白压；出了问题不会定位，前两件事攒下的水位数据永远躺在纸面上。本节沿着这条主线展开，主线场景是秒杀（脉冲流量）与物联网平台（连接与写入洪峰），穿插桶装水商城与 MES。

### 4.1 容量规划：把业务目标翻译成资源数量

秒杀的容量推演永远从两个问题开始：**流量有多少？每个环节能扛多少？**——这也是所有系统容量规划的通用方法，秒杀只是把数字放大到无法糊弄。

**第 1 步 流量估算**（读、写分开算）。业务设定：晚 8 点开抢，60 万用户到场，库存 1000 件。

| 流量项 | 推演 | 结果 |
|---|---|---|
| 商品页读 | 60 万用户开抢前每 3 秒刷新一次详情页 | 600000 / 3 ≈ **20 万 QPS**（读） |
| 下单写 | 点击集中在开抢后 10 秒内（脉冲） | 600000 × 80% / 10 ≈ **4.8 万 QPS**（写） |
| 真实成交 | 库存只有 1000 件 | 支付仅 1000 笔/15 分钟，压力可忽略 |

**第 2 步 分层消化**（关键认知：20 万读 QPS 和 4.8 万写 QPS 绝不能原样打到应用层）：

| 环节 | 手段 | 到达下游的流量 |
|---|---|---|
| 商品页读 | 页面静态化 + CDN + 多级缓存，回源约 5% | 应用层约 1 万 QPS，DB 近乎 0 |
| 下单写 | 网关限流 + MQ 异步排队削峰（呼应[第三阶段-限流熔断](../03-第三阶段/01-分布式系统核心技术.md)） | 同步链路只做校验 + Redis 预扣；落库按 MQ 消费速率 2000/s 恒定 |
| 库存扣减 | Redis 原子扣减防超卖，DB 乐观锁兜底 | Redis 约 4.8 万 QPS，DB 最终 1000 次 |

**第 3 步 实例数**：同步下单链路（校验+预扣）承接 4.8 万 QPS，压测得出单实例在 P99 < 300ms 水位下稳定 2000 QPS（依赖 4.2）→ 48000 / 2000 = 24 → 加约 30% 冗余 ≈ **32 实例**（冗余不是给流量的，是给发布摘流量与单机故障的）。

**第 4 步 全链路核对**：应用够了 ≠ 系统够了。DB 连接数、Redis 分片与热点 key、MQ 堆积与消费速率、第三方（支付渠道限频 500 QPS 就得排队/合并）逐项核对——**容量遵循木桶效应，取决于最短的板**。

要点：**脉冲系数**是因为流量不匀速，开抢前 10 秒的瞬时 QPS 是分钟均值的数倍，按分钟均值规划必然失守。容量规划与限流熔断是一对：规划是“算”出来的承诺，限流是“守”住的底线，超预期流量靠限流与降级兜底而不是无限扩容；秒杀完整拆解见[第六阶段-实战与案例分析](../06-第六阶段/01-实战与案例分析.md)。

**对照：物联网平台的写入型洪峰**。方向相反、方法相同——先算流量：100 万设备 × 每 10 秒上报 1 条 = **10 万条/秒**（入口写洪峰，持续而非脉冲）→ 接入网关无状态水平扩展 → MQ 削峰 → 消费端**批量聚合写入**：每批 500 条，10 万 / 500 = 200 批/秒，实测单消费者实例稳定扛 60 批/秒 → 4 个消费者实例 + 1 冗余。读洪峰拼缓存与静态化，写洪峰拼队列与批量化；容量指标从“每秒请求数”变成“每秒写入点数 + 批大小 + 堆积水位”。

物联网平台的连接洪峰是流量估算的另一个变体：100 万设备同时在线是**稳态连接数**，断电恢复后的百万设备**重连补传**才是洪峰——连接数洪峰压的是接入网关的内存与文件句柄（每条 TLS 连接吃几 KB~几十 KB），补传洪峰压的是入口吞吐与 MQ 堆积。两者时间尺度、压的资源都不同，要分开估。规划时用“重连风暴”这个更坏的数字：按运维经验，市电恢复后 5 分钟内 80% 设备会涌回来，按 4 分钟完成 80 万条连接重建估算——每秒 3300+ 条新建握手，这才是接入网关的容量目标。

#### 4.1.1 容量规划四步法：从两个案例里沉淀的通用方法

把上面两段推演（读洪峰的秒杀、写洪峰的物联网）抽象掉业务外皮，剩下的骨架就是任何系统通用的**容量规划四步法**：

| 步骤 | 核心动作 | 关键产出 | 常见错误 |
|---|---|---|---|
| ① 定目标 SLA | 和业务对齐“服务承诺”：多少用户、什么体验、允许多大错误率 | 一组**可验证**的指标：目标 QPS / P99 时延上限 / 错误率上限 / 可用性目标 | 目标写成“系统要快”“用户体验要好”——不可验证的 SLA 等于没有 SLA |
| ② 估流量模型 | 日活 × 峰值系数 × 脉冲系数，读写/连接/消息分开算 | 各条链路的目标流量（读 QPS、写 QPS、条/秒、连接数） | 拿日均值当峰值容量（峰均比 10 倍时差一个数量级）；只算分钟均值忽略秒级脉冲 |
| ③ 算资源 | 利特尔法则算并发需求 + 压测出单机水位 → 相除得实例数 | 每层需要的实例数、连接数、分片数 | 拿官方跑分或“理论 TPS”当单机水位；只算应用层，忘了 DB 连接、MQ、第三方限频这些短板 |
| ④ 留水位 | 目标流量对照水位线纪律折算成“可装载上限” | 水位红线：常态运行 ≤ 峰值容量的 40% | 把“压测极限”当“可运行容量”；水位 80% 时一次滚动发布摘流量就把集群推进过载 |

四步各自有一条工程判据：

- **第①步判据：SLA 必须可测量、可否决。**“P99 < 300ms、错误率 < 0.1%，压测不过不上线”是一句话 SLA；它是后面三步的总开关。注意 SLA 的类型要匹配流量形态：桶装水商城周期购“每周一早 6 点批量生成配送单”的承诺是“7 点前全部生成完”——这是**批处理 SLA**（按时完成量），别拿在线接口的 P99 时延去套它；MES 产线看板“数据延迟 ≤ 5 秒”是流式 SLA，要用端到端延迟分布验证。
- **第②步判据：三个系数是三台不同倍率的放大镜。**峰值系数放大“日内波动”（电商高峰小时 / 日均小时约 3~5 倍），脉冲系数放大“秒级尖峰”（秒杀开抢瞬时可达分钟均值几十倍），恢复系数放大“故障后的报复性回流”（物联网重连风暴、缓存集体失效）。秒杀的数在原推演里已经算过：20 万读 + 4.8 万写，全是脉冲系数的产物；物联网的数则是稳态（10 万条/秒持续）+ 恢复系数（重连补传）的组合。反例：某团队按“日订单 50 万 ÷ 86400 秒 ≈ 6 QPS”给下单接口做容量——差了四个数量级，上线当晚就被晚高峰压垮。
- **第③步判据：分子分母都要“实测”。**分子（并发需求）用利特尔法则算（下一小节），分母（单机水位）只能压测得出（4.2 节）——厂商跑分、同事口述、去年档案都只能当先验，不能当承诺。
- **第④步判据：水位是纪律不是建议。**40% 水位线的完整算账见 4.1.3；它必须写进发布准入检查（容量复审时逐集群过一遍），否则一定会在大促前夜被“先上线再说”突破。

第②步的三个系数是流量估算的全部杠杆，取值来源速查：

| 系数 | 放大什么 | 典型量级 | 取值依据 |
|---|---|---|---|
| 峰值系数 | 日内波动（高峰小时 / 日均小时） | 电商 3~5 倍；办公类系统 2~3 倍（上班打卡脉冲） | 自己的历史监控曲线，取近 30 天最大小时 |
| 脉冲系数 | 秒级尖峰（瞬时 / 分钟均值） | 秒杀数十倍；推送唤醒 5~10 倍 | 业务方给的到场与转化预估 + 历史活动复盘 |
| 恢复系数 | 故障后的报复性回流（重连/补传/缓存重灌） | 物联网重连 5 分钟内涌回 80%；缓存集体冷启动 | 运维演练与故障复盘数据，没有就先按 2 倍估并排演练 |

注意三个系数**缺一不可**：只看峰值系数会被秒级脉冲击穿，只看脉冲系数会低估全天成本——规划用的“峰值”必须是三者放大后的最坏叠加。

#### 4.1.2 利特尔法则：容量推演的第一公式

**L = λ × W**——系统内平均请求数（并发数 L）= 到达率 λ × 平均停留时间 W。这是排队论里少数既严格成立又一眼能用的公式，容量规划的第③步全靠它。它有两种读法，两种都要会用：

- **正着读（算容量需求）**：已知到达率和目标停留时间，求需要多少并发槽位。秒杀例：同步下单链路到达 4.8 万 QPS、要求平均停留 ≤ 250ms → L = 48000 × 0.25 = 12000 并发；单实例压测水位 2000 QPS（单实例自己的并发能力是另一维度，见下）→ 折算实例数。
- **反着读（压测回检）**：压测时已知并发数和实测吞吐，求平均停留 W = L / X。这是审压测数据自洽性的利器——4.2.4 的最小压测器输出里专门印了这一行，数字对不上就说明压测本身有问题。

用桶装水商城算个直观账：配送员 App 的“今日线路”接口，300 名配送员每 10 秒刷新一次 → λ = 30 请求/秒；接口平均停留 200ms → L = 30 × 0.2 = **6 并发**。一台普普通通的实例就能扛。但如果哪天接口停留恶化到 2 秒——到达率一个请求都没涨——L 就变成 60，并发需求翻了 10 倍。**停留时间是容量需求的乘数：优化时延就是在直接省机器。**这就是性能、容量、成本三者在一条公式里会师的地方。

公式很简单，但“过载时会发生什么”值得亲手跑一遍：下面的 Kotlin 示例用信号量模拟 64 个并发槽位的服务，按固定节奏灌入 200 请求/秒，对比停留时间 250ms（稳定）与 1000ms（过载）两种情形，实时采样“排队 + 处理中”的在途并发，并对照利特尔法则的理论值。

```kotlin
import java.util.concurrent.Semaphore
import java.util.concurrent.atomic.AtomicInteger
import kotlin.concurrent.thread

/**
 * 利特尔法则直观模拟：L = λ × W（并发数 = 到达率 × 平均停留时间）
 *
 * 场景A（稳定）：到达 200/s，平均停留 250ms，服务容量 64 并发
 *   → 需求 L = 200 × 0.25 = 50 < 64：队列不堆积，实测在途并发 ≈ 50
 * 场景B（过载）：平均停留升到 1000ms，其他不变
 *   → 需求 L = 200 × 1 = 200 > 64：超出的 (200 - 64) 个/秒 只能排队，
 *     4 秒灌入窗口结束时队列 ≈ 136 × 4 ≈ 544，且持续增长
 */
fun simulate(name: String, arrivalPerSec: Int, serviceMs: Long, capacity: Int, windowSec: Int) {
    val slots = Semaphore(capacity, true)    // 服务容量：同时最多处理 capacity 个请求（公平模式 = 先到先服务）
    val inService = AtomicInteger(0)     // 正在处理
    val queued = AtomicInteger(0)        // 在排队等待空位
    val completed = AtomicInteger(0)
    val samples = mutableListOf<Int>()   // 每 100ms 采样一次在途并发 = 排队 + 处理中
    val sampler = thread(isDaemon = true) {
        while (true) {
            samples.add(queued.get() + inService.get())
            try { Thread.sleep(100) } catch (_: InterruptedException) { return@thread }
        }
    }

    val startAt = System.nanoTime()
    val intervalNs = 1_000_000_000L / arrivalPerSec
    val workers = mutableListOf<Thread>()
    for (i in 0 until arrivalPerSec * windowSec) {
        val due = startAt + i * intervalNs          // 按固定节奏放请求进来
        while (System.nanoTime() < due) Thread.sleep(1)
        val w = thread(isDaemon = true) {
            queued.incrementAndGet()
            slots.acquire()                          // 排队抢一个服务空位
            queued.decrementAndGet()
            inService.incrementAndGet()
            try { Thread.sleep(serviceMs) }          // "处理耗时" = 停留时间
            finally {
                inService.decrementAndGet()
                slots.release()
                completed.incrementAndGet()
            }
        }
        workers.add(w)
    }
    val queuedAtWindowEnd = queued.get()             // 最后一个请求到达时的队列长度
    workers.forEach { it.join() }
    sampler.interrupt()
    sampler.join()

    val avgConc = samples.dropLast(3).average()
    println("=== $name ===")
    println("λ=$arrivalPerSec/s，W=${serviceMs}ms，服务容量=$capacity 并发，${windowSec}s 共灌入 ${arrivalPerSec * windowSec} 个请求")
    println("利特尔法则需求 L = λ×W = ${arrivalPerSec * serviceMs / 1000.0} 并发")
    println("实测平均在途并发（排队+处理中） ≈ ${"%.1f".format(avgConc)}，完成 ${completed.get()} 个")
    println("灌入窗口结束时队列长度 = $queuedAtWindowEnd（理论值 ${(arrivalPerSec - capacity * 1000 / serviceMs).coerceAtLeast(0) * windowSec}）")
    println()
}

fun main() {
    println("利特尔法则：L = λ × W。需求并发超过服务容量时，超出的部分不会消失，只会排队。")
    simulate("场景A 稳定：W=250ms", arrivalPerSec = 200, serviceMs = 250, capacity = 64, windowSec = 4)
    simulate("场景B 过载：W=1000ms", arrivalPerSec = 200, serviceMs = 1000, capacity = 64, windowSec = 4)
    println("结论：到达率不变，停留时间从 250ms 涨到 1s，并发需求 50 → 200；")
    println("容量 64 不变，多余的 136 个/秒全部压进队列——延迟恶化不是变慢，是排队。")
}
```

编译运行输出（kotlinc 2.2.20，JDK 21）：

```text

=== 场景A 稳定：W=250ms ===
λ=200/s，W=250ms，服务容量=64 并发，4s 共灌入 800 个请求

=== 场景B 过载：W=1000ms ===
λ=200/s，W=1000ms，服务容量=64 并发，4s 共灌入 800 个请求
利特尔法则需求 L = λ×W = 200.0 并发
实测平均在途并发（排队+处理中） ≈ 306.2，完成 800 个

```

三个读数要点：

1. **场景 A 实测在途 ≈ 48.9 ≈ 理论 50**：利特尔法则对“需求并发”的预测精准到个位数；差的一两点是采样与调度抖动。
2. **场景 B 窗口结束队列 543 ≈ 理论 544**：过载时队列增长速率严格等于“到达率 − 服务速率”（200 − 64 = 136 个/秒），4 秒就是 544 个——堆积是**线性、可预测**的，这也是 MQ 堆积监控能提前告警的数学基础。
3. **过载时公式怎么读**：L = λW = 200 是“需求”，容量 64 是“供给”，需求超过供给的部分不会消失，只会变成队列——所以延迟恶化的本质不是“每个请求变慢了”，而是“队伍变长了”。

❌ 反例：“接口要扛 1000 QPS，我单实例开 250 个工作线程，一个实例就够了。”——把线程数当容量，完全没算 W。若平均停留 300ms，1000 QPS 需要 L = 300 > 250 线程，必然排队；停留涨到 500ms，需要 500。✅ 修正：先用压测/Trace 量出 W，再让 L = λW 对齐容量，最后留水位。另一个常见误读是把公式里的 W 只算“处理耗时”不算排队——利特尔法则里的停留时间必须是**端到端**的（从进系统到出系统），只统计处理段会系统性低估并发需求，这正是排队段在监控里“不可见”、而在压测里原形毕露的原因。

工程判据：**容量工作点钉在 ρ ≤ 0.7~0.8**（ρ = 到达率 / 服务速率）。ρ > 0.9 处的“极限吞吐”是自欺——真实流量的抖动、GC 停顿、慢查询会把工作点瞬间推过 1，队列爆炸、延迟雪崩（排队论与“留 30% 余量”的完整论证见[第一阶段-架构质量属性](../01-第一阶段/04-架构质量属性.md) 3.2.1）。

#### 4.1.3 水位线纪律：为什么是 40% 而不是 80%

原推演第 3 步那句“冗余不是给流量的”值得展开成一条纪律：**常态运行水位 ≤ 峰值容量的 40%**。40% 的账是这么算的——

1. **发布摘流量**：滚动发布期间每个批次要摘掉一批节点（见[部署与发布策略](03-部署与发布策略-CICD与灰度.md)），摘流量瞬间剩余节点要吃下全量。40% 水位意味着流量翻倍仍在线性区内，发布窗口从容。
2. **单机/单分片故障**：一台宕机，它的份额瞬时压向同伴；40% 水位让这次冲击落在余量里，而不是触发级联过载（一台过载变慢 → 重试风暴 → 全集群雪崩，机理见[高可用与稳定性](../03-第三阶段/06-高可用与稳定性-限流熔断与多活.md)）。
3. **流量自身抖动**：规划用的“峰值”是估算，真实脉冲可能再高 50%；40% 水位给估算误差留了位置。

反过来看 80% 水位的下场：发布摘掉 1/4 节点 → 每台负载从 80% 跳到 107% → 队列爆炸 → 健康检查超时摘除更多节点 → 雪崩。**水位线的本质是给“下次坏事情”预留的跑道，不是资源浪费。**三种让水位数字失真的造假手法要警惕：按压测极限算水位（极限 ≠ 可运行容量）；按均值算水位（峰均比被抹平）；按集群均值算水位（热点 key 让个别 Redis 分片 95% 而集群均值 30%——木桶效应在分片内部重现）。水位审计的正确做法是**逐实例、逐分片看峰值**，每季度做一次（节奏见文末），日常由监控自动计算“实测峰值 / 实测容量”并超线告警。

MES 的水位账有个独有形状：白班/夜班**交接的 10 分钟**，500 个终端同时登录 + 看板全量刷新 + 交班报表导出三件事叠加，瞬时负载可达日常 5 倍。MES 的容量水位必须按“交接脉冲”核算，按日均负载规划的车间系统，永远在每天早 8 点准时卡顿。桶装水商城同理：月度订阅扣款批处理（月初 1 号）与会员日促销（每月 18 号）若在同一天叠加，水位按**最坏组合**算，不按单项峰值算。

水位线与容量数据最终要落成一个“总账本”——**容量档案**。它是 4.1（规划）、4.2（压测）、4.3（定位）三个环节共同读写的单一事实来源，最小字段集：

| 字段 | 内容 | 更新时机 |
|---|---|---|
| 链路与场景 | 哪条链路服务哪个场景（如“秒杀同步下单链路”“IoT 消费批量入库”） | 链路结构变化时 |
| 流量模型 | λ、W、峰值/脉冲/恢复系数及来源 | 季度复审重估 |
| 单机水位 | 压测得出的 QPS（或批/秒）+ 对应 P99 + 资源占用快照 | 每次基准回归后 |
| 规划实例数 | 四步法第③步的计算结果与冗余系数 | 季度复审 |
| 拐点与极限 | 压力测试的拐点位置、极限值、过载行为（优雅降级还是雪崩） | 大促全链路压测后 |
| 当前水位 | 实测峰值 / 实测容量，逐实例逐分片 | 每月巡检自动写入 |
| 版本与责任人 | 哪次压测、谁在何时更新 | 每次变更 |

没有档案，水位线只是口口相传、没有落档的记忆；有了档案，季度复审就是半小时的逐行核对，而不是一周的考古。

### 4.2 压测：验证容量的唯一手段

| 类型 | 目的 | 场景举例 |
|---|---|---|
| 基准测试 | 摸清单实例容量 | 秒杀下单链路单实例水位 QPS；IoT 消费者单实例每秒批量入库点数 |
| 负载测试 | 验证预期流量达标 | 1.2 倍预估峰值持续 30 分钟，P99 与错误率不破线 |
| 压力测试 | 找极限与崩溃方式 | 持续加压直至错误率上升，看先打满的是 CPU、DB 连接还是 Kafka 堆积 |
| 浸泡测试 soak | 长跑暴露泄漏 | 中位流量跑 6~24 小时，观察内存/连接是否缓慢上涨——IoT 的长连接与攒批缓冲尤其需要 |
| 尖峰测试 | 瞬时洪峰恢复力 | 秒杀 0 → 4.8 万 QPS 瞬冲；IoT 断电恢复后百万设备重连补传的二次洪峰 |

#### 4.2.1 压测类型谱系：每类跑多久、盯什么、怎么算过

上表的“目的”告诉你为什么压，这张谱系表补齐“跑多久”和“盯什么”——压测计划里写不清楚这两列的，多半会压成一笔糊涂账：

| 类型 | 典型时长 | 盯什么 | 达标判据 |
|---|---|---|---|
| 基准测试 | 单场景 10~30 分钟 | 单实例水位 QPS、资源占用曲线（CPU/内存/GC） | 产出可回填容量公式的单机水位；与上次基准对比无莫名劣化 |
| 负载测试 | 30~60 分钟 | P95/P99、错误率、各层水位（缓存命中率、DB 连接、MQ 堆积） | 预期峰值（通常取 1.2 倍）下 SLA 全绿，且**末段不劣化** |
| 压力测试 | 每档 10~15 分钟阶梯加压 | 第一个饱和的资源、崩溃方式、过载行为 | 说得出极限值与“先崩哪层”；过载时优雅降级（限流/排队）而非雪崩 |
| 尖峰测试 | 1~5 分钟瞬时冲击 | 冲击瞬间错误率、限流是否及时生效、峰值过后回落速度 | 瞬冲不雪崩；峰值过后 P99 在分钟级回落到基线 |
| 浸泡测试 | 6~24 小时（IoT 建议 ≥24h 覆盖完整上报周期） | 内存/连接数/文件句柄是否单调上涨、老年代 GC 趋势、慢查询累积 | 无泄漏迹象；堆内存与连接数呈锯齿平稳而非爬坡 |

五类有严格的先后依赖：**基准 → 负载 → 压力 → 尖峰 → 浸泡**，前一类是后一类的前提。连单机水位都没摸过就直接全链路加压，等于闭着眼睛开灯跳闸——压不出结论，只能收获一次事故。MES 报工链路压测的推荐顺序是个好范例：先基准（单实例报工 TPS 与 PLC 采集写入水位）→ 负载（1.2 倍班产量峰值）→ 浸泡（跑满一个完整班次 12 小时，含交接脉冲）——浸泡时长直接照着业务周期取，比凭主观判断的“24 小时”更有说服力。

每一类压测开跑前，压测计划至少要回答七个格子：**目标**（验证哪条 SLA）、**场景脚本**（压谁、按什么节奏、虚拟用户行为怎么拟真）、**环境**（影子/等比/单机外推）、**时间窗**（避开业务高峰与批处理窗口）、**值守**（谁盯盘、触达水位的停止条件）、**通过判据**（哪几条曲线达标才算过）、**产出物**（水位数据回填哪个档案条目）。七个格子里空三个以上的压测计划，大概率会压成一次“事故演练”。

Gatling（Kotlin DSL）秒杀压测脚本骨架：

```kotlin
val httpProtocol = http
    .baseUrl("https://staging.example.com")
    .header("X-Load-Test", "true")          // 压测标：全链路识别压测流量

val users = csv("users.csv").circular()      // 每个虚拟用户独立账号，避免缓存热点

val seckill = scenario("秒杀压测")
    .feed(users)
    .exec(http("商品页").get("/api/skus/1001")           // 读链路也要压：验证缓存命中与回源比例
        .check(status().`is`(200)))
    .pause(1)
    .exec(http("登录").post("/api/auth/token")
        .body(StringBody("""{"userId":"#{userId}"}""")).check(jmesPath("token").saveAs("tk")))
    .exec(http("下单").post("/api/seckill/orders")
        .header("Authorization", "Bearer #{tk}")
        .body(StringBody("""{"skuId":"1001","quantity":1}"""))
        .check(status().in(200, 429)))      // 429=限流排队，属预期行为，不算失败

setUp(seckill.injectOpen(rampUsersPerSec(500).to(48000).during(10.minutes))).protocols(httpProtocol)  // 阶梯加压复现脉冲
```

IoT 写洪峰的压测做法（与秒杀对照）：

- **模拟连接而非真实设备**：百万设备不可能真开机，用分布式施压集群模拟 MQTT 长连接与上报节奏（每施压节点扛约 1 万连接）；压的不是 HTTP P99，而是**入口吞吐、MQ 堆积、消费端写入速率**三者是否匹配——生产速率持续大于消费速率，堆积就会无限增长，直到磁盘或延迟先崩（背压与流控见[第三阶段](../03-第三阶段/01-分布式系统核心技术.md)）。
- **容量测算闭环**：压出“单消费者实例 60 批/秒、批 500 条、P99 入库延迟 800ms”这样的水位数据，回填 4.1 的公式。

❌ 反例：直接压生产且不打标——压测订单混进真实经营报表；库存被压成负数；“下单成功”的短信真实发给了用户；IoT 压测数据触发真实告警、自动生成工单派给了现场。✅ 修正：

1. 压测流量全链路打标（`X-Load-Test: true`），数据写**影子表**或压测后按标记清理；
2. 旁路统计：经营报表与告警规则按标记剔除压测流量；
3. 第三方依赖（真实支付渠道、短信网关、银行接口）用挡板/mock，只压自己的链路；
4. 压测全程盯 RED/USE 指标（见 [02-可观测性-日志指标与链路追踪](02-可观测性-日志指标与链路追踪.md) §1.3），触达水位立即停止——目的是找瓶颈，不是压垮环境；
5. 结果沉淀为容量档案：单机容量回填 4.1 的规划公式，形成“规划 → 压测 → 修正”闭环。

#### 4.2.2 压测环境的三种做法

在哪压，和用什么方式压一样重要。三种主流做法各有明确的适用边界：

| 做法 | 怎么做 | 优点 | 风险 | 适用 |
|---|---|---|---|---|
| 生产影子压测 | 压测流量全链路打标，走**真实生产集群**，数据写影子表、第三方走挡板 | 数据最真实：缓存分布、数据量级、网络拓扑、热点 key 全是真的 | 误伤生产（报表/告警/资金/库存）只能靠打标隔离兜底；需要全链路改造一次到位 | 大促场景的事实标准；有专职稳定性团队后才能上 |
| 等比缩放环境 | 搭 1/10 规模的同构环境（同版本中间件、同拓扑），按比例外推 | 成本可控、可反复压、可故意压垮 | 缩放后中间件行为**不等比**：缓存命中率、连接数、分片热点、GC 行为全会走样，外推误差常达数倍 | 日常回归、验证“代码变快了没有” |
| 单机外推 | 只压单实例得水位，乘以实例数 | 最便宜，任何团队都做得起，正是 4.1 第③步的输入 | 隐含“无共享”假设：共享层（DB、缓存、MQ）的真实瓶颈完全测不到 | 只用于算实例数；**不能当全链路结论** |

三种做法的可靠度排序是 影子 > 等比 > 单机外推，成本排序恰好相反，所以关键是知道每种做法**能回答什么问题**：单机外推回答“单实例扛多少”，等比环境回答“这次改动有没有让代码变快”，影子压测回答“系统到底扛不扛得住”。拿等比环境的结论当全链路结论是最常见的误用——桶装水商城在 1/10 环境压商品详情，缓存命中率 95%、DB 几乎零压力；放大 10 倍后热点商品 key 挤爆单个 Redis 分片、命中率跌到 70%，DB 瞬间接住 30% 穿透直接报警。**等比环境的外推前提是“各层行为不随规模突变”，而这个前提必须拿一次全链路影子压测校准过才可信。**反过来说，没有条件上影子压测的团队，单机外推 + 等比环境的组合也远好于不压——只是要给所有外推结论打上“待生产校准”的标签，并且上线后用真实流量爬坡（灰度放量）代替最后一次验证。

一旦决定上影子压测，开跑前的准入清单五项缺一不可：

1. **打标覆盖率核对**：入口 → 网关 → 应用 → 缓存 → DB → MQ → 下游服务的**每一段**都识别并透传压测标记——中间任何一段丢了标记，压测数据就从影子漏进真实（这是全链路压测事故的第一大来源）；
2. **影子设施就位**：影子表/影子队列建好，第三方依赖全部 mock；
3. **旁路剔除验证**：报表、告警、工单、资金四条旁路按标记剔除，且要**实际验证**过剔除逻辑（不是配置了就算）；
4. **施压容量核算**：施压集群自身能发出目标量且余量 3 倍以上（否则你测的是压测机）；
5. **应急与值守**：触达水位的停止条件、一键停压开关、压测期间的名单制值守。

#### 4.2.3 压测数据可信度五问

拿到一份压测报告，先过五问再谈数字。每问都配一句判据：

1. **回源了吗？**压测流量有没有真正穿透到 DB 和下游依赖，还是全被挡板挡住了？挡板只该挡第三方，自己的核心链路必须真跑。判据：压测期间 **DB QPS 与下游调用量必须同步上涨**——压测时应用层曲线猛涨而 DB 曲线纹丝不动，你测的是挡板不是系统。
2. **缓存预热了吗？**冷缓存第一轮全穿透，热缓存第二轮高得失真，两个数字能差 10 倍。判据：报告必须**声明缓存状态**（冷/热/半热）——负载与压力测试用热态，尖峰测试要专门补一次冷态（大促 0 点缓存可能被凌晨的定时任务洗掉，“缓存全冷的开抢第一秒”是独立场景）。
3. **压测机瓶颈排除了吗？**施压端先饱和（CPU、带宽、端口数、虚拟用户线程），测出来的 P99 是压测机自己的 P99。判据：施压机 CPU < 30%、带宽余量 3 倍以上；数字好得不敢相信时，先看施压机是不是已经宕机。单机施压不够就上分布式施压（Gatling/JMeter 都支持多注入器）。
4. **网络路径一致吗？**压测机常走内网直连应用，绕过了 CDN、WAF、网关、防火墙；生产用户走公网全链路，两者的时延构成完全不同。判据：压测入口与真实用户入口**一致**，或者明确声明差异并论证为什么可忽略（例如只关心应用层水位、网关已单独压过）。
5. **时间够长吗？**跑 1 分钟的“高吞吐”可能只是 JIT 预热后的一阵风；连接池泄漏、慢查询累积、内存碎片、GC 恶化都要时间才显形。判据：负载测试 ≥ 30 分钟，浸泡 ≥ 6 小时；**吞吐曲线跑到尾段仍然平稳**才算数，前高后低的曲线是慢性问题的自白书。

五问联动的效果：某团队报告“单实例 8000 QPS、P99 45ms”，按五问审出两处硬伤——压测机 CPU 92%（第 3 问，施压端先饱和）、压测脚本用同一个账号打所有请求（缓存热点 + 服务端本地缓存 100% 命中，第 1 问连带第 2 问）。换成真实账号分布重新压，实为 5200 QPS、P99 110ms。数字没有造假，**口径让数字失去了意义**——这就是五问存在的理由。

五问之外还有两个常被漏掉的检查，一并补上：**数据量等比吗**——压测库只有 1 万条订单而生产 1 亿条，索引深度、执行计划、缓冲池命中完全是两套行为，等比环境压出的 SQL 时延不能外推（建压测数据要按生产量级的 1/10~1/1 灌数）；**行为拟真吗**——虚拟用户的思考时间（pause）、购买转化漏斗（浏览 20 次、加购 3 次、下单 1 次）、新老会话比例，都决定到达模式与缓存分布，“全体虚拟用户取消思考时间连续开火”压出的吞吐天然偏高、缓存行为天然失真。

#### 4.2.4 最小压测器：亲手压出容量拐点

压测工具的原理并不神秘，用几十行 Kotlin 就能写出核心机制：N 个虚拟用户（线程）按闭环模式（每个用户完成一次请求立刻发起下一次）对目标施压，统计延迟分位数与吞吐。目标服务用信号量模拟“容量上限”——40 个并发槽位，每次处理 50ms±20ms 抖动，于是理论极限吞吐 = 40 / 0.05s = **800 QPS**，与客户端并发数无关。

```kotlin
import java.util.Collections
import java.util.concurrent.Semaphore
import kotlin.concurrent.thread

/**
 * 最小压测器：对"处理耗时 50ms±20ms 抖动"的模拟服务施压，
 * 用信号量模拟服务容量上限，演示"并发翻倍、吞吐不翻倍"的拐点。
 *
 * 服务容量 = 40 并发，单次处理均匀分布在 [30,70]ms（均值 50ms）
 * → 理论极限吞吐 = 40 / 0.05s = 800 QPS，与客户端并发数无关。
 */
object FakeService {
    // 第二个参数 true = 公平模式（FIFO 排队）。真实服务器的线程池并不严格公平，
    // 尾部延迟会比这个理想化模型更差——这里取理想队列以便对照利特尔法则。
    val capacity = Semaphore(40, true)
    fun handle() {
        capacity.acquire()                       // 超过 40 个并发请求就要排队
        try { Thread.sleep((30..70).random().toLong()) }  // 50ms±20ms 均匀抖动
        finally { capacity.release() }
    }
}

fun runPhase(label: String, concurrency: Int, seconds: Int): Double {
    val latencies = Collections.synchronizedList(ArrayList<Long>())
    val deadline = System.nanoTime() + seconds * 1_000_000_000L
    val startedAt = System.nanoTime()

    val workers = (1..concurrency).map { id ->
        thread(isDaemon = true, name = "vuser-$id") {
            while (System.nanoTime() < deadline) {
                val s = System.nanoTime()
                FakeService.handle()
                latencies.add((System.nanoTime() - s) / 1_000_000)  // 排队 + 处理的完整耗时
            }
        }
    }
    workers.forEach { it.join() }

    val wallSec = (System.nanoTime() - startedAt) / 1.0E9
    val sorted = latencies.toList().sorted()
    fun pct(p: Double): Long = sorted[((p / 100) * sorted.size).toInt().coerceIn(0, sorted.size - 1)]
    val tps = sorted.size / wallSec
    println("【$label】并发=$concurrency，施压 ${seconds}s")
    println("  完成 ${sorted.size} 个请求，吞吐 ≈ ${"%.0f".format(tps)} QPS")
    println("  延迟 P50=${pct(50.0)}ms  P95=${pct(95.0)}ms  P99=${pct(99.0)}ms  Max=${sorted.last()}ms")
    println("  利特尔法则回检：平均停留 W = 并发/吞吐 = ${"%.0f".format(concurrency / tps * 1000)}ms")
    return tps
}

fun main() {
    println("服务容量上限 = 40 并发，单次处理 50ms±20ms → 理论极限 ≈ 800 QPS")
    println()
    val t1 = runPhase("阶段1", concurrency = 100, seconds = 30)
    val t2 = runPhase("阶段2", concurrency = 200, seconds = 15)
    val t3 = runPhase("阶段3", concurrency = 400, seconds = 15)
    println()
    println("结论：并发 100 → 200 → 400（×2、×4），吞吐始终钉在容量极限附近；")
    println("加的并发没有变成吞吐，全部变成了排队延迟——这就是容量拐点。")
    println("阶段1~3 吞吐比：${"%.2f".format(t2 / t1)} / ${"%.2f".format(t3 / t1)}（并发比 2.0 / 4.0）")
}
```

编译运行输出（kotlinc 2.2.20，JDK 21）：

```text

【阶段1】并发=100，施压 30s

```

这份输出是理解“容量拐点”最直观的教材，四个读数：

1. **吞吐纹丝不动**：三个阶段并发翻 2 倍、再翻 4 倍，吞吐始终钉在 ~705 QPS（吞吐比 1.00 / 1.00）——**吞吐由服务容量决定，与客户端并发无关**，这是压测里最重要的单一结论。再注意理论极限 800、实测 705：公平信号量的线程唤醒与调度开销吃掉了约 12%——**算术算得出上限，折扣只有压测量得出来**，这正是“算”与“验”缺一不可的直接证据。
2. **延迟严格按利特尔法则上涨**：P50 = 141 → 281 → 564ms，与每阶段回检的 W = L/X = 142 / 283 / 566ms 完全吻合。加的并发没有变成吞吐，**全部变成了排队时间**。
3. **这个模型把队列理想化了，而真实系统更糟**：公平信号量 = FIFO 队列，排队时间高度确定，所以 P99（169ms）紧贴 P50（141ms）。真实线程池并不公平——刚干完活的线程往往立刻抢到下一个任务（barging 插队），轮空的调用方被饿出秒级长尾。开发本示例时先试了非公平版本：P50 纹丝不动（57ms），P99 却冲到 3.8~15 秒。两个版本一对照就看清了：**P99 与 P50 的差距里，藏着队列公平性这类实现细节**——这也是生产系统 P99 的恶化远比教科书曲线剧烈、且容量监控要盯 P99 的原因之一。
4. **拐点的判读口径**：吞吐曲线走平、延迟曲线加速上翘的那一点就是拐点；工作点必须钉在拐点左侧（对应 ρ ≤ 0.7~0.8）。压测报告如果只报“极限 800 QPS”不报“拐点在哪、过载后行为如何”，等于只给了油箱容积没给红线转速。

这个实验同时解释了一个日常错觉：“服务卡了就加客户端并发/线程池”——并发是**负载**不是**容量**，容量没变时加并发只会让队伍更长。真正的动作是把 40 个槽位变大（加机器、降停留时间），或者减少到达率（限流）。

瓶颈处理顺序：先看**架构**（加缓存、异步化、削峰、批量）→ 再看**配置**（索引、连接池、线程池、JVM）→ 最后才**加机器**。慢 SQL 与锁竞争，加机器无效。

### 4.3 性能问题的定位路径

容量规划与压测负责“事前”，定位路径负责“事中”：SLA 还是失守了，P99 告警响了，从现象到根因要走一条固定的路径。这条路径的价值在于**每一步都有明确的判据**，不靠灵感。

#### 4.3.1 从“P99 涨了”开始的定位决策树（文字版）

把决策树写成带判据的四个下钻步骤（指标采集与 Trace 手法详见[可观测性](02-可观测性-日志指标与链路追踪.md)）：

- **第 1 步：看 RED 三条曲线谁先动。**
  - 错误率先涨 → 容量击穿或依赖故障，直接跳第 2 步找“先饱和的资源”；
  - 流量先涨 → 脉冲（大促/推送）、攻击、或上游故障引发的重试风暴，先限流止血再定位；
  - 只有时延涨、错误率与流量都不动 → 资源饱和或锁/慢查询，继续往下。
  - 判据：**最先动的那条曲线决定排查方向**。
- **第 2 步：盘 USE 饱和度，找先到顶的资源。**按层扫：应用层（线程池活跃数与队列长度、GC 停顿频率）→ 缓存层（命中率跌幅、热点 key QPS）→ DB 层（慢查询数、锁等待、连接池等待线程数）→ 系统层（CPU、IO、带宽）。判据：**谁先逼近 100%，谁就是第一嫌疑人。**但要区分“凶手还是受害者”：DB 连接等待高，可能是上游线程池开太大挤兑连接（上游是凶手），也可能是慢查询占住连接不放（DB 是凶手）——第 3 步分辨。
- **第 3 步：Trace 分段对比，找变慢的那一段。**取告警时段与基线时段各若干条慢请求的 Trace，按 span 分段（网关 → 应用 → 缓存 → DB → 外部调用）对比耗时占比。判据：**自研代码段没变慢而总时长涨 = 等待下游**，此时优化自己的代码是无用功，方向是下游扩容/修复或加超时熔断。
- **第 4 步：定位到代码。**慢 span 内部：DB 段看慢 SQL 日志与执行计划；应用段抓火焰图（采样 profiling），对比发布前后两份火焰图。判据：**火焰图里新增的那块宽度就是嫌疑代码**；没有发布对照就和自己上周的比。

四个场景的速查表（每个场景第 2 步的“第一嫌疑人”不同）：

| 场景 | 现象 | 第 2 步先看 | 为什么 |
|---|---|---|---|
| 秒杀 | 开抢后 P99 飙升 | Redis 热 key QPS、限流队列长度 | 所有请求挤同一个库存 key，单分片先饱和 |
| 物联网平台 | 上报入库延迟上涨 | MQ 堆积水位、生产/消费速率差 | 写入型链路的瓶颈在管道，堆积是唯一必经的蓄水池 |
| MES | 看板数据慢半分钟 | 消费端攒批窗口、设备上报洪峰叠加 | 攒批批量变大是延迟的第一来源，先排除配置再找代码 |
| 桶装水商城 | 配送员刷新线路变慢 | DB 慢查询、连接池等待 | 线路查询是重读接口，慢 SQL 与连接挤兑最常见 |

把四步完整走一遍（MES 看板延迟半分钟的案例，指标采集手法与[02 篇 §1.5 的排障闭环](02-可观测性-日志指标与链路追踪.md)互为印证，这里只看决策）：看板延迟告警响起 → 第 1 步，错误率与流量平稳、只有时延涨，方向锁定“资源饱和或慢查询”；第 2 步，应用层线程池空闲、GC 正常，缓存命中率 99% 没跌，消费端攒批等待队列却到了 3000——第一嫌疑人锁定攒批队列；第 3 步，Trace 分段显示自研代码段耗时没变、总时长涨在“等待攒批窗口”这一段——等待的不是下游服务，是**攒批配置**；第 4 步，对照发布记录，上周把攒批窗口从 200ms 调到 2s（为了省入库批次）——根因是一次没有走容量记账的配置变更。全程没有看一行代码，四步判据就把“半分钟的延迟”钉在了两行配置上。

#### 4.3.2 性能优化收益的正确记账

定位到根因、改完代码，最后一道关卡是**记账**：一笔优化值不值得上线，不取决于单点指标提升了多少，而取决于综合账。公式化地说，任何性能优化申请要算三边：

> **收益 = 吞吐账（QPS / 实例数） × 时延账（用户体验与转化） − 成本账（资源 + 复杂度 + 风险）**

三个反例与一个正例，把账算给你看：

- ❌ **局部优化全局劣化**：把下单服务线程池从 100 调到 400，本服务 P99 降 40%，压测报告一片绿。一周后同一 DB 上的其他服务全线 P99 涨 3 倍——400 线程把共享 DB 连接池挤兑殆尽。判据：**优化前先声明“这次优化把压力转移给了谁”**，被转移方的容量账一起算、一起压。
- ❌ **低频接口滥加缓存**：给 30 个接口统一加 Redis 缓存，其中 20 个接口日调用量百级、命中率不到 20%。换来的吞吐增益可忽略，付出的却是失效一致性逻辑、内存成本与排查复杂度。判据：只优化“**流量 × 可优化时延**”乘积排序靠前的接口——先排序，再动手，别平均用力。
- ❌ **假收益**：“我重构了这段代码，应该快了”——没有复测就没有收益。判据：**收益必须用同一压测口径复测入账**（同一环境、同一数据量、同一缓存状态），否则不算数。
- ✅ **正例（秒杀链路的架构级优化）**：把“校验 + Redis 预扣”与“落库”分离——同步链路停留时间从 800ms 降到 250ms（利特尔法则下并发需求直降 2/3，吞吐账赢），用户开抢体验从秒级变成亚秒级（时延账赢），代价只是引入 MQ 与消费端幂等（成本账可控、收益覆盖）。**三边账都为正的优化才值得动架构**；只赢一边的优化，通常配置调优就够。

最后把闭环接回去：每一笔优化入账后，都要把新的单机水位回填 4.1 的容量档案、更新水位基线——性能工程的三个环节（规划、压测、定位）就通过这本**容量档案**首尾相接。

### 容量与压测联动年度节奏

容量规划（算）、压测（验）、定位（修）不能等出事才想起来，它们要落在日历上。一张可以直接抄走的节奏表：

| 节奏 | 频率 | 做什么 | 产出与准入 |
|---|---|---|---|
| 基准回归 | 每次版本发布前 | 对核心接口跑基准测试，对比上一版单机水位 | 水位无莫名劣化才放行发布；劣化则回滚或立项优化（对应[发布策略](03-部署与发布策略-CICD与灰度.md)的发布准入） |
| 水位巡检 | 每月（监控自动） | 自动计算各集群“实测峰值 / 实测容量”，超 40% 红线告警 | 水位报告；触发扩容排期或性能优化排期 |
| 全链路压测 | 大促/活动前：T-30 构建压测能力与打标改造 → T-14 首轮摸底 → T-7 修复后复压 → T-1 静态核对（预案、限流值、扩容单） | 按目标脉冲量做影子全链路压测，逐轮修复瓶颈 | 各轮压测报告；限流/扩容/降级预案三方确认签字 |
| 季度容量复审 | 每季度 | 重估流量模型（业务增长、新功能、旺季系数）；逐实例逐分片水位审计；重测单机基准；更新容量档案 | 容量档案新版本，回填 4.1 的全部公式 |
| 尖峰专项 | 按事件触发 | IoT 固件 OTA 前做“连接洪峰 + 补传”尖峰测试；MES 新产线接入前做交接脉冲负载测试 | 尖峰场景专项报告与预案 |

两个把节奏跑起来的实例：桶装水商城按季节做容量——夏季旺季前（季度复审）把配送员 App 与下单链路的水位目标上浮 50%，并给周期购批量生成窗口加做一次负载测试；物联网平台把 OTA 升级公告当作“计划内的连接风暴”，每次固件推送前尖峰测试必跑——**升级公告一发出，就是一场自己邀请的重连压测，与其被动挨打，不如主动压过**。容量工程做到最后，拼的不是某次漂亮的压测数字，而是这套“日常回归、事前演练、事后回填”的年度节奏。
