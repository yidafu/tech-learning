## 1. 混沌工程是什么

### 1.1 定义与动机

**定义**：混沌工程（Chaos Engineering）是在**受控实验**中向系统注入**真实世界的故障**，验证系统对湍流条件的**弹性假设**的学科。这句话里每个词都有分量：

| 关键词 | 含义 | 反面（不满足就不是混沌工程） |
|---|---|---|
| 受控 | 爆炸半径可控、有自动化停止条件、有审批与旁观者 | 生产上随手 kill 一个 pod，没有任何兜底思考 |
| 实验 | 有稳态指标、有可证伪的假设、可复现 | “弄坏了看看会怎样”的猎奇式破坏 |
| 真实故障 | 注入超时、分区、时钟漂移这类**真实形态**的故障，而不是 mock 的理想故障 | 单测里 mock 一个“准时抛异常”的依赖——真实的坏是“慢到超时”和“慢三秒后才报错” |
| 弹性假设 | 验证“你以为有兜底”和“兜底真的存在”之间的差距 | 从不写下预期结果，坏了才想起来找原因 |

**为什么有了测试和压测还不够？** [02-可观测性](02-可观测性-日志指标与链路追踪.md)讲过“已知/未知”四象限：单元与集成测试验证的是**已知输入下的正确行为**，压测验证的是**已知负载下的容量上限**（这就是[性能工程分册](05-性能工程-容量规划与压测.md)的地盘）。但分布式系统里最贵的故障往往不是“某个组件坏了”，而是**每个组件都各自正常、组合起来坏了**：A 依赖慢 200 毫秒导致线程池被占满，B 接口跟着全挂；缓存节点重启引发击穿，数据库被自己的恢复流量二次打死。这类“组合态故障”无法靠枚举输入来测试——组件间的相互作用空间是组合爆炸的，没人能枚举完。混沌工程的态度是：既然枚举不完，就在受控条件下**主动制造**其中一部分，看看系统真实的反应。

**演练 ≠ 混沌工程**。这两个词经常混用，但验证的对象完全不同：

| | 故障演练（drill） | 混沌实验（chaos experiment） |
|---|---|---|
| 验证什么 | **已知剧本**：预案写对了没有、人会不会执行 | **未知弱点**：系统在没预料到的故障下会怎样 |
| 类比 | 消防演习：疏散路线人人会走 | 随机拉响警报：看哪层楼没预案 |
| 成功标准 | 处置步骤按剧本完成，MTTR 达标 | 稳态指标在注入期间保持稳定；假设被证实**或**弱点被发现（发现弱点也是成功） |
| 剧本来源 | 预案库（历史事故沉淀） | 假设（对系统弹性的猜想，可能没有预案） |
| 典型产出 | 演练报告 + 剧本修订 | 实验报告 + 新弱点（转预案、转监控、转改进项） |

两者的关系是**上下游而非二选一**：演练成熟（预案库有货、处置动作形成肌肉记忆）是混沌实验的组织前提——连已知故障都处置不好，暴露未知弱点只会白添事故；反过来，混沌实验发现的每个弱点都该回流进预案库，变成下一次演练的内容。本文件第 2 节讲混沌实验，第 3 节讲演练与组织，就是这个顺序。

**起源：为什么恰恰是 Netflix 催生了混沌工程**。2010 年前后 Netflix 把整条业务从自营数据中心迁往 AWS。迁移中他们发现两件事：其一，云上虚拟机实例**会随机消失**——这是云的日常属性而非异常事件，AWS 不承诺单机存活；其二，单体时代“整机故障、备机顶上”的思路失效了，拆分成几百个微服务后，故障形态变成“**部分依赖时好时坏**”，组合态多到无法枚举。Netflix 的选择是放弃“预防一切故障”（做不到），转向“**与故障共存**”（让每个服务把“上游依赖随时会没”当作设计前提）。怎么让这个前提不是口号？2011 年他们公开了 Chaos Monkey：工作日随机挑生产实例**直接关掉**，工程师被迫设计出“少一台实例业务无感”的服务——因为你永远不知道猴子上周关掉了谁的机器。随后演化出延迟注入、区域级故障的整套工具（Simian Army），2014~2016 年方法学成形（Principles of Chaos Engineering），此后工具生态逐步成熟（Chaos Toolkit、Litmus、Chaos Mesh、AWS FIS、Gremlin 等）。**迁云之所以是催化剂**：不是云更不可靠（单机可靠性从来都不可靠），而是分布式把故障从“整机事件”变成了“依赖组合事件”，预防思维失效，只能靠实验思维。

### 1.2 什么时候不该做混沌实验：四条红线

混沌工程的前提是“实验有底线”。以下四条任一命中，实验必须取消或延期——**这四条红线本身比任何注入技巧都重要**：

1. **系统处于大事故恢复期**。刚出过 P0 且复盘未闭环、正在恢复数据或重建信任，此时再注入是往伤口上撒盐：新故障与旧故障的因果会被搅在一起，复盘归因失真，组织对混沌工程的信任也一次性烧光。恢复期内一切“非必要变更”都该冻结——混沌注入是变更，且是最刺激的一种（变更冻结纪律见[03-部署与发布策略](03-部署与发布策略-CICD与灰度.md)）。
2. **核心指标已异常**。实验的逻辑前提是“稳态可证明”：你得先能证明系统当前是健康的，注入后的对比才有意义。核心指标已经飘红时注入，等于给发烧病人做过敏试验——观察不到任何有效结论，只剩风险。
3. **没有停止条件**。说不清“出现什么情况立刻终止实验”，就不许开始。停止条件不是口头约定“不对劲就停”，而是自动化的断路器（指标阈值 + 时长上限 + 人工熔断开关，见 2.3）。“先注入，出事我再想办法”是赌博不是实验。
4. **没有监控**。注入之后看不到系统内部反应，等于蒙眼开车。[02-可观测性](02-可观测性-日志指标与链路追踪.md)的三支柱不是混沌工程的附属品而是**前置条件**：稳态指标要有数据源，关键链路要有 Trace，异常要有告警。可观测性不及格的系统，第一步是补观测，不是制造故障。

除了这四条硬红线，还有两条**软红线**同样别碰：组织没准备好（值班的 oncall 不知道有实验、没有书面授权——实验触发的告警打给一个毫不知情的值班员，就是把实验变成了事故）；合规窗口禁止（大促封网期、财务结算日、监管检查窗口，一切生产变更暂停，混沌也不例外）。

❌ **反例**：某团队“周五下午顺手 kill 了生产上一个看起来闲置的服务实例”，无审批、无停止条件、无人旁观——那个实例恰好被定时任务依赖，任务积压后连环重试把客服工单系统拖垮，值班工程师花了三小时才定位到“这是一次 nobody 知道的实验”。✅ **修正**：这不是混沌工程的失败，因为那根本不是混沌工程——受控、假设、停止条件、旁观者四样一样都没有。工程判据：**每次实验开始前过一遍五项检查**——稳态已证明、假设已书面化、停止条件已自动化、审批与通知已发出、回滚动作演练过。五项缺一，不做。

## 2. 混沌实验方法论

### 2.1 六步循环

混沌实验不是“随意破坏”，是一个标准的科学实验循环。六步环环相扣，每一步都配一个桶装水商城的例子——贯穿假设是：**“排线服务挂 1 台，下单不该受影响”**。

1. **定义稳态指标**：先用可测量的判据说明“什么叫正常”。稳态指标必须是**业务级**而非机器级——CPU 不高、内存正常不代表系统健康。例：下单成功率 ≥ 99.9%、下单接口 P99 < 300ms，且处于近 7 天基线的 ±10% 以内。这一步与可观测性分册的 SLI 定义是同一件事（SLI/SLO 的铺垫见[第一阶段：架构质量属性](../01-第一阶段/04-架构质量属性.md) 3.2.8）。
2. **提出假设**：把两件事写成一句可证伪的话——**注入什么 + 预期什么**。例：“关闭排线服务 3 个副本中的 1 个，下单成功率与 P99 不变（负载均衡自动摘除故障实例，重试覆盖在途请求）。”
3. **注入变量**：在最小爆炸半径上执行注入。例：只挑低峰期、只对 1 个实例、只注入 5 分钟。
4. **观察与假设对照**：盯着稳态指标看它是否保持，同时**留意预期之外的现象**——预期内的结果只回答“假设对不对”，预期外的现象才是新发现。例：P99 稳住了（假设成立），但发现用户推送通知服务的报错率涨了——没人预料到推送依赖排线服务的调用链。
5. **执行停止条件**：稳态指标跌破阈值、注入时长到达上限、人工熔断开关被按下——三者任一触发，立即撤销注入并恢复。这一步在实验开始前就已自动化，不是临时判断。
6. **结论沉淀**：假设成立 → 写进“弹性资产清单”（哪些机制被实验证实过有效）；假设不成立 → 弱点转三件事：改进项（带负责人期限）、预案更新（这次的处置路径入预案库）、监控补盲（这次靠人工发现的指标固化成告警）。实验报告归档：注入参数、系统版本、时间窗、全部数据——**不可复现的实验等于没做过**。

六步不是瀑布，是循环：第 6 步的每个结论都会催生下一个假设（“排线挂 1 台没问题，那挂 2 台呢？”），实验的成熟度就体现在循环的半径稳步扩大、而每次的结论都在加深对系统的理解。

> **片段**（示意，未单独编译运行）：六步循环落到工程上是“实验即代码”——实验声明成为可评审、可执行、可归档的产物：
> ```kotlin
> data class ExperimentSpec(
>     val name: String,                      // "排线单实例宕机-下单不受影响"
>     val steadyState: List<MetricQuery>,    // 第1步：稳态指标（成功率/P99 查询）
>     val hypothesis: String,                // 第2步：可证伪的假设
>     val injection: FaultAction,            // 第3步：注入什么、打谁、多大
>     val abort: AbortCondition,             // 第5步：三要素停止条件
>     val blastRadius: BlastRadiusPlan,      // 环境阶梯当前档位 + 回滚动作
>     val owner: String, val approvedBy: String
> )
> ```
> 字段就是六步的逐一落位——评审一份实验申请，就是对照六步逐一提问。

### 2.2 故障类型全景表

注入什么故障？下表是八个最常用的故障类型。重点看**常见未预期后果**一列——混沌实验的价值恰恰在这：每类故障都有一些“文档上没写、但生产上会咬人”的二阶效应。

| 故障类型 | 模拟的真实事故 | 常见未预期后果 | 典型发现 |
|---|---|---|---|
| 节点宕机 | 实例被云厂商回收、宿主机断电 | 长连接设备集体重连形成**重连风暴**；宕掉的恰好是热点缓存分片引发击穿；会话全丢、用户被批量登出 | 物联网平台百万设备重连无退避，恢复瞬间把接入层打爆——“故障恢复”比“故障”本身杀伤更大 |
| 网络延迟 | 交换机老化、跨机房链路劣化 | 慢调用占满线程池/连接池，拖垮**无辜接口**；超时预算没有沿调用链递减，末端永远超时 | A 依赖慢 200ms，B 接口跟着挂——没有舱壁隔离（超时预算分配见[第三阶段：高可用](../03-第三阶段/06-高可用与稳定性-限流熔断与多活.md) 5.3.1） |
| 网络分区 | 机房网络抖动、交换机分区 | 双主脑裂各写各的；分区两侧都在重试，恢复瞬间请求洪峰对撞；本地缓存旧数据被当作新数据读 | 订单与库存服务分区期间重复扣库存——幂等缺失（重试三前提见[第三阶段：高可用](../03-第三阶段/06-高可用与稳定性-限流熔断与多活.md) 5.3.2；CAP 里那个 P 的实战形态见[第二阶段：分布式理论](../03-第三阶段/02-分布式理论基础-CAP共识与一致性.md)） |
| 磁盘满 | 日志疯涨、临时文件堆积 | 进程**僵死而非崩溃**（写日志阻塞主线程）；WAL 满导致数据库拒写；告警系统自己也在那块盘上，一起哑掉 | 磁盘水位告警设了 95%，但日志轮转策略先把告警进程的写路径堵死了——“报警的人质也被劫持” |
| 证书过期 | 内部 mTLS/对外 TLS 证书到期 | 服务间调用全量握手失败；上游把它当业务错误重试，放大成雪崩 | 证书轮换全靠人工日历提醒，过期前没有任何告警——已知-已知问题靠事故发现，是可观测性的耻辱 |
| 时钟漂移 | NTP 断源、虚拟机时钟飘移 | 幂等键去重窗口错乱；限流的滑动窗口算错；Token 过期判定失灵——要么全拒要么全放 | 某台机器时钟快了 90 秒，签名校验把它的所有请求判为过期；代码用**本地时钟**做过期判断而不是信服务端——漂移测试专钓这一类 |
| 依赖限流 | 上游配额用尽、网关 429 | SDK 默认自动重试 3 次 → 流量放大 4 倍，限流被放大成全面拒绝（**重试风暴**） | 限流响应没有 Retry-After 处理、重试无退避无抖动——限流本来是保护，重试把它变成攻击（指数退避见[第三阶段：高可用](../03-第三阶段/06-高可用与稳定性-限流熔断与多活.md) 5.3.3） |
| 资源耗尽 | CPU 打满、连接池耗尽、内存压满 | GC 停顿拉长 → 健康检查超时 → 被 LB 摘除 → 剩余实例压力更大 → **假死循环**；连接池耗尽时抛错而非排队，错误直冲用户 | 连接池没有上限与排队策略；健康检查阈值比 GC 最长停顿还短，等于鼓励 LB 摘除正在自救的实例 |

这张表是“菜单”不是“计划”。真正该注入什么，取决于**你自己的依赖图**：先从链路追踪（[02-可观测性](02-可观测性-日志指标与链路追踪.md) 1.4）拉出核心业务的依赖拓扑，问“哪条边坏了伤害最大、而我们从来没验证过”，再从表里选对应故障类型。另一个实用次序：**历史上真实发生过的故障优先复现**——它自带业务影响证据，说服力最强，且预案已有雏形，实验安全边际大。

### 2.3 爆炸半径控制

混沌工程与“生产上乱来”的分界线就是爆炸半径控制。三个维度：

**维度一：注入规模阶梯——从最小开始，逐步放大**。单实例 → 单可用区 → 多区。每一档的前提是上一档的假设已被证实。永远先问：“这个故障历史上发生过吗？”发生过 → 从复现历史故障的最小等价注入开始；没发生过 → 从单实例开始。例：验证排线服务的容灾，先 kill 1 个实例（假设成立）→ 再压测单可用区整体失联的预案（进入下一档前需要重新评审，因为影响面性质变了）。

**维度二：实验环境阶梯——测试环境 → 预发 → 生产影子 → 生产低峰**。每一级通过才升下一级：

| 环境档位 | 能验证什么 | 验证不了什么 |
|---|---|---|
| 测试环境 | 代码逻辑对故障的基本反应 | 真实数据量、真实第三方限流、真实时钟与网络 |
| 预发环境 | 与生产同构的依赖组合下的反应 | 生产流量模式、真实用户行为 |
| 生产影子 | 真实流量进影子链路接受验证，不回写生产 | 影子链路的资源隔离与生产不完全一致 |
| 生产低峰 | 真实的一切 | 低峰的容量余量比高峰大——结论要打折换算 |

为什么最终必须去生产？因为**测试环境通过的弹性不是弹性**：测试环境里第三方支付不会真的限你流、数据量只有生产的百分之一、没有哪个租户在跑三个月前的批量导出。爆炸半径控制的意义不是“永远不去生产”，而是“带着证据、沿着阶梯、在受控的前提下去生产”。

**维度三：中止条件三要素**。三者独立生效，缺一不可：

1. **指标阈值**：稳态指标跌破预设线自动撤销注入。要业务级指标（下单成功率 < 99% 即中止），不是机器级——机器指标是滞后的间接信号。自动化是因为故障蔓延速度远快于人的反应。
2. **时长上限**：注入动作自带到期自动撤销（“最多持续 10 分钟”）。防止实验者本人被别的事情拖住、忘了自己在生产上挂着故障。
3. **人工熔断开关**：一键撤销全部注入的总闸，演练指挥全程可按。它是给“自动化也没料到的情况”留的最后一道闸——自动停止条件覆盖已知风险，人工开关覆盖未知风险。

> **片段**（示意，未单独编译运行）：三要素的最小实现骨架：
> ```kotlin
> class AbortCondition(
>     private val metric: MetricQuery,      // 业务级稳态指标
>     private val threshold: Double,        // 成功率下限等
>     private val maxDurationMs: Long,      // 注入时长上限
>     private val manualSwitch: KillSwitch  // 人工总闸
> ) {
>     fun shouldAbort(elapsedMs: Long): Boolean =
>         manualSwitch.isPulled() ||                          // 人工优先
>         elapsedMs > maxDurationMs ||                        // 到点即撤
>         (metric.read() ?: Double.NaN) < threshold           // 指标破线
> }
> ```
> 注意 `?: Double.NaN` 的语义：**读不到指标视为破线**——观测断了就当最坏情况处理，这是四条红线第 4 条的代码化。

围绕爆炸半径还有两条纪律容易被忽略。**通知与授权**：实验窗口要公告——谁、何时、注入什么、预期影响面、中止手段、联系人；值班与相关方书面确认。**回滚先于注入**：撤销注入的动作必须在注入前演练过——“kill 实例”的回滚是“把实例拉起来”，如果拉起来的路径本身没验证过，你的实验就建立在第二个未验证假设上。

## 3. 故障演练：从混沌实验到组织能力

### 3.1 演练剧本化：预案库、升级路径与演练日历

混沌实验发现弱点，演练把弱点变成肌肉记忆。演练能力的核心资产是**预案库**——每条预案是一个结构化条目，而不是一段自由文本：

| 字段 | 说明 | 桶装水商城示例 | MES 示例 |
|---|---|---|---|
| 故障场景 | 触发条件、影响面初判 | 排线服务整体不可用 | 边缘网关与 MES 断连 |
| 预期表现 | 降级行为、用户可见变化 | 下单转“次日排线”，承诺时效顺延 | 产线本地续采，恢复后补传 |
| 处置步骤 | 按序编号、每步可执行可验证 | ①确认熔断已开 ②切备用排线通道 ③公告配送时效 | ①确认车间自治运行 ②排障网关链路 ③核对补传数据完整 |
| 回滚动作 | 处置失败的退路 | 回退到纯人工排线（Excel 模板预置） | 手动导出本地缓存（脚本预置） |
| 责任人 | 值班角色而非具体人名，附升级路径 | 配送组 oncall → 排线负责人 | MES oncall → 车间自动化工程师 |
| 最后演练日期 | 超期未演练的预案标记待刷新 | 2026-10 季度演练通过 | 2026-09 桌面推演通过 |

预案从哪来？三个来源：历史事故的复盘产出（3.2）、混沌实验发现的弱点、以及**桌面推演时的空白**——推演到某一步发现“没人知道这一步该谁做”，这个空白本身就是预案素材。

演练的升级路径，每级验证的对象不同：

1. **桌面推演**（验证：预案写没写对）：团队围桌按预案口述走一遍，红队扮演“现实”不断追加条件（“备用通道也超时了怎么办？”）。零风险、成本低，新预案入库前必过一遍。
2. **红蓝对抗**（验证：人会不会执行）：蓝队守系统，红队按剧本注入故障或模拟攻击，掐表测 MTTR——预案上的每一步，真实执行比口头陈述慢多少，答案是常态三到五倍。对抗暴露的是组织问题：权限没开、电话打不通、升级路径没人接。
3. **真实注入**（验证：系统撑不撑得住）：进入混沌实验范畴，按 2.1 六步与 2.3 爆炸半径执行。前两级成熟之前不该到这一级——系统层面的弹性验证，前提是“人这一层不会添乱”。

演练日历保证演练不是“想起来才练”，三类例行：

- **季度例行**：核心链路预案抽查 + 所有新入库预案推演。抽查而非全量——全量演练的成本会逼死执行率。
- **大促前全链路**：秒杀场景是标准考题——库存 Redis 扣减、MQ 排队下单、非核心功能降级预案全部真实过一遍，而且要演练**预案的激活条件本身**：谁有权按降级开关、按了之后怎么确认真的生效了、开关误按怎么收回。大促前演练的产出还包括容量复核（与[性能工程分册](05-性能工程-容量规划与压测.md)的压测结论互相验证：压测证明“扛得住”，演练证明“坏了也不散架”）。
- **新服务上线必演练**：作为发布门禁的一部分（呼应[03-部署与发布策略](03-部署与发布策略-CICD与灰度.md) 2.1 的门禁清单）——没有预案、没做过桌面推演的服务不发放量。这一条把“演练”从运动式变成流水线式。

> **片段**（示意，未单独编译运行）：预案库条目的最小数据结构，字段即上表：
> ```kotlin
> data class PlaybookEntry(
>     val scenario: String,            // 故障场景
>     val expectedBehavior: String,    // 预期表现（降级行为）
>     val steps: List<String>,         // 处置步骤（可执行可验证）

> ```

### 3.2 复盘文化：无责复盘五问与产出三件套

演练、实验、真实事故，最后都汇入同一个复盘池。复盘质量决定组织是否真的在学习。

**无责复盘（blameless postmortem）五问**：

1. **发生了什么**：以监控数据、日志、Trace 重建客观时间线，不靠当事人回忆——回忆会自动自我辩护。时间线精确到分钟，标注每个检测点与动作点。
2. **影响面**：业务量化——多少单失败、多少资金受影响、多少用户受波及、持续多久。“用户体验不好”不是影响面，“12:03~12:17 之间 437 笔下单失败，其中 23 笔超时后实际成功需客服核对”才是。
3. **根因**：连续追问（5 Whys）到**机制层**而非**人名层**。“操作员删错了配置”不是根因——“为什么生产配置删除没有二次确认、没有变更审计”才是。
4. **为什么监控没有提前发现**：这一问比“谁干的”重要十倍。用户先于告警发现故障，就是可观测性的欠账（告警质量三问见[02-可观测性](02-可观测性-日志指标与链路追踪.md)）；这次是靠老师傅的经验看出来的，那这个经验就必须固化成告警。
5. **怎么防止复发**：只接受**机制性**措施——校验、自动化、架构改进；“加强责任心”“下次注意”一律不算数，因为它们不改变系统允许错误发生的条件。

无责（blameless）不是无标准：追问的矛头始终对准“**系统为什么允许这个错误发生**”，而不是“谁犯了错”。道理很直白：惩罚个人的组织，下一次人人倾向隐瞒与免责性记录，同样的事故换个名字再发生一遍；无责的组织里人才愿意写下“我当时以为……”，复盘才有真相可用。对事严、对人宽，是复盘文化的全部秘密。

**复盘产出三件套**（缺一即复盘未闭环）：

1. **ActionItem**：每条带负责人与期限，进迭代跟踪，逾期自动升级到复盘发起人的上级。没有期限的改进项是许愿。
2. **预案更新**：这次的处置路径写成预案条目入库（3.1 的字段照填），下次同类故障按剧本处置。
3. **监控补盲**：这次的发现路径固化成告警——本次靠什么信号发现的，就把那个信号配上阈值与通知；本次是用户反馈才发现的，就要补上本该先响的那条告警。

❌ **反例**：磁盘满事故的复盘纪要全文两句：“运维同学巡检不及时，后续加强责任心，避免类似问题再次发生。”两个月后另一块盘以同样的方式满掉。✅ **修正**：同一事故的无责复盘——时间线重建发现日志翻倍增长无人知晓；三件套：ActionItem“日志轮转加上限与占用预估上线（张三/两周）”；预案“磁盘满处置剧本入库（含告警系统自身受影响时的带外通知渠道）”；监控“分区使用率 > 85% 告警 + 预测 72 小时内写满提前告警”。判断一份复盘合格与否，就看三件套是否全部落地、可验证。

### 3.3 MES 工控场景的特别纪律：产线上不能直接注入

MES 是混沌工程纪律最严的场景，因为代价结构完全不同：IT 系统故障的代价是“用户体验变差、订单损失”；OT 侧故障的代价是**物理性的**——产线停机按分钟计损失、设备可能损坏、极端情况涉及人身安全。在电商系统注入故障是“花钱买教训”，在产线上注入故障是“制造真事故”。所以 MES 的故障演练先立规矩，再谈技术。

**分层划界**：按 ISA-95/Purdue 分层（L4 ERP / L3 MES / L2 SCADA·HMI / L1 PLC·DCS / L0 传感器设备，模型详见[示例项目场景](../示例项目场景/00-导览.md)的 MES 场景小节），注入的允许范围是：

| 层 | 能否注入 | 说明 |
|---|---|---|
| L4 ERP / L3 MES 及其集成链路 | 允许（受控） | IT 侧，断 MES 与上游集成的演练常态化 |
| L2 SCADA/HMI | 限制级 | 只读类注入（如制造数据延迟）需评估，控制类动作禁止 |
| L1 PLC/DCS、L0 设备 | **禁止** | 安全联锁与急停逻辑归现场，IT 团队没有也不该有控制权 |

IT/OT 的网络隔离与“指令下发须经现场安全联锁校验、急停控制权永远归现场”的 Fail-Safe 原则，在[04-安全架构](04-安全架构-认证授权与零信任.md)里已从安全角度讲过——演练纪律与它是同一条边界的两面：**IT 侧可以模拟“我这边坏了”，绝不模拟“我替现场决定”**。

**替代手段三级**（产线不能停，就在不停产的前提下找“可以坏”的地方）：

1. **仿真环境 / 数字孪生**：虚拟产线 + 模拟设备数据源跑真实的 MES 逻辑，注入随便打——网关断连、消息乱序、时钟漂移都可以在仿真里制造。这是 MES 混沌实验的主战场，成本在搭仿真，收益是注入完全无风险。
2. **离线产线时段**：检修窗口、停产排班时段做受限注入。注意这里的审批不止 IT：设备科、安全科联合签字——产线“停着”不等于“没有安全状态要维护”。
3. **单工位隔离**：备用产线或旁通工位物理隔离出沙箱，真实硬件、真实协议（OPC UA/Modbus）、真实边缘网关，但坏了不影响主产线节拍。验证“协议层故障”比仿真更真实。

**演练剧本的特别要求**：MES 每个演练剧本必须包含“**若 IT 侧处置失败，现场如何手动接管**”——人机分工的降级预案（看板不可用改用白板、报工不可用改用纸质单据事后补录），且手动接管流程要真的演练，不能只写在纸上。演练指挥席位必须有**现场安全负责人的一票否决权**：任何注入动作，现场判断有安全疑虑即中止，IT 侧无权驳回。MES 演练的典型目标也和互联网系统相反：不是“让产线停摆看反应”，而是验证“**MES 宕机，产线还能不能照常跑**”——边缘自治（车间网断连时本地续采、恢复补传）才是产线连续性的底线，这恰好是混沌注入“断 MES 集成链路”能安全验证的部分。

工程判据一句话：**MES/工控的故障演练，注入点永远在 IT 侧，验证目标永远是“OT 侧在 IT 侧失血时还能自主活多久”。**

## 4. 最小故障注入器（Kotlin 完整示例）

前面都是方法论，现在把最小的闭环跑起来。这个示例用纯 Kotlin + JDK 实现，演示混沌工程最核心的一组对比：**同样的故障注入，打在无防护的调用方 vs 打在带熔断降级的调用方，业务表现天差地别；注入停止后，熔断器自动恢复**。

业务场景沿用桶装水商城：下单时调用“配送排线服务”计算配送路线。设计四要素：

- **注入代理**：包在真实下游外面，对调用方透明，按固定种子的概率注入三类故障——`TIMEOUT`（下游卡死 3 秒，远超调用方 500ms 预算）、`ERROR`（下游抛异常）、`LATENCY`（额外 200ms 但最终成功）。种子固定保证注入序列**可复现**——这是“实验”区别于“乱来”的第一要求。
- **无防护调用方**：限时等待 + 结果透传，没有任何降级。
- **熔断降级调用方**：最小三状态熔断器（CLOSED/OPEN/HALF_OPEN，机制详解见[第三阶段：高可用](../03-第三阶段/06-高可用与稳定性-限流熔断与多活.md) 5.2.1），熔断时走兜底“沿昨日线路”，业务继续、只是路线次优。
- **共享线程池（4 线程）**：模拟下游的处理线程资源，让“卡死任务占满线程”的连锁反应真实发生。

完整代码（已用 kotlinc 2.2.20 编译运行验证）：

```kotlin
import java.util.concurrent.Callable
import java.util.concurrent.ExecutionException
import java.util.concurrent.Executors
import java.util.concurrent.ThreadPoolExecutor
import java.util.concurrent.TimeUnit
import java.util.concurrent.TimeoutException
import kotlin.random.Random

// ==================================================================
// 最小故障注入器：调用层包一个注入代理，按概率注入 超时/异常/延迟，
// 对比"无防护调用方"与"熔断降级调用方"在同样注入下的业务表现，
// 并演示注入停止后的自动恢复。
// 业务场景：桶装水商城——下单时调用"配送排线服务"计算路线。
// ==================================================================

// ---------- 下游：配送排线服务 ----------
interface RouteService {
    fun planRoute(orderId: String): String
}

/** 真实下游：正常处理约 50ms。 */
class RealRouteService : RouteService {
    override fun planRoute(orderId: String): String {
        Thread.sleep(50) // 模拟真实排线计算耗时
        return "路线[8站/50ms]"
    }
}

// ---------- 故障类型与注入策略 ----------
enum class FaultType { NONE, TIMEOUT, ERROR, LATENCY }

/**
 * 注入策略：各类故障的注入概率 + 随机种子。
 * 种子固定 → 注入序列可复现——这是"实验"区别于"乱搞"的第一要求。
 */
class FaultPolicy(
    private val timeoutProb: Double, // 注入"下游卡死"的概率
    private val errorProb: Double,   // 注入"下游抛异常"的概率
    private val latencyProb: Double, // 注入"额外延迟但最终成功"的概率
    private val hangMs: Long = 3_000,  // 卡死时长，远超调用方 500ms 预算
    private val latencyMs: Long = 200, // 额外延迟，仍在预算内
    seed: Long = 42
) {
    private val rnd = Random(seed)
    fun draw(): FaultType {
        val p = rnd.nextDouble()
        return when {
            p < timeoutProb -> FaultType.TIMEOUT
            p < timeoutProb + errorProb -> FaultType.ERROR
            p < timeoutProb + errorProb + latencyProb -> FaultType.LATENCY
            else -> FaultType.NONE
        }
    }
}

// ---------- 故障注入代理：包在真实下游外面对调用方透明 ----------
class FaultInjectingProxy(
    private val real: RouteService,
    private val policy: FaultPolicy
) : RouteService {
    val injected = mutableMapOf<FaultType, Int>()

    override fun planRoute(orderId: String): String {
        val f = policy.draw()
        injected.merge(f, 1, Int::plus)
        return when (f) {
            FaultType.NONE    -> real.planRoute(orderId)
            FaultType.LATENCY -> { Thread.sleep(200); real.planRoute(orderId) }
            FaultType.ERROR   -> throw IllegalStateException("[注入]排线服务500(订单$orderId)")
            FaultType.TIMEOUT -> { Thread.sleep(3_000); real.planRoute(orderId) } // 迟到的响应
        }
    }
}

// ---------- 调用方侧：结果记录 ----------
enum class Outcome { SUCCESS, TIMEOUT, ERROR, FALLBACK }

class CallRecord(val orderId: String, val outcome: Outcome, val elapsedMs: Long, val detail: String)

class CallTask(private val service: RouteService, private val orderId: String) : Callable<String> {
    override fun call(): String = service.planRoute(orderId)
}

/** 打印一条业务侧结果。 */
fun printCall(r: CallRecord) {
    val tag = when {
        r.outcome == Outcome.SUCCESS && r.elapsedMs > 300 -> "成功(慢)"
        else -> when (r.outcome) {
            Outcome.SUCCESS  -> "成功    "
            Outcome.TIMEOUT  -> "超时    "
            Outcome.ERROR    -> "下游异常"
            Outcome.FALLBACK -> "降级兜底"
        }
    }
    println("#${r.orderId}  $tag  ${r.elapsedMs}ms  ${r.detail}")
}

// ---------- 版本一：无任何防护的调用方 ----------
class NaiveOrderFlow(
    private val pool: ThreadPoolExecutor,
    private val routeService: RouteService,
    private val budgetMs: Long = 500
) {
    fun place(orderId: String): CallRecord {
        val t0 = System.currentTimeMillis()
        val future = pool.submit(CallTask(routeService, orderId))
        return try {
            val r = future.get(budgetMs, TimeUnit.MILLISECONDS)
            CallRecord(orderId, Outcome.SUCCESS, System.currentTimeMillis() - t0, r)
        } catch (e: TimeoutException) {
            future.cancel(false) // 只放弃等待，不打断任务：模拟"线程还在下游卡着"
            CallRecord(orderId, Outcome.TIMEOUT, System.currentTimeMillis() - t0,
                "预算${budgetMs}ms 内无响应，本次下单失败")
        } catch (e: ExecutionException) {
            CallRecord(orderId, Outcome.ERROR, System.currentTimeMillis() - t0,
                e.cause?.message ?: "未知异常")
        }
    }
}

// ---------- 版本二：熔断器（三状态最小实现） ----------
enum class BreakerState { CLOSED, OPEN, HALF_OPEN }

class MiniBreaker(
    private val failThreshold: Int = 3, // 连续失败阈值
    private val openMs: Long = 2_000    // 熔断冷却期
) {
    private val epoch0 = System.currentTimeMillis() // 用于输出相对时间戳
    var state: BreakerState = BreakerState.CLOSED
        private set
    private var consecFails = 0
    private var openedAt = 0L
    val transitions = mutableListOf<String>()

    private fun rel(now: Long) = now - epoch0

    /** OPEN 状态下冷却期还剩多少毫秒；非 OPEN 返回 0。 */
    fun cooldownRemainingMs(now: Long): Long =
        if (state == BreakerState.OPEN) maxOf(0L, openedAt + openMs - now) else 0L

    /** 是否放行本次真实调用；OPEN 且冷却期满则转 HALF_OPEN 并放行试探。 */
    fun tryAcquire(now: Long): Boolean = when (state) {
        BreakerState.CLOSED -> true
        BreakerState.OPEN ->
            if (now - openedAt >= openMs) {
                state = BreakerState.HALF_OPEN
                transitions += "t=${rel(now)}ms OPEN->HALF_OPEN(冷却期满,放行试探)"
                true
            } else false
        BreakerState.HALF_OPEN -> true
    }

    fun onSuccess(now: Long) {
        if (state == BreakerState.HALF_OPEN)
            transitions += "t=${rel(now)}ms HALF_OPEN->CLOSED(试探成功,恢复放行)"
        state = BreakerState.CLOSED
        consecFails = 0
    }

    fun onFailure(now: Long) {
        when (state) {
            BreakerState.HALF_OPEN -> {
                state = BreakerState.OPEN; openedAt = now
                transitions += "t=${rel(now)}ms HALF_OPEN->OPEN(试探失败,重新熔断)"
            }
            else -> {
                consecFails++
                if (consecFails >= failThreshold) {
                    state = BreakerState.OPEN; openedAt = now; consecFails = 0
                    transitions += "t=${rel(now)}ms CLOSED->OPEN(连续失败${failThreshold}次,熔断)"
                }
            }
        }
    }
}

// ---------- 版本二：带熔断降级的下单流程 ----------
class ProtectedOrderFlow(
    private val pool: ThreadPoolExecutor,
    private val routeService: RouteService,
    private val breaker: MiniBreaker,
    private val budgetMs: Long = 500
) {
    fun place(orderId: String): CallRecord {
        val now = System.currentTimeMillis()
        if (!breaker.tryAcquire(now)) {
            // 熔断打开：根本不打下游，直接走兜底（业务继续，只是路线次优）
            return CallRecord(orderId, Outcome.FALLBACK, 0, "熔断打开,不打下游|兜底=沿昨日线路")
        }
        val t0 = System.currentTimeMillis()
        return try {
            val future = pool.submit(CallTask(routeService, orderId))
            val r = future.get(budgetMs, TimeUnit.MILLISECONDS)
            breaker.onSuccess(System.currentTimeMillis())
            CallRecord(orderId, Outcome.SUCCESS, System.currentTimeMillis() - t0, r)
        } catch (e: TimeoutException) {
            breaker.onFailure(System.currentTimeMillis())
            CallRecord(orderId, Outcome.FALLBACK, System.currentTimeMillis() - t0,
                "调用超时,计入熔断|兜底=沿昨日线路")
        } catch (e: ExecutionException) {
            breaker.onFailure(System.currentTimeMillis())
            CallRecord(orderId, Outcome.FALLBACK, System.currentTimeMillis() - t0,
                "${e.cause?.message},计入熔断|兜底=沿昨日线路")
        }
    }
}

// ---------- 工具：等线程池里的残留任务排空 ----------
fun waitDrain(pool: ThreadPoolExecutor): Long {
    var waited = 0L
    while (pool.activeCount > 0 || pool.queue.size > 0) {
        Thread.sleep(100); waited += 100
    }
    return waited
}

fun summarize(tag: String, records: List<CallRecord>) {
    val byOutcome = records.groupBy { it.outcome }.mapValues { it.value.size }
    println("-- $tag 业务结果统计: 成功=${byOutcome[Outcome.SUCCESS] ?: 0}(含慢) " +
        "超时=${byOutcome[Outcome.TIMEOUT] ?: 0} 下游异常=${byOutcome[Outcome.ERROR] ?: 0} " +
        "降级兜底=${byOutcome[Outcome.FALLBACK] ?: 0} / 共${records.size}单")
}

fun main() {
    val budgetMs = 500L
    val pool = Executors.newFixedThreadPool(4) as ThreadPoolExecutor

    // ---- 阶段0：稳态基线（不注入，先确认"稳态"成立） ----
    println("== 阶段0 稳态基线：不注入 ==")
    val baseline = FaultInjectingProxy(RealRouteService(), FaultPolicy(0.0, 0.0, 0.0))
    val naive0 = NaiveOrderFlow(pool, baseline, budgetMs)
    val rec0 = (0 until 4).map { naive0.place("B0$it") }
    rec0.forEach(::printCall)
    summarize("阶段0", rec0)
    println("注入统计: ${baseline.injected}")

    // ---- 阶段1：开始注入，无防护调用方 ----
    println()
    println("== 阶段1 注入开始(卡死50%/异常20%/延迟15%)，无防护调用方，下游线程池=4 ==")
    val proxy1 = FaultInjectingProxy(RealRouteService(), FaultPolicy(0.50, 0.20, 0.15))
    val naive1 = NaiveOrderFlow(pool, proxy1, budgetMs)
    val rec1 = (0 until 12).map { naive1.place("A%02d".format(it)) }
    rec1.forEach(::printCall)
    summarize("阶段1", rec1)
    println("注入统计(对下游实际执行的注入): ${proxy1.injected}")
    println("此刻线程池: 活跃=${pool.activeCount} 排队=${pool.queue.size} (被卡死任务占用)")

    // 等残留的卡死任务跑完，让下一阶段从干净环境开始（真实事故里它们仍在占线程）
    val waited = waitDrain(pool)
    println("残留任务已排空(额外等待 ${waited}ms)——被放弃的调用并未消失，只是调用方先走了")

    // ---- 阶段2：同样的注入策略，带熔断降级的调用方 ----
    println()
    println("== 阶段2 同款注入(卡死50%/异常20%/延迟15%)，熔断+降级调用方 ==")
    val proxy2 = FaultInjectingProxy(RealRouteService(), FaultPolicy(0.50, 0.20, 0.15))
    val breaker = MiniBreaker(failThreshold = 3, openMs = 2_000)
    val protected1 = ProtectedOrderFlow(pool, proxy2, breaker, budgetMs)
    val rec2 = (0 until 12).map { protected1.place("C%02d".format(it)) }
    rec2.forEach(::printCall)
    summarize("阶段2", rec2)
    println("注入统计(对下游实际执行的注入): ${proxy2.injected} <- 熔断打开后下游少挨了打")
    println("熔断器状态: ${breaker.state}")

    // ---- 阶段3：注入停止，观察自动恢复 ----
    println()
    println("== 阶段3 注入停止(概率全 0)，观察熔断器自动恢复 ==")
    val remaining = breaker.cooldownRemainingMs(System.currentTimeMillis())
    if (remaining > 0)
        println("下游已恢复，但熔断冷却期还剩 ${remaining}ms——先不放流量，冷却期满后第一笔请求作为试探")
    Thread.sleep(remaining + 50)
    val proxy3 = FaultInjectingProxy(RealRouteService(), FaultPolicy(0.0, 0.0, 0.0))
    val protected2 = ProtectedOrderFlow(pool, proxy3, breaker, budgetMs)
    val rec3 = (0 until 8).map { protected2.place("D%02d".format(it)) }
    rec3.forEach(::printCall)
    summarize("阶段3", rec3)

    println()
    println("熔断器状态翻转轨迹:")
    breaker.transitions.forEach { println("  $it") }
    println("最终熔断器状态: ${breaker.state}")
    pool.shutdown()
}
```

**四个值得逐行品读的现象**——每一条都是生产事故的常见剧本：

1. **无防护时业务损失超过注入率**。注入了 6 次“卡死”，业务却出现 7 次超时：多出的那 1 次是排在卡死任务后面的正常请求——它本身没被注入任何故障，只是排队排到超过了 500ms 预算。看 A09：注入的是异常，却耗时 479ms 才失败，因为它先在队列里等了约 400ms。**排队延迟在调用方眼里和下游故障一模一样**，这就是容量问题如何伪装成可用性问题的经典路径（容量视角见[性能工程分册](05-性能工程-容量规划与压测.md)）。
2. **被超时放弃的调用并没有消失**。“残留任务已排空(额外等待 2500ms)”——调用方在 500ms 处转身走了，卡死的任务还在下游线程里继续睡满 3 秒。生产上的对应物是：调用方超时了，数据库里那条慢查询还在跑、还占着连接。**超时只是调用方的止损，不是下游的止损**。
3. **熔断让下游少挨打**。阶段2 的 12 笔请求只有 7 笔真正打到下游（注入统计 4+2+1=7），后 5 笔被熔断器直接挡下走兜底——熔断不仅是自我保护，同时给了下游喘息恢复的空间。业务侧对比阶段1：同样 12 单，失败 10 单 vs 失败 0 单，兜底让“排线服务宕机”降级成“路线次优”，而不是“订单下不了”。
4. **自动恢复是设计出来的，不是等出来的**。熔断器在 t=2119ms 打开、t=4175ms 冷却期满转 HALF_OPEN 放试探、t=4226ms 试探成功转 CLOSED——全程无人工介入。注意阶段3 开头那行“冷却期还剩 1999ms”：如果注入停止后立刻放流量，这些请求会在 OPEN 期间全部走兜底，恢复被人为推迟；**恢复节奏是熔断器设计的一部分**（试探失败还会重新熔断——把 `failThreshold` 调大或注入去掉“异常”只保留“卡死”，可以自己实验出这条路径）。

**与生产级工具的差距**——本示例是教学骨架，真实工具在每个维度上都要补齐：

| 维度 | 本示例 | 生产级（Chaos Mesh / Litmus / Chaos Toolkit 等） |
|---|---|---|
| 注入层次 | 进程内代理（应用层故障） | OS/容器/内核层：真实 kill、tc 网络延迟、磁盘 IO、时钟 |
| 观测 | 内存里的 Map 与打印 | 对接指标系统，稳态指标自动对照（对应六步第 1、4 步） |
| 停止条件 | 无（靠脚本编排） | 自动 abort + 一键总闸（对应 2.3 三要素） |
| 实验管理 | main 里写死 | 实验声明、审批流、报告归档、可复现 |
| 恢复 | 熔断器演示 | 注入自动撤销 + 拓扑级验证恢复完整 |

落位指引：把注入器做成 Sidecar 或平台功能后，实验的下发与撤销走[03-部署与发布策略](03-部署与发布策略-CICD与灰度.md)的审批与灰度通道——混沌实验本质上是一种**计划内的变更**，就该用变更的管理办法管。
