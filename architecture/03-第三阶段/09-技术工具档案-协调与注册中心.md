## 0. 先看全景：同一个问题的四次回答

先给一条时间线，四个工具的诞生顺序本身就是一部“分布式协调进化史”：

| 年份 | 事件 | 解决的当务之急 |
| --- | --- | --- |
| 2006 | Google 公开 Chubby 论文（分布式锁服务）；Yahoo! 内部启动 ZooKeeper | 大数据生态（Hadoop）的脑裂与选举 |
| 2008~2010 | ZooKeeper 捐赠 Apache 孵化器，2010 年毕业成顶级项目 | 协调能力从 Yahoo 走向全行业 |
| 2013 | CoreOS 发布 etcd | 容器时代要一个“轻的 ZK” |
| 2014 | HashiCorp 发布 Consul | 微服务时代要“带健康检查的服务发现” |
| 2018 | 阿里开源 Nacos（7 月）；etcd 加入 CNCF（12 月） | 国内微服务栈要“注册+配置二合一” |
| 2020~2025 | etcd 从 CNCF 毕业（2020-11）；Kafka 4.0 移除 ZooKeeper 依赖（2025-03，KRaft） | 协调服务与业务系统的解耦与再耦合 |

一句话总纲：**四个工具都在回答同一道题——“一群对等进程，如何在部分失败和网络分区下，对'谁是活的、谁是主、配置是什么'达成一致？”**，但各自的诞生背景使答案面貌完全不同。带着这条主线往下读。

## 1. ZooKeeper：协调服务的鼻祖

### 1.1 概况：出身档案

- **作者**：Yahoo! 的 Patrick Hunt、Mahadev Konar、Flavio Junqueira、Benjamin Reed 等团队（系统论文见 2010 年 USENIX ATC《ZooKeeper: Wait-free Coordination for Internet-scale Systems》）。
- **诞生**：2006 年前后在 Yahoo! 内部起步。背景：Yahoo 是 Hadoop 最早的大规模使用者，Hadoop 生态（MapReduce 的 JobTracker 主备、HBase 的 Master 选举与 RegionServer 存活感知）全都缺一个“大家信得过的协调者”。设计蓝本是 Google 的 **Chubby**（2006 年 OSDI 论文公开的分布式锁服务）——ZooKeeper 常被称作“开源版 Chubby”。2008 年捐赠 Apache 进入孵化器，2010 年 11 月毕业成为顶级项目。
- **归属**：Apache 软件基金会（Apache 2.0 协议），Java 编写。
- **一句话定位**：**分布式协调服务**——它不直接提供“锁/选举/配置中心”，只提供两个低阶原语：**znode 树**（一个所有客户端看到一致视图的小型分层存储）+ **一次性 Watcher**（变更通知），锁、Leader 选举、配置推送都是用户在这两个原语上“搭”出来的配方（recipe）。

### 1.2 解决了什么问题：出现前的痛

回到 2006 年的 Yahoo。Hadoop 集群已经上千台，三个反复失血的痛点：

**痛点一：脑裂（split-brain）**。HBase 同一时间只能有一个 Master 改 meta 表。Master 假死（长 GC、网络抖动）时，监控系统以为它死了，启动备 Master——旧 Master 实际仍在运行，两个 Master 同时写 meta，数据彻底撕裂。每个系统都试过自己写选举：版本号、心跳、仲裁……几乎每个自研选举都败在“假死误判”上。

**痛点二：假死与真死分不清**。一个进程 3 秒没回心跳，是死了、还是 GC 停顿、还是网络抖动？不同系统给出不同答案，且都靠各自实现——故障检测代码重复编写了 N 遍，没有一版真正正确。

**痛点三：配置与元数据没有“单一事实源”**。上千台 TaskTracker 的配置文件靠运维 scp 分发，改一个参数要一周窗口；集群拓扑（谁活着、谁是主）散落在各系统各自的私有记录里，互相矛盾。

三大痛点指向同一个缺口：**需要一个小小的、所有人都信任的强一致存储 + 通知机制**。ZooKeeper 就是为填这个缺口而生。

### 1.3 如何解决：核心机制拆解

#### 1.3.1 ZAB 原子广播：为了“顺序”而偏离 Paxos

ZooKeeper 的每个写请求最终由 **ZAB**（ZooKeeper Atomic Broadcast，ZooKeeper 原子广播协议）复制到多数派。ZAB 与 Paxos 同属“多数派投票 + 主从提交”家族——官方文档自己说“ZAB 与 Paxos 相似但不同”（协议细节与 Paxos/Raft 的逐步对照见 [02-分布式理论基础-CAP共识与一致性.md](02-分布式理论基础-CAP共识与一致性.md)），这里只讲它**为什么不同**：

- **唯一活跃 Leader（primary）**：任意时刻只有一个节点能广播提案。Paxos 理论上允许多个提议者竞争（靠 ballot 解决），ZAB 直接用“选主”消灭竞争——代价是要处理选主切换，换来的是广播阶段没有活锁。
- **主序保证（primary order）**：提案按 Leader 接收的顺序编号广播、按序提交、FIFO 应用。Paxos 只保证“决议不冲突”，不天然保证全序——而 ZooKeeper 的 znode 树语义（后写覆盖先写、子节点列表变更有序）恰恰要求顺序。
- **zxid = epoch + 计数器**：64 位，高 32 位 epoch（Leader 纪元，等价于 Paxos 的 ballot / Raft 的 term），低 32 位是纪元内单调计数。崩溃恢复时新 Leader 必须持有“最高的已提交 zxid”，未过半提交的提案直接丢弃——与 Raft “只有日志最新的候选人才能当选”是同一个思想（对照 02 分册的 Raft 选举模拟示例）。
- **广播两阶段**：Leader 广播 PROPOSE → 收到多数派 ACK → 广播 COMMIT。像极了两阶段提交，但只需多数派而非全体——这正是它扛得住部分节点宕机的原因（对照 [05-分布式事务-从2PC到最终一致.md](05-分布式事务-从2PC到最终一致.md) 里“全体确认”型 2PC 的阻塞问题）。

#### 1.3.2 znode 树与临时顺序节点：三种节点撑起所有配方

数据模型是一棵像文件系统的树，每个节点（znode）可存 1MB 以内数据（`jute.maxbuffer` 默认限制——这是“存元数据，别存业务数据”的制度性提醒）。三种节点类型是一切配方的根基：

- **持久节点**：创建者断开也还在——配置、成员名单用。
- **临时节点（ephemeral）**：与创建者的**会话**绑定，会话一断（心跳停止超时），节点自动删除——“谁活着”这件事第一次有了权威答案：**节点存在 = 会话活着**。脑裂问题就此有了仲裁：两个都想当 Master？都去创建 `/master` 临时节点，只有一个成功；旧 Master 断线后节点消失，不存在双主。临时节点不允许有子节点。
- **顺序节点（sequential）**：创建时父节点自动在名字后追加 10 位单调递增序号（`lock-0000000007`）。**临时顺序节点** = 锁与选举的基石：公平锁、排队、选“序号最小者当主”全靠它（本章 §6 的 Kotlin 示例就是完整实现）。

#### 1.3.3 一次性 Watcher 与读写路径：性能与易用性的取舍

**Watcher 四条语义**（每条都影响上层配方的正确性）：

1. **一次性**：注册后触发一次即失效，想继续盯必须重新注册。
2. **轻量**：只通知“这个节点变了”（新建/删除/数据变更/子节点变更），**不带数据本体**——客户端收到事件后必须重新读取。
3. **顺序保证**：客户端保证先收到“导致该事件的写操作结果”，再收到事件本身——不会看到比事件更旧的本地状态。
4. **注册与读取非原子**：处理事件到重新注册之间有窗口，窗口内可能再发生变更丢失——所以标准做法是“读数据 + 注册 Watch”循环，每轮回读状态补齐窗口。

这套语义换来了服务端极低的 Watch 成本（内存一张表，触发即删），但把复杂度推给了客户端——这正是后文 etcd “流式 Watch + 版本续传”要修复的缺陷。3.6 版本才补充了持久/递归 Watch（`addWatch`）。

**读写路径**：写一律走 Leader，ZAB 过半提交；**读默认在任意 Follower 本地内存完成**——保证顺序一致（能看到全部已提交写、顺序与全局一致），但可能滞后，不是线性一致；要线性一致读得先 `sync()` 再读（概念辨析见 02 分册）。这个默认值就是 ZooKeeper 在 CAP 中**读路径偏向可用性**的巧妙安排：多数派分区时，少数派一侧仍能提供（陈旧的）读。

#### 1.3.4 典型配方：锁、选举、配置

- **分布式锁**：create 临时顺序节点 → 取父节点 children → 自己序号最小则持锁，否则只 Watch 前驱（详见 §6 示例）。
- **Leader 选举**：人人创建临时顺序节点，序号最小者为 Leader；其余 Watch 自己前驱，前驱消失则重新判断——本质是“谁都不用抢”的锁。
- **配置中心**：配置写在 znode，客户端 Watch 节点变更，变更即重读——推送的雏形，但没有灰度、审计、控制台（后文 Nacos 会补齐这些）。

### 1.4 对比同类：鼻祖的余晖与老态

**最重要的当代注脚：Kafka 用了 ZooKeeper 十四年，随后亲手将其移除**。Kafka 从诞生起用 ZK 做 broker 成员管理、controller 选举与元数据存储（早期连消费者偏移也放 ZK）。规模扩大后问题暴露：元数据变更要走“ZK → controller → broker”的外部链路；分区规模到百万级时，controller 故障切换时间随分区数线性膨胀，可达分钟甚至小时级；运维团队要同时维护 JVM 的 ZK 集群和 Scala/Java 的 Kafka 集群。**KIP-500（KRaft）** 把元数据放进 Kafka 自己的 Raft 日志（`__cluster_metadata` topic）：2.8 引入（2021，早期体验）、3.3 生产可用、3.9 是最后支持 ZK 的大版本、**4.0（2025 年 3 月）起 KRaft 是唯一模式**。这背后的一半故事（Kafka 侧）在 [07-技术工具档案-消息队列.md](07-技术工具档案-消息队列.md)；另一半属于本篇：**当一个系统只把协调服务当“元数据库”用时，外部依赖的耦合与运维成本可能超过它带来的价值**——把共识协议内嵌进自己（Raft 库），比外挂一个协调服务更轻。

**“鼻祖但老态”的判据**，逐条都是工程理由而非情怀：

1. JVM 技术栈：与云原生 Go 生态格格不入，镜像大、内存调优繁琐。
2. 一次性 Watcher：每个上层配方都要处理重注册窗口，客户端复杂度高（官方也建议使用 Apache Curator——Netflix 开源的高层封装——而不是裸客户端）。
3. 无多数据中心能力：跨 DC 只能靠应用层双集群。
4. 容量与性能：单节点 znode 数据 1MB 上限、全树规模与写吞吐（万级/秒）有限。
5. 生态重心迁移：Kafka 移除依赖、Kubernetes 从未采用、新一代项目默认 etcd。

**何时仍选它**：Hadoop/HBase/Solr/老版本 Kafka/Dubbo 存量生态（这些系统今天仍内建 ZK 依赖）；需要极成熟稳定的锁与选举且团队已有 Curator 经验。**新项目的协调与元数据首选 etcd**；把它当注册中心则要慎重（§7 详述）。

## 2. etcd：为容器时代而生的分布式 KV

### 2.1 概况：出身档案

- **作者**：CoreOS 公司（2013 年成立，做容器操作系统 CoreOS Linux）的 Brandon Philips 等团队，Go 编写。
- **诞生**：2013 年。背景：CoreOS 的容器集群调度器 fleet 需要一个所有节点都信任的轻量元数据存储。他们考察了现有选项：MySQL 是单点；ZooKeeper 太重——要为几百台轻量容器宿主机拖一台 JVM 集群，客户端还是出了名的难写。名字即宣言：**etcd = “/etc” + distributed**——把 Unix 存配置的 `/etc` 目录做成分布式的。
- **归属**：2018 年 12 月加入 CNCF（孵化），**2020 年 11 月从 CNCF 毕业**（顺带纠正常见误传：2018 年是“加入”不是“毕业”）。CoreOS 2018 年被 Red Hat 收购后，etcd 由 CNCF 社区维护。Apache 2.0。
- **一句话定位**：**分布式、高一致的键值存储**——Kubernetes 的唯一状态存储。

### 2.2 解决了什么问题：出现前的痛

2013 年的场景故事：CoreOS 集群有几百台机器，调度器要回答“这个容器单元（unit）在哪台机器上跑、谁来锁、谁是主”。这些元数据的特点是**量极小、变更极少、但绝对不能错、且要在节点故障时秒级收敛**。

没有合适的选择：

**痛点一：ZooKeeper 的“重”与“难”**。JVM 运维成本先不论，裸客户端要自己管会话、管 Watch 重注册、管连接状态机——“ZK 客户端是协议迷宫”是当年工程圈的名言。CoreOS 想要的是“`curl` 就能读写”的简单体验。

**痛点二：通知机制不可靠**。ZK Watcher 一次性、断线重连丢事件；容器 IP 漂移如此频繁（重启即换 IP），注册表的事件流稍有缺口，调度器的本地视图就永久落后。

**痛点三：单点元数据无处安放**。用 MySQL 存集群状态？主库宕机调度即瘫痪；自己实现多数派复制？等于每个项目重新发明一遍 Paxos。

etcd 的三个目标由此确定：**单二进制轻量部署、Raft 强一致、可靠的 watch**。第三个目标最终演化成了它对 ZooKeeper 最锋利的差异点。

### 2.3 如何解决：核心机制拆解

#### 2.3.1 Raft：把共识做成“库”

etcd 用 Raft（而不是自己发明协议）复制日志——2013 年正是 Raft 论文（Ongaro & Ousterhout）发布的年份，etcd 的 Go 实现 `etcd/raft` 后来成为 Go 生态的事实标准 Raft 库（Consul、CockroachDB、TiKV 都基于它或其变体——一个工具选对协议，整个生态跟着受益）。选举与日志复制细节见 02 分册的 Raft 选举模拟示例，这里只讲 etcd 的实现选择：**默认线性一致读**（ReadIndex 机制：向 Leader 确认自己仍最新后本地应答，不用把读也写进日志），追求吞吐时可显式降级为串行读——与 ZK “默认本地读、sync 才线性一致”的默认值恰好相反，两种默认值代表了两种主流用法：etcd 的用户（K8s）读的是“绝不能错”的控制面状态，ZK 的用户读的常常是“尽量新就行”的注册表。

#### 2.3.2 MVCC 多版本：全局 revision 是钥匙

每次写操作让全局版本号 **revision** 单调 +1，每个 key 保留全部历史版本（直到 compaction 压缩）。收益有三个：

1. **Watch 可以按版本续传**：客户端记录最后收到的 revision，断线重连后从这个 revision 继续收——事件流有了“断点续传”，根治了 ZK 的丢事件窗口。
2. **历史可查**：能读“key 在版本 N 时的值”，审计与调试友好。
3. **乐观并发**：事务里可以拿 `mod_revision`（最后一次修改的版本）做条件——“只有没人动过它我才写”，即 CAS 原语。

#### 2.3.3 gRPC 流式 Watch：一条连接上的事件长河

v3 起 Watch 是**服务端流**：一条 gRPC 连接上可以同时挂任意多个 watch（按前缀、按 key），服务端把“自你指定的 revision 起”的变更持续推下来（gRPC 与流式调用本身见 [03-远程通信-协议序列化与演进.md](03-远程通信-协议序列化与演进.md)）。对比 ZK“每个 watcher 一次性、事件不带数据”的设计，etcd Watch 的设计动机就一句话：**注册表类系统的正确性，一半建立在事件流不丢不乱之上**。

#### 2.3.4 Lease 租约：临时节点的泛化

ZK 的临时节点把“生命周期”绑在会话上；etcd 把它抽出来做成独立对象：**Lease**（租约，TTL 秒级到天级）。客户端通过长连接 keepalive 保活；租约可以挂**任意多个 key**——进程假死后租约超时，名下所有 key 一次性消失。这是比临时节点更通用的原语：服务注册（实例 key + 心跳保活）、分布式锁（锁 key + keepalive）、选主（leader key + keepalive）都是它的变体。配合 **txn 小事务**（compare → then/else 原子执行，条件可用 create_revision/mod_revision/value）就有了完整 CAS：锁 = “以租约保护、CAS 创建成功者为持有者”。

#### 2.3.5 v2 → v3：一次推倒重来的演进

v2（2013~2016）：HTTP/JSON 接口、目录模拟层级、TTL 直接挂 key、Watch 用长轮询、**没有 MVCC**（事件历史只留有限条，重连即可能丢）。Kubernetes 1.0~1.5 用的就是 etcd2。v3（2016 起）：gRPC + MVCC + 流式 Watch + Lease + txn + 前缀 range 查询；K8s 1.6 起默认切 etcd3。v2 API 于 3.4 弃用、3.5 默认关闭、3.6 移除。这段演进的教学价值：**一个基础设施的核心语义缺陷（事件可靠性）是修补不掉的，只能换代**。

#### 2.3.6 “Kubernetes 唯一状态存储”

所有 K8s 对象（Pod、Service、ConfigMap、Event……）以 `/registry` 前缀存在 etcd 里，API Server 是唯一读写者；controller-manager、scheduler、kubelet 全靠 **list-watch**（先全量拉一次，再用 watch 增量维护本地缓存）驱动各自的最终一致控制回路——可以说 **Kubernetes 本身就是构建在 etcd Watch 之上的一套状态机体系**。这带来两条工程红线：① etcd 抖动 = 整个控制面抖动（但数据面已调度的 Pod 照常运行，见 §7 的解耦分析）；② etcd 只存元数据——默认后端配额 2GB，超限触发 NOSPACE 告警、集群进入只读，必须靠 compaction（压版本）+ defrag（碎片整理）日常运维（部署侧细节见 [../章节5/03-部署与发布策略-CICD与灰度.md](../05-第五阶段/03-部署与发布策略-CICD与灰度.md)）。

### 2.4 对比同类：何时选它

- **在 K8s 上搭建平台/中间件**：无需犹豫，跟随平台即可，etcd 是 K8s 生态的“官方元数据层”，提供托管 K8s 的云厂商都在代为运维 etcd。
- **需要一个正确的分布式锁/选主/小 KV**（如自研调度器、Patroni 式数据库 HA）：单二进制、gRPC 多语言客户端、`etcdctl` 命令行，运维心智低于 ZK 一个量级。
- **不适合**：大数据量、大 value（配额与 watch 放大效应）、多数据中心强需求（跨机房 Raft 会被延迟拖垮，灾备用快照，不是活集群）。

## 3. Consul：健康检查驱动的服务发现

### 3.1 概况：出身档案

- **作者**：HashiCorp（Mitchell Hashimoto 与 Armon Dadgar 创立于 2012，Vagrant/Terraform/Nomad/Vault 的出品公司），Go 编写。
- **诞生**：2014 年。背景：微服务化刚成为主流（2013~2014，Docker 发布、Netflix OSS 走红），“服务实例自动发现”从奢侈品变成刚需。
- **归属**：HashiCorp 公司项目，2014~2023 年 Apache 2.0；**2023 年 8 月 HashiCorp 全线改 BSL 1.1 协议**（源码公开、限制云厂商转售），生态为此震动，选型时须把协议条款纳入考量。
- **一句话定位**：**以健康检查为核心的服务网络栈**——服务发现 + KV + 多数据中心 + 服务网格（Connect），一切围绕“哪些服务实例**真正可用**”组织。

### 3.2 解决了什么问题：出现前的痛

用我们的示例场景讲故事（画像见 [示例项目场景.md](../示例项目场景/01-导览.md)）：桶装水商城微服务化后（演进过程见 [../章节2/03-微服务架构.md](../02-第二阶段/03-微服务架构.md)），订单服务扩到 20 个实例。大促前夜自动扩容 10 个新实例，但网关的 upstream 列表是静态配置的——一半流量继续被路由到已回收的老实例，超时报警如雪片般涌来。三个痛点：

**痛点一：实例漂移 vs 静态配置**。容器时代实例 IP 分钟级变化，任何“人工维护的列表”（LB 配置、hosts 文件、配置文件里的地址）都注定过期。

**痛点二：会话存活 ≠ 服务可用**。当时的替代方案 ZK 能当注册表用：实例注册临时节点、断线自动摘除。但 ZK 判断的是**协调会话**的存活——进程还活着（会话在）但依赖的数据库连接池耗尽、健康端点返回 500、磁盘满了，ZK 无从知晓，仍会把它留在“服务列表”里。**注册中心真正要回答的不是“谁活着”，而是“谁能正常处理请求”**。

**痛点三：多数据中心天然存在**。商城华东、华北双机房部署（同城双活的需求见 [06-高可用与稳定性-限流熔断与多活.md](06-高可用与稳定性-限流熔断与多活.md)），ZK/etcd 的答案都是“每个 DC 一套集群 + 应用层自行拼接”——而跨 DC 服务发现（A 机房整体宕机时查 B 机房）恰恰是容灾的关键路径。

### 3.3 如何解决：核心机制拆解

#### 3.3.1 Agent 架构：把注册与检查下沉到每个节点

Consul 部署形态是“**每节点一个 agent**”：client agent（无状态，转发写、执行健康检查、应答本地查询）+ 少量 server（3 或 5 台，用 Raft 维护全局 catalog）。服务向**本节点** agent 注册——写压力天然分散，节点再多也不会压垮中心。设计动机：注册与探测是高频本地事件（实例每几秒上报），把这类事件**集中化**到中心集群等于自造瓶颈；只有“目录的最终状态”才值得过 Raft。

#### 3.3.2 两层 Gossip：把故障检测从 quorum 挪出去

Consul 的网络分两层（Gossip 协议本身——SWIM 的探测、怀疑、收敛机制——见 02 分册，这里只讲为什么分两层）：

- **LAN gossip**：同 DC 内全部 agent 参与，负责**成员关系与故障检测**——哪个节点掉线，靠节点间点到点探测 + 谣言式扩散，秒级全网收敛，不经过 Raft、不需要 quorum。
- **WAN gossip**：跨 DC 的 server 之间单独 gossip，组成联邦。

为什么不让 Raft 包办一切？因为故障检测是**高频且必须低延迟**的工作，让每个节点只探测几个邻居再互相传话（O(log n) 轮收敛），比“全部向 Leader 心跳”便宜得多、也没有单点热点；而**数据一致性**（catalog、KV）交给 Raft。**用 gossip 做可用性层、用 Raft 做一致性层，各管一段**——这是 Consul 对“协调服务怎么组合协议”最精彩的一次回答。

#### 3.3.3 健康检查驱动的发现：DNS/HTTP 双接口

健康检查类型覆盖 script / HTTP / TCP / gRPC / TTL（服务自己主动汇报“我还活着”）等，由本地 agent 周期执行，结果汇总进 catalog。查询侧给两个接口：

- **DNS**：`dig web.service.consul` 直接得到**健康的**订单服务实例地址（支持 A/SRV 记录、 unhealthy 默认被过滤）——任何语言、任何框架、甚至 nginx 的 resolver 都能直接用，**零 SDK**。
- **HTTP API**：`/v1/health/service/web` 结构化结果，适合 SDK 与网关。

这就是“健康检查驱动”的完整闭环：**注册解决“我是谁”，检查解决“我行不行”，DNS/HTTP 解决“你去哪找”**。补充一个反例修正：TTL 检查模式下实例假死，agent 会在超时后自动把服务标记为 critical——又是“不依赖对方自觉”的故障检测哲学。另外 KV 存储（Raft，CP）顺带提供了配置能力，但没有灰度与推送管理，一般只放简单的开关类配置；**Connect** 服务网格（2018 年 v1.2 起内建 mTLS 与代理）本文一笔带过，需要 sidecar/service mesh 时再展开。

### 3.4 对比同类：何时选它

- **HashiCorp 技术栈**（Terraform/Nomad/Vault）+ 多 DC 服务发现强需求：Consul 几乎是唯一原生答案，多 DC 联邦是它最深的护城河。
- **希望服务发现“零侵入”**（多语言技术栈、不想引 SDK）：DNS 接口即拿即用。
- **考量项**：每节点都要装 agent 的运维面（K8s 环境里要与 kube-proxy/DNS 存在职责冲突，需要 consul-k8s 同步层）；2023 年 BSL 协议与社区顾虑；健康检查虽强，但检查规则本身也需要维护（检查脚本故障导致误报 critical 是常见事故源）。

## 4. Nacos：注册 + 配置二合一的双模选手

### 4.1 概况：出身档案

- **作者**：阿里巴巴中间件团队。
- **诞生**：2018 年 7 月开源（与 Dubbo、Sentinel 等组成的“开源三件套”同期）。名字 = **Na**ming **a**nd **Co**nfiguration **S**ervice 的缩写，直白宣告双职能。血统来自阿里内部十年的超大规模实践：配置中心 Diamond 与内部寻址系统多年打磨后的整合开源。
- **归属**：Alibaba 开源（GitHub alibaba/nacos），Apache 2.0 协议；阿里云 MSE（微服务引擎）提供托管版。
- **一句话定位**：**注册中心 + 配置中心二合一、AP/CP 按数据类型分治的动态服务发现与配置管理平台**。

### 4.2 解决了什么问题：出现前的痛

2018 年国内微服务栈的典型困境，用两个场景讲：

**场景一：三件套的运维税**。一个桶装水商城规模的团队做微服务（注册发现与配置热更的原理见 [../章节2/03-微服务架构.md](../02-第二阶段/03-微服务架构.md)），当时的主流组合是 **Eureka（注册，AP）+ Spring Cloud Config（配置，Git 后端）+ 也许再加一套 ZK（给 Dubbo）**——三个系统、三种协议、三套运维、三个控制台。配置热更尤其棘手：Spring Cloud Config 原生只解决“集中管理”，要实现热更推送还需再搭建 Spring Cloud Bus + 消息队列，链路越拼越长。

**场景二：MES 配置的凌晨变更**。MES 场景（画像见 [示例项目场景.md](../示例项目场景/01-导览.md)）里，产线切换要改 PLC 采集频率、工序超时阈值这类配置，变更窗口在凌晨两点：要求**秒级生效、可灰度（先让 1 条产线验证）、可秒级回滚、有审计**。Eureka 不做配置；Config + Bus 的推送既不灰度也难回滚。工单中心的 SLA 阈值、路由规则同理——配置变更从来不是“改个值”，是“一次小型发布”。

**场景三：大促心跳风暴**。万级实例每 5 秒向单一注册中心集群发心跳，2013~2017 年的阿里内部与后来的社区用户都遭遇过：注册中心集群在心跳洪峰下抖动，抖动导致误判下线，误判触发更大规模的重新注册——正反馈雪崩。

Nacos 的答案是把三件套合成一个、并给不同数据配不同的协议。

### 4.3 如何解决：核心机制拆解

#### 4.3.1 二合一模型：服务与配置同址

**服务模型**：namespace（命名空间，租户/环境隔离）→ group → service → cluster → instance；**配置模型**：namespace → group → dataId。注册与配置共用一套部署、一个控制台、一套鉴权。模型中内建多租户：命名空间让“商城 dev/test/prod”或“不同业务线”互不可见——这是四个工具里最直接的租户原语。

#### 4.3.2 双模一致性：Distro（AP）与 Raft（CP）分治

Nacos 最有教学价值的设计——**同一个产品内，按数据类型选一致性协议**：

- **临时实例（ephemeral=true，默认）走 Distro 协议（AP）**：Nacos 自研，核心是“负责制 + 增量同步”——每台 server 平等地接收写请求，对自己收到的数据负责，异步批量同步给其他节点；新节点加入先拉全量快照再增量追平；任何节点都可应答读。分区期间各节点继续可读可写自己负责的份额，恢复后增量同步收敛（最终一致）。
- **持久实例与配置走 Raft（CP，基于蚂蚁开源的 SOFAJRaft）**：过半提交。

为什么这样分？回到数据性质：**实例表错一会儿，消费端有重试、熔断、本地缓存兜底**（兜底机制见 [06-高可用与稳定性-限流熔断与多活.md](06-高可用与稳定性-限流熔断与多活.md)）；**配置错一秒，所有实例同时行为异常**，且配置的“灰度中/已全量”状态绝不能在不同节点上有不同答案。所以：发现数据可用性优先（AP），配置数据正确性优先（CP）。这正是 §7 要展开的“注册中心选 AP 还是 CP”的产品化答案——Nacos 把这道选择题预先为你拆成了两道判断题。

#### 4.3.3 健康检查双轨：心跳与探测各管一种实例

- **临时实例**：客户端主动心跳（1.x 为 HTTP 心跳，默认 5s 一次、15s 标记不健康、30s 剔除；2.x 升级为 gRPC 长连接，连接本身就是心跳）。实例失联后自动摘除——适配容器时代的“短命、漂移”实例。
- **持久实例**：服务端主动探测（TCP/HTTP），不健康只标记**不剔除**，下线必须显式注销——适配数据库、Redis 这类“地址基本不变、绝不能自动消失”的基础设施注册。

一套注册中心同时服务“易变的业务实例”与“稳定的基础设施地址”，这是双轨设计的动机。

#### 4.3.4 配置中心能力：把配置变更当发布对待

- **推送**：1.x 客户端 30s 长轮询（服务端挂起请求直到配置变更，长轮询原理见 [03-远程通信-协议序列化与演进.md](03-远程通信-协议序列化与演进.md)）；2.x 换 gRPC 长连接服务端主动推，秒级生效。
- **灰度**：控制台 Beta 发布——新配置先推给指定实例，验证后再全量；配合命名空间/分组可以做环境级隔离。
- **可回滚**：历史版本一键回滚；监听查询能回答“哪个实例正在监听哪份配置、当前 MD5 是多少”——变更影响面可视化。
- **工程配套**：导入导出、配置加密插件、权限与审计。

对照 §3 的 Consul KV：同为“注册中心里的配置能力”，Nacos 把配置当**一等公民**（发布流程管理），Consul 把它当**副产品**（裸 KV）。也正因配置领域的纵深，专业配置中心 Apollo（携程开源）仍是强敌——Nacos 的胜负关键在“二合一”的集成度而非单点最强。

#### 4.3.5 生态位：Spring Cloud Alibaba 与 Dubbo 的默认枢纽

Spring Cloud Alibaba 的服务注册（替代 Eureka）与配置（替代 Config+Bus）两个 starter 都指向 Nacos；Dubbo 的注册中心与配置中心原生适配；Sentinel 规则持久化、Seata 配置也常用 Nacos 承载。对国内团队这意味着**引入一个中间件，覆盖整个微服务脚手架**——这是它在国内迅速成为事实标准的主因。多数据中心**非原生**（靠 nacos-sync 等工具做跨集群同步，或直接用 MSE 多活方案），与 Consul 的原生联邦形成鲜明对比。

### 4.4 对比同类：何时选它

- **Spring Cloud Alibaba / Dubbo 技术栈**：默认答案，生态咬合无出其右。
- **要控制台、要灰度、要“注册+配置”一站式**：四者中唯一把配置发布流程做完整的。
- **考量项**：多 DC 与海外社区弱于 Consul/etcd；公司级选型要考虑“国内生态绑定”的路径依赖。

## 5. 横向对比总表

| 维度 | ZooKeeper | etcd | Consul | Nacos |
| --- | --- | --- | --- | --- |
| 一致性协议 | ZAB（Paxos 家族，主序广播） | Raft | Raft（catalog/KV）+ LAN/WAN 两层 Gossip（成员与故障检测） | Distro（AP，临时实例）+ Raft/JRaft（CP，持久实例与配置） |
| 默认 CAP 取向 | CP：写过半提交；读默认本地（顺序一致），sync 才线性一致 | CP：默认线性一致读，可降串行读 | CP 骨架（Raft 写）；故障检测走 gossip 不占 quorum；可开 stale 读 | 临时实例 AP、配置与持久实例 CP（按数据分治） |
| 服务发现 | 无内建（靠 recipes 自建） | 无内建（K8s 在其上实现） | 内建核心能力 | 内建核心能力 |
| 健康检查 | 无（仅会话存活=节点存在） | Lease 保活（≈会话存活） | 最强：script/HTTP/TCP/gRPC/TTL | 双轨：客户端心跳（临时）+ 服务端探测（持久） |
| 配置中心能力 | znode + Watch（原始原语） | KV + 流式 Watch（原语级，无管理面） | KV（副产品级） | 专业：控制台/灰度/回滚/监听查询/推送 |
| 多数据中心 / 多租户 | 均无（chroot 隔离） | 均无内建（灾备用快照） | 多 DC 原生联邦；多租户需企业版 | 多租户 namespace 原生；多 DC 靠同步工具 |
| K8s 亲和度 | 低 | 最高（K8s 状态存储本体） | 好（consul-k8s 同步、mesh） | 一般（可用、非原生） |
| 客户端 / SDK | Java 原生 + Apache Curator；多语言参差 | gRPC 多语言 + HTTP/JSON + etcdctl | 零 SDK（DNS/HTTP）+ 官方客户端 | Java/Go/Python 等多语言；SCA/Dubbo 深度集成 |
| 运维复杂度 | 中：JVM、会话与 GC 调优 | 中低：单二进制；compaction/defrag、配额 | 中高：全节点 agent + server Raft | 低：单二进制 + 开箱控制台（集群配 MySQL/Derby） |
| 社区与云托管 | Apache；无托管 | CNCF 毕业项目；所有托管 K8s 内建 | HashiCorp（2023 起 BSL）；HCP Consul 托管 | Apache 2.0 开源；阿里云 MSE 托管 |

三条解读：

1. **协议列是四部进化史**：ZAB（为顺序而生）→ Raft（为可理解而生）→ Raft+Gossip 分层（为规模与多 DC 而生）→ Distro+Raft 分治（为“数据性质不同”而生）。没有更好的协议，只有更合适的组合。
2. **“健康检查”一列是注册中心的分水岭**：ZK/etcd 回答“进程在不在”，Consul/Nacos 回答“服务行不行”。把前者当注册中心用的团队，最后都会自己在客户端重造一层健康过滤——不如一开始就选后者。
3. **“配置中心能力”一列别轻视**：配置变更 = 一次发布，灰度与回滚不是锦上添花，是凌晨两点救命的绳索（MES/工单中心场景反复验证）。

## 6. 专题：分布式锁的三种载体

协调服务最经典的高阶应用是分布式锁，而三种主流载体恰好对应本篇三位主角加 08 分册的 Redis。

### 6.1 三种载体的机制对比

| 维度 | ZooKeeper | etcd | Redis（细节见 [08-技术工具档案-缓存.md](08-技术工具档案-缓存.md)） |
| --- | --- | --- | --- |
| 加锁原语 | create 临时顺序节点 + 比序号 | txn CAS 抢建前缀 key + 比 createRevision | `SET key uid NX PX ttl`（单主） |
| 防惊群 | 只 Watch 前驱（序号即队列） | 只 Watch 前一个 key 的删除 | 无（抢跑制，先到先得） |
| 持有者崩溃 | 会话超时自动删节点 | Lease 超时批量回收 key | TTL 到期自动释放 |
| 公平性 | 严格 FIFO（序号） | 严格 FIFO（revision） | 无公平性 |
| 故障时正确性 | ZAB CP：分区时少数派不可写，不会双主 | Raft CP：同左 | 主从异步复制：主库宕机提升从库，锁可能**双持**（RedLock 争议详见 08 分册） |
| 典型实现 | Apache Curator `InterProcessMutex` | clientv3 `concurrency` 包 | Redisson（看门狗自动续期） |

三者的锁语义都可归纳为同一个配方：**一个绑定了生命周期的独占节点（顺序化排队）+ 对前驱的一次监听（惊群避免）+ 服务端的强一致裁决**。Redis 少了最后一环，所以只能做“尽力而为”的互斥。

### 6.2 效率锁 vs 正确性锁：选型判据

**效率锁（efficiency lock）**：锁是为了**避免重复劳动**，双持有只是浪费一点算力。例：定时任务多实例只需一个运行（重复执行只是多发一封日报邮件）、缓存击穿时单飞加载（重复回源只是多打一次数据库——本地 singleflight 思想见 [04-数据架构-缓存分库与选型.md](04-数据架构-缓存分库与选型.md)）。**载体：Redis 足够**——简单、快速、运维团队普遍熟悉。

**正确性锁（correctness lock）**：锁本身承担不变量，双持有=资损或数据损坏。例：支付账户扣款、库存扣减防超卖、唯一流水号分配。**载体必须 ZK/etcd（CP）**，并且**还必须加 fencing token（栅栏令牌）**——因为任何锁都防不住持有者在临界区里长 GC 停顿：停顿期间会话/租约超时、锁被让给后来者，停顿结束旧持有者“复活”继续写——两个进程同时在临界区。修正方法：每个锁附带单调递增的令牌（etcd 的 revision 天然可用；ZK 可用 zxid 思路或业务自增版本），**资源端（数据库等）只接受“比已见过的最大令牌更新”的写**。归根结底：正确性最终要靠资源端校验或幂等设计（幂等与唯一请求号见 [05-分布式事务-从2PC到最终一致.md](05-分布式事务-从2PC到最终一致.md)），锁只是第一道门。

一句话判据：**自问“如果这把锁偶尔失效两次，最坏损失是什么？”——损失是浪费，用效率锁；损失是事故，用正确性锁 + fencing；损失不可承受，把互斥改成单写者队列/数据库约束，别用锁。**

### 6.3 可运行示例：MiniFairLock.kt——ZooKeeper 风格公平锁（含羊群效应对照）

下面这个单文件 Kotlin 示例（无第三方依赖）完整模拟了 ZooKeeper 公平锁协议，两个场景对照：

- **场景 A（反例）**：四个任务抢建**同一个**锁节点，抢不到就全员盯着它——持有者一释放，所有人被同时惊醒、蜂拥争抢，只有一人成功，其余空跑（**羊群效应**，ZooKeeper 官方文档明确警告过的模式）。
- **场景 B（正例）**：四个工单导出任务各建**临时顺序节点**、按序号排队、每个等待者**只 Watch 自己的直接前驱**——持有者假死（停止心跳）后会话超时自动释放、唯一后继无缝接管；正常释放同理。全程零惊群、严格 FIFO。

```kotlin
// MiniFairLock.kt —— 模拟 ZooKeeper 风格"临时顺序节点公平锁"，并对照"人人盯同一节点"的羊群效应
// 无第三方依赖；编译运行：
//   kotlinc MiniFairLock.kt -include-runtime -d app.jar && java -jar app.jar

/** 伪 ZooKeeper：内存版，只实现本例需要的原语——会话/心跳、临时节点、顺序号、一次性 Watch */
class FakeZk(private val sessionTimeoutTicks: Int = 3) {
    class ZNode(val path: String, val ephemeral: Boolean, val owner: Long)

    private val nodes = LinkedHashMap<String, ZNode>()
    private val sessions = HashMap<Long, Int>()                        // 会话 -> 剩余心跳预算
    private val watches = HashMap<String, MutableList<() -> Unit>>()   // 路径 -> 一次性回调
    private var seqGen = 0
    private var sessionGen = 100L
    var wakeups = 0         // 统计：被唤醒的"客户端·次"
    var wastedRaces = 0     // 统计：被唤醒后抢锁失败的"空跑"次数

    fun openSession(): Long {
        val s = ++sessionGen
        sessions[s] = sessionTimeoutTicks
        return s
    }

    fun heartbeat(s: Long) {
        if (s in sessions) sessions[s] = sessionTimeoutTicks
    }

    /** 推进一个时间片：所有会话预算减一；预算归零的会话过期，其全部临时节点被自动删除并触发 Watch */
    fun tick() {
        val expired = sessions.filterValues { it <= 1 }.keys.toList()
        sessions.keys.toList().forEach { s -> sessions[s] = sessions[s]!! - 1 }
        expired.forEach { s ->
            sessions.remove(s)
            println("    [ZK] 时间片推进：会话 #$s 超时过期，自动回收其全部临时节点")
            nodes.values.filter { it.ephemeral && it.owner == s }.map { it.path }
                .forEach { removeAndFire(it) }
        }
    }

    /** 创建临时顺序节点：序号在父节点内单调递增、零填充 10 位（对齐真实 ZK 语义） */
    fun createSeq(parent: String, prefix: String, owner: Long): String {
        val path = "$parent/${prefix}%010d".format(++seqGen)
        nodes[path] = ZNode(path, ephemeral = true, owner = owner)
        return path
    }

    /** 场景 A 用：人人抢建同一个节点（非顺序），抢不到就盯着它 */
    fun createIfAbsent(path: String): Boolean {
        if (nodes.containsKey(path)) return false
        nodes[path] = ZNode(path, ephemeral = false, owner = -1)
        return true
    }

    fun children(parent: String): List<String> =
        nodes.keys.filter { it.startsWith("$parent/") }
            .filter { !it.removePrefix("$parent/").contains('/') }
            .sorted()

    /** 一次性 Watch：节点被删除时触发；若注册时节点已不存在则立即触发（对齐真实 ZK 语义） */
    fun watch(path: String, cb: () -> Unit) {
        if (path !in nodes) cb()
        else watches.getOrPut(path) { mutableListOf() }.add(cb)
    }

    fun delete(path: String, note: String) {
        println("    [ZK] 删除 $path（$note）")
        removeAndFire(path)
    }

    private fun removeAndFire(path: String) {
        nodes.remove(path) ?: return
        val cbs = watches.remove(path) ?: return
        wakeups += cbs.size
        cbs.forEach { it() }
    }
}

/** 场景 A 的竞争者：盯住锁节点本身，被唤醒就冲进去抢（羊群效应参与者） */
class HerdClient(val name: String, private val zk: FakeZk, private val path: String) {
    var holding = false
        private set

    fun tryAcquire(): Boolean {
        if (zk.createIfAbsent(path)) {
            holding = true
            println("  $name 抢建成功 → 持有锁")
            return true
        }
        return false
    }

    fun watchAndRush() {
        zk.watch(path) {
            println("  $name 被唤醒，冲进去抢")
            if (!tryAcquire()) {
                zk.wastedRaces++
                println("  $name 抢建失败，空跑一次，只能继续 Watch")
                watchAndRush()
            }
        }
    }
}

/** 场景 B 的竞争者：走完整公平锁协议——建顺序节点、看队首、只 Watch 直接前驱 */
class FairClient(val name: String, private val zk: FakeZk, private val root: String) {
    private var sid = -1L
    private var myPath: String? = null
    var holding = false
        private set
    var alive = true
        private set

    fun join() {
        sid = zk.openSession()
        myPath = zk.createSeq(root, "lock-", sid)
        println("  $name 上线，创建临时顺序节点 ${myPath!!.substringAfterLast('/')}")
        recheck(quiet = false)
    }

    fun beat() {
        if (alive) zk.heartbeat(sid)
    }

    private fun recheck(quiet: Boolean) {
        val mine = myPath ?: return
        val kids = zk.children(root)
        if (kids.first() == mine) {
            holding = true
            println("  $name 排在队首 → 获得锁")
        } else {
            val pred = kids[kids.indexOf(mine) - 1]
            if (!quiet) println("  $name 非队首，只 Watch 直接前驱 ${pred.substringAfterLast('/')}")
            zk.watch(pred) {
                println("  $name ：收到前驱删除事件 → 重新检查队列")
                recheck(quiet = true)
            }
        }
    }

    fun crash() {
        alive = false
        holding = false
        println("  $name 假死（kill -9 / 长 GC）：不再心跳，但没有任何人替它删节点")
    }

    fun release() {
        alive = false
        holding = false
        zk.delete(myPath!!, "持有者 $name 正常释放")
    }
}

fun main() {
    val line = "─".repeat(62)

    println(line)
    println("场景 A（反例）：人人盯同一个锁节点 —— 羊群效应")
    println(line)
    val zkA = FakeZk()
    val lockPath = "/ticket-center/report-lock"
    val herd = listOf("任务#1", "任务#2", "任务#3", "任务#4").map { HerdClient(it, zkA, lockPath) }
    var winner: HerdClient? = null
    for (c in herd) if (c.tryAcquire()) { winner = c; break }
    herd.filter { !it.holding }.forEach {
        println("  ${it.name} 抢建失败，Watch 锁节点本身（所有失败者盯的是同一个节点）")
        it.watchAndRush()
    }
    zkA.delete(lockPath, "持有者 ${winner!!.name} 正常释放")
    println("统计（场景 A）：一次释放唤醒 ${zkA.wakeups} 个客户端、${zkA.wastedRaces} 次空跑")

    println()
    println(line)
    println("场景 B：临时顺序节点 + 只 Watch 前驱 —— ZooKeeper 公平锁")
    println(line)
    val zk = FakeZk(sessionTimeoutTicks = 3)
    val root = "/ticket-center/export-lock"
    val clients = listOf(
        FairClient("工单导出#1", zk, root),
        FairClient("工单导出#2", zk, root),
        FairClient("工单导出#3", zk, root),
        FairClient("工单导出#4", zk, root),
    )
    println("—— 第一幕：四个竞争者按到达顺序入队 ——")
    clients.forEach { it.join() }

    println("—— 第二幕：持有者 #1 假死，靠会话超时自动释放（无人出手，锁自愈） ——")
    clients[0].crash()
    repeat(3) { i ->
        clients.drop(1).forEach { it.beat() }
        println("  （时间片 ${i + 1}：活着的实例正常心跳，假死者的倒计时在走）")
        zk.tick()
    }

    println("—— 第三幕：#2 干完活正常释放，#3 无缝接管 ——")
    clients[1].release()

    println()
    println("统计（场景 B）：总共唤醒 ${zk.wakeups} 次、空跑 ${zk.wastedRaces} 次")
    println("  获锁顺序 #1 → #2 → #3 = 到达顺序：公平性由序号保证，不由网速决定")
    println()
    println("两代锁法对照：")
    println("  A 人人盯一个节点：1 次释放惊醒全部 N 个等待者，N-1 次空跑（羊群效应）")
    println("  B 顺序节点+只看前驱：每次交接只惊醒 1 个直接后继，0 空跑，严格 FIFO")
    println("  B 的隐藏红利：持有者假死后无需任何人出手——会话超时自动删节点，锁自愈")
}
```

## 7. 综合选型判据：注册中心选 AP 还是 CP

这是四个工具放在一起时绕不开的终审判决式问题，也是历史上真实发生过的论战（2017 年前后“Eureka 自我保护 vs ZooKeeper 注册中心”论战）。

**第一步：把“注册中心”拆成两类数据。** 实例表（谁在线）和配置/元数据（该怎么做）性质完全不同：实例表错了，消费端有超时重试、熔断、本地缓存三重兜底（见 [06-高可用与稳定性-限流熔断与多活.md](06-高可用与稳定性-限流熔断与多活.md)），短暂陈旧通常只是多一次失败重试；配置错了，所有实例**同时**行为异常，且“灰度到一半”这种中间状态必须全局唯一。结论：**发现数据可用性优先（AP 足够），配置数据正确性优先（CP 必须）**。Eureka 的自我保护（续约量骤降时宁可冻结列表也不清空）与 Nacos 的 Distro/Raft 分治，都是这个结论的产品化。

**第二步：裁决三问。** 面前这套系统分区时——① 消费端更怕“查不到实例”还是“查到已死实例”？前者占多数（查不到=直接失败，查到已死实例还能重试下一个）。② 消费端有没有本地缓存兜底（注册中心整体宕机也能凭最后一份名单运行一段时间）？③ 服务分区期间注册不上去的损失，是否会被“恢复后重新注册”自然抹平？三问都偏“可用”，就应选 AP 或至少“AP 行为”的注册中心。

**第三步：理解 K8s 为什么用 CP 的 etcd 却未落入典型陷阱。** 这是最容易被忽视的一点：etcd 是彻头彻尾的 CP，但它存的是**控制面状态**（期望的部署拓扑），而“实例能否接收请求”由**数据面本地判断**——kubelet 在本机探测容器、kube-proxy/DNS 用本地缓存的规则转发流量。控制面分区时，已部署的服务照常互通，只是不能发布变更。**把“元数据一致性”与“服务可达性”解耦到两个平面，CP 就不再伤害可用性**——这个架构教训比“选 AP 还是 CP”本身更有价值（部署与灰度实践见 [../章节5/03-部署与发布策略-CICD与灰度.md](../05-第五阶段/03-部署与发布策略-CICD与灰度.md)）。

**最终决策顺序**（先问生态，再问特性）：

1. 在 K8s 上跑 → **etcd**（跟随平台，不自建第二套事实源）。
2. HashiCorp 栈或多 DC 服务发现是硬需求 → **Consul**（多 DC 联邦独此一家）。
3. Spring Cloud Alibaba / Dubbo 栈、要控制台与配置灰度 → **Nacos**（二合一+国内生态）。
4. Hadoop/老 Kafka 存量生态 → **ZooKeeper**（维护为主，不再新增职责）。
5. 都不是 → 默认 **etcd** + 按需补 Consul/Nacos 的能力，警惕用 ZK 承担新角色。

## 8. 反例与修正

**反例一：拿 ZooKeeper 当注册中心，跨机房网络一抖全站下线。** 某工单中心把服务实例注册在 ZK 临时节点上。机房间断网 30 秒：半数节点失联 → Leader 重选 → 大量客户端会话超时 → 临时节点批量消失 → 网关拿到“空实例列表”→ 逐级熔断，故障从 30 秒网络抖动放大成 10 分钟全站事故。**修正**：① 消费端永远保留最后一份非空实例快照（本地缓存兜底），“查不到”绝不等于“清空”；② 注册中心选 AP 语义（Nacos 临时实例 / Eureka 自我保护思想）；③ 会话超时时间不要为“快速感知”一味调小——误杀的代价比迟到更高。

**反例二：把业务数据当元数据塞进 etcd。** 团队认为 etcd“稳定且查询方便”，把两百万条商品标签写入其中当业务库使用。半年后超过默认 2GB 后端配额，触发 NOSPACE 告警，etcd 进入只读——同一个 etcd 上跑着的 K8s 控制面随之瘫痪，连“删掉多余数据自救”都要先修 etcd。**修正**：etcd/ZK 这类协调存储只放元数据（容量红线内、key 小、变更频率低），业务数据放专门的存储；日常运维把 compaction/defrag 和配额告警当作常规项。

**反例三：用 Redis SETNX 锁保护资金操作。** 支付回调用 Redis 锁防重复处理：主库 SET 成功、还没同步到从库时主库宕机，从库提升后锁“消失”，第二个实例加锁成功——两个进程同时处理同一笔扣款。**修正**：按 §6.2 判据，这是正确性锁，载体换 ZK/etcd；再加 fencing token 让资源端拒绝旧持有者的迟到写入；或者釜底抽薪——把“防重”改成唯一请求号 + 数据库唯一约束的幂等设计（见 [05-分布式事务-从2PC到最终一致.md](05-分布式事务-从2PC到最终一致.md)）。

**反例四：手写 ZK 锁，人人 Watch 全部子节点。** 开发者为图省事：等待者 Watch 父节点的子节点列表，任何释放都惊醒全部等待者去重查——几千个等待者的集群里每次交接都是一次读风暴，ZK 集群被内部锁流量压垮。**修正**：临时顺序节点 + 只 Watch 前驱（§6.3 示例的场景 B 即正解）；且优先用 Curator `InterProcessMutex` 这类久经考验的库——**分布式锁的正确性细节多到不值得手写**（本例的 FakeZk 已是最小化实现，真实客户端还要处理连接断开、会话迁移、可重入等）。
