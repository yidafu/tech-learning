## 3.1 缓存体系：多级缓存、Redis、穿透 / 击穿 / 雪崩（秒杀 + 桶装水商城）

**多级缓存**（秒杀是教科书场景）：CDN/页面静态化（商品详情页提前渲染成静态 HTML 推到边缘节点，活动开始后大多数刷新根本到不了源站）→ 本地缓存（Caffeine，进程内零网络开销，放极热的秒杀活动信息，容忍秒级旧数据）→ Redis（集中式、容量大，放商品详情与库存计数）→ MySQL。桶装水商城则是典型**读多写少**：商品浏览量远大于下单量，读几乎全被缓存挡住，写（扣库存）走库。

**扩展：先做容量推演，再决定缓存投入**。缓存不是免费的（引入一致性问题、失效链路、运维面），上不上、上多大，用一笔账算清：**缓存收益 ≈ 命中率 × 单次回源成本 × 回源 QPS**。桶装水商城商品读写比 ≈ 100:1，且热 key 高度集中（20% 的商品占 80% 的浏览量），命中一个请求就省一次 MySQL 查询（几毫秒到几十毫秒）——这种形状的数据缓存收益极高；反过来，后台报表类低频查询、命中率注定 10% 以下的长尾数据，上缓存只是给系统加状态。容量估算同样有笔账：**预算 ≈ 日活跃 key 数 × 平均 value 大小 × 热集系数**——例如日均被访问 500 万个商品 key、平均 2KB、热集系数 0.3（访问集中在 30% 的 key 上），Redis 需要 ~3GB 起步再留 50% 水位。这笔账的真正作用是倒逼你回答“我的访问到底集不集中”：不集中的访问模式，加多少缓存都无效，该走读写分离或搜索引擎。

**扩展：本地缓存的适用与雷区**。多级缓存里的“本地缓存”最容易被想当然地用，三个雷区先踩明白：

- **雷区一：数据量上限**。进程内存是全应用最贵的存储——JVM 堆要给业务对象和 GC 留余地，本地缓存通常只配每实例几十到几百 MB。它放“热”不放“全”：秒杀活动配置、商品类目树、字典表、限流阈值快照这类“条目少、每实例都高频命中”的小热集是它的主场；把全量商品详情灌进本地缓存属于用错地方。工程上用 Caffeine 的 `maximumWeight` 显式声明容量预算（按条目数或按序列化后字节数加权），并给每个条目估好平均大小——“以为放得下、实际把堆撑爆”是常见事故。
- **雷区二：广播失效**。Redis 的失效一处生效即全局，本地缓存在每个实例各有一份，改了配置或数据后必须让**所有实例**的本地副本同时失效。常用三种手段：Redis pub/sub 或 MQ 广播失效消息（即时但要处理消息丢失）、配置中心/版本号轮询（实例发现版本变了整批刷新）、或最朴素的短 TTL 兜底。关键认知：**广播失效是“加速失效”，短 TTL 是“保底失效”**——广播丢了、实例恰好重启错过消息，都靠 TTL 保证各实例的旧数据最多活到过期，否则各实例的数据版本会静默漂移。
- **雷区三：权重配比**。多级缓存的容量预算怎么分？经验配比是“本地小而热、Redis 大而全”：本地缓存占全应用缓存内存的小头，只挡每实例必然命中的头部流量（收益是省一次网络往返，约 0.5~2ms）；大部分容量和命中率预算交给可横向扩容的 Redis 集群。本地缓存命中率从 0 提到 80% 收益巨大，从 80% 再往上堆容量往往性价比急剧下降——值得用命中率监控数据来定配比，而不是凭主观判断。另外要认清本地缓存的语义：它是**有损缓存**，天然容忍秒到分钟级旧数据；不容忍旧值的数据（秒杀剩余库存）绝不能只放本地。

**Cache-Aside 读写模式**（最常用）：读——先缓存、未命中查库并回填；写——**先更新库，再删除缓存**（不是更新缓存：并发写下更新缓存容易把旧值写回去，而删除让下次读触发回源，天然懒加载）。

**扩展：缓存一致性四象限**。Cache-Aside 的“先更库后删缓存”并不是唯一方案，工程上常见四种做法，按**正确性 × 复杂度**摆成一张对照表（判据各一行，选型看最后一列）：

| 方案 | 做法 | 正确性 | 复杂度 | 适用判据 |
|---|---|---|---|---|
| 先更库后删缓存（Cache-Aside） | 写：UPDATE 库 → DEL 缓存 | 高：读写并发产生脏缓存的窗口极小（读请求恰在“更库后、删缓存前”回源旧值且回填更晚），概率低且下次写自愈 | 低：业务代码两行 | **绝大多数业务的默认选择**，先从这里起步 |
| 先删缓存后更库 | 写：DEL 缓存 → UPDATE 库 | 差：删除到提交之间，并发读把**旧值**回填缓存；这个脏值比库新值更晚写入，会一直活到 TTL 或下次删除——脏数据停留时间不可控 | 低 | 几乎不单独使用；只在写前确定无并发读（如单人维度的极小数据）勉强可行 |
| 延迟双删 | 写：DEL → UPDATE 库 → 等待 Δt → 再 DEL 一次 | 中：第二次删除清掉并发窗口内回填的旧值，把脏窗口压到 Δt 之内；但 Δt 取值靠经验（略大于一次回源耗时），窗口内仍是脏的 | 中：要定 Δt、要保证第二次删除不丢（失败要重试） | 读写并发高、又不想引入 binlog 链路的**过渡方案** |
| 订阅 binlog 异步失效 | 业务只管更库；Canal/Flink CDC 等订阅 binlog，变更事件驱动 DEL 缓存 | 高：以数据库变更事实为准，失效是变更的下游动作，天然有序、不依赖业务代码自觉、不会漏删 | 高：要运维 binlog 解析组件 + MQ 链路，事件乱序/重复要幂等处理 | 缓存多、删除点分散易漏、已有 MQ 基础设施的中大型系统；binlog 变更事件本身就是[事件驱动架构](../02-第二阶段/04-事件驱动架构.md)里“事件通知”形态的标准应用 |

四象限的共同前提值得点破：**缓存一致性从定义上就是最终一致**（一瞬间的旧值在所难免），追求“缓存与库永远一致”是方向性错误——真要强一致就读库、用库的事务，缓存根本不该出现在这条路径上（一致性模型的分级见 [02-分布式理论基础-CAP共识与一致性.md](02-分布式理论基础-CAP共识与一致性.md)）。所以选型的真实问题不是“哪个方案绝对正确”，而是“哪个方案把脏窗口压到业务可容忍的范围、且复杂度我养得起”。落地还有两条通用补丁：删除缓存失败要重试（塞进延迟队列/MQ，不能 fire-and-forget）；主从库场景下延迟双删的 Δt 要把**主从复制延迟**也算进去，否则第二次删除打到从库时效之外。

**三大经典问题**，先分清现象再谈方案：

| 问题 | 触发条件 | 现象 |
|---|---|---|
| 穿透 | 请求的 key **根本不存在**（黄牛拿随机 skuId 试探） | 缓存永远无法命中，请求全部落到 DB |
| 击穿 | **单个热点 key 过期的瞬间**，海量并发同时回源 | 秒杀 sku 缓存过期 → DB 瞬间被该 key 的回源流量压垮 |
| 雪崩 | **大批 key 同时过期**，或 **Redis 整体宕机** | DB 被全面冲垮，故障面是全部 key |

**穿透：反例与修正**：

```kotlin
// ❌ 反例：不存在的 skuId 每次都穿到数据库
fun getSku(skuId: String): Sku? {
    redis.get("sku:$skuId")?.let { return deserialize(it) }
    return skuRepo.findById(skuId)     // 脚本拿 99999999 这类不存在的 id 高频请求 → 全部落库
}

// ✅ 修正：布隆过滤器前置挡"肯定不存在"，空值缓存挡"刚查过确实没有"
fun getSku(skuId: String): Sku? {
    if (!bloomFilter.mightContain(skuId)) return null      // 布隆说没有 → 一定没有，不用查库
    return when (val v = redis.get("sku:$skuId")) {
        NULL_SENTINEL -> null                               // 命中空值缓存，直接返回"不存在"
        null -> skuRepo.findById(skuId)?.also {
            redis.setex("sku:$skuId", 3600, serialize(it))
        } ?: redis.setex("sku:$skuId", 60, NULL_SENTINEL).let { null }   // 空值也要缓存，TTL 短
        else -> deserialize(v)
    }
}
```

**击穿：singleflight 互斥回源**（同一 key 只放一个请求去重建）：

```kotlin
// ✅ 热点 key 失效瞬间，只允许一个请求查库重建，其余等它写回后读缓存
fun getSeckillStock(skuId: String): Int {
    redis.get("stock:$skuId")?.let { return it.toInt() }
    return mutexGuard(key = "lock:stock:$skuId", waitMs = 200) {    // 拿到锁的少数人回源
        redis.get("stock:$skuId")?.toInt() ?: reloadAndCache(skuId) // 双重检查：等锁期间可能已被重建
    } ?: throw BusyException()                                      // 等锁超时：快速失败而非压垮 DB
}
```

更省心的替代：**逻辑过期**——key 不设 TTL，value 里带过期时间戳，读到过期就返回旧值并异步触发重建，业务永远不被回源阻塞。

**扩展：singleflight 的完整可运行实现**。上面 `mutexGuard` 是伪代码，“同 key 并发回源合并为一次”值得落成真实代码看清机制：不用分布式锁（那要碰 Redis），**进程内一个 `ConcurrentHashMap<String, CompletableFuture>` 就够了**——首个到达的请求 `putIfAbsent` 成功成为“带头回源者”，其余请求拿到已存在的 Future 挂起等待，结果由带头者广播给全班。下面的完整示例模拟缓存失效瞬间 100 个并发请求打向同一个 key：

```kotlin
// 完整示例（单文件可运行）：SingleFlightDemo.kt
import java.util.concurrent.ConcurrentHashMap
import java.util.concurrent.CompletableFuture
import java.util.concurrent.CountDownLatch
import java.util.concurrent.atomic.AtomicInteger

// 模拟数据库回源：记录真实被调用的次数（教学桩，替代真实 Repo）
val dbLoadCount = AtomicInteger(0)
fun loadFromDb(key: String): String {
    dbLoadCount.incrementAndGet()
    Thread.sleep(100)                       // 模拟慢查询：100ms
    return "value-of-$key"
}

/** 单飞（singleflight）：同一个 key 的并发回源合并为一次真实调用，其余等待并复用结果 */
class SingleFlight {
    private val inflight = ConcurrentHashMap<String, CompletableFuture<String>>()

    fun execute(key: String, loader: () -> String): String {
        val myFlight = CompletableFuture<String>()
        val existing = inflight.putIfAbsent(key, myFlight)
        if (existing == null) {
            // 我是"带头回源"的那个：查库，结果广播给所有同 key 等待者
            try {
                val v = loader()
                myFlight.complete(v)
                return v
            } catch (e: Throwable) {
                myFlight.completeExceptionally(e)
                throw e
            } finally {
                inflight.remove(key)        // 航班结束：下一个新请求开启新一轮回源
            }
        }
        // 其余 99 个请求：挂在同一架"航班"上等结果，而不是各自去砸数据库
        try {
            return existing.get()
        } catch (e: java.util.concurrent.ExecutionException) {
            throw e.cause ?: e
        }
    }
}

fun main() {
    val sf = SingleFlight()

    // ---- 第一波：缓存失效瞬间，100 个请求同时打向同一个 key ----
    val ready = CountDownLatch(1)
    val done = CountDownLatch(100)
    val results = ConcurrentHashMap<Int, String>()
    repeat(100) { i ->
        Thread {
            ready.await()                   // 100 个线程就位，一起起跑
            results[i] = sf.execute("stock:1001") { loadFromDb("stock:1001") }
            done.countDown()
        }.start()
    }
    ready.countDown()
    done.await()

    println("第一波：并发请求数 = 100")
    println("第一波：真实回源数据库次数 = ${dbLoadCount.get()}")
    println("第一波：所有请求拿到的结果 = ${results.values.toSet().single()}")

    // ---- 第二波：航班已结束（finally 移除），新请求允许开启新一轮回源 ----
    Thread.sleep(50)
    repeat(50) { i ->
        Thread {
            results[1000 + i] = sf.execute("stock:1001") { loadFromDb("stock:1001") }
        }.start()
    }
    Thread.sleep(300)
    println("第二波（航班结束后的新请求）：累计回源次数 = ${dbLoadCount.get()}")
}
```

编译运行验证（kotlinc 2.2.20，`kotlinc SingleFlightDemo.kt -include-runtime -d singleflight.jar && java -jar singleflight.jar`），真实输出：

```text
第一波：并发请求数 = 100
第一波：真实回源数据库次数 = 1
第一波：所有请求拿到的结果 = value-of-stock:1001
第二波（航班结束后的新请求）：累计回源次数 = 2
```

三个设计点值得对照着读：

- **`putIfAbsent` 抢位而不是加锁**：没有 `synchronized`，抢不到位的请求直接复用别人的 Future——100 个并发里 1 个回源、99 个等待，DB 调用次数从 100 降到 1。等待者 `existing.get()` 拿到的是带头者 `complete` 的同一个结果对象，天然一致。
- **`finally` 移除是关键一步**：航班结束后必须把 key 从 `inflight` 摘掉，否则新请求会永远复用第一波的结果——那就不叫合并回源、叫永久缓存了。第二波 50 个新请求又触发恰好 1 次新回源（累计 2 次），证明“每一代请求合并一次、代与代之间正常失效”。
- **失败也广播**：带头者查库抛异常时 `completeExceptionally`，99 个等待者同样拿到异常快速失败，而不是各自再试一轮把 DB 压垮——回源失败要么集体快速失败、要么由少量重试兜底，绝不退化成“每个等待者自己再查一遍”。

落地组合拳：singleflight 只解决“击穿瞬间并发合并”，通常与逻辑过期叠加——读请求永远不阻塞（逻辑过期返回旧值 + 异步线程里走 singleflight 重建），singleflight 保证同一时刻只有一个重建在跑。还要注意它的**进程内边界**：合并只发生在单个实例内部，100 个实例各放行 1 个回源、共 100 个——DB 侧还要叠加分布式层面的互斥（Redis SETNX 锁）或限流兜底，两层防线各管各的并发面。

**雪崩：组合拳**——TTL 加随机抖动错开过期时间、Redis 哨兵/集群保高可用、多级缓存（Redis 宕机时本地缓存仍可接管读请求）、回源路上加限流熔断兜底：

```kotlin
// ✅ 过期时间加随机抖动，避免同一批预热 key 在同一秒集体失效
redis.setex(key, 3600 + Random.nextInt(0, 600), value)
```

**秒杀防超卖：Redis + Lua 原子预扣**。库存扣减必须“读—判断—写”原子完成，先 GET 再 DECR 的两步写法在并发下必超卖：

```kotlin
// ❌ 反例：GET 与 DECR 之间有间隙，两个请求都读到"还剩 1 件"，各扣一次 → 超卖
// ✅ 修正：Lua 脚本在 Redis 内原子执行"判断 + 扣减"
val DEDUCT_LUA = """
    local stock = tonumber(redis.call('GET', KEYS[1]) or '-1')
    if stock < tonumber(ARGV[1]) then return -1 end      -- 不够：拒绝，不再碰库存
    return redis.call('DECRBY', KEYS[1], ARGV[1])        -- 够：一步扣掉
""".trimIndent()

fun preDeduct(skuId: String, qty: Int, reqId: String) {
    val left = redis.eval(DEDUCT_LUA, listOf("seckill:stock:$skuId"), listOf("$qty")) as Long
    if (left >= 0) {
        mq.send("seckill.deducted", Deducted(skuId, qty, reqId))   // 预扣成功 → MQ 异步落库建单（削峰）
    } else {
        throw SoldOutException(skuId)                              // 已抢完，快速失败
    }
}
// Redis 只是"预扣"：真实库存以 DB 为准，消费侧用乐观锁兜底，防 Redis 与 DB 漂移
```

**热点 key 拆分**：100 万请求打同一个 `seckill:stock:1001`，Redis 集群里这个 key 只能落在单个分片上。可把库存拆成 N 个子 key（`stock:1001:0` ~ `stock:1001:9`），请求随机路由到一个子 key 扣减、汇总校对——单分片压力除以 N。

**扩展：Redis 本身的工程规范**。缓存体系的坑不都在“策略”上，还有一批出在 Redis 的使用方式上，三条规范先立住：

- **键命名有层级**：统一 `业务:对象:id` 的冒号分层（`seckill:stock:1001`、`water:order:889`），一眼读出归属与用途；禁止无前缀裸 id——多人协作下 `stock:1001` 与 `sku:1001` 谁也说不清是谁的。带可枚举维度（租户、渠道）的把维度放中间层（`water:tenant:56:order:889`），为将来按前缀批量清理留路——清理用 `SCAN` 游标匹配前缀，绝不用 `KEYS *`：它会阻塞单线程，把同一分片上的所有请求卡在后面。
- **value 控制在小对象**：单个 value 保持几 KB 量级（经验上限 10KB 以内）。原因同上：命令处理单线程，一次大 value 的读写会把整个分片堵住（网络传输 + 序列化都发生在这条命令的生命周期里）；大列表、大集合按页拆 key（`feed:1001:page:0`），序列化选紧凑格式（JSON 与二进制编码的体积/兼容性权衡见 [03-远程通信-协议序列化与演进.md](03-远程通信-协议序列化与演进.md)）。
- **TTL 是设计出来的，不是默认的**：不设 TTL 的缓存等于把失效责任全押在“下次删除”上（先更库后删缓存路线下可行，但漏删一次就是永久脏值）；设 TTL 就要显式决策**绝对过期**（到点失效，保证新鲜度上限）还是**滑动过期**（每次命中续期，适合“持续热”的数据），再叠加上文的随机抖动防同批失效。组合出常见套路：热数据 + 逻辑过期 + singleflight 重建、冷数据 + 短 TTL + 空值缓存——每种数据走哪套组合是有意识的选择，不是随手一个 setex。

## 3.2 读写分离、分库分表（Feed 流 + 桶装水订单）

**读写分离**：写走主库，读走从库，主从异步复制分担读压力。代价是**复制延迟**（毫秒到秒级）。

❌ 反例：用户刚发完帖立刻刷新个人主页，请求被路由到还没复制完的从库 → 帖子“消失” → 以为发布失败又发一遍。
✅ 修正：**读己之写**——写后若干秒内该用户的读强制走主库（网关按 userId 打标），或前端用写接口回带的快照渲染。

**分库分表**：Feed 流是天然推手——用户与发帖量持续增长，单库的时间线表迟早放不下；桶装水商城订单量从日均几千涨到几十万也是同一条路。垂直分库（按业务拆：内容库/关系库/互动库）+ 水平分片（按分片键把行散到多库多表）。核心决策是**分片键**：

```kotlin
// ✅ Feed 时间线、桶装水订单表都以 user_id 为分片键（"刷我的时间线/查我的订单"是最高频查询）
fun shardOf(userId: Long): Pair<String, String> {
    val db = "feed_db_${(userId % 4).toInt()}"             // 4 个库
    val table = "timeline_${((userId / 4) % 8).toInt()}"   // 每库 8 张表
    return db to table
}
```

❌ 反例：Feed 按 `post_id` 分片，用户刷自己时间线时没有 post_id，只能**全库全表扫描**。
✅ 修正：分片键与主查询维度一致（user_id）；post_id 里可嵌入 user_id 分片位（基因法）；运营/客服等次要维度另建异构索引，binlog 同步到 ES（3.3）。

**扩展：分片键选择五问**。分片键一定下来，这个表未来三五年的查询能力就被锁死了，改分片键 ≈ 重搬一遍数据。所以决策要慢，用五个问题逼自己把候选键过一遍——以桶装水商城订单表的三个候选（`userId` / `orderId` / `merchantId`）为例：

**第一问：查询模式——最高频的查询带什么条件？** 订单表的真实负载：C 端“我的订单”列表（按 userId + 时间倒序分页）占绝对大头；水站/配送员工作台“我要送的今日订单”（按 merchantId + 日期）；客服按 orderId 点查详情。三个候选对照：`userId` 让 C 端主查询一次直达分片；`orderId` 只让点查占优，“我的订单”没有 orderId 只能全片广播；`merchantId` 让水站侧直达、C 端受伤。判据：**让占流量 80% 的查询直达，别为 5% 的查询牺牲 80%**。

**第二问：倾斜风险——键值分布均匀吗？** userId 来自海量 C 端用户，哈希后天然均匀；merchantId 是危险维度——大水站（连锁、写字楼集中区）的日订单量可能是小站的几十倍，按商户分片会出现一个分片装下全站三成流量、其余分片闲置的“热分片”；orderId 哈希绝对均匀但没有任何业务语义。判据：倾斜维度要么弃用，要么做组合扰动（如 `merchantId + 日期`、`merchantId + orderType` 拼接后再哈希，把大商户摊薄到多个分片），但组合键会让“按单一维度查”退化成多片查询——扰动也有代价。

**第三问：扩容迁移——将来搬家按什么粒度搬？** 分片键决定数据的再分布单位。按 orderId 哈希，迁移粒度是单行，理论上最平滑但每次扩容几乎全量重分布；按 userId，同一用户的全部订单天然同片，迁移以“用户”为单位成组搬，关联数据（收货地址、周期购订阅）可以跟着用户走，逻辑上更完整。判据：优先选**能成组迁移**的键——搬家按用户搬，永远比按行搬好对账。

**第四问：跨片查询——哪些维度注定要跨片？** 选了 userId，“某商户今日全部订单”（水站对账）就注定跨片。处理顺序：先看这条查询的频率和时效要求——水站工作台可以接受秒级延迟 → binlog 异构同步一份数据到 ES 或按商户维度建异构索引表（读侧多一份数据，换写侧分片键干净）；真的高频且强实时，才考虑冗余双写。判据：**接受一两个跨片维度走异构索引，绝不为了消灭跨片把分片键做成拼接怪物**。

**第五问：事务边界——分片键能帮事务省多少事？** “下单扣库存 + 建订单”若同库可走本地事务，但桶装水的库存往往独立分片甚至独立服务（库存中心），水桶押金又是另一个上下文——分片键把“同一用户订单相关数据”聚到一起，能缩小事务边界，却消除不了跨服务一致性问题（解法在第 4 节分布式事务）。判据：分片键按查询模式选，事务边界用事务方案补，**不要让事务需求绑架分片键**——为凑本地事务把库存硬塞进用户分片，等于把库存做成了用户维度的私有表，反向制造倾斜。

五问结论（桶装水订单）：**主键选 `userId`**——查询模式最占优、分布均匀、可成组迁移；`orderId` 用基因法嵌入 userId 分片位让点查也直达；`merchantId` 视角走异构索引。这套问法同样适用于 Feed 时间线（user_id）与工单表（tenant_id + 创建时间）。

**扩展：分库分表前的三道省命题**。分库分表是“数据架构里最贵的手术”，动手前先确认便宜的招都试过了：**第一招索引与慢查询治理**——一半的“数据库扛不住”其实是缺索引或低质量 SQL（全表扫、深分页、隐式类型转换），先看慢查询日志，很多时候一行索引把 P99 从 2 秒压到 20 毫秒；**第二招归档与冷热分离**——订单表 3 亿行里 90% 是两年前的不活跃数据，把冷数据按年归档出去，热表瘦身一个量级，比拆库便宜且可逆；**第三招读写分离 + 缓存**——读压力大走 3.1 与本节开头的读写分离，命中率上去了单库寿命再延长数倍。三招都使完、单库写入仍然逼近上限（磁盘 IO、连接数、锁竞争任一触顶），才进入分库分表——拆早了的代价是跨片查询、分布式事务、全局 ID 一整套复杂度提前进场。

**路由与扩容**：`userId % 4` 这种取模路由，4 库扩 8 库时约一半数据要迁移。常用解法是**预分片**——一开始就建 1024 个逻辑分片（哈希后对 1024 取模），映射到 4 个物理库；扩容时只改“逻辑分片 → 物理库”的映射，迁移量可控。桶装水商城订单涨 50 倍时走的正是这条路。

**扩展：扩容的三条路线——迁移量与路由改动对比**。“预分片”背后的通用思想值得展开：数据位置不要靠算术硬算，要变成**可管理的映射**。三种主流路线（取模路由作对照基线）：

| 路线 | 数据定位方式 | 4 库 → 8 库的迁移量 | 路由改动 | 适合场景 |
|---|---|---|---|---|
| 取模路由（基线） | `hash(key) mod N` 直接算 | **翻倍迁移一半**：模数翻倍（N→2N）时恰好一半 key 落点改变（4→8 即 50%）；改成非倍数模数才近乎全量 | 客户端改模数，新旧数据并存期间要按新旧两套规则双查 | 只适合一步到位、之后不再扩容的场景 |
| 一致性哈希（+虚拟节点） | key 与节点都放到哈希环上，顺时针找最近节点 | **约 1/(N+1)**：每加一个节点只接管环上相邻区间的数据，其余不动 | 客户端要拿到环视图（元数据），节点增删需广播刷新 | 节点频繁增删、无预规划的缓存类集群；分布均匀性依赖虚拟节点数量 |
| 翻倍扩容 | 固定翻倍：N → 2N，`hash(key) mod 2N` | **恰好 50%**：旧库 i 的数据一半留在 i、一半搬去 i+N，映射规则简单可增量执行 | 模数从 N 改 2N，配合双写 + 按站灰度切读，可回滚 | **关系库分库的主路线**：行级迁移成本高，翻倍让迁移可分批、可对账；桶装水订单 4→8→16 每次都翻倍 |
| 槽位映射（预分片） | 固定 S 个逻辑槽（如 1024/16384），槽 → 物理节点是一张可编辑映射表 | **按槽精确计**：只搬被重新分配的那部分槽的数据，迁移前就能算出确切工作量 | 客户端路由逻辑**零改动**，只从配置中心拉新映射表 | 要“路由代码不再因扩容而改”的系统；Redis Cluster（16384 slot）、Kafka 分区、分库分表中间件（ShardingSphere 类）共同的路由哲学 |

三条路线的共同点：都把“数据在哪”从**算术直接计算**降级为**区间/映射查询**，扩容从“全量重算”变成“局部搬家”。选型判据一句话：节点经常动态增删、存的是可再生缓存 → 一致性哈希；关系库分库、要分批迁移可灰度可回滚 → 翻倍扩容；追求扩容不碰路由代码 → 槽位映射。落地时再叠加两件工程保险：迁移期间新旧路由**双写**（写都写，读切灰度），迁移完成后用对账任务校验新旧两侧数据一致再摘旧写——这与微服务拆库的影子对拍手法同源（见第二阶段微服务的渐进拆分）。

**连带问题**：跨分片无法用数据库自增主键 → 全局 ID 用雪花算法；跨分片事务 → 第 4 节；跨分片排序分页 → 游标翻页 + 各分片归并，深度翻页要限制。

**扩展：雪花算法的两个经典坑**。连带问题里点到雪花 ID，它值得单独交代，因为分库分表上线后主键是“改起来最痛”的基础设施——所有外键、索引、对账都建立在它上面。结构是 64 位：1 位符号 + 41 位毫秒时间戳 + 10 位机器 ID + 12 位毫秒内序列号，单机每毫秒可发 4096 个，天然趋势递增，对 B+ 树索引友好（近似顺序插入，不频发页分裂）。两个坑：**时钟回拨**——NTP 校时把机器时钟往回调，新生成 ID 的时间戳位小于已发出的 ID，趋势递增被破坏甚至重复；常规处理是回拨小于阈值就自旋等待时钟追上、超过阈值直接拒绝服务并告警（美团 Leaf 等工业方案在此基础上再持久化最近时间戳做兜底）。**机器 ID 分配**——10 位机器 ID 必须全局唯一，靠配置文件手填迟早撞号（撞号 = 两个节点发出完全相同的 ID，极难排查），工程上要经 ZooKeeper 顺序节点、数据库号段或注册中心申请，不能相信“运维保证不会填重”。另有一个选型辨析：**订单号别直接用雪花 ID 对外暴露**——时间戳位泄露下单速率、ID 连续可枚举（竞争对手按序遍历能估算你的单量）；对外的业务单号另走一层带校验位的映射号，雪花 ID 只做库内主键。

## 3.3 NoSQL 选型：KV / 文档 / 列族 / 图 / 搜索引擎（IM + Feed）

| 类型 | 代表 | 数据模型 | 擅长 | 场景用法 | 不擅长 |
|---|---|---|---|---|---|
| KV | Redis | key-value | 极低延迟读写、丰富数据结构 | 秒杀预扣库存（3.1 的 Lua）、IM 在线状态/未读数、Feed 热榜缓存 | 复杂查询、大 value |
| 文档 | MongoDB | JSON 文档、schema 灵活 | 字段多变、嵌套结构 | Feed 帖子与评论（图文嵌套）、桶装水订单快照 | 多表关联、强事务 |
| 列族 | HBase / Cassandra | 宽表、按 rowkey | 海量写入、按主键点查/范围扫 | **IM 全量消息落档**（会话 ID+序号作 rowkey）、IoT 时序数据 | 二级查询、聚合分析 |
| 图 | Neo4j | 点和边 | 多跳关系查询 | 风控（同收货地址/同设备的欺诈团伙）、Feed 好友关系 | 大范围扫描 |
| 搜索 | Elasticsearch | 倒排索引 | 全文检索、多维过滤聚合 | 工单/订单/帖子搜索（通用能力），配合分库分表做异构索引 | 强一致、点查、计数 |

**IM 为什么选宽表/KV**：消息写入是持续高吞吐（百万在线 × 每秒多条），且读取模式极其固定——“按会话拉最近 N 条、按序号范围补拉”。rowkey = 会话 ID + 单调递增序号，天然按会话聚簇、天然有序，正是列族库的主场；热会话再叠一层 Redis。**Feed 时间线**读取也是“按用户拉取、按时间排序”，结构同构，可复用同一选型。

**扩展：宽表 rowkey 设计三原则**。选了列族库，rowkey 就是唯一的索引——它设计错了，后面没有第二条路可补救。三条铁律：**查询对齐 rowkey**——所有查询必须能从 rowkey 前缀定位（前缀匹配才能走聚簇范围扫）。IM 的“按会话拉最近 N 条”对齐“会话 ID+序号”，但“列出某用户的全部会话”就对不齐，解法是冗余一份用户的会话 ID 集合放 Redis（会话列表与消息体分开存），而不是让消息表去迁就第二个查询维度。**防单调热点**——rowkey 若以单调递增的时间戳开头，写入永远落在集群最后一个 region/分片上，加多少台机器写吞吐都不涨（水平扩容完全失效）；把时间戳放到 key 尾部（如 `会话ID+序号`，序号本身才递增），或做翻转（`MAX-时间戳`），让写入散到各个分片。**长度克制**——rowkey 越长，每一行、每个索引项、每次 compaction 的存储与比较开销都乘一遍；IM 的会话 ID 用定长短 ID（如 8 字节哈希）而不是完整群号拼字符串。这三条与 3.2 的分片键选择是同一套思想：**写入时定下数据分布，读取时按同一把钥匙取**——分布键选错，两个方向一起遭殃。

❌ 反例：用 ES 扣库存——ES 是**近实时**（refresh 前后读到的不一致），写入可见性有延迟，并发扣减必超卖。
✅ 修正：扣减只在强一致存储（MySQL 事务或 Redis+Lua），ES 只承担“搜”，通过 binlog/消息异构同步，接受秒级延迟。

**扩展：先问四个问题再选 NoSQL**。上面的五型对照表是“答案集”，真到选型现场要有一套**提问顺序**，让数据自己走到正确的类型上。四个问题按序问，每一问的典型答案直接映射候选类型：

**问题一：数据的形状是什么？** 扁平键值对（在线状态、计数器、配置项）→ KV；嵌套文档、字段随业务类型变（帖子正文带图文混排、订单商品快照、低代码表单数据）→ 文档库；按时间顺序追加、只按主键范围读（IM 消息、设备上报、埋点流水）→ 宽表/时序；**实体之间的关系本身就是查询对象**（关注链、同设备团伙）→ 图；非结构化文本 + 任意字段组合过滤（工单描述、商品搜索）→ 倒排索引。形状不对，后面全白费——用宽表存嵌套文档，取一个字段要读整行大 value，等于自残。

**问题二：查询模式是什么？** 按 key 点查 / 主键范围扫 → KV、宽表的主场；任意字段组合过滤 + 聚合（“近 7 天 P0 工单按类目分组计数”）→ 搜索引擎；固定路径的多跳遍历（“这个人关注的人里谁也关注了他”）→ 图；全表扫描聚合分析 → 谁都不该干，归列式分析库/数仓。判据：**把系统前三名的查询写下来**，每种 NoSQL 只服务它能直达的那几名，剩下的转交给对应组件。

**问题三：一致性要求是什么？** 余额、库存这类“错一次就是资损”的写 → 关系库事务（或 3.1 的 Redis+Lua 预扣 + DB 兜底），绝大多数 NoSQL 是最终一致、直接用会埋雷；计数、点赞数这类“短暂漂移无所谓”的 → Redis 甚至 CRDT（收敛机制见 [02a-示例-cap-algorithms/](02a-示例-cap-algorithms) 的 G-Counter 示例）；搜索结果可接受秒级陈旧 → ES 近实时完全够用。判据：先给每类数据标“一致性等级”，再让存储对号入座——一致性等级与存储类型的错配（用 ES 管钱、用关系库扛日志洪峰）是选型事故的两大主源。

**问题四：规模与增速是多少？** 单表千万行以内、写入每秒几千以下——别折腾 NoSQL，关系库 + 索引 + 3.2 的分表足够，引入新存储的运维成本远大于收益；写入每秒十万级、单表预估十亿行、数据按时间天然分区（消息、上报）——宽表/时序库上场；增量不可删减、近期热远期冷——时序库 + 冷热分层。判据：**规模不到不上 NoSQL**，“为了简历好看引入 MongoDB”是选型界的经典笑话，但每一年都在真实上演。

四个答案指向同一个类型 → 放心用；指向两个以上类型 → 说明系统里有**多个负载**，正确做法是拆开（消息归宽表、搜索归 ES、主数据归关系库），而不是找一个“全都能干”的库——那种库不存在，存在的只是每样都会一点、每样都不极致的数据库。

**扩展：用关系库 + JSON 字段替代文档库的判据**。最常被过度引入的就是文档库——“字段会变”不等于“需要 MongoDB”。满足下面四条，关系库加一个 JSON 列就是更优解：

1. **规模没触发分库分表**：数据量在单库可容纳范围内，关系库的索引、事务、备份体系全部保留。
2. **查询只按稳定的少数列过滤**：列表页按 id、type、status、时间查，可变字段只做展示；偶有按可变字段查的高频项，用 3.4 的生成列 + 索引局部提升——不需要文档库的“任意字段任意查”。
3. **事务需求真实存在**：订单主表与明细要原子写、外键约束要兜底，文档库的弱事务反而是倒退。
4. **团队运维面要克制**：已有成熟的关系库监控/备份/容灾，为一个“字段灵活”引入一整套新存储的运维成本，大于它换来的灵活性。

反过来，出现以下信号才真正换文档库：规模已到要分库分表且文档之间无关联查询；可查询字段维度失控（几百个字段都可能成为筛选条件，生成列索引维护不过来）；写入吞吐超出单关系库上限；读模式是“整个文档一次取走”而非“多表拼装”。还有一条反例预警：引入了 MongoDB 却按关系库的范式建模（文档里只存外键、读时多次回查“join”），等于付了文档库的运维钱、用了文档库最差的用法——文档建模就要**内嵌聚合**，一次读取拿全整个业务对象。

## 3.4 动态字段存储：低代码平台的三方案（数据架构经典 trade-off）

低代码平台的表单由用户拖拽配置，字段集合随时变：今天报修单有“故障照片”，明天巡检单加“设备序列号”。工单中心“新增工单类型只配表单不改代码”，本质是同一个问题。**用户自定义字段怎么存**是必考的存储选型，三种方案各有明码标价的代价。

**方案 A：EAV 表**——一行存一个字段（`form_data(entity_id, field_code, value_str)`）：

```kotlin
// ❌ EAV：按自定义字段过滤要"行转列"，字段一多 SQL 膨胀、索引难命中
// SELECT entity_id FROM form_data WHERE field_code='priority' AND value_str='P0'
// INTERSECT
// SELECT entity_id FROM form_data WHERE field_code='device_line' AND value_str='A1'
// —— 查"紧急 + A1 产线"的工单：条件越多交集越多，且 value 全是字符串，类型与统计口径失控
fun findTickets(conds: Map<String, String>) = formDataTable.query(conds)  // 加字段零成本，但查询代价巨大
```

**方案 B：JSON 列**——一行一张表单，自定义字段收进 JSON：

```kotlin
data class Ticket(
    val id: Long,
    val typeId: Long,          // 工单类型 → 对应哪份表单 Schema
    val schemaVersion: Int,    // 历史单据按提交时的旧版 Schema 渲染与校验（版本化）
    val fields: String         // JSON：{"priority":"P0","device_line":"A1","photos":["url1"]}
)

// ✅ 高频过滤字段用"生成列 + 索引"提升为真正的索引列（MySQL 8 / PostgreSQL JSONB 均有等价能力）
// ALTER TABLE ticket ADD COLUMN priority VARCHAR(8)
//   GENERATED ALWAYS AS (fields->>'$.priority') STORED, ADD INDEX idx_priority(priority);
fun findP0Tickets(typeId: Long) =
    ticketRepo.where("type_id = ? AND priority = 'P0'", typeId)   // 走索引，而不是全表扫 JSON
```

**方案 C：动态建表**——每个表单 DDL 一张专表，字段即列。查询性能最好（原生列、原生索引、原生聚合），但代价沉重：改表单 = ALTER TABLE（DDL 审批、锁表风险）；表数量激增拖累连接池与元数据；跨表单聚合要 UNION 大量结构各异的表；Schema 版本演进最痛。只适合字段集合稳定、数据量大的少数专有场景（如某大客户的定制工单类型）。

**三方案对比**（务必记住这张表）：

| 维度 | A：EAV 表 | B：JSON 列 + 生成列索引 | C：动态建表 |
|---|---|---|---|
| 加字段 / 写入灵活度 | 极高（插一行即可） | 高（新字段直接进 JSON） | 低（ALTER TABLE / DDL 治理） |
| 按自定义字段过滤 | 差（行转列、难索引） | 中（生成列索引覆盖高频字段） | 好（原生列与索引） |
| Schema 演进成本 | 低 | 低（老数据按 schemaVersion 兼容） | 高（历史表迁移） |
| 聚合统计 | 差（类型靠约定） | 中（类型来自 Schema 定义） | 好（SQL 原生） |
| 运维复杂度 | 低 | 低 | 高（表数量失控、DDL 风险） |
| 适用 | 字段极多但极少按字段查 | **大多数低代码平台的默认解** | 字段稳定 + 数据量大的专表场景 |

默认答案是 **B**：查询性能不足时，只把少数热点字段“提升”为生成列索引——性能问题局部治，不为个别字段付出全局 DDL 成本；C 留作逃生舱。这与第二阶段“元数据驱动 + 解释器模式”呼应：Schema 是解释执行的配置，存储方案要让配置演化足够便宜。

**扩展：三方案的数据模型对照——同一条查询的三种写法**。对比表容易背，真正内化要看“同一份数据、同一条业务查询”在三种存储下的代码形状。业务设定统一为：报修工单，自定义字段“优先级（priority）”与“设备产线（device_line）”，业务查询是**“找出紧急且 A1 产线的工单”**。

```kotlin
// 片段：方案 C 宽表（动态建表）——字段即列，一个表单类型一张专表
data class RepairTicketWide(           // 对应表 repair_ticket，字段都是原生列
    val id: Long,
    val title: String,
    val priority: String,              // 原生列：有类型、可索引、可 AVG/GROUP BY
    val deviceLine: String,            // 新增字段 = ALTER TABLE 加列（代价在写侧）
    val photos: List<String>
)
// 查询怎么写：平面条件直接 AND，最自然
val hits = repairTicketRepo.where("priority = ? AND device_line = ?", "P0", "A1")
```

```kotlin
// 片段：方案 B JSON 列——一张主表，可变部分收进 fields JSON 字段
data class TicketJson(
    val id: Long,
    val typeId: Long,                  // 哪份表单 Schema
    val schemaVersion: Int,            // 按提交时版本渲染
    val fields: TicketFields           // 持久化为 JSON 列
)
data class TicketFields(
    val priority: String? = null,
    val deviceLine: String? = null,
    val photos: List<String> = emptyList()
)
// 查询怎么写：稳定列用普通条件，自定义字段用 JSON 取值表达式；
// 不建生成列索引时是这样（可能全表扫）：
val hits1 = ticketRepo.where("type_id = ? AND fields->>'$.priority' = ? AND fields->>'$.device_line' = ?",
    typeId, "P0", "A1")
// 高频后按上文 ALTER TABLE 把 priority 提升为生成列，查询退化为普通条件走索引：
val hits2 = ticketRepo.where("type_id = ? AND priority = ?", typeId, "P0")
```

```kotlin
// 片段：方案 A EAV——一行存一个字段值，查询靠"每个条件取一批行 + 集合交集"
data class FieldRow(val entityId: Long, val fieldCode: String, val valueStr: String)
// 查询怎么写：条件不在一行上，而在多行之间——每个条件各查一遍再求交集
val p0 = fieldRepo.where("field_code = ? AND value_str = ?", "priority", "P0").map { it.entityId }.toSet()
val a1 = fieldRepo.where("field_code = ? AND value_str = ?", "device_line", "A1").map { it.entityId }.toSet()
val hits = p0 intersect a1             // N 个条件 = N 次子查询 + 交集；条件越多越慢，且全是字符串比较
```

三条查询摆在一起，差异一目了然：**宽表**是“列 = 值”的平面条件，索引、类型、统计全是数据库原生能力，查询最省、写侧（DDL）最贵；**JSON 列**是“取值表达式 = 值”，写侧最灵活，查询要靠生成列索引把热点条件“翻译回”平面条件——性能按需局部购买；**EAV** 是“每个条件一批行 + 集合运算”，写入最灵活，查询成本随条件数线性膨胀，且 `value_str` 一律字符串，`priority < 'P2'` 这类范围比较、按数值聚合全部失真。同一条“P0 + A1 产线”的查询，三者检索成本通常差一到两个数量级——这正是对比表里“按自定义字段过滤：差 / 中 / 好”三格的代码级注脚。顺带一提 3.3 的判据在这里同样成立：如果平台规模根本没到分库分表，方案 B 的“关系库 + JSON”连新存储都不用引入，一套 MySQL 走到底。

**扩展：生成列索引的治理红线**。方案 B 的“热点字段提升为生成列”用顺手后容易泛滥，两条红线先立住。**红线一：单表的生成列索引控制在个位数**——每加一个都是一份写放大与一次 DDL 变更，“哪个字段查询变慢就提升哪个”无节制地做下去，等于把方案 C 的 DDL 成本从后门请回来（只是化整为零了）；提升哪个字段由**查询埋点数据**决定（慢查询日志、P99 耗时排行），不是由产品经理“以后可能想按这个筛”决定。**红线二：发布顺序是先 DDL 后发版**——生成列与 JSON 原值的一致性由数据库保证（STORED 列随行更新，存量行也会被回填），但新字段的生成列必须先建好再让新版代码写入，否则上线窗口内会出现“JSON 写入成功、生成列还没建”的行，按该字段过滤时凭空查不到；这与低代码平台“Schema 先行、灰度发布”的治理节奏是同一件事（示例场景详见 [示例项目场景/00-导览.md](../示例项目场景/00-导览.md) 低代码平台的发布治理小节）。

## 存储方案速查决策表

按负载类型直接查表，配合 3.1~3.4 的展开内容使用（首选方案点到组件，细节回对应小节）：

| 负载类型 | 典型场景 | 首选方案 | 备选 | 何时不够用（升级信号） |
|---|---|---|---|---|
| 读多写少 | 商品详情、配置、字典（桶装水商城商品页） | 多级缓存（CDN + 本地 + Redis，3.1）+ 关系库主存 | 读写分离：主库写 + 从库分担缓存未命中的回源读 | 命中率上不去（长尾 key 太散、缓存全是冷数据）→ 先问业务要不要这么多数据；单 key 热点打满单分片 → 热点 key 拆分 + CDN 扛前一层 |
| 写洪峰 | 设备上报、报工采集、IM 消息落档 | MQ 削峰 + 列族宽表/时序库批量写（3.3） | 关系库分区表 + 攒批插入（量级未到时） | 单集群写入逼近上限、要按时间自动过期/降采样 → 时序库 + 冷热分层；查询维度超出 rowkey → 补异构索引 |
| 复杂关联 | 订单 + 用户 + 商户多维关联、报表（分库分表前的日常） | 关系库同库 JOIN（单库时代默认答案） | 只读从库跑重查询；T+1 归档到数仓 | 分库分表后跨片 JOIN 失效 → 读侧冗余宽表或 binlog 异构到 ES；重型多维分析 → 列式分析引擎，别压在交易库上 |
| 全文检索 / 多维过滤 | 工单搜索、订单多条件查询、帖子搜索 | Elasticsearch，binlog/消息异构同步（3.3） | 关系库 LIKE / 前缀索引（数据量小、模式固定时兜底） | 需要强一致点查或精确计数 → 搜到 id 后回查主存，ES 只当“目录”；相关性排序要求极高 → 专用召回与排序链路 |
| 时序数据 | 监控曲线、传感器流水、售水机上报 | 时序数据库（按时间分区、预聚合、TTL） | 宽表按“rowkey + 时间戳”范围扫（3.3 列族路线） | 要任意维度即时 ad-hoc 聚合（不限预聚合维度）→ 归档到列式分析引擎；要按设备属性反查设备集合 → 补一份元数据倒排 |

速查表背后只有一条总判据：**先认清负载（读写比、一致性等级、规模），再让存储对号入座；一个系统多种负载就多种存储各司其职，用异构同步（binlog/消息）把它们粘起来**——而不是寻找一个万能库，也不是把最熟悉的那个库用到它的不擅长区（3.3 的 ES 扣库存反例就是典型）。
