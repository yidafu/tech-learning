把一次函数调用从进程内挪到网络对面，它就失去了三样东西：**确定的时间**（多快返回没人承诺）、**确定的可靠性**（可能超时、可能重复、可能丢）、**确定的边界**（一次发送对应一次接收吗？不保证）。本节讲的就是在“不可靠且有成本”的网络之上，怎么选接口风格（2.1）、怎么定报文格式（2.2）、以及这一切共同的物理前提（2.3）。

## 2.1 REST vs gRPC vs 消息 + 物联网多协议接入

**内部服务间选型**（以桶装水商城拆出的微服务为例）先看这张表：

| 维度 | REST | gRPC | 消息（MQ） |
|---|---|---|---|
| 协议/格式 | HTTP/1.1 + JSON | HTTP/2 + Protobuf | AMQP/Kafka 私有协议 |
| 通信模式 | 请求-响应（同步） | 同步 + 四种流式 | 异步、单向 |
| 性能 | 文本序列化，体积大、较慢 | 二进制 + 多路复用，快 | 吞吐高，但有延迟 |
| 契约 | OpenAPI（弱约束） | .proto 强类型 IDL，代码生成 | 消息 schema（可选） |
| 耦合 | 调用方知道对方地址和接口 | 同左，但有版本化工具 | 生产者只发事件，不知道谁消费 |
| 典型场景 | 对外 API、BFF、低频管理接口 | 内部高频服务调用、跨语言 | 事件广播、削峰、异步解耦 |

**选型原则**（桶装水商城落地）：对外——小程序/H5 的商品、下单 API 用 REST（通用、可 curl 调试、网关生态友好）；内部——下单服务到库存服务的高频同步预扣用 gRPC（省流量、低延迟、.proto 契约清晰）；旁路——下单成功后通知配送排线、记押金流水、发短信，不需要立刻知道结果，一律上消息。

### 接口风格选型四问

上表是三种风格的静态对照；真正选型时按顺序问四个问题，答案会把绝大多数接口“推”到唯一合理的位置上：

**第一问：调用方是谁？**
- 组织外（小程序/H5、第三方合作方、开放平台）→ REST。HTTP+JSON 是最大公约数：谁都能调、能 curl 调试、能直接享受 CDN 与 API 网关生态，第三方接入文档成本也最低。
- 组织内的服务 → 进入第二、三问再定。
- 设备 → 不由你选，由设备侧能力决定（MQTT/CoAP/HTTP/厂商私有 TCP），接入层做适配，见本节末“多协议适配层”。

**第二问：这次调用对时延与吞吐的要求是什么？**
- 必须“此刻有结论”且高频（下单预扣库存、支付风控查询）→ gRPC：二进制省带宽、HTTP/2 多路复用省连接、强契约省联调。
- 必须“此刻有结论”但低频（后台管理、运营配置）→ REST 足够，不必为低频接口背上 IDL 工具链。
- 不需要此刻有结论（通知、广播、削峰）→ 消息。用“时延”换“吞吐与解耦”，是一笔划算的交易。

**第三问：契约演进频率如何？**
- 字段经常增改、消费方多且各自独立部署 → 强 IDL（Protobuf/Avro）+ 兼容纪律（见 2.2 的 schema 演进规则），靠代码生成与编译期检查挡住破坏性变更。
- 接口基本冻结、以读为主 → JSON 的弱约束反而是灵活性。

**第四问：团队技术栈与运维能力如何？**
- 多语言团队、跨技术栈互调 → gRPC/REST 这类有成熟多语言生态的方案，慎用绑定单一语言的协议。
- 想上消息，先自问有没有运营 MQ 的能力：消息可靠性、消费幂等、顺序、堆积告警、死信处理是一整套运维设施——没有这套设施，消息不是免费午餐（主笔记 §3.4 事件驱动补充场景列过四条“该上消息”的共性信号，反过来读就是“没准备好别上”）。

**四问 → 决策树（文字版）**：

1. 调用方在组织外？→ 是：REST（网关处可做“外部 HTTP → 内部 gRPC”的协议转换，对外形态不变）。
2. 这次调用需要“此刻有结论”吗？
   - 不需要 → 消息（旁路异步，消费端必须幂等，见下文）。
   - 需要 → 再看频率：内部高频走 gRPC，低频或调试密集走 REST。
3. 是设备接入？→ 按设备能力选协议，接入层插件化适配。
4. 全链路强同步的层数已经 ≥ 3？→ 先考虑把末段改异步——可用性会“相乘”（见下文超时传播一节与自测第 4 题）。

一句话判据：**接口风格不是气质问题，而是“调用方 × 时延要求 × 演进频率 × 运维能力”四个约束的求解结果**；同一系统里三种风格并存是常态，不是摇摆。

**反例**：❌ 下单成功后同步串起所有旁路：

```kotlin
// ❌ 同步长链：短信网关挂 30 秒，整个下单就挂 30 秒
fun placeOrder(cmd: PlaceOrderCmd) {
    orderRepo.create(cmd)
    inventoryClient.deduct(cmd.skuId, cmd.qty)
    couponClient.use(cmd.couponId)          // 每一步都是一次网络往返
    depositClient.record(cmd.userId, cmd.deposit)   // 押金流水也要此刻记完？
    smsClient.notify(cmd.userId)            // 短信网关一抖，用户下单失败
}
```

**修正**：✅ 交易核心同步（gRPC 调库存），旁路异步（发一条 `order.created` 事件，押金/排线/积分/短信各自订阅）：

```kotlin
// ✅ 核心同步、旁路异步：下单只依赖真正决定成败的两步
fun placeOrder(cmd: PlaceOrderCmd) {
    val orderId = orderRepo.create(cmd)                 // 本地事务：订单落库 + 消息出站记录（见 4.5）
    inventoryClient.deduct(cmd.skuId, cmd.qty)          // gRPC 同步：扣库存必须此刻有结论
    outbox.publish("order.created", OrderCreated(orderId, cmd.userId))
}   // 押金/排线/短信由各自消费者订阅 order 生命周期事件，失败重试互不影响下单
```

旁路异步之所以敢“失败就重试”，前提是每个消费者都幂等——消息中间件默认给的是 at-least-once 语义（至少送达一次，可能重复）。幂等怎么落到 HTTP 语义上，值得单独展开。

### 把幂等设计落到 HTTP 语义

幂等（idempotent）指同一操作执行一次与执行多次，效果相同。HTTP 方法语义里其实早就内置了这层设计，很多人天天在用却说不清：

**天然幂等的方法**。GET 只读，执行多少次都无副作用；PUT 按“资源标识 + 整体覆盖”设计时天然幂等——`PUT /orders/SO-001` 携带完整订单状态，重复提交也只是覆盖成同一个状态；DELETE 按 id 删除，第二次执行只是“删了个不存在的东西”，结果一致。但要警惕把幂等方法用出不幂等的语义：`PUT /cart/counter?inc=1`（在原值上加 1）虽然方法叫 PUT，执行两次计数就多了 2——**幂等性属于语义，不属于方法名**。反过来，GET 也不该藏副作用（“GET 一下触发发货”），副作用要显式走命令/消息。

**POST 天然不幂等**，而交易动作（下单、支付、退款、核销）全是 POST。工程防重是三层防线，缺一不可：

1. **入口层**：Idempotency-Key 去重（下一段展开）；
2. **业务层**：状态机检查——订单已是“已支付”状态就拒绝再次支付（桶装水押金状态机同理，见[示例项目场景/02-桶装水商城](../示例项目场景/02-桶装水商城.md)的“押金管理”模块）；
3. **数据层兜底**：数据库唯一约束（流水表 `unique(user_id, out_trade_no)`）。前两层都可能被并发击穿：用户双击、重试风暴、主备切换后的重复执行——只有唯一约束能保证并发同撞时必有一方失败。

**Idempotency-Key 头的工程用法**。这是 HTTP 生态的标准实践（Stripe 等支付平台对外 API 的标配），四条约定：

- **生成**：客户端在“一次业务意图”开始时生成（UUID，或业务号如 `userId+毫秒时间戳+序号`），整条重试链路复用同一个值。重试时重新生成 key 是最常见的实现事故——去重直接失效，下面的可运行示例会演示后果。
- **命中行为**：服务端发现同 key 已处理过，**重放上次响应**而不是报错——调用方要的就是“上一次的结果”。也可约定返回 `409 Conflict` 附原结果引用，但重放对客户端最友好。
- **并发保护**：两个同 key 请求同时到达，必须只放行一个执行（唯一约束插入或分布式锁），晚到者直接拿重放结果。
- **时效与作用域**：去重记录带 TTL（覆盖最大重试窗口，常见 24 小时），并在 key 上拼接调用方标识（如 `app:watermall:key`），防止不同商户生成同样的 key 互相“命中”。

同一个模式换三身衣服：支付渠道的重复回调（第六阶段支付场景）、IM 客户端弱网重发、水表断网补传（本节自测第 2 题）——本质都是“at-least-once 传输 + 以业务意图为单位的去重”。

### 可运行示例：同一 Idempotency-Key 重复提交只处理一次

场景：桶装水商城“创建订单”接口。模拟网络层规则：每个新 key 的**第一跳必超时**——服务端其实已处理成功，只是响应在回程丢失；同一 key 的重试畅通。这正是分布式系统最经典的困境：**超时不等于失败，服务端可能已经成功**。完整代码（不依赖任何框架，纯 Kotlin 手写网络模拟与 Map 去重，已实际编译运行验证，kotlinc 2.2.20）：

```kotlin
// IdempotentRetryDemo.kt —— 最小 HTTP 风格接口的幂等重试演示
import java.util.concurrent.ConcurrentHashMap

// ---------- 应用层：幂等的下单服务 ----------
data class CreateOrderReq(val skuId: String, val qty: Int)
data class CreateOrderResp(val orderId: String, val replayed: Boolean) // replayed=true 表示重放上次结果，本次未执行业务

class OrderService {
    private val results = ConcurrentHashMap<String, CreateOrderResp>() // key = Idempotency-Key → 上次结果
    var executedCount = 0                                               // 业务逻辑真正执行过的次数
        private set

    // synchronized：同一个 key 并发同时到达，也只放行一个，另一个拿重放结果
    fun createOrder(idemKey: String, req: CreateOrderReq): CreateOrderResp = synchronized(this) {
        val hit = results[idemKey]
        if (hit != null) return CreateOrderResp(hit.orderId, replayed = true) // 已处理过 → 重放，不再执行
        executedCount++
        val resp = CreateOrderResp(orderId = "SO-" + executedCount.toString().padStart(4, '0'), replayed = false)
        results[idemKey] = resp
        println("  [服务端] 真正执行业务：key=$idemKey sku=${req.skuId} qty=${req.qty} -> ${resp.orderId}")
        resp
    }
}

// ---------- 网络层：每个新 key 的第一跳必超时（响应丢失），同一 key 的第二跳畅通 ----------
class LossyNetwork(val server: OrderService) {
    private val firstHopFailed = ConcurrentHashMap.newKeySet<String>()

    fun post(idemKey: String, req: CreateOrderReq): CreateOrderResp {
        if (firstHopFailed.add(idemKey)) {
            server.createOrder(idemKey, req)                       // 服务端其实处理成功了
            throw IllegalStateException("SocketTimeoutException：响应在回程丢失")
        }
        return server.createOrder(idemKey, req)                    // 重试到达服务端
    }
}

fun main() {
    val net = LossyNetwork(OrderService())

    println("== 用例 1：同一 Idempotency-Key 重试（正确姿势）==")
    val key = "idem-20260301-0001"
    val r1 = try {
        net.post(key, CreateOrderReq("bwc-19L", 2))
    } catch (e: IllegalStateException) {
        println("  [客户端] 第一次尝试失败：${e.message}")
        println("  [客户端] 携带同一个 key 重试：$key")
        net.post(key, CreateOrderReq("bwc-19L", 2))
    }
    println("  [客户端] 收到 orderId=${r1.orderId} replayed=${r1.replayed}；服务端业务执行次数=${net.server.executedCount}")

    println()
    println("== 用例 2（反例）：每次重试都换新 key ==")
    var last: String? = null
    repeat(3) { attempt ->
        val newKey = "idem-20260301-naive-$attempt"                // 朴素实现：重试时重新生成 key
        try {
            last = net.post(newKey, CreateOrderReq("bwc-19L", 2)).orderId
        } catch (e: IllegalStateException) {
            println("  [客户端] 第 ${attempt + 1} 次尝试（新 key=$newKey）失败：${e.message}")
        }
    }
    println("  [客户端] 3 次尝试全部超时，放弃。last=$last")
    println("  [账实核对] 客户端没有拿到任何确认，服务端却已执行 ${net.server.executedCount} 次 —— 同一个意图产生多张订单！")

    println()
    println("== 用例 3：不同的业务请求，各自的 key（互不干扰）==")
    val keyB = "idem-20260301-0002"
    val r3 = try {
        net.post(keyB, CreateOrderReq("bwc-16L", 1))
    } catch (e: IllegalStateException) {
        net.post(keyB, CreateOrderReq("bwc-16L", 1))
    }
    println("  [客户端] 收到 orderId=${r3.orderId} replayed=${r3.replayed}；服务端业务执行次数=${net.server.executedCount}")
}
```

三个要点值得逐字读进脑子：

1. 用例 1 中客户端拿到 `replayed=true`：服务端没有重复执行业务，客户端却拿到了与第一次完全相同的订单号——**幂等去重的正确产出是“重放”，不是报错，更不是再扣一次**。
2. 用例 2 是最常见的线上事故形态：客户端“聪明地”每次重试都生成新 key，结果自己一次确认都没拿到，服务端却执行了 3 次——用户以为没买成的订单，库存被扣了三次。**key 必须绑定“业务意图”，而不是“网络尝试”**。
3. 示例里的 `results` Map 在生产中的对应物是 Redis（带 TTL）+ 数据库唯一约束的双层结构，`synchronized` 对应并发防护（唯一约束兜底）；把它压进一个进程只是为了让机制肉眼可见。

### 超时传播与重试预算

风格选完、幂等备好，同步调用还差两块仪表盘：超时怎么定，重试怎么放。

**超时预算：上游必须大于下游之和。** 一条同步链上，每一层的超时预算 = 自己的总预算 − 已消耗时间，且必须大于下游各跳之和再加本地处理余量。反着配（上游 300ms、下游各自 500ms）会出现最滑稽的浪费：上游 300ms 就放弃并断开连接，下游毫无知觉地干完整个 500ms——结果白算，还白占下游线程池。gRPC 把这件事做成了机制：deadline propagation（超时随调用链自动传递，下游拿到的是“剩余预算”）；REST 里则要靠网关/SDK 透传 deadline 头，或在 BFF 层显式分配。

算一笔账（桶装水商城 BFF，对用户承诺 800ms）：BFF → 订单服务 300ms；订单服务内部，库存预扣（200ms）与优惠券核销（150ms）**并行**发起，随后**串行**调营销服务（300ms）。并行分支的预算按“最长一支”算（200ms），不按相加算；串行段必须相加（200+300=500ms），已超过分给订单服务的 300ms——要么并行化营销调用，要么承认 BFF 的 800ms 承诺给不起，把营销改旁路异步。预算表的纪律是：**画出来，别凭主观判断**——每个服务对外承诺多少、给下游留多少，写进服务目录（第六阶段秒杀场景“从点击到落库”的容量推演用的就是同一张预算表）。

**重试风暴：三层各重试三次 = 27 倍流量。** 下游偶发超时，上游重试是善意；但一条链上每一层都在善意重试，流量就按层相乘：BFF×3 × 订单×3 × 库存×3 = 27 倍请求打到本来就已过载的下游——把“偶发抖动”放大成“全链雪崩”；重试流量还挤占了首次请求的容量，让恢复期一次次被打回去（这正是主笔记 §5.2 熔断要跳闸的典型前夜）。

四条约束把重试关进笼子：

1. **一条链只允许一层重试**——通常是离故障最近、且操作已幂等的那一层；其余层失败就透传。
2. **重试预算**：重试流量 ≤ 总流量的 10%（Envoy 等网关的现成配置），预算烧完，本时间段内不再重试。
3. **只重试“值得重试”的错误**：超时、503、连接拒绝这类瞬态错误；4xx 参数错误重试一万次也不会成功。
4. **指数退避 + 抖动（exponential backoff + jitter）**，并与熔断联动：熔断器 OPEN 时重试器直接短路，不再制造探测流量（§5.2）。

一句话判据：**超时是预算，重试是奢侈品，两者都要按“全局账”来管，而不是每个调用点各自拍一个数。**

**外部设备接入：多协议适配层（物联网平台）**。平台面对的不只是自己的服务，还有百万台设备：水表走 MQTT、老款电表走厂商私有 TCP、低功耗传感器走 CoAP（UDP）、售水机走 HTTP——报文格式各异，且**明天还会接入新协议**。❌ 反例：把每种协议的解析逻辑写进接入网关主流程，每接一批新设备改一次网关代码、全量回归。✅ 修正：协议适配层 + 编解码器插件化——**开闭原则的硬件版**：

```kotlin
// ✅ 网关只认统一的内部模型；每种协议一个编解码器，新增协议 = 注册新插件，网关零改动
interface ProtocolCodec {
    val scheme: String                                        // "mqtt" / "coap" / "tcp-vendor-a" / "http"
    fun decode(raw: ByteArray, meta: ConnMeta): DeviceUplink // 各协议报文 → 统一上行模型
    fun encode(cmd: DownlinkCommand): ByteArray               // 统一下行指令 → 各协议报文
}

class ProtocolGateway {
    private val codecs = mutableMapOf<String, ProtocolCodec>()
    fun register(codec: ProtocolCodec) { codecs[codec.scheme] = codec }   // 新厂商协议即插即用

    fun onMessage(raw: ByteArray, meta: ConnMeta) {
        val codec = codecs[meta.scheme] ?: throw UnknownProtocolException(meta.scheme)
        pipeline.accept(codec.decode(raw, meta))
        // MQTT 的 JSON、私有 TCP 的二进制、CoAP 的 CBOR……到这一行全变成了同一种 DeviceUplink
    }
}
```

这与第二阶段六边形架构的防腐层是同一个思想：**把“协议差异”挡在核心之外**，核心只面对统一模型。指令下发同理（encode 反向走一遍）。

## 2.2 序列化协议

序列化决定了每一次跨进程调用的体积与耗时，是“看不见的性能”：

| 协议 | 格式 | 体积 | 速度 | Schema | 可读性 | 典型场景 |
|---|---|---|---|---|---|---|
| JSON | 文本 | 大 | 慢 | 弱（可配 JSON Schema） | 好 | REST、日志、配置 |
| Protobuf | 二进制 | 小（约为 JSON 的 1/3~1/5） | 快 | 强 IDL | 差 | gRPC、存储通信 |
| Avro | 二进制 | 小 | 快 | 强且“读写各自 schema” | 差 | Kafka、数据仓库 |

### 序列化选型对比大表：五种主流协议

把上表扩到五种主流协议，补齐工程上最关心的四个维度：

| 协议 | Schema 演进能力 | 跨语言 | 体积/速度 | 生态与典型舞台 |
|---|---|---|---|---|
| JSON | 弱：加字段天然兼容，删改无约束（可配 JSON Schema 做校验） | 一切语言 | 大、慢 | 无处不在：REST、日志、配置、原型验证 |
| Protobuf | 强：字段号 + `reserved` 机制，加字段安全、复用编号编译期报错 | 官方多语言代码生成 | 小（约 JSON 的 1/3~1/5）、快 | gRPC、内部 RPC、存储引擎通信 |
| Avro | 最强：读写双方各自持 schema、按字段号对齐，配合 Schema Registry 独立演进 | 多语言 | 小、快 | Kafka 消息、数据仓库/数据湖（Hive/Spark 生态标配） |
| Thrift | 强：IDL + 字段号，机制与 Protobuf 同族 | 多语言 | 小、快 | Facebook 出身；HBase/Cassandra 内部 RPC，存量系统多 |
| Hessian | 弱：自描述但无严格的版本兼容承诺 | JVM 系为主，其他语言实现质量参差 | 中 | 国内 Dubbo 存量系统的默认序列化之一 |

两个容易答错的点。其一，Avro 与 Protobuf 的核心差异不在体积而在**演进模型**：Avro 允许“写方 schema 与读方 schema 各自独立演进”——读数据时自带读方 schema，按字段号对齐解读，这正适合 Kafka 里“生产者今天写的消息，消费者下个月才读”的时差场景；Protobuf 则是读写双方共用同一份 `.proto` 的不同版本，靠兼容规则兜住。其二，Thrift/Hessian 活跃度下降不是技术失败，而是生态位被 gRPC+Protobuf 挤占——新系统默认 Protobuf，见到 Hessian 优先想到“存量迁移”，而不是“新项目采用”。

同一个平台两副面孔：

- **设备上行报文（IoT）**：一台设备秒级多条 × 百万台，一条水位读数的 JSON 约 120 字节，Protobuf/CBOR 紧凑二进制压到 20~40 字节——带宽与解析 CPU 同时降一个量级，弱网下还省电省流量。
- **工单/订单管理 API**：人来调试、跨团队协作、字段低频演化——JSON 可读可 curl，弱约束反而是优点。

**两条纪律**：

1. **兼容性演化**：Protobuf 加字段没问题，但**绝不能改字段编号、不能复用已删字段的编号**——老消费者会按编号把新数据读成完全错误的类型。JSON 加字段天然兼容，这是它在外部 API 上长盛不衰的原因。
2. **禁止 Java/Kotlin 原生序列化**（`Serializable`）：体积大、慢、跨语言失败，且反序列化漏洞是经典攻击面。

### schema 演进兼容规则

两条纪律落到日常变更，是三条可执行规则——它们与第二阶段微服务“契约管理与向后兼容”的 Tolerant Reader、消费者驱动契约是一套组合拳（结构靠规则、语义靠契约测试，见 [03-微服务架构.md](../02-第二阶段/03-微服务架构.md) 2.6）：

**规则一：加字段，必须带默认值。** 新增字段的消费方要回答“老报文里没有这个字段时取什么”：显式默认值（0、空串、可空类型），并把默认值的业务含义写进契约。不允许“新字段必填”——那等于要求所有消费方同步发版，独立部署立刻破产。结构上，消费方一律按 Tolerant Reader 写解析：只取自己关心的字段，未知字段跳过；但**必填字段缺失要显式失败**，不许静默兜底硬撑。

**规则二：删字段，先停写、观察一个存留期、再停读。** 第一步，生产方停止发送该字段（读方代码还在，读了也读不到）；第二步，等历史数据自然过期——归档文件、Kafka 重放、对账单里的旧报文比你想象的长寿，账期类数据往往要留一年以上；第三步，才删读取逻辑。跳步的代价是某天为了补数重放一个月前的消息时，解析当场崩溃。

**规则三：改类型或改语义，等于发新字段，不做原地修改。** 金额单位从元改分、字符串改枚举，正确路径是：新增字段（新编号、新名字）→ 生产方双写过渡 → 消费方迁移到新字段 → 旧字段走规则二退役。最贵的是“字段名不变、悄悄换语义”——解析不报错、数值差一个数量级，等对账发现已损失一个账期（第二阶段的契约测试语义断言就是为卡住这类变更而存在）。

Protobuf 还给规则二配了语法保险：删除字段时在 `.proto` 里写 `reserved 3; reserved "old_field";`——编号与名字都进保留名单，此后任何人复用，编译器直接报错。**把纪律变成工具能拦的错误**，是三条规则的共同精神。

### 可运行示例：手写极简二进制编码与字段跳过

Protobuf 的 wire format 之所以能“旧读新、新读旧”，机制其实只有一个：**每段数据自带字段号（tag）**——读者按号取用，不认识的字段按长度整段跳过。下面手写一个教学简化版编码器验证这个思想：每个字段 = 1 字节字段号 + 2 字节大端长度 + 值（tag-length-value）；数值编码为 8 字节大端 long，字符串为 UTF-8。真实 Protobuf 用 varint/zigzag 编码更省字节，但思想与此完全一致。完整代码（已实际编译运行验证，kotlinc 2.2.20）：

```kotlin
// MiniCodecDemo.kt —— tag-length-value 思想：旧读者跳过未知字段
import java.io.ByteArrayOutputStream
import java.nio.ByteBuffer

// ---------- 字段号登记表（一旦对外发布，只增不改不删不复用） ----------
const val F_USER_ID = 1        // v1 起就有
const val F_NAME = 2           // v1 起就有
const val F_LOYALTY_TIER = 3   // v2 新增：会员等级，long
const val F_ADDRESS = 4        // v2 新增：收货地址，string

// ---------- 编码端 ----------
fun writeField(out: ByteArrayOutputStream, tag: Int, value: ByteArray) {
    out.write(tag); out.write(value.size ushr 8); out.write(value.size and 0xFF); out.write(value)
}
fun longBytes(v: Long): ByteArray = ByteBuffer.allocate(8).putLong(v).array()
fun stringBytes(s: String): ByteArray = s.toByteArray(Charsets.UTF_8)

// v1 时代的产品：只发两个字段
fun encodeV1(userId: Long, name: String): ByteArray {
    val out = ByteArrayOutputStream()
    writeField(out, F_USER_ID, longBytes(userId))
    writeField(out, F_NAME, stringBytes(name))
    return out.toByteArray()
}

// v2 时代的产品：多发了两个字段
fun encodeV2(userId: Long, name: String, tier: Long, address: String): ByteArray {
    val out = ByteArrayOutputStream()
    writeField(out, F_USER_ID, longBytes(userId))
    writeField(out, F_NAME, stringBytes(name))
    writeField(out, F_LOYALTY_TIER, longBytes(tier))
    writeField(out, F_ADDRESS, stringBytes(address))
    return out.toByteArray()
}

// 反例用：v3 删掉字段 3 后又立刻用编号 3 装了完全不同类型的值（string）——违反纪律
fun encodeV3Bad_ReusedField(userId: Long, vipLevelName: String): ByteArray {
    val out = ByteArrayOutputStream()
    writeField(out, F_USER_ID, longBytes(userId))
    writeField(out, F_LOYALTY_TIER, stringBytes(vipLevelName)) // 编号 3 被复用，类型从 long 变 string
    return out.toByteArray()
}

// ---------- 解码端 ----------
// v1 时代的读者：只认识字段 1、2，其余一律按 len 跳过
fun decodeV1(bytes: ByteArray) {
    println("[v1 读者] 开始解码 ${bytes.size} 字节：")
    var i = 0
    while (i < bytes.size) {
        val tag = bytes[i].toInt() and 0xFF
        val len = ((bytes[i + 1].toInt() and 0xFF) shl 8) or (bytes[i + 2].toInt() and 0xFF)
        val value = bytes.copyOfRange(i + 3, i + 3 + len)
        when (tag) {
            F_USER_ID -> println("  字段 1 userId = ${ByteBuffer.wrap(value).long}")
            F_NAME -> println("  字段 2 name = ${String(value, Charsets.UTF_8)}")
            else -> println("  字段 $tag（长度 $len 字节）—— v1 读者不认识：整段跳过，不报错、不错位")
        }
        i += 3 + len
    }
}

// v2 时代的读者：认识字段 1~4；读到老报文缺字段时取默认值
fun decodeV2(bytes: ByteArray) {
    println("[v2 读者] 开始解码 ${bytes.size} 字节：")
    var i = 0
    var tier = 0L; var address = ""
    var sawTier = false
    while (i < bytes.size) {
        val tag = bytes[i].toInt() and 0xFF
        val len = ((bytes[i + 1].toInt() and 0xFF) shl 8) or (bytes[i + 2].toInt() and 0xFF)
        val value = bytes.copyOfRange(i + 3, i + 3 + len)
        when (tag) {
            F_USER_ID -> println("  字段 1 userId = ${ByteBuffer.wrap(value).long}")
            F_NAME -> println("  字段 2 name = ${String(value, Charsets.UTF_8)}")
            F_LOYALTY_TIER -> { tier = ByteBuffer.wrap(value).long; sawTier = true; println("  字段 3 tier = $tier") }
            F_ADDRESS -> { address = String(value, Charsets.UTF_8); println("  字段 4 address = $address") }
            else -> println("  字段 $tag（长度 $len 字节）—— 本代读者也不认识：跳过")
        }
        i += 3 + len
    }
    if (!sawTier) println("  报文里没有字段 3 → tier 取默认值 0（显式缺省，不当作真实业务值）")
    if (address.isEmpty()) println("  报文里没有字段 4 → address 取默认空串")
}

fun main() {
    // ---- 第 1 幕：同一份数据，JSON 与二进制的体积对比 ----
    val json = """{"userId":10086,"name":"张三","loyaltyTier":3,"address":"杭州市西湖区文一西路 100 号"}"""
    val v2 = encodeV2(userId = 10086, name = "张三", tier = 3, address = "杭州市西湖区文一西路 100 号")
    println("== 第 1 幕：体积对比 ==")
    println("JSON   : ${json.toByteArray(Charsets.UTF_8).size} 字节")
    println("迷你二进制: ${v2.size} 字节（真实 Protobuf 因 varint 编码还会更小）")

    println()
    // ---- 第 2 幕：旧读者读新报文（v1 读者解 v2 字节）——向后兼容的关键场景 ----
    println("== 第 2 幕：旧读者（v1）解新报文（v2 生产）——跳过未知字段 ==")
    decodeV1(v2)

    println()
    // ---- 第 3 幕：新读者读旧报文（v2 读者解 v1 字节）——缺字段取默认值 ----
    val v1 = encodeV1(userId = 10086, name = "张三")
    println("== 第 3 幕：新读者（v2）解旧报文（v1 生产）——缺字段取默认值 ==")
    decodeV2(v1)

    println()
    // ---- 第 4 幕（反例）：删掉字段 3 后复用编号装新值，旧读者把它当 long 读 ----
    val v3bad = encodeV3Bad_ReusedField(userId = 10086, vipLevelName = "黄金会员")
    println("== 第 4 幕（反例）：字段号 3 被删除后复用、类型从 long 改 string ==")
    println("v3 生产者想说：vipLevelName = 黄金会员")
    decodeV2(v3bad)   // v2 读者仍按 long 解字段 3 → 读出一串毫无意义的数字
    println("→ 结论：编号复用不是'报错'而是'读成完全错误的值'，最贵的静默语义漂移。")
}
```

运行输出（实际运行结果）：

```text
  字段 1 userId = 10086
  字段 2 name = 张三
  字段 3（长度 8 字节）—— v1 读者不认识：整段跳过，不报错、不错位
  字段 4（长度 38 字节）—— v1 读者不认识：整段跳过，不报错、不错位

```

四个要点：

1. 第 2 幕是“加字段安全”的机制根源：v1 读者遇到字段 3/4，靠 `len` 原地跳过整段——**跳过的前提是每个字段自带长度**。反过来看，这也解释了为什么裸字节流的私有协议加字段是灾难：没有长度边界，旧解析器遇到新字段直接错位（对应 2.3 的事实三）。
2. 第 3 幕是规则一的可执行形态：新读者对老报文缺失的字段显式缺省——默认值是契约的一部分，不是随手写的 0。
3. 第 4 幕是两条纪律里最贵一条的实证：编号复用后，v2 读者把“黄金会员”的 UTF-8 字节按 long 读出 `-1604542703690718020`——不是异常，是**一条看起来合法的错误数据**，直到对账才被发现。`reserved` 的意义就是让这类错误在编译期而非对账期暴露。
4. 教学编码与真实 Protobuf 的差距只在压缩效率（varint 对小数值用 1 字节、zigzag 处理负数、wire type 折进 tag），兼容机制（按字段号对齐、未知字段跳过）完全同构。

## 2.3 网络世界的三个物理事实

前两节的选型与防御，归根到底是对网络物理性质的敬畏。以下三个事实不随框架、语言、厂商变化——先记数字，再看对策。

**事实一：延迟不可能为零。** 光在光纤里走 1000 公里单程约 5 毫秒，再加上设备转发、排队、序列化开销，真实数字只多不少。先记量级表（记量级，不记小数）：

| 链路 | 往返时延（RTT）量级 |
|---|---|
| 同进程调用 | 纳秒~微秒 |
| 同机房 | 0.1~1 ms |
| 同城两机房 | 1~3 ms |
| 跨城（如北京↔上海） | 25~40 ms |
| 跨国（如中国↔美国西海岸） | 130~200 ms |

工程后果：一次页面渲染串行调 5 个服务，就算同城机房每个 RTT 只算 2ms 也是 10ms 起步；服务跨城部署时（异地多活的常态，见主笔记 §5.5），5 次跨城串行调用就是 150ms 纯网络时间——“调用是免费的”这条本地编程直觉，在分布式里直接破产。IM 场景对它最敏感：一条消息的端到端时延 = 接入 RTT + 投递 RTT，跨城部署直接决定“对方秒回”的体感。

对策：能并行不串行（超时预算按最长一支算，见 2.1）；能批量不逐条（N 次 RTT 合成 1 次，MES 报工采集与 IoT 数据入库的批量写入都是这条）；热数据就近（缓存与 CDN 是主笔记第 3 节的主战场）；跨城链路上不做强同步长链（异地多活的“单元化”就是为了让用户请求在一个单元内闭环，不出城）。

**事实二：带宽有限，大报文按字节计税。** 算一笔物联网平台的账：100 万台水表，每台每分钟上报 1 条水位读数，入口流量 = 1,000,000 ÷ 60 ≈ 1.7 万条/秒。若用 JSON（120B/条），仅第一跳就是约 2MB/s ≈ 16Mbps 的持续流量；而接入层多副本、落库、跨机房同步通常要再乘 3~5 倍，轻松过百 Mbps。换成 2.2 的紧凑二进制（约 30B/条）直接省 75%——而且文本解析的 CPU 成本比二进制高一个量级，省下的不只是网卡，还有解析线程与 GC 压力。

工程后果：报文体积不是“性能调优”这种锦上添花，而是容量预算的乘数——算容量时把“每条字节数 × 每秒条数 × 副本数”写成等式，数字自己会说话。

对策：高频通道用紧凑二进制（设备侧 CBOR/Protobuf，内部 gRPC）；对外供人阅读的接口保持 JSON（可读性的价值大于省下的带宽）；批处理管道再叠加压缩（gzip、列存——时序库的降采样与列式存储正是把这条算到极致，见第六阶段物联网场景）。

**事实三：网络会丢包、重排，且 TCP 不保证应用层消息边界。** 两层含义常被混为一谈：

- TCP 把“不可靠字节管道”升级成“可靠**字节流**”——不丢、不乱序是**字节**层面的承诺；
- 但字节流没有**消息**边界：发送方两次 write，接收方一次 read 可能收到“一条半”（粘包），也可能只收到半条（拆包）。MTU 分段、Nagle 合并、两端缓冲区都在制造这件事；弱网下的重传与重排，则把时延抖动暴露给应用。

工程后果：私有 TCP 接入若不设计分帧，解析器必然随机错位——收到 1.5 条报文时，第二条的字节全部对不上号；把“TCP 可靠”误读成“我的消息必达且按条到达”，是设备接入类事故最常见的思维源头。

对策三件套：

1. **应用层分帧**：定长帧、分隔符、长度前缀三种选法，通用的是长度前缀（帧头 N 字节声明本帧长度）——2.2 示例里 TLV 的 `len` 字段就是它的最小形态；
2. **应用层确认与去重**：TCP 的 ACK 只证明“对端内核收到了字节”，不代表应用处理成功——IM 的会话序号与去重、IoT 断网补传去重（本节自测第 2 题）、支付回调幂等，都是在 TCP 之上补“业务级必达”；
3. **会话内有序**：同一会话用单调递增序列号，接收方按号重排、检测空洞（IM 消息顺序的标准做法，见第六阶段 IM 场景）。

**三个事实，四个习惯**：把远程调用当贵重操作（预算时延与超时）；把报文当花钱的字节（预算体积）；把每条消息当可能重复与丢失（幂等与确认）；把连接当无边界字节流（显式分帧）。2.1 与 2.2 的全部工程手法，都是这四个习惯的具体化。
