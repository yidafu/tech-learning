## 0. 总纲：两类通用数据库难以承载的负载，两种专用引擎

把搜索与时序放进同一份档案并非生硬拼凑，而是因为它们在架构账本上的位置惊人地相似：

- **同一种病根**：都是通用关系库（MySQL/PostgreSQL）的结构性盲区。搜索的病根是“多条件全文匹配 + 相关性排序”无法走 B+ 树（`LIKE '%x%'` 究竟慢在哪里，见 [07-场景拆解-搜索](07-场景拆解-搜索.md) 1.6.2）；时序的病根是“高频追加 + 按时间/设备查询 + 价值随时间衰减”撞上索引膨胀与更新放大两个死穴（见 [08-场景拆解-物联网数据采集](08-场景拆解-物联网数据采集.md) 1.7.5）。
- **同一种药方**：换一种**存储与索引结构**，换取某种查询形态的量级加速——搜索引擎的答案是倒排索引 + 不可变段；时序库的答案是时间分区 + 列存压缩 + 预聚合降采样。代价都是丢掉另一些能力（事务、随机更新、join 或强一致），这正是选型判据的来源。
- **同一种误用**：两者都常被当成“更好的数据库”全量承接业务——把 ES 当主存储、把时序库当业务库。本档案每个工具的“对比同类”段都会给“何时**不**选它”。

一句话分工，先记牢再看档案：**搜索找几条（倒排召回 + top-k 排序）、时序画曲线（时间范围 + 聚合）、OLAP 算全量（列存扫描 + 分组聚合）、关系管事实（事务 + 点查 + 关联）**。

## 第一部分：搜索引擎

### 1. Elasticsearch：从“给妻子写菜谱搜索”到行业标准

#### 1.1 概况（出身档案）

- **作者与出身**：Shay Banon。2004 年，妻子在伦敦进修厨艺，Banon 给她写了一个菜谱搜索引擎 **Compass**——建在 Lucene 上的第一个开源作品。Compass 历经五年打磨已相当成熟，但它是**嵌入应用的 Java 库**（与应用同进程），单机、无分布式、无独立服务形态。2009~2010 年 Banon 决定推倒重写，目标：独立部署的搜索**服务**、天生分布式、JSON over HTTP、开箱即用。2010 年初 **Elasticsearch** 发布，短短几年便占据搜索市场的大半份额。
- **底座**：[Apache Lucene](https://lucene.apache.org/)——Doug Cutting（也是 Nutch 与 Hadoop 的作者）在上世纪九十年代末写出的全文检索引擎，2000 年开源、2001 年捐赠 Apache 基金会，是事实上的单机检索引擎之王（倒排索引、段结构、打分模型都出自它；命名来自他妻子的中间名）。ES 的几乎所有检索能力都是 Lucene 的，ES 自己做的是**分布式与产品化**这层壳。倒排索引的原理与最小实现见 [07-场景拆解-搜索](07-场景拆解-搜索.md) 1.6.2 的 InvertedIndexDemo，此处不重复。
- **当前归属**：2012 年 Banon 与 Steven Schuurman 等创立公司（今 Elastic NV），2018 年纽交所上市。许可几经变化：Apache 2.0 → 2021 年改 SSPL/Elastic License 双许可（直接引爆 OpenSearch 分家，见第 2 章）→ 2024 年 8 月起增加第三选项 AGPLv3（8.16 版生效），算是“回归开源”的折中。
- **一句话定位**：基于 Lucene 的分布式**近实时**搜索与分析引擎——“搜索引擎”是本职，“日志分析平台”与“半个数据湖”是它后来长出的副业。

#### 1.2 解决了什么问题

Lucene 强到“没有对手”，但它只是一个**库**：没有网络接口、没有集群、索引躺在单机文件系统里。2009 年前后想给海量数据做搜索服务，就得自己搭建一整套东西：如何把大索引拆到多台机器（分片）、文档该路由到哪台（路由）、机器宕机怎么办（副本与故障转移）、如何暴露给业务方（API）、如何让新手五分钟跑起来（产品化）。

当时的候选 Solr 已经回答了一部分（见第 3 章），但它的分布式方案 SolrCloud 要到 2012 年（Solr 4.0）才成熟，此前主从复制笨拙且扩容靠人工。ES 的发布精准命中三个时代需求：**UGC 与电商数据爆炸**（索引单机放不下）、**日志与监控想统一检索**（ELK 的起点）、**REST + JSON 成为事实标准**（业务方不用写 Java 也能接）。

#### 1.3 如何解决：核心机制拆解

**（1）近实时（NRT）：内存 buffer + refresh 生成段。** 一条写入先进入内存索引 buffer，此时**搜不到**；每隔 refresh_interval（默认 1 秒）buffer 被刷成一个新**段**（segment）——不可变的、自带倒排索引的文件，段一出现即可被搜索。这就是“近实时”：秒级可见，不是实时。“最近一秒的数据搜不到”正是索引延迟窗口的来源，业务侧如何兜底见 [07-场景拆解-搜索](07-场景拆解-搜索.md) 1.6.6。

**（2）translog：不可变段的代价与崩溃恢复。** 段不可变换来无锁读与页缓存友好，但“内存 buffer 还没刷成段时机器断电怎么办”？答案是每次写请求同时追加**事务日志 translog**（与数据库 WAL 同一思想，呼应[消息队列档案](../03-第三阶段/07-技术工具档案-消息队列.md)里“日志是基础设施的通用形态”）。重启时重放 translog 补回未刷段的数据。translog 的 fsync 策略决定可靠性档位：默认每请求 fsync（最安全）；可改为 async 每 5 秒一刷（吞吐换至多丢 5 秒）。周期性的 **flush** = 段落盘 + translog 清空归零。

**（3）分片与副本：索引的横向扩展。** 一个 ES 索引在物理上是 P 个**主分片**（每个分片就是一个独立的 Lucene 实例），文档落在哪个分片由路由公式决定：`shard = hash(routing) % P`（默认 routing 取文档 _id）。**P 在建索引时一经固定便不可修改**——因为改了 P，hash 取模结果全变，老文档按新公式便找不到归属分片。扩容只能靠 reindex 重建或 split API。副本分片数 S 可动态调整，主分片宕机后由主节点（master）主持选举接替。这套“分片 + 副本 + 路由”与 [消息队列档案](../03-第三阶段/07-技术工具档案-消息队列.md)里 Kafka 的“分区 + 副本 + leader”是同构的分布式模式，只是路由公式与一致性取舍不同。

**（4）段合并。** 每秒刷一个段很快会把目录填满：文件句柄暴涨、查询要开几十个段各查一遍再归并。后台**段合并**（tiered 策略）持续把小段并成大段，顺带物理清除“打删除标记”的文档（ES 里删除与更新都不是原地改——更新 = 旧文档打标记 + 新文档进新段，这与第二阶段讲的不可变数据、追加式存储一脉相承）。合并是 IO 大户，`force merge` 要慎用——把全部段并成一个，此后每次写入都要重新从小段开始积累。

**（5）分布式聚合分析：越界成“数据库”的资本。** ES 搜索分两阶段：query phase（各分片本地查 top-k，协调节点归并）+ fetch phase（按文档 id 取原文）。聚合同理：每分片本地分桶 → 协调节点 reduce。terms / date_histogram / cardinality 一整套聚合 DSL，让 ES 在“搜出来”之外还能“算出来”——ELK 日志分析、APM、SIEM 都建在这上面。但要记住两个精度陷阱：terms 聚合每分片先取 top-k 再归并，边缘词项计数可能偏小（doc_count_error）；cardinality 是 HyperLogLog++ **近似值**。“聚合结果 ≠ 精确值”是用 ES 做分析的第一课。

#### 1.4 对比同类：用错场景与“它是谁的配角”

完整对比表见第 5 节。这里只说判据。ES 最常被用错的三个场景：

- **当主存储/交易库**：无跨文档事务、近实时非实时、mapping（字段结构）固定后变更要 reindex 全量重建、深分页被 `max_result_window`（默认 1 万）卡住——翻页过深需改用 search_after + PIT 游标。
- **当唯一副本**：分片副本 ×N 已经是存储成本直接乘 N，再把“可从 MySQL 重建的索引”当唯一数据源，等于丢了“可重建”这张最大的安全牌。
- **当精确对账/统计口径**：聚合近似 + 段可见性延迟，注定它给不出“精确到分”的答案。

正确的架构位置：**派生读模型**——主数据在 MySQL/PostgreSQL，通过 binlog → MQ → 索引构建器（Projector）建索引，索引丢失可全量重建。这条管道图与一致性权衡见 [07-场景拆解-搜索](07-场景拆解-搜索.md) 1.6.3，“ES 还是不用”的判决表见同分册 1.6.7。**何时选 ES**：全文检索为主 + 需要分布式横向扩展 + 需要配套聚合分析与生态（Beats/Logstash、Kibana、APM、向量检索 8.x 起内建 HNSW）。商城的商品搜索、工单知识库检索、日志检索（联动[可观测性栈](../05-第五阶段/10-技术工具档案-可观测性栈.md)）都是标准主场。

### 2. OpenSearch：一次许可证变更催生的分家

#### 2.1 概况（出身档案）

2021 年 1 月，Elastic 宣布 ES 与 Kibana 从 Apache 2.0 改为 SSPL / Elastic License 双许可——导火索是 Elastic 认为云厂商（尤其 AWS）以 Apache 2.0 的 ES 做托管服务获利丰厚、而回馈不足。三周后 AWS 发布博客《Stepping up for a truly open source Elasticsearch》，宣布维护一个 Apache 2.0 的分支；2021 年 4 月 **OpenSearch** 首个版本发布，fork 自 ES 7.10.2——最后一个 Apache 2.0 版本。2024 年 9 月项目移交 Linux 基金会旗下的 OpenSearch 软件基金会，摘掉了“一家云厂商说了算”的帽子。而 Elastic 也在 2024 年 8 月宣布给 ES 增加第三许可选项 AGPLv3，姿态上“回归开源”——但生态分裂已经成型，两边各自演进再未合并。

#### 2.2 解决了什么问题

表面是许可证之争，实质是**开源商业模式的利益冲突**，三份许可证就是三种立场：

- **Apache 2.0**：可任意使用、自由商用——最受云厂商青睐，却是原创者的痛点（自己的代码成了别人云服务的原料）。
- **SSPL**（MongoDB 2018 年首创）：如果你把软件“作为服务”提供，必须开源**整个服务栈**（连管理系统也必须开源）——云厂商不可能接受；SSPL 也不是 OSI 认证的开源协议。
- **AGPLv3**：网络使用即触发传染条款——用户通过网络用你改过的 AGPL 软件，你就有义务开源修改——云厂商同样避讳，但至少是 OSI 认证的开源协议。

对用户来说，OpenSearch 解决的是“许可与供应链确定性”：今天免费的版本，明天会不会改协议？fork 之后还能否跟上新特性？

#### 2.3 如何解决

fork 最后一个 Apache 2.0 版本，重命名包与配置（`elasticsearch.yml` → `opensearch.yml`），保留 REST API 兼容（带兼容响应头），之后各自演进：ES 走 8.x/9.x（向量检索、ES|QL 查询语言、时序数据流 TSDS），OpenSearch 走 2.x/3.x（k-NN、ML Commons、Data Prepper、OpenSearch Dashboards）。功能大体趋同，内核同源于 Lucene，插件与客户端生态却已两套。迁移工具与版本对齐成为两地用户的长期税。

#### 2.4 对比同类：“许可证如何改变开源格局”的活案例

这是本档案里最值得记的一课：**一行 license diff，分裂了一个十年生态**——AWS 被迫从云服务厂商变成开源项目维护者，Elastic 丢了部分生态又靠商业许可保住收入，用户被迫做迁移评估。选型判据链：① 你的合规部门接受 SSPL/AGPL 吗？② 你的云在哪家（AWS 的 OpenSearch Service/Serverless 最顺）？③ 你的插件、客户端、既有集群绑定哪边？**何时选 OpenSearch**：需要纯 Apache 2.0（再分发/SaaS 合规）、深度 AWS 生态、或对 Elastic 商业许可变化心有余悸。**何时选 ES**：要用 Elastic 生态的最新特性（ES|QL、TSDS、官方 APM 闭环）且许可可接受。两个引擎能力重合度极高——多数业务场景直接选托管版本都不会错。

### 3. Solr：Lucene 的同门前辈

#### 3.1 概况（出身档案）

Yonik Seeley 2004 年在 CNET Networks 内部为网站搜索开发，2006 年开源，2007 年进入 Apache 孵化器，2008 年毕业成为 Apache 顶级项目，2010 年与 Lucene 项目合并管理（同仓库、同版本号发布——“同引擎同节奏”的极致）。比 ES 年长六岁，2008~2012 年是企业搜索的事实标准（电商、门户、图书馆目录）。

#### 3.2 解决了什么问题

比 ES 更早回答“Lucene 是个库，怎么变成服务”：HTTP 接口（XML/JSON）、可插拔查询解析器、三层缓存（过滤器/查询/文档）、Web 管理界面、主从复制。当年“要让 Java 之外的业务系统用上全文检索”，Solr 几乎是唯一选择。

#### 3.3 如何解决

一个 core 就是一个 Lucene 索引实例，单机多 core；分布式靠 **SolrCloud**（Solr 4.0，2012 年）：ZooKeeper 管集群元数据，collection → shard（leader/replica），文档按 compositeId 哈希路由；update log（ULOG）对应 ES 的 translog；**soft commit**（新文档可见但不 fsync，开销小）与 hard commit（fsync 落盘）分离——近实时的另一套实现。看懂第 1 章再来看 Solr，会发现“同引擎、同概念、不同名词”。

#### 3.4 对比同类：同引擎，不同包装

ES 与 Solr 的差异几乎全在“包装”层：ES 把**分布式 + REST/JSON + schema 自由**做成默认体验（字段类型自动推断、容忍文档结构漂移），代价是“魔法”多、黑盒深；Solr 把**配置可控 + 经典 Java 生态**做成默认体验（solrconfig.xml 精细调优、SolrJ 客户端），代价是上手陡、分布式来得晚。社区热度 ES 完胜（ELK 生态虹吸），但 Solr 至今每半年稳定发版，存量企业搜索（尤其 Java 系）依然庞大。**何时选 Solr**：存量系统与团队经验、Hadoop 时代的技术栈、需要精细的缓存与查询调优、经典分面导航（faceted search）场景。**新项目默认不再选用**——除非已有继续使用的理由。

### 4. ClickHouse 对照：搜索与 OLAP 分析的边界

#### 4.1 概况（出身档案）

2016 年 6 月，俄罗斯搜索引擎公司 Yandex 开源（主创 Alexey Milovidov），动机朴素而极端：网站分析产品 Yandex Metrica 要对每天数十亿次页面浏览做**实时**多维分析，当时没有任何开源系统能低延迟扫完这个量级。答案是一套自研 C++ 列存引擎：**列存 + 向量化执行 + MergeTree 存储族**，Apache 2.0 许可，2021 年成立 ClickHouse Inc. 做云服务。

#### 4.2 边界判据：“找几条”与“算全量”

ClickHouse 不是搜索引擎，但它是搜索工程师最容易混淆的邻居——日志场景两者时常短兵相接。判据是**返回行数/扫描行数之比**：

- **搜索**：从亿级文档里**找出少数相关条目**（返回 10 条，扫描靠倒排剪枝只碰命中链）——关键词找一条报错栈、商品标题模糊匹配 top-10。
- **OLAP 分析**：对海量行**整体算出一个数或一组桶**（扫一亿行，返回 20 行聚合结果）——90 天每服务每小时错误率、全站 UV、按地区汇总销量。

MergeTree 的机制值得记两点：每次 insert 落成一个按主键排序的 **part**，后台持续合并（类 LSM 思路）；主键索引是**稀疏**的——每 8192 行（一个 granule）记一个主键值，不索引具体行——所以它不擅长“按主键精确点查一条”（需解压整个 granule），而擅长全列扫描 + 聚合。列式压缩用 DoubleDelta/Gorilla 等编码，与下文时序库的压缩手段同宗同源。

交叉地带的裁决示例（日志平台）：按 trace id 查取一条慢请求的完整日志 → ES 主场；统计每接口 P99 延迟按天分组 → ClickHouse 主场。不少日志架构直接采用双引擎双写：检索走 ES、统计走 ClickHouse。ES 也能做聚合（近似、且要为倒排结构付存储税），ClickHouse 近年也补了实验性倒排与布隆跳过索引——**边界在收窄，但架构重心不可互换**。

## 第二部分：时序数据库

先立一个共同的靶子：为什么时序数据不值得留在 MySQL？两个结构性死穴——**索引膨胀**（(device_id, ts) 的 B+ 树条目比数据本身长得还快，随机 deviceId 写入打满整棵树）与**更新放大**（为“可更新”付出 redo/undo/binlog 三份账，而时序数据只追加从不更新）。完整论证与时序三板斧（时间分区、列存压缩、预聚合降采样）见 [08-场景拆解-物联网数据采集](08-场景拆解-物联网数据采集.md) 1.7.5，本部分只讲“三板斧由哪个引擎、用什么机制兑现”。

### 6. InfluxDB：监控公司转型而来的时序引擎

#### 6.1 概况（出身档案）

Paul Dix 与 Todd Persen 2013 年创办做应用性能监控的公司 **Errplane**；监控后端需要一个时序存储，市面上 Graphite/RRDtool/OpenTSDB 各有硬伤（见 6.2），于是自研，2013~2014 年拆出独立开源项目 **InfluxDB**（Go 语言），2016 年公司更名 **InfluxData**。它的版本演进在所有数据库产品中最为曲折，以下三段都要记住：

- **存储引擎三连换**：0.8 用 LevelDB → 0.9 换 BoltDB → 高基数下性能崩溃 → 0.10/0.11 引入自研 **TSM**（Time Structured Merge tree）预览 → 1.0（2016 年）TSM 定型，性能数量级改善。
- **查询语言三段曲折**：1.x 的 InfluxQL（类 SQL）→ 2.x（2020 年）全面切换自创函数式语言 **Flux** → 3.x（2023 年 10 月起，Rust 重写、底层换 Apache Arrow/DataFusion/Parquet）宣布 Flux 弃用、**回归 SQL**。两次“革命”都让存量用户把查询重写了两遍。
- **许可几经反复**：1.x / 2.x 开源单机版 MIT（**集群/企业版闭源收费**——0.x 时代的开源集群方案被撤回，“开源单机、闭源集群”从此成为它社区口碑的暗面）；3.x 重写后核心一度只随云/企业版发布（2023~2024 空窗）；2025 年 1 月 **InfluxDB 3 Core** 以 MIT / Apache 2.0 双许可公开 alpha，回归宽松开源（注意：网上流传“3.x 转 AGPL”的说法**不准确**——core 从未 AGPL）。Core 定位是“近 72 小时热数据引擎”，长保留与高可用在企业版和云。

#### 6.2 解决了什么问题

2013 年前后的监控/IoT 时序存储选项：**RRDtool**（环状固定文件，聚合粒度建库时固定、无法更改）、**Graphite/Whisper**（固定间隔文件，无标签维度）、**OpenTSDB**（功能够用但绑死 HBase，运维成本使团队望而却步）。共同缺失的一块是“标签维度”：同一个指标（温度）挂在哪个设备、哪个机房、哪个型号上——这套维度过滤在上述系统里要靠命名约定硬编码。InfluxDB 的卖点：**单二进制开箱即用 + HTTP 线协议 + 标签数据模型 + 内建保留策略与降采样**——把监控场景的整套组件装进一个进程。

#### 6.3 如何解决

- **数据模型与线协议**：measurement（指标）+ tags（标签，建索引、必须低基数）+ fields（值，不索引）+ timestamp。**线协议**（line protocol）一行文本写多个点，紧凑易生成，Telegraf 采集器生态完全依赖它。
- **TSM 引擎**：类 LSM——写 WAL → 内存 → 压成按时间有序的只读文件，后台压缩合并；与通用 LSM 的差别是按“时间结构”组织：同一 series（同设备同指标）的值物理聚集，时间戳 delta 编码、浮点 Gorilla XOR 编码（借自 Facebook 2015 年 Gorilla 论文，下文 Prometheus 同样受益于此），压缩比可达数倍到数十倍。
- **生命周期内建**：**保留策略 RP**（retention policy，到期自动删）+ **连续查询 CQ**（continuous queries，定时把高粒度 SELECT 聚合 INTO 低粒度表——本质是“定时 CTAS”物化）；2.x 改叫 bucket + task（Flux 脚本），3.x 又改回 SQL 物化视图。机制名词三换，方法论一字未变——就是 [08-场景拆解-物联网数据采集](08-场景拆解-物联网数据采集.md) 1.7.5 的“预聚合降采样 + 冷热分层”。**策略随数据走、引擎内建定时**，无需外部 cron，这是专用引擎相对“MySQL + 脚本”的真正红利。

#### 6.4 对比同类

**何时选 InfluxDB**：监控/IoT 中小规模自建（单机即够、开箱即用）、已在 Telegraf/线协议生态深度投入、或直接使用其云托管。**何时避开**：需要集群与高可用但不愿购买企业版（这正是 TimescaleDB/TDengine 抢走其市场的切口）；已大量使用 Flux（已被官方弃用的语言）；需要 join 业务数据（弱项）。3.x 的 Core/Enterprise 双轨定位要读清楚——所需的“免费版”如今只覆盖近 72 小时热数据。

### 7. TimescaleDB：不另起炉灶的 PostgreSQL 扩展

#### 7.1 概况（出身档案）

2015 年，Princeton 出身的系统研究者 Mike Freedman 等在纽约创立 Timescale 公司；2017 年发布 **TimescaleDB 1.0**——形态上不是独立数据库，而是 **PostgreSQL 扩展**（extension）：装进 PG，建表时指定为 hypertable，即得时序能力。2025 年 6 月公司更名 **TigerData**（云产品 Tiger Cloud；扩展本身仍叫 TimescaleDB）。许可双轨：**Apache 2.0**（timescaledb-oss，基础功能）+ **TSL/Timescale License**（社区版默认包含压缩、连续聚合等“企业”功能；source-available——可自由使用、可自部署，唯一限制是**不得把 TimescaleDB 本身包装成竞品云服务卖**）。对比 Elastic 的 SSPL 激进版，这是“防云厂商”的温和版：OSI 不认它是开源，但用户几乎感受不到限制。

#### 7.2 解决了什么问题

大量团队的真实处境是：“我们已经会 PostgreSQL、已有 PG 运维体系（备份、逻辑复制、监控、RDS 托管），时序数据来了，我**不想再养一种数据库**。”原生 PG 硬扛时序的问题：分区表要手工建（或 pg_partman）、单表索引膨胀、VACUUM 压力大。TimescaleDB 的回答：**不另起炉灶**——时序能力以扩展形式长在 PG 上，SQL、join、事务、窗口函数、整个 PG 生态（PostGIS、pg_dump、Supabase/RDS……）原封不动。

#### 7.3 如何解决

- **hypertable 自动分块**：用户看到的就是一张普通 PG 表（INSERT 照写、SQL 照查），底层按 `chunk_interval`（可自适应）自动切成 chunk（子表），可选再按空间维（设备 id 哈希）二维分片；后台任务自动创建/删除 chunk。查询带时间条件时只碰相关 chunk（分区裁剪）。
- **列式压缩**：老 chunk（默认 7 天以上）自动转为列式排列（按 segmentby 分组、orderby 排序）+ delta-delta/浮点编码压缩，官方口径常见 90%+ 压缩——新数据行存可更新、老数据列存极致压缩，一个表内完成冷热换装。
- **连续聚合（continuous aggregates）**：增量物化视图——只刷新新到的时间桶，旧桶不动；查询时自动路由：物化部分读聚合表、最新未物化部分实时补算。这就是降采样的 SQL 形态。
- **保留策略（retention policy）**：整块 drop 过期 chunk——**删 chunk 是删文件，不是逐行 DELETE**，对比“MySQL 删 30 天前数据锁三小时”是两种文明。

#### 7.4 对比同类

**何时选 TimescaleDB**：团队 PG 技能深、时序要与业务表 join（设备元数据 × 遥测联查、水表读数直接并入账务报表——桶装水商城的水表周期购正是这种“时序 + 业务”混合查询的典型）、已有 PG 运维与托管。**何时避开**：极端写入吞吐（单机数十万~百万行/秒级需求）或超大规模分布式分片——专核引擎（TDengine/ClickHouse）的上限更高；以及不想被 TSL 条款审查的竞品云场景。

### 8. TDengine：为物联网而生的国产引擎

#### 8.1 概况（出身档案）

连续创业者陶建辉 2017 年组建涛思数据（北京）研发 **TDengine**，定位“物联网大数据平台”；2019 年 7 月在 ArchSummit 全球架构师峰会宣布开源，两周 GitHub star 破 6800，一度占据榜首——国产基础软件开源的标志性事件。2022 年 3.0 重构分布式架构（元数据与数据面分离、按 vgroup 分片多副本）。许可同样“一企一策”：核心服务 taosd **AGPL-3.0**，连接器与 taosAdapter **MIT**——官方明确表示选择 AGPL 是为防止云厂商直接以其提供托管服务（又一个“许可证即商业策略”的典型案例，可与第 2 章对照记忆：Elastic 选了更激进的 SSPL，Timescale 选了更温和的 TSL，TDengine 选了 OSI 认证的 AGPL）。

#### 8.2 解决了什么问题

IoT 采集的画像：**百万级采集点**、每点秒级/毫秒级上报、查询 90% 是两种形态——“某设备某时段的曲线”与“按标签圈定一组设备做聚合”（“3 号车间所有压机昨天的平均温度”）。除了 6.2 的通用死穴，还有第三个：**标签维度查询**在行存里是全表扫描。通用库与时序库（InfluxDB/TimescaleDB）用“标签倒排/索引”解决，TDengine 给出了更彻底的答案——让数据物理布局就按采集点组织。

#### 8.3 如何解决

- **“一个数据采集点一张表”**：同一设备的所有数据追加进它自己的子表——写入天然变成顺序追加（时间有序），画单设备曲线只碰一张小表。百万元素的“大表随机写”变成“百万张小表的各自追加”，索引膨胀从根源上消失。
- **超级表（super table）**：同型号设备共用一张超级表——定义公共列结构（时间戳、温度、压力）+ **标签**（tags：厂区、车间、型号、安装日期）；子表是超级表在具体标签组合下的实例。按标签圈选查询时，先用超级表元数据（标签有索引）定位目标子表，再只扫这些子表——**写入按设备局部化、查询按标签路由**，一鱼两吃。
- **存储与压缩**：按时间 + 数据量双维度分片（vgroup，多副本），列存压缩（时间戳 delta-delta、浮点降精度/XOR）；官方口径：相对通用数据库“写入快 10 倍 +、存储省 90%、计算资源 1/5”——具体数字取决于基准场景，但量级方向无误。
- **All-in-One 卖点**：内建每设备**最新值缓存**（查“当前温度”不碰磁盘）、内建**消息订阅**（消费组拉增量，类 Kafka 用法）、内建**流计算**（触发器式的窗口聚合）——“装一个 TDengine 顶缓存 + 消息队列 + 计算 + 存储四件套”。红利确实存在（IoT 小团队可省三套运维）；耦合也确实存在（每项能力都比专用系统浅一档）——是否算“红利”，取决于团队规模。

#### 8.4 对比同类

**何时选 TDengine**：国内 IoT/MES 场景、设备与采集点数量大（十万~亿级）、高频写入、要“最新值直读”与标签圈选、边缘到云同构部署；对国产化与本地支持有要求。**注意**：AGPL 的传染针对“通过网络提供修改版服务”——自用且不修改核心无碍；修改核心又对外提供服务，则须开源修改；介意者可选择商业授权。**何时避开**：复杂 SQL/join 需求（SQL 子集）、非 IoT 形态的数据（无标签维度红利）、海外交付对国产栈的顾虑。

### 9. 顺带说明：Prometheus TSDB、OpenTSDB/HBase 系与云托管

- **Prometheus TSDB**：源于 SoundCloud（2015 年公开、2016 年 1.0，灵感来自 Google 内部 Borgmon），CNCF 第二个毕业项目，Kubernetes 时代的指标标配。2.0（2017 年 11 月）自研存储：内存 head + WAL + 2 小时块，样本编码同样用 Gorilla XOR。设计哲学是刻意的**单机不集群**（拉模型 + 服务发现，长期存储与水平扩展交给 Thanos/Mimir/VictoriaMetrics 等外围组件）——它只服务“指标”这一种时序（规整采样 + 聚合查询 + 告警），不要用它存储事件明细。指标栈全景见[可观测性栈档案](../05-第五阶段/10-技术工具档案-可观测性栈.md)。
- **OpenTSDB 与 Graphite（历史坐标）**：OpenTSDB（约 2010 年，StumbleUpon）建在 HBase 上，用大表的行键设计模拟时序——“用大数据表存时序”的上一代思路，运维 HBase 的成本使大多数后来者望而却步；Graphite/Whisper 用固定大小的环状文件（RRD 思想），聚合粒度建库即定。它们的历史功劳是定义了 **metric + tags + timestamp** 数据模型——InfluxDB、Prometheus 都是继承者。
- **云托管**：AWS Timestream 家族的分合很有代表性——自研的 Timestream for LiveAnalytics 2024 年底起停止接收新客户，AWS 转而主推 **Timestream for InfluxDB**（托管开源引擎）；国内有阿里云时序数据库 TSDB/InfluxDB 版、腾讯云 CTSDB 等。判据：托管省心 vs 数据出口与长期成本锁定；MES/工控场景常因“数据不出厂”的合规要求选择开源自建（TDengine/TimescaleDB）。

## 11. 动手实验：MiniTsdbRollup——亲手验证降采样与保留策略

07 分册的 InvertedIndexDemo 演示了倒排索引的骨架，08 分册的 EventTimeWindow 演示了事件时间窗口与迟到处理（[08-场景拆解-物联网数据采集](08-场景拆解-物联网数据采集.md) 1.7.4）。本实验补上时序三板斧的第三块拼图——**存储侧的生命周期账本**：原始 1s 粒度明细如何逐级聚合为 1min / 1h、热温冷三档保留期如何裁剪、磁盘究竟省了多少。模拟情境是 MES 车间 3 台压机的温度遥测（写入侧的凑批与背压见同分册 1.7.3，本实验只关注落库之后的部分）。三步：

1. **模拟写入**：3 台设备 × 30 天 × 1s，含“换班时段丢样 40%、平时丢样 0.2%”——设备不可靠是常态，缺样会造成 count<60 的不完整分钟桶；
2. **降采样管道**：1s → 1min 桶（min/max/sum/count）→ 1h 桶。关键细节：第二级聚合**从 1min 桶级联**而不是回读 1s 明细（真实时序库的 continuous aggregate 正是如此实现），avg 必须**按 count 加权**——对分钟 avg 求简单平均是常见错误；
3. **三档保留裁剪**：热（1s 明细，7 天）/ 温（1min 聚合，90 天）/ 冷（1h 聚合，370 天），输出各档行数与磁盘估算。

```kotlin
// MiniTsdbRollup.kt —— 最小"降采样与保留策略"模拟（单文件、无第三方依赖）
// 情境：MES 车间 3 台压机温度遥测，1s 粒度、连续 30 天。
// 演示：1s 明细 → 1min 桶（min/max/sum/count）→ 1h 桶（由 1min 级联加权）
//      → 热/温/冷三档保留裁剪 + 各档数据量与磁盘占用估算。
// 运行：kotlinc MiniTsdbRollup.kt -include-runtime -d app.jar && java -jar app.jar

import java.time.Instant
import java.time.ZoneOffset
import java.time.format.DateTimeFormatter
import kotlin.math.abs
import kotlin.math.sin
import kotlin.random.Random

/** 原始数据点：秒级时间戳 + 测量值 */
data class Point(val ts: Long, val value: Double)

/** 一行降采样结果：桶起点 + min/max/sum/count（真实时序库的 rollup 表就长这样） */
data class Rollup(
    val bucketStart: Long,
    val min: Double,
    val max: Double,
    val sum: Double,
    val count: Long,
) {
    val avg: Double get() = sum / count
}

/** 保留层：名称、粒度、保留期（秒）、每行字节数（磁盘估算用） */
data class Tier(val name: String, val granularity: String, val retentionSec: Long, val bytesPerRow: Int)

/** 把按 ts 升序排列的点流，按 windowSec 对齐的时间桶做聚合 */
fun rollup(points: List<Point>, windowSec: Long): List<Rollup> {
    if (points.isEmpty()) return emptyList()
    val out = ArrayList<Rollup>()
    var i = 0
    while (i < points.size) {
        val bucketStart = points[i].ts - points[i].ts % windowSec
        var mn = points[i].value
        var mx = mn
        var sum = 0.0
        var cnt = 0L
        while (i < points.size && points[i].ts - points[i].ts % windowSec == bucketStart) {
            val v = points[i].value
            if (v < mn) mn = v
            if (v > mx) mx = v
            sum += v
            cnt++
            i++
        }
        out += Rollup(bucketStart, mn, mx, sum, cnt)
    }
    return out
}

/** 第二级聚合：由 1min 桶级联出 1h 桶。min 取最小、max 取最大、sum 与 count 直接累加——
 *  avg 因此天然是"按 count 加权"的正确平均；对 1min 的 avg 求简单平均是常见错误 */
fun cascadeToHour(minuteRollups: List<Rollup>, windowSec: Long = 3600): List<Rollup> {
    if (minuteRollups.isEmpty()) return emptyList()
    val out = ArrayList<Rollup>()
    var i = 0
    while (i < minuteRollups.size) {
        val hourStart = minuteRollups[i].bucketStart - minuteRollups[i].bucketStart % windowSec
        var mn = minuteRollups[i].min
        var mx = mn
        var sum = 0.0
        var cnt = 0L
        while (i < minuteRollups.size &&
            minuteRollups[i].bucketStart - minuteRollups[i].bucketStart % windowSec == hourStart
        ) {
            val r = minuteRollups[i]
            if (r.min < mn) mn = r.min
            if (r.max > mx) mx = r.max
            sum += r.sum
            cnt += r.count
            i++
        }
        out += Rollup(hourStart, mn, mx, sum, cnt)
    }
    return out
}

fun humanBytes(bytes: Long): String {
    val kib = 1024.0
    return when {
        bytes >= kib * kib -> String.format("%.1f MiB", bytes / kib / kib)
        bytes >= kib -> String.format("%.1f KiB", bytes / kib)
        else -> "$bytes B"
    }
}

fun main() {
    val fmt = DateTimeFormatter.ofPattern("yyyy-MM-dd HH:mm:ss").withZone(ZoneOffset.UTC)
    val daySec = 86_400L

    // ── 1. 模拟写入：3 台压机 × 30 天 × 1s；换班时段（UTC 01:00–01:20）丢样 40%，平时 0.2% ──
    val devices = listOf("mes-press-01", "mes-press-02", "mes-press-03")
    val endTs = Instant.parse("2026-11-04T00:00:00Z").epochSecond   // "现在"
    val startTs = endTs - 30 * daySec
    val rnd = Random(42)
    val raw = devices.associateWithTo(HashMap<String, MutableList<Point>>()) { ArrayList(2_592_000) }
    var theoretical = 0L
    var dropped = 0L
    for (ts in startTs until endTs) {
        val secondOfDay = ts % daySec
        val lossProb = if (secondOfDay in 3600..4800) 0.40 else 0.002
        for ((di, d) in devices.withIndex()) {
            theoretical++
            if (rnd.nextDouble() < lossProb) { dropped++; continue }
            // 温度 = 设备基线 + 日周期正弦 + 白噪声
            val v = 70.0 + di * 0.5 +
                8.0 * sin(2 * Math.PI * (secondOfDay - 6 * 3600) / daySec) +
                (rnd.nextDouble() - 0.5) * 0.8
            raw.getValue(d).add(Point(ts, v))
        }
    }
    val received = theoretical - dropped
    println("== 1. 模拟写入：${devices.size} 台压机 × 30 天 × 1s（换班时段丢样 40%，平时 0.2%）==")
    println(
        "理论点数 %,d，实际收到 %,d，缺失 %,d——设备不可靠是常态，缺样会造出 count<60 的"不完整分钟桶""
            .format(theoretical, received, dropped)
    )

    // ── 2. 降采样管道：1s → 1min → 1h（级联加权） ──
    val minuteByDev = devices.associateWith { rollup(raw.getValue(it), 60) }
    val hourByDev = devices.associateWith { cascadeToHour(minuteByDev.getValue(it)) }
    val totalMin = minuteByDev.values.sumOf { it.size }
    val partialMin = minuteByDev.values.sumOf { list -> list.count { it.count < 60L } }
    val totalHour = hourByDev.values.sumOf { it.size }
    println()
    println("== 2. 降采样管道：1s → 1min（min/max/sum/count）→ 1h（由 1min 级联加权）==")
    println("1min 桶 %,d 个（缺样桶 %,d 个），1h 桶 %,d 个；点密度 1/s → 1/60s → 1/3600s".format(totalMin, partialMin, totalHour))

    // 抽检：找"分钟 avg 的简单平均"与"加权平均"差距最大的一个小时，验证级联无损、展示陷阱
    val dev = devices[0]
    var pickHour: Rollup? = null
    var pickNaive = 0.0
    var pickBuckets = 0
    var maxGap = -1.0
    for (h in hourByDev.getValue(dev)) {
        val mins = minuteByDev.getValue(dev)
            .filter { it.bucketStart >= h.bucketStart && it.bucketStart < h.bucketStart + 3600 }
        if (mins.size < 2) continue
        val naive = mins.sumOf { it.avg } / mins.size
        val gap = abs(naive - h.avg)
        if (gap > maxGap) { maxGap = gap; pickHour = h; pickNaive = naive; pickBuckets = mins.size }
    }
    val h = pickHour!!
    val direct = rollup(
        raw.getValue(dev).filter { it.ts >= h.bucketStart && it.ts < h.bucketStart + 3600 }, 3600
    ).first()
    println("级联抽检（$dev，${fmt.format(Instant.ofEpochSecond(h.bucketStart))} UTC 起的那一小时，含 $pickBuckets 个分钟桶）：")
    println("  ① 直接从 1s 明细重算：min=%.3f max=%.3f avg=%.6f（%,d 点）".format(direct.min, direct.max, direct.avg, direct.count))
    println("  ② 1min→1h 级联加权：min=%.3f max=%.3f avg=%.6f（%,d 点）".format(h.min, h.max, h.avg, h.count))
    println("  ③ 错误做法·分钟 avg 的简单平均：avg=%.6f（偏差 %.6f，桶间缺样越不均匀偏得越多）".format(pickNaive, abs(pickNaive - h.avg)))
    println("  ①与② avg 差异 = %.2e（浮点求和顺序不同，实质无损）".format(abs(direct.avg - h.avg)))

    // ── 3. 三档保留裁剪：热(1s,7天) / 温(1min,90天) / 冷(1h,370天) ──
    val tiers = listOf(
        Tier("热", "1s", 7 * daySec, 16),    // 点：8B 时间戳 + 8B 浮点
        Tier("温", "1min", 90 * daySec, 40), // 行：8B 桶起点 + 24B 三个聚合值 + 8B count
        Tier("冷", "1h", 370 * daySec, 40),
    )
    println()
    println("== 3. 保留策略裁剪（now = ${fmt.format(Instant.ofEpochSecond(endTs))} UTC，总历史 30 天）==")
    var totalBytes = 0L
    for (t in tiers) {
        val cutoff = endTs - t.retentionSec
        val kept = when (t.granularity) {
            "1s" -> raw.values.sumOf { list -> list.count { it.ts >= cutoff } }
            "1min" -> minuteByDev.values.sumOf { list -> list.count { it.bucketStart >= cutoff } }
            else -> hourByDev.values.sumOf { list -> list.count { it.bucketStart >= cutoff } }
        }
        val bytes = kept.toLong() * t.bytesPerRow
        totalBytes += bytes
        println("  ${t.name}层 | ${t.granularity} 粒度 | 保留 ${t.retentionSec / daySec} 天 | 裁剪后 %,9d 行 | ${humanBytes(bytes)}".format(kept))
    }
    val baseline = received * 16L
    println("-".repeat(72))
    println("三档合计 %s；对照：30 天 1s 明细全量保留 = %s（%,d 点 × 16B）".format(humanBytes(totalBytes), humanBytes(baseline), received))
    println("分层 + 降采样省下 %.1f%% 磁盘——时序数据的价值随时间衰减，精度与保留期同步衰减。".format(100.0 * (baseline - totalBytes) / baseline))
}
```


**解读三件事**：

- **级联是无损的（①=②）**：1h 聚合由 1min 桶级联得出而不回读明细，min 取最小、max 取最大、sum/count 累加——与从 1s 明细直接重算完全一致（差异 2.34e-13 只是浮点求和顺序）。这正是 InfluxDB CQ / Timescale 连续聚合 / TDengine 流计算的共同骨架：**降采样是聚合的聚合**，每级只读上一级，明细过期删除也不影响粗粒度继续生成。
- **“平均的平均”是典型陷阱（③）**：换班时段 40% 丢样与平时 0.2% 丢样的分钟桶混在同一小时里，桶的 count 从 36 到 60 不等；对分钟 avg 求简单平均等于给稀疏桶和完整桶同等权重，偏差 0.043——本例温度日幅度 8 度，偏差约 0.5%，看似不大，但缺样与数值趋势相关时（故障时段掉线更多）误差是系统性的。加权（乘 count）是唯一正确做法。
- **节省磁盘的是保留策略，而不只是聚合**：32.5 MiB 对 117.8 MiB 的 72.4% 节省，主要来自“直接删除 7 天前的 1s 明细”——因为温层已有分钟级聚合兜底。反过来说，**先想清楚每一层“删了它我还能回答什么问题”，再定保留期**：热层管“回查故障现场”，温层管“趋势与周报”，冷层管“年度对账与合规”。这正是 [08-场景拆解-物联网数据采集](08-场景拆解-物联网数据采集.md) 1.7.5 冷热分层表的算术版。（磁盘按未压缩行存 16B/点、40B/聚合行估算——真实列存引擎压缩后数字小 5~10 倍，但三档之间的比例关系不变。）

## 12. 结尾选型：这份数据该去哪

### 12.1 “数据该去哪”判据表

| 数据形态 | 判据特征 | 该去哪 | 反例信号 |
| --- | --- | --- | --- |
| 关系数据（订单/工单/账务/押金） | 事务、强一致、按主键点查、外键关联 | MySQL / PostgreSQL | “为了一个模糊搜索框把整个业务搬进 ES” |
| 全文搜索（商品/帖子/工单知识库） | 分词 + 多条件 + 相关性排序，返回 top-k | Elasticsearch / OpenSearch（存量可 Solr） | `LIKE '%x%'` 上线后 CPU 打满、慢查询堆积 |
| 日志分析 | 海量追加 + 关键词检索 + 时序统计 | 检索走 ES、统计走 ClickHouse（联动[可观测性栈](../05-第五阶段/10-技术工具档案-可观测性栈.md)） | 把日志塞进 MySQL，或用搜索引擎承担全量统计报表 |
| 设备时序（MES 遥测/水表/售水机） | 高频追加、按时间 + 设备/标签查、价值随时间衰减 | TDengine / InfluxDB / TimescaleDB + 降采样分层（[08 分册](08-场景拆解-物联网数据采集.md)三板斧） | 时序进 MySQL：两个月后表 800GB、曲线查询 40s |
| 指标（CPU/QPS/P99） | 规整采样 + 聚合查询 + 告警 | Prometheus 系（长存储配 Thanos/VM/M3） | 用通用时序库自行拼装告警与采集轮询 |

三问定去留（比记表更重要的判据）：① **查询形态**——找几条、算全量、画曲线，还是点查关联？② **写入形态**——事务性变更，还是追加洪峰？③ **生命周期**——永久保值（关系），还是随时间衰减（时序）？三个答案对了，表自然就对了。

### 12.2 反例与修正

**反例一：商城把订单全量同步进 ES，当“订单查询主库”。** 客服系统直接在 ES 里改收货地址、退款标记——结果：无跨文档事务导致并发改写互相覆盖；mapping 固定后新字段要 reindex 全量重建，重建期间读写两套口径；一次集群故障暴露“ES 是唯一完整副本”的险境。**修正**：订单事实在 MySQL，ES 只做搜索读模型（CQRS 的查询侧投影）；一切写操作回源 MySQL，经 binlog → MQ → Projector 异步更新索引——管道与一致性方案见 [07-场景拆解-搜索](07-场景拆解-搜索.md) 1.6.3。判据一句话：**“这份数据丢了能不能从别处重建”——不能重建的，就不该只存在派生存储里。**

**反例二：MES 设备 1s 遥测全量进 MySQL。** (device_id, ts) 复合索引两个月膨胀到超过数据本身，随机写入打满 B+ 树；为“从不发生的更新”付 redo/undo/binlog 三份账；查询“昨天全车间温度曲线”要扫两千万行，40 秒起步（两个死穴的完整推导见 [08-场景拆解-物联网数据采集](08-场景拆解-物联网数据采集.md) 1.7.5）。**修正**：时序库承接写入 + 1min/1h 两级降采样 + 7 天/90 天/1 年三档保留——存储侧的账目正是上面 MiniTsdbRollup 算出的那一笔：自 72.4% 起步的节省，且查询自动路由到合适粒度。

**反例三：“一套 InfluxDB 走天下”。** 团队尝到时序库的甜头后，把工单、用户画像、水桶押金流水也塞进 measurement——随后发现：无 join（押金流水无法关联用户表）、无事务（退押金的对账口径永远差一分钱）、高基数标签把内存压垮（将 user_id 当作 tag 使用，series 数爆炸）。**修正**：时序库只存时序；业务数据留在关系库；确需联查就选 TimescaleDB（它本来就是 PG）或在应用层聚合。**专用引擎的红利来自“假设数据形态单一”——塞进去的每一种异形数据，都在偷偷偿还这份红利。**
