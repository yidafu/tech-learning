## 0. 本册要回答的问题

三个业务现场，全部来自站内示例项目场景，读完本册应能给出机械级答案：

- **现场一（工单中心抢单）**：两个客服同时点“接单”，最后工单的 assignee 是谁？什么隔离级别下会两个人都看到“接单成功”？正确写法为什么要 `SELECT ... FOR UPDATE` 或乐观锁版本号？
- **现场二（桶装水商城扣库存）**：库存余 1，两个并发下单各扣 1，结果卖超了。这是丢失更新还是写偏斜？为什么把隔离级别提到“可重复读”**仍然可能**防不住（取决于数据库），而一条原子 `UPDATE` 反而防得住？
- **现场三（支付日终对账）**：对账事务里同一笔流水第一次查是“成功”、几秒后再查变成“退款中”。这是不可重复读；对账程序该怎么写才不被并发更新晃倒？

数据库间行为差异最大的领域就是本册（“可重复读”在不同数据库里含义不同），因此本册的纪律是：**机制以通用原理推导，落到具体系统的事实逐条标注出处性质（官方文档/经典论文），拿不准的不写**。

## 1. ACID 的实义：四个字母各自的承诺与代价

ACID 里的四个字母经常被当成一句口号背诵。逐个拆开，每个字母都对应一份具体的机械。

### 1.1 A 是“可中止性”：中途失败不能留半个结果

**原子性的实义**：事务要么全部效果可见，要么全部效果不存在——哪怕中途进程崩溃。Kleppmann 的观点（DDIA 第 7 章）值得记住：这个词的实质是 **abortability（可中止性）**：重点不是“一起成功”，而是“失败后能干净地一起消失”。

机械：**undo 日志**。修改前把旧值（或逆操作）记进 undo log，回滚时逆序重放。第 2 册讲过 redo（重放让提交的效果活下来）；undo 是它的镜像（重放逆操作让未提交的效果死掉）。InnoDB 的回滚就是沿 undo 链逆行——这也是 4.4 节 MVCC 版本链的同一份结构：**undo 日志身兼两职，回滚用一次，旧版本读用一次**。

业务层的对应物是第三阶段 Saga 的补偿：补偿就是“应用层 undo”，而它做不到干净——所以 Saga 才“没有隔离性”（见 6.5 节的分工表）。

### 1.2 C 是被用滥的字母：数据库管不了你的业务不变量

**一致性（consistency）**在 ACID 里指“事务把数据库从一个合法状态带到另一个合法状态”——但“合法”由**应用定义的不变量**说了算：账户借贷相平、库存不超卖、外键引用存在。数据库只提供**工具**（主键/唯一约束、外键、CHECK、级联），把“不变量声明出来”仍是应用的责任。C 是 A、I、D 加上应用正确使用的**共同结果**，不是数据库单独承诺的东西——DDIA 与教科书（Gray & Reuter）在此观点一致。

工程含义：把不变量尽量下沉为数据库约束。唯一键是最便宜的并发防线（6.3 节写偏斜解法之一）；靠“应用层先查再写”守护的不变量，在并发下就是给写偏斜开门。

### 1.3 I 是光谱：隔离级别是“允许哪些并发异常”的档位

隔离性（isolation）：并发事务的执行效果**等价于某个串行顺序**（可串行化，serializability）是最强档；代价是并发控制的开销，所以数据库商品化出一串**弱化档位**——每一档都是“为了性能，允许某些异常发生”的明码标价。档位与异常的对照表是第 2 节的主角。

**可串行化（serializability）的定义要精确**：存在某个串行执行顺序，使并发执行的结果与其一致——注意是“**某个**顺序”而不是“时间上真实发生的顺序”，后者更强（叫严格串行性/strict serializability，单机数据库的 2PL/SSI 提交协议通常附带这个更强性质；跨节点的线性一致读才是第三阶段 CAP 话题）。本册在单机范围内用“可串行化”默认指前者。

### 1.4 D 是分层承诺：提交不丢，丢到哪一层算数

**持久性（durability）**：一旦提交，效果不因崩溃消失。机械是第 2 册第 4 节的 WAL + fsync。但“不丢”有层级：**单盘 fsync**（盘没坏就不丢）→ **RAID/电池缓存** → **同步复制多数派**（机房级故障不丢）→ **跨机房/异地**。第三阶段 05 分册的 2PC 就是在“多节点 D”上做文章；工程上说一个事务“提交了”，要能回答“这个提交在 D 的哪一层”。

### 1.5 单对象与多对象：事务的承诺边界

- ACID 的 A/I 传统上指**多对象**（多行多表一次事务里的原子与隔离）。单对象的原子性几乎所有存储都免费提供（一条日志记录的事务性），**用单对象原子操作模拟多对象事务**（“扣库存用 Redis 原子减、订单写 MySQL”两个独立原子操作）不等于事务——中间态会漏出去，这正是第三阶段分布式事务的问题起源。
- **事务边界即锁与快照的生存期**：事务开到提交之间，数据库替你持有锁/维持快照/阻止 vacuum 清理——所以“事务里做 RPC 调用”是经典反模式（锁横跨网络往返，超时与吞吐一起崩）。长事务的完整事故链见 6.4。

## 2. 并发异常动物园：从脏写到写偏斜

### 2.1 为什么不默认可串行化

可串行化的并发控制（2PL 或 SSI）在竞争高时有真实代价（阻塞/死锁/重试），1980~1990 年代的商业数据库因此把档位做成旋钮，**默认放在“够用且便宜”的一档**——历史选择延续至今，成了“数据库默认隔离级别不一致”的根源。理解弱档位的正确姿势不是背名字，而是**记住每一档允许哪些异常**，再问业务能不能忍。

下面逐个展示异常。约定记号：T1/T2 两个并发事务，表格按时间从上到下。

### 2.2 脏写与脏读

**脏写（dirty write）**：T2 覆盖了 T1 未提交的写。若 T1 随后回滚，T2 的效果悬空（建立在从未发生过的状态上）。

| 时刻 | T1 | T2 |
|---|---|---|
| t1 | update 工单 set assignee=客服A where id=1 | |
| t2 | | update 工单 set assignee=客服B where id=1 |
| t3 | rollback（T2 的写入悬空） | |

所有档位（含读未提交）都禁止脏写——这是底线，实现上靠“写加 X 锁到提交”（哪怕最弱的档位也保留写锁）。

**脏读（dirty read）**：读到别人未提交的数据。读未提交允许它（或干脆不允许该级别存在——PG 根本不实现脏读，官方文档明确说明），读提交起全部禁止。脏读的业务杀伤：读到“即将消失”的中间值并据此决策——支付系统读到一笔未提交的扣款流水就给用户发货，随后对方回滚。

### 2.3 不可重复读（non-repeatable read）

同一事务内两次读**同一行**结果不同（别人提交了修改）。

| 时刻 | T1（对账程序） | T2 |
|---|---|---|
| t1 | select 状态 from 流水 where id=99 → “成功” | |
| t2 | | update 流水 set 状态=‘退款中’ where id=99；commit |
| t3 | select 状态 from 流水 where id=99 → “退款中”（!） | |

读提交允许它（每条语句一个新快照）；可重复读档位起禁止。对账程序的防御：要么把隔离级别提到 RR/SI（整事务一个快照），要么对账读加锁（`FOR SHARE`），要么业务上接受“读到较新值再重查”——第三种其实是把对账改成幂等重试，见 6.2。

### 2.4 幻读（phantom read）：谓词条件的坑

同一事务内两次**按条件查询**，第二次多出/少了行（别人提交了插入或删除）。与不可重复读的区别：改的是**行的集合**，不是某行的内容。

| 时刻 | T1（查“当天全部待分账”） | T2 |
|---|---|---|
| t1 | select count(*) from 分账单 where day=今天 and status=待处理 → 100 | |
| t2 | | insert 新分账单（day=今天）；commit |
| t3 | select count(*) … → 101 | |

幻读难防的机械原因：**行锁只能锁住已存在的行，锁不住“还不存在的行”**。防它需要把锁加在**谓词（条件本身）**上——谓词锁/间隙锁（3.4 节）。SQL 标准的可重复读**允许幻读**（标准只承诺到不可重复读为止）；但 PostgreSQL 的可重复读（快照实现）防幻读、InnoDB 的可重复读用 next-key 锁在锁定读上防幻读——“可重复读防不防幻读”这个面试题的答案必须先问“哪个库的 RR”（2.7 与 4.6 节展开）。

### 2.5 丢失更新（lost update）：标准没登记的一等公民异常

两个事务都执行“读-改-写”，后提交者覆盖先提交者的修改，前者的更新**无声丢失**。现场二就是它：库存余 1，T1/T2 都读到 1、都算出 0、都写入 0——卖出 2 件库存却只减 1 次。

| 时刻 | T1 | T2 |
|---|---|---|
| t1 | 读库存 → 1 | |
| t2 | | 读库存 → 1 |
| t3 | 写 库存=0；commit | |
| t4 | | 写 库存=0；commit（T1 的扣减丢失） |

关键事实（评审高频踩空）：**SQL 标准的四个隔离级别表里没有“丢失更新”这一行**——按标准字面实现的可重复读**允许**丢失更新。现代数据库的实际行为分三派（以官方文档为准）：

- PostgreSQL：可重复读（SI）带**写冲突检测**——T2 提交时发现同被 T1 改过，**报错** `could not serialize access due to concurrent update`（官方文档 §13.2.3 明确此行为；快照隔离的“先提交者胜”）；
- MySQL InnoDB：可重复读下快照读不报错（T4 直接写入），但**锁定读/UPDATE 走当前读 + next-key 锁**，`SELECT ... FOR UPDATE` 后再改就串行化了；普通 UPDATE 语句本身是原子的当前读，天然防丢失更新；
- 快照读 + 应用层写入（先 SELECT 再 UPDATE ... WHERE 不带条件）：**任何默认档位都防不住**——丢失更新多数是应用代码自己写的。

### 2.6 写偏斜（write skew）：两个都没违规、合起来违规

写偏斜是快照隔离的**标志性漏洞**（DDIA 第 7 章重点展开）。定义式描述：两个事务读**不相交的行集**、基于读到的前提做判断、各自写**不同的行**——单看每个事务都合法，合起来破坏了“读集与写集之间的不变量”。

经典例子（DDIA 的值班医生）：约束是“至少一名医生值班”。两名值班医生同时请假：各自看到“还有另一人值班”（读前提成立），各自把自己置为休息（写不同行），提交都成功——结果没人值班，约束被无声破坏。

工单中心版本：约束“每张工单同一时刻最多一个处理人”。两个客服各自查询“这张工单当前无处理人”（都成立），各自 insert 一条“接单处理人”记录到不同表/不同行——重复接单。分账版本：“账户 A 余额 100，两笔各 60 的分账都检查 A 余额充足后扣款到不同收款方”——余额穿底。

与丢失更新的区别一句话：**丢失更新是写了同一行（系统能检测），写偏斜写的是不同的行（快照隔离检测不到写冲突）**。防它要靠：约束下沉（唯一键）、锁定读、物化冲突、或真可串行化（SSI）——四类解法见 6.3。

### 2.7 异常 × 隔离级别矩阵

把 2.2~2.6 汇总成一张总表。“标准”列按 SQL-92 的字面定义；“实际”列的口径差异正是 4.6 节的主题：

| 异常 | 读未提交 | 读提交 | 可重复读（标准字面） | 可串行化 |
|---|---|---|---|---|
| 脏写 | 禁止 | 禁止 | 禁止 | 禁止 |
| 脏读 | 允许 | 禁止 | 禁止 | 禁止 |
| 不可重复读 | 允许 | 允许 | 禁止 | 禁止 |
| 幻读 | 允许 | 允许 | 允许（标准） | 禁止 |
| 丢失更新 | 允许 | 允许 | **标准允许；主流库实际大多防住**（PG 报错/InnoDB 锁定读） | 禁止 |
| 写偏斜 | 允许 | 允许 | 允许 | 禁止 |

两个考点钉死：**丢失更新和写偏斜都不在 SQL 标准的异常表里**；**可串行化是唯一全禁的档位**——选择弱档位的每一次省钱，都要能在这张表里指出“我接受的是哪一行的允许”。

## 3. 两阶段锁（2PL）：悲观路线的机械

### 3.1 锁规则与“两阶段”的含义

2PL（两阶段锁；并发控制教科书级出处：Bernstein、Hadzilacos 与 Goodman 1987 年的《Concurrency Control and Recovery in Database Systems》，全文公开）的规则：

- 事务读行前加**共享锁（S）**，写行前加**排他锁（X）**；S 与 S 相容、S 与 X / X 与 X 互斥；
- **两阶段**：增长阶段只加锁不放锁；收缩阶段只放锁不再加锁。

“两阶段”不是两轮提交，而是纪律：**一旦放过任何锁，就不能再拿新锁**。没有这条纪律，锁的先后关系不再有序，无法推出等价串行顺序。工程实现几乎都是**严格两阶段锁（S2PL）**：写锁全部持有到事务结束才统一释放（读锁可以早放）——这样提交前别人绝无可能读到/覆盖你的写，abort 也只需逆序回滚。

### 3.2 S2PL 与可串行化的关系：充分不必要

S2PL **能保证**可串行化（锁的获取顺序构成等价串行序），但只对**行读写**成立——谓词查询（范围扫描）锁不住未来会插入的行，所以 **S2PL + 谓词锁**才是完备的串行化方案（3.4 节）。另一个方向：S2PL 会产生**假冲突**（两个事务摸同一行但都只读，仍按锁互斥排上了队）——可串行化但不必串行。MVCC（第 4 节）正是从这点切入的。

### 3.3 意图锁：层级锁的捷径

表与行两级加锁时，给某行加 X 锁前怎么确认“没人在整表上加 S 锁”？逐行检查太贵，于是引入**意图锁（IS/IX）**：给行加锁前先在表上挂意图标记（IS = 打算在下面行加 S，IX = 打算加 X）；表级锁之间按相容矩阵快速裁决（SIX = 持 S 同时下面还要 IX）。InnoDB 与 SQL Server 的表级 IS/IX 即此（官方文档可查）。评审时点：**DDL 与大范围操作申请表级锁时要等行级意图清空**——“一条长事务卡住整表 DDL”的机械就是它。

### 3.4 谓词锁 → 间隙锁 → next-key：防幻读的工程化

理论上的谓词锁：锁定“满足 WHERE 条件的行的集合”（含不存在的行），插入前检查谓词相交。精确谓词锁的匹配代价高（索引结构决定可行性），工程把它近似为**索引项上的锁**：

- **间隙锁（gap lock）**：锁住**索引记录之间的间隙**，阻止他人在此区间插入——谓词“day=今天”近似为“day 索引上今天的两条边界之间的间隙”；
- **next-key 锁**：索引记录锁 + 该记录前的间隙锁，合成一个左开右闭的锁定区间。

InnoDB 的准确表述（MySQL 官方手册“InnoDB Locking”一节）：**可重复读档位下，锁定读（`FOR UPDATE`/`FOR SHARE`）与 UPDATE/DELETE 使用 next-key 锁搜索的索引范围**，从而阻止其他事务插入到该范围——这是 InnoDB 声称“RR 防幻读”的机械；而**普通快照 SELECT 不加锁、不防**（它读旧快照，天然看不到新插入的行，另一种意义上的“防”）。还要注意：**读提交档位下间隙锁基本关闭**（官方手册：RC 下 gap locking 仅用于外键与唯一性检查）——所以“RC + SELECT ... FOR UPDATE 防幻读”在 InnoDB 上并不成立，范围扫出的缺口别人仍可插入。

行锁挂在哪里也是 InnoDB 的特色：**锁加在索引记录上**；UPDATE 没有可用索引时走全表扫描，沿途记录全部上锁（官方手册“Transaction Isolation Levels”与“Locks Set by Different SQL Statements”说明）——**没有索引的更新语句是锁事故的头号来源**。

### 3.5 死锁：检测与超时

两个事务交叉持锁互等即死锁。两条工业路线：

- **等待图（waits-for graph）检测**：锁管理器维护“谁在等谁”的图，出现环即选牺牲者回滚。InnoDB 用检测，且选择**改动行数较少**的事务当牺牲者（回滚代价小，官方手册 §15.7.5 Deadlock Detection）；
- **锁等待超时**（`innodb_lock_wait_timeout`，默认 50 秒，可配）：简单但钝——把“慢”当“死”处理。

工程上死锁无法根除，只能降低概率与兜底：**按固定顺序访问资源**（如多行更新按主键升序）、缩短事务、把“先查再改”换成原子语句；应用层必须**把死锁错误当可重试错误**处理（牺牲者回滚不是故障，是机制在正确工作）。

### 3.6 2PL 的代价清单

- **读阻塞写、写阻塞读**：读写互斥是吞吐天花板，读多写少的互联网负载尤其吃亏；
- **死锁**是 S2PL 的内生现象（交叉加锁不可避免），必须有检测/超时/重试配套；
- **锁本身是内存与管理成本**：百万行逐个加锁不可行——SQL Server 有锁升级（行→页→表，官方文档），InnoDB 不升级但依赖索引把锁范围缩小；
- **竞争敏感**：并发冲突高时吞吐断崖（排队与回滚雪崩），而非线性下降。

这份账单解释了为什么主流互联网数据库默认不靠 2PL 提供隔离——而是下一节的 MVCC。

## 4. MVCC 与快照隔离：把“读不加锁”变成默认

### 4.1 核心思想：写者建版本，读者读快照

**多版本并发控制（MVCC）**：更新不覆盖旧版本，而是产生新版本；每个事务按自己的**快照**决定能看到哪些版本。效果：

- **读不阻塞写、写不阻塞读**——读者看旧版本，写者造新版本，互不相扰（对照 3.6 的第一条代价）；
- 读的“一致性”来自快照的静止性，而非锁的排他性。

MVCC 不是隔离级别，是**实现材料**：读提交/可重复读/快照隔离/SSI 都可以用它造出来。第 2 册 4.6 节的 LMDB（copy-on-write B+ 树）、第三阶段 09 档案 etcd 的多版本 revision、第二阶段 3.2 的事件溯源，都是“不覆盖旧版本”这个思想在不同载体的重现——**一次学会，处处认得**。

### 4.2 版本与可见性判定：通用规则

每个行版本带两个标记：**创建者事务 xid（xmin）**与**删除者事务 xid（xmax，空表示仍在世）**。事务 T 的快照记下“我出生时，哪些事务正在进行（活跃集合）+ 下一个将分配的 xid”。判定某版本对 T 是否可见：

1. xmin 未提交且 xmin ≠ T → 不可见（未提交的创建）；
2. xmin 是活跃集合里的事务且 ≠ T → 不可见（我出生时它还没完）；
3. xmin 已提交，但提交顺序在我的快照**之后**（xid ≥ 快照上界）→ 不可见；
4. 通过 1~3 则版本可见；再看 xmax：xmax 已提交且对 T 可见（该删除我看得见）→ 版本已被删，不可见；否则可见。

读一行 = 沿版本链找到**对当前快照可见的最新版本**。这套规则是 PostgreSQL 的实际做法（官方文档 §13 并发控制对可见性判断有完整描述），InnoDB 语义等价但版本链放在 undo 日志里（4.4 节）。

### 4.3 PostgreSQL 实现：xmin/xmax、clog 与 VACUUM

- 每个元组头部带 xmin/xmax；事务提交状态记在提交日志（clog）里；快照记录活跃事务集合（官方文档 §13.2）。
- **读提交：每条语句拍一个新快照**；**可重复读：整个事务用第一个查询时的快照**——两档的差别只有“快照换不换”，机械极简。
- **更新 = 插入新版本 + 旧版本打 xmax**：死版本（没有任何快照还看得见它）由 **VACUUM** 回收。
- **事故链（必背）**：长事务持有旧快照 → 数据库必须保留它能看见的死版本 → VACUUM 无法推进 → 表与索引膨胀、事务 ID 回卷防护告警。PG 上“一条跑了几小时的报表查询把库拖垮”多半是这条链。InnoDB 对应的病症是 undo 链超长（4.4 节）。

### 4.4 InnoDB 实现：undo 链与 ReadView

- InnoDB 的表是聚簇 B+ 树（第 2 册 3.4 节），**行内只有最新版本**，旧版本存在**回滚段（undo log）**里，行的隐藏字段记创建/删除它的事务 id 与回滚指针（roll pointer），沿指针逆行即可重建任意旧版本（MySQL 官方手册 “InnoDB Multi-Versioning” 一节）。
- 每次读建立 **ReadView**：活跃事务集合、已分配最大 xid 等；可见性判定与 4.2 规则同构。
- **读提交：每条语句新建 ReadView；可重复读：事务内第一条查询建立、复用到事务结束**——与 PG 的档位语义一致，但实现载体不同（PG 版本就地堆着，InnoDB 版本在 undo 链上）。
- **长事务的账**在 InnoDB 侧表现为 undo 膨胀：所有快照需要的旧版本都挂在回滚段上不能清除，回滚段暴涨拖慢一切需要走版本链的读。

### 4.5 快照隔离（SI）防什么、不防什么

**快照隔离（snapshot isolation）**：事务全程一个快照（读不脏、可重复、无幻——读侧三个异常全防），写侧配**写-写冲突检测**：提交时发现**任何一行**被别的事务（在快照建立后）改过并提交 → **先提交者胜，后提交者中止**。

| 异常 | SI 下 | 靠什么 |
|---|---|---|
| 脏读 / 不可重复读 / 幻读（读侧） | 全防 | 快照静止性 |
| 丢失更新 | 防 | 写-写冲突检测（同行才能检测） |
| 写偏斜 | **不防** | 写的是不同的行，检测不到 |

SI 的价值公式：**用 2PL 一小半的代价（无读写阻塞、死锁更少）买到读侧全部 + 丢失更新的防护**；账单上唯一没付的就是写偏斜。

### 4.6 “可重复读”同名不同义：四库对照

落到具体系统（以下均出自各库官方文档，标注在行内）：

| 数据库 | 默认级别 | “可重复读”实际是什么 | 可串行化是什么 |
|---|---|---|---|
| PostgreSQL | 读提交 | **快照隔离**：官方明确 RR 防脏读/不可重复读/**幻读**（快照读天然防），但不防写偏斜；同行并发更新报 `could not serialize access due to concurrent update`（PG 手册 §13.2） | SSI（第 5 节），9.1（2011 年）起 |
| MySQL/InnoDB | 可重复读 | 快照读用整事务 ReadView；锁定读/写用 next-key 锁防幻读（MySQL 手册 InnoDB Locking/Isolation Levels） | 隔离级别 SERIALIZABLE：普通 SELECT 自动转锁定读（FOR SHARE），接近 S2PL 形态 |
| Oracle | 读提交 | （Oracle 无名为 RR 的档位）其 SERIALIZABLE 即快照隔离（Oracle 概念手册） | SERIALIZABLE = SI（**不含写偏斜防护**，说明书明确剩余风险） |
| SQL Server | 读提交（悲观） | 无 RR；提供 RCSI（读提交快照，语句级）与 SNAPSHOT（事务级 SI），均需显式开启（SQL Server 文档“Snapshot Isolation”） | SERIALIZABLE = S2PL + 谓词/范围锁 |

三个工程结论：①“提隔离级别”必须先回答“哪个库的哪一档”；②**MySQL 的 RR 与 PG 的 RR 都“防幻读”，但机制不同（锁定 vs 快照）、对写偏斜同样束手**；③“串行化”这档也不统一——PG 是 SSI（乐观），MySQL/SQL Server 是锁（悲观）——选它还要选路线。

### 4.8 MVCC 的三个角落：读己之写、唯一约束、二级索引

**读己之写**。可见性规则对自己放行（xmin == 我 → 可见），所以自己未提交的写自己看得见——这是事务语义的底线。要小心的坑在**应用侧的“假事务”**：应用代码用两次独立查询拼一个“读-改-写”（没有包在一个数据库事务里），第一次读和第二次读之间世界已经变了——这不是数据库的隔离级别问题，是根本没有事务。

**唯一约束检查必须“当前读”**。两个事务并发插入同一个唯一键，第二个不能只看快照（快照里没有第一个未提交的行，看起来键可用），必须**读最新状态并等第一个定案**：PG 的行为是第二个插入**阻塞等待**，直到对方提交（报唯一冲突）或回滚（插入成功）——官方文档 §13.6 对 Unique Indexes 的说明；InnoDB 的重复键检查同样走当前读（官方手册在隔离级别一节提到 RC 下 gap lock 仅保留外键与唯一性检查两个用途）。这个细节有两重价值：①它是 6.3 节“约束下沉防写偏斜”能成立的机械基础——**唯一键的并发正确性由数据库的当前读 + 等待保证，不需要应用加锁**；②它解释了一类诡异现象：**一条 INSERT 毫无理由地卡住，可能是另一个事务握着同键的未提交插入**（排查方向是看活跃事务，不是看锁表死磕）。

**二级索引上的可见性**。MVCC 的版本信息挂在“行”上，而二级索引条目是“键 → 行位置”的附属结构：PG 的索引条目不记版本，可见性判断必须回堆表做（所以 PG 有位图扫描先攒一批堆引用再回堆，减少随机 IO）；InnoDB 的二级索引不记逐行版本，需要时回聚簇索引沿 undo 链取版本。工程含义：**覆盖索引的“免回表”在 MVCC 数据库里是尽力而为**——需要判断可见性时还是要碰主键树；给高频查询设计覆盖索引时，把“命中后是否回表”当作可能发生来留余量。

### 4.9 动手：MiniMvcc

[03a-示例-mvcc-snapshot/MiniMvcc.kt](03a-示例-mvcc-snapshot/MiniMvcc.kt) 把 4.2 的可见性规则逐条实现成可跑的迷你引擎（220 行，kotlinc 2.2.20 编译运行验证）：单调事务号、提交时钟、版本链（xmin/xmax）、RC/RR 两档快照、first-committer-wins 冲突检测，然后连演六幕。⑤⑥ 两幕的真实输出（写偏斜与 SSI）：

```text
== ⑤ 写偏斜穿透快照隔离（SI：值班医生都请成假了）==
   A 读到 B=on_call → 判断“还有人在班”，A 请假
   B 读到 A=on_call → 判断“还有人在班”，B 请假
   tA 提交 → 成功；tB 提交 → 成功
   最终：A=off B=off —— 约束“至少一人在班”被无声破坏（写的是不同的行，SI 的冲突检测看不见）

== ⑥ SSI 拦下同一场景（rw 反依赖追踪 + 危险结构检测）==
   tA 提交 → 成功（in=1、out=0：只有一条 rw 边，放行）
   [SSI] 事务3 处于危险结构（in=1, out=1）→ 中止（40001）
   最终：A=off B=on_call —— 至少一人在班被保住（应用收到 40001 重试 B 的方案即可）
```

六幕依次对照 2.2~2.6 的时序表；动手方向：把 ④ 幕改成 RC 模式重跑（冲突检测仍生效——first-committer-wins 是 SI 的属性），把 ⑥ 幕的提交顺序反过来（先提交 B），观察“危险结构跟着后提交者走”。

## 5. 可串行化快照隔离（SSI）：乐观的串行化

### 5.1 rw 反依赖与危险结构

SSI 的出处：Cahill 的博士论文（2009）与 Cahill、Röhm、Fekete 的 VLDB 2008 论文 *Serializable Isolation for Snapshot Databases*；PostgreSQL 9.1（2011 年）是它的第一个主流生产实现（PG 官方文档 §13.2.3 明确致谢该论文）。

**rw 反依赖（anti-dependency）**：T2 写了 T1 读过的数据且 T2 后提交——T1 的读前提被 T2 的写推翻。单条 rw 边无害；**危险结构**是“**两个连续的 rw 边**”：

```text
T1 --rw--> Tp（枢纽）--rw--> T2，同时 T2 --ww/wr--> T1
```

枢纽事务 Tp 先根据读前提做判断，后写数据推翻别人的读前提——写偏斜正是这种结构（Tp=医生1：读了医生2 在班，写了医生1 休息；同时医生2 对称操作，两条 rw 边首尾相接成环）。SSI 的判定：检测到某事务同时处于“一条入边 + 一条出边”（既被人推翻过前提、又推翻过别人前提）的枢纽位置，就**中止它**，打破潜在的环。

### 5.2 实现要点

PG 的做法（官方文档口径）：读集用**粗粒度 SIREAD 谓词锁**记录（页/关系级，可能误伤、绝不阻塞 anybody）；每个事务维护 in/out 冲突计数；提交时若本事务“入边与出边皆非零”则中止（错误码 40001，可重试）。要点三条：①**只中止、不阻塞**——运行中谁都不等谁；②检测是**保守的**（粗粒度读集导致假阳性中止）；③中止要在**提交时**才能判定——事务白干了一场才被叫停，这是乐观路线的固有成本。

### 5.3 行为与选型

| | S2PL（锁串行化） | SSI（乐观串行化） |
|---|---|---|
| 冲突少 | 读也要加锁，白付管理成本 | 几乎零额外成本 |
| 冲突多 | 排队、吞吐断崖，但每个事务终会轮到 | 中止/重试风暴，活锁风险 |
| 死锁 | 有（需检测） | 无（不等待） |
| 应用要求 | 处理锁等待超时 | **必须实现 40001 重试**（且重试要真幂等） |

工程判断：**热点行竞争激烈（秒杀扣同一 SKU）用锁或干脆换模型（第三阶段 Redis+Lua 预扣）；读多写少、冲突稀散的分析/后台负载用 SSI 最舒服**。“把整库设成 SERIALIZABLE 一劳永逸”在没有重试框架的地方是事故预约——上游会随机收到 40001 并把它当故障报警。

## 6. 隔离级别选型实战

### 6.1 默认级别是怎么来的、互联网为什么常见 RC

InnoDB 默认 RR 有历史原因（基于语句的 binlog 复制需要 RR 保证主从一致；行格式 binlog 后该约束已不存在——MySQL 官方手册在隔离级别章节有说明），而高并发互联网负载常把默认调到 RC：间隙锁基本关闭、锁冲突与死锁更少、不可重复读由业务按需处理。这条调优在国内很常见（如阿里巴巴《Java 开发手册》的数据库规约建议改 RC，公开可查）。调到 RC 的代价清单必须同步交代：**语句间快照不一致**（一个事务两条语句可能读到前后不搭的两个世界）、**InnoDB 下间隙锁失效**（依赖 FOR UPDATE 防幻的范围逻辑要重新审）。

### 6.2 丢失更新的四种武器

以桶装水扣库存为例，四种写法从弱到强：

1. **原子语句**：`UPDATE stock SET n = n - 1 WHERE sku=? AND n >= 1`——数据库内部“当前读 + 行锁”，天然不丢失，**首选**；
2. **乐观锁**：`UPDATE stock SET n=n-1, ver=ver+1 WHERE sku=? AND ver=?`——影响行数为 0 则重试；无锁等待、高冲突时重试成本高；
3. **悲观锁定读**：`SELECT n FROM stock WHERE sku=? FOR UPDATE` 再改——同事务内行锁在手，最直观；持有时间 = 事务剩余部分；
4. **提到快照隔离/RR**：利用写-写冲突检测（PG 会报错重试；InnoDB 的普通快照读**不**触发，别指望它）。

评审红线：**“先 SELECT 再无条件 UPDATE”在所有默认档位下都是丢失更新**——2.5 节的三派行为都救不了不带条件的写。

### 6.3 写偏斜的四类解法

以“每张工单最多一个处理人”为例：

1. **约束下沉**：处理人表加 `(ticket_id)` 唯一键——数据库替你挡并发插入，最便宜；能唯一下沉的约束不要在应用层判断；
2. **锁定读**：接单前 `SELECT ... FOR UPDATE` 锁住工单行（把“读前提”变成当前读）——InnoDB PG 都适用；注意 RC 下间隙锁失效，锁范围要落在**行**上而不是范围上；
3. **物化冲突**：把“约束的冲突组”变成一行真实数据，先锁/改它再干活——DDIA 给的经典技巧：会议室场景先 insert “(room, slot) 锁行”再预约；
4. **真串行化**：SSI 一把梭——业务代码最干净，代价是必须写好 40001 重试（5.3 节）。

### 6.4 长事务的事故链（两库版本）

- **PG 版**：长事务的快照挡住 VACUUM → 死元组堆积 → 表和索引膨胀 → 全表扫描变慢 → 更长的查询……恶性循环；事务 ID 回卷防护（xidWraparound）会进一步逼停写入（官方文档 §13.2 有完整叙述）；
- **InnoDB 版**：长事务的 ReadView 挂住 undo 清理 → 回滚段膨胀 → 版本链变长 → 一致性读沿链回溯变慢 → 锁等待时间被拉长……

共同根因：**MVCC 用空间换并发，长事务把“空间”无限期化**。工程防御：事务超时上限（应用侧与 `max_execution_time`/`statement_timeout` 类参数）、监控 `pg_stat_activity` 里 oldest 事务/`information_schema.innodb_trx` 里 trx_started、把报表与导出挪到只读副本或增量快照（CDC，第 4 册第 8 节）。

### 6.5 与第三阶段分布式事务的分工

| 问题 | 本册（单机内核） | 第三阶段第 4 节（分布式） |
|---|---|---|
| 单行原子/同库多行 | 存储引擎 + 隔离级别直接给 | 无需出场 |
| 跨库/跨服务多对象 | — | 2PC/TCC/Saga/本地消息表 |
| 中间态可见性 | 隔离性挡住（未提交不可见） | Saga 无隔离，三块补丁（状态语义化/幂等可查/超时监控） |
| 丢失更新 | 冲突检测/锁/原子语句 | 应用幂等键 + 唯一约束兜底 |
| 写偏斜 | SSI/约束/锁定读 | 分布式层无解，仍要落回单库约束 |
| 串行化 | S2PL/SSI | 全局串行化代价极高，实践用业务级隔离（分层取舍，第三阶段 4.6） |

一句话分工：**能被一个本地事务罩住的问题永远别升级成分布式事务；罩不住时，本册给的“约束、锁定读、幂等键”仍是分布式方案里每个本地步骤的内部实现**。
