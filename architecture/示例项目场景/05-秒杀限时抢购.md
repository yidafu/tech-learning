# 秒杀/限时抢购：瞬时高并发场景

> 返回：[示例项目场景](00-导览.md) · [软件架构学习大纲](../软件架构学习大纲.md)
> 定位：第三阶段缓存体系与限流熔断降级的教科书场景；架构深度拆解见[06-第六阶段/02-场景拆解-秒杀](../06-第六阶段/02-场景拆解-秒杀.md)，本文聚焦业务画像与核心模块底料。主要对应大纲：三-3 缓存体系、三-5 限流熔断降级、六-1 场景拆解。

## 业务画像

限量商品限时开放抢购：活动开始瞬间流量是平时的百倍，库存极少，且要防黄牛与机器人脚本。

**与普通购买的三个特殊约束**：

1. **瞬时洪峰**：活动开始前大量用户反复刷新页面，开始那一刻请求集中涌入，峰值可能是日常的 100 倍以上，持续几十秒后断崖回落。
2. **库存极少**：100 万人抢 1000 件商品，99.9% 的请求注定失败——系统必须“优雅地拒绝”而不是被打垮。
3. **对抗性**：黄牛用脚本比人快得多，纯技术防不住业务层面的套利，风控必须在线。

**用户角色**：C 端用户（抢购）、运营（活动配置）、风控（策略配置与复盘）、客服（客诉与订单查询）。

**教学量级假设**（容量推演的标准数字）：预约用户 100 万，开抢瞬间 50 万 QPS 打向商品页，下单转化约 100 万次点击，库存 1000 件，单机网关容量 1 万 QPS。这套数字支撑“每一层过滤掉多少流量”的逐层推演。

**核心业务流**：

1. 活动预热：商品页展示“X 日 20:00 开抢”，用户可订阅提醒；
2. 开抢：用户点“立即抢购”→前端拿活动令牌→提交下单请求；
3. 系统逐层过滤：网关限流→风控拦截→缓存库存预扣→进入异步下单队列；
4. 队列消费者创建订单、扣减数据库库存（乐观锁兜底）、锁定结果；
5. 用户收到“抢购成功，请在 15 分钟内支付”或“已抢完”；
6. 未支付订单释放库存回流，支持“捡漏”；活动结束复盘。

## 模块总览

| 模块 | 一句话职责 | 关键数据 |
|---|---|---|
| 活动管理 | 活动配置、预热与开关 | 活动表 |
| 活动商品与库存 | 秒杀价与独立的活动库存 | 活动库存 |
| 抢购入口 | 令牌发放与请求过滤 | 抢购资格/令牌 |
| 异步下单 | 排队削峰、订单创建 | 下单队列、结果 |
| 风控与防刷 | 识别拦截机器与黄牛 | 风控名单、画像 |
| 订单兜底 | 超时释放、库存回流、防超卖 | 秒杀订单 |

秒杀通常不是独立系统，而是“交易系统的一层特殊通道”——活动库存独立于普通库存，下单链路复用交易系统但入口与库存扣减完全独立。这个定位本身就是一个架构决策的讨论点。

## 系统上下文与逐层过滤图

秒杀架构的形状就是一条**漏斗**：每一层过滤掉一批注定失败的请求，让极少数“有效下单”到达数据库：

```mermaid
flowchart LR
    U["100 万预约用户<br/>反复刷新"] --> CDN["CDN + 页面静态化<br/>（读洪峰就地消化）"]
    CDN --> GW["网关限流<br/>（粗限：保全局容量）"]
    GW --> TOK["令牌校验<br/>（读流量与写流量分家）"]
    TOK --> RC["风控打分<br/>（机器与黄牛拦截）"]
    RC --> STOCK["缓存库存原子扣减<br/>（分段 key）"]
    STOCK --> MQ["下单队列<br/>（削峰：按消费能力放行）"]
    MQ --> ORD["交易系统建单<br/>（数据库乐观锁兜底）"]
    ORD --> RES["结果查询<br/>（轮询/推送）"]
```

漏斗的三条设计纪律（三-3、三-5 的取材骨架，逐层数字推演见下文容量小节）：

- **过滤越早越好**：每早一层拦截，下游所有层的成本同比例下降——CDN 挡掉 90% 的读、网关挡掉超容量写、令牌把“刷新者”与“下单者”分开、风控把“非人”剔除，最后只有约等于库存量级的请求碰数据库。
- **每一层只做一件事**：限流不懂业务、令牌不管风控、库存不管排队——层与层通过明确的通过/拒绝信号串联，任何一层失效时下一层仍能自保（限流挂了还有令牌，令牌没了还有库存原子扣减兜底）。
- **数据库永远最后**：所有花哨手段的共同目标只有一个——把到达数据库的写入压到它能承受的速率；反过来，容量推演永远从数据库能扛多少开始倒推。

## 核心模块

### 活动管理

**职责**：配置活动（商品、秒杀价、库存、开始/结束时间、限购），控制预热与上下线。

**关键实体与数据**：`seckill_activities`：`activity_id`、`sku_id`、`seckill_price`、`stock_total`（活动库存，独立于普通库存）、`start_at`、`end_at`、`per_user_limit`、`status`（草稿/预热/进行中/已结束）。

**典型流程**：运营建活动→审批→预热期推送商品页静态化与缓存加载→准点开闸→结束或售罄自动关闭→复盘数据导出。

**设计要点与典型陷阱**：活动配置的错误在开抢前必须发现（价格配错小数点、库存超过仓库实物）——配置校验与审批流；开闸时间以服务端为准（前端倒计时只做展示，防止用户本地改时间提前提交）；活动结束的“已结束”状态要全网一致生效（缓存短过期 + 版本标记）。

### 活动商品与库存（防超卖的心脏）

**职责**：维护活动库存的原子扣减，回答“还有没有、扣不扣得到”。

**关键实体与数据**：Redis 中的 `activity_stock:{activity_id}` 计数器；数据库 `seckill_stocks`（`activity_id`、`remaining`、`version`）做兜底与对账。

**典型流程**：预热时把库存加载进 Redis→请求到达执行原子 DECR→减到负数即拒绝（回补 +1）→下单成功后异步同步数据库。

**设计要点与典型陷阱**：

- **反例（先查后减）**：`GET stock` 判断大于 0 再 `DECR`，两步之间并发穿透，1000 件卖出 1200 件。**修正**：单条原子命令 `DECR` 后判负回补，或 Lua 脚本把“判断+扣减”合一；数据库侧用条件更新 `UPDATE ... SET remaining = remaining - 1 WHERE remaining > 0` 乐观兜底。
- **热点 key**：50 万 QPS 全打在一个 `activity_stock` 键上，单分片扛不住。**修正**：库存分段——把 1000 拆成 100 段，请求哈希到段，某段扣完再从富余段调拨。
- **扣减与建单的时序**：缓存扣减成功 ≠ 下单成功——消费者建单时数据库库存可能已被并发扣完（Redis 与库短暂不一致），此时要**反向补偿**：缓存加回 + 结果置失败。这条补偿路径必须与扣减路径一样经过测试，否则“极小概率”在百万请求下必然出现。

分段库存扣减骨架：

```kotlin
class ShardedStock(private val shards: Int) {
    // 每段独立计数器，请求按用户哈希路由，避免单 key 热点
    private val remainders = java.util.concurrent.atomic.AtomicIntegerArray(shards)

    fun init(total: Int) { repeat(shards) { remainders.set(it, total / shards) } }

    fun deduct(userId: Long): Boolean {
        val idx = (userId.hashCode() % shards + shards) % shards
        return tryDeduct(idx) || tryStealFromOthers(idx) // 本段不足时尝试从其他段调拨
    }

    private fun tryDeduct(idx: Int): Boolean {
        while (true) {
            val cur = remainders.get(idx)
            if (cur <= 0) return false
            if (remainders.compareAndSet(idx, cur, cur - 1)) return true
        }
    }

    private fun tryStealFromOthers(exhausted: Int): Boolean {
        for (i in 0 until shards) {
            if (i != exhausted && tryDeduct(i)) return true  // 简化模型：段间调拨；生产实现需考虑公平性
        }
        return false
    }
}
```

### 抢购入口（令牌与资格）

**职责**：在请求进入交易链路前完成第一层过滤。

**关键实体与数据**：抢购令牌（开抢前发放/开抢瞬间短时发放的签名 token，含用户与活动维度）；`participations`（`activity_id`、`user_id`、`result`——参与即留痕，支撑限购与复盘）。

**典型流程**：用户点抢购→校验令牌与资格（限购、黑名单、答题/验证码）→通过者进入库存扣减。

**设计要点与典型陷阱**：令牌把“刷新页面的读流量”与“真正下单的写流量”分开——令牌发放可以再叠加随机丢弃（放 N 倍于库存的令牌，抢完即止）；**资格预校验的度**：校验越多拦截越早，但用户体验越差，逐层递进（网关粗筛→令牌→风控→库存）。

**令牌发放量的推演**（假设口径）：库存 1000 件，放多少张令牌？三个输入——真实用户的到达分布（开抢后 10 秒内集中）、人手点击到提交的延迟（秒级）、风控层还会再剔一批。假设真用户瞬时到达 1 万人、其中持令牌者先到先得，发 3000~5000 张是常见起点：远大于库存（允许缓存扣减层继续竞争过滤），又远小于总点击（把过滤前置）。**定性结论：令牌层的目标不是精确，是“把数量级砍下来”**——精确过滤交给库存原子扣减。

**资格预校验的层次表**（每往下一层，用户感知变差、拦截变准）：

| 层 | 手段 | 用户感知 | 拦截对象 |
|---|---|---|---|
| 网关粗筛 | 速率阈值超限直接 429 | “系统繁忙” | 无差别流量整形 |
| 令牌 | 无令牌请求直接拒绝 | 与正常失败无异 | 刷新党与脚本的第一波 |
| 验证码/答题 | 强制人机交互 | 明确感知“门槛” | 低级脚本 |
| 风控画像 | 注册时长、历史行为、设备指纹打分 | 少数人被拦 | 专业黄牛 |
| 库存扣减 | 原子竞争 | “已抢完” | 剩下的所有人（终局裁决） |

### 异步下单（削峰填谷的核心）

**职责**：把 100 万次点击排成队列，以数据库可承受的速率消费。

**关键实体与数据**：下单队列（MQ）；`seckill_results`（`user_id`、`activity_id`、`status` 排队中/成功/失败/已超时）——前端轮询的唯一依据。

**典型流程**：扣减缓存库存成功→投递下单消息（带幂等键）→立即返回“排队中”→消费者建单、扣数据库库存→写结果→前端轮询/推送得知结局。

一次抢购点击的**事件时序逐步表**（从点击到看到结局，前端体验与后端状态逐行对齐）：

| 步 | 动作 | 数据变更 | 失败与并发时的行为 |
|---|---|---|---|
| ① | 点击抢购，携带令牌 | 无 | 令牌无效/过期→立即拒绝，不进任何后续层 |
| ② | 限购与风控校验 | 写 `participations`（参与留痕） | 已参与/黑名单→拒绝；参与记录唯一约束挡重复点击 |
| ③ | 缓存库存原子扣减 | Redis 分段计数 -1 | 扣到负→回补并返回“已抢完” |
| ④ | 投递下单消息（幂等键=活动+用户） | MQ 消息 | 投递失败→**缓存库存加回**，返回“系统繁忙请重试” |
| ⑤ | 返回“排队中” | 写 `seckill_results=排队中` | 前端进入轮询（间隔递增） |
| ⑥ | 消费者建单 + 数据库库存条件更新 | 订单 + `remaining-1` | 库存已空→缓存加回、结果置失败 |
| ⑦ | 写最终结果 | `seckill_results=成功/失败` | 重复消费→幂等键挡住，只建一单 |
| ⑧ | 前端得知结局 | 无 | 成功→跳支付（15 分钟时限）；失败→“已抢完” |

表里有两条“加回”路径（④⑥）——**凡是在缓存里扣了但最终没成单的，都必须有对应的回补**，且回补本身要幂等；这是秒杀库存“不超卖也不少卖”的另一半（少卖比超卖隐蔽：库存明明还有，页面却显示抢完）。

**设计要点与典型陷阱**：**反例（同步建单）**：扣完 Redis 直接同步调交易系统建单，交易库在洪峰前 10 秒被拖垮，连普通订单都不能买。**修正**：队列隔离 + 结果异步通知；排队体验（轮询间隔递增、排队位置提示）是产品设计问题但决定客诉量；消费失败重试必须幂等（同一幂等键只建一单）。

### 风控与防刷

**职责**：在技术过滤之外识别“不是人”或“恶意的人”。

**关键实体与数据**：设备指纹、账号画像（注册时长、历史行为）、黑名单、风控规则（同 IP 请求数、同设备账号数、下单频率）。

**典型流程**：请求特征采集→规则/模型打分→低分拦截或弹验证码→事后复盘把新特征加进规则。

**设计要点与典型陷阱**：风控本质是攻防对抗，规则会失效，架构上要支撑“规则热更新”（与工单分派规则配置化同构）；误杀正常用户的成本与漏过黄牛的成本要做业务权衡——风控分数的灰度区间（可疑但不确定的放行 + 事后回溯）。

### 订单兜底

**职责**：抢购成功后的支付时限、库存回流、防“占着不买”。

**关键实体与数据**：秒杀订单（带 `activity_id`，支付时限通常比普通订单短，如 15 分钟）；未支付释放回流事件。

**典型流程**：成功未支付→超时取消→活动库存回补（Redis 与数据库双向一致）→支持后端“捡漏”购买。

**设计要点与典型陷阱**：库存回流的原子性与幂等（取消消息重复投递不能重复回补——回补也要幂等键）；“已抢完”的判定要给回流留活口（显示“已抢完”但后台还有未支付单可能回流，前端文案与库存语义要对齐，这是经典的产品-技术口径问题）。

## 逐层过滤的容量推演

用教学量级假设（预约 100 万、开抢瞬间 50 万 QPS 商品页、下单点击约 100 万次、库存 1000 件、单机网关 1 万 QPS）推演每一层的进出流量（演算口径，非实测；完整全链路拆解以[06-第六阶段/02](../06-第六阶段/02-场景拆解-秒杀.md) 为准）：

| 层 | 进入 | 出口（假设口径） | 依据与手段 |
|---|---|---|---|
| CDN + 静态化 | 50 万 QPS 读 | ≈ 0 到达源站 | 商品页静态化后 CDN 就地消化，回源仅剩少量动态接口 |
| 网关粗限 | 100 万次点击（秒级集中） | 按全局容量放行（如 20 万 QPS 量级） | 10 节点 × 1~2 万 QPS；超出部分快速失败，保护后端 |
| 令牌校验 | 20 万 | ≈ 放 N 倍于库存（如 5000） | 令牌发放量=库存×倍数：倍数太小“真用户抢不到”，太大过滤不够 |
| 风控拦截 | 5000 | 扣除机器与黄牛（假设两成） | 规则+画像打分，可疑进验证码 |
| 缓存库存扣减 | ≈ 4000 | 成功 ≈ 1000（等于库存） | 分段 key 原子扣减，负数即回补拒绝 |
| 下单队列消费 | 1000 | 按数据库可承受速率建单 | 削峰：洪峰期间队列有积压，数据库平稳消费 |
| 数据库 | ≤ 1000 行级更新 | 1000 张订单 | 条件更新兜底，与缓存对账 |

这张表的教法：先只给学生第一行和最后一行——“50 万 QPS 进来、数据库只能接住 1000 单”，让他们自己设计中间的每一层并给数字，再对答案。误差不重要的层（风控拦截率）与必须精确的层（库存扣减）要区分对待。

## 关键数据表设计与取舍

| 表 | 取舍点 | 结论与理由 |
|---|---|---|
| `seckill_stocks` | 与普通库存共表还是分表 | 分表：活动库存生命周期与普通库存完全不同（活动结束即废弃），且写入热点隔离 |
| 库存真相在哪 | Redis 为准 vs 数据库为准 | 数据库为准、Redis 是高速前置：Redis 扣减只是“预过滤”，建单仍走数据库条件更新，活动结束以数据库对账收尾 |
| `participations` | 参与即留痕 vs 只有成功者留痕 | 留痕：限购判定需要“参与过”的事实；量级=点击数（百万级/活动），按活动分区、活动结束归档 |
| `seckill_results` | 结果实时算 vs 状态表 | 状态表：前端轮询的唯一依据，`(activity_id, user_id)` 唯一约束天然幂等 |
| 订单上的 `activity_id` | 复用普通订单表 | 加列不复用新表：秒杀订单走同一履约链路，特殊字段（活动、支付时限）以列区分 |

## 容量与失败模式的边界推演

- **回补的幂等**：取消消息重复投递是常态，回补动作必须带幂等键（订单号）——重复回补会把库存越补越多，出现“已抢完又复活”的资损（多卖）。
- **“已抢完”的活口**：前端显示“已抢完”时，后台还有未支付订单可能回流——文案与库存语义要对齐（“已抢完”≠“永远没有”，捡漏入口常驻）。
- **队列积压的用户体验**：百万点击在数十秒内排空，轮询间隔递增（1s→2s→5s）+ 排队位置提示，把“等待”从焦虑变成可感知的过程——客诉量主要由产品设计决定，但架构必须提供“位置”这个数据。

失败模式清单：

| 失败模式 | 触发 | 后果 | 预设对策 |
|---|---|---|---|
| 缓存扣减成功、建单失败 | 步⑥数据库库存已空 | 用户被“抢到”又落空 | 反向补偿：缓存加回 + 结果置失败 |
| 重复回补 | 取消消息重投 | 库存虚增、超卖 | 回补幂等键（订单号） |
| 消息丢失 | MQ 故障 | 排队中永远无结果 | 结果超时置失败 + 对账任务回收缓存计数 |
| 活动配置错误 | 价格/库存配错 | 资损 | 审批流 + 配置校验 + 开抢前预演 |
| 提前开闸 | 用户改本地时间 | 提前提交 | 服务端时间为准，前端倒计时仅展示 |
| 结束状态不一致 | 缓存与数据库不同步 | 活动结束后仍可下单 | 结束判定以数据库为准，缓存短过期 + 版本标记 |

## 演进：秒杀链路的搭建与下线

秒杀与普通交易的关系是“战时通道”——**上线要有迁移路径，活动后要有下线路径**（常被遗忘）：

| 阶段 | 动作 | 迁移方式 | 回滚/下线方式 |
|---|---|---|---|
| 1 复用交易链路 | 活动库存独立表，入口普通 | 无（起步） | — |
| 2 读侧静态化 | 商品页出缓存/CDN | 预热期灰度切流（先 1% 流量） | 切回动态渲染 |
| 3 限流与令牌 | 网关粗限 + 令牌层 | 按活动逐个启用规则 | 规则下线即回普通链路 |
| 4 异步下单 | 下单走队列 | 双路径并存（小活动同步、大活动异步），按活动选择 | 切回同步路径 |
| 5 活动收尾 | 库存对账、参与数据归档 | 活动结束自动触发对账任务 | —（对账差异人工处理后才允许清理） |

注意第 5 步：**活动结束不是终点**——缓存计数与数据库库存的对账、参与表的归档、未支付回流订单的最终处理，都是收尾清单项；没有收尾清单的秒杀系统，跑过三次活动后留下一地临时开关。

## 面试官追问点

- “为什么活动库存要与普通库存分开？”——写入热点隔离、生命周期不同、扣减语义不同（秒杀扣减可接受“缓存预扣+库兜底”的两级模型，普通销售不需要）。
- “令牌发放量设几倍合适？”——依据是“真实转化率”：倍数太小会误伤手慢的真用户，太大过滤不足；工程上宁可略大，因为库存扣减层还能兜住。
- “Redis 扣减成功但建单失败，算谁的？”——算系统的：必须反向补偿并给用户明确结果；宁可整体失败率略升，不能出现“告诉你抢到了又没有”。
- “队列消费速率怎么定？”——由数据库可承受的平稳写入速率倒推（洪峰持续时间可拉长，数据库不能被拖垮）；这正是“削峰填谷”四个字的定量版。
- “秒杀挂了，普通交易要不要一起陪葬？”——绝不要：入口隔离、资源隔离（独立网关分组/独立服务分组）是保命底线，秒杀故障的爆炸半径必须圈在活动内。

## 如果规模再大十倍

假设 1000 万预约、500 万 QPS 商品页、库存 1 万件：

- **静态化比率要更高**：动态接口（剩余库存数）降级为“有/无”两态或干脆隐藏——精确剩余数在洪峰期没有业务价值，只有技术成本。
- **库存分段更细 + 本地缓存预扣**：单 key 分段不够时，网关节点本地预扣配额（每节点分一段，本地内存扣减），Redis 只承担段间调拨——与发号器分段预取同一思想第三次出现。
- **多机房/多活**：500 万 QPS 单地域带宽与接入扛不住——按用户地域分机房开抢，库存总量预先按比例分配到机房（余量跨机房调拨是难点，宁可各机房少放）。
- **结果推送替代轮询**：千万级轮询本身就是读洪峰——长连接推送（IM 场景的通道复用）或边缘计算节点就近应答。
- **风控前置到客户端**：设备指纹与行为采集在端上初筛，服务端只做复核——对抗升级的标准走向（对应“风控是攻防对抗”的定性）。
