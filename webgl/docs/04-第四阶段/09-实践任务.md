# 实践任务

## 任务说明：交付物定义

本阶段实践任务的完成标准（全部勾掉才算完成）：

- [ ] 框架有名字，npm 包名可用且已占用
- [ ] `npm install <你的框架>` 在空项目可用，三行代码出图
- [ ] README 完整：一句话介绍、最小示例、API 概览、文档链接
- [ ] 在线示例站可访问：至少 6 个示例（对应 P1~P6），每个可交互
- [ ] 大纲实践任务条目勾选

三个子任务有依赖顺序：定名 -> 发布 -> 示例站（示例站引用已发布的包，或引用 monorepo 本地包）。

**时间预算**（按本阶段末尾一周的空闲时间排）：定名含占位发布 1 天（大头是筛选与纠结，不是操作）；发布 1~1.5 天（tsup/CI 配置在 08 册 7.4 已完成大半，本册的 checklist 是验收）；示例站 2~3 天（六个示例里 P1~P4 的代码本来就有，新写的是"套上三件套"的壳）。总计约一周——**示例站占一半以上**，排期时别把它当"顺便"。

预算超了的减法顺序也是预定的：先砍示例数量（六个砍到四个，砍 P5 蒙皮与 P6 glTF 里较难的那个——它们在第五、六阶段还有机会补）而不是砍每个示例的交互；再降 CI（先本地手动跑，workflow 后补）；**README 与"三行出图"永不砍**——它们是发布闭环的最小内核。

**为什么收官是这三件事**：第四阶段的主题是"工程化"，而工程化的终极检验是**换个视角看自己的代码**——定名逼你想清"它到底是什么"（一句话定位）；发布逼你站到使用者的角度（安装、引入、类型提示，全都从零开始体验一遍）；示例站逼你把"我以为很好用"变成"陌生人也能跑起来"。02~08 册写代码时你是作者，这三件事让你第一次当自己的用户——多数"设计得不顺手"的问题都是在这一刻暴露的。它与 [08-工程化](08-工程化.md) 7.4（打包发布）是同一件事的两面：7.4 讲配置怎么做，本册讲做完之后怎么验收。

顺带把心态摆正：学习型框架的发布不为获取用户（大概率没有），为的是**完成"代码 → 包 → 可引用依赖 → 在线可验证"的完整闭环**——这个闭环本身就是要练的工程能力，第五、六阶段的毕业项目会原样复用（框架以 npm 包/内部模块进入项目工程，示例站模式变成 Pages 发布的骨架）。

## 框架定名

### 命名的三个硬约束

1. **npm 唯一性**：`npm view <name> version` 返回 404 才可用；返回版本号说明被占。带 scope（`@yidafu/xxx`）永远可用，但传播性弱于裸名；
2. **可搜索性**：npm 搜索与 Google 里能搜到。太通用的名字（`gl`、`web`）会沉进结果海；生造词要先搜一遍有没有撞名项目（不只 npm，还有 GitHub）；
3. **可读性**：全小写、无空格（npm 规范），连字符分词不超过两段。`minigl`、`nano3d` 是合格形态；`MiniGL-Framework-js` 不合格。

### 命名策略对比

| 策略 | 例子 | 优点 | 缺点 |
|---|---|---|---|
| 迷你/学习前缀 | minigl、tinygl | 定位清晰，心智预期对（学习库） | 撞名率高（先查再定） |
| 造词 | regl、oasis | 独占性好，品牌感 | 需要解释成本 |
| 个人 scope | @yidafu/gl | 零撞名 | 用户记忆与输入成本高 |
| 功能描述 | mini-scene-graph | SEO 好 | 名字长，功能变了名字就错 |

建议路径：先列 5 个候选 -> 逐个 `npm view` 与 GitHub 搜索过滤 -> 前 3 个给同事/朋友 10 秒记忆测试（念一遍，隔一天还能拼出来吗）-> 定名。**定名后立刻发布 0.1.0 占位**（哪怕 API 还在动），防止想好的名字被人截胡。

### 候选从哪来

列不出 5 个候选时，用四个生成方向凑齐再筛：

1. **缩写法**：项目全称的首字母组合再元音化（"mini scene graph renderer" → msgr → misger → 不行，换方向）；
2. **隐喻法**：框架像什么？搭建用的（brick/beam/strut）、会画画的（brush/pigment）、小的生物（ant/bee）——隐喻名自带记忆钩子（regl 是 "REgular GL"、oasis 是绿洲）；
3. **组合法**：核心概念 + 前后缀（gl-/3d/web- + 你的特色词），注意避开已有知名项目的组合空间；
4. **致敬改造法**：从致敬对象出发改一个音节（three → four？不行，这是反例——太贴近会被当山寨）。命名空间里"像但不一样"是最差的位置：要么完全无关联，要么就是致敬到让人一眼看出出处。

筛的时候心里放一杆秤：**名字是承诺**——叫 minigl 就不能长成全家桶，叫 scene-graph 就不该塞进 PBR 渲染器。名字与野心的错位，将来会变成 README 里尴尬的"不是什么"声明。

**给纠结者的最后一条心理建设**：名字对学习型项目的重要性被普遍高估——它影响的是"第一眼的好感"，而你的示例站、README 与笔记链接才是真正被反复消费的东西。生态里既有名字起得随性但活得很好的库，也有名字精巧但无人问津的项目。把命名当三天纠结的事，不如把它当一小时的决策 + 后续用质量赎回——这也是"工程化"视角的答案：**发布得早、迭代得名正言顺，好过为完美名字延迟一切**。

### 定名 checklist

- [ ] `npm view <name> version` 404
- [ ] GitHub 搜索无同名活跃项目
- [ ] 无商标冲突（避免 WebGL/Three 等既有品牌的近似变体）
- [ ] 域名/仓库路径可用（github.com/<you>/<name>）
- [ ] 10 秒记忆测试通过

**定名之后的全仓改名**：名字定晚了的代价是改名——包名、仓库名、README 标题、import 语句、示例里的 alias，五处联动。改法：一次全局搜索替换（对旧名零散出现有奇效），替换完 `npm run test` + 六个示例各点一遍；仓库改名在 GitHub Settings 里做（旧 URL 自动重定向，但 Pages 地址会变——示例站 base 与 README 链接要跟着改）。**结论藏在这里：定名要早**——占位 0.1.0 发得越早，后来改名的成本越低为零。

**定名的时间盒**：一整天。命名是典型的"收益递减"决策——前两小时的候选质量与第八小时没有差别，差别只在焦虑水平。时间盒到了就在候选里挑一个过了 checklist 的，把纠结写进周记（"最后在 A 与 B 之间选了 A，因为……"），往前走。

## 发布 checklist

### 仓库侧（发布前置）

- [ ] `package.json`：name、version、description、keywords（`webgl`、`3d`、`scene-graph`、`typescript`）、license、repository、author 全部填真值——npm 搜索页与图谱抓的是这些字段
- [ ] `LICENSE` 文件（MIT 全文 + 你的名字与年份）
- [ ] `README.md`：一句话定位 -> 安装 -> 最小可运行示例（10 行内）-> API 概览表 -> 在线示例站链接。README 首屏决定留存，示例代码必须真的能跑
- [ ] `CHANGELOG.md`：Keep a Changelog 格式，0.1.0 首条记录
- [ ] `.npmignore` 或 `files: ["dist"]` 生效；源码与示例不进包
- [ ] CI（GitHub Actions）：push 跑 `vitest` + `tsup`，main 分支绿
- [ ] `prepublishOnly` 钩子就位（08 册 7.4.2）

### 发布执行

- [ ] `npm run test` 全绿
- [ ] `npm run build` 产出 dist（esm/cjs/d.ts/sourcemap）
- [ ] `npm pack` 预览：`tar -tzf *.tgz` 只有 dist + README + LICENSE + package.json；体积记录在案
- [ ] 空项目冒烟：`npm i <name>` + 三行代码出三角形（08 册 7.4.3 的下游视角验证）
- [ ] `npm version 0.1.0`（打 git tag）
- [ ] `npm publish --access public`（scope 包首次必带）
- [ ] 发布后 30 分钟内到 npmjs.com 检查页面渲染（README 图片、关键字）
- [ ] `git push --follow-tags` 推 tag

### npm pack 审计：发布前的白盒检查

`npm pack` 产出的 tgz 是你与用户之间唯一的界面，值得逐项审一遍而不是只看总体积：

| 审计项 | 怎么查 | 常见问题 |
|---|---|---|
| 文件清单 | `tar -tzf *.tgz` | 源码/src、示例、测试快照混进包（`files` 白名单没生效）；`.` 开头的杂文件（.DS_Store） |
| 类型声明 | dist 里 .d.ts 与 .d.ts.map 齐全 | 忘了打 d.ts，用户侧所有类型变 any |
| 双格式 | dist 里有 esm 与 cjs 两个入口 | 只发 esm，老工具链 import 报错 |
| sourcemap | .map 文件与 js 同目录 | 缺失时用户报错栈定位到压缩后代码 |
| package.json 元数据 | 解包后 cat 一遍 | `main`/`module`/`types`/`exports` 指错路径（本地测试用的是源码 alias，包里路径对不上） |

最后一项最阴险：本地开发走 alias 直接引 src，一切正常；包里的 `exports` 字段写错一个字母，只有用户才会踩到——**空项目冒烟（发布执行第 4 条）必须真的从 npm 安装**，`npm link` 或 alias 方式都测不出这个问题。

### 版本与变更纪律

0.x 阶段（semver 语义：0.x 的 minor 可以破坏兼容）也要有纪律，否则 CHANGELOG 会烂掉：

1. **每次 publish 必有 CHANGELOG 条目**——哪怕是"内部重构，无 API 变化"一句；断更一次就会永远断更；
2. **破坏性变更三件套**：minor 版本号 +1、CHANGELOG 标 Breaking、旧 API 留一个废弃版本周期（控制台 warn 指向新 API）——学习型框架用户只有你自己与未来的你，但"未来的你"三个月后回来，warn 比翻 git log 快十倍；
3. **1.0.0 的含义提前想好**：对学习型框架，建议把 1.0.0 留给第六阶段毕业项目结束时（v1.0.0 tag 正是里程碑计划的 M4 交付物之一）——它标记"经过完整项目验证"，不是"功能够了"。

### 发布演练：从 pack 到 install 的全链路

checklist 是静态的，这里给一条**动态走查脚本**（发布日当天从上到下执行一遍，每步的"预期"就是对不对的判据）：

```bash
# 1. 干净构建（先删 dist，防止旧产物混入）
rm -rf dist && npm run build && npm run test

# 2. 打包预览（审文件清单与体积，对照 npm pack 审计表）
npm pack && tar -tzf *.tgz

# 3. 空项目冒烟（关键：必须是真安装，不是 link）
mkdir /tmp/smoke && cd /tmp/smoke && npm init -y
npm i <你的包的绝对路径>/minigl-0.1.0.tz   # 直接装 tgz，连 registry 都不需要
node -e "import('minigl').then(m => console.log(Object.keys(m)))"

# 4. 三行出图：在 smoke 里起 vite，贴 README 的最小示例，浏览器出三角形
# 5. 全过 -> 回主仓 npm version 0.1.0 && npm publish --access public
```

第 3 步直接安装本地 tgz 有个额外好处：**不占用 npm 的版本号**——演练发现问题（比如 exports 路径错）可以反复修反复装，直到全链路绿了才真 publish。npm 上没有"撤回重发"（同版本号删除后也不能复用），把第一次 publish 留给确定能跑的包。

### README 最小结构模板

```markdown
# minigl

> 一个用于学习的迷你 WebGL 3D 框架：场景图 + 状态托管渲染器 + 材质系统 + glTF 加载。

[在线示例](https://<you>.github.io/minigl/) | [文档](./docs) | MIT

## 安装
npm i minigl

## 三行出图
（最小示例：Renderer + PerspectiveCamera + Mesh，一张截图）

## 特性
- 场景图与脏标记更新（见 docs/03-场景图.md）
- GL 状态缓存机（见 docs/02-框架总体架构.md）
- ...（每条链到对应学习笔记——学习型库的差异化就在这里）

## 不是什么
- 不是 three.js 替代品：面向学习，性能与功能完整性让位于可读性
```

"是什么"之外写清"**不是什么**"，学习型库的 README 这是关键一节——它替你挡掉"为什么没有 X"的 issue。

模板逐段的分工（照抄结构前先懂每段在干什么，改起来才有分寸）：

| 段 | 服务的读者问题 | 失败形态 |
|---|---|---|
| 一句话 + 徽章行 | "这是什么、值不值得看" | 写成功能清单（没有人读完） |
| 安装 + 三行出图 | "五分钟内能不能跑起来" | 示例超过 10 行或依赖隐藏步骤 |
| 特性（带文档链接） | "有我没有的东西吗" | 特性与笔记脱节，链接 404 |
| 不是什么 | "我该不该用" | 缺席——将来被迫在 issue 里解释 |

## 示例站搭建指引

### 技术选型：vite 多入口 + 本地包引用

示例站的诉求：每个示例一个页面（独立 JS 入口）、共享导航首页、引用框架源码（改库即时生效）、静态产物可托管。vite 多页应用（MPA）天然匹配：

```text
minigl/                      # 框架仓库根（monorepo 化）
  src/                       # 框架源码（02~08 册的产物）
  examples/
    index.html               # 示例导航首页
    01-state-cache/          # P1：状态缓存对比
      index.html
      main.ts
    02-scene-graph/          # P2：脏标记性能对比
    03-uber-shader/          # P3：宏变体
    04-picking/              # P4：拾取与事件冒泡
    05-skinning/             # P5：动画混合与蒙皮
    06-gltf-viewer/          # P6：glTF 加载器
  vite.examples.config.ts
```

```typescript
// vite.examples.config.ts —— 多入口构建 + 源码级引用（示例改动即热更，无发布依赖）
import { defineConfig } from "vite";
import { resolve } from "node:path";
import { readdirSync } from "node:fs";

const examples = readdirSync(resolve(__dirname, "examples"))
  .filter((name) => /^\d/.test(name)); // 01-xxx 形式的目录

export default defineConfig({
  // 示例直接 import 框架源码：改 src 即时生效，示例站永远与源码同步
  resolve: { alias: { minigl: resolve(__dirname, "src/index.ts") } },
  build: {
    outDir: "dist-examples",
    rollupOptions: {
      input: Object.fromEntries(
        examples.map((name) => [
          name, resolve(__dirname, `examples/${name}/index.html`),
        ]),
      ),
    },
  },
  base: "/minigl/",   // GitHub Pages 的仓库名子路径，漏配则资源 404
});
```

alias 引源码而非发版包：示例站永远演示"当前源码"，发布前后不会出现"示例与包行为不一致"。若仓库不是 monorepo、示例要引用已发布版本，则去掉 alias 直接 `import { Renderer } from "minigl"`。

**为什么多入口而不是单页路由**（SPA + 路由切换 demo）：三个理由都在维护侧——其一，示例互相隔离，一个 demo 崩了不影响其他页（学习期代码经常崩）；其二，按需加载天然成立，打开 hello-triangle 不会加载 gltf-viewer 的解析器；其三，每个示例的 URL 天然稳定可分享（`/06-gltf-viewer/` 直接发给别人验收）。SPA 的优势（切换快、状态保持）对低频切换的示例站毫无价值——选型时"对手的优势在你的场景不重要"是最省心的否决理由。

**参照工程**：本仓库 webgl 站的 `examples/` 就是这套模式的完整落地——vite 多页入口 + `src/common/` 公共层（gl/math/geometry/controls 四个模块，来自各分册的提炼）+ 每示例一个目录（index.html + main.ts，按需拆辅助 ts）。它从第一阶段的 hello-triangle 一路递进到第五阶段的 frustum-culling 十余个示例，结构没有变过——**"示例目录结构要不要随项目演进"这个问题，它用一年以上的稳定回答了**。它的 README 还做对了一件事：示例清单表格里每一行都链到对应分册（分册路径可反查），双向可导航。

照着参照工程再抄三条隐性约定，能省掉自己踩坑：

1. **公共层只放"被三个以上示例用到"的东西**——两个示例共用先忍着（复制），第三个出现时再提取（提取的时机由重复度决定，不是预见）；`src/common/` 的四个模块都是这么长出来的；
2. **每个 main.ts 顶部注释标注对应分册**（"对应分册：《05-第五阶段/08-基于图像的光照.md》"）——示例多了以后这是最快的反查路径，比翻 README 表格快；
3. **示例编号与学习阶段对齐而不是严格连续**——01~06 对应第四阶段的 P1~P6，后面 07~13 是第五阶段的递进；编号即阅读次序，新示例插中间会破坏编号语义（所以宁可追加不插入）。

### 导航首页：示例站的门面

`examples/index.html` 是所有访客的落地页，做对的要点（参照工程同款）：**清单表格三列**——示例名（链接）、对应分册（链接）、一句话"演示什么"（要写现象不写技术名词："空格开关环境光对比"好过"IBL 合成"）；**零 JS**——纯 HTML + 内联样式即可，导航页不需要框架与构建逻辑（它坏了整个站就"看起来"坏了）；**移动端可读**——表格加个横向滚动容器，手机上打开至少能看清清单。导航页十分钟做完，但它决定了示例站"是个作品还是一堆文件"。

### 部署：GitHub Pages

```yaml
# .github/workflows/deploy-examples.yml
name: deploy-examples
on:
  push: { branches: [main] }
permissions: { pages: write, id-token: write }
jobs:
  build-deploy:
    runs-on: ubuntu-latest
    steps:
      - uses: actions/checkout@v4
      - uses: actions/setup-node@v4
        with: { node-version: 20 }
      - run: npm ci && npm run build:examples
      - uses: actions/configure-pages@v5
      - uses: actions/upload-pages-artifact@v3
        with: { path: dist-examples }
      - uses: actions/deploy-pages@v4
```

仓库 Settings -> Pages -> Source 选 GitHub Actions 即可。每次 push main 自动更新示例站——示例站从此变成 7.3 节说的"浏览器端集成测试"：发布前人肉过一遍六个示例，等于最小的回归测试套件。

部署初期的两个配置项别漏：`permissions` 块（pages write + id-token write，缺了 deploy 步骤会因权限被拒）与 Settings → Pages 的 Source 必须选 **GitHub Actions**（默认是分支模式，不切过去 workflow 会一直等一个不存在的 gh-pages 分支）——这两项占"第一次部署失败"原因的大多数。

这套 workflow 也是第六阶段毕业项目发布（[05-毕业项目-里程碑计划](../06-第六阶段/05-毕业项目-里程碑计划.md) 3.8）的模板——`path` 与构建命令一改就是毕业项目的发布链路。在这里跑通一次，毕业项目周三的"丑但在线"预演就是十分钟的事而不是两小时的排查。

### 示例编写规范（每条对应一个实践任务的验收）

| 示例 | 验收标准 | 演示的知识点 |
|---|---|---|
| 01-state-cache | 页面显示 savedCalls/帧 与总状态调用/帧 两个数字，开关缓存可对比 | 02 册 1.2 |
| 02-scene-graph | 1000+ 节点树，脏标记开关切换，帧耗时实时曲线 | 03 册 2.2 |
| 03-uber-shader | 同一模型切换 USE_MAP/USE_SKINNING，页面上显示 `programCache.size` | 04 册 3.4 |
| 04-picking | 悬停高亮、点击事件冒泡到父节点（父节点计数器 +1） | 05 册 4.4 |
| 05-skinning | idle/walk 键切换 0.5s crossfade | 06 册 5.2/5.3 |
| 06-gltf-viewer | 加载 .gltf（层级 + 贴图 + 蒙皮），控制台零报错 | 07 册 6.3 |

每个示例三件套：可交互的开关（证明行为可变）、数字/曲线（证明性能可测）、对应学习笔记链接（站与笔记互链）。没有交互与数字的示例只是截图，起不到回归验证作用。

三件套再展开一层——**什么样的开关与数字才算数**：

- **开关要翻转到"坏的另一面"**：01 号示例的价值在于关掉缓存后 watched 数字飙升的对比；开关只有一档（开了就再关不掉）等于没有。设计时问自己：这个开关关掉后，用户会看到什么变差？说不出"变差什么"的开关是装饰；
- **数字要能解释因果**：帧耗时曲线旁要有节点数标签（1000 节点 @ 60fps），否则曲线只是装饰。理想状态是数字之间能做除法（总调用/节省调用 = 缓存命中率）；
- **链接要落在具体小节**：链到分册首页让读者自己找，多半找不到；直接 `03-场景图.md#22-脏标记优化` 锚到小节（站内 markdown 锚点由标题自动生成）。

**HUD 与交互约定**：示例的键位/按钮说明统一放在页面左上角的固定 HUD（一段绝对定位的 DOM），格式"键名 + 一句作用"——参照工程里 09-pbr-ibl（空格开关环境光）、11-gpu-timer（↑/↓ 调负载）、12-csm（`[`/`]` 调分割、S/B/C 观察调试视图）、13-frustum-culling（V/F 线框与幽灵体）都是这个约定。统一位置与格式的收益是**验收者零学习成本**：任何人打开任何示例，眼睛先看左上角就知道能按什么。交互还要求**键位冲突自检**——两个示例共用的键（比如空格）在同一示例里只允许一个含义。

**示例即测试：回归的三层**。示例站的回归价值分三层，了解层次才能在时间紧时砍对地方：第一层（CI 已覆盖）——`tsc` 类型检查与 vitest 单测，push 即跑，守住纯逻辑；第二层（示例站提供）——六个示例"能打开、不报错、数字合理"，人肉五分钟，守住集成路径（GL 初始化、资源加载、装配）；第三层（可选）——用 Playwright 之类把第二层自动化成"打开示例 → 断言 canvas 非全黑"的冒烟脚本。本阶段做完前两层即可，第三层知道存在就行——第六阶段如果示例数继续增长，它才是划算的投资。

### 单个示例的内部结构约定

一个示例目录长什么样（以参照工程的复杂示例为模板），按"代码量超过单文件可读阈值就拆"的原则分层：

| 文件 | 职责 | 拆分时机 |
|---|---|---|
| `index.html` | canvas + HUD + 内联样式，一屏以内 | 永远不拆 |
| `main.ts` | 装配：建 GL、组场景、主循环 | 超过 300 行就开始拆 |
| `shaders.ts`（可选） | 模板字符串的 GLSL | 出现第三段着色器时从 main 拆出 |
| 辅助模块（可选，如 `ibl.ts`、`raycast.ts`） | 独立可讲的子系统 | 该 subsystem 有自己的初始化管线时 |

两条内部纪律：**main.ts 只做装配**——它读起来应当是"第一步建天空、第二步生成资产、第三步组装场景"的叙事，任何超过二十行的算法块都值得出去单独成文件；**着色器永远进 ts 模板字符串**而不是独立 .glsl 文件——后者需要额外的构建插件，且失去类型工具的跳转与重命名支持（参照工程所有示例都是 `/* glsl */` 模板字符串）。

### 示例站的验收清单（发布日自查）

对照跑一遍，全部打勾示例站才算交付（不是"部署成功"就算）：

- [ ] 六个示例每个打开都无控制台报错（P6 的 glTF 加载走真实网络路径，不是内联数据）；
- [ ] 每个示例的三件套齐全：开关能动、数字在变、笔记链接可达；
- [ ] HUD 键位逐个按过一遍，行为与说明一致；
- [ ] 手机浏览器打开导航页与至少一个示例可看（布局不崩即可）；
- [ ] 导航页表格里的分册链接全部可达（相对路径在 Pages 子路径下正确）；
- [ ] 从 CI 绿到 Pages 更新的全链路走过一次（push 一个小改动，几分钟后线上可见）；
- [ ] 示例在浏览器缩放 200% 与一半窗口宽度下不崩（布局烂可接受，画布冻结不可接受）；
- [ ] 冷加载二次（禁缓存）首开正常——dpr/resize 的初始化时序问题常只在冷启动暴露。

最后一条常被跳过但它最重要——**"部署流水线通"和"部署流水线看起来通"是两回事**，只有亲眼看着自己最新的 push 出现在线上，发布链路才算验收完毕（这条经验在第六阶段毕业项目的 W3 周三"丑但在线"预演会再兑一次）。

### 常见坑

1. **`base` 路径漏配**：本地开发正常，Pages 上白屏——资源全部 404（请求了 `/assets/...` 而非 `/minigl/assets/...`）。
2. **示例资源（.gltf/.png）被构建器转 base64**：小于 4KB 的资产 vite 默认内联，模型文件解析路径测试意义就没了；示例目录配 `assetsInlineLimit: 0` 保持真实网络加载（这正是 07 册加载队列要验证的路径）。
3. **跨域贴图污染 canvas**：示例贴图走 CDN 时 `crossOrigin = "anonymous"`（6.1.3 已处理），否则 texImage2D 抛 SecurityError。
4. **示例站成了唯一文档**：示例要链回笔记、笔记要链向示例，单向链接的最终形态是没人能找到另一头。
5. **示例间复制公共代码**：第二个示例开始就想把相机/几何生成器复制过去——忍住，提到 `src/common/`（或框架内）。复制会在第五阶段演示"同一份 OrbitControls 的六个版本行为各不相同"。
6. **dist-examples 混进 npm 包**：`files: ["dist"]` 白名单只写了主包 dist，但 `.npmignore` 方案下 examples 的构建产物可能漏网——发布前 `npm pack` 审计（本册发布节）照做一遍。
7. **示例"能看不能动"**：写完忘了接交互（开关/键位），或交互只在桌面鼠标下有效——按三件套自查，交互缺失的示例按未完成计。
8. **README 的"三行出图"依赖隐藏步骤**：示例代码里用了别名导入或没写的配置（"先建一个 vite 项目"这类前置没交代）——空项目冒烟时照着 README 逐字敲一遍，敲不出来就是README 错了，改文档而不是怪用户。
9. **占位包发了空壳**：0.1.0 占位发布时 tgz 里只有 README——占位也要保证 `npm i` 不报错（至少导出一个空的 entry），否则"名字占上了、包是坏的"，比不占更伤。

## 阶段收尾：自查与衔接

发布完成后，回 01-导览的"阶段自测"过一遍 15 题——答不出的题号就是回炉的分册。然后两件事：

1. 把大纲第四阶段（含实践任务）全部条目勾成 `[x]`；
2. 预读第五阶段第一项（shadow map）：你的分层架构里，阴影贴片的深度 pass 应该放在渲染层的哪个位置？多 pass 渲染对渲染队列设计提出什么新要求？——带着问题进入下一阶段，第六阶段对标 three.js 源码时你会反复用到这四周搭起来的骨架。

收尾还建议留半小时做一件小事：**把示例站的六个 URL 发给一个没读过本系列的朋友，只说"帮我看看能不能打开"**——五分钟的外部视角会暴露你自己永远注意不到的问题（哪个示例打开就报错、哪个交互不知道怎么触发）。这半小时是"工程化"主题最后一块拼图：开发者与用户之间隔着的那堵墙，只有真的翻过去一次才知道在哪里。

**发布后第一周的维护姿势**（学习型项目同样适用，成本极低）：CI 保持绿（黄了当天看，多半是依赖小版本变动）；npm 周下载量不用看（没有用户很正常），但 **npmjs.com 的包页面每周扫一眼**——确认 README 渲染正常、没有意外的依赖告警；示例站随每次 push 自动更新，自己隔几天点一遍六个示例（它们就是 7.3 节说的回归套件）。三件事合计每周十分钟——维护的意义不在"有用户要伺候"，在于**交付物持续处于可用状态**这个习惯本身，毕业项目与将来的开源参与都吃这个习惯的红利。

> 阶段结论一句话：**框架 = 分层 + 托管 + 工程**。分层决定改动波及面（02/03/04），托管决定用户心智负担（状态/资源/生命周期），工程决定别人敢不敢用（类型/测试/发布）。三件事都立住了，第五、六阶段的进阶渲染与源码对标才有地方落。
