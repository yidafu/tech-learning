# 2. 场景图（Scene Graph）

## 2.1 父子变换链与 worldMatrix 更新

### 2.1.1 设计动机：为什么需要一棵树

没有场景图时，"车轮跟着车身转、车身跟着底盘走"要靠手写每一级的矩阵乘法，物体一多就是灾难。场景图（Scene Graph）用**组合模式（Composite Pattern）**把变换关系建成树：每个节点只保存"相对父节点"的局部变换（local matrix），世界变换（world matrix，记作 matrixWorld）按链路自根向下合成：

```text
matrixWorld(子) = matrixWorld(父) × localMatrix(子)
```

这行乘法就是场景图的全部灵魂：**局部坐标系一层层嵌套**——车轮在"车身坐标系"里只管转，车身在"世界坐标系"里开多远，车轮的世界矩阵自动跟上。

局部矩阵由平移（translation）、旋转（rotation，用四元数 quaternion 存）、缩放（scale）三要素合成（compose）：

```text
localMatrix = T(position) × R(quaternion) × S(scale)
```

顺序固定为 T·R·S 的原因：先缩放（沿自身轴）、再旋转（绕自身原点）、最后平移，任何其他顺序都会让"绕自身转 + 挪位置"产生耦合项。矩阵乘法不可交换，这个顺序是"模型变换直觉"的数学化。

### 2.1.2 方案对比：矩阵怎么存

| 方案 | 节点存什么 | 改 position 后 | 适用 |
|---|---|---|---|
| 只存 localMatrix 一个 4×4 | 16 个浮点数 | 手工改矩阵第 12~14 列，旋转缩放难独立调 | 极端省内存，不好用 |
| 只存 TRS 三要素 | 9~10 个数 | 更新三要素，localMatrix 每次按需 compose | 状态少，但矩阵读取频繁时重复计算 |
| TRS + 缓存 localMatrix（本方案） | TRS + matrix + 脏标记 | 改三要素只标脏，用到才重算 | 读写都便宜，多 16 个浮点的内存 |

第三方案是"缓存换计算"的最小实践，也正好为 2.2 的脏标记铺路。

### 2.1.3 完整核心代码：Node3D 与 worldMatrix 合成

```typescript
// scene/Node3D.ts —— 场景图节点：变换链 + 层级管理
import { Vec3 } from "../math/Vec3";
import { Quaternion } from "../math/Quaternion";
import { Mat4 } from "../math/Mat4";

export class Node3D {
  readonly position = new Vec3(0, 0, 0);
  readonly quaternion = new Quaternion(0, 0, 0, 1); // 单位四元数
  readonly scale = new Vec3(1, 1, 1);

  /** 缓存的局部矩阵，仅在 matrixNeedsUpdate 时重算 */
  matrix = new Mat4();
  /** 世界矩阵，由 updateMatrixWorld 维护 */
  matrixWorld = new Mat4();

  matrixAutoUpdate = true;
  /** 局部矩阵脏标记 */
  protected matrixNeedsUpdate = true;
  /** 世界矩阵脏标记 */
  protected matrixWorldNeedsUpdate = true;

  parent: Node3D | null = null;
  readonly children: Node3D[] = [];
  readonly name: string;

  constructor(name = "") {
    this.name = name;
    // 监听三要素变化自动标脏（Vec3/Quaternion 内部 onChanged 回调，
    // minmath 第三阶段已实现；直接赋新对象也要触发，故用 setter 包装亦可）
    this.position.onChanged(() => (this.matrixNeedsUpdate = true));
    this.quaternion.onChanged(() => (this.matrixNeedsUpdate = true));
    this.scale.onChanged(() => (this.matrixNeedsUpdate = true));
  }

  // ---------- 层级管理：所有结构变更都顺带标脏 world ----------
  add(child: Node3D): this {
    if (child.parent !== null) child.parent.remove(child);
    child.parent = this;
    this.children.push(child);
    child.matrixWorldNeedsUpdate = true; // 换了父，世界矩阵必变
    return this;
  }

  remove(child: Node3D): this {
    const i = this.children.indexOf(child);
    if (i >= 0) this.children.splice(i, 1);
    child.parent = null;
    return this;
  }

  traverse(fn: (node: Node3D) => void): void {
    fn(this);
    for (const child of this.children) child.traverse(fn);
  }

  // ---------- 变换链：局部合成 + 自上而下传播 ----------
  /** 重算局部矩阵：T × R × S */
  updateMatrix(): void {
    Mat4.compose(this.matrix, this.position, this.quaternion, this.scale);
    this.matrixNeedsUpdate = false;
    this.matrixWorldNeedsUpdate = true;
  }

  /** 自上而下更新世界矩阵；force 表示"父链已变，本节点必须重算" */
  updateMatrixWorld(force = false): void {
    if (this.matrixAutoUpdate && this.matrixNeedsUpdate) this.updateMatrix();

    if (this.matrixWorldNeedsUpdate || force) {
      if (this.parent === null) {
        Mat4.copy(this.matrixWorld, this.matrix);
      } else {
        // 世界 = 父世界 × 局部（列主序下右乘）
        Mat4.multiply(this.matrixWorld, this.parent.matrixWorld, this.matrix);
      }
      // 本节点世界变了，整棵子树的世界都必须跟着重算
      this.matrixWorldNeedsUpdate = false;
      force = true;
    }

    for (const child of this.children) child.updateMatrixWorld(force);
  }

  /** 便捷方法：局部 -> 世界点变换（拾取、挂点用） */
  localToWorld(out: Vec3, point: Vec3): Vec3 {
    return Vec3.transformMat4(out, point, this.matrixWorld);
  }
}
```

两个关键设计决策要展开讲：

**为什么更新必须自上而下（先父后子）**：子节点的世界矩阵依赖父节点的**新**世界矩阵。如果自下而上更新，父节点这帧还没算完，子节点拿到的是上一帧的父矩阵——整棵树滞后一帧，动画上表现为"子物体拖着残影"。`updateMatrixWorld` 的递归结构天然保证了"算我之前，我的 parent 一定已算完"。

**为什么子树要 force 传播**：节点 P 的世界矩阵变了，P 的所有后代的世界矩阵**全部**失效——即使它们局部没动。所以 `force = true` 一路传下去。初学者常在这省事：只重算 P 不传播，结果"车轮不跟车身"。反过来，**P 的祖先变了也必须能传到 P**，这靠的不是遍历方向（我们只有自根向下的入口），而是"根到 P 的路径上某个祖先会 matrixWorldNeedsUpdate 或 force"——由于更新从根（Scene）开始，祖先重算时 force 传到 P，正确闭环。

### 2.1.4 常见坑

1. **改了 position 画面不动**。忘了每帧调 `scene.updateMatrixWorld()`，或节点 `matrixAutoUpdate` 被误设 false。前者的征兆是"第一帧对、之后全静止"。
2. **缩放非均匀 + 旋转，法线出错**。本节只处理顶点矩阵；法线要用法线矩阵（normal matrix，模型矩阵左上 3×3 的逆转置），在 04 册材质内置 uniform 里处理，此处埋个钩子。
3. **行列主序想混**。`Mat4.multiply(out, a, b)` 按"列主序、out = a × b"约定（与 `uniformMatrix4fv` 对接），读别人代码先确认约定，第一阶段的痛不要在框架里重演。
4. **用欧拉角存 rotation 再转四元数**。暴露欧拉角 API 可以（用户友好），内部一律四元数，转换发生在 setter。两套并存迟早出现"改了 euler 没同步 quat"的 bug。

## 2.2 脏标记优化：什么操作标脏、updateMatrixWorld 怎么剪枝

### 2.2.1 设计动机：1000 个节点不必每帧算 1000 次矩阵乘法

静态场景（建筑模型）里，绝大多数节点整帧不动，但"每帧全量重算 worldMatrix"会照样做 1000 次 4×4 乘法。脏标记（Dirty Flag）模式的核心：**修改时只立一个旗子"我变了"，读取/使用时检查旗子决定是否重算，没立旗的直接跳过**。把计算从"写多读少"的时机挪到"必读"的时机，且能剪掉整棵干净子树。

### 2.2.2 方案对比

| 方案 | 每帧成本（N 节点、D 个脏节点） | 额外复杂度 |
|---|---|---|
| 每帧全量重算 | N 次 compose + N 次乘法 | 无 |
| 版本号失效（每节点 version，子记父 version） | D 次重算 + 全树遍历比较 | 中，调试直观 |
| 双脏标记（本方案，同 three.js） | D 所在路径重算，干净子树整枝剪掉 | 低，两个字段 |

双脏标记即 2.1.3 的 `matrixNeedsUpdate`（局部）+ `matrixWorldNeedsUpdate`（世界）：局部脏触发局部重算并连带标世界脏；世界脏触发世界重算并 force 子树。剪枝发生在两处：

- **节点级**：`matrixNeedsUpdate` 为假时跳过 `compose`。
- **子树级**：本节点世界矩阵干净且无 force 时，**整棵子树的递归仍然进入但不重算**——注意代码里 `for` 循环总会执行，子节点收到 `force=false` 且自身不脏时只做一次布尔判断就返回。整枝剪掉的其实是最贵的"矩阵乘法"，遍历本身（每次几条比较指令）保留。

版本号方案更适合"多渲染器/多消费者各自订阅"的场景，迷你框架用不着，知道有这个选项即可。

### 2.2.3 什么操作必须标脏（清单）

漏标任何一条都会产生"偶发不更新"的诡异 bug——这类 bug 的特征是"动一下别的物体，它突然又对了"：

| 操作 | 需要的标脏 | 原因 |
|---|---|---|
| 修改 position / quaternion / scale | matrixNeedsUpdate（经 onChanged 自动） | 局部矩阵失效 |
| 直接改 matrix（比如从 glTF 读 node.matrix） | matrixWorldNeedsUpdate + matrixNeedsUpdate=false | 局部矩阵已是权威值，只有世界失效 |
| add / remove / 换 parent | 子节点 matrixWorldNeedsUpdate | 父链变了 |
| parent 的世界矩阵重算 | force 向下传播（代码内自动） | 子树世界全部失效 |
| 手动设 matrixAutoUpdate=false | 无自动标脏，用户全权负责 | "你要静态，我信你" |

### 2.2.4 验证剪枝收益（P2 实践任务）

```typescript
let multiplyCount = 0;
// 临时包一层计数（也可给 Mat4.multiply 加静态计数开关）
const scene = buildTree(depth: 10, fanout: 2); // 1023 个节点

scene.updateMatrixWorld(true); // 首帧强制全量：multiplyCount ≈ 1023
multiplyCount = 0;
scene.updateMatrixWorld();     // 无任何修改：multiplyCount === 0
scene.children[0]!.position.x += 1;
multiplyCount = 0;
scene.updateMatrixWorld();     // 只有第一子树重算：约 511 次
```

期望结果：不动时零乘法、动一个枝时只付该枝的代价。如果你的实现"不动时也在乘"，回去查是不是把 `force` 写成了无条件 true。

### 2.2.5 常见坑

1. **onChanged 忘了覆盖"间接修改"**。`node.position.x = 1` 走 Vec3 的 setter 链能触发回调；但 `node.position.set(1,2,3)` 若绕过 setter 直接写字段就断链。minmath 的约定必须统一：一切修改走会触发回调的方法。
2. **matrixNeedsUpdate 与 matrixWorldNeedsUpdate 混用**。只标局部脏、忘了在 `updateMatrix` 里连带标世界脏（代码里是 `this.matrixWorldNeedsUpdate = true`），出现"局部变了世界没变"。
3. **透明物体排序依赖的 worldMatrix 在排序后才更新**。渲染主流程的顺序铁律：先 `updateMatrixWorld`，再收集与排序，最后 draw。顺序反了，排序用的是上一帧的位置，透明物体前后穿插错一帧。

## 2.3 渲染队列：不透明先渲染、透明按距离排序

### 2.3.1 设计动机：为什么不能"树的顺序"直接画

`updateMatrixWorld` 后按遍历顺序直接画，有两个独立的问题：

1. **性能**：遍历顺序 = 场景组织顺序，同材质物体被随机穿插。相邻两次绘制若材质不同，就要换 program、换纹理、改状态——第二阶段已知道状态切换是大头开销。**按材质分簇**能把状态切换次数从"物体数"降到"材质数"。
2. **正确性**：透明物体依赖混合（blend）,"后画的叠在先画的上面"。必须按**由远到近**（back-to-front）画透明物体；不透明物体则相反，**由近到远**画能吃满提前深度测试（early-z rejection）的收益——近处物体先写深度，远处被遮挡的片元直接被深度测试裁掉，省掉昂贵的片元着色。

于是标准结构：**不透明队列在前，透明队列在后**，各自内部再排序。

### 2.3.2 方案对比：排序键怎么选

| 排序策略（不透明） | 优点 | 缺点 |
|---|---|---|
| 仅按材质 id | 状态切换最少 | 完全放弃 early-z 收益 |
| 仅按深度（近到远） | 填充率最优 | 状态切换随场景波动 |
| 材质 id 为主、深度为辅（本方案） | 状态切换最少；同材质内吃 early-z | 两目标偶有冲突时牺牲填充率 |

透明队列不用纠结：**只有深度（远到近）一个键**。因为透明物体之间混合顺序错了是肉眼可见的错，而"多一次纹理切换"只是慢一点——正确性优先级高于性能。排序比较函数里体现为材料键根本不参与。

深度值取什么？用 mesh 包围球中心到相机的距离（不是最近点也不是最远点）——统一、便宜、对常规场景足够。追求精确可分层做（每个三角形排序，即 order-independent transparency 的反面），迷你框架不做。

### 2.3.3 完整核心代码：渲染队列与 Renderer 主流程

```typescript
// renderer/RenderQueue.ts —— 渲染清单：收集、排序
import { Node3D } from "../scene/Node3D";
import { Mesh } from "../scene/Mesh";
import { Camera } from "../scene/Camera";
import { Vec3 } from "../math/Vec3";

export interface RenderItem {
  mesh: Mesh;
  depth: number; // 包围球中心到相机的距离
}

const _v = new Vec3();

export class RenderQueue {
  readonly opaque: RenderItem[] = [];
  readonly transparent: RenderItem[] = [];

  /** 遍历场景图收集；剔除（视锥/距离）也在此扩展 */
  collect(scene: Node3D, camera: Camera): void {
    this.opaque.length = 0;
    this.transparent.length = 0;

    scene.updateMatrixWorld(); // 铁律：先更新矩阵再收集（见 2.2.5 坑 3）
    scene.traverse((node) => {
      if (!(node instanceof Mesh)) return;
      const m = node;
      // TODO（第五阶段）：视锥剔除——包围球与 6 个裁剪面判定
      // 深度：世界坐标下包围球中心到相机距离
      Vec3.set(_v, ...m.boundingSphereCenterWorld);
      const depth = Vec3.distance(_v, camera.worldPosition);
      const item: RenderItem = { mesh: m, depth };
      (m.material.transparent ? this.transparent : this.opaque).push(item);
    });

    this.sort(camera);
  }

  /** 不透明：材质分簇 + 近到远；透明：远到近 */
  protected sort(_camera: Camera): void {
    this.opaque.sort((a, b) => {
      // 第一键：材质 id（program/纹理切换分簇）
      if (a.mesh.material.id !== b.mesh.material.id) {
        return a.mesh.material.id - b.mesh.material.id;
      }
      // 第二键：同材质内近的先画，吃 early-z
      return a.depth - b.depth;
    });
    this.transparent.sort((a, b) => b.depth - a.depth); // 远的先画
  }
}
```

```typescript
// renderer/Renderer.ts —— 主流程（整合 02 册 StateCache）
export class Renderer {
  readonly state: StateCache;
  private readonly queue = new RenderQueue();

  constructor(private gl: WebGL2RenderingContext) { /* 同 02 册 */ }

  render(scene: Node3D, camera: Camera): void {
    const gl = this.gl;
    this.state.setViewport(0, 0, gl.drawingBufferWidth, gl.drawingBufferHeight);
    this.state.setClearColor(0.05, 0.05, 0.08, 1);
    gl.clear(gl.COLOR_BUFFER_BIT | gl.DEPTH_BUFFER_BIT);

    camera.updateMatrixWorld(); // 相机也是节点
    this.queue.collect(scene, camera);

    this.setMaterialState(false);            // 不透明段：关混合、开深度写
    for (const item of this.queue.opaque) this.draw(item.mesh, camera);
    this.setMaterialState(true);             // 透明段：开混合、关深度写
    for (const item of this.queue.transparent) this.draw(item.mesh, camera);
  }

  private draw(mesh: Mesh, camera: Camera): void {
    mesh.geometry.upload(this.gl);                          // 懒上传（02 册 1.3.3）
    mesh.geometry.bind(this.state);                         // 内部走 state.bindVertexArray(vao)
    const program = mesh.material.acquireProgram(this.gl);  // 04 册：变体 program
    this.state.useProgram(program);
    mesh.material.uploadUniforms(this.gl, this.state, mesh, camera); // 04 册：含内置矩阵 uniform
    mesh.geometry.draw(this.gl);                            // drawElements / drawArrays
  }
}
```

两段式（不透明段/透明段）切换状态各一次，而不是每个物体切一次——这本身就是 02 册状态缓存思路在更高层的应用：**排序即状态管理**。

### 2.3.4 常见坑

1. **透明物体"depthMask(false)"后仍被剔除**。关的是"写深度"，深度测试还开着（2.2 节 02 册坑 4 的镜像）。反过来把 `depthMask(false)` 写成 `disable(DEPTH_TEST)` 的，透明物体直接穿透不透明物体。
2. **透明物体之间的排序用"原点距离"**。大体积透明物体（一面大玻璃）包围球中心在玻璃后面、实际覆盖屏幕前部，与前景小物体排序错。缓解：用"距相机最近点"（中心距离减包围球半径）作排序键，仍不完美，完美的要 OIT（order-independent transparency，第五阶段后处理再议）。
3. **材质 id 不稳定**。id 用自增数没问题；但若用 `Math.random()` 或哈希，同一材质每帧排序键都变，排序完全失效。id 必须进程内稳定且创建即定。
4. **透明物体落进不透明队列**（忘了设 `material.transparent = true`）：混合公式还在算，但画序在队列前段且开着深度写，玻璃后面物体被玻璃"挡死"——黑色玻璃是这类 bug 的经典长相。
5. **粒子系统每帧排序抖动**。数千粒子每帧 `sort` 抖动性能，且距离相近粒子排序闪烁。粒子通常整体作为一个透明物体渲染（第五阶段 instancing），不逐粒子排序。
