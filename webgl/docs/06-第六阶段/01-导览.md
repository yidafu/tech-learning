## 阶段目标

前五个阶段已经产出一套自研迷你框架（minmath 数学库 + 场景图 + 渲染器 + 材质与资源系统 + 阴影/后处理/PBR/粒子）。第六阶段只做两件事：**拿 Three.js 源码给自研框架做一次"体检"，再用毕业项目验证框架能不能扛住完整场景**。拆成四条可检验的目标：

1. 能徒手画出 Three.js `src/` 的目录职责地图，说清它与自研框架分层的同与不同；
2. 逐点对照四大机制（GL 状态托管、渲染队列、变换脏标记、材质与着色器缓存），产出一份"查漏补缺清单"；
3. 能说清 Babylon / regl / Oasis 各自用什么换走了什么，以及自研框架在这个坐标系里的定位；
4. 用自研框架交付一个完整可交互场景，发布到 GitHub Pages，通过验收 checklist。

## 阅读路线

- **主线**：02 → 03 → 04 → 05。02 是本阶段的重头（约占一半时间），03 是轻松的横向阅读，04/05 是项目落地。
- **并行建议**：不要等源码读完才开工。02 分册的研读节奏已按"半周一个模块"拆开，与毕业项目 W1/W2 并行推进（见 [05 分册](05-毕业项目-里程碑计划.md)的甘特图）。

## 阶段自测

学完本阶段分册并完成项目后作答：

1. 不看资料，画出 Three.js `src/` 的一级目录并说出各自职责。哪一层是"唯一懂 GL 的层"？这个约定与第四阶段的分层有什么对应关系？
2. WebGLState 为什么"只记账、不回读"？对照自研 StateCache，差距清单里最重要的一条是什么？
3. 三条渲染队列（opaque / transmissive / transparent）各自用什么策略排序？为什么不透明队列不干脆完全按距离排？
4. `matrixWorldNeedsUpdate` 的脏标记如何沿树传播？为什么"子动父不动"不需要给父标脏？静态场景该怎么利用 `matrixAutoUpdate`？
5. 一个 `MeshStandardMaterial` 从 getParameters 到 program 缓存命中，中间经过哪几步？`customProgramCacheKey()` 默认返回什么、什么时候必须覆写？
6. Babylon、regl、Oasis 三者各自牺牲了什么换来了什么？你的自研框架牺牲了什么？三个可低成本借鉴的设计分别是什么？
7. 毕业项目五项必选技术点，各自复用前五阶段的哪个成果？哪一项在你的方案里风险最高、回退方案是什么？
8. 发布到 GitHub Pages 后模型纹理 404，最先检查哪两处？

> 全部作答后回到 [大纲](../WebGL与3D框架学习大纲.md) 勾选第六阶段条目；查漏补缺清单中"记录在案"的条目，就是自研框架 v1.1 的 roadmap。
