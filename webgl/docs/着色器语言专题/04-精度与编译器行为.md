# 精度与编译器行为

> [返回：WebGL 与 3D 框架学习大纲](../WebGL与3D框架学习大纲.md)
> 本文是"着色器语言专题"的精度与编译器分册：把 precision 从"认识三档"推进到"掌握规则、会算截断、能定策略、看得懂编译器在干什么"。分工说明：精度限定符的初次介绍在 [01-第一阶段/04-GLSL基础](../01-第一阶段/04-GLSL基础.md) 3.3.1；移动端真实事故案例（顶点抖动/时间冻结/高光条带）在 [工程专题/02-移动端与兼容性](../工程专题/02-移动端与兼容性.md) 2.2；本文负责**语言规范侧的完整规则、截断的手算方法与编译器优化的可预期行为**，案例细节不重复。

着色器开发者对"精度"通常有三个误区：一是以为三档只是"快慢档位"，二是以为规范规定的是"实际实现"而不是"最低保证"，三是以为源代码写什么 GPU 就执行什么。本文按"规则 → 截断机制 → 检测与策略 → 编译器行为 → 跨驱动纪律"五步展开，每一步的结论都指向同一个目标：**写出的着色器在桌面调试通过后，到移动端仍然正确**。

## 4.1 精度体系规则

### 4.1.1 三档精度的规范下限

GLSL ES 的精度限定符（precision qualifier）有三档：`highp` / `mediump` / `lowp`。规范（GLSL ES 3.00 规范 4.5 节）给出的是**最低要求（minimum requirement）**，不是实际实现——实际硬件只能比它好，不能比它差：

| 限定符 | float 范围下限 | float 精度下限 | int 范围下限（ES 3.00） | 真实实现的典型形态 |
|---|---|---|---|---|
| highp | (-2^62, 2^62) | 相对精度 2^-24 | [-2^31, 2^31 - 1]，完整 32 位 | fp32（IEEE 754 单精度，23 位存储尾数）；int 为 32 位整数通路 |
| mediump | (-2^14, 2^14) | 相对精度 2^-10 | 约 [-2^15, 2^15 - 1]，16 位量级 | 移动端常用**真 fp16**（范围 ±65504、10 位存储尾数）；桌面多直接当 fp32 处理 |
| lowp | (-2.0, 2.0) | **绝对精度 2^-8** | 约 [-2^8, 2^8 - 1]，8 位量级 | 移动端可能是 8 位定点；桌面多直接当 fp32 处理 |

三处必须划重点的读法：

1. **mediump 的范围下限只有 ±2^14（16384）**。真 fp16 硬件（±65504）已经"超额完成"规范要求；超出 ±16384 的量在"只达下限"的实现上行为未定义。这就是"桌面好好的、手机上爆掉"的规范根源——桌面的 mediump 就是 fp32，你以为的安全只是 fp32 的安全。
2. **lowp 的精度约束是绝对值 2^-8**，不是相对值：在 [-2, 2] 整个区间内步长约为 1/256。这与浮点的"相对精度"语义完全不同（详见 4.2.2）。
3. **int 也有三档**，而且 ES 1.00 时代的整数保证更弱（早期移动 GPU 常用浮点通路凑整数运算），到 ES 3.00 才明确 highp int 为完整 32 位。ES 3.00 另有 `uint`（无符号整数），回绕语义用它表达更稳（见 4.5.2）。

### 4.1.2 默认精度完整规则

每个着色器阶段、每种类型的默认精度如下：

| 阶段 | 类型 | 默认精度 | 来源 |
|---|---|---|---|
| 顶点着色器 | float | **highp** | 规范保证 |
| 顶点着色器 | int | **highp** | 规范保证 |
| 顶点着色器 | sampler2D / samplerCube（及 ES 3.00 全部采样器） | **lowp** | 规范默认 |
| 片元着色器 | int | **mediump** | 规范默认 |
| 片元着色器 | sampler2D / samplerCube（及 ES 3.00 全部采样器） | **lowp** | 规范默认 |
| 片元着色器 | **float** | **没有默认，必须显式声明** | 规范刻意留白 |

**为什么规范这样设计**：片元着色器的执行次数（每像素，1920×1080 屏一次全屏约 200 万次）比顶点着色器（每顶点，几万到几十万次）高一到两个数量级。在 GLSL ES 诞生年代（OpenGL ES 2.0，2007 前后）的移动 GPU 上，片元里做高精度浮点的代价比顶点高得多——有的硬件片元通路根本没有 fp32。规范于是把选择权**强制**交给作者：不给 float 设默认，漏写直接编译失败（[04-GLSL基础](../01-第一阶段/04-GLSL基础.md) 常见坑第 1 条的 `No precision specified for type 'float'` 就是它）。顶点着色器则相反，量少、必有坐标计算，直接默认 highp 零负担。采样器默认 lowp 的理由则是：过滤后的纹素几乎总在 [0, 1] 内，8 位精度对颜色足够。ES 3.00 时代片元 fp32 已是标配，但规范保留了这条规则——它成了一道"提醒你正在写会跑在异构硬件上"的防线。

两个阶段的推荐头部写法：

```glsl
// ---- 顶点着色器（1.00 与 3.00 皆可） ----
precision highp float;   // 与默认一致，写出来是自文档：坐标计算依赖它

// ---- 片元着色器 ----
precision highp float;   // WebGL2 / 桌面 WebGL1 皆安全；
                         // 若要兼容不支持片元 highp 的老 WebGL1 设备，
                         // 用 GL_FRAGMENT_PRECISION_HIGH 条件编译（4.3.2）
```

### 4.1.3 precision 语句、变量级限定符、构造器与字面量的优先级

三种写法同时存在时，优先级从低到高依次是：

```mermaid
flowchart LR
    A["precision 语句<br/>（设定类型的默认精度，<br/>只影响其后声明的变量）"] --> B["变量级限定符<br/>（highp/mediump/lowp 写在声明上，<br/>覆盖默认，只管这一个变量）"] --> C["表达式求值规则<br/>（运算按操作数中的最高精度执行，<br/>结果在赋值/传参时舍入到目标精度）"]
```

规则展开成五条：

1. **precision 语句设默认，且只影响"其后"**：`precision mediump float;` 之后声明的 float 默认 mediump；语句可以多次出现，中途切换只影响后面的声明。这就是它通常写在文件最顶的原因。
2. **变量级限定符覆盖默认**：`highp vec3 worldPos;` 在一片 mediump 默认的着色器里独享高精度。可以对全局变量、局部变量、函数参数、函数返回值使用。
3. **表达式求值精度取操作数中最高的一档**：`highpVec * mediumpVec` 按 highp 算；内建函数与构造器同样按"实参中最高精度"求值。所以"一个 highp 变量参与的表达式整条都是高精度"——精度只会在**存储**时丢，不会在**运算中途**悄悄降级。
4. **截断发生在三处**：赋给低精度变量时、传给低精度形参时、跨阶段传给低精度声明时（4.3.3 展开）。
5. **字面量与常量表达式在编译期折叠**：`0.5 * 2.0`、`sin(3.14)` 这类编译期常量由编译器按其内部精度（至少满足 highp 下限）算好再嵌入，赋值时按目标精度舍入。所以 `mediump float x = 0.1;` 里的 0.1 是"先按 fp32 折叠、再舍入到 mediump"，不是"按 mediump 的算术算出来"。

```glsl
precision mediump float;        // 本文件默认 mediump

highp vec3 u_worldPos;          // 变量级限定符：这个变量是 highp
uniform vec3 u_color;           // 吃默认：mediump

void main() {
  mediump float d = distance(u_worldPos, u_worldPos + vec3(1.0));
  //  distance 的实参是 highp（u_worldPos）与 mediump（vec3(1.0) 字面量构造）
  //  → 表达式按 highp 求值，结果赋给 mediump 变量 d 时舍入一次
  highp float dH = distance(u_worldPos, u_worldPos + vec3(1.0));
  //  同样的计算，dH 保留了全程高精度——两者在大坐标场景下结果可观测不同
}
```

一句总结优先级：**precision 语句决定"没写的时候用什么"，变量限定符决定"这个变量存成什么"，求值规则决定"算的过程用什么精度"；丢精度只发生在存的那一刻。**

## 4.2 精度如何截断

### 4.2.1 10 位尾数的实际含义：手算位置抖动

"mediump 有 10 位尾数"的准确含义是：真 fp16 实现里，浮点数按 `1 位符号 + 5 位指数 + 10 位尾数` 编码。落在区间 [2^e, 2^(e+1)) 内的数，相邻两个可表示数的间距（步长）是 **2^(e-10)**——数值越大，绝对步长越大：

| 数值所在区间 | fp16 步长（2^(e-10)） | 对应物理量级（单位米） |
|---|---|---|
| [1, 2) | 2^-10 ≈ 0.001 | 毫米级尚可 |
| [64, 128) | 2^-4 = 0.0625 | 6 厘米一格 |
| [1024, 2048) | 2^0 = 1 | 米级一格 |
| [4096, 8192) | 2^2 = 4 | 4 米一格 |
| [16384, 32768) | 2^4 = **16** | 16 米一格 |

手算一个"大世界坐标顶点抖动"的完整过程。设场景单位为米，某顶点 x = 20003，相机移动使它更新为 20011（顶点动画或实例偏移）：

```text
第一步：定位区间
  2^14 = 16384 ≤ 20003 < 32768 = 2^15   → e = 14

第二步：算步长
  步长 = 2^(14-10) = 2^4 = 16 米

第三步：量化到最近的可表示数
  20003 → 候选 20000（距离 3）与 20016（距离 13）→ 落到 20000
  20011 → 候选 20000（距离 11）与 20016（距离 5）→ 落到 20016

第四步：观测结论
  顶点实际只动了 8 米，屏幕上却跳了 16 米一整格；
  相邻两次可观测位置之间没有任何中间值——这就是"一格一格抖"
```

修复方案是**相机相对渲染**（把世界原点锚到相机附近再提交 GPU，[工程专题/02](../工程专题/02-移动端与兼容性.md) 2.2 案例一的做法）：相机在 (19990, ...)，顶点坐标减去相机后是 13 与 21，落在 [8, 16) 与 [16, 32) 区间，步长 2^-7 ≈ 0.0078 米——同样是 mediump，分辨率从 16 米恢复到 8 毫米。**精度问题的根治手段几乎总是"让数值变小"，而不是"把精度调高"**。

相机相对渲染在两阶段的分工落点（细节属于引擎侧，这里只看数值量级的变化）：

```glsl
// ---- 顶点着色器：worldPos 全程 highp，但绝对值已被 CPU 压到几十以内 ----
uniform mat4 u_viewProj;        // 相机相对空间下的 VP（CPU 侧把平移分量扣掉）
in vec3 a_position;             // 相机相对模型的顶点（单位米，量级 < 100）
void main() {
  gl_Position = u_viewProj * vec4(a_position, 1.0);   // 数值小，步长小
}
```

```typescript
// ---- CPU 侧：每次相机移动后重建锚点 ----
// viewMatrix = inverse(cameraAtAnchorWorldPos) ；模型矩阵乘以 anchorWorldPos 的逆
// 等价地：所有 worldMatrix 先右乘 translate(-anchor)，再进 VP
const anchor = camera.worldPosition.clone();   // 锚点 = 当前相机位置
scene.root.matrixWorld.premultiply(translation(-anchor.x, -anchor.y, -anchor.z));
```

同样的算术解释了 `u_time` 动画冻结：t = 1024.5 秒在 [1024, 2048) 区间步长为 1，0.5 秒的推进被整段吞掉（详见 [工程专题/02](../工程专题/02-移动端与兼容性.md) 2.2 案例二，修法是 CPU 侧先取模）。

最后强调规范下限的另一面：mediump 的**范围**下限只有 ±16384。真 fp16 硬件上超出 ±65504 直接变 inf；在"恰好只达规范下限"的实现上，超出 ±16384 就已无保证。给 mediump 变量喂 20003 这种值，在两种实现上都是走钢丝。

### 4.2.2 lowp 的 [-2, 2]：范围 + 精度的双重约束

对 lowp 有两个方向的误读，都值得拆开：

**误读一："范围只有 [-2, 2]，所以超过 2 就完全不能用。"** 方向对了但结论不对：约束是"值域 [-2, 2] + 全域统一步长 2^-8"。恰好 [0, 1] 区间能放下 256 个步长，与 8 位色深一一对齐——这正是 lowp 为颜色设计的原因。反过来说，[0, 1] 内也**不是任意精度**：0.003 以下的小差异全部被抹平。

**误读二："只要值在 [-2, 2] 内就安全。"** 不。lowp 的步长是**绝对值** 1/256，浮点的步长是**相对值**。看这个光照累加的例子：

```glsl
lowp vec3 acc = baseColor;                    // [0,1]，安全
for (int i = 0; i < 4; i++) {
  acc += light[i].color * light[i].attenuation;  // 累加四次，可能到 2.5
}
// 真 lowp 硬件上：acc 一路被钳/绕，超界行为未定义；
// 桌面（lowp=fp32）上：完全正常。
// 可移植写法：累加器用 mediump/默认精度，只在最终颜色输出前考虑 lowp
```

规律：**lowp 适合"终值"，不适合"过程"**。任何会做加减累积、乘以大于 1 的系数、或者中间量可能出 [0,1] 的计算，都不要用 lowp 当累加器。颜色 albedo、纹理采样结果、布尔/掩码量是 lowp 的主场。

还要点破一个可移植性陷阱：桌面 GPU 几乎都把 lowp（和 mediump）实现为 fp32，所以**在桌面上写超出 lowp 约束的代码没有任何报错、任何症状**——直到它跑在真 8 位通路的手机上。精度错误是最典型的"桌面测不出来"类别，纪律要靠写代码时建立，不能靠调试发现。

### 4.2.3 哪些量永远别降精度，哪些通常安全

| 永远 highp | 理由 | 通常安全（mediump 或更低） | 理由 |
|---|---|---|---|
| 顶点位置（局部/世界/裁剪全链路） | 坐标即量级，量级即步长（4.2.1） | 颜色 / albedo | [0,1] + 8 位对齐 |
| 深度值、shadow map 坐标 | 深度差是可见性判据，低精度直接 z-fighting | 纹理采样结果 | 同上 |
| 时间 uniform（参与三角函数前） | hash/相位对 t 的分辨率极敏感 | 归一化法线（读取后） | 分量 [-1,1]，10 位尾数偏差对光照几乎不可见 |
| 相机位置 / 视线向量的**输入** | 大数相减的灾难性抵消（[工程专题/02](../工程专题/02-移动端与兼容性.md) 2.2 案例三） | UV 坐标（mediump 起步） | 通常 [0,1]，但大图集 UV 要小心，lowp 会色带 |
| 距离/长度类中间量 | `distance` 的结果是"大数相减"的产物 | 粗糙度、金属度等 [0,1] 材质参数 | 天然有界 |
| 骨骼矩阵、粒子位置积分 | 累积误差不可回收 | 雾系数、mix 的 t 参数 | 天然有界 |

判据只有两条：**数值的绝对量级**（决定步长）与**业务需要的分辨率**（步长必须显著小于要分辨的最小差异）。拿不准就 highp——中端机上"该降而没降"损失的是一点带宽功耗，"不该降而降了"损失的是正确性。

## 4.3 检测与策略

### 4.3.1 getShaderPrecisionFormat 的读法

[工程专题/02](../工程专题/02-移动端与兼容性.md) 2.2 给过"片元 highp 一行检测"，这里把 API 本身讲透。它按"着色器阶段 × 精度档"查询，返回三个字段，**全部是按 2 为底的对数编码**：

```typescript
const fmt = gl.getShaderPrecisionFormat(gl.FRAGMENT_SHADER, gl.MEDIUM_FLOAT);
// fmt.rangeMin / fmt.rangeMax：可表示范围的指数界限（log2）
// fmt.precision：float 为尾数位数；int 恒为 0
console.log(fmt.rangeMin, fmt.rangeMax, fmt.precision);
```

| 返回 | 字段含义 | 典型值（示例，以实机为准） |
|---|---|---|
| `{127, 127, 23}` | 指数上下界 2^127，23 位尾数 | 桌面 HIGH_FLOAT（就是 fp32） |
| `{15, 15, 10}` | 指数界 2^15，10 位尾数 | 真 fp16 硬件的 MEDIUM_FLOAT |
| `{31, 30, 0}` | 指数界覆盖 [−2^31, 2^31−1] | 32 位整数的 HIGH_INT（int 无尾数概念） |

读法要点：

1. **先看阶段再看档位**：第一个参数是 `gl.VERTEX_SHADER` 或 `gl.FRAGMENT_SHADER`——同一档精度在两个阶段可以不同（老设备片元弱于顶点）。
2. **precision 字段是"尾数位数"**，0 对 float 表示"该档不支持"（WebGL1 老设备上 `FRAGMENT_SHADER + HIGH_FLOAT` 查出 precision 为 0 就是这个含义）；对 int 类型恒为 0，此时看 rangeMin/rangeMax。
3. **报告的是"实现宣称"**：实现必须至少兑现规范下限（mediump 至少报 10 位尾数），多数桌面直接报 fp32 的数值——所以"查出来是 23"说明 mediump 按全精度处理，但**不能反推所有驱动永远兑现**，跨机型结论要靠 2.6 那样的测试矩阵落地。

### 4.3.2 GL_FRAGMENT_PRECISION_HIGH 预定义宏

片元着色器里有一个由实现预定义的宏：支持片元 highp 时 `GL_FRAGMENT_PRECISION_HIGH` 被定义为 1，不支持则不定义。注意它**只在片元着色器里有意义**（顶点的 highp 是规范保证的，宏在顶点着色器里处于未定义状态，不要依赖）：

```glsl
// 片元着色器通用头部（兼容不支持片元 highp 的老 WebGL1 设备）
#ifdef GL_FRAGMENT_PRECISION_HIGH
precision highp float;
#else
precision mediump float;   // 退而求其次，且必须保证算法在 10 位尾数下仍正确
#endif
```

版本边界记两条：WebGL1（GLSL ES 1.00）片元 highp **可选**，必须用宏或 4.3.1 的查询兜底；WebGL2（GLSL ES 3.00）**强制支持**，宏恒为 1，条件编译可以退役但写了无害。工程侧的完整降级头策略见 [工程专题/02](../工程专题/02-移动端与兼容性.md) 2.2，不重复。

### 4.3.3 精度传染规则与分层降级策略

"精度传染"指精度如何沿声明链传播、截断发生在哪一环。按存储类别给出规则表：

| 存储类别 | 规则 | 截断发生的时机 |
|---|---|---|
| 局部变量 | 声明精度（或默认精度）决定存储；参与运算时提升到操作数最高精度 | **赋值那一刻**：`mediump float d = highpExpr;` 求值高精度、存入即舍入 |
| 函数形参/返回值 | 形参的声明精度在函数体内生效 | **传参那一刻**：highp 实参传入 mediump 形参即舍入 |
| uniform | 着色器里的声明精度决定驱动可用的存储/转换路径；数值由 JS 按位上传 | **读取进表达式时**按声明精度解释；声明 mediump 允许驱动按 fp16 存省带宽 |
| varying / in / out | 两阶段各自声明；**有效精度取两边较低者** | **跨阶段传递时**：顶点写 24 位、片元声明 10 位，插值与读取只有 10 位 |
| 精度不匹配的 varying | 规范对"顶点声明 highp、片元声明 mediump"这类组合没有给出统一的链接结论，实测中有的驱动接受并按片元侧转换、有的（如部分 Mesa/V3D）直接链接失败 | 不可移植区域——**规避，不要利用** |

最常被忽略的不匹配现场：两边的 varying 都是"裸声明"，精度全靠各自默认值——

```glsl
// ---- 顶点着色器 ----                // ---- 片元着色器 ----
precision highp float;                 precision mediump float;
out vec3 v_worldPos;   // highp        in vec3 v_worldPos;   // mediump！
// 同名同类型，但有效精度不同：
// 有的驱动直接链接失败；接受的那批，插值只剩 10 位——大坐标下片元拿到的
// v_worldPos 已经是 4.2.1 里"16 米一格"的量化值，光照全部算错
```

由此得到分层降级的实操策略：

| 层 | 策略 | 说明 |
|---|---|---|
| 第 0 层：文件头 | `precision highp float;` 两阶段统一 | 默认全高精度，正确性优先 |
| 第 1 层：变量级降级 | 颜色类局部变量、采样结果显式写 `lowp`/`mediump` | 只降"终值型"变量（4.2.3 安全列） |
| 第 2 层：varying 对齐 | 两阶段同名 varying 的 precision 限定符**写成完全一致** | 最常见的隐性不匹配：顶点吃 highp 默认、片元头部 `precision mediump float;` 后同名 varying 吃 mediump——两边的"裸声明"实际精度不同 |
| 第 3 层：uniform 降级 | 大量颜色/参数类 uniform 声明 mediump，位置/矩阵类保持 highp | 需要实测收益再上，多数场景收益在移动端带宽 |
| 永不降级清单 | 位置、深度、时间、距离、相机输入（4.2.3） | 无条件 highp |

一个演示三层联用的片段：

```glsl
// ---- 片元着色器 ----
precision highp float;            // 第 0 层：默认高精度
in  vec3 v_worldPos;              // 第 2 层：与顶点侧声明完全一致（同为默认 highp）
in  vec2 v_uv;
uniform sampler2D u_albedo;
uniform vec3 u_lightColor;        // 候选降级点（颜色类）
void main() {
  lowp vec3 albedo = texture(u_albedo, v_uv).rgb;   // 第 1 层：终值型 lowp
  highp vec3 toLight = normalize(u_lightPos - v_worldPos);
  //                          ^ 大数相减：保持 highp（4.2.3 永不降级清单）
  outColor = vec4(albedo * u_lightColor, 1.0);
}
```

## 4.4 编译器优化行为

### 4.4.1 常量折叠、死代码消除与"消失的分支"

对着色器源码，驱动编译器（GPU compiler）会做一整套与 C++ 编译器同源的优化，三件最常见：

**常量折叠（constant folding）**：编译期能算出结果的表达式直接替换为常量。`0.5 * 2.0` 变 `1.0`；`sin(3.14)` 常参版同样折叠；`vec2(1.0, 2.0) * 3.0` 折成 `vec2(3.0, 6.0)`。

**死代码消除（dead code elimination）**：不影响输出的声明与代码整段删除。最常咬人的是**未使用的 uniform/varying 被删**——`getUniformLocation` 返回 null、后续 uniform 调用全部静默忽略，症状是"值怎么传都不变"（[04-GLSL基础](../01-第一阶段/04-GLSL基础.md) 常见坑第 5 条）；同理，写了但没被 `main` 可达路径用到的函数也整段消失。

**"写了 if 其实没分支"**：当条件是编译期常量时，整个分支结构在编译期被解开，机器码里既没有判断也没有跳转：

```glsl
#define ENABLE_FOG 0              // 编译期开关

vec3 applyFog(vec3 c, float dist) {
#if ENABLE_FOG                    // 预处理期：分支根本不存在
  return mix(c, fogColor, clamp(dist / fogFar, 0.0, 1.0));
#else
  return c;
#endif
}

void main() {
  vec3 col = shade();
  const bool debugNormal = false; // 常量条件
  if (debugNormal) {              // 编译期常量 → 驱动消除整个分支
    outColor = vec4(vNormal * 0.5 + 0.5, 1.0);  // 这段不进机器码
    return;
  }
  outColor = vec4(applyFog(col, vDist), 1.0);
}
```

这就是 `#define`/`const bool` 开关与"uniform 开关"的本质区别：前者在编译期生效、关闭时**零开销**（还减少编译产物），后者保留在运行期、两个分支都编译进机器码。uber shader 的变体管理用的是前者（[04-第四阶段/04-材质与着色器系统](../04-第四阶段/04-材质与着色器系统.md)）。

补一个运行期分支的真相：即便条件是 uniform（编译期不知道），现代 GPU 也常把短分支**压平（predication）**——两个方向都算、按条件选取，避免相邻线程分道扬镳的代价。所以"if 很慢"是被夸大的；真正危险的是**分支内采样纹理**：非均匀控制流（non-uniform control flow）里的隐式导数是未定义行为，mipmap 层级可能取错（4.5.2）。

死代码消除的"受害者"可以在 JS 侧主动审计——把链接器眼中实际存在的 uniform 集合拉出来对账：

```typescript
// 列出"编译器没删掉"的 uniform：与源码声明对账，找出被静默优化的名字
function auditActiveUniforms(gl: WebGL2RenderingContext, program: WebGLProgram) {
  const count = gl.getProgramParameter(program, gl.ACTIVE_UNIFORMS) as number;
  const report: Array<{ name: string; type: string }> = [];
  for (let i = 0; i < count; i++) {
    const info = gl.getActiveUniform(program, i)!;
    report.push({ name: info.name, type: glEnumName(info.type) });  // sampler/float/vec3...
  }
  return report;
  // 源码里声明了但这里没出现的 uniform = 被死代码消除
  // 它的 getUniformLocation 必然返回 null，uniform 调用静默失效（不是 bug，是语义）
}
```

用两个视角看同一段代码，编译器做了什么一目了然：

```glsl
// 你写的                                                     // 编译器产出的（概念等价）
const float RADIUS = 2.0;                                     // （常量直接内联）
uniform bool u_showNormal;                                    // 保留：运行期才知道
vec3 shade(vec3 n, vec3 l) {                                  // （单调用点 → 内联展开）
  return vec3(max(dot(n, l), 0.0));                           // dot/max 保留
}
void main() {
  vec3 c = shade(vNormal, u_lightDir);                        // 内联 + RADIUS 死代码消除
  c *= 0.5 * RADIUS;                                          // 常量折叠为 c * 1.0 → 再消除
  if (u_showNormal) outColor = vec4(n, 1.0);                  // 运行期分支：保留（可能压平）
  else outColor = vec4(c, 1.0);
}
```

### 4.4.2 循环展开：收益与代价

循环边界是编译期常量时，驱动通常直接**展开（unrolling）**——把循环体复制 N 份内联。行为推论：

```glsl
// 9 次采样的模糊核：展开后是 9 段完全内联的采样代码
for (int i = -4; i <= 4; i++) {
  acc += texture(uTex, v_uv + vec2(texelSize.x * float(i), 0.0)).rgb;
}

// 边界来自 uniform 的循环：编译期不可知，通常保持循环（或在少数驱动上部分展开）
for (int i = 0; i < u_tapCount; i++) { ... }
```

- 展开消除了循环变量维护与跳转，GPU 上通常更快——但**指令体积暴涨**：64 次采样的循环展开后代码体积翻几十倍，超出指令缓存反而变慢。
- 展开发生在**编译期**，直接推高编译时长——这正是 4.4.3 的入口。
- 历史包袱：GLSL ES 1.00 附录 A 曾要求循环"可静态展开"（常量初始化、常量边界、常量步进），WebGL 一线实现早已放宽到接受动态循环，但个别老移动驱动对动态循环仍会生成错误代码。**在 WebGL1 着色器里，能用常量边界的循环就别用动态边界**——这不是风格，是兼容性。

### 4.4.3 编译时长的坑：首帧卡顿与 iOS 编译超时

WebGL 的着色器编译是**惰性且昂贵**的：`compileShader` / `linkProgram` 可能只做前端解析，真正的机器码生成往往推迟到**第一次 draw 使用该 program** 时。由此产生两类工程事故：

1. **首帧卡顿**：进入场景的第一帧里串行发生"编译 + 链接 + 后端代码生成"，一个复杂 uber shader 的变体集合可以轻松让首帧卡住数百毫秒到数秒——加载条走完了，画面却定格。
2. **iOS 编译超时崩溃**：Safari/WebKit 有看门狗（watchdog）机制，着色器编译/链接占用主线程过久会被判定为页面失控，轻则上下文丢失，重则直接杀页面。变体越多、循环展开越大，越容易触顶。

缓解手段清单（GLSL 侧与流程侧配合）：

| 手段 | 做什么 | 针对 |
|---|---|---|
| 拆分着色器 | 大而全的 uber shader 按用途拆成若干小 shader；`#define` 组合数从"特性全排列"收敛为"实际用到的变体集" | 编译时长、iOS 超时 |
| 常量下沉 | 编译期常量从 shader 挪到 JS，CPU 侧算好传 uniform，减少折叠与展开负担 | 编译时长 |
| 加载期预热 | loading 屏期间对全部变体执行 link + 画一个 1×1 像素的离屏首 draw，把真正的代码生成提前 | 首帧卡顿 |
| 异步编译 | 启用 `KHR_parallel_shader_compile` 扩展，`linkProgram` 后**轮询** `COMPLETION_STATUS_KHR`（不要假定同步返回即完成） | 主线程卡顿（扩展表见 [工程专题/02](../工程专题/02-移动端与兼容性.md) 2.1） |
| 延迟编译 | 非首屏效果的着色器等用到时再编（配合异步扩展） | 冷启动 |

预热的最小实现：

```typescript
// 预热：把"链接 + 后端代码生成"挪进 loading 屏
const ext = gl.getExtension('KHR_parallel_shader_compile');
function precompile(sources: Array<[string, string]>): Promise<void[]> {
  return Promise.all(sources.map(([vsSrc, fsSrc]) => new Promise((resolve) => {
    const vs = compile(gl.VERTEX_SHADER, vsSrc);
    const fs = compile(gl.FRAGMENT_SHADER, fsSrc);
    const prog = link(vs, fs);                 // 有 ext 时为异步提交
    const poll = () => {
      const done = !ext || gl.getProgramParameter(prog, gl.COMPLETION_STATUS_KHR);
      if (done) {
        // 关键一步：一次 1 像素的离屏 draw，强制驱动完成机器码生成
        warmDraw(prog);
        resolve();
      } else {
        requestAnimationFrame(poll);           // 轮询，不阻塞主线程
      }
    };
    poll();
  })));
}
```

## 4.5 跨驱动差异

### 4.5.1 同一 GLSL 在不同 GPU 上的行为差异清单

| 差异维度 | 桌面典型 | 移动典型 | 你要做的 |
|---|---|---|---|
| mediump/lowp 实现 | fp32 直接顶上（三档无差别） | 真 fp16 / 8 位定点 | 按 4.2 的规范下限写代码，别用桌面表现当规范 |
| 循环优化 | 边界常量的循环激进展开 | 展开策略保守，个别老驱动动态循环出错 | 常量边界优先；超长核注意体积 |
| pow 负底数等未定义输入 | 返回 NaN（继续扩散） | 可能返回 0 或垃圾值（症状完全不同） | 入口处 max 钳制（4.5.2） |
| 精度不匹配的 varying 链接 | 接受、按片元侧转换 | 有的接受、有的链接失败 | 两边声明写一致（4.3.3） |
| 未初始化变量 | 多为 0（碰巧） | 常是上一帧寄存器残值（闪烁） | 永远初始化再使用 |
| 编译期报错信息 | 方言差异大（[05-ES3特性与调试规范](05-ES3特性与调试规范.md) 5.5.3 的三方言对比） | —— | 解析前统一归一化行号 |

另一类隐蔽差异是**不变性（invariance）**：同一个表达式在不同 program 里可能被不同驱动编译成不同的指令序列（例如乘法结合顺序不同），导致两个 program 算出的 `gl_Position` 有细微差别——两块共面几何分别用两个 program 渲染时出现 z-fighting。规范对此的解法是 `invariant` 限定符：对两阶段中名字相同的输出（典型是 `gl_Position`）声明 `invariant gl_Position;`，要求编译器在表达式一致时产出一致的结果。多 pass 对齐深度时记得它：

```glsl
// 两个 program 都要声明（在赋值前生效；写在全局作用域）
invariant gl_Position;

void main() {
  // ...两条管线用完全相同的表达式计算 gl_Position 时，
  // invariant 保证逐位一致 —— 阴影 pass 与着色 pass 的共面几何不再 z-fighting
  gl_Position = u_viewProj * u_model * vec4(a_position, 1.0);
}
```

### 4.5.2 避免依赖未定义行为清单

未定义行为（undefined behavior）的可怕之处在于"桌面正常"恰恰是它的症状之一。高频雷区与可移植写法：

| 未定义行为 | 实际表现差异 | 可移植写法 |
|---|---|---|
| `pow(负底数, 非整数幂)` | 桌面 NaN；部分移动返回 0/垃圾 | `pow(max(x, 0.0), y)`；需要负底数语义时用分段手写 |
| 非均匀流中的导数（`dFdx/dFdy`、分支内的隐式导数采样） | mipmap 层级取错、块状纹理 | 采样与求导移出分支；分支内用 `textureGrad` 显式导数（见 [工程专题/01](../工程专题/01-调试与诊断.md) 1.5 的 NaN 源头清单） |
| 有符号整数溢出 | 溢出结果无保证（ES 3.00 规范同样未定义回绕；INT_MIN / -1 明确允许两说） | 需要回绕语义用 `uint`；做大数运算前先换算到小数值域 |
| 除零 / `mod(x, 0)` | 结果未定义（不崩溃，但可能是垃圾） | 分母先 `max(y, 1e-4)`（量级见 [05-ES3特性与调试规范](05-ES3特性与调试规范.md) 5.5.2 屏蔽数值技巧） |
| `atan(0, 0)` / `log(≤0)` / `sqrt(负)` | NaN 或实现自定义值 | 入口钳制输入域 |
| 未初始化的变量/成员读取 | 桌面常为 0，移动为残值 | 声明即初始化 |
| 移位 ≥ 32、未写 `gl_Position` | 任意结果 | 位运算掩码 shift 距离；main 必写 gl_Position |

写可移植着色器的纪律总结成五条：

1. 把规范下限当真实硬件：mediump 按 10 位尾数与 ±2^14 心算一遍，lowp 按 [-2,2] + 1/256 心算一遍。
2. 数值量级主动管理：世界坐标近原点、时间取模、大数先移近再减。
3. 未定义输入一律在入口钳制，而不是指望驱动的"合理表现"。
4. 两阶段的类型、精度、插值限定符逐字对齐，链接器不接受的灰色写法一律不用。
5. 任何"在我的机器上是对的"结论，都要过一遍 [工程专题/02](../工程专题/02-移动端与兼容性.md) 2.6 的测试矩阵才算数。

## 常见坑

1. **以为 precision 只是性能开关**：它是规范行为合约。桌面三档都等于 fp32 的现实，恰恰让所有精度错误在桌面隐身。
2. **片元 float 忘声明精度**：ES 1.00 与 3.00 都没有默认，直接编译失败；顶点却默认 highp，两阶段规则不同是记忆点。
3. **varying 两边"裸声明"精度不一致**：顶点默认 highp、片元头部 mediump 后，同名 varying 两边实际精度不同——部分驱动链接失败，另一部分悄悄降精度。两边逐字对齐。
4. **lowp 当累加器**：光照累加、多次混合的中间量超 [-2,2]，真 lowp 硬件上钳死；lowp 只放终值。
5. **大世界坐标直接 mediump**：16384 以上步长 16 米起；先用相机相对渲染把量级降下来，再谈精度选择。
6. **期望"uniform 开关"和 `#define` 开关等价**：前者运行期判断、两个分支都在；后者编译期剪枝、关闭时零开销零体积。
7. **着色器里没用的 uniform 还想 getUniformLocation**：死代码消除后返回 null，且静默；同理 varying 没被片元使用，顶点侧写入全白发。
8. **超长循环 + 巨型 uber shader 堆给 iOS**：编译超时触发看门狗；用拆分、预热与异步编译三件套（4.4.3）。
9. **依赖整数回绕/负底数 pow 的"桌面表现"**：都是未定义行为，移动端表现完全不同；按 4.5.2 表逐条规避。
10. **跨 program 的共面几何 z-fighting 忘了 invariant**：不同 program 对同一表达式编译结果不保证一致，深度对齐的 pass 需要声明 `invariant gl_Position;`。
