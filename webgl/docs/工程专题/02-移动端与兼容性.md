## 2.1 能力检测体系

### 概念：不猜设备，只问能力

兼容性问题的第一原则：**不要按 userAgent 猜机型，要按能力（capability）编程**。同一台手机的不同浏览器（iOS Safari 与 Chrome 都走 WebKit 渲染、微信 WKWebView 又有差异）支持的扩展集合不同；能力检测在运行时问三件事——支持吗（getExtension / 查询常量）、支持的规格是多少（getParameter）、不支持时走哪条回退路线（降级策略）。

### 方法与完整代码：能力清单模块

能力检测只做一次、结果全局缓存，供渲染器初始化时选择路径：

```typescript
// src/renderer/caps.ts —— 能力检测清单（初始化时调用一次）
export interface Caps {
  maxTextureSize: number;
  maxAnisotropy: number;            // 1 = 不支持各向异性
  floatRenderable: boolean;         // 浮点渲染目标（bloom/高精度阴影的前提）
  halfFloatRenderable: boolean;     // 半浮点渲染目标（移动端常用的折中）
  floatLinear: boolean;             // 浮点纹理可线性过滤
  srgb: boolean;                    // sRGB 纹理硬件支持
  compressed: string[];             // 支持的压缩纹理格式
  renderer: string;                 // GPU 描述（尽力而为，见下）
}

export function detectCaps(gl: WebGL2RenderingContext): Caps {
  const ext = (name: string) => gl.getExtension(name);
  const aniso = ext('EXT_texture_filter_anisotropic');
  // 注意：扩展对象上挂着它的常量，而不是 gl 上
  const maxAniso = aniso ? gl.getParameter(aniso.MAX_TEXTURE_MAX_ANISOTROPY_EXT) as number : 1;

  // 浮点渲染目标：WebGL2 核心有 EXT_color_buffer_float / half_float 才能绑为 FBO 附件
  const floatRenderable = !!ext('EXT_color_buffer_float');
  const halfFloatRenderable = floatRenderable || !!ext('EXT_color_buffer_half_float');

  // 隐私考虑，WEBGL_debug_renderer_info 正被各浏览器移除：能拿到就用，拿不到不许报错
  const debugInfo = ext('WEBGL_debug_renderer_info');
  const renderer = debugInfo
    ? String(gl.getParameter(debugInfo.UNMASKED_RENDERER_WEBGL))
    : gl.getParameter(gl.RENDERER) as string;

  return {
    maxTextureSize: gl.getParameter(gl.MAX_TEXTURE_SIZE) as number,
    maxAnisotropy: maxAniso,
    floatRenderable,
    halfFloatRenderable,
    floatLinear: !!ext('OES_texture_float_linear'),
    srgb: true,                     // WebGL2 核心（SRGB8_ALPHA8）；WebGL1 需 EXT_sRGB
    compressed: [                   // 与 6.4 的 KTX2/Basis 转码目标对应
      's3tc', 'astc', 'etc2',
    ].filter((f) => {
      const map = { s3tc: 'WEBGL_compressed_texture_s3tc', astc: 'WEBGL_compressed_texture_astc',
                    etc2: 'WEBGL_compressed_texture_etc' };
      return !!ext(map[f as 's3tc' | 'astc' | 'etc2']);
    }),
    renderer,
  };
}
```

常用扩展速查表：

| 扩展 | 作用 | 不可用时的影响 |
|---|---|---|
| EXT_color_buffer_float | 浮点纹理可绑为 FBO 附件 | HDR 后处理链（bloom/色调映射）的高精度目标没了 |
| EXT_color_buffer_half_float | 半浮点同上（常与上面二选一） | 移动端最常见的折中路线也没了 |
| OES_texture_float_linear | 浮点纹理线性过滤 | 浮点目标放大出现块状，需手动双线性 |
| EXT_texture_filter_anisotropic | 各向异性过滤 | 斜视角地面糊，退回三线性 |
| WEBGL_compressed_texture_s3tc / astc / etc | 块压缩纹理（[6.4](../05-第五阶段/07-性能优化与调试.md)） | 显存与带宽翻 4~8 倍 |
| KHR_parallel_shader_compile | 着色器异步编译 | 编译卡首帧，需分帧轮询改同步 |
| WEBGL_lose_context | 模拟上下文丢失 | 只影响测试（[1.3](01-调试与诊断.md)），不影响功能 |
| EXT_disjoint_timer_query_webgl2 | GPU 计时查询 | 拿不到真实 GPU 耗时，用 CPU 帧时间近似 |

### 方法：降级策略表

检测的目的不是"支持就开心"，是为每条高级特性预先设计好回退路线，运行时按能力走分支：

| 高级特性 | 检测项 | 回退路线（依次降级） |
|---|---|---|
| 浮点 HDR 渲染目标 | floatRenderable → halfFloatRenderable | RGBA16F 目标 → RGBA8 + RGBM 编码（alpha 存量级，7 位尾数）→ 放弃 HDR 直出 LDR |
| 各向异性过滤 | maxAnisotropy > 1 | 各向异性 4x/8x → 三线性 + mipmap |
| sRGB 纹理 | WebGL2 核心 | 硬件 sRGB → 着色器里手动 pow 2.2（[二阶段 Gamma](../02-第二阶段/01-导览.md)） |
| PCF 软阴影（[五阶段 02](../05-第五阶段/02-阴影与PCF软阴影.md)） | 采样数预算 | PCF 3x3 → 硬阴影单采样 → 关阴影换简单的球体投影假阴影 |
| MSAA | antialias 建项 / WebGL2 多采样 renderbuffer | FXAA（[五阶段 03](../05-第五阶段/03-后处理管线.md) 2.3）→ 无 AA |
| instancing | WebGL2 核心（WebGL1 看 ANGLE_instanced_arrays） | 实例化 → 逐物体 draw（[6.2](../05-第五阶段/07-性能优化与调试.md) 合批表） |
| 压缩纹理 | caps.compressed | KTX2/Basis 转码上传 → RGBA8（显存预算重算，见 2.4） |

降级设计的纪律：**每条路线都要真的跑过测试**（进 2.6 的测试矩阵），否则"支持率 1% 的降级路径"就是薛定谔的代码——没跑过的分支约等于不工作。

## 2.2 精度坑

### 概念：mediump 不是"中等精度"，是"最低保证很差"

GLSL 的精度限定符（precision qualifier）规范给的下限：

| 限定符 | 规范下限 | 真实实现 |
|---|---|---|
| highp | 对应 fp32（尾数 23 位） | 桌面与移动基本都兑现 |
| mediump | 范围 ±2^14（16384）、相对精度 2^-10（约 10 位有效二进制位） | **部分移动 GPU 用真 fp16 实现（范围 ±65504、尾数 10 位）以省带宽与功耗**；桌面常直接当 fp32 处理 |
| lowp | 范围 ±2、精度 2^-8 | 移动端常见 8 位定点/半字节实现 |

问题的根源：**你在桌面写代码时 mediump 表现得和 fp32 一样**，一切正常；换到用 fp16 实现 mediump 的手机上，超出 ±16384 的量直接变 inf 或被钳制，小差异被 10 位尾数抹平——这就是"桌面好、手机坏"的经典成因之一。另外 WebGL1 里片元着色器的 highp 是**可选**的，必须检测。

### 方法：检测 + 头部策略 + 三个案例

```typescript
// 片元 highp 支持检测（WebGL1 必须；WebGL2/GLSL ES 3.00 已保证，但 mediump 仍可能是 fp16）
const fmt = gl.getShaderPrecisionFormat(gl.FRAGMENT_SHADER, gl.HIGH_FLOAT);
const fragHighp = fmt.precision > 0;   // precision 为 0 即不支持
```

```glsl
// 精度头策略：片元着色器开头
#ifdef GL_FRAGMENT_PRECISION_HIGH
precision highp float;       // 有 highp 用 highp
#else
precision mediump float;     // 没有只能退（并保证算法在 10 位尾数下仍正确）
#endif
// 顶点着色器的 highp 是保证有的，直接写 precision highp float;
```

三个真实排查案例（症状 → 根因 → 修复）：

1. **顶点抖动（vertex jitter）**。症状：中端安卓上相机一转，远处模型顶点一格一格跳动，桌面完全正常。根因：场景以"毫米"为单位（模型导出时的单位），世界坐标到几万，超出 mediump 的 ±16384，fp16 把相邻的毫米值量化到同一个数。修复：顶点着色器 position 用 highp；更彻底的是**相机相对渲染**——提交 GPU 前把世界原点锚到相机附近，数值量级降回几十。
2. **时间噪声"冻结"**。症状：用 `u_time` 驱动的水面/噪声动画，跑几分钟后在部分手机上停止变化或出现色带。根因：u_time 以秒计到几百上千，mediump 的 10 位尾数下 `frac(sin(t) * k)` 这类 hash 的小数部分已分辨不出变化（t 加 1，尾数第 10 位以后全被截掉）。修复：CPU 侧传 `t % 60`（或 `t % 3600`，视动画周期），着色器拿到的是小数值。
3. **高光条带**。症状： specular 高光在移动端拉出一条条色带，桌面细腻。根因：`viewDir = normalize(eye - worldPos)`，eye 与 worldPos 都很大而差很小——大数相减的灾难性抵消（catastrophic cancellation）在 10 位尾数下被放大，归一化方向出现阶梯。修复：varying 与关键中间量升级 highp；或同案例一改相机相对坐标，从源头把数值变小。

通用预防：**世界坐标保持小（近原点）、时间 uniform 取模、大数相减先移近再减**；对正常量级（±100 内、8 位尾数够用的颜色类计算）放心用 mediump——它在移动端更快更省电，无脑全 highp 是另一个极端的浪费。

## 2.3 DPR 与分辨率策略

### 概念：物理像素是按平方收费的

设备像素比（Device Pixel Ratio，DPR）是物理像素与 CSS 像素之比。iPhone 的 DPR 为 3：390pt 宽的逻辑屏对应 1170 物理像素。填充率成本随物理像素**平方增长**：全屏 RGBA16F（8 字节/像素）渲染目标在 1179×2556 上单张约 24MB，ping-pong 两张加 bloom mip 链合计 60MB 以上——而后处理链每一档都还要再花带宽读写。**渲染 3D 内容到 3x 与 2x 的观感差异，远小于它带来的显存与带宽代价**，所以工业界通行做法是给 DPR 封顶（cap）。

### 方法与完整代码：DPR 封顶 + 动态分辨率

```typescript
// src/renderer/resolution.ts —— DPR 封顶的画布尺寸管理
export function setupCanvas(canvas: HTMLCanvasElement, cap = 2): () => void {
  const fit = () => {
    const dpr = Math.min(window.devicePixelRatio || 1, cap);   // 封顶
    const w = Math.round(canvas.clientWidth * dpr);
    const h = Math.round(canvas.clientHeight * dpr);
    if (canvas.width !== w || canvas.height !== h) {           // 避免无变化时重置画布
      canvas.width = w;
      canvas.height = h;
      // 交给使用方：gl.viewport 与各 FBO 重建（监听返回的 resize 事件或回调）
    }
  };
  const ro = new ResizeObserver(fit);
  ro.observe(canvas);
  fit();
  return () => ro.disconnect();   // 组件卸载时反注册
}
```

DPR 封顶解决"静态预算"，动态分辨率渲染（dynamic resolution rendering）解决"负载波动"：场景渲染进一个乘以缩放系数的低分辨率 FBO，最终合成 pass 全屏放大——这正好落在 [五阶段后处理管线 2.5](../05-第五阶段/03-后处理管线.md) 的效果链架构上（在链头插一个缩放目标即可，全屏后处理仍在全分辨率）。缩放系数由实测帧时间驱动，带迟滞（hysteresis）防抖：

```typescript
// src/renderer/adaptive.ts —— 动态分辨率调度器：帧时间驱动的升降档
export class AdaptiveResolution {
  private scale = 1;
  private frames = 0;
  private accMs = 0;
  constructor(
    private readonly min = 0.5,
    private readonly max = 1,
    private readonly step = 0.1,
    private readonly downMs = 19,     // 平均帧时间超过它就降档（60fps 目标 16.6ms + 余量）
    private readonly upMs = 12,       // 明显富余才升档：升档阈值远离降档阈值 = 迟滞
    private readonly window = 45,     // 每 45 帧决策一次，不做逐帧抖动
  ) {}

  tick(frameMs: number): number {
    this.accMs += frameMs;
    if (++this.frames < this.window) return this.scale;
    const avg = this.accMs / this.frames;
    this.frames = 0;
    this.accMs = 0;
    if (avg > this.downMs && this.scale > this.min) {
      this.scale = Math.max(this.min, this.scale - this.step);
    } else if (avg < this.upMs && this.scale < this.max) {
      this.scale = Math.min(this.max, this.scale + this.step);
    }
    return this.scale;   // 使用方据此重建场景 FBO 尺寸（重建是廉价操作，见 6.3）
  }
}
```

### 苹果移动端的纹理尺寸预算

3x 屏的直觉是"贴图也要 3x"，但 3D 场景纹理多数情况 2x 已够（视角持续运动、压缩损失、FXAA/TAA 类处理都在掩盖细节差异）。预算示例：屏幕按 1179×2556 物理像素算，一张铺满屏幕的 3x 纹理等于 300 万像素；用未压缩 RGBA8 就是 12MB（含 mip 约 16MB），换成 Basis/ETC1S 压缩（[6.4](../05-第五阶段/07-性能优化与调试.md)）降到约 1.5MB。iOS 还有画布总像素上限（约 4096×4096 量级，随机型而异）与整体内存红线（2.4），纹理预算按"压缩 + 2x 封顶 + mipmap 必开"三件套设计。

## 2.4 移动端性能预算

### 方法：中端机参考预算表

预算是设计期就用的工具——场景开工前先知道盘子多大。以下为社区经验起点（面向 2019 年后中端安卓，如骁龙 7 系；60fps 目标），**上线前必须用目标机型实测校准**：

| 指标 | 参考预算 | 依据 |
|---|---|---|
| drawcall | ≤ 100~150/帧 | 移动浏览器单次调用 CPU 开销高于桌面（[6.1](../05-第五阶段/07-性能优化与调试.md) 的四层路径更慢），且移动 CPU 单核弱 |
| 三角形 | ≤ 30~50 万/帧 | 中端移动 GPU 顶点吞吐约为桌面独显 1/5~1/10 |
| 纹理内存 | ≤ 150~250MB | 含后处理 FBO；iOS 超限不是变慢，是被 jetsam 直接杀页面 |
| 全屏 pass | ≤ 3~4 个 | 移动端首要瓶颈是填充率与带宽，不是顶点 |
| 着色器复杂度 | 片元 ALU 控制在百条指令量级 | PBR 要按移动档简化（合并项、查表），照搬桌面版必超 |

预算落到实现就是 2.3 的动态分辨率 + [6.2](../05-第五阶段/07-性能优化与调试.md) 的合批决策 + [6.4](../05-第五阶段/07-性能优化与调试.md) 的压缩纹理三件事。

### 方法：发热与降频的识别

移动端性能测试最大的陷阱：**跑分式短测**。SoC 会热降频（thermal throttling）：同一场景开局 60fps、五分钟后 40fps 不是代码变了，是 SoC 降频了。识别方法：

- 连续跑 10 分钟，每分钟记录平均帧时间与 P95——曲线单调劣化即降频特征；
- 摸——设备明显发烫时的一切数字都不可作数；
- 对策：30fps 封顶（很多场景 30 稳定比 60 跳动体感好）、常驻负载低于峰值预算一档、用 2.3 的动态分辨率让降频期自动降档。

### iOS Safari 系列坑

| 坑 | 现象 | 处理 |
|---|---|---|
| video 纹理 | 黑屏或点击后视频全屏接管 | `<video>` 必须加 `playsinline muted`（否则 iOS 强制全屏、且无法作为纹理源循环更新）；自动播放策略要求静音；`crossorigin` 缺失时跨域视频上传纹理直接失败 |
| alpha 上下文 | 画布与页面合成发灰、多一层合成开销 | `getContext('webgl2', { alpha: false })`——WebGL 默认 alpha 为 true，Safari 的合成路径对透明画布处理代价更高 |
| 双缓冲行为 | 帧结束后 `toDataURL`/读回是空白 | `preserveDrawingBuffer: false`（默认）下 drawingbuffer 内容在呈现后不保证保留；读回必须在同一帧的回调里（1.1 局部症状表） |
| canvas 尺寸上限 | 大画布直接黑屏 | 总像素约 4096×4096 量级上限，随机型而异；超大视口分块或降 DPR |
| 内存红线 | 页面无征兆闪退，控制台无 OOM | jetsam 杀进程不报错；纹理与 FBO 预算保守（上表），多用压缩纹理 |

## 2.5 输入差异：触摸映射与 pointer events 统一

### 概念：一套事件收三类输入

鼠标（拖拽/滚轮）、触摸（单指/双指）、触控笔的差异，用指针事件（Pointer Events）统一收口：每个手指是一个带 `pointerId` 的独立 pointer。映射约定沿用桌面轨道相机的语义（[三阶段 2.2 OrbitCamera](../03-第三阶段/03-引擎最小核心.md)）：单指拖拽 = 旋转，双指捏合 = 缩放，双指同向平移 = 平移，滚轮 = 缩放。

### 完整代码

```typescript
// src/interaction/pointerOrbit.ts —— 触摸/鼠标统一映射到轨道相机
export interface OrbitLike {
  rotate(dx: number, dy: number): void;
  dolly(factor: number): void;      // >1 拉远，<1 拉近
  pan(dx: number, dy: number): void;
}

export class PointerOrbitAdapter {
  private pointers = new Map<number, { x: number; y: number }>();
  private lastDist = 0;
  private lastMid = { x: 0, y: 0 };

  constructor(private el: HTMLElement, private controls: OrbitLike) {
    el.style.touchAction = 'none';                       // 关键：否则单指先滚动页面而不是转相机
    el.addEventListener('pointerdown', this.onDown);
    el.addEventListener('pointermove', this.onMove);
    el.addEventListener('pointerup', this.onUp);
    el.addEventListener('pointercancel', this.onUp);
    el.addEventListener('wheel', this.onWheel, { passive: false });
  }

  private onDown = (e: PointerEvent) => {
    (e.target as HTMLElement).setPointerCapture(e.pointerId);  // 移出元素也能持续收 move
    this.pointers.set(e.pointerId, { x: e.clientX, y: e.clientY });
    this.refreshPinch();
  };

  private onMove = (e: PointerEvent) => {
    const prev = this.pointers.get(e.pointerId);
    if (!prev) return;
    const cur = { x: e.clientX, y: e.clientY };
    this.pointers.set(e.pointerId, cur);

    if (this.pointers.size === 1) {
      this.controls.rotate(cur.x - prev.x, cur.y - prev.y);
    } else if (this.pointers.size >= 2) {
      const { dist, mid } = this.pinch();
      if (this.lastDist > 0 && dist > 0) {
        this.controls.dolly(this.lastDist / dist);            // 捏合张开 dist 增大 → 因子 <1 → 拉近
        this.controls.pan(mid.x - this.lastMid.x, mid.y - this.lastMid.y);
      }
      this.lastDist = dist;
      this.lastMid = mid;
    }
  };

  private onUp = (e: PointerEvent) => {
    this.pointers.delete(e.pointerId);
    this.refreshPinch();
  };

  private pinch(): { dist: number; mid: { x: number; y: number } } {
    const [a, b] = [...this.pointers.values()];
    return {
      dist: Math.hypot(a.x - b.x, a.y - b.y),
      mid: { x: (a.x + b.x) / 2, y: (a.y + b.y) / 2 },
    };
  }
  private refreshPinch(): void {
    if (this.pointers.size >= 2) {
      const { dist, mid } = this.pinch();
      this.lastDist = dist;
      this.lastMid = mid;
    } else {
      this.lastDist = 0;   // 手指数变化时重置基线，避免跳变
    }
  }

  private onWheel = (e: WheelEvent) => {
    e.preventDefault();                                          // 阻止页面随滚轮滚动
    this.controls.dolly(Math.exp(e.deltaY * 0.001));            // 指数缩放：手感均匀
  };
}
```

两个容易漏的点：`touch-action: none` 不设则浏览器先把触摸事件拿去滚动页面，`pointercancel` 不监听则系统手势（通知中心下拉）打断后状态泄漏——地图上"卡死的一根手指"几乎都是它。

## 2.6 兼容性测试矩阵

### 方法：按维度组合，不追求全组合

全浏览器 × 全机型 × 全 GPU 是天文数字。可行的矩阵按三个维度各选代表，组合"必测 + 抽测"两档：

| 维度 | 必测 | 抽测 |
|---|---|---|
| 浏览器 | Chrome/Edge（桌面）、Safari（macOS）、iOS Safari（近两个大版本）、Android Chrome、微信内置浏览器 | Firefox、Samsung Internet |
| 机型档位 | 一台中端安卓（预算基准机，2.4 表的校准机）、一台旧 iOS（内存/精度红线机）、一台桌面核显 | 旗舰机（上限体验）、低端 2GB 安卓 |
| GPU 家族 | Adreno（骁龙）、Mali（联发克/三星）、Apple GPU（ANGLE Metal） | Intel 核显、N/A 独显 |

覆盖依据优先用**自家埋点的真实分布**（1.6 的统计上报、站点分析），没有数据时参考 webglstats.com 的扩展支持率与 caniuse。每个矩阵项跑一份标准清单：能力检测输出（2.1）、示例站全部页面、上下文丢失恢复（[1.3](01-调试与诊断.md)）、十分钟烤机（2.4 降频曲线）。

### 方法：远程调试

真机上的问题看不到 DevTools，按平台接：

- **iOS Safari 远程检查**：手机"设置 → Safari → 高级 → Web 检查器"打开，数据线连 Mac，Mac Safari"开发"菜单选设备与页面——完整的控制台/审查器/时间线；
- **Android Chrome**：手机开"开发者选项 → USB 调试"，桌面访问 `chrome://inspect`——可 inspect 该设备上所有 WebView 与 Chrome 页面；
- **微信/第三方 WebView**：装不了开发工具时用页内控制台（vconsole/eruda 脚本注入），配合 1.6 的调试基建把日志/统计落到页面上；
- **真机抓帧**：Spector 插件装不进移动浏览器，用嵌入版 `Spector.displayUI()`（[1.4](01-调试与诊断.md)），手机上打开页面直接抓。

## 常见坑

1. **按 userAgent 判机型走分支**——同一 UA 下浏览器能力不同（iOS 上所有浏览器共享 WebKit 但 WebGL 实现细节有差）；只按 2.1 的能力检测分派。
2. **能力检测做了、降级路径从没跑过**——RGBM 降级、无阴影档这些分支平时不执行，真到低端机上是死代码。降级路径进 2.6 矩阵必测清单。
3. **`getExtension` 返回 null 直接解引用**——`ext.MAX_TEXTURE_MAX_ANISOTROPY_EXT` 在 ext 为 null 时抛 TypeError；检测代码自身要先判空。
4. **全场景无脑 highp**——精度坑的反面：颜色类计算用 mediump 在移动端更省带宽功耗；按数据量级选精度，不是"高就是好"。
5. **DPR 不封顶**——3x 全屏浮点目标链上百 MB，中端机直接崩；cap 2 是默认纪律，2.3 有预算算式。
6. **动态分辨率逐帧调档**——帧时间噪声让分辨率抖动，画面呼吸感；必须窗口平均 + 迟滞阈值。
7. **移动端性能用桌面开发机评估**——差一个数量级；中端基准机是团队标配，烤机测试见 2.4。
8. **`touch-action` 忘设**——单指旋转变成页面滚动，双指捏合触发浏览器缩放；canvas 上必须 `touch-action: none`。
9. **只监听 pointerup 不监听 pointercancel**——系统手势打断后 pointers Map 残留"幽灵手指"，交互永久错乱。
10. **iOS 测试只测新款**——旧机型的内存红线（jetsam 闪退）和精度上限最先把问题暴露出来；矩阵里留一台旧 iPhone。
